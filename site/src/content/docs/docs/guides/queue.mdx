The queue has a window of its own: click **`More ▴`** at the bottom of the sidebar (the gear in the icon bar), then **`queue`**, or press `e` in the [keys menu](../../reference/keyboard-and-mouse/#the-prefix-key). It opens with or without a project open. While entries [wait for room](#wait-for-room), a yellow **`queue 3`** button between **`More ▴`** and **`Help`** opens it too. It lists the scheduled agents of every project (a [bot's](../bots/#a-bots-routines) routines are in the bot, and a dim line after the last row says how many there are), each with its time, its name, and its state, agent and place. A failed entry is red, a missed one yellow and a started one green, unless its agent never took the prompt: then it reads `started · pane N · prompt not taken` in yellow. Entries that [wait for room](#wait-for-room) come first, in their turn, then upcoming entries, by the time they start (routines that are not paused and one-off entries not started yet), then paused routines, then the one-off entries that already ran, newest first. A routine's runs are listed right under it (see [Routines](#routines)). Typing filters the list, by time, name, state and the first line of the prompt.

## Schedule an issue or a prompt

In [Issues](../issues-and-agents/), click **`schedule`** beside **`start`**. Choose the agent and destination as usual, then enter the time. Once saved, the Queue window opens with the new entry selected; `Esc` or **`cancel`** goes back to the issue instead. GitHub, GitLab, Shortcut, Linear, Jira, Plane and Asana issues use your configured [prompt template](../../reference/prompt/).

For a free prompt, click **`new`** in the Queue window and type the prompt: `Enter` starts a new line there, the field is taller when the window has room (3 rows in a 24-row terminal, up to 8 in a taller one), the mouse wheel scrolls it, and `↑ 3 more` and `↓ 2 more` say how many lines are out of sight. Then choose **When**, **Where**, the **Agent** and its **Mode**: each is a list that opens below it on a click, or with `Space`, `↑` or `↓` when it has the keys. Pick an option with a click or the arrows and `Enter`; typing filters a long list, such as the places. **Mode** opens on the mode chosen for that agent in **settings → Agents**; **default** starts it with no mode arguments. In a repository root, **Open in** chooses a **new tab** or a **new worktree**, and a new worktree asks for its branch beside it. A workspace always gets a new tab. An issue already supplies its usual branch name. Once you have [accounts](../accounts/), an **Account** list beside the agent chooses the account it starts with (the default until you pick another); the entry keeps it, whatever the default is when it runs, and fails and says why if that account was removed meanwhile.

<Screen name="queue-form" alt="The schedule form with the prompt, When set to in 2 hours, Where, Open in a new worktree with its branch, Agent and Mode" caption="Choose a kind of time first, then its values." />

**Where** lists the open projects and their workspaces, and no bots: to schedule for a [bot](../bots/#a-bots-routines) use **` + routine `** in its routines, and editing a bot's entry from there shows the bot in **Where** as fixed grey text. With a bot's place the form hides Open in, Mode, Account and the cleanup box, the Agent row reads `set by the bot`, and each run is a new conversation of the bot, which answers in its chat; all the kinds of time work, and a one-off entry is a reminder.

**When** asks the kind of time first, then shows only the values it needs on the row below:

| When | Values | It starts |
| --- | --- | --- |
| `at` | a clock, `14:30` | The next 14:30, today or tomorrow. |
| `tomorrow at` | a clock | Tomorrow at that time. |
| `on` | a date, `2026-10-20`, and a clock | That date at that time. |
| `in` | a number and minutes, hours, days or weeks | After that delay. |
| `every` | a number and minutes, hours, days or weeks | A [routine](#routines): repeats on that interval. |
| `every day at`, `every weekday at` | a clock | A routine: every day, or Monday to Friday, at that time. |
| `every week on` | a day and a clock | A routine: that day of every week, at that time. |
| `Claude reset`, `Codex reset` | none | At the next reset of that agent's five-hour plan window. |
| `when there is room` | none | As soon as this computer or one of your [machines](../machines/) has the memory it needs, in turn: see [Wait for room](#wait-for-room). |

The commands take the same times as text: `14:30`, `tomorrow 9:00`, `2026-10-20 09:00`, `in 30m`, `in 2h`, `in 1w`, `claude reset` and `codex reset`. A routine takes `--every` instead (see below), and an entry that waits for room `--when free`.

Clock times use the zone shown in the form, supplied by the client that opened it, including a remote terminal or browser. Dates use that zone's daylight saving rules. A local time that does not exist or occurs twice is rejected; choose another time or a delay. A time such as `02:30` that has already passed today means tomorrow, even on the day the clocks change. The entry is saved as an absolute UTC instant.

A reset choice runs the existing plan usage probe on the server when you save. It freezes the returned reset time; it does not keep polling or follow later changes to the window. If the probe fails or reports no future five-hour reset, the form shows the reason and keeps your text.

Click **`schedule`** to save, or press `Enter` in any field but the prompt (in the prompt, `Enter` starts a new line, as the hint above it says; press `Tab` to leave it first). `Esc` or **`cancel`** closes the form (with a list open, `Enter` picks and `Esc` closes only the list). Click a text field to edit it, use the arrow keys (`Ctrl+←` `Ctrl+→` or `Option+←` `Option+→` move by word; `Shift` selects, and the mouse does too, with a right-click menu to copy or cut), `Home`, `End`, `Backspace` and `Delete`, or paste text. `Tab` and `Shift+Tab` move between the fields and lists. The prompt keeps the line breaks of a paste, a template or `--prompt`; a text pasted in another field goes in as one line.

**Queued launches always accept the agent's folder trust question**, even with `accept_trust_prompts` off. This lets unattended starts proceed. The form states this before saving. Immediate starts keep your global trust setting. Agent approval modes remain the ones you selected. Queued launches submit their stored prompt automatically, even when automatic submission for immediate issue starts is off.

## When entries run

The server starts every due entry, with no concurrency limit. Entries at the same instant start in insertion order. Each uses the normal worktree, tab and agent launch path and leaves the active pane selected. A toast and desktop notification announce success or failure. Claude Code gets its prompt once its input is ready, and cornercase presses `Enter` again while it sits idle with the prompt unsent. If the agent still never takes it, the notice says `started, but its agent did not take the prompt` instead, and the entry keeps the `prompt not taken` mark until the agent works.

The server must be running, with its session opened at least once after a restart, by a window or by `cornercase start-server`. Closing the UI leaves scheduled work running. The queue does not wake a sleeping machine or start a stopped server.

An entry more than ten minutes late becomes **`missed`** and waits for you. Waking or restarting within ten minutes still starts it. Select an entry to act on it: **`start now`** starts a pending, missed or failed one at once, and **`remove`** removes it; the notice that follows has **`undo`** for six seconds. Click a pending, missed or failed row, or press `Enter` on it, to edit and reschedule it. An entry shows `starting` while its worktree or agent is being prepared; it cannot be cancelled or edited then.

Started entries stay until **`clear started`** or **`remove`** removes them, both undoable from their notice (the window's button leaves a bot's runs alone; the `clear-started` command still clears every one). Click one to close the window and jump to its pane while it is still open in that server. Once its pane is gone, or after a restart, a click or `Enter` opens [what its agent did](#what-each-run-did) instead; it cannot point to a different pane with the same id. Removing a started entry does not stop its agent.

The agent command, mode, prompt and destination are captured when scheduled. Editing the prompt or time keeps that agent and mode, even if their settings changed or a custom agent was removed; choosing another agent or mode captures its current command. A closed project or workspace, a workspace that cannot be uniquely identified after restart, or a missing executable fails with a reason. If the server stops partway through starting, the entry asks you to check its workspace before retrying.

## Wait for room

Choose **when there is room** as the kind of time (or `--when free`) and the entry has no time: it waits in line until a computer has the free memory it needs, then starts there. It suits work you want done as soon as possible without overloading one computer, such as a batch of issues for several machines.

- **Where it can start**: this computer, or any [machine](../machines/) that is linked and has a clone of the project (found by its repository), the one with the most [free memory](../machines/#free-memory), this computer on a tie. `--machine torre` waits for that machine only. The form always counts every computer.
- **What it needs**: its flow's [`memory`](../flows/#the-memory-a-run-needs), else **a start needs** in [Settings › Machines](../machines/#free-memory) (`4GB` by default). Once it starts, that memory counts as taken on that computer for 5 minutes, while the run grows, so the next entry goes elsewhere or waits.
- **In turn**: the entries start in the order they were added, one after the other. When the first one fits nowhere, the ones behind it wait too, even if they would fit, so nothing jumps the line. **`first`** (on an entry behind the first, in the Queue window, or `queue first ID`) puts it at the head. **`start now`** starts a waiting entry at once on the computer with the most free memory, without counting what it needs.
- **When it is tried**: while entries wait, cornercase reads the machines' memory every 30 seconds and tries the line again, and again whenever a reading comes in. The server must be running, as for any entry.
- **A flow**: on this kind the **Agent** list offers the flows too, as `Name (flow)`, as a routine's does (`--flow` on the command line); the prompt is the orchestrator's task.

In the Queue window, the waiting entries come first, each with its turn where the time would be (`#1 in line`), and with how long it has waited and why: `waits 12m · needs 6 GB · best: torre 4.1 GB`, or `waits 3m · behind queued agent 7` for one behind the first. Until it is first tried it reads `waits for room`.

A notice says when an entry starts to wait (`queued agent 7 waits for room: 1st in line, needs 6 GB · best: torre 4.1 GB`, or `…: 2nd in line, behind queued agent 7`), once, and when it starts, where: `started queued agent 7 on torre`, or `on this computer`. Like the queue's other notices, both are a toast, a desktop notification and, while you are [away](../telegram/), a message on Telegram and Discord.

**An entry that started on a machine** belongs to that machine: its tab is in your sidebar under the machine, and its row reads `started on torre · working`, with its agent's status there, `started on torre · paused while torre is unreachable` while the machine is down (followed again once it is back), or `started on torre · tab closed`. A click or `Enter` shows its tab, as a click on it in the sidebar does. cornercase looks for its pull request by its branch, with `gh` on this computer, every 2 minutes for a day, and says when it opens: `queued agent 7's pull request opened: #123 Fix the login`.

An entry that waits for room can't be given a time, and one with a time can't start waiting: add a new entry instead. A [bot](../bots/#a-bots-routines) can't wait for room, since it runs in its own folder.

## What each run did

Every queued agent, and every run of a routine, keeps a **result**: what its agent last said, the branch and the pull request with its state and checks as they were then. cornercase keeps it each time the agent ends a turn (not only when you have not looked at the tab), when its pane closes, and right before a routine [removes the run's workspace](#remove-the-workspace-when-it-finishes), so the run that ended as `removed` still says what it did. A run of a flow keeps what its orchestrator said. The text is at most 4 KiB, cut at that size with a note, and lives in the entry in `queue.json`; the agent's own record of the conversation is read when you ask for it.

To make that last message worth keeping, **every queued prompt ends with one more sentence**, after a blank line:

> When you finish, end your last message with a short summary of what you did and what is left to do.

The sentence is added when the prompt is sent. It is not saved in the entry, shown in the Flow panel or counted as part of the task, but it is in the agent's conversation, so you see it there.

Click or press `Enter` on a started entry whose pane is gone, on a `removed` run and on a failed or missed **run** of a routine to open its **Result**: when it started and when the result was kept, its agent, branch and pull request, and the last message, wrapped. A failed or missed one-off entry still opens its form, and one whose pane is still open still jumps to it. The hint under the list says which. In the dialog:

- **`conversation`** loads the whole conversation, prompts and replies without tool calls, for as long as the agent keeps it (the newest 1,000 messages, each cut at 32 KiB); **`result`** goes back. It only shows when the record can still be read.
- **`copy`** copies what is shown. The wheel and `↑` `↓` scroll.
- **`done`**, `Esc` or a click outside go back to the Queue window with the list as it was, as the schedule form does.

What is missing says why: an agent without a record cornercase can read (a custom command) keeps only the branch and the pull request, a run whose agent never finished a turn while cornercase watched it has no result, one whose agent never took the prompt says so (press `Enter` in its tab if the prompt is still in the input box), and a failed run shows the reason it did not start. cornercase does not notify you when a result is kept, and it watches only the entries the running server started: nothing is kept while the server is stopped, and an entry from before a restart keeps what it had.

## Routines

A **routine** is a queue entry that repeats. Choose **`every`**, **`every day at`**, **`every weekday at`** or **`every week on`** as the kind of time (or `--every` on the command line), and each time the routine fires it starts its agent, or a [flow](../flows/) (choose it in the **Agent** list as `Name (flow)`, or `--flow`; the prompt is the orchestrator's task), in **a new workspace of its own**.

<Screen name="queue-routine" alt="The schedule form with When set to every day at 09:00, Where limited to repository roots, Open in a new worktree in grey, and the checkbox to remove the workspace when it finishes" caption="A routine: each run gets a new worktree, and the checkbox removes it when the run finishes." />

| Repeat | Text | Meaning |
| --- | --- | --- |
| `every 30m`, `every 2h` | `30m`, `2h` | A fixed time apart, however the clocks change. |
| `every 3d`, `every 2w` | `3d`, `2w` | Every 3 days or 2 weeks, at the clock time you added it; the first run is 3 days or 2 weeks from today. |
| `every day at 09:00` | `'day 09:00'` | Every day at that local time. |
| `every weekday at 09:00` | `'weekday 09:00'` | Monday to Friday. |
| `every week on monday at 09:00` | `'monday 09:00'` | That day of every week. |

- **At least 30 minutes apart, and at most a year**, since each run starts an agent; the form and the commands refuse anything else and say why.
- Occurrences are counted from the schedule, not from when the last run ended, so they never drift. Days and weeks follow the local clock of the zone shown in the form, so `every day at 09:00` stays at 09:00 across daylight saving changes. Unlike a one-off entry, a local time that does not exist or occurs twice does not fail: it shifts as Jiff's `Compatible` rule does (a 02:30 that does not exist runs at 03:30 that day, and at 02:30 again the next).
- **Each run makes its own workspace.** cornercase fetches the project's remote (`origin`, else its first remote) and makes a new worktree from the remote's default branch, on `routine/<name>-<date>-<time>`, then the project's [setup script](../worktrees/) runs as in any worktree. If the fetch fails (offline, authentication), the run **fails and says why**: it never starts from stale code without telling you. A project without a remote uses its local `main` or `master`. Only git repositories can have routines: a plain folder is refused when you add it. The form's **Where** lists only repository roots, and **Open in** says `new worktree` in grey.
- **A run always starts**, even while the previous one is still working or waiting. Nothing is skipped and nothing is stopped; an interval shorter than the work is yours to fix.
- **The server must be running.** A routine only fires while cornercase's server is up, as for any queued entry: nothing wakes a sleeping machine or starts a stopped server. If the server was down for several occurrences, one **`missed`** run records the gap and the routine goes on with the next occurrence after now; there is no catch-up. A run less than ten minutes late still starts.
- The row of a routine shows its next time (or `paused`), its name and `↻ every day 09:00 · agent · project`. Its **last 10 runs** are listed right under it, indented and newest first, each with its time, its state (`started` with a link to the pane, or `started` with `prompt not taken`, `failed`, `missed`, `removed` or `kept`) and its agent and place. A routine with runs shows `▾`: click it, or press `←` on the routine or one of its runs, to fold them (`▸`, and the row ends with ` · 3 runs`), and click it again or press `→` to unfold them. Folds last until the server stops, for every window; typing a filter shows every match, folded or not. Older runs drop out of the list, and dropping a run never stops its agent or removes its workspace. **`pause`** and **`resume`** stop and restart it (resuming picks the next occurrence after now, with no catch-up), **`start now`** runs it once more right away without moving its schedule, a click or `Enter` edits it (the runs to come, not the ones already going), and **`remove`** removes the routine and its runs, with **`undo`**. **`clear started`** clears finished runs, never a routine.
- Each run uses the accounts chosen on the routine (`--account`), checked when it runs: an account removed meanwhile fails that run with the reason. A run starting, failing, missed or kept appears in a toast and a desktop notification, and in Telegram and Discord while you are [away](../telegram/).

### Remove the workspace when it finishes

The checkbox **`remove the workspace when it finishes`** (`--cleanup`, off by default) removes a run's workspace and the branch the routine made once the run is finished:

- **Finished** means the agent's status is `done` and stays `done` for 3 minutes, so a turn that ends while subagents or background work are still running is not cut short. If the agent works again during those 3 minutes, the count starts over. An agent that is `waiting`, has failed or is waiting for review is never removed, and **looking at a run's tab keeps its workspace** (the status then becomes `idle`): the routine leaves it to you. For a flow, finished is the run's end, followed by the same 3 minutes.
- **Only when nothing would be lost.** First comes the same check as the [Worktrees dialog](../worktrees/): nothing uncommitted, nothing unpushed and no lock, in the run's worktree and in every role's. If anything is there, the workspace stays, the run shows `kept · 2 uncommitted, 1 unpushed`, and a toast and notification say `routine <name> left changes in <workspace>`. Otherwise it is removed as in the Worktrees dialog (its teardown run, its shells stopped, the worktree and its folder; a program started outside the panes keeps running, and so does its port), the run shows `removed`, and the local branch is deleted if it holds nothing unpushed.
- The conversation goes with the workspace, since removing it forgets its closed agents: that is what ticking the box asks for.
- An agent cornercase cannot read the status of (a custom command) cannot have the checkbox: it is greyed out with the reason. `cornercase config --json` says which, as `reads_status` in [`agents`](../scripts-and-agents/#settings).
- The 3 minutes are counted in memory, by the server that started the run: removing the run from the list, closing its workspace or restarting the server (an update included) cancels the count and the workspace stays. A run that is still counting is not dropped from the last 10.

## Commands

```sh
cornercase queue add --at 'in 2h' --agent claude --prompt 'Fix the login form'
cornercase queue add --at 'tomorrow 9:00' --agent codex --worktree fix-login --prompt 'Fix the login form'
cornercase queue add --at 'claude reset' --agent claude --issue https://github.com/acme/shop/issues/482
cornercase queue add --at 14:30 --agent codex --source linear --issue ENG-123 --workspace 12
cornercase queue add --at 14:30 --agent codex --source asana --issue 1205551234567890 --workspace 12
cornercase queue list
cornercase queue list --json
cornercase queue edit 1 --at 'in 3h' --prompt 'Fix logout too'
cornercase queue edit 1 --name 'Login follow-up'
cornercase queue run 1
cornercase queue remove 1
cornercase queue remove 2 --json
cornercase queue clear-started
cornercase queue clear-started --json
cornercase queue restore 7
cornercase queue show 7
cornercase queue show 7 --json
cornercase queue show 7 --conversation
cornercase queue add --every 2h --agent claude --prompt 'Check the CI of main'
cornercase queue add --every 'day 09:00' --agent claude --cleanup --prompt 'Review the open pull requests'
cornercase queue add --every 'weekday 09:00' --agent codex --prompt 'Triage the new issues'
cornercase queue add --every 'monday 09:00' --flow Quick --prompt 'Update the dependencies'
cornercase queue add --when free --agent claude --issue '#482'
cornercase queue add --when free --machine torre --flow Review --prompt 'Review the login form' --project 2
cornercase queue first 9
cornercase queue add --bot prs --every 'weekday 09:00' --prompt 'Review my pull requests' --name 'Review PRs'
cornercase queue add --bot prs --at 'tomorrow 9:00' --prompt 'Check whether #482 merged'
cornercase queue list --bot prs
cornercase queue pause 3
cornercase queue resume 3
cornercase queue run 3
```

`add` prints the entry's persistent id. `--bot` (a bot's id or name) schedules a [bot's own work](../bots/#routines) instead of an agent in a project, and does not mix with `--project`, `--workspace`, `--worktree`, `--issue`, `--source`, `--flow`, `--cleanup`, `--agent`, `--mode`, `--account` or `--fresh` (the bot has its own agent and account): that is wrong usage, exit 2. Inside a bot (`CORNERCASE_BOT` set), a `queue add` with none of `--project`, `--workspace` or `--worktree` means that bot. `queue list --bot prs` lists only that bot's entries (the text list shows `bot prs` where an agent's name would be), and `edit`, `pause`, `resume`, `remove`, `run`, `restore` and `clear-started` work on them as on any entry; an edit cannot move an entry between a bot and a project. A bot's run ends in the state **`answered`**, not `started`: its answer is in the bot's chat, and a click on its routine in [the bot's routines](../bots/#a-bots-routines) shows the chat at that run. Its place reads `bot prs`. `--fresh` and `--no-fresh` choose, for a one-off entry that makes a worktree, whether a branch that does not exist yet starts from the up-to-date default branch, fetched when the entry runs, or from the project's `HEAD`; without either, the setting **new branches** decides at that time (see [`fresh_branches`](../../reference/configuration/#fresh_branches)). `--every` makes a [routine](#routines) and does not mix with `--at`, `--issue`, `--workspace` or `--worktree`; `--project` names its repository, `--cleanup` (or `--no-cleanup`) belongs to routines, and `--flow` to routines and to entries that wait for room. `--when free` makes an entry that [waits for room](#wait-for-room) and does not mix with `--at`, `--every` or `--bot`; `--machine NAME` (only with it) waits for that machine, and `auto`, the default, for this computer or any linked machine with the project. `queue first ID` puts an entry that waits for room at the head of the line. `pause` and `resume` take a routine's id, and `run` on a routine starts one more run and prints its id. `queue list` adds ` · ↻ every day 09:00` to a routine and ` · routine 3` to its runs, and gives an entry that waits for room its turn and why where the state goes, and ` · on auto` (or the machine) after it: `3 since 2026-11-25 10:00 waits #1 · needs 6 GB · best: torre 4.1 GB fix · claude · on auto`; one that started on a machine reads `started on torre`. `--workspace` selects an open workspace; `--project` selects an open project root; `--worktree` selects or creates a branch in that project. Without a destination, a prompt uses the current workspace and an issue uses its usual worktree when the project is a repository root. Use `--source` for ambiguous keys and self-hosted tracker URLs.

An issue URL must belong to the project: GitHub and GitLab issues are read from the project's own repository, and Jira, Plane, Linear, Shortcut and Asana ones from the site or workspace you are connected to, so a URL of another repository or site is refused instead of starting the wrong issue. An Asana link works in its old (`/0/<project>/<task>`) and new (`/1/<workspace>/project/<project>/task/<task>`) forms and must name a task of the account you are connected to. A bare key goes to the only tracker that can read it: `#7` to the project's GitHub or GitLab, `sc-482` to Shortcut, a number to the repository or Shortcut, and keys such as `ENG-7` to Linear, Jira, Plane or Asana. A bare number is never taken for Asana: use `--source asana` to read a task by its id. When two trackers could read it, add `--source`. `--mode` names one of the agent's modes, or `default` for no mode arguments (without it, `add` takes the mode chosen in **settings → Agents** and `edit` keeps the entry's; before sending `default` the command checks the server's `mode-default` [feature](../scripts-and-agents/#ask-the-server-first), since an older server would read it as the mode chosen in settings), `--account AGENT=ACCOUNT` the [account](../accounts/) that agent starts with (`AGENT=` for its own login; without it, the default when it runs; `edit` changes only the agents it names, and cannot set one back to the default when it runs: remove the entry and add it again), and `--name` sets the entry and tab name. Without `--name`, an entry is named after its prompt: its first line with text, cut after a whole word at 40 characters with `…` (an issue's entry is named after the issue, `#482` and its title); the whole prompt stays in the entry (`queue list --json`). `edit` can omit `--at` to keep the exact scheduled instant; `add` needs `--at` (or `--every`, or `--when free`) and either `--prompt` or `--issue`. Editing an entry's `--issue` moves it to the new issue's branch, unless you also pass `--worktree`. `add`, `edit`, `list`, `remove` and `clear-started` support `--json`.

`show 7` prints what an entry's agent did: its state, when it started, the branch, the pull request and the last message. `--conversation` adds the whole conversation, oldest first, and exits **3** (after printing the result) when it cannot be read because the agent no longer has its record; `--json` prints the answer, whose `result.conversation` says whether it can be read. `queue list --json` gives each entry that started its `started` time and, once it kept a result, `result_at`, never the text. `show` checks the server's `queue-results` [feature](../scripts-and-agents/#ask-the-server-first) first.

`remove` and `clear-started` print an **undo number**, which is separate from the entry id. `clear-started` removes every started entry, and every finished run of a routine, at once and leaves pending, starting, failed and missed one-off entries and routines alone; removing history does not stop its agents. With `--json`, both answer `{"entries": [...], "undo": 7}` with the complete removed entries. When nothing started, `clear-started` prints nothing, or `{"entries": []}` with `--json`, without using an undo number.

`restore 7` puts that removal back with its original ids, captured prompt, agent, mode, destination, accounts and state, in time and insertion order. Restored pending entries follow the usual scheduling and lateness rules; restoring started history does not start agents again. The server keeps the last 16 nonempty command removals until it stops, independently of the window's six-second undo notice. Undo numbers are opaque and change with the server boot. An undo number works once; an unknown, used or expired number fails. The commands check the server's `queue-undo` [feature](../scripts-and-agents/#ask-the-server-first) before removing or restoring anything.

## Storage

`queue.json` lives next to `session.json`, with its own format version (2 only while it holds a routine, its runs or a `removed` or `kept` state, 3 while it holds a bot's entry or an `answered` state, and 4 while it holds an entry that waits for room or started on a machine, or a one-off entry with a flow, so an older cornercase finds a version it refuses instead of starting a routine once as a plain entry). For a custom socket whose session is `server.json`, the queue is `server.queue.json`, keeping different servers in the same folder separate. Its entry ids survive restarts and are not reused when an entry is removed. An entry that started also keeps its start time and its result (about 4 KB), which an older cornercase ignores and drops the next time it saves. The server saves changes after they settle and flushes the queue on shutdown. A missing, corrupt or unsupported-version file starts an empty queue. An unreadable file is kept unchanged until you change the queue.

The queue is independent of the [TODO list](../todo/). One-off entries run once; a [routine](#routines) repeats.
