Besides opening the window, the `cornercase` command drives the server that is already running. A script can open a tab and run the tests in it, a git hook can leave a note, and a coding agent in one tab can start others in their own worktrees, wait until they finish or need an answer, read what they wrote and send them the next step, or follow all of them at once as things happen.

```sh
pane=$(cornercase new-tab --name tests -- cargo test)
cornercase wait --pane "$pane" --until shell --timeout 900
cornercase read --pane "$pane" --lines 40
```

These commands never start a server, except [`start-server`](#start-without-a-window). Without one, they say `no cornercase server is running` and exit with status 1.

## Start without a window

A server waits for its first window before it restores your session, and until then commands that open terminals refuse. A script, a cron job or another UI that never opens a window starts the server with `start-server` first:

```sh
cornercase start-server
pane=$(cornercase start claude --prompt "fix the failing test" --worktree fix/test)
```

It starts the server if none runs, restores the saved session once (or opens the folder you ran it from), and returns once its terminals exist; run again, it does nothing and says the server is already running. Until a window attaches, terminals are 160×48, or `--cols` and `--rows`. A window that attaches later finds the same tabs, with the same ids, takes over the size and gives the terminals its colours, unless you [gave them](#colours-for-programs) with `--theme FILE`. See [Command line](../../reference/command-line/#cornercase-start-server) for its output.

## On another machine

`--remote DESTINATION`, or `CORNERCASE_REMOTE=DESTINATION`, sends any of these commands to the server of another machine through your own `ssh`, as [`cornercase remote`](../remote/) attaches the window:

```sh
cornercase --remote devbox status --json
cornercase --remote devbox events --notices --host --json
```

Arguments and standard input arrive as they are, a stream ends there when the command ends here, and only `start-server` starts a server. See [Commands for scripts and agents](../remote/#commands-for-scripts-and-agents) for what it needs and which commands refuse it. When that machine's cornercase is older than yours, every command that sends a request refuses with [status 5](#exit-status) (`update`, `restart`, `kill-server`, `logs` and the plugin commands that work on its files run there without checking) and says how to update it from here; with `--json` it also prints that as JSON.

## Ids and where commands act

`cornercase status` lists every project, workspace, tab and pane with its id:

```text
project 1  web-shop  ~/code/web-shop  (shown)
  workspace 2  main  ~/code/web-shop  branch main  (shown)
    tab 3  claude  working  (shown)
      pane 4  claude  working  Opus 5.5 · 23%  ~/code/web-shop  (shown)
    tab 6  zsh
      pane 5  zsh  ~/code/web-shop  (you)
    tab 14  claude  working
      pane 13  claude  working  Opus 5.5 · 4%  ~/code/web-shop  (parent 5)
  workspace 7  fix/login  ~/.cornercase/worktrees/web-shop/fix-login  branch fix/login  worktree
group 9  personal  collapsed
  project 10  blog  ~/code/blog
```

- Ids come from one counter and last as long as the server runs: after a restart, the same tabs get new ids. Take them from `status`, or from what a command printed. `close`, `rename`, `mark`, `move-pane`, `collapse`, `expand`, `account restart` and `context` can say which run an id is from, with [`--boot`](#arrange).
- Every pane's shell has `CORNERCASE_PANE` set to its id. Inside a pane, commands act on that pane, its tab, workspace and project unless you name another one; `(you)` marks it in `status`. Run from anywhere else, they act on what the window shows, marked `(shown)`.
- A pane opened by `start`, `new-tab`, `split` or `setup` run inside another pane remembers that pane as its parent, marked `(parent 5)` in `status` (and `(collapsed)` while the agent in it has its children collapsed in the agents section): an agent that starts others finds them as its children, and the [agents section](../projects-workspaces-tabs/#the-agents-section) lists them under it. A flow's members have its orchestrator as parent, and `(role coder)` in `status` says which role each plays. Run from anywhere else, the new pane has none. The mark goes once the parent pane closes or the agent that ran the command is no longer there; for a pane started from a plain shell, it holds while no agent runs in that shell, and until the server restarts. A flow's members keep their orchestrator's pane.
- Where a command takes `--workspace ID`, `--worktree BRANCH` names the workspace on that branch instead, looked up in the same project: the one the command runs in, else the shown one. `cornercase start claude --worktree fix/login` made it, so `cornercase close --worktree fix/login --remove-worktree` can take it down without reading its id from `status`. A branch that no workspace there is on, or that several are on (a workspace without a worktree of its own shares its project's branch), exits with status 2 and lists the workspaces to pick from.
- The pane is what `send`, `keys`, `read` and `wait` work on. Where they take `--tab ID`, it stands for the tab's agent pane, or its active pane when no agent runs in it.
- **Nothing changes what the window shows** except `focus`, `go` and the `--focus` option. Whoever is looking at the window keeps seeing what they were looking at while a script opens tabs next to them. With `--view ID` they move that [view](#a-view-of-your-own) instead, and the window stays where it is.
- With `--view ID`, the defaults are what that view shows: its project, workspace, tab and that tab's active pane, even inside a pane.

### Look

```sh
cornercase status                  # the tree above
cornercase status --json           # the same, as JSON
cornercase status --panes          # one line per pane, for scripts
cornercase status --panes --json   # the same, as JSON
cornercase status --follow         # the whole state as JSON, again after each change
cornercase status --app            # the TODO list, queue, away, update and keep awake as JSON
cornercase status --app --follow   # the same, again after each change
```

Each pane shows its program and folder. Recognised agents that emit [OSC 7501](../../reference/agents/#program-status-protocol) show their reported status, including when no session reader exists. A pane running Claude Code, Codex, Gemini CLI, opencode, Grok Build, Cursor CLI, Vibe CLI or GitHub Copilot CLI also shows what the agent is doing (`working`, `waiting` for an answer, `pending` review, `done` while you were elsewhere, `failed`, `idle`; without OSC 7501, opencode is never `waiting`), its model and how full its context is, as the [tab icons](../projects-workspaces-tabs/#what-your-agents-are-doing) do. `working (background shell)` is a Claude Code agent whose turn is over while a shell it started in the background (a test watcher, a dev server) still runs: its tab keeps showing it as working, since Claude wakes up when that shell ends, but a script can tell it apart and stop waiting with [`--until turn-over`](#wait). `working (2 subagents)` is an agent whose own turn is over while subagents it started (Claude Code, GitHub Copilot CLI) still run: it goes on when they report back, so it stays working, and the default, `--until idle` and `--until turn-over` [waits](#wait) keep waiting for them. `(dialog open)` is a Claude Code agent showing something else where its input box should be (a picker, the transcript view, a background shell's details, its `!` shell mode), which [`send`](#talk-to-a-pane) refuses. `(survey open)` is Claude Code's feedback survey above its input box, which `send` refuses too. `Opus 5.5 · compacted` is an agent whose conversation was just compacted: its context is empty until its next reply, which brings it back (`compacted` in the JSON). A workspace shows its branch, `worktree` when it has one of its own, the commits it is behind, and its [pull request](../worktrees/#pull-requests-and-their-checks) with the state of its checks, such as `pull request #485 open, checks failing`, or `pull request #486 open, conflicts with main, checks passing` when it has merge conflicts. A pull request in a GitHub stack adds its layer, `pull request #483 open, checks pending, layer 2 of 2 of stack #484 on main`. On GitLab it reads `merge request !486 open, conflicts with main, pipeline passing`.

#### One line per pane

A script that coordinates agents mostly needs the panes: which agent runs where, what it is doing, in which worktree. `status --panes` lists them flat, so nothing has to walk the tree: one line per pane, in the order of the sidebar, under a header line that names the columns, separated by tabs.

```text
pane	tab	workspace	project	program	agent	status	background_shell	dialog	at_prompt	model	context	caller	shown	active	tab_name	workspace_name	branch	worktree	project_name	path	survey	resuming	parent	subagents	role	held_sends	draft	account_restart	pid	memory	compacted
4	3	2	1	claude	claude	working	false	false	false	Opus 5.5	23	false	true	true	claude	main	main	false	web-shop	/home/ana/code/web-shop	false	false	-	2	-	1	true	-	48213	-	false
5	6	2	1	zsh	-	-	false	false	true	-	-	true	false	true	zsh	main	main	false	web-shop	/home/ana/code/web-shop	false	false	-	0	-	0	false	-	48190	-	false
12	11	7	1	codex	codex	waiting	false	false	false	gpt-5.4	41	false	false	true	codex	fix/login	fix/login	true	web-shop	/home/ana/.cornercase/worktrees/web-shop/fix-login	false	false	5	0	-	0	false	-	51377	-	false
```

| Column | What it holds |
| --- | --- |
| `pane`, `tab`, `workspace`, `project` | The ids of the pane and of the tab, workspace and project it is in. |
| `program` | The program in the foreground, as the tab names it. |
| `agent` | `claude`, `codex`, `gemini` or `opencode` when one runs in the pane. |
| `status` | What the agent is doing: `working`, `waiting`, `pending`, `done`, `failed` or `idle`. |
| `background_shell`, `dialog`, `at_prompt` | As in the [JSON](#json): the agent's turn is over but a background shell still runs; a Claude Code agent shows a dialog instead of its input box; the shell sits at its prompt with nothing running. |
| `model`, `context` | The agent's model and how full its context is, in percent. |
| `caller` | `true` for the pane running the command. |
| `shown` | `true` for the pane the window shows. |
| `active` | `true` for its tab's active pane. |
| `tab_name`, `workspace_name`, `branch`, `worktree`, `project_name` | The tab's and workspace's names, the workspace's branch and whether it has a worktree of its own, and the project's name. |
| `path` | The folder of the program in the foreground, in full. |
| `survey` | As in the [JSON](#json): a Claude Code agent shows its feedback survey above its input box, which `send` refuses until `keys --pane … 0` dismisses it. |
| `resuming` | As in the [JSON](#json): the pane's agent is coming back in its conversation after a restart, and takes no input until it is back. |
| `parent` | The id of the pane this one was started from, while that pane is open and still runs what started it (an agent, or a shell running no agent): `start`, `new-tab`, `split` or `setup` run inside it. A flow's members have their orchestrator's pane, whatever runs there. |
| `subagents` | How many subagents the pane's agent started that still run (Claude Code, GitHub Copilot CLI), `0` otherwise. While it is above 0, subagents keep an otherwise idle (or background-shell) agent's `status` at `working`, even when its own turn is over; a question (`waiting`) and an OSC 7501 report still take precedence, so scripts must still handle the reported `status`. |
| `role` | The role the pane plays in a [flow](../flows/) run (`orchestrator`, `coder`…) while the run lives, `-` otherwise. |
| `held_sends`, `draft` | As in the [JSON](#json): how many messages `send` is holding for this pane, and whether someone is typing a draft in it. |
| `account_restart` | As in the [JSON](#json): `waiting` while the pane's agent waits for its turn to [restart on another account](../accounts/#restart-open-agents-on-another-account), `-` otherwise. |
| `pid` | The process id of the pane's shell, not of the program running in it; `-` when it is not known. |
| `memory` | As in the [JSON](#json): the memory the pane's shell and the programs under it use, in bytes, while [**memory**](../projects-workspaces-tabs/#how-much-memory-a-tab-uses) is on, `-` otherwise. |
| `compacted` | `true` while the agent's `context` is empty because its conversation was just compacted (`/compact`, `/compress`, or its own automatic compaction), until its next reply sets it again; `false` otherwise. The last column. |

- The values are the ones `--panes --json` gives: `true` or `false`, numbers without a unit, full paths. A `-` stands where there is no value (no agent, no branch, a field the server is too old to know), so a column never goes missing and `read` keeps them in place. A tab or a line break in a name shows as a space.
- The columns keep their order, and new ones only ever go at the end, so `$7` stays the status.
- `--panes --json` prints `{"panes": [...]}`, one object per pane with the columns as keys, in the same order, and `null` where the text shows `-`.

```sh
# the agents that wait for an answer
cornercase status --panes | awk -F'\t' '$7 == "waiting" { print $1 }'

# each pane with its agent and status, skipping the header
cornercase status --panes | tail -n +2 | while IFS=$'\t' read -r pane tab workspace project program agent status rest; do
  echo "$pane $agent $status"
done

# the agents in the worktree of fix/login
cornercase status --panes --json | jq '.panes[] | select(.branch == "fix/login" and .agent != null) | .pane'
```

#### Follow the whole state

Another UI for cornercase, or a script that draws the sidebar somewhere else, needs the whole session and every change to it: names, order, groups, folds and how each tab is split. `status --follow` prints it as one JSON line, first as it is now, then again shortly after each time something in it changes:

```sh
cornercase status --follow | jq -c '[.revision, (.projects | length)]'
cornercase status --follow | while read -r state; do echo "$state" > /tmp/cornercase-state.json; done
```

- Each line is what `status --json` prints, plus `revision`, a number that grows with every line, except `caller`, which is always `null`: find your own pane with `CORNERCASE_PANE` or `status --json` instead. It is always JSON, with `--json` or without, and it can't be combined with `--panes`.
- Each line is the whole state and replaces the one before: there are no differences to apply, so a reader can skip lines and lose nothing but the steps in between.
- `revision` only compares within one `boot`, the start of the server it came from. It ends, with status 0, when the server stops or restarts, or once whatever reads it is gone; to go on, run it again: its first line is the state at that moment, so nothing is missed. The same goes for a connection that ended (status 1).
- A change a command makes when no line went out in the last half second comes at once (not for `input`, `scroll`, `selection` and the other requests that come at a pointer's pace, which wait their turn), and the changes that follow within that half second come together in the next line, not one line for each. Output alone (a program printing in a pane) gives none, but what `status --json` shows moves too, such as an agent's status, its context or a pane's folder, and each of those gives a line, so a working agent can bring one every few seconds.
- A reader that falls behind isn't disconnected for it: the server keeps up to four lines waiting for it, which it still reads, older ones first; past those it keeps only the latest, so once it has read them it reads the state as it is now, with a jump in `revision`. One that stops reading altogether is disconnected once the server has waited a second to write to it, like any client.

#### Follow a workspace's changes

The changes panel's data is there for another UI too: the changed files with their status and counts, each file's diff with the words that changed and its highlighting, the unchanged lines between two hunks, the branch it compares with and the files you marked as viewed.

```sh
cornercase changes list                      # the workspace you are in, uncommitted
cornercase changes list --every --follow     # every project's uncommitted changes, as JSON lines
cornercase changes list --worktree fix/login --mode commits --json
cornercase changes file src/main.rs --json   # one file's diff
cornercase changes gap src/main.rs --hunk 1  # the unchanged lines before its second hunk
cornercase changes base origin/main          # compare Commits and All with another branch
cornercase changes viewed src/main.rs        # mark it viewed; --clear clears it
cornercase changes stage src/main.rs         # put its changes in git's index, as git add does
cornercase changes unstage src/main.rs       # take them out of the index; the file keeps them
cornercase changes discard src/main.rs       # put it back as in the last commit; asks first, --yes for scripts
cornercase changes discard src/main.rs --digest 550a7a517a389403 --yes  # only the version you saw
cornercase changes shared                    # the files other workspaces of the project change too (shared_files on)
cornercase changes merge-check               # merge it into its base and with those workspaces, in a scratch copy
cornercase changes merge-check --with 12 --json  # only the merge with workspace 12
```

- `changes` (`cornercase changes list --follow`) is a stream, one per connection. It answers a first summary at once, which may say `"state": "loading"` while git reads, then sends a whole new one each time the files change, with a higher `revision`; a line is only sent when its content differs from the last. Each summary replaces the one before it, and a reader that falls behind reads the latest, as with `status --follow`.
- A summary has `boot`, `stream` (its number, for `changes-mode`), `revision`, `scope` (`project` or `every`), `mode` (`uncommitted`, `commits` or `all`), `state` (`loading`, `ready` or `failed`, with `error`) and `workspaces`: each with `project`, `workspace`, `base` (what Commits and All compare with, `null` in Uncommitted), `added`, `removed` and `files`. A file has `path`, `old_path` (for a rename), `status` (`modified`, `added`, `deleted`, `renamed` or `untracked`), `added`, `removed`, `fold` (`open`, `lockfile`, `binary` or `large`: lockfiles show their lines, binary and large files have none), `viewed`, `staged` (`no`, `partly` or `yes`: how much of the file is in git's index; only in Uncommitted and Every project, left out in Commits and All) and `digest`. Summaries have ids only; the names are in `status`.
- A project stream has one workspace entry, with no files when there are none. An Every project stream (`--every`, only for Uncommitted) has one entry per workspace with changes, in the sidebar's order, and never ends by itself. A project stream ends when its workspace or project closes. A workspace nobody follows costs nothing more than the rows' count: git runs only for what a stream or the window shows, and for the rows a window or a visible view draws (see `against_base` below).
- **The mode belongs to the stream**: `changes-mode` changes a running stream's mode, and the window's tabs don't move. It only reaches a stream the same connection opened, so it is a request for a program holding the stream's connection open over the socket: a separate command invocation uses a new connection and gets `not-found`, which is why `cornercase changes` has no command for it (start another `changes list --mode …` instead). A second `changes` on one connection is refused with `conflict`. **The base and the viewed marks are shared** with the window: choosing a base here changes what its panel compares with, and a mark set here shows as its `✓`.
- `changes-file` answers a file's `hunks`: `old_start`, `new_start`, `context` and `lines`, each with `kind` (`context`, `removed` or `added`), `old` and `new` numbers (`null` where the line is not on that side), `text` (what a window draws, tabs as four spaces), `raw` (the line as it is in the file, tabs included, left out when it would be the same as `text`), `emphasis` (the words that changed, as `[start, end)` pairs in characters of `text`) and `syntax` (runs of `style` and `text`, left out where the line isn't highlighted). `styles` is the table the runs point into, in the same shape as a [surface](#stream-a-tabs-terminals)'s: palette indices, never RGB, so the client's own theme and tints apply; entry 0 is plain. To copy a line as the file has it, take its `raw`, or its `text` when it has none: a tab of `raw` is always four characters of `text`, so a selection made in `text` maps back to `raw`. `cornercase changes file Makefile --json | jq -r '.hunks[].lines[] | .raw // .text'` prints the lines with their tabs.
- `changes-gap` answers `lines` with their `old` and `new` numbers, `text`, `raw` and `syntax`, as in `changes-file`, for the lines between hunk `hunk` and the one before it (`hunk` is the index in `changes-file`'s `hunks`, counted from 0, so hunk 0 has no gap). `changes-base` without arguments lists `branches`, the `default` branch and the current `base`; with `base` it sets it (the default branch goes back to following the default) and with `clear` it clears it. `changes-viewed` sets a mark with the file's `digest`, or clears it with `clear`: a mark set with the digest of a version the file no longer has does not apply, as when the file changes under the window's mark.
- `changes-discard` takes the file's `path` and the Uncommitted `digest` you saw, and throws its changes away: the file goes back to the last commit, and one that git doesn't track or that was added since is deleted. It is refused with `conflict` if the file changed since that digest, and `not-found` if the file has no change. It answers `workspace`, `path`, `old_path` and `status`. The window shows no message. One sent while another runs in the same repository can fail on git's index lock.
- `changes-stage` takes the file's `path` and the Uncommitted `digest` you saw, and puts its changes in git's index, as `git add` does; with `staged` set to `false` it takes them out instead (`staged` is `true` when left out). The file keeps its changes either way. It is refused with `conflict` if the file changed since that digest, and `not-found` if the file has no change. It answers `workspace`, `path`, `old_path`, `status` and `staged`. The window shows no message. One sent while another git runs in the same repository can fail on git's index lock.
- `changes-merge-check` merges a workspace's work, committed or not, in a scratch copy with `git merge-tree` (git 2.38 or later) and answers `workspace` and `checks`, one per merge: `with` (a workspace) or `base` (a branch) for what it was merged with, `clean`, `conflicts` (`path`, `kind` such as `contents`, `modify/delete` or `add/add`, and git's `message`), `left_out` (untracked files over 1 MiB, or past 8 MiB in all, which the check left out) and `error` (`clean` is false when it is set). Without arguments it checks the workspace's base branch (the one the changes panel compares with) and each workspace that shares files with it; `with` checks only that workspace of the same project, `base` only that branch, and the two together are `malformed`. An unknown branch is that entry's `error`, not a refusal; a workspace outside a git repository, a `with` in another project and a `with` in the same folder are `conflict`. No checkout, index, branch or object of the repository changes. `cornercase changes merge-check` prints `into main  merges cleanly`, or `with workspace 12 feat/dark-mode  1 conflict` and a line for each conflicting file, and exits with status 3 when any check has an `error` (conflicts are an answer, not a failure); `--json` prints the answer. `cornercase changes shared` prints the files the workspace shares with each other workspace, or `{"workspace": 11, "shared": [...]}` with `--json`; it reads `status`, where each workspace has `shared` (see the table below).
- `cornercase changes viewed`, `stage`, `unstage` and `discard` read the file's `digest` just before they act, so they act on the version there at that moment, but only when `--digest` is absent. A UI that showed a diff passes the `digest` it showed with `--digest`, and the command then reads nothing and sends that one (`discard` without `--yes` still reads the file, only to form its confirmation question, and asks first). A file that changed since is left alone: `stage`, `unstage` and `discard` fail with the `conflict` message, and `viewed` sets a mark that only applies to the version seen. For `stage`, `unstage` and `discard` it is the Uncommitted `digest` (Every project's is the same); one from `--mode commits` or `all` is refused as changed.
- `digest` is a string of 16 hexadecimal digits that changes whenever the file's change does. `status --json` also gives each workspace `changes` (`files`, `added`, `removed` and `mode`), for a badge like the button's, while cornercase keeps it current: the window's workspace, one a stream follows, or any while a stream follows every project; it is left out otherwise.

#### Browse and read a workspace's files

The files panel's tree, viewer and search are there for another UI too, which matters when that UI runs on another machine than the server (see [Another machine](../remote/#commands-for-scripts-and-agents)): it can't read that disk itself, and copying the panel's rules (what git ignores, the size limits, what is an image or a binary) would drift from them.

```sh
cornercase files list --workspace 3 --json                 # the workspace's root: name, kind, size, modified, hidden, git status
cornercase files list src docs --workspace 3 --json        # several folders in one answer
cornercase files list '~/code' --json                      # any folder on the server's machine
cornercase files list src --workspace 3 --follow           # a JSON line again whenever the folders change
cornercase files read src/main.rs --workspace 3 --json     # text, an image as base64, or what else it is
cornercase files read notes.txt                            # the text, as it is
cornercase files search parse --text --workspace 3 --json  # the lines that match; --names searches file names
```

- **Paths** are relative to the workspace (the one you are in, or `--workspace` or `--worktree`), never to the folder the command runs in. An absolute path, or one starting with `~/` (the server's home folder), reaches any folder on the server's machine and needs no workspace; git's marks only show for what is inside the workspace. A path is echoed as you wrote it (`path`) and in full (`dir`, `file`).
- **`files list`** answers `workspace` and `folders`, one entry per folder you asked for (the root with none): `path`, `dir`, `entries`, `more` (`true` when entries were left out: at most 10,000 per folder) and `error` (`null`, or why it could not be listed: `no such folder`, `not a folder`, `permission denied`; the other folders still answer, and the command exits with 3). An entry has `name`, `kind` (`file`, `folder` or `other`: a device, a pipe, a socket or a link to nothing), `link`, `hidden`, `bytes` (files only), `modified` (UTC) and `status` (`modified`, `added`, `deleted`, `renamed`, `untracked` or `null`: what is not committed yet, as the tree marks it; a folder is `added` when everything in it is new and `modified` when it holds changes). Entries come in the tree's order, folders first. What git ignores and `.git` are left out, and hidden files are listed: hide them yourself with `hidden`. The text output is a table with a header line, `.` for the root and `-` for nothing.
- **`files read`** answers `path`, `file`, `kind`, `bytes`, `modified`, `language`, `text` and `image`. `kind` is `text` (the whole file, up to 8 MB, with the `language` the viewer highlights it with), `image` (told by its first bytes, up to 32 MB: `image` has `format`, `width`, `height` and `data`, the file in base64), `binary`, `too-large` (with its `bytes`; nothing of it is sent), `folder` or `missing`. Only regular files are read, so a link to a device answers `binary`. A 32 MB image is about 43 MB of base64, in one line. The text output is the file as it is, or one line saying what it is; a folder or a missing file exits with 1.
- **`files search`** answers the panel's search, in the workspace only. With `--names` (the panel's name mode), `names`: the best 200 files, ranked, smart-cased, each with `path` and `indices`, the characters of the path that matched. By text (the default), `files`: each with `path` and `lines` (`number`, `text` and `ranges`, `[start, end)` pairs in characters of the text), at most 1,000 matches in all. Both have `workspace`, `query`, `mode`, `matches` and `capped`. The text output is one path per line for names, and `path:line:text` for text, as `grep -n` prints it. It walks the files fresh each time and stops when your command goes away.
- **`--follow`** on `list` and `read` keeps running and prints a JSON line each time what it shows changes: folders are listed again every 2 seconds and a file is checked every second, next to the disk, so a client on another machine doesn't poll through `ssh`. The first line is the answer as it is now, with `boot`, `stream`, `revision` (counting from 1) and the same fields as above; each line replaces the one before, and a reader that falls behind reads the latest. A line is only sent when the folders (or the file) changed, so a busy folder sends about one every 2 seconds. It ends when the workspace closes, or once what reads it is gone. A connection follows one stream at a time (`conflict`); to open another folder, start the stream again with one more.
- The requests are `files-list` (`workspace`, `folders`, `follow`), `files-read` (`workspace`, `path`, `follow`) and `files-search` (`workspace`, `query`, `mode`: `text` or `names`). Without `--follow`, one answer. Queries and file contents never reach the server's log.
- `status --json` gives `home`, the server's home folder, so a client shows `~/…` for paths there as the window does.

#### Follow the rest of the app

The session is not all of cornercase's state. The [TODO list](../todo/), the [queue](../queue/), whether you are [away](#away-on-telegram-or-discord) on each chat app, the update found and [keep awake](../../reference/agents/#keep-the-computer-awake) live outside it, and another UI needs them too. `status --app` prints them as one JSON object, and `--follow` prints it again each time one of them changes:

```sh
cornercase status --app
cornercase status --app --follow | jq -c '[.revision, (.todos | length)]'
```

- `todos`: the items as `todo list --json` has them, in the panel's order. `queue`: the entries `queue list --json` has, prompts included, with `started` and `result_at` once an entry started and kept a [result](../queue/#what-each-run-did), never the result's text.
- `away`: one row per chat app, `telegram` then `discord`, each with `ready` (paired, and the bot's token not refused) and `away`. Discord's row also has `forum` once [forum mode](../discord/#forum-mode) is on or a forum is saved: `on`, `ready`, `guild` and `channel` (ids, as text) and `pending`, the setup step still left, or `null`. While that step is picking a server, it also has `servers`, each with `id` (as text) and `name`, which [`config forum-server ID`](#pick-the-forums-server) picks from.
- `update`: `release` (`version` and its `notes`, each with a `version` and `text`), or `none` saying why there is no release: `disabled` (a development build), `off` (`check_updates` is off and nothing was checked), `unchecked`, `up-to-date` or `failed`. Also `checking`, `checked` (UTC time of the last answer), `error` (why the last check failed), `install` (`{"method": "replace", "path": …}` when cornercase can replace itself, `{"method": "command", "command": …}` when you must run a command, as with Homebrew), `installing`, `installed` (restart to use it) and `install_error`. [`update-check` and `update-install`](#updates-from-a-program) drive it.
- `keep_awake`: as in `status --json`, or `null` while the setting is off. `version` and `boot` are the server's, as in `status`.
- `popup`: while a plugin's [popup](../plugins/#popups) is open, `plugin`, `action` and its size, `cols` and `rows`; left out otherwise. `plugin popup-close` closes it, and [`surface --popup` and `input --popup`](#a-plugins-popup) show it and type into it.
- `machines`: the rows of [`machines`](#machines), there only while you list some. A line comes when a machine's state changes or a failed try moves its `retry_at`, not as its `unreachable · 8 s` counts up or that time draws near, since `seen` and `retry_at` are times.
- `accounts_revision`: a number that moves each time the accounts [`account list`](#accounts-and-profiles) names change: `account add`, `account remove`, or a folder another program made or deleted, seen within a second. It is left out until it first moves, so a server that never had an account does not have it, and one that starts with accounts has it from its first line. List the accounts again when it moves, rather than on a timer: a first account added by a command typed in a pane changes nothing else you can see. An account's name, a default and a profile do not move it, they move `config.revision`, so list again for either. Like `revision`, it only compares within one `boot`. An older server leaves it out too, so a client that stops asking on its own checks the `accounts-revision` [feature](#ask-the-server-first) first.
- `tour`: the [guided tour](../../first-steps/#the-guided-tour-and-help): `active` (the `tour` and `step` ids on screen, its `index` and whether the window shows its `card`, or `null`), `offered` (whether it was shown by itself already), and `progress`, one row per tour with the steps `done` and whether it is `finished`. See [Draw the tour](#draw-the-tour).
- It follows the rules of [`status --follow`](#follow-the-whole-state): every line is the whole state and carries a `revision` that grows by one per line, `revision` only compares within one `boot`, a reader that falls behind reads at most four older lines and then the latest, and it ends when the server stops or restarts. A line goes out at most twice a second, and only while someone follows. It is a stream of its own so that the session's lines do not carry the queue's prompts and the release notes every half second.

#### Follow a flow run

A [flow](../flows/) run is state of its own: the stage the work is in, the loops, each role's pane and status, what the roles sent each other, the files they wrote. Another UI needs it to draw the Flow panel, and a script needs it to know whether a team is done.

```sh
cornercase flow runs
cornercase flow runs --follow | jq -c '[.revision, (.runs | length)]'
cornercase flow messages --worktree fix-login --follow
cornercase flow files --worktree fix-login
```

- **`flow runs`** prints one block per running flow: its workspace, the stage (counted from 1 for people), the rounds of its loops, the task's first line, each role's pane and status (`closed` once its pane is gone; `awaited` is `working`, then `finished` until cornercase has told the orchestrator, while the role holds work the orchestrator sent it; a run whose agents were [closed to reopen later](#close-and-reopen-a-workspaces-agents) is listed too, with `state: "closed"` and every role's pane `null`), the last step and the last one outside the plan, and whether the orchestrator marked its pane for review, which is how a run ends. `--follow` prints the same as one JSON line each time something changes, until the server stops. The request is `flow-runs`, a stream like [`status --app`](#follow-the-rest-of-the-app): every line is the whole state with a `revision` (see [`status --follow`](#follow-the-whole-state) for what that guarantees), a line goes out at most every half second and only while someone follows.
- **A run in the JSON** has `run` (its id, which `flow run` answers too and which a restore changes), `project`, `workspace`, `flow` (the plan the team was briefed with, as in [Manage flows](#manage-flows), frozen at the start: editing or deleting the flow does not change it), `task`, `dir` (the run's folder), `roles` (the orchestrator first, then the flow's roles in order; each with `role`, `pane`, `tab`, `status`, `closed`, and `worktree` and `branch` for a role with a worktree of its own; a role with no pane, after a restore that could not bring it back, has `null` for all), `stage`, `rounds`, `holder`, `last`, `outside`, `ended`, `messages` and, on a run that closes its agents once its pull request merges (see [Start a flow](#start-a-flow)), `close_when_merged` (left out otherwise).
- **`flow close-when-merged`** (`--workspace ID`, `--worktree BRANCH`, `--off`) sets, for a run that is already going, whether its agents close once its pull request merges, as `flow run --close-when-merged` does from the start. The request is `flow-close-when-merged` (`workspace`, `off`, both always written) and the answer has `run`, `project`, `workspace`, `close_when_merged` and `changed`: it sets the choice and never toggles it, so saying it twice changes nothing the second time. It refuses with `not-found` for an unknown workspace and `conflict` when the workspace runs no flow, when its agents are closed (reopen them first) and when turning it on for a flow that leaves the commits. The text says `the agents of workspace 7 close once its pull request merges and none of them works`, `… already close …`, `… stay open after its pull request merges` or `… already stay open …`.
- **Stages here count from 0**, the index in `flow.stages`, unlike a loop's `back.to`, which counts from 1 as in the flow's file. `stage` is the stage the work is in (`null` before the orchestrator sends anything), `rounds` has one number per stage (how many times its loop went back), and `holder` is the role that last got the work. A step is `{"edge": …, "from": …, "to": …, "time": …}`, where `edge` is `{"kind": "forward", "stage": N}` (it leaves stage N), `{"kind": "loop", "stage": N}` (stage N's loop) or `{"kind": "outside", "from": N or null, "to": M}` (a role of a stage the plan does not lead to), `from` is the role that held the work before (not the sender, which is always the orchestrator) and `time` is UTC. `outside` is the last step outside the plan, and `ended` is `true` once the orchestrator's pane is marked for review. Only what the orchestrator sends into a role moves the work, as in the diagram.
- **`flow messages`** prints what the orchestrator and the roles of a run sent each other: its sends, and the keys it pressed, the screens it read and the waits it made, each with its time, who, to whom and the text. `--workspace ID` or `--worktree BRANCH` names the run (the one in the pane's own workspace, else the shown one, by default); with no run there it says so. `--follow` goes on printing until the run ends. With `--json` each message is one line: `run`, `workspace`, `seq` (counted from 1 for the run), `time`, `from`, `to`, `kind` (`send`, `keys`, `read` or `wait`), `text` (`null` when there was none), `bytes` (the real size: a text is kept up to 32 KiB) and `edge`, the step along the plan it moved the work through (`null` when it moved nothing); the backlog comes first, expanded into those lines. Only the last 256 messages of a run are kept, in memory, and never logged or saved, so a run that was restored starts with none. The request is `flow-messages`, a stream of its own on its connection: its answer is `{"boot", "run", "workspace", "messages": [...]}` with every message kept so far, then each new message is one line, in order, with no gap in between, and it ends (`Detached`) when the run does. A client that cannot keep up gets a `{"event": "dropped", "count": N}` line, as in [Follow events](#follow-events), and reconnects to read what is kept. A second `flow-messages` on one connection is `conflict`.
- **`flow files`** lists the files of the run's folder, newest first, at most 200, as a table (`name`, `bytes`, `modified`, `path`; `--json` prints `workspace`, `run`, `dir`, `files` and `more`). After the run ended it lists the last folder the workspace's runs made, for as long as the workspace lives; a workspace that never ran a flow is `conflict`, and a folder that was deleted `failed`. The request is `flow-files`, one answer. To read a file, `cornercase files read` with its `path` (see [Browse and read a workspace's files](#browse-and-read-a-workspaces-files)).

#### Stream a tab's terminals

A program that draws cornercase's terminals itself, such as an editor extension or a GUI, needs more than `read`'s plain text: the cells with their colours, where the cursor is, which modes the program turned on, and how the tab is split. `surface` streams all of it for one tab, laid out at the size you give, as one JSON line:

```sh
cornercase surface --tab 3 --cols 120 --rows 40
cornercase surface --tab 3 --cols 120 --rows 40 | jq -c '[.revision, [.panes[].pane]]'
```

The first line is the tab as it is now, the next ones come when something it shows changes, at most about 60 a second and never twice the same. Each line is complete and replaces the one before, unless you ask for [patches](#patches). Find the tab's id with `cornercase status`. The tab doesn't have to be the one the window shows, and streaming it doesn't switch to it or change anything the window shows. It works on a server started with `start-server`, with no window.

A line has these keys:

- `boot`, `session`, `surface` and `revision`: the server's start (see [Contract and compatibility](#contract-and-compatibility)), the `revision` of the latest [`status --follow`](#follow-the-whole-state) line sent before this one was drawn (0 if none was sent since the server started), this stream's id (the one [`resize`](#drive-a-tabs-terminals) takes) and its own counter, from 1, up by one per line. A line from another `boot` is stale. To get a complete baseline again, run the command again: its first line is always complete.
- `tab`, `cols` and `rows`: what you asked for.
- `layout`: the tab's whole split tree, as in `status --json`, hidden panes included. `dividers`: each divider with its `dir`, its `path` through `layout` (`false` for the first side, `true` for the second), the region it divides (`area`) and its cells (`line`).
- `panes`: the panes the surface shows, each with `pane` (its id), `active`, `rect` (`x`, `y`, `cols`, `rows`: where to draw it in the surface), `size` (its terminal's own columns and rows), `cursor` (`x`, `y`, `shape` as `block`, `bar`, `underline` or `block_hollow`, and `blinking`, or `null` when hidden or scrolled out of view), `modes`, `scroll`, `colours`, `wrapped` and `lines`.
- `modes`: `mouse` (`none`, `press`, `press_release`, `button_motion` or `any_motion`), `mouse_encoding` (`default`, `utf8` or `sgr`), `alternate_screen`, `alternate_scroll`, `bracketed_paste`, `application_cursor`, `focus_events` and `kitty_keyboard` (the flag bits). They are what you need to turn keys and the mouse into what the program expects.
- `scroll`: `total` rows of history plus screen, `offset` of the view's first row, and `rows` in the view. What is under the view is `total - offset - rows`. A pane scrolled up shows its history in `lines`.
- `hyperlinks`: the table the runs' `hyperlink` numbers index, shared by all the panes, left out when no cell has a link: `[{"uri": "https://example.com"}]`, from OSC 8 (`ls --hyperlink`, compilers, `gh`). A link is its address: cells with the same address are one entry, so a link that wraps onto the next line is one link, and two separate spans to the same address open the same place. OSC 8 ids aren't sent.
- `colours`: the colours the pane's program changed, left out when it changed none: `fg`, `bg` and `cursor` as `[r, g, b]` (OSC 10, 11, 12) and `palette`, such as `{"1": [255, 0, 0]}` (OSC 4). Resolve a colour `{"index": n}` through `palette` before your own palette, and draw default-coloured cells with `fg` and `bg` when they are there. Your theme is never listed: only what the program set, until it resets it.
- `wrapped`: the rows, numbered as in `lines`, whose line goes on in the next row because the terminal wrapped it there, left out when no row does. `"wrapped": [2, 3]` says rows 2, 3 and 4 are one line, so a web address a program printed across them can be opened whole. To join a row to the next, pad its cells to `size.cols` with blanks first (`lines` leaves trailing blanks out): the next row's first cell follows its last column. Where a wide character did not fit at the end of a row, the terminal left that last column empty, and the frame doesn't say which one, so padding adds a blank there that the line never had: harmless in a web address, but it can split a line that holds wide characters. A line that ends with a newline is never listed, even when it fills its row. In a pane scrolled up, the last row is listed when its line goes on below the view, and nothing says whether the first row goes on from a row above it. A server without the feature `surface-wrapped` never sends `wrapped`, so there its absence says nothing.
- `lines`: one entry per row of the pane's terminal (`size.rows`), each a list of runs, `{"style": 1, "hyperlink": 0, "cells": ["o", "k"]}`: consecutive cells of one style and one hyperlink (`hyperlink` is left out when the run has none). A blank that is part of a link is kept at the end of a line. A cell is a string, the character with any combining marks. The right half of a wide character is `""`: don't draw it, the cell before covers it. The cells after the last one that isn't a blank in the default style are left out, so an empty line is `[]` and the rest of a line is blank.
- `styles`: the table the runs' `style` numbers index, shared by all the panes. Entry 0 is `{}`, the terminal's default colours. Others have `fg` and `bg` (absent for the default colour, `{"index": 0-255}` for a palette colour, which your theme decides, or `{"rgb": [r, g, b]}`) and the attributes that are on: `bold`, `dim`, `italic`, `underline`, `blink`, `inverse`, `invisible`, `strikethrough`, `overline`, and for underlined cells `underline_style` (`double`, `curly`, `dotted` or `dashed`; a plain underline has none) and `underline_colour` (like `fg`). A client that knows only `underline` draws every style as a plain one. A selection made in a window shows as `inverse`.

##### Patches

A long-lived program that parses every line pays for the whole tab each time, and so does a link that carries it. With `--patches` the first line is complete and the next ones carry only what changed:

```sh
cornercase surface --tab 3 --cols 120 --rows 40 --patches
```

A server from before patches ignores the option and sends complete lines, which you apply the same way, and `cornercase contract` lists the feature `surface-patches` to check for it. A line with no `base` is complete, as above. A line with `base` is a patch, and has `boot`, `session`, `surface`, `revision`, `tab`, `cols` and `rows` as before (and `view` and `projection` for `--view`), then:

- `base`: the `revision` it applies to, always the one before it. Apply a patch only when `base` is the `revision` of the last line you applied; otherwise ask for a complete line with `cornercase redraw --surface ID`, or connect again.
- `styles` and `hyperlinks`: tables for this patch's runs only. A run's `style` and `hyperlink` in a patch index these, not the tables of the line you hold, so resolve them as you apply a row and keep what you resolved.
- `panes`: only the panes that changed, each with `pane` and `cursor` (always: `null` is a hidden cursor), and only what changed of `active`, `modes`, `scroll`, `colours` (`{}` once the program resets them), `wrapped` (the whole list, `[]` once no row goes on), `copy` and `lines`. A pane that is not listed did not change.
- `copy`: `from`, `to` and `count`. Before you apply `lines`, take rows `from` to `from + count - 1` of the pane as you held them and write them at `to`. It is how output that scrolls arrives: the rows that moved, not their content. Rows it doesn't cover keep what they had.
- `lines`: row number (`"3"` is row 3) to that row's whole line of runs, as in a complete line; `[]` is a blank row. Replace those rows after `copy`.

The layout, dividers, the set of panes, their `rect` and `size`, and the tab and size of the surface never change in a patch: when any of them does, the next line is complete. It is also complete when the view's `projection` changes, after the server held back a line because you were slow to read, and when you ask:

```sh
cornercase redraw --surface 4
```

`redraw` takes the `surface` of the lines. The surface's next line is complete and comes at once, even if nothing changed. It works with or without `--patches`. An unknown or ended surface is `not-found`, and no `--surface` is wrong usage.

Things to know:

- The panes are laid out in your `cols` × `rows` the way the window lays out a tab, including when the tab is too small for all its panes: then only the active one shows, over the whole surface. The terminals keep the size of whoever sizes the tab (the window, or [a view](#a-view-of-your-own)), though, so a pane's `size` can differ from its `rect`: `lines` and `cursor` follow `size`. Streaming a `--tab` doesn't resize anything.
- `cols` is 1 to 1000 and `rows` 1 to 500. A connection streams one tab; `cornercase resize --surface ID` changes the size of one given with `--tab` in place, and another tab needs another connection.
- It ends, with status 0, when the tab closes, the server stops or restarts, or whatever reads it is gone (stopping it yourself leaves the shells running). A pane whose shell exits drops out of the next line. A tab that doesn't exist, or an out-of-range size is an error, with status 1; a missing `--tab`, `--cols` or `--rows` is wrong usage, with status 2.
- A reader that falls behind gets fewer lines, each complete (with `--patches`, the line after falling behind is complete), so it never has to repair a picture: the server draws a new line only while little is waiting for it. One that stops reading altogether is disconnected once the server has waited a second to write to it, like any client.
- Keys added later, such as `hyperlinks`, `colours`, `wrapped`, `underline_style`, `underline_colour` and `overline`, are left out when empty, so a reader that doesn't know them keeps working and a terminal that uses none of them sends exactly what it did.
- Not sent yet: images, OSC 8 link ids, pixel sizes and a terminal size set pane by pane. A pane's title is in `status --json`, and its bells and clipboard writes in [`events --host`](#follow-events).

- `against_base` (feature `against-base`) is what the Changes panel's All mode counts for a workspace: `base` (such as `origin/main`), `files`, `added` and `removed`. It is present only while a window or a visible view draws the workspace's row and a count is held, and left out otherwise; `files: 0` means counted and clean. `cornercase status` prints it as `16 files +640 −9 vs origin/main`. A view's lines also carry `changes` (Uncommitted) for the workspace that view shows, and a hidden view (`view-set --hidden`) draws nothing, so it keeps no count running.

#### A view of your own

Two programs that draw cornercase, or a program and the window, shouldn't have to share one selection and one size. `view` opens a **view**: its own project, workspace and tab, an optional size, and an active flag. It keeps running and prints the session as one JSON line each time it changes, like `status --follow`, plus a `view` object, and the view lives as long as the command does: stopping it closes the view and hands its tabs back. The processes keep running.

```sh
cornercase view --cols 120 --rows 40 > view.jsonl &
id=$(head -n 1 view.jsonl | jq .view.id)
cornercase new-tab --view "$id" --focus --name logs
cornercase surface --view "$id"
```

- `view` has `id`, `projection`, `active`, `cols` and `rows` (`null` without a size), `shown` (the `project`, `workspace`, `tab` and `pane` it shows) and `controls` (whether it sizes its tab's terminals now). It starts on what the window shows, or on `--tab`, `--workspace` or `--project`; the window doesn't move. Each tab in the lines has `controller`: the id of the view sizing it, absent when the window does.
- `--view ID` works on `status`, `focus`, `open`, `clone`, `new-workspace`, `new-tab`, `split`, `setup`, `start`, [`flow run`](#start-a-flow), `send`, `keys`, `held`, `read`, `wait`, `mark`, `rename`, `go`, `surface` and [`plugin run`](#plugins), `account add --login` and [`account login`](#accounts-and-profiles), also from separate commands. The view's tab is their default, and `focus`, `--focus` move the view, not the window or the other views. `focus --view --json` prints the view's new tab and its `projection`. Other commands refuse it. A server without views is refused up front, naming the update.
- When something the view shows goes away, it moves like the window would: a closed tab to the one before it, a closing workspace or project to its neighbour. That never resizes a tab for it.
- `surface --view ID` streams the tab the view shows, at the view's size, and follows the view to other tabs. It takes no `--tab`, `--cols` or `--rows`, and each frame carries `view` and `projection`.
- `view-set --view ID` changes it: `--cols` and `--rows`, `--active` or `--inactive`, `--hidden` or `--visible` (see below), and `--claim` to size the tab it shows from now on. A view without a size, or inactive, sizes nothing and streams no terminals, but its lines keep following the session.
- The tab a view shows counts as seen, like the window's, while the view is active, has a size and is visible: an agent there gets no `✓`, toast or desktop notification. `view --hidden` and `view-set --hidden` say its window is hidden or minimised, so agents there notify again, and `--visible` says it is back, which also asks again at once for every open [pull request](../worktrees/#pull-requests-and-their-checks) not read in the last 10 seconds, as coming back to the window does. While a view is open, the window's tab counts as seen only while a window is attached; a program that only shows notices can open a view without a size.

**Who sizes a tab.** One at a time, so two programs showing the same tab never fight over its size. The window is the default. A view claims the tab it shows when it opens, moves there, turns active, or with `--claim`; using a window (a key, a paste, a click) takes back the tab it shows, until the window shows another tab. The latest claim sizes the tab's terminals at the view's `cols` × `rows`, without the window's sidebar or panels; when it lets go (inactive, moved on, closed) the tab goes to the latest one left, else the window.

**`projection`** starts at 1 and goes up each time what the view's surface shows changes: its tab, its size or whether it is active. Show a frame only when its `projection` is the latest one you know: an older one was drawn before your last move.

Still shared with the window and every other view: the programs and their output, how a tab is split, which pane of a tab is focused (`focus --view --pane` moves it for everyone), the scroll position and the selected text. The window's overlays, side panels and sidebar scrolling are its own.

#### Drive a tab's terminals

A program that draws a tab with `surface` also has to type into it and handle its own mouse. A window's keys and clicks go through the window, where a dialog or a field can take them and a click is a cell of the window's layout. These commands act on a pane or tab you name, whatever the window shows:

```sh
cornercase input --pane 12 '{"text": "ls"}' '{"key": {"code": "enter"}}'
cornercase input --pane 12 '{"key": {"code": "c", "mods": ["ctrl"]}}'
cornercase input --pane 12 '{"mouse": {"kind": "scroll-up", "x": 10, "y": 5}}'
cornercase input --pane 12 --follow --json -
cornercase scroll --pane 12 --up 10
cornercase selection --pane 12 --from 0,3 --to 79,5 --copy
cornercase ratio --tab 3 --path second 0.3
cornercase resize --surface 4 --cols 100 --rows 30
cornercase link --pane 12 --cell 10,3
```

- `input` takes one JSON event per argument, sent in order (`-` reads one per line from standard input): `{"key": {"code": "c", "mods": ["ctrl"], "kind": "press"}}` (`code` as for [`keys`](#talk-to-a-pane); `mods` any of `ctrl`, `alt`, `shift`, `super`; `kind` `press`, `repeat` or `release`), `{"text": "héllo"}` (committed text, no control characters), `{"paste": "two\nlines"}` (bracketed when the program asked for it) and `{"mouse": {"kind": "down", "button": "left", "x": 3, "y": 1, "mods": []}}` (`kind` `down`, `up`, `drag`, `moved`, `scroll-up`, `scroll-down`, `scroll-left` or `scroll-right`; `x` and `y` are cells of the pane's terminal, from 0, as in the `lines` of a frame).
- Events are encoded the way the program in the pane asked for, the way the window encodes what you type: its keyboard protocol, application cursor keys, bracketed paste and mouse mode and encoding, all in the `modes` of a frame. Keys, text and pastes bring the pane's view back to the bottom. They don't set the shared window size and don't answer for the agent: unlike `send` and `keys`, `input` types into an agent's dialogs and answers its permission prompts, because it is a person typing through another UI. Scripts and agents should keep using `send` and `keys`, which check first.
- A mouse event the program doesn't take in its current mode, or a key release when it didn't ask for event types, is not sent and is listed in the answer's `skipped` (`{"event": 0, "why": "mouse"}`; the command prints a warning). Everything else is encoded first and written in one go: when one event is wrong, or the program isn't reading its input, nothing is sent. Add `"size": {"cols": 80, "rows": 24}` to the request to say which terminal size your coordinates are for: if the pane has another size now, nothing is sent (`conflict`).
- `scroll` moves the pane's view through its history by `--up` or `--down` rows, or to `--top` or `--bottom`, and answers with its `scroll` as a frame has it. The view is the pane's, so the window shows the same one. On the alternate screen, or when the program reads the mouse, the program scrolls itself: send it keys, or the wheel with `input`; `scroll` refuses with `conflict`.
- `selection` with `--from X,Y --to X,Y` selects between two cells of the pane's view (columns and rows from 0, as in `lines`; `--rectangle` for a block) and prints the text. Without them it prints what is selected, `--clear` removes the selection, and `--copy` also copies it through the window, as selecting there does, and prints what it copied (the answer's `text`), so a program without a window can put it in the clipboard itself. The selection is shared with the window, which shows it as `inverse`, and with every client; the last one to change it wins.
- `ratio RATIO` sets the share of the first side of a tab's divider, between 0 and 1. `--path` names the divider as the `path` of a frame's `dividers` does (`first` or `second` at each level down; without it, the outermost). The terminals follow at once, with the window's geometry. To open or close splits use `split` and `close`.
- `resize` lays a running `surface` out at another size without starting it again; `ID` is the `surface` of its lines. Its next line comes at the new size, with the next `revision`. It resizes no terminal: they keep the size of whoever sizes the tab. A surface that follows a view (`surface --view`) takes the view's size, so `resize` refuses it: change the view with `view-set`.
- `link --cell X,Y` says which file a click on that cell of the pane's view opens in the window (columns and rows from 0, as in `lines`), so you get cornercase's detection of the paths programs print without copying it: the path under the cell, looked up from the folder of the program in the foreground, then from the root of the pane's workspace, with its line or lines. It prints `path`, `path:12` or `path:12-30`, and nothing, with status 0, when the cell holds no file; `--json` also says whether the file is inside the workspace. It opens nothing, and OSC 8 links are in the frame's `hyperlinks`, not here. Web addresses aren't looked up: find them in the frame's cells, joining the rows its `wrapped` lists.
- `input --follow -` keeps running, so a program types through one process rather than one per batch of keys, and with [`--remote`](../remote/#commands-for-scripts-and-agents) through one `ssh` connection. It reads one event per line from standard input and sends each line as soon as it arrives. Lines that arrive while the previous request is on its way go together in the next one, so there is one request at a time, in order.
- A line can name its pane, `{"pane": 14, "key": {"code": "enter"}}`; without `pane` it goes to `--pane`. One process can type into every pane of a view.
- Each request is all or nothing on its own. With `--json` it prints one line per request: the answer with `events` (how many of your lines it answers; blank lines are skipped) and each `skipped` event counted from the first line read, or `pane`, `error` and `events` when a request was refused or a line wasn't an event. The next lines still go.
- `input --follow` ends when standard input ends, after the last answer: with 0, with 3 if some line wasn't sent, or with 1 once the server stops or the connection drops (it notices at the next line). A program on the socket does the same by keeping its connection and sending each `input` after the answer to the one before.
- Requests on different connections aren't ordered: send the next `input` after the answer to the previous one, put several events in one request, or keep one `input --follow` running. Unlike the other commands, these six log at debug level, since a program sends them as fast as someone types or drags.

#### Many commands through one process

A program that draws cornercase (a window of its own, an editor's panel) sends many small commands: a focus, a scroll, a split. Run one by one, each is a whole process, and through [`--remote`](../remote/#commands-for-scripts-and-agents) a whole `ssh` session. `requests --follow -` keeps one running and sends them all through one connection:

```sh
cornercase requests --follow -
cornercase --remote devbox requests --follow -
printf '%s\n' '{"args": ["status", "--json"]}' | cornercase requests --follow -
```

```json
{"args": ["focus", "--tab", "6", "--view", "21"]}
{"args": ["send", "--pane", "5", "-"], "stdin": "cargo test"}
```

- A line is one JSON object: `args` is the command line after `cornercase`, read by the same parser, so every flag works and each command's `--help` stays the contract; `stdin` is what the command reads from `-` (text; for bytes use a file argument). Other keys are refused, so a typo never runs `send -` with no text. Blank lines are skipped.
- Each line gets one answer line, in order: `status` (the exit status the command would have had: 0, 1, 2, 3 or 4), `json` (what it printed with `--json`), `text` (what else it printed, such as the id `new-tab` prints), `stderr` (its warnings) and `error` (its message). Only `status` is always there: empty `json`, `text`, `stderr` and `error` are left out, and a status 1 or 3 may have no `error` (its reason is in `stderr` or in its `json`). New fields may be added; read what you know. A line that isn't JSON, is refused or fails does not stop the next ones.
- It runs the commands that send requests. The streams (`events`, `surface`, `view`, `changes list`, `config pair`, every `--follow`), `update`, `restart`, `kill-server`, `logs` and the plugin commands that work on the files need a process of their own and are refused with status 2, as are `start-server` (it needs no connection, and `requests` needs a running server: run it first), `--remote` on a line and the commands that act on this machine (`remote`, `skill`, `plugin windows` and so on).
- Lines run one at a time, each after the answer to the one before. A line that waits (`wait`, `send --wait`, `start --wait`) holds the lines after it; to put a key before a focus, send both through `requests`. Lines aren't ordered with other connections.
- It ends when standard input ends, after the last answer (with 5, before the first line, when `--remote` reaches an older cornercase): with 0 if every line had status 0, with 3 if some didn't, with 1 once the server stops or the connection drops (it never reconnects, because ids change with a restart: start it again and look at `status`), and with 0 when what reads its answers is gone, even while a line waits. Between lines it waits for the next one without watching the server or the reader, so it notices that either is gone at the next line.

#### A plugin's popup

A plugin's [popup](../plugins/#popups) is a terminal too, so a program that draws cornercase can show it and type into it the same way, with `--popup` instead of a tab or a pane:

```sh
cornercase surface --popup
cornercase input --popup --pane 40 '{"key": {"code": "down"}}' '{"key": {"code": "enter"}}'
```

- `surface --popup` streams the popup open in the window, in the same lines as a tab: one pane, the popup's terminal, at the popup's own size (`cols` and `rows`, which follow the window's size, or with no window attached the size of the view it opened for), with `popup` naming it: its id (`pane`, the same as its pane's), its `plugin` and its `action`; `tab` is 0, `layout` `null` and no `dividers`. `--patches` works as for a tab. It takes no `--tab`, `--cols`, `--rows` or `--view`, and `resize` refuses it. It ends when the popup closes, like a tab's surface when the tab closes; for the next popup, run it again.
- `input --popup` types into the popup's program, with the events `input` takes for a pane (mouse cells are the popup terminal's, as in its `lines`). The answer's `pane` is the popup's id. Add `--pane ID` with the `popup.pane` of the lines you drew, as a program that draws the popup always should: if that popup closed and another one opened since, nothing is sent and it fails with `not-found`, so keys meant for one popup never reach the next. Without `--pane` it types into whichever popup is open.
- Without a popup open, both fail with `not-found`. Watch [`status --app`](#follow-the-rest-of-the-app)'s `popup` to know when one opens. Nothing changes in the window: the popup is still there, and you can still type into it there.
- Every program that can reach the server, an agent in a pane included, can read what a popup shows and type into it, as it can for panes. See [Popups](../plugins/#popups) for what that means for a plugin.
- A server without the `popup-terminal` feature doesn't know `--popup`: it refuses `surface` and `input` with `popup` alone, but types `input --popup --pane ID` into pane `ID`, if one has that id. Check [`contract`](#contract-and-compatibility) before sending `"popup": true`.

#### Paste a file from another machine

An agent reads an image or a file from a path. When you work on another machine than the server (`cornercase remote`, the browser, a program that draws cornercase), a file on yours has no path there. `paste-file` sends it:

```sh
cornercase --remote devbox paste-file --pane 12 ~/Desktop/shot.png
pngpaste - | cornercase --remote devbox paste-file --pane 12
wl-paste --type image/png | cornercase --remote devbox paste-file --pane 12 --name error.png
```

- The command reads `FILE`, or standard input without it or with `-`, **on the machine where it runs**, also with `--remote`. It takes files up to 32 MB and refuses an empty one before it connects.
- The server keeps the bytes in a folder of its own, `pasted/` next to `session.json` (one folder per paste, `0700`; the file is `0600`), and pastes the file's path into the pane followed by a space: as a paste, bracketed when the program asked for pastes, quoted only if the path needs it. It prints the path; `--json` prints `pane`, `path` and `bytes`.
- The name there is `--name`, else the file's name, cleaned to letters, digits and `. _ + -` so the path needs no quoting (`Screenshot 2026-10-27 at 10.03.12 AM.png` becomes `Screenshot-2026-10-27-at-10.03.12-AM.png`). A name without an extension gets an image's own (`png`, `jpg`, `gif`, `webp`, `bmp` or `ico`), told by the first bytes, so `pngpaste -` gives `pasted.png`.
- A paste's folder is removed when its pane closes, and what an earlier server left in `pasted/` after 7 days.
- Like `input`, it pastes whatever the program in the pane is doing: a dialog or a question there gets the path too, and none of `send`'s safeguards apply.
- A program on the socket sends `{"command": "paste-file", "args": {"pane": 12, "name": "shot.png", "data": "<base64>"}}` and gets `pane`, `path` and `bytes` once the file is kept and the path pasted. `data` is standard base64, padding optional, line breaks ignored. It fails with `malformed` (no pane, empty `data`, not base64, over 32 MB), `not-found` (no such pane), `busy` (the program is not reading its input, or a `send` is between its paste and its Enter) or `failed` (the file could not be kept). A client that leaves before the answer gets nothing pasted. An older server refuses the request by name (`unsupported`).
- A program that types through `input --follow` should wait for `paste-file`'s answer before sending more, as the two travel on different connections and are not ordered.

#### Colours for programs

Programs in the terminals ask for the colours they are drawn with (OSC 10, 11 and 4, and the light or dark query): Claude Code, Neovim and delta pick their look from the answer. The server takes them from the first window, so a program that drives cornercase without one has to give them:

```sh
cornercase start-server --theme dark.json
cornercase theme light.json        # the system switched to light
cornercase theme - < dark.json     # read from standard input
cornercase theme                   # client colours, dark
cornercase theme --clear           # back to the window's colours, or the defaults
```

```json
{
  "foreground": [192, 202, 245],
  "background": [26, 27, 38],
  "palette": [[21, 22, 30], [247, 118, 142], [158, 206, 106], [224, 175, 104],
              [122, 162, 247], [187, 154, 247], [125, 207, 255], [169, 177, 214],
              [65, 72, 104], [247, 118, 142], [158, 206, 106], [224, 175, 104],
              [122, 162, 247], [187, 154, 247], [125, 207, 255], [192, 202, 245]]
}
```

- The foreground, the background and the 16 ANSI colours are required, as `[r, g, b]`. `palette` may go up to 256 entries; entries 16 and up are optional (absent or `null` keeps the default cube and greys). A theme that misses a part is refused (`malformed`, and `cornercase` exits 1 before connecting). Over the socket the request is `{"command": "theme", "args": {"theme": {…}}}`, `{"args": {"clear": true}}` or `{"args": {}}` to read; `start-server` takes the same object as `args.theme`.
- The answer, and `theme` in [`status --json`](#json), `status --follow` and the `start-server` answer, say where the colours come from: `{"from": "default" | "window" | "client", "scheme": "light" | "dark" | null}`.
- These colours win over a window's until you give others, clear them, or the server stops. They are not saved: after a restart give them again. A window that attaches later draws its own chrome with its own colours and leaves the terminals' alone; clearing gives the terminals the first window's colours, if one ever gave them. `start-server --theme` applies even when the server already runs. The last theme given wins.
- Every open terminal and every one made afterwards takes the new colours at once. Programs that turned on colour scheme reports (mode 2031) are told when light and dark switch. A program that read the colours once at start keeps its guess until it asks again, and a colour a program set itself (OSC 4, 10, 11) wins over these.
- [`surface`](#stream-a-tabs-terminals) frames keep palette indices: resolve them with the colours you gave, so the program's guess and your drawing agree.
- Not covered: the cursor colour, colours per view, and the TUI's own colours, which stay the window's.

#### Find where something was said

`search` answers "which pane dealt with this?" without opening tabs one by one. It looks, ignoring case, in what the coding agents in your panes were told and answered (Claude Code, Codex, Gemini CLI, opencode, Grok Build, Cursor CLI, Vibe CLI and GitHub Copilot CLI: the records `read --last-message` reads) and in the history of every pane, shells included. It is the same search as [in sessions](../search/#in-sessions) in the window, and leaves out panes of projects being closed and workspaces being removed.

```sh
cornercase search 'migration failed'
cornercase search --json checkout
pane=$(cornercase search --json 'tax bug' | jq -r '.matches[0].pane')
cornercase focus --pane "$pane" --reveal 'tax bug'
```

`--settings` also looks in the settings, as the search in the window does: `--json` adds a `settings` list with the fields of [`config search`](#settings), left out when nothing matches, and text prints them as a second table after a blank line. Without it, `search` only looks in what was said. On a server without it the command says so.

Text is one line per match under a header, separated by tabs, the way `status --panes` is. Matches come in the order of the sidebar, an agent's messages first, newest first, then the pane's history from the bottom up.

```text
pane	who	source	place	line	text
4	claude	reply	web-shop › feat/dark-mode › claude	-	The checkout tax bug is in src/checkout.rs:42, where the rate is rounded twice.
4	claude	prompt	web-shop › feat/dark-mode › claude	-	Why is the checkout tax wrong for gift cards?
9	zsh	screen	orders-api › main › zsh	118	migration failed: duplicate key value violates unique constraint
```

| Column | What it holds |
| --- | --- |
| `pane` | The pane's id, for `read`, `send`, `focus` and the other commands. |
| `who` | The agent's name, else the program in the foreground. |
| `source` | `prompt` or `reply` when it comes from an agent's record, `screen` when it comes from what the pane printed. |
| `place` | `project › workspace › tab`. |
| `line` | The line in the pane's history, for `screen` matches; `-` for an agent's messages. |
| `text` | The matching line, cut to about 160 characters around the match. |

- A `-` stands where there is no value, and a tab or a line break shows as a space, so every row is one line with the same columns. New columns only ever go at the end.
- A match of a screen that the agent's record already holds (agents print what they say) is listed once, as the agent's message.
- It lists at most 20 matches per pane and 300 in all. With `--json` `capped` says some were left out.
- No match prints the header alone and exits 0, since finding nothing is an answer. An empty search is an error.
- `--json` prints `{"matches": [...], "capped": false}`, each match with `pane`, `tab`, `workspace`, `project` (the ids), `place`, `who`, `source`, `line` (`null` when there is none), `text` and `written` (when an agent's message was written, in UTC, or `null`).
- The text you search for is never written to `server.log`.
- `focus --pane ID --reveal TEXT` goes to the pane, scrolls it to the text and selects it, as `Enter` on a result in the window does. `TEXT` is what you searched for. `--line` takes a `screen` match's `line`; leave it out for an agent's message, which takes the newest place the pane shows the text. `--json` prints `revealed`, which is `false` when the pane no longer holds the text: the pane is still shown, a warning goes to stderr and the exit status is 0. A program that reads the mouse takes the pane back to the bottom. With `--view ID` the view shows it, not the window.
- Over the socket: `{"command": "focus", "args": {"item": {"pane": 9}, "reveal": {"query": "migration failed", "line": 118}}}` answers `{"ok": {"revealed": true}}`. Check the `focus-reveal` feature first: an older server ignores `reveal` and only shows the pane.

### Create

```sh
cornercase open ~/code/orders-api                # prints the project's id
cornercase open ~/code/orders-api --into 3        # the same, in group 3
cornercase new-workspace experiments             # a workspace in the project's folder
cornercase new-workspace fix/login --worktree    # a git worktree on branch fix/login
cornercase new-workspace fix/login --worktree --fresh  # from the up-to-date default branch, fetched first
cornercase new-tab --name server -- npm run dev  # prints the new pane's id
cornercase split --down -- tail -f server.log    # splits the pane below
cornercase setup --worktree fix/login            # runs its setup again, prints the pane's id once it is done
```

- `open` finds a project that is already open instead of opening it twice. `--into GROUP` puts it in that group, as the group's **add project** does, moving it there when it is already open; a group that isn't there is refused before anything opens.
- `new-workspace` adds to the project the command runs in (`--project ID` for another one). With `--worktree`, the project must be at a repository's root, as in the [new workspace dialog](../worktrees/): the checkout goes in the worktrees folder from settings, the branch is created from `HEAD` when it does not exist, and, when the project has no setup, the command returns once git has made it. Each new workspace gets one tab, which runs the project's [setup](../worktrees/#set-up-each-new-worktree) first when it has one; `new-workspace --worktree` and `start --worktree` wait for it and answer an error naming the exit status if it fails, or saying so if its tab closes first; `status --json` shows a workspace's `setup` as `running` or `failed`. `close --remove-worktree` runs the project's teardown first; if that fails the worktree is still removed and the command prints `warning: …` on stderr.
- A branch that does not exist yet starts from the project's `HEAD`. `--fresh` (`"fresh": true` over the socket) makes it from the project's default branch, fetched from its remote first (`origin`, else the first one), as a [routine](../queue/#routines)'s runs do, and `--no-fresh` (`"fresh": false`) asks for `HEAD` whatever **settings → Worktrees → new branches** ([`fresh_branches`](../../reference/configuration/#fresh_branches)) says. Both go on `new-workspace --worktree`, `start --worktree` and `start --issue`, `flow run` and `queue add`/`edit`. A fetch that fails fails the command with git's reason (`could not fetch origin: …`) and makes nothing; a branch that already exists is checked out as it is, with no fetch. `--fresh` needs the `fresh-branches` [feature](#contract-and-compatibility), which an older server lacks and would answer by branching from `HEAD`, so the command checks it first; `--no-fresh` checks nothing.
- `new-tab` opens the tab in the workspace the command runs in (`--workspace ID` or `--worktree BRANCH` for another one). `split` splits the pane it runs in (`--pane ID` for another one), and refuses a pane too small to split.
- `setup` runs the project's [setup](../worktrees/#set-up-each-new-worktree) again in a new tab of the worktree the command runs in (`--workspace ID` or `--worktree BRANCH` for another one), as **run setup** in the workspace's menu does: with `CORNERCASE_ROOT`, `CORNERCASE_WORKTREE` and `CORNERCASE_BRANCH` set, the workspace's `setup` reads `running` and its failed mark is gone, agents started there wait for it, and the tab then becomes a shell. Typing the script into a `new-tab` does none of that. It answers as `new-workspace --worktree` does, once the setup is done however long it takes: the new pane's id, or `--json`'s ids, or status 1 and an error naming the exit status and the pane to `read`, or that its tab closed before it ended. It refuses, with status 1 and the reason (`conflict` on the socket), what the menu does not offer: a workspace that is not a worktree, a project with no setup, a setup already running. Stopping the command does not stop the setup: press `Ctrl+C` in its tab (`keys --pane N ctrl+c`) or close the tab. On the socket it is `{"command": "run-setup", "args": {"workspace": 16, "focus": false}}`, and a server without it refuses the name. A program that offers it reads `worktree` and `setup` from `status --json` and the project's `setup` from [`config`](#settings).
- After `--`, the words of a command are joined with spaces and typed at the prompt once the shell is ready, as `ssh` does with its command, so quote what the shell should read as one argument: `-- 'cargo test 2>&1 | tee test.log'`. The command returns once it is typed.
- Each prints the new pane's, workspace's or project's id, so `pane=$(cornercase new-tab …)` needs nothing else. `--json` prints every id: `{"project": 1, "workspace": 2, "tab": 8, "pane": 9}`.
- `--focus` also shows what was made.
- `--machine NAME` makes the workspace on one of your machines instead: see [Start work on a machine](#start-work-on-a-machine).

#### Import a VS Code workspace

```sh
cornercase open ~/code/work.code-workspace          # prints the group's id
cornercase open ~/code/work.code-workspace --focus  # also shows its first project
cornercase open ~/code/work.code-workspace --into 3 # into group 3
cornercase --remote devbox open '~/code/work.code-workspace' --json
```

`open` also takes a `.code-workspace` file and [imports it as the folder picker does](../projects-workspaces-tabs/#import-a-vs-code-workspace): a group named after the file (a group of that name is reused), each of its folders a project in it, in order. A folder that is already open moves into the group, a folder's `name` names a project you haven't named, and folders that are gone or on another machine are skipped. A folder named `work.code-workspace` is still a folder, and any other file is refused as before.

- The file is read on the server's machine, so with `--remote` it is the other machine's, given by its absolute path or with `~/`, quoted so that your shell leaves it alone.
- `--json` prints `{"group": 3, "name": "work", "projects": [4, 5], "missing": 1, "failed": 0}`: the group's id (`null` when nothing could be imported, since the new group is then removed), its name, the ids of the projects, in the file's order, how many folders were not found, and how many could not start a shell (`server.log` says why). A folder on another machine (a `vscode-remote://` address, a network path on Windows) is in neither count, as the picker's message leaves it out. With `--focus --view` it adds `projection`.
- It exits with 3 when a folder was not found or couldn't start its shell, or nothing was imported, after printing all that, and without `--json` says so on stderr: `warning: 1 project imported into work, 1 not found`. A folder on another machine doesn't change the status. A file that can't be read or parsed is an error, and nothing changes.
- Nothing moves in the window without `--focus`, and a folded group stays folded. `--into GROUP` imports into that group whatever its name, and the group stays even when nothing came in.
- It is the request `{"command": "open", "args": {"path": "~/code/work.code-workspace", "focus": false, "into": 3}}`, without `into` for a group of its own. Check the `open-code-workspace` [feature](#ask-the-server-first) before sending `into`, which an older server ignores and then opens the folder outside the group, or before offering these files, which it refuses as `… is not a folder`.

#### Clone a repository

```sh
cornercase clone git@github.com:acme/orders-api.git ~/code   # prints ~/code/orders-api in full
cornercase clone https://github.com/acme/orders-api          # into the current folder
cornercase --remote devbox clone git@github.com:acme/orders-api.git ~/code
```

`clone` runs `git clone` on the server's machine into a new folder inside FOLDER, named after the repository as git names it (`orders-api` for both URLs above; a `?query` or `#fragment` of the URL is left out), opens that folder as a project, as `open` does, and prints its path once git is done. Without FOLDER the clone goes in the current folder, and with `--remote` in the other machine's home folder; a FOLDER given with `--remote` is that machine's, absolute or starting with `~/`, and a FOLDER with `..` in it is refused. Folders missing on the way are made.

- A folder of that name that exists and is not empty is refused; an empty one is used. While a clone runs, another one into the same folder, or into a folder inside it or around it, is refused.
- A repository on the same machine can be given by its path: a relative one is read from the folder you run the command in. With `--remote`, give the other machine's absolute path.
- A repository named `.git` (such as `…/.git.git`) is refused, since its clone would be a `.git` folder that every git command under FOLDER would read.
- A clone that fails leaves no folder behind, the folders it made on the way included, and says what failed: the URL is not a git repository (or one you can read), access was denied, or git's own reason, such as a host it cannot reach. A folder that was there before is never removed. The messages never repeat the URL (git's own reason may name its host and path, never its user name, password, query or fragment), so a token in it stays out of them and out of the [log](../../reference/files-and-environment/).
- git never asks for a password, a passphrase or a browser login: it uses the ssh keys, ssh agent and git credentials of the server's machine as they are, and a missing one fails at once as access denied. Prefer a credential helper to a token in the URL: like `git clone`, the clone keeps its URL in `.git/config`.
- The command waits for git with no timeout, as long as the clone takes. Stopping the command does not stop the clone, and its project still opens.
- `--json` prints `{"path": "/home/ana/code/orders-api", "project": 4, "workspace": 9, "tab": 12, "pane": 13}`. `--focus` also shows the project; when the view it should show in closed while git ran, the clone is still answered, without showing it.

`--file` copies files into the new clone once git is done, such as the git-ignored `.env` a project needs to run, as the [Clone on machine dialog](../machines/#clone-the-project-there) does with the ones you tick:

```sh
cornercase clone --list-ignored --from ~/code/orders-api --json
cornercase --remote devbox clone git@github.com:acme/orders-api.git '~/code' --file .env --file web/.env.local --from ~/code/orders-api --json
```

- `--file PATH`, repeated for more, is read by the command, on the machine it runs on also with `--remote`, and sent with its permissions. `PATH` goes from the root of the repository that `--from FOLDER` is in (the current folder by default, and always a folder of this machine).
- These are refused before anything is cloned, naming the file at fault and never the URL: a path that is absolute, goes up with `..` or goes into `.git` (status 2), and a file that isn't there, a folder, a link, a file over 1 MiB, more than 200 files or more than 8 MiB in all (status 1).
- A file the clone couldn't take, such as one the repository has, isn't written and doesn't undo the clone. The command names it on standard error (`not copied: README.md (it is already in the clone)`), or `--json` lists it under `unwritten`, and it exits with status 3.
- `cornercase clone --list-ignored [--from FOLDER]` prints what the dialog offers and clones nothing: the git-ignored files in that folder, each by its path from the repository's root, without ignored folders or links, and how many more past the first 200. `--json` prints `{"root": "/home/ana/code/orders-api", "files": [{"path": ".env", "size": 42, "mode": 384, "too_big": false}], "left_out": 0}`, where `too_big` is a file `--file` refuses. It reads this machine's folder, so it needs no server, and `--remote` changes nothing for it: the files are here even when the clone goes elsewhere.
- On Windows, `--file` and `--list-ignored` say they aren't supported yet, and nothing is cloned.

It is the request `{"command": "clone", "args": {"url": "…", "parent": "~/code", "focus": false}}`; a refusal has the [code](#errors-with-a-code) `not-found` when the URL is not a repository, `conflict` when the folder is not empty, `busy` when a clone into that folder, or into one inside or around it, is already running, `malformed` for a relative folder or one with `..`, a relative path to a repository, or a URL with no usable name in it, and `failed` for the rest, access denied included. An older server answers that it has no such command. There is no button for it in the window: the one place the window clones is [on a machine](../machines/#clone-the-project-there).

`files` is what `--file` sends, for a client that reads the files itself: each has a `path` relative to the clone, its `data` in base64, and its `mode` (`420`, that is `0o644`, when left out). A path that is absolute, goes up with `..`, goes into `.git` or names a file the clone already has is not written, and more than 200 files, or more than 8 MiB in all, refuses the request as `malformed` before git runs, as bad base64 does. A file that can't be written doesn't undo the clone: the answer lists it under `unwritten`, with its `path` and `why`. The log says how many files and bytes, never their names or content. On a server running on Windows, `files` are not written yet: each one comes back in `unwritten`, saying so, and the clone itself is made.

### Start an agent

```sh
cornercase start claude --worktree fix-login --prompt 'Fix the login form, then commit'
cornercase start codex --prompt-file task.md --wait --timeout 1800
git diff | cornercase start claude --prompt-file -
cornercase start claude --worktree fix-login --placed --json
```

`start` does what **start** does in the [issue browser](../issues-and-agents/#the-launch): it opens a tab, types the agent's command with its arguments and mode from **settings → Agents**, waits for its folder trust question to be answered (by you, unless **trust prompts** is on), and once the agent is ready pastes the prompt and presses Enter. It returns then, printing the pane's id, or fails if the agent never shows up.

- **Which agent**: the one you name (`claude`, `codex`, `gemini` or any [other kind](../../reference/agents/)); without one, the default from **settings → Agents**, or, when that is *auto*, the agent running in the pane the command runs in.
- **Where**: a new tab in the workspace the command runs in; in another workspace with `--workspace ID`; or with `--worktree BRANCH`, in the workspace on that branch, made as a new worktree when there is none.
- `--name` names the tab, `--prompt` gives the prompt and `--prompt-file` reads it from a file, or from standard input with `-`. Without a prompt, the agent just starts.
- `--model` starts it with that model, through the agent's own flag (`--model opus`, `--model gpt-5.5`), replacing a model set in its arguments. `--mode` picks another of the agent's modes, as **settings → Agents** lists them (`--mode plan`), instead of the one chosen there; `--mode default` starts it with no mode arguments, only its extra arguments, whatever mode is chosen there. A mode the agent lacks is refused with the list of its modes, `default` first. `--effort` sets how hard the agent thinks, through its own switch (`--effort high` for Claude Code, `-c model_reasoning_effort=high` for Codex, `--reasoning-effort high` for Grok Build and GitHub Copilot CLI; Cursor CLI takes it in the model id), replacing an effort set in its arguments; a level the agent does not take is refused with its levels, and Gemini CLI, opencode and Cursor CLI, which have no effort switch, refuse any. A server older than these options refuses them rather than start the agent with the settings' mode, which could be one that never asks.
- `--issue KEY` starts the agent on an [issue](#issues) instead of a prompt, as the Issues dialog's **start** does: the branch is the one named after the issue (or what **settings → Worktrees → issue branches** makes of it; `--worktree BRANCH` names another), the prompt comes from **settings → Issues → prompt**, and it is always submitted, whatever **send the prompt** says there. A key such as `#482`, `sc-48` or `ENG-42`, or the issue's URL; `--source` picks the tracker when a key could be several. A GitHub or GitLab issue is worked on in the repository of `--project ID` (default: the one the command runs in, else the shown one), in a worktree on its branch; a workspace already on that branch gets a new tab with the agent. Shortcut, Linear, Jira, Plane and Asana issues aren't tied to a repository, so with several places open the command lists them and asks for `--project ID` (a new worktree) or `--workspace ID` (a new tab). The workspace is named after the issue unless `--workspace-name NAME` (the `workspace_name` field) says otherwise, and so is a tab unless `--name` does. `--workspace-name` needs a server with the `issue-names` [feature](#ask-the-server-first), which the command checks first, since an older one would ignore it.
- `--wait` then waits like [`wait`](#wait) does, and prints how it ended on a second line. `--until` with one of `wait`'s states (`idle`, `working`, `waiting`, `shell`, `turn-over`) waits for that one instead.
- `--placed` (`"placed": true` over the socket) answers as soon as the tab is open, after its worktree is made or its issue read, with the same ids, and the launch goes on, as the window's dialogs do. It is for a program that shows the new tab itself: without it, the ids wait for as long as the agent's trust question stays. The agent still gets its prompt once it is ready, even after you answer its question, but the command can no longer say that it never showed up. **`wait` and `send` only work once that launch is over, and the answer doesn't mean it is.** Until the agent runs, `wait` answers `runs no agent`; until its prompt is typed, `wait` can end on `idle`; and `send` goes to whatever reads the pane then, the shell, or the trust question, which it would answer. `status` has no field for the launch, so read the pane there: `agent` is `null` until the agent runs and reports, and `at_prompt` `true` while its shell still waits for it; `agent` with the status `idle` only says it runs, since it may still be asking its question and its prompt may not be typed; and the status `working` says it took its prompt, so the launch is over. Once `agent` is there, `wait --until working` waits for that. Without a prompt, or with an agent that reports no status, only its screen says so ([`read`](#talk-to-a-pane)). To `send` or `wait` right after `start`, leave `--placed` out: its answer then comes when the launch is over. It takes no `--wait`, `--until` or `--timeout` (over the socket, `wait` or `timeout` with it is `malformed`). An older server would ignore it and hold its answer, so check the `machine-start` [feature](#ask-the-server-first) first, as the command does; it came with `placed`.
- `--machine NAME` starts the agent on one of your machines instead, with that machine's ids, agents, accounts and trackers; it takes no `--wait`, `--until` or `--timeout`. See [Start work on a machine](#start-work-on-a-machine).

### Accounts and profiles

```sh
cornercase account add claude work --login
cornercase account login claude work --focus
cornercase account list --json
cornercase account use claude work
cornercase account rename claude --system Personal
cornercase start claude --account claude= --prompt 'fix the tests'
cornercase profile new Work claude=work codex=work
cornercase profile use Work
cornercase start claude --profile Home --prompt 'fix the tests'
```

`account` and `profile` manage the [accounts and profiles](../accounts/) agents start with. Every answer has the same shape (`--json`): the agents that take accounts, each with its variable, its accounts (name, canonical `path`, `label` when you named it, and `unshared`, the settings that stopped being links), `system_label`, `system_path` and `system_login` for the agent's own login, and `active`, its default account (left out for its own login); then the profiles with their accounts, and `profile`, the active one (`""` for none). `account use AGENT ACCOUNT` (`account-use`) makes an account that agent's default (`--system`, `""` on the wire, for its own login), the one new workspaces and requests without a pane start with, keeping the other agents' and leaving any active profile; `account rename AGENT ACCOUNT NAME` (`account-rename`) sets the name the window shows (`--system` for the agent's own login, `--clear` or `""` to remove it): a name already used by another account of that agent is a `conflict`. Both name an account by its folder, never by its name. `--account AGENT=ACCOUNT` on `start`, `new-tab`, `flow run` and `queue add|edit` (the `accounts` field, `AGENT=` for its own login) starts with that account once, over a profile; `--profile NAME` on `start`, `new-tab` and `flow run` uses a profile once without changing the active one (`--profile ''` is every agent's own login). Without `--profile`, `start` and `new-tab` run inside a pane of this server start from that pane's accounts, as `split` does, `--account` changing only the agents it names; from outside a pane, and `flow run` always, start from the default accounts. An unknown agent, account or profile fails with `not-found` before anything opens. A server without accounts, or without `account-switch` for `--account`, would ignore the field, so the command checks the server's [contract](#contract-and-compatibility) first and refuses. `profile use --system` (`profile-use` with `""`) also forgets the accounts chosen with `account use`, so every agent goes back to its own login. `status --app` gives `accounts`, each agent's default account, and [`accounts_revision`](#follow-the-rest-of-the-app), which moves when the accounts themselves change. `status --json` names a pane's `account`, and a pane's `opened` event its `accounts`. `account list --check` (the `check` field of `account-list`, behind the `account-login` [feature](#ask-the-server-first)) first asks each account whether it is logged in, with the agent's own `claude auth status` or `codex login status`, and answers once they have all replied: each account then has `login` (`state`: `signed-in`, `signed-out`, `unknown` or `failed`; `email` and `plan` when the agent gives them; `checked`, UTC). `tokens` lists the names, never the values, of the token variables set where the server runs, which win over the accounts. With `check`, `agents` lists each agent the server knows, with its `command` and `installed`, whether the server finds that command on its `PATH` (a shell in a tab may find more). A queue entry keeps its `accounts`; one whose account was removed before its time fails and says why.

`account login AGENT ACCOUNT` (`account-login-tab`: `provider`, `account`, `""` with `--system` for the agent's own login, `workspace`, `focus`) opens the tab `account add --login` opens, for an account that exists or the agent's own login, and answers the same shape with `login`, the tab's ids. An unknown account is `not-found`; an agent without accounts, or without a login command (Gemini CLI), is `malformed`. `--focus` shows the tab in the window, or with `--view ID` in that view (`--json` adds the view's `projection`), and `account add --login --focus` takes `--view` too. A server without the `account-login-tab` feature is refused up front, naming the update. Through `--remote` the tab opens on that machine.

```sh
cornercase account restart claude                 # every open claude on another account, onto the default
cornercase account restart claude personal --pane 4 --json
cornercase --remote vps account restart claude work --pane 9 --json --boot 4242-1700000000
```

`account restart AGENT [ACCOUNT]` (`account-restart`, behind the `account-restart` [feature](#ask-the-server-first)) [restarts open agents on another account](../accounts/#restart-open-agents-on-another-account), in the same pane and conversation: every pane of that agent whose account is not ACCOUNT (its default when you leave it out, `--system` or `""` for its own login), or only the panes given with `--pane` (`panes`). It answers once each agent that could restart now has its conversation in the other account's folder, with `restarted` (the panes restarting now), `waiting` (the ones that restart when their turn is over) and `skipped` (`pane` and `why`: a flow's agent, a `custom` account, a pane that already uses that account, a conversation that could not be moved). A pane given with `--pane` that is a shell at its prompt, without that agent, starts a new shell in its place and folder with that account and is listed in `restarted`; one running another program is skipped with `stop <program> first`, and one being set up or resuming with `wait for its setup` or `wait for it to resume`. Without `--pane`, shells are left alone. A pane given that does not exist is `not-found` before anything restarts, and an agent without accounts `malformed`. A server without `account-restart` would refuse the request, so the command checks the [contract](#contract-and-compatibility) first. With [`--boot BOOT`](#arrange), a server that restarted since you read the pane ids refuses with status 4 and restarts nothing. Each restart is logged in `server.log` (`agent restarted`, with how the conversation went: `linked`, `copied`, `moved` or `fresh`).

### Start a flow

```sh
cornercase flow list
cornercase flow run Quick --prompt 'Fix the login form'
cornercase flow run 'Full issue' --prompt-file issue.md --worktree fix-login --json
cornercase flow run 'Full issue' --issue ENG-42 --project 3
cornercase flow run 'Full issue' --issue '#482' --prompt-file task.md
```

`flow list` prints each [flow](../flows/), yours, the built-in ones (those you have not replaced) and the project's, in the user's [order](../flows/#choose-a-default-and-an-order) (by name for the flows not placed in it) with the default one tagged `default`, with its description, its roles with their agents, models and efforts, and what keeps it from running, if anything; files it cannot read are listed with their error. `flow run` starts one as the window's **start** does: it makes the worktree (from `--worktree`, else from the task's first words, with a short suffix when they give nothing, a default branch or a branch already taken), opens a tab per role, starts every agent without permission prompts and answers their trust questions, and starts the orchestrator last with its brief. It answers once the tabs exist, while the agents are still starting: the workspace's id, then one line per role with its pane's id and the role's name, separated by a tab. The run's [folder for its files](../flows/#the-runs-folder) is printed on stderr (`run_dir` with `--json`), and every pane of the team has it in `$CORNERCASE_RUN_DIR`. To follow a run's end, watch `run.reached` in `status --follow`; `run.close_when_merged` says the run will close its agents once merged.

```text
8
10	orchestrator
12	coder
14	reviewer
```

- A role set to `worktree = "own"` gets a [worktree of its own](../flows/#a-worktree-of-its-own) on the branch `<branch>--<role>`, made from the run's branch, with the project's setup. `--json` then adds, for each such role, its `worktree` (the folder) and `branch`; the other roles' entries have neither. The answer waits for every worktree and its setup, and a role worktree that cannot be made opens nothing.
- The task comes from `--prompt`, or from a file with `--prompt-file` (`-` reads standard input), or from an issue with `--issue KEY`, as the dialog's **start a flow** takes it: its branch (`--worktree` names another), its prompt template (`--prompt` or `--prompt-file` with `--issue` replace it with your own task and keep the issue's branch and name, behind the `flow-issue-prompt` feature, which the command checks first), the workspace named after it (`--workspace-name NAME` names it otherwise, behind the `issue-names` feature) and, for an issue that isn't tied to a repository, `--project ID` when several projects are repositories (see [Issues](#issues)).
- The flows of the project the command runs in, else the shown one, else `--project ID`, are found too. A name is looked up in yours, then the built-in flows, then the project's: yours replaces a built-in flow of its name, and a project's flow, which comes with the repository, never stands in for another of the same name; the command says so on standard error when a name is in several places. A built-in flow you deleted in [settings → Flows](../flows/#edit-flows) is refused, and keeps its name: a project's flow named like it does not run either. An unknown name lists the flows.
- It refuses before anything opens a flow with problems, an agent that is not installed, a project that is not the root of a git repository, a branch that already runs a flow, and a `--worktree` that is `main`, `master`, the project's default branch or the one its own folder is on: a flow works on a branch of its own.
- Nothing changes in the window unless you pass `--focus`, which shows the orchestrator's tab and opens the [Flow panel](../flows/#the-flow-panel). A program that draws cornercase itself adds `--view ID`: the orchestrator's tab then shows in that [view](#a-view-of-your-own) instead, `--json` adds the view's `projection`, and the window and its Flow panel stay as they are (draw your own from [`flow runs`](#follow-a-flow-run)). A server without the `flow-run-view` feature is refused up front, naming the update. With `--machine`, `--focus` takes no `--view`.
- `--close-when-merged` closes the team's agents, as [`agents close`](#close-and-reopen-a-workspaces-agents) does (and tells programs that draw cornercase, as a `flow-merged` message on `events --notices`), once the run's pull request (or merge request) has merged and none of them has worked, waited, started or been typed into for 3 minutes; a shell in one of the team's tabs keeps them open, and nothing is removed. A flow that leaves the commits is refused before anything opens, and a server without the `flow-close-when-merged` [feature](#ask-the-server-first) is refused up front, since it would start a run that never closes its agents. `--json` has `close_when_merged: true`, and the text form prints one more line on stderr naming `agents reopen --workspace ID`. With `--machine` the machine's own server does the closing, and the up-front refusal is of this server's features: a machine running an older cornercase that has not yet reported its first snapshot may drop the field and start a run that never closes its agents, which the answer shows by lacking `close_when_merged: true`. See [Close them once the pull request merges](../flows/#close-them-once-the-pull-request-merges).
- `--machine NAME` runs the flow on one of your machines instead: that machine's flow of that name, with its agents and accounts. See [Start work on a machine](#start-work-on-a-machine).

`flow export NAME` prints a flow as TOML, so `cornercase flow export Quick > quick.toml` makes a file to send, and `--json` prints its name, origin, path and text. `flow import SOURCE` (a file, `-` for standard input, an `https://` address or `OWNER/REPO` on GitHub, see [community flows](../flows/#community-flows)) adds one to yours, or to the project's with `--to project`, and prints where it went. A flow from an address or a repository, or that sets `env` or `args`, asks first, or needs `--yes` without a terminal; a name that is taken is refused unless `--replace` overwrites it or `--name` gives the new one another. A text over 256 KiB is refused. See [Share a flow](../flows/#share-a-flow).

`flow import SOURCE --check --json` previews an import without asking or saving, including with no terminal or with `-` for standard input. It sends `flow-import` with `check: true`, using the same `--to`, `--project`, `--name` and `--replace` options as the later import with `--yes`. The answer has `name`, `origin` (`user` or `project`), `path` (`null` when checking), `replaced` (whether an existing file would be overwritten), and `roles` (orchestrator first, each with `role`, `agent`, `model`, `effort`, `edits` and optional `worktree` (`own`; omitted for a shared worktree)). Optional `check` names the variables and arguments that run unattended; the CLI adds the warning about an unreviewed source when fetching from the web. Optional `note` names agents that are not installed here. These fields are also available over the socket and after an import; older servers omit `roles` and `check`, which the CLI fills from the source it already read before printing either text or JSON. Without `--json`, the preview is text on standard output. A successful check exits 0; bad text, a flow that cannot run or a name conflict exits 1. `--check` and `--yes` cannot be combined.

### Manage flows

```sh
cornercase flow list --json
cornercase flow save draft.json --check
cornercase flow delete 'Quick mine'
cornercase flow hide Quick
cornercase flow restore Quick
cornercase flow default Quick
cornercase flow order Quick 'Full issue'
```

Each verb means one thing. `flow delete NAME` deletes the file of a flow of yours or the project's (`--in yours` or `--in project` when both have the name, `--project ID`, or `--path FILE` for a file that cannot be read, as `flow list --json` gives it) and nothing else: a run already going keeps the plan it was started with. It refuses a built-in flow, which has no file, and your version of one, with the command that does what you mean (`conflict`). `flow hide NAME` is what the delete button of [settings → Flows](../flows/#edit-flows) does with a built-in flow: it hides its name, and deletes your version of it if you edited it. `flow restore NAME` brings a hidden built-in back and deletes your version of it. Both change nothing when there is nothing to do (`changed` is `false`), and name only built-in flows (`not-found` for others). None asks first, and `--json` prints `name`, `origin`, `deleted` (the file), `hidden` and `changed`.

`flow default NAME` is what **`set default`** does in [settings → Flows](../flows/#choose-a-default-and-an-order): the start dialog opens with that flow selected, as long as it can start, and `--clear` chooses none. `flow order NAME…` puts the flows in the order you name, as dragging them does; the flows left out go after, by name, and `--clear` gives name order back. Both take `--project ID` for the flows they look in, accept a name ignoring case, and change nothing when there is nothing to do (`changed` is `false`). A name no flow has is `not-found` (and so is a built-in flow that was deleted), a blank name or a name given twice is `malformed`, and a flow with problems can still be the default. `--json` prints `name` and `changed` for `flow default`, and `names` (every flow of the scope in its new order) and `changed` for `flow order`. The requests are `flow-default` (`name`, `null` to clear it, and `project`) and `flow-order` (`names` and `project`); an open Flows dialog refreshes. `flow run NAME` still needs the name: a script says what it runs.

An app with an editor of its own works on the flow as JSON. `flow list --json` gives each flow whole as `flow`: `name`, `description`, `notes`, `end` (`pull_request` or `commits`), `orchestrator` and `roles` (each with `name`, `agent`, `model`, `effort`, `args`, `env`, `edits`, `worktree` (`shared` or `own`) and `prompt`) and `stages` (`roles` and `back`, `null` or `to` counted **from 1**, as in the file and the editor, `when` and `at_most`), with `edited` for your version of a built-in. The deleted built-ins come as `hidden`, and `builtins` lists every built-in name, which stays reserved even while it is hidden. The request `flow-save` takes that same `flow`, `place` (`yours` or `project`), `project`, `path` (the file of the flow being edited, as `flow list --json` gave it, when it is renamed or moved: the old file is deleted; any other path is `not-found`) and `check`:

```json
{"command": "flow-save", "args": {"flow": {"name": "Quick mine", "description": "", "notes": "", "end": "pull_request", "orchestrator": {"name": "orchestrator", "agent": "claude", "model": null, "effort": null, "args": [], "env": {}, "edits": false, "worktree": "shared", "prompt": "Run it."}, "roles": [{"name": "coder", "agent": "claude", "model": null, "effort": null, "args": [], "env": {}, "edits": true, "worktree": "shared", "prompt": "Write it."}], "stages": [{"roles": ["coder"], "back": null}]}, "place": "yours", "path": null, "check": true}}
```

With `check` it answers `problems` (what the editor shows in red: the flow's own, then a name conflict), `own_problems` (how many of `problems`, from the first, are its own) and the `check` text (what a project's flow runs unattended: its `env` and `args`), and writes nothing; without it, it saves, answers the `path` and is refused as `malformed` while the flow has problems of its own. So an editor keeps its save available while `own_problems` is `0`: a name conflict alone, another flow of that name that runs instead, is saved and listed, as Settings › Flows does. A save answers `0` (and the conflict it now has); an older server leaves the key out. A request is `not-found` for a project that is not open and a `path` that is no flow file, and `malformed` for another place. The last write wins over an editor open on the same flow, as with a file edited by hand. The editor's form offers a role the agents whose `flows` is true in [`config --json`](#settings)'s `agents`, their `models` as suggestions and their `efforts` as the effort's choices.

`flow save FILE` sends that request from the command line, with the flow read as JSON from a file or, with `-`, from standard input (at most 1 MiB): `cornercase flow list --json | jq '.flows[0].flow' > draft.json` gives one to edit. `--to yours` or `--to project` is the `place` (by default the place of the `--path` file, else yours, so an edit never moves a flow unless you ask), and `--project ID`, `--path FILE` (taken without `.` and `..`, so it matches the path `flow list --json` gives) and `--check` are the request's. Keys left out take their defaults, so a form can send only what it has, and a key a flow does not have is refused with its place (`roles.0.promt`). It prints where the flow went and what still stops it from running; with `--check` it says whether the flow can be saved (a name conflict alone does not stop it), prints the problems and saves nothing, and exits with 0 whether or not the server finds problems (a draft the command cannot read, such as invalid JSON or a stray key, is still an error). `--json` prints the request's answer. Without `--path` it makes a new flow, so save again with the `--path` it printed: the same draft saved twice makes a second flow of that name, listed with the clash.

### Issues

```sh
cornercase issue sources
cornercase issue list --source github --assignee me
cornercase issue list --closed --json
cornercase issue read '#482'
cornercase issue people jira
cornercase start claude --issue '#482'
```

These read the trackers through the connections the server already holds, the ones the [Issues dialog](../issues-and-agents/) uses: GitHub through `gh`, the others through the tokens saved in settings or set in the environment. They change nothing at a tracker. Another program that wants the issues gets them without keeping a client for each tracker or a token of its own.

`issue sources` says, for the project (`--project ID`, default the one the command runs in, else the shown one), which trackers are connected and as whom, in the order of the dialog's tabs, then the others. Each is one of:

- `connected`, with its account and where its token comes from (`through gh`, `saved`, or `from LINEAR_API_KEY`, followed by `over the saved one` when a saved token is there too but unused). In `--json`, `from` is `gh`, `saved` or `env`, `env` names the variable, and `shadowed` is `true` when the variable hides a saved token.
- `missing`, with what is missing: `token` (connect it with `cornercase config secret SOURCE`, the token on standard input), `site` and `email` for Jira (`cornercase config set jira_site …`), `workspace` for Plane (`plane_workspace`), or `repository` (the project isn't a git repository, or for GitLab none of its remotes is on `gitlab_url`). An Asana token with several workspaces shows as `failing` until `asana_workspace` is set.
- `failing`, with the reason the last list failed (a rejected token, naming whether it was the saved one or which variable it came from, a rate limit, an Asana token that belongs to several workspaces). It is a list's failure only, and the next good list or a change to that tracker's token or settings clears it.

It ends with the places an issue that isn't tied to a repository can be worked on: a repository-root project is `a new worktree`, an open workspace of any other project `a new tab`, and the one you are in is marked.

`issue list` prints one line per issue under a header, separated by tabs (`source`, `key`, `state`, `author`, `updated_at`, `title`, `url`, `branch`, with `-` for nothing; new columns only at the end). Without `--source` it lists every connected tracker the project can use, newest first, as the dialog's All tab does. `--closed` adds closed issues, and `--assignee` and `--author` (also `--owner` and `--requester`, `--creator`, `--reporter`, the names the dialog uses) take `me`, `anyone`, a handle or, for Jira, Plane and Asana, an id from `issue people`; a handle needs `--source`, since a filter names one tracker's people. `--cached` answers from the lists the server already holds, without asking any tracker, and an empty answer then means nothing was held for those filters. A tracker that fails does not stop the others: it is named on standard error with its reason, its cached list (if there is one) is still printed, and the command exits 3 after printing the rest (see [Exit status](#exit-status)).

`issue read KEY` prints the issue's title, the dialog's info line, its URL and the branch `start` would use, then its description as Markdown and its comments. `KEY` is a key or a URL, as for `start --issue`; a URL of another repository, site or workspace than the project's is refused. `issue people SOURCE` prints whom that tracker's filters can name, one per line with the handle, name and id.

With `--json`, `sources` prints `{"project", "closed", "sources": [...], "places": [...]}`, `list` prints `{"project", "issues": [...], "sources": [{"source", "count", "cached", "account", "error"}]}`, `read` prints `{"issue", "info", "body", "comments", "prompt"}` and `people` prints `{"source", "fields", "cached", "people"}`. They are four requests, `issue-sources`, `issue-list`, `issue-read` and `issue-people`, with the same options as fields (`people` is the two filters in the order `fields` names them: `"me"`, `"anyone"` or `{"person": {"handle": "bo", "id": null}}`). A request is refused with `not-found` for an unknown project, `malformed` for an unknown source or a person without one, and `conflict` for an issue of a tracker that is not connected or that was reconnected while it was read. `start` and `flow-run` take `issue` and `source`, which an older server would ignore, so check the `issues` [feature](#ask-the-server-first) first. `flow-run` also takes `prompt` together with `issue`, in place of the template's; an older server refuses both as `malformed`, so check `flow-issue-prompt`.

### Talk to a pane

```sh
cornercase send --pane 12 --enter 'Now add tests for it'
cornercase send --pane 12 --enter --wait --timeout 900 - < next-step.md
cornercase send --pane 12 --enter --wait --until turn-over 'Run the tests'
cornercase keys --pane 12 ctrl+c
cornercase keys --pane 12 down enter
cornercase held --pane 12 --send-now
cornercase held --pane 12 --wait-turn --json
cornercase read --pane 12
cornercase read --pane 7 --lines 200
cornercase read --pane 12 --last-message
cornercase read --last-message --pane 12 --pane 15
cornercase read --last-message --pane 12 --pane 15 --json
```

- `send` pastes the text in one go, bracketed when the program asked for it, as a paste from your terminal would be. `-` reads it from standard input. `--enter` then presses Enter once the screen settles.
- With `--enter`, `send` to Claude Code, Codex, Gemini CLI, opencode, Grok Build, Cursor CLI, Vibe CLI or GitHub Copilot CLI returns once the agent has recorded the prompt in its own history (Claude Code's transcript, Codex's rollout, Gemini's session file, opencode's database, Grok Build's session, Cursor CLI's chat store), so its success means the prompt was submitted, not just typed. When the agent records nothing, it fails with `not confirmed: the prompt may not have been submitted`: read the pane before sending it again. Codex, Gemini, Grok Build, Cursor CLI, Vibe CLI and GitHub Copilot CLI keep a prompt sent while they work until they take it, so `send` returns then; `--timeout` gives up earlier, with status 1. Grok Build queues that one Enter. Pressing Enter again sends the queued prompt now and cancels the turn, which `send` does not do. A compact command (`/compact` for Claude Code, Codex and Vibe CLI) returns once the agent records the compaction, however long that takes while the agent works on it (a compaction of a long conversation can take minutes); `--timeout` bounds it. In any other program, `send --enter` returns once Enter is pressed.
- GitHub Copilot CLI's `/` and `!` lines and a lone `?` write no prompt record, so `send --enter` returns after Enter for them; `? text` is a real prompt. A prompt typed while it works is queued, and Copilot records it when it takes it, so the confirmation waits for that.
- Cursor CLI's `/` commands and `!` shell input return after Enter without a prompt confirmation too. Cursor's chat store is read from its code, not a live session, so a prompt it records in a layout cornercase cannot read fails with `not confirmed`; read the pane then.
- Gemini local slash commands, `?` help and `!` shell input return after Enter without a prompt confirmation, so they do not fail with `not confirmed`; use `read` to inspect their result. Gemini has no calibrated input-box check, so read its screen before sending into a picker or dialog.
- `--wait` then waits until the agent stops working; it fails if the agent does not start working within 10 seconds of the Enter, rather than waiting forever for an agent that never got the text. `--until` waits for another of `wait`'s states, as `start` does.
- `send` refuses a pane whose agent is `waiting` for an answer to a question or a permission prompt: whatever it typed would answer it. Answer such a prompt with `keys`, after deciding what the answer should be.
- `send` also refuses a Claude Code agent that shows a dialog, a panel or its shell mode instead of its input box: in the details of a background shell an `x` stops the shell and Enter closes the panel, and in shell mode (`!`) a prompt would run as a command. cornercase tells from the screen, and only once it has seen that agent's input box, so a Claude Code that draws it differently is never refused. Read the pane, close what is open and send again; `--force` sends anyway.
- `send` also refuses a Claude Code agent that shows its feedback survey above its input box (`How is Claude doing this session? (optional)`, then `1: Bad  2: Fine  3: Good  0: Dismiss`): one digit sent alone answers the survey instead of reaching the agent, so `send --enter 2`, the answer to a numbered question, would be lost. `cornercase keys --pane 12 0` dismisses the survey without answering it; then send again. `--force` sends anyway: a longer text hides the survey and goes to the input box, as when you type over it.
- `send` also refuses a pane whose agent is resuming its conversation after a restart (`resuming` in `status`): before the agent is back, text would land in front of the resume command or in the agent's start-up. Wait until `status` no longer shows it, or pass `--force`. `keys` is not refused.
- `send` (with or without `--enter`) and `todo send` wait while a person is typing in the pane, so your text never joins theirs and they never send half a sentence. It waits while the pane has a draft (text typed or pasted into it from a window, the browser or `cornercase input` and not yet sent with Enter or dropped with `Esc`, `Ctrl+C` or `Ctrl+U`; a draft lapses after a minute without typing, and for Claude Code as soon as its input box is empty again), while someone typed in it in the last 2 seconds, and while an earlier message to that pane has not gone out. Then it pastes, presses Enter and confirms as usual; messages held for one pane go out one at a time, in the order they came. Meanwhile a bar on the pane's bottom row says `1 message waiting from pane 40 · goes after yours`, with ` send now ` (sends it at once, as `--force`, but while the person has a draft it pastes the message after it and leaves the Enter to them, so their half-written line never goes with it, and a toast says so; a sender with `--enter` then gets an error saying the message is in their input) and ` wait turn `, which only says the person saw it: the bar stays, with the working icon and `queued: goes right after yours`, and a new held message shows ` wait turn ` again. Either way the message goes out right after the person's prompt. `status` shows `held_sends`, `held_from`, `held_queued` and `draft` for each pane. `--timeout` bounds the wait and its error says whether the pane had a draft or recent typing; `--force` sends at once. While a message sits between its paste and its Enter (at most about 3 seconds), what a window types into that pane is dropped with a toast. `keys` never waits.
- `held` is those two buttons, for a program that draws cornercase and its own bar. Give one of them. `--send-now` sends the first held message at once, as `--force` does, still after the Enter of a message sent just before it, so `held_sends` may only drop a moment later; the others keep waiting. If the person has a draft in the pane then, it pastes the message after the draft and leaves the Enter to them: nothing half written is sent, they see both and send them with Enter or edit them first. Its sender gets the usual answer, an error saying the message is in the person's input when the Enter was left to them, or the refusal when the pane can't take it then. `--wait-turn` only says the person saw it, and covers the messages held so far. Both exit 1 and say why when nothing is held in the pane (it may just have gone out), and `--send-now` also while the pane is resuming, when the window has no bar. It prints what is held now, and `--json` prints `pane`, `held_sends`, `held_from`, `held_queued` and `after_draft`, `true` when `--send-now` left the Enter to the person (check the `held-after-draft` [feature](#ask-the-server-first): an older server sends both as one line). `--pane`, `--tab` and `--view` work as for `send`. On the socket it is `{"command": "held", "args": {"pane": 12, "action": "send-now"}}`, or `"wait-turn"`.
- To draw the same bar, read each pane in `status --json`, `status --follow` or [`view`](#a-view-of-your-own), which send a line when any of these change. While `held_sends` is above 0, `held_from` is the pane that sent the first held message (`null` for a sender outside a pane; a pane since closed keeps its id, and ids last one run of the server), and `held_queued` is `true` once **wait turn** covers the newest one. The window then reads `1 message waiting from pane 40 · goes after yours`, `3 messages waiting, the first from pane 40 · goes after yours`, or without a sender `2 messages waiting · goes after yours`; and once queued `queued: goes right after yours` or `2 queued: the first goes right after yours`, with no **wait turn** button. While `draft` is `true`, **send now** puts the message after the person's line instead of sending both, so with the `held-after-draft` feature a client can say so before the click.
- `keys` presses keys, encoded the way the program in the pane asked for: `enter`, `esc`, `tab`, `backspace`, `space`, `up`, `down`, `left`, `right`, `home`, `end`, `pageup`, `pagedown`, `delete`, `insert`, `f1` to `f12`, or one character, each after any of `ctrl+`, `alt+` and `shift+` (`shift+tab`, `ctrl+c`, `alt+x`).
- A program that draws the terminals itself should type with [`input`](#drive-a-tabs-terminals) instead: it sends keys, text, pastes and mouse events to the pane you name without checking what the agent shows, which is right for a person typing and wrong for a script. Scripts and agents keep `send` and `keys`.
- `read` prints the screen as text. `--lines N` prints the last `N` lines instead, scrollback included (a pane keeps its last 10 MB of output, about 14,000 lines at 80 columns). Lines the terminal wrapped come back as one, and empty lines at the end are left out.
- A Claude Code screen may end with its feedback survey right above the input box, `● How is Claude doing this session? (optional)` and `1: Bad  2: Fine  3: Good  0: Dismiss`: that is Claude Code asking you, not something the agent wrote. `status` marks it `(survey open)`, and `keys --pane 12 0` dismisses it.
- `read --last-message` prints the last message the agent in the pane wrote, as plain text. It comes from the agent's own record, not the screen: Claude Code's transcript, Codex's rollout, Gemini's session file or opencode's database, the ones cornercase already reads for the [context line](../projects-workspaces-tabs/#how-full-the-context-is). So the message comes whole even once it scrolled off, without the input box, the status lines or a suggestion Claude Code shows in grey, and nobody has to ask an agent to write its report to a file. While the agent works it is the newest message so far, such as a note on what it is about to do; once its turn is over it is its answer. `--json` adds `written`, when the agent wrote it, and `turn_over`.
- With `--last-message`, repeat `--pane` or `--tab` to read several agents in one call, using the ids from [`status --panes`](#one-line-per-pane). Each message appears under a header with its pane id, agent, `turn_over` and `written`; unknown metadata is `unknown`. `--json` gives `{"panes": [...]}`, with the usual individual answer in each entry. Panes come first, then tabs, each in the order given, and a repeated id is read once. A failed target gets its own error block or JSON entry with `error` and the requested `pane` (or `tab`, when its pane could not be resolved). The command reads every target before exiting 3 if any failed (see [Exit status](#exit-status)); with no server it prints nothing and exits 1. One distinct target keeps the usual output exactly. Reading screens takes only one target.
- `read --last-message` fails, with status 1 and a message saying why, on a pane without Claude Code, Codex, Gemini CLI, opencode, Grok Build, Cursor CLI, Vibe CLI or GitHub Copilot CLI, before the agent has written anything, and while cornercase has not found its record: Codex writes its rollout from its first turn on, and two Codex, two Gemini with the same home, or two opencode, in the same folder can't be told apart. Read the screen then. A permission prompt or a question the agent is asking is not a message either: it is only on the screen.

### Wait

```sh
cornercase wait --pane 12 --timeout 600                        # until the agent stops working
cornercase wait --pane 12 --until waiting                      # until it needs an answer
cornercase wait --pane 12 --until turn-over                    # until its turn is over, background shells or not
cornercase wait --pane 7 --until shell                         # until the program ends
cornercase wait --pane 7 --text 'test result: (ok|FAILED)'     # until a line matches
cornercase wait --pane 7 --quiet 5                             # until it writes nothing for 5 s
```

`wait` blocks until its condition holds, then prints how it ended:

| Condition | Ends when | Prints |
| --- | --- | --- |
| *(none)* | the agent stops working: it is idle, done, failed, pending review or waiting | `idle`, `done`, `failed`, `pending` or `waiting` |
| `--until idle` | the agent is idle, done, failed or pending review | `idle`, `done`, `failed` or `pending` |
| `--until working` | the agent is working | `working` |
| `--until waiting` | the agent waits for an answer to a question or a permission prompt | `waiting` |
| `--until turn-over` | the agent's turn is over: it stops working, as with no condition, or only a background shell it started still runs (subagents still running keep it waiting) | `idle`, `done`, `failed`, `pending`, `waiting` or `shell` |
| `--until shell` | the program in the foreground ended and the shell is back, quiet (a second when cornercase never saw the program run) | `shell` |
| `--text REGEX` | a line on the screen matches, one already there included | the line |
| `--quiet SECONDS` | the pane wrote nothing for that long | `quiet` |

- The agent conditions need a recognised agent reporting [OSC 7501](../../reference/agents/#program-status-protocol), or a reader for Claude Code, Codex, Gemini CLI, opencode, Grok Build, Cursor CLI or GitHub Copilot CLI in the pane. On a pane with no agent status or supported reader, wait for `shell`, a line or quiet instead.
- A Claude Code agent that ends its turn while a shell it started in the background still runs counts as working: it wakes up when that shell ends, and may then carry on. So the plain `wait` keeps waiting, and its timeout says that only a background shell is left. `--until turn-over` ends there and prints `shell`; read the pane to see what the agent said, and stop the shell yourself if nothing should wake the agent. An agent whose own turn is over while subagents it started still run (`working (2 subagents)`) keeps the default, `--until idle` and `--until turn-over` waits waiting, since it wakes up for their results; the timeout names them. Codex, Gemini and opencode report no such state: their turn ends when they say so, whatever they left running, so for them `turn-over` ends as the plain `wait` does.
- After a prompt reached the agent (through `start`, `send --enter` or `keys … enter`), a wait for it to stop first gives the agent up to 10 seconds to take the prompt, so it doesn't end at once on an agent that hasn't started yet. If the agent shows no change in that time, the wait fails: it may have finished at once, or never got the text, and `read` tells which. If the agent was already working when the text arrived, the wait ends when it next stops. An agent that only had a background shell left counts as taking the prompt once it works again.
- Waits run in the server and don't slow it down. They end with their condition, their `--timeout` (none by default) or when you interrupt the command. A timeout exits with status 1 and says what the pane was doing. It doesn't prove that the agent missed what you sent: read the pane before sending it again.

#### Several panes at once

```sh
cornercase wait --any --pane 12 --pane 15 --tab 9 --timeout 1800   # until the first of them stops
cornercase wait --all --pane 7 --pane 8 --until shell               # until both programs end
```

Repeat `--pane` and `--tab` to wait on several panes, with `--any` or `--all` (several without either is wrong usage). The condition and the `--timeout` apply to each of them.

- `--any` returns as soon as one of them meets the condition and prints one line: the id you gave and how it ended, such as `15 idle`. When several meet it at the same moment, it prints the first in the order you gave them; wait again on the rest to hear about the others.
- `--all` returns once every one of them has met the condition, and prints one such line each, in the order you gave them (`--pane` ones first, then `--tab` ones). A pane that met the condition counts as done even if it changed again before the others caught up.
- The id on each line is the one you gave, so a `--tab` line starts with the tab's id; panes and tabs never share an id.
- A pane that closes while you wait ends as `closed` (`12 closed`) instead of failing the wait, so `--all` goes on with the others and `--any` returns it. Anything else that fails a wait on one pane (its agent exits, it doesn't take a prompt) fails the whole wait, naming the pane.
- A timeout says what each pane still being waited for is doing.
- `--json` prints `{"panes": [...]}`, one entry per line of text.

### Follow events

```sh
cornercase events                          # everything, until the server stops
cornercase events --pane 12 --pane 14      # only these panes, until they all closed
cornercase events --host --json            # also clipboard writes and bells of programs
cornercase events --notices --json         # also the notices about agents, with their tokens, and the server's other notices
cornercase events --json | while read -r event; do …; done
```

`events` keeps running and prints one line per event, as it happens, so a script that coordinates agents can react to each change, such as an agent asking for an answer or a pane closing, instead of polling `status` or waiting again after each `wait`:

```text
tab 15  opened in workspace 2
pane 14  opened in tab 15 from pane 12
pane 14  claude  none → idle
pane 14  claude  idle → working
pane 12  claude  working → waiting
pane 14  claude  working → shell
pane 7  cargo  exited
pane 7  clipboard  11 bytes
pane 7  bell  3 times
pane 14  closed
tab 15  closed
workspace 2  notice  claude needs you in web-shop › main  cc-3f2a9c-4
machine vps  notice  claude on vps needs you in web-shop › main  cc-3f2a9c-5
notify  the release build is ready
workspace 2  flow-merged  pull request merged in fix-login: 3 agents closed · ▶ on the workspace reopens them
```

| Event | When |
| --- | --- |
| `pane ID  AGENT  FROM → TO` | An agent changed state: `working`, `shell` (its turn is over, but a [background shell](#look) it started still runs), `waiting` for an answer, `pending` review, `done` while you were elsewhere, `failed`, `idle`, or `none` before it started and once it left the pane. Every recognised agent reporting OSC 7501, or Claude Code, Codex, Gemini CLI, opencode, Grok Build, Cursor CLI, Vibe CLI and GitHub Copilot CLI through their readers, as for `wait`. |
| `pane ID  PROGRAM  exited` | The program in the foreground ended and the shell is back, or another program took its place. |
| `pane ID  clipboard  N bytes` | Only with `--host`: a program wrote to the clipboard (OSC 52, such as a yank in Neovim). The text is in `--json`'s `text`, never in the line. Reads and the primary selection are not told. |
| `pane ID  bell` | Only with `--host`: a program rang the bell (a BEL character, not one that ends another escape sequence). It reads `bell  N times` when several rang. |
| `workspace ID  notice  MESSAGE  TOKEN` | Only with `--notices`: cornercase told you an agent needs you, failed or finished, as the window's toast says it, with the same rules (a second's wait, once per change, never for a tab seen in the window or in a view). `--json` has `token`, `agent`, `status`, `place`, `message` and `panes`, and `sound` (`needs-you` or `finished`), the sound the server chose for it when [**sound**](../projects-workspaces-tabs/#a-sound) is on for this agent (left out otherwise), so a program that draws cornercase plays the same sounds the window does. It says which sound was chosen, not that one played: a window in a plain `ssh` session, the browser or a machine without a player plays nothing. A notice about an agent started by another agent or by a flow has `subagent: true`, left out for the others, so a program can leave those out by itself; with [`notify_subagents`](../../reference/configuration/#notify_subagents) off there are no such notices. A `--pane` reader gets the notices naming its panes. `cornercase go TOKEN [--view ID]` does what a click on the notification does; it fails for a token the server never gave or no longer keeps (the last 64) and when the agent and its workspace are gone. Check the `notices` feature before sending `--notices`. The server's other notices have no token: see the `workspace ID  KIND  MESSAGE` row below. |
| `machine NAME  notice  MESSAGE  TOKEN` | Only with `--notices`: the same for an agent on one of your [machines](../machines/#in-your-sidebar), with the machine's name in the message. `--json` adds `machine`, and its `panes` are the machine's ids, with no `project` or `workspace` here, so a `--pane` reader never gets it. `cornercase go TOKEN` shows that workspace of the machine, as a click on its row does, in the window only: with `--view` it is refused. |
| `workspace ID  KIND  MESSAGE` | Only with `--notices`: one of the server's other notices, which have no token, as the window's toast says it. The kinds are `notify` ([`cornercase notify`](#leave-notes), naming the pane it ran in, none when run outside cornercase); `queue-started`, `queue-failed`, `queue-missed` and `queue-kept` (a [queued](#queue-work-for-later) agent or routine run that started, failed or kept its workspace, or a routine's run that missed its time, the `state` its entry now has; a one-off entry that missed its time sends none, and `queue-failed` and `queue-missed` name no pane or workspace); `setup-failed` (a [setup](../worktrees/#set-up-each-new-worktree) that failed while nobody was looking at its tab, in the window or a view); `flow-consent` (a [flow](../flows/)'s member waits for you to accept or refuse Claude Code's bypass permissions mode in its tab); and `flow-merged` (a run's agents closed once its pull request merged, as [`--close-when-merged`](#start-a-flow) asks; closing agents yourself sends none). A message about no workspace starts with its kind. `--json` has `kind` (read it as a string: a newer server adds kinds), `message`, `panes` (`[]` when it names none) and the `project` and `workspace` ids when it is about one. A `--pane` reader gets the messages naming its panes. There is no token: go there with `focus --pane` or `--workspace` (see [Arrange](#arrange)), and bring a merged run's agents back with `agents reopen --workspace ID`. A server without the `notice-messages` feature sends only the agents' notices. |
| `KIND ID  opened in PARENT` | A project, workspace, tab or pane opened. A pane started from another pane (see [Ids](#ids-and-where-commands-act)) ends with ` from pane ID`. |
| `KIND ID  closed` | A project, workspace, tab or pane closed. A pane closes when its shell exits, whatever closed it. |

- `--pane ID`, given once or more, keeps only what happens to those panes, and ends the command once they have all closed. Without it, `events` ends when the server stops (`kill-server`, a restart), with status 0. Either way it also ends, with status 0, once whatever reads it is gone, such as an `ssh` running it on another machine (see [Exit status](#exit-status)).
- `--json` prints one JSON object per line instead: `event` (`status`, `exited`, `opened`, `closed`), `time` (UTC, as in the [server's log](../../reference/command-line/#cornercase-logs)), the `project`, `workspace`, `tab` and `pane` ids it concerns, and `agent`, `from` and `to` for a `status` (`null` for no agent), `program` for `exited`, `kind` for `opened` and `closed`, and `parent` for an `opened` pane started from another pane (left out when it has none).
- `--host` is how a program that draws the panes learns what their programs ask of the terminal: a UI has no window to receive an OSC 52 write, so it puts `text` in the clipboard itself. Readers without `--host` get none of it. Bells come at most one line a second per pane, with how many rang (`count`). A server without the `host-events` feature refuses `--host`; check [`contract`](#contract-and-compatibility) before sending `"host": true`. A reader that falls behind loses these events like any other, clipboard texts included.
- It only tells what happens after it starts. Start it before what you want to follow, or read `cornercase status` once it runs, so nothing falls in between.
- cornercase looks at the program in each pane every half second while something follows events, so a program that runs for less than that may not show. To wait for one program, `wait --until shell` is exact.
- A reader that falls far behind (over a thousand events waiting for it) loses events, and gets a line such as `12 events dropped` when it catches up, so it knows to read `status` again. One that stops reading altogether is disconnected once the server has waited a second to write to it, like any client; the command then says the connection ended and exits with status 1.

### Arrange

```sh
cornercase close --tab 9
cornercase close --worktree fix/login --remove-worktree
cornercase close --worktree fix/login --remove-worktree --check
cornercase close --worktree fix/login --remove-worktree --unlock
cornercase close --agent --pane 12 --check
cornercase close --agent --pane 12
cornercase close --workspace 5 --boot 4242-1700000000
cornercase group new work
cornercase group style 12 --icon '★' --colour 99
cornercase group delete 12 --close-projects
cornercase move --project 5 --into 12
cornercase move --tab 9 --before 7
cornercase move --worktree fix/login --last
cornercase collapse --group 12
cornercase collapse --pane 12
cornercase expand --worktree fix/login
cornercase collapse --pane 12 --boot 4242-1700000000
cornercase move-pane --pane 4 --target 7 --place below
cornercase move-pane --pane 4 --target 7 --place below --boot 4242-1700000000
cornercase rename 'review #42'
cornercase rename --workspace 5 ''
cornercase rename --workspace 5 docs --boot 4242-1700000000
cornercase focus --pane 12
cornercase mark --pane 12
cornercase mark --pane 12 --reviewed
cornercase mark --pane 12 --boot 4242-1700000000
```

- `close` takes exactly one of `--pane`, `--tab`, `--workspace`, `--worktree` or `--project` and stops its shells, as its `×` would, but never asks first, not even for a project. A worktree's workspace stays listed while its worktree is on disk; `--remove-worktree` removes the worktree too and answers once it is gone. Without `--force`, a worktree with uncommitted or untracked changes is refused before anything stops; `--force` throws those changes away. A locked worktree (`git worktree lock`) is refused before anything stops, even with `--force`; the error gives the reason and the `git worktree unlock` command to run, and `--unlock` does what the dialog's **unlock and remove** does. It does not imply `--force`: changes still need it. The branch is never deleted. To remove a worktree that is not open in cornercase, or its branch too, use [`worktrees remove`](#removing-worktrees).
- `close --remove-worktree --check` only says what removing the worktree would lose, as the Remove workspace dialog does, and stops nothing: whether it has changes that are not committed, its lock with the reason and whether the process the reason names still runs, the worktrees of a flow's roles that go with it, and whether the project's teardown runs first. `--json` prints `workspace`, `path`, `branch`, `changed`, `lock` (`reason`, `path`, `role`, `pid`, `running`, or `null`), `roles` (`role`, `path`, `branch`) and `teardown`. Run it before removing a worktree you did not just make.
- `close --agent --pane ID` closes an agent as the agents section's **close agent** does, but never asks first: the agent's whole tab and the tabs of the agents it started in the same workspace, at any depth. When the agent is a member of a [flow](../flows/)'s run, its whole team closes and the run ends. Agents it started elsewhere keep running. It never removes anything from disk: a worktree and its branch stay (`close --workspace ID --remove-worktree` removes a worktree), and `--force` and `--unlock` are refused with `--agent`. It takes only `--pane` (a pane that runs no agent cornercase reads is refused with `conflict`).
- `close --agent --check` only says what closing would do, and stops nothing: `--json` prints `pane`, `agent`, `project`, `workspace`, `removes` (always `null`) and `branches` (always empty), both kept for older servers, `tabs`, `stops` and `keeps` (panes with `agent`, `project`, `workspace` and `tab`; `keeps` are the agents that keep running), `run` (the flow run that ends when its team closes), `closed` and `warning`. Without `--check`, `--json` prints the same once it is done, with `closed` true. Run the check first when you did not start the agent yourself.
- `group new NAME` creates a group with the next icon and colour, as **new group** does, and prints its id. `group style ID` sets `--icon` (one of `● ◉ ◐ ◆ ■ ▲ ▼ ★ ✦ ♥ ♣ ♠`) and `--colour` (a palette index: `1 9 208 214 3 11 2 10 6 14 4 12 99 5 13 205`); with neither it prints the group's style, and `--json` also lists both sets. `group delete ID` keeps the group's projects, outside any group; with `--close-projects` it closes them and deletes the group once their shells have stopped.
- `move` puts a group, project, workspace or tab (`--group`, `--project`, `--workspace`, `--worktree`, `--tab`) `--before` another of the same kind, or `--last` at the end of its list. A project moved before another joins that project's group; `--into GROUP` puts it after the projects of that group and `--ungroup` after the ones that have none. A workspace stays in its project and a tab in its workspace. Programs keep running, and the window keeps showing what it showed.
- `collapse` and `expand` fold or unfold a group, project or workspace (`--group`, `--project`, `--workspace`, `--worktree`), or an agent's pane (`--pane`, refused with `conflict` for a pane that runs no agent cornercase lists), whose agents then hide under it in the agents section for as long as the agent running there now keeps running, whatever it was.
- `move-pane --pane ID --target ID --place swap|left|right|above|below` swaps two panes of a tab or moves one to that side of the other, as dragging a pane with the right button does. It is refused (`conflict`) when the tab would have no room for every pane at the size it has, or when the panes are in different tabs; the moved pane becomes the tab's active one. `--json` prints the tab's new `layout`. Over the socket the requests are `group-new`, `group-style`, `group-delete`, `move`, `collapse`, `expand`, `move-pane` and `removal-check`, and `close` takes `unlock`; each change shows in the next `status --follow` snapshot.
- `rename` renames the tab it runs in, or the `--tab`, `--workspace`, `--worktree`, `--project` or `--group` you name. An empty name goes back to the default one (a group always keeps a name).
- `close`, `rename`, `mark`, `move-pane`, `collapse`, `expand`, [`account restart`](#accounts-and-profiles) and [`context`](#context) take `--boot BOOT`, the `boot` of the `status --json` you read the id in, or of a [machine's entry](#machines-workspaces) there. Ids last one run of the server, so one that restarted since refuses, with [`stale-boot`](#errors-with-a-code)'s message and [status 4](#exit-status), and nothing closes, changes, folds or unfolds, moves or restarts, and `context` starts no second `claude`; without the flag, the command acts on whatever has that id now. Comparing the `boot` yourself before sending leaves a gap, since the server can restart in that moment; here the server compares as it acts. It works in every form of these commands, `close`'s `--worktree`, `--check` and `--agent`, every form of `collapse` and `expand` (`--group`, `--project`, `--workspace`, `--worktree`, `--pane`), and `--tab` of `mark` and `context` included, and on a [line of `requests --follow`](#many-commands-through-one-process), for that line only. Any other refusal says what it says without the flag, with status 1. A server from before `boot` would ignore it and act, so it is refused first, without being sent anything else (`… would ignore --boot …`), and one older than an option of the command refuses it as `unknown-field`, where it would otherwise ignore it: restart it so it runs the version you installed.
- `focus` shows a pane, tab, workspace or project, as picking it in the [search](../search/) does. `--reveal` also scrolls a pane to a text and selects it (see [Find where something was said](#find-where-something-was-said)). `--machine NAME` picks a workspace or tab of a [machine](#machines) as the one shown instead, whose tab the window [shows from the machine](../machines/#clicking-a-machines-workspace) (see [Machines' workspaces](#machines-workspaces)).
- `mark` marks the agent in the pane it runs in, or in the `--pane` or `--tab` you name, as [pending review](../projects-workspaces-tabs/#pending-review): its tab shows a blue `●` until it is marked `--reviewed` or the agent starts working again on a new prompt or an answer, and `status` and `events` give it as `pending`. A pane without Claude Code, Codex, Gemini CLI, opencode, Grok Build, Cursor CLI, Vibe CLI or GitHub Copilot CLI is refused. An agent that ends its turn with work for you to check can run it on its own pane.

### Close and reopen a workspace's agents

```sh
cornercase agents close
cornercase agents close --worktree fix/login --check
cornercase agents close --workspace 7 --force --json
cornercase agents reopen --workspace 7
cornercase agents forget --workspace 7 --yes
```

- `agents close` closes the tabs of a workspace (the one you are in, or `--workspace` or `--worktree`) that run an agent, whole, and keeps what each needs to start again, as the window's **close agents** does. It refuses, with `conflict`, what the window would ask about: an agent that is working or waiting, one that cannot resume its conversation, or other panes in those tabs; `--force` closes anyway, and `--check` says what would close and closes nothing. It prints `closed 4 agents in workspace 7; cornercase agents reopen --workspace 7 reopens them`.
- `agents reopen` brings them back after the other tabs, a line per pane (`pane 31  claude  coder  resumes`, or `starts over`). It needs a window's size, so it is refused when no window has ever attached. Every agent's command must be on the server's `PATH`, or nothing opens (`failed`).
- `agents forget` drops them for good and ends a kept flow run, asking first on a terminal and needing `--yes` in a script.
- `--json` prints the answers: `agents-close` gives `project`, `workspace`, `tabs`, `agents` (`pane`, `tab`, `agent`, `role`, `status`, `resumes`), `stops` (the other panes that go with them), `run`, `closed` (false for a check) and `closed_agents`; `agents-reopen` gives the new `tabs`, `panes` and `run`; `agents-forget` gives `forgot` and `run`. The requests are `agents-close` (`workspace`, `check`, `force`), `agents-reopen` and `agents-forget` (`workspace`); an older server refuses them by name.
- `status --json`, `watch` and `view` carry `closed_agents` on a workspace that holds some, and `flow runs` lists a run whose agents are closed with `state: "closed"` and every role's `pane` null; a [flow run](#start-a-flow) can also close them by itself once its pull request merges. See [Close agents and reopen them later](../projects-workspaces-tabs/#close-agents-and-reopen-them-later).

### Leave notes

```sh
cornercase notify 'the release build is ready'
cornercase todo add review the login fix    # prints the item's id
cornercase todo list
cornercase todo done 3                      # checks it off, or back on
cornercase todo undone 3                    # puts a done item back among the ones to do
cornercase todo edit 3 review the login fix again
cornercase todo move 3 --before 5           # or --last
cornercase todo send 3 --pane 5             # types it into the agent and checks it off
cornercase todo rm 3                        # prints a number that restore takes
cornercase todo clear-done                  # the same, for every done item
cornercase todo restore 7
```

`todo` does what the TODO panel does. An item moves among its kind: before an item of the other kind it stops at the end of the ones to do (or becomes the first done one). `done` checks an item off or back on; `undone` only puts a done item back, and does nothing for one still to do. `rm` and `clear-done` print an `undo` number (`--json` prints the removed items with it); `restore` puts that removal back where it was. The server keeps the last 16 removals until it stops, and `clear-done` with nothing done removes nothing and prints no number. Over the socket these are the `todo` request's `edit`, `undone`, `move`, `clear-done` and `restore`, listed as the `todo-panel` [feature](#contract-and-compatibility).

`notify` shows a toast in the window and sends a [desktop notification](../projects-workspaces-tabs/#notifications) through the terminal of every open window, like the one for an agent that needs you. A program that follows `events --notices` gets it too, as a `message` of kind `notify` naming the pane the command ran in.

`todo send` types an item's text into an agent and presses Enter, exactly as [`send --enter`](#talk-to-a-pane) does: the same target (`--pane` or `--tab`, else the pane the command runs in, else the one the window shows), the same refusals (an agent waiting for an answer, resuming, showing a dialog, a panel, its shell mode or its feedback survey, a program that stopped reading; `--force` for the ones `send --force` lifts) and the same confirmation that the agent recorded the prompt. Once it did, the item is checked off and the command prints `sent todo 3 to pane 5`. A refused or unconfirmed send leaves the item pending, prints the reason and exits 1. When cornercase cannot confirm that kind of send at all (a `/` command, an agent it does not read), the text is sent and the command exits 0 with `sent todo 3 to pane 5, but cornercase cannot tell whether the agent took it, so it stays to do`; the item stays pending, and `--json` has `"unconfirmed": true`. An item edited while it is being sent is not checked off: the command prints `sent todo 3 to pane 5, but it changed while it was sent, so it stays to do` and `--json` has `"checked": false`. Only a pending item can be sent: a done one is refused until it is unchecked. The [TODO panel's `▸` button](../todo/#send-an-item-to-an-agent) does the same from the window.

### Away on Telegram or Discord

```sh
cornercase away          # agents message you on Telegram or Discord
cornercase away --off    # they stop
```

`away` turns on the away mode of every chat app paired, [Telegram](../telegram/) and [Discord](../discord/), as **`More ▴` › remote… › continue on Telegram** (or **on Discord**) does: while it is on, an agent that needs you or finishes its turn sends you its question or its last message, and what you reply goes to it, until you turn it off. It succeeds when at least one of them went away, and fails when none could, saying where to set it up. An agent can run it for you when you tell it you are leaving.

### Updates from a program

`cornercase update` checks and installs from its own process. A program that drives the server's own update flow, such as a GUI's update button, uses the requests `update-check` and `update-install`, the dialog's own check and install, whose state is the `update` of [`status --app`](#follow-the-rest-of-the-app):

```json
{"command": "update-check", "args": {}}
{"command": "update-install", "args": {}}
```

- `update-check` asks GitHub whatever `check_updates` says, and answers the `update` object when it ends. A check already running is joined. A failure is `failed` with the reason, and the release found before is kept.
- `update-install` installs the release found, and answers the `update` object when it ends, with `installed` true: restart to use it ([`restart`](#restart-without-cutting-an-agent-off) or `restart --when-idle`). It is `conflict` when there is no release (ask for `update-check` first) or when cornercase can't replace itself here (the message names the command to run). An install already running is joined, one done answers at once, and a failure is `failed` and can be asked again.
- A development build, which never looks for updates, lists both as unavailable in [`contract`](#contract-and-compatibility) and refuses them with `unavailable`.

There is no command for them: `cornercase update` does the same from a shell, and works without a server.

### Restart without cutting an agent off

An agent that coordinates others may need a newer cornercase, for a command that was just released. A plain restart would stop every agent in the middle of its turn. `--when-idle` restarts the server only once no agent is working, in the same step it sees that, so none starts a turn in between:

```sh
cornercase update --when-idle --yes --timeout 3600
cornercase restart --when-idle --yes
```

The pane the command runs in doesn't hold the restart, so an agent can run it as its last step: the restart stops it too, and its conversation [resumes](../sessions/#agents-resume-their-conversations). Until then every window says a restart is pending, with a button that cancels it. [`cornercase restart`](../../reference/command-line/#once-no-agent-is-working) has the details.


### Draw the tour

```sh
cornercase tour list --json
cornercase tour start todo --no-card
cornercase tour complete todo add
```

The `tour` request (`action`: `list`, `start`, `next`, `back`, `skip`, `end`, `complete`, `reset`, with `tour`, `step` and `card`) moves the [guided tour](../../first-steps/#the-guided-tour-and-help) and answers `{"state", "tours"}`: `state` is the `app` feed's `tour`, and `tours`, filled for `list`, holds every tour as data, so another UI draws the same steps: `id`, `title`, `docs` (its docs page), and each step's `id`, `title`, `text`, `target` (what it points at: `new-project`, `projects`, `workspaces`, `tabs`, `pane`, `agents`, `issues`, `changes`, `files`, `todo`, `search`, `settings`, `usage`, `remote`, `help` or `none`), `done` (what completes it: `{"kind": "next"}` for a step that only explains, or an action such as `project-opened`, `workspace-made`, `tab-opened`, `prompt-confirmed`, `panel` with its `panel`, `opened` with its `dialog`, `todo-added`) `offer` (`prompt`, `agents-section` or `null`) and `show` (the section the window opens for the step: `{"kind": "panel"}` with its `panel`, `issues`, `queue`, `search`, `keys`, `settings` with its `page` (`agents`, `accounts`, `flows`, `ui`, `remote`, `plugins`), `help-menu`, `remote-menu`, or `null`). `card: false` moves the tour without drawing the window's card or opening its sections. `complete` marks a step done, and moves on when it is the step on screen. A tour or step that does not exist is `not-found`, a move without a tour on screen is `conflict`.

### Plan usage

```sh
cornercase usage
cornercase usage --json
cornercase usage --cached
cornercase usage --machine all --json
```

`usage` prints what the Limits tab of the [Usage dialog](../projects-workspaces-tabs/#usage-and-stats) shows, so a script or another app can read how much of your plan is left:

```text
Claude Code · max plan  updated just now
  session (5h)   34% · resets in 2h 14m
  week           81% · resets in 3d 4h
  week · Opus    12% · resets in 3d 4h
  extra usage: 12.34 USD of 50.00 USD

Codex
  usage unavailable: codex did not answer in time
```

It asks the installed agents (Claude Code and Codex; both when neither is installed, each saying why it could not run) by running `claude` and `codex` on the server's machine, the ones [`agent_commands`](../../reference/agents/#your-own-agents) names. That sends no prompt and costs no tokens, and each agent gets at most ten seconds. A probe already running, started by the dialog or by another `usage`, is waited for rather than started again. Nothing is asked between requests: a program that polls should use `--cached`, which answers at once with the last answer and its age and asks nothing. The command needs a running server, since the probes and their last answers live there. It exits 3, after printing every agent, when one could not be asked; that agent's error says why (see [Exit status](#exit-status)).

With `--json` it prints `{"agents": [...]}`, one entry per agent with every key present (`null` when it has no value): `agent` and `title`, `loading` (a probe is running now), `read_at` (UTC) and `age` (seconds) of the last answer with numbers, `plan`, `limited` (`false` means the account has no plan limits, `null` that nothing was read yet), `limits`, `extra` (Claude Code's extra usage or Codex's credits, as text), `notice` (what the dialog shows instead of bars, such as `not signed in · run codex login`) and `error`. After a failed probe, `plan`, `limits` and the rest are from the answer before it, as old as `age` says. A limit has `label` (the dialog's text), `kind` (the agent's own name for it: Claude Code's `session`, `weekly_all` or `weekly_scoped`, or Codex's `primary` or `secondary`), `scope` (the model or bucket it applies to, `null` for the whole plan), `percent`, `severity` (`normal`, `warning` or `critical`; read it leniently) and `resets_at` (UTC, or `null`). `kind` and `scope` together name a limit from one answer to the next. With [accounts](../accounts/#plan-usage-per-account), an agent has one entry for its usual login and one per account, which adds `account` (its folder name) and `label` (the name you gave it, or `System` for the usual login); the default account's entry (the usual login's when that agent has no default account) has `active: true`. These keys are left out when there is nothing to say, so an answer without accounts is the same as before.

It is the request `{"command": "usage", "args": {"cached": false}}`. An older server answers that it has no `usage` command.

#### Every machine's limits

`--machine NAME` asks one of your [machines](../machines/#stats-and-usage-of-each-machine) instead, through your server: it prints a line with the machine's state and when it was read, then its agents as that machine gives them, with its own accounts. `--machine all` prints this computer's agents, then each machine's. It exits 3 when a machine couldn't be read, or an agent here or there couldn't be asked. With `--cached`, the machines aren't asked either: you get the last answer your server read from each.

With `--json`, a machine adds `machine`, and `all` adds `machines`, one per machine in the order of `config.json`, each with its `agents`:

```json
{"agents": [...],
 "machines": [{"name": "vps", "state": "linked", "seen": "2026-10-31T16:00:00.000Z",
   "read_at": "2026-10-31T16:04:12.000Z", "error": null, "agents": [...]}]}
```

`state` and `seen` are the link's, as [`machines`](#machines) gives them; `read_at` is when your server read that machine's answer, `null` if never; `error` is why the last try failed, or why the machine is down, or, with no `read_at`, why it was never read (`still connecting`, `its cornercase is older than this one`, `not read yet`). A machine that is down answers the numbers it gave last. With none, `--machine NAME` fails with why, while `--machine all` still answers this computer's and the other machines' agents and lists that machine with its `error` and no `agents`. An unknown name is `not-found`.

An agent whose account can be told apart has `identity`, the same text on every machine for the same account of the same provider, so another app can list an account seen on two machines once. It is a fingerprint: it holds neither the email nor the organization, though whoever knows both can check them against it. Only Claude Code gives one, for a claude.ai login; Codex, an API key, Bedrock and Vertex don't, and rows without it are never merged.

The request is `{"command": "usage", "args": {"machine": "all"}}`. [`contract`](#contract-and-compatibility) lists the feature `machine-usage`: an older server ignores `machine` and answers for this computer, so check it first, as `--machine` does.
### Recap

```sh
cornercase recap
cornercase recap yesterday --language Spanish
cornercase recap week --fresh --json
cornercase recap --dossier yesterday
```

`recap` prints the [Recap panel](../recap/)'s summary: `now` (the default), `yesterday` (the last day with agent activity) or `week`. A current result is printed at once, and a `now` that no longer matches what is open is written again; otherwise the command waits for the agent that writes it. The text starts with a line such as `yesterday · fri 31 oct · Claude Code · 14 conversations · 41k tokens · 2 h ago`, and names each conversation `project › workspace › tab` and each pull request `#212`.

- `--fresh` writes it again. `--agent`, `--account`, `--model`, `--effort` and `--language` change the settings for that run only, and write it again.
- `--dossier` prints the dossier the agent would read, with no agent run.
- Nothing to sum up prints why and exits 0. A run that fails prints the last good text, then `recap unavailable:` and the reason, and exits with 3.
- With `--json` it prints `range`, `day`, `label`, `from`, `to`, `zone`, `written_at`, `age`, `agent`, `title`, `account`, `model`, `effort`, `language`, `tokens`, `conversations`, `text`, `places`, `dossier`, `loading`, `progress`, `empty`, `error`, `outdated` and `changed`, every key present (`null` when it has no value, `false` and `[]` for the last two). `outdated` is `true` when a `now` no longer matches what is open and `changed` lists the ids of the places that changed; asking for `now` again writes it again, so you meet them after a run that failed. `text` keeps the ids (`[c3]`, `[p1]`), and `places` maps each to its project, workspace, tab, agent, conversation, the `pane` it was last seen in and that server's `boot` and, for a pull request, its number and address. Each place also has `status` (the status its conversation had when the recap was written, `open` when its pane reported none, `null` when it was closed) and `checks` (a pull request's checks then, `null` unless read from an open workspace).
- To follow a conversation's place to the pane it is in now, also after [`restart`](../../reference/command-line/#once-no-agent-is-working) or [`agents close` and `agents reopen`](#close-and-reopen-a-workspaces-agents) moved it, look in [`status --json`](#json) for the pane with the place's `agent` and `conversation`, as the panel's links do. A `null` `conversation` matches nothing, and opencode's is always `null`. A pane's `agent` can be `null` while nothing reports its state (Gemini CLI with its window title off, for one), and then its `conversation` alone names it. Without a match, try the place's `pane` while its `boot` is the one `status --json` gives, since ids start again with every start of the server, then its workspace and project by their `path`. An older server gives its panes no `conversation` key.
- It is the request `{"command": "recap", "args": {"range": "yesterday", "fresh": false, "dossier": false, "agent": null, "account": null, "model": null, "effort": null, "language": null, "zone": null}}`. A run of that range already going is waited for when the options are the same and refused with `busy` when they differ. An older server is refused by the contract feature `recap`.
- `events` reports `{"event": "recap", "state": "started" | "finished" | "failed", "range", "agent", "error"}` to every reader that did not filter by `--pane`.

### Context

```sh
cornercase context
cornercase context --pane 4 --json
cornercase context --tab 3 --cached
cornercase context --pane 4 --json --boot 4242-1700000000
```

`context` prints what the [Context dialog](../projects-workspaces-tabs/#what-fills-the-context) shows for an agent's pane, so a script can see what fills its context before it compacts. Without `--pane` or `--tab` it reads the pane it runs in; a tab means its agent's pane.

```text
Claude Code · Opus 5.5  read just now
251.9k of 1M tokens · 25%
  System prompt        2.7k    0.3%
  System tools         4.9k    0.5%
  MCP tools            8.5k    0.8%
  Memory files        19.7k    2.0%
  Messages           206.2k   20.6%
  Free space         715.1k   71.5%
not loaded: MCP tools 199.9k · System tools 19.0k
memory files:
  ~/code/web-shop/AGENTS.md  8.5k
```

For Claude Code it starts a second `claude` on the server's machine (the one [`agent_commands`](../../reference/agents/#your-own-agents) names) that loads the same conversation in the same folder, account and model. It sends no prompt and spends no tokens, starts your MCP servers a second time, turns the hooks off and waits up to 8 seconds for the MCP servers, so a read takes 3 to 10 seconds. `--cached` prints the last answer with its age and starts nothing. The other agents answer their model and percentage with a `notice`; a pane that runs no agent exits with 1.

With `--json` it prints `{"pane", "agent", "title", "model", "percent", "compacted", "loading", "read_at", "age", "breakdown", "notice", "error"}` with every key present (`null` when it has no value). `breakdown` is `null` until a read worked, then `{"model", "conversation", "total_tokens", "max_tokens", "percent", "auto_compact_at", "categories", "memory_files", "mcp_servers", "mcp_instructions", "skills", "messages"}`: `categories` are `{id, name, tokens, kind}` with `kind` one of `used`, `deferred`, `buffer` and `free` (read it as a string: a newer Claude Code may add one), `memory_files` `{path, kind, tokens}`, `mcp_servers` `{name, tools, loaded, tokens}` (the tokens of the loaded tools), `mcp_instructions` `{name, tokens}` (the server's display name, which is not always the name of `mcp_servers`), `skills` `{total, included, tokens}` and `messages` the tokens of the calls, results, attachments, assistant and user text, with the tools and attachment kinds that took the most. `conversation` is `null` when the pane had none yet and the numbers are those of a new one. When the read fails, `error` says why beside the numbers of the last good read, and the command exits with 3.

It is the request `{"command": "context", "args": {"pane": 4, "cached": false}}`. A pane that runs no agent is a `conflict` and an unknown pane `not-found`. An older server answers that it has no `context` command.

`--boot BOOT` reads only on that run of the server: one that restarted since refuses with [status 4](#exit-status) and starts nothing (see [Arrange](#arrange)).

### Pull requests

```sh
cornercase pull-request
cornercase pull-request --worktree feat/login --json
cornercase pull-request --workspace 4
```

`pull-request` prints a workspace's [pull request](../worktrees/#pull-requests-and-their-checks) (the merge request on GitLab) as its dialog shows it: its state, the rollup and every check, failed first, then pending, passed and skipped, each with its workflow (a GitLab job's stage) and the link to its job. An agent can read why its checks fail and open the failed jobs' logs with `gh run view` or `glab ci trace`:

```text
pull request #482 open, checks failing
Returns page crashes on an empty address
https://github.com/acme/web-shop/pull/482
failed   tests (ubuntu-24.04)  CI  https://github.com/acme/web-shop/actions/runs/1001/job/2001
pending  tests (macos-15)  CI  https://github.com/acme/web-shop/actions/runs/1001/job/2002
passed   lint  CI  https://github.com/acme/web-shop/actions/runs/1001/job/2003
passed   review-bot
skipped  deploy  Pages  https://github.com/acme/web-shop/actions/runs/1002/job/2004
```

From a pane it reads that pane's workspace, elsewhere the one shown; `--workspace ID` or `--worktree BRANCH` picks another. It asks gh (or glab) at once, as opening the dialog does, even while cornercase waits after a failed read, and answers when that workspace was read. A read that fails exits with 1 and says why (`gh is not logged in: run gh auth login`, `install gh, GitHub's CLI, to see them`, gh's own line). A workspace cornercase never asks about is answered at once, with exit 0 and `null`, saying why: pull requests are off in settings, it is not on a branch, its repository has no remote, or it is on the default branch. So is a branch without a pull request (`no pull request for feat/x`).

With `--json` it prints `{"workspace", "branch", "pull_request", "reason"}`, every key present. `pull_request` is the object [`status --json`](#look) gives (`number`, `title`, `url`, `state`, `checks`, `failed`, `conflicts`, `base`, `provider`, `stack`) plus `all_checks`, a list of `{"name", "workflow", "outcome", "url"}` in the dialog's order: `outcome` is `failed`, `pending`, `passed` or `skipped`, `workflow` is empty for a commit status and `url` for a check without a link. `pull_request` is `null` and `reason` says why when there is none. It is the request `{"command": "pull-request", "args": {"workspace": 4}}`, answered once gh has answered; an older server answers that it has no `pull-request` command.

### Ports

```sh
cornercase ports
cornercase ports --worktree feat/login --json
cornercase ports --all
```

`ports` lists the TCP ports a workspace's programs listen on, so an agent that just started a dev server can find its URL, and you can tell which `localhost:5173` belongs to which worktree:

```text
http://localhost:5173  127.0.0.1  node vite  pid 48211  workspace 4, pane 12
http://localhost:6006  0.0.0.0 ::  node storybook dev  pid 48390  workspace 4, agent claude in pane 9
http://localhost:3000  127.0.0.1  node next dev  pid 51007  workspace 4, cwd
```

A program belongs to a workspace when one of its panes started it (the shell, or anything started from it), or, in a workspace with a [worktree](../worktrees/) of its own, when it works inside that worktree. A plain workspace shares its folder with the others, so only its panes count. `agent claude in pane 9` means the agent in that pane, or a program it started, listens there; `cwd` means a program started elsewhere (another terminal, say) works in the worktree. Every TCP listener is listed, HTTP or not, with the URL to open: `http://localhost:PORT` when it listens on every address or on `127.0.0.1`, `http://[::1]:PORT` when only on `::1`, else the address it listens on.

From a pane it lists that pane's workspace, elsewhere the one shown; `--workspace ID` or `--worktree BRANCH` picks another, and `--all` lists every port your programs listen on, with the workspace each belongs to, or none. Nothing listening prints `nothing is listening on a port`. cornercase's own ports (such as [browser access](../phone/)) are left out.

With `--json` it prints `{"ports": [...]}`, each with every key present (`null` when it does not apply): `port`, `addresses`, `url`, `pid`, `program`, `args` (the program's command line), `project`, `workspace`, `pane`, `via` (`pane`, `agent` or `cwd`; `null` for no workspace) and `agent` (the agent's name when `via` is `agent`). It is the request `{"command": "ports", "args": {"workspace": 4, "all": false}}`, answered once the server has looked; an older server answers that it has no `ports` command.

The text shows each program with its arguments cut to 40 characters; `--json` keeps `args` whole. The [Ports dialog](../projects-workspaces-tabs/#ports-a-workspace-listens-on) in a workspace's menu shows the same list.

```sh
cornercase ports stop 5173
cornercase ports stop 3000 --pid 48211 --json
```

`ports stop PORT` stops the program of a workspace that listens on that port, as the dialog's **stop** does: it checks that the program still holds the port, sends it `SIGTERM`, waits up to three seconds for the port to be released, then sends `SIGKILL`. Only that process gets the signals, never the shell or agent that started it. It prints `stopped node (pid 48211) on port 5173`, `killed …` when it ignored `SIGTERM`, or that it is still running, and exits 1 in that last case. It refuses a port no program listens on, and one held by a program of no workspace (the ones only `--all` lists), so it never stops a program outside your workspaces. When several programs listen on the port, `--pid` says which. With `--json` it prints `{"port", "pid", "program", "outcome"}`, `outcome` being `stopped`, `killed` or `still-running`; it is the request `{"command": "stop-port", "args": {"port": 5173, "pid": null}}`.

Ports published by Docker (`docker run -p`, `docker compose up`) are held by Docker's own process, not by the `docker` command in your tab, so they belong to no workspace: on macOS they show only with `--all`, and on Linux, where Docker's proxy runs as root, not at all. A program of another user, or one in a container or another network namespace, is not seen either.

### Tunnels

```sh
cornercase tunnels
cornercase tunnel open 5173
cornercase tunnel close 5173
cornercase tunnel forget 5173
cornercase --remote devbox tunnel open 5173 --json
cornercase --remote devbox tunnel hold 5173
```

A [tunnel](../remote/#tunnel-a-port-to-your-laptop) forwards a port of the server's machine to the computer of a window opened with `cornercase remote`, and the window holds it, so these commands drive what the windows attached to that server hold. `tunnels` lists them: `5173 → localhost:5174  up`, `3000  down: Could not request local forwarding.`, `4000  opening`, `3000  closed`, with ` (window 3)` added when several windows hold tunnels (and ` (hold 9)` for a tunnel held by `tunnel hold`). With no window attached it says ``no window holds tunnels for this server: open one with `cornercase remote` from the computer that should listen``, and with windows but none open, `no tunnels`.

`tunnel open PORT` asks every attached window and waits until each says whether it came up (at most 45 seconds), printing `port 5173 is tunnelled to localhost:5174` for each. It exits 1, saying why, when no window is attached (tunnels are held by windows, never by a command) or none came up (`could not tunnel port 5173: Permission denied`). The window shows a toast, `a program tunnelled port 5173 to localhost:5174`, with a **close** button. `tunnel close PORT` closes it in every window that holds it (`closed the tunnel of port 5173`) and exits 1 when none does; the tunnel stays listed as `closed`, because windows remember their tunnels per machine. `tunnel forget PORT` removes it (`forgot the tunnel of port 5173`), with the same exit status. A port is 1 to 65535, or the command exits with status 2.

With `--json` they print `{"tunnels": [...], "windows": N}`, each tunnel with every key present: `port`, `local` (the port on the window's computer, `null` before there is one), `state` (`opening`, `up`, `down` or `closed`), `error` (ssh's last line when `down`, else `null`), `holder` (the number of the holder's connection, which keeps several holders' tunnels apart) and `kind` (`window`, or `hold` for a tunnel held by `tunnel hold`). `windows` is how many windows hold tunnels for this server. They are the requests `tunnels`, `tunnel-open`, `tunnel-close` and `tunnel-forget` (`{"port": 5173}`) and `tunnel-hold` (`{"port": 5173, "local": 5174}`); an older server answers that it has no such command.

[`status --json`](#look) has the same entries as `tunnels` (left out while there are none), and [`events`](#follow-events) sends `{"event": "tunnel", "port", "local", "state", "error", "holder"}` to a reader that did not ask for one pane, with the state `closed` once a tunnel is closed and `gone` once it is forgotten, its window leaves or its hold ends; a hold's events carry `"kind": "hold"`.

`tunnel hold PORT` is for a program with no window, such as another interface for cornercase. It needs `--remote DESTINATION` (it exits with 2 without it), because it runs on the computer that should listen: it starts its own `ssh -N -L` to that machine, waits until it is up and prints one line, `{"port": 5173, "local": 5174, "url": "http://localhost:5174"}`, then holds the tunnel until it ends. It exits 0 when it is killed (`SIGTERM`, `SIGINT` or `SIGHUP`), when what reads its output leaves, or when `tunnel close PORT` or `tunnel forget PORT` is run on the server, and 1 when `ssh` fails, before or after the tunnel was up, or the connection to the server is lost; it is not retried, and it remembers nothing. The server lists it with `kind` `hold`, and `windows` does not count it, so `tunnel open` still needs a window. Killed with `SIGKILL`, it leaves its `ssh` until the connection drops.

### Processes

```sh
cornercase processes
cornercase processes --pane 12 --json
cornercase processes --workspace 3 --interval 2000
```

`processes` lists what every pane runs, as the [Processes dialog](../projects-workspaces-tabs/#processes) does: for each pane the processes under its shell, each with its CPU and memory, then cornercase's own use and the total:

```text
pane 12  npm  98.0%  812 MB
  4200    zsh                                         0.0%      4 MB
  4210    npm run dev                                 0.1%     60 MB
  4211    └ node vite                                97.9%    740 MB
cornercase  0.8%  85 MB
total: 1 pane, 3 processes, cpu 98.8%, 897 MB
```

CPU is the share of one core over `--interval` milliseconds (100 to 10000, default 1000: the command takes that long), so it can pass `100%`. Memory is each process's footprint, the figure the tab rows show. By default it lists every pane; `--pane ID`, `--workspace ID` or `--worktree BRANCH` narrow it, and then leave cornercase's line out. The text sorts the panes by CPU, highest first; `--json` keeps the sidebar's order.

With `--json` it prints `{"interval", "total", "panes", "cornercase"}`. `total` has `cpu`, `memory`, `panes` and `processes`. Each pane has `pane`, `tab`, `workspace`, `project`, `program`, `agent`, `foreground` (the pid of its foreground program when it is not the shell), `pid` (its shell), `cpu`, `memory` and `processes`, each process with `pid`, `parent`, `name`, `args`, `started`, `cpu` and `memory`, in tree order; a figure the server cannot read is `null`. `started` is only to be passed back to `stop`. It is the request `{"command": "processes", "args": {"pane": 12, "interval": 1000}}`, answered once the server has measured; `cornercase contract` lists it.

```sh
cornercase processes stop 4211
cornercase processes stop 4211 --started 81240 --json
```

`processes stop PID` stops a program of a pane and everything it started, as the dialog's **stop** does: `SIGTERM`, up to three seconds, then `SIGKILL` to what still runs. It prints `stopped node (pid 4211) and 2 programs it started`, `killed …` when they ignored `SIGTERM`, or that something is still running, and exits 1 in that last case. It refuses with `conflict` a pane's shell (`cornercase close --pane ID` closes the pane instead), cornercase itself and any process of no pane, and with `not-found` a pid that is not running; `--started` refuses a pid that another program reused since the list. With `--json` it prints `{"pid", "program", "pane", "outcome", "processes"}`, `outcome` being `stopped`, `killed` or `still-running`; it is the request `{"command": "stop-process", "args": {"pid": 4211, "started": null}}`. Both commands work with `--remote`.

### Worktrees

```sh
cornercase worktrees list
cornercase worktrees list --project 2 --json
cornercase worktrees size --worktree feat/login
cornercase worktrees free-builds --worktree feat/login --check
cornercase worktrees free-builds --worktree feat/login
cornercase worktrees remove --path ~/.cornercase/worktrees/web-shop/feat-login --check
cornercase worktrees remove --path ~/.cornercase/worktrees/web-shop/feat-login --delete-branch
```

`worktrees list` prints every worktree on disk as the [Worktrees dialog](../worktrees/#clean-up-worktrees) lists it, in its order: the leftovers first (`prunable`, `repository gone`, `unknown to git`), then the merged ones, then the rest, the oldest first. Each shows its project and branch, its folder, when it last changed, its size with the part in build folders and, under it, what removing it would lose or stop, in the words of the dialog's confirmation:

```text
web-shop › fix/login  ~/.cornercase/worktrees/web-shop/fix-login  3 days ago  2.4 GB (2.1 GB of builds)  merged  workspace 7
  nothing uncommitted or unpushed
web-shop › feat/gift-cards  ~/.cornercase/worktrees/web-shop/feat-gift-cards  2h ago  1.1 GB (900 MB of builds)  workspace 9
  3 files changed
  2 commits not pushed
  codex running in it; they stop
3.5 GB in 2 worktrees · 2.1 GB of builds idle 7+ days
```

It covers the worktrees of the open projects and those that closed projects left in the worktrees folder; `--project ID` lists one project's (it must be at a repository's root, else it is refused). It removes nothing. Measuring walks every worktree, two at a time, which takes a while with a big `node_modules` or `target/`; `--no-sizes` answers without it. A worktree that could not be checked or measured says so, and the command exits 3 after printing the rest.

With `--json` it prints `{"worktrees": [...]}`, each with `path`, `kind` (`linked`, `prunable`, `repository-gone` or `unknown-to-git`), `project_name`, `repository`, `branch`, `project` and `workspace` (their ids when it is open in cornercase, else `null`), `last_changed` (UTC), `changed` and `unpushed` (`null` when it was not checked), `merged`, `no_commits`, `upstream_gone`, `lock` (as `close --check` gives it), `running` (the programs of its workspace), `outside` (processes working in it that cornercase did not start), `other_tabs`, `removing`, `run_role` (it goes with its flow run's workspace), `safe`, `risks`, `error`, `size` (as `worktrees size --json`, `null` with `--no-sizes`) and `size_error`. `safe` is true when removing it loses no uncommitted file and stops no program: it was checked, has no changed or untracked file and no lock, and nothing runs in it. Commits not pushed stay on its branch, so they do not make it unsafe; deleting the branch too loses them unless it is `merged` at that commit. `risks` lists what the dialog's confirmation would say, empty when nothing. It is the request `{"command": "worktrees", "args": {"project": null, "sizes": true}}`; [`cornercase contract`](#contract-and-compatibility) lists the operation `worktrees`, and an older server answers that it has no such command. To remove what it lists, see [`worktrees remove`](#removing-worktrees).

`worktrees size` measures a worktree, as the [Worktrees dialog](../worktrees/#clean-up-worktrees) does: the bytes removing it would free, and the part in build folders, the folders git ignores whose names are on the project's list (`node_modules`, `target`, `.next`, `.turbo`, `dist`, `build`, `.venv` and `__pycache__` unless `config project --builds` changed it):

```text
2.4 GB  ~/.cornercase/worktrees/web-shop/feat-login  (2.1 GB of builds)
  1.9 GB  node_modules
  180 MB  packages/web/.next
```

The target is a workspace with a worktree of its own (`--workspace ID`, `--worktree BRANCH`, or the one the command runs in), or any linked worktree by `--path`, open in cornercase or not. A plain workspace has no worktree of its own and the main checkout is not one: both are refused. A walk of a big tree takes a second or more.

`worktrees free-builds` deletes those folders and keeps the worktree, its branch, its files and its uncommitted changes. `--check` prints `would free 2.1 GB in …` and `running: node, claude`, the programs working in the worktree, and deletes nothing. Without `--force` it refuses (exit 1) while a program runs there or a build folder holds a git checkout of its own, naming them; the dialog only warns, but a script cannot read a warning, so tell the person first and pass `--force` once they agreed. A worktree being removed is refused whatever the flags, as its teardown may need those folders. The list is checked again when it deletes, so a folder git stopped ignoring is kept. A folder that could not be deleted, or was kept, is named and the command exits 3, after printing everything else.

With `--json`, `size` prints `{"path", "bytes", "builds_bytes", "builds": [{"path", "bytes"}], "nested"}` (`nested` lists git checkouts found inside build folders), and `free-builds` prints `{"path", "check", "bytes", "folders", "kept", "failed": [{"path", "error"}], "running"}`. They are the requests `{"command": "worktree-size", "args": {"workspace": 4}}` and `{"command": "free-builds", "args": {"path": "/…/feat-login", "check": true, "force": false}}`, each with `workspace` or `path` (not both); an older server answers that it has no such command. [`cornercase contract`](#contract-and-compatibility) lists the feature `build-folders`.

#### Removing worktrees

`worktrees remove --path FOLDER…` removes what the [Worktrees dialog](../worktrees/#clean-up-worktrees) removes, each worktree named by its folder as `worktrees list` prints it, open in cornercase or not. Each goes the dialog's way: an open workspace stops its programs, runs its project's teardown and goes; a closed project's worktree runs that teardown too; a `prunable` entry leaves git's list; a folder whose repository is gone or that git no longer knows is deleted.

Only a folder `worktrees list` knows is ever touched, compared by its real path. Anything else is refused for that folder, in words, and left alone: a repository's main checkout, a project's own folder, a plain folder, a folder inside a worktree, a link to any of those. A link to a listed folder removes that folder and leaves the link, but a worktree moved away with a link left where git records it is refused, since git would delete through the link: move it back or run `git worktree repair`. A folder holding another listed worktree or an open project is refused too, since that one would go with it unseen: remove the inner one first, or close the project. What the dialog cannot tick is refused as well: a worktree of a role of a live [flow](../flows/#a-worktree-of-its-own) run (it goes with the run's workspace, also when you name both), one being removed or closed, one whose build folders are being freed, also through `worktrees free-builds`, or a run's workspace when that is happening to one of its roles. So is an open workspace whose folder git no longer knows: close it, then remove the folder.

`--check` prints what the dialog's confirmation would name, stops nothing and deletes nothing:

```text
web-shop › fix/login  ~/.cornercase/worktrees/web-shop/fix-login
  nothing uncommitted or unpushed
web-shop › feat/gift-cards  ~/.cornercase/worktrees/web-shop/feat-gift-cards
  3 files changed
  2 commits not pushed
  locked: on a usb disk
  codex running in it; they stop
  1 process outside cornercase: node
  teardown runs first
  removing it takes --force and --unlock
```

Without `--check` the folders are checked again the same way before anything stops. The dialog names a risk and lets you go on, but a script cannot read a warning, so a folder at risk is refused until you say so:

- `--force` is needed when it has uncommitted files or could not be checked, when programs work in it (its workspace's, in another tab or outside cornercase), when its files are all that is left (`repository gone`, `unknown to git`), when it holds commits on no branch, or when `--delete-branch` would lose commits. Commits not pushed on a branch that stays do not need it.
- `--unlock` is needed for a locked worktree, `--force` or not, and does not imply `--force`.

`--delete-branch` deletes the branch checked out there once the worktree is gone, and a run's workspace also deletes its roles' branches. It follows the dialog's rules: never the default branch or the main checkout's, and only the branch still checked out when the removal starts, at the commit the check saw, so one switched or moved since is kept and named. A merged pull request covers a branch only at the commit it ended at: a commit made after the merge counts as lost.

The command waits until every removal has ended and prints one line per folder:

```text
removed ~/.cornercase/worktrees/web-shop/fix-login and the branch fix/login
did not remove ~/.cornercase/worktrees/web-shop/feat-gift-cards: 3 files changed, codex running in it; they stop; add --force to remove it anyway
did not remove ~/code/web-shop: it is a repository's main checkout, which is never removed
```

It exits 3, after printing the rest, when some folder was not removed, its branch was kept or could not be deleted, its teardown failed, or only git's entry went and its folder stays; with `--check`, when some folder or role cannot be removed or checked. So exit 3 does not mean the folder is still there: read its line. If the command goes away before the removals start, for example with `Ctrl+C` during the check, nothing happens; once they started they run to their end. The window shows no message, as for `close --remove-worktree`.

With `--json` it prints `{"check", "folders": [...]}`, one per `--path`, in order, each with `path` (the listed folder), `outcome` (`removed`, `failed`, `refused`, or `removable` with `--check`), `why`, `needs` (`force`, `unlock`: what removing it takes), `removed_with` (a role's run's workspace), `branches` (deleted), `kept` (branches kept, and why), `warnings` (a failed teardown, a role that stayed, a branch that could not go or, when a run's workspace failed, the roles that had already gone), `lines` and `lost` (what the confirmation names, and in red with the branch deleted, whether you asked for that or not), `unchecked` (what could not be checked, its own folder's or a role's), `teardown`, `roles` (`role`, `path`, `branch` of the worktrees that go with it) and `worktree` (the row as `worktrees list --json` gives it). It is the request `{"command": "worktrees-remove", "args": {"paths": ["/…/feat-login"], "check": false, "force": false, "unlock": false, "delete_branch": false}}`, a path there must be absolute; [`cornercase contract`](#contract-and-compatibility) lists the operation `worktrees-remove`, and an older server answers that it has no such command. It works with `--remote`, where each path is the machine's.

### Stats

```sh
cornercase stats
cornercase stats --json
cornercase stats --share
cornercase stats --machine all
cornercase stats --cached --machine all --json
```

`stats` prints the parallel-work headline, the 24 h / 7 days / total table and a text heatmap (`·░▒▓█`). With a server it includes numbers still in memory; without one it reads `stats.json`. An older server that has no stats command says to update cornercase and restart it.

`--json` prints an object with `since` (UTC), `windows` (`24h`, `7d`, `total`) and `blocks` (newest first). Each window has `agents`, `prompts`, `turns`, `agent_seconds`, `busy_seconds`, `most_at_once`, `waited_seconds`, `tokens` (`in`, `out`, `cache_read`, `cache_write`) and `by_agent` (`claude`, `codex`, `gemini`, `opencode`). Durations preserve milliseconds as fractional seconds. Busy time and most-at-once span all kinds; the per-agent counters contain starts, prompts, turns, working/waiting durations and token kinds. Every key is present, even when zero. Each block gives `agent_seconds`. `merged_pull_requests` is `null` unless the server has read your merged pull requests (see [Usage and stats](../projects-workspaces-tabs/#usage-and-stats)); otherwise it has `24h`, `7d`, `total`, `complete` (false when a count is a lower bound) and `accounts` (`provider`, `host`, `login`, `error`). The text form adds a `merged PRs` row, with a `+` after an incomplete number; a server is needed for it.

`--share` prints the same share link as Usage → Stats → share. Copy and post it yourself; anyone with the link sees the numbers on the card. See [Usage and stats](../projects-workspaces-tabs/#usage-and-stats) for the counting rules and privacy.

`--machine NAME` prints the stats of one of your [machines](../machines/#stats-and-usage-of-each-machine) instead, with a line above that says when it was read, and `--machine all` the sum of this computer's and every machine's, followed by the list of what was summed:

```text
most at once: the largest peak of one machine, not a sum
summed from:
▭ this computer
● vps   read 4 min ago
○ mini  ssh: connect to host mini port 22: Connection refused · not summed
```

The numbers add up hour by hour. `most_at_once` is the largest peak of one machine, not a sum; `busy_seconds` adds up, so it counts machine-hours; `merged_pull_requests` stays only when every machine reads the same accounts. A machine that is down is summed from the numbers it gave last: its `blocks` move on by the whole days since `read_at`, while its `24h` and `7d` count as they were read. With `--json`, a machine adds `machine` (`name`, `state`, `seen`, `read_at`, `error`, as in [Plan usage](#every-machines-limits)), and `all` adds `machines`, where a machine is in the sum when its `read_at` isn't `null`. `--machine` needs a running server, which asks the machine. It is the request `{"command": "stats", "args": {"machine": "vps"}}`, with the feature `machine-usage`.

`--cached` with `--machine` asks nothing and answers at once from the numbers your server read last, so a program can show them while it asks again: run it first, then the same without `--cached`, and show the fresh answer when it comes. The answer is the same, with `machine` or `machines` saying when each machine was read and seen, its state and any error, and a copy's `blocks` moved on by the whole days since `read_at`. Under `all`, a machine with no numbers yet is left out of the sum with the `error` `not read yet`; named alone, it fails, naming the machine and why. Without `--machine`, `--cached` changes nothing, since `stats` never waits. It is the request `{"command": "stats", "args": {"machine": "all", "cached": true}}`, with the feature `stats-cached`: an older server ignores `cached` and asks the machine, so check it first, as `--cached` does.

### Settings

```sh
cornercase config
cornercase config --json
cornercase config --json | jq -c '.agents[] | select(.flows) | .name'
cornercase config search def ag
cornercase config set sidebar tree
cornercase config set fetch_minutes 10 counts false
cornercase config set issue_tabs github,linear
cornercase config set shell /usr/bin/fish shell.args -l
printf '%s' "$LINEAR_API_KEY" | cornercase config secret linear
cornercase config remove linear
cornercase config project ~/code/web-shop --setup 'npm ci' --teardown 'rm -rf node_modules'
cornercase config project ~/code/web-shop --builds 'node_modules .next'
cornercase config pair browsers --json
```

`config` lists every setting of the [Settings dialog](../../reference/configuration/), the connections (accounts and bots), each project's setup, teardown and build folders and, with `--json`, what each agent can do. A setting that the dialog shows as a row has a `key`, the name of its `config.json` key (an agent's mode and extra arguments are `agents.claude.mode` and `agents.claude.extra`, and the issue tabs are one list, `issue_tabs`; every choice of an agent's mode, `default` included, is a value that `start --mode` and `queue add --mode` take), so a program can draw a form from the answer instead of knowing each row.

`set` takes `KEY VALUE` pairs and changes them as the dialog does: the same checks, the same live effects (browser access starts or stops, keep awake takes effect, the layout changes) and the same notices. Either every value is accepted and saved, or nothing is. On the command line the value is converted by the setting's `type`: `true` or `false` (also `on`, `off`, `yes`, `no`) for a `switch`, a whole number, a comma-separated list for `list`, otherwise text.

A token is never an argument. `secret KEY` reads it from standard input (hidden on a terminal), checks it with its service exactly as the dialog does (a tracker's token check, a bot's `getMe`), saves it and answers with the account, never the token. `remove KEY` forgets a token, a bot, a paired chat (`telegram.chat`, `discord.chat`) or the paired browsers (`browsers`). A token that comes from an environment variable cannot be replaced or removed from here, as in the dialog. Pairing a phone stays in the window: it needs its QR code.

`project` sets what a project's folder runs when a worktree is made and before one goes; `--project ID` or the folder names it, and an empty text removes the commands. Only a repository's root has worktrees, so a folder that isn't one is refused.

`search` finds settings as the [search of the Settings dialog](../../reference/configuration/#search-the-settings) does, with the same matching and order: every word must start a word of a row's label, section, tab, value or note. It prints one tab-separated row per result under a header (`place`, `key`, `value`, `note`, `-` for what is missing), or with `--json` `{"results": [...]}`, each with `title`, `page`, `section`, `label`, `key` (absent on a tab or a row with no key), `shown`, `note` and `hidden`, true for a row that does not show now, whose `note` says what it needs. No match prints the header alone and exits 0.

Over the socket, every other answer has the same shape and the request is `{"command": "config", "args": {"action": "get"}}` (or `"set"`, `"project"`, `"secret"`, `"remove"`, each with its `entry`; `"search"` takes the text as its `entry`, needs the feature `settings-search` and answers `results`):

```json
{"command": "config", "args": {"action": "set", "entry": {"fetch_minutes": 10, "sidebar": "tree"}}}
{"command": "config", "args": {"action": "project", "entry": {"path": "~/code/web-shop", "setup": "npm ci"}}}
{"command": "config", "args": {"action": "secret", "entry": {"key": "linear", "value": "lin_api_…"}}}
{"command": "config", "args": {"action": "remove", "entry": "linear"}}
```

- `settings`: for each one, `key`, `page` and `section` (where the dialog shows it), `label`, `type` (`switch`, `number`, `text`, `choice`, `list` or `key`), `value` and `default` (as JSON), `shown` (what the dialog shows as its value), `note`, `choices` (for a `choice` and the `list`: `value`, `note`, `dangerous`; for `shell`, a `text`, the shells found, offered as suggestions while any program is taken), `field` (the label of its edit field), `question` (the title of its pick), `dangerous` and `restart`. `restart` says the change only applies after a restart; none of today's settings does. `set` takes strict JSON types: `true`, a number, a string, a list of strings.
- `connections`: `key` (`shortcut`, `linear`, `jira`, `plane`, `gitlab`, `asana`, `browsers`, `telegram`, `telegram.chat`, `discord`, `discord.chat`), `kind`, `label`, `note`, `state` (`missing`, `connected` or `refused`), `account` (who it is connected as), `from` (`saved` or `env`) and `env` for a token from the environment, `count` for the paired browsers, `field` (what to paste) and `removable`. A token or a bot is set with `secret`, never through `set`.
- `projects`: `folder`, `key` (as written in `config.json`), `project` (the id of the open project in that folder), `repository`, `setup` and `teardown`.
- `agents`: each agent the default agent setting can name, in the order of its choices (`auto` aside): the agents cornercase knows, the others it can start, then your own from `agent_commands`. Each has `name`; `title`, for an agent cornercase knows (`Claude Code`), left out for the others; `reads_status`, true when cornercase reads its status by itself, so a [routine can remove its workspace when it finishes](../queue/#remove-the-workspace-when-it-finishes) (`queue add --cleanup` refuses the others) and `wait` can wait on it without OSC 7501 reports; `flows`, true when a [flow](../flows/)'s role can run it (`flow save --check` names the others as a problem); `models`, the models the flow editor offers for it, as suggestions (any other is passed on as given, except that Vibe CLI takes no model: a role's model for it is a problem, and so is `start --model`; an empty list offers none); and `efforts`, the levels `start --effort` and a role's `effort` take, empty when it has no effort switch. `reads_status` and `flows` agree today but may not later, so read each for what it says. The models opencode keeps in its own cache, which the flow editor reads when you pick it, are not listed. The text form leaves the agents out, and a server without the feature `config-agents` leaves out `agents`.

  Two of them:

  ```json
  {"name": "claude", "title": "Claude Code", "reads_status": true, "flows": true, "models": ["opus", "sonnet", "haiku"], "efforts": ["low", "medium", "high", "xhigh", "max"]}
  {"name": "amp", "reads_status": false, "flows": false, "models": [], "efforts": []}
  ```

- `revision`, `path` (the `config.json` file), `problem` (why it cannot be read, when it cannot) and `notices`: what the dialog would have said for each change made.

`revision` goes up when a setting, a project's commands or a connection changes, however it changed (the dialog, a request, or an edit of the file), and `status --json`, `status --follow` and `view` lines carry it as `config.revision`: a program that mirrors the session reads the settings again when it grows. Notes that change by themselves, such as the keep-awake state, don't move it.

A refusal has a code: `not-found` for a key that names no setting or connection, `malformed` for a value of the wrong type or one the dialog's check refuses (the message is the dialog's), `conflict` for what the current state blocks (a token set by an environment variable, Jira's site and email missing, a folder that isn't a repository, a `config.json` cornercase cannot read), and `failed` when the service refused a token. Changes made through `set` never write over a `config.json` that cannot be read.

#### Pair a phone

```sh
cornercase config set remote true
cornercase config pair browsers --json
printf '%s' "$BOT_TOKEN" | cornercase config secret telegram
cornercase config pair telegram.chat --json
cornercase config pair discord.chat
```

`config pair KEY` does what the window's dialog does, for a program that draws cornercase itself: for `browsers` what opening **`More ▴` › remote… › open in your phone's browser** does ([From your phone](../phone/)), for `telegram.chat` and `discord.chat` what `Enter` on the **phone** row does ([On Telegram](../telegram/), [On Discord](../discord/)). The keys are the ones `config remove` takes. Nothing opens in the window.

It prints what the dialog draws, and again each time that changes: with `--json`, one line of JSON each, for your program to draw the QR code from `url`. Without `--json` it prints the same for a person to read.

```json
{"url": "https://mac.tail1234.ts.net:8443/pair?t=0123456789abcdef0123456789abcdef", "lines": ["scan the code with your phone's camera.", "the phone needs the Tailscale app, logged in as ada@example.com."]}
```

`url` is `null` while there is none: while Tailscale starts, `lines` says so, and the next line has the address or, if Tailscale isn't ready (logged out, say), is the last line and says why. On Discord a new line says what to change in the Developer Portal, or a failure. On either bot, a chat that can't be saved isn't paired: a new line says why, and the phone can try again.

It stays open while it waits, and its last line, the only one with `paired`, says how it ended:

- `{"paired": true}` once a browser took the code, or `{"paired": true, "chat": "@ada"}` with the name of the chat that was paired, and status 0.
- `{"paired": false, "error": "…"}` and status 1 once nothing can pair: Tailscale is not ready, remote access was turned off, the bot was removed or its token refused, or ten minutes went by without a phone. The error also goes to standard error.

What cannot start at all prints nothing and exits with 1, with the reason on standard error: `remote access is off…`, `paste the bot's token first`, Tailscale not installed, the port taken, or a key that cannot be paired. Over the socket these are refusals with a code: `conflict` for what you can change, `unavailable` for what you can't from here (Tailscale not installed, the port taken), `malformed` for another key.

The code is dropped when the command ends, also when whoever reads its output goes, as for every command that follows a stream. A code works once, and the address holds it, so treat the line as a secret; cornercase never writes it to its log. A command or the window's dialog that holds the same key shares that code: the same address shows in all of them, its ten minutes start again with each one that comes, a phone taking it ends them all, and it is dropped when the last one goes, so closing the dialog doesn't stop a command, nor the reverse. Once paired, the window says so as it does for its own dialog, whether or not you are looking at it.

Discord has no code: the link adds the app to your account, and cornercase asks Discord for the owner while this runs or the dialog is open. With [`--remote`](../remote/#commands-for-scripts-and-agents) the address is that machine's, and the phone pairs with its cornercase.

Over the socket the request is `{"command": "config-pair", "args": {"key": "browsers"}}`, and each line above comes as `{"ok": …}` on that connection, which holds one pairing. A line of [`requests --follow`](#many-commands-through-one-process) refuses it, since it keeps a connection of its own.
#### Pick the forum's server

With [forum mode](../discord/#forum-mode) on and the app in several of your servers, the setup waits for you to pick one. Discord's row of [`status --app`](#follow-the-rest-of-the-app) says so and lists them, as the dialog does:

```json
{"platform": "discord", "ready": true, "away": false, "forum": {"on": true, "ready": false, "guild": null, "channel": null, "pending": "pick the server for the forum", "servers": [{"id": "1041234567890123457", "name": "home"}, {"id": "1041234567890123459", "name": "work"}]}}
```

```sh
cornercase config forum-server 1041234567890123459
cornercase status --app --follow | jq -c '.away[] | select(.platform == "discord") | .forum'
```

`config forum-server ID` is a click on that server in the **Discord forum** dialog: the forum channel is made there, `Discord forum ready in <server> › #cornercase` shows, and `forum` goes on to `ready`, with its `guild` and `channel`. `servers` is there only while picking is the step `pending` names, not while an earlier step is left, so whatever it lists can be picked.

It answers as soon as the pick is taken, before Discord is asked: with `--json` the server's `id` and `name`, otherwise a line saying so. A forum that cannot be made keeps trying and may never be ready, so nothing waits for it. `pending` moves on to the step that makes the channel at once: follow `status --app` until `ready` is true. What stops it, such as a permission the bot lacks, is the `note` of `discord_forum` in `config`, and if the app left that server, `pending` asks for the pick again and the list comes back.

Over the socket it is `{"command": "forum-server", "args": {"id": "1041234567890123459"}}`, and the id is text, as in `servers`: Discord's ids don't fit a JavaScript number, so a number is `malformed`. An id that isn't listed is refused with `not-found`, which names the ones that are, and a wrong moment with `conflict`, which says why: no bot, no paired phone, forum mode off, or no pick waiting, with the step left or what failed. An older server refuses the request by name, and `contract`'s `operations` lists it on one that has it; `pending` naming the pick with no `servers` also means the server is older, and only its window can pick.

#### Share your setup

```sh
cornercase config export --to team.toml
cornercase config import team.toml
cornercase config import team.toml --only agents,worktrees
cornercase config import - --yes < team.toml
cornercase config import team.toml --preview --json
```

`config export` prints the settings you can hand to a colleague, as the TOML text that ` copy my setup ` copies in the [settings](../../reference/configuration/#share-your-setup), or writes it to the file `--to` names, readable only by you. Standard error says what it left out (tokens, bots, paired chats and browsers, accounts and profiles, `jira_email`, remote access and keep awake, and each project that has no git remote) and, after a `!`, every place where a setup, an argument or a prompt looks like it holds a secret.

`config import` shows on standard error what the file would change, section by section, with the same notes as **Settings › Import**, then asks `Import these settings? [y/N]`. Reading standard input (`-`), or with no terminal to ask on, it imports only with `--yes`. `--only` takes some of the sections: `agents`, `issues`, `worktrees`, `interface` and `repositories`. Either the ticked sections are all saved, or nothing is: a file from a newer cornercase's format, a value the settings refuse or two repositories matching one project leave `config.json` as it was, and the command exits with `1` and the reason. A setting this cornercase does not know is skipped and named, not refused.

`config import --preview` prints that same preview and exits 0, without asking and without saving anything. On standard output it is the text an import shows before the question; with `--json` it is the preview a program can draw, each section's changes and notes. It works when reading standard input and when there is no terminal, so it needs no `--yes`. A file that is not a setup, a newer format, a value the settings refuse, two repositories matching one project, or a project that stopped being a repository still exits with 1 and the reason, and nothing is saved. `--preview` and `--yes` cannot be used together. Show the preview, then import the sections you want with `config import FILE --only agents,interface --yes`.

Over the socket, `config-export` answers `text`, the counts of `settings` and `repositories`, `left_out` and `warnings`. `config-import` takes the `text`, `sections` (every one when left out) and `apply`:

```json
{"command": "config-export", "args": {}}
{"command": "config-import", "args": {"text": "version = 1\n[interface]\nsidebar = \"tree\"\n", "sections": ["interface"], "apply": false}}
```

Without `apply` nothing is saved and the answer is the preview: `sections`, each with its `id`, its `changes` (`key`, `label`, `from` and `to`, as the dialog shows them; a repository's setup and teardown are a change each, `repositories.setup` and `repositories.teardown`, labelled with the project's folder and holding the whole script) and its `notes`, then the `notes` that belong to no section; each note has a `kind` (`risk`, `secret`, `missing`, `connect`, `repository` or `unknown`) and its `text`. With `apply` it saves the sections and answers as `config` does, with the `notices`. An import is refused with `malformed` for a file that is no setup, a newer format or a value the settings refuse, and `conflict` for a project that stopped being a repository or a `config.json` cornercase cannot read; a preview is refused for the same reasons, but the last, so what it shows can be imported.

### Machines

```sh
cornercase machines --json
cornercase machines add vps ana@vps.example.com --icon server
cornercase machines edit vps --folder '~/src'
cornercase machines retry
cornercase machines update mini --json
```

`machines` lists the [machines](../machines/) of **Settings › Machines**, each with the state of the link your server keeps to its server, and changes the list with the Settings tab's own checks. It needs no window. Over the socket it is one request, with an `action` and its `entry`, and every action answers the whole list:

```json
{"command": "machines", "args": {"action": "list"}}
{"command": "machines", "args": {"action": "set", "entry": {"name": "vps", "new_name": null, "icon": "server", "destination": "ana@vps.example.com", "folder": null, "create": true}}}
{"command": "machines", "args": {"action": "remove", "entry": "vps"}}
{"command": "machines", "args": {"action": "update", "entry": "mini"}}
{"command": "machines", "args": {"action": "retry", "entry": null}}
```

```json
{"here": {"icon": "▭", "version": "0.12.225"},
 "machines": [{"name": "vps", "icon": "☁", "destination": "ana@vps.example.com", "folder": "~/code",
   "state": "linked", "version": "0.12.225", "server_version": "0.12.225", "seen": "2026-10-29T10:00:00.000Z",
   "error": null, "updating": false, "problem": null}]}
```

- `state` is `connecting`, `linked`, `unreachable` or `older`. `version` is the cornercase installed there (for `older`, the old one) and `server_version` the one its server runs, which differ until that server restarts.
- `seen` is when the link was last up, as a UTC time, or `null`; `error` is why it is down (what `ssh` said, cornercase not found there, this computer, the same server as another machine, or what a failed update printed last); `updating` is `true` while an `update` runs; `problem` is what is wrong with the entry in `config.json`, which then gets no link.
- `retry_at` is when a link that fell tries next, as a UTC time in the form of `seen`, for a card that counts down like the window's `reconnecting in 4 s`. It is one moment per failed try: it stays put until that try fails, and a time that has passed means the try is under way. `retry`, this computer waking up or changing network, and an edit of a machine that is down try at once and move it to that moment. It is left out while the link is `linked` or `connecting`, and while it waits on a person: `state` says why when it is `older`, and `error` when cornercase is not found there, or it is this computer or the same server as another machine. The time is on the clock of the server that answers, as `seen` is. An older server never sends it: check the `machine-retry-at` [feature](#ask-the-server-first) before reading a machine with no `retry_at` as one that waits on a person.
- `set` takes the machine's `name` and what changes: `new_name`, `icon` (the glyph or its name), `destination` and `folder`; a new machine needs a `destination`, and gets `☁` and `~/code` unless you give them. `create` set to `true` only adds, and a name already listed is a `conflict`; `false` only edits, and an unknown name is `not-found`; `null` does either. A value the rules refuse is `malformed`, and a name or destination another machine has is a `conflict`, with the same texts as the form.
- `remove` takes the name; the machine's server keeps running there. `retry` takes a name, or `null` for every machine, and tries those links now. `retry` and `update` of a machine whose entry has a problem are `not-found`, with the problem.
- `update` takes the name of an `older` machine and answers once `cornercase update` ended there: the list, or `failed` with what it printed last. It is a `conflict` while one runs for that machine, and for a machine that isn't `older`.
- Unknown names are `not-found`. [`cornercase contract`](#contract-and-compatibility) lists the operation `machines` and the feature `machines`, and the `app` stream carries the same rows as [`machines`](#follow-the-rest-of-the-app).

#### The machines a window reached

```sh
cornercase remote --known --json
cornercase remote --remember me@10.0.0.5 --command '~/bin/cornercase'
cornercase remote --forget devbox
```

`machines` is your server's list. The machines a window on this computer reached with [`cornercase remote`](../remote/#switch-machines-from-the-window), or a program added, which its machine button offers, are another list: `remote --known` prints them, `{"machines": [{"destination": "devbox", "command": null}]}` with `--json`, in the menu's order, each with its `--command`, and `"unreached": true` until a window has connected to a machine a program added (left out otherwise). `--remember` adds a machine or replaces its `--command` (none clears it) and `--forget` takes it off, so a machine your program reached shows in the window's menu too; the window asks before its first connection there. They read and write this computer's list with no server and no `ssh`, so `CORNERCASE_REMOTE` changes nothing for them and `--remote` is refused. A destination that isn't one word, or starts with `-`, exits with 2, and forgetting a machine that isn't listed writes nothing and exits with 1. A window that is open sees the change at its next connection or forget, or when it is opened again, and a window that is on that machine writes it back, with the `--command` it reached it with, when it reconnects. Pass a machine on as `cornercase remote DESTINATION --command COMMAND`, or `--remote DESTINATION --remote-command COMMAND` for a command, leaving out the command flag when `command` is `null`.

#### Machines' workspaces

```sh
cornercase status                                  # after what is here, each machine and what it has
cornercase status --json | jq '.machines[] | {name, projects: [.projects[] | {name, repo, paired}]}'
cornercase focus --machine vps --workspace 4       # pick workspace 4 of vps as the one shown
cornercase focus --machine vps --tab 9 --json      # pick tab 9 of vps and print what is picked
```

Your server reads what each linked machine has, so `status` lists it after the projects of this computer:

```
machine vps  ☁  linked
  project 1  web-shop  /home/ana/web-shop  paired with project 3  (shown)
    workspace 2  main  /home/ana/web-shop  (shown)
      tab 5  claude  (shown)
```

- A machine's project is **paired** with a project here when both are clones of the same repository, whatever address each one was cloned with: `git@github.com:acme/web-shop.git`, `https://github.com/acme/web-shop` and an ssh alias from that machine's `~/.ssh/config` are all `github.com/acme/web-shop`, taken from the `upstream` remote, else `origin`, else the first one.
- A machine that is down keeps what it last sent, and says `unreachable · seen 2 min ago`. Paths are the machine's, in full. While a machine's workspace is picked, nothing of this computer is marked `(shown)`.
- In `status --json`, each project has `remotes` (`name`, `url`, without passwords or tokens) and `repo`, that identity, both left out when it has no remotes. `machines` has one entry per machine that has sent what it has: `name`, `icon`, `state`, `seen`, `retry_at` (as in [`machines`](#machines), so a failed try sends a line of `status --follow`), `boot` (its server's, not yours) and its `projects`, as `projects` gives yours, with `machine` on each project and workspace, `group` always `null`, and `paired`, the id of the project here it pairs with, or `null`. Its ids are the machine's own: use them with `focus --machine`, never with `--pane`, `--tab` or `--workspace` alone. `shown_remote` (`machine`, `boot`, `project`, `workspace`, `tab`, `path`) is the machine's workspace picked with `focus --machine` or a click on its row, and its `stream` says how the window's view of that tab is doing: `connecting` until the machine sends its first screen, `live`, or `down` while the machine or that connection is down. `stream` is left out while no window is open, since the tab is only streamed for a window. `status --follow` carries them too, and both are left out when there is nothing to say.
- `focus --machine NAME --workspace ID` (or `--tab ID`) picks that workspace or tab of the machine as the one shown, and with `--json` prints its `shown_remote`. The window shows it as a click on its row does, with [the machine's tab](../machines/#clicking-a-machines-workspace) in the pane area, and `status` reports it as `shown_remote` and `(shown)`. Your server doesn't pass that tab's screen on: to draw it in a UI of your own, open it on the machine with [`cornercase --remote DESTINATION`](#on-another-machine) `view`, `surface` and `input`, with the machine's `destination` from `machines` and the ids `status` gives under `machines`. It takes no `--view`, `--pane`, `--project`, `--worktree` or `--reveal`. A machine not listed, one whose entry has a problem (such as a destination another machine has), or an id it doesn't have, is `not-found`; one that has sent nothing yet is `unavailable`. Over the socket it is `{"command": "focus-machine", "args": {"machine": "vps", "item": {"workspace": 4}}}`. Check the `machine-workspaces` feature first.
- To rename, close or remove a machine's workspace, as its `×` and ` ⋯ ` do in the window, ask the machine itself with [`--remote`](#on-another-machine) and its own ids: `cornercase --remote ana@vps.example.com rename --workspace 4 docs`, `close --workspace 4`, `close --workspace 4 --remove-worktree --check` to see what removing it would lose, then `close --workspace 4 --remove-worktree` (with `--force` or `--unlock` as [Arrange](#arrange) says). Give each one the machine's `boot` from `status --json` with [`--boot`](#arrange) (over the socket, `boot` in the request), so a machine that restarted refuses ([`stale-boot`](#errors-with-a-code), status 4) instead of acting on another workspace that got the same id. The same goes for the panes of a machine's tab, by the ids its `view` lines and `surface` frames give: `mark`, `move-pane`, `account restart --pane` and `context` take `--boot` too. To fold one of its [agents](../machines/#its-agents-in-the-agents-section) as its `▾` does, send `cornercase --remote ana@vps.example.com collapse --pane 9 --boot BOOT` (or `expand --pane 9`), with the pane's id under the machine's entry: the fold is kept on the machine, so its own window shows it too.

#### Start work on a machine

```sh
cornercase start claude --issue '#482' --project 2 --machine vps --focus
cornercase new-workspace notes --project 2 --machine vps --json
cornercase flow run Quick --prompt 'Fix the login form' --project 2 --machine vps
```

`start`, `new-workspace` and `flow run` take `--machine NAME` (any case), and your server sends the request to that machine's server, which does it as if the command ran there, as the window's [`run on`](../machines/#start-work-on-a-machine) row does. Over the socket it is the `machine` field of the same requests, and of `start-with` (what `start` sends with `--model`, `--mode` or `--effort`): `{"command": "start", "args": {"agent": "claude", "project": 2, "issue": "#482", "machine": "vps"}}`.

- **The ids are the machine's**: `project` and `workspace` as `status --json` lists them under `machines` (`paired` gives the project here it pairs with), and so are the ids answered. The agent, its modes, the accounts, profiles and trackers, the flows and the prompt template are the machine's too.
- **The answer** is the machine's, with `machine` added: `{"project": 2, "workspace": 7, "tab": 11, "pane": 12, "machine": "vps"}`. `focus` selects what started in this window once the machine lists it, as a click on its row would: a flow run's orchestrator, an agent's tab, a new workspace. Picking anything else before then leaves it alone. With `focus`, a machine that hasn't sent what it has yet is `unavailable` (try again), and `--view` is `malformed`: what a machine shows is the window's.
- **Errors**: a machine not listed is `not-found`, one that isn't linked `unavailable`, with why. The machine's own refusals keep their code, and the request carries the `boot` of what the machine last sent, so one that restarted in between answers `stale-boot` and starts nothing. A machine that takes too long gives up with `failed` and `it did not answer in time`, after 10 minutes for a start, a flow or a workspace with a worktree and 15 seconds for a plain workspace; what still runs there goes on.
- **No waiting**: `wait`, `until` and `timeout` with `machine` are `malformed`. `placed` (`--placed`) goes to the machine as it is, so a start there answers once its tab is open; the window's dialogs send it, so they close while the agent there asks whether to trust the folder. Follow the agent on the machine with [`cornercase --remote DESTINATION wait`](#on-another-machine) and its ids, but after `placed` only once the launch there is over, as [Start an agent](#start-an-agent) says: `wait` and `send` before then fail or reach the wrong place. `status --json` here lists that pane under `machines`, and its status turns `working` when the agent has taken its prompt.
- An older server would ignore `machine` and start the work on this computer, so check the `machine-start` [feature](#ask-the-server-first) first, as the command does.

### Plugins

```sh
cornercase plugin status
cornercase plugin status --json
cornercase plugin actions
cornercase plugin actions --context pane --json
cornercase plugin run acme.notes note --pane 5
cornercase plugin run acme.notes note --worktree feat/x
cornercase plugin run acme.notes browse
cornercase plugin popup-close
cornercase plugin windows --json
cornercase plugin install acme/notes --preview --json
cornercase plugin install acme/notes --commit "$commit" --yes
cornercase plugin update acme.notes --preview --json
```

`plugin status` prints what Settings › Plugins shows, asking the running server. The text gives the revision, then each plugin's state (`on`, `off` or `cannot-run`), its label and note, and each service (`running` with its pid, `stopped` with the seconds until it starts again, or `starting`). With no plugin it says so. When `plugins.json` cannot be read it prints why, instead of an empty list. `--json` prints the `plugin-list` answer, with hidden characters escaped as in `plugin list --json`. `plugin list` still reads the files and works with no server, and has no service states.

`plugin actions` lists what the plugins you turned on add to the menus, in the order the menus show them (your plugins in the order of `plugins.json`, then each manifest's actions), for one kind of row (`--context project`, `workspace`, `tab` or `pane`), for the plugins' buttons (`--context button`) or all of them. The text is a tab-separated table under a header, `plugin`, `action`, `contexts`, `title`, so `cut` and `awk` can read it.

`plugin run` runs one on what you name (`--pane`, `--tab`, `--workspace`, `--worktree` or `--project`) the way its menu entry does: in the workspace's folder (the project's for a project), with the ids of what you named in the environment, stopped after 5 minutes, its output in the plugin's log. It waits for the action, prints how it ended and exits with 1 when it failed. Nothing changes in the window: no toast, no focus. A workspace being removed or closing, and a project closing, are refused, since the action would run in a folder being deleted.

An action offered on its plugin's [button](../plugins/#a-button-of-its-own) runs without naming anything, as the button does: on what the window shows, in its workspace's folder, with `CORNERCASE_CONTEXT=button`. Any other action needs a target. A [popup](../plugins/#popups) action opens its popup in the window and `plugin run` waits until it closes, then prints how its program ended; with no window attached it fails (`no window is attached`), since nobody could see it. While a dialog or another popup is open in the window it fails at once with `conflict` (`a dialog is open in the window`, `a popup is already open`), so it never replaces what you are doing there. `plugin popup-close` closes the open popup as its `×` does, and fails with `not-found` when none is open.

A program that draws cornercase itself adds `--view ID` (a [view of its own](#a-view-of-your-own)):

- A `button` action with no target runs on what that view shows, wherever the window is: `CORNERCASE_CONTEXT=button`, the view's ids and its workspace's folder (the project's with no workspace open, your home folder with no project). `--pane`, `--tab`, `--workspace`, `--worktree` or `--project` still say what it runs on, for the actions offered there, and any other action still needs one.
- A popup action opens as long as that view lives, with no window attached too, so someone who only uses that program can open one. While no window is attached its size comes from the view, and follows `view-set`; a view without a size opens it at `width`×`height`, or 80×24. A window that attaches sizes it as usual, and the view takes over again when the last window leaves. Your program draws it and types into it with [`surface --popup` and `input --popup`](#a-plugins-popup), and it is still one popup for everybody: a window shows it too, and a dialog or another popup makes it fail with `conflict`.
- If the view goes away, the popup stays open at the size it has, as it does when the last window leaves, and `plugin run` goes on waiting. A program that comes back finds it in [`status --app`](#follow-the-rest-of-the-app)'s `popup`, then shows it again or closes it with `plugin popup-close`, since no other popup opens until then.
- A view that closed is `not-found`, a server without `plugin-run-view` is refused up front, naming the update, and without `--view` nothing changes.

A program that installs or updates a plugin for the user shows the preview itself and confirms the exact commit: `plugin install SOURCE --preview --json` fetches the plugin, installs nothing, asks nothing and needs no terminal, and prints one object with `id`, `name`, `version`, `description`, `repo`, `url`, `ref` and `subdir` (the same keys `plugin list --json` has in `source`, `null` when absent), the full `commit`, `permissions`, `download` (`url` and `sha256` for this machine, or `null`), `build` (the argv of each build step, empty when a download applies), `runs` (what it runs once on, in the preview's order: `entry` is `service`, `window`, `action` with `title` and `contexts`, or `hook` with `on`, each with its `command`), `replacing` (`null` for a new plugin, else the installed `commit` and whether it is `enabled`) and `lines`, the lines the terminal preview prints. Progress (`fetching …`) goes to standard error. Once the user approves, `plugin install SOURCE --commit COMMIT --yes` installs only if the source still gives that commit; otherwise it exits 1 and installs nothing. Unlike `SOURCE@COMMIT`, which pins the plugin there for good, the plugin keeps following its branch or tag. `plugin update ID --preview --json` (an ID is required with `--json`) prints the same object plus `"up_to_date": false`, or only `{"id", "commit", "up_to_date": true}` when nothing changed, and `plugin update ID --commit COMMIT --yes` updates to exactly that commit. A preview exits 0; a refusal (an unknown ref, a plugin linked or installed from another address, a commit that changed) exits 1 with the reason on standard error; a wrong combination of options (`--preview` with `--yes` or `--commit`, `--json` without `--preview`) exits 2.

Actions are named by plugin id and action id, and listed with a `revision` that goes up each time the plugins change (counted from the server's start, so send `boot` too). `plugin run` refuses a revision the plugins moved past, `conflict`, as a menu opened before the change does nothing, so an action whose command or contexts changed since you listed it never runs by surprise. Left out, `--revision` is the current one, which `plugin actions --json` also prints.

The requests behind them are `plugin-list`, `plugin-actions` and `plugin-run`. `{"command": "plugin-actions", "args": {"context": "pane"}}` answers `revision` and `actions` (`plugin`, `name`, `action`, `title`, `contexts`, `placement`, `job` or `popup`, and for a popup `width` and `height` when the manifest gives them; `context` may be `button`). `{"command": "plugin-run", "args": {"plugin": "acme.notes", "action": "note", "revision": 3, "item": {"pane": 5}}}` takes every field, the `item` as `close` and `focus` do (left out for a `button` action, to run it on what the window shows, or on what a view shows with `"view": 21` beside `command`, as for the other requests that take one), and answers when the action ends (for a popup, when it closes):

```json
{"plugin": "acme.notes", "action": "note", "context": "pane", "project": 1, "workspace": 2, "tab": 3, "pane": 5,
 "ended": "exited", "code": 0, "signal": null, "error": null, "ms": 41, "log": "/…/plugins/state/acme.notes/plugin.log"}
```

`ended` is `exited` (with `code`), `signal` (with `signal`), `timeout` or `error` (it could not start), and for a popup `closed` (its `×` or `plugin popup-close` closed it first); a popup's program ended by a signal has `signal` `null` and the signal's name in `error`. `error` is `null` exactly when it exited with 0, so `plugin run` exits with 1 for a popup closed by hand. An action that ran and failed is an answer, not a refusal. A group, or an action run on a kind of row it isn't offered for, is `malformed`; a plugin that is unknown, off or cannot run, an action it lacks, or an id that names nothing is `not-found`. A client that leaves before the action ends gets no answer, and the action runs to its end.

`plugin status --json` prints this answer with those same escapes. `plugin-list` answers what Settings › Plugins shows: `revision`, `problem` (why `plugins.json` cannot be read, or `null`) and `plugins`, one row per plugin with `id`, `enabled`, `state` (`on`, `off` or `cannot-run`), `error`, Settings' `label` and `note`, `source`, `log`, `manifest`, `services` and `button`, there only for a plugin with a button (`title`, `icon` and `actions`, the ids of its `button` actions in order). A service is `running` (with its `pid`), `stopped` (with `restart_in`, the seconds until it starts again) or `starting`. Processes a plugin keeps running in each local window belong to those windows, so the server can't tell; a program that keeps them running itself reads their state from [`plugin windows`](#window-processes-beside-your-own-window). Turning plugins on and off, installing and updating stay with `cornercase plugin`, which works on the files; a program shows an install or an update with `plugin install SOURCE --preview --json` instead (below). Through [`--remote`](../plugins/#on-another-machine) the same commands, `plugin list --json`, `enable`, `disable`, `remove` and `logs` act on that machine's plugins, so a program can manage another machine's plugins with no `ssh` of its own. `{"command": "plugin-popup-close", "args": {}}` closes the popup as its `×` does. An older server refuses each of these requests by name, and a `plugin-run` without `item` as `malformed`.

#### Window processes beside your own window

A program that draws cornercase itself runs this for as long as its window is open:

```sh
cornercase plugin windows --json
```

What each plugin that is on declares as [`[[window]]`](../plugins/#window-processes) then runs beside your window, as it does beside cornercase's own: it starts what is wanted, picks up within a second a plugin turned on or off or a changed manifest, starts again what stops (after 1, 2, 4… up to 60 seconds) and keeps the files [`plugin remove`](../plugins/) reads to wait for them. Two programs run two copies, as two windows do, and each process inherits this command's environment.

It reads the plugins of this machine and sends no request, so it needs no server and works with any server. With no server, with no plugin that has a window process, or with a `plugins.json` it cannot read, it keeps running and waits. A restart of the server doesn't touch it, and neither does an update: it stays the old version until you start it again, and what it starts meanwhile gets the new binary as `CORNERCASE_BIN`.

Each change is one line. With `--json` it is an object with `plugin`, `id`, `state` (`running` or `stopped`), `pid` and `restart_in`, the seconds until it starts again, `null` once it won't because the plugin was turned off or lost that entry:

```json
{"plugin":"acme.notes","id":"panel","state":"running","pid":4242,"restart_in":null}
{"plugin":"acme.notes","id":"panel","state":"stopped","pid":null,"restart_in":1}
{"plugin":"acme.notes","id":"panel","state":"stopped","pid":null,"restart_in":null}
```

Without `--json` it says the same in words, such as `acme.notes panel: stopped, restarts in 2s`, after a first line that says what it does. `plugin logs ID` says why one stopped.

It stops them all and exits with status 0 when it gets `SIGTERM`, `SIGINT`, `SIGHUP` or `SIGQUIT` (on Windows Ctrl+C, `taskkill` without `/f`, or its console closing), and when the reader of its standard output leaves, even if it has nothing to print. So give it a pipe: closing the pipe ends it, and so does your program dying. Its output ends once everything has stopped.

`SIGKILL` can't be caught, and it is what Rust's `Child::kill` sends: on Linux and macOS what the command runs then keeps running, and nothing restarts it, as when a window is killed that way. Close the pipe or send `SIGTERM` instead. On Windows a process killed that way takes what it runs along, but a reader that left is noticed only at the next line it can't write, so end the command yourself, or start it in a Job object that kills it with your program.

Window processes run on the machine that shows the window, so `--remote` is refused with status 2, and so is a line of [`requests`](#many-commands-through-one-process).

## Exit status

| Status | Meaning |
| --- | --- |
| `0` | Done. |
| `1` | An error or a timeout; the message says which. |
| `2` | Wrong usage, such as an unknown option. |
| `3` | A partial answer: `usage`, `issue list`, `files list`, `worktrees list`, `worktrees free-builds`, `worktrees remove` and `read --last-message` with several targets printed their whole answer, but an agent, a machine, a tracker, a folder, a worktree or a pane in it failed, `clone --file` made the clone but couldn't write a file, `input --follow` couldn't send some of its lines, a line of `requests --follow` failed, or a folder of the `.code-workspace` file given to `open` was gone or couldn't start its shell. Each says why in its `error` (`issue list` also names failed trackers on standard error). With `--json`, the output is a complete answer whenever the status is 0 or 3. |
| `4` | A command given [`--boot`](#arrange) named another run of the server: it restarted since, so its ids may name other items now. Nothing was done; read `status` again. |
| `5` | The cornercase on the machine [`--remote`](#on-another-machine) reached is older than this one, or too old to say its version, so nothing was sent. Update it from here with `cornercase --remote DESTINATION update` (add `--remote-command PATH` if you gave one): the message gives the command for an older release, and the `update` of the JSON line below gives it for both. A `--remote-command` wrapper that exits with 5 passes it through too. `cornercase remote` exits with 5 too when the other machine is the older one. |

With `--json`, status 5 also prints one line of JSON on standard output, and the message goes to standard error as `error: …`:

```json
{"error":{"code":"older","message":"`vps` runs cornercase 0.13.19 and this machine 0.13.22. Update it from here with `cornercase --remote vps update`","destination":"vps","there":"0.13.19","here":"0.13.22","update":["cornercase","--remote","vps","update"]}}
```

`destination` is what `--remote` was given, `there` the other machine's release (`null` when its cornercase is too old to say), `here` yours, and `update` the command that updates that machine from here, as words to run without a shell (with `--remote-command` when you gave one; replace `cornercase` with your own path if you run another). `view`, `surface` and `requests --follow` take no `--json` and print nothing on standard output; `contract --json` gives the facts.

A command that follows something until it ends (`events`, `status --follow`, `status --app --follow`, `changes list --follow`, `files list --follow`, `files read --follow`, `flow runs --follow`, `flow messages --follow`, `surface`, `view` and `config pair`) also ends with 0, without a message, soon after whatever reads its output is gone: the program it prints into exited or closed its end, or the `ssh` running it on another machine was killed or lost its connection. A terminal that closes ends it like any program, and one printing into a file or `/dev/null` runs until it ends by itself.

`input --follow` and `requests --follow` end when their standard input ends, once the last line is answered, or when what reads their answers is gone (`input --follow` with `--json`); while they wait for the next line they notice neither that nor a stopped server, until that line comes.

## Contract and compatibility

The commands and the server don't have to come from the same release (through [`--remote`](#on-another-machine) the other machine must run this version or a newer one): after `cornercase update`, a command of the new version talks to the server still running the old one, and the other way round. A program of your own, such as another UI for cornercase, can rely on the same rules, through the commands or straight through the socket.

### Ask the server first

```sh
cornercase contract
cornercase contract --json
```

```text
cornercase 0.12.137
contract 1
boot 4242-1700000000
commands 78 (78 available)
stream events 1
stream watch 1
stream surface 1
stream view 1
stream app 1
stream changes 1
stream flow-runs 1
stream flow-messages 1
stream files 1
stream config-pair 1
features boot, structured-errors, strict-fields, views, host-events, theme, notices, surface-patches, config, close-unlock, sound, issues, todo-panel, changes, agent-folds, accounts, account-login, account-switch, issue-names, account-restart, tour, close-agent-tabs, queue-undo, focus-reveal, popup-terminal, files, shared-files, build-folders, machines, machine-usage, stats-cached, machine-workspaces, machine-start, queue-routines
```

`--json` prints an object with:

- `version`: the server's release.
- `contract`: the version of the rules on this page, an integer starting at 1. It goes up only when something that was there changes meaning or shape, never when something is added.
- `boot`: which start of the server this is. It changes on every start, `cornercase restart` included, since ids start again from 1. It is the same value as `CORNERCASE_SERVER` in the panes and `boot` in `status --json`.
- `operations`: every request the server takes, by name, with `available`. A server with `start-server` among them can be started without a window; one without it needs a window before it opens terminals. One that is not available on this server has `available: false` and a `reason`; the others keep working.
- `features`: what a request can ask for (below): `boot`, `structured-errors`, `strict-fields`, `views` (the `view` field and `--view`; a client checks it before sending a view to a server), `host-events` (the `host` field of `events`, which an older server would ignore; a client checks it before sending it) `theme` (the `theme` request and `start-server`'s `theme`; check it before sending colours), `notices` (a view's `visible`, the `notices` field of `events` and the `go` request; check it before sending them), `surface-patches` (the `patches` field of `surface`; an older server ignores it and sends complete lines, so check it before asking) `config` (the `config` request and `config.revision`) `close-unlock` (the `unlock` field of `close`, which an older server ignores and then refuses with the lock's message; check it before sending it), `sound` (a notice's `sound` field: an older server never sends it), `issues` (the `issue` and `source` fields of `start` and `flow-run`, which an older server ignores and then starts the agent without the issue; check it before sending them), `todo-panel` (the `todo` request's `edit`, `undone`, `move`, `clear-done` and `restore`; an older server refuses them as malformed, so check it before sending them), `changes` (the `changes` requests and the `changes` count of `status`), `agent-folds` (the `pane` item of `collapse` and `expand`; an older server refuses it as malformed, so check it before sending it), `accounts` (the `account-*` and `profile-*` requests and the `profile` field of `start`, `start-with`, `new-tab` and `flow-run`, which an older server ignores and then starts the agent with its own login; ### What stays compatible

- Fields are only added, never renamed or removed. Read answers leniently: ignore keys you don't know, and don't depend on their order (`events` lines come out with their keys sorted).
- A new behaviour that must not be ignored gets a new request name, which an older server refuses with `has no … command` rather than doing something else.
- `contract` goes up when something that was there changes. Additions show in `operations`, `features` and `streams` instead.
- The format of each stream has its own version. Format 1 of `events` is the one described in [Follow events](#follow-events), format 1 of `watch` the one in [Follow the whole state](#follow-the-whole-state), format 1 of `surface` the one in [Stream a tab's terminals](#stream-a-tabs-terminals), format 1 of `app` the one in [Follow the rest of the app](#follow-the-rest-of-the-app), format 1 of `changes` the one in [Follow a workspace's changes](#follow-a-workspaces-changes).

### Errors with a code

A request through the socket is JSON: `{"command": "status", "args": {}}`, its `args` named after the command's options; the repository's `tests/fixtures/control/` holds examples of what goes over the socket. It is answered with `{"ok": …}` or `{"error": "…"}`. A request that also carries `"contract": 1`, or `"boot": "…"`, gets errors with a code instead:

```json
{"error": {"code": "not-found", "message": "there is no pane 9; `cornercase status` lists them"}}
```

| Code | Meaning |
| --- | --- |
| `unsupported` | The server has no such request, or the request's `contract` is newer than the server's. Nothing was done. |
| `malformed` | The request is not one: a plugin action run on a group or on a kind of row it isn't offered for, its arguments don't have the expected types, a setting's value is of the wrong type or one the Settings dialog refuses, or it names a `view` and takes none (`` `stats` takes no view ``). |
| `stale-boot` | The request's `boot` is not this server's: it restarted since, and the ids you hold may name other panes now. Nothing was done. |
| `not-found` | A plugin that isn't on or an action it doesn't have, no group, project, workspace, tab, pane, view, surface or changes stream has that id, a file has no change or a hunk no gap, `changes-mode` names a stream another connection opened, a branch doesn't exist, no setting or connection has that key, the tab has no divider at that path, or the URL given to `clone` is not a git repository. A view is gone once the connection that opened it closes. |
| `unknown-field` | A field this server doesn't know, named by its path, such as `args.bogus`. Nothing was done. |
| `unavailable` | The request is listed in `operations` with `available: false`, with the `reason` as its message. A development build turns off `update-check` and `update-install`; a release turns off none. |
| `busy` | The pane's program isn't reading its input: 16 MiB are waiting for it. Only `input` answers this; `send` and `keys` keep answering `failed`. Nothing was sent. For `clone`, a clone into that folder, or into one inside or around it, is already running. |
| `conflict` | The request doesn't fit the current state: a plugin action listed at another `revision` of the plugins, the pane's terminal has another size, a cell is outside it, the program scrolls itself, nothing is selected to copy, nothing is held in the pane given to `held`, or it is resuming its agent, or, for `update-install`, no release found or a cornercase that can't replace itself, a workspace for `changes` or `changes-merge-check` isn't in a git repository, a `with` of `changes-merge-check` in another project or in the same folder, a connection already follows changes, a file changed since the digest `changes-discard` or `changes-stage` was given, or, for `config`, a token set by an environment variable, a project folder that isn't a repository or a `config.json` that cannot be read; or a row moved before one of another workspace or project, a pane moved to another tab, or where its tab has no room; or an issue of a tracker that is not connected, a place to choose for an issue that isn't tied to a repository, or tracker settings that changed during the lookup; or, for `clone`, a folder that exists and isn't empty; or, for `run-setup`, a workspace that is not a worktree, a project with no setup or a setup already running. Read the latest state and try again. Nothing was done. |
| `failed` | Anything else. |

The `message` is the text the command would print. Text that is not JSON at all gets the plain form, `{"error": "…"}`, since the server can't tell what the request asked for. Without `contract` or `boot`, a field the server doesn't know is ignored, as it always was; with them it is refused, so a newer option never passes for done on an older server. Either one set to `null` counts as not sent. A `contract` newer than the server's is refused with `unsupported`, so a client written for later rules learns it at once instead of being read under older ones. The `cornercase` commands themselves send neither, so what they print doesn't change, except that the commands that take [`--boot`](#arrange) send `boot` when you give it.

With `boot` set to the value from `contract` or `status`, a request kept across a restart is refused before it acts on an id the new server gave to something else.

### Talking to the socket directly

The [socket](../../reference/command-line/#the-socket) takes one request at a time per connection: send the next once the previous one is answered (`input --follow` and `requests --follow` send through one connection this way). Each message is framed as its length, 4 bytes little-endian, then its [postcard](https://postcard.jamesmunns.com/) encoding: a request is variant 4 followed by the JSON text (its length as a varint, then its UTF-8 bytes), an answer variant 5 in the same form. `events` sends one answer per event and ends with variant 2, 3 or 4 (its panes closed, the server stopped, or it restarted); `watch`, the request behind `status --follow`, answers with the state and then sends it again in the same form after each change, until variant 3 or 4, and `app`, the request behind `status --app --follow`, does the same with the rest of the app's state; `surface` does the same with a tab's frame, and ends with variant 2 when the tab closes (or its view does); `view` sends the state, with the view in it, and holds the view open until the connection closes. A request for a view carries its id as `view` next to `command`, once `contract` lists the feature `views`. Only your own user can connect. Nothing needs to be sent before the request.

## Teach your agents

An agent only knows what is in its context, so it doesn't know about these commands until you tell it. cornercase ships a short set of instructions as an agent skill (a `SKILL.md` in the repository); install it for Claude Code, Codex and other agents with:

```sh
npx skills add usecornercase/cornercase-terminal --skill cornercase -g
```

Only the skill's name and description stay in the agent's context; the rest loads when a task needs it. `cornercase skill` prints the copy that matches your version; for an agent without skills, put that text in your `AGENTS.md` or `CLAUDE.md`. cornercase never installs it by itself, for the same reason it installs no hooks: it doesn't write into your agents' setup.

The instructions tell agents to use the commands only when you ask them to open tabs, run something in another pane, or start and coordinate agents; to learn the syntax from `cornercase --help`; to find panes with `status --panes` rather than walking the tree; never to steal focus, run `kill-server` or close what they didn't open; not to answer another agent's permission prompt without asking you; to read a pane before sending again after a timeout or a prompt that was not confirmed; to keep their `--timeout` under their own command timeout; to read several agents' answers in one `read --last-message` call; and to restart or update cornercase only when you ask, with `--when-idle`.

## Environment

| Variable | Use |
| --- | --- |
| `CORNERCASE` | `1` in every pane. The commands work there; only opening the window inside cornercase is refused. |
| `CORNERCASE_PANE` | The id of the pane a shell runs in. The commands use it to know where they run. |
| `CORNERCASE_RUN_DIR` | In the panes of a [flow](../flows/#the-runs-folder) run only: the folder where the team keeps its files. |
| `CORNERCASE_REMOTE` | Send the commands to the server of this machine, through `ssh`, as `--remote` does (the flag wins). Set it for one program, not in a shell's rc file: panes see it too, though servers never hand it to them. |
| `CORNERCASE_SERVER` | Which server started the shell, the `boot` of [`contract`](#contract-and-compatibility). A server only takes `CORNERCASE_PANE` as the pane a command runs in when this is its own, since every server numbers its panes from 1. |
| `CORNERCASE_SOCKET` | Which server to talk to, as for every `cornercase` command. Panes don't get it: a shell inherits the server's environment, so `cornercase` in a pane finds its own server anyway, and setting it would also move `config.json` and the session (see [Files and environment](../../reference/files-and-environment/#with-cornercase_socket)). |

## Security

As before, only your own user can reach the server's socket. But whoever reaches it can type into every shell, and change your settings and tokens, so a coding agent that can run `cornercase` can run anything in any pane, and run commands outside its own sandbox through another pane. Keep the socket out of reach of agents you sandbox: run them in a container or under another user without access to it, or don't give them a shell inside cornercase.

## Queue work for later

`cornercase queue add --at 'in 2h' --agent claude --prompt 'Fix the login form'` schedules work and prints its persistent id. Use `--issue URL_OR_KEY` for an issue, `--workspace ID` for a tab, or `--worktree BRANCH` for a worktree. `--at 'claude reset'` and `--at 'codex reset'` use the next five-hour plan reset. `queue list --json`, `queue edit ID --at TIME`, `queue remove ID` and `queue run ID` inspect and manage it. `--every 'day 09:00'` (or `2h`, `'weekday 09:00'`, `'monday 09:00'`, at least 30 minutes apart) makes a routine that starts its agent, or a `--flow`, in a new worktree from the up-to-date default branch each time, `--cleanup` removes that workspace when it finishes if nothing would be lost, and `queue pause ID` and `queue resume ID` stop and restart it. `--fresh` or `--no-fresh` on a one-off entry that makes a worktree keeps the choice with the entry (the `fresh` field, shown by `queue list --json`); without either, the entry follows [`fresh_branches`](../../reference/configuration/#fresh_branches) when it runs, and a routine is always fresh and refuses `--no-fresh`. Over the socket, `queue add` and `queue edit` take `repeat`, `flow` and `cleanup`, and `queue list` and `status --app` give a routine's `repeat`, `next`, `paused`, `flow` and `cleanup`, each run's `routine`, and the states `removed` and `kept`. See [Queue agents](../queue/) for formats and flags. Queued launches accept folder trust prompts automatically.

`queue remove ID` and `queue clear-started` print an undo number, or with `--json` answer `{"entries": [...], "undo": 7}`. `clear-started` removes every started entry in one request, and also the runs of a routine that ended (`removed`, `kept`, `failed` or `missed`), and leaves pending entries, starting runs and the routines themselves alone; an empty clear prints nothing, or `{"entries": []}`, without consuming history. `queue restore 7` puts that removal back with its captured fields, state and ids in their original order. The last 16 nonempty command removals stay available until the server stops, independently of the window's undo notice. A number works once; an unknown, used or evicted number is `not-found`.

Over the socket, these use the `queue` request and the `queue-undo` [feature](#ask-the-server-first) (the routine actions and fields, `pause`, `resume` and `add` with `repeat`, need `queue-routines`), with the following `args`:

```json
{"action": "remove", "entry": 5}
{"action": "clear-started"}
{"action": "restore", "entry": 7}
{"action": "pause", "entry": 3}
{"action": "resume", "entry": 3}
{"action": "add", "entry": {"repeat": "day 09:00", "flow": "Quick", "cleanup": true, "prompt": "…", "zone": "Europe/Madrid"}}
```

A **routine** has `repeat` (`30m`, `2h`, `3d`, `day 09:00`, `weekday 09:00`, `monday 09:00`; the same text `--every` takes, at least 30 minutes apart), and optionally `flow` (a flow's name, with no `agent` or `mode`) and `cleanup`. `cleanup` is refused for an agent whose `reads_status` is false in [`config`](#settings)'s `agents`: cornercase cannot tell when it finishes. It does not take `at`, `issue`, `workspace` or `worktree`. The entries of `queue list` and the `queue` of `status --app` give a routine's `repeat`, `next` (its next time, left out while it is paused), `paused`, `flow` and `cleanup`, and each of its runs' `routine` (the routine's id) and the new states `{"state": "removed"}` and `{"state": "kept", "pane": 7, "server": "…", "reason": "2 uncommitted"}`; `paused`, `cleanup` and the other new fields are left out when empty, so absent means false. `pause`, `resume` and `run` on a routine answer `{"id": 3}` (`run` also answers `{"id": 3, "run": 8}`, the new run's id). `remove` on a routine answers it with its runs and one `undo`. The additive `queue-routines` feature advertises all of this.

`restore` answers `{"entries": [...]}` without a new undo number. The new commands check the feature first so an older server cannot silently remove an entry without undo.

**What an entry's agent did.** Each time a queued agent or a routine's run ends a turn, when its pane closes and right before a routine removes its workspace, cornercase keeps the agent's last message (at most 4 KiB), the branch and the pull request as they were. `queue list` and `status --app` give each entry that started `started` (UTC seconds) and, once it kept a result, `result_at`, and never the text. `cornercase queue show ID [--json]` prints the entry's state, when it started, the branch, the pull request and the last message, and `--conversation` adds the whole conversation, oldest first: it exits **3**, after printing the rest, when the agent no longer has its record. The `queue-show` request takes `{"id": 7, "conversation": true}` and answers every key below, `null` when there is nothing; an unknown id is `not-found`. It needs the `queue-results` [feature](#ask-the-server-first).

```json
{"command": "queue-show", "args": {"id": 7, "conversation": true}}
```

```json
{"id": 7, "state": "removed", "started": 1794474060, "result_at": 1794476460, "label": "Review the open pull requests",
 "result": {"at": 1794476460, "text": "Reviewed #480 and #482.", "cut": false, "written": "2026-11-12T09:41:00.000Z",
            "agent": "claude", "branch": "routine/review-20261112-0900", "conversation": true,
            "pull_request": {"number": 482, "title": "Fix the login", "url": "https://github.com/acme/shop/pull/482",
                             "state": "open", "checks": "passing"}},
 "messages": [{"role": "prompt", "text": "…", "written": null, "cut": false},
              {"role": "reply", "text": "Reviewed #480 and #482.", "written": "2026-11-12T09:41:00.000Z", "cut": false}],
 "earlier": false, "note": null}
```

The answer also has the entry's other fields as `queue list` gives them. `result` is `null` when nothing was kept, `messages` is `null` without `conversation` or when the record cannot be read (`note` says why, and `result.conversation` is false), and `messages` holds the newest 1,000 prompts and replies, each cut at 32 KiB (`cut`), with `earlier` true when older ones were left out. The conversation is read when asked, so the answer can take a moment; it never carries the agent's file paths. The `remove`, `clear-started` and `restore` answers carry `started` and `result` (with its text) in the entries they return. Every queued prompt is sent with this sentence after it, which is not stored in the entry: "When you finish, end your last message with a short summary of what you did and what is left to do."
