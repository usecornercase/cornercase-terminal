The issue browser turns "I should look at #482" into a running agent in a few clicks: pick an issue, read it, press **start**. cornercase creates a worktree on a branch named after the issue, opens a tab there, starts your coding agent and hands it the issue.

## Open the issue browser

Click **`Issues`** at the bottom of the sidebar. The browser opens for the active project, with one tab per source:

| Tab | Shows |
| --- | --- |
| **All** | Every connected source together, most recently updated first. |
| **GitHub** | Issues of the project's repository, read with the `gh` CLI. |
| **GitLab** | Issues of the project's repository, on gitlab.com or your own GitLab server. |
| **Shortcut** | Stories from your Shortcut workspace. |
| **Linear** | Issues from your Linear workspace. |
| **Jira** | Issues from your Jira Cloud site. |
| **Plane** | Work items from your Plane workspace, on Plane Cloud or a self-hosted server. |
| **Asana** | Tasks assigned to you in your Asana workspace, or the tasks of the projects you choose. |

You can hide tabs and change their order in **settings → Issues → Sources shown**. The browser remembers the last tab you used.

## Connect your trackers

<Tabs>
<TabItem label="GitHub">

GitHub goes through the [GitHub CLI](https://cli.github.com), `gh`, using its own login. There is nothing to configure in cornercase:

```sh
gh auth login
```

cornercase runs `gh` in the project folder, so it lists the issues of that folder's repository. The project must be inside a git checkout; otherwise the GitHub tab says *this project is not in a git repository*.

If `gh` isn't on your `PATH`, set its location in [`config.json`](../../reference/configuration/) with the `gh` key.

</TabItem>
<TabItem label="GitLab">

GitLab needs its server and a personal access token. gitlab.com and self-hosted servers both work.

1. In GitLab, open **Edit profile → Access tokens** and create a personal access token with the `read_api` scope.
2. In cornercase, open the **GitLab** tab of the issue browser. Type your server's address, such as `https://gitlab.acme.dev`, or leave the field empty for gitlab.com, and press `Enter`; then paste the token and press `Enter`. **back** returns to the server. Type the address the server ends up at: requests carry your token, so cornercase doesn't follow redirects.

cornercase checks the token against the server and, if it works, saves it. The server is saved in your settings (`gitlab_url` in [`config.json`](../../reference/configuration/)), and you can change it in **settings → Issues → GitLab**, where the token can also be pasted. You can set the `GITLAB_TOKEN` environment variable instead of saving the token (the name `glab` uses too, so a token you already export for it works); the server then comes from your settings.

Like the GitHub tab, the GitLab tab lists the issues of the project's own repository: cornercase reads the repository's remotes (`origin` first) and takes the first one on your GitLab server, over SSH or HTTPS, subgroups included. The project must be inside a git checkout; otherwise the tab says *this project is not in a git repository*. When no remote is on the server, the tab says where the remotes are. A remote that goes through a host alias of your `~/.ssh/config` isn't recognised; add one with the server's real name.

</TabItem>
<TabItem label="Shortcut">

Shortcut needs an API token:

1. In Shortcut, open **Settings → Your account → API Tokens** and create one.
2. In cornercase, open the **Shortcut** tab of the issue browser (or **settings → Issues → Accounts**), paste the token and press `Enter`.

cornercase checks the token against Shortcut and, if it works, saves it. You can also set `SHORTCUT_API_TOKEN` in your environment instead.

</TabItem>
<TabItem label="Linear">

Linear needs a personal API key:

1. In Linear, open **Settings → Security & access → Personal API keys** and create one.
2. In cornercase, open the **Linear** tab of the issue browser (or **settings → Issues → Accounts**), paste the key and press `Enter`.

cornercase checks the key against Linear and, if it works, saves it. You can also set `LINEAR_API_KEY` in your environment instead.

</TabItem>
<TabItem label="Jira">

Jira Cloud (`https://<site>.atlassian.net`) needs three things: your site, the email of your Atlassian account and an API token.

1. At [id.atlassian.com](https://id.atlassian.com/manage-profile/security/api-tokens), open **Security → Create and manage API tokens** and create one (a classic token, without scopes).
2. In cornercase, open the **Jira** tab of the issue browser. Type your site (`acme.atlassian.net`, or just `acme`) and press `Enter`, then your email and `Enter`, then paste the token and press `Enter`. **back** returns to the previous step.

cornercase checks the token against Jira and, if it works, saves it. The site and the email are saved in your settings (`jira_site` and `jira_email` in [`config.json`](../../reference/configuration/)), and you can change them in **settings → Issues → Jira**, where the token can also be pasted. You can set `JIRA_API_TOKEN` in your environment instead of saving the token; the site and the email are still asked once.

The Jira tab lists the issues of the whole site you can see. To narrow it down, set a **Jira filter** in **settings → Issues → Jira**: a JQL condition such as `project = SHOP`, which is combined with the closed and people filters.

Jira Server and Data Center are not supported.

</TabItem>
<TabItem label="Plane">

Plane needs your workspace and an API key. Plane Cloud (`app.plane.so`) and self-hosted servers both work.

For a self-hosted server, first set **Plane URL** in **settings → Issues → Plane** to its address, such as `https://plane.acme.dev`. Empty means Plane Cloud, and the key is checked against the server set there. The server must be recent enough to serve Plane's `/api/v2` work item list.

1. In Plane, open **Profile settings → Personal access tokens** and create one.
2. In cornercase, open the **Plane** tab of the issue browser. Type your workspace, the part of the address after the server's name (`acme` in `app.plane.so/acme`), and press `Enter`, then paste the key and press `Enter`. **back** returns to the previous step.

cornercase checks the key against Plane and your workspace and, if it works, saves it. The workspace is saved in your settings (`plane_workspace` in [`config.json`](../../reference/configuration/)), and you can change it in **settings → Issues → Plane**, where the key can also be pasted. You can set `PLANE_API_KEY` in your environment instead of saving the key; the workspace is still asked once.

The Plane tab lists the work items of every project in the workspace you can see. To narrow it down, set a **Plane filter** in **settings → Issues → Plane**: query parameters of Plane's work item list, such as `priority=high` or `project_id=…&label_id=…`, which are added to the request together with the closed and people filters. cornercase does not check them: if Plane refuses them, its answer is shown in the list. Plane's rate limit is 60 requests a minute per key, and a list takes three.

</TabItem>
<TabItem label="Asana">

Asana needs a personal access token:

1. In Asana, open **Settings → Apps → Developer apps** (or [app.asana.com/0/my-apps](https://app.asana.com/0/my-apps)) and create a personal access token.
2. In cornercase, open the **Asana** tab of the issue browser (or **settings → Issues → Asana**), paste the token and press `Enter`.

cornercase checks the token against Asana and, if it works, saves it. If your account belongs to several workspaces, it then asks which one to use: type its name or ID and press `Enter` (**back** returns to the token). The workspace is saved in your settings (`asana_workspace` in [`config.json`](../../reference/configuration/)), and you can change it in **settings → Issues → Asana**. You can set `ASANA_ACCESS_TOKEN` in your environment instead of saving the token; with several workspaces, set the workspace in the settings too.

Without further settings the Asana tab lists the open tasks assigned to you. To list the tasks of some projects instead, set **Asana projects** in **settings → Issues → Asana** to their IDs or links, separated by spaces or commas; links copied from Asana's address bar, in the old and the new format, are turned into IDs. In that case the **people** filters work on the tasks of those projects. Subtasks, milestones and approvals are not listed. A task's key is the value of its ID field (`ENG-42`) when its project has one, and its number otherwise. Asana allows 150 requests a minute on free plans, and a list takes at least three.

</TabItem>
</Tabs>

<Screen
  name="issues-token"
  alt="The Shortcut tab of the issue browser asking for an API token, with instructions to create one and a note that it is saved in ~/.config/cornercase/secrets.json"
  crop={[2, 4, 106, 15]}
/>

Saved tokens go to `secrets.json` next to your `config.json`, readable only by you (mode `0600`). They are never written to logs, to the issue cache or to the screen. The **disconnect** button in a tracker's tab removes its saved token.

<Aside type="caution" title="Environment variables win">
When `GITLAB_TOKEN`, `SHORTCUT_API_TOKEN`, `LINEAR_API_KEY`, `JIRA_API_TOKEN`, `PLANE_API_KEY` or `ASANA_ACCESS_TOKEN` is set, it takes precedence over a saved token, and cornercase won't let you change it from the app. The server reads these variables when it starts, so after changing them, restart it with `cornercase kill-server`.
</Aside>

Each row shows the issue's key, its title and, on the right, its state (for closed or tracker states), labels, author and age. Up to 100 issues are listed per source.

- **Type** to filter the list by key, title, author, state, labels or assignees.
- `↑` `↓`, `PgUp` `PgDn` or the mouse wheel move through it; `Tab` and `Shift+Tab` switch source tabs.
- **refresh** reloads the list. Lists are also cached on disk, so they appear instantly the next time while cornercase fetches the latest.

Two toggles at the top right narrow the list down:

- **closed** includes closed (GitHub, GitLab), done (Shortcut), completed and canceled (Linear), done (Jira) completed and cancelled (Plane) or completed (Asana) issues.
- **people** filters by person, with the fields each tracker has: *assignee* and *author* on GitHub and GitLab, *owner* and *requester* on Shortcut, *assignee* and *creator* on Linear, *assignee* and *reporter* on Jira, *assignee* and *creator* on Plane and Asana. An Asana list of *your* tasks is already yours: to filter it by someone else's assignments, set **Asana projects**.

## Read an issue

Click an issue, or select it and press `Enter`, to read it:

<Screen
  name="issue-detail"

  crop={[2, 4, 106, 30]}

At the top you see the issue's details and its link, then exactly what **start** will do:

| Line | Meaning |
| --- | --- |
| **start** | Where the work happens: in its own worktree and on which branch, or in a new tab. |
| **agent** | Which agent will be started, in which mode, and its full command line. |
| **prompt** | What will be pasted into the agent, and whether it is sent for you or left for you to send. |

Below comes the description, rendered from Markdown (Jira, Plane and Asana descriptions and comments are converted to Markdown first; Asana images show as `[image]`): headings, lists and task lists, tables, quotes, links and code blocks with syntax highlighting in your terminal's colours, then the comments.

- Scroll with the wheel, `↑` `↓`, `PgUp` `PgDn`, `Space`, `Home` and `End`.

## Start working on it

Press **start** in the issue, or select an issue in the list and press **start** there. cornercase then works out three things.

After **schedule** (see [Schedule for later](#schedule-for-later)), **start a flow**, in the list or in the issue, gives the issue to a whole team of agents instead, a coder, reviewers and a tester run by an orchestrator agent, with the same prompt and the same branch; see [Flows](../flows/#start-a-flow).

### Where

- **GitHub** and **GitLab** issues belong to the project you opened the browser from.
- **Shortcut**, **Linear**, **Jira**, **Plane** and **Asana** issues aren't tied to a repository, so when more than one place is open, cornercase asks **where…**: every project that is a git repository is offered as *a new worktree*, and the workspaces of other projects as *a new tab*. The place you are in is marked *where you are*.

In a repository, the issue gets its own worktree on a branch named after it. By default each tracker has its own name:

| Source | Example issue | Branch |
| --- | --- | --- |
| GitHub | #482 Returns page crashes on empty address | `issue-482-returns-page-crashes-on-empty-address` |
| GitLab | #482 Returns page crashes on empty address | `482-returns-page-crashes-on-empty-address` |
| Shortcut | sc-48 Dark mode | `sc-48-dark-mode` |
| Linear | ENG-123 Returns page crashes | `ENG-123-returns-page-crashes` |
| Jira | SHOP-77 Returns page crashes | `SHOP-77-returns-page-crashes` |
| Plane | ENG-42 Fix login redirect | `ENG-42-fix-login-redirect` |
| Asana | ENG-42 Fix login redirect | `ENG-42-fix-login-redirect` |
| Asana, no ID field | 1205555555555555 Fix login redirect | `asana-1205555555555555-fix-login-redirect` |

GitLab branches start with the issue's number and a dash, GitLab's own convention: a merge request from such a branch gets `Closes #482` in its description, so, with the project's automatic issue closing on (GitLab's default), the issue closes when the merge request is merged into the default branch.

The title part is lowercased, accents become plain letters, everything else becomes dashes, and it is cut at a word boundary to at most 40 characters. The workspace is named after the issue's key and title, like `#482 Returns page crashes on empty addr…`.

Before the worktree is made, cornercase shows both names, filled in, so you can follow your team's convention for this one issue:

<Screen
  name="issue-names"
  alt="Start #482 Returns page crashes on empty address in a new worktree: the branch issue-482-returns-page-crashes-on-empty-address and the workspace #482 Returns page crashes on empty addr…, both editable, with start and back"
  crop={[2, 4, 106, 9]}
/>

Edit either, `Tab` moves between them, and `Enter` or **start** goes on; `Enter` straight away keeps the names as they are, `Esc` or **back** goes back to the issue. A name git would refuse (a space, `..`, a `:`…) is pointed out before anything is made. An empty workspace name keeps the issue's.

If the branch already exists, the worktree checks it out; if a workspace on that branch is already open, cornercase takes you there instead of creating another one, and only starts the agent if the workspace has no tab open. Outside a repository, the agent starts in a new tab of the chosen workspace, the tab is named after the issue, and nothing is asked.

#### Your team's branch names

To set the convention once, write a template in **settings → Worktrees → issue branches** ([`issue_branch`](../../reference/configuration/#issue_branch)), such as `feat/{key}-{slug}`. It is what the field starts with, and what [scheduled](#schedule-for-later) issues, [flows](../flows/) started from an issue and the [commands for scripts](../scripts-and-agents/#issues) use:

| Placeholder | Meaning | #482 on GitHub | ENG-123 on Linear |
| --- | --- | --- | --- |
| `{key}` | The issue's key, without `#` | `482` | `ENG-123` |
| `{number}` | Its number: the digits after the key's last dash | `482` | `123` |
| `{slug}` | Its title, as above | `returns-page-crashes-…` | `returns-page-crashes` |
| `{source}` | The tracker | `github` | `linear` |
| `{user}` | Your git `user.name`, slugged | `ana-garcia` | `ana-garcia` |

The template needs `{key}` or `{number}`, so each issue gets a branch of its own. What it makes is cleaned into a name git takes: spaces and other characters become dashes, and an empty part (a `{user}` git does not know) is dropped. Empty keeps each tracker's own name. `{user}` comes from the repository's git config, else `~/.gitconfig` or `~/.config/git/config`. GitLab closes an issue by itself only from a merge request whose branch starts with the issue's number and a dash, so the setting warns when a template does not start with `{number}-` (or `{key}-`, which is the same on GitLab).

### Which agent

cornercase picks the agent in this order:

1. the one you chose for this issue with **agent…**;
2. the default agent from **settings → Agents**;
3. when the default is `auto`, the agent already running in your current tab;
4. otherwise it asks:

  alt="The agent picker: claude, codex, gemini, opencode, grok, cursor, copilot, amp, droid, pi, qwen, kimi, cline, goose and aider, each with its command"

When you pick an agent that isn't your default, a **make default** button appears so you can keep that choice. Once you have [accounts](../accounts/) of the chosen agent, **start** (or `Enter`) first asks which account it starts with, with the default selected, so `Enter` again keeps it; **account…** on the issue's page chooses it ahead. Neither changes the default account; **start a flow** passes it on. An account removed before you click **start** stops the start and says so. How each agent starts (its permission mode and extra arguments) is set in **settings → Agents**; see [Agents](../../reference/agents/).

### The launch

Once the worktree exists, cornercase opens a tab in it and drives the new shell for you:

<Steps>

1. It waits for your shell's prompt to settle, then types the agent's command line, for example `claude --permission-mode plan`, and presses `Enter`.

2. It waits until the agent has taken over the terminal and its screen has been still for a moment.

3. If the agent asks whether you trust the folder, cornercase waits for you to answer: saying yes lets the agent use the repository's own agent settings, so it is your call. With **settings → Agents → trust prompts** turned on, cornercase answers yes for you instead.

4. It pastes the prompt. By default the prompt is your issue's link, typed on one line and left at the agent's prompt for you to read and send with `Enter`. With **settings → Agents → send the prompt** turned on, it is pasted as written and sent for you.

</Steps>

Readiness is detected from what the terminal shows, so a slow agent may take a few seconds. If the shell still hasn't started the agent a few seconds after the command was typed, cornercase gives up and leaves the tab as it is; the reason is written to the server log.

<Aside type="tip" title="Make the prompt yours">
The prompt is a template. Instead of just the link, you can send a whole instruction, such as `Fix {url} on branch {branch}. Start by writing a failing test.` See [Prompt template](../../reference/prompt/) for every placeholder.
</Aside>

### Review the result

You don't need to keep an eye on the agent's tab. With Claude Code, Codex, Gemini CLI, opencode, Grok Build, Cursor CLI or GitHub Copilot CLI, the tab shows `◐` while it works (or a spinner, with [working icon](../../reference/configuration/#working_icon) set to *spinner*), and if it asks you something (Claude Code, Codex, Gemini CLI, Grok Build, or Cursor CLI with `/status-indicators` turned on or OSC 7501 reports) or finishes while you are elsewhere, the tab, its workspace and its project show `!` or `✓`, and a [notification](../projects-workspaces-tabs/#notifications) tells you where; see [What your agents are doing](../projects-workspaces-tabs/#what-your-agents-are-doing).

The issue's workspace is a git worktree, so its [changes panel](../changes/) shows what the agent is doing as it saves files. Open it with **`Changes`** next to `Issues`, switch to **All** to see the commits too, and hover a hunk to **ask agent** about it: cornercase types the file and lines into the agent's prompt for you.

## Schedule for later

Click **`schedule`** beside **`start`** to put an issue in the [agent queue](../queue/), the **`Queue`** tab at the end of this dialog. Choose a clock time, delay, or the next Claude or Codex five-hour plan reset. The queue starts each due agent in its chosen worktree or tab and accepts its folder trust question automatically.

## From scripts and other apps

Everything above is reachable without the window. `cornercase issue sources` says which trackers are connected for a project and what is missing, `issue list` lists issues with the dialog's filters from the same lists, `issue read` prints an issue with its comments and `issue people` the people the filters can name. `cornercase start --issue '#482'` does what **`start`** does: a worktree on the issue's branch with your prompt template, or a tab when the project isn't a repository, asking `--project` or `--workspace` when an issue isn't tied to a repository and several places are open. See [Scripts and agents](../scripts-and-agents/#issues).
