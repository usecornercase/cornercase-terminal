**Settings › Machines** lists the other computers your work can run on: a cloud VM, the desktop at home, a Mac mini under the desk. For each one, your cornercase server keeps a link to the cornercase server on that machine, through your own `ssh`. The link is what lets cornercase work with that machine's projects and agents, and the row shows whether it is up.

A linked machine's workspaces show [in your sidebar](#in-your-sidebar), under the project here that is a clone of the same repository, and its agents tell you when they need you as yours do. Your server can also [ask each machine for its stats and plan usage](#stats-and-usage-of-each-machine). Click one of those workspaces and its tab shows here, live, and you [work in it](#working-in-a-machines-tab) as in one of yours. You can [rename, close and remove the worktree of a machine's workspace](#acting-on-a-machines-workspace) from its row. Opening tabs or starting agents on those machines from this window comes later; until then, [`cornercase remote`](../remote/) opens a window on one of them.

## Add a machine

Click **`+ add machine`** at the end of the list. The form asks for:

| Field | What it is |
| --- | --- |
| **name** | What the window calls it: letters, digits, `.`, `_` and `-`, at most 20 characters, different from every other machine's, and not `all`, which means every machine. |
| **icon** | One of ☁ server, ▭ laptop, ▣ desktop, ◫ mini, ⌂ home server or ◆ other. |
| **destination** | Anything `ssh` takes: a `Host` of your `~/.ssh/config`, or `user@host`. Your config, keys and agent apply, and cornercase never sees a password or a key. |
| **folder** | Where clones go on that machine, `~/code` unless you change it: an absolute path, `~`, or one starting with `~/`. Nothing is made there yet. |

` add ` saves it, and the link starts at once. A value the form refuses says why under its field, and nothing is saved. Click a machine, or select it and press `Enter`, to change it in the same form; its link carries on unless you change the destination.

The `×` at the end of a row, or `Backspace`, removes a machine at once. The machine's server keeps running there.

## What a link does

The link is one `ssh` connection from your cornercase server to the cornercase server on the machine. It is the server's, not the window's, so it stays up while no window is open.

- **It uses the server running there**, or starts one when none runs, as [`cornercase start-server`](../../reference/command-line/#cornercase-start-server) does.
- **It never stops anything there.** Removing the machine, stopping or restarting cornercase on this computer, this computer going to sleep and a dropped connection all end the link only; the server on the machine and everything in it keep running.
- **A server you stop there comes back.** After `cornercase kill-server` on the machine, the link starts it again on its next try. To stop it for good, remove the machine here first.
- **It goes one way.** The machine can't act on this computer through the link: a tab you look at is drawn as text and colours only, nothing it sends is played or opened here, the one thing copied is the text you select on it, and the link's `ssh` forwards neither your agent, nor X11, nor any port.

## States

| Row | Means |
| --- | --- |
| `◌ connecting…` | The link's first try hasn't answered yet. |
| `● linked · 0.12.225` | Linked, with the version of cornercase installed there. When its server still runs an older one, the row adds `· its server runs 0.12.224 until it restarts there`. |
| `○ unreachable · 8 s` | Down since that long, or `not seen yet` when it has never been up since your server started. Select the row and the line at the bottom shows why: what `ssh` said, `cornercase was not found on vps: install it there`, `that is this computer`, or `the same server as vps` when two destinations reach one machine. |
| `◐ older · 0.0.1` | Its cornercase is older than yours, so it is not linked. |

A link that drops is tried again after 1, 2, 4 and 8 seconds, then every 15 seconds, and every minute while something on the machine needs you: an older cornercase, a missing one, or a destination that turns out to be this computer or a machine already listed. All of them try again at once when this computer wakes up or changes network, and when you change a machine that is down. `cornercase machines retry` tries them now.

### Update an older machine

An `older` machine has an **`update…`** row under it. It runs `cornercase update` on the machine, without a terminal, so it installs the new release and restarts nothing: the server there keeps running its version until it restarts, and the row says so. Once the update ends, the link tries again. When it fails, the line at the bottom shows what the update printed last, such as the Homebrew command to run there.

## What you need

- **cornercase on the machine**, in your version or a newer one. It is looked for on the `PATH` of a command run through `ssh`, then in `~/.local/bin` (where the [install script](../../installation/) puts it), `~/.cargo/bin` and Homebrew's folders. A machine has no `--command` as `cornercase remote` does: when it lives somewhere else, link it into one of those folders.
- **A key that never asks.** The link's `ssh` runs with `BatchMode=yes`: it never asks for a password, a passphrase or an unknown host key, since nobody is there to answer. Use a key in your SSH agent, or one without a passphrase, and connect once by hand to accept the host key:

```sh
ssh ana@vps.example.com true
```

- **Your own `ControlMaster`, if you like.** The link holds one connection, but `cornercase machines update` and [`--remote` commands](../remote/#commands-for-scripts-and-agents) open their own; a shared one makes them faster:

```text
Host vps
  HostName vps.example.com
  User ana
  ControlMaster auto
  ControlPath ~/.ssh/cm-%C
  ControlPersist 10m
```

<Aside>
A connection that died without a word is noticed within about 15 seconds: `ssh` checks it every 5 (`ServerAliveInterval=5`, `ServerAliveCountMax=3`), and gives up on a machine that doesn't answer after 10 (`ConnectTimeout=10`).
</Aside>

## In your sidebar

Once a machine is linked, your server reads what it has, and the sidebar shows it beside your own projects:

```text
▌ web-shop (2)          !
  blog (1)          ☁ vps

  ▾ login
▌ ├ › nvim
  └ + Tab

  ▾ api           ! ☁ vps
  ├ ! claude
  │   opus · 40%
  └ › zsh
```

- **A workspace on a machine shows under the project here that is a clone of the same repository**, after its own workspaces, with the machine's icon and name. Two clones pair whatever address each one was cloned with: `git@github.com:acme/web-shop.git`, `https://github.com/acme/web-shop` and an ssh alias from that machine's `~/.ssh/config` are the same repository, read from the `upstream` remote, else `origin`, else the first one. The project's count and its `!` include them.
- **A project on the machine with no clone here** is a row of its own at the end of the list, outside your groups, with the machine's tag.
- **Its tabs show what their agents are doing**, with the same icons and the model and context line as yours.
- **A machine that is down keeps its rows**, dimmed, and an agent's tab says what it was doing and when the machine was last seen: `working · seen 2 min ago`.
- **A machine's workspace has a `×` and a ` ⋯ ` menu**, as yours do: see [Acting on a machine's workspace](#acting-on-a-machines-workspace). Its tabs have no buttons, no row has `+ Tab`, and they can't be dragged. Folding a workspace works: it is kept by your server, not on the machine, until your server restarts.

### Acting on a machine's workspace

Hover over a machine's workspace (in compact mode its buttons always show) and use its buttons as you would on yours. Each one sends the machine the request a script would send, over a connection of its own, and the machine does it as if you had clicked in its own window:

- **` ⋯ `**, or a right-click on the row, opens a menu with **rename workspace**. Leave the name empty to go back to the branch name. The new name shows when the machine sends its next update.
- **`×` on a plain workspace** asks first, also when the window is wide: `Close the workspace notes on vps?`. Its shells stop on the machine.
- **`×` on a workspace with a worktree** asks the machine what removing it would lose, as the [remove a worktree](../worktrees/#remove-a-worktree) dialog does here: changes that aren't committed (**remove anyway**), a lock (**unlock and remove**), its roles' worktrees and its teardown. Then the row says `removing…` until the machine answers with `removed feat/dark-mode on vps`, or, if its teardown or a role's worktree failed there, `removed feat/dark-mode on vps, cleanup failed in part, see server.log`, as a removal here says; the reason is in this computer's log (`cornercase logs`). If the machine can't check, the dialog closes and a toast says why; nothing is removed.
- **If the machine is down**, the menu says `vps unreachable` (or why the link is waiting) and its items are greyed out, and the `×` says the same with `nothing was sent`. Nothing is kept to send later.
- **While the machine works on one of them**, the workspace's **rename workspace** is greyed out and its `×` says `notes on vps is still waiting for its last action` with `nothing was sent`. A row that says `removing…` takes no clicks.
- **If the machine restarted** after you opened a dialog, the dialog closes, or, if you confirm first, nothing is changed there and a toast says so, since its workspaces may have new ids by then.

A rename or a close gives up after 15 seconds, the check after a minute and a removal after 10 minutes, with `it did not answer in time`; a removal that took longer goes on on the machine. Scripts can do the same with [`--remote`](../scripts-and-agents/#machines).

### Clicking a machine's workspace

Click a machine's workspace or tab, or [`cornercase focus --machine vps --workspace ID`](../scripts-and-agents/#machines), and its row is marked as picked. Where a pane would be, you see that workspace's active tab as it is on the machine: its panes, its splits and what their programs print, as it happens. Its panes take the size of this window's pane area, and follow it when you resize the window or open a side panel, so what runs there draws for this window. If someone uses that tab in the machine's own window meanwhile, the last one to size it wins, and the other sees it cut or with blank space, as with any tab shown in two windows.

Until the machine sends the tab's first screen, a card says where it runs:

```text
╭─ runs on vps ──────────────────────╮
│                                    │
│ claude is waiting for you          │
│ ~/code/web-shop                    │
│                                    │
╰────────────────────────────────────╯
```

While the machine is down, the tab's last screen stays, dimmed, under a card that reads `vps unreachable`, then `reconnecting in 4 s`, counted down to the link's next try (or why it is waiting, such as an older cornercase there), and `claude keeps working there`: the link going down stops nothing on the machine. When only the connection that shows the tab dropped, the card says `reconnecting…` and the tab comes back by itself. Once the machine is back, the tab is live again, with nothing restarted here or there.

### Working in a machine's tab

Once its screen shows, the tab works as one of yours, on the machine:

- **What you type and paste** goes to its active pane, keys as the program there asked for them.
- **The mouse** goes to a program that reads it, such as `vim` or `htop`, as it would here. A click on another pane makes it the active one; a right-click on it goes on to its program when it reads the mouse.
- **The wheel** scrolls a pane's history, or moves through a full-screen program's lines, and a click on ` ↓ 12 more `, at the bottom of a pane that is scrolled up, takes it back down.
- **Selecting text** with the mouse, where no program reads it, copies it to this computer's clipboard, cleaned as a selection here is, and a toast says so. A click where you pressed clears it.
- **The dividers** between its panes drag, and a double click puts one back in the middle. `Esc` ends a drag.

Before its first screen arrives, and while the machine is down, nothing you type, click or scroll there is sent, or kept for later: a toast says `vps unreachable: nothing was sent`. When the program in a pane doesn't take what you send, the toast says so too.

While a machine's workspace shows, the sidebar, the tools, the tabs above the pane and the prefix key's menu still work; what that menu does to a tab or a pane, such as a split, first goes back to this computer. The project here it pairs with becomes the active one, and the tabs above the pane, **Changes** and **Files** keep showing that project's workspace you were on here. Click anything of this computer to go back to it.

### Notices from a machine

When an agent on a linked machine that was working needs you, fails or finishes, you get the toast, the desktop notification and the [sound](../projects-workspaces-tabs/#a-sound) you'd get for one here, with the machine's name: `claude on vps needs you in web-shop › main`. ` go `, or a click on the notification, shows that workspace of the machine.

- The machine's workspace you have picked never tells you, like the tab on your screen.
- Nothing is told for what changed while the link was down, nor for a shell an agent left running in the background.
- A notice you missed while the window was in the background doesn't show again when you come back, unlike one about an agent here.

Scripts get them from [`cornercase events --notices`](../scripts-and-agents/#follow-events), with the machine's name.

### What isn't there yet

- A project on a machine with no workspaces can't be picked.
- Starting an agent, a script or an issue's work on a machine.
- Closing or renaming a machine's tabs, `+ Tab`, splitting or closing its panes, and the prefix key's menu acting there.
- **Changes** and **Files** for a machine's workspace.
- In a machine's tab: clicking a path, the pane's right-click menu, moving panes, the accounts row, opening links, and pictures.
- Picking a machine's workspace with ` go ` or `focus --machine` doesn't scroll the tree, or the workspaces column, to its row.

## Stats and usage of each machine

The [Usage dialog](../projects-workspaces-tabs/#usage-and-stats) and `cornercase stats` and `cornercase usage` read the other machines too. Your server asks the machine's server for them, through a new `ssh` connection each time, as [`--remote`](../remote/#commands-for-scripts-and-agents) does.

### In the Usage dialog

Click **`More ▴`**, then **usage**. With machines listed, a row above **Limits** and **Stats** picks **this computer**, one machine by its name, or **all**. It starts on **all** and keeps your pick until the server restarts. Opening the dialog, switching tabs or picking asks the machines you picked; nothing is asked while it is closed.

- **Stats** shows what you picked: this computer's numbers, one machine's, or under **all** their sum (see [how the numbers add up](#how-the-numbers-add-up)). Under the table, notes say that **most at once** is the largest peak of one machine, not a sum, which machines were summed from the numbers they gave last (`vps: seen 5 min ago`), and which weren't summed and why. **share** copies the link of what you picked: under **all**, the sum.
- **Limits** under **all** lists this computer, then each machine under its name, with the accounts logged in there and their own labels. A Claude Code account logged in with a claude.ai login on two machines shows once, under the first, marked `on this computer, vps` under its title, with the most recent of the two readings; its percentages are never added, since it is the same limit. Every other row shows once per machine: Codex, API keys, Bedrock and Vertex give no way to tell two machines' accounts apart. Picking one machine shows its accounts as that machine sees them, merged with nothing.
- A machine that is down shows the numbers it gave last, with when it was last seen; one whose last answer failed shows them too, with why and when they were read (`vps: … · numbers read 5 min ago`); one never read says `not seen yet` or why. With many machines on a narrow window, their names in the row are shortened so that every one, and **all**, can still be clicked.

### From a terminal

`cornercase stats` and `cornercase usage` take `--machine`:

```sh
cornercase stats --machine vps      # the stats of the agents that run on vps
cornercase usage --machine vps      # the plan limits of the accounts logged in on vps
cornercase stats --machine all      # this computer's stats and every machine's, summed
cornercase usage --machine all      # this computer's limits, then each machine's
```

A line above the numbers says which machine they come from and when they were read:

```text
▭ this computer
Claude Code · max plan  updated just now
  session (5h)   34% · resets in 2h 14m
  week           81% · resets in 3d 4h

● vps  read just now
Claude Code · max plan  updated just now
  session (5h)   34% · resets in 2h 14m
  week           81% · resets in 3d 4h
```

Scripts and other apps send the same `machine` to the `stats` and `usage` requests: see [Stats](../scripts-and-agents/#stats) and [Plan usage](../scripts-and-agents/#plan-usage). To ask a machine you haven't listed, use `cornercase --remote vps usage`.

### How the numbers add up

- **Stats under `all` are a sum**: prompts, turns, tokens and agent time add up, hour by hour, and so does the heatmap. The peak of agents working at once is the largest one machine had, since nobody knows whether two machines' peaks came at the same time. Busy time adds up too, so the hours it shows are machine-hours. Merged pull requests are never added: the row stays only when every machine reads the same accounts. The dialog's notes and the list at the end of `cornercase stats --machine all` say which machines are in the sum and which aren't, and why. A machine that is down is summed from the numbers it gave last: its heatmap moves on by the days since they were read, but its 24 h and 7 days count as they were then, so a machine down for three days still adds its last 24 hours.
- **Limits are never added**: they are the provider's. Each machine lists the accounts logged in there, with its own labels. The dialog shows an account it can tell is the same on two machines once; `cornercase usage` lists it under each machine, with the same `identity`.
- **Only a linked machine is asked**, and it gets 15 seconds to answer, plus the time its own probes take for plan limits. When it is down or doesn't answer, you get the numbers it gave last, with why it is down. With none, asking for that machine alone is an error, and `all` lists it with why and no numbers. `usage` exits with status 3 when a machine or an agent couldn't be read.
- **Its numbers stay in your server's memory**, and are gone when it restarts. `cornercase stats` without a server reads this computer's `stats.json` only.
- **Each machine runs its own probes**, with the `claude` and `codex` of its own [`agent_commands`](../../reference/agents/#your-own-agents).

## From the command line

`cornercase machines` prints the same list, and its subcommands change it as the Settings tab does:

```sh
cornercase machines
cornercase machines add vps ana@vps.example.com --icon server
cornercase machines edit vps --folder '~/src'
cornercase machines retry vps
cornercase machines update mini
cornercase machines remove vps
```

Scripts and other apps read and change the list with the `machines` request: see [Machines](../scripts-and-agents/#machines).

The list lives under [`machines`](../../reference/configuration/#machines-1) in `config.json`, and an edit of the file applies within a second. It isn't part of the settings you [share](../../reference/configuration/#share-your-setup): a colleague can't reach your machines.
