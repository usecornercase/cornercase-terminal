Your agents can run on a bigger machine than the one you carry: a dev server, a cloud VM, the desktop at home. `cornercase remote` opens the window on your laptop and attaches it to the cornercase server on that machine:

```sh
cornercase remote devbox
```

`devbox` is anything `ssh` takes: a host from `~/.ssh/config`, or `user@host`. cornercase runs your own `ssh`, so your config, keys, agent, `ProxyJump` and `ControlMaster` all apply, and cornercase never sees a password or a key.

```text
 your laptop                                        devbox
 cornercase remote ── ssh ───────────▶ cornercase proxy ──▶ cornercase server ── shells, agents
```

On the other machine, `ssh` runs `cornercase proxy`, which finds the server (or starts one if none is running), whatever environment the SSH session has, and passes the window's keys and the server's screens back and forth. It is the same server that `cornercase` on that machine attaches to, so you can also open it from a terminal there: the windows mirror each other, as described in [Sessions and the server](../sessions/#several-terminals-at-once).

## What you need

cornercase on both machines, in the same version for the window, and for [commands](#commands-for-scripts-and-agents) the same or a newer one on the other machine (see [Versions](#versions)). On the other machine, it is looked for on the `PATH`, then in `~/.local/bin` (where the [install script](../../installation/) puts it), `~/.cargo/bin` and Homebrew's folders, since the `PATH` of a command run through `ssh` is often shorter than your login shell's. If it lives somewhere else, say how to run it with `--command`:

```sh
cornercase remote devbox --command '~/tools/cornercase'
```

The other machine's `sh` reads it, so `~` and `$HOME` work.

## A Windows machine at the other end

The other machine can run Windows, with [cornercase installed there](../../installation/) and Windows' OpenSSH Server running (an optional feature of Windows; adding it needs an administrator). Its `sshd` runs commands with cmd or PowerShell rather than `sh`, so the first time you connect, cornercase finds out which one with a harmless `echo`, then runs the proxy in a line written for that shell, and remembers the answer for that host, so later connections and reconnects go straight to it. That first connection takes three `ssh` sessions instead of one (three password prompts, if you log in with a password). A Linux or macOS machine pays nothing when the connection works; only when it fails before reaching cornercase in a way that cmd or PowerShell could explain (an exit status of 1) does cornercase send that `echo` once before reporting the error, one more `ssh` session and, with a password login, one more prompt.

The answer is kept in `remote-shells.json`, in cornercase's state folder on the machine you connect from (`~/.local/state/cornercase/`, or `%LOCALAPPDATA%\cornercase\` on Windows). When the remembered shell stops working, for instance because the name now reaches another machine, cornercase asks again by itself; deleting the file, or that host's entry in it, makes it forget.

The first time, `cornercase --remote winbox kill-server`, `restart` and `update` fail there and tell you to run them again, since cornercase doesn't repeat a command that may already have done something; `logs` is run again through the right shell by itself.

There, cornercase is looked for on the `PATH`, then in `%USERPROFILE%\.local\bin`, where the PowerShell installer puts it, and `%USERPROFILE%\.cargo\bin`. `--command` takes the path of `cornercase.exe`, the same for cmd and PowerShell, with `~\` for your profile folder:

```sh
cornercase remote me@winbox --command 'C:\tools\cornercase.exe'
cornercase --remote me@winbox --remote-command '~\tools\cornercase.exe' status
```

A path holding `%`, `!` or `"` is refused when the shell there is cmd, which would read them as its own.

<Aside type="caution">
For an administrator account, Windows' OpenSSH Server opens elevated sessions, so a server that `cornercase remote` starts there runs its shells and agents as administrator, and a window opened at that computer's desktop attaches to the same server. To keep them unelevated, start cornercase at the desktop first, or connect with an account that is not an administrator.
</Aside>

## What runs where

Everything that touches files or programs stays on the other machine: the shells, the agents, worktrees and git, the [changes](../changes/) and [files](../files/) panels, ` open ` (your editor opens in a new tab there), Usage and stats, the issue trackers (`gh` and your tokens live there), and its `config.json`, `session.json` and `stats.json`. A stats share link still copies to your local clipboard through OSC 52.

Your laptop only shows the window. Keys, the mouse, pastes and your terminal's colours come from it, and copying, [desktop notifications](../projects-workspaces-tabs/#notifications) and the [images](../files/#images) the files panel shows go through it, so the text lands in your local clipboard, the notification on your local screen and the picture in your local terminal. A [sound](../projects-workspaces-tabs/#a-sound) plays on your laptop too, with a file path read there; a window opened with `ssh -t host cornercase` plays none.

**open in…** can't open the other machine's folders in your laptop's Finder or editors, since they aren't there: the project, workspace and pane menus offer **copy path** instead, which copies the path as the other machine knows it. See [Open in another app](../projects-workspaces-tabs/#open-in-another-app).

## When the connection drops

The window stays open and says so:

  name="remote-reconnecting"
  alt="The cornercase window attached to devbox after the connection dropped: the last screen stays behind a Connection lost dialog that says reconnecting to devbox…, connecting…, the ssh error Connection refused, that its shells keep running on devbox, and a quit button"
  caption="The last screen stays behind the notice until the connection is back."

It tries again at once, then after 1, 2, 4 and 8 seconds, then every 15 seconds, and shows the last thing `ssh` said. Your shells and agents keep running on the other machine meanwhile, and once it is back the window shows them as they are now. A laptop that slept or changed Wi-Fi comes back on its own.

`Esc` or ` quit ` gives up: the window closes and everything keeps running there, so `cornercase remote devbox` attaches again later. The ` Quit ` in the sidebar works as always: it detaches, and nothing reconnects.

<Aside>
Reconnecting never asks for a password or a passphrase, since the window has your keys: use a key that is in your SSH agent, or one without a passphrase. The first connection, before the window opens, can still ask for them. To notice a connection that died without a word, cornercase asks `ssh` to check every 5 seconds (`ServerAliveInterval=5`, `ServerAliveCountMax=3`), so it reacts within about 15 seconds.
</Aside>

## Switch machines from the window

Once a window has reached another machine, the bottom of the sidebar names the machine it is on, on a row of its own under **`Worktrees`** and **`Recap`**: `devbox ▴`, or `this machine ▴` once you come back. Click it to move the window somewhere else without closing it:

- **this machine** attaches it to the server on your laptop, and starts one if none is running.
- Every machine a window reached before, with `cornercase remote` or from this menu, attaches it there, with the `--command` you gave last time. The one the window is on has a `✓`.
- **add machine…** asks for a destination, anything `ssh` takes, such as `devbox` or `me@gpu-box`.
- **forget…** takes a machine off the list.

The shells and agents of the machine you leave keep running there, and when you come back the window shows them as they are now. Until the other machine answers, the window says where it's going and stays where it was: **back** (or `Esc`) returns at once. If the switch fails, for instance because `ssh` refused the key or the other machine runs another version, the window says why and you stay where you were.

Before reaching a machine it has never reached, the window asks first: **connect** (or `Enter`) goes, **back** stays. The question comes from the window on your laptop, not from the server it shows, so a server on another machine can't send your laptop's `ssh` anywhere without you.

<Aside>
Like reconnecting, switching never asks for a password, a passphrase or an unknown host key, since the window holds your terminal. Use a key in your SSH agent, and for a new host run `cornercase remote <host>` once in a terminal, so `ssh` can ask you about its key; that also puts it on the list.
</Aside>

The list is kept on your laptop, in `machines.json` in cornercase's state folder (`~/.local/state/cornercase/`, or `%LOCALAPPDATA%\cornercase\` on Windows), beside `remote-shells.json`. The button shows only once a window has reached another machine, so it stays out of the way if you never use one. With the [icon bar](../projects-workspaces-tabs/#the-icon-bar) it's an icon above **`Help`**, and on a [small screen](../small-terminals/) it shares the **`Worktrees`** band of the projects menu.

## Versions

For the window, both machines must run the same version of cornercase. When they don't, it says which one to update before opening the window:

```text
`devbox` runs cornercase 0.11.9 and this machine 0.11.12. Run `cornercase update` there
```

When the other machine is the older one, it offers to run `cornercase update` there for you, through `ssh`, and attaches once that is done. When yours is older, run `cornercase update` on it.

The [commands for scripts and agents](#commands-for-scripts-and-agents) are more relaxed: the other machine may run the same version or a newer one, so a script on your laptop keeps working when only `devbox` updates. When the other machine is the older one they refuse, since its server could ignore what a newer command asks for, and say how to update it from here:

```text
`devbox` runs cornercase 0.11.9 and this machine 0.11.12. Update it from here with `cornercase --remote devbox update`
```

When the binary on the other machine was updated but its old server still runs, cornercase asks before restarting it, as it does [on your own machine](../../reference/command-line/#a-server-from-another-build), and then runs `cornercase kill-server` there. After an update from the window's own [update dialog](../../installation/#update), which updates the other machine, the window reconnects to the new server by itself, and tells you if your laptop now needs the same update.

## Commands for scripts and agents

The commands for [scripts and agents](../scripts-and-agents/) reach another machine's server too, with `--remote`. A script, an agent on your laptop or another interface can drive the server on `devbox` without building the `ssh` line itself:

```sh
cornercase --remote devbox status --json
cornercase --remote devbox events --notices --host --json
cornercase --remote devbox send --pane 12 - < prompt.md
cornercase --remote devbox files list '~/src' --json
cornercase --remote devbox paste-file --pane 12 shot.png
cornercase --remote devbox clone git@github.com:acme/shop.git '~/src'
cornercase --remote devbox start-server
```

`CORNERCASE_REMOTE=devbox` does the same without the flag, and the flag wins. Set it for one program, never in a shell's rc file: it also applies in your panes, and the commands it sends away would stop acting on this machine. `--remote-command` is `--command` for these commands.

- **Arguments and standard input arrive as they are**, whatever the login shell there is: they travel inside cornercase's own messages, not through a shell.
- **The other machine may be newer** than this one, but not older: the window needs the same version on both, the commands accept a newer one there and refuse an older one, saying how to update it with `cornercase --remote devbox update`.
- **It never asks** for a password, a passphrase or an unknown host key, since a script cannot answer: use a key in your SSH agent, and connect once by hand to accept the host key.
- **Only `start-server` starts a server there.** The other commands say `no cornercase server is running on devbox`, as they do on your machine.
- **A stream ends there when the command ends here**, even when it is killed, so `events` or `status --follow` never leaves a command running on `devbox`.
- **Ids are that server's, and last one run of it.** `cornercase --remote devbox close --workspace 7 --boot BOOT` or `rename --workspace 7 NAME --boot BOOT`, with the `boot` of the `status --json` you read the id in, refuses with status 4 when the server there restarted since, instead of acting on whatever has that id now. See [Arrange](../scripts-and-agents/#arrange).
- **Paths are the other machine's**, and the ones you type must be absolute: `open`, `clone` (its folder and a repository's path), `config project` and `flow save --path` refuse a relative one. On a Windows machine they are Windows paths, such as `C:\Users\me\src` or `\\host\share\src`. `open` and `clone` also take `~/…`, in that machine's home folder (`clone` without a folder clones there), and `status` shows `~/…` for paths there. A `.code-workspace` file given to `open` is read there too, so its folders are that machine's. `files` paths are relative to the workspace, or absolute or `~/…`. The exception is `paste-file`'s file, which is read here.
- **Give an agent there a file from here**: `cornercase --remote devbox paste-file --pane 12 shot.png` copies the file to `devbox`, keeps it in cornercase's state folder there and pastes its path into pane 12, so the agent in it can open it, with no `scp`. See [Paste a file from another machine](../scripts-and-agents/#paste-a-file-from-another-machine).
- **Clone there with files from here**: `cornercase --remote devbox clone git@github.com:acme/shop.git '~/src' --file .env --from ~/code/shop` reads `.env` here, from the repository `--from` is in, and the clone there gets it, with no `scp`. See [Clone a repository](../scripts-and-agents/#clone-a-repository).
- **Another interface can show that machine's files**: `files list`, `files read` and `files search` give the files panel's tree, viewer and search, and `files list ~/` a folder picker's listing, so a UI on your laptop needs no `ssh` of its own to read that disk. See [Browse and read a workspace's files](../scripts-and-agents/#browse-and-read-a-workspaces-files).
- **`update`, `restart`, `kill-server` and `logs` run on that machine**, as its own `cornercase` through `ssh`: they ask their questions when you are at a terminal (`--yes` skips them), print what they print there and exit with the status they have there. `logs --follow` follows that machine's log and ends when nothing reads it. Ending or killing the command here calls off a `--when-idle` restart that waits there, as `Ctrl+C` does on your own machine (both machines need 0.12.226 or newer). The plugin commands that install or change plugins still act on the machine they run on and refuse `--remote`, with status 2.

```sh
cornercase --remote devbox update --yes
cornercase --remote devbox restart --when-idle --yes
cornercase --remote devbox logs --follow
```
- **`cornercase --remote devbox` alone** opens the window, as `cornercase remote devbox`.
- **`input --follow` types through one connection**: a program that draws the terminals keeps one running for everything it types, instead of a command, and an `ssh` connection, for each batch of keys.
- **`requests --follow` sends every command through one connection**: a program that draws cornercase keeps one running and pays a round trip per action instead of an `ssh` connection, as [Many commands through one process](../scripts-and-agents/#many-commands-through-one-process) describes.
- **One `ssh` connection per command** (except those two). To share one, use your own config:

```text
Host devbox
  ControlMaster auto
  ControlPath ~/.ssh/cm-%C
  ControlPersist 10m
```

## Good to know

- **Latency**: every key goes to the other machine and comes back as a screen update, the same as typing in plain `ssh`.
- **One window, one server**: the sidebar shows the projects of one machine, though your [machines](../machines/#in-your-sidebar)' workspaces do show in yours. Open another window to work on another machine.
- **A link to each of your machines**: list them in **Settings › Machines**, and your cornercase server keeps a link to the server on each one, starting it when none runs and never stopping it. See [Machines](../machines/).
- **Commands for scripts and agents** act on the server of the machine they run on, unless you give them [`--remote`](#commands-for-scripts-and-agents).
- **Inside a pane**: `cornercase remote` works inside one of cornercase's own panes, unlike `cornercase`, since the other server is a different one.
