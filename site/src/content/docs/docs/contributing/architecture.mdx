cornercase is a single Rust binary that plays two roles: a **server** that owns every terminal and all the state, and a thin **client** that only shows frames and forwards input. This page explains how the pieces fit, for contributors. The reasons behind each decision are kept in [`DESIGN.md`](https://github.com/usecornercase/cornercase-terminal/blob/main/DESIGN.md) in the repository.

## The big picture

```text
 terminal ─ cornercase ─┐                     ┌───── cornercase server ─────────────┐
 terminal ─ cornercase ─┼── Unix socket ────▶ │  App ──▶ View ──▶ frame per client  │
 terminal ─ cornercase ─┘  events ▶  ◀ frames │   ▲                                 │
                                              │  PTYs + libghostty-vt emulators     │
                                              └───┬─────────────────────────────────┘
                                                  ▼
                                    your shells, editors and agents
```

- `src/main.rs` hands the arguments to `cli.rs`, which parses them with `clap`: none for the client, `server`, or `kill-server`; `restart` restarts the server; `update` installs the latest release and restarts the server; `--version` only prints the version; the [commands for scripts and agents](../../guides/scripts-and-agents/) send one request to the running server and print its answer.
- The **client** (`client.rs`) starts the server if needed, queries the outer terminal's colours and name, sets up raw mode, mouse capture, bracketed paste and the kitty keyboard flags, sends a `Hello`, then has two jobs: write every frame it receives to stdout, and send every crossterm event it reads to the server.
- The **server** (`server.rs`) owns the `App`, every PTY and every emulator. It renders a ratatui frame for each client and sends the bytes.

## The server loop

The accept thread, one reader thread per client, the signal thread and a forwarder for PTY output all send `ServerEvent`s down one `mpsc` channel. Each turn of the loop:

1. drives pending agent launches, answers the waits of the commands for scripts whose condition holds and, at most once a second, looks for new git worktrees;
2. draws one frame per client;
3. lets the session `Saver` decide whether to write the session to disk;
4. waits for an event or a 500 ms tick, then drains everything queued, feeding input and PTY output to the `App`.

Each step (the refresh, sending the answers to commands, the draw, the save and every event) runs under `catch_unwind`. A step that panics is dropped, the loop goes on, and the user sees `cornercase hit a bug, see server.log`; a command for scripts that the panic left without an answer fails with the same message instead of waiting forever; a panic in input or drawing also closes the open dialog or menu and ends any drag, and one while drawing starts every client's screen over. Otherwise a single bug would end the process and every shell in it. Background jobs that the UI waits for turn a panic into an error answer (`panics::job`), so no dialog stays busy forever. That is why every profile must keep `panic = "unwind"`.

After every step that can change the app (a refresh, input, a command, a background job's answer), `App::trace` compares the projects, workspaces, tabs and panes, the focus and the open dialog with what it saw before and writes what changed to `server.log`, so each code path doesn't have to log on its own. Lines are formatted on the thread that logs them and written by a thread of their own, so a slow disk never holds up the loop. When you debug cornercase, start with `cornercase logs`, and restart the server with `CORNERCASE_LOG=debug` to see every event it handled. What the log may and may not contain is in `DESIGN.md`, under Log.

Each client has its own writer thread, so a slow client never blocks the loop. All clients share one size, that of the client that attached, typed or clicked last (a smaller client gets the frame cropped), and see the same `App`, which is why hover, menus and scroll positions are mirrored.

## Protocol

`protocol.rs` frames messages with a little-endian length prefix and encodes them with `postcard`; messages over 64 MiB are refused.

- `Hello` carries a protocol version and a build id (the executable's modification time). A server rejects a client from another build with `ServerMessage::Rejected`.
- After an in-app update, or when `cornercase update` sends `ClientMessage::Restart`, the server saves the session and sends every client `ServerMessage::Restart`; each client waits for the old server to exit and runs its own executable (which the update replaced), and that starts a new server. A server from before `Restart` cannot decode it and answers `Rejected`, so `cornercase update` falls back to `KillServer`.
- `ClientMessage::KillServer` and `ServerMessage::Rejected` must stay the first variants of their enums, so that any two builds can still tell each other to stop. `protocol::tests::compatibility` guards this.
- The commands for scripts send `ClientMessage::Request` and get one `ServerMessage::Response`, both carrying JSON (`control.rs`) instead of postcard, so a command and a server from different releases still understand each other: unknown fields are ignored, and an unknown command is answered with an error that names the server's version. They skip the build check of `Hello`, and a server from before them answers `Rejected`. The server handles a request on its loop like input, but it never counts as a use, so it never changes the shared size. Waits stay in `App` (`app/control.rs`) as pending requests, checked on every turn of the loop, and are dropped when their client goes.
- One server per socket is enforced with `flock` on `server.lock`. The server calls `setsid` and ignores `SIGHUP`.

## Rendering

`ui::draw` takes a plain `View`, built by `App`, and knows nothing about PTYs. That makes every screen testable with ratatui's `TestBackend` and `insta` snapshots.

Geometry functions such as `ui::layout`, `entry_row`, `workspace_row`, `form_buttons` and `picker_item` are shared by drawing and hit testing, so a click lands exactly on what was drawn, and tests take their click positions from the same functions.

Colours are palette indices (cyan, the brand purple `99`, the surfaces `236` and `254`, the lines `239` and `250`), so the user's terminal theme applies. Grey text is `View::muted`: the theme's bright black, or the fixed greys `243` and `245` when that one would not show (`ui::muted`). Below 90 columns, `ui::compact_layout` reuses the same areas with a top bar and three-row bands.

## Terminal emulation

Panes are emulated with [libghostty-vt](https://github.com/ghostty-org/ghostty), Ghostty's terminal core, wrapped in `emulator.rs`:

- It answers the terminal queries programs wait for (DSR, DA, DECRQM, kitty keyboard queries…) and reflows text on resize.
- Its types are `!Send`, so every emulator lives on the server's main thread; each PTY's reader thread only forwards bytes. Replies go out from `on_pty_write`, in order with the output that asked for them. Everything written to a PTY, keys, pastes and replies alike, goes through a writer thread per pane, so a program that stops reading never blocks the server.
- Cells keep palette indices. The colours queried from the outer terminal (OSC 10, 11 and 4, with DA1 as an end marker) become every emulator's defaults. The same query asks for the terminal's name (XTVERSION), which decides how desktop notifications are written to it.
- `take_copied` hands over OSC 52 clipboard writes from programs; reads and primary-selection writes are dropped.

Keys are encoded in `keys.rs`: Ghostty's encoder for special keys, and for every key once a program enables the kitty protocol; a legacy encoder for the rest. Mouse events are encoded in `mouse.rs`, in the mode and encoding the program asked for, relative to its pane.

`process.rs` finds the cwd, name and arguments of a PTY's foreground process: `/proc` on Linux, `proc_pidinfo`, `proc_name` and `sysctl(KERN_PROCARGS2)` on macOS (the only `unsafe` code). Tab names, agent detection and agent launches depend on it. It also lists a process's descendants and reads the memory each holds on its own (`RssAnon` and `VmSwap` in `/proc/<pid>/status`, `ri_phys_footprint` from `proc_pid_rusage` on macOS) for the memory on a tab's second line.

## State and side effects

- **Ids, not indices.** Every project, workspace, tab and pane gets an id from one counter. Menus, dialogs and background jobs refer to ids, so nothing breaks when the lists change underneath them.
- **Closing is asynchronous.** Closing kills processes; a pane is removed when its shell exits, whether its PTY reader sends `Exited` or `App::refresh` finds the shell reaped first (a detached process can keep the PTY open long after the shell is gone).
- **Pure state machines.** `issues::browser::Browser`, `settings::Settings` and `launch::Launch` contain no I/O: they take input and return actions or steps, which `App` carries out on threads. Answers carry their query and issue key, so stale ones are dropped.
- **Saving settles.** `state::Saver` writes `session.json` (and `todos.json`) only after the state has been stable for 2 seconds, and `state.rs` migrates older session versions.

## Module map

| Module | Responsibility |
| --- | --- |
| `main.rs` | Hands the arguments to `cli.rs` (the only place using `anyhow`). |
| `cli.rs` | The `clap` definitions of every command, and the commands for scripts: sending a request, printing its answer. |
| `control.rs` | The JSON of requests and answers, shared by the commands and the server. |
| `client.rs` | Terminal setup and teardown, colour query, starting the server, forwarding events, writing frames; `kill-server`, `restart` and `update`. |
| `server.rs` | The daemon: owns `App` and every terminal, accepts clients, draws a frame per client. |
| `panics.rs` | Containing panics: `catch_unwind` around each step of the server loop and each background job, and the hook that writes them to `server.log`. |
| `log.rs` | `server.log`: levels, the `key=value` line format, the writer thread and its rotation, background job timings, and `cornercase logs`. `app/trace.rs` logs what changed in the app after each step of the server loop. |
| `protocol.rs` | Messages, framing, socket and lock paths, build id. |
| `app.rs` | Application state; turns events into actions; builds the `View`. `app/control.rs` answers the commands for scripts and keeps their waits. |
| `ui.rs` | Layout, hit testing and drawing from a plain `View`; `ui/tab_bar.rs` lays out and draws the tab bar above the pane. |
| `project.rs` | Project › workspace › tab › panes, labels, removal. |
| `split.rs` | A tab's split tree: rects, dividers, splitting, removing, ratios. |
| `term.rs` | A shell in a PTY, its emulator, and the reader thread. |
| `emulator.rs` | The libghostty-vt wrapper; plain snapshots for the UI. |
| `keys.rs`, `mouse.rs` | Key and mouse encoding for programs. |
| `host_theme.rs` | Asking the outer terminal for its colours and its name. |
| `notify.rs` | Desktop notifications through the outer terminal: which escape sequence each terminal understands, and how it is written. |
| `process.rs` | A process's cwd, name, arguments, environment, children and memory footprint, per platform. |
| `git.rs` | Branch from `.git/HEAD`, repository roots, linked worktrees, without running git. |
| `worktree.rs` | `git worktree add` and `remove`, checkout paths, `.worktreeinclude`. |
| `issues/` | The issue model and clients for GitHub (`gh`), Shortcut (REST), Linear (GraphQL) and Jira Cloud (REST, with an Atlassian Document Format to Markdown converter), the browser state and the on-disk cache. |
| `agents.rs` | Known agents, modes and arguments, choosing and detecting an agent, the trust prompt. |
| `activity.rs` | What the agent in a pane is doing: Claude Code's session file and terminal title, Codex's terminal title and turns, opencode's turns, and the finished-but-unseen mark. |
| `context.rs`, `context/codex.rs`, `context/opencode.rs` | Model/context lines for Claude Code, Codex and opencode. Claude uses its session transcript and configured window rules; Codex follows the process's open rollout, recorded model and latest usage/window, reading incrementally and clearing obsolete context on session changes and compaction. opencode reads the SQLite database its process holds open, on a thread: the session in its folder, whether a turn is running, and the last answer's tokens over the window in opencode's `models.json`. |
| `memory.rs` | How much memory a pane uses: the memory its shell and everything under it hold on their own, measured on a thread every 2 seconds. |
| `usage/` | Plan usage: `claude.rs` asks `claude` over its control protocol, `codex.rs` asks `codex app-server` over JSON-RPC; `mod.rs` runs either, reads the answer and keeps the dialog's state, one section per agent. |
| `launch.rs` | Starting an agent in a new tab, as a pure state machine. |
| `todo/` | The TODO list (`mod.rs`: ordering, undo, `todos.json`) and the text field with a cursor (`editor.rs`); `ui/todo.rs` draws the panel and `app/todo_panel.rs` wires it into `App`. |
| `files/` | The files panel: its state per workspace, the tree's git marks and the marks beside each line (`mod.rs`), reading folders and files on threads (`disk.rs`), the list of files and the name and text searches (`search.rs`), and the paths printed in panes (`link.rs`); `ui/files.rs` draws the panel and `app/files_panel.rs` wires it into `App`. |
| `syntax.rs` | The files panel's highlighting: tree-sitter grammars through arborium, the language of a file, palette colours. |
| `markdown.rs`, `highlight.rs` | Markdown to wrapped lines; syntax highlighting of code blocks with palette colours. |
| `search.rs`, `picker.rs` | Global search; the folder picker. |
| `settings.rs`, `config.rs`, `secrets.rs` | The settings modal; `config.json`; `secrets.json`. |
| `state.rs` | The saved session, its migrations, and the `Saver`. |
| `update.rs` | The hourly check for a newer release on GitHub and its changelog; downloading, verifying and swapping the binary. |
| `clipboard.rs` | OSC 52. |
| `error.rs` | The library's error type. |
