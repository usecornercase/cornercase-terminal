# Settings

Code: `config.rs`, `settings.rs`, `settings/`, `settings/search.rs`, `app/settings_dialog.rs`, `app/share_settings.rs`, `app/share_settings/`, `app/share_settings_dialog.rs`, `ui/dialog/share_settings.rs`, `cli/config/share.rs`

- `app/settings_dialog.rs` assembles `ui::Settings` from the model, and `App::overlay_view` wraps it in `ui::Overlay::Settings`. Sections, removal and movement controls, pick items and scroll, edit errors and the busy note belong to that assembly. The model imports no `ui` types.
- `Settings` owns the row labels, values, notes and danger flags as `RowText`, the edit field's label and masked value, the pick title and clamped selection, and the hint. These are rules about the settings, so their existing text tests read the model directly. `Row::movable` is shared by view assembly and mouse hit testing; both must offer source reordering on the same rows. Sidebar and tab choices are read from `config`, their owner.
- **Flows tab** (#322): flows were one row of the Agents tab that opened a dialog, which hid them: they are teams and plans, with their own list, diagram and editor. The tab is `Overlay::Flows` drawn in the settings frame (`Dialog::in_settings`), not a page of the `Settings` model: one model keeps the list, editor, import page, confirmations, model reads, fetch jobs and `refresh_flows`, so the settings model has no flows code and `Page::Flows` has no rows. Choosing the tab (a click, `Tab`, `←` `→`, or reopening on the remembered page) makes `open_flows_tab` replace `Overlay::Settings`; a click on another tab or `Tab`/`←`/`→` at the list level (`Action::Tab`, `Action::StepTab`, via `Page::step`) goes back through `open_settings`. `↑` `↓` move between flows there, and the buttons end with ` restart ` and ` done ` like every settings tab. The settings dialog takes the Flows dialog's size, 140×40, **on every tab** (`settings_area` is `flows_area`), so switching tabs never moves the tab row or the buttons, the diagram fits beside the list from 112 columns and the editor opens in the same box; the alternative of 110×30 would always put the diagram behind a button. Only the editor and import page change the title (`Flows › X`) and drop the tabs. The start dialog's ` edit ` keeps its own frame (title `Flows`, no settings tabs), since a click on a settings tab there would leave the start dialog behind, as Settings has no back. The icon bar's Settings is lit for `Overlay::Flows` too. Agents added with `+ another agent…` and not configured stop being listed after a visit to the tab (its transient state goes with the overlay).
- Tabs: Worktrees, Agents, Accounts (see Accounts and profiles), Flows, Issues, UI, Remote (the browser, then a section per chat app: Telegram, Discord), Plugins (see Plugins). Every change is saved to `config.json` at once (turning a plugin on or off goes to `plugins.json`). The prefix key row is the one that captures a key instead of editing text (see Keyboard shortcuts). File: `$XDG_CONFIG_HOME/cornercase/config.json` (a debug build's `cornercase-dev/`), or next to the socket when `CORNERCASE_SOCKET` is set (so tests never touch the real one). Missing keys take defaults; a file that cannot be read at start means all defaults, and while the server runs it keeps the settings in use (below).

- **config.json is watched** (#336, `app/config_file.rs`): it was read once, in `App::new`, and every save wrote the whole in-memory copy back, so an edit from outside was neither seen nor kept. `App::watch_config`, in `refresh_at` right after `reap`, looks once a second at the file's mark (inode, modification time and size: `persist::mark`, shared with the `plugins.json` watcher) and applies a change through `set_config`, so an outside edit has the modal's live effects: `remote` starts or stops browser access and `keep_awake` takes effect in the same refresh (both reconcile from `self.config`), layout keys on the next draw, tracker caches are forgotten, and an open modal shows the new values (`Settings::take_config`). The mark of cornercase's own write is taken from the temporary file just before the rename (`persist::write_marked`; a rename keeps inode, time and size), not by a `stat` after it: a program writing right after ours would otherwise be taken for our own write and lost. An unreadable file (invalid JSON, a wrong type, a FIFO, over 4 MiB: `config::read` opens it non-blocking and refuses what is not a regular file, so a FIFO named `config.json` cannot hang the server loop; `O_NOFOLLOW` is not used, since dotfile managers symlink it) keeps the settings in use, logs a `WARN`, shows a toast and puts `problem` in `config`'s answer; cornercase then refuses to write over it (the modal's note, a request's `conflict`) until it is fixed or removed. This changes today's behaviour, where the first save wrote the defaults over a corrupt file. A missing file while the server runs also keeps the settings (editors rename a file and write a new one, so for a moment there is none) and the next change writes it again; only a server that starts with a broken file runs on the defaults, and it does not write until the file is fixed.
- **One write path** (#336): every change to `config.json` goes through `App::change_config` (or `write_config` for a whole `Config`): it reads the file again if its mark changed, then writes only the top-level keys the change touches (`config::Changes`, a project's entry only for project settings), over what is on disk. The five writers use it: the modal's `Action::Save`, the project settings form, the issues browser's default agent and connection forms, and the Flows tab's hidden list; `config::save` is called nowhere else. The rule when both sides change at once: a change made in cornercase is applied to the file as it is on disk at that moment, so the rest of an outside edit stays, and a key changed in both places takes cornercase's change, which came last. A write that lands between cornercase's read and its rename is lost; that window is a few microseconds, and a lock file was rejected as more machinery than the window deserves. The five writers' errors keep their text (`failed to save the settings: …`).
- **Settings through the server** (#336, `control/config.rs`, `settings/describe.rs`, `settings/apply.rs`, `app/control/config.rs`, `cli/config.rs`): a GUI needs a preferences screen, and the modal's rules were reachable only by clicking. The `config` request drives the `Settings` model instead of copying its rules: `describe` walks `every_row()` (the modal's rows without the page filter) and `apply` goes to the row, then flips it, edits it with the value as the input and submits it, or picks it, so the checks, the refusal texts, the notices and the live effects are the modal's own, and a new row without a key fails `settings::tests::requests` until it has one. The settings are the modal's rows (Worktrees, Agents, Issues, UI, Remote) with the key of their `config.json` entry; an agent's two rows are `agents.<kind>.mode` (a choice, only for agents with modes) and `agents.<kind>.extra`, for every known agent, not only the listed ones; the eight issue tabs are one `list` setting, `issue_tabs`, since the modal's rows are one checkbox each but the config is one ordered list. Choices are checked against `describe`'s, never the pick's items (the UI-only `extra arguments…` is not a value). Left out: the Plugins page (it has `cornercase plugin`; its rows are the `plugin-list` request since #343), the Flows page (the `flow-*` requests), and the keys with no row (`prompt`, `gh`, `glab`, `agent_modes`, `agent_commands`, `trust_prompt_pattern`, `remote_port`, `hidden_flows`), which are edited in the file, now applied live; `get` gives its `path`. **Connections** are rows with a removal, not settings: a tracker's token (`shortcut`, `linear`, `jira`, `plane`, `gitlab`, `asana`), the paired `browsers`, a bot (`telegram`, `discord`) and its chat (`telegram.chat`, `discord.chat`), with a `state` (`missing`, `connected`, `refused`), the `account` it is connected as, where a token comes from (`saved` or `env`) and whether `remove` does something now. **`restart`** is a flag on each setting and false for all of them: every row is read live through `App.config` (`resume_agents` applies at the next restore by design, and its note says so; `remote_port` has no row and takes effect the next time browser access starts). **Pairing a phone stays in the window**: it is a QR code with a single-use ten-minute token; `get` shows the chat and `remove` forgets it. **Discord's forum mode** (#437, see Discord) is a switch, `discord_forum`, set like any other, but its setup stays in the window too: `set` never opens the dialog, so the mode waits until someone opens it, and `get`'s note names the first step left. Like every row, its key exists only while its row shows (a bot and a paired chat), so `set discord_forum` before pairing is `there is no setting`.
- **The forum mode row** (#437, `Row::Forum(Via)`, Remote › Discord, under **phone**, only with a bot and a paired chat: the mode needs the owner's identity and the DM to fall back on): `[x] on` / `[ ] off`, with a note that, off, says what the mode does (the value already says off) and, on, says `<server> › #cornercase` when ready, else the first step left or the last failure (`enter sets it up` before Discord was read). `Enter` on it while off turns it on and opens the setup dialog (`Action::Forum` carries the new config, since an action is one thing and turning on must also save); while on but not ready it opens the dialog again; while ready it turns the mode off. Each change applies live: turning it on or off restarts the link with the intents of the mode.
- **The closed workspaces row** (#437, `Row::ForumClose(Via)`, right under **forum mode** and only while `discord_forum` is on, since it means nothing without posts): a pick of `archive` (the default) or `delete`, saved as `discord_forum_close` and read when a workspace's post is cleaned up, so a change applies to the next workspace closed, not to posts already archived. Archive is the default because it can be undone (see Discord). A value the app does not know reads as `archive`, the safe one; `config set` refuses it like any choice. Its key, like the row, exists only while the mode is on.
- **The revision** (#336): `config_file.revision` starts at 1 and goes up through `App::settings_changed`, called by `set_config` on a real change (the modal, a dialog, a request, an outside edit), when a `problem` appears, when a tracker's account is learned or forgotten (`learn_account`, `forget_issues`), by every `refresh_messenger_note` (a bot set, removed, refused, paired, forgotten), and when the paired browsers are forgotten or one pairs; it also marks the watch snapshot changed, because `trace_refresh` only does on agent reads. `Report.config` is `{"revision"}`, always present from this server, so a missing one can only mean an older server. Notes that move by themselves (the keep-awake state, pull requests, a problem reaching Telegram) do not bump it: `get` reads them.
- **Sharing settings** (#414, `settings/share.rs`, `settings/share/`, `app/share_settings.rs`, `app/share_settings/`, `app/share_settings_dialog.rs`, `ui/dialog/share_settings.rs`, `cli/config/share.rs`): setting cornercase up the way a team works (branch template, prompt, agents and their modes, arguments and commands, the worktrees folder, issue tabs and tracker settings, each repository's setup and teardown, the UI switches) took a colleague a row at a time, or a copied `config.json` that carried machine paths and personal values and said nothing about what was missing. It is a **one-off hand-off**, the `flow export` / `flow import` pattern applied to settings: copy a text (or write a file), paste it on the other machine, see every change, untick what is not wanted, confirm. **Team defaults kept in a repository** (a `.cornercase/config.toml` read like `.cornercase/flows/`) were left for later by the user's decision, as were syncing between machines; flows (they have `flow export`), plugins, the session, stats, TODOs and the queue are not settings to hand over.
  - **What goes in** (the contents are the user's decision: every Settings row, the UI included; the sections are a design choice): five sections, `agents`, `issues`, `worktrees`, `interface` and `repositories`, each a table the importer can untick. Left out: every secret in any form (tracker tokens, `*_TOKEN` variables, bots, paired chats and browsers) and what is personal or bound to a machine (`jira_email`, `remote`, `remote_port`, `keep_awake`, accounts and profiles, and Discord's `discord_forum` and `discord_forum_close`, which belong to the user's own bot and server), `hidden_flows`, `default_flow` and `flow_order` (they name flows the colleague may not have), and `projects`, which goes as `repositories`. A key of `Config` in no section and not in the left-out list fails `settings::share::tests`, so a new setting is placed on purpose, as `settings::tests::requests` does for the `config` request. **Export writes every key of a section**, defaults included, so the importer gets the exporter's setup exactly; the preview lists only what differs, and a key the file does not mention (an older build's file) is left as it is, never reset.
  - **The format is TOML**, like flows: readable before it is accepted, and it diffs in a chat. `toml`'s `preserve_order` keeps the file in the sections' key order and the unknown keys in the file's order. `version` goes up only for an incompatible change of the format (a key renamed, a section moved, a meaning changed), never for a new setting; a missing one is refused as not a setup and a higher one with "update cornercase". **An unknown key is skipped and named, not refused** (the user's decision): since export writes every key, every file from a newer build carries settings an older one lacks, and refusing would make every export from a newer build fail on older ones; the preview names it, so nothing is dropped silently. A known key in the wrong section counts as unknown. Paths stay as written (`~/…`). 256 KiB at most on export, import and paste, for the flows' reasons (OSC 52, tmux's buffer); a leading BOM is ignored and parse errors say `line N:`. `connect` lists the trackers the exporter is connected to, by id only, so the preview can say which to connect; never a token, an account or an email.
  - **Repositories are keyed by their git remote, not their folder** (the user approved it): folders differ between machines, remotes do not. Each entry lists every remote of the folder as `host/path`, origin first, so a fork's `upstream` still matches a colleague's clone, and it always carries both `setup` and `teardown` (an empty one as `""`): it is the whole project setting, not part of one. An entry matches every open repository root with one of those remotes (the host compared in lowercase); two entries matching one project are refused, naming both; one with no open match is named in the preview and skipped. A folder that is gone or has no remote, and a second folder sharing a remote, are named in the export's notes instead.
  - **An import is all or nothing**: the result is built on a copy of the `Settings` model and `config.json` is written once through `write_config`, so a newer version, an invalid value, a bad repository or an unreadable `config.json` leaves the file byte for byte as it was. Keys with a row go through `Settings::apply`, so the checks, refusal texts, notices and live effects are the modal's; the keys with no row (`prompt`, `gh`, `glab`, `agent_modes`, `agent_commands`, `trust_prompt_pattern`, and `agent_args`, kept in its raw `config.json` shape rather than translated into `agents.<kind>.extra`) are set on the `Config` after serde reads them, as an outside edit of the file would be. Repositories go through the `config` request's `project` rules (a repository root, `ProjectSettings::normalised`). **The preview runs the same build and refuses as an import would**, so what it shows can be applied. Only the ticked sections are applied; the log says `config imported` / `config exported` with sizes and section names, never values.
  - **The preview's notes**: in red, what will run unattended (setup and teardown in full, as flows show `env` and `args`: each is a change of its own, `repositories.setup` or `repositories.teardown`, labelled with the project's folder and carrying the whole script, so the window draws each of its lines on a row of its own in red, wrapping a long one rather than cutting it (as it wraps every long change line: the preview scrolls only up and down, so a cut value could not be read), and the CLI prints them indented under the change; one string joining both scripts lost the line breaks in the window and read the teardown as part of the setup; `agent_commands`, `gh`, `glab`; a built-in mode `agents::is_dangerous` flags, once a kind's new `agent_args` hold its arguments and the current ones do not: judged against the built-in modes only, never the file's `agent_modes`, since a file could rename the dangerous arguments as a longer harmless-sounding mode, or blank the built-in one, and hide them from the note; trust prompts answered by themselves); what is missing on this machine (a path, `worktrees_dir` saying it will be made, a program not on the `PATH`, an agent not installed); trackers to connect; unmatched repositories; unknown keys; possible secrets. **Secrets typed into free text** (setup, teardown, `agent_args`, `agent_modes` (every level of a nested value is read, named `agent_modes of claude.fast`), `agent_commands`, `prompt`, `trust_prompt_pattern`, the tracker filters) are copied as they are, by the user's decision: export warns in red where a name holding `TOKEN`, `KEY`, `SECRET`, `PASSWORD` or `PASS` gets a value, a `--…key`/`--…token` flag takes one, or a long `Bearer …` appears (in the toast, on the CLI's stderr, and among the preview's notes), and never redacts or refuses, as `share::env_warning` does for flows. Since it may hold one, `config export --to` writes the file readable only by its owner (`0600`), also over an existing file that was open to others. The notes that belong to no section (secrets, trackers to connect) always show, whatever is ticked.
  - **In the window**: a ` share ` button before ` restart ` and ` done ` on every tab with those buttons (on the Flows tab's list it is the first dropped when the row is narrow) opens **Settings › Share** in the settings' frame, without tabs: ` copy my setup ` copies through `App::copy` (OSC 52) and the toast says how many settings and repositories went and what was left out, counting the repositories the export's `left_out` names beyond the fixed entries (`NEVER_SHARED`: a folder with no remote, gone, or sharing a remote with an earlier one), and the hint line names each of them before the possible secrets, since a toast cut at the window's width was the only place they showed; a paste field like the flow import page's, and ` preview `, whose error stays under the field. **Settings › Import** lists a checkbox per section with its changes and notes, and ` back ` and ` import `; a section with no changes cannot be ticked. A paste on a Settings tab with no field open opens Share with the text, as a paste on the Flows list opens its import page. The model (`settings/share/dialog.rs`) keeps its own sizes and imports no `ui` type. Over the socket and on the command line: `config-export` and `config-import` (see Commands for scripts and agents › Reading and changing settings).
- **Searching the settings** (#561 step 1, `settings/search.rs`, `app/settings_dialog.rs`, `ui/dialog/settings.rs`): finding a setting meant knowing its tab. The field sits under the tab row, in what was the blank row, so the body keeps its size and hits. Decisions, the user's after looking at Zed, VS Code and herdr:
  - **Word prefix, every word (AND)**, over label, section, tab, value and note: `def ag` finds default agent, `ose` nothing. The issue's exact, prefix, substring was dropped, and so was fuzzy: Zed went from fuzzy through BM25 to prefix because of noise, and its users asked for all words. Words split on anything not a letter or digit, in the query too, so `ctrl+b` is two words. Rank is where the worst word matched: label, then section or tab, then value or note; ties keep the tabs' order, then the rows'.
  - **The field has the keys whenever the modal is idle**, with no focus state, so opening it (prefix `,`, `f ,`, the button) is ready to type. While it is empty every key without text meaning (arrows, `Enter`, `Space`, `Tab`, `Backspace`, `Esc`) keeps its list meaning, so the modal works as it did; letters did nothing there before. With text, `↑` `↓` pick, `Enter` goes, `Esc` clears, the rest edit. A capture, an edit field or a pick is checked first, so a prefix key being captured never reaches the field. `Backspace` that empties the field must not go on to remove the selected row, so removal waits until the list is used again (`Finder::just_typed`); the Flows tab keeps that across the switch back to its list (`Dialog::erase`), where the same key would ask to delete or hide a flow.
  - **Results replace the rows** while there is a query, as `Tab › label`, with the section only when two rows share a label (`Remote › Telegram › bot`). Each tab shows its count and a tab with none is dimmed, like VS Code's table of contents. A click on a tab drops the query.
  - **A hidden child row is listed muted with what it needs and is never revealed**: all of them are gated by state (a bot, a paired phone, forum mode, a paired browser), so showing one would mean changing that state, and turning forum mode on saves and opens a dialog, too much for a search. Choosing one lands on the nearest row that shows, with a notice, and saves nothing. Choosing any result only selects.
  - **Flows and Plugins**: every tab's name is a result, so `flows` reaches the Flows tab. Single flows are not searched: they are not in this model (see Flows tab) and the tab is one click away. Plugins are rows, so they are matched as rows. The Flows tab draws the same field row; it is `Overlay::Flows`, so a letter typed at its list level opens `Overlay::Settings` on `Page::Flows` with the query, and clearing it returns (`settings_handled`). A click there does nothing more: the list already sends its letters to the search.
  - **A paste** of several lines (`\n` or a bare `\r`) still opens Share; one line goes to the field. A setup is always several lines.
  - **Over the socket** see Commands for scripts and agents › Reading and changing settings: `search` uses the same `Settings::search`.
- **Icons (#450)**: `icons` (`auto`, `on`, `off`) is a choice row of the UI tab like `tabs`, listed after `icon_bar`, and shared like the other interface keys. Its value is global but its effect is decided per window (Layout › Icons), so `config get` reports the setting and never a window's decision, which is drawing and exempt from the contract. An unknown value reads as `auto`.
