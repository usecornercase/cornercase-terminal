# Files panel

Code: `files/`, `highlight/syntax.rs`, `ui/files.rs`, `app/files_panel.rs`, `app/links.rs`

- ` Files ` (on the todo row, under ` Issues `; ` ▤ ` in the compact bar) opens a panel in the changes panel's column with the active workspace's folder, so each worktree shows its own files; git or not. Read only: editing goes through ` open `.
- **Tree**: folders first, then files, by name ignoring case. Where the window draws icons (Layout › Icons, #450), a folder keeps its `▸`/`▾` and gets an open or closed folder icon, and a file the icon of its type, in the same column, so icons line up per level; the name keeps its git status colour and moves two cells right. Each open folder is listed on its own, on a thread, with `ignore` (one level; `.gitignore`, `.ignore`, the global and `.git/info/exclude` rules, also from parent folders; hidden files shown, `.git` never), at most `disk::MAX_ENTRIES` (10,000) entries. Listing per folder rather than walking the whole workspace keeps a huge folder (a home folder opened as a project) free until it is opened. The root and the open folders are listed again every `LIST_EVERY` (2 s) while the panel shows, one job at a time, so files an agent creates appear. Open folders, scroll, the open file and the last one opened live per workspace in `files::Panel`, in memory; the session keeps only whether the panel is open.
- **Viewer**: a click on a file reads it on a thread (`disk::read`): at most `disk::MAX_BYTES` (8 MiB) for text, or `disk::MAX_IMAGE_BYTES` (32 MiB) for a file whose first bytes are a recognised image (see Images), NUL in the first 8000 bytes means binary, invalid UTF-8 is replaced. Only regular files are read: the tree lists a link to a device or a FIFO as a file (a cloned repository can hold one to `/dev/zero`), and reading it would never end, growing the server's memory until it dies with every shell, or block its thread for good, so it shows as binary. The read itself stops after `MAX_BYTES + 1` bytes, so a file that grows after the size check cannot get past the cap. The first read answers plain text at once and the highlighted text after; then the file is checked every `CHECK_EVERY` (1 s) by size and modification time and read again when they change, answering only highlighted text, so colours never flash while an agent writes. Lines are cut at the panel's edge with `…`, tabs are four spaces. ` ‹ ` goes back to the tree or the kept search results, with the file's row marked when it belongs to the workspace. An outside file is remembered as the last file too, per workspace and only in memory, but has no tree row or git margin marks. An image file (by its first bytes, not its name) is not text: see Images.
- **Highlighting** (`highlight/syntax.rs`): tree-sitter through arborium, about 60 grammars compiled in: the languages agents touch most (TypeScript, TSX, JavaScript, Python, Rust, Bash, Markdown, Java, C) and every grammar under 0.3 MB (Go, JSON, YAML, TOML, HTML, CSS, GraphQL, Lua, HCL, Vue, Svelte, Dockerfile, Make…). Grammars weigh 0.01-17 MB each (SQL 9 MB, C++ and Kotlin 5 MB); all 112 of arborium's made a 169 MB binary. A language without a grammar borrows a relative's by its comment syntax (`highlight::syntax::FAMILIES`): `//` JavaScript, `#` Python, `--` Lua, `;` Scheme, so comments and strings come out right and only some keywords stay plain; a hand-written fallback lexer was built and dropped in favour of this table. Every JavaScript file goes to the TSX grammar, whose query colours JSX tags and attributes (JavaScript's does not). The grammar comes from the file name, then the extension, then the shebang. Captures map to palette colours (`highlight::syntax::style`) so the terminal's theme applies: keyword magenta, function blue, type cyan, string green, number and constant yellow, property and tag red, comment the muted grey in italics. tree-sitter was picked for speed and precision: a 3,500-line TypeScript file takes 48 ms against 0.47 s for syntect with fancy-regex and the JavaScript syntax (2.4 s with a real TypeScript one), and it colours types and fields the same everywhere. Sources over `highlight::syntax::MAX_BYTES` (2 MiB) stay plain. syntect still colours the changes panel and Markdown.
- **Git marks** follow the changes panel's project scope: its model for the active workspace, with its mode and base. A changed file gets its status letter and colour in the tree; a folder holding changes gets a `●`, yellow, or green when everything under it is new. Deleted files are not on disk, so only the changes panel lists them. In the viewer every change block of the file's hunks marks the margin (`files::gutter`): `▎` green on added lines, `▎` blue on changed ones, `▁` red on the line after which lines went (`▔` on line 1 when they were above it); an untracked or added file is all green. A click on a mark shows the old lines above the block in red, tinted like the changes panel's removed lines, and another click hides them (`Viewer::unfolded`, keyed by the line the block sits before; `files::Lines` maps rows to lines and old lines).
- **Search**: with icons (#450) a names result and each file of a text search show the file's icon before its path, and the matched lines move right by the same two cells so their numbers stay under the path. One bar under the title (`files::Query`, per workspace), with no query the tree shows everything. It searches the text in the files; the ` ▤ ` at its right switches it to file names and back (`files::Mode`, lit while on). Tabs (tree, names, text) were built first and dropped: one bar with a toggle is less to read, and an empty bar giving the whole tree makes the tree the search's starting point. The bar takes the keys like the changes panel's filter (`Query::focused`; a click on it takes them, any press outside the panel gives them back): typing searches at once, `↑` `↓` pick a result, `Enter` opens it, ` × ` clears it and `Esc` clears it and gives the keys back, or closes the panel when the bar is empty (see TODO panel). Until the answer to what was typed comes, the list keeps the previous results under `searching…` instead of going blank on every key (a text search can take tens of milliseconds on a large repository); an `Enter` pressed meanwhile waits for that answer and opens its first result (`Query::enter`), so typing and pressing `Enter` at once never opens a result of the previous query. Any other key, or a press outside the panel, drops the waiting `Enter`. Both modes search an index of the workspace's file paths (`search::index`: one parallel `ignore` walk with the tree's rules, at most `search::MAX_FILES` (200,000)), built on a thread once the bar is used, when the query changes or the bar takes focus again, and when an already listed folder changes. An idle bar never starts a periodic workspace walk (#494). The tree's existing two-second listings detect additions, removals and renames in the root and expanded folders; changes inside closed folders are picked up on the next query edit or focus. Watching every folder was left out to avoid a second recursive walk and OS watch limits on very large workspaces. A newer request, a workspace switch, closing the panel or forgetting its workspace cancels the previous walk (`AtomicBool`), including before a timed-out job is retried, and late answers are dropped by workspace and generation. The walker uses at most 8 threads, like text search. An answer remembers the index it came from; identical paths keep the same index and cached search answer, so a refresh with nothing new does not search the files again. Measured on a 32,000-file repo: the walk takes 25 ms, a name search 1-20 ms, a text search 52 ms for everything and 1-3 ms for the first 50 matches.
- **Names** (`search::names`): nucleo's matcher (Helix's, fzf's scoring) with its path bonuses and smart case, best `MAX_NAMES` (200) first; on a tie the shorter file name, then the shorter path, so the file a query names comes before longer names in shallower folders (`workspace-session` gave `src/relay/workspace-session-handler.ts` before `src/renderer/src/lib/workspace-session.ts`); the matched letters are lit, and a path too long for the row loses its start so the file's name stays. One job at a time; a newer query waits for it and goes next.
- **Text** (`search::text`): ripgrep's `grep-searcher` and `grep-regex` over the indexed paths on up to 8 threads, the query a literal with smart case (regular expressions were left out: one more thing to learn for a quick look), binary files skipped (a NUL ends the file), at most `MAX_MATCHES` (1,000) matches: each match takes a slot before it is kept, so the threads together never keep more, and the search goes on until one more match is seen, so `Text::capped` (the note's `the first 1000 matches`) means a match was really left out, not just that the count reached the cap. A new query cancels the running search (`AtomicBool`) and starts at once. Results come grouped by file in path order; each line keeps its number, its text without the indent (at most 400 characters) and where it matched, and a long line is shifted so the first match shows. Opening a match opens the file at that line, selected so ` ask agent ` takes it at once, and with the find field open holding the query at that match (see Find in the file); ` ‹ ` returns to the results.
- **Paths in panes** (`files/link.rs`): a path printed in the active pane, by an agent, a compiler, `git` or `rg`, opens in the files panel on a click, at its line or lines (`:12`, `:12:5`, `:12-30`, `#L12-L30`) and with them selected, so ` ask agent ` takes them at once; the panel opens if it was closed. The path is the run of path characters under the pointer (letters, digits, `_-./~@+,%:#`; brackets, quotes and backticks end it, a trailing `.,:;#` is dropped, a URL is none). A leading `~/` expands with the server's home folder (`config::expand_home`), and relative paths resolve from the foreground program's folder, then the workspace's root. Any regular file is taken, including one outside the workspace; folders, devices and FIFOs are not links. The canonical path stays relative inside the workspace and absolute outside it, so reading, ` open `, ` ask agent ` and copying the path reach the same file even when the agent runs in the workspace; a symlink is classified by its target. The one under the pointer is underlined in cyan (`ui::TabView::link`), checked on each draw: a snapshot row is already there and the check is a `canonicalize`. Claude Code's fullscreen renderer reads the mouse, so its clicks would never reach cornercase, but a plain click on a path does nothing there (it opens links with Ctrl+click, through a desktop file manager a server lacks). So a press on a path in a program that reads the mouse is held back (`Drag::Link` in `App::drag`): released on the same cell it opens the file and the program never sees it; moved to another cell, the held press is sent first and the drag goes on, so the program's own selection still works. The cost: a click right on a path in a Claude tool's header no longer expands it (a click elsewhere on the row does). A program that does not read the mouse keeps cornercase's selection (`Drag::Selection`, carrying the pending `LinkPress`); a release without moving opens the path instead of copying nothing. A pending path press whose release never reaches the pane is replaced by the next drag, so it cannot linger alongside another drag. `files::link::under` is the one lookup the click, the hover and the `link` request share (see the `link` request). Modifier clicks were rejected: the protocol cannot carry Cmd, and Ctrl and Alt clicks are taken by the outer terminal on some systems.
- **Lines for the agent**: a press on a line selects it and dragging selects a range (`Drag::Lines` in `App::drag`, holding the workspace, path and anchor (`Anchor::File { line, text }`; the changes panel's lines use `Anchor::Diff { spot, text }`, and the drag, the edge scrolling and the wheel are one code for both, see Changes panel › Lines), the window's area, whether it moved and when it last scrolled, followed by `continue_drag` even outside the panel; past the body's edges the nearest line counts). The next mouse event ends it if the files panel no longer shows that file in that workspace, replacing the resets in the panel's close and file-open methods. Any event but a left drag or the wheel ends it, like the other drags: a release outside the window may never be reported, and the next click would be swallowed. ` ask agent ` pastes `path:a-b ` (`path ` with nothing selected) into the workspace's agent like the hunk action, ` copy ` copies the selected lines, or the whole file with nothing selected (an image, a binary file, or one too large, gone or not read yet copies its path), ` open ` opens the editor at the first selected line in a new tab, ` open in… ` the apps of the computer the window is on (see Opening in other apps).
  - **Scrolling while selecting**: a file longer than the panel could only be selected one screen at a time, so it could not be copied whole. Once the drag has moved, a pointer on the body's first row or above it, or on its last row or below it (`ui::files::edge`; the body usually ends at the window's bottom, below which a terminal reports no row, so the last row itself is the edge), scrolls the viewer one line every `LINES_SCROLL_EVERY` (50 ms) and moves the selection's end to the line at that edge, as `↑ n more` does in the lists: on each drag event and, while the pointer stays still, on the loop's turns (`App::auto_scroll_lines`; `App::tick` wakes for it only while `App::lines_edge` says the pointer is at an edge that can still scroll, so a selection in the middle costs no frames). One line every 50 ms, like tmux's copy mode, rather than the lists' one item every 150 ms: a line is smaller than an item. A press that has not moved does not scroll, so a click on the last line shown only selects it. The wheel during the drag scrolls the viewer and moves the selection's end to the line under the pointer instead of ending the drag.
  - **Characters (#440)**: a line row has two zones. The cells left of the code (the numbers, the git mark's cell and the blank after it) keep selecting whole lines; the cells from the code's first column on (`ui::files::code_x`) select characters, and the git mark cell of a block keeps its fold. A press and a release on the code without moving still selects that line (`line n`): only a drag that reaches a cell standing for other characters than the press's makes a character selection (`Viewer::stretch`, a `text::stretch::Stretch<u32>`, beside `selection`, which a press sets to the line so a drag that comes back to the press cell falls back to it).
    - **A stream, cell inclusive, like a pane's**: it runs across lines from the press to the pointer and holds both cells' characters, as Ghostty's selection does in a pane (`Stretch::dragged` keeps the rule in one place: the hull of what the press cell and the pointer cell stand for; the pointer back on the press cell keeps that one character; a hull that holds nothing, both past the end of one line, goes back to the press's line).
    - **What a cell stands for** (`ui::code::chars_at`, in the line's shown characters, then mapped to the file's own by `text::stretch::source_range`): a drawn grapheme, its characters (a wide character's two cells and an emoji sequence are one); each of a tab's four cells, the tab; the cut `…`, everything it hides up to the end of the line, so a selection that crosses a cut line takes the rest of it; blank cells past the text, the end of the line; cells left of the code or off the panel to the left, the start of the line; rows above or below the body, the first or last row shown with the pointer's column, as `line_near` does; an unfolded removed row, the end of the line above it (the start of line 1 above line 1).
    - **Covered lines**: the footer, ` ask agent ` and ` open ` use the lines with a selected character or a selected line break (`Stretch::lines`): a last line with nothing selected, which is a stretch ending at its offset 0, is left out, so ending the drag in a line's numbers selects the lines above it. ` copy ` takes the selected characters from the file's own text (`Content::cut`), joined with `\n`, never from the drawn text.
    - **The look**: the selected cells are drawn reversed, which is how a pane's selection shows (`term/emulator.rs::selected`, the simulation's `INVERSE`), and a line whose break is selected (every line of a stretch but its last) is reversed from its first selected cell to the row's right edge, as a pane's is. A character selection draws no line look (no surface background, no cyan numbers). Rejected: a cyan background, since the find field's current match is black on cyan and the two would read the same.
    - **Kept by what it selected**: content positions (a line and a character offset into its own text), never rows or cells, so folds, scrolling and rescans cannot move it. A re-read keeps it and every reader clamps it to the text (`Content::clamped`), `reset_interaction` drops every viewer's (`Panel::drop_stretches`) so a draw that panics on one cannot repeat, and a press on the numbers or another line replaces it with lines. Edge scrolling, the wheel during the drag and the end of the drag on any other event are the lines' code, passing the pointer's column too.
    - **Copying stays on ` copy `**: there is no copy on release, which a pane has. A stray drag would replace the clipboard, and the panels have one way to copy. Left for later: double-click a word and triple-click a line.
    - **Rejected**: storing rows or cells (they drift with folds, scrolling and rescans), offsets into the shown text (a selection could start inside a tab's four spaces), per-character widths (wrong for emoji sequences: a VS16 emoji and a ZWJ family are one grapheme of two cells, so `unicode-segmentation`'s graphemes with ratatui's own cell width are used, the rule `Buffer::set_stringn` draws with) and the host terminal's own selection (it crosses the columns and copies the numbers and the `…`).
    - **One rule for drawing and hit testing** (`ui::code::fit`, `chars_at`, `columns`, `source_at`, `paint`): both panels cut a line of code at the same place, and the drawing, the hit test and the reversed cells all ask the same function, so the selection follows what is shown by construction. It counts cells, not characters, which also fixes two glitches of the old rule: no `…` was drawn when wide characters overflowed, and a narrow character was drawn after a wide one that did not fit at the edge. `ui::files::lit` clips to what `fit` of the whole line keeps, not to the width, so zero-width characters cannot make the `…` and the hit test disagree. Known limit: a grapheme split by a style boundary (a find match ending inside an emoji sequence) is drawn run by run and can sit a cell off its layout.
    - **Nothing on the socket**: the selection is pointer state and drawing, like the line selection.
  - **Copy takes the file's own text** (`Body::Text`'s `source`, an `Arc<str>` kept beside the shown lines, read through `Content::text`): the shown lines have their tabs turned into four spaces and lose a `\r`, so a Makefile copied from them broke. The whole file is copied byte for byte (after the lossy UTF-8 decoding every read has), selected lines are joined with `\n`. It costs one more copy of the file per open viewer (8 MiB at most), plus `Body::Text::starts`, the byte offset of each line (8 bytes a line, 1.8 MiB on the largest allowed file): a drag asks for the line under the pointer on every event and painting asks for the first and last line of the selection on every frame, and finding line n by walking the file costs 2-5 ms at 229k lines (`Content::source_line` is O(the line)), and `disk::read` now returns the `Content` itself, since the source its `Read` carried for highlighting is in the body. Copying the path with nothing selected was dropped for the whole file: the header shows the path, and ` ask agent ` without an agent still copies it.
- **Full screen** (#278): an open file reads better with the whole window than with a column that has to be dragged out and back, which also stops at `MIN_PANE_WIDTH` and the sidebar. A button just left of the title row's ` × ` (`ui::files::full_screen_button`, only on a file: text, image, binary or gone, never the tree or the results) turns `▢` into `❐` while it is on, muted, cyan on hover and cyan while on, like the changes filter's ` ⌕ `; with Nerd glyphs the codicons `screen-full` and `screen-normal` (`icons::Glyphs`). The glyphs follow the window-title convention (one window to maximise, two stacked to restore), are one cell wide and not emoji; `⤢`/`⤡` were rejected for font coverage (not in DejaVu Sans Mono) and for saying nothing about in and out, `⛶`, `□` and `▣` for ambiguous width, `⊞`/`⊟` for reading as tree folding. One flag, `files::Panel::full_screen` (not `expanded`, which means open folders), cleared whenever the file or the panel closes (`close`, `open_file`, `close_file`) so it is never per workspace or saved: the session keeps only whether the panel is open. `App::file_full_screen` also requires the panel shown and a viewer open, and `Areas::with_full_screen` (after `with_tab_bar`, in `App::layout` and `ui::draw`) only moves `changes` to the whole window and empties its border, so `pane`, and with it the PTY sizes, and `Widths::changes` are never touched: restoring gives back the exact width, automatic or dragged. `ui::draw` draws only the panel and what goes over it (overlays, star card, toast): otherwise the active pane's cursor and the icon bar's tooltip would show through, and nothing under the panel is hit, since a press inside `Areas::changes` already goes to the panel first. Ways out: the button, `Esc` (before the `Esc` that closes the panel), ` ‹ `, ` × `, opening another file or a files search, every `App::goto` (` open `, ` ask agent ` that found an agent, results, notification clicks, ` go `, the keys menu's jumps: a jump shows its destination), any change of the focused tab, workspace or project seen by `App::follow` (keys, a new tab, the active tab closing, `cornercase focus`) and `reset_interaction`, so a viewer that panics while drawing cannot keep the window stuck. ` copy ` and ` ask agent ` without an agent stay full screen. Keys still go to the active pane even though it is covered, as in compact mode where the panel also covers it, so typing, pasting or an `Enter` act on a program the user cannot see until `Esc` or the button brings the panes back; that is the known cost of the choice; swallowing them or scrolling the viewer with the arrows would be new keyboard shortcuts, which AGENTS.md asks about first. The compact layout shows the button too and full screen also covers its top bar: one rule everywhere. While full, the covered tab counts as not visible (`App::visible_tab`, `App::shows`, like under the compact menu), so an agent finishing there gets its `✓`, toast and notification and its output stops forcing frames; `link_hover` skips its path lookups. The trace logs `ui: file shown full screen` / `file back in its panel`. The words are *full screen* and *back in the panel*, never *expand*, which is for rows. Rejected: remembering it per workspace or across restarts, a keys-menu entry, and full screen for the tree, the results or the other side panels.
- **Find in the file** (#412): the viewer had no way to look for a word (the bar only shows on the tree and the results), and could light an occurrence only when the file came from a text search. A button ` ⌕ ` just left of ` ▢ ` (`ui::files::find_button`, text files only, empty file included: never an image, an unreadable, binary, too large or gone file, nor while reading, the tree or the results; muted, cyan on hover and while the field is open, and left out where it would cover ` ‹ `, as the full screen button is) opens a field on the row under the header (`Viewer::find`, a `files::find::Find`: text, focus, every occurrence, the current one). The body moves down one row while it shows (`ui::files::body`, which every row to line computation uses, so a click lands on the line drawn there). It is built like the changes filter (a click takes the keys, a press outside the panel gives them back and keeps the query, ` × ` closes). No keys-menu entry and no `Ctrl+F`: a new shortcut is a decision AGENTS.md asks about first, and `Ctrl+F` steals the shell's binding, so the button is the only way in; a click on ` ⌕ ` with the field open gives it the keys instead of closing it, as the filter's does. The field shows only while the content is text or still unknown (`Viewer::finding`), and `Panel::typing` follows it, so a find on a file that turned binary swallows no keys unseen.
  - **Matching**: the text search's own matcher (`search::matcher`: a literal, smart case, trimmed like the bar, a blank query finds nothing), so a query behaves the same in both places, over the shown lines (`Content::lines()`: tabs as four spaces, no `\r`), not `Content::text`: the lights land exactly on what is drawn. A query cannot hold a tab (the Tab key is not text and a paste drops control characters), so the two differ only when spaces in a query meet a tab in the file. Unfolded old lines (`Line::Removed`) are not part of the file and are never searched. Regexes, whole word and case switches, marks on a scrollbar and replace were left out (one more thing to learn for a quick look; the viewer is read only).
  - **Counting**: one pass of grep-regex per line on the server loop, per edit of the query and per re-read whose lines changed; never while drawing (`FileView` clones an `Arc` of the occurrences, and each drawn row asks for its own with two binary searches). Occurrences are stored at 12 bytes each with no cap, so the count and the steps stay exact; byte offsets become character columns incrementally with an ASCII fast path, because counting from the start of the line for every match is quadratic on a minified one-line file. Measured on 2026-10-20 on the largest allowed file (8 MiB, 229,278 lines): 13-27 ms for ordinary queries and about 40 ms for one letter with 635,670 occurrences (7.6 MB); the earlier per-line `Vec<char>` search took 170-220 ms. A job, as the name search, remains the way out if it ever shows. A drawn line is cut to what shows before the matches are painted, so a long line costs what is on screen.
  - **Moving**: typing goes to the first occurrence at or after the top line of the view, wrapping to the first; `↓` and `Enter` go to the next, `↑` to the previous, wrapping, and ` ↑ ` ` ↓ ` in the field do the same beside the count (`3/17`, or `no matches` when the query is not blank and the file is read; nothing while it is blank or reading). The arrows are always drawn so the field does not change shape while typing. A jump scrolls only when the line is off screen, to three rows below the top (`CONTEXT`, where opening a result puts its line). The current occurrence is black on cyan and bold (cyan is the app's colour for where you are), the others `LIT`.
  - **Selection**: finding never touches `Viewer::selection`: the current line is not selected, so a selection made by hand before searching keeps working for ` ask agent ` and ` copy `. Opening a text result still selects its line, as before.
  - **Live files**: a re-read (`CHECK_EVERY`) counts again only when the lines changed (the first read answers twice, plain then highlighted, and the second costs nothing), and the current occurrence moves to the nearest by line from where it was, the one below on a tie. The view never moves.
  - **From a result**: opening a match opens the field holding the query (`Find::new`), at that match, so `↓` goes on through the file; it takes the keys only if the bar had them, so a click on a result while the keys were in a pane does not take them from the shell. ` ‹ ` returns to the results.
  - **Leaving**: ` × `, or `Esc`, which goes one step per press: text cleared (the field stays, with the keys), the field closed, full screen ended (#278), the panel closed (see TODO panel). `Esc` closes the field only while it has the keys, as with the files `Query`: after a press outside the panel it goes to the next step of the chain. The find is per viewer and in memory: `open_file`, `close_file` and closing the panel drop it. The prefix key still works while the field has the keys. The query is never logged (see Log).
  - **External clients**: nothing on the socket: #345 lists the files panel's listing and viewer under *Left out on purpose* (a GUI reads the disk itself), and finding in a shown file is drawing.
