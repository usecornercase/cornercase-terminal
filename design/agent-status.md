# Agent status

Code: `agents/activity.rs`, `agents/{claude,codex,gemini,opencode,grok,cursor,copilot}/mod.rs`, `app/agent_watch.rs`

- **Program status comes first** (#249, `term/status.rs`, `term/status/stream.rs`): OSC 7501 reports override the agent's file and title heuristics while a record exists. The protocol uses `error`, which becomes `Activity::Failed`, `Status::Failed` and the script-facing `failed`, a bold red `!`. `blocked` becomes waiting; `working` stays working; reported `idle` is `Activity::Ready` so cancelling a turn does not create a guessed completion; explicit `done` marks unseen work even without a preceding working sample and stays acknowledged once the tab is opened. Reported idle preserves an existing unseen mark, including one restored with the conversation, but never creates one by inference. Failed stays visible until replaced or cleared. Waiting outranks failed, then pending, done, working and idle. Failure settles and notifies with the same one-second rule, including the chat apps while away. Failed ends a turn for stats, `wait --until idle` and idle restart. Model, context, resume and last-message readers stay agent-specific.
- **Any recognised agent can report status**: `activity::Pane` follows the kind's string, including the launch-only catalogue and `agent_commands`, rather than requiring a `Known` reader. Process arguments still establish identity; an OSC `app` cannot turn a shell or a build into an agent. Each record is associated with the foreground pid that emitted it, so retained results do not override a later agent. Changing foreground process expires active and idle records; done and error records survive back at the shell with the originating agent identity (`Term::status_agent`), and are never applied to a new foreground agent. A finished result at the shell is acknowledged when its tab is seen; failure remains until replaced or cleared. Shell output never inherits the identity of a departed agent; already recorded results retain their original pid. A shell prompt (OSC 133 A) expires active and idle records too. Alternate-screen switches and soft resets keep records; RIS clears all. `clear` removes an id and its descendants (or all records at the root), returning to heuristics when no applicable record remains. The most urgent record wins, including children whose parent has no record.
- **Keep the published Ghostty binding pinned**: `libghostty-vt` 0.2.2 predates the upstream OSC 7501 callback. A bounded streaming observer beside the emulator recognises OSC, shell prompts and RIS without reading strings embedded in DCS/APC/PM/SOS. Ghostty continues to receive every byte and owns rendering and its existing replies. For a support query, the emulator feeds the prefix through Ghostty before sending the fixed reply through the same PTY writer, so replies stay in request order even within one read. The observer accepts BEL and ST across arbitrary read boundaries, validates the revision 0.4 grammar and all size/base64/control-character limits before applying a report, keeps at most 256 records and evicts the oldest updated one. Optional labels and messages are validated but not displayed; `kind`, `progress` and `app` do not affect presentation. No heartbeat, settings, hooks or new dependencies. The specification is [Program Status Protocol](https://www.superlogical.com/rex/docs/build/program-status); the upstream implementation is [ghostty#14560](https://github.com/ghostty-org/ghostty/pull/14560).
- Every 500 ms (`WATCH_AGENTS_EVERY`, from `App::refresh`) each pane whose foreground process is Claude Code, Codex, Gemini CLI or opencode (`agents::detect` on its arguments) gets an `Activity`: working, waiting or idle. For Claude the source is the file Claude Code keeps for each running process, `<CLAUDE_CONFIG_DIR or ~/.claude>/sessions/<pid>.json`, the registry behind `claude agents --json` (its documented interface for status bars): `status` is `busy`, `waiting` (permission prompt, question, dialog), `idle` or `shell` (turn over but a Bash it started with `run_in_background` still runs). `shell` counts as working, like Claude's own agents view: Claude wakes up when the command ends, so it was not done (a dev server left running keeps the tab `◐`). It is its own `Activity::Shell` all the same, which `Pane::status` shows as working (so the UI, the rollups and the notifications are unchanged) and only the commands for scripts tell apart (`Pane::background_shell`, `Pane::state`; see Commands for scripts and agents): an orchestrating agent whose agents leave watchers behind had no way to stop waiting for them (#127). A Monitor that runs a command is a background Bash too, so it gives `shell` (checked live on 2.1.289); one on a WebSocket runs no shell and may leave it `idle`. Its fields are not documented, so a missing file or an unknown value falls back to the title Claude sets (`◐`/`◑`, or braille in older versions, while busy; `✳` otherwise; it stays `✳` when Claude sees `TMUX`, `STY` or `ZELLIJ`), then to idle.
- No hooks and no screen scraping. Hooks mean editing the user's `~/.claude/settings.json` (or shipping a plugin), `Stop` never fires on an Esc interrupt and the permission notification comes ~6 s late; Claude's screen changes too often to match. The session file turns idle within a tick of an interrupt and waiting as soon as a prompt shows.
- `Status` adds done: a pane that went from working or waiting to idle while its tab was not seen (`App::seen_tabs`: the window's visible tab, the active tab unless the compact menu or a file shown full screen covers the pane, and the tab of every active, sized, visible view, see Commands for scripts and agents) is done until that tab is shown. `watch_agents` clears it for the visible tab on every `refresh`, not only every 500 ms, so a click shows `○` at once. An unknown state counts as idle, so a fresh Claude never looks done.
- **Pending review** (`Status::Pending`, a bold `●` in the brand blue 27): a mark the user puts on an agent's pane by hand, because launching several agents left finished work to review and `✓` was not a record of it: it goes the moment the tab is shown, a quick look through the tabs wiped it, and a restart lost it. The mark lives on the pane (`activity::Pane::pending`), not the tab, since the agents section and a split tab hold one agent per pane; a tab's menu (` ⋯ ` or right-click on its row, in the lists, the tree and the tab bar) marks or reviews every agent pane in it, the pane's right-click menu, a right-click on its row in the agents section (`App::open_agent_menu`, the one menu those rows have, so a busy list can be gone through without leaving the pane being read) and the keys menu's `m` act on that pane, and `cornercase mark [--pane|--tab] [--reviewed]` lets a script or an agent do it (its own pane by default, so an agent can mark itself at the end of its turn). Only panes with an agent cornercase reads take it (`Pane::agent`); others are refused or offered nothing. Showing the tab does not clear it (`Pane::see` leaves it); it goes when marked as reviewed, which clears `done` too, or when the agent goes from idle or waiting to working, which means it got a new prompt or an answer and the user is iterating on it again. Going from a background shell to working does not clear it (the agent woke up by itself), and neither does a mark put on while it works: it shows once the turn is over. It sits between done and waiting: a question still comes first, and it beats `✓` since it is the user's own statement. It needs you (`Status::needs_you`), so it reaches the workspace, project and group rows, the compact `≡` and the keys menu's `a`, but it never notifies (`Status::notifies` is waiting, failed and done only: the user just put it there) and stats do not count it as time waiting for the user (it may stay for days). Waits end on it as on idle (`--until idle`, the default, `turn-over`, `restart --when-idle`); `status`, `--panes` and `events` give it as `pending`. Only by hand for now: turning every unseen finish into a sticky mark was left out, to see first how the manual mark is used.
- A tab shows its most urgent pane (`Tab::status`, the order of `Status`): waiting `!` > failed red `!` > pending `●` > done `✓` > working `◐` > idle `○`, before the name. **Working icon** (`working_icon` in `config.json`, Settings → UI, `config::WorkingIcon`): `moon`, the default, keeps the still `◐` (`activity::MOON`); `spinner` steps through `⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏` (`activity::SPINNER`), one frame every 100 ms (`activity::SPIN_EVERY`), the same frame on every row, from the time since the process started (`activity::spin_frame`). `View::spin` carries the frame, `None` for the moon, so one value reaches every place the icon is drawn (tabs, the tab bar, the agents section, the compact `≡`, the toast). `App::tick` wakes for the next frame only with the spinner on and some tab working; otherwise the loop stays on its 500 ms tick. The spinner was the only icon in 0.12.84 to 0.12.86 (#240): it shows at a glance that a turn is still going, but a column of moving icons keeps pulling the eye away from the pane being read, and with an agent working it draws every window ten times a second, so the moon came back as the default and the spinner became a choice. A pick rather than a switch, like `tabs`, since the row names what it shows. A still with the spinner on, such as a test, shows the first frame. Chat messages (Telegram, Discord) keep `◐` whatever the setting, since a message does not move. `!`, `✓`, `○` and the shell marks never move. A tab without an agent shows its shell instead (`TabEntry::icon`), in the muted grey: `▸` while a program runs in the foreground of any of its panes (`Tab::running`), `›` at the prompt. Every tab has an icon so their names start in one column: a shell tab used to start two cells to the left of an agent's, and the list read as two indents. Two states rather than one fixed mark, so the icon answers what an agent's does (is it doing something?) and a dev server that died back to its prompt shows at a glance. It is `!Term::shell_in_foreground()`, read when the row is drawn, like the tab's label (an editor started with a command counts as running); caching it on the 500 ms agent reads was tried and dropped: the label already looks up the foreground process on every draw, and the cache only added a field and up to half a second of lag. Grey, never yellow, so a dev server that runs for hours does not compete with an agent working, and no done: every `ls` in a hidden tab would leave a mark. The agents' own glyphs were rejected for the same reason (a `◐` then a `○` means done for an agent and would not for a program), and `▶` because it has an emoji presentation that some fonts draw wider than a cell. Shell icons never reach the workspace, project or group rows. Workspace, project and collapsed group rows show only what needs you (`agents::activity::attention`: waiting, pending or done), right-aligned and before `↓n`; working stays on the tab so the sidebar is not always full of icons. A collapsed workspace is the exception (#294): its tabs are hidden, so its row shows the most urgent status of its agents (`agents::activity::highest`, the order of `Status`, so `◐` or the spinner and `○` too), in the tree and the lists (`ui::workspaces::Badge`); shells show nothing. The compact `≡` shows the same for every tab but the visible one (`View::attention`). The agents section (see Layout) lists each agent pane with its own status, not its tab's.
- **Codex** (`agents::codex::Reader::activity`, checked live on 0.160.0): waiting while the title starts with `[ ! ] Action Required` or `[ . ] Action Required` (it blinks between the two during an approval); working while it starts with a braille spinner and a space (`⠴ <thread> | <project>`) or while the rollout the context line follows (`agents/codex/rollout.rs`) is inside a turn (`task_started`, until `task_complete` or `turn_aborted`); otherwise idle (the title is then `<thread> | <project>`, or just the project). Approvals are never written to the rollout, so `!` needs the title; the title's items are configurable (`/title`, `tui.terminal_title`), and without its activity item the rollout still gives working and done. Both rather than one: the rollout alone has no waiting, the title alone breaks when its activity item is removed. Hooks were rejected as for Claude (they mean writing to `~/.codex`).
- **opencode** (`agents::opencode::Reader::activity`, checked live on 1.18.35): no status until the job has found its database, read it and told its session apart (a query that fails, or two opencode in one folder, give none, rather than an idle that would turn a working pane into a false done); idle while it has no session yet; working while the newest message of its session is the user's (sent, its reply not written yet) or an assistant message without `time.completed` (an Esc interrupt completes it, with a `MessageAbortedError`; `/compact` is a reply like any other, with `summary: true`), else idle. The session comes from the database the context line reads (`agents/opencode/database.rs`, see Context use), on the same thread. opencode never says it waits for you: a permission or a question lives only in its memory (the tool part already reads `running`), its title stays `OpenCode` or `OC | <session title>` whatever it does, and its log (`log/opencode.log`, shared by every process, no pid) writes `asking` but never the answer, so a pane waiting for you shows `◐`. Rejected: reading that log (a format of its own, cut by `--log-level`, and the reply would have to be guessed from the database), its HTTP API (`/session/status`, `/permission`, which only exists with `--port` and then listens on localhost without a password), and its own notifications (`attention` in its TUI config, off by default and only while its window is unfocused, so cornercase would have to inject a config and report focus). It asks no trust question, so a launch goes straight to the prompt once its screen is quiet.
- **Gemini CLI** (`agents::gemini::Reader::activity`, 0.63.0): trim the padded OSC 0 title; `✋` means waiting, `✦` and `⏲` working, `◇` idle. Fixed (`ui.dynamicWindowTitle` off), hidden (`ui.hideWindowTitle` on) and unknown titles give no status, because losing a signal does not mean the turn ended. There is no session fallback: the file has no turn markers, text can precede a pending tool, and tool results and message updates arrive separately. Hooks would require writing the user's settings, so they are rejected. Follow Gemini's quiet-shell `✋` heuristic even when it mistakes a slow command for input; guessing from descendants would be less reliable. Fixtures pin working, ready, thought, fixed, confirmation and silent-shell titles observed inside tmux. Hidden titles were checked against the source. The source has no tmux, screen or Zellij exception; screen and Zellij were not checked live.
- **Grok Build** (`agents::grok::Reader::activity`, checked live on 1.0.52): no status until `active_sessions.json` has a row for the foreground pid. On Linux that row's `pid_start` must equal field 22 of `/proc/<pid>/stat`; macOS has no start time, so a missing one does not reject the row. The previous status stays on screen while the next read runs, including while that read holds the session tails. A turn is open from `events.jsonl` `turn_started` until `turn_ended` (`completed` or `cancelled`). The reader keeps one tail per file and the fold, and applies only new lines; a replaced or truncated file clears the fold. The first read, and a reset, seeds the open turn from the newest `turn_started` or `turn_ended` behind the tail, so a turn whose start is more than a megabyte earlier still reads as working. If that backwards scan reaches its bound without either marker, the turn is unknown, not closed: newer phase or tool events keep it working until a `turn_ended` arrives, so a wait or an idle restart does not treat it as finished. Waiting is a `permission_prompt` phase, a `permission_requested` with no later `permission_resolved` for that same tool, or an open `ask_user_question` or `exit_plan_mode` until its `tool_completed`. Resolving one permission does not clear another tool's request. A question's permission returns `allow` with `wait_ms` 0 and the phase goes back to `tool_execution` while the question is still unanswered, so that phase does not close the ask; `tool_completed` does, and the same turn then continues (`loop_started`) as working. `enter_plan_mode` is how a turn enters plan mode and is not itself the approval. A live `/plan` called `exit_plan_mode`; its permission returned `allow` with `wait_ms` 0 while the approval was still open, and `tool_completed` arrived when it was approved, after which the same turn continued (`loop_started`, then another tool). The ask stays open until that `tool_completed`. Any other tool, including `run_terminal_command`, is working. `waiting_for_model` is how a healthy turn starts. An unknown model is rejected before any turn. Starts that have `turn_started` and no `turn_ended` in real logs are not explained yet, and there is no timeout. A background command with `block_until_ms: 0` ended the turn while the process kept running, so there is no `Activity::Shell`. Esc did not end a turn. Ctrl+C did (`cancelled`, `mid_turn_abort`, `cancellation_context.trigger` `ctrl_c`). One Enter while a turn is open queues the text and leaves the turn running. A second Enter is Grok's send now: the open turn ends `cancelled` with trigger `send_now`, and the next `turn_started` has `redirect_kind` `queued_after_cancel`. `send` presses Enter once, so it queues and is not refused. A title containing `Action Required` forces waiting only while the turn is open. A braille spinner, and the word Waiting in a compact title, do not, and neither overrides `turn_ended`. The trust screen says "Do you trust the contents of this directory?" and "Yes, proceed", which the default trust pattern already matches; cornercase does not write `trusted_folders.toml`.
- **Cursor CLI** (`agents::cursor::Reader::activity`): the title is OSC 0 and carries no state by default (the chat's name or `Cursor Agent`); with `display.showStatusIndicators` (`/status-indicators` in Cursor, off by default) it reads `<name> - <emoji> <text>`. The last ` - ` is taken, so a chat name holding one is no problem: `❓` and `🔐` mean waiting, `⏳` `🧭` `⌨️` `📋` `📝` working and `✅` idle; any other (`🔄` reconnecting, `📂` loading, `📤` moving to the cloud) says nothing and falls through, as does a title without one. Without a title signal the status comes from the transcript (`agent-transcripts/<chat id>/<chat id>.jsonl`, read with the shared incremental tail): a `user` line opens a turn, `{"type":"turn_ended"}` (`success`, `aborted` or `error`) closes it, and a rewrite (compaction) is read again from the start of its tail; the file has no timestamps. "Send now" writes no `turn_ended`, so the next user line keeps the turn open. Nothing on disk says waiting, so without `/status-indicators` a permission prompt shows as working, like opencode, and `!` never appears; the optional fallback of reading the screen's `Waiting for decision (y/n/p)...` placeholder was left out, since this design avoids reading the screen for status. A fresh Cursor before its first turn has no store and shows idle, so a first turn without indicators shows working a moment late. Cursor writes no OSC 7501.
- **GitHub Copilot CLI** (`agents::copilot::Reader::activity`, `agents/copilot/session.rs`, `events.rs`, live-checked): the pane's session is the folder `<home>/session-state/<id>/` whose `inuse.<pid>.hold` the pane's process (or a Copilot process under it: the npm loader's child, `gh copilot`'s) holds **open** (`process::open_files`; `<home>` is `$COPILOT_HOME` or `~/.copilot`, read from the process's own environment). Holding the file proves the pid is alive and is not a reused pid, so a lock left by a `kill -9` is ignored without reading its `.lock`; the package folder under `~/.cache/copilot/pkg/` has an `inuse.<pid>.hold` of its own, which does not count, since only one directly under `session-state/<id>/` does. A process holding two sessions (an overlap during `/clear`) has none until the next poll. Before it holds one (a resumed pane, whose session takes its lock with the first prompt, live), the session is named by `--resume=<id>`, `-r`, or `--session-id` in the process's arguments, only when that folder exists and no live process outside the family has a lock in it, and shows idle. **Working** is `working` for that id in `<home>/open-sessions-state.json` (`{id: {schemaVersion, openedAt, refreshedAt, working}}`, which Copilot rewrites, so a read that does not parse keeps the last value, and a missing file or entry is unknown, never a guessed idle that would end a wait). `true` is waiting when `events.jsonl` has an open `permission.requested`, or an open `tool.execution_start` of `ask_user` or `exit_plan_mode` (the plan review: live, it stays open until the plan is accepted or cancelled), else a background shell when the turn is over and an `async` bash is still running, else working. `false` is idle. **A background shell** keeps `working` true after the last `assistant.turn_end` until the shell ends (live: 25 s, then a `system.notification` of kind `shell_completed` wakes the agent), so it is `Activity::Shell`, like Claude Code's `run_in_background`: the shell is started by a `tool.execution_complete` whose `toolTelemetry.properties.executionMode` is `async` and whose result says `started in background with shellId: N`, and ends by the notification; the wake-up message is a `system.notification`, never a `user.message`, so it is not a prompt. `abort` (`user_initiated` for Ctrl+C, `user_abort` for Esc, live) and `session.shutdown` clear what was pending. One prompt gives several `assistant.turn_start`/`turn_end` pairs, so they are not the end of the work, and the presence file, not the events, says it. **Not detected**: the title carries no state (and can be turned off), so it is not used; the rate-limit, session-limit and auto-mode-switch questions are ephemeral events that are never written and show as working; `session.error` is not mapped to `Failed` (model errors are retried and no reader reports a heuristic `Failed`, which would stick until replaced). Copilot writes no OSC 7501, so the program-status protocol takes over only for what reports it.
- **Background subagents keep the agent working** (#358, `Activity::Subagents`, `agents/context.rs`, `agents/claude/transcript.rs`, `agents/copilot/events.rs`): an agent can end its own turn while subagents it started in the background still run, and goes on when they report back. The tab then showed `✓`, notified "finished", and again when the work really ended; waits, `restart --when-idle` and the chat notices ended early. `Activity::Subagents` means "the agent's own turn is over (idle, or only a background shell left) but subagents it started still run". `context::Pane::activity` promotes the reader's `Idle` and `Shell` to it while `Reader::subagents()` is above 0; a question (`Waiting`) is never promoted, so `!` wins, and `Working` stays `Working`. Subagents beat a background shell: the agent wakes up for their results, so the turn is not over even for `--until turn-over`, the opposite of the shell. It maps to `Status::Working`, and `state()` stays `working`, so no new value reaches scripts or events: waits, `--when-idle`, keeping awake, stats and chat notices read `status()`/`state()` and needed no change. `Subagents → Idle` is a finish like `Working → Idle` (unseen `✓`, one notice after the settling second), and a pending mark stays through it like through a shell. OSC 7501 still comes first (`agent_in`), so a program that reports status decides, and the count stays. A turn with subagents is one turn that ends when the last subagent does, and its whole time counts as working time. The server log gets an `activity` line `subagents` when the flag flips (`state()` does not change between working and subagents, so the `status` line says nothing).

"busy" : "idle"`), so cornercase's own check is a backup and what gives the count. The files are the ones `Subagents` already tails for stats: `<transcript without .jsonl>/subagents/agent-<id>.jsonl` and its `agent-<id>.meta.json`. A file counts as running when all hold: it was written since the pane first saw the process (a resumed conversation's finished subagents never count); it was written within 10 minutes (`SUBAGENT_STALE`, `context::fresh`, shared with Copilot: a subagent can wait minutes on one tool, and the agent's own status covers that wait; the guard only keeps one that died from holding the tab for good); its meta does not say `finished: true` or `stoppedByUser: true` (written since 2.1.301); the newest assistant line read from it is not a final reply (`stop_reason` `end_turn` or `stop_sequence`: how versions before 2.1.301 end it, and a revived subagent writes new lines and counts again); it was written after the newest `[Request interrupted by user` user line of the parent transcript (Esc aborts foreground subagents and parks background ones, which stop writing); and its meta says `requestShape: "background"` or the parent is busy or waiting (a foreground subagent cannot outlive the tool call that started it, so one that crashed without a final reply never holds an idle parent). Teammates and workflows (`subagents/workflows/`) are not counted: Claude's own `busy` covers them. **Known limits**: a background subagent stuck in one long tool call for over 10 minutes writes nothing, so it stops counting; the parent then shows `✓` and notifies, and notifies again when the subagent really ends (the price of a guard that a crashed one cannot hold the tab for good; Claude's own `busy` still keeps the tab working while it reports it). After `/clear`, the reader keeps the old session's subagents until its next background job returns, so the count can be wrong for a tick or two. - Claude Code, Codex, Gemini CLI, opencode and Grok Build; supported agents register through `Known` as described under Agents. `activity::Pane` stores the kind string so launch-only and custom agents can report OSC 7501, while `context::Pane` stores `Option<Known>` for its readers; `app::agent_watch::agent_in` detects the identity, updates its reader, remembers its conversation, calibrates the input-box check through `Known`, and asks the pane for activity. It has no agent-specific arm. An agent running through `ssh` or in a container is not seen (no local process, no local file).
- **Notifications**: `Pane::update` returns `Waiting`, `Failed` or `Done` once that status has held for `NOTIFY_AFTER` (1 s) and its tab was not seen, in the window or a view, meanwhile, once per change, so a prompt answered at once stays quiet. `App::notify` sets a toast with the status icon (`<agent> needs you in <project> › <workspace>`, the agent's kind such as `claude` or `codex`, control characters stripped) and queues a `host::notify::Notification`, which the server encodes per client. Panes of the same agent that settle on the same status in the same workspace on one tick give one notice: the text would be the same, and Ghostty drops a repeat within 5 s anyway. The agent is part of that key, so Claude and Codex in one workspace each get theirs. A pane's state remembers its agent (`agents::activity::Pane::follow`) and starts over when another one takes the pane, so a Codex replacing a waiting Claude without a tick in between still notifies. They go through the outer terminal like OSC 52, so they work over SSH (no `notify-send`/`osascript` on the server's machine).
- The channel is the client's: inside tmux, screen or Zellij it is BEL (tmux drops notification OSCs, passthrough is off by default, BEL goes through); otherwise `host::notify::detect` trusts the XTVERSION reply when there is one (asked with the colours, so it survives SSH, where only `TERM` arrives; env vars may also be inherited from another terminal), else `TERM_PROGRAM`, `LC_TERMINAL` (iTerm2 sets it for SSH), `TERM`, `KITTY_WINDOW_ID`, `KONSOLE_VERSION`. OSC 777 for Ghostty, WezTerm, Warp, Rio, foot before 1.18 and Konsole before 24.12 (or with no version); OSC 9 for iTerm2 (its only one); OSC 99 with `o=unfocused` for kitty, Contour, VS Code (VS Code knows only 99), foot 1.18+ and Konsole 24.12+ (from the XTVERSION version, or `KONSOLE_VERSION` 241200, since those two report a click); BEL otherwise. Never several, since terminals that know several would show each.
- OSC 9 and 777 end with BEL, which every parser accepts; OSC 99 with ST, as kitty's spec says. `;` in the text becomes `,`: WezTerm, Rio and Konsole cut the body at it, WezTerm drops an OSC 9 holding one. Ghostty on macOS, foot, Konsole and Warp hide notifications while their window is focused; the others show them. `desktop_notifications` (`auto`, a channel, `off`) overrides the channel; the toast always shows. The visible tab never notifies, even while the outer window is unfocused: focus reporting (`CSI ? 1004 h`) is now on, but it is per window while what is visible is shared, so it only brings a toast back (below).
- **Clicking a notification (#316)**: a desktop notification carried only its text, so a click could not say which agent it was for.
  - **Tokens**: each agent notice (`App::notify`, through `App::tell` in `app/notifications.rs`) gets `cc-<nonce>-<n>` (`[a-zA-Z0-9_+.-]`, the nonce per server run like the chat buttons', so a notification left in the notification centre across a restart is ignored rather than taken for a pane that now has its id). `Notices` keeps 64 (`notify::KEPT`, oldest out) with the agent, place, status, project, workspace and the panes behind it: the dedup key of `notify` (agent, status, workspace) covers several panes, so `watch_agents` collects them. `cornercase notify`, queue, setup-failure and flow bypass-consent notices keep no token and the old sequence.
  - **Asking for the report**: `Channel::Osc99` with a token encodes `ESC ] 99 ; i=<token> : a=focus,report : o=unfocused ; text ESC \`. `a=focus` keeps what the terminal did; terminals that know neither key ignore them, as kitty's spec requires. kitty (checked live on 0.45), VS Code, Contour (`i=x:p=activated;`), foot 1.18 and Konsole 24.12 write back `ESC ] 99 ; i=<token> ; [button] ESC \`. Ghostty parses OSC 99 but does not act on it (ghostty-org/ghostty#5634), so it stays on OSC 777 and its click only focuses the window; the same goes for iTerm2, WezTerm, Warp and Rio. A `p=?` query in the startup probe was left out: kitty's answer alone is about 230 bytes and the probe's largest reply is kept under macOS' 1024-byte tty input queue.
  - **The client reads the answer**: `ESC ] 99 ;` joins `REPLY_PREFIXES`, so it is never decoded as `Alt+]` and typed text. `host::notify::activation` parses leniently (the metadata before the first `;`, `i` of 1 to 64 allowed characters, `p` absent, empty or `activated`, so `close`, `alive` and `?` answers give nothing) and the decoder emits `client::input::Input::Activated`, which the window sends as `ClientMessage::Activated` (last client variant, `protocol::VERSION` 5, 6 since the sound below; the browser bridge sends it too). A split inside the 5-byte prefix is held only while replies are expected or more bytes wait, like every reply, since Alt+`]` must not be delayed; a terminal writes its answer in one write. Bracketed paste stays text.
  - **The app jumps**: `App::notification_clicked` ignores an unknown token (not logged), drops the notice's own toast and missed mark, goes (through `App::act_on_notice`, shared with `go`, #337) to the first of its panes in sidebar order whose agent still needs you, else the first that exists, through `jump_to_pane`; with all its panes gone, to the workspace if it is open, else a toast `<agent> in <place> is gone`. A project closing or a workspace being removed counts as gone. An open overlay stays, and focus is shared, so every window shows the jump as after any click. The log says the pane or `workspace` or `gone`, never the text.
  - **The toast's ` go `** (`Toast::go`, `ui::ToastButton::Go`) does the same for the same token in any terminal, also inside tmux, and lasts 6 s like an ` undo `. It is the way to the agent where a click reports nothing.
  - **The toast again on focus**: the client enables `?1004` and disables it on every way out (`restore_input_modes`, `release_screen`); the server passes `FocusGained` and `FocusLost` to `App::window_focus` and they are not a use. State is per window (`Notices::windows`, dropped in `forget`): a notification sent while a window is unfocused marks it missed, and on gaining focus its toast shows again with ` go ` if the agent still needs you and none of its panes is in the tab on screen. Ghostty, iTerm2 and WezTerm bring the window forward on a click, usually after the 6 s. Jumping straight to the agent on focus was left out: alt-tabbing back looks the same. In kitty the click's answer and the focus arrive in either order; the click drops the missed mark and a notice whose tab is on screen is skipped, so there is no duplicate.
  - **Leaving**: the server keeps what it sent each window (`notify::Sent`, the tokens of notices sent as OSC 99, 64 at most) and sends their closes (`p=close`) before `Detached`, `Shutdown` or `Restart`, so a click later writes no answer into the shell that outlives cornercase. A killed or lost window can still leave one; its answer then shows as typed text in the shell.
