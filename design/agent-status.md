# Agent status

Code: `agents/activity.rs`, `agents/{claude,codex,gemini,opencode,grok,cursor,copilot,vibe}/mod.rs`, `app/agent_watch.rs`

- **Program status comes first** (#249, `term/status.rs`, `term/status/stream.rs`): OSC 7501 reports override the agent's file and title heuristics while a record exists. The protocol uses `error` (Claude Code's API-error turns also become `Failed`, see below), which becomes `Activity::Failed`, `Status::Failed` and the script-facing `failed`, a bold red `!`. `blocked` becomes waiting; `working` stays working; reported `idle` is `Activity::Ready` so cancelling a turn does not create a guessed completion; explicit `done` marks unseen work even without a preceding working sample and stays acknowledged once the tab is opened. Reported idle preserves an existing unseen mark, including one restored with the conversation, but never creates one by inference. Failed stays visible until replaced or cleared. Waiting outranks failed, then pending, done, working and idle. Failure settles and notifies with the same one-second rule, including the chat apps while away. Failed ends a turn for stats, `wait --until idle` and idle restart. Model, context, resume and last-message readers stay agent-specific.
- **Any recognised agent can report status**: `activity::Pane` follows the kind's string, including the launch-only catalogue and `agent_commands`, rather than requiring a `Known` reader. Process arguments still establish identity; an OSC `app` cannot turn a shell or a build into an agent. Each record is associated with the foreground pid that emitted it, so retained results do not override a later agent. Changing foreground process expires active and idle records; done and error records survive back at the shell with the originating agent identity (`Term::status_agent`), and are never applied to a new foreground agent. A finished result at the shell is acknowledged when its tab is seen; failure remains until replaced or cleared. Shell output never inherits the identity of a departed agent; already recorded results retain their original pid. A shell prompt (OSC 133 A) expires active and idle records too. Alternate-screen switches and soft resets keep records; RIS clears all. `clear` removes an id and its descendants (or all records at the root), returning to heuristics when no applicable record remains. The most urgent record wins, including children whose parent has no record.
- **Keep the published Ghostty binding pinned**: `libghostty-vt` 0.2.2 predates the upstream OSC 7501 callback. A bounded streaming observer beside the emulator recognises OSC, shell prompts and RIS without reading strings embedded in DCS/APC/PM/SOS. Ghostty continues to receive every byte and owns rendering and its existing replies. For a support query, the emulator feeds the prefix through Ghostty before sending the fixed reply through the same PTY writer, so replies stay in request order even within one read. The observer accepts BEL and ST across arbitrary read boundaries, validates the revision 0.4 grammar and all size/base64/control-character limits before applying a report, keeps at most 256 records and evicts the oldest updated one. Optional labels and messages are validated but not displayed; `kind`, `progress` and `app` do not affect presentation. No heartbeat, settings, hooks or new dependencies. The specification is [Program Status Protocol](https://www.superlogical.com/rex/docs/build/program-status); the upstream implementation is [ghostty#14560](https://github.com/ghostty-org/ghostty/pull/14560).
- Every 500 ms (`WATCH_AGENTS_EVERY`, from `App::refresh`) each pane whose foreground process is Claude Code, Codex, Gemini CLI or opencode (`agents::detect` on its arguments) gets an `Activity`: working, waiting or idle. For Claude the source is the file Claude Code keeps for each running process, `<CLAUDE_CONFIG_DIR or ~/.claude>/sessions/<pid>.json`, the registry behind `claude agents --json` (its documented interface for status bars): `status` is `busy`, `waiting` (permission prompt, question, dialog), `idle` or `shell` (turn over but a Bash it started with `run_in_background` still runs). `shell` counts as working, like Claude's own agents view: Claude wakes up when the command ends, so it was not done (a dev server left running keeps the tab `◐`). It is its own `Activity::Shell` all the same, which `Pane::status` shows as working (so the UI, the rollups and the notifications are unchanged) and only the commands for scripts tell apart (`Pane::background_shell`, `Pane::state`; see Commands for scripts and agents): an orchestrating agent whose agents leave watchers behind had no way to stop waiting for them (#127). A Monitor that runs a command is a background Bash too, so it gives `shell` (checked live on 2.1.289); one on a WebSocket runs no shell and may leave it `idle`. Its fields are not documented, so a missing file or an unknown value falls back to the title Claude sets (`◐`/`◑`, or braille in older versions, while busy; `✳` otherwise; it stays `✳` when Claude sees `TMUX`, `STY` or `ZELLIJ`), then to idle.
- No hooks and no screen scraping. Hooks mean editing the user's `~/.claude/settings.json` (or shipping a plugin), `Stop` never fires on an Esc interrupt and the permission notification comes ~6 s late; Claude's screen changes too often to match. The session file turns idle within a tick of an interrupt and waiting as soon as a prompt shows.
- `Status` adds done: a pane that went from working or waiting to idle while its tab was not seen (`App::seen_tabs`: the window's visible tab, the active tab unless the compact menu or a file shown full screen covers the pane, and the tab of every active, sized, visible view, see Commands for scripts and agents) is done until that tab is shown. `watch_agents` clears it for the visible tab on every `refresh`, not only every 500 ms, so a click shows `○` at once. An unknown state counts as idle, so a fresh Claude never looks done.
- **Claude Code turns that end on an API error (#802)** (`agents/claude/transcript.rs` `Transcript::failed`, `agents/claude/mod.rs` `Reader::activity`): a turn whose newest assistant line (not a sidechain one) has `"isApiErrorMessage": true`, as `read --last-message` already recognises it, is `Activity::Failed`, so `Status::Failed`, the red `!`, the `failed` notice (with the needs-you sound), `send` taking the next prompt, `wait --until turn-over` ending `failed` and a flow waking its orchestrator. Before, the session file said `waiting` (cornercase saw `waiting` with `dialog: false`, `at_prompt: false`) or `idle`, a question nobody had asked: `send` refused the pane, nothing woke the orchestrator and flows stalled for 50 minutes, twice in a day. Both `idle` and `waiting` of the session file map to `Failed` while the error is the newest of the transcript's error, reply and prompt (`failed` clears on a human prompt, a queued prompt or a typed `/` command, and on any later reply); `working` and `shell` stay as they are, since a busy session is a new turn or a retry and a background shell wakes Claude. System, meta and tool-result lines after the error leave it (real files hold `system`, `last-prompt` and `queue-operation` lines after it). **A logged-out account is not told apart** (decided without asking, #802 left it open): an expired login is `authentication_failed` with no `apiErrorStatus`, the Cloudflare block of #802 is the same `error` with status 403, and there are also `rate_limit` 429 and `invalid_request` safeguard refusals (17 transcripts of this machine, read 2026-11-13), so `error` cannot tell them apart and only the absence of an undocumented status would; all of them need a person (`failed` notifies like `waiting`) and the only difference is that automation may try again, once and bounded (see Flows › Waking the orchestrator). Limits: a menu shown after a 429 still reads `failed`, but `send` refuses it by its `dialog` check and the flow wake falls back to the person; other agents are not covered (Copilot's `session.error` stays unmapped as decided in Each agent's reader, Codex, Gemini and opencode write nothing known, Vibe already reports `error` over OSC 7501); a turn shorter than one 500 ms read is never seen working, so it wakes no one, as before.
- **Pending review** (`Status::Pending`, a bold `●` in the brand blue 27): a mark the user puts on an agent's pane by hand, because launching several agents left finished work to review and `✓` was not a record of it: it goes the moment the tab is shown, a quick look through the tabs wiped it, and a restart lost it. The mark lives on the pane (`activity::Pane::pending`), not the tab, since the agents section and a split tab hold one agent per pane; a tab's menu (` ⋯ ` or right-click on its row, in the lists, the tree and the tab bar) marks or reviews every agent pane in it, the pane's right-click menu, a right-click on its row in the agents section (`App::open_agent_menu`, the one menu those rows have, so a busy list can be gone through without leaving the pane being read) and the keys menu's `m` act on that pane, and `cornercase mark [--pane|--tab] [--reviewed]` lets a script or an agent do it (its own pane by default, so an agent can mark itself at the end of its turn). Only panes with an agent cornercase reads take it (`Pane::agent`); others are refused or offered nothing. Showing the tab does not clear it (`Pane::see` leaves it); it goes when marked as reviewed, which clears `done` too, or when the agent goes from idle or waiting to working, which means it got a new prompt or an answer and the user is iterating on it again. Going from a background shell to working does not clear it (the agent woke up by itself), and neither does a mark put on while it works: it shows once the turn is over. It sits between done and waiting: a question still comes first, and it beats `✓` since it is the user's own statement. It needs you (`Status::needs_you`), so it reaches the workspace, project and group rows, the compact `≡` and the keys menu's `a`, but it never notifies (`Status::notifies` is waiting, failed and done only: the user just put it there) and stats do not count it as time waiting for the user (it may stay for days). Waits end on it as on idle (`--until idle`, the default, `turn-over`, `restart --when-idle`); `status`, `--panes` and `events` give it as `pending`. Only by hand for now: turning every unseen finish into a sticky mark was left out, to see first how the manual mark is used.
- A tab shows its most urgent pane (`Tab::status`, the order of `Status`): waiting `!` > failed red `!` > pending `●` > done `✓` > working `◐` > idle `○`, before the name. **Working icon** (`working_icon` in `config.json`, Settings → UI, `config::WorkingIcon`): `moon`, the default, keeps the still `◐` (`activity::MOON`); `spinner` steps through `⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏` (`activity::SPINNER`), one frame every 100 ms (`activity::SPIN_EVERY`), the same frame on every row, from the time since the process started (`activity::spin_frame`). `View::spin` carries the frame, `None` for the moon, so one value reaches every place the icon is drawn (tabs, the tab bar, the agents section, the compact `≡`, the toast). `App::tick` wakes for the next frame only with the spinner on and some tab working; otherwise the loop stays on its 500 ms tick. The spinner was the only icon in 0.12.84 to 0.12.86 (#240): it shows at a glance that a turn is still going, but a column of moving icons keeps pulling the eye away from the pane being read, and with an agent working it draws every window ten times a second, so the moon came back as the default and the spinner became a choice. A pick rather than a switch, like `tabs`, since the row names what it shows. A still with the spinner on, such as a test, shows the first frame. Chat messages (Telegram, Discord) keep `◐` whatever the setting, since a message does not move. `!`, `✓`, `○` and the shell marks never move. A tab without an agent shows its shell instead (`TabEntry::icon`), in the muted grey: `▸` while a program runs in the foreground of any of its panes (`Tab::running`), `›` at the prompt. Every tab has an icon so their names start in one column: a shell tab used to start two cells to the left of an agent's, and the list read as two indents. Two states rather than one fixed mark, so the icon answers what an agent's does (is it doing something?) and a dev server that died back to its prompt shows at a glance. It is `!Term::shell_in_foreground()`, read when the row is drawn, like the tab's label (an editor started with a command counts as running); caching it on the 500 ms agent reads was tried and dropped: the label already looks up the foreground process on every draw, and the cache only added a field and up to half a second of lag. Grey, never yellow, so a dev server that runs for hours does not compete with an agent working, and no done: every `ls` in a hidden tab would leave a mark. The agents' own glyphs were rejected for the same reason (a `◐` then a `○` means done for an agent and would not for a program), and `▶` because it has an emoji presentation that some fonts draw wider than a cell. Shell icons never reach the workspace, project or group rows. Workspace, project and collapsed group rows show only what needs you (`agents::activity::attention`: waiting, pending or done), right-aligned and before `↓n`; working stays on the tab so the sidebar is not always full of icons. A collapsed workspace is the exception (#294): its tabs are hidden, so its row shows the most urgent status of its agents (`agents::activity::highest`, the order of `Status`, so `◐` or the spinner and `○` too), in the tree and the lists (`ui::workspaces::Badge`); shells show nothing. The compact `≡` shows the same for every tab but the visible one (`View::attention`). The agents section (see Layout) lists each agent pane with its own status, not its tab's.
- Claude Code, Codex, Gemini CLI, opencode, Grok Build, Cursor CLI, GitHub Copilot CLI and Vibe CLI; supported agents register through `Known` as described under Agents. `activity::Pane` stores the kind string so launch-only and custom agents can report OSC 7501, while `context::Pane` stores `Option<Known>` for its readers; `app::agent_watch::agent_in` detects the identity, updates its reader, remembers its conversation, calibrates the input-box check through `Known`, and asks the pane for activity. It has no agent-specific arm. An agent running through `ssh` or in a container is not seen (no local process, no local file).
- **An agent that exits by itself** (#826: SIGTERM, a crash, `/exit`) leaves its pane at the shell and its status gone. A flow role's pane keeps its conversation so the role can be brought back: see Saved session › A flow role whose agent exited by itself. The Flow panel draws such a role as `exited` with the reopen `▶`, not as idle (#829, see Flows › Recording, progress, the diagram and the Flow panel).
