# Remote windows

Code: `remote.rs`, `remote/shell.rs`, `remote/known.rs`, `client.rs`, `client/window.rs`, `client/requests.rs`, `cli/reach.rs`, `ui/remote.rs`, `process/handles.rs` (`hand_down_nothing`)

- **`cornercase remote <destination>`** (#104) runs the window locally and attaches it to the server of another machine: `ssh -T … -- <destination> sh -c '<PATH>; exec cornercase proxy'`, and the protocol goes through ssh's stdin and stdout instead of the socket. The user's own `ssh`, so their config, keys, agent, `ProxyJump` and `ControlMaster` apply and cornercase never handles a credential; `--` ends ssh's options, so a destination can never be read as one. Nothing in the protocol needed the socket: frames, OSC 52 and notifications already went through the client, and the colours and the notification channel come from the local terminal in `Hello`. `ssh -t host cornercase` already worked but ends with the connection and puts one more terminal layer on the remote side.
- **`cornercase proxy`** (hidden, like `server`) prints a banner line, `cornercase-proxy <protocol> <release>`, reads the client's first message, and only then connects (finding the server, and starting it only for a window's `Hello` or a `start-server` request, `remote::starts`; `cli` hands `remote::proxy` a closure that calls `client::find_or_start` or `client::running`, so `remote` imports nothing from `client`; moving it into `protocol` was rejected, since it would drag the server's start, the log file and a polling interval into the framing module), so a client that refuses the version starts nothing there. It reaches the same server whatever environment the ssh session has, since the socket no longer depends on it (#355). Then it copies bytes both ways; the socket's end ends it, and its stdin's end shuts the socket's write side, so the server sees the client go. The banner is a text line rather than postcard so that any future version can read it; the client skips other lines first (`BANNER_LINES`, `BANNER_BYTES`), since some shell rc files print in non-interactive shells, and reads it byte by byte through the `BufReader` it then keeps for the protocol. The socket folder and peer checks stay, since the proxy is a local process of the same user there.
- **Versions**: `Hello`'s build id is the binary's modification time, so two machines never match (and are often not the same platform). The client attaches only when the banner's protocol and release equal its own, and says which side to update otherwise (`Error::RemoteOlder` / `RemoteNewer`, from `version::newer`); a cornercase from before the proxy fails with clap's `unrecognized subcommand` (`RemoteTooOld`), a missing one with sh's 127, or 126 and `No such file or directory` from bash, which is macOS' `sh` and says so for a path that is not there, or 127 from the lines written for cmd and PowerShell (`RemoteMissing`; see A Windows machine at the other end). With a terminal, an older remote is offered `cornercase update` through `ssh -t`. The proxy replaces the build in the forwarded `Hello` with its own and empties its openers (`remote::rebuilt`), so the server's check still means what it means locally: the server must come from the binary that answers. A server from an older build there is offered a restart like locally, through `ssh <destination> cornercase kill-server`, with `update::restart::confirmation(None)` (asking the old server for its list would take another ssh connection).
- **PATH**: a command run through ssh gets a short `PATH` without the login shell's profile, where the install script's `~/.local/bin` and Homebrew's folders are usually added. The remote command appends those, `~/.cargo/bin` and `/usr/local/bin` to the `PATH` (after it, so the user's own order wins) and `--command` replaces `cornercase`, put in the script as is so `~` and `$HOME` expand. The script is single-quoted for the login shell, which may be fish or zsh, and run by `sh`.
- **A Windows machine at the other end** (#603, `remote/shell.rs`, `remote/known.rs`): Windows' OpenSSH Server (Win32-OpenSSH) runs a command with its `DefaultShell` (`HKLM\SOFTWARE\OpenSSH`): `cmd.exe /c "<command>"` unless an administrator set it, often to `powershell.exe -c <command>` or `pwsh`. Neither has `sh`, and cmd reads no single quotes, so sh's line failed there with status 1 (see Windows › Beyond this machine).
  - **sh's line first, a probe only after a failure**: the line for `sh` goes first, unchanged, so a Linux or macOS machine costs nothing more when it works. Only when it ends without the banner, and with a status that is not ssh's 255, sh's 127 (or 126 and `No such file`), 0, or clap's `unrecognized subcommand` (`Failed::maybe_another_shell`), cornercase sends one probe, `echo cornercase-shell-"x"-$true`, and reads its line: cmd keeps quotes and knows no `$` (`cornercase-shell-"x"-$true`), PowerShell joins the quoted word and expands `$true` (`cornercase-shell-x-True`), sh joins it and expands an unset variable (`cornercase-shell-x-`). No environment variable (`%OS%` was the first idea) and no message (cmd's and PowerShell's are translated: here cmd says `"sh" no se reconoce como un comando interno o externo`), and nothing but `echo`, so a shell that reads it otherwise (fish drops a word whose variable is unset, csh refuses an undefined variable) prints nothing cornercase reads and runs nothing else. An answer of sh, or none, keeps the first failure, so the probe never makes cornercase run another command than the one it tried; an answer of cmd or PowerShell sends the line for that shell.
  - **Remembered per destination** (`remote/known.rs`): cmd or PowerShell is written to `remote-shells.json` beside `session.json` (the client's state folder, a debug build's own), so later commands and a window's reconnects take one connection again; sh is what cornercase tries anyway and is never written, so for a Linux or macOS machine the file is only read, once per process. A remembered shell whose line fails in the same way is asked again and replaced: cmd's line under Windows PowerShell 5.1 is a parse error at `&&`; PowerShell's under cmd runs nothing, since cmd looks for a program named `'C:\…'` with its quotes; either under `sh` is a syntax error. The file is read again before each write, so two commands that learned two machines keep both.
  - **The cost**: the first connection to a Windows machine takes three sessions (sh's line, the probe, the right line), and three password prompts for a password login. A process command (`update`, `restart`, `kill-server`, `logs`) has its stderr inherited, so the far shell's `'sh' is not recognized` shows first, then `` `winbox` runs commands with cmd.exe, not sh: running it again for it ``; holding its stderr back would change how those commands print everywhere. Nothing ran the first time, so running it again changes nothing twice. For those commands the probe follows only status 1, what cmd and PowerShell give for a missing `sh`, so a Linux machine whose command failed with 1 (`logs` with no log yet) pays the probe after that failure, never after a success.
  - Rejected: probing first (a round trip more on every Linux or macOS connection); one line that sh, cmd and PowerShell all read (their quoting differs, and cmd would still find no `sh`); a `--shell` flag (the user seldom knows sshd's `DefaultShell`, which an administrator can change); sshd's `RemoteCommand` or a subsystem (configuration only an administrator can change); cmd's line running `powershell -Command` to have one language (about half a second more on every connection, and two quoting layers).
  - **cmd's line** (`shell::cmd_line`): `set "PATH=%PATH%;%USERPROFILE%\.local\bin;%USERPROFILE%\.cargo\bin" && [set "CORNERCASE_TIED=1" && ]("%SystemRoot%\System32\where.exe" /q <program> || exit 127) && <program> <words>`. The folders are where the PowerShell installer puts cornercase (`install-path`, which it also adds to the user's `Path`; Win32-OpenSSH builds a session's `PATH` from the machine's and the user's in the registry, so it is usually there already) and `cargo install`'s. `where` comes first because cmd ends with status 1, not its own 9009, when it finds no program, and with 1 too for a path that is not there (`The system cannot find the path specified`), so a missing cornercase looked like any failure; `where /q "<folder>\:<file>"` looks in that folder with `PATHEXT` as cmd does (checked: a folder, `%SystemRoot%:`, a drive's root, a name without `.exe`; a folder of that name is not a match). An `if errorlevel` after the program was rejected: a false `if` sets the status to 0 (checked), and `call exit %^ERRORLEVEL%` works only through a caret trick. The line never starts with a quote, which `/c` would strip together with the line's last one. A word is bare when it holds only letters, digits and `-_./\:,+=@`, else double-quoted with the backslashes before the closing quote doubled for the C runtime; `&|<>^()` are plain inside quotes, while `"`, `%` and `!` (with `DelayedExpansion` set in the registry) are read even there, so a word or `--command` holding one is refused (`Error::WrongUsage`, saying which character), as is a control character.
  - **PowerShell's line** (`shell::powershell_line`): `$env:PATH = $env:PATH + ';' + $env:USERPROFILE + '\.local\bin' + …; [$env:CORNERCASE_TIED = '1';] try { & '<program>' '<word>' … } catch [System.Management.Automation.CommandNotFoundException] { exit 127 }; exit $LASTEXITCODE`. `-Command` ends with 1 whenever its last command failed and drops a native program's own status, so `exit $LASTEXITCODE` passes it on (3, `Partial`, came through), and a missing program, a terminating error caught there, exits 127 as sh does. Words are single-quoted (`agents::powershell_quoted`, typographic quotes doubled too), and what Windows PowerShell 5.1 hands a program in pieces is refused as in an agent's line (`agents::splits`, `--%`), with an empty word (5.1 drops it) and two spaces in a row: in a terminal session (`ssh -t`, `update`'s question) Win32-OpenSSH appends the command to `powershell -c` unquoted, so it is split at spaces and PowerShell joins the words with one. The line holds no `"`, so Win32-OpenSSH's quoting of it (`"` as `\"`, backslashes doubled only before a quote, not at the end, read in its `build_commandline_string`) has nothing to get wrong. Under both shells 127 reads as `RemoteMissing`, as sh's does, so its texts did not change.
  - **`--command` there is a path**, or a name, not shell text: which shell runs it depends on sshd, a path means the same to both, and quoting it is what lets the line tell a missing program apart. `~\` or `~/` at its start stands for `%USERPROFILE%` (`$env:USERPROFILE`), and `/` becomes `\`. sh's line still reads it as sh does, so the first try on a machine not yet known is the same as before.
  - **Bytes pass through both shells**: cmd only starts the program on the session's pipes, and Windows PowerShell 5.1 does not redirect a native command whose output it does not capture, inside `try` too; 00, FF, CR LF and 80 came back unchanged through both (checked with a program that copies its input to its output).
  - **The proxy keeps its handles from the server** (`process::hand_down_nothing`, Windows only, called first in `remote::proxy`): in the check below, the window through PowerShell never noticed its killed `ssh.exe`, while the one through cmd did, and it did once the proxy kept every handle from what it starts. So Windows PowerShell hands a native program inheritable handles besides its three standard ones, a second copy of the session's pipes among them, and the server the proxy started inherited that copy, since `spawn_detached` clears only the three standard handles (Windows › The server in the background), and held the pipe open (the handles were not listed one by one). With a real sshd the local `ssh` would still end, but the session there would linger on the pipe the server holds. Now the proxy clears the inherit flag of every handle it has, from the snapshot `NtQueryInformationProcess` gives (the one the context line reads, `process/handles.rs`), before it can start a server, which gets its log and `NUL` only. In the proxy and not in `spawn_detached`: clearing every handle of a process while another thread starts a child (the test binary does, and std makes that child's handles inheritable only around its `CreateProcess`) could leave the child without its standard handles, and the proxy starts nothing else and runs no other thread by then. Rejected: `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` (std's `raw_attribute` is unstable, and a `CreateProcessW` of our own gives up std's `Child`).
  - **The session there**, read in Win32-OpenSSH's source (`contrib/win32/win32compat`, branch `latestw_all`, on 2026-11-04): sshd, running as SYSTEM (its default), loads the user's profile (`LoadUserProfileW`) and starts the session with `CreateEnvironmentBlock` for the user's token, so `USERPROFILE`, `APPDATA` and `LOCALAPPDATA` are the user's and `paths` finds the socket a window at that desktop uses; without `LOCALAPPDATA` it takes `%USERPROFILE%\AppData\Local`, the same folder unless it was redirected (checked with the stand-in below). The shell runs in a job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE | JOB_OBJECT_LIMIT_BREAKAWAY_OK`, whose handle it holds last, so what is left in it ends with the session; the server starts with `CREATE_BREAKAWAY_FROM_JOB` (Windows › The server in the background), and leaving a job that allows it leaves the jobs above it that allow it too (Microsoft's Nested Jobs), so the server outlives the session and nothing needed changing. A key logon is an S4U network logon, a password one `LOGON32_LOGON_NETWORK_CLEARTEXT`; an administrator's session is elevated, by design (Win32-OpenSSH #1652), so a server started through ssh runs its shells and agents elevated, and a window at that desktop still attaches to it (the peer check reads the user's SID, which a process that is not elevated can read from an elevated one, see Windows › The local socket), which UAC, in Microsoft's terms not a security boundary, does not stop. A server started at the desktop first stays as it was for both.
  - **Not covered**: `restart --when-idle`'s tie reaches the command (`CORNERCASE_TIED`, tested through both shells), but Windows cornercase does not watch its input yet (`client::watched` answers `None` there), so killing the command here leaves the wait there, as before #537. A key logon has no network credentials and no DPAPI key, so Credential Manager (where `gh` and Git Credential Manager keep tokens) may not work in the panes of a server started through ssh (not checked). A machine whose `DefaultShell` is bash (Git's or WSL's) counts as a POSIX one, as before.
  - **Checked live** (2026-11-04, Windows 11 10.0.26200, Windows PowerShell 5.1.26100, a debug build): there is no sshd here (installing OpenSSH Server needs an administrator), so a stand-in `ssh.exe` skipped the options and the destination, joined the rest as ssh does, put itself in a job with `KILL_ON_JOB_CLOSE | BREAKAWAY_OK`, gave the shell only its standard handles (as Win32-OpenSSH's `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` does), a session's `PATH` (the machine's and the user's from the registry, with no `sh.exe` in it), `HOME` and `SSH_CONNECTION`, with and without `LOCALAPPDATA`, and started `cmd.exe /c "<command>"` or `powershell.exe -c <command>` quoted as Win32-OpenSSH does. Through each shell: the first command (`logs --path`) took sh's line, the probe and the right line, three sessions, and wrote the answer; then one session per command: `start-server`, `status` with the same `boot` as a local `status`, `new-tab`, `send` and `keys` into a pane there and `read` here showing it, `logs --path`, `open` with a `C:\…` path (and `\Windows` refused), `kill-server`; the server outlived every session's job, with no stand-in, shell or proxy left; a missing `--command` path gave `RemoteMissing` for a request and for `kill-server`, and a `%` in it was refused for cmd; a wrong remembered shell was asked again (three sessions) and replaced. The window, in a ConPTY read with vt100, through each shell: attached after those three sessions, ran a typed line there, showed Connection lost when its `ssh.exe` was killed, attached again through one session with the remembered shell, the same pane still held its variable, and ` More ▴ ` › `quit` ended it with status 0. The tests of `remote::shell` run both lines through the real `cmd.exe` and `powershell.exe` on Windows (plain and as a terminal session runs them): found in `.local\bin`, words with `& | < > ^ ( ) '` and spaces arriving whole, status 3 passed on, a missing program 127, `~\`, the tie. Not checked: a real sshd, so neither its environment, job and handle list nor a PowerShell session's profile (sshd passes no `-NoProfile`; what a profile prints before the banner is skipped like an rc file's), PowerShell 7 (`pwsh`, not installed here) as `DefaultShell`, a password login, a Linux or macOS client reaching a Windows machine (its ssh passes the status in 8 bits, which 1 and 127 keep), a real elevated session.
- **Reconnecting**: a remote window does not end when its link does (`Received::Ended`, or the server's `Restart` after an update, which it never `exec`s for). It keeps the last screen and draws a notice over it (`ui::remote`: the rounded dialog, ` quit ` as a grey pill, written cell by cell to the backend so the blank cells inside cover the old screen, which ratatui's diff would skip). Attempts run on a thread (`Incoming::Linked`, numbered by `generation` so a late answer for a dropped link is ignored): at once, then after 1, 2, 4, 8 and every 15 s (`backoff`), the countdown redrawn on the second (`until_next_second`). A link counts as healthy only once it showed a frame (`Retries`): the banner comes before the proxy reaches the socket, so a proxy that fails after it (a socket folder it refuses, a server that does not start) would otherwise reset the count and run ssh back to back; the notice then shows the remote's error. ssh errors are retried and shown (`remote::Stderr` keeps the first 8 and the last 20 lines of ssh's stderr; the shown reason is the proxy's own `Error: …` line when there is one, else the last line, since a proxy run with `RUST_BACKTRACE` set ends in dozens of backtrace lines that would otherwise push its first line out and leave `no cornercase server is running` unrecognised, as CI showed); a version mismatch, a missing cornercase or a rejection ends the window (`remote::fatal`). Once linked, the client sends `Hello` again and the server, which counts it as a new client, clears and redraws everything. `Esc` or a press on ` quit ` gives up, a detach and not an error. The sidebar's ` Quit ` (`Detached`) and `kill-server` (`Shutdown`) still close the window.
- **Noticing a dead link**: a laptop that sleeps or changes network leaves a TCP connection that nobody closes. ssh's `ServerAliveInterval=5` and `ServerAliveCountMax=3` end it within ~15 s; they override the user's config (the command line wins in ssh), which was preferred to a heartbeat in the protocol, since an old server would not answer one. `ConnectTimeout=10` bounds each attempt. Reconnects add `BatchMode=yes`: a password or passphrase prompt would read the terminal the window holds in raw mode. The first connection is made before the window opens, on the plain terminal, so it can still prompt (ssh asks on `/dev/tty`; its stderr is piped and kept for the error).
- **The client loop** (`Window`): one channel (`Incoming`) for terminal input, server messages, link attempts and signals, so the main thread can draw the notice and take `Esc` while no server is there. Messages to the server go through a writer thread per link (a hung ssh blocks it, not the loop). The input thread polls the tty for at most 100 ms and stops when `attach` returns (`Threads`), waiting at most 300 ms for it. Each read follows readiness and EOF or hangup detaches the window (Client / server), including while reconnecting. A thread left reading after a rejection could consume the terminal's answer to the next window's colour query; owning the bounded reader and decoder also gives each attach fresh parser state. Its signal thread is closed there too (`Handle::close`).
- **Tests**: a fake `ssh` first on the `PATH` (`fake_ssh` in `tests/e2e/remote.rs`) skips the options and the destination and `exec`s the command locally, so the proxy reaches the test's own socket and keeps the fake's pid: killing it drops the connection, while without `exec` a `sh -c` left between them would keep the pipe open. It also appends its pid to `ssh.runs`, so a test counts the connections a command opens.
- **Commands on another machine (#476)**: `cornercase --remote DESTINATION <command>` (or `CORNERCASE_REMOTE`) sends a command for scripts and agents through the same `Remote::connect`, so the banner, the `PATH` search, `--remote-command` (the window's `--command`), the keep-alives and `ConnectTimeout` are not each client's to rebuild.
  - **Why**: every client that ran `ssh devbox cornercase …` met the same things: cornercase is not on the `PATH` of a command run through ssh, each argument has to be quoted for an unknown login shell (fish reads `\\` and `\'` inside single quotes, sh does not), there is no banner or version check, and a stream kept running there after the local `ssh` ended (#475). The request travels in-band, as the proxy's first message, so arguments and standard input never pass through a shell. The proxy ends its socket when its stdin ends, so a stream stops there when the command stops here, even if it is killed.
  - **How**: `client::requests` keeps a `OnceLock<Remote>` (`use_remote`, like the view) and every request opens a `Link`, a socket or ssh's pipes, which window and commands share, or takes the one its feature check asked on (#557, see One ssh connection per request). Unit tests never set the static: it is process-wide.
  - **A stream stops when nothing reads it** (#475) there too: `client::Source` lets the follow loop poll the link, a socket or ssh's stdout pipe (and tell when its `BufReader` already holds a message), next to the command's own stdout, so a closed reader ends the command, which drops the link and kills ssh. Not checked live: real ssh, and how a macOS pipe reports its reader leaving over ssh (`HUP`); only the fake `ssh` of the e2e test (`a_remote_follow_ends_when_its_reader_leaves`).
  - **Always `BatchMode=yes`**: a script or an agent cannot answer a prompt, and an agent's command shares its pane's terminal, where ssh would ask on `/dev/tty`. An unknown host key is refused: connect once by hand.
  - **Commands take the same release or a newer one, the window only the same** (#480, `Remote::check`, `remote::Use`): `Use::Window` keeps the rule of before (protocol and release equal), `Use::Command` accepts a release equal or newer (`version::newer`) and ignores the protocol number. A request connection only ever receives `Response`, `Rejected`, `Detached`, `Shutdown` and `Restart`; `Sound`, `Open`, `Browse` and frames go to clients with a screen only, and `ClientMessage::Request` and `ServerMessage::Response` keep their postcard indices. So **a new `ServerMessage` variant must go to windows only**, or an older command that `--remote` lets through would read `InvalidData` and report `OldServer`. An older remote is refused (`Error::RemoteBehind`, with the `cornercase --remote DESTINATION update` line to run): an older server drops the fields a newer command sends without a word (`changes stage`, `unstage` and `discard` always send `digest`, so a server from before it would act on a newer version of the file than the one the user saw), and two machines can stay apart for weeks, not minutes. Rejected: accepting any release (what the local promise says, but the gap is longer here); a structured mode with strict fields (the CLI serializes every field, `null` included, so an older server would refuse every request whose struct gained a field); a warning on stderr (noise on every command of a UI). The same text still says `there` for the window, which offers the update through `ssh -t`.
  - **A server lacking a feature there** (`client::requests::require_on`): a newer binary can still run a server nobody restarted, since requests skip `Hello`'s build check. The message then names `cornercase --remote DESTINATION restart` and `update`, not this machine's, and takes the remote as a parameter because unit tests never set the static.
  - **Only `start-server` starts a server there**, as locally (`remote::starts`). The proxy used to start one for any first message, so a program speaking the framed protocol through it directly now gets `no cornercase server is running`.
  - **Errors after the banner**: when ssh's stdout ends before the answer, the link waits at most 2 s for ssh to exit and for its last stderr line (`Remote::ended`). The proxy's `no cornercase server is running` becomes `Error::RemoteNoServer`, which is not `Error::NoServer`: `stats` would fall back to the local `stats.json`. A clean exit keeps the local meaning, anything else is `Remote::failure`. The wait costs up to 2 s only when the link ended without an answer (ssh not yet gone, or a stderr line still being read), never on a normal command. Rejected: a framed error answer from the proxy, since `read --last-message` would keep it per pane as `Error::Control`, the regression #472 removed, and `Rejected` already means too old.
  - **Which commands take it** (`cli/reach.rs`): the commands that only send requests, `start-server`, `stats` (no local fallback) and the plugin commands that ask the server; with no command it is `cornercase remote`. `update`, `restart`, `kill-server` and `logs` run there as processes (#480, `reach::there`, `reach::run_there`): `ssh -o BatchMode=yes … sh -c 'PATH=…; exec cornercase kill-server --yes'`, with the arguments rebuilt from the parsed structs by destructuring them completely, so a new flag fails to compile until it is forwarded. They are not requests because they act on that machine's own lock (`kill-server` and `restart` wait on it), binary (`update`), log file (`logs` works with no server) or `ClientMessage::Restart`, and running the remote's own CLI works whatever version runs there, with no banner. `-t` only when stdin and stdout are both terminals, so the remote can ask its `[y/N]` and `Ctrl+C` reaches it, since with `-t` a piped `logs | grep` would get CRLF line ends from the pty; always `BatchMode`, as for every command. Stdout and stderr are inherited, and stdin with `-t`; without a terminal stdin is a pipe this command holds (see the next point). The exit status passes through (0 and 1 as they are, 3 `Partial`, 127, or 126 (what bash, macOS' `sh`, gives for a path that is not there; the message is the remote's, since the streams are inherited), `RemoteMissing`, any other code, ssh's 255 included, `Error::Exited`, which `main` turns into that exit code without a message since the remote or ssh already said why). The plugin commands that install or change plugins act on this machine (their sources are paths here, and they ask for trust) and refuse with exit 2, the variable included: quietly acting here would act on the wrong machine for a client that set it once. `remote`, `skill`, `server` and `proxy` refuse the flag and ignore the variable, so the proxy there never obeys it. `--remote-command` alone is exit 2.
  - **A wait there ends when the command here does** (#537): `restart --when-idle` and `update --when-idle` wait on the server there, and without a pty sshd sends the command no hangup when the link drops, so killing the command here (the local ssh outlives it) used to leave the restart pending, and the server restarted once its agents were idle, stopping every program in its panes for a restart its client thought cancelled. Now `reach::run_there` without a terminal runs ssh, for a command with `--when-idle` only (the others keep the caller's stdin), with a pipe for stdin (`remote::Run::Tied`) that it holds and never writes to, and the script exports `CORNERCASE_TIED=1` beside `PATH`. `Command::status` and `Child::wait` close a piped stdin before waiting, so `Remote::run` takes it out of the child and drops it after the wait; with `status` the wait there would end at once. Killing the command, even with `SIGKILL`, closes the pipe, ssh reads the end and sends it on, and the command there sees its stdin end. Only `cli::update::restart_when_idle` reads the variable: while it waits it polls stdin beside the server socket (`client::input_ended`, only when stdin is a pipe or a socket, as `client::watched` decides, so a terminal or `/dev/null` never ends a wait). The end is `POLLHUP` on a pipe, or `POLLIN` and a read of 0 bytes on a socket pair whose writer only shut down, which is what sshd may hand the command; any other event or error stops the watch and never cancels. It watches only before the server's answer, since an answer means the restart is decided. It then shuts the socket, the server reads the end, `App::forget` drops the pending restart and the toast clears, and the command exits quietly with status 0, as a follow whose reader left. A check before the request keeps a command killed while `update` installed, or while ssh connected, from sending it at all. The variable is not a flag because an older cornercase there refuses an unknown flag with status 2, and `update` is the command that runs against older ones; an older one ignores the variable and waits as before (the same reason as `CORNERCASE_RESTARTED`). `ssh -o SetEnv` was rejected: sshd takes only what its `AcceptEnv` lists. The proxy never gets it, and `start_server` removes it from servers, so no pane inherits it. The tie needs this release on both machines; the first `--remote … update --when-idle` to it still runs the old wait there, untied. Rejected: the wait as a `restart-when-idle` request through the proxy (`update` still has to install there as a process, the proxy's version rule would refuse `restart --when-idle` against an older remote, and the old binary's restart offer would need a flag), and `-tt` (a pipe gets CRLF line ends and the local ssh still outlives a killed command). Not covered: a link that drops without closing, such as a sleeping laptop, which sshd there notices only through `ClientAliveInterval` or TCP keep-alive, like the proxy's streams. Not checked live: a real sshd's end of the command's stdin (pipe or socket pair) and `ControlMaster` clients; only the fake `ssh` (`killing_a_remote_restart_when_idle_calls_it_off_there`).
  - **`CORNERCASE_REMOTE` reaches `kill-server`, `restart`, `update` and `logs` too** (#480): they used to refuse it so that a client which set it once would not stop the wrong server here; now that they run there, the variable sends them there like every other command, so a program that set it means that machine for all of them, and `kill-server`'s help says so, since a surprise costs most there.
  - **The variable** is kept out of servers (`start_server` removes it) but applies inside panes: `CORNERCASE_REMOTE=devbox ./script` in a pane is deliberate, and ignoring it would act here without a word. It is meant per program, not in a shell's rc file.
  - **Paths** the CLI resolves in its own folder (`open`, `config project`, `flow save --path`) must be absolute with `--remote`, since the folder here says nothing about there. The path is the remote's, so it is judged and written by a Unix server's rules (or a Windows one's, below), not this system's (`cli::reach::path_on`, #603): it must start with `/`, which Windows' `is_absolute` refused as relative for want of a drive. From Windows, its backslashes become `/` and a Windows path (a drive, `C:x`, `\…`, `\\host\share`) is refused with how to write a Unix one, unless the machine there runs Windows: Git Bash turns an argument like `/srv/x` into `C:/Program Files/Git/srv/x` before cornercase sees it, so the message names `//srv/x` and `MSYS_NO_PATHCONV=1`. `flow save --path` and `flow delete --path` drop `.` and `..` by `/` too, rather than through std's components, which on Windows rebuilt `/srv/f.toml` as `\srv\f.toml` and matched no file the server listed; `config project`'s folder goes through the same rules, where a drive path used to pass as absolute here. A Unix client sends the path as before. **A Windows path to a Windows machine** (#603, `reach::windows_there`) is judged by Windows' rules instead, from any client: a drive and a separator (`C:\…`, `C:/…`) or a share (`\\host\share\…`) is absolute and goes with `\` for `/`; `C:x` and `\…` are relative to something here and refused. Whether the machine runs Windows is the remembered shell (A Windows machine at the other end), and when nothing is remembered, the probe, sent only for a path in Windows' form, which was refused before anyway (`Remote::on_windows`); a `/…` path never asks and goes as before, and a Windows server reads it on its own drive. `flow save --path` and `flow delete --path` drop `.` and `..` of such a path by `\`, keeping its drive or share (`flow::clean_there`). A Windows machine whose `DefaultShell` is bash counts as POSIX and takes Unix paths. `open` also takes `~` and `~/…` (#477), sent as they are and expanded by the server with its own home: this machine's `HOME` says nothing about that one's, and a path that starts with `~/` cannot be relative to anything here. `paste-file` reads its FILE, or standard input, on this machine: that is its point (#479). `files` paths are never resolved by the CLI: they are relative to the workspace, or absolute or `~/…` on the server. `status` abbreviates paths with the `home` the server reports (the server's own, not `HOME` here), so `--remote` shows `~/…` too, where it used to print full paths. `caller` and `server` are sent as always: a local pane's `CORNERCASE_SERVER` token never matches the server there, which ignores the caller.
  - **One ssh connection per request, its feature check included** (#557): measured against a local sshd (2026-10), a shared connection made a command more than twice as fast, so the docs show the user's own `ControlMaster auto` and `ControlPersist`. A `ControlMaster` of cornercase's own was rejected: it would override the user's config, and a persisted master outlives the command. `input --follow` (#478) and `requests --follow` (#558, any command that sends requests, one JSON line each) send all their requests over one. A command that checks a feature before its request (`client::requests::require`, behind `--view`, `--reveal`, `--unlock`, `--issue`, `--profile`, `--account`, `--notices`, `--patches`…) asked `contract` on a link of its own and dropped it, so it paid two ssh sessions: on 2026-10-31, from a Mac to an Ubuntu machine over Tailscale (~55 ms round trip, 0.12.230 on both, no `ControlMaster`), `focus --tab N --view V` took 1.2–1.4 s and `scroll` 0.65–0.8 s (0.6 s and 0.3 s through a `ControlMaster`), and a window that draws cornercase (#345) adds `--view` to nearly every action. Now a passed check keeps its link (`CHECKED`) and the next request takes it (`connect`); a second check takes it too and asks `contract` again, a round trip rather than a session. The server has answered each request of a connection in turn since `contract` exists (#302), the proxy copies both ways after the first message, and a check passes only on a server with `contract`, so no older server meets the second request. The check and the request also reach the same server, which two connections did not promise across a restart. `start-server` (`ask_starting`) and `report_now` keep links of their own: the proxy starts a server only when the first message is `start-server`, and `report_now` sets a read timeout. A link that no request took (the command failed after its check) is closed when `cli::run_control` returns, since a static is never dropped. Rejected: sending the request unchecked and asking `contract` only after a failure (one round trip less even locally, but an older server drops a field it does not know without a word, which is what the check catches, #480); running the checks inside the request's own connect (one `contract` for several checks and no link in a static, but the checks would come after the command's local work, such as reading standard input, and change which error comes first); handing the link from each check to its request by hand (every caller of `use_*` and `ask` changes for the same result); keeping the descriptor for the process (it saves a round trip only for the few commands with two checks). A command that sends two requests of its own (`--worktree BRANCH` looks the workspace up with `status`, `read --last-message` asks per target, `changes list` reads `status` for its names) still opens one connection per request.
