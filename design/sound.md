# Sound

Code: `host/sound.rs`, `app/agent_watch.rs`, `app/notifications.rs`, `server.rs`, `client/window.rs`, #230

- **Why**: a desktop notification is often silent exactly when it matters. Ghostty on macOS, foot, Konsole and Warp hide it while their window is focused, which is when you work in cornercase on another tab; inside tmux, screen or Zellij it falls back to BEL, whose sound is whatever the terminal makes of it, often nothing. And no notice told "needs you" from "finished" by ear. So cornercase can play a sound of its own, with one sound for each.
- **On by default** (`sound` in `config.json`, Settings › UI after **desktop notifications**): it was off at first, so nothing would change on update, and the user asked for it on once they had tried it. Only the agents you started sound (below), so a flow or a harness run does not beep at every step, and turning it off is one click. The toast and the desktop notification stay as they were, and the sound does not depend on `desktop_notifications`: it plays with the channel `off` too, since a sound is what that user may want instead.
- **The server decides, at the moments it already notifies**: `App::notify`, so the same second of settling (`NOTIFY_AFTER`), never for a tab that is seen (the window's or a view's), once per change, one per notice group. `App::tell` queues a `host::sound::Cue` (`kind` and `path`) in the `Outbox` beside the notification. Waiting and failed play `needs-you`, done (the orchestrator's mark included) plays `finished`: failed asks for a person too, and the issue asked for two sounds, not three. Only agent notices sound: `cornercase notify`, the queue, a failed setup and a flow's consent go through other paths and stay silent, left for whoever asks.
- **Only the agents you started, unless asked** (`sound_subagents`, off by default): a pane drawn as a child in the agents section's tree is a subagent (`App::subagent_panes` takes the rows of the whole `App::agent_tree`, folds aside, below the first level, see Layout), so the two cannot disagree: a live parent with an agent state, and in a cycle (a hand-edited session) the first agent in sidebar order still counts as one you started. So a flow's members and agents an agent started with `start`, `new-tab` or `split` stay silent, while an agent started from a shell, or whose parent has closed, sounds. A notice groups several panes, so it sounds when any of them qualifies, once. The user asked for this: a flow or a harness run would otherwise beep at every step. The cost is that a flow member waiting on a permission the orchestrator must not answer only toasts and notifies, as before; turning subagents on brings it back.
- **It plays where the window is**, as notifications go through the outer terminal so they work over ssh: playing on the server would beep on the wrong computer under `cornercase remote`. There is no escape sequence for "play this file", so it is a message of its own, `ServerMessage::Sound(Cue)`, the last variant (index 6), and `protocol::VERSION` went from 5 to 6 (a client of another build is already refused, so the number only says the wire changed). `Server::flush` sends it, after the notifications, to every client with a screen but the browser bridge's (its `Hello` names the terminal `browser`, `protocol::BROWSER`, so `server.log`'s `sound sent` counts only the clients that play it), so windows and `cornercase remote`'s proxy; several cues in one flush become one per client, `needs-you` winning (`host::sound::loudest`), since two sounds at once read as noise. The bridge would ignore it anyway: a page can play sound only with Web Audio after a gesture, left for an issue of its own.
- **The client plays it** (`host::sound::Player`, made in `client::window` only when the client is on the machine you sit at): `afplay` on macOS; on Linux the first of `pw-play`, `paplay` and `aplay` on the `PATH`; nothing else on the machine is needed. Resolving the file, writing the built-in one and starting the player run on a thread of their own, so a file on a hung network mount never blocks the input loop; the player runs as a child with null stdio, and that thread reaps it every 50 ms and kills it after 5 s, so a stuck player leaves no zombie and blocks nothing. A sound that comes less than a second after the last one is dropped (counted from when the last one was asked for, even if its player then failed to start), so two notices close together do not overlap. No player, a spawn that fails or a file that cannot be read never fail the window; they log a `WARN` from the client. Two local windows on one machine play twice, as they notify twice.
- **Under plain ssh it stays silent**, and `sound::local_machine` is the same test the openers use (see Opening in other apps): a client whose environment has `SSH_CONNECTION` or `SSH_TTY` (`ssh -t host cornercase`, or cornercase started in a pane of an ssh session) runs on the remote machine, so a sound there would play in an empty room or nowhere. `cornercase remote` runs the window locally, and is the way to hear it; the docs say so. Detecting the outer terminal's machine any other way was not possible. A tmux session started over ssh keeps those variables when it is reattached on the machine itself, so a window opened there stays silent; the troubleshooting page says how to clear them.
- **Built-in sounds are made in code** (`host::sound::wav`): two notes of 0.14 s each, a sine with a short fade so they never click, 16-bit mono PCM at 22050 Hz; rising (880 to 1318 Hz) for `needs-you`, falling (1046 to 784 Hz) for `finished`, so the two tell apart without looking. WAV because `afplay`, `pw-play`, `paplay` and `aplay` all read it. Generated rather than shipped as files: no asset, no licence, and the same sound on macOS and Linux; the system's own sounds (`Glass.aiff`, freedesktop's `complete.oga`) were rejected because Linux machines often lack them. The client writes them once to `sounds/<kind>.wav` in its state folder (the folder of `paths::session()`, so a debug build's tree has its own), private (folder 0700, file 0600, written through a temporary file named with the process id, so two windows writing at once never share it, then a rename), and writes again only when its bytes differ from the sound this build makes, so a later release that changes a sound replaces it.
- **Your own files** (`sound_waiting`, `sound_done`; empty is the built-in one): kept in the server's `config.json`, so Settings and the `config` request edit them like any setting, and sent in the cue as text, resolved on the client's machine (`~` with the client's `HOME`): under `cornercase remote` the path names a file on the laptop, which the row's note says. The path must be absolute or start with `~/`: a relative one would be read from the folder the window was opened in, and one starting with `-` would reach the player as an option, so Settings and the `config` request refuse them (`config::check_sound_file`) and the client plays the built-in sound for one written in `config.json` by hand (`host::sound::resolve`). A path that is empty, missing or not a readable regular file plays the built-in one too. Settings refuses control and invisible characters and never checks the file exists, since it is the client's. `aplay` reads only WAV; `afplay` reads most formats and `pw-play` and `paplay` WAV, OGG and FLAC. The client sending its own paths in `Hello` was rejected: one place to edit them, by mouse or by request, matters more, and locally the machines are the same.
- **Left out**: sound in the browser, a sound for notices that do not go through `App::notify`, playing on the server, per-agent sounds (herdr has them), a volume, mp3 on Linux, a preview from Settings and muting one client.
- **Tests**: the module's pure parts (the player picked on a fake `PATH`, `~`, a missing file, the WAV header, the two sounds differ, the loudest cue, the ssh check) in `host/sound/tests.rs`; the decision with fake agents in `app::tests::agent_status::sound` (a hidden tab, back to working within the second, done, a visible tab, off, desktop notifications off, a subagent with and without `sound_subagents`, a shell parent); the wire in `protocol::tests` and the window's `next` in `client::window::tests`. No test plays a sound: `new_app` turns `sound` off, and the e2e harness and the docs captures set `SSH_CONNECTION`, so their windows make no player.
