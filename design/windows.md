# Windows

Code: `os.rs`, `os/`, the `imp` pairs in `client/requests/watch.rs`, `client/input.rs`, `client/probe.rs`, `client/window.rs`, `cli/config.rs`, `cli/requests.rs`, `highlight/limit.rs` and `term.rs`, `cli.rs` (the refusal), `.github/workflows/ci.yml` (the `windows` job)

- **Native, not WSL** (#586): inside WSL cornercase already runs, but on another machine's files, `PATH` and agents. The port runs it on Windows itself, one step at a time in small pull requests to `main`, each one tracked under #586.
- **Possible** (spike on 2026-11-02, Windows 11, Rust 1.99.0, Zig 0.15.2, Visual Studio Build Tools 2022 with MSVC 14.44): `libghostty-vt` 0.2.2 builds for `x86_64-pc-windows-msvc`, and a `Terminal` parses VT input and formats it back as text. Every dependency checks, portable-pty included (its Windows backend is ConPTY). What does not compile is ours: the socket, the console, processes, file modes, git paths as bytes and the host helpers, all on Unix-only APIs.
- **Every step keeps Linux and macOS as they are**: their code is only moved behind a per-OS layer, a `mod imp` per OS with a fallback, as `process.rs` already does. Windows can be incomplete, never half-working: what is not ported returns `Unsupported`, and the window says so.
- **The per-OS layer** (#588): `os/` is a shared leaf with one file per area of the port, each holding a `mod imp` for `cfg(unix)` and one for every other system: `console.rs` (descriptors, standard input and output, the log taking stderr), `ffi.rs` (git's paths as bytes, see Git's paths), `fs.rs` (file modes, metadata, links, locks, `access`, the user's ids), `process.rs` (signals, process groups, sessions, `exec`, the server's stop signals) and `socket.rs` (the local socket). On Unix an `imp` re-exports what the code used before (`std::os::unix`'s traits, `std::os::fd`, std's `UnixStream`, rustix's functions), so most callers only changed a `use` line. Where rustix's own types (`Errno`, `FlockOperation`) sat in the caller's logic, the Unix code moved into the `imp` as it was, behind a function of our own: `fs::try_lock` and `fs::locked`, `fs::writable`, `fs::uid` and `fs::gid`, `fs::set_mode` and `fs::set_file_mode` for `Permissions::from_mode`, which no Windows type can build, `process::alive`, `process::on_stop_signal` and `console::redirect_stderr`. Code whose Unix calls are woven into one module's own logic and types keeps its `imp` pair in that file instead: `client/requests/watch.rs` (whether the reader of a command's output or its input went away), `client/input.rs` and `client/probe.rs` (polling and reading the terminal), `client/window.rs` (the window's signals), `cli/config.rs` (a token typed without echo), `cli/requests.rs` (setting standard input and output aside), `highlight/limit.rs` (waiting for the painter, with its own `Fail`) and `term.rs` (a pane's foreground process group, through portable-pty). `rustix` and `signal-hook` are Unix-only dependencies: production code reaches them only inside a Unix `imp`, and only Unix-only tests use them directly. Each later step replaces one Windows `imp`.
- **What the stubs answer**: an empty list, `None`, `false` or 0 for what is read (a pid's name, a file's inode or mode, whether a process is alive), `io::ErrorKind::Unsupported` for what acts (a signal, a lock, a link, a mode set on a path, a socket, `exec`), and nothing for a builder's mode or flags (`OpenOptionsExt::mode`, `DirBuilderExt::mode`, `CommandExt::process_group`), which cannot fail. The types that cannot exist yet (`UnixStream`, `UnixListener`, `OwnedFd`, the window's signal handle) hold `Infallible`, so their methods are `match self.0 {}` and never run; a `BorrowedFd` is a token that every stub refuses. None panics. Paths as bytes were the one stub that worked, until #590 replaced them (see Git's paths). Two stubs act as the Unix code does when it cannot: the token prompt's echo stays on (as when standard input is no terminal), and the painter's wait reports a broken worker rather than a timeout, so a file is not marked as too slow for good.
- **Stubs that guard safety must fail closed before the refusal goes**: a 0 read where the Unix code compares or checks makes the check pass. Two files' `dev` and `ino` are both 0, so `accounts::transfer` takes any two files for the same one. The socket folder's owner and mode, and a plugin manifest's, read 0 against our uid 0, so neither is ever refused, and `NOFOLLOW` is 0, so a manifest behind a link is followed. `process::alive` is false, so a worktree lock whose holder runs reads as gone. The log's rotation by inode is never seen, and every size on disk is 0. Nothing reaches them while `cli::run` refuses; each step that ports one gives a real answer or refuses (#589 for files, #596 for processes), and the refusal goes only once none is left.
- **Git's paths** (#590): git prints a path as bytes (`worktree list --porcelain`, `rev-parse`, `ls-files -z`, the `gitdir` and `commondir` files it writes), and the changes panel, the merge check, the worktrees and the worktrees dialog turn them into paths and back. One set of helpers in `os/ffi.rs` does it, a leaf because `git`, `changes` and `worktrees` all use it and its Unix side needs `std::os::unix::ffi`: `to_path` (git's bytes to a path), `to_bytes` and `text` (a path to git's bytes or text), `to_os` (bytes to an argument or a variable), `join` (a path git wrote, onto a folder), `plain` (a path handed to git), `same` (comparing a path from git with one from std) and `LIST_SEPARATOR`. They replaced the stubbed `OsStrExt` and `OsStringExt`. On Unix they are what the code did before: the raw bytes both ways, so names that are not UTF-8 still work, `plain` is the path itself and `same` is `==`. On Windows git writes UTF-8 with forward slashes (`C:/Users/me/repo`): `to_path` decodes it and turns `/` into `\`, `to_bytes` encodes UTF-8 with `/`.
  - **Bytes that are not UTF-8** are decoded lossily (`U+FFFD`), not skipped: Git for Windows prints only UTF-8, since it converts the system's UTF-16 names, so such bytes can only come from a tree committed elsewhere whose name no Windows file has. A lossy name keeps the entry in the list, like every name the changes panel already shows on any system, and the file system call on it fails as for a file that went away. The empty path the stub gave was worse: an empty `rev-parse --absolute-git-dir` would have read `locked` in the current folder.
  - **The `\\?\` prefix**: on Windows `canonicalize` gives a verbatim path (`\\?\C:\Users\me\repo`), and cornercase canonicalises project folders. Git cannot take one: `git worktree add` fails with `could not create leading directories of '//?/C:/…'` and `git clone` reads it as an ssh host (Git for Windows 2.39.2, checked 2026-11-02); and inside a verbatim path `/` is no separator, so a relative path from git joined onto one names no file. So every path handed to git goes through `plain`, which drops the prefix (`-C`, `worktree add`, `remove` and `unlock`, `--exclude-from`, `--pathspec-from-file`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, the alternates), and every path git wrote goes onto its folder through `join`, which makes the separators native and drops the prefix too (std's `push` resolves the `..` of `commondir` on a verbatim folder). Nothing is lost: std adds the prefix back itself for a path over `MAX_PATH`. The folders cornercase stores keep the prefix for now, shown as is; dropping it where they are canonicalised is a step of its own.
  - **Comparing**: `Path`'s `==` and `Hash` already treat `/` and `\` alike on Windows, so the worktree discovery's sets of canonical paths match git's paths as they are. `same` also ignores the `\\?\` prefix and the drive letter's case (`c:` and `C:`), and is what the prune check uses before it canonicalises. A folder's own case still counts: both sides come from `canonicalize` or from git given the canonical folder, so they agree.
  - **The alternates** are a list split on git's `PATH_SEP`, `;` on Windows and `:` on Unix, so `LIST_SEPARATOR` is what makes the merge check quote a path.
  - **Line endings** (checked 2026-11-02): with `core.autocrlf=true`, Git for Windows' default, `git diff` compares a file's cleaned (LF) content, so a file checked out with CRLF and left alone is not listed and an edited one shows only its edit. The panel splits a patch and an untracked file with `str::lines`, which drops the `\r` of a CRLF line, and its digests hash git's output, which does not change between two reads. Nothing needed fixing; tests keep it so.
  - **Tests**: `TempDir` is canonical without the prefix on Windows, what the app should store too; the Windows tests hand `\\?\` folders, names out of ASCII and paths with forward slashes to the changes panel's loader, the merge check, the worktree list and scan, and `worktree::create`, `lock` and `remove`. The tests of `changes`, `git` and `worktrees` that need only git run on Windows, the merge check's and the worktrees' included (all passed locally on 2026-11-02, with Git for Windows 2.39.2); those that need a symbolic link, `/bin/sh`, a process, a name with `*` or a file's blocks stay `#[cfg(unix)]`.
- **On Windows, cornercase says so**: `cli::run` refuses every command with `Error::NotOnWindows` (cornercase does not run on Windows yet, with a link to #586) and exit status 1, before anything reaches the server, the socket or the console. `--help` and `--version` still work, since clap answers them before `run`. One check in one place rather than one per command, so nothing half-works over the socket; it goes once the socket, server and console steps land.
- **Tests that need Unix** are `#[cfg(unix)]`: the whole test file, with `#![cfg(unix)]` on its first line, where most of it needs Unix (file modes, symlinks, `UnixStream::pair`, rustix, the server's attached client), else the group or the test, and the test helpers only they use carry `#[cfg(unix)]` under their `#[cfg(test)]`. Never `#[cfg(all(test, unix))]`: clippy (its exemptions for tests) and `tests/layers.rs` only see code under a literal `#[cfg(test)]` as test code, and the combined form made clippy lint `worktrees::tests` as production code. `test_util`'s `Locked`, `Sleeper` and `Family` go through `os/` instead, since half the suite uses them. Tests that only run shell scripts or `/bin/sh` panes still compile on Windows. The e2e crate is `#![cfg(unix)]`. Nothing runs the suite on Windows yet (#601).
- **CI** (#587, #588): a `clippy (windows-2025)` job runs `cargo clippy --all-targets --all-features --locked -- -D warnings` with the same toolchain, Zig and cache as the other jobs, so a change that breaks the Windows build shows a failing check on its pull request. It is not yet among the checks `main`'s ruleset requires, so it does not block a merge on its own. It does not run the tests. A few lints differ on Windows and are silenced there only: `large_enum_variant` on the server's `Step` (paths are larger on Windows), `dead_code` on the window's `Signal` event, which nothing sends until the console is ported, on `Supervisor::steps` in Windows test builds and on the painter's `Fail::Timeout`, and `trivially_copy_pass_by_ref` and `unused_self` on the console's Windows stub.
- **Long paths** (checked 2026-11-02): Ghostty's sources, cloned inside `target/`, hold files (its fuzz corpus) deep enough to pass Windows' `MAX_PATH` on the runner, and git cannot check them out without `core.longpaths`, so the job sets it before anything clones. A short `CARGO_TARGET_DIR` was not needed: what the linker writes stays well under the limit under the runner's checkout, and the default `target/` keeps `Swatinem/rust-cache` working without a mapping. A `target/` folder nested deep in the file system does hit it: the linker fails with `LNK1104`.
