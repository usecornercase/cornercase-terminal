# Windows

Code: `os.rs`, `os/` (`os/fs/windows.rs` for files), `paths.rs` (the folders), the `imp` pairs in `client/requests/watch.rs`, `client/input.rs`, `client/probe.rs`, `client/window.rs`, `cli/config.rs`, `cli/requests.rs`, `highlight/limit.rs` and `term.rs`, `cli.rs` (the refusal), `.github/workflows/ci.yml` (the `windows` job)

- **Native, not WSL** (#586): inside WSL cornercase already runs, but on another machine's files, `PATH` and agents. The port runs it on Windows itself, one step at a time in small pull requests to `main`, each one tracked under #586.
- **Possible** (spike on 2026-11-02, Windows 11, Rust 1.99.0, Zig 0.15.2, Visual Studio Build Tools 2022 with MSVC 14.44): `libghostty-vt` 0.2.2 builds for `x86_64-pc-windows-msvc`, and a `Terminal` parses VT input and formats it back as text. Every dependency checks, portable-pty included (its Windows backend is ConPTY). What does not compile is ours: the socket, the console, processes, file modes, git paths as bytes and the host helpers, all on Unix-only APIs.
- **Every step keeps Linux and macOS as they are**: their code is only moved behind a per-OS layer, a `mod imp` per OS with a fallback, as `process.rs` already does. Windows can be incomplete, never half-working: what is not ported returns `Unsupported`, and the window says so.
- **The per-OS layer** (#588): `os/` is a shared leaf with one file per area of the port, each holding a `mod imp` for `cfg(unix)` and one for every other system: `console.rs` (descriptors, standard input and output, the log taking stderr), `ffi.rs` (paths as bytes), `fs.rs` (file modes, metadata, links, locks, `access`, the user's ids), `process.rs` (signals, process groups, sessions, `exec`, the server's stop signals) and `socket.rs` (the local socket). On Unix an `imp` re-exports what the code used before (`std::os::unix`'s traits, `std::os::fd`, std's `UnixStream`, rustix's functions), so most callers only changed a `use` line. Where rustix's own types (`Errno`, `FlockOperation`) sat in the caller's logic, the Unix code moved into the `imp` as it was, behind a function of our own: `fs::try_lock` and `fs::locked`, `fs::writable`, `fs::uid` and `fs::gid`, `fs::set_mode` and `fs::set_file_mode` for `Permissions::from_mode`, which no Windows type can build, `process::alive`, `process::on_stop_signal` and `console::redirect_stderr`. Code whose Unix calls are woven into one module's own logic and types keeps its `imp` pair in that file instead: `client/requests/watch.rs` (whether the reader of a command's output or its input went away), `client/input.rs` and `client/probe.rs` (polling and reading the terminal), `client/window.rs` (the window's signals), `cli/config.rs` (a token typed without echo), `cli/requests.rs` (setting standard input and output aside), `highlight/limit.rs` (waiting for the painter, with its own `Fail`) and `term.rs` (a pane's foreground process group, through portable-pty). `rustix` and `signal-hook` are Unix-only dependencies: production code reaches them only inside a Unix `imp`, and only Unix-only tests use them directly. Each later step replaces one Windows `imp`.
- **What the stubs answer**: an empty list, `None`, `false` or 0 for what is read (a pid's name, a file's inode or mode, whether a process is alive), `io::ErrorKind::Unsupported` for what acts (a signal, a lock, a link, a mode set on a path, a socket, `exec`), and nothing for a builder's mode or flags (`OpenOptionsExt::mode`, `DirBuilderExt::mode`, `CommandExt::process_group`), which cannot fail. The types that cannot exist yet (`UnixStream`, `UnixListener`, `OwnedFd`, the window's signal handle) hold `Infallible`, so their methods are `match self.0 {}` and never run; a `BorrowedFd` is a token that every stub refuses. None panics. Paths as bytes are the one stub that works: `as_bytes` gives the encoded bytes, and bytes that are not UTF-8 become an empty path rather than an invalid one. Two stubs act as the Unix code does when it cannot: the token prompt's echo stays on (as when standard input is no terminal), and the painter's wait reports a broken worker rather than a timeout, so a file is not marked as too slow for good.
- **Stubs that guard safety must fail closed before the refusal goes**: a 0 read where the Unix code compares or checks would make the check pass. #589 settled the files: an identity, an owner or a mode that Windows cannot give reads as unknown, nobody's or `0o777`, so the checks refuse (see Files: identity and listings below), and `NOFOLLOW` opens a link itself. Still open: `process::alive` is false, so a worktree lock whose holder runs reads as gone (#596). Nothing reaches them while `cli::run` refuses, and the refusal goes only once none is left.
- **Folders** (#589, `paths.rs`): the settings in `%APPDATA%\cornercase\` (roaming, like the settings themselves), and the state (session, log, socket and lock, accounts, plugin state, run folders) in `%LOCALAPPDATA%\cornercase\`, which stays on this machine, as a server and its socket do. A debug build keeps `cornercase-dev\` and `cornercase-dev\<key>\` the same way (Client / server). Without the variable, `%USERPROFILE%\AppData\Roaming` or `Local`, then the temp folder; relative values are ignored, as on Unix. They are read from the environment, which Windows sets for every logon, rather than with `SHGetKnownFolderPath`, so `paths` stays pure over a lookup and its tests cover the Windows rule (`paths::Base`, one per OS). **`XDG_*` and `HOME` are not read on Windows**, even when set: Git Bash and MSYS2 users set them in an rc file, which a cornercase started from PowerShell, cmd, Explorer or the Start menu never sees, so honoring them would give one user two sockets, and two servers on two sessions, depending on the shell that started it, the split #355 removed on Unix. `CORNERCASE_SOCKET` still overrides everything. No earlier socket is probed (`paths::earlier_sockets` is empty: no release before 0.12.140 ran on Windows), so finding the socket never needs a uid. Limit: `secrets.json` sits next to the settings, so a roaming profile copies the tokens to the domain's profile server, as it does for `gh`'s.
- **File modes** (#589): `set_mode`, `set_file_mode` and the builders' `mode` succeed without doing anything. Every caller asks for a private file or folder (`0600`, `0700`), which the default ACL of the user's profile already gives (the user, SYSTEM and Administrators only), or for a program (`0755`, the update's binary), which Windows tells by its extension. Limit: a private file written outside the profile (`CORNERCASE_SOCKET` elsewhere, `config share` into a shared folder) takes that folder's ACL; writing an owner-only DACL was left for when it is needed.
- **Files: identity and listings** (#589): std's Windows `volume_serial_number` and `file_index` are unstable (`windows_by_handle`), so `os::fs::stat` and `stat_file` read them with `GetFileInformationByHandle`, opening a path with no access rights and `FILE_FLAG_BACKUP_SEMANTICS` as std's own `metadata` does (a folder opens, and no sharing mode is in the way). Every caller that compares files goes through them: `persist::mark`, a transcript's `jsonl` reader, `log::Follower` (a rotation) and `accounts::transfer::same`. On ReFS the 64-bit index can repeat (`FileIdInfo` has 128 bits); left for later. A listing (`DirEntry::metadata`, from `FindNextFile`) has no handle, and opening every file would make a walk of `node_modules` many times slower, so `MetadataExt` answers what a listing knows: `blocks` the length in 512-byte blocks, rounded up (a worktree's size counts the length, not clusters, compression or sparse files), `mtime` and `ctime` the last write (std has no stable change time), so the changes panel's stamp moves with every write, `nlink` 1 (each hard link is counted, an overcount for a pnpm store) and `dev` 0. One device is the true answer for the walks that read it: Windows mounts a volume inside a folder only through a reparse point, which `symlink_metadata` and `DirEntry::metadata` report as a link and never as a folder, so `disk::usage` and `crosses_device` never enter one, `builds::deletable` refuses a folder that is one (no longer a folder) or is reached through one (its canonical parent leaves the worktree), and `remove_dir_all` removes a junction or a mount point without entering it.
  - **What guards safety fails closed**: `ino` is a new number on every call, so an unknown identity never equals another (`disk.rs` never reads it, since `nlink` is 1); `uid` and `gid` are `u32::MAX`, nobody's, while the user's own (`os::fs::uid`) is 0; and `mode` reads `0o777`. So `protocol::check_socket_dir` and `socket_dir_is_safe` refuse every socket folder (it belongs to another user) and the plugin manifest's `guarded` refuses every plugin, until the socket (#591) and plugins (#595) check the owner's SID and the folder's DACL instead (and replace the socket folder's `tighten`, whose `set_mode` does nothing here). `PermissionsExt::mode` stays 0, so no file reads as a program to the agents' or the host helpers' searches (#599, #600). `NOFOLLOW` is `FILE_FLAG_OPEN_REPARSE_POINT`, which `custom_flags` passes on, so a manifest opened without following is the link itself, not a file, and is refused.
- **Links** (#589, `os::fs::link_to`, `links_to`, for an account's shared settings, Accounts and profiles): a symbolic link needs Developer Mode or an administrator, so a folder becomes a directory junction (a mount point reparse point, set with `FSCTL_SET_REPARSE_POINT` on a new empty folder, which needs no privilege), and a file a hard link, one file under two names, so an edit through either shows in both. Where the volume holds no hard link (FAT, or another volume) the file is copied, with `create_new` so nothing is replaced. `links_to` counts a symbolic link or a junction (std's `is_symlink` covers both, being name surrogates) or a file with its original's identity; a copy, or a hard link an agent broke by writing atomically, is reported as not shared, as a replaced symbolic link is on Unix. A junction leads only to a local disk, so a default home on a network share fails the account's links. Removing an account's folder removes its junctions and hard links and leaves what they lead to (tested). Rejected: a symbolic link first and a junction when it fails, since the result would depend on Developer Mode, and `mklink /J`, a process per link through `cmd`'s quoting.
- **Locks and the rest** (#589): `try_lock` is std's `File::try_lock` and `try_lock_shared` (`LockFileEx` with `LOCKFILE_FAIL_IMMEDIATELY`). As with `flock`, a lock belongs to the open file, keeps out a second open in the same process and goes with the handle; Windows locks are mandatory, which costs nothing here, since nothing reads or writes a lock file. `writable` creates and removes a probe file, since an ACL decides and there is no `access`. `truncate` (the log starting over when it cannot rotate) goes through a second handle, since an append handle has no `FILE_WRITE_DATA` on Windows. Checked live on 2026-11-02 (Windows 11 10.0.26200, NTFS, Rust 1.99.0, without Developer Mode, so no symbolic link could be made): the tests of `os/fs/` (junctions, hard links, copies, identity across a rename, locks, removing a folder of links), `accounts::links`, `paths`, `persist`, `log` and the context readers pass.
- **On Windows, cornercase says so**: `cli::run` refuses every command with `Error::NotOnWindows` (cornercase does not run on Windows yet, with a link to #586) and exit status 1, before anything reaches the server, the socket or the console. `--help` and `--version` still work, since clap answers them before `run`. One check in one place rather than one per command, so nothing half-works over the socket; it goes once the socket, server and console steps land.
- **Tests that need Unix** are `#[cfg(unix)]`: the whole test file, with `#![cfg(unix)]` on its first line, where most of it needs Unix (file modes, symlinks, `UnixStream::pair`, rustix, the server's attached client), else the group or the test, and the test helpers only they use carry `#[cfg(unix)]` under their `#[cfg(test)]`. Never `#[cfg(all(test, unix))]`: clippy (its exemptions for tests) and `tests/layers.rs` only see code under a literal `#[cfg(test)]` as test code, and the combined form made clippy lint `worktrees::tests` as production code. `test_util`'s `Locked`, `Sleeper` and `Family` go through `os/` instead, since half the suite uses them. Tests that only run shell scripts or `/bin/sh` panes still compile on Windows. The e2e crate is `#![cfg(unix)]`. Nothing runs the suite on Windows yet (#601).
- **CI** (#587, #588): a `clippy (windows-2025)` job runs `cargo clippy --all-targets --all-features --locked -- -D warnings` with the same toolchain, Zig and cache as the other jobs, so a change that breaks the Windows build shows a failing check on its pull request. It is not yet among the checks `main`'s ruleset requires, so it does not block a merge on its own. It does not run the tests. A few lints differ on Windows and are silenced there only: `large_enum_variant` on the server's `Step` (paths are larger on Windows), `dead_code` on the window's `Signal` event, which nothing sends until the console is ported, on `Supervisor::steps` in Windows test builds and on the painter's `Fail::Timeout`, and `trivially_copy_pass_by_ref` and `unused_self` on the console's Windows stub.
- **Long paths** (checked 2026-11-02): Ghostty's sources, cloned inside `target/`, hold files (its fuzz corpus) deep enough to pass Windows' `MAX_PATH` on the runner, and git cannot check them out without `core.longpaths`, so the job sets it before anything clones. A short `CARGO_TARGET_DIR` was not needed: what the linker writes stays well under the limit under the runner's checkout, and the default `target/` keeps `Swatinem/rust-cache` working without a mapping. A `target/` folder nested deep in the file system does hit it: the linker fails with `LNK1104`.
