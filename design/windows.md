# Windows

Code: `os.rs`, `os/` (`os/fs/windows.rs` for files, `os/fs/windows/acl.rs` for owners, DACLs and a process's user, `os/socket/windows.rs` for the socket, `os/process/windows.rs` for the server's process: starting it in the background, its Ctrl events, the restart in place; and for stopping a process: its windows, its end, Job objects; `os/process/windows/session_end.rs` for the window that hears a logoff or a shutdown), `protocol.rs` (the socket's folder and its peer), `paths.rs` (the folders), `client/server_process.rs` (starting the server), the `imp` pairs in `client/requests/watch.rs`, `client/input.rs`, `client/probe.rs`, `client/window.rs`, `cli/config.rs`, `cli/requests.rs`, `highlight/limit.rs` and `term.rs`, `term/shell.rs` (the default shell), `client.rs` (keeping and restoring the console's modes), `process.rs` (its Windows `imp`, `program_name`, `is_shell`, `signal_group`), `script.rs` (what runs a script: Git's `sh` or PowerShell), `process/handles.rs` (the files a process holds open), `agents.rs` (`basename`), `cli.rs` (the refusal), `.github/workflows/ci.yml` (the `windows` job)

- **Native, not WSL** (#586): inside WSL cornercase already runs, but on another machine's files, `PATH` and agents. The port runs it on Windows itself, one step at a time in small pull requests to `main`, each one tracked under #586.
- **Possible** (spike on 2026-11-02, Windows 11, Rust 1.99.0, Zig 0.15.2, Visual Studio Build Tools 2022 with MSVC 14.44): `libghostty-vt` 0.2.2 builds for `x86_64-pc-windows-msvc`, and a `Terminal` parses VT input and formats it back as text. Every dependency checks, portable-pty included (its Windows backend is ConPTY). What does not compile is ours: the socket, the console, processes, file modes, git paths as bytes and the host helpers, all on Unix-only APIs.
- **Every step keeps Linux and macOS as they are**: their code is only moved behind a per-OS layer, a `mod imp` per OS with a fallback, as `process.rs` already does. Windows can be incomplete, never half-working: what is not ported returns `Unsupported`, and the window says so.
- **The per-OS layer** (#588): `os/` is a shared leaf with one file per area of the port, each holding a `mod imp` for `cfg(unix)` and one for every other system (`cfg(windows)` once its Windows side is real, as in `console.rs`, `fs.rs`, `process.rs` and `socket.rs`: cornercase builds for Unix and Windows only, so no third `imp` is kept for targets nothing builds): `console.rs` (descriptors, standard input and output, the log taking stderr, and on Windows the console's modes, its input and its Ctrl events), `ffi.rs` (git's paths as bytes, see Git's paths), `fs.rs` (file modes, metadata, links, locks, `access`, the user's ids), `process.rs` (signals, process groups, sessions, `exec`, the server's stop signals) and `socket.rs` (the local socket). On Unix an `imp` re-exports what the code used before (`std::os::unix`'s traits, `std::os::fd`, std's `UnixStream`, rustix's functions), so most callers only changed a `use` line. Where rustix's own types (`Errno`, `FlockOperation`) sat in the caller's logic, the Unix code moved into the `imp` as it was, behind a function of our own: `fs::try_lock` and `fs::locked`, `fs::writable`, `fs::uid` and `fs::gid`, `fs::set_mode` and `fs::set_file_mode` for `Permissions::from_mode`, which no Windows type can build, `process::alive`, `process::on_stop_signal`, `process::spawn_detached`, `process::leave_launch_folder` and `process::launch_folder` (#592) and `console::redirect_stderr`. Code whose Unix calls are woven into one module's own logic and types keeps its `imp` pair in that file instead: `client/requests/watch.rs` (whether the reader of a command's output or its input went away), `client/input.rs` and `client/probe.rs` (polling and reading the terminal), `client/window.rs` (the window's signals), `cli/config.rs` (a token typed without echo), `cli/requests.rs` (setting standard input and output aside), `highlight/limit.rs` (waiting for the painter, with its own `Fail`) and `term.rs` (a pane's pseudo terminal: its foreground program, its environment and closing it; see Panes in ConPTY). `rustix` and `signal-hook` are Unix-only dependencies: production code reaches them only inside a Unix `imp`, and only Unix-only tests use them directly. Each later step replaces one Windows `imp`.
- **What the stubs answer**: an empty list, `None`, `false` or 0 for what is read (a pid's name and whether a process is alive, until #596), `io::ErrorKind::Unsupported` for what acts (`setsid`; a lock, a link, a socket, `exec`, the log taking stderr and a signal until #589, #591, #592 and #597 ported them, and a mode set on a path until #589 made it succeed without doing anything), and nothing for a builder's mode or flags (`OpenOptionsExt::mode`, `DirBuilderExt::mode`, and `CommandExt::process_group` until #597), which cannot fail. The types that cannot exist yet (`OwnedFd`, and `UnixStream` and `UnixListener` until #591, the window's signal handle until #593) hold `Infallible`, so their methods are `match self.0 {}` and never run; a `BorrowedFd` is a token that every stub refuses (the console's input is read without one, below). None panics. Paths as bytes were the one stub that worked, until #590 replaced them (see Git's paths). One stub acts as the Unix code does when it cannot: the painter's wait reports a broken worker rather than a timeout, so a file is not marked as too slow for good.
- **Stubs that guard safety must fail closed before the refusal goes**: a 0 read where the Unix code compares or checks would make the check pass. #589 settled the files: an identity, an owner or a mode that Windows cannot give reads as unknown, nobody's or `0o777`, so the checks refuse (see Files: identity and listings below), and `NOFOLLOW` opens a link itself. #591 replaced the socket folder's refusal with a real check of its owner and DACL (see The socket's folder below). `process::alive` asks Windows since #596, so a worktree lock whose holder runs reads as running. Nothing reaches them while `cli::run` refuses, and the refusal goes only once none is left.
- **Processes are read for real** (#596): `process.rs` has a Windows `imp` beside Linux's and macOS' (its sources and limits are under Processes), and `os::process::alive` asks Windows (`OpenProcess`, then `GetExitCodeProcess` against `STILL_ACTIVE`; a process it may not open is alive, as `EPERM` is on Unix). So trees, names, arguments, folders, environments, memory, CPU and start stamps are there for the Processes dialog, the memory line, agent detection and a worktree lock's holder (which read as `Gone` while `alive` was a stub). A pane's foreground program came with #594 (see Panes in ConPTY), and each agent's own files and npm scripts with #599 (see The coding agents).
- **Ports are read for real** (#598): `ports/listen.rs` has a Windows `imp` that asks iphlpapi for the listening TCP table with each socket's owner and when it was made (`GetExtendedTcpTable`, `TCP_TABLE_OWNER_MODULE_LISTENER`, IPv4 then IPv6), dropping a row whose pid started after its socket was made (the pid changed hands), so the Ports dialog and `cornercase ports` list a workspace's servers, matched to its panes and worktrees by the same attribution (its sources and limits are under Ports). Stopping one goes through the stop of #597 (see Stopping a process), after the check that the pid still holds the port.
- **Names without `.exe`**: Windows names a process `node.exe` and a command line starts with `C:\…\claude.exe`, while every comparison (`process::is_shell`, `agents::detect`, `term::program`'s interpreters) holds Unix names. `process::program_name` drops a last `.exe` in any case, on Windows only: the Windows `imp`'s `name` goes through it, and so does `agents::detect` for each argument and for the configured command, so `claude.exe` is `claude` and `node.exe` is the `node` interpreter, whose script argument then reaches the agents' `runs_as`. `agents::detect` then compares the names in any case on Windows (`process::same_file_name`, Unicode lowercase), whose file names ignore case, so `CLAUDE.EXE` is Claude Code too, and so do the agents' `runs_as` rules for each path component they look at (`agents::named`: Copilot's `@github\copilot\npm-loader.js`, Cursor's `cursor-agent\versions\…\index.js`, and the npm scripts of #599 below; `agents::is_program`, a name without its `.exe`, for Vibe's `vibe-rs` and Codex's `codex`). The Unix side is untouched (`program_name` returns the name as it is and `same_file_name` compares exactly), so a Linux program really named `foo.exe` keeps its name. `cmd` and `powershell` are shells on Windows only; `is_shell` compares through `program_name` and `same_file_name` (#594), so `pwsh.exe` and `BASH.EXE` are shells there (`pwsh`, `nu`, `bash` and `sh` were already in the list every system shares). An agent installed with npm runs as `node.exe` with its package's script (`…\npm\node_modules\@anthropic-ai\claude-code\cli.js`) rather than a `claude` link, so it is seen only where its `runs_as` knows that path (see The coding agents).
- **The coding agents** (#599, `paths::HOME_VAR`, `process/program.rs`, `agents::typed_line`, `agents::context::discovery::npm_script`): their default folders come from `USERPROFILE`, never `HOME`; a program cornercase starts itself (a usage probe, a login check, Claude Code's context breakdown) or looks for (`agents::installed`) is found through `PATHEXT`, the openers' lookup moved to `process::program` and shared, so npm's `.cmd` shims are found and started through `cmd`; a launch is typed with PowerShell's quoting, and refused when PowerShell would run a `.cmd` or `.bat` with a character `cmd.exe` reads in the line; and the script an npm shim runs with `node.exe` names its agent. So no step of Claude Code's, Gemini CLI's, Grok's or Vibe's is Unix-only any more (none was run live), while Codex, Copilot, Cursor and opencode find their records through the files their process holds open (#618). The sources, the checks and the limits are under Agents (On Windows).
- **The files a process holds open** (#618, `process/handles.rs`): `process::open_files`, how Codex, Copilot, Cursor and opencode find their records, reads the process's own handle table on Windows, naming each file on a worker thread with a timeout, since a name can hang on a handle another thread is reading (topic: The files a process holds open).
- **Stopping a process and what it started** (#597): how a pane's program is stopped, and why not with Ctrl+C, is under Processes (Windows); this is the layer under it.
  - **`os::process`**: `kill_process` with `KILL` is `TerminateProcess` (exit code 1, as std's `Child::kill`); `TERM` and `HUP` post `WM_CLOSE` to the process's main windows and succeed when it has none; `askable` says whether it has one (always true on Unix). `Pid` holds the pid now. `EnumWindows` and `PostMessageW` are `user32.dll`'s, which the binary loads since #600, so they change nothing for a logoff or a shutdown (see The server's stop events).
  - **Process groups**: `process_group(0)` sets `CREATE_NEW_PROCESS_GROUP`, as `os::desktop::detach` does, so a child cornercase starts in a group does not get a Ctrl+C sent to the server's console, as a Unix group does not get the terminal's. The flag's "ignore Ctrl+C" passes to what that child starts, which none of these children needs; the server itself is started without it (see No `CREATE_NEW_PROCESS_GROUP`). `creation_flags` replaces the flags, so a step that adds others (`CREATE_NO_WINDOW`, #595) must set them together.
  - **Job objects**: the children whose group cornercase ends (`process::output_within`'s commands, the highlight worker, plugin actions, build steps and services) are spawned through `os::process::Grouped`, a `Child` with its group: the process group on Unix, on Windows a Job object with `KILL_ON_JOB_CLOSE` and `BREAKAWAY_OK`, assigned right after the spawn. It derefs to its `Child`, so the call sites keep `id`, `wait` and `kill`. `signal(KILL)` ends the whole job (`TerminateJobObject`); `signal(TERM)` closes the main windows of the job's processes and says whether there was any, so the supervisor skips its 2 s when nothing could be asked. The handle lives in the value rather than in a table by pid: it goes with the child it belongs to, with nothing to clean, and a pid in a table can be reused.
  - **Dropping a `Grouped` lets go of the job**: it clears `KILL_ON_JOB_CLOSE` before closing the handle, so what a child left running on purpose (a plugin action's background server, a browser that git's credential helper opened) keeps running, as on Unix, where nothing ends the group after a normal exit. Ending the tree on every close was rejected for that browser. Only when the server dies without dropping it does Windows close the handle with the flag set and end the tree.
  - **Not in a job**: `host/open.rs`'s last step (an editor or file manager, which must outlive it) is detached (`os::desktop::detach`) rather than grouped, and `process::stop`'s children (`ssh`, the tmux check) are in no group on Unix either, where `Child::kill` already works. A plugin popup's shell is a pane: `process::signal_group` takes its tree before the first step and gives each process the step, until ConPTY (#594) says more.
  - **Exit status**: `ExitStatusExt::signal` is `None` on Windows, so a plugin action ended by force reads as `exited` with its code (1 from the hard step), never `signal`.
  - **Texts** are chosen at compile time (`cfg!(windows)`), so a Windows build names no Unix signal and the Linux and macOS texts, snapshots and site pages did not change. A command run with `--remote` from Windows against a Linux server (#603) would describe Windows' steps around a Linux outcome.
  - **Known limits**: the child runs for a moment before it joins its job, so a grandchild started in those microseconds escapes it (creating it suspended would need its main thread, which std's `Child` does not give, and `PROC_THREAD_ATTRIBUTE_JOB_LIST` needs the unstable `raw_attribute`); when the job cannot be made or assigned, the hard step ends the child alone; the polite step reads at most 256 of a job's processes.
- **Git's paths** (#590): git prints a path as bytes (`worktree list --porcelain`, `rev-parse`, `ls-files -z`, the `gitdir` and `commondir` files it writes), and the changes panel, the merge check, the worktrees and the worktrees dialog turn them into paths and back. One set of helpers in `os/ffi.rs` does it, a leaf because `git`, `changes` and `worktrees` all use it and its Unix side needs `std::os::unix::ffi`: `to_path` (git's bytes to a path), `to_bytes` and `text` (a path to git's bytes or text), `to_os` (bytes to an argument or a variable), `join` (a path git wrote, onto a folder), `plain` (a path handed to git), `same` (comparing a path from git with one from std) and `LIST_SEPARATOR`. They replaced the stubbed `OsStrExt` and `OsStringExt`. On Unix they are what the code did before: the raw bytes both ways, so names that are not UTF-8 still work, `plain` is the path itself and `same` is `==`. On Windows git writes UTF-8 with forward slashes (`C:/Users/me/repo`): `to_path` decodes it and turns `/` into `\`, `to_bytes` encodes UTF-8 with `/`.
- **Copying files into a clone is refused** (the remote hosts' clone, #541 and #543, merged after the port began; `git/ignored.rs`, `git/clone/files.rs`): reading a git-ignored file the Clone on machine dialog offers goes through `openat` with `O_NOFOLLOW`, folder by folder from a pinned folder, and Windows has no such call in std, so that `imp` answers `Unsupported` and `ignored::list` fails at the pin: the dialog shows the files step as failed and clones without them. Writing the `files` a `clone` request carries is refused as well, each one coming back in `unwritten`: Windows opens `.git` under other names (trailing dots or spaces, 8.3 short names such as `GIT~1`, `:` streams) that the guard against writing into `.git` does not see, and a file's mode sets no ACL, so a `.env` would get whatever its folder passes down. Both fail closed until a step ports them; the clone itself and its project work.
  - **Bytes that are not UTF-8** are decoded lossily (`U+FFFD`), not skipped: Git for Windows prints only UTF-8, since it converts the system's UTF-16 names, so such bytes can only come from a tree committed elsewhere whose name no Windows file has. A lossy name keeps the entry in the list, like every name the changes panel already shows on any system, and the file system call on it fails as for a file that went away. The empty path the stub gave was worse: an empty `rev-parse --absolute-git-dir` would have read `locked` in the current folder.
  - **The `\\?\` prefix**: on Windows `canonicalize` gives a verbatim path (`\\?\C:\Users\me\repo`), and cornercase canonicalises project folders. Git cannot take one: `git worktree add` fails with `could not create leading directories of '//?/C:/…'` and `git clone` reads it as an ssh host (Git for Windows 2.39.2, checked 2026-11-02); and inside a verbatim path `/` is no separator, so a relative path from git joined onto one names no file. So every path handed to git goes through `plain`, which drops the prefix (`-C`, `worktree add`, `remove` and `unlock`, `--exclude-from`, `--pathspec-from-file`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, the alternates), and every path git wrote goes onto its folder through `join`, which makes the separators native and drops the prefix too (std's `push` resolves the `..` of `commondir` on a verbatim folder). Nothing is lost: std adds the prefix back itself for a path over `MAX_PATH`. The folders cornercase stores no longer have the prefix (see Canonical folders below), so `plain` and `join` now mostly see plain paths; they stay, since a folder that keeps its prefix, or one a user typed with it, still reaches git.
  - **Comparing**: `Path`'s `==` and `Hash` already treat `/` and `\` alike on Windows, so the worktree discovery's sets of canonical paths match git's paths as they are. `same` also ignores the `\\?\` prefix and the drive letter's case (`c:` and `C:`), and is what the prune check uses before it canonicalises. A folder's own case still counts: both sides come from `canonicalize` or from git given the canonical folder, so they agree.
  - **The alternates** are a list split on git's `PATH_SEP`, `;` on Windows and `:` on Unix, so `LIST_SEPARATOR` is what makes the merge check quote a path.
  - **Line endings** (checked 2026-11-02): with `core.autocrlf=true`, Git for Windows' default, `git diff` compares a file's cleaned (LF) content, so a file checked out with CRLF and left alone is not listed and an edited one shows only its edit. The panel splits a patch and an untracked file with `str::lines`, which drops the `\r` of a CRLF line, and its digests hash git's output, which does not change between two reads. Nothing needed fixing; tests keep it so.
  - **Tests**: `TempDir` is canonical without the prefix on Windows (`os::fs::canonicalize`, what the app stores); the Windows tests hand `\\?\` folders, names out of ASCII and paths with forward slashes to the changes panel's loader, the merge check, the worktree list and scan, and `worktree::create`, `lock` and `remove`. The tests of `changes`, `git` and `worktrees` that need only git run on Windows, the merge check's and the worktrees' included (all passed locally on 2026-11-02, with Git for Windows 2.39.2); those that need a symbolic link, `/bin/sh`, a process, a name with `*` or a file's blocks stay `#[cfg(unix)]`.
- **Canonical folders** (#613, `os::fs::canonicalize` and `canonical`, the rule in `os/fs/windows/verbatim.rs`): std's `canonicalize` gives a verbatim path on Windows, which cornercase showed, wrote to `session.json` and handed to shells, agents and git, and many programs refuse or misread one (git, above). So the app canonicalises through `os::fs::canonicalize` (`canonical` falls back to the path as given, as the code did with `unwrap_or`), which is std's on Unix and on Windows drops the `\\?\` of a drive path (`\\?\C:\…`) when Win32 reads the plain one the same way. The rules are based on the `dunce` crate's (1.0.5) and keep the prefix in more cases, never fewer: on a share (`\\?\UNC\…`) or a volume (`\\?\Volume{…}\…`); on a drive without its root (`\\?\C:`, which plain is that drive's current folder; not in `dunce`); on a path over 260 UTF-16 units with its prefix, `dunce`'s limit, which leaves a margin under `MAX_PATH` (std adds the prefix back itself for a long path); and on a name Win32 would read otherwise: `.` or `..`, a trailing dot or space (Win32 strips them), a device name with or without an extension, cut at its first dot (`CON`, `PRN`, `AUX`, `NUL`, `COM1`-`COM9`, `LPT1`-`LPT9`, and beyond `dunce` `CONIN$`, `CONOUT$`, `COM0`, `LPT0` and the `¹²³` ones, any case), a character of `<>:"/\|?*` or below a space (in a verbatim name `/` is no separator and `:` names a stream), over 255 units, or not Unicode. Keeping the prefix is the safe side, since it is what std gave. Windows 11 (10.0.26200) reads `aux.rs` or `con.h` in a plain path as a file (checked 2026-11-03), older Windows as the device, so a name like that keeps its prefix. Written by hand rather than taking `dunce`: the rules fit in one small file, and the crate would be a dependency for one call.
  - **Where**: every folder the app stores, shows or hands to a program: projects (the picker, the `open` request, the server's own folder through `open_here`), workspaces and worktrees (`git::registered_worktrees`, a new worktree, a flow's run and role worktrees, `worktree-remove`'s target, the worktree discovery and dialog), session restore, config keys matched to a project (`names_folder`, the `config` request, sharing settings), accounts' folders (given to agents as `CLAUDE_CONFIG_DIR` and the like, so Claude Code's keychain key comes from the plain path), a linked plugin's folder and an install spec, the binary the updater replaces, and the ports' worktree folders, matched against a process's folder, which Windows gives plain.
  - **Left on std's**: checks that canonicalise both sides themselves and keep nothing, so both sides always agree: the agents' discovery (a process's folder and home against the folders agents record), an account shell's custom home and `accounts::named`, the prune check (`worktrees::remove`, beside `ffi::same`), and the containment checks of a build folder (`builds::deletable`), of a plugin's program (`manifest::resolve`) and of a path link's file in its workspace (`files::link::resolve`, which then passes only the file through `simplified`, for what it shows and reports), where a plain root and a child that keeps its prefix (a long path, or a name like `aux.rs`) would otherwise come in two forms and the child read as outside; also `host::open`'s Zed check, the highlight worker's binary and the junction's drive check.
  - **Sessions**: `state::load` passes every path it reads through `os::fs::simplified` (projects, workspaces, pane folders, a closed tab's panes, role worktrees), so a session saved with verbatim paths opens with plain ones and nothing migrates by hand; restoring canonicalises the project and workspace folders again.
  - **Tests**: the rule on Windows (`os/fs/windows/verbatim/tests.rs`), `canonicalize` and `canonical` on both systems (`os/fs/tests.rs`), a path link to `src\aux.rs` that stays inside its workspace (`files/link/tests.rs`), a project opened by its verbatim folder through `open_project` (the picker's and the server's call) and through the `open` request is stored plain (two app tests that start `cmd.exe` through `new_app_with_shell`), and a session file with verbatim paths loads plain ones (`state/tests.rs`); all passed on Windows 11 on 2026-11-03. The app tests' own `canonicalize()` calls give the same paths on Unix; once they run on Windows (#601) they compare through `os::fs::canonicalize`, as `app::tests::canonical` already does.
- **Folders** (#589, `paths.rs`): the settings in `%APPDATA%\cornercase\` (roaming, like the settings themselves), and the state (session, log, socket and lock, accounts, plugin state, run folders) in `%LOCALAPPDATA%\cornercase\`, which stays on this machine, as a server and its socket do. A debug build keeps `cornercase-dev\` and `cornercase-dev\<key>\` the same way (Client / server). Without the variable, `%USERPROFILE%\AppData\Roaming` or `Local`, then the temp folder; relative values are ignored, as on Unix. They are read from the environment, which Windows sets for every logon, rather than with `SHGetKnownFolderPath`, so `paths` stays pure over a lookup and its tests cover the Windows rule (`paths::Base`, one per OS). **`XDG_*` and `HOME` are not read on Windows**, even when set: Git Bash and MSYS2 users set them in an rc file, which a cornercase started from PowerShell, cmd, Explorer or the Start menu never sees, so honoring them would give one user two sockets, and two servers on two sessions, depending on the shell that started it, the split #355 removed on Unix. `CORNERCASE_SOCKET` still overrides everything. No earlier socket is probed (`paths::earlier_sockets` is empty: no release before 0.12.140 ran on Windows), so finding the socket never needs a uid. Limit: `secrets.json` sits next to the settings, so a roaming profile copies the tokens to the domain's profile server, as it does for `gh`'s.
- **File modes** (#589): `set_mode`, `set_file_mode` and the builders' `mode` succeed without doing anything. Every caller asks for a private file or folder (`0600`, `0700`), which the default ACL of the user's profile already gives (the user, SYSTEM and Administrators only), or for a program (`0755`, the update's binary), which Windows tells by its extension. Limit: a private file written outside the profile (`CORNERCASE_SOCKET` elsewhere, `config share` into a shared folder) takes that folder's ACL; writing an owner-only DACL was left for when it is needed, and the socket's folder is the one place that writes one (#591).
- **Files: identity and listings** (#589): std's Windows `volume_serial_number` and `file_index` are unstable (`windows_by_handle`), so `os::fs::stat` and `stat_file` read them with `GetFileInformationByHandle`, opening a path with no access rights and `FILE_FLAG_BACKUP_SEMANTICS` as std's own `metadata` does (a folder opens, and no sharing mode is in the way). Every caller that compares files goes through them and compares the device with the inode (`Stat::id`), since a file index, like an inode, is unique only within its volume: `persist::mark`, a transcript's `jsonl` reader, `log::Follower` (a rotation) and `accounts::transfer::same`. On ReFS the 64-bit index can repeat (`FileIdInfo` has 128 bits); left for later. A listing (`DirEntry::metadata`, from `FindNextFile`) has no handle, and opening every file would make a walk of `node_modules` many times slower, so `MetadataExt` answers what a listing knows: `blocks` the length in 512-byte blocks, rounded up (a worktree's size counts the length, not clusters, compression or sparse files), `mtime` and `ctime` the last write (std has no stable change time), so the changes panel's stamp moves with every write, `nlink` 1 (each hard link is counted, an overcount for a pnpm store) and `dev` 0. One device is the true answer for the walks that read it: Windows mounts a volume inside a folder only through a reparse point, which `symlink_metadata` and `DirEntry::metadata` report as a link and never as a folder, so `disk::usage` and `crosses_device` never enter one, `builds::deletable` refuses a folder that is one (no longer a folder) or is reached through one (its canonical parent leaves the worktree), and `remove_dir_all` removes a junction or a mount point without entering it.
  - **What guards safety fails closed**: `ino` is a new number on every call, so an unknown identity never equals another (`disk.rs` never reads it, since `nlink` is 1); `uid` and `gid` are `u32::MAX`, nobody's, while the user's own (`os::fs::uid`) is 0; and `mode` reads `0o777`. So the plugin manifest's `guarded` refused every plugin (it belonged to another user) until #595 made it read the owner's SID and the DACL, as the socket's folder does since #591 (`os::fs::owner_and_mode`, see The socket's folder and Scripts and plugin commands without sh); `uid` and `mode` then left the Windows `MetadataExt`, since nothing read them any more, so no later caller can compare a made-up owner or mode. `PermissionsExt::mode` stays 0, so no file reads as a program by its mode; the agents' and the host helpers' searches go by `PATHEXT` there instead (#599, #600). `NOFOLLOW` is `FILE_FLAG_OPEN_REPARSE_POINT`, which `custom_flags` passes on, so a manifest opened without following is the link itself, not a file, and is refused.
- **Links** (#589, `os::fs::link_to`, `links_to`, for an account's shared settings, Accounts and profiles): a symbolic link needs Developer Mode or an administrator, so a folder becomes a directory junction (a mount point reparse point, set with `FSCTL_SET_REPARSE_POINT` on a new empty folder, which needs no privilege), and a file a hard link, one file under two names, so an edit through either shows in both. Where the volume holds no hard link (FAT, or another volume) the file is copied into a temporary file beside the link, synced, and only then given the link's name with `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` (std's `rename` replaces), so a crash mid-copy leaves no partial file under the name `links::ensure` would keep, and a name taken meanwhile is left alone; the temporary file goes on any failure. `links_to` counts a symbolic link or a junction (std's `is_symlink` covers both, being name surrogates) or a file with its original's identity; a copy, or a hard link an agent broke by writing atomically, is reported as not shared, as a replaced symbolic link is on Unix. A junction leads only to a local disk, so a default home on a network share fails the account's links: the configured path must start with a drive (checked first, so a share is never reached), and so must its canonical path, which catches a folder on a drive that is a symbolic link to a share; the junction then leads to that canonical path, the one checked, so a link changed after the check cannot move it to a share. Removing an account's folder removes its junctions and hard links and leaves what they lead to (tested). Rejected: a symbolic link first and a junction when it fails, since the result would depend on Developer Mode, and `mklink /J`, a process per link through `cmd`'s quoting.
- **Locks and the rest** (#589): `try_lock` is std's `File::try_lock` and `try_lock_shared` (`LockFileEx` with `LOCKFILE_FAIL_IMMEDIATELY`). As with `flock`, a lock belongs to the open file, keeps out a second open in the same process and goes with the handle; Windows locks are mandatory, which costs nothing here, since nothing reads or writes a lock file. `writable` creates and removes a probe file, since an ACL decides and there is no `access`. `truncate` (the log starting over when it cannot rotate) goes through a second handle, since an append handle has no `FILE_WRITE_DATA` on Windows. Checked live on 2026-11-02 (Windows 11 10.0.26200, NTFS, Rust 1.99.0, without Developer Mode, so no symbolic link could be made): the tests of `os/fs/` (junctions, hard links, copies, identity across a rename, locks, removing a folder of links), `accounts::links`, `paths`, `persist`, `log` and the context readers pass.
- **The local socket** (#591, `os/socket/windows.rs`): AF_UNIX over Winsock (Windows 10 1803 and later), with the API the Unix side takes from std (`connect`, `bind`, `incoming`, `try_clone`, the read and write timeouts, `shutdown`, `Read`, `Write`), so `protocol.rs`, the server's acceptor, the client, the proxy and the browser bridge are unchanged, and the path stays a file next to the session, found, locked and removed as on Unix. Rejected: named pipes (#591), another namespace with another lifetime, no file for the folder's ACL to guard and no `CORNERCASE_SOCKET` path; and the `uds_windows` crate, which is built on `winapi`, adds `tempfile` for its pair and has no way to ask for the peer, where a wrapper of about 200 lines over `windows-sys` (already a dependency) has all three. Its answers: a socket is made with `WSA_FLAG_NO_HANDLE_INHERIT`, as std's are with `SOCK_CLOEXEC`, so the shells the server starts never hold the listener or a client (an accepted socket inherits it; tested), and Winsock is started once (`WSAStartup`, never cleaned up, as std does). The path goes in `sun_path` as UTF-8, which Windows reads as UTF-8 (a folder named `Usuário ñ` works; tested), so a path that is not Unicode is refused, and `MAX_SOCKET_PATH` stays 107 bytes; verbatim (`\\?\C:\…`) and relative paths work. `try_clone` shares one socket through an `Arc` rather than `WSADuplicateSocket` (which works too), so it acts as `dup` does: closing waits for the last clone, and a shutdown reaches every clone. `shutdown` of the read side does not wake a `recv` blocked in another thread on Windows (it does on Unix, and the server's writer counts on it to end its reader), so it also cancels the socket's pending I/O (`CancelIoEx`), and once the read side is shut a failed read is the end (`Ok(0)`), as on Unix, rather than `WSAEINTR` (which `read_exact` would retry) or `WSAESHUTDOWN`. **A read waits in `WSAPoll`, never in a blocking `recv`** (found on 2026-11-03, Windows 11 10.0.26200): a `recv` already blocked when the peer's last bytes arrive and the peer closes right after can miss the end for good. The bytes come, the next `recv` blocks forever, although `WSAPoll` on the same socket says `POLLHUP` and a fresh `recv` returns 0 at once, so Windows knows the peer left and only the waiting `recv` is not told. It happened in about 1 of 5 such closes under load (a `shutdown` before the close only made it rarer; a pause before the close avoided it), and the same would hang a real read, such as `kill-server` waiting for the server's end or a server's reader of a client that wrote and left. So `read` first waits with `WSAPoll` for data or the end, in slices of 200 ms that look at the socket again, so a missed wakeup costs at most one slice, then calls `recv`, which then never blocks; `CancelIoEx` wakes the poll as it woke the `recv`. The read timeout is kept by `read` itself (the slices stop at its deadline with `WSAETIMEDOUT`) rather than `SO_RCVTIMEO`, which only a blocking `recv` would honour. Limit: two threads reading one socket at once could both see it ready and one block in `recv`; nothing reads a socket from two threads. `the_end_right_after_the_last_bytes` repeats the race 200 times and fails without the poll. A timeout fails with `TimedOut` where Unix says `WouldBlock`; every caller treats both as an error. A dead listener's file refuses connections (`ConnectionRefused`) and a second bind on it says `AddrInUse`, as on Unix, so the stale-file and lock logic is the same. `UnixStream::pair` has no Windows call: the test-only one binds a listener in the temp folder, connects and accepts. Checked live on 2026-11-02 (Windows 11 10.0.26200, NTFS, Rust 1.99.0): the tests of `os/socket/`, `protocol`, `client::server_process`, `client::requests`, `cli::requests` and the proxy pass.
- **The socket's folder** (#591, `os/fs/windows/acl.rs`, `os::fs::owner_and_mode`, `make_private`, `create_private_dir_all`): `protocol`'s check keeps its rules and reasons, and only what it reads moved behind `os::fs` (on Unix the same `uid`, `mode`, `DirBuilder` with `0o700` and `chmod 700` as before). On Windows the folder's owner and DACL are read from a handle that does not follow a link, and turned into what the check compares: the owner is the user's (`uid`, 0) when it is the user's SID, SYSTEM or Administrators, and nobody's otherwise; the mode is `0o700` with `0o055` when anyone else may read and `0o077` when anyone else may write (a write is any right that adds, deletes or renames inside, or changes attributes, the DACL or the owner, or a generic write or all). SYSTEM and Administrators count as the user's because they can take any file anyway (`SeTakeOwnershipPrivilege`, `SeBackupPrivilege`), as root is not counted on Unix, and because the default ACL of a profile names them, so refusing them would refuse every folder; a folder an elevated cornercase made belongs to Administrators, and is accepted. Also harmless: `CREATOR OWNER` and `OWNER RIGHTS`, which stand for the owner, and app package and capability SIDs (`S-1-15-…`), which only add a second check for sandboxed apps, every access still needing the user's own grant: the profile's `%LOCALAPPDATA%` and `%TEMP%` carry such entries (seen live). An entry counts where it reaches: the folder itself unless it is inherit-only, and the files made inside (the socket and its lock) when it is object-inherit, so an inherit-only entry for files counts and one for subfolders only does not. Entries are read in order, as Windows does, with generic rights mapped to the file rights: a right is taken away from a later allow when earlier plain denies that name Everyone (but for an allow to Anonymous, whom Everyone leaves out) or the same SID deny it everywhere the allow reaches (Windows itself splits an entry with generic rights into one for the folder and an inherit-only one for what is made inside); a deny for another group, a deny after the allow, a deny that stops at the folder while the allow reaches the files, and callback or object denies (whose conditions may not hold) take nothing away, so the reading errs towards refusing. A missing DACL, an entry of an unknown type, or a folder that cannot be read counts as anyone may write and nobody's, so the check fails closed. Making it private (the `tighten` of cornercase's own folder) writes a protected DACL with full control for the user, SYSTEM and Administrators, inherited by what is made inside; a missing folder is created with that descriptor and the user as owner in one `CreateDirectory`, as `DirBuilder` with `0o700` does, so a new folder in a shared one is private at once. What keeps other users out is the socket file's own DACL, inherited from the folder: connecting needs access to it (checked live: a socket file that grants only SYSTEM refuses the user with `WSAEACCES`); bypass traverse checking lets anyone walk through a folder they cannot list, so the folder's own entry is not what protects it.
- **The peer** (#591, `process::peer_uid`): `SIO_AF_UNIX_GETPEERPID` gives the other end's process id (the one that connected or accepted), and its token's user SID is compared with this process's: the same user reads as the user's `uid`, another user, or a process whose token cannot be opened (`ERROR_ACCESS_DENIED`), as nobody's, so `protocol::check_peer` refuses it as on Unix, and a process that cannot be found is an error, which refuses too. Kept although the folder already keeps other users out, as on Unix, where a loose umask is the reason. Limits: the id is read after the connection, so a peer that exits and leaves its id to another process of the user is taken for that process (getting that far needs access to the socket file first); a non-elevated end probably cannot open an elevated peer's token, so an elevated server and a plain window refuse each other, as root and a user do on Unix (not checked live: no elevated session was at hand).
- **Setting standard input and output aside** (#591, `cli/requests.rs`, for `cornercase requests -`): standard output and input are copied (`DuplicateHandle`) for the answers and the lines, then standard input becomes `NUL` and standard output the standard error (`SetStdHandle`), as `dup` and `dup2` do on Unix. The originals stay open until the process exits, where `dup2` closes them, so a reader of standard output sees its end only then; `requests` exits as soon as it is done. It is not covered by a unit test, since it changes the test process's own standard handles.
- **The server in the background** (#592, `os::process::spawn_detached`): a child spawned as on Unix shares the terminal's console, so closing that window or a Ctrl+C in it ends the server and every shell. The client starts `cornercase server` with `CREATE_NO_WINDOW`, which gives it a console of its own with no window: what happens to the terminal's console no longer reaches it, and its output still goes to `server.log`. Unix is unchanged (`spawn_detached` is `spawn` there, and the server calls `setsid` itself; on Windows `setsid` stays `Unsupported` and is ignored).
  - **`CREATE_NO_WINDOW` rather than `DETACHED_PROCESS`**: a process with no console at all gives every console program it starts without flags (git, gh, the host helpers, the usage probes) a new console of its own, with a window (Windows' "Creation of a Console"; not tried live, to keep windows off the screen); under a hidden console they share it (checked live: a grandchild's `GetConsoleProcessList` named itself and its parent, and `GetConsoleWindow` was null). The panes do not need the server's console either way: ConPTY makes one per pane, and portable-pty starts each shell on its pseudoconsole with invalid standard handles rather than the server's (#594). The issue's three flags together amount to `DETACHED_PROCESS`, which wins over `CREATE_NO_WINDOW`.
  - **No `CREATE_NEW_PROCESS_GROUP`**: a console of its own already keeps the terminal's Ctrl+C, Ctrl+Break and close away, and the flag also sets "ignore Ctrl+C" in the new process, which every process it starts inherits (as the documentation of `SetConsoleCtrlHandler` says), the panes' programs included.
  - **Out of the terminal's job**: a terminal or an IDE may run its shells in a job object that ends every process in it when it closes (`KILL_ON_JOB_CLOSE`), and the server with them. So the server starts with `CREATE_BREAKAWAY_FROM_JOB` too, and again without it when the job does not allow leaving (`ERROR_ACCESS_DENIED`); the server then ends with that job. Checked live with a kill-on-close job made for the check: with `BREAKAWAY_OK` the child was out of it, without it the spawn was refused and the retry put the child in the job. The tests run the retry too where they were run, inside a job that does not allow leaving.
  - **The folder it was started in** (`os::process::leave_launch_folder`, `launch_folder`): Windows keeps a process's current folder open, so the folder cannot be renamed or removed while the process runs, and a server started from a worktree kept that worktree until `kill-server` (checked live: renaming a child's current folder failed with a sharing violation, error 32, and worked once the child had moved to another folder). So the server remembers the folder it started in and moves to its socket's folder, which it holds anyway, before it takes any client; `open_here` and a pane started without a folder take the remembered one, and a program it starts without a folder starts in the socket's folder. A relative `CORNERCASE_SOCKET` keeps it where it started, since the socket and the files next to it are relative to that folder. Unix is unchanged: a folder in use can be removed there, so the server stays where it started and `launch_folder` is `current_dir`.
  - **The client's standard handles stay out of it**: std spawns with `bInheritHandles` and offers no handle list (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`), so every inheritable handle of the client reached the server, its standard output among them; whoever reads that output (`$out = cornercase start-server --json` in PowerShell, a script's pipe) then waited for the server to end rather than for the command. Checked live with a stand-in that lives 8 s: a capturing PowerShell took 8.5 s, and 0.12 s once the handles were not inheritable. So `spawn_detached` first clears `HANDLE_FLAG_INHERIT` on the client's three standard handles, for good: std still hands them to any later child, since it duplicates them as inheritable for each one (the restart below). Limit: other inheritable handles the client got from its parent still reach the server.
  - **The log takes stderr** (`console::redirect_stderr`): `SetStdHandle` with a copy of the log's handle, which std's `stderr` reads on every write, so panics and messages of a server started in the foreground go to the log, as `dup2` does on Unix. `dup2` closes the descriptor it replaces; here the handle the log took is closed one rotation later (every 8 MB), so a thread that read it just before the rotation still writes to an open handle, never to a closed value that another object took. Closing it then also frees the file it points to, which that rotation's rename has just replaced (std's `rename` replaces a file held open; checked live): an open handle keeps a replaced file's data on disk, unseen, so keeping every handle cost one hidden 8 MB file per rotation. The handle the server started with is never closed, since the C runtime's descriptor 2 holds it; with standard output, which points at the same first log, it keeps that one replaced log of at most 8 MB, as descriptor 1 does on Unix.
- **The server's stop events** (#592, `os::process::on_stop_signal`): `SetConsoleCtrlHandler` stands in for `SIGINT`, `SIGTERM` and `SIGHUP`. Ctrl+C and Ctrl+Break stop the server the way a signal does (its loop ends, the socket is removed, the TODO list, the queue and the stats are written, then plugins stop, see Client / server; `session.json` is written only for a restart, on every OS); a closed window, a logoff and a shutdown do too, but Windows ends the process as soon as the handler returns, so the handler then waits for the process to end on its own. The first event stops. While that stop runs, a closed window, a logoff or a shutdown waits for it the same way, so closing the window after a Ctrl+C does not cut it short; only a second Ctrl+C or Ctrl+Break goes on to Windows' default, which exits at once. Registering also clears an inherited "ignore Ctrl+C" (`SetConsoleCtrlHandler(NULL, FALSE)`), as a signal handler replaces an inherited `SIG_IGN`, so the server and what it starts get Ctrl+C. Only a server run in the foreground (`cornercase server`) gets a terminal's events. A server started in the background has only its hidden console, where a Ctrl+C or a Ctrl+Break can only come from a program attached to it (a setup script's `GenerateConsoleCtrlEvent` for its group, which is the whole console): on a console without a window (`GetConsoleWindow` is null) both are answered without stopping. Checked live: under a pseudoconsole (the app's terminal panel) `GetConsoleWindow` gave a window, and under `CREATE_NO_WINDOW` it was null, as it was under the hidden console a tool's shell ran in, where nobody can type a Ctrl+C either. Since #600 the binary loads `user32.dll` (through `shell32.dll` and `ole32.dll`), and Windows sends neither a logoff nor a shutdown to the Ctrl handler of a process that loads it (before #600, with neither `user32.dll` nor `gdi32.dll` loaded, checked with `dumpbin /dependents`, the hidden console got both), so a hidden window of the server takes them (below). `SIGHUP` keeps the server alive on Unix, where it survives its terminal; no console event can, so a closed window stops a foreground server cleanly instead.
  - **No hard stop**: the client never signals the server. `kill-server` and `restart` go over the socket, and `wait_for_exit` (`SERVER_EXIT_TIMEOUT`) only waits for the lock, on every OS, so there is nothing to turn into `TerminateProcess`.
  - **A logoff and a shutdown reach a hidden window** (#617, `os/process/windows/session_end.rs`), as the documentation of `SetConsoleCtrlHandler` advises a console program that loads `user32.dll`. `on_stop_signal`, which only the server calls, starts a thread that makes a hidden top-level window of a class of its own (`CreateWindowExW` with no style, no extended style and no parent) and pumps its messages. `WM_QUERYENDSESSION` is allowed at once and stops nothing, since another program may still refuse the end. `WM_ENDSESSION` with `wParam` true runs the stop the Ctrl handler runs, taken from the same slot, so whichever comes first stops the server and the other waits for it; then, as the Ctrl handler does, the window holds its reply, since Windows may end the process as soon as it answers, and the process ends on its own once `run` returns, mid-wait. It holds it 4 s at most (`WAIT`): Windows ends a program without a visible window that takes more than 5 s to answer either message, so the window answers before that rather than be cut off. An end called off (`wParam` false) does nothing. The Restart Manager (an installer closing the programs that hold its files) sends the same two messages, with `ENDSESSION_CLOSEAPP`, and gets the same stop. If the window cannot be made, the server says so in its log and runs without it.
    - **Top-level, not message-only** (`HWND_MESSAGE`, which #617 first proposed): Windows sends the end of a session to top-level windows, as it sends broadcasts, and a message-only window is not one and takes part in neither (Raymond Chen's The Old New Thing; a Stack Overflow report saw a build with `HWND_MESSAGE` stop getting `WM_QUERYENDSESSION`). Microsoft's own sample (Registering a Control Handler Function) makes this same window: no parent, no instance. A test checks that `EnumWindows`, which lists top-level windows, finds it (it fails with `HWND_MESSAGE`), and that it is hidden.
    - **`WM_CLOSE` stops it too**: `taskkill /pid` without `/f` sends one (checked by hand: it reached the window, message-only or not), and `DefWindowProc` would destroy the window and leave the server deaf to the end of the session; so it runs the same stop and keeps the window, as `SIGTERM` stops the server on Unix. #597 closes only visible windows, so it never sends this one anything.
    - **Asked first** (`SetProcessShutdownParameters(0x3FF, 0)`, called with the window): Windows ends processes from the highest level down, and every process starts at 0x280, so the server, at the top of the applications' range, stops while its shells and agents still run, before their exits could reach it. No `SHUTDOWN_NORETRY`: since Vista, Windows already ends a program without a visible window after 5 s without asking anyone, and never lets one cancel the end ("Shutdown Changes for Windows Vista"). Rejected for the same reason: `ShutdownBlockReasonCreate` while the stop runs. Only a program with a visible window is listed on the screen that holds the end, so the reason would never show; and the stop is short and bounded anyway.
    - **Limits**: `session.json` is not written at that stop, as at every signal stop on every OS (Saved session writes it after 2 s of quiet), so a change made in the last 2 s before a logoff is lost. Not checked with a real logoff or shutdown: the tests send the messages to the window with `SendMessageW`, and by hand (2026-11-03, Windows 11 10.0.26200, a debug build with the refusal lifted, not committed) a PowerShell script found a foreground `cornercase server`'s window with `EnumWindows` and sent it both with `SendMessageTimeoutW`, as Windows does: the question got `TRUE`, and after the end the log said `stopping on a signal` and `stopped`, the socket was gone and the process exited 0, 26 ms later.
- **The restart without `exec`** (#592, `CommandExt::exec`): Windows has no `exec`, so the client runs the new binary in its place: same console and standard handles (std duplicates them), waits for it, and exits with its exit code, so whoever started the window (the shell) waits for the new window as it did for the old one, and the code comes through (`process::exit` takes Windows' 32 bits whole). While it waits, a Ctrl handler that answers every event keeps Ctrl+C and Ctrl+Break from ending the waiting process and leaving the new window to fight the shell for the console, as `cargo run` does; a handler rather than `SetConsoleCtrlHandler(NULL, TRUE)`, whose "ignore Ctrl+C" the new window, its server and their panes would inherit. A closed window still ends both. The console's modes stay right: the old window restores them before it runs the new one (#593), the new one keeps those and restores them when it ends, and the waiting one touches the console no more, so nothing in it may read the console once the window ended (#593's reader stops with the window). Limits: each restart leaves one waiting process until the window is closed, a chain over many restarts; making the first one start every later binary itself was left for later, since the new binary would have to hand the restart back as an exit code instead of starting its own. And each waiting process keeps its binary's file in use, which the update's rename has to allow (#602).
- **Checked by hand** (2026-11-03, Windows 11 10.0.26200, a debug build with the refusal lifted for `start-server`, `status`, `kill-server`, `restart`, `logs` and `server`, not committed): `start-server` in a terminal tab started the server (its answer was the expected error, since no pane can start yet, #594), the tab was closed (the terminal kills every process on its console), and from a second tab `status --json` answered with the same server's `boot` and `kill-server` stopped it (`kill-server received`, `stopped` in the log, the socket file removed). `start-server` with its output redirected to a file returned at once. `restart --yes` with no window left no server, as on Unix. A foreground `cornercase server` stopped on Ctrl+C (`stopping on a signal`, `stopped`); under a pseudoconsole that was then closed it logged the same and exited 0 within 5 ms; and a server started by `start-server` under a pseudoconsole that was then closed kept running until `kill-server`. The server's hidden console was a `conhost.exe 0x4` child of it. Not checked: the restart of a window (it needs the console and the panes, #593, #594), and a logoff or shutdown. Commands run inside Claude Code's sandbox could not bind or reach the socket (`WSAEINVAL`): the checks ran in a terminal outside it. Seen on the way, for #594: portable-pty prefers a `conpty.dll` found on the DLL search path over the system's, and here took WezTerm's (with its `OpenConsole.exe`) from the `PATH`. - **The console in raw VT mode** (#593): the window keeps its own byte decoder (see Keys and mouse), and the console hands it the bytes a Unix terminal sends. `os::console` keeps the input and output modes and sets raw VT mode before `ratatui::init`, so before crossterm's raw mode and the VT processing it turns on, and before ratatui writes its first sequence: the input goes to `ENABLE_VIRTUAL_TERMINAL_INPUT` and `ENABLE_EXTENDED_FLAGS` without `ENABLE_LINE_INPUT`, `ENABLE_ECHO_INPUT`, `ENABLE_PROCESSED_INPUT` and `ENABLE_QUICK_EDIT_MODE` (Quick Edit eats clicks), and the output to `ENABLE_VIRTUAL_TERMINAL_PROCESSING` and `DISABLE_NEWLINE_AUTO_RETURN`; every other bit stays. A console that refuses ends the window with `Error::Console` rather than run it without VT input. The kept modes are written back as they were rather than by turning bits back on (crossterm's `disable_raw_mode` turns line input, echo and Ctrl+C on whatever they were), and after `ratatui::restore`, so the alternate screen is left while VT processing is still on: at the end of `open`, before a restart's `exec`, in `release_screen`, and on a panic through a hook installed before ratatui's, which runs after ratatui's restore and before the message is printed. Crossterm turns VT output on once per process and never looks again, so once the kept modes are back (VT output off in the legacy conhost) nothing may write a sequence before raw mode is set again: a second window in the same process (the `[y/N]` answer to a server of another build) sets it before `ratatui::init`, and `release_screen` sets it before it writes, as after a restart's `exec` that failed. The panic hook is installed once per process, so a second window's hooks write their sequences before it restores the modes. On Unix the three calls are empty: crossterm's termios raw mode is all it needs.
- **Mouse, paste, focus and keyboard modes are written as text on every OS**: crossterm's `EnableMouseCapture` goes through the legacy console API on Windows, which sets the input mode to mouse records and so turns VT input off, and its `PushKeyboardEnhancementFlags` is refused there, which stopped `execute!` halfway. `Command::write_ansi` gives the bytes `execute!` wrote on Unix, unchanged, which `client::tests` checks on Unix.
- **Reading waits on the console's handle, without a thread**: `console::wait_input` waits with `WaitForSingleObject` on the input handle, then reads the records that woke it with `ReadConsoleInputW`, at most as many as `GetNumberOfConsoleInputEvents` counts, so a read never blocks past the deadline when another reader of the console took them first (none queued: it waits again). It keeps the characters of key-down records (and of Alt's key-up, which carries a character composed on the numpad, as libuv reads it), drops the rest (focus, size, menu and mouse records, key-ups) and waits again until its deadline. NUL (Ctrl+Space, Ctrl+@) has no character to keep: the console writes it as a key-down of virtual key `0x40`, a code no key uses, with Ctrl held and the character 0 (seen in Windows Terminal and conhost), so that record alone is kept as `0x00`, and a Ctrl pressed alone is not. A read returns once it took a byte, never 0, which would read as the end of input. The UTF-16 becomes UTF-8, a high surrogate waiting across reads for its other half, in one queue that the probe and then the window's input thread read. Rejected: reading with `ReadFile` or `ReadConsoleW` after the wait, which blocks when only focus or size records woke it; a reader thread feeding a channel, simpler and the same on every OS, which cannot be stopped while it blocks in a console read, so after the window ends it would keep taking keys from whatever reads the console next (the `[y/N]` question when a server of another build rejects the window, or the new binary of a restart, which Windows runs as a child since it has no `exec`); and `std::io::stdin`, which on a console drops a trailing Ctrl+Z. The wait and the decoding take the console as a trait, so their tests run on made-up records; a read that fails on a handle that is gone (`ERROR_INVALID_HANDLE`, `ERROR_BROKEN_PIPE`, `ERROR_HANDLE_EOF`) ends the input as `EIO` does on Unix.
- **Resizes are polled**, since Windows has no `SIGWINCH`: a thread of the window reads `crossterm::terminal::size()` (`GetConsoleScreenBufferInfo`) every `INPUT_POLL` (100 ms) and sends the same `Event::Resize` as the Unix signal thread when it changed; a size it cannot read is skipped. The console's own size records are dropped with the others, since the thread sees the change within 100 ms.
- **The window's Ctrl events stand in for `SIGINT`, `SIGHUP` and `SIGTERM`**: `SetConsoleCtrlHandler` turns `CTRL_C_EVENT`, `CTRL_BREAK_EVENT`, `CTRL_CLOSE_EVENT`, `CTRL_LOGOFF_EVENT` and `CTRL_SHUTDOWN_EVENT` into the window's `Signal`, which detaches it. With processed input off a typed Ctrl+C is the byte `0x03` for the pane, while a Ctrl+C sent by a program (`GenerateConsoleCtrlEvent`) and Ctrl+Break still reach the handler. Windows ends the process once the handler of a closed window returns, and the server sees the link close as a detach. An event is handled only while a window takes it, else it goes on to the next handler (Windows' default exits); the handler goes when the window's threads stop.
- **A token typed without echo** (`cli/config.rs`) turns `ENABLE_ECHO_INPUT` off, keeps line input so the token is still read as a line, and writes the mode back. Where that fails, though standard input is a terminal (mintty and Git Bash's own window, whose pipes `is_terminal` takes for a terminal but which have no console mode), `config secret` refuses to prompt and says to pipe the token in, rather than show it as it is typed; documenting the echo as a limit was rejected, since a token on screen is the one thing the prompt is there to avoid. On Unix the prompt never refuses (`Hidden::on` keeps the Windows `Option` under an `#[expect(clippy::unnecessary_wraps)]`).
- **The console, checked by hand** (2026-11-02, Windows 11 26200, Windows Terminal 1.24.12741.0 and the legacy conhost), with a throwaway ignored test started in a new console: the modes went from `0x1f7`/`0x7` (conhost `0x3`) to `0x3b0`/`0xf` and back exactly; records written with `WriteConsoleInputW` came back as `aé😀`, `0x03` and an up arrow as `ESC [ A` (the console turns a key into VT when the record is written); Windows Terminal answered OSC 11, OSC 10, DA1 and a cursor report, and conhost all but OSC 10 and 11, which the probe's 1 s timeout covers; `GenerateConsoleCtrlEvent` reached the handler for Ctrl+C and Ctrl+Break; the echo went off and back; on 2026-11-03, Ctrl+Space and Ctrl+@ written the same way came back as `0x00`. Not checked: keys, clicks and the wheel from a person, resizes, and the whole window against a server, which needs the panes (#594). The console's tests are `#[cfg(windows)]` (`os::console::tests`, `client::window::tests::console`) and were run by hand with filters until #601.
- **The desktop** (#600): `os/desktop.rs` holds the calls the window and the server make on the user's desktop, and this step's `unsafe`, through `windows-sys` (pinned with `=`, a Windows-only dependency, its features listed in `Cargo.toml`): `shell_open` (`ShellExecuteExW`, for File Explorer and the default app), `windows_folder` (`GetSystemWindowsDirectoryW`, where Explorer is), `dangerous` (`AssocIsDangerous`), `play` (`PlaySoundW`), `Awake` (`SetThreadExecutionState` on a thread of its own) and `detach` (`CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`, where Unix gives a process group of its own). Its pair is inverted: the real `imp` is `cfg(windows)` and the other one stubs everything but `detach`, which is `process_group(0)` there. The callers choose by OS at run time, never with `cfg` around their code: `host::sound::Os` is passed down to what differs (the `PATH` lookup, `Kind`, `Openers`), and `agents::awake::tools` reads `cfg!(windows)`. So the Windows paths compile and are linted on every system, the stubs are reached, so nothing is dead code on Unix, and the rules that need no Windows call are tested on every system. Each area's note says what it decided: Opening in other apps, Sound, Keeping awake. A string with a NUL is refused before it reaches a call, rather than cut there.
- **Panes in ConPTY** (#594): portable-pty's native system is ConPTY on Windows (10 1809 and later), so `Term` keeps one code path, and `term.rs`'s Windows `imp` handles what ConPTY and Windows do their own way. What ConPTY does to the bytes (it repaints, passes a mouse mode only from a program that reads VT input or asks the console for the mouse, holds the shell until its cursor request is answered) is under Terminals.
  - **The mouse needs nothing of ours** (#616): a program that asks for it gets it through ConPTY (Terminals › ConPTY), so vim with `set mouse=a`, or a program reading mouse records, takes clicks, drags and the wheel as on Unix; the one change is that X10 presses stop at column and row 95, and releases and drags past it come there (Keys and mouse). Passthrough mode was tried and rejected: the system ignores it and WezTerm's `conpty.dll` hangs with it, and using it would have meant creating the pseudo console ourselves instead of through portable-pty. A program that writes a mouse mode without reading VT input (cmd's `prompt`) keeps it in the host; it could not read the reports anyway.
  - **The pane's environment is the server's**: portable-pty builds a Windows command's environment from ours and then overwrites it with the registry's system and user variables (`PATH` the two joined), as a new login would, so a pane lost the `PATH` the server started with (Git Bash's `usr\bin`, a developer prompt's tools; checked). `imp::inherit` sets the server's own environment back over it, so a pane starts from the server's environment as on Unix, with cornercase's variables on top; a variable only the registry holds still comes through. A pane given no folder starts in `os::process::launch_folder` (#592).
  - **The foreground program** (ConPTY has no process groups, so no `tcgetpgrp`): the pane's tree from its shell (`process::children`, the newest child by start stamp at each step), down to the first program that is not a shell (`process::is_shell`); through nothing but shells, the deepest one (Git for Windows' `bin\bash.exe` launcher and the `usr\bin\bash.exe` it starts, a `cmd` started from pwsh), as Unix names a nested interactive shell. Not the deepest program: an agent's tools and MCP servers are its children, and on Unix they share its process group. **At the prompt** (`shell_in_foreground`, which launches, `wait` and the worktree checks read) is the pane's shell or a shell under it in the foreground (`imp::at_prompt`), so the launcher, or a shell started from the pane's, still counts as at its prompt; on Unix it stays the pane's shell itself. The cost is a few `OpenProcess` per call on the 50 ms snapshot, and `Term::feed` asks once per read.
  - **A background job counts as the foreground** (a limit): `start /b npm run dev` in cmd, `&` in pwsh 7 or Git Bash leave a program under the shell while the shell waits at its prompt, and nothing on Windows tells it from a program the shell waits for (no process group, no `tcgetpgrp`; the console's process list holds both). So while one runs the tab is named after it, `shell_in_foreground` is false (`wait` blocks, a launch waits, closing a worktree says a program runs), and agent detection looks at it. Rejected: a job object or the console's process list, which would not tell the two apart either, and asking the shell, which only a prompt hook could (see The pane's folder).
  - **The pane's folder** (`Term::cwd`): the current folder of the foreground process, as on Unix, which cmd and bash keep in step with `cd`. PowerShell does not: `Set-Location` moves its location and never its process folder (checked with Windows PowerShell 5.1 on 2026-11-03; pwsh 7 was not installed here). So when PowerShell is in the foreground (`pwsh` or `powershell`, by name), the folder its prompt reported wins, when it names a folder that exists: an OSC 7 `file://` URL (host dropped, percent escapes decoded, `/C:/…` read as `C:/…`) or ConEmu's OSC 9;9 path (quotes dropped), which libghostty-vt keeps raw as `pwd` (OSC 1337's `CurrentDir` too). A program PowerShell starts gets its location as its folder, so a running program's own folder is right. **The default PowerShell prompt reports nothing**, so until the user's prompt does (Windows Terminal's documentation gives the line for OSC 9;9, and oh-my-posh and Starship can emit it), a PowerShell pane's folder is the one it started in: a relative path clicked in it, `status`'s path, the terminal request's folder, the files opened from it and a new tab's folder start from there. Other readers of a process's folder (ports, the worktrees dialog's busy check) see the same. No prompt hook is injected: it would mean starting PowerShell with a command of ours (so the pane would count as started with a command, not a shell), running code of ours at every prompt in the user's session, and fighting the prompt frameworks that replace `prompt`; on Unix nothing is injected into a shell either. On Unix the reported folder is not read (`imp::reported_folder` answers nothing), so nothing changes there.
  - **The exit and closing**: ConPTY keeps its output pipe open after the shell exits, so the reader never saw the end and `Event::Exited` never came (only `App::reap`'s poll noticed). A thread per pane waits on the shell's process handle and then closes the pseudo console (dropping the master), which sends the last frame, ends the console host and closes the pipe, so `Exited` comes after the last output as on Unix. Closing never runs on the main thread (the waiter, or a thread from the master's `Drop`): `ClosePseudoConsole` waits for the host, and the host waits for the answer to its startup cursor request (portable-pty sets `PSEUDOCONSOLE_INHERIT_CURSOR`) while nothing has fed the pane's output to the emulator, which answers it. So the closer first writes a cursor report (`ESC[1;1R`) into the pane, where nothing reads it any more. Without it a pane dropped while the request waits never closed under WezTerm's `OpenConsole.exe`, while the system's `conhost.exe` (build 26200) closed at once anyway; so its test (`exit::a_pane_dropped_with_the_cursor_request_unanswered_closes_even_under_openconsole`) fails without it only when WezTerm is on the `PATH` of the test run, and passes under conhost either way.
  - **Which console host**: portable-pty loads a `conpty.dll` from the DLL search path before the system's (seen under #592): with WezTerm on the `PATH` every pane ran WezTerm's `OpenConsole.exe`, else the system's `conhost.exe`. The tests passed under both (Terminals says where they differ); the search was left as it is, since taking it from portable-pty would mean keeping a fork of it.
  - **The default shell** (`term::shell::default`, once when the server starts): `$SHELL` if Windows can start it (a full path, or a bare name found on the `PATH`, without surrounding quotes), else `pwsh.exe` on the `PATH`, else `powershell.exe` on the `PATH`, else `%COMSPEC%` if it names a program, else `cmd.exe`; each is started by its full path. A candidate counts only as a file ending in `.exe` or `.com` (a name without one gets `.exe`), the programs `CreateProcessW` starts by themselves: an extensionless npm or Scoop shim beside the program, or a `.cmd`, would have been taken and then failed for every pane, with nothing to fall back to. A `$SHELL` Windows cannot start as it is (a Unix path such as `/usr/bin/bash`, a relative one) is skipped with a warning in the log, not mapped: Git Bash and MSYS2 hand their `SHELL` to native programs already as a Windows path (`C:\Program Files\Git\usr\bin\bash.exe`, checked), so a Unix path comes from a setting not meant for Windows, and looking its name up on the `PATH` could start WSL's `bash.exe`. That `usr\bin\bash.exe` finds `ls` only with Git's `usr\bin` on the `PATH` (Git's `bin\bash.exe` launcher adds it), which a server started from Git Bash now hands its panes. The shell starts without arguments, as on Unix, so PowerShell prints its banner and loads the user's profile. pwsh from the Microsoft Store is an app execution alias, a reparse point `metadata` may not follow, so a file counts when `metadata` or `symlink_metadata` says it is one.
  - **Tests** start `cmd.exe /d` (no AutoRun commands, cmd's profile) with `PROMPT=$G` and a `PATH` of `System32` alone: the `PATH` cargo gives a test (every build script's folder, about 8,600 characters here) passes the 8,191 characters cmd can expand, and cmd then finds no program at all. PowerShell runs there with `-NoProfile`. The mouse tests have it compile a reader of ours (`tests/fixtures/conpty/mouse.cs`, with `Add-Type`, which Windows PowerShell 5.1 does with the .NET Framework's compiler that comes with Windows) that asks for the mouse with VT codes or through the console API and prints what it reads, as hex for VT input, since Windows ships no program that asks for the mouse, and Git for Windows' vim is not on every machine. Under Constrained Language Mode (AppLocker or WDAC) PowerShell refuses `Add-Type`: the reader's start then catches the refusal and the test fails at once with PowerShell's answer, rather than after its 30 s wait (checked with a call the reader does not have; Constrained Language Mode itself was not tried). Paths given to PowerShell are single-quoted with their quotes doubled (`single_quoted`), so a folder with an apostrophe still works. One test starts a pane without setting `PATH` and compares the shell's own (`process::env`) with the test's, which cargo made unlike the registry's, so it fails without `imp::inherit`.
- **On Windows, cornercase says so**: `cli::run` refuses every command with `Error::NotOnWindows` (cornercase does not run on Windows yet, with a link to #586) and exit status 1, before anything reaches the server, the socket or the console. `--help` and `--version` still work, since clap answers them before `run`. One check in one place rather than one per command, so nothing half-works over the socket; with the socket, the server's process, the console and the panes ported (#591, #592, #593, #594), lifting it is the next step.
- **Tests that need Unix** are `#[cfg(unix)]`: the whole test file, with `#![cfg(unix)]` on its first line, where most of it needs Unix (file modes, symlinks, descriptors, rustix, the server's attached client), else the group or the test, and the test helpers only they use carry `#[cfg(unix)]` under their `#[cfg(test)]`. Never `#[cfg(all(test, unix))]`: clippy (its exemptions for tests) and `tests/layers.rs` only see code under a literal `#[cfg(test)]` as test code, and the combined form made clippy lint `worktrees::tests` as production code. `test_util`'s `Locked`, `Sleeper` and `Family` go through `os/` instead, since half the suite uses them. Tests that only run shell scripts or `/bin/sh` panes still compile on Windows. Since #591 `UnixStream::pair` exists on Windows too, for tests only (a listener on a temporary path, connected and accepted), so the tests that only need a socket run on both: `protocol`'s paths and peers, `client::server_process`, `client::requests` but its readers and inputs, `cli::requests`' streams and the proxy's slow ssh. The e2e crate is `#![cfg(unix)]`. Nothing runs the suite on Windows yet (#601); the Windows process tests (`process::tests::on_windows`, `process::handles::tests::on_windows`, the `on_windows` groups of the Codex, Copilot, Cursor and opencode readers, `git::worktree::tests::lock_holder_on_windows`, the detection cases of `agents::tests`) and pane tests (`term::tests::on_windows`, `term::shell::tests::on_windows`) were run by hand, and there `test_util::exited_pid` gives a pid Windows never hands out (`i32::MAX - 3`) instead of running `/bin/sh`: Windows gives an exited process's pid to the next process within milliseconds, and tests spawning in parallel took each other's. So were the stop's (#597): `os::process::windows::tests` (ending a process, a program with no window left as it was by the polite step, a job that holds a `cmd` and its two `ping`s, ends them on the hard step and when closed by the system, and leaves what an ended child started when dropped), `processes::stop::tests::on_windows`, `process::escalation::tests` on every OS, the CLI texts and a plugin action ended by the hard step, which reads as `exited` with code 1. Their `cmd` lines run `ping` by its full path: under `cargo test` here, `cmd` found no `ping` on the `PATH`.
- **CI** (#587, #588): a `clippy (windows-2025)` job runs `cargo clippy --all-targets --all-features --locked -- -D warnings` with the same toolchain, Zig and cache as the other jobs, so a change that breaks the Windows build shows a failing check on its pull request. It is not yet among the checks `main`'s ruleset requires, so it does not block a merge on its own. It does not run the tests. A few lints differ on Windows and are silenced there only: `large_enum_variant` on the server's `Step` (paths are larger on Windows), `dead_code` on `Supervisor::steps` in Windows test builds and on the painter's `Fail::Timeout`, and `trivially_copy_pass_by_ref` and `unused_self` on the console's `BorrowedFd` stub. - **Long paths** (checked 2026-11-02): Ghostty's sources, cloned inside `target/`, hold files (its fuzz corpus) deep enough to pass Windows' `MAX_PATH` on the runner, and git cannot check them out without `core.longpaths`, so the job sets it before anything clones. - **Scripts and plugin commands without sh** (#595, `script.rs`): what runs a project's setup and teardown, the editor opened from a panel, and a plugin's `#!` program. What each area decided is in its note (Worktree setup, Plugins); this is the layer under them.
  - **One place picks the interpreter**: `script::Shell::here()`, once per process. On Unix it is `/bin/sh` and every command line is the one it was (`sh -ec SCRIPT` for a teardown, `sh -c TEXT NAME ARGS…` for the setup's wrapper and the editor). On Windows it is Git for Windows' `sh` when found, else PowerShell 7 (`pwsh`) when `process::program` finds it on the `PATH`, else Windows PowerShell by its full path, `System32\WindowsPowerShell\v1.0\powershell.exe` in the Windows folder (`os::desktop::windows_folder`), never by name through the `PATH`, where that folder may be missing and an earlier entry could hold another `powershell.exe` (`Shell::pick`, given what was found, so its tests choose; the bare name only if Windows could not give its folder). The callers branch on the kind at run time, never with `cfg` around their code, so the Windows paths compile and are linted everywhere and the Unix build reaches them only as `Shell::Sh` with `git: false`.
  - **Finding Git's `sh`**: only inside Git's own install, whose root is found two ways and nowhere else. First `git --exec-path` (run through `process::program`), which Git for Windows 2.x answers with `<root>\mingw64\libexec\git-core` (`clangarm64` on ARM) even when the `git` on the `PATH` is a shim (scoop's `shims\git.exe`): the root is three folders up, taken only when the answer ends in `libexec\git-core` and `git.exe` is in that platform folder's `bin`. Else the folder of the `git` that `process::program` finds: `cmd` or `bin` (the root is its parent) or `mingw64\bin` (its grandparent), taken only when `<root>\cmd\git.exe` is there. In that root `usr\bin\sh.exe`, then `bin\sh.exe`, and only a file that belongs to the user, SYSTEM or Administrators and that no one else may write (`os::fs::owner_and_mode`; Program Files' files pass). It must be a plain file, not a symbolic link or another reparse point (`symlink_metadata`, `os::fs::reparse_point`): the owner and the DACL are read without following a link, so a link the user owns that leads to an `sh.exe` others can write would otherwise pass while its target ran. A hard link needs nothing more, since it shares its file's DACL. The symbolic link's test needs Developer Mode and says it skipped without it. `usr\bin\sh.exe` comes first: `bin\sh.exe` is a launcher that puts Git's folders first on the `PATH` of everything it starts, the shell that follows a setup included. Rejected (review of #595): searching the folder of the `git` on the `PATH` and its parents, which for scoop's global shims (`C:\ProgramData\scoop\shims`) reached `C:\ProgramData\bin\sh.exe` and `C:\bin\sh.exe`, folders any signed-in user can create on a default Windows, so another account could have run its program as the user in every setup, teardown and plugin script. The folders above `sh.exe` are not checked: Program Files' grant `TrustedInstaller` full control, which the owner and DACL reading would count as another user, and the root comes from git's own answer. Found once per process, so a Git installed later is seen after a restart of the server.
  - **Paths in arguments**: when a program of Git's `sh` starts a Windows program, MSYS2 rewrites every argument that looks like a Unix path (`/api/v1` becomes `C:/Program Files/Git/api/v1`, `--dir=/tmp/x` a folder of the temp, and `/c` `C:/`; checked 2026-11-03). A plugin's `#!` program gets `MSYS2_ARG_CONV_EXCL=*`, so what it hands a Windows program (`node` behind `#!/usr/bin/env node`, a `cmd /c`) arrives as written, and its children inherit that. A setup and a teardown keep the rewriting, as Git Bash does, since a script tried in Git Bash expects it; one that does not can set the variable itself.
  - **Nothing variable goes on an `sh` command line**: a program of Git's `sh` (MSYS2) parses its Windows command line itself, not as `CommandLineToArgvW` does. Outside quotes `'` opens a quoted string (so `it's` takes the rest of the line), `*`, `?`, `[…]`, `{a,b}` and a leading `~` are expanded and a leading `@` reads a file in; inside double quotes `\\` becomes one backslash. std and portable-pty quote an argument only when it holds a space (checked on 2026-11-03 with Git for Windows 2.39.2: an argument `it's` swallowed every argument after it). So the text to run goes in `CORNERCASE_SCRIPT` and the positional arguments in `CORNERCASE_ARGS`, as words quoted for `sh`, and the command line is a fixed adapter that sets them with `eval "set -- …"`, unsets both and runs the text, so the script never sees them. Rejected: quoting each argument for MSYS2 with `raw_arg` (it works for std's `Command`, but a pane goes through portable-pty, which quotes in its own way), and a script file in a private folder (a file to make, keep private and remove for every run).
  - **What Git's `sh` cannot write to**: a handle opened for appending only (`FILE_APPEND_DATA` without `FILE_WRITE_DATA`, which std's `append` gives); its writes fail and the command exits 1. Only a plugin's log is such a handle, so a plugin's job through `sh` appends with `>>` (Plugins).
  - **PowerShell** gets its script after `-NoProfile -Command`, quoted by std or portable-pty as `CommandLineToArgvW` reads it, which PowerShell 5.1 and 7 both do (checked). A setup's script reaches its child PowerShell through `-EncodedCommand` (base64 of UTF-16), so it is never quoted twice, and every value written into the wrapper's text is a single-quoted literal with each `'` doubled, and each of `‘ ’ ‚ ‛`, which PowerShell also takes for a single quote.
  - **cmd** never runs a script (see Worktree setup).
  - **The editor** (`app/actions.rs`, a panel's ` open `): through Git's `sh` the same `exec ${VISUAL:-${EDITOR:-vi}} "+LINE" FILE`, with Git's `usr\bin` first on its `PATH`, so `vi` is Git's vim; through PowerShell `VISUAL`, else `EDITOR`, split on spaces as `sh` splits it, and Notepad when neither is set, since Windows has no editor for a terminal of its own (Notepad opens its own window and the tab ends at once).
  - **Stopping**: nothing new. The teardown runs through `process::output_within` and a plugin's jobs through `Places::spawn`, both on `os::process::Grouped` (see Stopping a process and what it started), so `sh` or PowerShell and everything they start share a Job object and the hard step ends the whole tree. A setup and a plugin's popup are panes, stopped as panes are. No creation flag is added (`creation_flags` replaces `CREATE_NEW_PROCESS_GROUP`): like every other child of the server they share its console, which has no window (see The server in the background), so no window opens and no console is made per run.
  - **The plugin manifest's check** replaces #589's refusal: see Plugins (On Windows) for the rule, and The socket's folder for how an owner and a DACL are read; `os::fs::file_owner_and_mode` reads them from an open handle and `os::fs::reparse_point` the file's attribute.
