# Windows

Code: `os.rs`, `os/`, the `imp` pairs in `client/requests/watch.rs`, `client/input.rs`, `client/probe.rs`, `client/window.rs`, `cli/config.rs`, `cli/requests.rs`, `highlight/limit.rs` and `term.rs`, `cli.rs` (the refusal), `.github/workflows/ci.yml` (the `windows` job)

- **Native, not WSL** (#586): inside WSL cornercase already runs, but on another machine's files, `PATH` and agents. The port runs it on Windows itself, one step at a time in small pull requests to `main`, each one tracked under #586.
- **Possible** (spike on 2026-11-02, Windows 11, Rust 1.99.0, Zig 0.15.2, Visual Studio Build Tools 2022 with MSVC 14.44): `libghostty-vt` 0.2.2 builds for `x86_64-pc-windows-msvc`, and a `Terminal` parses VT input and formats it back as text. Every dependency checks, portable-pty included (its Windows backend is ConPTY). What does not compile is ours: the socket, the console, processes, file modes, git paths as bytes and the host helpers, all on Unix-only APIs.
- **Every step keeps Linux and macOS as they are**: their code is only moved behind a per-OS layer, a `mod imp` per OS with a fallback, as `process.rs` already does. Windows can be incomplete, never half-working: what is not ported returns `Unsupported`, and the window says so.
- **The per-OS layer** (#588): `os/` is a shared leaf with one file per area of the port, each holding a `mod imp` for `cfg(unix)` and one for every other system: `console.rs` (descriptors, standard input and output, the log taking stderr), `ffi.rs` (paths as bytes), `fs.rs` (file modes, metadata, links, locks, `access`, the user's ids), `process.rs` (signals, process groups, sessions, `exec`, the server's stop signals) and `socket.rs` (the local socket). On Unix an `imp` re-exports what the code used before (`std::os::unix`'s traits, `std::os::fd`, std's `UnixStream`, rustix's functions), so most callers only changed a `use` line. Where rustix's own types (`Errno`, `FlockOperation`) sat in the caller's logic, the Unix code moved into the `imp` as it was, behind a function of our own: `fs::try_lock` and `fs::locked`, `fs::writable`, `fs::uid` and `fs::gid`, `fs::set_mode` and `fs::set_file_mode` for `Permissions::from_mode`, which no Windows type can build, `process::alive`, `process::on_stop_signal` and `console::redirect_stderr`. Code whose Unix calls are woven into one module's own logic and types keeps its `imp` pair in that file instead: `client/requests/watch.rs` (whether the reader of a command's output or its input went away), `client/input.rs` and `client/probe.rs` (polling and reading the terminal), `client/window.rs` (the window's signals), `cli/config.rs` (a token typed without echo), `cli/requests.rs` (setting standard input and output aside), `highlight/limit.rs` (waiting for the painter, with its own `Fail`) and `term.rs` (a pane's foreground process group, through portable-pty). `rustix` and `signal-hook` are Unix-only dependencies: production code reaches them only inside a Unix `imp`, and only Unix-only tests use them directly. Each later step replaces one Windows `imp`.
- **The desktop** (#600): `os/desktop.rs` holds the calls the window and the server make on the user's desktop, and the only `unsafe` of the port so far, through `windows-sys` (pinned with `=`, a Windows-only dependency, its features listed in `Cargo.toml`): `shell_open` (`ShellExecuteExW`, for File Explorer and the default app), `play` (`PlaySoundW`), `Awake` (`SetThreadExecutionState` on a thread of its own) and `detach` (`CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`, where Unix gives a process group of its own). Its pair is inverted: the real `imp` is `cfg(windows)` and the other one stubs everything but `detach`, which is `process_group(0)` there. The callers choose by OS at run time (`host::sound::Os::Windows`, `cfg!(windows)` in `agents::awake::tools`, `host::open::Kind`), never with `cfg` around their code, so the Windows paths compile and are linted on every system, and the stubs are reached, so nothing is dead code on Unix. Each area's note says what it decided: Opening in other apps, Sound, Keeping awake. A string with a NUL is refused before it reaches a call, rather than cut there.
- **What the stubs answer**: an empty list, `None`, `false` or 0 for what is read (a pid's name, a file's inode or mode, whether a process is alive), `io::ErrorKind::Unsupported` for what acts (a signal, a lock, a link, a mode set on a path, a socket, `exec`), and nothing for a builder's mode or flags (`OpenOptionsExt::mode`, `DirBuilderExt::mode`, `CommandExt::process_group`), which cannot fail. The types that cannot exist yet (`UnixStream`, `UnixListener`, `OwnedFd`, the window's signal handle) hold `Infallible`, so their methods are `match self.0 {}` and never run; a `BorrowedFd` is a token that every stub refuses. None panics. Paths as bytes are the one stub that works: `as_bytes` gives the encoded bytes, and bytes that are not UTF-8 become an empty path rather than an invalid one. Two stubs act as the Unix code does when it cannot: the token prompt's echo stays on (as when standard input is no terminal), and the painter's wait reports a broken worker rather than a timeout, so a file is not marked as too slow for good.
- **Stubs that guard safety must fail closed before the refusal goes**: a 0 read where the Unix code compares or checks makes the check pass. Two files' `dev` and `ino` are both 0, so `accounts::transfer` takes any two files for the same one. The socket folder's owner and mode, and a plugin manifest's, read 0 against our uid 0, so neither is ever refused, and `NOFOLLOW` is 0, so a manifest behind a link is followed. `process::alive` is false, so a worktree lock whose holder runs reads as gone. The log's rotation by inode is never seen, and every size on disk is 0. Nothing reaches them while `cli::run` refuses; each step that ports one gives a real answer or refuses (#589 for files, #596 for processes), and the refusal goes only once none is left.
- **On Windows, cornercase says so**: `cli::run` refuses every command with `Error::NotOnWindows` (cornercase does not run on Windows yet, with a link to #586) and exit status 1, before anything reaches the server, the socket or the console. `--help` and `--version` still work, since clap answers them before `run`. One check in one place rather than one per command, so nothing half-works over the socket; it goes once the socket, server and console steps land.
- **Tests that need Unix** are `#[cfg(unix)]`: the whole test file, with `#![cfg(unix)]` on its first line, where most of it needs Unix (file modes, symlinks, `UnixStream::pair`, rustix, the server's attached client), else the group or the test, and the test helpers only they use carry `#[cfg(unix)]` under their `#[cfg(test)]`. Never `#[cfg(all(test, unix))]`: clippy (its exemptions for tests) and `tests/layers.rs` only see code under a literal `#[cfg(test)]` as test code, and the combined form made clippy lint `worktrees::tests` as production code. `test_util`'s `Locked`, `Sleeper` and `Family` go through `os/` instead, since half the suite uses them. Tests that only run shell scripts or `/bin/sh` panes still compile on Windows. The e2e crate is `#![cfg(unix)]`. Nothing runs the suite on Windows yet (#601).
- **CI** (#587, #588): a `clippy (windows-2025)` job runs `cargo clippy --all-targets --all-features --locked -- -D warnings` with the same toolchain, Zig and cache as the other jobs, so a change that breaks the Windows build shows a failing check on its pull request. It is not yet among the checks `main`'s ruleset requires, so it does not block a merge on its own. It does not run the tests. A few lints differ on Windows and are silenced there only: `large_enum_variant` on the server's `Step` (paths are larger on Windows), `dead_code` on the window's `Signal` event, which nothing sends until the console is ported, on `Supervisor::steps` in Windows test builds and on the painter's `Fail::Timeout`, and `trivially_copy_pass_by_ref` and `unused_self` on the console's Windows stub.
- **Long paths** (checked 2026-11-02): Ghostty's sources, cloned inside `target/`, hold files (its fuzz corpus) deep enough to pass Windows' `MAX_PATH` on the runner, and git cannot check them out without `core.longpaths`, so the job sets it before anything clones. A short `CARGO_TARGET_DIR` was not needed: what the linker writes stays well under the limit under the runner's checkout, and the default `target/` keeps `Swatinem/rust-cache` working without a mapping. A `target/` folder nested deep in the file system does hit it: the linker fails with `LNK1104`.
