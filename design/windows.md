# Windows

Code: `os.rs`, `os/`, the `imp` pairs in `client/requests/watch.rs`, `client/input.rs`, `client/probe.rs`, `client/window.rs`, `cli/config.rs`, `cli/requests.rs`, `highlight/limit.rs` and `term.rs`, `client.rs` (keeping and restoring the console's modes), `cli.rs` (the refusal), `.github/workflows/ci.yml` (the `windows` job)

- **Native, not WSL** (#586): inside WSL cornercase already runs, but on another machine's files, `PATH` and agents. The port runs it on Windows itself, one step at a time in small pull requests to `main`, each one tracked under #586.
- **Possible** (spike on 2026-11-02, Windows 11, Rust 1.99.0, Zig 0.15.2, Visual Studio Build Tools 2022 with MSVC 14.44): `libghostty-vt` 0.2.2 builds for `x86_64-pc-windows-msvc`, and a `Terminal` parses VT input and formats it back as text. Every dependency checks, portable-pty included (its Windows backend is ConPTY). What does not compile is ours: the socket, the console, processes, file modes, git paths as bytes and the host helpers, all on Unix-only APIs.
- **Every step keeps Linux and macOS as they are**: their code is only moved behind a per-OS layer, a `mod imp` per OS with a fallback, as `process.rs` already does. Windows can be incomplete, never half-working: what is not ported returns `Unsupported`, and the window says so.
- **The per-OS layer** (#588): `os/` is a shared leaf with one file per area of the port, each holding a `mod imp` for `cfg(unix)` and one for every other system: `console.rs` (descriptors, standard input and output, the log taking stderr, and on Windows the console's modes, its input and its Ctrl events), `ffi.rs` (paths as bytes), `fs.rs` (file modes, metadata, links, locks, `access`, the user's ids), `process.rs` (signals, process groups, sessions, `exec`, the server's stop signals) and `socket.rs` (the local socket). On Unix an `imp` re-exports what the code used before (`std::os::unix`'s traits, `std::os::fd`, std's `UnixStream`, rustix's functions), so most callers only changed a `use` line. Where rustix's own types (`Errno`, `FlockOperation`) sat in the caller's logic, the Unix code moved into the `imp` as it was, behind a function of our own: `fs::try_lock` and `fs::locked`, `fs::writable`, `fs::uid` and `fs::gid`, `fs::set_mode` and `fs::set_file_mode` for `Permissions::from_mode`, which no Windows type can build, `process::alive`, `process::on_stop_signal` and `console::redirect_stderr`. Code whose Unix calls are woven into one module's own logic and types keeps its `imp` pair in that file instead: `client/requests/watch.rs` (whether the reader of a command's output or its input went away), `client/input.rs` and `client/probe.rs` (polling and reading the terminal), `client/window.rs` (the window's signals), `cli/config.rs` (a token typed without echo), `cli/requests.rs` (setting standard input and output aside), `highlight/limit.rs` (waiting for the painter, with its own `Fail`) and `term.rs` (a pane's foreground process group, through portable-pty). `rustix` and `signal-hook` are Unix-only dependencies: production code reaches them only inside a Unix `imp`, and only Unix-only tests use them directly. Each later step replaces one Windows `imp`. A replaced `imp` is `cfg(windows)` rather than `cfg(not(unix))`, since it calls Win32 through `windows-sys` (a Windows-only dependency, pinned with `=`); no third stub is kept for other systems, which nothing builds for (Ghostty, portable-pty).
- **What the stubs answer**: an empty list, `None`, `false` or 0 for what is read (a pid's name, a file's inode or mode, whether a process is alive), `io::ErrorKind::Unsupported` for what acts (a signal, a lock, a link, a mode set on a path, a socket, `exec`), and nothing for a builder's mode or flags (`OpenOptionsExt::mode`, `DirBuilderExt::mode`, `CommandExt::process_group`), which cannot fail. The types that cannot exist yet (`UnixStream`, `UnixListener`, `OwnedFd`) hold `Infallible`, so their methods are `match self.0 {}` and never run; a `BorrowedFd` is a token that every stub refuses (the console's input is read without one, below). None panics. Paths as bytes are the one stub that works: `as_bytes` gives the encoded bytes, and bytes that are not UTF-8 become an empty path rather than an invalid one. One stub acts as the Unix code does when it cannot: the painter's wait reports a broken worker rather than a timeout, so a file is not marked as too slow for good.
- **Stubs that guard safety must fail closed before the refusal goes**: a 0 read where the Unix code compares or checks makes the check pass. Two files' `dev` and `ino` are both 0, so `accounts::transfer` takes any two files for the same one. The socket folder's owner and mode, and a plugin manifest's, read 0 against our uid 0, so neither is ever refused, and `NOFOLLOW` is 0, so a manifest behind a link is followed. `process::alive` is false, so a worktree lock whose holder runs reads as gone. The log's rotation by inode is never seen, and every size on disk is 0. Nothing reaches them while `cli::run` refuses; each step that ports one gives a real answer or refuses (#589 for files, #596 for processes), and the refusal goes only once none is left.
- **On Windows, cornercase says so**: `cli::run` refuses every command with `Error::NotOnWindows` (cornercase does not run on Windows yet, with a link to #586) and exit status 1, before anything reaches the server, the socket or the console. `--help` and `--version` still work, since clap answers them before `run`. One check in one place rather than one per command, so nothing half-works over the socket; it goes once the socket, server and console steps land.
- **The console in raw VT mode** (#593): the window keeps its own byte decoder (see Keys and mouse), and the console hands it the bytes a Unix terminal sends. `os::console` keeps the input and output modes before `ratatui::init`, so before crossterm's raw mode and the VT processing it turns on, then sets the input to `ENABLE_VIRTUAL_TERMINAL_INPUT` and `ENABLE_EXTENDED_FLAGS` without `ENABLE_LINE_INPUT`, `ENABLE_ECHO_INPUT`, `ENABLE_PROCESSED_INPUT` and `ENABLE_QUICK_EDIT_MODE` (Quick Edit eats clicks), and the output to `ENABLE_VIRTUAL_TERMINAL_PROCESSING` and `DISABLE_NEWLINE_AUTO_RETURN`; every other bit stays. A console that refuses ends the window with `Error::Console` rather than run it without VT input. The kept modes are written back as they were rather than by turning bits back on (crossterm's `disable_raw_mode` turns line input, echo and Ctrl+C on whatever they were), and after `ratatui::restore`, so the alternate screen is left while VT processing is still on: at the end of `open`, before a restart's `exec`, in `release_screen`, and on a panic through a hook installed before ratatui's, which runs after ratatui's restore and before the message is printed. On Unix the three calls are empty: crossterm's termios raw mode is all it needs.
- **Mouse, paste, focus and keyboard modes are written as text on every OS**: crossterm's `EnableMouseCapture` goes through the legacy console API on Windows, which sets the input mode to mouse records and so turns VT input off, and its `PushKeyboardEnhancementFlags` is refused there, which stopped `execute!` halfway. `Command::write_ansi` gives the bytes `execute!` wrote on Unix, unchanged.
- **Reading waits on the console's handle, without a thread**: `console::wait_input` waits with `WaitForSingleObject` on the input handle, then takes the records that woke it with `ReadConsoleInputW`, which does not block once the handle is signalled. It keeps the characters of key-down records (and of Alt's key-up, which carries a character composed on the numpad, as libuv reads it), drops the rest (focus, size, menu and mouse records, key-ups) and waits again until its deadline. The UTF-16 becomes UTF-8, a high surrogate waiting across reads for its other half, in one queue that the probe and then the window's input thread read. Rejected: reading with `ReadFile` or `ReadConsoleW` after the wait, which blocks when only focus or size records woke it; a reader thread feeding a channel, simpler and the same on every OS, which cannot be stopped while it blocks in a console read, so after the window ends it would keep taking keys from whatever reads the console next (the `[y/N]` question when a server of another build rejects the window, or the new binary of a restart, which Windows runs as a child since it has no `exec`); and `std::io::stdin`, which on a console drops a trailing Ctrl+Z. The wait and the decoding take the console as a trait, so their tests run on made-up records; a read that fails on a handle that is gone (`ERROR_INVALID_HANDLE`, `ERROR_BROKEN_PIPE`, `ERROR_HANDLE_EOF`) ends the input as `EIO` does on Unix.
- **Resizes are polled**, since Windows has no `SIGWINCH`: a thread of the window reads `crossterm::terminal::size()` (`GetConsoleScreenBufferInfo`) every `INPUT_POLL` (100 ms) and sends the same `Event::Resize` as the Unix signal thread when it changed; a size it cannot read is skipped. The console's own size records are dropped with the others, since the thread sees the change within 100 ms.
- **Ctrl events stand in for `SIGINT`, `SIGHUP` and `SIGTERM`**: `SetConsoleCtrlHandler` turns `CTRL_C_EVENT`, `CTRL_BREAK_EVENT`, `CTRL_CLOSE_EVENT`, `CTRL_LOGOFF_EVENT` and `CTRL_SHUTDOWN_EVENT` into the window's `Signal`, which detaches it. With processed input off a typed Ctrl+C is the byte `0x03` for the pane, while a Ctrl+C sent by a program (`GenerateConsoleCtrlEvent`) and Ctrl+Break still reach the handler. Windows ends the process once the handler of a closed window returns, and the server sees the link close as a detach. An event is handled only while a window takes it, else it goes on to the next handler (Windows' default exits); the handler goes when the window's threads stop.
- **A token typed without echo** (`cli/config.rs`) turns `ENABLE_ECHO_INPUT` off, keeps line input so the token is still read as a line, and writes the mode back.
- **Checked by hand** (2026-11-02, Windows 11 26200, Windows Terminal 1.24.12741.0 and the legacy conhost), with a throwaway ignored test started in a new console: the modes went from `0x1f7`/`0x7` (conhost `0x3`) to `0x3b0`/`0xf` and back exactly; records written with `WriteConsoleInputW` came back as `aé😀`, `0x03` and an up arrow as `ESC [ A` (the console turns a key into VT when the record is written); Windows Terminal answered OSC 11, OSC 10, DA1 and a cursor report, and conhost all but OSC 10 and 11, which the probe's 1 s timeout covers; `GenerateConsoleCtrlEvent` reached the handler for Ctrl+C and Ctrl+Break; the echo went off and back. Not checked: keys, clicks and the wheel from a person, resizes, and the whole window against a server (#591, #592). The console's tests are `#[cfg(windows)]` (`os::console::tests`, `client::window::tests::console`) and were run by hand with filters until #601.
- **Tests that need Unix** are `#[cfg(unix)]`: the whole test file, with `#![cfg(unix)]` on its first line, where most of it needs Unix (file modes, symlinks, `UnixStream::pair`, rustix, the server's attached client), else the group or the test, and the test helpers only they use carry `#[cfg(unix)]` under their `#[cfg(test)]`. Never `#[cfg(all(test, unix))]`: clippy (its exemptions for tests) and `tests/layers.rs` only see code under a literal `#[cfg(test)]` as test code, and the combined form made clippy lint `worktrees::tests` as production code. `test_util`'s `Locked`, `Sleeper` and `Family` go through `os/` instead, since half the suite uses them. Tests that only run shell scripts or `/bin/sh` panes still compile on Windows. The e2e crate is `#![cfg(unix)]`. Nothing runs the suite on Windows yet (#601).
- **CI** (#587, #588): a `clippy (windows-2025)` job runs `cargo clippy --all-targets --all-features --locked -- -D warnings` with the same toolchain, Zig and cache as the other jobs, so a change that breaks the Windows build shows a failing check on its pull request. It is not yet among the checks `main`'s ruleset requires, so it does not block a merge on its own. It does not run the tests. A few lints differ on Windows and are silenced there only: `large_enum_variant` on the server's `Step` (paths are larger on Windows), `dead_code` on `Supervisor::steps` in Windows test builds and on the painter's `Fail::Timeout`, and `trivially_copy_pass_by_ref` and `unused_self` on the console's `BorrowedFd` stub. The window's `Signal` event lost its `dead_code` silence once the console's Ctrl events sent it (#593); the other way round, `unnecessary_wraps` is silenced on Unix's `console::enter_raw`, which keeps the Windows `Result`.
- **Long paths** (checked 2026-11-02): Ghostty's sources, cloned inside `target/`, hold files (its fuzz corpus) deep enough to pass Windows' `MAX_PATH` on the runner, and git cannot check them out without `core.longpaths`, so the job sets it before anything clones. A short `CARGO_TARGET_DIR` was not needed: what the linker writes stays well under the limit under the runner's checkout, and the default `target/` keeps `Swatinem/rust-cache` working without a mapping. A `target/` folder nested deep in the file system does hit it: the linker fails with `LNK1104`.
