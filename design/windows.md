# Windows

Code: `os.rs`, `os/` (`os/fs/windows.rs` for files, `os/fs/windows/acl.rs` for owners, DACLs and a process's user, `os/socket/windows.rs` for the socket), `protocol.rs` (the socket's folder and its peer), `paths.rs` (the folders), the `imp` pairs in `client/requests/watch.rs`, `client/input.rs`, `client/probe.rs`, `client/window.rs`, `cli/config.rs`, `cli/requests.rs`, `highlight/limit.rs` and `term.rs`, `cli.rs` (the refusal), `.github/workflows/ci.yml` (the `windows` job)

- **Native, not WSL** (#586): inside WSL cornercase already runs, but on another machine's files, `PATH` and agents. The port runs it on Windows itself, one step at a time in small pull requests to `main`, each one tracked under #586.
- **Possible** (spike on 2026-11-02, Windows 11, Rust 1.99.0, Zig 0.15.2, Visual Studio Build Tools 2022 with MSVC 14.44): `libghostty-vt` 0.2.2 builds for `x86_64-pc-windows-msvc`, and a `Terminal` parses VT input and formats it back as text. Every dependency checks, portable-pty included (its Windows backend is ConPTY). What does not compile is ours: the socket, the console, processes, file modes, git paths as bytes and the host helpers, all on Unix-only APIs.
- **Every step keeps Linux and macOS as they are**: their code is only moved behind a per-OS layer, a `mod imp` per OS with a fallback, as `process.rs` already does. Windows can be incomplete, never half-working: what is not ported returns `Unsupported`, and the window says so.
- **The per-OS layer** (#588): `os/` is a shared leaf with one file per area of the port, each holding a `mod imp` for `cfg(unix)` and one for every other system (`cfg(windows)` once its Windows side is real, as in `fs.rs` and `socket.rs`: cornercase builds for Unix and Windows only, so no third `imp` is kept for targets nothing builds): `console.rs` (descriptors, standard input and output, the log taking stderr), `ffi.rs` (paths as bytes), `fs.rs` (file modes, metadata, links, locks, `access`, the user's ids), `process.rs` (signals, process groups, sessions, `exec`, the server's stop signals) and `socket.rs` (the local socket). On Unix an `imp` re-exports what the code used before (`std::os::unix`'s traits, `std::os::fd`, std's `UnixStream`, rustix's functions), so most callers only changed a `use` line. Where rustix's own types (`Errno`, `FlockOperation`) sat in the caller's logic, the Unix code moved into the `imp` as it was, behind a function of our own: `fs::try_lock` and `fs::locked`, `fs::writable`, `fs::uid` and `fs::gid`, `fs::set_mode` and `fs::set_file_mode` for `Permissions::from_mode`, which no Windows type can build, `process::alive`, `process::on_stop_signal` and `console::redirect_stderr`. Code whose Unix calls are woven into one module's own logic and types keeps its `imp` pair in that file instead: `client/requests/watch.rs` (whether the reader of a command's output or its input went away), `client/input.rs` and `client/probe.rs` (polling and reading the terminal), `client/window.rs` (the window's signals), `cli/config.rs` (a token typed without echo), `cli/requests.rs` (setting standard input and output aside), `highlight/limit.rs` (waiting for the painter, with its own `Fail`) and `term.rs` (a pane's foreground process group, through portable-pty). `rustix` and `signal-hook` are Unix-only dependencies: production code reaches them only inside a Unix `imp`, and only Unix-only tests use them directly. Each later step replaces one Windows `imp`.
- **What the stubs answer**: an empty list, `None`, `false` or 0 for what is read (a pid's name, a file's inode or mode, whether a process is alive), `io::ErrorKind::Unsupported` for what acts (a signal, a lock, a link, a mode set on a path, a socket, `exec`), and nothing for a builder's mode or flags (`OpenOptionsExt::mode`, `DirBuilderExt::mode`, `CommandExt::process_group`), which cannot fail. The types that cannot exist yet (`OwnedFd`, the window's signal handle, and `UnixStream` and `UnixListener` until #591) hold `Infallible`, so their methods are `match self.0 {}` and never run; a `BorrowedFd` is a token that every stub refuses. None panics. Paths as bytes are the one stub that works: `as_bytes` gives the encoded bytes, and bytes that are not UTF-8 become an empty path rather than an invalid one. Two stubs act as the Unix code does when it cannot: the token prompt's echo stays on (as when standard input is no terminal), and the painter's wait reports a broken worker rather than a timeout, so a file is not marked as too slow for good.
- **Stubs that guard safety must fail closed before the refusal goes**: a 0 read where the Unix code compares or checks would make the check pass. #589 settled the files: an identity, an owner or a mode that Windows cannot give reads as unknown, nobody's or `0o777`, so the checks refuse (see Files: identity and listings below), and `NOFOLLOW` opens a link itself. #591 replaced the socket folder's refusal with a real check of its owner and DACL (see The socket's folder below). Still open: `process::alive` is false, so a worktree lock whose holder runs reads as gone (#596). Nothing reaches them while `cli::run` refuses, and the refusal goes only once none is left.
- **Folders** (#589, `paths.rs`): the settings in `%APPDATA%\cornercase\` (roaming, like the settings themselves), and the state (session, log, socket and lock, accounts, plugin state, run folders) in `%LOCALAPPDATA%\cornercase\`, which stays on this machine, as a server and its socket do. A debug build keeps `cornercase-dev\` and `cornercase-dev\<key>\` the same way (Client / server). Without the variable, `%USERPROFILE%\AppData\Roaming` or `Local`, then the temp folder; relative values are ignored, as on Unix. They are read from the environment, which Windows sets for every logon, rather than with `SHGetKnownFolderPath`, so `paths` stays pure over a lookup and its tests cover the Windows rule (`paths::Base`, one per OS). **`XDG_*` and `HOME` are not read on Windows**, even when set: Git Bash and MSYS2 users set them in an rc file, which a cornercase started from PowerShell, cmd, Explorer or the Start menu never sees, so honoring them would give one user two sockets, and two servers on two sessions, depending on the shell that started it, the split #355 removed on Unix. `CORNERCASE_SOCKET` still overrides everything. No earlier socket is probed (`paths::earlier_sockets` is empty: no release before 0.12.140 ran on Windows), so finding the socket never needs a uid. Limit: `secrets.json` sits next to the settings, so a roaming profile copies the tokens to the domain's profile server, as it does for `gh`'s.
- **File modes** (#589): `set_mode`, `set_file_mode` and the builders' `mode` succeed without doing anything. Every caller asks for a private file or folder (`0600`, `0700`), which the default ACL of the user's profile already gives (the user, SYSTEM and Administrators only), or for a program (`0755`, the update's binary), which Windows tells by its extension. Limit: a private file written outside the profile (`CORNERCASE_SOCKET` elsewhere, `config share` into a shared folder) takes that folder's ACL; writing an owner-only DACL was left for when it is needed, and the socket's folder is the one place that writes one (#591).
- **Files: identity and listings** (#589): std's Windows `volume_serial_number` and `file_index` are unstable (`windows_by_handle`), so `os::fs::stat` and `stat_file` read them with `GetFileInformationByHandle`, opening a path with no access rights and `FILE_FLAG_BACKUP_SEMANTICS` as std's own `metadata` does (a folder opens, and no sharing mode is in the way). Every caller that compares files goes through them and compares the device with the inode (`Stat::id`), since a file index, like an inode, is unique only within its volume: `persist::mark`, a transcript's `jsonl` reader, `log::Follower` (a rotation) and `accounts::transfer::same`. On ReFS the 64-bit index can repeat (`FileIdInfo` has 128 bits); left for later. A listing (`DirEntry::metadata`, from `FindNextFile`) has no handle, and opening every file would make a walk of `node_modules` many times slower, so `MetadataExt` answers what a listing knows: `blocks` the length in 512-byte blocks, rounded up (a worktree's size counts the length, not clusters, compression or sparse files), `mtime` and `ctime` the last write (std has no stable change time), so the changes panel's stamp moves with every write, `nlink` 1 (each hard link is counted, an overcount for a pnpm store) and `dev` 0. One device is the true answer for the walks that read it: Windows mounts a volume inside a folder only through a reparse point, which `symlink_metadata` and `DirEntry::metadata` report as a link and never as a folder, so `disk::usage` and `crosses_device` never enter one, `builds::deletable` refuses a folder that is one (no longer a folder) or is reached through one (its canonical parent leaves the worktree), and `remove_dir_all` removes a junction or a mount point without entering it.
  - **What guards safety fails closed**: `ino` is a new number on every call, so an unknown identity never equals another (`disk.rs` never reads it, since `nlink` is 1); `uid` and `gid` are `u32::MAX`, nobody's, while the user's own (`os::fs::uid`) is 0; and `mode` reads `0o777`. So the plugin manifest's `guarded` refuses every plugin (it belongs to another user) until plugins (#595) check the owner's SID and the folder's DACL instead, as the socket's folder does since #591 (`os::fs::owner_and_mode`, see The socket's folder). `PermissionsExt::mode` stays 0, so no file reads as a program to the agents' or the host helpers' searches (#599, #600). `NOFOLLOW` is `FILE_FLAG_OPEN_REPARSE_POINT`, which `custom_flags` passes on, so a manifest opened without following is the link itself, not a file, and is refused.
- **Links** (#589, `os::fs::link_to`, `links_to`, for an account's shared settings, Accounts and profiles): a symbolic link needs Developer Mode or an administrator, so a folder becomes a directory junction (a mount point reparse point, set with `FSCTL_SET_REPARSE_POINT` on a new empty folder, which needs no privilege), and a file a hard link, one file under two names, so an edit through either shows in both. Where the volume holds no hard link (FAT, or another volume) the file is copied into a temporary file beside the link, synced, and only then given the link's name with `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` (std's `rename` replaces), so a crash mid-copy leaves no partial file under the name `links::ensure` would keep, and a name taken meanwhile is left alone; the temporary file goes on any failure. `links_to` counts a symbolic link or a junction (std's `is_symlink` covers both, being name surrogates) or a file with its original's identity; a copy, or a hard link an agent broke by writing atomically, is reported as not shared, as a replaced symbolic link is on Unix. A junction leads only to a local disk, so a default home on a network share fails the account's links: the configured path must start with a drive (checked first, so a share is never reached), and so must its canonical path, which catches a folder on a drive that is a symbolic link to a share; the junction then leads to that canonical path, the one checked, so a link changed after the check cannot move it to a share. Removing an account's folder removes its junctions and hard links and leaves what they lead to (tested). Rejected: a symbolic link first and a junction when it fails, since the result would depend on Developer Mode, and `mklink /J`, a process per link through `cmd`'s quoting.
- **Locks and the rest** (#589): `try_lock` is std's `File::try_lock` and `try_lock_shared` (`LockFileEx` with `LOCKFILE_FAIL_IMMEDIATELY`). As with `flock`, a lock belongs to the open file, keeps out a second open in the same process and goes with the handle; Windows locks are mandatory, which costs nothing here, since nothing reads or writes a lock file. `writable` creates and removes a probe file, since an ACL decides and there is no `access`. `truncate` (the log starting over when it cannot rotate) goes through a second handle, since an append handle has no `FILE_WRITE_DATA` on Windows. Checked live on 2026-11-02 (Windows 11 10.0.26200, NTFS, Rust 1.99.0, without Developer Mode, so no symbolic link could be made): the tests of `os/fs/` (junctions, hard links, copies, identity across a rename, locks, removing a folder of links), `accounts::links`, `paths`, `persist`, `log` and the context readers pass.
- **The local socket** (#591, `os/socket/windows.rs`): AF_UNIX over Winsock (Windows 10 1803 and later), with the API the Unix side takes from std (`connect`, `bind`, `incoming`, `try_clone`, the read and write timeouts, `shutdown`, `Read`, `Write`), so `protocol.rs`, the server's acceptor, the client, the proxy and the browser bridge are unchanged, and the path stays a file next to the session, found, locked and removed as on Unix. Rejected: named pipes (#591), another namespace with another lifetime, no file for the folder's ACL to guard and no `CORNERCASE_SOCKET` path; and the `uds_windows` crate, which is built on `winapi`, adds `tempfile` for its pair and has no way to ask for the peer, where a wrapper of about 200 lines over `windows-sys` (already a dependency) has all three. Its answers: a socket is made with `WSA_FLAG_NO_HANDLE_INHERIT`, as std's are with `SOCK_CLOEXEC`, so the shells the server starts never hold the listener or a client (an accepted socket inherits it; tested), and Winsock is started once (`WSAStartup`, never cleaned up, as std does). The path goes in `sun_path` as UTF-8, which Windows reads as UTF-8 (a folder named `Usuário ñ` works; tested), so a path that is not Unicode is refused, and `MAX_SOCKET_PATH` stays 107 bytes; verbatim (`\\?\C:\…`) and relative paths work. `try_clone` shares one socket through an `Arc` rather than `WSADuplicateSocket` (which works too), so it acts as `dup` does: closing waits for the last clone, and a shutdown reaches every clone. `shutdown` of the read side does not wake a `recv` blocked in another thread on Windows (it does on Unix, and the server's writer counts on it to end its reader), so it also cancels the socket's pending I/O (`CancelIoEx`), and once the read side is shut a failed read is the end (`Ok(0)`), as on Unix, rather than `WSAEINTR` (which `read_exact` would retry) or `WSAESHUTDOWN`. A timeout fails with `TimedOut` where Unix says `WouldBlock`; every caller treats both as an error. A dead listener's file refuses connections (`ConnectionRefused`) and a second bind on it says `AddrInUse`, as on Unix, so the stale-file and lock logic is the same. `UnixStream::pair` has no Windows call: the test-only one binds a listener in the temp folder, connects and accepts. Checked live on 2026-11-02 (Windows 11 10.0.26200, NTFS, Rust 1.99.0): the tests of `os/socket/`, `protocol`, `client::server_process`, `client::requests`, `cli::requests` and the proxy pass.
- **The socket's folder** (#591, `os/fs/windows/acl.rs`, `os::fs::owner_and_mode`, `make_private`, `create_private_dir_all`): `protocol`'s check keeps its rules and reasons, and only what it reads moved behind `os::fs` (on Unix the same `uid`, `mode`, `DirBuilder` with `0o700` and `chmod 700` as before). On Windows the folder's owner and DACL are read from a handle that does not follow a link, and turned into what the check compares: the owner is the user's (`uid`, 0) when it is the user's SID, SYSTEM or Administrators, and nobody's otherwise; the mode is `0o700` with `0o055` when anyone else may read and `0o077` when anyone else may write (a write is any right that adds, deletes or renames inside, or changes attributes, the DACL or the owner, or a generic write or all). SYSTEM and Administrators count as the user's because they can take any file anyway (`SeTakeOwnershipPrivilege`, `SeBackupPrivilege`), as root is not counted on Unix, and because the default ACL of a profile names them, so refusing them would refuse every folder; a folder an elevated cornercase made belongs to Administrators, and is accepted. Also harmless: `CREATOR OWNER` and `OWNER RIGHTS`, which stand for the owner, and app package and capability SIDs (`S-1-15-…`), which only add a second check for sandboxed apps, every access still needing the user's own grant: the profile's `%LOCALAPPDATA%` and `%TEMP%` carry such entries (seen live). An entry counts where it reaches: the folder itself unless it is inherit-only, and the files made inside (the socket and its lock) when it is object-inherit, so an inherit-only entry for files counts and one for subfolders only does not. Entries are read in order, as Windows does, with generic rights mapped to the file rights: a right is taken away from a later allow when earlier plain denies that name Everyone (but for an allow to Anonymous, whom Everyone leaves out) or the same SID deny it everywhere the allow reaches (Windows itself splits an entry with generic rights into one for the folder and an inherit-only one for what is made inside); a deny for another group, a deny after the allow, a deny that stops at the folder while the allow reaches the files, and callback or object denies (whose conditions may not hold) take nothing away, so the reading errs towards refusing. A missing DACL, an entry of an unknown type, or a folder that cannot be read counts as anyone may write and nobody's, so the check fails closed. Making it private (the `tighten` of cornercase's own folder) writes a protected DACL with full control for the user, SYSTEM and Administrators, inherited by what is made inside; a missing folder is created with that descriptor and the user as owner in one `CreateDirectory`, as `DirBuilder` with `0o700` does, so a new folder in a shared one is private at once. What keeps other users out is the socket file's own DACL, inherited from the folder: connecting needs access to it (checked live: a socket file that grants only SYSTEM refuses the user with `WSAEACCES`); bypass traverse checking lets anyone walk through a folder they cannot list, so the folder's own entry is not what protects it.
- **The peer** (#591, `process::peer_uid`): `SIO_AF_UNIX_GETPEERPID` gives the other end's process id (the one that connected or accepted), and its token's user SID is compared with this process's: the same user reads as the user's `uid`, another user, or a process whose token cannot be opened (`ERROR_ACCESS_DENIED`), as nobody's, so `protocol::check_peer` refuses it as on Unix, and a process that cannot be found is an error, which refuses too. Kept although the folder already keeps other users out, as on Unix, where a loose umask is the reason. Limits: the id is read after the connection, so a peer that exits and leaves its id to another process of the user is taken for that process (getting that far needs access to the socket file first); a non-elevated end probably cannot open an elevated peer's token, so an elevated server and a plain window refuse each other, as root and a user do on Unix (not checked live: no elevated session was at hand).
- **Setting standard input and output aside** (#591, `cli/requests.rs`, for `cornercase requests -`): standard output and input are copied (`DuplicateHandle`) for the answers and the lines, then standard input becomes `NUL` and standard output the standard error (`SetStdHandle`), as `dup` and `dup2` do on Unix. The originals stay open until the process exits, where `dup2` closes them, so a reader of standard output sees its end only then; `requests` exits as soon as it is done. It is not covered by a unit test, since it changes the test process's own standard handles.
- **On Windows, cornercase says so**: `cli::run` refuses every command with `Error::NotOnWindows` (cornercase does not run on Windows yet, with a link to #586) and exit status 1, before anything reaches the server, the socket or the console. `--help` and `--version` still work, since clap answers them before `run`. One check in one place rather than one per command, so nothing half-works over the socket; it goes once the server and console steps land (#592, #593), the socket being ported (#591).
- **Tests that need Unix** are `#[cfg(unix)]`: the whole test file, with `#![cfg(unix)]` on its first line, where most of it needs Unix (file modes, symlinks, descriptors, rustix, the server's attached client), else the group or the test, and the test helpers only they use carry `#[cfg(unix)]` under their `#[cfg(test)]`. Never `#[cfg(all(test, unix))]`: clippy (its exemptions for tests) and `tests/layers.rs` only see code under a literal `#[cfg(test)]` as test code, and the combined form made clippy lint `worktrees::tests` as production code. `test_util`'s `Locked`, `Sleeper` and `Family` go through `os/` instead, since half the suite uses them. Tests that only run shell scripts or `/bin/sh` panes still compile on Windows. Since #591 `UnixStream::pair` exists on Windows too, for tests only (a listener on a temporary path, connected and accepted), so the tests that only need a socket run on both: `protocol`'s paths and peers, `client::server_process`, `client::requests` but its readers and inputs, `cli::requests`' streams and the proxy's slow ssh. The e2e crate is `#![cfg(unix)]`. Nothing runs the suite on Windows yet (#601).
- **CI** (#587, #588): a `clippy (windows-2025)` job runs `cargo clippy --all-targets --all-features --locked -- -D warnings` with the same toolchain, Zig and cache as the other jobs, so a change that breaks the Windows build shows a failing check on its pull request. It is not yet among the checks `main`'s ruleset requires, so it does not block a merge on its own. It does not run the tests. A few lints differ on Windows and are silenced there only: `large_enum_variant` on the server's `Step` (paths are larger on Windows), `dead_code` on the window's `Signal` event, which nothing sends until the console is ported, on `Supervisor::steps` in Windows test builds and on the painter's `Fail::Timeout`, and `trivially_copy_pass_by_ref` and `unused_self` on the console's Windows stub.
- **Long paths** (checked 2026-11-02): Ghostty's sources, cloned inside `target/`, hold files (its fuzz corpus) deep enough to pass Windows' `MAX_PATH` on the runner, and git cannot check them out without `core.longpaths`, so the job sets it before anything clones. A short `CARGO_TARGET_DIR` was not needed: what the linker writes stays well under the limit under the runner's checkout, and the default `target/` keeps `Swatinem/rust-cache` working without a mapping. A `target/` folder nested deep in the file system does hit it: the linker fails with `LNK1104`.
