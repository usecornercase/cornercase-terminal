# Commands for scripts and agents

Code: `cli.rs`, `cli/`, `cli/requests.rs`, `cli/line.rs`, `client/requests.rs`, `control.rs`, `app/control.rs`, `app/control/`, `app/events.rs`

- `clap` (derive) parses every command, the old ones included; `cornercase` alone still opens the UI and `server` is hidden. Help texts go in `about`/`help`/`after_help` attributes, never `///`. Features: `std`, `derive`, `help`, `usage`, `error-context`, `suggestions` (no colours, no wrapping). Exit status: 5 when the cornercase `--remote` reaches is older (below), 2 for wrong usage (clap's), 1 for errors and timeouts (the message says which), 3 for a partial answer (below), 4 for a `--boot` that names another run of the server (see Contract), 6 when `update` has to be done by hand (Updates › What it did, for a program). A `requires` pointing into an exclusive `#[group]` is satisfied by any member of the group (it conflicts with the one given), so `--remove-worktree` uses `conflicts_with_all` instead.
- **Another machine's server** (#476, #480): `--remote DESTINATION` or `CORNERCASE_REMOTE`, see Remote windows › Commands on another machine. `update`, `restart`, `kill-server` and `logs` run there as that machine's own command and exit with its status (`update --json` too).
- **An older cornercase there exits with 5** (#718, `cli/older.rs`, `main.rs`, `Remote::update_words`): a command that `--remote` refused because the cornercase there is older (`RemoteBehind`), or too old to have the proxy (`RemoteTooOld`), exited with 1, which is also an unreachable machine, a missing cornercase or a crash. A program that wanted to offer an update had to match the message: cornercase-gpui showed it as why the machine was lost and kept retrying. Now the command exits with 5 and prints `error: …` on stderr, as for 2 and 4. `update`, `restart`, `kill-server` and `logs` run there without checking the version, so their success proves nothing about it, and a `--remote-command` wrapper that exits with 5 passes that status through for reasons that have nothing to do with the version. `cornercase remote`'s `RemoteOlder` exits with 5 too, so the status always means "update that machine"; `RemoteNewer` ("update here") keeps 1, and a window has no `--json`.
  - **The facts with `--json`**: one line on stdout, `{"error": {"code": "older", "message": "…", "destination": "vps", "there": "0.13.19", "here": "0.13.22", "update": ["cornercase", "--remote", "vps", "update"]}}`, the socket's structured-error shape (A versioned contract) with the facts beside `code` and `message`, so a client reads both with one type. `older` is the word `machines` uses for the same state. `there` is the banner's release, or `null` from before the proxy. `update` is the command as words, built by `Remote::update_words`, from which `Remote::line` builds the line the message gives, so the two never drift. For `RemoteTooOld` the message says to run `cornercase update` there, while `update` is the same update started from here (`cornercase --remote DESTINATION update`, with `--remote-command` as given), so a program offers the second and a person may do either.
    - Rejected: the flat `{"error": "remote-behind", …}` (`error` is already the message in `requests --follow` answers and legacy errors), `host` (the value is a destination), and a pretty-printed document (a stream given `--json` is read line by line).
  - **Only with `--json`**, found in clap's matches (`cli::parse`: any subcommand's `json`, so a command that gains the flag needs nothing; a unit test fails on a `--json` flag under another id). `view`, `surface` and `requests --follow` print only JSON but take no `--json`: their stdout gets nothing, since their lines are a stream format a refusal must not pose as; `contract --json` gives the facts.
    - Rejected: always printing it (a person at a terminal would read JSON); printing it when stdout isn't a terminal (output that changes with where it goes surprises a script); a JSON line on stderr (programs show stderr as the reason); a global `--json` (clap can't have it beside the commands' own).
  - **No opt-in**, unlike 4: the refusal comes before any request, so a script that tested for exactly 1 now sees 5. `requests --follow` meets the refusal before its first line, since its lines share the link it opens first, so the command exits with 5 and a line's `status` never is.
  - **No feature and no contract change**: the server isn't involved. A client knows the status from its own binary's version.
  - **Checked**: e2e with a fake older cornercase behind the fake `ssh`; unit tests of the JSON, the `--json` lookup, the classification and the words on every system. Not checked live: a real sshd or a real older release.
- **A partial answer exits with 3** (#472): `usage`, `issue list` and `read --last-message` with several targets ask several sources and keep going when one fails. They printed their whole answer, each failed entry with its `error`, then exited 1, which a program could not tell from a command that printed nothing (no server, a refused request). An external UI's generic runner threw that output away, so its Usage and Issues views showed nothing when one agent or tracker failed. 3 means the answer is printed and complete and some entries failed, each saying why (`error` with `--json`; `issue list` also names them on stderr, `usage` and `read` in their text). With `--json`, stdout is a complete document whenever the status is 0 or 3. It is 3 even when every entry failed: a failed entry may still carry data (a tracker's cached list, a probe's previous numbers), and a client shows the document either way. `read` keeps only a target the server refused (`Error::Control`) with that target. Failing to reach the server (none running, too old, gone) fails the whole command with 1 and prints nothing, as for every command; before, each target carried `no cornercase server is running`. The CLI works out the status from the answer, so there is no protocol change. `main` turns `Error::Partial` into 3 without a message, as it turns `Error::WrongUsage` into 2; making every command's `Result<bool>` a three-way outcome was rejected (about 95 call sites for one state). Answers that report a source's failure as data keep exiting 0 (`stats`' merged pull requests, `issue sources`' `failing`, `account list --check`, `flow list`, `plugin list` and `plugin status`), since 3 would break scripts relying on that 0. A command whose single action failed keeps 1, since that failure is its answer (`plugin run`, `ports stop`). Also rejected: exiting 0 with the errors only in the JSON (hides the failure from scripts that check `$?`), a `--partial-ok` flag (more surface, still per command), and keeping 1 with each client parsing stdout after a failure. `input --follow` exits 3 when some of its lines were not sent (#478), each with its `error` line, `requests --follow` when some of its lines had a status other than 0 (#558), and `open` on a `.code-workspace` when a folder is gone or its shell could not start, or nothing was imported (#673).
- One request at a time per connection (a command sends one, after the `contract` its feature checks ask on the same connection (#557, see Remote windows › Commands on another machine); except `input --follow`, #478, and `requests --follow`, #558, which run each command over one link, sending each request after the answer to the one before; a request answered later, `wait` or `send --enter`, holds the place until it is answered, since `Requests` keeps one open request per client): `ClientMessage::Request(json)`, answered by one `ServerMessage::Response(json)`, both after the existing variants (`protocol::tests::compatibility`). JSON, not postcard, so a command and a server from different releases still work together after `cornercase update`: unknown fields are ignored (`#[serde(default)]` everywhere) and an unknown command answers an error naming the server's version (`Command::NAMES`, checked before parsing). Requests skip `Hello`'s build check. A server from before them reads `InvalidData` and answers `Rejected`, which the command turns into "too old, restart it". The connection is an ordinary client without a size, so it gets no frames and never counts as a use (it never changes the shared size). `events`, `watch` and `surface` are the requests answered by a stream (see Following events, Watching the session and Streaming a tab's terminals).
- **A follow ends when its reader is gone** (#475): every command that follows a stream (`events`, `status --follow`, `status --app --follow`, `changes list` and its `--follow`, `flow runs --follow`, `flow messages --follow`, `surface`, `view`, and since #669 `config pair`) waits in `client::requests::follow_from`, which blocked in `protocol::recv` and learned that its reader had left only when its next line met `EPIPE`: on a quiet server, hours later. A terminal that closes sends `SIGHUP`, but `ssh host cornercase events` has no terminal: killing the local `ssh` closes the channel while the remote command kept its connection and its subscription, so every reconnect of an external UI (#345) left one more, as did a local client that crashed. `follow_on` now polls the socket and standard output together before each message. `POLLHUP` or `POLLERR` on standard output (`POLLERR` for a pipe on Linux, `POLLHUP` on macOS and for a socket pair) shuts the socket down, so the server reads the end and `App::forget` drops the subscription at once, and ends the command with status 0 and no message, as a write that met `EPIPE` already did (`cli::quietly`). `requests --follow` does the same while a line waits for its answer (#558). Only a pipe or a socket is watched (`fstat`): a terminal's hangup already ends the command, a terminal that is also the input turns readable when typed into, and a file or `/dev/null` has no reader to lose (macOS refuses to poll `/dev/null`). `poll` asks for `POLLIN` too: macOS reports the hangup only through the read filter that `POLLIN` or `POLLHUP` registers, and watches nothing with no events. A standard output that turns readable instead (a socket that is also standard input, with bytes nobody reads) is no longer watched rather than polled in a loop, and that command learns at its next write, as before; so does one whose `poll` fails. `protocol::recv` reads the socket with no buffer of its own, so `poll` never waits on a message already read. Rejected: a thread that watches standard output and shuts the socket down from the side (it outlives the follow, and the loop needs a flag to tell that end from a lost server), a read timeout (it wakes a quiet command for nothing and still lags by the timeout), and a heartbeat line (it changes every stream's output). Checked on Linux 7.0 (2026-10-26): a pipe and a named FIFO give `POLLERR` and a socket pair `POLLHUP` once the reader closes, and nothing, at no CPU, while it is there; macOS 26.6 gives `POLLHUP` for a pipe and a socket pair (the issue). Not checked: a named FIFO on macOS, whose reader leaving may go unseen (the tests check only that it is not taken for gone). `logs --follow` reads the log file, not the socket, so it polls its stdout between reads of the file (`client::reader_gone_within`, with the same `watched` rules and no server to watch) and ends within 200 ms of the reader leaving (#480). `plugin windows` reads no socket either and does the same, stopping what it runs (#674, see Plugins).
- Ids come from the app's counter, so they last one server run. Every shell gets `CORNERCASE_PANE=<id>` and `CORNERCASE_SERVER=<token>` (`App::pane_env`, with `control::server_token`: the server's pid and start time; `term` knows nothing of them, `App::spawn` and `App::open_in_editor` pass them in `SpawnOptions::env`); the command sends both, and a server takes the pane as the `caller` only when the token is its own: every server numbers its panes from 1, so a pane of another server (reached through `CORNERCASE_SOCKET`) would be taken for one of its own, and `send --enter` would type into it. Inside a pane the defaults are the caller's pane, tab, workspace and project; outside, the active ones (`Here`); with `--view ID` they are what that view shows, before the caller's pane (an explicit flag beats the inherited `CORNERCASE_PANE`; view ids come from this same counter). `--tab` means the tab's agent pane, else its active one. `CORNERCASE_SOCKET` is never added to panes, except by a debug build's own server (Client / server): it would also move `config.json` and `session.json`; shells inherit the server's environment, so `cornercase` in a pane finds its server anyway.
- **Which pane started a pane** (#347): `start`, `new-tab`, `split` and `setup` sent from a pane of this server give the new pane that pane as its parent (`Term::parent`, set by `App::adopt` from the request's `caller`, which the server token already filters; `Then` carries it when `start --worktree` waits for git). From outside, or from another server's pane, there is none. A caller that no longer exists, or the pane itself, is not stored. `new-workspace`, the queue, the bots' `/new` and panes opened by hand have no caller, so no parent. The link records what ran in the caller's pane when it asked (#717, `agents::parent::By`): the agent by its conversation (`Term::resume`) once that conversation was read from that very process, else by its process (`Term::agent_pid`, looked up again when the request comes, since the watch reads every 500 ms), else the pane's shell. `App::live_parent` answers none once the pane is gone or no longer runs it: another conversation (`/clear` included), the agent exited, or, for a shell's link, an agent runs there. A process link takes the conversation once it is read (`App::learn_conversations`), so it survives what a conversation survives: a restart that resumes it, an account restart that moves it. A flow member's link is the run's (`By::Pane`, #378). Rejected: clearing `parent` when the agent exits, since it would have to tell an exit from a restart or a resume, and a conversation resumed by hand would not get its children back; comparing pids only, since restarts change the process; pane-bound links for shells, since an agent started later in that shell would get them. Scripts see it as `parent` on every pane of `status --json`, `watch` and `view` (always present, `null` without a live parent; a newer command reads `null` from an older server), the last column of `status --panes` (`-`), `(parent N)` among the pane's marks in the text tree, and `parent` on a pane's `opened` event. A parent closing changes the `watch` snapshot (`App::refreshed` hashes the live parent). All of it is additive, so `CONTRACT` and the stream versions stay 1. #717 narrows when a parent is live, not what `parent` means (the live parent, or `null`, which clients already handle), so `CONTRACT` stays 1 there too; a link that stops holding changes the `watch` snapshot through `App::refreshed`, as a parent closing does.
- **A workspace by its branch** (#132): every command that takes `--workspace ID` (`new-tab`, `setup`, `close`, `rename`, `focus`) also takes `--worktree BRANCH`, the flag `start` already had, so a script that started `start --worktree feat/x` closes it with `close --worktree feat/x --remove-worktree` instead of parsing `status` for the id. Only `start` makes the worktree when it is missing; the others only look it up. It is looked up in the project the defaults use (the caller's, else the shown one: `Report::workspace_on`), by the branch `git::branch` reads, among every workspace there and not only those with a worktree of their own, as `start --worktree` reuses whichever workspace has the branch open; so `--worktree main` finds the project's own checkout, and a plain workspace sharing it makes the name ambiguous. No match or several exit with 2 (`Error::WrongUsage`, which `main` turns into clap's `error: ` and status), listing the project's workspaces or the matching ones like `status` does, so the script or agent can pick an id. The lookup runs in the command, through a `status` request, and sends the usual request with the id: no protocol change, so it works against a server from before it, whereas a `worktree` field in the requests would be ignored by such a server (unknown fields are) and a `new-tab --worktree` would open its tab in the caller's workspace instead. The cost is a second request and the window between them, in which the workspace may close; the id request then fails as with a stale id. `--branch` as the name was rejected: `start` already says `--worktree`, and one flag for one meaning reads better in `--help`. A `--project` to look in another project was left out: `close` and `focus` already use `--project` for the item itself.
- **Nothing changes what the UI shows except `focus`, `go` and `--focus`** (with `--view` they move that view instead, and the window stays): the selection is shared by every client, so an agent opening a tab must not move everyone's view. The creation helpers (`push_tab`, `add_project`, `split_pane(.., focus)`) never touch the active indices; `add_tab`/`open_project` are the UI's focusing wrappers.
- A server that never had a window nor a `start-server` has no size and has not restored the session, so commands that create terminals refuse instead of making 1×1 ones (`area: None`), and `NO_SIZE` names `cornercase start-server` (or a window) as the way out. `start-server` (see Client / server) is the request a script sends first: an operation in `Command::NAMES`, so an older server refuses it by name and the caller knows it needs a window. Its answer goes through `refuse_or_answer` like every request, after the server took it from `App`'s outbox (`take_start`, as `take_restart`): the restore lives in `Server`, beside its `Saver`, so it is not done twice.
- **The TUI is one client among others** (the rule is in AGENTS.md): cornercase is meant to be built on, by native UIs (a Tauri or GPUI app, an editor extension), scripts, plugins and whatever the community comes up with. The server's state and actions are what is built on, and the TUI is the client that ships with them. A feature only the TUI can reach is a gap someone files later: when the rule was set, #345 tracked fourteen of them (#331 to #344), from the colour theme to the changes panel. So a feature's state goes into a snapshot or a stream and its actions into requests in the same change, additive under the contract's rules above (new operation names, optional fields), at no cost while no client uses them. What only means something inside the TUI stays out: overlays, hover, the toast, the keys menu, the compact layout and how anything is drawn. Exposing some features is a large job of its own (the issue trackers, the changes panel); such a feature may land in the TUI first, with an issue for the rest, rather than wait.
- `skills/cornercase/SKILL.md` (Agent Skills format) is what teaches agents: installed with `npx skills add usecornercase/cornercase-terminal --skill cornercase -g`, printed by `cornercase skill` (`include_str!`), never installed by cornercase (like hooks). It stays short and points to `cornercase --help`.
- A panic must not leave a command waiting forever: its timeout lives in the server too. `Requests::open` lists the clients still owed an answer; after every contained panic `Server::contain` calls `App::answer_lost_requests`, which answers `Error::Bug`'s text to each of them that has no pending entry left (the request panicked while it was handled, or `check_requests` lost the entries it had taken out). Pending ones keep waiting, so whatever answers an entry takes it out of `pending` before doing the work that can panic (`worktree_ready`, `worktree_gone`); one left behind would wait for an answer that never comes.
- Whoever reaches the socket can type into every shell; the docs page says so for sandboxed agents.
- **Tunnels** (#735, `control/tunnels.rs`, `app/control/tunnels.rs`, `cli/tunnels.rs`; `cornercase tunnels`, `tunnel open PORT`, `tunnel close PORT`, `tunnel forget PORT`, `tunnel hold PORT [--local N]`, `tunnel hold --reverse LOCAL [--there PORT]`, `tunnel close|forget --reverse PORT`, `tunnel orders`, `tunnel failed PORT REASON`; #766, #776, #786, #794; the feature is Remote windows › Tunnelling a port): `tunnels` lists what the attached windows hold (`{tunnels: [{port, local, state, error, holder, kind, direction}], windows, takers}` (`direction` is `reverse` for a reverse hold and left out for the others), `state` also `closed` for a tunnel a window remembers but closed, and `kind` `window` or `hold`; `windows` and `takers` tell a script whether `tunnel open` can work), `tunnel-open` asks every attached window and waits up to 45 s for each to settle (refused `unavailable` with no window and no program taking orders attached, `failed` with the reasons when none came up, `malformed` for port 0), `tunnel-close` waits up to 10 s (`not-found` when no holder lists the port and no program takes orders) and leaves the tunnel listed as `closed`, `tunnel-forget` removes it (same waits and refusals), and `tunnel-hold {port, local, direction}` registers a program that holds its own ssh: it is listed with `kind: "hold"`, its connection stays open as a stream, and a close or a forget ends it with `Detached` (`conflict` for a second hold on one connection, `malformed` for port or local 0); `cornercase tunnel hold PORT` is its command (`--remote` required). `tunnel-orders` registers a program with no window that takes orders as a stream (the answer is the list, counting it; then `{order, port}` lines for each open, close and forget), counted in `takers` so that `tunnel-open` asks it and waits, and `tunnel-failed {port, error}` fails the opens waiting for a program (`tunnel orders` and `tunnel failed` are their commands; see Remote windows › Tunnelling a port). `holder` is the connection id of the window, stable while it stays attached: it keeps several windows' entries apart without another name. Both go through `--remote`, like every command.
- **Machines** (#540, `control/machines.rs`, `app/control/machines.rs`, `cli/machines.rs`; `cornercase machines [add|edit|remove|update|retry]`; the links are Remote windows › Machines' links, the page Settings › Machines tab): the list, the states and the actions are on the socket, so another UI can draw its own machines page.
  - **One operation, tagged by `action`** with its content in `entry`, like `config` and `queue`: `list` (the default), `set`, `remove`, `update` and `retry`. An older server refuses `machines` by name, and an action it does not know fails to parse instead of being read as another.
  - **The window's machines are another list** (#705, #751): `cornercase remote --known` prints the machines a window on this machine offers, and `--remember` and `--forget` add and take them off, all with no server; see Remote windows › Switching machines from the window.
  - **Every action answers the whole list**: `here` (this computer's icon and version), then `machines`, the same rows as the `app` stream's. So a client never asks again after a change. It needs no window, like `status`.
  - **`set` takes the machine's name and what changes**: `new_name`, `icon` (a glyph or its name), `destination` and `folder`. It runs the form's checks with the form's texts: `malformed` for a bad value, `conflict` for a name or destination in use.
    - `create` makes it add only (`true`: a name in use is `conflict`) or edit only (`false`: an unknown name is `not-found`), and `null` does either. The CLI's `add` and `edit` send it, so `machines add vps …` never edits an existing `vps`, and `machines edit typo …` never creates `typo`.
    - Every field is serialized, `null` included, as strict fields need.
  - **`update` answers when its job ends**, with the list, or `failed` and the last line printed there, its destination named by the machine (`machines::hide_destination`, done in the job, so also when the machine went away while it ran), since refusals are logged. It is a pending request, dropped when its client leaves. It answers `conflict` while an update of that machine runs, and for a machine that is not `older`.
  - **`retry`** pokes one machine's link, or every link.
  - **`retry_at`** (#680, feature `machine-retry-at`): a row says when a link that fell tries next, in the UTC form of `seen`, so a client can draw the window's `reconnecting in 4 s`; `status`'s `machines` has it too. It is left out (`skip_serializing_if`) while the link is up or connecting and while it waits on a person, so a healthy row keeps its bytes. A feature, since its absence says something (read `state` or `error`, a person has to act: an `older` machine has no `error`) and on a server from before it says nothing. The time is on this server's clock, as `seen` is. Working it out in the client from the documented schedule was rejected: it drifts, since `retry`, a wake and a change of network try at once and the client does not hear of the failures in between. How the link holds it, and why a time that has passed stays, is in Remote windows › Machines' links › Retries.
  - **The log** has the action, the name, and whether a destination was given, never the destination itself.
  - **`cornercase machines`** prints this computer, then a line per machine with its mark, icon, name, destination, folder and state, and the reason on the line under it; `--json` prints the answer. A refusal, or an update that failed there, exits 1. `--remote` reaches it like any request.
  - **`focus-machine`** (#542; `cornercase focus --machine vps --workspace ID|--tab ID`) picks a machine's workspace or tab as the shown one, by the ids in `status`'s `machines`, as a click on its row does, and answers the `shown_remote` it made. The window then shows that tab, or the workspace's active tab, streamed from the machine (#545, see Remote windows › A machine's tab), with the machine's card until its first frame arrives (see Layout › A machine's rows and its card). A machine not listed, an id it does not have and a `pane` or anything but a workspace or a tab are `not-found` or `malformed`, and a machine that has sent nothing yet is `unavailable`; each leaves the shown workspace alone. An entry `config.json` refuses (a name or destination another entry has, a bad name) never gets a link, so it is `not-found` with its problem, here and for `machines retry` and `update`, not `unavailable`: a script that retries on `unavailable` would wait for it forever (found by the review of the whole feature, 2026-11-04). A request of its own, not a field of `focus`: an older server would drop the field and show one of its own workspaces with that id. It takes no `--view`, since the remote selection is the window's, shared by every client.
  - **Acting on a machine's workspace needs no request of its own** (#544; how the window does it is Remote windows › Acting on a machine's workspace): `cornercase machines --json` gives the destination, `status --json` the machine's `boot` and its workspaces' ids under `machines`, and `cornercase --remote DESTINATION rename --workspace ID NAME`, `close --workspace ID [--remove-worktree [--force] [--unlock]]` and `close --workspace ID --remove-worktree --check` do there what its `×` and ` ⋯ ` do here. A structured client sends that `boot` with each request, so a machine that restarted refuses with `stale-boot` instead of acting on another workspace with the same id; the CLI sends it with `--boot` (A versioned contract). So `Command::NAMES` and the contract's operations stay as they were.
  - **Folding a machine's agent needs no request of its own** (#663, #709; how the window does it is Layout › The agents section › A machine's rows fold there): the fold is kept on the machine, so a client folds one there with `cornercase --remote DESTINATION collapse --pane ID` or `expand --pane ID`, by the pane ids under the machine's entry in `status --json`, and passes that entry's `boot` with `--boot` (A versioned contract), so a machine that restarted refuses with `stale-boot` (status 4) instead of folding another agent's team.
  - **A client streams a machine's tab itself** (#545): this server does not pass on the machine's `surface` or `input`. A client that wants to draw the tab opens it on the machine with `cornercase --remote DESTINATION view|surface|input` (or the same requests over its own ssh), using the machine's `destination` from `machines` and the ids from `status`'s `machines`; `shown_remote.stream` says only how this window's stream is doing. Passing the machine's streams on through this server was left out as a large job of its own, to be an issue if a client needs it. It acts on that tab's panes there too, by the ids of its frames, with `mark`, `move-pane`, `account restart --pane` and `context`, each with `--boot` and the machine's `boot` (#723, #729), and hands its agents a prompt, a paste or a file with `send`, `input` and `paste-file`, also with `--boot` (#795), and drives the tab with `keys`, `held`, `input --follow`, `scroll`, `selection`, `split`, `ratio`, `resize`, `redraw` and `view-set`, each with `--boot` (#801).
  - **Reading a machine's diff and files needs no request of its own** (#546; how the window does it is Remote windows › The side panels on a machine): the side panels are the window's, and `status --json` gives the machine's workspaces' ids under `machines`, so a client reads them there with `cornercase --remote DESTINATION changes list|file|gap` and `files list|read|search --workspace ID`. `status.shown_remote` says which one the window shows.
- **Every machine's stats and usage** (#547; the answers are Stats and Plan usage, the asking Remote windows › Asking a machine): `stats` and `usage` take `machine`, a machine's name (any case) or `all` for this computer and every machine, so a client reads the numbers of each machine from one server. Without it both answer for this computer, byte for byte as before.
  - **A field, not a new operation**: the answers keep their shape and add `machine` or `machines`, so two more names would only repeat `stats` and `usage`. The cost is that an older server in legacy mode drops the field and answers for itself, which reads like the machine's numbers. Hence the feature `machine-usage`, which `stats --machine` and `usage --machine` require (`client::use_machine_usage`) before they send it.
  - **`all` is a value, not a flag** (a separate `every: bool` was rejected: it makes the CLI harder than `--machine all`), so no machine may be called `all` (Settings › Machines tab).
  - **Strict fields**: `machine` is skipped when absent, so the CLI's requests are as before; a structured client that sends `"machine": null` is read as leaving it out (see Contract).
  - **`--machine` and `--remote` do different things**: `--remote vps stats` asks the server there for its own numbers, `--machine vps` asks this server for its copy of them, and only the latter can sum.
  - **`cached` on `stats`** (#675; what it answers is Stats › Every machine's stats): a field, as on `usage`, not a new operation, since the answer has the shape of `stats` with `machine`. The feature `machine-usage` does not cover it: a server that has that one but not this field drops `cached` in legacy mode and asks the machine, so a read meant to come at once waits for the machine, up to its 15 s cap, without a word. Hence the feature `stats-cached`, which `stats --cached --machine` requires (`client::use_stats_cached`) in place of `machine-usage`, since a server with the new one has both; a client on the socket checks it before sending `cached`, and an older server answers it `unknown-field` in structured mode. `usage --cached --machine` needs no feature of its own because `usage` had `cached` (#341) before it had `machine`. Without `--machine` the command sends the plain request and checks nothing. `cached` is skipped when false, so a request without it, the one this server sends a machine too, stays `{"command":"stats","args":{}}` byte for byte, and a `false` one from a structured client is read as leaving it out (see Contract).
- **Starting work on a machine** (#543, `app/control/relay.rs`, `machines/send.rs`, `app/machine_links/relay.rs`, `app/machine_links/selection/awaited.rs`, `cli/args/machine.rs`, `cli/help/start.rs`; how the window does it is Remote windows › Starting work on a machine): `start`, `start-with`, `new-workspace` and `flow run` take `machine`, a machine's name (any case), and this server sends the request to that machine's server, which starts the work as its own; `cornercase start|new-workspace|flow run --machine NAME` send it (`start` with `--model`, `--mode` or `--effort` sends `start-with`).
  - **The machine's ids**: `project` and `workspace` are the machine's, as `status` lists them under `machines`, and so are the ids answered. A client that knows only this computer's project finds its pair through `paired`. Pairing them here was rejected: a request whose ids mean two things by a field would be easy to get wrong, and `focus-machine` already takes the machine's.
  - **The answer** is the machine's, with `machine` added, and its errors keep their codes (`stale-boot` among them, since the request goes with the `boot` of the machine's last snapshot). A machine not listed is `not-found`, one not linked `unavailable`. `focus` is not sent there, so what starts never takes the focus of the machine's own window.
  - **The relay** (`machines/send.rs`, `app/machine_links/relay.rs`): the request goes over a connection of its own, as a machine's stats do (`spawn_ask`), with the `boot` of the machine's last snapshot, so a machine that restarted since answers `stale-boot` and starts nothing. `machine`, `focus` and the waits are taken out: the machine never relays again.
  - **Caps** (`Send::timeout`): `start`, `flow run` and `new-workspace` with a worktree 10 minutes, the cap of removing a worktree there, since git and the project's setup run first; a plain `new-workspace` 15 s. At the cap the answer is `failed`, `it did not answer in time`, and nothing is retried; what runs there goes on, and the next snapshot shows it.
  - **The log** says `relay` with the machine's name, the verb and the project's id there, never the destination. A refusal from the machine is logged by its code and its size alone: its text may quote a URL, a path or a file there, and the client or the dialog gets it whole.
  - **`focus` here** (`app/machine_links/selection/awaited.rs`): the answer comes before the snapshot that lists what started, so the made tab (for `flow run`, the first member's, the orchestrator) or workspace is awaited and selected as the shown remote once a snapshot lists it. The awaited selection is dropped when the user picks anything else, also between the request and its answer (`Machines::picks` counts the picks, and the relay remembers the count it was sent at), when the machine's `boot` changes or it is removed, and after 30 s.
    - **Not before the machine's first snapshot**: `focus` to a machine that is linked but has not sent one is `unavailable` (`has not reported yet; try again`), since without its `boot` nothing could be awaited and `focus` would do nothing without a word. Without `focus` the request goes, with no `boot`.
    - **No view**: `focus` with `machine` and `view` is `malformed` (`relay::viewless`: `start`, `start-with`, `new-workspace`, and `flow-run` since it takes a view, #706), since the shown remote is the window's, shared by every client, as for `focus-machine`.
  - **No waiting**: `wait`, `until` and `timeout` with `machine` are `malformed`, and the CLI refuses `--wait`, `--until` and `--timeout` with `--machine` with the same text. Waiting would hold a relay open for an agent's whole turn over a connection of its own; following the work on the machine with `--remote` already does it.
  - **A field, not new operations**, as for `stats` and `usage`: an older server in legacy mode would drop `machine` and start the work here, so the feature `machine-start`, which the CLI requires (`client::use_machine_start`) before sending it. Skipped when absent, so the requests without it are as before (strict fields).
