# Commands for scripts and agents

Code: `cli.rs`, `cli/`, `client/requests.rs`, `control.rs`, `app/control.rs`, `app/control/`, `app/events.rs`

- `clap` (derive) parses every command, the old ones included; `cornercase` alone still opens the UI and `server` is hidden. Help texts go in `about`/`help`/`after_help` attributes, never `///`. Features: `std`, `derive`, `help`, `usage`, `error-context`, `suggestions` (no colours, no wrapping). Exit status: 2 for wrong usage (clap's), 1 for errors and timeouts (the message says which), 3 for a partial answer (below). A `requires` pointing into an exclusive `#[group]` is satisfied by any member of the group (it conflicts with the one given), so `--remove-worktree` uses `conflicts_with_all` instead.
- **Another machine's server** (#476): `--remote DESTINATION` or `CORNERCASE_REMOTE`, see Remote windows › Commands on another machine.
- **A partial answer exits with 3** (#472): `usage`, `issue list` and `read --last-message` with several targets ask several sources and keep going when one fails. They printed their whole answer, each failed entry with its `error`, then exited 1, which a program could not tell from a command that printed nothing (no server, a refused request). An external UI's generic runner threw that output away, so its Usage and Issues views showed nothing when one agent or tracker failed. 3 means the answer is printed and complete and some entries failed, each saying why (`error` with `--json`; `issue list` also names them on stderr, `usage` and `read` in their text). With `--json`, stdout is a complete document whenever the status is 0 or 3. It is 3 even when every entry failed: a failed entry may still carry data (a tracker's cached list, a probe's previous numbers), and a client shows the document either way. `read` keeps only a target the server refused (`Error::Control`) with that target. Failing to reach the server (none running, too old, gone) fails the whole command with 1 and prints nothing, as for every command; before, each target carried `no cornercase server is running`. The CLI works out the status from the answer, so there is no protocol change. `main` turns `Error::Partial` into 3 without a message, as it turns `Error::WrongUsage` into 2; making every command's `Result<bool>` a three-way outcome was rejected (about 95 call sites for one state). Answers that report a source's failure as data keep exiting 0 (`stats`' merged pull requests, `issue sources`' `failing`, `account list --check`, `flow list`, `plugin list` and `plugin status`), since 3 would break scripts relying on that 0. A command whose single action failed keeps 1, since that failure is its answer (`plugin run`, `ports stop`). Also rejected: exiting 0 with the errors only in the JSON (hides the failure from scripts that check `$?`), a `--partial-ok` flag (more surface, still per command), and keeping 1 with each client parsing stdout after a failure. `input --follow` exits 3 when some of its lines were not sent (#478), each with its `error` line.
- One request at a time per connection (a command sends one, except `input --follow`, #478, which sends each after the answer to the one before; a request answered later, `wait` or `send --enter`, holds the place until it is answered, since `Requests` keeps one open request per client): `ClientMessage::Request(json)`, answered by one `ServerMessage::Response(json)`, both after the existing variants (`protocol::tests::compatibility`). JSON, not postcard, so a command and a server from different releases still work together after `cornercase update`: unknown fields are ignored (`#[serde(default)]` everywhere) and an unknown command answers an error naming the server's version (`Command::NAMES`, checked before parsing). Requests skip `Hello`'s build check. A server from before them reads `InvalidData` and answers `Rejected`, which the command turns into "too old, restart it". The connection is an ordinary client without a size, so it gets no frames and never counts as a use (it never changes the shared size). `events`, `watch` and `surface` are the requests answered by a stream (see Following events, Watching the session and Streaming a tab's terminals).
- **A follow ends when its reader is gone** (#475): every command that follows a stream (`events`, `status --follow`, `status --app --follow`, `changes list` and its `--follow`, `flow runs --follow`, `flow messages --follow`, `surface`, `view`) waits in `client::requests::follow_from`, which blocked in `protocol::recv` and learned that its reader had left only when its next line met `EPIPE`: on a quiet server, hours later. A terminal that closes sends `SIGHUP`, but `ssh host cornercase events` has no terminal: killing the local `ssh` closes the channel while the remote command kept its connection and its subscription, so every reconnect of an external UI (#345) left one more, as did a local client that crashed. `follow_on` now polls the socket and standard output together before each message. `POLLHUP` or `POLLERR` on standard output (`POLLERR` for a pipe on Linux, `POLLHUP` on macOS and for a socket pair) shuts the socket down, so the server reads the end and `App::forget` drops the subscription at once, and ends the command with status 0 and no message, as a write that met `EPIPE` already did (`cli::quietly`). Only a pipe or a socket is watched (`fstat`): a terminal's hangup already ends the command, a terminal that is also the input turns readable when typed into, and a file or `/dev/null` has no reader to lose (macOS refuses to poll `/dev/null`). `poll` asks for `POLLIN` too: macOS reports the hangup only through the read filter that `POLLIN` or `POLLHUP` registers, and watches nothing with no events. A standard output that turns readable instead (a socket that is also standard input, with bytes nobody reads) is no longer watched rather than polled in a loop, and that command learns at its next write, as before; so does one whose `poll` fails. `protocol::recv` reads the socket with no buffer of its own, so `poll` never waits on a message already read. Rejected: a thread that watches standard output and shuts the socket down from the side (it outlives the follow, and the loop needs a flag to tell that end from a lost server), a read timeout (it wakes a quiet command for nothing and still lags by the timeout), and a heartbeat line (it changes every stream's output). Checked on Linux 7.0 (2026-10-26): a pipe and a named FIFO give `POLLERR` and a socket pair `POLLHUP` once the reader closes, and nothing, at no CPU, while it is there; macOS 26.6 gives `POLLHUP` for a pipe and a socket pair (the issue). Not checked: a named FIFO on macOS, whose reader leaving may go unseen (the tests check only that it is not taken for gone). `logs --follow` reads the log file, not the socket, and still notices at its next write.
- Ids come from the app's counter, so they last one server run. Every shell gets `CORNERCASE_PANE=<id>` and `CORNERCASE_SERVER=<token>` (`App::pane_env`, with `control::server_token`: the server's pid and start time; `term` knows nothing of them, `App::spawn` and `App::open_in_editor` pass them in `SpawnOptions::env`); the command sends both, and a server takes the pane as the `caller` only when the token is its own: every server numbers its panes from 1, so a pane of another server (reached through `CORNERCASE_SOCKET`) would be taken for one of its own, and `send --enter` would type into it. Inside a pane the defaults are the caller's pane, tab, workspace and project; outside, the active ones (`Here`); with `--view ID` they are what that view shows, before the caller's pane (an explicit flag beats the inherited `CORNERCASE_PANE`; view ids come from this same counter). `--tab` means the tab's agent pane, else its active one. `CORNERCASE_SOCKET` is never added to panes, except by a debug build's own server (Client / server): it would also move `config.json` and `session.json`; shells inherit the server's environment, so `cornercase` in a pane finds its server anyway.
- **Which pane started a pane** (#347): `start`, `new-tab` and `split` sent from a pane of this server give the new pane that pane as its parent (`Term::parent`, set by `App::adopt` from the request's `caller`, which the server token already filters; `Then` carries it when `start --worktree` waits for git). From outside, or from another server's pane, there is none. It is kept even when the caller is a shell, since `status` shows it; only the agents section needs a listed parent. A caller that no longer exists, or the pane itself, is not stored. `new-workspace`, the queue, the bots' `/new` and panes opened by hand have no caller, so no parent. The id is stored as it is and read through `App::live_parent`, which answers none once that pane is gone: ids are never reused within a run, so a dangling one does no harm. Scripts see it as `parent` on every pane of `status --json`, `watch` and `view` (always present, `null` without a live parent; a newer command reads `null` from an older server), the last column of `status --panes` (`-`), `(parent N)` among the pane's marks in the text tree, and `parent` on a pane's `opened` event. A parent closing changes the `watch` snapshot (`App::refreshed` hashes the live parent). All of it is additive, so `CONTRACT` and the stream versions stay 1.
- **A workspace by its branch** (#132): every command that takes `--workspace ID` (`new-tab`, `close`, `rename`, `focus`) also takes `--worktree BRANCH`, the flag `start` already had, so a script that started `start --worktree feat/x` closes it with `close --worktree feat/x --remove-worktree` instead of parsing `status` for the id. Only `start` makes the worktree when it is missing; the others only look it up. It is looked up in the project the defaults use (the caller's, else the shown one: `Report::workspace_on`), by the branch `git::branch` reads, among every workspace there and not only those with a worktree of their own, as `start --worktree` reuses whichever workspace has the branch open; so `--worktree main` finds the project's own checkout, and a plain workspace sharing it makes the name ambiguous. No match or several exit with 2 (`Error::WrongUsage`, which `main` turns into clap's `error: ` and status), listing the project's workspaces or the matching ones like `status` does, so the script or agent can pick an id. The lookup runs in the command, through a `status` request, and sends the usual request with the id: no protocol change, so it works against a server from before it, whereas a `worktree` field in the requests would be ignored by such a server (unknown fields are) and a `new-tab --worktree` would open its tab in the caller's workspace instead. The cost is a second request and the window between them, in which the workspace may close; the id request then fails as with a stale id. `--branch` as the name was rejected: `start` already says `--worktree`, and one flag for one meaning reads better in `--help`. A `--project` to look in another project was left out: `close` and `focus` already use `--project` for the item itself.
- **Nothing changes what the UI shows except `focus`, `go` and `--focus`** (with `--view` they move that view instead, and the window stays): the selection is shared by every client, so an agent opening a tab must not move everyone's view. The creation helpers (`push_tab`, `add_project`, `split_pane(.., focus)`) never touch the active indices; `add_tab`/`open_project` are the UI's focusing wrappers.
- A server that never had a window nor a `start-server` has no size and has not restored the session, so commands that create terminals refuse instead of making 1×1 ones (`area: None`), and `NO_SIZE` names `cornercase start-server` (or a window) as the way out. `start-server` (see Client / server) is the request a script sends first: an operation in `Command::NAMES`, so an older server refuses it by name and the caller knows it needs a window. Its answer goes through `refuse_or_answer` like every request, after the server took it from `App`'s outbox (`take_start`, as `take_restart`): the restore lives in `Server`, beside its `Saver`, so it is not done twice.
- **The TUI is one client among others** (the rule is in AGENTS.md): cornercase is meant to be built on, by native UIs (a Tauri or GPUI app, an editor extension), scripts, plugins and whatever the community comes up with. The server's state and actions are what is built on, and the TUI is the client that ships with them. A feature only the TUI can reach is a gap someone files later: when the rule was set, #345 tracked fourteen of them (#331 to #344), from the colour theme to the changes panel. So a feature's state goes into a snapshot or a stream and its actions into requests in the same change, additive under the contract's rules above (new operation names, optional fields), at no cost while no client uses them. What only means something inside the TUI stays out: overlays, hover, the toast, the keys menu, the compact layout and how anything is drawn. Exposing some features is a large job of its own (the issue trackers, the changes panel); such a feature may land in the TUI first, with an issue for the rest, rather than wait.
- `skills/cornercase/SKILL.md` (Agent Skills format) is what teaches agents: installed with `npx skills add usecornercase/cornercase-terminal --skill cornercase -g`, printed by `cornercase skill` (`include_str!`), never installed by cornercase (like hooks). It stays short and points to `cornercase --help`.
- A panic must not leave a command waiting forever: its timeout lives in the server too. `Requests::open` lists the clients still owed an answer; after every contained panic `Server::contain` calls `App::answer_lost_requests`, which answers `Error::Bug`'s text to each of them that has no pending entry left (the request panicked while it was handled, or `check_requests` lost the entries it had taken out). Pending ones keep waiting, so whatever answers an entry takes it out of `pending` before doing the work that can panic (`worktree_ready`, `worktree_gone`); one left behind would wait for an answer that never comes.
- Whoever reaches the socket can type into every shell; the docs page says so for sandboxed agents.
