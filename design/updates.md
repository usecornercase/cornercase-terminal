# Updates

Code: `update.rs`, `cli/update.rs`, `version.rs`, `http.rs`, `app/update_dialog.rs`

- Release builds only (`debug_assertions` off), so `cargo run` and tests never call GitHub. The server asks `releases/latest` when it starts and then every hour (`update::CHECK_EVERY`, `check_updates` in config). Unauthenticated, GitHub allows 60 requests an hour per IP, so hourly leaves room for many servers behind one address; a refused check is only logged and the next hour tries again. A newer one turns ` More ▴ ` cyan, adds **update to x.y.z** at the top of its menu (see Layout › The footer) and shows a toast; a later release found before updating replaces it and toasts again, the same one stays quiet. The dialog shows every `CHANGELOG.md` section after the running version up to the release, newest first, so a skipped release's notes are not lost: `CHANGELOG.md` is a release asset (`extra-artifacts` in `dist-workspace.toml`), downloaded only once a newer release is found (never by `cornercase update`). Releases without that asset, or a download that fails, fall back to the `## Release Notes` part of the release body. Scrolled by wheel or ↑/↓.
- Updating downloads `cornercase-<target>.tar.gz` and its `.sha256`, unpacks with `tar` next to the binary, runs `--version` on it (a binary that cannot run here never replaces a working one), then renames it over the old one. Homebrew installs (`/Cellar/`…), a folder we cannot write and unknown platforms get a command to copy instead. Homebrew's is `brew update && brew upgrade cornercase`: `brew upgrade` refreshes taps only when the last refresh is older than `HOMEBREW_AUTO_UPDATE_SECS` (a day by default), so on its own it often answered that the release cornercase had just announced was not there. The check still reads GitHub's latest release, not the tap's formula, although the formula is pushed about a minute after the release: a check that falls in that minute is rare, and trying again later fixes it.
- **`cornercase update [--check] [-y|--yes]`** (`cli::update::update`) does the same from a shell: `update::install_latest` (check, then `update` or the command for `Install::Command`, which it prints and exits 1 without running), then, if a server is running, asks `RESTART` (`--yes` skips; no terminal and no `--yes` means no restart) and sends `ClientMessage::Restart`. It never attaches. Debug builds refuse unless `CORNERCASE_RELEASES_URL` is set (the e2e tests serve a fake release and update a copy of the binary). `--check` exits 0 either way, so 1 stays for errors. A same-version server from another build (after `brew upgrade`) is left to the client's `[y/N]`.
- **Before a restart, say what stops** (`update/restart.rs`): every restart (` restart now `, settings' ` restart `, `cornercase update`, `cornercase restart`, a client rejected by another build) first lists what runs in the terminals, from a `status` `Report`: agents counted by what they do, other programs by name and place, and panes at their shell prompt and the pane that asks left out (`PaneInfo::at_prompt`; a server from before it is told apart by the program's name). The app builds the Report itself, and the commands ask the running server, the old one: requests are JSON and skip the build check, and they wait at most 1 s (`client::running_now`), so a hung server or one older than requests falls back to `update::restart::generic` and never hangs the command. The text leads with what stops, not with "your session comes back", which read as if nothing was lost (#92). The installed step's dialog has ` restart now ` and ` later `, and `Enter` still restarts (the user's call); its message is one short line and the list goes in the scrollable notes area, since the message row is three lines high and the release notes were already shown before installing. `Term::shell_in_foreground` is false for a pane started with a command (`/bin/sh -c 'exec $EDITOR …'` from the changes panel, `Term::interactive`): its program runs in the shell's pid, so comparing pids alone called an editor idle, here and for `wait --until shell`. An agent always counts as running. The dialog's list is built when it opens and every `WATCH_AGENTS_EVERY` while it is open, not on every frame, since a `status` report looks up every pane's process. `cornercase update --yes` prints the list before restarting, and it and `kill-server` print what they stopped. Waiting until no agent is working is `--when-idle` (below).
- **Restarting on demand**: the settings modal has a grey ` restart ` left of ` done ` (`ui::settings_restart`, `settings::Action::Restart`), and `cornercase restart [-y|--yes]` does it from a shell. Both take the update's path: the button opens `Overlay::Restart`, the update dialog's view with its own title and message, listing what stops and refreshed like the installed step (`Overlay::lists_running`), and ` restart now ` sets `App`'s `outbox.restart`; `take_restart` hands the server the replaced binary after an update, else `current_exe`. The command shares `cli::update::restart_if_confirmed` with `update`, so it asks the same `[y/N]` with the same list and prints what it stopped; without a server it says so and succeeds, like `kill-server`. Before, the only restart without an update was `kill-server`, which closes every window instead of bringing them back. It sits in settings, not in the footer next to ` Quit `, where a slip would stop every agent.
- **Restarting once no agent is working** (#142, `cornercase restart --when-idle`, `update --when-idle`): every restart stops every program, and an agent in the middle of a turn loses the turn (its tool call, its build) even though its conversation resumes, so whoever runs several long agents could not take a release without watching for the moment they were all idle. A script could `wait --all --until turn-over` then restart, but an agent can start a turn between the two; the server instead restarts in the same step it sees every agent stopped.
  - **A request**: `restart-when-idle` (JSON, with `timeout`) is a pending `Stage::Restart` in `App`, checked by `check_requests` after `watch_agents` like the other waits. JSON rather than a new `ClientMessage`: a server from before it refuses an unknown command by name, which the command turns into `the running cornercase server is too old to wait for its agents`, whereas a postcard variant it cannot decode gets `Rejected`, which reads as another build. A command of its own rather than a field of a `restart` request, for the reason `last-message` is one: an older server would drop the field and restart at once. The plain restart stays `ClientMessage::Restart`, which older servers understand.
  - **Stopped** is the rule of `--until turn-over` (`Condition::TurnOver`) on every pane with an agent: idle, done, waiting for you, or a Claude Code turn that is over with only a background shell left (the issue's choice: waiting means the turn needs a person anyway). Also held (`App::holding`): a launch still typing (`start`, `send --enter`, `new-tab --command`), unless it is parked on a trust prompt, which waits for a person like `waiting`; a pane running an agent that got input in the last 2 s (`INPUT_HOLDS`: a prompt typed in the window shows as busy in the status file only once the agent took it, up to a read later); and a submission the agent has not reacted to within 10 s (`Term::submitted`, the reaction check of `wait`). It fires only on a refresh that has just read every agent's state (`app.agents.watched == Some(now)`), so the decision is never older than its own step, and answers with that moment's `status` Report, which the command prints as what it stopped. Programs that are not agents (a dev server, a build) never hold it, since they may run for days and the confirmation already names them; neither does an agent cornercase cannot read. opencode never says it waits for you, so one at a permission prompt holds it until the timeout. The pane the command runs in never holds it, as `wait` refuses to wait on its own pane: an agent running `update --when-idle` in its turn would wait for itself; the restart stops it like any program.
  - **The server** takes `App`'s `outbox.restart` after any step (`Server::step`) and leaves the loop at once, so no event (a key, a `send`) is handled between the check and the restart; `shutdown` sends the answers still queued before `ServerMessage::Restart`, so the command reads its answer first. A command that gets `Restart` without an answer (someone else restarted meanwhile) counts it as done; `Shutdown` (`kill-server`) is an error, since nothing comes back by itself.
  - **Giving up**: `--timeout` answers `timed out after …: the agent in pane N has not ended its turn, so the server keeps running` (status 1); a command that is interrupted closes its connection, and `App::forget` drops its pending restart like a wait.
  - **The window says so**: while a restart is pending, every window shows `↻ restart pending until 2 agents end their turn` with a ` cancel ` button (`ui::ToastIcon::Restart`, `ui::ToastButton::Cancel`, beside ` undo `), so nobody starts a long turn by surprise. Toasts last 2 s, so this one is not timed (`Toast::lasts`): `App::show_pending_restart`, after `check_requests`, puts it back whenever no other toast shows, keeps its count current and drops it once nothing is pending; a toast that comes meanwhile (an agent needs you) shows for its own time first. ` cancel ` answers every pending restart `the restart was cancelled in the window` (status 1), since whoever sits at the window may not see the command's terminal (a script, an agent, another machine). A mark in the footer or on the settings row was rejected: the toast is where the window says things, and covering a corner of the pane while it waits is the price of nobody missing it.
  - **Confirming**: the `[y/N]` is asked when the command starts, not when the restart comes: nobody sits at a prompt for an hour, and the answer covers what the list names (the agents resume, the other programs stop). The question is `Restart it once no agent is working?`; `--yes` skips it and works without a terminal, and no terminal without `--yes` does not restart, as before. `update --when-idle` installs first, then waits, so the release is on disk however the wait ends, and the restart reaches the new binary the usual way (the clients `exec` their own replaced file).
- **From a program** (#338, `app/control/updates.rs`, `app/update_dialog.rs`, `control/app_state.rs`): the dialog's check and install are reachable by requests `update-check` and `update-install`, for a GUI's own update button; the progress now lives in `Updates` (`checking`, `answered`, `error`, `installing`, `install_error`) and not in the dialog's step, so the dialog shows `downloading…` for an install a request started and cannot start a second one.
  - `update-check` runs the hourly check's job and answers its `UpdateInfo` when it ends; it ignores `check_updates` (an explicit ask, like `cornercase update --check`) and restarts the hourly clock; a request while a check runs joins it (one call to GitHub, every client answered). A failed check answers `failed` with the reason and keeps the last release.
  - `update-install` runs the dialog's job and answers when it ends. `conflict` when no release was found, or when this cornercase cannot replace itself (Homebrew, a read-only folder: the message names the command); an install already running is joined; an installed update answers at once; a failure answers `failed` and can be asked again. A check that answers during an install does not swap the release being installed. The restart stays `restart`/`restart-when-idle`.
  - **A development build lists both as unavailable** (`Updates::enabled` false: `unavailable` with the reason `this is a development build, which never looks for updates`), the first real use of the code and of `operations[].available: false`; app tests set `enabled` to exercise them.
  - **No CLI**: `cornercase update` already checks and installs from its own process, without a server and against older ones; the requests are for programs driving the server's own flow.
- `ClientMessage::Restart` (last variant) makes the server save and send `ServerMessage::Restart`, like ` restart now `, so attached clients come back, even when `update` ran inside one of its panes (it prints everything first). A server from before it cannot decode it and answers `Rejected` (`protocol::tests::compatibility`), so `client::restart_server` falls back to `KillServer`, whose clients just exit.
- The running server keeps the old code. ` restart now ` saves the session, sends `ServerMessage::Restart(path)`, and each client `exec`s its own executable (`current_exe`, read at start; the update replaced that file), never the path in the message, which starts a new server that restores the session. A new client rejected by an older server asks `[y/N]` on the plain terminal before running `kill-server`.
- **The window stays on screen across a restart** (#144): the client used to leave the alternate screen and raw mode before its `exec`, and the new one started the server on the plain screen, then entered a blank alternate screen, so every restart showed the shell the window was started from, its scrollback, then a blank screen: it read like a crash right after an update, and every merged pull request is a release. Now, on `Ending::Restart`, the client deletes its images, pops its keyboard flags (else the terminal's stack grows by one per restart), turns mouse and bracketed paste off and leaves raw mode, but keeps the alternate screen, which is the terminal's state and survives `exec`, so the last frame stays up while the old server stops and the new one starts; the server's first frame for the new client clears and redraws it. Raw mode goes because crossterm keeps the attributes it found before entering it in the process's memory, which `exec` loses: a new client started raw would take raw for the original and leave the shell raw when it quits (`e2e::updates::a_restart_keeps_the_window_on_the_alternate_screen` runs it under a shell that prints `stty -a` after it). Mouse and paste go with it, so a mouse moved during the restart is not echoed over the frame as text; a key typed then is, until the first frame. The new process learns it comes from a restart from `CORNERCASE_RESTARTED` (`protocol::RESTARTED_ENV`), set on the `exec`: an environment variable rather than a hidden flag, so an older binary `exec`'d after a downgrade ignores it instead of clap refusing it. It then builds its `Terminal` with `ratatui::init_with_options` (raw mode and the panic hook, no `EnterAlternateScreen`: `?1049h` while already there clears the screen on some terminals). `start_server` removes the variable, so neither the server nor its shells inherit it, and only the first `open` reads it (the `[y/N]` after a rejection opens again on the plain screen). An `exec` that fails, or a new client that cannot reach or start its server, turns mouse and paste off and leaves the alternate screen before the error is printed, so the terminal is never left raw with an invisible message. A `restarting…` notice over the frozen frame was left out: the frame stays up for about as long as the server takes to restore the session. The first update to the release with this still flashes, since the old client does the `exec`; remote windows never `exec` and already reconnect on the alternate screen.
