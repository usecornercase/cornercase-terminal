# Queue

- A global queue separate from TODO: each entry carries an absolute UTC second, the client's zone, a captured prompt, agent command and mode, and a destination. It has a modal of its own, `Queue` (`Overlay::QueueList`, `queue::dialog` the model, `ui/dialog/queue_list.rs` the drawing, `app/queue_list_dialog.rs`; #896), opened from ` More ▴ ` › `queue` and from `e` in the keys menu. It was the last tab of the Issues modal until #896: scheduled agents and routines are not issues, and behind `Issues` › last tab they were hard to find. A footer button always there was rejected again, since the footer, the compact menu and the icon bar already hold seven buttons (a count shows only while entries wait for room, see [Waiting for room](queue/free.md)); ` More ▴ ` is two clicks, as `Issues` › `Queue` was, works in every layout, and opens with or without a project. A ` queue ` button inside the Issues modal was left out: it would push ` schedule ` out of a narrow button row sooner, and a save from ` schedule ` already lands on the queue. The modal is the Issues modal's size (`issues_area`), with its filter field, list, hint and button row. It lists every project's entries, since the queue is global, and none of a bot's (#888: a bot's routines are in the bot, see [Bot routines](bots/routines.md)), whose count stays as a dim line at the end; each row is the local time, the label, and `status · agent · place`, the status coloured (failed red, missed yellow, started green), built by `App::queued_rows` and handed to the model (`queue::dialog::Dialog::set`) on every refresh and before each key or click, since the model is pure. **Order and groups** (`queue::dialog::arranged`): unpaused routines and pending or starting one-off entries first, by their next time, since what starts next is what the list is opened for; then paused routines; then one-off entries that ran, newest first. A routine's runs are right under it, indented, newest first, and never anywhere else; a run shows its status where a row shows its name, since ten rows repeating the routine's name under it would be noise, and the routine's row right above carries it. A run whose routine is gone is listed as a one-off that ran. **Folding**: a routine with runs shows `▾`; a click on the mark, or `←` on the routine or one of its runs, folds the group (`▸`, the meta ending with ` · N runs`, drawn after the cut so it always shows), and a click or `→` unfolds it. Groups start unfolded, since the issue asks for the runs listed below with a way to tame a long history. The folds live in `QueueRuntime::folded`, in memory for the server's run and shared by every window like other overlay state, not in `session.json` (a restart unfolds them all); typing a filter ignores them, showing a routine when it or one of its runs matches. **The selection is an entry id** (`list::Chosen`, shared with the bot routines dialog), not an index as in the Issues list, so a run that appears above the selected row does not move the selection to another entry; opened with no entry chosen, the modal records the row it shows first (`Dialog::set`), so the highlight stays on it too. Its buttons follow the selected row: `new`, `start now` (pending, failed or missed, or a routine), `pause` or `resume` (a routine), `remove` (not starting), `clear started` (when something started, the first left out of a narrow row) and `done`, not ` cancel `, since the modal is no longer a step of something else; `Enter` or a click edits a pending, failed or missed entry, opens a started one's pane and closes the modal (once its pane is gone, or for a removed run or a failed or missed run, it opens what the run did: see Results), and does nothing while it starts. Typing filters. The schedule form keeps the dialog it was opened from (`QueueRuntime::back`) and goes back to it when it closes, with the list as it was; after a save the saved entry is selected, and a filter it does not match is cleared, since a save that leaves its entry out of sight would read as lost. From an issue's ` schedule `, cancel, `Esc` or a click outside go back to the Issues modal as it was, and a save opens the queue modal with the new entry selected, so a scheduled issue shows up in the list. Nothing on the ` Issues ` button says that entries are pending (a dot was offered and declined); toasts and notifications say when one starts or fails. Rows are chronological with insertion order for ties. Editing prompt or time preserves the captured agent and mode, including a removed custom choice; changing those choices captures the current command. Pending, failed and missed entries can be edited or started now; removing pending work cancels it. Started entries remain until cleared and link to their pane in the same server, with its token guarding against id reuse after a restart. Removing history does not stop an agent. `remove` and `clear started` remove at once and offer ` undo ` in the toast for 6 s, as the TODO panel does, instead of confirming. No concurrency limit: what holds an entry back is a time, or the memory it needs ([Waiting for room](queue/free.md)).
- **Time**: Jiff parses client-local times (`14:30`, tomorrow and an explicit date), delays, and daylight saving transitions. The terminal's `Hello` carries its IANA zone or fixed offset, preserved by the remote proxy; the browser sends its own zone. A form captures the opening client's zone rather than changing under another client. Commands send their client's zone with each add/edit request. Ambiguous and nonexistent local times fail rather than guessing. A bare clock time is compared with the local clock before it is resolved, so `02:30` asked at 10:00 on the day the clocks go back means tomorrow's 02:30 instead of failing on today's repeated hour. A system zone without an IANA name (a copied `/etc/localtime`) falls back to `TZ` (an IANA name, a zoneinfo path or a POSIX rule such as `EST5EDT,M3.2.0,M11.1.0`), then to `/etc/timezone`, and only then to today's fixed offset, which would put a time chosen across a daylight saving change an hour off. Jiff bundles the time zone database (`tzdb-bundle-always`, about 200 KB), used when the server has no `/usr/share/zoneinfo`, so a zone name a client sends is never rejected for want of the system's files. `claude reset` and `codex reset` run the existing usage probe once while preparing an entry and capture the future `session (5h)` reset, with no account credentials read by cornercase and no polling. Missing, expired and unsupported resets fail visibly.
- **Destinations** use the project's path and, for a workspace, its path and optional custom name. Its id and server token identify it exactly during that server run; after restart a unique path/name match restores the destination. Closed, renamed or ambiguous restored destinations fail instead of falling back to whatever is active. Root starts use a workspace in the root, making one when absent. A new worktree uses its recorded branch. Issue URLs and keys are resolved by the existing tracker clients while adding (`issues::locate`, which moved out of the queue when `start --issue`, `flow run --issue` and `issue read` began to share it, #340); neither tokens nor tracker connections are saved in the queue. A URL names its tracker by its host, and the issue is then fetched through the connection of the project's tracker: GitHub and GitLab by its number in the project's own repository, the others by key. The URL found must name the same repository, site or workspace up to the issue's key (`issues::locate::place`; GitLab's `/-/work_items/N` counts as `/-/issues/N`), so a URL of another repository, Jira site, Plane workspace or Asana task fails instead of fetching the connected tracker's issue with the same key and starting it in the wrong worktree. A bare key goes to the only tracker that can read it: `#7` to the project's repository tracker (GitLab when it is connected and a remote in `.git/config` is on its server, else GitHub in a git repository), a number to that tracker or Shortcut, `sc-` to Shortcut, other keys to Linear, Jira, Plane or Asana (an ID-field key such as `ENG-42` looks the same in all four); when two can, `--source` is required rather than one being guessed. A bare number is never taken for Asana, whose task ids are 16-digit numbers: `--source asana` reads one by gid. An `app.asana.com` URL names Asana, and its task gid is the segment after `task` (`/1/<workspace>/project/<p>/task/<t>`, `/1/<workspace>/task/<t>`) or the third of the old `/0/<project>/<task>[/f]`; a URL with no task gid is an error. Asana compares the task gid only (`issues::locate::same_issue`), since Asana has moved its links between formats and a pasted one may differ from the `permalink_url` the API returns, so one of another task is refused as for the other trackers. `Issue` has no gid field (its key is the ID-field value when the project has one); the gid is read from the permalink, and `Issue::number`, which is 0 when a gid does not fit a `u64`, is not relied on. Editing an entry's issue moves its worktree branch to the new issue's (named by the `issue_branch` template, see Issues), unless `--worktree` names one. UI scheduling uses the issue already selected and the configured prompt template. **A destination can also be a bot** (`Place.bot`, #846; the window reaches it only from the bot's routines dialog, never from Where, #888): the run is a new conversation of the bot that answers in its chat, ends `answered` (with the run's `session`) and makes no worktree; the time, missed, pause, `start now`, history and undo rules are the same (see [Bot routines](bots/routines.md)).
- **Execution** reuses control's `Start`, worktree jobs and `Launch`, with internal clients in a separate range from terminal and chat app clients. Replies update the queue rather than going to a socket. Queued launches always accept folder trust questions, explicitly shown in the form; immediate starts still use `accept_trust_prompts`. They submit the captured prompt automatically rather than following the immediate issue start's `submit` setting, since the schedule form already lets the user edit it and waiting for Enter would stall unattended work; an explicit control request can still retain a draft. They keep the current focus. A launch failure or missing executable records the reason, with a toast and notification. An in-flight start is marked `starting` and written before creating terminals or worktrees; restore converts it to an interrupted failure so it cannot silently start twice. Starting entries cannot be edited or removed. The queue becomes ready once the server has a size and a restored session: from a window, or from `cornercase start-server` (`App::set_queue_area`, since `follow`, which sets it otherwise, only runs when a window is drawn); a stopped server or sleeping machine is not woken by an entry. A server is started by a window (`cornercase`, or the proxy of `cornercase remote`) or by `start-server`, and it keeps the last size after every window detaches, so the queue goes on running unattended. Restoring the session headless on every start when `queue.json` has entries, as a review suggested, stays rejected: the session would be restored before the first window's `Hello` on every start, with a size and colours nobody chose. `start-server` restores headless only when asked, with a size it was given or its 160×48 (see Client / server). A restart with no window attached leaves no server at all, which the queue does not change.
- **Accounts per entry** (#379): `Task::accounts` (`{agent: account}`, `""` the agent's own login; empty, left out of `queue.json` so a file without accounts is byte for byte as before, is the selection when it runs) is chosen in the form's Account combo or with `--account AGENT=ACCOUNT` (the `accounts` field, feature `account-switch`, since an older server would drop it) and checked when added or edited (`requested_accounts`: an unknown agent or account is `not-found` and nothing is added). `edit` merges by agent, so `{}` keeps them; an agent cannot be set back to "the one in use when it runs" by a request or the CLI, only by adding the entry again. When it runs, `Start.accounts` goes over the selection, and an account removed before then fails the entry with the reason, with no tab. `queue list` text adds ` · claude: home`. See Accounts and profiles.
- **In the app feed** (#338): the entries are the `queue` of `status --app`, as `queue list` has them (see Commands for scripts and agents, Following the rest of the app).
- **Clock and persistence**: `App::refresh_at` and `tick_at` take wall time separately from `Instant`, so scheduler tests advance it without sleeps. A due entry more than 600 seconds late becomes missed; exactly 600 seconds is within grace. The next due entry participates in `tick` after a window size exists, avoiding zero-duration wakeups before the session opens. `queue.json` beside `session.json` has its own version and durable ids; another session filename uses its stem plus `.queue.json` to isolate servers sharing a socket directory. Its `persist::Saver` is observed with the other independent stores and flushed on shutdown. Missing, corrupt or other-version files yield an empty queue. The saver starts from a valid file's original state, so restored missed/interrupted transitions are saved; an unreadable file uses the empty in-memory baseline and is not overwritten until an actual edit. Historical started links carry the original server token and never resolve against another server.
- **Forms and commands**: the schedule form asks the kind of time first (`at`, `tomorrow at`, `on`, `in`, `Claude reset`, `Codex reset`), then shows only that kind's values on the row below (a clock, a date and a clock, an amount and a unit, or nothing for a plan reset) and turns them into the same text the commands take (`14:30`, `tomorrow 9:00`, `2026-10-20 09:00`, `in 2h`, `claude reset`), so the server and the CLI did not change. A first version had one free text field for every format, with the formats listed in its label and reset buttons under it, and the place, agent and mode were rows that cycled on each click, with a `○`/`✓` toggle for a new worktree: what a click would pick next was invisible. Place, agent, mode and the delay's unit are comboboxes (see Dialogs), and `Open in` (`new tab` or `new worktree`) replaces the toggle; it is a choice only in a repository root, and the branch field shows only for a new worktree. A blank row separates the fields (the kind of time and its values stay together, as one field), since packed rows read as one block, and `Open in` keeps its row, saying `new tab` in grey where nothing else is possible, so the form keeps its height when the place changes. Field keys remain confined to that modal; `Tab` and `Shift+Tab` move through the shown controls, and `Enter` saves unless a list is open or the prompt has the focus. **The prompt is a multi-line field** (#896): `Enter` breaks the line there, the bot form's rule for its About field, and saves from every other field; a paste keeps its line breaks, as a prompt from a template or `--prompt` does. This changes a habit (typing a prompt and pressing `Enter` saved it), so a dim hint on the label row says `enter breaks the line · tab moves on` while the prompt has the focus. **The form's height follows the window, not the text**: the prompt has 3 rows in a 24-row window, where the form keeps its 23 rows, and one more for each row the window has past that, up to 8 rows (a 28-row form) from 30 rows up; every row below the prompt moves down with it (`ui::queue_form::at`). Growing with the text was rejected: a centred dialog would jump as lines are typed, and its area would depend on the text, which `Overlay::area`, clicks and drags would all have to follow. The wheel over the prompt scrolls it (`Form::scroll_prompt`), and ` ↑ n more ` on the label row and ` ↓ n more ` on the blank row under the field say how many lines are hidden, the marks of the comboboxes (`ui::combo::more`), since the app has no scrollbar anywhere. A click lands on the line it shows: the first shown line is `ui::queue_form::top`, the prompt's scroll clamped to its lines at the field's width, shared by drawing, the click and a drag, so a window made narrower cannot leave them disagreeing. Editing an entry reveals the end of its prompt; an issue's ` schedule ` reads it from the top. In a window shorter than the form its error note takes the rows right above the buttons, over the trust notice. The issues browser drops ` schedule ` before anything else when its button row is too narrow, so ` start ` is never cut, and `Enter` on an issue always starts it, whatever button was pressed before. The issues browser's schedule action preserves its agent and place pickers. `queue add`, `list`, `edit`, `remove`, `clear-started`, `restore` and `run` use the existing JSON request channel, including asynchronous preparation for issue reads and plan probes. Adds print the queue id; list exposes pending, started, failed and missed entries as text or JSON. `queue add` without `--at`, or without `--prompt` or `--issue`, is wrong usage (exit 2) before the server is asked. The text list reads each entry's fields leniently, so a state or field added by a newer server prints instead of failing. Editing keeps unspecified properties. The Mode list opens on the mode Settings chose, an entry captured without a mode reopens on `default`, and `default` is no mode arguments (see Agents › The mode `default`).
- **An entry's name** (`Task::label`, `--name`, the request's `label`; #774) is what the user wrote, kept as written (control characters dropped, spaces collapsed), an issue's `#482 <title>` (whole, as before), or else the prompt's (`queue::prompt_name`): its first line with any text, control characters as spaces, cut after its last whole word within 40 characters with `…` (`text::first_words`; 40 is an issue's workspace name, `issues::workspace_name`), and cut inside the word when the words that fit are under half of that, so a URL after `Fix` does not leave `Fix…`. It used to be the whole first line: a prompt of one paragraph named the run's tab with the paragraph, which `status` printed on one line and `status --json` gave as the tab's `name` and `custom_name`, and the queue modal, `queue list`, the notices and the chat apps carried it too. The name is cut where it is made, not where it is shown: cutting only the tab's name, or only `status`' text, was rejected, since the other places and every client would still get the paragraph. The whole prompt stays in `prompt` (`queue list --json`, `queue show --json`, the form). The routine's branch is still the name's slug (32 characters cut at a word); a 40-character name usually leaves it as it was, and a name cut before a URL only shortens the branch of the runs to come. A name older releases made (the whole first line) is cut the same way once, when a `queue.json` written before this release is loaded (`rename_older`, gated by `Saved::names`, a marker every save writes, since the file's version cannot say it: an other-version file loads as empty), so a routine made before needs no edit; in such a file a name written equal to the prompt's whole first line cannot be told from a derived one and is cut too, and a file this release wrote keeps it. The edit form treats the name as written only when it differs from `prompt_name` of the prompt, so editing the prompt of an entry nobody named renames it. The queue modal's filter also matches the prompt's first line with text (`queue::dialog::Row::first_line`, the text the name used to hold), so a word past the cut still finds its entry; the whole prompt would make every issue entry match its template's words. Tabs already open keep their names. A client cannot tell a written name from a derived one without `prompt_name`'s rule (the form and the website's simulation copy it); exposing it as a field of `queue list` is a follow-up. Checked with tests and by hand in a dev build (the Queue tab, the form, the load, `status`) on 2026-11-12.

- **Undo through requests** (#463): `remove` and `clear-started` answer the removed `entries` and an `undo` number; an empty clear answers only an empty `entries` array and consumes no history. `restore` takes that number and answers the entries put back. The queue runtime keeps the last 16 nonempty request removals until the server stops, separately from the panel's six-second toast, so a request cannot replace its undo and panel removals cannot evict request history. Undo numbers are opaque hashes of the server boot and a removal counter, kept within JavaScript's exactly representable 53-bit integers so another UI can round-trip the JSON number. This separates removals across restarts without persisting their prompts or adding another CLI argument. A number is consumed once; unknown, consumed and evicted numbers are `not-found`. Restoration uses the original ids and every captured task and state field, sorted by time and insertion id, skipping ids already present. Restoring pending work makes it eligible for the normal scheduler again, including its lateness rules; restoring started history never starts another agent. The additive `queue-undo` contract feature advertises both actions and the removal answer; the CLI checks it before any of the three, since an older server would otherwise remove an entry without an undo. Text removals print only the number, nothing for an empty clear; `--json` prints the complete answer.
