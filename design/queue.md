# Queue

Code: `queue/`, `git/worktree/fresh.rs`, `app/routine_cleanup.rs`, `issues/browser.rs`, `ui/dialog/queue.rs`, `app/queue_panel.rs`, `app/queue_dialog.rs`, `app/control/queue/`

- A global queue separate from TODO: each entry carries an absolute UTC second, the client's zone, a captured prompt, agent command and mode, and a destination. It is the last tab of the Issues modal, `Queue` (`issues::browser::Tab::Queue`, always appended after the configured trackers), rather than a side panel with a footer button of its own: the footer, the compact menu and the icon bar already held seven buttons, the `schedule` action already sat beside `start` in that modal, and the modal's tabs, filter field, list, hint and button row fit a list of entries. The tab lists every project's entries, not only the modal's project, since the queue is global; each row is the local time, the label, and `status · agent · place`, the status coloured (failed red, missed yellow, started green), built by `App::queued_rows` and handed to the browser (`Browser::queued`) on every refresh and before each key or click, since the browser is a pure model. Its buttons follow the selected entry: `new`, `start now` (pending, failed or missed), `remove` (not starting), `clear started` (when something started) and `cancel`; `Enter` or a click edits a pending, failed or missed entry, opens a started one's pane and closes the modal, and does nothing while it starts. Typing filters. The schedule form keeps the browser it was opened from (`QueueRuntime::back`) and goes back to it when it closes: as it was on cancel, `Esc` or a click outside, and on the `Queue` tab after a save, so a scheduled issue shows up in the list. Nothing on the ` Issues ` button says that entries are pending (a dot was offered and declined); toasts and notifications say when one starts or fails. Without an open project the modal, and so the queue, cannot be opened, but nothing can be scheduled then either. Rows are chronological with insertion order for ties. Editing prompt or time preserves the captured agent and mode, including a removed custom choice; changing those choices captures the current command. Pending, failed and missed entries can be edited or started now; removing pending work cancels it. Started entries remain until cleared and link to their pane in the same server, with its token guarding against id reuse after a restart. Removing history does not stop an agent. `remove` and `clear started` remove at once and offer ` undo ` in the toast for 6 s, as the TODO panel does, instead of confirming. No concurrency limit.
- **Time**: Jiff parses client-local times (`14:30`, tomorrow and an explicit date), delays, and daylight saving transitions. The terminal's `Hello` carries its IANA zone or fixed offset, preserved by the remote proxy; the browser sends its own zone. A form captures the opening client's zone rather than changing under another client. Commands send their client's zone with each add/edit request. Ambiguous and nonexistent local times fail rather than guessing. A bare clock time is compared with the local clock before it is resolved, so `02:30` asked at 10:00 on the day the clocks go back means tomorrow's 02:30 instead of failing on today's repeated hour. A system zone without an IANA name (a copied `/etc/localtime`) falls back to `TZ` (an IANA name, a zoneinfo path or a POSIX rule such as `EST5EDT,M3.2.0,M11.1.0`), then to `/etc/timezone`, and only then to today's fixed offset, which would put a time chosen across a daylight saving change an hour off. Jiff bundles the time zone database (`tzdb-bundle-always`, about 200 KB), used when the server has no `/usr/share/zoneinfo`, so a zone name a client sends is never rejected for want of the system's files. `claude reset` and `codex reset` run the existing usage probe once while preparing an entry and capture the future `session (5h)` reset, with no account credentials read by cornercase and no polling. Missing, expired and unsupported resets fail visibly.
- **Destinations** use the project's path and, for a workspace, its path and optional custom name. Its id and server token identify it exactly during that server run; after restart a unique path/name match restores the destination. Closed, renamed or ambiguous restored destinations fail instead of falling back to whatever is active. Root starts use a workspace in the root, making one when absent. A new worktree uses its recorded branch. Issue URLs and keys are resolved by the existing tracker clients while adding (`issues::locate`, which moved out of the queue when `start --issue`, `flow run --issue` and `issue read` began to share it, #340); neither tokens nor tracker connections are saved in the queue. A URL names its tracker by its host, and the issue is then fetched through the connection of the project's tracker: GitHub and GitLab by its number in the project's own repository, the others by key. The URL found must name the same repository, site or workspace up to the issue's key (`issues::locate::place`; GitLab's `/-/work_items/N` counts as `/-/issues/N`), so a URL of another repository, Jira site, Plane workspace or Asana task fails instead of fetching the connected tracker's issue with the same key and starting it in the wrong worktree. A bare key goes to the only tracker that can read it: `#7` to the project's repository tracker (GitLab when it is connected and a remote in `.git/config` is on its server, else GitHub in a git repository), a number to that tracker or Shortcut, `sc-` to Shortcut, other keys to Linear, Jira, Plane or Asana (an ID-field key such as `ENG-42` looks the same in all four); when two can, `--source` is required rather than one being guessed. A bare number is never taken for Asana, whose task ids are 16-digit numbers: `--source asana` reads one by gid. An `app.asana.com` URL names Asana, and its task gid is the segment after `task` (`/1/<workspace>/project/<p>/task/<t>`, `/1/<workspace>/task/<t>`) or the third of the old `/0/<project>/<task>[/f]`; a URL with no task gid is an error. Asana compares the task gid only (`issues::locate::same_issue`), since Asana has moved its links between formats and a pasted one may differ from the `permalink_url` the API returns, so one of another task is refused as for the other trackers. `Issue` has no gid field (its key is the ID-field value when the project has one); the gid is read from the permalink, and `Issue::number`, which is 0 when a gid does not fit a `u64`, is not relied on. Editing an entry's issue moves its worktree branch to the new issue's (named by the `issue_branch` template, see Issues), unless `--worktree` names one. UI scheduling uses the issue already selected and the configured prompt template.
- **Execution** reuses control's `Start`, worktree jobs and `Launch`, with internal clients in a separate range from terminal and chat app clients. Replies update the queue rather than going to a socket. Queued launches always accept folder trust questions, explicitly shown in the form; immediate starts still use `accept_trust_prompts`. They submit the captured prompt automatically rather than following the immediate issue start's `submit` setting, since the schedule form already lets the user edit it and waiting for Enter would stall unattended work; an explicit control request can still retain a draft. They keep the current focus. A launch failure or missing executable records the reason, with a toast and notification. An in-flight start is marked `starting` and written before creating terminals or worktrees; restore converts it to an interrupted failure so it cannot silently start twice. Starting entries cannot be edited or removed. The queue becomes ready once the server has a size and a restored session: from a window, or from `cornercase start-server` (`App::set_queue_area`, since `follow`, which sets it otherwise, only runs when a window is drawn); a stopped server or sleeping machine is not woken by an entry. A server is started by a window (`cornercase`, or the proxy of `cornercase remote`) or by `start-server`, and it keeps the last size after every window detaches, so the queue goes on running unattended. Restoring the session headless on every start when `queue.json` has entries, as a review suggested, stays rejected: the session would be restored before the first window's `Hello` on every start, with a size and colours nobody chose. `start-server` restores headless only when asked, with a size it was given or its 160×48 (see Client / server). A restart with no window attached leaves no server at all, which the queue does not change.
- **Accounts per entry** (#379): `Task::accounts` (`{agent: account}`, `""` the agent's own login; empty, left out of `queue.json` so a file without accounts is byte for byte as before, is the selection when it runs) is chosen in the form's Account combo or with `--account AGENT=ACCOUNT` (the `accounts` field, feature `account-switch`, since an older server would drop it) and checked when added or edited (`requested_accounts`: an unknown agent or account is `not-found` and nothing is added). `edit` merges by agent, so `{}` keeps them; an agent cannot be set back to "the one in use when it runs" by a request or the CLI, only by adding the entry again. When it runs, `Start.accounts` goes over the selection, and an account removed before then fails the entry with the reason, with no tab. `queue list` text adds ` · claude: home`. See Accounts and profiles.
- **In the app feed** (#338): the entries are the `queue` of `status --app`, as `queue list` has them (see Commands for scripts and agents, Following the rest of the app).
- **Clock and persistence**: `App::refresh_at` and `tick_at` take wall time separately from `Instant`, so scheduler tests advance it without sleeps. A due entry more than 600 seconds late becomes missed; exactly 600 seconds is within grace. The next due entry participates in `tick` after a window size exists, avoiding zero-duration wakeups before the session opens. `queue.json` beside `session.json` has its own version and durable ids; another session filename uses its stem plus `.queue.json` to isolate servers sharing a socket directory. Its `persist::Saver` is observed with the other independent stores and flushed on shutdown. Missing, corrupt or other-version files yield an empty queue. The saver starts from a valid file's original state, so restored missed/interrupted transitions are saved; an unreadable file uses the empty in-memory baseline and is not overwritten until an actual edit. Historical started links carry the original server token and never resolve against another server.
- **Forms and commands**: the schedule form asks the kind of time first (`at`, `tomorrow at`, `on`, `in`, `Claude reset`, `Codex reset`), then shows only that kind's values on the row below (a clock, a date and a clock, an amount and a unit, or nothing for a plan reset) and turns them into the same text the commands take (`14:30`, `tomorrow 9:00`, `2026-10-20 09:00`, `in 2h`, `claude reset`), so the server and the CLI did not change. A first version had one free text field for every format, with the formats listed in its label and reset buttons under it, and the place, agent and mode were rows that cycled on each click, with a `○`/`✓` toggle for a new worktree: what a click would pick next was invisible. Place, agent, mode and the delay's unit are comboboxes (see Dialogs), and `Open in` (`new tab` or `new worktree`) replaces the toggle; it is a choice only in a repository root, and the branch field shows only for a new worktree. A blank row separates the fields (the kind of time and its values stay together, as one field), since packed rows read as one block, and `Open in` keeps its row, saying `new tab` in grey where nothing else is possible, so the form (23 rows) keeps its height when the place changes. Field keys remain confined to that modal; `Tab` and `Shift+Tab` move through the shown controls, `Enter` saves unless a list is open. A prompt from a template or `--prompt` keeps its line breaks (one row each); typing and pasting still turn line breaks into spaces. A click in a scrolled prompt lands on the line it shows (`ui::queue_form::first_line`, shared by drawing and the click). In a window shorter than the form's 23 rows its error note takes the rows right above the buttons, over the trust notice. The issues browser drops ` schedule ` before anything else when its button row is too narrow, so ` start ` is never cut, and `Enter` on an issue always starts it, whatever button was pressed before. The issues browser's schedule action preserves its agent and place pickers. `queue add`, `list`, `edit`, `remove`, `clear-started`, `restore` and `run` use the existing JSON request channel, including asynchronous preparation for issue reads and plan probes. Adds print the queue id; list exposes pending, started, failed and missed entries as text or JSON. `queue add` without `--at`, or without `--prompt` or `--issue`, is wrong usage (exit 2) before the server is asked. The text list reads each entry's fields leniently, so a state or field added by a newer server prints instead of failing. Editing keeps unspecified properties.

- **Undo through requests** (#463): `remove` and `clear-started` answer the removed `entries` and an `undo` number; an empty clear answers only an empty `entries` array and consumes no history. `restore` takes that number and answers the entries put back. The queue runtime keeps the last 16 nonempty request removals until the server stops, separately from the panel's six-second toast, so a request cannot replace its undo and panel removals cannot evict request history. Undo numbers are opaque hashes of the server boot and a removal counter, kept within JavaScript's exactly representable 53-bit integers so another UI can round-trip the JSON number. This separates removals across restarts without persisting their prompts or adding another CLI argument. A number is consumed once; unknown, consumed and evicted numbers are `not-found`. Restoration uses the original ids and every captured task and state field, sorted by time and insertion id, skipping ids already present. Restoring pending work makes it eligible for the normal scheduler again, including its lateness rules; restoring started history never starts another agent. The additive `queue-undo` contract feature advertises both actions and the removal answer; the CLI checks it before any of the three, since an older server would otherwise remove an entry without an undo. Text removals print only the number, nothing for an empty clear; `--json` prints the complete answer.

## Routines (#653)

- **A routine is an entry that repeats**, not a new store: `Task::repeat` is set, its state is always `pending` and its `at` is its next occurrence. The form, places, clock, `queue.json`, undo and the requests were reused, which is why a routine lives in the `Queue` tab and not in a panel of its own. **A run is an ordinary entry** with `Task::routine` set to the routine's id, made when the routine fires or on ` start now `; after that it follows the one-off path (`due`, `run_queued`, `Start` or `run_flow`, `queue_answered`). Runs are history: never edited, never restarted, only removed or cleared. The new `Task` fields (`repeat`, `flow`, `cleanup`, `paused`, `routine`) are left out of the file when empty, so a queue without routines is byte for byte as before. `Removed` and `Kept` are new states of a run.
- **`queue.json` is version 2 only when a routine, a run, a flow or a `removed`/`kept` state is in it** (`Queue::saved`; the flows' `Flow::file_version` set the precedent), and cornercase reads 1 and 2. An older release would read a routine as a one-off entry and start it once in the project's root, and it would fail on `state: "removed"`; a version it refuses gives it an empty queue instead, and it never overwrites the file until an edit.
- **The repeat is stored and sent as its canonical text** (`Repeat`, `3d 10:03`, `day 09:00`, `weekday 09:00`, `monday 09:00`, `30m`, `2h`), the same text `--every` and the socket's `repeat` take. For days and weeks the clock is part of the repeat, captured from the client's clock when it was added (`--every 3d` added at 10:03 means 10:03), so occurrences never drift. `queue list` and `status --app` add `next` to a routine that is not paused (`queue::Listed`), so a paused routine's stale `at` is never read as its next run.
- **Minimum 30 minutes, maximum a year**, checked in `Repeat::parse`, so the form (which shows the server's error) and the socket refuse alike: each run makes a worktree, and a shorter gap would only be a loop. `--every` does not mix with `--at`, an issue, a workspace or a worktree (the same issue every time makes no sense; a routine always makes its own worktrees), and an edit cannot turn a one-off entry into a routine or back, nor change a run.
- **Occurrences are counted from the schedule** (`Repeat::walk`, `after`, `first`): minutes and hours are absolute (`at + k·step`), days, weeks and the clock kinds are civil dates in the routine's zone at the repeat's own clock, resolved with Jiff's `Disambiguation::Compatible`. A routine that failed every March would be useless, so a nonexistent or repeated local time shifts instead of failing (a 02:30 becomes 03:30 on the spring-forward day and comes back to 02:30 the next day, because each occurrence is computed from the previous one's date, not its clock). A one-off entry keeps failing on them.
- **Missed** (`Queue::fire`): the routine walks to the latest occurrence not after now. If occurrences were skipped, or the last was more than the 600 s grace ago, **one** `missed` run is recorded at the old time; a last occurrence within the grace is run. The routine then goes on with the next occurrence after now. Catching up was rejected: a week of downtime would start dozens of agents. `load` does not fire routines (it cannot send notices); `drive_queue` does, once the queue has an area, so the same rules as for one-off entries apply, and a stopped server or a sleeping machine is not woken (the docs say so plainly).
- **A run always starts**, even while the previous one is still working. Skipping it was rejected: a routine that sometimes does not start would read as cornercase failing, and each run has a worktree of its own. An interval shorter than the work is the user's to fix.
- **Each run gets a fresh worktree from the up-to-date default branch** (`git::worktree::fresh`): `git fetch` of `origin` (else the first remote in `.git/config`, read with `git::remote_urls`, since `git::remote::primary` drops plain-path remotes), then the branch from `refs/remotes/<remote>/HEAD`, else `<remote>/main` or `<remote>/master`; a project without a remote uses its local `main` or `master`. A fetch that fails (offline, auth, 120 s) fails the run with git's reason: it never starts from stale code without saying so. Starting from the project's `HEAD` was rejected (stale, and whatever was left in the root). Nothing is pruned and no ref of the user's is written beyond the fetch. The branch is `routine/<slug>-<YYYYMMDD-HHMM>` (the run's time, in the routine's zone), with `-2`, `-3` added while a branch, an open workspace, a checkout folder or another starting run has the name, and is chosen before the run is marked starting, so two runs in one refresh never collide. The job knows it is a routine's run through the internal client (`QueueRuntime::fresh`), as trust and the prompt do, so the wire `Start` did not change. A flow's own worktree is made the same way (`RunTrees::fresh`); role worktrees branch from it.
- **Runs of one project take turns to fetch and branch** (`fresh::one_at_a_time`, a lock per repository): two runs starting together (a routine started now twice, two routines on one project, or a flow and an agent) made git fail with `incorrect old value provided` while both updated `refs/remotes/origin/main`, and the app's own background fetch (the `↓n` check) races with them the same way, which a lock inside cornercase cannot prevent; so a fetch that fails with a ref-lock clash (`incorrect old value`, `cannot lock ref`, `Unable to create`) is tried again up to five times, 0.3 s apart, and only then fails the run. A new branch is made with `git worktree add --no-track`: a start point on a remote ref would otherwise write `branch.<name>.merge` into the shared `.git/config`, which failed with `unable to write upstream branch configuration` when two runs started together, and a routine's branch has no business tracking `origin/main`. Found by a flaky test that started two runs at once.
- **Flows only in routines** (`--flow`, the form's agent list gains `<name> (flow)`): the flow is looked up by name at each run, so edits to the flow apply to the runs to come, and the routine's prompt is the orchestrator's task. A flow in a one-off entry stays left for later.
- **Cleanup** (`routine_cleanup.rs`, `--cleanup`, off by default): finished means the agent's status is `done` (done and not yet seen) after the pane worked since the run started, held for 180 s (`CLEANUP_GRACE`). `Working` (which includes background shells and subagents), `Waiting`, `Pending`, `Failed`, `Idle` and no status restart it: `idle` means someone looked at the tab, and removing a workspace a person is reading was rejected, so looking at a run's tab keeps its workspace. For a flow, finished is the run's end with no member working or waiting. After the grace a job runs the Worktrees dialog's scan on the run's worktree and every role worktree (`worktrees::scan::left_over`): anything uncommitted, unpushed, locked or failing to scan keeps the workspace, the run becomes `kept · <reason>`, and a toast, a desktop notification and the chat apps say `routine <name> left changes in <workspace>: <reason>`. A clean result removes the workspace the ordinary way, without `--force`, so a file written after the scan makes git refuse and the run is kept instead of destroyed. The run becomes `removed`, and a job deletes its branch and its roles' branches, each only after `branch_commits` finds nothing unpushed. A custom agent has no readable status, so the checkbox is greyed with that reason and the request refuses it. The countdown lives in memory: removing the run from the list, closing the workspace, a pane that is gone or a server restart drops it and the workspace stays. That satisfies "dropping a run never removes its workspace"; keeping the countdown across a restart is left for later.
- **History**: the last 10 runs of a routine stay (`RUNS_KEPT`), never a pending or starting one, nor a started one whose cleanup is still counting (so a long run past the tenth still gets its cleanup; after a restart its countdown is gone and it can be dropped, its workspace staying). Re-arming after a restart was rejected: pane ids do not survive it, so there is nothing to watch; dropping a run stops no agent and removes no workspace. ` remove ` on a routine removes it and its runs as one undo and is refused while a run is starting. ` clear started ` removes one-off started entries and runs that are started, removed, kept, failed or missed, never a routine.
- **Notices**: a run starting, failing, missed or kept goes to the toast, a desktop notification and, new, every chat app that is away (`App::announce`). `queue_notice` is shared, so a one-off entry's start and failure reach Telegram and Discord too; a missed one-off entry stays silent, as before.
- **The form** keeps its 23 rows. For a repeat kind row 16 is the checkbox (greyed with its reason on row 17 when the agent cannot be read), the trust notice moves to rows 18 and 19, `Open in` says `new worktree` in grey with no branch field, and Where lists only repository roots (`Form::refit`). The Account row is hidden and Mode says `set by the flow's roles` when a flow is chosen. The unit list gains `weeks` for `in` and for `every`.
- **Contract**: the additive `queue-routines` feature; the CLI checks it before it sends `repeat`, `flow` or `cleanup`, `pause` or `resume`, since an older server would take a routine as a one-off entry.
- **Checked live** on 2026-11-04 with the tests only (fake agents, a clone of a repository with an origin, `refresh_at` on a virtual clock): no real agent ran and no real remote was fetched. Left for later: picking the next issue with a label on each run, a countdown shown on the run's row, removing the outside processes of a run's worktree (the Worktrees dialog names them; the cleanup ignores them), and waking a sleeping machine.
