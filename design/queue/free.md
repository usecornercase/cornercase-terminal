# Queue › Waiting for room

Part of [Queue](../queue.md). How memory is read and a machine picked is [Free memory](../free-memory.md).

- **Why**: one computer is handed tasks without limit (an always-on laptop as the orchestrator) and should send each to a machine that has the memory for it, some of which come and go (a desktop that boots into Windows). The only reason to hold a task back is memory, never a count of tasks: a cap per machine was rejected, since a small task and a flow of five agents are not the same load.
- **An entry that waits for room** (`Task::wait = Some(Wait::Free)`, `queue add --when free`, the form's `when there is room`): its `at` is when it joined, which gives the order, and it is never started by the clock (`Queue::due`, `next` and the routine firing leave it out). `Task::machine` is `auto` (this computer or any linked machine with the project; the default) or one machine's name (that machine only, never this computer). `--when free` does not mix with `--at`, `--every`, `--cleanup` or a bot, and an edit cannot turn a timed entry into one or back. A one-off entry can now run a flow, but only one that waits for room: a timed flow is still a routine's, which `refuse_mix` says.
- **Strict FIFO** (`Queue::waiting`): the entries in order of `first` (newest first), then `at`, then id. When the first fits nowhere, the ones behind it wait too, so a big task is never starved by small ones behind it. Letting a smaller entry overtake was rejected for now: it needs a rule for how long a big one may wait, and the user asked for a line. `queue first ID` and ` first ` put an entry at the head: `Task::first` is a counter one above the highest, so the last one put first leads; a time would tie within a second.
- **Dispatch** (`app/control/queue/room.rs`, from `drive_queue` after the timed entries, and again whenever a machine's memory answer arrives): nothing is decided while a reading is being asked, so a machine whose reading is on its way is not passed over for one whose reading was already there. Each waiting entry in turn takes its memory (its flow's, else `default_memory`), is offered to the picker (only its machine when it names one) and starts there, reserving that memory for 5 minutes, or else says why it waits and stops the walk; the ones behind say `behind queued agent 7`. A start that fails (the project closed here, the agent not installed) fails the entry as a timed one would and the walk goes on. `queue run` and ` start now ` start a waiting entry at once on the machine with most room, counting nothing.
- **Asking**: every 30 s while an entry waits (`QueueRuntime::wake` returns 30 s then), readings older than 30 s are asked again; between two answers, nothing is asked twice.
- **Why it waits** (`QueueRuntime::waits`, in memory, rebuilt by every walk): the position, the picker's reason (`needs 6 GB · best: torre 4.1 GB · mac unreachable`) or the entry ahead, the needs, and since when it waits. It is not saved: after a restart the next walk says it again. `queue list` and `status --app` carry it as `waiting` on each waiting entry.
- **On this computer** the entry starts as a timed one does (`queued_start`, `launch_start`; a flow through `run_queued_flow`, the routines' flow start with the entry's own branch and `fresh`). **On a machine** it is relayed as `start --machine` or `flow run --machine` is (`machines::send::Send`), from one of the queue's internal clients, with the machine's id of the project (paired by its repository, as `auto` does), the prompt with the closing sentence, the agent's name and the accounts; the machine uses its own command and mode for that agent, since the ones captured here may not exist there (a limit). The answer comes back to `queue_answered` through the relay, carrying `machine`.
- **A run on a machine** (`Entry::there`: the machine, its workspace and tab; `State::Started { pane, server }` with the machine's pane and boot): `State` was left as it was and the place went in a field of its own, since every `Started { pane, server }` pattern would have changed and an older release reads the entry as a started one anyway. It is followed through the machine's snapshot (`app/queue_there.rs`): its pane's status shows on its row (`started on torre · working`), a turn that ends keeps a result (the branch and the pull request; the agent's message stays on the machine, whose record cornercase cannot read here), and while the machine is down the row says `paused while torre is unreachable` and nothing fails: when the link comes back the same pane is followed again. A click shows its tab there. Its pull request is found by branch with `gh pr list --head <branch>` in the project's folder here, every 2 minutes for a day after it started, until one is found; a branch the machine named (an issue's, a flow's default) is read from the start's answer.
- **Notices**: `queue-waiting` once when an entry starts to wait (its position and why: `queued agent 7 waits for room: 1st in line, needs 6 GB · best: torre 4.1 GB`), `queue-pull-request` when the pull request of an entry that waited for room opens (here from the workspace's pull request, on a machine from `gh`), and the started notice names the machine (`started queued agent 7 on torre`, `on this computer`). They go through `queue_notice`, so the toast, the desktop notification, the chat apps while away and the `message` events all get them. The pull request notice is limited to these entries so routines, which open pull requests every run, do not start sending a new notice.
- **Seeing it** (the footer, `ui::queue_button`): while entries wait, a yellow `queue 3` between ` More ▴ ` and ` Help ` opens the Queue modal. The earlier refusal of a footer button was about a button always there; this one shows only while something waits, which is when the line is what one wants to see. The icon bar's More carries the count as its badge, and the More menu's item reads `queue · 3 waiting`. A `cornercase remote` window draws the same view, so it shows there too. In the modal the waiting entries come first in their turn, `#1 in line` in the time column and `waits 12m · …` as their status, and ` first ` shows on any but the head.
- **`queue.json` version 4** only while an entry waits, targets a machine, was put first, ran on a machine or is a one-off flow (`Entry::uses_free`); a file without them is written as before, so an older release keeps reading it. One that cannot read version 4 starts with an empty queue and does not overwrite the file until an edit, as for version 3.
- **Contract**: the feature `queue-when-free`: `when` and `machine` in `queue` `add`/`edit`, the `first` action, `wait`, `machine`, `first`, `waiting` and `there` in the entries, and the message kinds `queue-waiting` and `queue-pull-request` (additive, like `message-flow-exited`; pinned by `message-queue-waiting.json`). `queue add --when free`, `--machine` and `queue first` check it first, since an older server would refuse the fields or the action with a less useful message.
- **Left out**: a smaller entry overtaking a bigger one; waking a machine that is off; counting the memory a running agent actually uses (only reservations); the agent's last message for a run on a machine; a routine or a timed entry that waits for room at its time.
- **Checked**: the model, the requests, the CLI and the dispatch with the fake machines of the app tests (`app/tests/machine_links/acting/auto.rs`: started on the machine with room, waiting with why, behind, `first`, paused while down, the footer). No real second machine was used.
