# Queue › Routines (#653)

Part of [Queue](../queue.md).

- **A routine is an entry that repeats**, not a new store: `Task::repeat` is set, its state is always `pending` and its `at` is its next occurrence. The form, places, clock, `queue.json`, undo and the requests were reused, which is why a routine lives in the `Queue` tab and not in a panel of its own. **A run is an ordinary entry** with `Task::routine` set to the routine's id, made when the routine fires or on ` start now `; after that it follows the one-off path (`due`, `run_queued`, `Start` or `run_flow`, `queue_answered`). Runs are history: never edited, never restarted, only removed or cleared. The new `Task` fields (`repeat`, `flow`, `cleanup`, `paused`, `routine`) are left out of the file when empty, so a queue without routines is byte for byte as before. `Removed` and `Kept` are new states of a run.
- **`queue.json` is version 2 only when a routine, a run, a flow or a `removed`/`kept` state is in it, and version 3 when a bot entry or an `answered` state is** (`Queue::saved`; the flows' `Flow::file_version` set the precedent), and cornercase reads 1 to 3. A version 1 or 2 file with no bot entry is written back byte for byte. An older release would read a routine as a one-off entry and start it once in the project's root, and it would fail on `state: "removed"`; a version it refuses gives it an empty queue instead, and it never overwrites the file until an edit. `Task::fresh` does not raise it (see Worktrees › Where a new branch starts).
- **The repeat is stored and sent as its canonical text** (`Repeat`, `3d 10:03`, `day 09:00`, `weekday 09:00`, `monday 09:00`, `30m`, `2h`), the same text `--every` and the socket's `repeat` take. For days and weeks the clock is part of the repeat, captured from the client's clock when it was added (`--every 3d` added at 10:03 means 10:03), so occurrences never drift. `queue list` and `status --app` add `next` to a routine that is not paused (`queue::Listed`), so a paused routine's stale `at` is never read as its next run.
- **Minimum 30 minutes, maximum a year**, checked in `Repeat::parse`, so the form (which shows the server's error) and the socket refuse alike: each run makes a worktree, and a shorter gap would only be a loop. `--every` does not mix with `--at`, an issue, a workspace or a worktree (the same issue every time makes no sense; a routine always makes its own worktrees), and an edit cannot turn a one-off entry into a routine or back, nor change a run.
- **Occurrences are counted from the schedule** (`Repeat::walk`, `after`, `first`): minutes and hours are absolute (`at + k·step`), days, weeks and the clock kinds are civil dates in the routine's zone at the repeat's own clock, resolved with Jiff's `Disambiguation::Compatible`. A routine that failed every March would be useless, so a nonexistent or repeated local time shifts instead of failing (a 02:30 becomes 03:30 on the spring-forward day and comes back to 02:30 the next day, because each occurrence is computed from the previous one's date, not its clock). A one-off entry keeps failing on them.
- **Missed** (`Queue::fire`): the routine walks to the latest occurrence not after now. If occurrences were skipped, or the last was more than the 600 s grace ago, **one** `missed` run is recorded at the old time; a last occurrence within the grace is run. The routine then goes on with the next occurrence after now. Catching up was rejected: a week of downtime would start dozens of agents. `load` does not fire routines (it cannot send notices); `drive_queue` does, once the queue has an area, so the same rules as for one-off entries apply, and a stopped server or a sleeping machine is not woken (the docs say so plainly).
- **A run always starts**, even while the previous one is still working. Skipping it was rejected: a routine that sometimes does not start would read as cornercase failing, and each run has a worktree of its own. An interval shorter than the work is the user's to fix.
- **Each run gets a fresh worktree from the up-to-date default branch** (`git::worktree::fresh`): `git fetch` of `origin` (else the first remote in `.git/config`, read with `git::remote_urls`, since `git::remote::primary` drops plain-path remotes), then the branch from `refs/remotes/<remote>/HEAD`, else `<remote>/main` or `<remote>/master`; a project without a remote uses its local `main` or `master`. A fetch that fails (offline, auth, 120 s) fails the run with git's reason: it never starts from stale code without saying so. Starting from the project's `HEAD` was rejected (stale, and whatever was left in the root). Other starts can ask for the same (#745, see Worktrees › Where a new branch starts). Nothing is pruned and no ref of the user's is written beyond the fetch. The branch is `routine/<slug>-<YYYYMMDD-HHMM>` (the run's time, in the routine's zone), with `-2`, `-3` added while a branch, an open workspace, a checkout folder or another starting run has the name, and is chosen before the run is marked starting, so two runs in one refresh never collide. A routine's run asks for `fresh: true` like any other start (#745, Worktrees › Where a new branch starts), for its agent (`Start`) and for its flow (`Starting`); role worktrees branch from the run's.
- **Runs of one project take turns to fetch and branch** (`fresh::one_at_a_time`, a lock per repository): two runs starting together (a routine started now twice, two routines on one project, or a flow and an agent) made git fail with `incorrect old value provided` while both updated `refs/remotes/origin/main`, and the app's own background fetch (the `↓n` check) races with them the same way, which a lock inside cornercase cannot prevent; so a fetch that fails with a ref-lock clash (`incorrect old value`, `cannot lock ref`, `Unable to create`) is tried again up to five times, 0.3 s apart, and only then fails the run. A new branch is made with `git worktree add --no-track`: a start point on a remote ref would otherwise write `branch.<name>.merge` into the shared `.git/config`, which failed with `unable to write upstream branch configuration` when two runs started together, and a routine's branch has no business tracking `origin/main`. Found by a flaky test that started two runs at once.
- **Flows only in routines** (`--flow`, the form's agent list gains `<name> (flow)`): the flow is looked up by name at each run, so edits to the flow apply to the runs to come, and the routine's prompt is the orchestrator's task. A flow in a one-off entry stays left for later.
- **Cleanup** (`routine_cleanup.rs`, `--cleanup`, off by default): finished means the agent's status is `done` (done and not yet seen) after the pane worked since the run started, held for 180 s (`CLEANUP_GRACE`). `Working` (which includes background shells and subagents), `Waiting`, `Pending`, `Failed`, `Idle` and no status restart it: `idle` means someone looked at the tab, and removing a workspace a person is reading was rejected, so looking at a run's tab keeps its workspace. For a flow, finished is the run's end with no member working or waiting. After the grace a job runs the Worktrees dialog's scan on the run's worktree and every role worktree (`worktrees::scan::left_over`): anything uncommitted, unpushed, locked or failing to scan keeps the workspace, the run becomes `kept · <reason>`, and a toast, a desktop notification and the chat apps say `routine <name> left changes in <workspace>: <reason>`. A clean result removes the workspace the ordinary way, without `--force`, so a file written after the scan makes git refuse and the run is kept instead of destroyed. The run becomes `removed`, and a job deletes its branch and its roles' branches, each only after `branch_commits` finds nothing unpushed. A custom agent has no readable status, so the checkbox is greyed with that reason and the request refuses it; both ask `agents::reads_status`, which `config` gives a client as `reads_status` (see Commands for scripts and agents › Reading and changing settings). The countdown lives in memory: removing the run from the list, closing the workspace, a pane that is gone or a server restart drops it and the workspace stays. That satisfies "dropping a run never removes its workspace"; keeping the countdown across a restart is left for later. A run that is also opted in to close its agents once merged waits for this cleanup (`App::cleaning_up`), since closing them first would end the run and the cleanup would never fire (see Flows › Closing a merged run's agents).
- **History**: the last 10 runs of a routine stay (`RUNS_KEPT`), never a pending or starting one, nor a started one whose cleanup may still be counting, up to twice the history (so a long run past the tenth still gets its cleanup; after a restart its countdown is gone and it can be dropped, its workspace staying). Re-arming after a restart was rejected: pane ids do not survive it, so there is nothing to watch; dropping a run stops no agent and removes no workspace. ` remove ` on a routine removes it and its runs as one undo and is refused while a run is starting. ` clear started ` removes one-off started entries and runs that are started, removed, kept, failed or missed, never a routine.
- **Notices**: a run starting, failing, missed or kept goes to the toast, a desktop notification and, new, every chat app that is away (`App::announce`). `queue_notice` is shared, so a one-off entry's start and failure reach Telegram and Discord too, and a `queue-started`, `queue-unsent`, `queue-failed`, `queue-missed` or `queue-kept` message reaches `events --notices` (`queue_notice` is shared with the routine's cleanup, `keep_run`); a missed one-off entry stays silent, as before.
- **The form** keeps its height (see Forms and commands). For a repeat kind the checkbox takes the row after Mode (greyed with its reason on the row under it when the agent cannot be read), the trust notice moves two rows down, `Open in` says `new worktree` in grey with no branch field, and Where lists only repository roots (`Form::refit`). The Account row is hidden and Mode says `set by the flow's roles` when a flow is chosen. The unit list gains `weeks` for `in` and for `every`.
- **Contract**: `queue add`/`edit --fresh` checks `fresh-branches` (see Worktrees › Where a new branch starts), and the additive `mode-default` feature, which `queue add` and `queue edit --mode default` check first (`client::use_mode_default`; the reason is in Commands for scripts and agents › A versioned contract), and the additive `queue-routines` feature; the CLI checks it before it sends `repeat`, `flow` or `cleanup`, `pause` or `resume`, since an older server would take a routine as a one-off entry.
- **Checked live** on 2026-11-04 with the tests only (fake agents, a clone of a repository with an origin, `refresh_at` on a virtual clock): no real agent ran and no real remote was fetched. Left for later: picking the next issue with a label on each run, a countdown shown on the run's row, removing the outside processes of a run's worktree (the Worktrees dialog names them; the cleanup ignores them), and waking a sleeping machine.
