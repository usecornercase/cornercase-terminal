# Queue › Results (#771)

Part of [Queue](../queue.md).

- **A started entry keeps a result**: what its agent last said (`Record::last_message`, at most 4 KiB, cut on a character boundary and marked `cut`), when it was captured, the agent, a pointer to the agent's record, the branch and the workspace's pull request with its state and checks as they were then (`queue::outcome::Outcome`, in the entry's `result`). A routine's run used to end as `removed` with nothing: the workspace, and so the branch and the pull request's link to it, were gone, and the conversation was found only by someone who knew where agents keep theirs. The text is copied into `queue.json` because the copy outlives the record (an agent prunes its own files); about 4 KB an entry, and an entry only has one.
- **It is captured on each turn end, not only on `done`.** In cornercase `done` means "finished and nobody looked": a turn that ends while its tab is shown goes `working → idle`, so a capture on `done` alone would miss every run somebody watched. The watcher (`app/queue_results.rs`, after each agent read) keeps the last status it saw of each started or kept entry's pane and captures when it leaves `working` or `waiting` for anything else (`done`, `idle`, `pending`, `failed`, or no agent any more); the first look never captures. It captures again on every later turn end, once when the pane is gone (from what it last saw of the pane: the record, the workspace and the pull request), and once right before a routine's cleanup removes the workspace (`capture_before_removal`; the entry is skipped by the watcher from then on, so the panes the removal closes are not captured a second time, until a failed removal makes it `kept`). A flow run's result is its orchestrator's. Only the server that started an entry watches it (the token in its state): an entry of a previous server run keeps what it had, and nothing is captured after the server stops, so a run whose turn never ended while cornercase watched has no result (the detail says so).
- **Reading the record runs on a job**; the loop never waits on a file. It only asks whether the record's file still exists (`Pointer::readable`, one `stat`, when a request is answered and when the dialog draws). Each read has a generation, and an older read that finishes after a newer one is dropped. A read that fails keeps the previous result untouched and the job's log line says so (WARN); a read that finds no message keeps the previous text and updates the rest. No toast, notification or chat message is sent: a result is data, not an event. A custom agent has no record cornercase can read, so its result is the branch and the pull request, and the detail says why there is no message.
- **The pointer is the Recap journal's** (`agents::context::Pointer`, moved out of `recap::journal` so the two stores share one name and one serialized shape; changing it would break both files). It is not answered to clients, as Recap's is not, not even in the `remove`, `clear-started` and `restore` answers (`answered` clears it; the undo copy keeps it): a request that wants the conversation reads it for them. An agent kind this release does not know, read from a newer release's file, leaves `record` empty instead of failing the whole file (`known_record`), since the queue would otherwise start empty and be overwritten.
- **`started` is a field of the entry** because `at` is wrong for ` start now ` (it keeps the scheduled time) and the detail has to say when the agent started. Entries from before show `scheduled <time>`.
- **`queue.json` stays version 1 or 2 by its old rule**: `started` and `result` are left out when empty, so a file without them reads and writes back byte for byte, and an older release reads the file, ignores them (`Entry` has no `deny_unknown_fields`) and drops them when it next saves. Removal, clear and undo carry whole entries, so a restored entry gets its result back, and the `remove`, `clear-started` and `restore` answers carry `started` and `result` without its pointer (additive: they answer "the complete removed entries").
- **`queue list` and the `app` feed carry `started` and `result_at`, never the text** (`Listed` clears the result and sets `result_at`): the feed is sent whole on each change and a 4 KB text an entry would be resent every time something else moved. A routine memory file, a `queue report` command, a summarising background agent and the result inside `queue list` were the alternatives the issue weighed; reading the agent's own record on the spot needs none of them.
- **A prompt that was not taken is not a run that worked** (#882): an entry became `started` as soon as `start` answered, and `start` answered at the Enter, so a routine whose prompt stayed unsent in Claude Code's input box (four of five hourly runs on 2026-11-15, see Agents › Confirming the Enter) read `started` and `queue show` said only that no turn was seen. Now the launch confirms its Enter (Agents), so the entry becomes `started` once the prompt is taken, up to a context read after the Enter (a limit: it is later than before). When it is never taken, the entry **keeps `started`** and gets `unsent: true`. A new state was rejected: it needs `queue.json` version 4, and a release that does not know the version drops the whole queue file (#771 added `started` and `result` as optional keys for the same reason). The flag is left out when false, so an entry from before serializes byte for byte, and an older release ignores it. The row reads `started · pane N · prompt not taken` in yellow (attention, like `missed` and `kept`), `queue list` appends ` · prompt not taken`, and `queue show`'s note says `no result: its agent did not take the prompt…`. The notice is `queue-unsent` in place of `queue-started`: a toast with the bug icon, a desktop notification, the chat apps while away and `events --notices` (`queue_started` in `app/queue_panel.rs`). A routine that starts a flow marks its entry from the orchestrator's brief (`queue_run_unsent`), since the flow's start answers before the brief is taken. The entry is looked at once when it becomes `started` (`queue_first_look`), since the prompt is taken as the agent starts to work and a turn that ends before the next read (500 ms) would otherwise never be seen working and keep no result. The flag clears only when the watcher sees the pane `working` (a person pressed Enter); keeping a result does not clear it, since a capture that was started by an earlier turn can come back after a later brief failed and would wipe that newer mark (CodeRabbit, #889). Reachable over the socket under the `prompt-unsent` contract feature.
- **`queue show` is a new operation, `queue-show`** (`{"id", "conversation"}`), advertised by the feature `queue-results`, and not a new `action` of `queue`: an older server refuses an unknown operation by name, but would answer a `queue` request it cannot parse as `malformed`. `cornercase queue show` checks the feature first, as `recap` does. It answers the entry as `queue list` has it, `result` (`at`, `text`, `cut`, `written`, `agent`, `branch`, `pull_request` and `conversation`, whether the record can still be read), `messages`, `earlier` and `note`, every key always there. An unknown id is `not-found`.
- **`--conversation` reads the whole conversation on a job** (`queue::conversation::read`, `Record::said`): the newest 1,000 messages, each at most 32 KiB (the flow message's cap), oldest first with `earlier` when older ones were left out; prompts and replies, no tool calls. Eight readers give their messages newest first and Vibe's oldest first (`Record::said_newest_first`), so the reader stops after 1,001 messages for the first and reads all for the second; then a stable sort by the record's own times when every message has one, as the dossier does. A record that is gone answers the result alone with `messages: null` and a `note`, at once; the CLI then exits 3 ("part of it failed", #472), still printing the result. The queued prompt's closing sentence shows in the conversation: it is what the agent got.
- **The closing sentence**: every queued prompt is typed with a blank line and `When you finish, end your last message with a short summary of what you did and what is left to do.` after it, so the last message that is kept reads as a summary. It is added where the prompt is sent (`queued_spec`) and never stored: not in the entry's `prompt`, nor in `queue.json`, nor in a flow run's `task`. For a routine's flow it follows the task in the orchestrator's brief (`Starting::summary`, `Run::summary`, in memory only), so the Flow panel and `flow runs` show the task as it was typed. A retained draft (`submit: false`, only through the socket) has it too, since the person sees it there. The sentence holds no quote, backslash or percent sign: the e2e fake prints it with `printf`.
- **The detail** (`Overlay::QueueResult`, `app/queue_result_dialog.rs`) is the notes dialog of the pull request and the flow message (`ui::Update`), not a form: the label and the row's meta, then `started`, `result`, `agent`, `branch` and `pull` and the text wrapped (`editor::wrap_text`), or the reason there is none (`queue::outcome::note`). ` conversation ` loads the conversation on a job and ` result ` goes back; ` copy ` copies what is shown; ` done `, `Esc` and a click outside go back to the queue modal with the list as it was, as the schedule form does (`QueueRuntime::back`). `Enter` or a click on a started or kept entry whose pane is still in this server focuses the pane, as before; on one whose pane is gone, on a removed run and on a failed or missed **run** it opens the detail; a failed or missed one-off entry still opens the form, since it can be edited and started again. The rows do not change; the hint under the list says what `Enter` does (`queue::dialog::Row::live` tells it whether the pane exists). The detail reads the entry on each draw, so a capture that lands while it is open shows at once, and it closes when its entry disappears. The conversation's lines are wrapped once per width, not on each frame (a cache the draw refreshes when the width changes). The fact rows wrap under their label, the label is cut to one row so the state line always shows, and ` copy ` copies what the dialog shows.
- **Limits**: a custom agent has no message; a flow's result is its orchestrator's; the pull request is not refreshed once the workspace is gone (what was known at the last capture stays); a turn shorter than 500 ms that starts and ends between two reads is caught at the next turn end or at the close; nothing is captured while the server is stopped.
- **Checked**: with fakes only (`FakeClaude`'s transcripts, a custom agent for the cleanup, the e2e fake that writes `said: <prompt>` replies); no real agent was run. The pure parts (cap, turn end, merging a capture, the note texts, the conversation's order and caps) run on every system, and the PTY tests are Unix-only like the other queue tests.
