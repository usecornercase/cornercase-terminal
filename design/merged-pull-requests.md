# Merged pull requests

Code: `pull_request/merged.rs`, `pull_request/merged/`, `git/remote.rs`, `app/merged_pull_requests.rs`, #293

- **Why**: Stats counted agent work but not what came of it. The pull requests you merged are the plainest number of work done, and they are already at GitHub and GitLab, so Stats asks for them: one row, `merged PRs`, in the Stats tab, `cornercase stats`, its JSON and the share card.
- **Whose tools**: only `gh` and `glab`, which hold the user's logins; cornercase's own GitLab token (the issues browser's) is not a source. Accounts come from `gh auth status --json hosts` (every host and login whose state is `success`; gh lists one twice when `GH_TOKEN` and the keyring hold it, so sources are deduplicated by provider, host and login, lower case) and `glab auth status --all --output json` (one account per host; it exits 1 when any host fails but still prints the JSON, so stdout is parsed whatever the status; the runner, the environment and this parse live in `pull_request/glab.rs`, shared with merge requests on the workspace rows, which keeps the hosts in error and Stats only the `success` ones). A missing tool, no logged-in account, or a tool too old for those flags makes that provider **unavailable**: dropped silently, and not a partial count. Any other discovery failure keeps the known sources and marks them failed.
- **The token exception**: "cornercase never reads a token" (Pull requests) holds for the active account, which runs with the inherited environment. An inactive `gh` account cannot be queried without switching, and switching would change the user's login behind their back and race other shells, so its token is read with `gh auth token --hostname H --user L` and given to that one search as `GH_TOKEN` and `GH_ENTERPRISE_TOKEN`, with `GITHUB_TOKEN` and `GITHUB_ENTERPRISE_TOKEN` removed from the child's environment. It lives in the job's memory only, never logged or stored, and is scrubbed from error text. `auth switch`, `login` and `logout` are never run. glab has one account per host, so nothing is injected; if glab refreshes its own OAuth token, that is its normal behaviour. Both tools run in the home folder (or `/`), never in a project, always with `--hostname`.
- **The query**: GitHub, one GraphQL search per account, `is:pr is:merged author:<login> merged:<from>..<to>` with UTC days from the day counting began, paginated by `gh api graphql --paginate` (one JSON document per page, read with a stream deserializer). No `repo:` qualifiers: one repository an account cannot see makes GitHub reject the whole query, and a global search keeps the cost at one call per account whatever the projects. GitHub caps a search at 1000 results, so a range reporting more is split in half by dates, at most six levels; a range that still passes the cap is `truncated` and makes the count partial. GitLab, `merge_requests?scope=created_by_me&state=merged&updated_after=<since>` (the REST API has no `merged_after`; a merge updates `updated_at`, so this is a superset) read one page of 100 at a time (`page=N`, up to `MAX_PAGES` 20, since `glab api --paginate` has no bound and a 60 s timeout would discard everything read), ending on a short page; reaching the bound with a full page, or a later page failing, keeps what was read and marks the list truncated (`n+`); a failing first page is the account's error. Then a local filter on `merged_at`. Every result is filtered locally on its merge time against `since`.
- **Scope and identity**: a result counts when its repository is a remote of an open project (`git::remote::of`: every remote of the project's common git config, so a fork's `upstream` counts and a worktree adds nothing). A remote is placed under the account host that serves it (equal, a subdomain such as `ssh.github.com` or `altssh.gitlab.com`, or glab's `ssh_host`; a GitLab web remote drops glab's `subfolder`). A remote matching no host (an SSH alias such as `github.com-work`) is kept as a bare path and matches any result with that path: the alias is never resolved and `~/.ssh/config` never read, since a work repository cloned through an alias is the common case. The identity of a pull request is host, repository (lower case) and number, so the same one found by two accounts, two projects or two remotes counts once. Scope is applied when counting, not when asking, so a new project needs no new query. `git/remote.rs` holds the remote URL parsing that the GitLab issues browser used (moved there unchanged).
- **Windows**: all three columns count merges at or after `Stats::since()`, with the hour-aligned 24 h and 7 d windows of the other rows (`stats::windows`), so total is never below the others and `counting for n days` states the period. Provider history older than that is ignored: a total beyond counting would not be comparable with the rows around it.
- **Cache and pacing** (`Cache`, in memory only): one entry per source with its last list and last error. A query that fails keeps the previous list and sets the error, so a failure never turns into zero; a source no longer listed is dropped. The row is `None` (hidden) until some source has ever succeeded; a real zero is `Some`. It is complete only when every source has a list, no error and no truncation, and no discovery failed; otherwise numbers show a `+` (`12+`). Nothing persists: `stats.json` is unchanged, so old files and older binaries are unaffected and `cornercase stats` without a server leaves the row out; the first read after a start takes seconds. `App::ask_merged` runs in the 1 s sync step: one job at a time (`pr merged`, level debug, promoted past 30 s), every 15 minutes, 5 minutes after a failure, when the set of remote hosts changes, and when Stats opens with data over 5 minutes old; drawing never waits. **No project with a parseable remote asks nothing**: that gate keeps every test repository, which has none, from running `gh` or `glab` (as `has_remote` does for pull requests), and `new_app` points both at `/nonexistent`.
- **The view**: `stats::View::merged` (`Option<MergedRow>`, JSON key `merged_pull_requests`, always present, `null` when hidden; `#[serde(default)]` so a newer command reads an older server) carries `24h`, `7d`, `total`, `complete` and the accounts with their errors; `App::stats_view` fills it, so the dialog, the share pill and the `stats` request agree. The rows come from `View::rows`, which the dialog and the text share, with the label appended last so the others keep their positions. The share link is `#v3` (an eleventh number per window) only when the row is shown and complete, else exactly `#v2`: a lower bound never goes on a public card. Logs: one `WARN` per new reason per provider and host (`cannot read merged pull requests`), then `info` when read again; hosts and counts only, never logins or tokens.
- **Hidden and shown cases**: no open project with a remote hides the row (an empty scope would otherwise show a real-looking zero). A remote on a host no account serves (Bitbucket, Gitea) matches nothing; only an SSH-alias-looking host (no dot, or starting with an account's host, such as `github.com-work`) matches by path, so a same-named repository on another service is never counted, while an alias that looks like neither is missed. With no agent counted yet the dialog still draws the table when the merged row exists (zeros for agents), since it is a separate metric and `cornercase stats` shows it; the share pill stays hidden until something is counted. The simulation's Stats page has the row too: its table is built from the site's `ROWS`, whose example carries the eleventh number.
- **glab's errors** (#402): read by `glab::said`, which prefers the JSON envelope on stdout, then fang's stderr without its `ERROR` header, case-insensitively (see Pull requests, GitLab); before, an old glab's `Unknown flag: --output.` styled by fang was not seen as old.
- **Setting**: `merged_pull_requests` (Settings → Worktrees, on by default, its note names the accounts or the reason) and `glab`, the command, beside `gh`. Off drops everything and asks nothing.
- **Tests**: fake `gh` and `glab` scripts over fixtures from gh 2.101.0 and glab 1.123.0 (`tests/fixtures/gh/2.101.0`, `tests/fixtures/glab/1.123.0`, synthetic logins) cover discovery, no switching, pagination, the cap and its split, unavailable and partial states, duplicates and remote matching; the share fixture `stats/share-v3.txt` is checked by Rust and the site. Rejected: reading `~/.ssh/config` to resolve aliases, a persisted cache, and cornercase's own GitLab token as a source.
