# Recap

Code: `recap/` (`mod.rs`, `journal.rs`, `journal/files.rs`, `range.rs`, `dossier.rs`, `dossier/`, `outdated.rs`, `prompt.rs`, `store.rs`, `text.rs`, `run.rs`), `agents/headless.rs`, `agents/claude/headless.rs`, `agents/codex/headless.rs`, `agents/probe.rs`, `app/recap_panel.rs`, `app/recap_panel/`, `app/control/recap.rs`, `control/recap.rs`, `cli/recap.rs`, `cli/args/recap.rs`, `cli/help/recap.rs`, `ui/recap.rs`, `settings/recap.rs`, `paths.rs` (#656, #741)

A **Recap** is a summary of what your agents did, written by an agent. It answers the daily's question ("what did I do yesterday?") and the midday one ("where do things stand?"), across every project, workspace and agent of the server. It covers only agent conversations: work done by hand in shells, and git activity no agent was part of, is not in it.

## One mode, always written by an agent

- There is no "plain" recap that cornercase writes itself. A list of prompts is not a summary, and a heuristic summary would be a second, worse feature to keep. The three choices (`now`, `yesterday`, `7 days`) differ only in the range and the prompt.
- What cornercase does without a model is the **dossier**: a bounded Markdown file of facts. `cornercase recap --dossier` prints it, so the input is inspectable and the agent's work is checkable.
- `now` is where things stand, in three short sections: `Needs you`, `In progress` and `Done today` (the range stays the last 24 hours), an empty one left out, one bullet per workspace (or per pull request) with limits on its words and on the bullets, and one closing line, `Closed halfway:`, for conversations closed while still working or waiting. `yesterday` is a stand-up (Done / In progress / On you), one bullet per workspace, at most 12 bullets of 15 words. `7 days` is one section per project: 2 or 3 theme bullets, `Merged:` with the ids, `Open:`, at most 25 lines. The limits are instructions to a model: nothing enforces them, so the tests pin the prompt and the canned simulation, and "fits the panel" with a real agent is a check by hand.
- **Needs you is chosen by cornercase and worded by the agent** (#741). The dossier of `now` begins with a `## Needs you now` list that cornercase builds from what is open when the recap is written: a pane whose status is `waiting`, `failed` or `pending` (`recap::NEEDS_YOU`: the statuses `Status::needs_you` counts, except `done`, each with its words in the dossier), and an open or draft pull request whose checks fail, read live from a workspace that is open now (not one being closed or removed). The prompt allows exactly those items in `## Needs you`, one line each. `done` is not in it: it is the end of every turn and would fill the section. Work closed halfway is not a place under Needs you, because nothing in the open waits on it; it gets the one closing line.

## "Yesterday" is the last day with agent activity

On Monday "yesterday" is Friday and after a holiday it still works, which is what the daily needs. The day is the last local day before today with a `prompt` entry or a `status → working` entry in the journal, searched back over the 30 days the journal keeps. The label carries the real date (`yesterday · fri 31 oct`). With no activity in 30 days it answers `No agent activity in the last 30 days.` and runs no agent. The day is in the client's zone: the window's (the queue keeps it, `App::panels.queued.zone()`) or the CLI's, sent with the request.

## The journal

The past has to be readable, and cornercase only knew the present: search in sessions reads the panes still open, `stats.json` counts but does not say where, and a workspace closed yesterday leaves nothing. So cornercase keeps a journal of conversations beside `stats.json` (`paths::journal`, per server, private instances included: `x.journal/` for `CORNERCASE_SOCKET=x.sock`), for 30 days (`KEPT_DAYS`).

- **A folder of day files**, `journal/YYYY-MM-DD.jsonl`, one JSON object per line, UTC days. Each file is append-only, and keeping 30 days is deleting old files, never rewriting a file the server is appending to. A `yesterday` recap reads one to three files. Rejected: one `journal.jsonl` pruned by rewriting it (a rewrite races the appender, and a crash in the middle loses the journal).
- **Pointers, not content**: time, agent, account, conversation, the transcript's path (`agents::context::Pointer`, the journal's own shape mapped to and from `agents::context::Record`, so renaming a `Record` variant never breaks an old file; it moved out of the journal so the queue's results (#771) share it, with the same serialized shape), and the project, workspace (label, branch, path, whether a worktree) and tab as they were then, plus the workspace's pull request and its checks at that moment. Transcripts stay on disk after a pane closes; what is lost with a worktree is which workspace they belonged to, and that is what the journal keeps.
- **Events**: `seen` (a conversation first seen in a pane, or a pane changing conversation), `prompt` (at the prompt's own time, from `Counted.prompts`), `status` (to `working`, `waiting`, `done`, `idle`, `pending` or `failed`) and `closed` (the pane closed, or another conversation took it over). `Journal::observe` is the pure diff, run after each agent read (every 500 ms, `app/recap_panel/journal.rs`), and it builds a place only for a pane that emits an entry.
- Appending is synchronous, in append mode, with no fsync: a few hundred bytes, and a lost last line costs one entry (readers skip a line that does not parse). `server.rs` has no room for a shutdown flush, which is the other reason to write as events happen. About 300 KB a busy day, 10 MB at 30 days.
- Pruning is a job (`recap prune journal`) at the first agent read and when the UTC day changes: a file older than 30 days goes, day 30 stays.
- The eight known agents are journaled through the readers `Record::said` already has. No server folder, no journal: app tests that set none write nowhere.
- It does not see other machines (each server has its own journal; see Remote windows) or anything before this version.

## The dossier

`recap::dossier::build` takes the journal entries of the range, a snapshot of the open panes (`Live`, built on the main thread before the job, like the search sources: status, place, the last 15 screen lines of a pane that waits, each workspace's pull request) and the transcripts, and writes Markdown with ids in reading order (for `now`, what needs you first, then by project and workspace): `[c3]` a conversation, `[p1]` a pull request. Per conversation: place, branch, agent, account, first and last activity, status now (or closed, and when), the pull request and its checks, the transcript's path, my prompts in the range, the last reply and, while waiting, the question.

- **Prompts**: every message is read through `Record::said` (it is not ordered the same way across agents, so they are sorted by their time when all have one) and kept inside the range, the newest ones past the cap dropped. A message without a time is kept when the journal saw a prompt in the range. `now` shows the newest first.
- **Noise is skipped**: empty prompts, slash commands, `!` shell lines, and `yes`, `go on`, `ok`, `thanks`, `sí`, `dale` and the like. A paste (over 2,000 characters or 20 lines) is its first line and `(pasted N lines)`.
- **The `## Needs you now` list** (`now` only; `yesterday` and `7 days` have none): one line per place of the dossier that needs you, sorted by id (`c2` before `c10`): `- [c1] waits for an answer`, `- [c4] failed`, `- [c6] marked for review`, `- [p2] #212 · checks failing`; with none, `- nothing needs you`. A conversation that needs you ranks first and is never left out of the dossier, so its place is in `places`; without that, with more waiting panes than fit, the outdated check would find a need the recap cannot name and ask for a rewrite on every show.
- **A conversation with no open pane reads `closed, last seen … while working`** when no `closed` entry was journaled (the server stopped or restarted): every choice attaches the open panes to their conversations, so no pane means it is not open now. Before it read `last seen … while working`, which the agent took for work in progress.
- **A pull request read from the journal only** (its workspace is not open) ends its line with `(as last seen)` and has no `checks` in its place, so an old "open, failing" can never count as needing you.
- **Places carry `status` and `checks`**: a conversation's status when written (`open` when its pane reported none, `null` with no open pane) and a pull request's checks (only when read live). They are what the outdated check compares with later.
- **Caps** (`Caps`, lowered in #741 because the recap now says a task in a few words and quotes only short prompts): prompts per conversation 4 (now), 5 (yesterday), 3 (7 days); characters per prompt 300, 300, 200; last reply 400, 400, 200; screen lines while waiting 15 by 160; conversations 60, 60, 120; the whole dossier 32 KiB, 48 KiB, 80 KiB. 300 characters keep a short prompt whole and the start of a long one; the newest 4 or 5 prompts say where a conversation is; 400 characters of the last reply say where it ended, and the screen lines still carry a waiting question. The totals fell less than the per-conversation caps so that more conversations keep their prompts. Past the total a conversation keeps only its header, and past even that it is left out (never one that needs you); the dossier says how many.
- `7 days` lists the pull requests whose last known state in the journal is merged. Rejected: the merged-pull-request cache (`pull_request::merged`) has keys and times but no titles or workspaces, and matching its remotes to projects is a second source of truth for one line.
- A conversation whose worktree is gone keeps its place from the journal, which is the point.
- **A conversation is keyed by its transcript's path** (the id when an agent has no path), not by its id: Claude Code names the transcript after the conversation but the id is known only once the file has content, and a key that changed then would close and reopen the conversation. Real panes of all eight agents are journaled (tests with the Claude, Codex, Gemini, Opencode, Grok, Cursor, Copilot and Vibe fakes); only a pane whose reader knows neither a path nor an id yet (before the agent's first turn) waits.
- **An id known late still reaches the journal** (#664): `seen` usually comes before the first prompt, so it has no id. `Journal::observe` takes the id on each look and puts it in the pane's template, so the entries after it carry it, `closed` included, and a conversation closed when a recap is written keeps its id in `places`. Without it a place that was not live when written had `conversation: null` for good, and neither a link nor a client could find the conversation once it was reopened. It writes no line of its own: the first prompt brings the id and an entry in the same look. A journal written before this has `null` in those places.
- The `7 days` list of merged pull requests understates when a pull request merges after its workspace's last journal entry, or its workspace never held an agent pane.

## The background agent

Claude Code and Codex, run **without a pane**, through the same runner as the usage probes (`agents::probe`, which gained `Limits::close_input`: stdin is closed after the first write, so a non-interactive agent reads end of input). Each agent folder has a `headless.rs` (`Known::headless()` is `Some` for those two only, `None` for the other six) with the arguments and a reader of the agent's JSON stream. The runner (`agents/headless.rs`) is shared with Bots (see Bots): Recap passes `Tools::Recap`, and two tests pin its exact arguments for both agents, so moving the runner changed none. Checked live with Claude Code 2.1.318 and Codex 0.164.0:

- `claude -p --setting-sources '' --no-session-persistence --strict-mcp-config --output-format stream-json --verbose --max-turns 40 --allowedTools Read,Grep,Glob,Bash(cornercase search:*) --disallowedTools Edit,Write,NotebookEdit,WebFetch,WebSearch,Task [--model M] [--effort E] -- <prompt>`. The `--` matters: `--allowedTools` takes a list, and without it the prompt would be read as a tool. The answer is the `result` line (`is_error` or a `subtype` other than `success` is a failure, with the agent's own text), its `usage` is the tokens, and the model comes from `system/init`. Each `tool_use` is a step of the progress.
- `codex exec --json --skip-git-repo-check --ephemeral --sandbox read-only -C <folder> [--model M] [-c model_reasoning_effort=E] -- <prompt>`. The answer is the last `agent_message` item, completed by `turn.completed` (its usage), or `turn.failed`.
- It runs in `recap/<choice>/` under the state directory (`paths::recap`, 0700), never in a project or a worktree, with the same environment as the usage probes (the session variables of Claude removed, the account's variable set) and `CORNERCASE_SOCKET` when the server's panes get one (a dev build), so `cornercase search` reaches this server.
- **Who writes `recap.md`: cornercase, from the agent's final message** (the issue said the agent writes it). The agent gets read-only tools (Claude: no edit tool; Codex: the OS sandbox), so "cannot edit a project" is enforced by the tool list and the sandbox, not by a path rule a model could break; the run never depends on the model remembering to write a file; and the fakes are `test_util::fake_program` fakes (canned output, recorded argv and folder) that run on every OS. `recap.md` and `recap.json` are written in the folder next to `dossier.md`, 0600, both through `persist` (a temporary file beside each, renamed over it; see Saved session); `dossier.md` alone is written in place.
- **git for Claude is a prefix rule, not a sandbox**: `Bash(git log:*)`, `Bash(git show:*)` and `Bash(git diff:*)` are allowed beside `cornercase search`, as the issue says the agent may run `git`. A prefix rule does not stop `git log --output=FILE`, and `Read` reaches any path, so "touches no project" rests on the write tools being denied and on the folder not being a project, not on confinement. Codex's read-only sandbox does the same job for it at the OS level. `cornercase search` may not work inside Codex's sandbox (a socket); it is optional.
- `--setting-sources ''` drops the user's settings (a custom base URL in `env`), as the usage probes do.
- **Failures** carry the agent's words (`Not logged in`, `usage limit`), or `claude exited without answering`, `could not run claude: …`, `claude did not answer in time` (10 minutes, `RECAP_TIMEOUT`, with a knob in the app's state for tests). The panel shows the reason with ` retry `.
- **Not counted in Stats**: the run is no pane's agent, so `watch_agents` never sees it, and Claude runs with `--no-session-persistence`, so its transcript is not kept either. The panel's header says the agent, the tokens and the age.

The prompt (`recap/prompt.rs`) carries the choice (and, for `yesterday`, the date), asks for a short recap read at a glance in a narrow panel, with the limits of each choice (words per bullet, bullets per section or in all), to start a bullet with its id and not repeat the place the id shows, never to name a path, and to write in the language: `auto` is "the language most of the developer's prompts are written in", anything else as typed. The settings' instructions are appended after `Also:`. The heading of the dossier's list is one constant (`NEEDS_HEADING`) used by the dossier and the prompt, so the two cannot drift.

**Quotes are the exception, reversing #656** (which asked to quote every prompt literally): quoting each prompt made the recap a wall of text, and a link takes you to the full conversation. The prompt says what was asked in a few words and quotes a prompt only when it is a few words long.

## The cache

Each choice keeps its last result in `recap/<choice>/recap.json` (loaded once at startup, shown with its age). `now` is written again when it is older than 30 minutes when shown (`NOW_FRESH`); `yesterday` once per active day (the job compares the day it computes with the cached one and answers `Kept`, so opening the panel never runs an agent for a day already written); `7 days` once per local day. ↻ and `--fresh` always write it again. An override on the command line (`--agent`, `--model`, …) writes it again too, since the cached result was written with other settings. One run per choice at a time: a second click only shows the progress. An empty dossier runs no agent.

`Recap.v` is 2 (`RECAP_VERSION`): a result written by an older version, with the old prompt, is written again the first time it is shown (`store::due`), so an old verbose `yesterday` does not stay up for a day.

**A `now` that no longer matches what is open is written again** (#741, `recap/outdated.rs`, pure). The state a place had when written is in `recap.json` (`Place.status`, `Place.checks`); showing or asking compares it with what is open (`Present`: the open panes with a conversation key, the live pull requests, the server's boot):

- A conversation place is held by an open pane of the same agent with the same conversation, or, with no conversation, the same pane number while the boot is the server's. Its status now is the pane's (`open` when it reports none) and `None` when no pane holds it.
- Only the places the text names (`[id]` in `text`) are compared: the dossier holds a place for every conversation of the day, and closing an agent tab the text never mentions must not cost a run.
- It has changed when it needed you (`waiting`, `failed`, `pending`) and its status now differs (answered, closed, another status that needs you), or it was open and is closed now. A change among `working`, `done`, `idle` and `open` is not a change: those flip on every turn, and "in progress" means the line of work, not the agent's turn.
- A pull request place has changed when its checks were failing on an open or draft pull request and no open workspace has that pull request failing now.
- `new` is true when an open pane needs you and no place held by it had that status, or a pull request fails in a workspace some place of the recap names and no failing place has it. New pull requests are limited to the workspaces the recap names so that the check stays in step with what the next dossier would include; otherwise it could ask for a rewrite forever.

When any of that holds, `recap_due` is true, and showing or asking passes `fresh = true`: `run::current` would otherwise answer `Kept` from the time rules alone. Nothing reruns while the panel only stays open: a run costs tokens and an open panel would run all day; the panel marks what changed and a click on `now` or ↻ writes it again. A conversation started after the recap was written does not make `now` outdated unless it needs you: it waits for the 30 minutes or ↻, which keeps the check from firing on every new prompt.

## The panel

A side panel in the column the Changes, Files, TODO and Flow panels share (`Side::Recap`; one at a time, `Esc` closes it), not a dialog, so it stays open while you click from one line of work to the next. Header: ` Recap   now · yesterday · 7 days   ↻  × `, the current choice cyan and bold. Under it one status line: the date, agent, conversations, tokens and age; the progress while it runs (the previous result stays visible); or the failure in red with ` retry `. The body is the recap's Markdown: headings bold, bullets `▸`, quotes in soft text, and every `[c3]` or `[p1]` a link in cyan (muted and struck through, in one piece with the spaces between its words, when its place changed since the recap was written; the status line starts with a yellow `outdated · `, first because the line is cut at its end, whenever `now` no longer matches what is open: a place changed, or something new needs you and there is no link to strike; a running or failed state keeps its own line), drawn as `project › workspace › tab` or `#212`, wrapped by our own word wrap so each link keeps its row and columns (`highlight::markdown` drops which span is which link). Geometry and hits come from the same `rows`.

- A link goes to the live pane whose agent and conversation match (`jump_to_pane`), or, for a place with a conversation, the pane it names while its `boot` is this server's; else to the workspace whose path matches, in the project whose path matches; else to the project; else a toast (`api › rate-limit is closed`). A pull request opens the workspace's pull request dialog when the workspace is open, else its address is copied.
- Opened from the footer button ` Recap ` (beside ` Worktrees `, since it belongs to no project, which is also why Worktrees is there), the icon bar (an icon right after Worktrees', codicon `history`), the compact projects menu and `s` in the keys menu (`r` is rename tab). It is not restored after a restart (no field in `session.json`): it reopens with one click and its results are on disk.
- It shares the right column, its width and its drag, and takes the whole screen below the bar in compact mode, like the others.

## Settings

Settings › Agents › Recap: `recap_agent` (auto: the default agent when it can write a recap, else Claude Code), `recap_account` (that agent's default account), `recap_model`, `recap_effort` (low by default: quick and cheap), `recap_language` (auto) and `recap_instructions`. Each is one flat key, so the `config` request has them. All but `recap_account` are shared by *share settings* (#414); the account is personal. Changing the agent clears a model, an effort and an account the new agent does not have. An effort that the agent does not know is ignored when the run starts.

## External clients

**Following a place** (#664): `conversation` on a pane in `status --json`, `watch` and `view` (see Commands for scripts and agents › `status`) is the id `places` gives, so a client takes the first pane whose `agent` and `conversation` match, then `pane` while `boot` is the server's, and the conversation is found after a restart, or `agents close` and `agents reopen`, moved it. Nothing changes in the window, which reads `recap_live_pane`. Where the two differ, deliberately left: a pane's `agent` is `null` while nothing reports its state (Gemini CLI with its window title off, Vibe before its first report), where the window compares the reader's kind, so the docs tell a client that `conversation` alone names such a pane, rather than filling `agent`, which would change a field scripts already read; and a place with no `conversation` (opencode) goes straight to its workspace in the window, without trying `pane` and `boot`, because `recap_live_pane` returns early, where a client can try them. Reading the agents' transcripts or the journal from the client was rejected in the issue: private files, and no use on another machine.

The `recap` request (feature `recap`, additive; `cornercase recap` refuses an older server by name) takes `range`, `fresh`, `dossier`, `agent`, `account`, `model`, `effort`, `language` and `zone`. A cached current answer comes at once; a run of that range already going is waited for when the options are the same and refused with `busy` when they differ; otherwise it starts one and waits. A client that leaves drops its request and the run fills the cache. Every key of the answer is always present, `null` when it has no value, as `usage`'s is. It gained `outdated` (a `now` that no longer matches what is open) and `changed` (the ids of the places that changed), and each place gained `status` and `checks`, in #741: additive, always present, no feature of its own (an absent key says the server is older, as with `conversation` on a pane). The request's arguments and the `recap` event did not change. Asking for `now` again writes an outdated one again, so a client meets `outdated: true` after a run that failed. `dossier: true` answers with the dossier and its `places`, runs no agent. `events` reports `{"event":"recap","state":"started|finished|failed","range","agent","error"}` to every reader that did not filter by `--pane` (like `dropped`): a few events a day need no opt-in. `server.log` has `recap run` job lines (range, agent, outcome) and never prompts, text, instructions or transcript paths.

## Tests

The journal, ranges, dossier, the outdated check (`recap/outdated/tests.rs`), text and cache are pure and run on every OS; the agents' readers are tested against real streams cut down (`tests/fixtures/claude/2.1.318/recap-*.jsonl`, `tests/fixtures/codex/0.164.0/recap-*.jsonl`), and the runs with `test_util::fake_program` fakes named `claude` and `codex` (`fake_program` also records the folder it ran in, `.cwd`). Nothing runs a real agent.

**The panel's and the request's tests give the window a zone at local noon** (#783). `yesterday` is the last local day before today with activity, and `recaps()` (`app/tests/recap_panel.rs`) writes its prompt ten minutes before now. In the host's zone that prompt fell on yesterday between 00:00 and 00:10, so the two tests that expect nothing to sum up ran the agent then. `recaps()` now sets the window's zone (`set_queue_zone`, which the server sets from the window in production) to the fixed offset that puts the test's start at local noon (`noon_zone`). A prompt minutes old is then today and one 48 hours old is the last active day, whatever the hour and the host's zone. Rejected: a clock in `App` that tests could set (code only tests need), and skipping or waiting near midnight (a test whose result depends on when it runs).

## Rejected

- One `journal.jsonl` (see above); importing the agents' past history (the journal starts when this version does); a dialog instead of a panel; a plain recap without an agent; sending a recap to Telegram or Discord or writing it on a schedule (a routine, #653, could do that later); other machines (#539, #547).
- **cornercase drawing the Needs you section itself at each draw**: it would parse the agent's sections in whatever language it writes, the text would have a second writer, items the agent never saw would need cornercase's own words, and `text` would no longer be the agent's answer.
- **Dropping outdated bullets in silence**: it hides what the user may still want; a struck link says what changed.
- **Rewriting while the panel stays open**: it costs tokens all day.
- **Workspace ids (`[w1]`)**: grouping by workspace uses the latest conversation's id instead.
