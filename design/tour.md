# Tour

Code: `tour.rs`, `tour/steps.rs`, `app/tour_card.rs`, `app/help_menu.rs`, `ui/tour.rs`, `control/tour.rs`, `app/control/tour.rs`, `cli/tour.rs`, #400

- **Why**: a new user lands on the logo and `+ New opens a folder`; nothing says what projects, workspaces and the agents section are for, or that the point is several agents side by side. A guided tour shows where things are and gets them to a first prompt, and a catalogue of short tours covers the rest, all reachable again from ` Help `. Shaped like JetBrains' onboarding tour plus its catalogue, with VS Code's rule that a step that asks for an action completes when the action happens. English only, like the rest of the app.
- **The model** (`tour.rs`, pure, no `app` or `ui`): a `Tour` (`id`, `title`, `docs`, the address of its docs page) is a list of `Step`s (`id`, `title`, `text`, `target`, `done`, `show`). `Target` names a part of the screen, never a position: `NewProject`, `Projects`, `Workspaces`, `NewWorkspace`, `Tabs`, `Pane`, `Agents`, `Settings`, `Help`, the footer and icon bar buttons, `None`. `Done` says what completes a step: `Next` (explanatory steps: the ` next ` button) or an action read from the app, `ProjectOpened`, `WorkspaceMade`, `TabOpened`, `PaneSplit`, `AgentStarted`, `PromptConfirmed`, `Panel(side)`, `Opened(dialog)`, `TodoAdded`, `AgentsSection`. The app hands the model a plain `Facts` (counts of projects, workspaces, tabs, panes and agents, prompts confirmed, the side panel and dialog showing, the TODO count, the switches that matter); a step records the facts it started with, and `Done::met(start, now)` decides, so every rule is a unit test and no code path has to remember to announce an action. The steps are data in `tour/steps.rs`: the core tour (seven steps, below) and thirteen short ones of three to five steps. A catalogue step that would need a fragile highlight (Telegram, plugins, scripts) has text and its docs link instead.
- **The core tour**: Projects (completes when a project opens; a folder cornercase was started in is already one, and the step only explains it), Workspaces (offers `+ New` → new workspace in a repository root; completes when one is made, or by ` next ` elsewhere), Tabs and panes (completes on a new tab or a split), Your first prompt (below), Agents and their status (the icons, and a ` turn on ` button for the agents section, the one setting the tour changes, and only on that click), Essential settings (names the rows and opens Settings › Agents, never changing one), Where to go next (Help, the docs, the catalogue).
- **The first prompt** goes through the `start` request as an internal client of its own range (`1 << 60`, beside the TODO panel's `1 << 61`), so refusals, the trust prompt (the card says what it is and leaves the answer to the user) and the launch are exactly a start's. The card shows the agent it will start (the `agent` setting, else the first installed one, `agents::installed`; none installed says how to install one and links the docs) and a field with a prompt idea for the project (`explain this repository's structure`, and two more behind ` another idea `), a `todo::editor::Editor` that takes the keys only while it is clicked, like the TODO field (any press outside gives them back, `Esc` drops the edit). ` start claude ` sends it. The step completes when that agent records the prompt (`context::Pane::prompted`, the confirmation `send --enter` uses).
- **Sections**: a step about a part of the window opens it (`Show`: a side panel, Issues or its Queue tab, Search, the keys menu, a page of Settings, the Help or Remote menu), since reading about a panel that is not there teaches less than looking at it. The tour closes on next, back, skip or end only what it opened itself, never what the user had open, and two steps in a row on the same section keep it open rather than flicker. It opens a dialog only when no overlay is open and a panel only when no panel is, so it never replaces the user's form, menu or panel; then the step only points. A step whose `done` is opening that section (`Open it`) leaves the opening to the user, or it would complete at once; the steps after it open the section if it was skipped (`tour::tests` checks the steps keep to this). The Remote steps open the Remote menu, not the browser dialog, because that dialog makes a pairing code. The Flow panel opens only while the workspace has a run, since without one it has nothing to show. The agents section is a setting, so its step keeps the ` turn on ` button rather than opening it. Usage has no step. With `card: false` nothing opens: a UI drawing its own tour reads `show` and decides.
- **A card, not an overlay**, like the star prompt (`View::tour`, drawn after everything, overlays included, so `Esc` closing a dialog never hides it): it takes only the presses on its own rect and gives every key to the pane, except while its field is focused. Buttons: ` back `, ` skip ` (leaves the step undone and goes on), ` next ` (only on explanatory steps, or ` skip ` stays the way past an action), ` docs ` (copies the step's docs address through OSC 52 and toasts it, since the server may be elsewhere) and ` end tour `, plus `n/7` in its title. It sits at the bottom right, or the opposite corner when the part it points at is under it (`ui::tour_area` takes the target's rect, so drawing and hit testing agree). Shared by every window, like overlays.
- **Pointing**: `ui::tour_target(areas, target)` turns the `Target` into a rect from the `Areas` the drawing and hit testing already use, with compact mode's own (` ≡ `, the menu's rows, its footer thirds), so the same step works in every layout. A button is drawn in the selection's cyan fill; a region (a list, the pane, a column) gets the cyan `▌` rail down its first column on blank cells, as `draw_rail` does. A target that is not on screen (the agents section off, a folded group) points at nothing and the text says where it is.
- **When it shows by itself**: only on a new install, decided once when the server starts (`tour::first_run`: no `session.json`, no `stats.json` and a `star.json` with nothing in it), and then only on the first window, so a headless `start-server` never spends it. An install from before the tour, the first time it meets one (`tour.json` missing), gets the toast `new: a guided tour, in Help` once, never the tour. `tour` in `config.json` (Settings › UI, on by default) turns showing by itself off; the rows under it are **start the tour** and **reset tour progress** (at once, with a notice: progress is easy to make again and nothing else is lost). The tour also opens from Help, the keys menu (`h` opens the Help menu) and `cornercase tour`.
- **Progress** is `tour.json` next to `session.json` (`paths::tour`, version 1): whether the core tour was offered, whether the update toast was shown, and per tour the steps done and whether it was finished. A missing, corrupt or other-version file reads as empty; on an existing install that means the toast once, not the tour. Reset empties the steps and the finished marks (one tour, or all), and keeps the offered and toast flags, so a reset never makes the tour pop up by itself.
- **` Help `**: right-aligned on the footer row under ` Usage ` / ` Remote ` (the ` Quit ` row), where ` Remote ` sits on the row above (`ui::help_button`, the geometry `remote_button` uses, on the quit rect), always shown; in compact mode on the Quit third when there is room; in the icon bar the slot under Remote (codicon `question`, `Item::Help`, so the bottom-up order is Quit, Settings, Usage, Help, Remote, update); the Quit button keeps the rest of its row (`ui::quit_button`), so drawing and hit testing agree. A click opens a menu (`Overlay::Menu`, `MenuAction::Help`): **tour** (continues where it stopped, or starts over once finished), **catalogue…** (a submenu of the tours with `✓` on finished ones and `n/m` on started ones), **docs** (copies the docs address), **keys menu** (only with a prefix key set) and **report a bug** (copies the new issue address, through OSC 52 like the star prompt).
- **Through the server** (AGENTS.md rule): the `app` feed gains `tour` (`active`: tour and step ids or `null`, `offered`, and per tour its steps done and `finished`), additive. One request, `tour`, tagged by `action` like `queue`: `list` (every tour and step as data: ids, titles, texts, the target's name, what completes it and the section it shows, with the progress, so another UI draws its own tour from the same steps), `start` (a tour id, default `core`, optional step), `next`, `back`, `skip`, `end`, `complete` (marks a step done, for a UI that watches its own actions), `reset` (one tour or all). `start` and the moves show the card in the window too; a UI drawing its own tour can pass `card: false`. Feature `tour`; an older server refuses the name. `cornercase tour [list|start ID|next|back|skip|end|reset [ID]] [--json]`.
- **Left out**: videos, telemetry, sample projects, translations, and the landing's simulation playing the tour (it shows the ` Help ` button and its menu).
- **Checked**: the model (steps, completion, progress, reset, first run) in `tour::tests`; the card, its clicks and keys, the prompt field, the sections it opens and closes, Help and the catalogue in `app::tests::tour`; the request and the feed in `app::tests::control_requests::tours`; snapshots of the card, the prompt field, compact mode, the Help menu and the icon bar in `ui::tests::tour`; fixtures `tour/tour.json` and `control/tour/v1/`. The first prompt was not checked with a real agent: the test starts `/bin/cat` as the agent and checks a tab opens with the note.
