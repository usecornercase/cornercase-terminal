# Bot secrets (#877)

A bot works for the user behind logins, so it needs a password or a token somewhere better than `bot.md`, `memory.md` or the chat (all plain text, all read by every agent of the user). Each bot has **secrets**: named values the user saves for it, kept encrypted, readable only by that bot's own turn through `cornercase bot secret get NAME`. A bot that lacks one asks the user for it (#878, see [Asks](asks.md)). Code: `bots/secrets.rs` (the file, the key, the cipher, the rules, the redaction), `app/bots/secrets.rs` (the operations), `app/bots/secrets_dialog.rs` (the window), `cli/bot/secret.rs`, the four actions of `control/bots.rs`.

## The model

- A secret is a `name` (1 to 40 characters of `a-z`, `A-Z`, `0-9`, `-` and `_`, unique in its bot ignoring the case of its letters, `secrets::same_name`: `GITHUB_TOKEN` and `github_token` are one secret, kept with the spelling saved last, and `get`, `remove`, an ask and a give find it however it is cased; upper case was refused until 2026-11-23, which turned away the usual spelling of a token's name, and telling two names apart by case alone would let a bot ask for one the person saved under the other), a value (1 to 8,192 bytes of UTF-8, kept as given, but for the one line break at the end of what `set` reads from standard input or a window's paste) and `saved` (UTC seconds). At most 20 per bot; the 21st is `conflict`, a replacement at 20 is not. A value is refused with its size, never cut. One value per secret: a login is two (`campus-user`, `campus-password`), or the user name goes in `bot.md`.
- **A name is logged only when it is one.** `get` carries free text before any validation, so a bot that passes a value for the name would have it in the request log and in the `not-found` text. `BotRequest::fields` logs `name` only when `name_refusal` passes and `name_bytes` otherwise, and `not-found` says `of that name` for what is not a name.
- **`secrets_unreadable`** (additive, under `bot-secrets`): `BotInfo.secrets` is 0 for an unreadable file, so `secrets_unreadable: true` tells a program that draws cornercase it is not "none".
- A name that equals its value (the name is then the secret) is logged as `name_bytes` by `secret set` too, in the request's fields and in the `secret set` line.
- The value is `issues::Secret` end to end: its `Debug` prints `Secret(..)`, so no `{:?}` of an entry, a request or a list shows it (`Entry`, `Kept` and `Key` print by hand, and a test checks them). It is never in `bot.json`, `bot list`, `status --app`, an event or the log.

## The file and the key

- **One encrypted file per bot**, `bots/<id>/secrets`, `0600`, written through `persist::write_bytes` (`Kind::Private`): `magic || nonce || ciphertext+tag`. The plaintext is `{"secrets": [...]}`; the cipher is **AES-256-GCM from `ring`**, with a 96-bit random nonce from `os::random` on every write and **the bot's id as the associated data**, so a file copied into another bot's folder does not open. `ring` was already in `Cargo.lock` through rustls (`tungstenite`, `ureq`), built on the three systems, so it adds no package; no cipher is written here. XChaCha20-Poly1305 (RustCrypto, about eight new crates) was the other candidate; a random 96-bit nonce is safe at this write rate (a write is a `set` or a `remove`, far below the 2^32 limit for one key).
- **Inside the bot's folder, not outside it.** `bot remove` deletes it with the folder, a rename keeps it (the id stays), it moves with the bot, and one list, `Ask::protected` (`bot.json`, `chat.jsonl`, `secrets`), keeps the agents from writing it (see The agents' rules). A bot can make a *directory* named `secrets` before the first save; that only breaks its own `set`, so it has no rule.
- **The key is a file**: 32 random bytes, `0600`, `bots.key` beside `session.json` (`x.bots.key` for `CORNERCASE_SOCKET=x.sock`, so a dev server has its own; `secrets::key_path` appends `.key` to the bots folder's path), made with the first secret and **never overwritten**: it is written to a temporary file (with the owner-only mode, and on Windows an owner-only ACL set before the bytes go in, not tried live there), flushed, and installed with a hard link, which fails when the destination exists (on a filesystem that refuses hard links, such as FAT or some network mounts, the key is created in place with `create_new`, and a partial one is removed), then the folder is synced so the key entry is on disk before any ciphertext is written (a no-op on Windows). A key that appeared since the server started (a restored backup) is left intact and the `set` is refused with `restart cornercase`. A server started with a custom `CORNERCASE_SOCKET` equal to that path no longer unlinks it: binding refuses to remove a regular file (Unix; Windows keeps its old behaviour). A key file that exists but cannot be read or is not 32 bytes is `Broken`: every `set` is refused and the file is left as it is. `bot secret list` says `key: file`.
- **A broken or lost key is not fixed by `remove --all`.** `remove --all` deletes a bot's *secrets file*, never the key, and the server keeps its `Broken` state until it restarts. To read the existing secrets again, restore the known-good `bots.key` and restart cornercase. If the key is lost, the secrets cannot be read at all; deleting `bots.key` and restarting makes a new one with the next `set`, and **every bot's** existing secrets files then stop opening (each shows as unreadable until its `remove --all`), so do it only when they are lost anyway.
- **What the key file protects**: copies. A backup, a synced folder, or an agent that searches the disk and reads `secrets` by accident, finds no value. It does **not** stop another program of the same user that reads both files, a `full` bot (it can run the cipher), or a `cornercase` bot that reads the key through `git -C <folder> diff --no-index --binary` or `cornercase files read`: a `cornercase` bot "reads anything", and its `Read(<key>)` deny only stops the accidental read the issue names. Say all this in the docs.
- **The memory is the truth.** `Live.secrets` (`Kept::Open(entries)` or `Kept::Unreadable`) is read once, with `bot.json`, in `set_bots_dir`; the file is written on `set` and `remove` and memory is updated only after the write succeeded. `BotInfo` is built up to every 500 ms for `status --app` and #876 rejected file reads there.
- **The disk is checked before every write.** Memory is the truth, but before a `set` or a named `remove` the file is read again and must equal what the server holds; a file that stopped opening, or changed, after the start is refused (`changed on disk since cornercase read them`), never saved over or erased, so only an explicit `remove --all` can erase it. A window's ` remove all ` also compares the list it asked about with the one it deletes, and refuses (`the secrets changed since you asked`) when a secret was saved meanwhile.
- **A file that does not open** (another key, a damaged or cut file, a directory, a FIFO or a file over 4 MiB, opened non-blocking and regular-file-only like `bot.md`) is `Unreadable`: `list`, `get`, `set` and `remove NAME` answer `failed` with `the secrets of <bot> cannot be read` (`list` adds `; cornercase bot secret remove <bot> --all starts again`), the file is never overwritten, and only `remove --all` deletes it. The server logs `secrets unreadable` at start.
- **Rejected for now: the system's store** (macOS Keychain, DPAPI, the Secret Service). A server started with no terminal may not reach the Keychain item, and the Keychain ties an item to the binary's signature, which changes with every release (an ad-hoc signed Rust binary changes its code-directory hash on every build), so each update would prompt or fail; neither was checked live. DPAPI and the Secret Service are per user, so they add nothing against the user's other programs. `list` already says which store is in use (`key: file`), so a later store can say `key: keychain` additively.

## Who may do what

The server decides at connect, from the connecting process, as for the boundary (`bots/boundary.md`): `BotClients` keeps **owners** beside the bound clients. A client is an owner of bot X when X has a running turn (a chat turn or a routine run) that **owns** the connecting pid: `Running::owns(pid)` is the root, a descendant by the parent walk, or what the lineage holds; `holds` is `owns` plus "the turn is contained". So a process in a contained turn's tree is owner and bound, one in a `full` turn's tree is **owner only** (no boundary and no cleanup is added to `full`, as #856 promises), and one found only by `CORNERCASE_BOT` in its environment, or an unreadable peer while a contained turn runs, is bound only.

- **A grant lasts while the bot answers.** Owners are revoked only when the bot has no running turn or run left (`bot_settled` returns early while it answers, then `revoke_owners`). A connection kept open past its own turn therefore stays an owner while a concurrent turn or run of that bot answers. `get` also needs the bot to be answering. A revoked owner is not a person: it becomes a *former* owner, still known as that bot's connection, so after the turn `get` stays refused and `set`, `remove` and `list` of another bot stay refused for it (a `full` bot's process has no other record, and would otherwise pass for the user).
- `get NAME` is answered **only to an owner**, with its own bot's secret. The user's shell, a plain client, the window, another bot's turn and a bound-only client are `failed`, `only the bot itself reads its secrets`. The environment is never trusted for `get`: any program of the user can set `CORNERCASE_BOT=<id>` on itself (that is safe for the boundary, which only refuses more, but would grant here), and the unreadable-peer rule that fails closed for the boundary must not grant either. This is also the issue's macOS wording: a command not seen as the bot's is refused (#856's gap stays).
- `set` and `remove`: refused to any bot connection, owner or bound (`a bot cannot save or remove secrets`). `list BOT`: refused to a bot connection when BOT is another bot (`a bot reads only its own secrets`), after resolving BOT, so an unknown one is `not-found`. All refusals are `failed`: #856 rejected a new code because strict clients read `Code` as an enum. The rules are enforced in the secrets handler, not in `bot_writes`, whose early return for non-bound clients would miss `full` owners.
- `cli/guard.rs` says the same before the server is asked (`set`, `remove`, `list` of a bot that is not the one running it). A known false positive: a bot listing *itself by its name* rather than its id is refused (the brief teaches `list` without BOT), like `flow import`'s.

## The agents' rules

`Ask::protected` holds `secrets`, so the three agents that have `cornercase` access cannot write it: Claude's `Edit(<folder>/secrets)` deny, Gemini's policy deny and Copilot's `--deny-tool write(<folder>/secrets)`. Gemini's deny is a case-insensitive *substring* match on `file_path`, so a Gemini bot also cannot write any path that contains `secrets` (a safe narrowing). Codex, opencode and Cursor are `full` only, so nothing changes for them.

A path that holds a comma cannot be written into Claude's comma-separated `--disallowedTools`, so a Claude `cornercase` turn whose folder or key path has one does not start (`holds a comma …`), failing closed. `Ask::unreadable` holds the key's path, and Claude's denied list gets `Read(<key>)` (the `//abs` form of `rule_path`) for `cornercase` access. Gemini and Copilot read only their own folder. **The deny of `Read(<path>)` was not checked live** with a real `claude` (the earlier rules for `Edit(<path>)` were): it was left unchecked on purpose, it costs a real run, and it is not a boundary anyway (above). The argv tests pin it.

## What cornercase never writes

`bot_append` is the one funnel every chat line goes through before it reaches `chat.jsonl`, the shown chat, the events, `say --wait`, the toast and the notification. It replaces each value of the bot's, of at least 6 bytes (shorter ones match too much), **longest first**, by `[secret NAME]` in the lines that can carry one: `step`, `bot` and `error`, and the text and body of `started`, `finished` and `waiting`, which can echo an agent the bot gave a value to. `you` (the user's own words) and `notice` (fixed texts) are left alone. A routine run's block goes through the same funnel, and the places that read the raw `Ran.text` afterwards (`queue show`'s `result.text`, what the chat is told, a failed run's reason) read the redacted line's text. The cost is a few string scans per line.

Redaction matches the *original* text once (longest value first, a span taken once) and never scans what it wrote, so names that hold values cannot multiply. A value replaced or removed while a turn or run is answering stays redacted until that bot is idle again (`Live.retired`, dropped by `bot_settled`), so the answer that already holds it is still redacted. It is a convenience, as Playwright MCP says of its own `--secrets`: a value the bot encodes or splits passes, a value removed while the bot still holds it is no longer replaced, and the agent's own session file keeps the plain text (a bot's session must be resumable, so `--no-session-persistence` is not an option). `markdown::warm` still warms the unredacted text in server memory (a cache miss only).

## The window

- **A Secrets dialog of its own**, not rows inside the form: the form saves on ` save `, a secret saves at once, so rows inside it would need a scrolled list and a cancel that cannot undo. It is the routines dialog's view and model (`ui::BotRoutines` with `new: "+ secret"`, `RoutineRow.detail`, `Button::Replace` and `RemoveAll`, `bots::routines::Dialog` with the secrets' positions as ids), so the two share their key and mouse code (`bot_list_key`, `bot_list_mouse`): name and `saved <when>` per row, ` replace… ` and ` remove ` on the selected row, ` + secret ` and ` done `, `key: file ·` and what a secret is in the hint. Empty and unreadable (one row, ` remove all `) say so.
- It opens from the bot's ` ⋯ ` menu (`secrets…`) and from a **Secrets row of the edit form** (a summary such as `2 saved: campus-user, campus-password` and ` manage… `, only when editing). From the form it keeps the form beside it (`back`), so closing it gets back to the form with its unsaved edits, and a cancelled form cannot leave a secret half-saved.
- Add is two steps (the name, then the value) and replace one; a paste holding a tab or another control character is refused with a reason rather than saved changed; the value goes into a field drawn as bullets (`Editor::masked`, as Settings' token rows), a paste's last line break is dropped, and the field's right-click menu has no copy or cut while it holds a value (`Overlay::hides_text`). Remove asks first (`Confirm`, dangerous). The three overlays are one variant, `Overlay::BotSecrets(Secrets)`, an enum of list, entry and removal, each with its `back`.
- The card has a `secrets` row under the access row (`2 secrets`, or `cannot be read` in red) when there is one. The simulation on the website has no secrets and no bot menu or edit form, so it is unchanged.
