# Bots: the boundary

Part of [Bots](../bots.md). What a bot's connection may type into, change, stop or have cornercase write, a project's git (the agent's own per-folder rules and `--output`), and why.

## The boundary (#856, #866, #867, #880, #883)

Under `cornercase` access, **a bot writes prompts to an agent, and nothing else**. `keys` and `input` are refused outright (`a bot cannot press keys or type as a window does`, see The rest below). `send`, `todo send`, `paste-file` and `held --send-now` are refused into a pane that runs no agent, into an agent that waits for an answer (`Status::Waiting`), that shows a dialog, a panel or its shell mode (`Term::dialog`), or that is starting or resuming (`resume_holds`), whatever `--force` says; `send` and `todo send` are also refused a text that starts with `/` or `!` after leading whitespace, or that the pane's agent takes as its own command (`Known::local_command`), and `send` with no text (Enter alone is a key). `new-tab` or `split` with a command are refused (their command is typed into the new shell). The same requests from any other client work as before. The refusals have code `failed` (as `send`'s others), exit 1, and those about the pane start `a bot can only type into a pane that runs an agent` (`boundary::HEAD`).

- **Owner and bound** (#877). The server also records which bot's turn *owns* the connecting process (`BotClients::owners`, `Running::owns`): the root, a descendant by the parent walk, or what the lineage holds, with or without containment. A `full` bot's turn is not contained, so its commands are owners but not bound: no boundary and no cleanup is added to `full`. The secrets (`bots/secrets.md`) answer `get` to an owner only, never to a connection found by `CORNERCASE_BOT` in its environment or by the unreadable-peer rule, which grant nothing.
- **Who is a bot is the connecting process, decided once per connection, at connect.** `Server::accept` reads the peer's pid from the socket (`os::socket::peer_pid`: `SO_PEERCRED` on Linux, `LOCAL_PEERPID` on macOS, `SIO_AF_UNIX_GETPEERPID` on Windows) and `App::client_connected` stores `client → bot id`. A connection a turn opened stays a bot's after its turn ends. **It fails closed**: while a contained turn runs, a connection whose peer pid cannot be read counts as that bot's (a real client is alive and readable while it waits for its answer). A pid that is read but whose process cannot then be inspected falls back to the walk and the environment: a gap. A Windows `Lineage` whose Job cannot be made (or the child assigned to it) fails the turn instead, closed. A process is a bot's when a running contained turn holds it (`Running::holds`: its root, a descendant by the parent walk, or on Windows a process of the turn's Job), or when its own environment, read by the server from the OS, sets `CORNERCASE_BOT` to anything but a `full` bot's id (an unknown id counts: the check only ever refuses more). It is logged as `a bot's client`, with the bot's id and never a text.
- **Why contained turns.** Claude Code runs every Bash command in a session and process group of its own (checked live), and a command sent to the background with `( … &)` is reparented to pid 1 once its shell exits, so neither a group nor a plain parent walk reaches it. On Linux the turn's root is a child subreaper (`prctl(PR_SET_CHILD_SUBREAPER)` in `pre_exec`), so the orphan is adopted by it and the walk still finds it. On Windows nothing is reparented, so the root is in a Job (`os::process::Lineage`, `IsProcessInJob` asks), with no `BREAKAWAY_OK`: Cygwin and MSYS2, so Git Bash, add `CREATE_BREAKAWAY_FROM_JOB` when the job allows it. **macOS** has no subreaper: a command sent to the background whose shell exits is reparented to launchd and is not seen, unless it keeps `CORNERCASE_BOT` in its environment (the fallback above), and cleanup does not reach it either.
- **What "runs an agent" means** is the pane's foreground program now (`agents::detect` over `Term::foreground_args`, what the agent watch and `status`'s `program` use, so also an agent the user put in `agent_commands`), not `status`'s `agent`, which keeps an agent that exited back to its shell while its finished status is held. So a pane whose agent exited, or that is resuming its agent after a restart, is refused. A machine's pane is out of reach: no typing request takes `--machine`.
- **Where it runs.** The gate sits at the top of `handle_request` for a bot's client (`boundary::bot_writes`), resolving the target as the handler does. The writes that happen later are checked again when they happen, keyed on the pending request (kept when its client leaves, the keys in `Clients::bots` (`boundary::BotClients`)): a held send when it goes out (`held::release`), `paste-file` when its stored file is pasted (`file_stored`), and the Enter cornercase presses after `send --enter` (`drive_launches` ends that launch, answers the request with the refusal and leaves the pasted text unrun on the shell's line). The Enter is also not pressed when the agent started waiting, or shows a dialog, a panel or its shell mode, in between (`boundary::takes_a_bots_enter`): the launch's submit stage writes its first `\r` once the screen is quiet without looking at a dialog, and only its later Enters are left to the confirm stage, which reads it. The refusal is the one `types_into` would give. What remains: a bot's pasted text can land on a shell's line in the instant an agent exits (its Enter is not pressed, but a shell without bracketed paste runs the lines of a text of several lines), and a question cornercase does not see (below).
- **`full` bots are unchanged** on the server: they can run anything themselves, so refusing them adds friction and no safety. Their turns are not contained. The command line's guard reads only `CORNERCASE_BOT`, which carries no access, so its rules (Bots › The guard, the #866 ones included) refuse a `full` bot's commands too; its brief says so, and it may run them without the variable.

**Also refused to a bot's connection** (it could lift the boundary itself): `bot new` with an access other than `cornercase` and `bot edit` with any access (`a bot cannot change a bot's access`), `bot say` to a bot with `full` access, `bot setup` of one, and any `bot edit` of one, `--about` writing its `bot.md` and `--memory` its `memory.md` included (`a bot cannot write to a bot with full access`), and a `view` or `view-set` naming a bot (`a bot cannot show a bot's chat in a view`, #869: naming one silences that bot's answers for as long as the view's connection lives, which a process a turn left behind can hold; clearing one is allowed, and so is a `view-set` that leaves the name alone; but one that turns `--visible` a view still naming a bot is refused too, since that is what makes the name count), and every write to the settings (`config` other than get and search, `config-import` applied: `a bot cannot change cornercase's settings`), since `agent_commands` decides which programs count as an agent.

**What is still not a boundary** after #866 (each is said where it belongs): the user's own Claude allow rules (`--setting-sources user` loads them on top of `--allowedTools`); `config export --to`, `update`'s own install, `plugin` and `--remote`, which only the command line's guard and the agent's allow rules stop (a process that drops `CORNERCASE_BOT` is not stopped); a question cornercase does not see (opencode never reports waiting, a prompt that appears between the check and the Enter, agents with no input-box check), which a bot's prompt can answer; the pasted text in the instant an agent exits (above); on macOS, the orphan (Bots › A turn, Not closed, and The rest below); moving what the window shows (`focus`, `go`), which can put the user's own typing in another pane; and a repository already on disk whose git config runs a program when it is opened as a project. Work you would give an assistant at your keyboard is the right size for a bot.

**Rejected**: a request field filled from `CORNERCASE_BOT`, or a token in the turn's environment (the bot controls its environment, and a token is readable by any process of the user); the turn's process group or session (every Bash command has its own); a socket per turn (the bot can name the main one); a wrapper process as the root (tests run turns with fakes, and macOS could still not adopt orphans); `status`'s `agent` as the test; a new error code (strict clients read `Code` as an enum); applying it to `full` bots.

**Checked live**: on Linux with Claude Code 2.1.325 (2026-11-14), every Bash command runs with `pgid = sid = ` its shell's pid, and a command sent to the background is reparented to pid 1 once that shell exits. Nothing was checked on macOS or Windows (the Job code was read against `windows-sys` 0.61.2 only), and no real turn ran: the tests use fakes.

**What stops or replaces the server (#867).** `bots::SERVER_STOPS` is one table: each entry maps a command the guard refuses (`kill-server`, `restart`, `update`) to the names it asks the server by (`asks`: `kill-server`; `restart` and `restart-when-idle`; `update-install`). The command line's guard reads the commands, the agents' denied rules read them through `Ask::stops` (so their argv did not change), the boundary reads `asks` for requests (`bots::stops_server(command.name())`, `Gated::ServerStop`), and `App::refused_stop` reads them for the two protocol messages that are not requests. All use the text `a bot cannot stop its own server` (`bots::STOP_REFUSED`); a request gets code `failed` (exit 1), a message `ServerMessage::Rejected`.

- `kill-server` and `restart` are `ClientMessage::KillServer` and `ClientMessage::Restart`, which `Server::message` used to obey from any connection, `cornercase proxy` and a command whose environment lost `CORNERCASE_BOT` included. `refused_stop` (called at the top of `Server::message`) answers a bot's connection `Rejected` and logs `a bot's message refused` (client, bot, what it asked; never a text). **The connection stays open and stays a bot's**: `Server::reject` removes the client, `App::forget` would then forget it was a bot's, and a second stop message already queued behind the first would be obeyed. For the same reason `Server::message` drops every message from a connection that was accepted (its id is below `next_client`) and is no longer in `Server::clients` (a stop queued behind a rejected `Hello`, a stream's end or a detach would otherwise find no bot to refuse, and a queued request would skip the typing boundary too). The command line (`client/server_process.rs`, `rejection`) stops reading at the first `Rejected`, since the server no longer closes, and `kill-server` and `restart` print it as an error (`restart` falls back to `kill-server` on a `Rejected`, as for a server of another build, and that one is refused too).
- **Not in the table**: `update-check` (changes nothing), `account-restart` (restarts agents, not the server), `start-server` (only answers that the server runs), and `machines update` (installs on and restarts another machine's server; refused to a bot since #866 with the other machine writes, see The rest).
- A `full` bot's connection is not refused by the server, as for the rest of the boundary; the guard and its agent's denied rules still refuse its commands.

**What a bot names for cornercase to write (#880).** The rule: cornercase writes nothing at a path a bot names.

- `config export --to FILE` is refused by the command line (Bots › The guard, rule 5, also on each `requests` line), because the command line's process writes the file and the server never sees the path. So it rests on the guard and on the agent's allow rules (`Bash(cornercase:*)` does not match `env -u CORNERCASE_BOT cornercase …`): a process of the turn that drops `CORNERCASE_BOT` is not stopped by cornercase, and the same holds for `update`'s own install. Without `--to` the settings are printed, and that is still allowed.
- `clone URL [FOLDER]` is refused by the server for a `cornercase`-access bot (`Gated::Clone`, whatever the folder): the server makes `FOLDER/<repo>` and any missing folders above it, so a bot could put a repository where another program runs it (`~/.vim/plugin/<repo>/x.vim`, which Vim loads); inside its own folder it would be a project inside the bot's folder, deleted by `bot remove`, which also breaks that project's worktrees; and the command line's default folder for a bot is its own.

**Rejected for #880**: allowing `--to` inside the bot's folder. The command line would need the bot's folder from the server, a canonical parent that exists, to refuse symlinks, `..` and the protected files, and an open that cannot follow a link swapped in. The bot gains nothing over printing the settings and writing them in its folder with its own tool.

**The audit of paths a caller names** (searched: every `value_name` FILE, FOLDER, PATH or SOURCE in `cli/args*`, the `PathBuf` fields of `control/`, and every file write in `cli/`; `config export --to` is the only write the command line does):

| Command (path argument) | What cornercase does with it | For a bot |
|---|---|---|
| `config export --to FILE` | the command line replaces FILE with the settings (0600) | refused by the guard (#880) |
| `clone URL [FOLDER]` | the server makes `FOLDER/<repo>` and the missing folders above it, clones, copies the `--file`s into it | refused by the server, `cornercase` access (#880) |
| `bot say --file`, `start --prompt-file`, `flow save FILE --check`, `flow import SOURCE --preview`, `config import FILE`, `theme FILE`, `start-server --theme`, `paste-file FILE`, `clone --file PATH --from FOLDER`, `clone --list-ignored`, `files list FOLDER`, `files read PATH` | read only; `files` runs git only in the workspace's own folder, never in the named one | allowed: a bot reads anything |

**A window (#883).** A `cornercase`-access bot's connection may send requests and nothing else a window sends. `Bash(cornercase:*)` covers `cornercase proxy`, which relays raw protocol frames from its standard input, so a bot could send `Hello` and then `Event`s: its keys and clicks reached the window as the user's own, past the typing boundary (keys into a shell pane) and the update dialog's restart, which the stop refusal never sees. `App::refused_window` refuses `Hello`, `Event`, `Graphics`, `Activated`, `OpenFailed`, `Machines` and `Tunnels` with `a bot cannot attach as a window` (`bots::WINDOW_REFUSED`) and logs `a bot's message refused`; `server/bots.rs` answers `Rejected` and closes the connection (`Server::reject`, as for a window of another build).

- `boundary::window_name` matches every `ClientMessage` without a wildcard, so a new message is a decision: only `Request` and the two stops (refused with their own text, above) are not a window's.
- **Closed, unlike a stop**: nothing a window sends is a bot's to send, so a flood of input ends at its first message, with one log line, and what is queued behind it is dropped (`Server::message` drops the messages of a removed connection, above). A request it left pending stays a bot's (`BotClients::forget` keeps its key).
- The command line's guard refuses the windows too (Bots › The guard, rule 6): `cornercase` with no command (here, or with `--remote`), `cornercase remote DESTINATION` and `cornercase proxy`. `client::run` and `client::remote` (`from_another_build`) do not take that refusal for a server of another build, so they offer no restart, and above all no `kill-server` of the far machine when a remote window is refused there by the fail-closed rule below.
- **The server a bot's command starts** (when none runs) is spawned without `CORNERCASE_BOT` (`server_process::server_command`), as it is without `CORNERCASE_PANE`. Otherwise that server, its shells and its browser bridge (a thread of the server, so its connection's peer is the server) would all count as the bot's, and the phone's window would be refused.
- **It fails closed as the rest does**: a window whose peer pid cannot be read while a contained turn runs counts as that bot's and is refused; it attaches once the turn ends. A window that connected before is not touched, since a connection is classified once, at connect, and only while a bot exists.
- Not refused: a `full` bot (as for the rest of the boundary). A window or a command through ssh (`--remote` and `cornercase remote`, whose server sees an ssh process) is refused by the guard only (#866, The rest), `--remote localhost` and this machine's own name included, which would reach this server past the boundary. The agents' denied rules do not name `proxy`: the server refuses every route to a window, and a `full` bot may run anything.

**Rejected for #883**: refusing `Hello` alone (an `Event` before any `Hello` is ignored today, but a window's other messages change what a window sees, and an allow list of requests fails closed); keeping the connection open as a stop does (a stop's text is an answer the command line prints; a window has nothing more to say); refusing only in the guard (a process that drops `CORNERCASE_BOT` would still attach).

**The queue** (#846): a bot's connection may add, edit, pause, resume, remove and run only its own bot's entries; `clear-started`, and project or other bots' entries, are refused (see [Bot routines](routines.md)).

- **A request's `bot` and `bot_run` never widen what a connection may do** (#847): they only label the panes a request creates. A marked connection tags with its own bot whatever it names, so a `cornercase` bot cannot make a `full` bot take turns on text it controls ([Following](following.md)).

## A project's git (#893)

A Claude Code bot with `cornercase` access reads the git of the user's projects with exact per-folder rules, and its git can neither write a file outside its folder nor run a program. All of this was checked live on macOS (Darwin 25.6) with git 2.50.1 and Claude Code 2.1.325, with headless `claude -p --permission-mode dontAsk` runs.

- **The rules.** `Bash(git -C <folder> log|show|diff|status:*)` for each folder of `Ask::repositories` and each spelling of it (bare when plain, `'…'`, `"…"`; Windows paths have the single-quoted one only, not checked). Claude matches a rule on the command's text, so a quoted command does not match an unquoted rule. A path that is not UTF-8, or holds a control character, a quote, `` ` ``, `$`, `!`, `,`, `(`, `)`, `*` or `?` (a comma would split `--allowedTools`, parentheses end `Bash(…)`, `*` and `?` are wildcards), or on Unix a backslash, gets no git rule. The folders are those of this computer's open projects and of their open worktree workspaces, not a closing project or workspace, nor anything under the bots' folder (a bot may have made it a repository). The bots' folder is compared canonicalized as well as as stored (`os::fs::canonical`), since the stored one may go through a link or be relative while a project's path is canonical; otherwise a project opened inside it would get rules. They are read when a turn starts: a project opened during a turn has no rule until the next one.
- **Why the bare `git log|show|diff|status` rules went, for every agent.** With `Edit(<folder>/**)` a bot may write `HEAD`, `config`, `objects/README` and `refs/README` in its folder (only `.git/config` was refused), which make the folder a bare repository. `git diff --no-index x1 x2` in it, allowed by `Bash(git diff:*)`, then ran the `diff.external` program named in that `config`: a `cornercase` bot could run any program. The bare rules gave nothing else, since the bot's folder is not a repository and `cd` is refused.
- **Why not a wildcard.** `Bash(git -C * log:*)` never matches (the legacy `:*` form's `*` is literal). `Bash(git -C * log *)` matches, but its `*` also spans `-c core.fsmonitor=<program>`: `git -C <repo> -c core.fsmonitor=<script> status` ran the script. Deny rules for `-c`, `--config-env`, `--exec-path` and `--git-dir` do not help against a folder the bot made, which still runs.
- **`--output`.** An allowed `git -C <repo> log -1 -p --output=<outside>` and `git -C <repo> diff --output=<outside>` wrote the file (section 3 of #893). `--disallowedTools Bash(git *--output*)` refuses it. Checked live on 2026-11-16 with Claude Code 2.1.325 under the exact per-folder rules: `--output=F`, `--output F`, `'--output=F'`, `"--output=F"`, `"--output" F`, `--"output"=F`, `--out'put'=F`, `-'-'output=F`, `-""-output=F`, `--outp\ut=F` and `$'--output=F'` were all refused and wrote nothing. Claude matches deny rules on the unquoted words, so the forms with no `--output` text are refused by Claude itself; the pattern has no space before `--output` so that the text-only rule model in the tests refuses the quoted forms too, and it also refuses the harmless `--output-indicator-*`. Git 2.50.1 takes no abbreviation of it (`--o` to `--outpu` fail on `log`, `show` and `diff`), and `git status` has no `--output`. This closes the write for bots; Recap's same write stays as it was (`design/recap.md`).
- **A glob in the bot's folder.** The shell expands a glob before git runs, and Claude matches the text it was given: `git -C <repo> log --format=tformat:TEXT --outpu?=/ANY/PATH`, with a file `<folder>/--output=/ANY/PATH` that the bot wrote with `Edit(<folder>/**)`, is allowed by the per-folder rule, passes the deny (no `--output` in its text) and writes TEXT to any path (checked live on 2026-11-16, Claude Code 2.1.325, git 2.50.1, zsh; `--outp*=` and `--outpu[t]=` work the same, and in zsh so do `--outpu(t)=` and a bare `*=`, so a deny list of glob characters cannot be complete). A glob can only produce a word starting with `-` by matching an entry of the working folder, which is the bot's folder, and cornercase writes nothing at a path a bot names, so `--disallowedTools Edit(<folder>/-*)` closes it: a bot cannot make a top-level name starting with `-`. Checked live: a write of `<folder>/--output=/…` and of `<folder>/-x` were refused, while `notes.md` and `sub/-y` were still allowed. It was possible before #893 too (`Bash(git log:*)` with a plain `--output`). Not checked: Windows, whose Bash tool globs the same way; and a folder that already holds names starting with `-` from before this keeps them, so a bot made earlier can still use one until they are removed.
- **The index.** `git status` and `git diff` would rewrite a project's `.git/index` and take `index.lock`; every turn's environment stops that (see `bots/environment.md`).
- **A size limit.** Each folder adds 4 rules per spelling, about 1.5 KB for a long path, and Linux refuses one argument over 128 KiB while Windows' command line is 32 K with the prompt on it. The rules get a budget (`GIT_BUDGET`, 64 KiB; `WINDOWS_GIT_BUDGET`, 6 KiB): past it only the single-quoted spelling is kept, and then the first folders in sorted order up to the budget, with a `bots` warning in the log. A folder dropped has no git rule. Not checked live: how many folders a real Windows command line takes.
- **Prefixes Claude refused** under these rules: `GIT_EXTERNAL_DIFF=`, `GIT_CONFIG_PARAMETERS=`, `GIT_CONFIG_COUNT=`, `env GIT_…` and `GIT_DIR=`. `LANG=`, `nice` and `timeout` pass, which is harmless.
- **Rejected.** A middle wildcard with or without those denies (a made folder still runs); `--add-dir <project>` with `cd` (still refused); `--git-dir` or `-c` (ruled out by the issue). Gemini CLI and Copilot CLI get no git at all, see `bots/agents.md`.
- **Not checked.** Windows' spellings; other Claude Code versions and Linux; a path whose accents the agent writes in another Unicode normalization; `gh` run without `-R` in a folder a bot made a repository (gh runs git to find remotes; no read of it was seen to run a program).
- **Opening the bots' folder** (suspected here, closed by #866): a bot could `cornercase open` its own folder as a project after making it a repository, and the server's own git would read its config (`git status` consults `core.fsmonitor`). The server refuses `open` of a path inside the bots' folder, and `worktrees size --path` there (see The rest).

## The rest (#866)

#866 closed what the boundary above still left open to a `cornercase`-access bot. Every refusal is the server's, with code `failed` (exit 1), and the same request from any other client works as before; `full` bots are untouched (their connections are never marked).

- **Every request is a decision** (`app/control/boundary/table.rs`). `CLOSED` names the requests refused by name, each group with its text; `RULED` the ones `gated` decides by their fields; `OPEN` the ones a bot sends as anyone. `boundary::tests::every_request_is_decided_once` fails when a name of `Command::NAMES` is in none or in two, so a new request cannot reach a bot by default. `gated` keeps its wildcard: the test is what forces the decision.
- **Closed by name**, and why: `keys` and `input` (an allow list of keys cannot be safe: Enter answers a permission prompt with its default, Shift+Tab changes Claude Code's permission mode, `Esc Esc` opens rewind, arrows recall a `!` line from history); `flow-run` (every flow role runs unattended, `UNATTENDED`, which is exactly starting agents that never ask) and every flow write (`flow-delete`, `-hide`, `-restore`, `-default`, `-order`, `-close-when-merged`) and every persona write (`persona-save`, `persona-remove`; `persona-import` is refused unless `check`, as `flow-import` is), since a persona is prompt text that a flow's agents follow without asking, so replacing one a flow follows is changing that flow; `plugin-run` and `plugin-popup-close` (a plugin runs as the user); `stop-process` and `stop-port`; `changes-discard`; `worktrees-remove`, `free-builds` and `free-merged-builds`; `agents-forget` and `group-delete`; every account and profile write; `config-pair` (a pairing code is a window's keys); `forum-server` (a setting); every `tunnel-*` write.
- **Ruled by their fields**: `flow-import`, `flow-save` and `persona-import` only with `check` (a preview); `close-agent` and `agents-close` only with `check`; `machines` set, remove and update refused (`list` and `retry` allowed); `close` of a pane or tab only when the bot started it, never a workspace, project or group; `open`, `worktrees size --path` and `agents-reopen` (in their handlers, below); `start` and `start-with` not in a mode that never asks; and the typing rules of The boundary.
- **Left open**, on purpose: reads, `changes-stage` (the #880 audit classed staging as allowed), `todo`, `rename`, `move`, `focus`, `go`, `away` and `run-setup`, which arrange the user's own things. The `bot` request's `show` (`focus --bot`) is `focus` too, and `memory` a read.
- **Closing only what it started** (`boundary/owning.rs`). A pane carries the id of the bot whose request made it (`Term::bot`, Following › Tagging); `close` of a pane passes when its tag is the connection's bot, of a tab when it has panes and all carry it. A workspace has no tag, so a worktree a bot made with `start --worktree` is the user's to close. An unknown id passes, and the handler answers `not-found`.
- **Modes that never ask** (`agents::never_asks`). It reads the arguments `start_line` would use (one `chosen` for both, so they cannot drift) and refuses when a mode named dangerous (`is_dangerous`) of the table, or of the agent's built-in modes, has its run in them, so a user's `agent_modes` entry that renamed the dangerous run, and a flag left in `agent_args` by Settings, are caught too. An agent can list runs that never ask with no mode of their own (`Known::never_asking`): Claude Code's `--permission-mode bypassPermissions`, in both spellings, which `normalized` must not rewrite since `mode_of` and `extra_args` read it for the launch line. A never-asking mode from Settings is refused, not downgraded: the refusal tells the bot to pass `--mode default`. `start`'s and `start-with`'s check sits in `start_spec` (not the queue's own `queued_spec`), and an issue's start checks it too. A bot's `start --prompt` gets the `/` and `!` check of `send`, since the prompt is pasted into the agent's input box.
- **Keys inside a text.** A bot's text (`send`, a TODO item's for `todo send`, `start --prompt`) is refused when it holds a control character other than a line break or a tab (`a bot writes prompts to an agent, not keys`): a program without bracketed paste reads the text as typed keys, and an escape could end a bracketed paste early. `term::bracketed` also removes every paste end, the ones that removing another leaves included (one pass of `replace` turned `\e[201\e[201~~` into `\e[201~`), in one pass that drops a marker as soon as its last byte is pushed, so a paste of nested markers costs linear time; it protects every paste, the user's included.
- **Another machine.** `relay_request` is the one funnel of what is relayed to a machine (`start`, `start-with`, `new-workspace`, and `flow-run`, closed before it), and refuses a bot's connection with `a bot works on this computer only: it cannot act on another machine` (`bots::ELSEWHERE`); reads that take `--machine` (`stats`, `usage`, `machines list`) do not go through it and stay open. `--remote` and `CORNERCASE_REMOTE` are refused by the command line only (`guard::refused_remote`, exit 2), as `config export --to` is, since the far server sees an ssh process; `--remote localhost` included. The guard also refuses `plugin` other than `list`, `status`, `actions` and `logs` (an allow list, so a new subcommand is refused until decided), `machines add|edit|remove|update`, `remote --remember` and `--forget` (Bots › The guard, rule 8) and every `tunnel` subcommand, with texts shared with the server (`bots::NO_PLUGINS`, `NO_MACHINES`, `NO_TUNNELS`).
- **Reopening** (`agents-reopen`, `bot_reopens`). It would relaunch closed agents with their saved mode, or a flow's roles, so a bot is refused when the kept agents are a flow run's or a flow's roles exited (the `flow run` text), or when a saved mode, `default` when none was saved, never asks (the `start` text). The user's reopen is unchanged.
- **Opening.** `open` of a path inside the bots' folder (compared as `turn::repositories` does, stored and canonical, one function `turn::inside`) is refused, and so is a `.code-workspace` file, whose folders could be anywhere. The check is in the handler, on the canonical path it then opens (`bot_opens` after `canonicalize`; `worktrees size` checks the target `linked_target` resolved), not in the gate: a bot could otherwise swap a link in its folder between the check and the handler's own resolution. A canonical path outside the bots' folder holds no link a bot can change. The audit of the other requests that take a folder: `files list`, `files read` and `files search` run git only in their workspace's own folder (the files panel's marks), never in the named one, so they stay open; `worktrees size --path` runs `git status` in the named folder when it is a linked worktree, so it is refused inside the bots' folder.
- **The brief** tells a `cornercase`-access bot the same in one sentence (`brief::BOUNDED`), after its access paragraph.
- **The macOS orphan is not closed**, and no code tries: macOS has no subreaper; `kqueue`'s `NOTE_FORK` gives no child pid and loses a `( … &)` double fork before its children can be listed; a sampler misses a shell that lives a few milliseconds; "an orphan started after the turn's root" needs a start time that macOS' `process::started` does not have, and would mark a launchd agent of the user's as a bot's; the responsible-pid API is private and changes which app macOS asks permissions for. `CORNERCASE_BOT` in the environment stays the only tell there.

**Rejected for #866**: an allow list of keys (above); letting a bot close a workspace it made (no tag on a workspace); carrying the boundary to the far server (a protocol addition older servers would ignore); downgrading Settings' never-asking mode to `default` instead of refusing (silent); refusing `#` as a first character (a Markdown heading is a common first line of a prompt).
