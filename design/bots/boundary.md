# Bots: the boundary

Part of [Bots](../bots.md). What a bot's connection may type into, change, stop or have cornercase write, and why.

## The boundary (#856, #867, #880)

Under `cornercase` access, **the server refuses what a bot types into a pane that runs no agent**: `send`, `todo send`, `keys`, `input` (a pane, and a plugin's popup always), `paste-file`, `held --send-now`, and `new-tab` or `split` with a command (their command is typed into the new shell). The same request into an agent's pane works, and so does the same request from any other client. The refusal has code `failed` (as `send`'s others), exit 1, and its text starts `a bot can only type into a pane that runs an agent` (`boundary::HEAD`).

- **Who is a bot is the connecting process, decided once per connection, at connect.** `Server::accept` reads the peer's pid from the socket (`os::socket::peer_pid`: `SO_PEERCRED` on Linux, `LOCAL_PEERPID` on macOS, `SIO_AF_UNIX_GETPEERPID` on Windows) and `App::client_connected` stores `client → bot id`. A connection a turn opened stays a bot's after its turn ends. **It fails closed**: while a contained turn runs, a connection whose peer pid cannot be read counts as that bot's (a real client is alive and readable while it waits for its answer). A pid that is read but whose process cannot then be inspected falls back to the walk and the environment: a gap. A Windows `Lineage` whose Job cannot be made (or the child assigned to it) fails the turn instead, closed. A process is a bot's when a running contained turn holds it (`Running::holds`: its root, a descendant by the parent walk, or on Windows a process of the turn's Job), or when its own environment, read by the server from the OS, sets `CORNERCASE_BOT` to anything but a `full` bot's id (an unknown id counts: the check only ever refuses more). It is logged as `a bot's client`, with the bot's id and never a text.
- **Why contained turns.** Claude Code runs every Bash command in a session and process group of its own (checked live), and a command sent to the background with `( … &)` is reparented to pid 1 once its shell exits, so neither a group nor a plain parent walk reaches it. On Linux the turn's root is a child subreaper (`prctl(PR_SET_CHILD_SUBREAPER)` in `pre_exec`), so the orphan is adopted by it and the walk still finds it. On Windows nothing is reparented, so the root is in a Job (`os::process::Lineage`, `IsProcessInJob` asks), with no `BREAKAWAY_OK`: Cygwin and MSYS2, so Git Bash, add `CREATE_BREAKAWAY_FROM_JOB` when the job allows it. **macOS** has no subreaper: a command sent to the background whose shell exits is reparented to launchd and is not seen, unless it keeps `CORNERCASE_BOT` in its environment (the fallback above), and cleanup does not reach it either.
- **What "runs an agent" means** is the pane's foreground program now (`agents::detect` over `Term::foreground_args`, what the agent watch and `status`'s `program` use, so also an agent the user put in `agent_commands`), not `status`'s `agent`, which keeps an agent that exited back to its shell while its finished status is held. So a pane whose agent exited, or that is resuming its agent after a restart, is refused. A machine's pane is out of reach: no typing request takes `--machine`.
- **Where it runs.** The gate sits at the top of `handle_request` for a bot's client (`boundary::bot_writes`), resolving the target as the handler does. The writes that happen later are checked again when they happen, keyed on the pending request (kept when its client leaves, the keys in `Clients::bots` (`boundary::BotClients`)): a held send when it goes out (`held::release`), `paste-file` when its stored file is pasted (`file_stored`), and the Enter cornercase presses after `send --enter` (`drive_launches` ends that launch, answers the request with the refusal and leaves the pasted text unrun on the shell's line). `keys` and `input` write at once, so the race of keys, `input` or a `send`'s paste (without `--enter`) written in the instant an agent exits remains.
- **`full` bots are unchanged**: they can run anything themselves, so refusing them adds friction and no safety. Their turns are not contained.

**Also refused to a bot's connection** (it could lift the boundary itself): `bot new` with an access other than `cornercase` and `bot edit` with any access (`a bot cannot change a bot's access`), `bot say` to a bot with `full` access, and any `bot edit` of one, `--about` writing its `bot.md` included (`a bot cannot write to a bot with full access`), and every write to the settings (`config` other than get and search, `config-import` applied: `a bot cannot change cornercase's settings`), since `agent_commands` decides which programs count as an agent.

**What is still not a boundary**: `config export --to` and `update`'s own install, which only the command line's guard and the agent's allow rules stop (see What a bot names for cornercase to write); the user's own Claude allow rules (`--setting-sources user` loads them on top of `--allowedTools`); an agent's own shell (Claude Code's `!` mode, which `send` and `keys` can type into), its permission prompts (which `keys` can answer), and starting agents in a mode that skips them; requests that change what cornercase runs (`flow-import`, `flow-save`, plugins); destructive requests (`close`, `stop-process`, `stop-port`, `changes-discard`, `worktrees-remove`); `--remote` over ssh (that machine's server sees an ssh process); on macOS, the orphan above, and a process that escapes a contained turn's cleanup (Bots › A turn, Not closed). Work you would give an assistant at your keyboard is the right size for a bot.

**Rejected**: a request field filled from `CORNERCASE_BOT`, or a token in the turn's environment (the bot controls its environment, and a token is readable by any process of the user); the turn's process group or session (every Bash command has its own); a socket per turn (the bot can name the main one); a wrapper process as the root (tests run turns with fakes, and macOS could still not adopt orphans); refusing a window's `Hello` from a bot's connection (a bot's commands have no terminal; a program that speaks the protocol needs the user's own allow rules); `status`'s `agent` as the test; a new error code (strict clients read `Code` as an enum); applying it to `full` bots.

**Checked live**: on Linux with Claude Code 2.1.325 (2026-11-14), every Bash command runs with `pgid = sid = ` its shell's pid, and a command sent to the background is reparented to pid 1 once that shell exits. Nothing was checked on macOS or Windows (the Job code was read against `windows-sys` 0.61.2 only), and no real turn ran: the tests use fakes.

**What stops or replaces the server (#867).** `bots::SERVER_STOPS` is one table: each entry maps a command the guard refuses (`kill-server`, `restart`, `update`) to the names it asks the server by (`asks`: `kill-server`; `restart` and `restart-when-idle`; `update-install`). The command line's guard reads the commands, the agents' denied rules read them through `Ask::stops` (so their argv did not change), the boundary reads `asks` for requests (`bots::stops_server(command.name())`, `Gated::ServerStop`), and `App::refused_stop` reads them for the two protocol messages that are not requests. All use the text `a bot cannot stop its own server` (`bots::STOP_REFUSED`); a request gets code `failed` (exit 1), a message `ServerMessage::Rejected`.

- `kill-server` and `restart` are `ClientMessage::KillServer` and `ClientMessage::Restart`, which `Server::message` used to obey from any connection, `cornercase proxy` and a command whose environment lost `CORNERCASE_BOT` included. `refused_stop` (called at the top of `Server::message`) answers a bot's connection `Rejected` and logs `a bot's stop refused` (client, bot, what it asked; never a text). **The connection stays open and stays a bot's**: `Server::reject` removes the client, `App::forget` would then forget it was a bot's, and a second stop message already queued behind the first would be obeyed. For the same reason `Server::message` drops every message from a connection that was accepted (its id is below `next_client`) and is no longer in `Server::clients` (a stop queued behind a rejected `Hello`, a stream's end or a detach would otherwise find no bot to refuse, and a queued request would skip the typing boundary too). The command line (`client/server_process.rs`, `rejection`) stops reading at the first `Rejected`, since the server no longer closes, and `kill-server` and `restart` print it as an error (`restart` falls back to `kill-server` on a `Rejected`, as for a server of another build, and that one is refused too).
- **Not in the table**: `update-check` (changes nothing), `account-restart` (restarts agents, not the server), `start-server` (only answers that the server runs), and `machines update` (installs on and restarts another machine's server: the open follow-up of #866's `--remote` part).
- A `full` bot's connection is not refused by the server, as for the rest of the boundary; the guard and its agent's denied rules still refuse its commands.

**What a bot names for cornercase to write (#880).** The rule: cornercase writes nothing at a path a bot names.

- `config export --to FILE` is refused by the command line (Bots › The guard, rule 5, also on each `requests` line), because the command line's process writes the file and the server never sees the path. So it rests on the guard and on the agent's allow rules: a process of the turn that drops `CORNERCASE_BOT` is not stopped by cornercase, and the same holds for `update`'s own install. Without `--to` the settings are printed, and that is still allowed.
- `clone URL [FOLDER]` is refused by the server for a `cornercase`-access bot (`Gated::Clone`, whatever the folder): the server makes `FOLDER/<repo>` and any missing folders above it, so a bot could put a repository where another program runs it (`~/.vim/plugin/<repo>/x.vim`, which Vim loads); inside its own folder it would be a project inside the bot's folder, deleted by `bot remove`, which also breaks that project's worktrees; and the command line's default folder for a bot is its own.

**Rejected for #880**: allowing `--to` inside the bot's folder. The command line would need the bot's folder from the server, a canonical parent that exists, to refuse symlinks, `..` and the protected files, and an open that cannot follow a link swapped in. The bot gains nothing over printing the settings and writing them in its folder with its own tool.

**The audit of paths a caller names** (searched: every `value_name` FILE, FOLDER, PATH or SOURCE in `cli/args*`, the `PathBuf` fields of `control/`, and every file write in `cli/`; `config export --to` is the only write the command line does):

| Command (path argument) | What cornercase does with it | For a bot |
|---|---|---|
| `config export --to FILE` | the command line replaces FILE with the settings (0600) | refused by the guard (#880) |
| `clone URL [FOLDER]` | the server makes `FOLDER/<repo>` and the missing folders above it, clones, copies the `--file`s into it | refused by the server, `cornercase` access (#880) |
| `bot say --file`, `start --prompt-file`, `flow run --prompt-file`, `flow save FILE`, `flow import SOURCE`, `config import FILE`, `theme FILE`, `start-server --theme`, `paste-file FILE`, `clone --file PATH --from FOLDER`, `clone --list-ignored`, `files list FOLDER`, `files read PATH`, `open PATH`, `worktrees size --path`, `plugin link FOLDER`, `plugin install SOURCE` | read only | allowed: a bot reads anything |
| `flow save --path FILE`, `flow delete --path FILE` | the server takes only a file `flow list` lists | allowed; changing flows is #866 |
| `changes file/gap/viewed/discard/stage/unstage PATH` | relative to the workspace, through git | allowed; `discard` is #866 |
| `worktrees remove FOLDER…`, `worktrees free-builds` | deletes linked worktrees or build folders it lists itself | #866 (destructive) |
| `config project FOLDER` | a settings write | already refused (#856) |
| `machines add/set --folder FOLDER` | a folder on that machine, kept in the settings | not refused: follow-up |
| `plugin link/install/enable` | write cornercase's own plugin files from the command line's process | #866 (plugins); the server cannot see them |
| `paste-file`'s stored copy, `bot new`, `account add`, `new-workspace --worktree`, `flow save`/`import` names | cornercase names the file itself, in its own folders | nothing named by the caller |

**The queue** (#846): a bot's connection may add, edit, pause, resume, remove and run only its own bot's entries; `clear-started`, and project or other bots' entries, are refused (see [Bot routines](routines.md)).
