# Bots: the agents (#849)

Which agents can be a bot, with which access, and what was checked live to decide it. The model, the access and the runner are in [Bots](../bots.md); this is the table and the reasons per agent.

An agent can be a bot when its command line has all three of these:

1. **A non-interactive mode with machine-readable output**: the final answer, its tool uses (for the `step` lines) and, when it gives them, its tokens.
2. **A session id in that output and a way to continue it** in a later run.
3. **Permissions fixed up front**: rules or a sandbox that hold the `cornercase` access (read, run `cornercase`, write only in the bot's folder), and a bypass for `full`.

Each agent's `headless.rs` is its spec in the shared runner (`agents/headless.rs`). An agent with the first two and without the third is `full` only, with the reason in `BotSupport::why`.

## Gemini CLI

- **Arguments.** `gemini --skip-trust --output-format stream-json --approval-mode default --policy <folder>/.gemini/cornercase-policy.toml [--model M] [--resume S] --prompt=<prompt>`; `full` is `--approval-mode yolo` without `--policy`. Without `--skip-trust` it exits 55 in an untrusted folder, and the bot's folder is not one it knows. `--prompt=<text>` as one word keeps a prompt that starts with `-`. There is no effort switch.
- **The stream.** `init` (session, model), `message` (the user's and the assistant's, which arrives in pieces with `delta`), `tool_use` and `tool_result`, then `result` with `stats` (`input` is the uncached input, `cached`, `output_tokens`, and `models` with each model's tokens: the router model and the main one appear, so the model shown is the one with the most tokens). An error is a `result` with `status: error` and its message; Gemini's standard error always starts with a colour warning, so it is not read.
- **The `cornercase` access is a policy file**, not the deprecated `--allowed-tools` (it warns that it goes in 1.0 and cannot deny a file). `Spec::prepare` writes `<folder>/.gemini/cornercase-policy.toml` before every turn, from the runner's own lists (`GH_READS`, `Ask::stops`, `Ask::protected`), so a file that was changed never outlasts one turn. It allows `cornercase`, the read-only gh prefixes, and writes with `write_file` and `replace`; it denies the commands that stop the server, and writes of `bot.json`, `chat.jsonl`, `secrets`, `.gemini/` and `.env` (Gemini reads a trusted folder's `.env` into its own environment, which `GIT_EXTERNAL_DIFF` could turn into a shell; not checked live). Gemini tests a rule's `argsPattern` against the arguments as JSON, but writes to the path it decodes and resolves afterwards, so a name could slip past by `%2E`, by a `"` that ends the match (`<folder>/"/../.gemini/x`) or, on macOS, by case. So the name rules are case-insensitive and a third rule denies any write whose path holds a `%` or a backslash. The name rule is a case-insensitive *substring* match, so `secrets` (#877) also keeps a Gemini bot from writing any path that holds that word, a safe narrowing; the rule for `secrets` was not run against Gemini. The rules were checked live before these two additions and are pinned by a test over the `regex` crate; the additions were not re-run against Gemini. **A letter that folds to `s` or `k` (#879).** On macOS' default disk (APFS, case-insensitive) a name is folded with Unicode's rules, so `ſ` (U+017F, long s) is `s` and `K` (U+212A, Kelvin sign) is `k`: `printf x > bot.jſon` overwrote `bot.json` (macOS 26.6.2, 2026-11-19). Since cornercase writes this rule's name match itself, each `s` class also holds `ſ` and each `k` class `K`. Claude Code's and Copilot's rules match names their own way and refused those spellings live (Checked on macOS, below); Gemini was signed out there, so the wider classes were **not run against Gemini**, only pinned by the test. Checked live: a write outside the folder is refused by Gemini's own workspace rule, `touch`, `cornercase … > outside`, `&&`, `;`, `$(…)`, backticks, `| tee` and `>>` are refused, `cornercase --version` and a write of `notes.md` run, a deny beats the allow, and a resumed turn keeps the session.
- **Why `.gemini/` is denied.** `--skip-trust` makes the bot's folder trusted, so a `.gemini/settings.json` there would be read as the project's settings on the next turn, and it can carry allowed tools, hooks or MCP servers: a bot that can write in its folder could give itself any shell. It allows no git since #893: the bare git prefixes gave a bot nothing (its folder is not a repository) and opened the made-repository hole of The boundary › A project's git, which was checked for Claude only. A project's git for Gemini needs a live check of `commandPrefix` per folder plus a `commandRegex = "git .*--output"` deny, per 0.67.0's own `docs/reference/policy-engine.md`; Gemini 0.67.0 was not signed in on the machine of #893 (#900).
- **It reads only its folder.** `read_file /etc/hostname` is refused (`Path not in workspace`); `web_fetch` works. This is narrower than the access promises, and a safe narrowing: the brief says `read and write only in your folder` for these agents (`BotSupport::reads_anywhere`), `bot agents` says it as `reads: "folder"` (feature `bot-reads`) so a form can write the same in its note under Access, and cornercase's own commands still show the user's work.
- **A read-only mode exists** (`--approval-mode default` without a policy: `read_file` works, `write_file` and `run_shell_command` come back as not found). It is the lead for Recap on Gemini, see below. One trivial run took 214 s.
- **Windows is `full` only** with `its rules are unchecked on this system`: the checks were seen with `sh`, and PowerShell evaluates `(…)` and `$(…)` inside a command's arguments.

## opencode

- **Arguments.** `opencode run --format json [--auto] [--session S] [--model M] -- <prompt>`; `--auto` is the bypass and goes only with `full`.
- **The stream.** Every line has `type`, `sessionID` and `part`: `step_start`, `text`, `tool_use` (one per tool, sent when it ends, `state.input` holding the command or path) and `step_finish` (`part.reason` is `tool-calls` or `stop`, with `tokens` of that step, which are added). There is no model in the stream. An error is an `error` line, and fails the turn at once.
- **The end of a turn (#879).** No line says the turn is over (Claude Code has `result`, Codex `turn.completed`). Until #879 the reader answered at the first `step_finish` that was not `tool-calls`, and that was wrong: a resumed turn that compacts first (1.18.35, macOS, 2026-11-19, forced with a small `limit.input`, see the fixture's README) prints a step whose `text` is the compaction summary (`## Objective…`) and which finishes with `stop`, then a `text` with `synthetic: true` and `metadata.compaction_continue` (`Continue if you have next steps…`), then the real step and its answer. The bot answered with the summary and the runner killed opencode two seconds later. Only what comes after the summary tells it apart, so the answer is the text opencode holds **when its output ends** (`Spec::ended`, `probe::Heard::End`): a `synthetic` text is never added, and one marked `compaction_continue` clears what came before it. `opencode run` exits once its session is idle: in about fifteen runs it always did, within a second or two of its last line; one that did not would end at the turn's time limit. A compaction in the middle of a turn (after a tool step) was not produced live; its mark follows the summary the same way, so it reads the same. The summary's step counts in the tokens, since it is real spend. A turn stopped by cornercase (a bot's `stop`, a routine's run) never answers at the end of the output, whatever text it already holds (`probe::Running::stopped`), so it stays `stopped`. Not handled: an opencode killed by something else, or one that crashes mid-turn without an `error` line, answers with the text it held; the runner does not read the exit status at that point.
- **Why `full` only.** `OPENCODE_PERMISSION` with `bash: {"cornercase *": "allow"}`, `edit` denied for `bot.json` and `chat.jsonl` and `external_directory: deny` held for a write outside, `touch`, `&&` and `bot.json`, but **`cornercase --version > <outside>/file` ran and wrote the file**. A deny on `*>*` stops that plain form only (#879, macOS, 1.18.35): `{ cornercase --version; } > out`, `(cornercase --version) > out`, `for i in 1; do cornercase --version; done > out` and `cornercase --version | cornercase --version > out` all ran and wrote their files. opencode's `packages/opencode/src/tool/shell.ts` (v1.18.35) says why: a rule is matched against each command it parses, and a redirect is part of a command's text only when it sits on that command; one on a group, a subshell, a loop or a pipeline belongs to none. So no rule on commands can keep a command's output in the folder, and the reason stays `a command can write outside its folder`. The lead left, not tried: opencode's own tools without its shell, a custom tool that runs `cornercase` with its arguments, with the project's config switched off.

## Cursor CLI

- **Arguments.** `cursor-agent -p --output-format stream-json --trust [--force] [--resume S] [--model M] -- <prompt>`; `--trust` is always there (it refuses an untrusted folder otherwise) and `--force` is the bypass.
- **The stream.** `system/init` (session, model, which is a display name), `user`, `thinking` (ignored), `assistant` (text), `tool_call` `started` and `completed` (the key is `shellToolCall`, `editToolCall` and so on) and `result` with `usage` in camelCase, where `inputTokens` leaves out cache reads. **`result.result` joins every assistant text of the turn**, so the answer is the text after the last tool call, and `result` is only the fallback when there is none. An error is on standard error only, as one line.
- **Why `full` only.** By default `-p` rejects shell commands that are not allowed, but **its edit tool wrote outside the folder and wrote `bot.json`**. With a workspace `.cursor/cli.json` (allow `Shell(cornercase)` and `Write(<folder>/**)`, deny `Write(<folder>/bot.json)`) it refused `bot.json`, `touch` and `&&`, but **a write outside still worked and `cornercase … > outside` ran**: an allow does not narrow the edit tool and a deny wins over an allow, so "only inside the folder" cannot be said. `--sandbox enabled` did not start on this machine (AppArmor). The reason is `its edits can leave its folder`.

## GitHub Copilot CLI

- **Arguments, `cornercase`.** `copilot --output-format json --no-auto-update --no-ask-user --disallow-temp-dir --disable-builtin-mcps --allow-all-urls --allow-tool shell(cornercase:*)`, then `--allow-tool shell(<c>:*)` for each read-only gh command, `--allow-tool write`, `--deny-tool shell(cornercase <stop>:*)` for each command that stops the server, `--deny-tool write(<folder>/<file>)` for each protected file, then `[--resume=S] [--model M] [--reasoning-effort E] --prompt=<prompt>`. Each `--allow-tool X` is two words, as checked. `full` is `--allow-all --no-ask-user`.
- **The stream.** Many event types; these matter: `session.auto_mode_resolved` (model), `assistant.message` (`content`, `model`, `parentToolCallId` when a subagent wrote it, `chunkIndex` when the answer is split), `tool.execution_start` (`bash` and `powershell` with a command, `apply_patch` with a patch string, other tools with a path or URL) and `result` (`sessionId`, `exitCode`). A new message from the main agent replaces the text, a chunk after the first adds to it, so the answer is what follows the last tool.
- **Checked live.** A write outside, `touch`, `> outside`, `&& touch`, `| tee`, `sed -i` and `find -delete` outside, `cat /etc/hostname`, `view /etc/hostname` and a write of `bot.json` are refused; `$(…)` was blocked before it ran; prefix rules are exact (`gh pr list` ran, `gh pr create` did not); the deny of `cornercase restart` beats the allow; a resume with the same arguments keeps the session. **A Copilot bot reads only its folder**, as Gemini does. Windows is `full` only for the same reason as Gemini.
- **No git (#893, 2026-11-16, Copilot 1.0.98 through `npx`).** With `shell(git log:*)` allowed, `git -C <a project> log` was still refused, and so were `-c`, `--output` and `--no-index` with folders outside the bot's. Its rules work per first-level subcommand, so they cannot name a folder or deny `--output`, and its path check keeps file access in the working folder (`--add-dir` or `--allow-all-paths` would let `write` leave the bot's folder). Whether the refusal came from the stem rule or the path check was not told apart.
- **Tokens are zero.** The stream gives only the session's running total (`session.usage_checkpoint`), which on a resumed turn is the sum of both, so there is no per-turn count to show.
- **Effort** goes only with a named model that is not `auto`, so `bot new` and `bot edit` (and the form) refuse an effort without one (`BotSupport::effort_needs_model`), instead of accepting a choice that does nothing (`auto` fails with `Model "auto" does not support reasoning effort configuration`). This account offers no model by name, so an effort with one was **not checked**.
- **The environment.** `COPILOT_ALLOW_ALL` (`true` would allow every tool) and `COPILOT_ASSISTED_APPROVAL` are removed with Copilot's session variables. Not run live: the variables were not set here.

## Standard error (`Spec::stderr`)

Cursor and Copilot say why they stopped only on standard error, as one line (`Error: Model "x" from --model flag is not available.`, `Cannot use this model: …`), with no `result`. Their specs ask for it: `probe::Limits::stderr` pipes it, a thread keeps the first non-empty line (cut to 200 characters) and reads on so the pipe never fills, and a run that ends without an answer says `<agent> exited without answering: <that line>`. The other agents keep it discarded: Gemini's always starts with a colour warning and its errors are in its stream.

## The answer

The four agents speak before and between tools. The answer is only what the agent says after its last tool use (`headless::heard` counts a step and clears the text), as Claude's and Codex's already are.

## The runner refuses what the spec does not list

Before any process starts, `run_watched` refuses a Recap from an agent whose spec cannot write one (`<agent> cannot write a recap`) and an access a spec does not list (`<agent> cannot be a bot with <access> access`). So "full only" holds also for a hand-edited `bot.json`, not only in the form.

## Windows

A headless prompt has line breaks (the brief). Rust refuses CR and LF in a batch file's arguments and `cmd.exe` would cut the line anyway, so an agent installed with npm (Gemini on Windows only comes that way, and so can Codex) could not start. `process::program::command_without_cmd` starts what an npm shim starts directly, as launches do (#632). **Not run on Windows.**

## Recap (#849, #879)

`Spec::recap` says which agents can write one, and the runner refuses the others: Claude Code and Codex since #656, **GitHub Copilot CLI and opencode since #879**, each in a read-only mode checked live on macOS (below). Copilot runs with the arguments its spec already built for `Tools::Recap` (`--output-format json --no-auto-update --no-ask-user --disallow-temp-dir --disable-builtin-mcps`, no `--allow-tool`, no `--allow-all`); opencode without `--auto`, as an agent of cornercase's own, `--agent cornercase-recap`, defined in `OPENCODE_CONFIG_CONTENT` as a primary agent whose `permission` is the read-only rules, with `OPENCODE_PERMISSION` set to the same rules. The rules name every built-in tool that can change something, since opencode merges them over the user's config key by key and the last matching rule wins: `*`, `bash`, `edit`, `task`, `skill`, `webfetch`, `websearch`, `todowrite` and `external_directory` denied, `read`, `glob`, `grep` and `list` allowed, and `doom_loop` allowed. That last one is opencode's guard against a model repeating itself: after three identical tool calls in a row it asks for `doom_loop`, a `*` deny refused it, and one of the first four live recaps failed that way; the repeated call still goes through its own rule, so allowing it lets only a read be read again.

**Why an agent of its own (CodeRabbit on #913).** `OPENCODE_PERMISSION` alone did not hold. opencode 1.18.35 merges it into the top-level `permission`, and an agent's own `permission` is applied over that. So a user config with `agent.build.permission.bash: allow` let a recap run `touch made.txt` (checked live on macOS with that config in a scratch `XDG_CONFIG_HOME`). opencode loads `OPENCODE_CONFIG_CONTENT` after the user's global and project configs, so the agent it defines has the last word over a user's agent of the same name, key by key. Passing `--agent` also makes the user's `default_agent` irrelevant. Checked live the same way (1.18.35, 2026-11-19): with that config, and with one that defines `cornercase-recap` itself with `*`, `bash` and `edit` allowed and allows `bash` and `edit` at the top level, the recap was offered no shell and no write tool and wrote nothing, and a `now` recap still answered in its form. Limits: a permission key the user's own `cornercase-recap` agent names and ours does not would survive the merge (ours names `*` and every built-in tool, so only a plugin's or an MCP server's tool could be one); the user's plugins still load, as they are the user's own code; and managed preferences, which an administrator sets, come after it. The reasons, the limits and Gemini's lead are in [Recap › Which agents write a recap](../recap.md#which-agents-write-a-recap-849-879).

## Checked on macOS (26.6.2, arm64, 2026-11-19, #879)

The rules of the earlier checks were kept: a fresh folder outside every repository, synthetic content only, `env -i` with `CORNERCASE_SOCKET` pointing at a socket that does not exist. opencode 1.18.35 and GitHub Copilot CLI 1.0.98 ran through `npx`, the fixtures' versions; Claude Code 2.1.328 was installed.

- **opencode.** The four ways past a `*>*` deny above. Its read-only rules (Recap): a read in its folder worked; the write, shell and subagent tools were not even offered, and a read of `/etc/hosts` was refused; asked to create a file, run `touch` and `cornercase --version`, write outside and start a subagent, it wrote nothing. The compaction stream of a resumed turn (The end of a turn), also seen the same in 1.19.6, the latest that day. `full` turns: a first turn with `--auto` ran `cornercase --version` and wrote a file in its folder, and a turn resumed with `--session` kept the session and answered from it; read back through the runner, both gave the session, the steps and the last answer, and opencode exited within a second of its last line each time.
- **GitHub Copilot CLI.** Its read-only arguments: a read in its folder worked; `apply_patch`, `bash` and a `view` of `/etc/hosts` were refused (`Permission denied because no interactive user response was available`). Its `cornercase` rules: updates of `bot.json`, `BOT.JSON`, `bot.jſon`, `Chat.jsonl` and `./sub/../bot.json` were refused by the deny rule, `notes.md` was written, and `cornercase --version > outside` and `{ cornercase --version; } > outside` were refused. `full` turns: a first turn with `--allow-all` and one resumed with `--resume=` behaved the same way, read back through the runner with the same session.
- **Claude Code.** With `Edit(/<folder>/**)` allowed and `Edit(/<folder>/bot.json)` and `chat.jsonl` denied, writes of `bot.json`, `BOT.JSON`, `bot.jſon` and `Chat.jsonl` were refused and `notes.md` was written.

- **A recap from each.** A synthetic dossier and the real `now` and `week` prompts, with the arguments each spec builds, read back through the runner: Copilot, `now` and `week` twice each, answered every time (model `gpt-5.6-luna`, its default here, 10 to 12 s); opencode (`opencode/big-pickle`), the same four and four more with the final rules, answered every time but the one that hit `doom_loop` (Recap, above), in 23 to 55 s. Not run there: Gemini CLI (signed out: 0.67.0 asks to open a browser to sign in), Cursor CLI, Grok Build and Vibe CLI (not installed).
