# Windows › Scripts and plugin commands without sh

Part of [Windows](../windows.md).

- **Scripts and plugin commands without sh** (#595, `script.rs`): what runs a project's setup and teardown, the editor opened from a panel, and a plugin's `#!` program. What each area decided is in its note (Worktree setup, Plugins); this is the layer under them.
  - **One place picks the interpreter**: `script::Shell::here()`, once per process. On Unix it is `/bin/sh` and every command line is the one it was (`sh -ec SCRIPT` for a teardown, `sh -c TEXT NAME ARGS…` for the setup's wrapper and the editor). On Windows it is Git for Windows' `sh` when found, else PowerShell 7 (`pwsh`) when `process::program` finds it on the `PATH`, else Windows PowerShell by its full path, `System32\WindowsPowerShell\v1.0\powershell.exe` in the Windows folder (`os::desktop::windows_folder`), never by name through the `PATH`, where that folder may be missing and an earlier entry could hold another `powershell.exe` (`Shell::pick`, given what was found, so its tests choose; the bare name only if Windows could not give its folder). The callers branch on the kind at run time, never with `cfg` around their code, so the Windows paths compile and are linted everywhere and the Unix build reaches them only as `Shell::Sh` with `git: false`.
  - **Finding Git's `sh`**: only inside Git's own install, whose root is found two ways and nowhere else. First `git --exec-path` (run through `process::program`), which Git for Windows 2.x answers with `<root>\mingw64\libexec\git-core` (`clangarm64` on ARM) even when the `git` on the `PATH` is a shim (scoop's `shims\git.exe`): the root is three folders up, taken only when the answer ends in `libexec\git-core` and `git.exe` is in that platform folder's `bin`. Else the folder of the `git` that `process::program` finds: `cmd` or `bin` (the root is its parent) or `mingw64\bin` (its grandparent), taken only when `<root>\cmd\git.exe` is there. In that root `usr\bin\sh.exe`, then `bin\sh.exe`, and only a file that belongs to the user, SYSTEM or Administrators and that no one else may write (`os::fs::owner_and_mode`; Program Files' files pass). It must be a plain file, not a symbolic link or another reparse point (`symlink_metadata`, `os::fs::reparse_point`): the owner and the DACL are read without following a link, so a link the user owns that leads to an `sh.exe` others can write would otherwise pass while its target ran. A hard link needs nothing more, since it shares its file's DACL. The symbolic link's test needs Developer Mode and says it skipped without it. `usr\bin\sh.exe` comes first: `bin\sh.exe` is a launcher that puts Git's folders first on the `PATH` of everything it starts, the shell that follows a setup included. Rejected (review of #595): searching the folder of the `git` on the `PATH` and its parents, which for scoop's global shims (`C:\ProgramData\scoop\shims`) reached `C:\ProgramData\bin\sh.exe` and `C:\bin\sh.exe`, folders any signed-in user can create on a default Windows, so another account could have run its program as the user in every setup, teardown and plugin script. The folders above `sh.exe` are not checked: Program Files' grant `TrustedInstaller` full control, which the owner and DACL reading would count as another user, and the root comes from git's own answer. Found once per process, so a Git installed later is seen after a restart of the server.
  - **Paths in arguments**: when a program of Git's `sh` starts a Windows program, MSYS2 rewrites every argument that looks like a Unix path (`/api/v1` becomes `C:/Program Files/Git/api/v1`, `--dir=/tmp/x` a folder of the temp, and `/c` `C:/`; checked 2026-11-03). A plugin's `#!` program gets `MSYS2_ARG_CONV_EXCL=*`, so what it hands a Windows program (`node` behind `#!/usr/bin/env node`, a `cmd /c`) arrives as written, and its children inherit that. A setup and a teardown keep the rewriting, as Git Bash does, since a script tried in Git Bash expects it; one that does not can set the variable itself.
  - **Nothing variable goes on an `sh` command line**: a program of Git's `sh` (MSYS2) parses its Windows command line itself, not as `CommandLineToArgvW` does. Outside quotes `'` opens a quoted string (so `it's` takes the rest of the line), `*`, `?`, `[…]`, `{a,b}` and a leading `~` are expanded and a leading `@` reads a file in; inside double quotes `\\` becomes one backslash. std and portable-pty quote an argument only when it holds a space (checked on 2026-11-03 with Git for Windows 2.39.2: an argument `it's` swallowed every argument after it). So the text to run goes in `CORNERCASE_SCRIPT` and the positional arguments in `CORNERCASE_ARGS`, as words quoted for `sh`, and the command line is a fixed adapter that sets them with `eval "set -- …"`, unsets both and runs the text, so the script never sees them. Rejected: quoting each argument for MSYS2 with `raw_arg` (it works for std's `Command`, but a pane goes through portable-pty, which quotes in its own way), and a script file in a private folder (a file to make, keep private and remove for every run).
  - **What Git's `sh` cannot write to**: a handle opened for appending only (`FILE_APPEND_DATA` without `FILE_WRITE_DATA`, which std's `append` gives); its writes fail and the command exits 1. Only a plugin's log is such a handle, so a plugin's job through `sh` appends with `>>` (Plugins).
  - **PowerShell** gets its script after `-NoProfile -Command`, quoted by std or portable-pty as `CommandLineToArgvW` reads it, which PowerShell 5.1 and 7 both do (checked). A setup's script reaches its child PowerShell through `-EncodedCommand` (base64 of UTF-16), so it is never quoted twice, and every value written into the wrapper's text is a single-quoted literal with each `'` doubled, and each of `‘ ’ ‚ ‛`, which PowerShell also takes for a single quote.
  - **cmd** never runs a script (see Worktree setup).
  - **The editor** (`app/actions.rs`, a panel's ` open `): through Git's `sh` the same `exec ${VISUAL:-${EDITOR:-vi}} "+LINE" FILE`, with Git's `usr\bin` first on its `PATH`, so `vi` is Git's vim; through PowerShell `VISUAL`, else `EDITOR`, split on spaces as `sh` splits it, and Notepad when neither is set, since Windows has no editor for a terminal of its own (Notepad opens its own window and the tab ends at once).
  - **Stopping**: nothing new. The teardown runs through `process::output_within` and a plugin's jobs through `Places::spawn`, both on `os::process::Grouped` (see Stopping a process and what it started), so `sh` or PowerShell and everything they start share a Job object and the hard step ends the whole tree. A setup and a plugin's popup are panes, stopped as panes are. No creation flag is added (`creation_flags` replaces `CREATE_NEW_PROCESS_GROUP`): like every other child of the server they share its console, which has no window (see The server in the background), so no window opens and no console is made per run.
  - **The plugin manifest's check** replaces #589's refusal: see Plugins (On Windows) for the rule, and The socket's folder for how an owner and a DACL are read; `os::fs::file_owner_and_mode` reads them from an open handle and `os::fs::reparse_point` the file's attribute. A file reparse point was made for the test with `FSCTL_SET_REPARSE_POINT` and a tag of no filter, which needs no privilege, unlike a symbolic link.
  - **Checked by hand** on 2026-11-03 (Windows 11 10.0.26200, Git for Windows 2.39.2, Windows PowerShell 5.1, no pwsh): `script::tests`, `git::worktree::setup::tests::on_windows`, `plugins::run::tests::on_windows` and `plugins::manifest::tests::on_windows`. They need Git for Windows. Not checked: a setup in a real pane, `Ctrl+C` in one, and pwsh 7.
