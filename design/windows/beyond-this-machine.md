# Windows › Beyond this machine

Part of [Windows](../windows.md).

- **Beyond this machine** (#603; checked 2026-11-03, Windows 11 10.0.26200, a debug build, OpenSSH_for_Windows 9.5p2, Git for Windows 2.39.2 with its OpenSSH 9.1p1, Tailscale 1.102.4):
  - **A Windows window, a server elsewhere** (`cornercase remote`, `--remote`) works. `ssh` is started as std starts any program, `ssh.exe` on the `PATH`: `C:\Windows\System32\OpenSSH\`, where Windows' OpenSSH Client is installed by default on Windows 10 1809 and 11 (from Git Bash, Git's own `ssh.exe` comes first). The command for the other end is one argument, which std quotes by the C runtime's rules and `ssh.exe` reads back unchanged and sends as it is, so the quoting written for the remote's `sh` (Remote windows) arrives intact. Checked end to end against an sshd run by hand on `127.0.0.1` with a temporary configuration, host key and client key (Git's MSYS `sshd`, whose shell is Git's bash, so the far end was this Windows with a POSIX shell), Windows' `ssh.exe` reached through a stand-in that only adds `-F` with that configuration, and `--command` naming this build: through `--remote`, `status`, `open` with a `/…` path, `send`, `wait`, `read`, and `logs` run there as a process; the window, in a ConPTY read with vt100, attached, ran a typed line in the far pane, showed `Connection lost` when its `ssh.exe` was killed, attached again on the first retry (`BatchMode`) with the screen redrawn and typing working, and ended with status 0 on ` More ▴ ` › `quit`. `ssh.exe` shares the window's console: input in raw mode kept working across its starts, so with `-T` it leaves the console's modes alone. Not checked: a password, passphrase or host key question on the first connection (`ssh.exe` asks on the console, before the window takes it), Git's `ssh.exe` as the client, a Linux or macOS server (none here), `ssh -t` for the questions of `update` and `kill-server`, and `restart --when-idle`'s tied input.
  - **A path given with `--remote`** is judged and written by the server's rules (Remote windows › Paths): from Windows, `/srv/x` was refused as relative, since Windows' `is_absolute` wants a drive, a drive path passed for `config project`, and `flow save --path` sent `\srv\…`, which the server never matched. To a Windows machine a Windows path is judged by Windows' rules instead (since 2026-11-04, below).
  - **A Windows server** (a window elsewhere reaching this machine; Remote windows › A Windows machine at the other end). On 2026-11-03 it was not supported: `cornercase proxy` itself ran here (the check above ran it under Git's bash: banner, first message, frames both ways, its end), but Windows' OpenSSH Server runs a command with its default shell, `cmd.exe /c` unless `DefaultShell` is set, and cmd finds no `sh` (Git for Windows puts only `Git\cmd` on the machine `PATH`) and does not read single quotes. Checked then: the exact command line, run through `cmd /c` and through `powershell -c` with the machine's `PATH`, failed in both with `sh` not recognized and status 1, which the window reported as an ssh error ending in cmd's last line, not as cornercase missing. Git's MSYS sshd gave its session neither `LOCALAPPDATA` nor `USERPROFILE`, so a proxy there looked for the socket under `%TEMP%` (that check set `CORNERCASE_SOCKET` through `--command`). Rejected then and still: a command line that cmd, PowerShell and `sh` all read, since their quoting rules differ and cmd would still find no `sh`.
    - **Since 2026-11-04** (#603) the client sends sh's line first, and after a failure that may come from another shell asks which shell it met (one `echo` that cmd, PowerShell and `sh` print three ways), then sends a line written for cmd or PowerShell, and remembers the answer per destination. On this side: Win32-OpenSSH loads the user's profile and builds the session's environment for the user (`USERPROFILE`, `LOCALAPPDATA`, the registry's `PATH`), unlike Git's MSYS sshd, so the proxy finds the socket a window here uses, and without `LOCALAPPDATA` `paths` still takes `%USERPROFILE%\AppData\Local`; its session job allows leaving (`JOB_OBJECT_LIMIT_BREAKAWAY_OK`), so the server, started with `CREATE_BREAKAWAY_FROM_JOB`, outlives the session with no change; the proxy now clears the inherit flag of all its handles before it may start a server, since Windows PowerShell handed it a second copy of the session's pipes that the server kept. An administrator's ssh session is elevated, so a server it starts runs elevated. All of it was read in Win32-OpenSSH's source and checked with a stand-in for sshd (a job with kill on close and breakaway allowed, only the standard handles, the registry's `PATH` without `sh.exe`, `cmd.exe /c "…"` and `powershell.exe -c …` quoted as Win32-OpenSSH does), not against a real sshd: OpenSSH Server is not installed here, and installing it needs an administrator. What was checked and what was not is in Remote windows › A Windows machine at the other end.
  - **Browser access** works: the listener is std's TCP, the bridge the server's socket, the codes `os::random`. Tailscale's CLI is `tailscale.exe` on Windows, which `tailscale::binary` looked for as `tailscale`, so it was never found and the dialog said Tailscale is not installed; it now looks for `tailscale.exe` on the `PATH`, then in `%ProgramFiles%\Tailscale\` (Browser access › Tailscale). Checked with a test server whose `PATH` had a stand-in `tailscale.exe` and not the real one, which was connected here, where `serve --bg` would have published a port on the user's tailnet: switching `remote` on ran `status --json` and `serve --bg --yes --https=8443 http://127.0.0.1:<port>`, off ran `serve --https=8443 off`; the Remote dialog showed the address and its QR code; `/` answered 401 before pairing, a wrong code 403, the dialog's code a cookie (303), `/` with it 200; a WebSocket with it attached as a client, a line typed through it ran in a pane and came back in its frames, and the window toasted `a browser connected`. The real `tailscale status --json` has the fields `parse_status` reads, and a throwaway test of `binary` and `status` against it, read only, found it on the `PATH` and parsed it. `web`'s unit tests run there, the finding of `tailscale.exe` and Tailscale's commands among them (their stand-in moved from a `#!/bin/sh` script to `test_util::fake_program`, see Test helpers); `app::tests::remote_access` still opens `/bin/sh` panes and does not. Not checked: the real `tailscale serve` on Windows, and a phone.
  - **Telegram and Discord**: HTTPS through `http` (ureq with rustls and webpki's roots), the Gateway's WebSocket (tungstenite with rustls), their files written by `persist` beside `config.json`, the pairing codes from `os::random`, the token typed without echo (see The console in raw VT mode); nothing reads a Unix path, a signal or a descriptor, and the Gateway's read timeout, `TimedOut` on Windows where Unix says `WouldBlock`, is taken as a wait as both are. Their unit tests pass on Windows (`telegram`, `discord` and `messenger`, 175, among them the Gateway against a local fake WebSocket and the links against `FakeHttp`); of the app's tests of them, Discord's pairing (`app::tests::control_requests::discord::pairing`) runs there, while its chat and away tests and Telegram's open `/bin/sh` panes and do not. Not checked live: there is no bot token here, so no bot was paired and away mode never reached Telegram or Discord.
- **Tunnels** (#735): `remote::tunnel` runs `ssh.exe -N -L …` like any ssh the window starts, and reads that its pid listens through `ports::listen`'s Windows table; the connect probe and the bind that choose the local port are std. `tunnel::owner` reads another process's command line through the PEB (`process::args`) and whether it listens through the same table, so windows of one computer share a tunnel there too; `tunnel hold` ends on console ctrl events (`on_end_signal`). `tunnel hold --reverse` (#794) runs `ssh.exe -N -R` and learns it is up from ssh's own stderr (`Allocated port`, or the `debug1` line under `LogLevel=DEBUG1`), not from that table; only the fake `ssh` (`test_util/program.rs`'s `.err`) has run it, never Win32-OpenSSH. None of it was checked live on Windows (it joins this list).

  - **Hints of a command run there in a terminal** (#834): `update`, `restart`, `kill-server` and the plugin commands run through `ssh -t` keep their stdio inherited on Windows, so what they print there is not rewritten with `--remote` (Win32-OpenSSH reads the console mode and size from its output handle, which a pipe would replace; Remote windows › Hints that name the machine). Not tried live.
