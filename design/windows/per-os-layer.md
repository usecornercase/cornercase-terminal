# Windows › The per-OS layer and its stubs

Part of [Windows](../windows.md).

- **The per-OS layer** (#588): `os/` is a shared leaf with one file per area of the port, each holding a `mod imp` for `cfg(unix)` and one for every other system (`cfg(windows)` once its Windows side is real, as in `console.rs`, `fs.rs`, `process.rs` and `socket.rs`: cornercase builds for Unix and Windows only, so no third `imp` is kept for targets nothing builds): `console.rs` (descriptors, standard input and output, the log taking stderr, and on Windows the console's modes, its input and its Ctrl events), `ffi.rs` (git's paths as bytes, see Git's paths), `fs.rs` (file modes, metadata, links, locks, `access`, the user's ids), `process.rs` (signals, process groups, sessions, `exec`, the server's stop signals), `random.rs` (the system's random bytes, see Lifting the refusal) and `socket.rs` (the local socket). On Unix an `imp` re-exports what the code used before (`std::os::unix`'s traits, `std::os::fd`, std's `UnixStream`, rustix's functions), so most callers only changed a `use` line. Where rustix's own types (`Errno`, `FlockOperation`) sat in the caller's logic, the Unix code moved into the `imp` as it was, behind a function of our own: `fs::try_lock` and `fs::locked`, `fs::writable`, `fs::uid` and `fs::gid`, `fs::set_mode` and `fs::set_file_mode` for `Permissions::from_mode`, which no Windows type can build, `process::alive`, `process::on_stop_signal`, `process::spawn_detached`, `process::leave_launch_folder` and `process::launch_folder` (#592) and `console::redirect_stderr`. Code whose Unix calls are woven into one module's own logic and types keeps its `imp` pair in that file instead: `client/requests/watch.rs` (whether the reader of a command's output or its input went away), `client/input.rs` and `client/probe.rs` (polling and reading the terminal), `client/window.rs` (the window's signals), `cli/config.rs` (a token typed without echo), `cli/requests.rs` (setting standard input and output aside), `highlight/limit.rs` (waiting for the painter, with its own `Fail`) and `term.rs` (a pane's pseudo terminal: its foreground program, its environment and closing it; see Panes in ConPTY). `rustix` and `signal-hook` are Unix-only dependencies: production code reaches them only inside a Unix `imp`, and only Unix-only tests use them directly. Each later step replaces one Windows `imp`.
- **What the stubs answer**: an empty list, `None`, `false` or 0 for what is read (a pid's name and whether a process is alive, until #596), `io::ErrorKind::Unsupported` for what acts (`setsid`; a lock, a link, a socket, `exec`, the log taking stderr and a signal until #589, #591, #592 and #597 ported them, and a mode set on a path until #589 made it succeed without doing anything), and nothing for a builder's mode or flags (`OpenOptionsExt::mode`, `DirBuilderExt::mode`, and `CommandExt::process_group` until #597), which cannot fail. The types that cannot exist yet (`OwnedFd`, and `UnixStream` and `UnixListener` until #591, the window's signal handle until #593) hold `Infallible`, so their methods are `match self.0 {}` and never run; a `BorrowedFd` is a token that every stub refuses (the console's input is read without one, see The console in raw VT mode). None panics. Paths as bytes were the one stub that worked, until #590 replaced them (see Git's paths). One stub acted as the Unix code does when it cannot: the painter's wait reported a broken worker rather than a timeout, so a file was not marked as too slow for good, until it was ported when the refusal went (see Lifting the refusal).
- **Stubs that guard safety had to fail closed before the refusal went**: a 0 read where the Unix code compares or checks would make the check pass. #589 settled the files: an identity, an owner or a mode that Windows cannot give reads as unknown, nobody's or `0o777`, so the checks refuse (see Files: identity and listings), and `NOFOLLOW` opens a link itself. #591 replaced the socket folder's refusal with a real check of its owner and DACL (see The socket's folder). `process::alive` asks Windows since #596, so a worktree lock whose holder runs reads as running. Nothing reached them while `cli::run` refused, and the refusal went only once an audit found none left (see Lifting the refusal).
- **The desktop** (#600): `os/desktop.rs` holds the calls the window and the server make on the user's desktop, and this step's `unsafe`, through `windows-sys` (pinned with `=`, a Windows-only dependency, its features listed in `Cargo.toml`): `shell_open` (`ShellExecuteExW`, for File Explorer and the default app), `windows_folder` (`GetSystemWindowsDirectoryW`, where Explorer is), `dangerous` (`AssocIsDangerous`), `play` (`PlaySoundW`), `Awake` (`SetThreadExecutionState` on a thread of its own) and `detach` (`CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`, where Unix gives a process group of its own). Its pair is inverted: the real `imp` is `cfg(windows)` and the other one stubs everything but `detach`, which is `process_group(0)` there. The callers choose by OS at run time, never with `cfg` around their code: `host::sound::Os` is passed down to what differs (the `PATH` lookup, `Kind`, `Openers`), and `agents::awake::tools` reads `cfg!(windows)`. So the Windows paths compile and are linted on every system, the stubs are reached, so nothing is dead code on Unix, and the rules that need no Windows call are tested on every system. Each area's note says what it decided: Opening in other apps, Sound, Keeping awake. A string with a NUL is refused before it reaches a call, rather than cut there.
