# Windows › The console in raw VT mode

Part of [Windows](../windows.md).

- **The console in raw VT mode** (#593): the window keeps its own byte decoder (see Keys and mouse), and the console hands it the bytes a Unix terminal sends. `os::console` keeps the input and output modes and sets raw VT mode before `ratatui::init`, so before crossterm's raw mode and the VT processing it turns on, and before ratatui writes its first sequence: the input goes to `ENABLE_VIRTUAL_TERMINAL_INPUT` and `ENABLE_EXTENDED_FLAGS` without `ENABLE_LINE_INPUT`, `ENABLE_ECHO_INPUT`, `ENABLE_PROCESSED_INPUT` and `ENABLE_QUICK_EDIT_MODE` (Quick Edit eats clicks), and the output to `ENABLE_VIRTUAL_TERMINAL_PROCESSING` and `DISABLE_NEWLINE_AUTO_RETURN`; every other bit stays. A console that refuses ends the window with `Error::Console` rather than run it without VT input. The kept modes are written back as they were rather than by turning bits back on (crossterm's `disable_raw_mode` turns line input, echo and Ctrl+C on whatever they were), and after `ratatui::restore`, so the alternate screen is left while VT processing is still on: at the end of `open`, before a restart's `exec`, in `release_screen`, and on a panic through a hook installed before ratatui's, which runs after ratatui's restore and before the message is printed. Crossterm turns VT output on once per process and never looks again, so once the kept modes are back (VT output off in the legacy conhost) nothing may write a sequence before raw mode is set again: a second window in the same process (the `[y/N]` answer to a server of another build) sets it before `ratatui::init`, and `release_screen` sets it before it writes, as after a restart's `exec` that failed. The panic hook is installed once per process, so a second window's hooks write their sequences before it restores the modes. On Unix the three calls are empty: crossterm's termios raw mode is all it needs.
- **Mouse, paste, focus and keyboard modes are written as text on every OS**: crossterm's `EnableMouseCapture` goes through the legacy console API on Windows, which sets the input mode to mouse records and so turns VT input off, and its `PushKeyboardEnhancementFlags` is refused there, which stopped `execute!` halfway. `Command::write_ansi` gives the bytes `execute!` wrote on Unix, unchanged, which `client::tests` checks on Unix.
- **Reading waits on the console's handle, without a thread**: `console::wait_input` waits with `WaitForSingleObject` on the input handle, then reads the records that woke it with `ReadConsoleInputW`, at most as many as `GetNumberOfConsoleInputEvents` counts, so a read never blocks past the deadline when another reader of the console took them first (none queued: it waits again). It keeps the characters of key-down records (and of Alt's key-up, which carries a character composed on the numpad, as libuv reads it), drops the rest (focus, size, menu and mouse records, key-ups) and waits again until its deadline. NUL (Ctrl+Space, Ctrl+@) has no character to keep: the console writes it as a key-down of virtual key `0x40`, a code no key uses, with Ctrl held and the character 0 (seen in Windows Terminal and conhost), so that record alone is kept as `0x00`, and a Ctrl pressed alone is not. A read returns once it took a byte, never 0, which would read as the end of input. The UTF-16 becomes UTF-8, a high surrogate waiting across reads for its other half, in one queue that the probe and then the window's input thread read. Rejected: reading with `ReadFile` or `ReadConsoleW` after the wait, which blocks when only focus or size records woke it; a reader thread feeding a channel, simpler and the same on every OS, which cannot be stopped while it blocks in a console read, so after the window ends it would keep taking keys from whatever reads the console next (the `[y/N]` question when a server of another build rejects the window, or the new binary of a restart, which Windows runs as a child since it has no `exec`); and `std::io::stdin`, which on a console drops a trailing Ctrl+Z. The wait and the decoding take the console as a trait, so their tests run on made-up records; a read that fails on a handle that is gone (`ERROR_INVALID_HANDLE`, `ERROR_BROKEN_PIPE`, `ERROR_HANDLE_EOF`) ends the input as `EIO` does on Unix.
- **Resizes are polled**, since Windows has no `SIGWINCH`: a thread of the window reads `crossterm::terminal::size()` (`GetConsoleScreenBufferInfo`) every `INPUT_POLL` (100 ms) and sends the same `Event::Resize` as the Unix signal thread when it changed; a size it cannot read is skipped. The console's own size records are dropped with the others, since the thread sees the change within 100 ms.
- **The window's Ctrl events stand in for `SIGINT`, `SIGHUP` and `SIGTERM`**: `SetConsoleCtrlHandler` turns `CTRL_C_EVENT`, `CTRL_BREAK_EVENT`, `CTRL_CLOSE_EVENT`, `CTRL_LOGOFF_EVENT` and `CTRL_SHUTDOWN_EVENT` into the window's `Signal`, which detaches it. With processed input off a typed Ctrl+C is the byte `0x03` for the pane, while a Ctrl+C sent by a program (`GenerateConsoleCtrlEvent`) and Ctrl+Break still reach the handler. Windows ends the process once the handler of a closed window returns, and the server sees the link close as a detach. An event is handled only while a window takes it, else it goes on to the next handler (Windows' default exits); the handler goes when the window's threads stop.
- **A token typed without echo** (`cli/config.rs`) turns `ENABLE_ECHO_INPUT` off, keeps line input so the token is still read as a line, and writes the mode back. Where that fails, though standard input is a terminal (mintty and Git Bash's own window, whose pipes `is_terminal` takes for a terminal but which have no console mode), `config secret` refuses to prompt and says to pipe the token in, rather than show it as it is typed; documenting the echo as a limit was rejected, since a token on screen is the one thing the prompt is there to avoid. On Unix the prompt never refuses (`Hidden::on` keeps the Windows `Option` under an `#[expect(clippy::unnecessary_wraps)]`).
- **The console, checked by hand** (2026-11-02, Windows 11 26200, Windows Terminal 1.24.12741.0 and the legacy conhost), with a throwaway ignored test started in a new console: the modes went from `0x1f7`/`0x7` (conhost `0x3`) to `0x3b0`/`0xf` and back exactly; records written with `WriteConsoleInputW` came back as `aé😀`, `0x03` and an up arrow as `ESC [ A` (the console turns a key into VT when the record is written); Windows Terminal answered OSC 11, OSC 10, DA1 and a cursor report, and conhost all but OSC 10 and 11, which the probe's 1 s timeout covers; `GenerateConsoleCtrlEvent` reached the handler for Ctrl+C and Ctrl+Break; the echo went off and back; on 2026-11-03, Ctrl+Space and Ctrl+@ written the same way came back as `0x00`. Not checked: keys, clicks and the wheel from a person, and resizes; the whole window against a server was checked once the refusal went (see Lifting the refusal). The console's tests are `#[cfg(windows)]` (`os::console::tests`, `client::window::tests::console`) and run in the Windows job since #601.
