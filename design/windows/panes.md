# Windows › Panes in ConPTY

Part of [Windows](../windows.md).

- **Panes in ConPTY** (#594): portable-pty's native system is ConPTY on Windows (10 1809 and later), so `Term` keeps one code path, and `term.rs`'s Windows `imp` handles what ConPTY and Windows do their own way. What ConPTY does to the bytes (it repaints, passes a mouse mode only from a program that reads VT input or asks the console for the mouse, holds the shell until its cursor request is answered) is under Terminals.
  - **The mouse needs nothing of ours** (#616): a program that asks for it gets it through ConPTY (Terminals › ConPTY), so vim with `set mouse=a`, or a program reading mouse records, takes clicks, drags and the wheel as on Unix; the one change is that X10 presses stop at column and row 95, and releases and drags past it come there (Keys and mouse). Passthrough mode was tried and rejected: the system ignores it and WezTerm's `conpty.dll` hangs with it, and using it would have meant creating the pseudo console ourselves instead of through portable-pty. A program that writes a mouse mode without reading VT input (cmd's `prompt`) keeps it in the host; it could not read the reports anyway.
  - **The pane's environment is the server's**: portable-pty builds a Windows command's environment from ours and then overwrites it with the registry's system and user variables (`PATH` the two joined), as a new login would, so a pane lost the `PATH` the server started with (Git Bash's `usr\bin`, a developer prompt's tools; checked). `imp::inherit` sets the server's own environment back over it, so a pane starts from the server's environment as on Unix, with cornercase's variables on top; a variable only the registry holds still comes through. A pane given no folder starts in `os::process::launch_folder` (#592).
  - **The foreground program** (ConPTY has no process groups, so no `tcgetpgrp`): the pane's tree from its shell (`process::children`, the newest child by start stamp at each step), down to the first program that is not a shell (`process::is_shell`); through nothing but shells, the deepest one (Git for Windows' `bin\bash.exe` launcher and the `usr\bin\bash.exe` it starts, a `cmd` started from pwsh), as Unix names a nested interactive shell. Not the deepest program: an agent's tools and MCP servers are its children, and on Unix they share its process group. **At the prompt** (`shell_in_foreground`, which launches, `wait` and the worktree checks read) is the pane's shell or a shell under it in the foreground (`imp::at_prompt`), so the launcher, or a shell started from the pane's, still counts as at its prompt; on Unix it stays the pane's shell itself. The cost is a few `OpenProcess` per call on the 50 ms snapshot, and `Term::feed` asks once per read.
  - **A background job counts as the foreground** (a limit): `start /b npm run dev` in cmd, `&` in pwsh 7 or Git Bash leave a program under the shell while the shell waits at its prompt, and nothing on Windows tells it from a program the shell waits for (no process group, no `tcgetpgrp`; the console's process list holds both). So while one runs the tab is named after it, `shell_in_foreground` is false (`wait` blocks, a launch waits, closing a worktree says a program runs), and agent detection looks at it. Rejected: a job object or the console's process list, which would not tell the two apart either, and asking the shell, which only a prompt hook could (see The pane's folder).
  - **The pane's folder** (`Term::cwd`): the current folder of the foreground process, as on Unix, which cmd and bash keep in step with `cd`. PowerShell does not: `Set-Location` moves its location and never its process folder (checked with Windows PowerShell 5.1 on 2026-11-03; pwsh 7 was not installed here). So when PowerShell is in the foreground (`pwsh` or `powershell`, by name), the folder its prompt reported wins, when it names a folder that exists: an OSC 7 `file://` URL (host dropped, percent escapes decoded, `/C:/…` read as `C:/…`) or ConEmu's OSC 9;9 path (quotes dropped), which libghostty-vt keeps raw as `pwd` (OSC 1337's `CurrentDir` too). A program PowerShell starts gets its location as its folder, so a running program's own folder is right. **The default PowerShell prompt reports nothing**, so until the user's prompt does (Windows Terminal's documentation gives the line for OSC 9;9, and oh-my-posh and Starship can emit it), a PowerShell pane's folder is the one it started in: a relative path clicked in it, `status`'s path, the terminal request's folder, the files opened from it and a new tab's folder start from there. Other readers of a process's folder (ports, the worktrees dialog's busy check) see the same. No prompt hook is injected: it would mean starting PowerShell with a command of ours (so the pane would count as started with a command, not a shell), running code of ours at every prompt in the user's session, and fighting the prompt frameworks that replace `prompt`; on Unix nothing is injected into a shell either. On Unix the reported folder is not read (`imp::reported_folder` answers nothing), so nothing changes there.
  - **The exit and closing**: ConPTY keeps its output pipe open after the shell exits, so the reader never saw the end and `Event::Exited` never came (only `App::reap`'s poll noticed). A thread per pane waits on the shell's process handle and then closes the pseudo console (dropping the master), which sends the last frame, ends the console host and closes the pipe, so `Exited` comes after the last output as on Unix. Closing never runs on the main thread (the waiter, or a thread from the master's `Drop`): `ClosePseudoConsole` waits for the host, and the host waits for the answer to its startup cursor request (portable-pty sets `PSEUDOCONSOLE_INHERIT_CURSOR`) while nothing has fed the pane's output to the emulator, which answers it. So the closer first writes a cursor report (`ESC[1;1R`) into the pane, where nothing reads it any more. Without it a pane dropped while the request waits never closed under WezTerm's `OpenConsole.exe`, while the system's `conhost.exe` (build 26200) closed at once anyway; so its test (`exit::a_pane_dropped_with_the_cursor_request_unanswered_closes_even_under_openconsole`) fails without it only when WezTerm is on the `PATH` of the test run, and passes under conhost either way.
  - **Which console host**: portable-pty loads a `conpty.dll` from the DLL search path before the system's (seen under #592): with WezTerm on the `PATH` every pane ran WezTerm's `OpenConsole.exe`, else the system's `conhost.exe`. The tests passed under both (Terminals says where they differ); the search was left as it is, since taking it from portable-pty would mean keeping a fork of it.
  - **The default shell** (`term::shell::default`, once when the server starts): `$SHELL` if Windows can start it (a full path, or a bare name found on the `PATH`, without surrounding quotes), else `pwsh.exe` on the `PATH`, else `powershell.exe` on the `PATH`, else `%COMSPEC%` if it names a program, else `cmd.exe`; each is started by its full path. A candidate counts only as a file ending in `.exe` or `.com` (a name without one gets `.exe`), the programs `CreateProcessW` starts by themselves: an extensionless npm or Scoop shim beside the program, or a `.cmd`, would have been taken and then failed for every pane, with nothing to fall back to. A `$SHELL` Windows cannot start as it is (a Unix path such as `/usr/bin/bash`, a relative one) is skipped with a warning in the log, not mapped: Git Bash and MSYS2 hand their `SHELL` to native programs already as a Windows path (`C:\Program Files\Git\usr\bin\bash.exe`, checked), so a Unix path comes from a setting not meant for Windows, and looking its name up on the `PATH` could start WSL's `bash.exe`. That `usr\bin\bash.exe` finds `ls` only with Git's `usr\bin` on the `PATH` (Git's `bin\bash.exe` launcher adds it), which a server started from Git Bash now hands its panes. The shell starts without arguments, as on Unix, so PowerShell prints its banner and loads the user's profile. pwsh from the Microsoft Store is an app execution alias, a reparse point `metadata` may not follow, so a file counts when `metadata` or `symlink_metadata` says it is one.
  - **Tests** start `cmd.exe /d` (no AutoRun commands, cmd's profile) with `PROMPT=$G` and a `PATH` of `System32` alone: the `PATH` cargo gives a test (every build script's folder, about 8,600 characters here) passes the 8,191 characters cmd can expand, and cmd then finds no program at all. PowerShell runs there with `-NoProfile`. The mouse tests have it compile a reader of ours (`tests/fixtures/conpty/mouse.cs`, with `Add-Type`, which Windows PowerShell 5.1 does with the .NET Framework's compiler that comes with Windows) that asks for the mouse with VT codes or through the console API and prints what it reads, as hex for VT input, since Windows ships no program that asks for the mouse, and Git for Windows' vim is not on every machine. Under Constrained Language Mode (AppLocker or WDAC) PowerShell refuses `Add-Type`: the reader's start then catches the refusal and the test fails at once with PowerShell's answer, rather than after its 30 s wait (checked with a call the reader does not have; Constrained Language Mode itself was not tried). Paths given to PowerShell are single-quoted with their quotes doubled (`single_quoted`), so a folder with an apostrophe still works. One test starts a pane without setting `PATH` and compares the shell's own (`process::env`) with the test's, which cargo made unlike the registry's, so it fails without `imp::inherit`.
