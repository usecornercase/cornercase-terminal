# The files a process holds open

Code: `process/handles.rs`, `process.rs` (its Windows `imp`), `test_util.rs` (`holding`, `holding_reading`) (#618)

Codex, Copilot, Cursor and opencode find their records by the file the agent holds open (`process::open_files`, see Context use), read from `/proc/<pid>/fd` on Linux and with `lsof` on macOS. Windows keeps no list of a process's open files, only its handles, so `open_files` reads those, as Process Explorer does: one code path for the four agents, the one Linux and macOS follow, rather than a rule per agent.

- **Only the pid's handles**: `NtQueryInformationProcess` with `ProcessHandleInformation` (Windows 8 and later) lists one process's handles, each with its object type. Rejected: the system's whole table (`NtQuerySystemInformation` with `SystemExtendedHandleInformation`), every handle of every process, megabytes on a busy machine, to keep one pid's. It needs `PROCESS_QUERY_INFORMATION` and `PROCESS_DUP_HANDLE`, so the user's own processes are read, and an elevated one or another user's lists nothing.
- **Only files**: a handle counts when its object type is `File`. The type's number changes between Windows builds but not while one runs, so it is learnt once, from a handle of cornercase's own to `NUL` found in its own list, rather than asking each handle's type name (`NtQueryObject`), one more call per handle. Folders, pipes, the console and sockets are `File` objects too, and go through the same steps.
- **The path**: each file handle is copied into cornercase (`DuplicateHandle`, the same access) and named with `GetFinalPathNameByHandleW` and `VOLUME_NAME_DOS`, the call `std::fs::canonicalize` makes, so a path reads `\\?\C:\Users\…` as the agents' homes do once `discovery::home` canonicalises them, and the readers' `starts_with` and `==` hold (tested per agent). That is std's form, not the plain one `os::fs::canonicalize` gives the folders cornercase stores (#628): the two sides must match, so a reader that moves its home to the plain form needs `open_files` to give it too. A file on a volume with no drive letter has no such name and is left out, as `canonicalize` fails on it. Closing the copy leaves the agent's byte-range locks (SQLite's) alone, since Windows drops only the locks of the process that closes its last handle to the file (tested: another process's lock holds after its files were read twice).
- **A name that blocks**: asking for the name of a handle that another thread is reading synchronously waits until that read ends, since a synchronous file object does one operation at a time. Checked live on 2026-11-03 (Windows 11 10.0.26200): `findstr` and PowerShell blocked on their standard input pipe each held the question up until they exited, and the tests hang without the timeout; a pane's console input blocks the same way (checked on 2026-11-04, below). So the names are asked in order on a worker thread, and each answer is given 1 s (`NAME_WITHIN`); when one takes longer, the call skips that handle and goes on with the next ones on a new worker. The worker that waits ends once it is answered, when the read ends, which the process's exit does for its own reads (tested).
- **A handle another process reads**: a process holds a copy of every inheritable handle of the one that started it (Rust's `Command`, cmd, PowerShell and most runtimes start children with `bInheritHandles` and no handle list), so one file object can be shared with processes the pid does not control: its parent and the parent's other children. When one of them keeps a synchronous read pending on it, the question about the pid's copy waits for that read, not for the pid, and outlives it, holding its place in the list until that read ends; the cap bounds it, and a later question about any copy of that object, in any process, is skipped at once (see The same question is the same object). Checked on 2026-11-04 (Windows 11 10.0.26200): a test's `findstr` holds about 25 copies of the test binary's inheritable handles (its standard handles, its folder, those its own parents passed down), and a question about its copy of a pipe another thread reads stayed after `findstr` was killed and ended with that read. On GitHub's Windows runner (Server 2025, 10.0.26100) a question about `findstr` outlived it by 30 s, so a handle the test binary passes down there is held in such a read (which one was not found; the runner closes the shell's standard input, so not that one). Rejected: asking only a pid's own handles (an inherited handle keeps its inherit flag, but so do the standard handles a child is given, where `holding` puts its file), and dropping a question once its pid exits (its thread still waits, so the 16 would no longer bound the threads).
- **It happens in every pane**: portable-pty starts the shell with `bInheritHandles` false and invalid standard handles, so none of the server's handles reach a pane, but the console handles the shell gets from its pseudoconsole are inheritable, so every program it starts holds copies of them, and a synchronous read on the console by any process of the pane, the shell's own prompt included, blocks the name of every copy of the console's input. Checked on 2026-11-04 (Windows 11 10.0.26200) in panes started by `Term` through portable-pty 0.9 (a throwaway test, not committed) and in a copy of its spawn: under `cmd /d` running `findstr x`, and under Windows PowerShell 5.1 (`-NoProfile`, PSReadLine at its prompt) with a `ping` started by `Start-Process -NoNewWindow`, the shell's and the program's handles to the console input were one object (`CompareObjectHandles`) and the questions about both waited; keyed by pid and handle, as the list was before, the program's copy took a second place and a second 1 s. A `node` launcher with `stdio: 'inherit'` whose `node` child read its standard input in line mode left the launcher and the child (with two handles of its own to it) holding one blocked input, three places for one read; a `node` reading in raw mode (libuv waits for input before it reads) blocked nothing. Not checked, since no agent could be installed here: which of the four agents reads the console in a way that blocks, and whether Codex's app-server daemon, which Rust's `Command` starts with every inheritable handle of the Codex that started it, holds a copy of that pane's console input (it would then wait whenever that pane's shell sits at its prompt).
- **One question per object, 16 at most**: a worker copies the handle (`DuplicateHandle`, which never waits) and takes the copy into the list of names being asked just before it asks, and gives it back once answered, both under one lock with the checks. A call whose worker meets a question about the same object in the list does not ask again: it takes that question's answer, waiting for it until the question has run as long as the call's own wait (1 s). So two readers that want one name at once both get it (an opencode pane's reader and another pane's check that its database is shared, say), and a question older than that is taken for blocked and skipped at once. Two calls that want the same blocked name ask it once and leave one thread behind, rather than each waiting a second and each leaving a thread (tested). The waiting worker takes no place in the list and is done within that second.
- **The same question is the same object**: what blocks is the file object (its one operation at a time), not a handle to it, and its name is the same through any handle, so a new copy is matched against every question in the list with `CompareObjectHandles`, whatever process and handle value each came from. One stuck object costs one place in all, however many processes hold copies of it and however many handles one of them has to it (tested with fakes, and on Windows with two `findstr` reading one pipe). The list used to key a question by pid and handle value, so each copy took a place of its own: a pane's console input took one per process asked (above), and the handles a test binary passes down to every child could fill the 16 alone, after which nothing was named. A handle value is reused once the process closes its handle, so a value that now names another file names another object and is asked anew while the old question still waits (tested, and the Windows tests check that two copies of one file are one object and a copy of another file is not). The check is in the object manager and never waits on the file; it is made against each question in the list, 16 at most per handle, and the copy each question holds keeps its object alive, so a later object cannot be taken for it. Rejected: a key of the object's own, since the handle list carries no object address, the system's list gives none to a process that is not elevated (all zero on 26200), and a file id (`FileIdInfo`) is asked of the file object and waits like the name (both checked on 2026-11-04, the second on a pipe with a read pending). It needs Windows 10 1607 or later, below the AF_UNIX socket's 1803 that cornercase already needs.
- **The cap**: the list's length is the number of questions in flight, waiting or not, and a worker that finds 16 (`MOST_ASKED`) asks nothing and ends its call; the check and the taking are one step, so two calls at once cannot both take the 16th place, which a count checked first and a handle marked stuck a second later allowed (tested). The first time the list is full `server.log` gets a warning (`process: open files are not named`), once per server, so an agent's missing line can be traced to it. A question that panics gives its place back too (`panics::contain`), so it cannot hold one for good.
- **1 s, not 100 ms**: a name that is slow but not blocked (every core busy with a build, a network drive, a filter driver such as an antivirus) is skipped like a blocked one, and the readers take a missing record as gone: Codex and Cursor drop it on one empty answer, so the line blinks off and Codex reads its rollout again from the start. A name is microseconds, so a whole second only runs out for a handle that is really waiting. The cost of the longer wait is paid once per blocked object, since it is then skipped for as long as it waits, on a reader's discovery job that runs every 500 ms per tab, never on the server's loop. Rejected: keeping a skipped handle's last name and answering with it (the readers would keep their record), since a handle value is reused once its handle is closed, so a stale name could name a file the process no longer holds, and it needs a cache per pid and its pruning; and telling the readers that a name was skipped, which changes `open_files` on every OS for a case only Windows has.
- **Rejected for a blocked name**: ending the stuck thread (`TerminateThread` can leave the heap's or the loader's locks held), `CancelSynchronousIo` (it cancels the thread's own requests, not a wait for another thread's), and picking pipes and consoles out first, with `GetFileType` (it waits on the same lock) or by their access masks (a database open to read and write has a pipe's mask).
- **Cost**: one list of the pid's handles and one name per file handle, microseconds each. A call has one worker at a time: it starts one, and a new one for the handles left after each handle it gives up on. A worker given up on while it asks stays blocked in that question, holding its place in the list, until the read ends (the process's exit ends its own reads, not another process's), and then ends; one given up on while it waits for another call's answer ends within that second, and one given up on before it took its next handle ends at once. So the threads left behind are the blocked askers, at most one per place, 16 in all across every call, plus waiters gone within a second. An object that blocks costs 1 s the first time a copy of it is asked (and what is left of that second to a call that comes meanwhile) and nothing while it stays blocked, whichever process's copy a later call meets. An agent waiting for input keeps that read blocked, so its handle is skipped until the read ends, and the next call then waits once more. Every reader asks from its own discovery job, never from the server's loop.
- **Rejected: each agent's records by what it writes** (the newest session file that names the pane's folder). Codex adds a folder rule only for its app-server daemon, which holds every session's rollout at once; such a rule cannot tell two agents of one kind in one folder apart, which the file each holds does, and it is a rule per agent and version where the handle table keeps one for all four.
- **Limits**: Codex's and Copilot's homes come from `CODEX_HOME` or `COPILOT_HOME`, else from `HOME`, which Windows does not set, so until #599 falls back to `USERPROFILE` those two find their records only where one of the three is set; Cursor and opencode need no home for their record (per agent under Context use). The pid the readers ask about is the tab's foreground program, found down the pane's process tree from its shell (see Panes in ConPTY, #594). None of the four agents could be run here: each reader is tested with a `findstr` holding its record where the agent would (`test_util::holding`), so that each agent holds its file open on Windows as it does on Linux is still to be checked live with #599.
- **Tests**: on every OS, the snapshot's parsing (one type, a count shorter than the list, a cut entry or header) and the naming with fake objects (every name, one that blocks and is skipped, then asked again once it answered, one asked once while a second call waits for its answer and takes it, a handle value reused for another object asked anew while the old question still waits, one blocked object held through two handles of one process and a handle of another asked once and in one place, a full list (of two in the test) that later questions find full while the first two still wait, warned of once over two such calls (`Waiting::filled` says whether to warn, and its caller logs), one that fails). `names` takes its wait and its list (`Waiting`, one per test, so a test that fills it cannot stop the others running beside it), so these give a good answer 30 s and only the blocking cases 2 s or 100 ms, and a loaded runner cannot skip a good one; the Windows tests wait for the file to be named rather than ask once, for the same reason. On Windows, `process::handles::tests::on_windows` (a file of this process, as `canonicalize` names it; two copies of one file as one object; an exited pid; a `findstr` whose blocked standard input, a pipe the test keeps a copy of (`holding_reading`), is skipped while its file is named, and whose question about it ends with it: only that question, found with `CompareObjectHandles` against the copy, since those about the handles it inherited from the test binary can wait on another process; two `findstr` reading one pipe, whose two copies of it take one place, which fails when questions are keyed by pid and handle; a PowerShell's lock kept, read only once it said it holds the lock, since the test's probe takes the lock itself whenever it is free; its line is read on a thread and given 30 s, so a child that stalls fails the test and is killed rather than hanging it) and the `on_windows` groups of the Codex, Copilot, Cursor and opencode readers.
