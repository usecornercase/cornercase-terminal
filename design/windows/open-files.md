# The files a process holds open

Code: `process/handles.rs`, `process.rs` (its Windows `imp`), `test_util.rs` (`holding`) (#618)

Codex, Copilot, Cursor and opencode find their records by the file the agent holds open (`process::open_files`, see Context use), read from `/proc/<pid>/fd` on Linux and with `lsof` on macOS. Windows keeps no list of a process's open files, only its handles, so `open_files` reads those, as Process Explorer does: one code path for the four agents, the one Linux and macOS follow, rather than a rule per agent.

- **Only the pid's handles**: `NtQueryInformationProcess` with `ProcessHandleInformation` (Windows 8 and later) lists one process's handles, each with its object type. Rejected: the system's whole table (`NtQuerySystemInformation` with `SystemExtendedHandleInformation`), every handle of every process, megabytes on a busy machine, to keep one pid's. It needs `PROCESS_QUERY_INFORMATION` and `PROCESS_DUP_HANDLE`, so the user's own processes are read, and an elevated one or another user's lists nothing.
- **Only files**: a handle counts when its object type is `File`. The type's number changes between Windows builds but not while one runs, so it is learnt once, from a handle of cornercase's own to `NUL` found in its own list, rather than asking each handle's type name (`NtQueryObject`), one more call per handle. Folders, pipes, the console and sockets are `File` objects too, and go through the same steps.
- **The path**: each file handle is copied into cornercase (`DuplicateHandle`, the same access) and named with `GetFinalPathNameByHandleW` and `VOLUME_NAME_DOS`, the call `std::fs::canonicalize` makes, so a path reads `\\?\C:\Users\…` as the agents' homes do once `discovery::home` canonicalises them, and the readers' `starts_with` and `==` hold (tested per agent). A file on a volume with no drive letter has no such name and is left out, as `canonicalize` fails on it. Closing the copy leaves the agent's byte-range locks (SQLite's) alone, since Windows drops only the locks of the process that closes its last handle to the file (tested: another process's lock holds after its files were read twice).
- **A name that blocks**: asking for the name of a handle that another thread is reading synchronously waits until that read ends, since a synchronous file object does one operation at a time. Checked live on 2026-11-03 (Windows 11 10.0.26200): `findstr` and PowerShell blocked on their standard input pipe each held the question up until they exited, and the tests hang without the timeout; the console's input should block the same way (not checked). So the names are asked in order on a worker thread, and each answer is given 1 s (`NAME_WITHIN`); when one takes longer, the call skips that handle and goes on with the next ones on a new worker. The worker that waits ends once it is answered, when the read ends or the process exits (tested). Until then the handle (pid and value) is marked stuck and later calls skip it without asking, so a blocked handle holds one thread at most, and with 16 stuck (`MOST_STUCK`) no call asks for any name until one ends; the first time that happens `server.log` gets a warning (`process: open files are not named`), once per server, so an agent's missing line can be traced to it.
- **1 s, not 100 ms**: a name that is slow but not blocked (every core busy with a build, a network drive, a filter driver such as an antivirus) is skipped like a blocked one, and the readers take a missing record as gone: Codex and Cursor drop it on one empty answer, so the line blinks off and Codex reads its rollout again from the start. A name is microseconds, so a whole second only runs out for a handle that is really waiting. The cost of the longer wait is paid once per blocked handle, since it is then skipped for as long as it waits, on a reader's discovery job that runs every 500 ms per tab, never on the server's loop. Rejected: keeping a skipped handle's last name and answering with it (the readers would keep their record), since a handle value is reused once its handle is closed, so a stale name could name a file the process no longer holds, and it needs a cache per pid and its pruning; and telling the readers that a name was skipped, which changes `open_files` on every OS for a case only Windows has.
- **Rejected for a blocked name**: ending the stuck thread (`TerminateThread` can leave the heap's or the loader's locks held), `CancelSynchronousIo` (it cancels the thread's own requests, not a wait for another thread's), and picking pipes and consoles out first, with `GetFileType` (it waits on the same lock) or by their access masks (a database open to read and write has a pipe's mask).
- **Cost**: one list of the pid's handles and one name per file handle, microseconds each, on one worker thread per call; a handle that blocks costs 1 s the first time and nothing while it stays blocked. An agent waiting for input keeps that read blocked, so its handle is skipped until the read ends, and the next call then waits once more. Every reader asks from its own discovery job, never from the server's loop.
- **Rejected: each agent's records by what it writes** (the newest session file that names the pane's folder). Codex adds a folder rule only for its app-server daemon, which holds every session's rollout at once; such a rule cannot tell two agents of one kind in one folder apart, which the file each holds does, and it is a rule per agent and version where the handle table keeps one for all four.
- **Limits**: the homes still come from `HOME` (or `CODEX_HOME`, `COPILOT_HOME`), which Windows does not set, so Codex and Copilot find their records once #599 reads `USERPROFILE` too; Cursor and opencode need no home for their record (per agent under Context use). None of the four agents could be run here: each reader is tested with a `findstr` holding its record where the agent would (`test_util::holding`), so that each agent holds its file open on Windows as it does on Linux is still to be checked live with #599. And a tab follows its pane's shell until ConPTY gives its foreground program (#594).
- **Tests**: on every OS, the snapshot's parsing (one type, a count shorter than the list, a cut entry or header) and the naming with a fake question (every name, one that blocks and is skipped, then asked again once it answered, one that fails). `names` takes its wait, so these give a good answer 30 s and only the blocking case 2 s, and a loaded runner cannot skip a good one; the Windows tests wait for the file to be named rather than ask once, for the same reason. On Windows, `process::handles::tests::on_windows` (a file of this process, as `canonicalize` names it; an exited pid; a `findstr` whose blocked standard input is skipped while its file is named, and whose stuck question ends with it; a PowerShell's lock kept) and the `on_windows` groups of the Codex, Copilot, Cursor and opencode readers.
