# Windows › Folders, files and links

Part of [Windows](../windows.md).

- **Folders** (#589, `paths.rs`): the settings in `%APPDATA%\cornercase\` (roaming, like the settings themselves), and the state (session, log, socket and lock, accounts, plugin state, run folders) in `%LOCALAPPDATA%\cornercase\`, which stays on this machine, as a server and its socket do. A debug build keeps `cornercase-dev\` and `cornercase-dev\<key>\` the same way (Client / server). Without the variable, `%USERPROFILE%\AppData\Roaming` or `Local`, then the temp folder; relative values are ignored, as on Unix. They are read from the environment, which Windows sets for every logon, rather than with `SHGetKnownFolderPath`, so `paths` stays pure over a lookup and its tests cover the Windows rule (`paths::Base`, one per OS). **`XDG_*` and `HOME` are not read on Windows**, even when set: Git Bash and MSYS2 users set them in an rc file, which a cornercase started from PowerShell, cmd, Explorer or the Start menu never sees, so honoring them would give one user two sockets, and two servers on two sessions, depending on the shell that started it, the split #355 removed on Unix. `CORNERCASE_SOCKET` still overrides everything. No earlier socket is probed (`paths::earlier_sockets` is empty: no release before 0.12.140 ran on Windows), so finding the socket never needs a uid. Limit: `secrets.json` sits next to the settings, so a roaming profile copies the tokens to the domain's profile server, as it does for `gh`'s.
- **File modes** (#589): `set_mode`, `set_file_mode` and the builders' `mode` succeed without doing anything. Every caller asks for a private file or folder (`0600`, `0700`), which the default ACL of the user's profile already gives (the user, SYSTEM and Administrators only), or for a program (`0755`, the update's binary), which Windows tells by its extension. Limit: a private file written outside the profile (`CORNERCASE_SOCKET` elsewhere, `config share` into a shared folder) takes that folder's ACL; writing an owner-only DACL was left for when it is needed, and the socket's folder is the one place that writes one (#591).
- **Files: identity and listings** (#589): std's Windows `volume_serial_number` and `file_index` are unstable (`windows_by_handle`), so `os::fs::stat` and `stat_file` read them with `GetFileInformationByHandle`, opening a path with no access rights and `FILE_FLAG_BACKUP_SEMANTICS` as std's own `metadata` does (a folder opens, and no sharing mode is in the way). Every caller that compares files goes through them and compares the device with the inode (`Stat::id`), since a file index, like an inode, is unique only within its volume: `persist::mark`, a transcript's `jsonl` reader, `log::Follower` (a rotation) and `accounts::transfer::same`. On ReFS the 64-bit index can repeat (`FileIdInfo` has 128 bits); left for later. A listing (`DirEntry::metadata`, from `FindNextFile`) has no handle, and opening every file would make a walk of `node_modules` many times slower, so `MetadataExt` answers what a listing knows: `blocks` the length in 512-byte blocks, rounded up (a worktree's size counts the length, not clusters, compression or sparse files), `mtime` and `ctime` the last write (std has no stable change time), so the changes panel's stamp moves with every write, `nlink` 1 (each hard link is counted, an overcount for a pnpm store) and `dev` 0. One device is the true answer for the walks that read it: Windows mounts a volume inside a folder only through a reparse point, which `symlink_metadata` and `DirEntry::metadata` report as a link and never as a folder, so `disk::usage` and `crosses_device` never enter one, `builds::deletable` refuses a folder that is one (no longer a folder) or is reached through one (its canonical parent leaves the worktree), and `remove_dir_all` removes a junction or a mount point without entering it.
  - **What guards safety fails closed**: `ino` is a new number on every call, so an unknown identity never equals another (`disk.rs` never reads it, since `nlink` is 1); `uid` and `gid` are `u32::MAX`, nobody's, while the user's own (`os::fs::uid`) is 0; and `mode` reads `0o777`. So the plugin manifest's `guarded` refused every plugin (it belonged to another user) until #595 made it read the owner's SID and the DACL, as the socket's folder does since #591 (`os::fs::owner_and_mode`, see The socket's folder and Scripts and plugin commands without sh); `uid` and `mode` then left the Windows `MetadataExt`, since nothing read them any more, so no later caller can compare a made-up owner or mode. `PermissionsExt::mode` stays 0, so no file reads as a program by its mode; the agents' and the host helpers' searches go by `PATHEXT` there instead (#599, #600). `NOFOLLOW` is `FILE_FLAG_OPEN_REPARSE_POINT`, which `custom_flags` passes on, so a manifest opened without following is the link itself, not a file, and is refused.
- **Links** (#589, `os::fs::link_to`, `links_to`, for an account's shared settings, Accounts and profiles): a symbolic link needs Developer Mode or an administrator, so a folder becomes a directory junction (a mount point reparse point, set with `FSCTL_SET_REPARSE_POINT` on a new empty folder, which needs no privilege), and a file a hard link, one file under two names, so an edit through either shows in both. Where the volume holds no hard link (FAT, or another volume) the file is copied into a temporary file beside the link, synced, and only then given the link's name with `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` (std's `rename` replaces), so a crash mid-copy leaves no partial file under the name `links::ensure` would keep, and a name taken meanwhile is left alone; the temporary file goes on any failure. `links_to` counts a symbolic link or a junction (std's `is_symlink` covers both, being name surrogates) or a file with its original's identity; a copy, or a hard link an agent broke by writing atomically, is reported as not shared, as a replaced symbolic link is on Unix. A junction leads only to a local disk, so a default home on a network share fails the account's links: the configured path must start with a drive (checked first, so a share is never reached), and so must its canonical path, which catches a folder on a drive that is a symbolic link to a share; the junction then leads to that canonical path, the one checked, so a link changed after the check cannot move it to a share. Removing an account's folder removes its junctions and hard links and leaves what they lead to (tested). Rejected: a symbolic link first and a junction when it fails, since the result would depend on Developer Mode, and `mklink /J`, a process per link through `cmd`'s quoting.
- **Locks and the rest** (#589): `try_lock` is std's `File::try_lock` and `try_lock_shared` (`LockFileEx` with `LOCKFILE_FAIL_IMMEDIATELY`). As with `flock`, a lock belongs to the open file, keeps out a second open in the same process and goes with the handle; Windows locks are mandatory, which costs nothing here, since nothing reads or writes a lock file. `writable` creates and removes a probe file, since an ACL decides and there is no `access`. `truncate` (the log starting over when it cannot rotate) goes through a second handle, since an append handle has no `FILE_WRITE_DATA` on Windows. Checked live on 2026-11-02 (Windows 11 10.0.26200, NTFS, Rust 1.99.0, without Developer Mode, so no symbolic link could be made): the tests of `os/fs/` (junctions, hard links, copies, identity across a rename, locks, removing a folder of links), `accounts::links`, `paths`, `persist`, `log` and the context readers pass.
