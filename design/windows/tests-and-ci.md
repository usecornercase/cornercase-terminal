# Windows › Tests on Windows and CI

Part of [Windows](../windows.md).

- **Tests that need Unix** are `#[cfg(unix)]`: the whole test file, with `#![cfg(unix)]` on its first line, where most of it needs Unix (file modes, symlinks, descriptors, rustix, the server's attached client), else the group or the test, and the test helpers only they use carry `#[cfg(unix)]` under their `#[cfg(test)]`. Never `#[cfg(all(test, unix))]`: clippy (its exemptions for tests) and `tests/layers.rs` only see code under a literal `#[cfg(test)]` as test code, and the combined form made clippy lint `worktrees::tests` as production code. Since the suite runs on Windows (#601), a test that only runs a shell script or a `/bin/sh` pane is `#[cfg(unix)]` too, and so are `test_util`'s `Locked`, `Sleeper`, `Family`, `child_running`, `sleep_named`, `signal` and `TITLE_SIGNAL`, which only such tests use (the Windows `CommandExt::arg0` stub went with `Sleeper`): the Windows build then checks that nothing that runs there reaches them. Since #591 `UnixStream::pair` exists on Windows too, for tests only (a listener on a temporary path, connected and accepted), so the tests that only need a socket run on both: `protocol`'s paths and peers, `client::server_process`, `client::requests` but its readers and inputs, `cli::requests`' streams and the proxy's slow ssh. The e2e crate is `#![cfg(unix)]`. The Windows process tests (`process::tests::on_windows`, `process::handles::tests::on_windows`, the `on_windows` groups of the Codex, Copilot, Cursor and opencode readers, `git::worktree::tests::lock_holder_on_windows`, the detection cases of `agents::tests`) and pane tests (`term::tests::on_windows`, `term::shell::tests::on_windows`) were run by hand before #601, and there `test_util::exited_pid` gives a pid Windows never hands out (`i32::MAX - 3`) instead of running `/bin/sh`: Windows gives an exited process's pid to the next process within milliseconds, and tests spawning in parallel took each other's. So were the stop's (#597): `os::process::windows::tests` (ending a process, a program with no window left as it was by the polite step, a job that holds a `cmd` and its two `ping`s, ends them on the hard step and when closed by the system, and leaves what an ended child started when dropped), `processes::stop::tests::on_windows`, `process::escalation::tests` on every OS, the CLI texts and a plugin action ended by the hard step, which reads as `exited` with code 1. Their `cmd` lines run `ping` by its full path: under `cargo test` here, `cmd` found no `ping` on the `PATH`.
- **Tests on Windows** (#601): the Windows job runs every test that is not `#[cfg(unix)]`, about three quarters of the suite (8,404 unit tests on 2026-11-04; about 35 s for the tests themselves on a laptop, once built): the parsers and readers (agents' records, issues, pull requests' and pipelines' JSON, diffs, config, settings, the saved session), the UI's renders, layouts and snapshots, the dialogs and panels that need no pane, git through Git for Windows (changes, worktrees, the merge check), the socket and the protocol, files and folders, and the Windows tests of processes, panes in ConPTY, the console, the desktop and scripts through Git's `sh` (they need Git for Windows, which the runner has). What stays `#[cfg(unix)]`, by area:
  - **The app tests that open a project** (`app::tests`: 144 of its 2,611 run on Windows): every pane `new_app` opens runs `/bin/sh`. They move to `cmd.exe` panes (`new_app_with_shell`, as `projects::on_windows` already does) area by area, with the step that ports it.
  - **Tests that run a `#!/bin/sh` fake or `/bin/sh`, `/bin/sleep` or `python3`**: the agents' status, conversation and discovery readers that follow a live fake (claude's pane and settings, codex, copilot, cursor, gemini, grok, opencode), the usage and context probes, `gh` and `glab` (pull requests, pipelines, stacks, merged counts, issues), the openers' fakes, the update's replacement of the binary, process trees, owners, memory and sampling, ports' attribution and stopping (a `python3` listener and SIGTERM), `remote` (a fake `ssh`), `project::hierarchy`'s and `project::view`'s tabs and the `term` tests on `/bin/sh`. Their fakes move to `test_util::fake_program` (Test helpers) when their step ports them.
  - **Unix semantics**: file modes and `Locked`, symbolic links, FIFOs and devices (`/dev/zero`), signals, descriptors.
  - **Rules that were still Unix's** (found here), all fixed after #601, with their tests running on Windows: a path given with `--remote` was judged by this system's `is_absolute`, so from Windows `/srv/x` was refused as relative (see Remote windows, Paths, #603), a plugin from a folder was recognised by a leading `/` only (see Plugins, Installing), the picker walked a typed path by `/` only (see Folder picker), and a path link with a drive and backslashes was not found in a pane's text (see Files panel, Paths in panes).
  Tests of platform-neutral logic that failed only on a Unix path literal or a `/` separator now run everywhere (`test_util::os_path`, paths built with `Path::join`, `test_util::verbatim` where a verbatim path is meant: `TempDir` is plain on Windows). The Windows tests that compare against a live process wait for it with `test_util::wait_until`, so the suite runs in parallel as on Unix. Three problems showed up only once the whole suite ran, in about one run in three, and are fixed in the tests (since then it passed eight runs in a row, two of them side by side on one machine): `FakeHttp` logged a request after answering it (Test helpers); `discord_forum::setup::done_closes_the_dialog_…` waited for a step label the dialog shows before any read, so it could count the requests before the first one, and now waits for the read itself, as its neighbours do; and the Ctrl+C test of `term::tests::on_windows::foreground` never had its Ctrl+C taken. A process passes on to the processes it starts whether Ctrl+C is ignored, so a test run started from something that ignores it (here an agent's shell) passed that on to every pane's `cmd` and its `ping`; the test passed only because its `ping -n 30` ended by itself after 29.4 s, inside the test's 30 s wait, and failed when the machine was loaded. The server clears the flag when it starts (`on_stop_signal`, `SetConsoleCtrlHandler(NULL, FALSE)`), so its panes take Ctrl+C; the ConPTY tests now clear it the same way before they start a pane (`ctrl_c_reaches_the_panes`), and that test waits 10 s, well before the ping would end, so it fails without the clearing. Even then, on a loaded machine, a Ctrl+C written as soon as `ping` showed in the pane's tree was once not taken (ping went on; why was not found), so the test writes it again every half second until `cmd` is back.
- **CI** (#587, #588, #601): a `clippy + tests (windows-2025)` job runs `cargo clippy --all-targets --all-features --locked -- -D warnings`, then `cargo test --locked`, with the same toolchain, Zig and cache as the other jobs, so a change that breaks the Windows build, or a test that runs there, shows a failing check on its pull request. It is not yet among the checks `main`'s ruleset requires, so it does not block a merge on its own. A few lints differ on Windows and are silenced there only: `large_enum_variant` on the server's `Step` (paths are larger on Windows), `dead_code` on `Supervisor::steps` and on `app::tests::flows_dialog`'s `Setup::project` (only the tests that open a project read it) in Windows test builds (and on the painter's `Fail::Timeout` until its wait was ported), and `trivially_copy_pass_by_ref` and `unused_self` on the console's `BorrowedFd` stub. The window's `Signal` event lost its `dead_code` silence once the console's Ctrl events sent it (#593); the other way round, `unnecessary_wraps` is silenced on Unix's `console::enter_raw` and the token prompt's `Hidden::on`, which keep the Windows `Result` and `Option`.
  - **The repository's line endings**: `.gitattributes` keeps every text file LF on any checkout (`* text=auto eol=lf`). The runner checks out with `core.autocrlf=true`, Git for Windows' default, which turned the fixtures and the site copy that tests compare byte for byte into CRLF, and 39 tests failed only on that; a contributor on Windows with the same default gets LF too.
- **Long paths** (checked 2026-11-02): Ghostty's sources, cloned inside `target/`, hold files (its fuzz corpus) deep enough to pass Windows' `MAX_PATH` on the runner, and git cannot check them out without `core.longpaths`, so the job sets it before anything clones. A short `CARGO_TARGET_DIR` was not needed: what the linker writes stays well under the limit under the runner's checkout, and the default `target/` keeps `Swatinem/rust-cache` working without a mapping. A `target/` folder nested deep in the file system does hit it: the linker fails with `LNK1104`.
