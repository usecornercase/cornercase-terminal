# Windows › Git's paths and canonical folders

Part of [Windows](../windows.md).

- **Git's paths** (#590): git prints a path as bytes (`worktree list --porcelain`, `rev-parse`, `ls-files -z`, the `gitdir` and `commondir` files it writes), and the changes panel, the merge check, the worktrees and the worktrees dialog turn them into paths and back. One set of helpers in `os/ffi.rs` does it, a leaf because `git`, `changes` and `worktrees` all use it and its Unix side needs `std::os::unix::ffi`: `to_path` (git's bytes to a path), `to_bytes` and `text` (a path to git's bytes or text), `to_os` (bytes to an argument or a variable), `join` (a path git wrote, onto a folder), `plain` (a path handed to git), `same` (comparing a path from git with one from std) and `LIST_SEPARATOR`. They replaced the stubbed `OsStrExt` and `OsStringExt`. On Unix they are what the code did before: the raw bytes both ways, so names that are not UTF-8 still work, `plain` is the path itself and `same` is `==`. On Windows git writes UTF-8 with forward slashes (`C:/Users/me/repo`): `to_path` decodes it and turns `/` into `\`, `to_bytes` encodes UTF-8 with `/`.
  - **Bytes that are not UTF-8** are decoded lossily (`U+FFFD`), not skipped: Git for Windows prints only UTF-8, since it converts the system's UTF-16 names, so such bytes can only come from a tree committed elsewhere whose name no Windows file has. A lossy name keeps the entry in the list, like every name the changes panel already shows on any system, and the file system call on it fails as for a file that went away. The empty path the stub gave was worse: an empty `rev-parse --absolute-git-dir` would have read `locked` in the current folder.
  - **The `\\?\` prefix**: on Windows `canonicalize` gives a verbatim path (`\\?\C:\Users\me\repo`), and cornercase canonicalises project folders. Git cannot take one: `git worktree add` fails with `could not create leading directories of '//?/C:/…'` and `git clone` reads it as an ssh host (Git for Windows 2.39.2, checked 2026-11-02); and inside a verbatim path `/` is no separator, so a relative path from git joined onto one names no file. So every path handed to git goes through `plain`, which drops the prefix (`-C`, `worktree add`, `remove` and `unlock`, `--exclude-from`, `--pathspec-from-file`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, the alternates, a plugin folder's `clone`), and every path git wrote goes onto its folder through `join`, which makes the separators native and drops the prefix too (std's `push` resolves the `..` of `commondir` on a verbatim folder). Nothing is lost: std adds the prefix back itself for a path over `MAX_PATH`. The folders cornercase stores no longer have the prefix (see Canonical folders below), so `plain` and `join` now mostly see plain paths; they stay, since a folder that keeps its prefix, or one a user typed with it, still reaches git.
  - **Comparing**: `Path`'s `==` and `Hash` already treat `/` and `\` alike on Windows, so the worktree discovery's sets of canonical paths match git's paths as they are. `same` also ignores the `\\?\` prefix and the drive letter's case (`c:` and `C:`), and is what the prune check uses before it canonicalises. A folder's own case still counts: both sides come from `canonicalize` or from git given the canonical folder, so they agree.
  - **The alternates** are a list split on git's `PATH_SEP`, `;` on Windows and `:` on Unix, so `LIST_SEPARATOR` is what makes the merge check quote a path.
  - **Line endings** (checked 2026-11-02): with `core.autocrlf=true`, Git for Windows' default, `git diff` compares a file's cleaned (LF) content, so a file checked out with CRLF and left alone is not listed and an edited one shows only its edit. The panel splits a patch and an untracked file with `str::lines`, which drops the `\r` of a CRLF line, and its digests hash git's output, which does not change between two reads. Nothing needed fixing; tests keep it so.
  - **Tests**: `TempDir` is canonical without the prefix on Windows (`os::fs::canonicalize`, what the app stores); the Windows tests hand `\\?\` folders, names out of ASCII and paths with forward slashes to the changes panel's loader, the merge check, the worktree list and scan, and `worktree::create`, `lock` and `remove`. The tests of `changes`, `git` and `worktrees` that need only git run on Windows, the merge check's and the worktrees' included (all passed locally on 2026-11-02, with Git for Windows 2.39.2); those that need a symbolic link, `/bin/sh`, a process, a name with `*` or a file's blocks stay `#[cfg(unix)]`.
- **Canonical folders** (#613, `os::fs::canonicalize` and `canonical`, the rule in `os/fs/windows/verbatim.rs`): std's `canonicalize` gives a verbatim path on Windows, which cornercase showed, wrote to `session.json` and handed to shells, agents and git, and many programs refuse or misread one (git, above). So the app canonicalises through `os::fs::canonicalize` (`canonical` falls back to the path as given, as the code did with `unwrap_or`), which is std's on Unix and on Windows drops the `\\?\` of a drive path (`\\?\C:\…`) when Win32 reads the plain one the same way. The rules are based on the `dunce` crate's (1.0.5) and keep the prefix in more cases, never fewer: on a share (`\\?\UNC\…`) or a volume (`\\?\Volume{…}\…`); on a drive without its root (`\\?\C:`, which plain is that drive's current folder; not in `dunce`); on a path over 260 UTF-16 units with its prefix, `dunce`'s limit, which leaves a margin under `MAX_PATH` (std adds the prefix back itself for a long path); and on a name Win32 would read otherwise: `.` or `..`, a trailing dot or space (Win32 strips them), a device name with or without an extension, cut at its first dot (`CON`, `PRN`, `AUX`, `NUL`, `COM1`-`COM9`, `LPT1`-`LPT9`, and beyond `dunce` `CONIN$`, `CONOUT$`, `COM0`, `LPT0` and the `¹²³` ones, any case), a character of `<>:"/\|?*` or below a space (in a verbatim name `/` is no separator and `:` names a stream), over 255 units, or not Unicode. Keeping the prefix is the safe side, since it is what std gave. Windows 11 (10.0.26200) reads `aux.rs` or `con.h` in a plain path as a file (checked 2026-11-03), older Windows as the device, so a name like that keeps its prefix. Written by hand rather than taking `dunce`: the rules fit in one small file, and the crate would be a dependency for one call.
  - **Where**: every folder the app stores, shows or hands to a program: projects (the picker, the `open` request, the server's own folder through `open_here`), workspaces and worktrees (`git::registered_worktrees`, a new worktree, a flow's run and role worktrees, `worktree-remove`'s target, the worktree discovery and dialog), session restore, config keys matched to a project (`names_folder`, the `config` request, sharing settings), accounts' folders (given to agents as `CLAUDE_CONFIG_DIR` and the like, so Claude Code's keychain key comes from the plain path), a linked plugin's folder and an install spec, the binary the updater replaces, and the ports' worktree folders, matched against a process's folder, which Windows gives plain.
  - **Left on std's**: checks that canonicalise both sides themselves and keep nothing, so both sides always agree: the agents' discovery (a process's folder and home against the folders agents record), an account shell's custom home and `accounts::named`, the prune check (`worktrees::remove`, beside `ffi::same`), and the containment checks of a build folder (`builds::deletable`), of a plugin's program (`manifest::resolve`) and of a path link's file in its workspace (`files::link::resolve`, which then passes only the file through `simplified`, for what it shows and reports), where a plain root and a child that keeps its prefix (a long path, or a name like `aux.rs`) would otherwise come in two forms and the child read as outside; also `host::open`'s Zed check, the highlight worker's binary and the junction's drive check.
  - **Sessions**: `state::load` passes every path it reads through `os::fs::simplified` (projects, workspaces, pane folders, a closed tab's panes, role worktrees), so a session saved with verbatim paths opens with plain ones and nothing migrates by hand; restoring canonicalises the project and workspace folders again.
  - **Tests**: the rule on Windows (`os/fs/windows/verbatim/tests.rs`), `canonicalize` and `canonical` on both systems (`os/fs/tests.rs`), a path link to `src\aux.rs` that stays inside its workspace (`files/link/tests.rs`), a project opened by its verbatim folder through `open_project` (the picker's and the server's call) and through the `open` request is stored plain (two app tests that start `cmd.exe` through `new_app_with_shell`), and a session file with verbatim paths loads plain ones (`state/tests.rs`); all passed on Windows 11 on 2026-11-03. The app tests' own `canonicalize()` calls give the same paths on Unix; once they run on Windows (they open `/bin/sh` panes, so they are still Unix-only, see Tests on Windows) they compare through `os::fs::canonicalize`, as `app::tests::canonical` already does.
