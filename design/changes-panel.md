# Changes panel

Code: `changes/`, `ui/changes.rs`, `app/changes_panel.rs`

- Git workspaces only: ` Changes n ` next to ` Issues ` (` ± ` in the compact bar) opens a fourth column right of the pane (full screen in compact mode). Its border drags; its width is `Widths::changes` (`None` = half the free space, at most `DEFAULT_WIDTH`).
- Tabs: uncommitted (`git diff HEAD` + untracked), commits (`git diff <merge-base> HEAD`), all (`git diff <merge-base>` + untracked). The base is `Workspace::base` (saved per workspace) or the default branch: `origin/HEAD`, else `main`/`master`. Comparing from the merge-base keeps commits made on the base later out of the diff.
- Git runs on a thread, one job at a time, every second while it or the files panel is open (`Panel::watched`, for its marks) and every 3 s while closed (for the button's count). Flags matter: `--no-optional-locks` and `-c diff.autoRefreshIndex=false`, because a plain `git diff` rewrites `.git/index` (takes `index.lock`) even with `--no-optional-locks` and would fight an agent's `git commit`. `--relative` keeps paths inside the workspace folder. Untracked files are read directly (never `git add -N`), capped at 1 MiB, NUL in the first 8000 bytes means binary; a symlink shows its target path, like git, never the file it points to. The branch list and "unchanged lines" also run on threads and answer with `AppEvent::Changes(ChangesEvent::Branches { … })` / `AppEvent::Changes(ChangesEvent::Gap { … })`.
- The job hashes git's output; an unchanged hash answers without a diff, and files whose patch section did not change are reused, so highlighting runs only for what changed. Highlighting is the files panel's tree-sitter engine (`highlight/syntax.rs`): each hunk side and each unchanged-line gap is one fragment, tabs expanded, and a side over 50,000 bytes stays plain. A paint is killed when its budget runs out. Only a block given the full 5 seconds stays plain until its text changes; one skipped because the job's 30 seconds were already gone is tried on the next refresh. The worker is this binary, from the path read at startup, with a Linux ` (deleted)` suffix removed after an in-place update (`fs::rename` over the running file). Its protocol is a language name and the source in, and the coloured lines out, and a later release keeps that: the server may still be the old one when it starts the binary that just replaced it.
- Rendering: lines paired delta-style (word tokens, changed share ≤ 60 %) get word emphasis; each hunk side (context + removed, context + added) is highlighted separately. Tints blend the host background with palette red/green when the client has `COLORTERM=truecolor` and the background is known; otherwise palette colours, and on dark themes only the `▎` bar, coloured numbers and word emphasis (palette greens and reds are too loud as line backgrounds).
- **Filter** (`changes/filter.rs`, pure): ` ⌕ ` left of the panel's `×` opens a field under the tabs (the header grows a row, so the summary and the base selector stay) that filters files by path only; searching the lines was tried and dropped as not useful. While it is focused (`Filter::focused`, and only while the panel shows and no overlay is open) keys and pastes go to it, like the global search: `Enter` keeps the filter and unfocuses, `Esc` or its `×` closes and clears. Any press outside the panel gives the keys back and keeps the query; a click on the field or ` ⌕ ` takes them again; closing the panel unfocuses it. Each word is an include, or an exclude with `!`; a file stays if it matches any include (or there is none) and no exclude, by its path or its old path. A word without `*`/`?` is a substring of the path; with them a `.gitignore`-like glob (no `/`: any path component, a trailing `/` only folders; with `/` or a leading `/`: the whole path, also everything under it; `*` and `?` stop at `/`, `**` crosses it). Smart case per word. Folds are untouched; typing resets the scroll. Shared by clients, never saved; switching tab or workspace keeps it. `Esc` on an empty field closes the panel (see TODO panel).
- Hunk actions on hover: open (new tab running `/bin/sh -c 'exec ${VISUAL:-${EDITOR:-vi}} "+$1" "$2"'`), ask agent (pastes `path:lines ` into the workspace's agent pane, found with `agents::detect`; without one it copies the reference), copy (the hunk as a patch, OSC 52). Viewed marks use a separate review identity, so they clear when the file changes while patch reuse and unchanged-line gaps follow its patch digest.
- **Scope** (#159): a row above the modes uses the dialogs' `tab_style`. The first tab is the active project's name, with ` › workspace` only when it has several workspaces, as in the agents section; `truncate_right` reserves the entire ` Every project ` tab and the filter/close buttons even at the minimum width. Project is the default and keeps its selected mode and base when another scope is chosen. Every project shows only uncommitted changes, with a muted `uncommitted` in place of the modes and no base selector: one base cannot describe unrelated repositories. Scope is shared and saved as an optional, defaulted field beside mode; session version remains 5.
- **Targets and grouping live in `changes/every.rs`** (#195): `targets` and `group` take the projects, the `sidebar_order` and the panel, and use neither `app` nor `ui`; `Body` moved into `changes` and `Header` into `every.rs`, where the app and `ui/changes.rs` import them. `App::every_targets` and `every_body` pass `sidebar_order`; `panel_view` keeps the folds, viewed marks, gaps and filter.
- **Grouping**: Every project follows `project::sidebar_order` with groups treated as open, then workspace order, so rows do not move according to how recently an agent saved. Only open git workspaces with changed files are listed; clean projects, plain folders and workspaces being closed or removed disappear. Each view resolves its scan targets once and shares them between grouping, the loading state and the live indicator, avoiding repeated reads of every checkout's HEAD during drawing and mouse handling. A project header carries its total files and line counts. Workspace headers appear only when several of that project's workspaces have changes, and use the workspace's label/branch. Clicking either header hides or reveals its file rows without switching focus or changing each file's fold. Project arrows sit one cell in, workspace arrows three and file arrows four, so files always read as children of their headers; project scope keeps its existing indentation. Scope tab drawing and clicks reserve the label's full cell width, including its trailing space, in the app and simulation. Headers whose files all fail the path filter are hidden; their totals still describe the complete group, like the panel's line totals. Until the first scan finishes an empty list says `reading changes…`; a completed empty view says `no changes in any project`. An open Every project view stays visible when the user switches to a plain folder or closes the last project; its entry buttons remain git-only.
- **Lazy patches**: Every project has separate file folds, initially folded, so opening it never inherits an expensive unfolded project view. Viewed marks and unchanged-line gaps remain keyed by workspace and path. A viewed file that changes loses its mark and opens again, as in project scope, so its new work becomes reviewable. The worker asks for porcelain v2 status and NUL-separated numstat, preserving renamed paths, binary files and workspace-relative paths. Untracked text uses the same byte, line and binary caps, without constructing hunks for the folded list. Patch parsing, tracked summaries and untracked reading share one fold classifier: binary first, then more than 3000 added and removed lines, then lockfiles, then ordinary text. The summary marks oversized tracked files as Large from numstat, before any unfold request, so they keep their counts-only state and never alternate between loading a large patch and discarding its hunks. Only unfolded files that can show lines and are visible under their headers and path filter get a patch and highlighting; their patches refresh on each visit. Folded headers therefore stop patch reads too. `collapse all` / `expand all` act across the collection; expanding all also reveals its headers. File actions carry their own workspace id and folder. Open and ask agent reveal the owning project, workspace and destination tab through the same navigation used by search and the agents list, unfolding the tree and closing the compact menu while keeping Every project open, so the user can immediately work in the editor or type a question after the reference. Copy keeps focus; ask agent without an agent keeps its clipboard fallback. An unfolded rename's patch request includes both its old and new paths: selecting only the destination prevents git from pairing the rename and incorrectly turns it into an added file.
- **Pacing and caches**: one shared worker slot serves both scopes, with a separate summary model per workspace so overview results cannot replace the project-mode diff used by the Files panel's git marks. Completion starts the next workspace immediately; each workspace waits at least three seconds between scans, and an unfold invalidates its wait. The slot stays taken until that job answers, including across scope switches and past 30 seconds, so a slow job is never joined by a second copy. Git commands for the job run in their own process group and are killed when the job's 30 seconds run out (`process::output_within`); highlighting uses the one worker process above, killed on its own budget. A timed-out job keeps the diff already shown and then frees the slot. A timeout with nothing shown yet is stored, so the one-second or three-second wait still applies and the next tick does not start another git immediately. An answer whose generation no longer holds the slot does not clear a newer job. Closing Every project stops the sweep and resumes the existing active-workspace job.
- **Counts while closed**: while Changes is closed and no client follows that workspace's diff, the refresh is a counts load (status, line counts, staged marks) instead of full patches. Highlighting and hunks are built only for the file open in the Files panel, so the button's count and the tree's git marks do not parse the whole diff. Opening Changes, or a client asking for the diff, still loads the full patches. Commits and All use the same counts shape against their comparison, with a patch only for that open file. The Changes button still counts only the active workspace (uncommitted while Every project is visible), never the collection. Summary jobs use the same index-lock-avoiding flags and `log::Job` timings, labelled `summary`, with a workspace id; failed workspaces are omitted from the grouped files and follow the existing debug job logging policy. If the collection would otherwise be empty, its first scan error is shown instead of claiming every project is clean. A workspace fold only stops patch reads while its sub-header exists, so the fold cannot conceal the sole changed workspace after the others become clean. Closing a workspace or project, starting worktree removal, and discovering an externally removed worktree forget their models, request pacing, file folds, viewed marks, gaps and header folds. Late results for forgotten workspaces are ignored, keeping a long-running server from retaining removed checkouts' parsed diffs. Workspace-relative status prefixes are derived from the nearest checkout's .git entry, including linked worktrees, avoiding an extra rev-parse process on every scan.
- **Digests**: the summary hashes status, numstat, untracked bytes/metadata, HEAD, open paths and their patch bytes before constructing its diff; an unchanged digest skips numstat parsing and highlighting. For uncommitted files, review identity combines HEAD, path, status, counts and the checkout file's size, modification time and change time, shared by both loaders. Metadata catches edits with the same line counts without reading folded tracked files; change time also catches replacements or restored modification times. Every materialized file retains its patch-section hash for reuse and gap caching, separate from its metadata-based viewed identity. A write between git reading a patch and the metadata stat can give old and new patches the same review identity; their distinct patch hashes still replace the old highlighted hunks and discard stale gaps. Folded summaries use the metadata fingerprint until a patch is materialized. The full project loader still hashes patch output and reuses unchanged highlighted files. A scope switch preserves review marks for the same uncommitted file. Commits and All retain their patch digests: a committed comparison can change without touching the checkout file, so metadata cannot identify its patch.
- **Models per (workspace, mode)** (#339): `Panel::models` held one model per workspace, the one of the panel's mode, so two readers of one workspace in two modes would have replaced each other's result every second. It is now keyed by `(workspace, mode)`, with `model_in(workspace, mode, base)`, `label_in` and `request_in(target, mode, every, now)` beside the old `model`, `label` and `request`, which are those at `Panel::mode`, so every call of the window keeps its meaning. Memory stays where it was for window-only use: `loaded` prunes a workspace's models to the window's mode, the one just read and the ones some stream follows (`Panel::follow`, which also drops the `requested` entry of a pair no stream wants, so a late answer for it is ignored). One worker slot still serves everything: the window's own request first, then the followed pairs, least recently asked first (`request_followed`, so a slow worker never starves the last pair), then, only when a stream wants Every project and the window does not show it, a counts-only sweep (`request_sweep(.., expand: false)`, which asks for no patches and does not read the window's folds or filter, since `folded()` with the Project scope would expand every file). No stream means no request beyond today's.
- **Demo regression coverage**: website checks run the simulation on its virtual clock in wide and compact layouts, exercising the full scope-tab label, header indentation, action focus and the hero tour. The existing esbuild version is a direct development dependency for bundling those tests with the same image imports as the demo, keeping the checks independent of a browser and wall-clock timers.
- **Discard (#421)**: hovering a file row shows `↺` left of the stage slot (and so of `✓`) in Uncommitted and Every project (`view.mode == Uncommitted`, which Every sets); Commits and All have no slot, no glyph and no hit, because their changes are already in commits. The 3-cell slots (discard's and stage's) are reserved whenever discard applies, like `✓`'s, so the tags never jump on hover, and they sit six cells further left for good. `↺` has East Asian width N (narrow, not an emoji); the site's JetBrains Mono subsets lack it, so `site/src/lib/term/glyphs.ts` draws it as a shape. A `Confirm` with `dangerous` (red submit) names the file; the texts differ for modified or deleted, added (it is deleted), untracked (`Delete …`) and renamed (old name comes back), and live in `changes/discard.rs`, shared with the CLI.
  - **The job** runs on a thread, logged at info like worktree removal, since it is deliberate and destructive. It resolves HEAD first (`git::head`: the sha, or the empty tree on an unborn branch), then looks the file up among git's own listing (summary loader, no patch, so no highlighting is paid for a file about to go) and compares its review digest with the one the person saw: not listed is `Gone`, a different digest is `Changed`, and nothing is touched in either case. Only `file.path` and `file.old_path` from git's listing reach git or the disk, never the request's path (a `../` path would restore a file outside the workspace). HEAD comes first so that if it moves between the two, the lookup's digest (which hashes HEAD) differs and the discard is refused, and if it moves after, `restore` still uses the commit that was compared.
  - **How**: an untracked file (a symlink included: only the link goes) is unlinked, and folders it leaves empty stay; everything else is `git --literal-pathspecs restore --source=<sha> --staged --worktree -- <path> [<old path>]`. `--literal-pathspecs` because `star*.txt` would otherwise restore `starA.txt` too; `--source` with a sha because `HEAD` does not resolve on an unborn branch; both paths of a rename because one alone makes git see an added file. A file added in a new folder takes the folder with it, as `restore` does. Submodules: `restore` does not recurse, so a submodule's row stays, on purpose: it never touches another repository.
  - **Limits**: the digest is the review identity, which is metadata (size, mtime, ctime), so a same-size write inside a coarse filesystem's timestamp resolution could be missed; the check and the git command are a few milliseconds apart and git has no compare-and-restore. `restore` takes `index.lock` even with `--worktree` alone; its message goes in the toast and nothing retries. Afterwards the file's viewed mark, folds and gaps are forgotten and the workspace's request pacing is dropped (`Panel::discarded`), so the next refresh rescans at once and the row goes when that answers; nobody edits the model by hand. A load that started before the discard would read the old state and could bring the row back, and the busy slot would delay the rescan, so `Panel::discarded` also records the generation counter as a floor for that workspace (older completions are ignored, cleared on `forget`) and frees the slot, and the app calls `refresh_changes` right after.
  - **Rejected**: an undo (the two mistakes it would catch are covered by the confirmation naming the file and by the digest check; a faithful one needs the index entry and the worktree file for both paths of a rename, somewhere to keep the content (loose objects outlive the toast until `git gc`, a copy grows with every discard) and its own changed-since check, and the socket would need a `changes-restore` with a token; if it is asked for later, keep the content under a ref such as `refs/cornercase/discarded/…`), and a busy note in the dialog. **Left for later**: discarding one hunk, and a whole workspace from its Every project header.
- **Staging (#426)**: between `↺` and `✓` a third 3-cell slot (`+`) stages the file in Uncommitted and Every project; Commits and All have no slot, glyph or hit. Without a mark the button would give no feedback, since the panel diffs HEAD against the worktree and a staged file looks the same, so the two came together.
  - **The slot** shows the index state in git's colours and how much of it in the shape: nothing staged is blank at rest, a dim `+` on a hovered row and a green `+` under the pointer; partly staged is a green `◐` (a green `+` under the pointer: stage the rest); fully staged is a green `●` (a yellow `−` under the pointer: unstage). That is lazygit's and Zed's toggle rule: stage while anything is unstaged, unstage once everything is. `●` is the persistent mark, at the right edge with `✓`. No confirmation and no success toast, since it is reversible and the mark is the feedback; toasts appear only for "changed meanwhile", "no changes any more" and git's errors.
  - **The scan** reads the index state from `git status --porcelain=v2 -z --untracked-files=all` (X and Y of each record; a rename's pair counts under its new path, and a rename git sees as two files, an added and a deleted one, comes out partly staged), parsed by `changes/porcelain.rs`. The summary loader already ran that command. The full loader runs it instead of `ls-files --others` in Uncommitted, so the number of git processes is the same; All keeps `ls-files` and Commits needs none, so `File::staged` is `None` there and the wire leaves the field out. The cost was measured in a worktree with a stale index and 1.6k files (2026-10): `ls-files --others` 12 ms, `status` 83 ms, `diff HEAD` 80 ms; that is the price of a correct X and Y. `--no-optional-locks` still holds, and the scan reads fine while `index.lock` is held. The full loader hashes the raw status bytes into its digest, because `git add` leaves `git diff HEAD` and the untracked list as they were, and `reuse` keeps an old file only when its `staged` is equal too (the hunks are reused, the mark replaced); the summary loader's `opened` carries the mark over to the file it unfolds.
  - **Review identity** must not change when a file is staged, or `✓` would drop and the row reopen. Staging leaves the worktree alone, so size, mtime and ctime stay; but an untracked file becomes `Added` once staged, and the fingerprint hashed the status, so `git::fingerprint` hashes `Untracked` as `Added`. The counts already agree (lines of text against numstat). The counts are left out of the identity of an `Added` (so of an untracked) file, since its size and times already tell when it changes; otherwise a binary or over-1 MiB untracked file, whose count is 0 until staged, would lose its mark when staged.
  - **The job** is `changes/act.rs`, shared with discard: HEAD first, then git's own listing, then the digest check (`Gone`, `Changed` or run), so only `file.path` and `file.old_path` from git reach git. Stage is `git update-index --add --remove -- <path> [<old path>]` and not `git add`: the `git add -- <path> <old>` of the first idea fails with `pathspec did not match` whenever a rename is already in the index (`R.`, `RM`), also with `-A`, `-u` and `--ignore-errors`, and `update-index` takes literal paths (no pathspec magic, so `star*.txt` is safe) and removes what is gone. Unstage is `git --literal-pathspecs restore --source=<sha> --staged -- <path> [<old path>]`, discard's command without `--worktree`; the sha is HEAD, or the empty tree on an unborn branch. Both were checked on git 2.53 for modified, deleted, untracked, in a new folder, intent-to-add, symlink, submodule, renamed (also edited) and a subfolder workspace, and a clean filter is applied. The job is logged at info, like discard, and `index.lock` held by another git shows its message in the toast; nothing retries. Afterwards `Panel::rescan` drops the pacing and records the generation floor, as discard does through `Panel::discarded`, but keeps the viewed mark, folds and gaps, since the file is still there.
  - **Staged is deliberately not in the digest**: the review digest answers whether the file's content changed, and staging does not change it; `staged` is read alongside it, so an index change made elsewhere still updates the mark (the status bytes are in the full loader's digest) but cannot make a stale click refuse, which is harmless because staging is idempotent and unstaging resets to HEAD. A file with a merge conflict is refused (`ls-files --unmerged`, "resolve the conflict first"), since `update-index` would mark it resolved with its markers still in it.
  - **Limits**: a change that is only in the index (staged, then the file put back to HEAD by hand) is not listed, since the panel diffs HEAD against the worktree; a submodule with dirty content stays `◐`, because that content is the submodule's to commit; the check and the git command are a few milliseconds apart, as for discard.
  - **Rejected or left for later**: a confirmation, a success toast, staging one hunk (`git apply --cached`), staging a whole workspace from its Every project header, a count of staged files in the footer, and showing the staged and unstaged diffs apart.
- **Lines (#428)**: a press on a line row (added, removed, context, or an unchanged line a gap shows) selects it and dragging selects a range, as in the files viewer (see Files panel › Lines for the agent); file rows, hunk headers' buttons and gap rows keep their actions, so only line rows start one, and a left press in the body on nothing (a hunk header outside its buttons, a spacer, the blank under the rows) clears it, which is the only way back to the fold button while lines are selected (an `Esc` step would be a new key meaning). The drag is the viewer's `Drag::Lines`, whose `anchor` says whose lines they are (`Anchor::File { line, text }`, `Anchor::Diff { spot, text }`), so the end of the drag on any other event, the wheel during it, the scrolling at the body's edges every `LINES_SCROLL_EVERY` and `App::tick`'s wake-up are one piece of code with two targets.
  - **One file**: the selection stays in the file where the press started, across its hunks; the row under the pointer counts as the last line of that file at or above it, else the file's first line (`ui::changes::line_near`), so other files' rows give its first or last line and a hunk header or gap row the line above. Two files have no `path:a-b`, and copying both had no use.
  - **Kept by what it selected, not by row**: `changes::Panel` holds the workspace, the path, the file's patch digest (`File::digest`) and two spots (hunk, then line or unchanged line, ordered as drawn). Rows move as files fold, gaps open and the panel rescans every second, so a row index would drift; one digest means one set of hunks, so a spot names the same line for as long as it resolves and a file that changed never shows a selection made on its old patch. `App::panel_view` resolves it (`View::selection`) only while both ends are among the panel's rows; while it does not (the patch changed, the filter, a folded header, another mode, scope or workspace, the panel closed) it is hidden, with the normal footer, and shows again with its lines, as the viewer keeps its selection per workspace. A change to its file's own fold or viewed mark (its row, `✓`, collapse or expand all, discard) drops it, in `Panel::toggle_fold`, `set_fold` and `set_viewed`, as do `Panel::forget` and `reset_interaction` (a draw that panics on it cannot repeat). Rejected: dropping it in every place that hides lines (each would need to know about it), and keying it by row. It is never saved with the session.
  - **Characters (#440)**: the cells left of the code (both numbers, the `▎` bar and the blank after it, `ui::changes::selection::code_x`) select whole lines as before; the code selects characters, with the files viewer's rules (see Files panel › Lines for the agent: a click without moving is still a line, the stream is cell inclusive, what a cell stands for, the reversed look). Here a row that is not a line of the selection's file stands for the end of that file's last line at or above it, else the start of its first (`ui::changes::stretch_near`, `line_near`'s rule), so the selection stays in one file over its added, removed and unchanged lines in the order shown. It lives in `changes::selection::Selection::stretch` (a `Stretch<Spot>`), and `range()` returns its lines, so it is hidden and shown again under exactly the line selection's rules (digest, folds, filter, mode, scope, workspace) and dropped by the same calls (`toggle_fold`, `set_fold`, `set_viewed`, `forget`, `clear_selection`, `reset_interaction`); `anchor` stays the press's spot, which `App::shows_diff_lines` compares with the drag's. The footer and ` ask agent ` use the covered lines (`changes::selection::covered`: a last line with nothing selected is left out); ` copy ` takes the characters from `Line::source()` and `GapLine::source()`, tab included. It draws no `▌` and no cyan numbers: the cells are reversed over the tint and a selected line break runs to the right edge. Nothing on the socket, as with lines.
  - **The look**: a cyan `▌` in the row's first cell and both numbers cyan and bold, the viewer's selected number (for lines; characters are reversed instead); the backgrounds stay, since here the tint says whether a line was added or removed (the viewer paints the surface colour because its lines have none). No hover cue: hovering a line already shows its hunk's actions.
  - **The footer** shows `lines a-b` (`line a`, or `removed lines a-b` with the old numbers when only removed lines are selected, shorter forms when narrow) with ` ask agent ` and ` copy ` in place of the fold button and the viewed count (`fold_all` is empty meanwhile, so it is not hit). No ` open `: at the minimum width the footer has no room for a third button.
  - **Copy** takes the selected lines (or the selected characters) as drawn, removed and added in their order, joined with `\n`, without the bar, signs or numbers: what is selected is what is seen. Unchanged lines between two hunks are copied only when a gap shows them. The text is the line's own: `Line::raw` and `GapLine::raw` keep what git printed or the file holds when `expand` changed it (a tab), since `text` has tabs as four spaces, the bug the viewer had with Makefiles (see Files panel › Copy takes the file's own text); a `\r` at the end of a line never reaches the model (the patch is read by lines), as the viewer drops it for selected lines. `git::new_side` returns the lines as read and `gap_lines` expands them. A line without a tab keeps no `raw`, so most lines cost nothing.
  - **Ask agent** pastes `path:a-b ` with the new side's numbers of the selected lines into the owning workspace's agent (so Every project reaches the owner and reveals it), like the hunk's, copying it without an agent. A selection of only removed lines has no new numbers, so it gets its hunk's reference (`Hunk::changed`: the lines that replaced them, or the line where they were removed), never old numbers: an agent reads `path:a-b` as the file as it is now, and a `(removed)` note was rejected for that reason.
  - **Nothing on the socket**: the selection is pointer state and drawing, like the viewer's; a client drawing its own panel has every line from `changes-file` and `changes-gap`. Left for later: an optional `raw` beside `text` on the wire (whose `text` stays the window's), and the hunk's ` copy ` taking `raw`, so that its patch applies to a file with tabs (`Hunk::patch` writes the expanded text).
- **File type icons (#450)**: where the window draws icons (Layout › Icons), a file row is the fold arrow, the status letter, the type's icon and the path. The icon comes from the file's current name (a rename's new one) and is muted with the row (viewed, large, binary); the name keeps its style. The path starts two cells later and is cut as before.
