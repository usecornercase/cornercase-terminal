# Worktree setup

Code: `git/worktree/setup.rs`, `project/settings.rs`, `app/worktree_setup.rs`, `app/project_settings_dialog.rs`, `ui/dialog/project_settings.rs`, #250, #485

- **Why**: a fresh worktree has no `node_modules`, no built tools, no `.env`; every issue started in one began with the agent (or the user) running the same commands by hand. A project can now say what to run when a worktree is made, and what to run before it goes.
- **Stored in `config.json`, per project folder** (`projects`: `{ "~/code/web-shop": { "setup": "…", "teardown": "…" } }`, `config::ProjectSettings`; keys match by expanding `~`, saving replaces every key naming the folder and removes it when both texts are empty). Not `session.json` (closing the project would lose it) and not a file in the repository: a cloned repository would run its own commands on the first worktree, which is why a project's flows show their `env` and `args` in red. A team shares setup by checking in a script and writing one line, `./scripts/setup.sh`.
- **Edited in a modal**, from ⋯ or right-click on a project row (**project settings**, only for a repository root, since only those have worktrees): two multi-line fields (`editor::Editor`, on ratatui-textarea; see Text fields), `Tab` between them, `Enter` a new line, **save** the button only (as the flow import page). No text box when a project is added: a question asked at the moment one only wanted a project (as with group colours). The New workspace dialog says what will run instead (`then runs the project's setup: npm ci …`, `Note::Info`). **No list of files to copy**: `.worktreeinclude` already does it and is copied before the setup runs.
- **Setup runs visibly in the new worktree's first pane, which then becomes the user's shell.** `Term::spawn` runs `/bin/sh -c WRAPPER cornercase-setup SCRIPT STATUSFILE $SHELL ROOT BRANCH`: the wrapper runs the script with `sh -ec` (the first failing command stops it; `CORNERCASE_ROOT`, `CORNERCASE_WORKTREE` and `CORNERCASE_BRANCH` set for that command only), prints `✓ setup finished` or `✗ setup failed with exit status N`, writes the status to `setup-<pane>.status` next to the socket (a private 0700 folder; `set_setup_dir` makes it absolute, a relative `CORNERCASE_SOCKET` would resolve inside the worktree) and `exec`s the user's shell. Progress bars, colours and prompts work, the output stays in the scrollback, `Ctrl+C` stops only the script, nothing is typed into the user's shell and no "keep the pane after its program exits" machinery is needed. Rejected: typing the script into the shell (depends on its syntax and prompt timing), a separate setup tab, an OSC sequence or the title as the signal, and a background job (no output, no prompts). It runs under `/bin/sh` rather than the user's shell so it behaves the same everywhere; call your own shell for its functions (`zsh -lic 'nvm use && npm ci'`). No timeout: it is visible and cancellable.
- **The pane's state** is `Term::setup` (`setup::Pane`): `Running { status, since }` while the wrapper runs (the pane stays a command pane: `▸`, not at its prompt, listed by restart as running), then `Failed { code, unseen }`. `App::watch_setups` (every refresh) reads the status file, **the only signal that a setup ended**: guessing from the wrapper's process arguments was tried and dropped, since a forked child shows its parent's arguments until it `exec`s and the write races the `exec`. A wrapper killed without writing one ends with its pane, which the next watch sees as a vanished pane (`App::setups` remembers each running setup's workspace and file): its status file is removed, the workspace's launches are dropped like on a failure and a flow's run ends. Status files are also swept at server start. A `Failed` mark is cleared when the workspace starts another setup or one succeeds, so a later unrelated failure is never blamed on it. When the setup ends the pane becomes a shell (`became_shell`).
- **Agents wait.** Every launch in a workspace with a running setup is held (`held_launch_panes`, skipped by `drive_launches` and not counted by `tick_at`, so a long `npm ci` does not redraw every client ten times a second). On success the launches restart their quiet clock (`Launch::wait_from`), so the command is typed once the shell's prompt settles; on failure they are dropped, requests waiting on them answer `the setup of workspace W failed with exit status N, so its agent did not start; cornercase read --pane P shows its output`, a flow's run ends, and a toast and (for a hidden tab) a desktop notification say `setup failed in project › workspace`. The failed tab shows a red `!` (`Tab::status` rolls it up like an agent's) until it is shown, in the window or a view. This covers the issues dialog, `start --worktree`, the queue, Telegram and Discord `/new` and flows, since they all go through launches. `restart --when-idle` counts held launches as typing, so a restart waits for the setup. Closing the setup tab drops every launch of the workspace, a flow's members included. `App::setups` is filled when the pane is spawned, not at the first watch, so a setup closed before the first tick is still noticed; a closed setup says so in a toast (`setup was closed in project › workspace: its agent did not start`) and the run ends with that reason in the log. A failed setup is blamed in an error answer (`setup_failure`) only until another tab or split starts in the workspace (`Failed.blame`), so a later unrelated failure is never reported as the setup's; the `!` and `status` stay.
- **Only when cornercase just made the worktree** (`worktree_created`, `open_workspace`'s `setup`, the control and flow paths after `git worktree add`), not for worktrees found outside cornercase, workspaces reused on an existing branch or restored sessions. **run setup** in a worktree workspace's menu opens a new tab running it with no agent, to retry after a fix. `new-workspace --worktree` answers once the setup is done (`Stage::Setup`; an error naming the exit status when it failed), and `status --json` gives each workspace a `setup` (`running` or `failed`), `(setting up)` / `(setup failed)` in the text.
- **Teardown runs in the removal job**, after the shells stopped and before `git worktree remove` (`/bin/sh -ec` in the worktree, empty stdin, the same variables, five minutes via `process::output_within`, which kills the process group). A failing teardown does not stop the removal: the toast says `removed X, cleanup failed in part, see server.log`, with the bug icon, and `server.log` gets the warning whole (`worktree: removed, cleanup failed in part workspace=X warning="exit status 1: <last line>"`, plus `machine=` for a machine's; `worktrees::removed`), since the toast is one line, and with the teardown's line, a role's teardown or a role's worktree left behind with its path, the part that says what to fix did not fit in 80 columns. The same words cover the teardown and a role's worktree that stays, both in the one warning. `close --remove-worktree` still prints the warning itself, `warning: …` on stderr, and exits 0 (`Done::warning`). The removal dialog says `Its teardown runs first.`
- **Logs** hold sizes, exit statuses and timings, never the script or its output; a failed teardown's one-line reason (its last output line, at most 160 characters) is in the removal's `WARN` line above, the one place that keeps it whole, since the toast only points at the log. That line stays at `WARN`, not `ERROR`: the worktree is gone and only part of the cleanup failed, a warning, and `CORNERCASE_LOG=error` is a choice not to see warnings. Output of a running teardown is not shown anywhere while the row says `removing…`: a known limit, as the removal runs in the background.
- **Rows**: a workspace running its setup shows a muted `setting up…` tag (`WorkspaceEntry::setting_up`).
- **Build folders** (#485): a project also keeps the names of the folders ` free builds ` deletes in its worktrees (see Worktrees dialog), `projects.<folder>.builds` in `config.json`, a list of folder names. Absent means the defaults (`config::DEFAULT_BUILDS`: `node_modules target .next .turbo dist build .venv __pycache__`) and an empty list means no folder of this project is a build folder; a list equal to the defaults, as a set, is stored as absent, so saving the defaults writes nothing, and a project whose only setting is a custom list keeps its key. The third field of project settings, **build folders**, is one line (`Editor::one_line_key`, names split on spaces and commas, a pasted text joined on one line): `Tab` cycles setup, teardown and it, and `Enter` there saves, since Enter submits a one-line field and the two script fields keep it as a new line; the hint says so. A name that is empty, `.`, `..`, `.git`, holds a `/` or a control character is refused with a notice and nothing is saved (`config::parse_builds`, also used by `cornercase config project --builds` and the request). Settings sharing (see Settings) does not carry it: the share format names `setup` and `teardown` per repository and a list of folder names is personal to a machine's disk habits, so an import keeps whatever list the user has.
