# Worktree setup

Code: `git/worktree/setup.rs`, `script.rs`, `project/settings.rs`, `app/worktree_setup.rs`, `app/project_settings_dialog.rs`, `ui/dialog/project_settings.rs`, `control/setup.rs`, `app/control/setup.rs`, `cli/setup.rs`, `cli/args/setup.rs`, `cli/help/setup.rs`, #250, #485, #595, #672

- **Why**: a fresh worktree has no `node_modules`, no built tools, no `.env`; every issue started in one began with the agent (or the user) running the same commands by hand. A project can now say what to run when a worktree is made, and what to run before it goes.
- **Stored in `config.json`, per project folder** (`projects`: `{ "~/code/web-shop": { "setup": "…", "teardown": "…" } }`, `config::ProjectSettings`; keys match by expanding `~`, saving replaces every key naming the folder and removes it when both texts are empty). Not `session.json` (closing the project would lose it) and not a file in the repository: a cloned repository would run its own commands on the first worktree, which is why a project's flows show their `env` and `args` in red. A team shares setup by checking in a script and writing one line, `./scripts/setup.sh`.
- **Edited in a modal**, from ⋯ or right-click on a project row (**project settings**, only for a repository root, since only those have worktrees): two multi-line fields (`editor::Editor`, on ratatui-textarea; see Text fields), `Tab` between them, `Enter` a new line, **save** the button only (as the flow import page). No text box when a project is added: a question asked at the moment one only wanted a project (as with group colours). The New workspace dialog says what will run instead (`then runs the project's setup: npm ci …`, `Note::Info`). **No list of files to copy**: `.worktreeinclude` already does it and is copied before the setup runs.
- **Setup runs visibly in the new worktree's first pane, which then becomes the user's shell.** `Term::spawn` runs `/bin/sh -c WRAPPER cornercase-setup SCRIPT STATUSFILE $SHELL ROOT BRANCH`: the wrapper runs the script with `sh -ec` (the first failing command stops it; `CORNERCASE_ROOT`, `CORNERCASE_WORKTREE` and `CORNERCASE_BRANCH` set for that command only), prints `✓ setup finished` or `✗ setup failed with exit status N`, writes the status to `setup-<pane>.status` next to the socket (a private 0700 folder; `set_setup_dir` makes it absolute, a relative `CORNERCASE_SOCKET` would resolve inside the worktree) and `exec`s the user's shell. Progress bars, colours and prompts work, the output stays in the scrollback, `Ctrl+C` stops only the script, nothing is typed into the user's shell and no "keep the pane after its program exits" machinery is needed. Rejected: typing the script into the shell (depends on its syntax and prompt timing), a separate setup tab, an OSC sequence or the title as the signal, and a background job (no output, no prompts). It runs under `/bin/sh` rather than the user's shell so it behaves the same everywhere; call your own shell for its functions (`zsh -lic 'nvm use && npm ci'`). No timeout: it is visible and cancellable.
- **The wrapper ends in the shell the `shell` setting chose** (#712): it `exec`s the program with its arguments after the fixed positionals (`shift 5` and `shift 7` for Git's sh), the same one `spawn_pane` would start (`App::chosen_shell`, the default when the program cannot be found). The PowerShell interpreter path (Windows without Git's sh) ignores it and the tab stays in the PowerShell that ran the script, whatever the setting says. A chosen program that resolves but then fails to `exec` ends the wrapper with sh's error and no shell: the fallback to the default shell is only in `spawn_pane`, not in the setup path.
- **The pane's state** is `Term::setup` (`setup::Pane`): `Running { status, since }` while the wrapper runs (the pane stays a command pane: `▸`, not at its prompt, listed by restart as running), then `Failed { code, unseen }`. `App::watch_setups` (every refresh) reads the status file, **the only signal that a setup ended**: guessing from the wrapper's process arguments was tried and dropped, since a forked child shows its parent's arguments until it `exec`s and the write races the `exec`. A wrapper killed without writing one ends with its pane, which the next watch sees as a vanished pane (`App::setups` remembers each running setup's workspace and file): its status file is removed, the workspace's launches are dropped like on a failure and a flow's run ends. Status files are also swept at server start. A `Failed` mark is cleared when the workspace starts another setup or one succeeds, so a later unrelated failure is never blamed on it. When the setup ends the pane becomes a shell (`became_shell`).
- **Agents wait.** Every launch in a workspace with a running setup is held (`held_launch_panes`, skipped by `drive_launches` and not counted by `tick_at`, so a long `npm ci` does not redraw every client ten times a second). On success the launches restart their quiet clock (`Launch::wait_from`), so the command is typed once the shell's prompt settles; on failure they are dropped, requests waiting on them answer `the setup of workspace W failed with exit status N, so its agent did not start; cornercase read --pane P shows its output`, a flow's run ends, and a toast and (for a hidden tab) a desktop notification say `setup failed in project › workspace`. The failed tab shows a red `!` (`Tab::status` rolls it up like an agent's) until it is shown, in the window or a view. This covers the issues dialog, `start --worktree`, the queue, Telegram and Discord `/new` and flows, since they all go through launches. `restart --when-idle` counts held launches as typing, so a restart waits for the setup. Closing the setup tab drops every launch of the workspace, a flow's members included. `App::setups` is filled when the pane is spawned, not at the first watch, so a setup closed before the first tick is still noticed; a closed setup says so in a toast (`setup was closed in project › workspace: its agent did not start`) and the run ends with that reason in the log. A failed setup is blamed in an error answer (`setup_failure`) only until another tab or split starts in the workspace (`Failed.blame`), so a later unrelated failure is never reported as the setup's; the `!` and `status` stay.
- **Only when cornercase just made the worktree** (`worktree_created`, `open_workspace`'s `setup`, the control and flow paths after `git worktree add`), not for worktrees found outside cornercase, workspaces reused on an existing branch or restored sessions. **run setup** in a worktree workspace's menu opens a new tab running it with no agent, to retry after a fix. `new-workspace --worktree` answers once the setup is done (`Stage::Setup`; an error naming the exit status when it failed, and another when the setup's tab closed before it ended), and `status --json` gives each workspace a `setup` (`running` or `failed`), `(setting up)` / `(setup failed)` in the text.
- **`cornercase setup`** (#672; the request `run-setup`, `app/control/setup.rs`): what **run setup** does, for a client that draws cornercase, which could show `setup failed` and offer nothing, and for a script, which could not retry. `new-tab -- SCRIPT` is not the same (no variables, no `sh -ec`, no state on the workspace, and the mark stays), and removing the worktree and making it again loses what is in it.
  - **The menu's tab**: `push_setup_tab_in`, so the wrapper, the three variables, `running` on the workspace, the failed mark gone and launches held are the same code, on Linux, macOS and Windows alike. It takes `--focus`, `--view` and `--json`, the accounts (the sender pane's, else the default) and the parent as `new-tab` does; no `--name` or `--profile`, which the menu has not either.
  - **The menu's predicate**: `App::setup_refusal` says why a workspace cannot run its setup. The menu's item (`setup_action`), its click (`run_setup`) and the request all ask it, so they cannot drift. Not a worktree, no setup and a setup already running (naming its pane) answer `conflict`; an id that is no workspace `not-found`, and a workspace being removed or closing `failed`, as every request that takes one (`usable_workspace`).
  - **The default** is where it runs, else what the view or the window shows, as for `new-tab`, except that a project with no workspace gets none made (`ensure_workspace`): the new plain workspace could only be refused, and would stay.
  - **Answered when the setup is done**, by the entry `new-workspace --worktree` waits with (`Waits`, `Stage::Setup`), with no timeout, since a setup has none: the new tab's ids and a focused view's `projection`, or `failed` with the words below. A client that wants to watch it meanwhile has `--focus`, `setup` in `status` and `watch`, and the tab's `opened` event.
  - **Its words name no agent**: `Stage::Setup` serves two requests that start none, so `the setup of workspace W failed with exit status N; cornercase read --pane P shows its output`. `so its agent did not start` stays for what a launch answers (`setup_failure`). The reply reads the failed mark whether or not it is still `blame`d, since that is for later failures and the mark it reads is the setup it waited for: a queue entry that opens a tab in the same refresh must not turn a failure into a success.
  - **Closed before it ended** is an error, `the setup of workspace W was closed before it ended`, also for `new-workspace --worktree`, which used to answer success with a pane that no longer existed: a setup that did not end did not succeed, and `start --worktree` already said so.
  - **The client leaving stops nothing**: the entry outlives its client (`outlives_its_client`), as for `new-workspace`, and its answer goes nowhere. A setup is visible and `Ctrl+C` stops it; ending it because a command's terminal or ssh went away would leave a half-installed worktree nobody asked for, and a command stopped with `Ctrl+C` only stops waiting.
  - **A new operation, no feature**: an older server refuses `run-setup` by name. A `setup` field on `new-tab` was rejected, since an older server drops an unknown field and opens a plain tab. `--worktree BRANCH` is resolved by the command through `status`, as for `new-tab`. A machine's worktree needs no field either: `cornercase --remote DESTINATION setup --workspace ID`, with the ids `status` lists under `machines`.
  - **Offering it**: nothing in `status` says whether the menu would list it. A client has what decides it, `worktree` and `setup` in `status` and the project's `setup` in `config`, and a refusal says why anyway; a field for one menu item was left out until a client needs it.
  - **Checked**: `app::tests::control_requests::run_setup` runs on every system (on Windows with `cmd.exe` panes and Git's `sh`, so only CI has run it there); what needs a `#!/bin/sh` fake agent, or closes the tab of a running setup, is in `control_requests::setup::run_again`, on Unix; the issue's steps through the real binary are in `tests/e2e/worktrees.rs`. Live on 2026-11-06, Linux, a debug build on top of 0.13.3: a setup that fails with `new-workspace --worktree`, `new-tab` typing `in []` with the mark still there, `setup` failing again with its status, then passing after a fix with its variables and the mark gone, the three refusals, and a second `setup` while one runs. Not tried by hand on macOS or Windows.
- **Teardown runs in the removal job**, after the shells stopped and before `git worktree remove` (`/bin/sh -ec` in the worktree, empty stdin, the same variables, five minutes via `process::output_within`, which kills the process group). A failing teardown does not stop the removal: the toast says `removed X, cleanup failed in part, see server.log`, with the bug icon, and `server.log` gets the warning whole (`worktree: removed, cleanup failed in part workspace=X warning="exit status 1: <last line>"`, plus `machine=` for a machine's; `worktrees::removed`), since the toast is one line, and with the teardown's line, a role's teardown or a role's worktree left behind with its path, the part that says what to fix did not fit in 80 columns. The same words cover the teardown and a role's worktree that stays, both in the one warning. `close --remove-worktree` still prints the warning itself, `warning: …` on stderr, and exits 0 (`Done::warning`). The removal dialog says `Its teardown runs first.`
- **On Windows** (#595): the scripts are written for `sh` almost always (`npm ci`, `cp .env.example .env`, `./scripts/setup.sh`), and a Windows machine that makes worktrees has git, which is Git for Windows nearly everywhere and ships an `sh`. So they run through **Git for Windows' `sh`** when it is found (in Git's own install, from `git --exec-path`, else from the folder of the `git` on the `PATH`; see Windows): the same wrapper, `sh -ec`, the same variables, with Git's `usr\bin` first on the script's `PATH` only, so `ls`, `rm` and `cp` are found while the shell that follows keeps the user's `PATH` (the wrapper's run line sets it for the script alone; the teardown's whole process gets it). `CORNERCASE_WORKTREE` is the worktree's Windows path (`C:\…`), passed in, rather than `$PWD`, which is `/c/…` under Git's `sh` and which a native program such as `node` reads as another folder. The user's shell then starts as the wrapper's child rather than through `exec`, and without what Git's `sh` added to the environment: `PWD` (`C:/…` with forward slashes), `SHLVL` (which `exec` sets again, hence no `exec`) and `HOME` when the server had none (the script itself keeps the `HOME` Git's `sh` gives it). The wrapper keeps ignoring `Ctrl+C` while that shell runs, so a `Ctrl+C` there does not end the wrapper and the pane with it. A known limit: Git's `sh` drops empty entries from the `PATH` it hands on. **Without Git's `sh`, PowerShell**: PowerShell 7 (`pwsh`) when it is on the `PATH`, else Windows PowerShell (`powershell.exe`, part of every Windows 10 and 11, started from the Windows folder rather than looked up on the `PATH`; see Windows). Chosen by what is installed rather than by the default shell, so it does not hang on `SHELL` (a cmd or nu user still gets a PowerShell to run scripts in). A teardown runs as `-NoProfile -Command` after `$ErrorActionPreference = 'Stop'` and `$PSNativeCommandUseErrorActionPreference = $true`, so a failing cmdlet stops it, and a failing program too from PowerShell 7.4; Windows PowerShell 5.1 goes on after a failing program, a known limit. The setup pane runs `-NoExit -Command` with a PowerShell wrapper that does what the `sh` one does: it moves to the worktree (the user's profile, loaded first as in any PowerShell, may have moved elsewhere), sets the three variables, runs the script in a child PowerShell (`-NoProfile -EncodedCommand`, so the script's `exit`, `cd` and variables stay in it), removes the variables, prints `✓ setup finished` or `✗ setup failed with exit status N` and writes the status file in a `finally`, so `Ctrl+C` in the script still writes it, and then the same PowerShell stays as the pane's shell. So without Git's `sh`, the setup's tab is that PowerShell, whatever the default shell is. **cmd is never used**: its `/C` runs only the first line of a script, nothing stops it at the first failing command, `%` is expanded inside its quotes and its quoting cannot carry arbitrary text, so a setup in cmd would have needed a batch file, its own quoting and an answer to how `Ctrl+C` ends a line; rejected for a case (no Git, a default shell of cmd) that a worktree user rarely has. The docs page on worktrees says which shell runs the scripts. Checked live on 2026-11-03 (Windows 11 10.0.26200, Git for Windows 2.39.2, Windows PowerShell 5.1): a setup through Git's `sh` and through PowerShell, a failing one, and a teardown (`git::worktree::setup::tests::on_windows`); `Ctrl+C` in a setup pane was not checked by hand.
- **Logs** hold sizes, exit statuses and timings, never the script or its output; a failed teardown's one-line reason (its last output line, at most 160 characters) is in the removal's `WARN` line above, the one place that keeps it whole, since the toast only points at the log. That line stays at `WARN`, not `ERROR`: the worktree is gone and only part of the cleanup failed, a warning, and `CORNERCASE_LOG=error` is a choice not to see warnings. Output of a running teardown is not shown anywhere while the row says `removing…`: a known limit, as the removal runs in the background.
- **Rows**: a workspace running its setup shows a muted `setting up…` tag (`WorkspaceEntry::setting_up`).
- **Build folders** (#485): a project also keeps the names of the folders ` free builds ` deletes in its worktrees (see Worktrees dialog), `projects.<folder>.builds` in `config.json`, a list of folder names. Absent means the defaults (`config::DEFAULT_BUILDS`: `node_modules target .next .turbo dist build .venv __pycache__`) and an empty list means no folder of this project is a build folder; a list equal to the defaults, as a set, is stored as absent, so saving the defaults writes nothing, and a project whose only setting is a custom list keeps its key. The third field of project settings, **build folders**, is one line (`Editor::one_line_key`, names split on spaces and commas, a pasted text joined on one line): `Tab` cycles setup, teardown and it, and `Enter` there saves, since Enter submits a one-line field and the two script fields keep it as a new line; the hint says so. A name that is empty, `.`, `..`, `.git`, holds a `/` or a control character is refused with a notice and nothing is saved (`config::parse_builds`, also used by `cornercase config project --builds` and the request). Settings sharing (see Settings) does not carry it: the share format names `setup` and `teardown` per repository and a list of folder names is personal to a machine's disk habits, so an import keeps whatever list the user has.
