# Bots

Code: `bots/` (`mod.rs`, `brief.rs`, `chat.rs`, `folder.rs`, `turn.rs`, `turn/link.rs`, `secrets.rs`), `agents/headless.rs`, `agents/{claude,codex,gemini,opencode,cursor,copilot}/headless.rs`, `agents/probe.rs`, `bots/form.rs`, `app/bots.rs`, `bots/follow.rs`, `app/bots/` (`secrets.rs`, `secrets_dialog.rs`, `follow.rs`, `reports.rs`, `turns.rs`, `manage.rs`, `shown.rs`, `window.rs`, `section.rs`, `talk.rs`, `menu.rs`, `form.rs`), `ui/bots.rs`, `ui/bots/`, `ui/dialog/bot.rs`, `app/control/bots.rs`, `control/bots.rs`, `cli/bot.rs`, `cli/bot/`, `cli/bot/secret.rs`, `bots/asks.rs`, `app/bots/asks.rs`, `app/bots/ask_dialog.rs`, `ui/dialog/bot_ask.rs` (#878), `cli/args/bot.rs`, `cli/help/bot.rs`, `cli/guard.rs`, `paths.rs` (#844, #845; `bin`, #892), `app/control/boundary.rs`, `os/socket.rs`, `os/process.rs` (`Lineage`), `processes/stop.rs`, `app/launches.rs` (#856), `process/program.rs` (`command_without_cmd`, #849), `client/server_process.rs`, `cli/requests.rs`, `cli/help.rs` (`TO_FILE`) (#867, #880), `server/bots.rs` (#883)

A **bot** is an agent of your own: a name, a folder, a memory and a chat. It belongs to no project, but it can see all of them and act on them through the `cornercase` command line. It exists for work that belongs to no project, or to all of them ("review my open pull requests every morning", "tell me which issues labelled `bug` came in today, in every project"), which today meant opening a folder as a fake project, or keeping an agent alive in a pane whose context grows for ever.

This is the base of the bots series (#844 to #849). It holds the model, the folders, the conversation, the shared runner, the commands, the requests and the events. The window draws them since #845 (see [The window](#the-window-845)), routines are in [Bot routines](bots/routines.md) (#846), following the agents a bot starts is in [Following](bots/following.md) (#847), there are no chat apps (#848), and Claude Code, Codex, Gemini CLI, opencode, Cursor CLI and GitHub Copilot CLI can be bots since #849 ([The agents](bots/agents.md)); Grok Build and Vibe CLI cannot yet.

**A bot made with what it is for sets itself up at once** (#887): `bot new` with an `about` that is not blank starts its first turn (see A turn); a bot made without one starts nothing and spends no tokens. After that a bot runs only when someone writes to it, when its routines run or on `bot setup`, and only while the server runs: a turn's process does not survive the server.

## Folders and files

`bots/` beside the session (`paths::bots(session)`, through `beside_session` as `journal` and `recap` are: `x.bots/` for `x.json`), so a dev server of another tree and a session with another file name each have their own. One folder per bot, `bots/<id>/`, 0700 on Unix:

- `bot.json` (0600, written through `persist`): `id` (a slug of the name, unique, kept when the bot is renamed), `name` (1 to 40 characters, unique ignoring case, no control characters), `agent`, `model`, `effort`, `account`, `access` (`cornercase` or `full`), `created` (UTC seconds) and `conversation` (the agent's session id for the chat; none before the first message and after `reset`).
- `bot.md` (0600): what the bot is for. Created from `--about` (may be empty); the user and the bot both write it, and the brief tells the bot to keep it up to date.
- `memory.md` (0600): what it keeps from one conversation to the next. Created empty; the bot adds to it, keeps it short and prunes it.
- `chat.jsonl` (0600): the chat, append-only.
- `secrets` (0600): the bot's encrypted secrets, made with the first one and deleted with the last (see [Secrets](bots/secrets.md)); the key is `bots.key` beside the session, not in the folder.

At most 50 bots (`MAX_BOTS`). A folder whose `bot.json` does not parse, or whose `id` is not the folder's name, is skipped when loading, but its name still counts as taken for a new bot's id, so a new bot never overwrites it. `remove` deletes the folder before it forgets the bot, so a folder that cannot be deleted leaves the bot where it was.

**The server never re-reads `bot.json` while it runs**: memory is the truth, and the server rewrites the file when it changes a bot. A bot's access lets it write in its own folder, and `bot.json` holds its `access`, so re-reading it would let a bot give itself full access. Claude's denied list also names `bot.json`, `chat.jsonl` and `secrets` (see Access). Codex's sandbox cannot exclude one file, so a Codex bot could rewrite `bot.json` for the next server start; this is not a real boundary, since a `cornercase` access already lets a bot start agents with `cornercase start`, and Codex bots are `full` only today anyway.

## The chat

`chat.jsonl` is cornercase's chat, not the agent's transcript. That way a routine's report (#846) and a line about an agent the bot started (#847) land in the same chat, and the chat survives `reset` and a change of model. One JSON object per line, never rewritten while the server appends to it (the same rule as the journal's day files, see Recap).

| `kind` | what it holds |
|---|---|
| `you` | the text the user sent; `held: true` when a turn was running |
| `bot` | the agent's final answer of a turn, in Markdown, with `model`, `tokens` and `conversation` |
| `step` | one tool the agent used, as one line (`cornercase status --json`, `Read src/main.rs`), with its `tool` |
| `error` | why a turn failed, in the agent's own words when it gave any |
| `started`, `finished`, `waiting` | an agent the bot started (#847, see [Following](bots/following.md)): `▶ started …`, `✓ claude finished in …` or `✗ … failed in …` with its last message as `body`, and `! … needs you in …` with the screen excerpt; each carries `agent` (kind, pane, workspace, project and the server's `boot`), and `run` when a routine run's conversation owns it |
| `notice` | cornercase's own lines: `new conversation`, `setting up` (the first line of a setup turn, in place of a `you` line), `stopped`, `interrupted by a restart`, `1 held message dropped` / `N held messages dropped`, a routine run's header `↻ <label> · <time>`, and an ask's `asks for a secret: …`, `secret saved: …` and `secret not given: …` (#878, see [Asks](bots/asks.md)) |

Every line has `id` (a number that increases per bot) and `at` (UTC seconds); a line of a routine's run has `routine` too, the run's queue id (see [Bot routines](bots/routines.md)); `agent`, `body` and `run` are only on the three new kinds and on the answer to a report turn that continued a run's session; `ask` is only on an ask's three notices. Absent optional fields are not written. The notice texts are fixed and part of the contract.

- **A torn last line** (the server stopped mid-write) is skipped by readers, and healed at load: if the file does not end with a newline, one is appended before the next line, so the next line parses.
- **Replay is the source of truth at load** (`chat::replay`): a `you` that is not held, or a `setting up` notice, starts a turn that runs; held ones are counted; a `bot` or `error` ends the turn, and held messages start the next one at once; `stopped` and `interrupted by a restart` leave it idle with nothing held. No extra field is kept for the turn. A turn still running in the replay gets `interrupted by a restart`, and held messages get the dropped notice, once (a second load finds the notice and appends nothing).

## A turn

A turn is one run of the agent without its interface, through the shared runner (below), in a conversation that continues.

- **The first message of a conversation starts a new session.** Its opening message is the brief, then `bot.md`, then `memory.md` (each cut to 8 KB on a character boundary, saying it was cut; an empty file reads `(empty)`), then what the user wrote. Later messages send the text alone and continue the session: Claude with `--resume <session>`, Codex with `codex exec … resume <session>`. The session id comes from the run's own output (Claude's `system/init` and `result` lines carry `session_id`; Codex's `thread.started` carries `thread_id`) and goes into `bot.json`.
- **A setup turn (#887)** ends with its own section instead of the user's text.
  - **Who starts it.** `bot new` with an `about` that is not blank, from any source (the window's form, `bot new --about`, the `bot` request). A blank one starts nothing, and loading the bots at server start never starts a turn.
  - **Its opening** is the brief, `bot.md`, `memory.md`, the routines' answers not yet told, then `## You were just made`. The section asks the bot to set itself up in a few steps without doing the work itself, to schedule what `bot.md` asks for, to write in `memory.md` what its runs will need, and to tell the user what it will do, what it scheduled and what it needs. It says not to read every `--help` (the runs look commands up when they run; the first live setup used 39 of the 40 steps) and to look at `cornercase queue list --bot <id> --json` first, so a setup cut short at the step limit and run again does not schedule the same routine twice. The brief tests check that every command and flag the section names exists.
  - **The notice `setting up`** is the turn's first line, written after the `thinking` event. It stands in for a `you` line: replay and `unseen` count it as the line that opens a turn, so a restart during the setup appends `interrupted by a restart` once, and the answers it already carried are not told again.
  - **Otherwise an ordinary chat turn**: one at a time (a message sent meanwhile is held and goes next), steps stream, `stop` and the 15-minute limit work, and its answer is unread with a toast and a notification when the chat is not on screen.
  - **It never resumes.** `bot setup` and ` retry ` open a new session even when the bot has one; on success it replaces `conversation`, and on failure the old one is kept (a new bot's stays empty). No `new conversation` notice is written: `setting up` marks the cut.
  - **Refusals** of `bot setup`: `busy` while a chat turn runs (a routine's run does not block it), and `conflict` when `bot.md` is empty.
- **The session id is kept only on success.** A first turn that fails, is stopped or times out leaves `conversation` empty, so the next message opens with the brief again; a later one that fails keeps the session, so the next message continues it.
- **One turn at a time per bot.** A message sent while a turn runs is held and goes as the next turn, joined with the others held by a blank line. Its `you` line is written at once with `held: true`. Different bots run at the same time.
- **Steps stream.** Each tool use read from the run's output is written as a `step` line and published as it happens, before the `bot` line.
- **`stop`** ends the running turn: the process and what it started (`processes::stop`, as the Processes dialog stops a tree: TERM, a grace, then KILL). It writes `stopped`, keeps the session id, and **drops the held messages** with a notice, so a stopped bot is idle. A stop that arrives before the process exists still ends it (`probe::Running` remembers it).
- **A contained turn stops what it started whenever it ends** (#856): the moment the answer is read (a turn closes the root's stdin at the start, but the root, such as Claude Code, usually still runs until it has printed its result, so its children, orphans it adopted included, can still be listed), the root's children are captured, the root is given its grace and then killed, and the captured trees are stopped; the root's children are listed again after its grace and before it is killed, only when it is still running then (an exited root is reaped and its pid could be reused) (what an earlier child orphaned meanwhile, adopted by the root on Linux), and when nothing was captured at the answer (a root that closed its output, an error) they are listed before it is killed; a root that already exited by then leaves nothing to list. **Not closed**: a process that outlives the root and its parent between captures, and (Windows) a child that starts a process in the moment between its spawn and its assignment to the Job; a descendant that survives the root's exit is no longer held by `Running::holds` (the root's pid guards against reuse), so it is told by its environment only (`processes::stop::below`, `stop_all`: TERM, a grace, KILL). Without it a command a bot left running could connect after its turn, when no turn holds it.
- **Time limit: 15 minutes per turn** (`TURN_TIMEOUT`; the app keeps it in `Bots::timeout` so tests shorten it, as Recap does with `RECAP_TIMEOUT`). A bot acts by starting agents and returning; it does not do long work itself. The timeout ends the whole process tree, and the `error` line says `claude did not answer in time`.
- **A restart** drops a turn's process with the server: see Replay above.
- **A second `stop`** adds what was held since to the ones to drop and starts no second job, so a `say --wait` held in between is answered with the dropped notice. **The server stopping** (`stop_background`, so `kill-server`, `restart` and an update) ends every running turn's process tree, one thread each, so the agent does not outlive the server it reports to. A message held while a stop was in flight runs as the next turn: replay keeps `held` at `stopped`, takes off the count a following `N held messages dropped` names, and reads what is left as the turn that runs.
- **`stop` also ends the bot's routine runs, and `remove` refuses while one answers** (`reset` does not: a run has its own session; see [Bot routines](bots/routines.md)).
- **`reset` and `remove` refuse while a turn runs** (`stop it first`), the same way: forgetting a session a process still uses, or deleting its folder under it, would leave the chat saying something false.
- **`reset`** (the window's ` new conversation `) forgets the session id and writes `new conversation`. `bot.md` and `memory.md` stay, so the next message starts a new session that reads them.
- **Failures keep the agent's words** (`Not logged in`, `usage limit`). Two are worded by cornercase: `error_max_turns` becomes `claude stopped after 40 steps, its limit for one message`, and a failure whose words name the context (`prompt is too long`, `context window`, `context length`, `maximum context`, `context_length_exceeded`) gets `; start a new conversation: cornercase bot reset <id>`.
- **Unread**: each bot counts the `bot` and `error` lines since a client last showed its chat (`bot seen`, a window showing it, or a visible view naming it). It lives in memory, so a restart shows nothing unread.
- **Notices**: a `bot` or `error` line makes a toast (` <name>: <first line> ` with a ` go ` that shows the chat; the first line is the answer's as plain text, `chat::preview` over `highlight::markdown::plain`, so Markdown marks, list marks, task boxes, a fence's language, links' URLs and HTML tags and comments are dropped (an HTML block keeps its text, through the stripper the chat uses), an answer with no words falls back to its raw first line, and an `error` keeps its text, which the chat draws as it is; reading `render`'s first row was rejected, since it gives a fence's language, bullets, a link's `(url)` and a rule's dashes, #864) and a desktop notification, whose click shows it too. A turn that a `say --wait` client waits on counts as shown, and so does one answered while a window shows the chat or a visible view names it (#869): it neither notifies nor counts as unread. Everything else does. Chat apps are #848.

## The brief

What cornercase tells the bot about itself. The server writes it from Rust constants (`bots/brief.rs`, one per section) and sends it in the opening message of every conversation. It is never written to the bot's folder, so a new release updates every bot at its next conversation. It says who the bot is and that it answers briefly, in the user's language, in Markdown; where its folder is and what `bot.md` and `memory.md` are for; how to see the user's work (`cornercase status --json`, `search`, `recap`, `worktrees list`, `read --pane ID`, read-only `git` and `gh`); how to act (`cornercase start --project ID …`, `send --pane ID`, `notify`, and that it must always name the project, since it runs in no pane); and what its access allows (for `cornercase` access, also one sentence on what cornercase refuses it, `BOUNDED`, #866), and last whether it is told when an agent it started finishes (`FOLLOW`, or `NOT_FOLLOWING` when the bot's `follow` option is off, see [Following](bots/following.md)). A test runs `--help` for every command the brief names, so it cannot name a command that does not exist.

A project's git (#893): the brief says that `cornercase status --json` gives each project's and workspace's folder (`path`) and teaches `git -C 'PATH' log …` (and `show`, `diff`, `status`) in single quotes, the one spelling that exists on every system, and `gh … -R` with a project's `repo`. The git line is left out for an agent without `BotSupport::reads_git` under `cornercase` access, which is told it cannot run git; `full` bots are taught it too. The access says to run one command per call: a loop, `$(…)` and a redirect were refused when checked.

Rejected:

- **Writing the brief into the folder as `AGENTS.md` or `CLAUDE.md`.** The agent would load it on its own, a second time, and an old copy would outlive an update.
- **The agents' system prompt flags.** `claude --append-system-prompt` exists and survives compaction, but Codex's `exec` has no stable equivalent, and one rule for both agents is easier to test with the fakes. A conversation that compacts may lose the brief; `reset` brings it back.

## Access

A turn runs without its interface, so the agent cannot stop halfway to ask for permission. What it may do is fixed when the bot is made (and changed by `bot edit` from the next turn; never by the bot itself, see the guard).

- **`cornercase` (the default)**: it reads anything, runs the `cornercase` command line, read-only git in the user's projects (Claude Code only) and gh, searches the web, and writes only in its own folder.
  - Claude: `claude -p --setting-sources user --output-format stream-json --verbose --max-turns 40 --permission-mode dontAsk --allowedTools Read,Grep,Glob,WebSearch,WebFetch,Bash(cornercase:*),Bash(gh pr list:*),Bash(gh pr view:*),Bash(gh pr checks:*),Bash(gh issue list:*),Bash(gh issue view:*),Bash(git -C <folder> log|show|diff|status:*),Edit(<folder>/**) --disallowedTools NotebookEdit,Task,Bash(git *--output*),Edit(<folder>/-*),Bash(cornercase kill-server:*),Bash(cornercase restart:*),Bash(cornercase update:*),Edit(<folder>/bot.json),Edit(<folder>/chat.jsonl) [--resume S] [--model M] [--effort E] -- <prompt>`. The git rules are `Bash(git -C <folder> log|show|diff|status:*)` per folder of `Ask::repositories` (see The boundary › A project's git for which folders, their spellings and the size limit); Gemini and Copilot run no git (see The boundary › A project's git). `--permission-mode dontAsk` denies what is not allowed instead of asking, and stops the user's own `defaultMode` (`auto`, `acceptEdits`, even `bypassPermissions`), which `--setting-sources user` loads, from applying.
  - Codex: `codex exec --json --skip-git-repo-check --sandbox workspace-write -C <folder> [-m M] [-c model_reasoning_effort=E] [resume S] -- <prompt>`, so it writes only in its folder. See the live checks: this access is not offered.
- **`full`**: Claude with `--permission-mode bypassPermissions` (only the commands that stop the server are denied), Codex with `--dangerously-bypass-approvals-and-sandbox`. `bot new --access full` and the form say what it means: it can change any file and run anything, unattended. **Off by default, never chosen for the user**: an agent that supports `full` only (Codex) is refused without `--access full`, with that warning.
- **Settings**: neither agent loads a project's settings, since there is no project. Claude loads the user's settings (`--setting-sources user`), so the user's MCP servers and `~/.claude/CLAUDE.md` work, unlike Recap's empty sources: a bot is the user's own assistant. No `--strict-mcp-config` and no `--no-session-persistence` (the session must be resumable). A Codex bot reads the user's own `~/.codex/config.toml` as it does without cornercase (no `--ignore-user-config`).
- **The other agents** (#849): Gemini CLI and GitHub Copilot CLI have both accesses, with rules that keep them to reading and writing only their folder (the brief says so); opencode and Cursor CLI are `full` only because their rules cannot keep a command's or an edit's writes in the folder. See [The agents](bots/agents.md).
- **What `bot agents` says**: `bot: false` with `why` (`not yet` for an agent without a headless spec, `not installed`), or `bot: true` with the `accesses` it supports and, when the access is limited, `why`: `its sandbox cannot reach cornercase` (Codex, Linux, checked), `its sandbox is not known to reach cornercase on this system` (Codex on macOS and Windows, not checked), `a command can write outside its folder` (opencode), `its edits can leave its folder` (Cursor CLI) or `its rules are unchecked on this system` (Gemini CLI and GitHub Copilot CLI on Windows). A UI builds its form from this list, so an agent added later appears without changes elsewhere.

## The shared runner

`agents/headless.rs` is **one runner for Recap and bots** (it was `agents/recap.rs`): `Ask`, `Ran`, `Spec`, `Call`, `run`, with each agent's `headless.rs` holding its arguments and its reader. `Known::headless()` replaces `Known::recap()`; an agent without it can be neither. What bots added on top, none of which changes Recap's arguments (two exact-argv tests, written before the move, pin them):

- `Ask::tools` (`Tools::Recap` or `Tools::Bot(Access)`) picks the arguments; `Ask::conversation` continues a session; `Ask::env` sets (`Some`) or removes (`None`) variables.
- `Ran::session` (the session id out) and `Ran::fresh` (the tools used since the last line, which `run_watched` hands to `Watch::steps` as they arrive). `Action` is a tool and its one-line summary (Bash: the command's first line; Read, Edit and Write: the path; Grep and Glob: the pattern; WebSearch, WebFetch: the query or URL).
- **`Spec::recap`, `Spec::stderr` and `Spec::prepare`** (#849): whether the agent can write a recap (Claude Code, Codex, GitHub Copilot CLI and opencode since #879), whether its standard error is read for the reason a run ended, and a step that runs before the process starts (Gemini writes its rules file). `run_watched` refuses a Recap or an access the spec does not list before anything starts. `BotSupport::reads_anywhere` is false for the agents that can read only their folder, which changes the brief. Programs start through `process::program::command_without_cmd`, which goes past `cmd.exe` for an npm shim.
- **`Spec::ended` and `probe::Heard`** (#879): a reader hears each line and then the end of the output (`Heard::End`, through `probe::run_heard`; `probe::run_in` keeps hearing lines only, for the usage probes and the breakdown). A spec with `ended` may answer there: opencode's, which has no line that ends a turn (see Bots › The agents › opencode). Without one, when it has nothing to answer with, or when the run was stopped (`Running::stopped`), the run fails as `<agent> exited without answering`, as before. Output that cannot be read (a line that is not UTF-8) fails the run the same way and is never taken for the end.
- `run_watched(call, ask, Watch)` carries the progress counter, the steps callback and a `probe::Running`. `Spec::bot` says whether the agent can be a bot, with its accesses and why they are limited (`BotSupport`, whose `reads_git` says that its `cornercase` access runs `git -C <folder>`). `Ask::repositories` is what a turn may run git in (#893).
- **`probe::Running`** lets a bot's `stop` end a run, also before its process exists; a timeout ends the whole tree (see Plan usage › A timeout ends the whole tree).

## Requests and events

One operation, **`bot`**, whose `args` are `{"action", "entry"}` (`entry` is the action's fields, left out for `agents` and `list`) (`agents`, `new`, `list`, `edit`, `about`, `remove`, `reset`, `seen`, `stop`, `setup`, `say`, `history`, `secret-set`, `secret-list`, `secret-remove`, `secret-get`, `secret-ask`, `secret-give`, `secret-decline`), adjacently tagged as `config`, `machines` and `queue` are (`{"command":"bot","args":{"action":"say","entry":{"bot":"prs","text":"hi","wait":true}}}`). `src/control.rs` was 989 lines and `tests/layers.rs` fails a file over 1,000, so ten request names with their lists did not fit; one name needs four lines, and every type lives in `control/bots.rs`. An older server refuses `bot` by name. All of it is behind the contract feature **`bots`**, which the CLI checks before any `bot` command (`the running cornercase server has no bots`). Request structs have no `skip_serializing_if`, so a strict client's unknown-field check works.

- **The four `secret-*` actions** (#877, behind the additive feature **`bot-secrets`**, which `cornercase bot secret` checks first): `secret-set` (`{bot, name, value}` → `{bot, name, saved}`), `secret-list` (`{bot}` → `{bot, key, secrets: [{name, saved}]}`), `secret-remove` (`{bot, name}` or `{bot, all}` → `{bot, removed}`) and `secret-get` (`{name}` → `{bot, name, value}`, for the bot that asks). `BotInfo.secrets` counts them, in `bot list --json` and `status --app`, and `secrets_unreadable: true` (left out when false, so the fixtures keep their bytes) says the file cannot be read, when `secrets` is 0 either way. Saving and removing publish `change: edited`. Their rules, the key and the redaction are in [Secrets](bots/secrets.md).
- **`secret-ask`, `secret-give` and `secret-decline`** (#878, behind **`bot-asks`**): a bot asks for secrets it lacks, the person gives or declines them; `BotInfo.asks` lists the waiting ones (left out when empty) and a chat line carries `ask`. See [Asks](bots/asks.md).
- `bot` names a bot by id, else by name ignoring case; an unknown one is `not-found`. Validation errors are `malformed` (a name that is empty, over 40 characters or has a control character; an unknown agent, model, effort, account or access; a message empty or over 20,000 characters, refused with its size rather than cut), `conflict` (a name taken; the 51st bot) or `busy` (`reset`, `remove` while a turn runs).
- `new` with a non-empty `about` answers `state: thinking` and the events come in this order: `created`, `thinking`, the `setting up` line, the steps, the `bot` or `error` line, `idle`. `setup` (`{bot}`) runs the setup turn again and answers `{bot, line}` with the `setting up` line; the contract lists the additive feature **`bot-setup`**, which `cornercase bot setup` checks.
- `about` (`{bot}`) answers `{bot, about}`, the text of `bot.md` read when asked. A missing file reads as `""`; one that cannot be read is `failed`, never an empty text a form could save over the real one. `folder::about` opens it non-blocking and refuses what is not a regular file (as `config::read` does), so a FIFO named `bot.md` cannot hang the server loop, which reads it. The text is never logged. It is behind the additive feature **`bot-about-read`**, which `cornercase bot about` checks.
- **Rejected: `about` in `BotInfo`** (#876). `BotInfo` is a list summary (`last` is cut to 200 characters); the app stream rebuilds `bots` up to every 500 ms while a program follows it, so a field would read up to 50 files of any size on the server's loop each time and put them in every `status --app`; and a cache would go stale, because the bot rewrites `bot.md` during its turns and runs and the person can edit it by hand.
- `say` answers at once with the `you` line. With `wait` it answers when that message's turn ends with the `bot`, `error` or `notice` line (`Stage::Bot`, which does not outlive its client; the answers are kept per bot for the waited ids only, at most 32). The CLI exits 3 unless the line is a `bot` line.
- `edit` cannot change the agent (`a bot keeps its agent: another agent cannot continue its conversation; make another bot`); an empty `model`, `effort` or `account` clears it; a change applies from the next turn and publishes `change: edited`.
- **Events** (`cornercase events`): `{"event":"bot","bot":ID,"line":{…}}` for each chat line, steps included; `{"event":"bot","bot":ID,"state":"thinking|idle"}`; `{"event":"bot","bot":ID,"change":"created|edited|removed"}`. Exactly one of the three keys is set. They go to every reader that did not filter by `--pane` (`Event::kind()` is `None`), as Recap's do. A client that shows a chat reads `history` once and follows the events. The lines appended at load are not published: no reader is connected yet.
- **`status --app`** has a `bots` key (the same as `bot list --json`, left out when empty so the v1 snapshot fixture keeps its bytes), so a UI updates its list without polling. `unread` and `seen` travel through it: `seen` publishes no event.
- `--remote` works as for any command. A bot on another machine is left for later.

## The guard: `CORNERCASE_BOT`

A bot runs in no pane, so a command that would default to "the one this runs in, else the shown one" would act on whatever the window shows. When `CORNERCASE_BOT` is set and not empty, `cli::parse` computes a refusal from the matches it already has (`cli/guard.rs`) and `cli::run` returns it as wrong usage (exit 2) before doing anything:

1. The commands of `bots::SERVER_STOPS` (`kill-server`, `restart`, `update`): `a bot cannot stop its own server`. This also covers Codex, whose sandbox cannot filter commands.
2. **A generic rule**: the deepest matched command has an argument whose help says `this runs in` (the marker shared by `HERE_PANE`, `HERE_WORKSPACE`, `BY_BRANCH`, `WAIT_PANE` and the literal defaults), and none of its place flags (`--workspace`, `--project`, `--pane`, `--tab`, `--group`, `--path`, `--all`, matched by their long name, since ids differ) was given: `a bot runs in no pane: name the place with --workspace ID or --project ID (cornercase status --json lists the ids)`. Nothing is listed by hand, so a new command whose help says `this runs in` is covered, and a test fails if someone rewords one of the four constants. **Known false positive**: `flow import` and `flow export` with `--to yours` and no `--project` are refused too; harmless, since a bot has no use for them.
3. `bot edit … --access` and `bot new … --access full`: `a bot cannot change a bot's access`.
4. `bot say` to its own id: `a bot cannot write to itself`, since a message held for itself would start another turn for ever. It matches the id in `CORNERCASE_BOT`; a bot that names itself by its name is not caught.
5. An argument whose help says `instead of standard output` (`help::TO_FILE`; today only `config export --to`), given on the command line: `a bot cannot have cornercase write to a file: leave out --to to print it instead` (#880). It is generic as rule 2 is, and a test pins the marker.
6. A window: `cornercase` with no command (here, or on another machine with `--remote`), `cornercase remote DESTINATION` and `cornercase proxy`: `a bot cannot attach as a window` (#883). `remote --known` stays allowed. The hidden `cornercase server` is refused too (`a bot cannot run cornercase's server`): it would run the server in the bot's own process, with `CORNERCASE_BOT` in its environment (see Bots › The boundary, A window). A line of `requests --follow -` without a command keeps its own answer (`a line needs a command`), so the first case is `guard::run_refusal`, which `cli::parse` calls, and not `refusal`.

7. `bot secret set` and `remove`: `a bot cannot save or remove secrets`; `bot secret list BOT` with a BOT that is not the bot running it (ignoring ASCII case, as rule 4): `a bot reads only its own secrets` (#877). A bot listing itself by its name rather than its id is refused too (a known false positive: the brief teaches `list` without BOT); `get` is left to the server. `bot secret give` and `decline`: `a bot cannot give or decline what a bot asks for` (#878); `ask` is left to the server.

8. `plugin` other than `list`, `status`, `actions` and `logs` (an allow list, so a new subcommand is refused until decided): `a bot cannot run or change cornercase's plugins`; `machines add`, `edit`, `remove` and `update`, and `remote --remember` and `--forget`: `a bot cannot change cornercase's machines` (the two `remote` flags write `config.json`'s `machines` from the command line's process, as `plugin` writes its files, so the guard is all that stops them; #898); every `tunnel` subcommand: `a bot cannot open or close a tunnel` (#866). The texts are `bots::NO_PLUGINS`, `NO_MACHINES` and `NO_TUNNELS`, shared with the server. Plugins write their files from the command line's process, which the server never sees, so the guard is all that stops them.
9. `--remote` or `CORNERCASE_REMOTE`, on any command: `a bot works on this computer only: it cannot act on another machine` (`bots::ELSEWHERE`, #866). `cli::run` checks it right after `reach::chosen`, since the far server sees an ssh process and cannot tell a bot; the window forms are refused earlier by rule 6 with their own text, and `remote --known`, which takes no `--remote`, stays allowed.

Every rule applies to a `full` bot too: `CORNERCASE_BOT` carries no access, and the guard asks nothing of the server. The `full` brief says which commands are refused (#866); a `full` bot may run them without the variable, which only prevents mistakes.

**Each line of `cornercase requests --follow -` goes through the same guard** (#867): before, a line skipped it. The server repeats the stops (`kill-server`, `restart` and `update`'s restart, as requests and messages), rule 3 (access changes) and rule 6 (a window's messages), and none of the others; what that leaves to the guard is in Bots › The boundary. A raw client (`cornercase proxy`, a program speaking the protocol) meets only the server's refusals.

The command line's guard only prevents mistakes: what a bot's commands may type into, and what it may change about bots and settings, is enforced by the server (The boundary, below).

Without `CORNERCASE_BOT` (unset or empty) the command line's guard changes nothing; the server's boundary does not depend on it. #846 uses the variable as the default for `queue add --bot`, and #847 (with `CORNERCASE_BOT_RUN`) to tag what a bot starts, in the request's envelope: it only labels, and a marked connection's own bot wins ([Following](bots/following.md)).

## Limits and log

- A message is at most 20,000 characters.
- **Texts are never logged** (see Log): the log says `bot say bot=prs bytes=120` (and `about_bytes` for `new`), `setup bot=prs` when a setup turn starts, then, for a connection that is a bot's, `a bot's client` (`client`, `bot`), then the turn's agent, model, tokens, duration and how it ended (`answered`, `error`, `stopped`, `timeout`) under the target `bots`. The turn's job returns `Ok` whatever the agent said, so the job never logs an agent's text as its error.
- A secret's value is never logged: `secret set` logs `bot`, `name`, `bytes` and `replaced`, `secret get` and `secret removed` the bot and the name, and a request's fields carry the name and the size only.
- Not counted in Stats: the turn is no pane's agent, as with Recap.

- **Claude's permission rules.** `--permission-mode dontAsk` is accepted and the run ends with a `result`; `--max-turns` is still accepted though `--help` no longer lists it. **A `Write(<path>)` rule does not apply** (denied for `Write(//abs/**)` and for `Write(./**)`), but **`Edit(<path>)` covers the Write tool too**: `Edit(//abs/**)` (and `Edit(./**)`, and the `///abs` spelling) allows a write inside the folder, a write outside is denied, and `--disallowedTools Edit(<folder>/bot.json)` blocks a write of that file though the folder is allowed. So the rules are `Edit` only, and the absolute path is `/` + the absolute path (`//home/u/…`; `rule_path`). On Windows the form `//c/Users/u/…` follows Claude Code's documentation and **is not checked**. `--resume <id>` remembers, and the session id is the same in `init` and `result`.
- **Codex's sandbox and the socket.** In `--sandbox workspace-write` a `cornercase` command cannot reach the server: `no cornercase server is running`, and with `-c sandbox_workspace_write.network_access=true` `Unknown error -1000`; with `--dangerously-bypass-approvals-and-sandbox` it works. So **a Codex bot cannot have `cornercase` access** on Linux: it is `full` only, `bot agents` says `its sandbox cannot reach cornercase`, and the form says so. On macOS and Windows the sandbox was not tried: they stay `full` only with the unverified wording, and the Known limitations list it.
- **Codex resume.** `codex exec --json --skip-git-repo-check --dangerously-bypass-approvals-and-sandbox -C F [-m M] [-c …] resume <thread> -- <prompt>` continues the conversation and names the same thread; the `exec` options go before `resume` (`resume` takes neither `--sandbox` nor `-C`).

The log held request sizes, never a text.

## Decisions on what the issue left open

- **Claude's brief**: the opening message, for both agents (Rejected above).
- **Context**: both agents compact on their own in print mode; a failure naming the context gets the `bot reset` hint.
- **Codex's own config**: a Codex bot reads the user's, as without cornercase.
- **Unread across restarts**: in memory only.
- **Reading `bot.md`**: a program reads it with `bot about`, as the window's form reads it when it opens; `BotInfo` does not carry it (#876).
- **Changing the agent**: `bot edit` refuses another agent; making another bot is the way.
- **Stats**: bot turns do not count.
- **`stop` drops held messages; `reset` and `remove` refuse while a turn runs.**
- **A waited turn counts as shown.**
- **Changing `about` later runs nothing** (`bot edit --about`, the form's ` save `): the chat is the way to change a job, and `bot setup` exists for whoever wants a new setup. There is no `--no-setup`: an empty `--about` is enough.
