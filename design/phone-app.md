# Phone app

Code: `web/phone.rs`, `web/phone/` (`cli.rs`, `code.rs`, `command.rs`, `link.rs`, `message.rs`, `pairing.rs`, `tls.rs`), `app/phone_app.rs`, `host/network.rs`, `host/name.rs`, `cli/reach.rs`, `control/pair.rs`, #838, #960

- **Why** (#838): a native phone app (cornercase-mobile, a Tauri app that, like cornercase-gpui, uses only the command line, #345) has neither the binary nor ssh, so it cannot run `status --json`, follow `events` or stream `surface --patches`. Browser access (see Browser access) does not help it: its QR code opens the web version, its `/ws` speaks the terminal client's protocol (a `Hello`, key bytes, frames) and it listens only through Tailscale. The app worked around it with a development bridge of its own on the Mac, a WebSocket server that ran `cornercase <argv>` per connection, with a fixed token, so it could not ship. cornercase serves the same thing itself.
- **Apart from the browser's access, on purpose.** Its own switch (`phone_app`, Settings › Remote › Phone app, off by default; `phone_app_port`, 47682 beside the browser's 47681, has no row), its own listener, its own `apps.json` beside `browsers.json`, its own code. Reusing the browser's code and cookie with `/cli` beside `/ws` was rejected: that code opens the web version, it works only through Tailscale, and a native app would have to follow a redirect meant for a browser. `Web` and `Phone` share only what is the same by nature: `Pairing` (a 16-byte code, single use, ten minutes), `Devices` (a hash per device, `<id>.<secret>`), `Request`/`Response` (`Response::text` too), the WebSocket upgrade (`http::upgrade`, generic over the stream), the timing constants, and the listener plumbing: `web::spawn_counted` (the cap at accept, the thread, the write timeout, one deadline), `web::read_head` and `Request::read_before` (the request head before that deadline, over any stream that can wait at most a time, `http::Timed`), and `bind_now`. Only the phone's listener speaks TLS (#960): the browser's sits behind Tailscale's `serve`, which already gives it HTTPS. A shared registry of open connections was rejected: the two `Shared` structs hold different things (the device id, `accepting` and the pairing here; counters there), so a generic type would tie the listeners together to save a few lines.
- **The code** (`web/phone/code.rs`) is the bridge's format with TLS and a pin (#960): `wss://<first-host>:<port>/?code=<code>&also=<host>&also=<host>&name=<percent-encoded name>&fp=<fingerprint>`. `fp` is last and always there (no code is shown without it), the SHA-256 of the DER certificate the listener presents, in base64url without padding: 43 characters, no `=` to escape in a query (the issue's `openssl … | basenc --base64url` check needs `tr -d '='`). The JSON field that carries it elsewhere is spelled out, `fingerprint`. The first route is in the authority, so IPv6 goes in brackets there and bare in `also=` (`SocketAddr` prints it so). The name is the computer's (`host/name.rs`: `scutil --get ComputerName` on macOS, else the host name without `.local`; `/proc/sys/kernel/hostname` on Linux; `COMPUTERNAME` on Windows; `/bin/hostname` runs only when `scutil` gives nothing, and the lookup is warmed on a thread when `phone_app` turns on, since `scutil` can take up to 2 s and must not delay the first draw of the dialog), cut to 64 characters and percent-encoded; no name, no `name=`; no route, no code. A QR code at level L with LAN and Tailscale IPv4 and a 21-character name was 49×25 modules before `fp`; the worst case the test pins (two long IPv4, a full IPv6, a 32-character code, a 64-character name and `fp`) is 248 bytes and 65 columns (measured November 2026); `ui::remote_access` already falls back to text when the dialog is smaller.
- **TLS and the certificate** (`web/phone/tls.rs`, #960): the listener speaks TLS with a self-signed certificate made once per computer and kept in `app-certificate.json` beside `config.json`: `{"version": 1, "certificate", "key"}`, both standard base64 of their DER (the key in PKCS#8), written as `apps.json` is (`0600`, synced, renamed into place). The key is kept beside the certificate because the pin is over the certificate: signing a new one with the same key would change the fingerprint anyway. ECDSA P-256 (every TLS stack takes it; Ed25519 is not in every phone's), one DNS name `cornercase` so the certificate is well formed (never an address: they change, and the pin is the identity), the subject's common name the computer's name cut to 64 characters (`cornercase` without one; the issuer repeats it, self-signed), and rcgen's default validity, 1975 to 4096: no clock is involved, the pin is what protects, and replacing it is by hand. It is made with `rcgen` (with `ring`, already in the tree, and `yasna`; no `pem`, no `x509-parser`, no `aws-lc-rs`), not with DER written by hand over `ring`: an X.509 writer of our own would be security code nobody else reviews. The server side is `rustls` (already built for `ureq` and `tungstenite`), with the `ring` provider named in `builder_with_provider`, so a later dependency that turns `aws-lc-rs` on cannot make the builder panic over two providers; TLS 1.2 and 1.3 both stay on, so the app may use its platform's stack. It is loaded or made on the tick that first listens (`Phone::listen`), so the name lookup it may wait for is the one already warmed when `phone_app` turns on; no certificate, no listener (`Phase::Failed`, retried at the next read): it never falls back to plain only. A file that does not parse (not JSON, or not even UTF-8), has another `version` or that rustls refuses is replaced with a new certificate and a warning (the old pin is dead anyway); any other read error is an error, so a certificate that may be fine is never replaced. A server restart or an `update` reads the same file: the code's `fp` stays.
- **Telling TLS from plain** (`web/phone/link.rs`, #960): plain `ws://` stays answered on the same port, so the apps paired before keep working. The first byte decides: `0x16` is a TLS handshake record and no HTTP method starts with it; anything else is plain. It is peeked, not read, so the plain path sees the request whole. One deadline covers the peek, the handshake and the request head (`Limits::head_within`, 10 s). rustls is driven by hand (`link::Encrypted`), the handshake and every read after it: `read_tls` with the time left, then `process_new_packets`, until there is plaintext, the end or the deadline. A read waits at most what `Timed::wait_at_most` last gave, in all, as a plain socket's read timeout does (the head's time left, then the pump's `POLL`), and then says `WouldBlock`. `StreamOwned` and `complete_io` were rejected: they loop over socket reads until a whole record decrypts, each read with the full timeout, so a client that finished the handshake and sent its request a byte at a time held its place, or a paired one the pump, past every limit (found in review). A setting that picks plain or TLS was rejected: it would need a switch, docs and a migration, and the first byte needs none. Every close the server starts and waits out ends with `Link::end`: a TLS `close_notify`, then the write side shut, since without `close_notify` a TLS client reads the end as an error. `Connected` keeps a clone of the TCP socket, so `forget`, `renew` and `close` still shut connections down whatever they speak. A TLS write only encrypts, after sending what is still pending, and `flush` sends: every writer flushes (`http::upgrade` too, after the `101`), a blocked send returns `WouldBlock` as the pump's backpressure expects, and since what was pending is gone first rustls always has room, never taking zero bytes (tungstenite reads a zero-length write as a reset). The logs say `tls` on `phone app paired` and `phone app command started`, so the apps still in clear can be counted before plain is dropped.
- **A new certificate** (`Phone::renew`, `config pair app --new-certificate`, the `config-pair` field `new_certificate`): the new certificate is made in memory, then, under one lock, every paired app is forgotten, every open connection is cut, and only then is the certificate written and put in use. Two files cannot change at once, so the order picks the safe half: if `apps.json` cannot be written nothing changes, on disk or in use; if the certificate cannot be written the apps stay forgotten (the revocation the change is for) with the old certificate on disk and in use, and the error says so. A failed renewal never leaves a certificate on disk other than the one in use (CodeRabbit on #969); the held code is kept and shown with the new `fp`. Forgetting the apps goes beyond the issue's "every app then needs a new code" on purpose: without it an old secret would stay valid over plain `ws://`, so replacing a certificate somebody may have copied would revoke nothing. The cost is that an app that only speaks plain is locked out until it updates. It is a field of `config-pair` behind the feature `cli-tls` (as `view --no-claim` is a field of `view`), not an operation of its own and not a Settings row: the change has no UI, the command line reaches every client, and a bot is already refused `config-pair` (see Bots › The server's boundary).
- **cornercase-mobile and the change of scheme** (#960): the app as shipped (November 2026) accepts only codes that start with `ws://` and has no TLS at all; it ignores query parameters it does not know, so `fp=` alone would not hurt it. So an app already paired keeps working in clear, but a shipped app cannot pair a new computer, or pair again, until it reads `wss://` and pins `fp`, its own task. Keeping `ws://` with `fp=` added would have avoided that window, but the scheme would then lie about what a pinning app speaks, and the issue asks for `wss://`.
- **The app trades the code for a secret with a WebSocket to the code's own address** (`web/phone/pairing.rs`), not a `POST`: the app's core has `tokio-tungstenite` and no HTTP client. Before it upgrades the server answers `426` without an upgrade, `400` for a bad key or version and a plain `403` for a wrong, spent or expired code (a cheap check that spends nothing). After the upgrade it spends the code and saves the device; a code lost to a race closes with 1008, a failure to write `apps.json` with 1011 (not a `500`: the 101 has gone out). Then it sends one text message `{"secret": "<id>.<64 hex>"}` and closes with 1000. If the secret cannot be written and flushed, the device is removed and, only when nobody asked for a new code or cancelled it meanwhile (a generation counter that `pair`, `unpair`, `close` and every spent code bump), the held code and its count are put back, so the dialog's address still works; `delivered` in the log covers the write and the flush. The device's name is the handshake's `User-Agent` (the app should send something like `cornercase-mobile/0.1.0 (Miguel's iPhone)`), at most 120 characters, as browsers are named; Settings says `phone app` when it is empty.
- **`apps.json`** is `browsers.json`'s format and `0600`: a SHA-256 of each secret, never the secret. `Device` gained `name`, and `browser` and `name` are skipped when empty, so a browser's bytes are what they were and a file without `name` loads. Both files go through `Devices`; the one for apps has `name` and no `browser`.
- **`/cli`, one WebSocket per command** (`web/phone/cli.rs`). The secret goes in `Authorization: Bearer <id>.<secret>` (checked before anything else: `403` and `not paired` without it or with a forgotten one, logged as `no-secret` or `unknown-secret`; `426` without an upgrade). A header, because tungstenite and tauri-plugin-websocket can set one and a browser cannot, so no web page can ride the endpoint and it needs no `Origin` check; `Sec-WebSocket-Protocol` would have been the answer for a client that cannot. Never in the URL or the logs. Nothing proxies to this listener, so there is no `owner_allowed` either: the secret is the boundary.
- **The protocol** is the bridge's, one JSON object per text message, exactly one known key (`web/phone/message.rs`, byte for byte `crates/core/src/protocol.rs` of the app). In: `{"argv": […]}` first and once, within 10 s; `{"stdin": "<line>"}` (written with a `\n`), `{"stdin_base64": "<standard, padded>"}` and `{"eof": true}`. Out: `{"stdout": "<line>"}` and `{"stderr": "<line>"}`, a line without its `\n` (a `\r` stays, a last line without `\n` goes, a final `\n` adds no empty line, invalid UTF-8 becomes U+FFFD), then `{"exit": n}` exactly once and last, then a close with 1000. `n` is the command's code, `128 + signal` on Unix, `-1` when waiting failed (Windows has no signals). **One way to refuse**: a protocol error, a refused argv, a spawn that failed, a line past 16 MiB and a message past 1 MiB are one `stderr` line (control characters become spaces) and `{"exit": 2}`, `Error::WrongUsage`'s status, with the command killed when it had started. The texts are the app's (`bad message: …`, `the first message must be \`argv\``, `\`argv\` was already sent`).
- **What may run is computed, not listed** (`cli/reach.rs`): `over_cli` parses the argv with clap as `cornercase` would, then asks `reach::checked`, the same check `requests --follow -` runs on each line (`cli/requests.rs` maps its refusals to its own texts), so one boundary serves both: `Kind::There` minus the window (no command) and `start-server` (the server is already running). `--remote` and `--remote-command` are refused in any position, after `--` too (`new-tab -- echo --remote` is a false refusal, as the bridge's); `--help` and `--version` run, since clap answers them without the server (the bridge allowed them only alone). A command added later is allowed exactly when `reach::kind` says `There`, so nothing is kept in step by hand; what may run is what the running server's build knows, so a command of a replaced binary gets a usage refusal until `restart`. `requests --follow -` gives many one-shots over one connection, as over ssh.
- **The command** (`web/phone/command.rs`) is `own_binary()` (the binary that replaced this one too) with the argv, in its own process group (`Grouped`: a group on Unix, a Job object on Windows), in the home folder as ssh does for `--remote`, without `CORNERCASE_REMOTE`, `CORNERCASE_PANE`, `CORNERCASE_SERVER`, `CORNERCASE_RESTARTED` and `CORNERCASE_TIED` (the last two only the window and `update` read, and both are refused) and with `CORNERCASE_SOCKET` set to this server's socket, so it reaches this server even when `update` replaced the binary on disk with one whose default socket rules differ. A reader thread per output stream, a thread for stdin.
- **Revocation holds** (review of #838): `Context::admit` checks the secret and registers the connection in one critical section, and `Shared.accepting` (set by `listen`, cleared first by `close`) makes a connection that passed its head after a close or a forget get `403` or `503` instead of running. A port change calls `stop_listening` only: connections, their commands and the held code survive it, so the dialog's address stays valid. A connection still waiting for its `argv` sees `stopping` and is closed with 1001.
- **Pairing order**: the code is checked, the WebSocket upgraded, and only then is the code spent and the device saved. If the secret cannot be written, the device is removed and the code comes back, so a failed handshake leaves neither an orphan row nor a dead code in the dialog.
- **Stdin never stops the pump from reading**: while the command does not read its stdin and the 16-chunk channel is full, the pump keeps reading, so pings, pongs and a close are seen. Messages that cannot go in wait in a backlog of at most 4 MiB, in order; only when it is full does the pump stop reading and sleep a poll. A close behind that much data cannot be seen, so the silence clock is never paused: a command that takes no stdin for 45 s while the client keeps sending is killed, and one that takes it slowly is not, since each message read starts the clock again.
- **Limits and backpressure**: a line is at most 16 MiB (`Out::TooLong` ends the command with the refusal above), a message at most 1 MiB, 64 connections at once (counted at accept; the browser's 32 are its own), a handshake head 10 s in all, the TLS handshake included (one deadline for the whole head, not per read, so a client trickling bytes cannot hold a place). Output waits in a queue bounded in bytes (4 MiB; one line bigger than that goes when it is empty) and the pump writes only while tungstenite has nothing left to flush, so a client that stops reading fills the socket, the queue and the pipes, and the child blocks on its own writes while the server's memory stays flat. Worst case per connection: 4 MiB of queue, two lines being read (2 × 16 MiB) and one frame in tungstenite (a 16 MiB line JSON-escaped six times is 7 × 16 MiB, `max_write_buffer_size`), plus rustls' own buffers over TLS (its plaintext and record buffers, tens of KiB). Over TLS a read does not wait on a pending encrypted write, so, as in plain, an app that stops reading is still heard.
- **Liveness**: a control Ping every 15 s; 45 s without hearing anything (text, ping, pong or close) kills the command and its group. A close or a broken link does too. When the leader exits, both streams are read to the end; a grandchild that keeps a pipe open gets the group killed after 2 s, so the `exit` always comes after every line.
- **Stopping**: when the server stops (`App::stop_background`, before the clients leave), or the access is turned off (`close()`), every command is killed and its connection is closed with 1001 and no `exit`; the app tells that from a finished command. The 1001 close (#861) writes the frame, shuts the write side, leaves the list `close()` waits on, then reads and discards what the app still sends until it closes, for at most `Limits::linger` (2 s), and only then drops the socket. On Windows a socket closed with bytes it never read, or receiving bytes after it closed, is reset, and the reset makes the peer lose what it had received but not read: the frame went missing on Windows CI, while Linux and macOS deliver queued data before the reset. The exact unread bytes in the failing run were not identified; the order is pinned by a test on every OS. The exit and refusal closes already waited for the app's close reply while registered; the 1001 close did not, to keep `close()` fast, so it drains after leaving the list and `close()` waits as long as before. The server stopping exits without waiting for the drains: its frames and FIN already went out. Forgetting an app (`Phone::forget`, Settings or `config remove app.ID`) shuts its streams down, so its pumps see a broken link and kill their commands; its secret then gets `403`. A change of port only rebinds: connections made stay up.
- **Where it listens** (`app/phone_app.rs`, `host/network.rs`): only while `phone_app` is on, on every address of the computer's interfaces that is a LAN address (IPv4 private: 10/8, 172.16/12, 192.168/16) or Tailscale's (100.64.0.0/10, `fd7a:115c:a1e0::/48`), on `phone_app_port`, one listener per address, polled by one accept thread. Everything else is out: loopback, link-local, the wildcards, multicast, other ULAs, IPv4 mapped into IPv6, public addresses. The route order is LAN before Tailscale, then by address, without duplicates. `App::sync_phone_app` reads the interfaces every 2 s (the `machines::wake` rhythm) and `Phone::listen` keeps the listeners whose address is still there and binds the new ones, so a network that comes or goes is followed without scanning again. A bind that fails is retried at the next read and is not retried with a wait (the browser's `bind` waits up to 1 s for the port; here it would stall the app's tick every 2 s while a port is taken); the code never holds an address nothing listens on. Each change of the phase, routes included, moves `config.revision` (see Settings › The revision). Phases: `Listening` (even when one address failed), `NoAddress` and `Failed(why)` (every address failed: the port is taken). `NoAddress` is not a refusal for `config pair app`, as Tailscale starting is not one for browsers; `Failed` is `unavailable` and `off` is `conflict`.
- **The addresses come from `if-addrs`** (the crate the bridge used; it adds one small crate, with `libc` and `windows-sys` already in the tree). The alternative, `host::network`'s UDP-connect probe toward the default route and Tailscale's `100.100.100.100`, needs no dependency, but it sees one LAN only (not Ethernet and Wi-Fi together) and can take an exit node's address for the LAN. A hand-written list of interface names was the bridge's first try and is rejected for the same reasons. The interface's up or down state is not read, as the bridge did not.
- **`CORNERCASE_PHONE_ADDRESSES`**, a comma-separated list of IPs, replaces the interfaces and skips the eligibility rules, for the e2e tests and for trying the listener on one computer (like the bridge's `--loopback`). Not in the website's docs.
- **Risks the bridge accepted and this keeps**: plain `ws://` is still answered for the apps paired before #960 (their secret and commands cross the Wi-Fi in clear; over Tailscale WireGuard encrypts them), and the pin protects only an app that pins: one that accepts any certificate gets encryption without knowing whom it talks to; carrier NAT (100.64/10 counts as Tailscale's range), a VPN in 10/8 and VM bridges count as a LAN; a LAN peer can hold handshake places for 10 s each; the other devices of a shared tailnet reach the port, and only a paired secret gets in.
- **Settings and the socket** (a feature reaches external clients in the same change): `phone_app` through `config get|set`; each paired app as an `app.<id>` entry of `config`'s `connections` (`kind` `app`; an older reader gets `other`), removed with `config remove app.<id>`; the code through `config-pair` with the key `app` (see Commands for scripts and agents › Pairing a phone); the addresses through `app-routes`, an operation of its own that `config pair app --routes` runs. It is one request where the issue wanted none: an operation was needed to ask the server for the addresses it listens on now, and a `routes` field on `config-pair` would have made one key of a stream operation answer once, and `requests` lines refuse it. An addition never raises `CONTRACT`; an older server refuses the name. The feature `cli-endpoint` in `contract --json` tells a client the server serves `/cli`; there is no CLI check, since a phone cannot read the contract before it reaches `/cli`: it is for clients that come another way. `cli-tls` (#960) says the listener speaks TLS, the code is `wss://…&fp=…`, `app-routes` answers `fingerprint` beside `routes` (empty, so left out, never while listening) and `config-pair` takes `new_certificate` with the key `app` (`malformed` with another key, `conflict` while the access is off, before anything is replaced); `config pair app --new-certificate` checks it first (`client::use_cli_tls`), so an older server says it cannot rather than ignore the field. `--routes` prints one `HOST:PORT` per line as before, since scripts read it by line; the fingerprint comes with `--json`.
- **The dialog** is the browser's (`Overlay::PhoneAppCode`, drawn as `ui::Overlay::Remote` with the title `Phone app`): the QR code, the address, two lines and ` done `. When an app pairs with a code the dialog held, it closes and the toast says `a phone app connected`, as for browsers. Its lines come from `App::app_shown`, the same function `config pair app` follows, so the two cannot drift. `More › remote…` and the green `●` stay the browser's: a connected phone app does not light it, though an app can type into every shell as a browser can (a candidate follow-up).
- **Logs** (target `web`): `phone app paired device name delivered tls`, `phone app command started command device pid tls`, `phone app certificate made|loaded fingerprint`, `phone app certificate replaced fingerprint forgotten`, a warning when the file could not be read, and at debug `phone app TLS handshake failed error`, `phone app command ended command code why` (`exited`, `closed`, `lost`, `silent`, `refused`, `stopped`), `phone app forgotten device`, `refused a /cli connection reason`, `refused a pairing code`. `command` is the first word (`plugin <action>` for a plugin), cut at 80 characters. **Never**: the secret, the code, the certificate's key or the file's text, the argv past its first word, input or output.
- **Per OS**: the child's group is a Job object on Windows, which has no signals, so an exit code is the code as it is; the name is `COMPUTERNAME`; the firewall asks once for private networks on Windows, and macOS' application firewall may ask for a debug build, and again after each rebuild. The in-crate tests of the listener run on every OS (`web/phone/tests.rs`, with the fake program); `tests/e2e/phone.rs` is Unix only, as every e2e test.
- **Checked**: unit tests for the messages, the code, the lines, the queue, the address rules and the auth file; in-crate tests of the listener with a fake `cornercase` (pairing, `403`, the argv, stdin, refusals, close, silence, backpressure, forgetting, 1001 and the order of its close (frame, end of stream, held until the app closes), following the addresses); the same listener over TLS with a client that pins the fingerprint (`web/phone/tests/tls.rs`: pairing and a command with a clean `close_notify`, another pin refused, one certificate on every route, backpressure, output while the command still runs, the 1001 close, a stalled or garbled handshake, a request sent a byte at a time, a new certificate, one that cannot forget the apps and one that cannot be written); the certificate's file (`web/phone/tls/tests.rs`); app and control tests of the settings, the dialog and the requests; e2e tests with the real binary, over TLS (a client that trusts only the certificate in the file, whose SHA-256 is the code's `fp`) and in clear, the same `fp` after a restart, and `--new-certificate`. **Not tested**: the rollback of a pairing whose secret cannot be delivered (a client cannot fail the delivery reliably). **Not checked live**: `openssl s_client` against a debug build and a `tcpdump` of the real app over TLS (the app does not speak TLS yet), the real app (cornercase-mobile's own task) on a simulator, an iPhone over the LAN or Tailscale, a Windows firewall prompt, and a computer with Tailscale joining or leaving while the listener is on.
