# Worktrees

Code: `git/worktree.rs`, `app/worktrees.rs`, `app/machines/acting/dialog.rs`

- Only when the project folder is a repo root. The name is the branch; the slugged name is the folder, under `<worktrees folder>/<repo>/<slug>` (`~/.cornercase/worktrees` by default). `git worktree add` runs on a thread and answers with an `AppEvent`.
- Every linked worktree of the repo shows up, also ones created outside cornercase (`App::refresh`, throttled to once a second). A worktree workspace with no tabs goes when git no longer lists it (`sync_worktrees` compares with `git::linked_worktrees`, read from `.git/worktrees`), not only when its folder is gone (#367): a `git worktree remove --force` that failed half way and a `git worktree prune` left a folder with a `.git` file pointing at a pruned gitdir, so the row stayed for good, `remove` failed with `is not a working tree` and put it back, and `close --workspace` only stopped its shells. The leftover folder stays on disk: git cannot delete it, and deleting it from cornercase would have to ask first, which was left out. A row being removed is kept, as before, and one with tabs stays until they close. Only a missing `.git/worktrees` counts as an empty list (`git::registered_worktrees`): any other failure to read it (a file in its place, no permission) keeps every workspace and adds none for that round, with one `WARN` per project until it reads again (`Upstream::unlisted`), since dropping every tabless worktree because a folder could not be read would lose rows git still has.
- Removing asks first (from the row's ` × ` or the Worktrees dialog; an agent's **Close agent** never removes a worktree, see Agents section), runs `git worktree remove` (`--force` after a "remove anyway") and keeps the branch unless the ` also delete the branch ` box of the Worktrees dialog is ticked (the Worktrees dialog can remove several worktrees at once, and their branches when asked, see Worktrees dialog). The worktrees a flow run gave its roles (#313, see Flows) go with the run's workspace: the check, the teardown and the removal cover each of them, and none is removed alone while its run lives.
- **Removal runs in the background** (#98): deleting a checkout with `node_modules` or a `target/` folder takes seconds, and the dialog used to stay open (`removing…`, unclosable) until git finished. Opening the dialog runs `git status --porcelain` on a thread (`git::worktree::changed`, `AppEvent::Worktree(WorktreeEvent::Checked { … })`), which is what makes `git worktree remove` refuse, so a worktree with changes says so at once and offers **remove anyway** before anything stops. Only an explicit clean answer counts as clean: a git status that fails (or a job that panics) counts as changes, so the shells keep running unless the user confirms **remove anyway**. Confirming closes the dialog (`Overlay::RemoveWorkspace`'s `Check`: `Running`, `Confirmed` when confirmed before git status answers, which shows `checking…` and goes on by itself when the answer is clean, then `Clean` or `Changed`, the latter being what offers **remove anyway**; `Esc` always closes it). The workspace becomes `Phase::Removing(label)`: its shells are stopped first, since an agent or a dev server would keep writing into a folder being deleted, and that is why the check comes before; the view steps off it to the nearest open workspace (`Project::step_off`), as closing does. `App::start_removal` is the one place that starts it, and only on an `Open` workspace, so a dialog and a command racing on one worktree start one removal. The phase keeps the label because a checkout git is deleting has no branch left to read: the row would turn into `default` halfway. Its row stays, dimmed, with `removing…` where `↓n` goes, without `×` or `+ Tab`; `App::workspace_hit` and `App::tree_hit` drop hits on it, so left clicks and right-click menus ignore it in every layout; search and the issue places list only `Workspace::open` ones. `sync_worktrees` keeps it even once its folder is gone, so the row does not vanish and come back while git cleans up. Git's answer drops the row with a `removed <name>` toast, or puts it back (`App::settle_removal`), without its tabs, with git's message in a toast; opening the dialog again checks again and offers **remove anyway**. Several removals can run at once. Checking at confirm time instead of on open was rejected: the dialog would need a busy state again. A server that stops meanwhile leaves `git` to finish on its own; `sync_worktrees` brings the worktree back if its folder survived.
- **Locked worktrees**: The removal check reads whether the worktree is locked (`git::worktree::lock`: `git rev-parse --absolute-git-dir`, then its `locked` file, whose text is the reason, as gitrepository-layout documents), since `git worktree remove` refuses a locked worktree even with `--force`, and that refusal used to come after the shells had stopped. Claude Code locks the worktrees it creates (`claude session <name> (pid N start …)`) and unlocks them only when it exits cleanly, so a ` restart now ` that kills it leaves the lock behind. A locked worktree's dialog names the reason and, when the reason names a pid (`git::worktree::Holder`), whether that process still runs (shown only: a pid can be reused, so it never decides anything), and its button is **unlock and remove** (`git worktree unlock`, then `git worktree remove`; the unlock runs only if the lock is still there, since a Claude Code in the workspace may have released it when its shell was stopped and `git worktree unlock` fails on an unlocked one; `--force` is added when it also has changes). A lock found after confirming early (`checking…`) stops there, like changes do. Unlocking silently when the pid is gone (it depends on Claude Code's undocumented format) and `--force --force` on **remove anyway** (which would skip locks under a button that only speaks of changes) were rejected. `cornercase close --remove-worktree` unlocks only with `--unlock` (#335), the command's **unlock and remove**: without it, with or without `--force`, it answers an error naming the reason, `--unlock` and `git worktree unlock <path>`, before anything stops; `--force` waits for the same check, and `--check` says first what the dialog shows (see Arranging the session).
- `cornercase close --remove-worktree` still answers once the worktree is gone and takes the same path: it checks first and answers an error, stopping nothing, when the worktree is locked or, without `--force`, has changes; then it stops the shells and removes, and a refusal puts the row back. Every command that names a workspace (`close`, `new-tab`, `start`, `focus`, `rename`) refuses one being removed or closed (`usable_workspace`): a tab opened there would run in a folder being deleted.
- **A machine's worktree** (#544, `app/machines/acting/dialog.rs`; the asking is Remote windows › Acting on a machine's workspace): the `×` of a machine's workspace with a worktree opens the same dialog, built from the same pieces (`removal_question`, `removal_view`, `removal_submit`, `lock_message`), naming the machine (`… on vps`) and its folder with the machine's home as `~`. The check is the machine's `removal-check`, so changes, a lock and whether its pid runs, its roles' worktrees and the teardown are what that machine sees; confirming sends `close` with `remove_worktree`, plus `force` after **remove anyway** and `unlock` after **unlock and remove**, and the machine stops the shells and removes as for its own window. Its row says `removing…` until the snapshot drops it, with a `removed <name> on vps` toast, or comes back with the machine's message in a toast. The machine's `warning` (a failed teardown, a role's worktree it could not remove) is not dropped: the toast is the one a removal here gives (`worktrees::removed`), `removed <name> on vps, but its teardown failed: …` with the bug icon, through `hide_destination` like every text from there. **A check that fails closes the dialog** with a toast saying why and that nothing was removed (a machine down, a cap, a refusal such as a role's worktree whose run lives): here a failed `git status` offers **remove anyway**, but there the removal would fail the same way, and a blind `force` on a machine was not wanted.
- `.worktreeinclude`: files matching it **and** ignored by git are copied into a new checkout, before the project's setup runs (see Worktree setup). Matching is delegated to git (`ls-files`, `check-ignore`).
- **Commits to pull** (`↓n` at the end of a workspace row, before the `×`): every 3 s a thread per project counts `HEAD..@{upstream}` in each workspace and answers with `AppEvent::Worktree(WorktreeEvent::Behind { … })`; it runs `git fetch --all` first once `fetch_minutes` (default 5, 0 turns all of it off) have passed. One thread per project at a time. Git never prompts (`GIT_TERMINAL_PROMPT=0`, empty `GIT_ASKPASS`, `SSH_ASKPASS_REQUIRE=never`); failures count as 0.
- **Inherited repository variables (#252)**: `git::worktree::command`, behind `git`, `git_within` and `git_within_env`, removes `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_COMMON_DIR`, `GIT_NAMESPACE` and `GIT_CONFIG_PARAMETERS` (`drop_inherited`, which the plugin installer's git also calls). A server started from a git hook or by another git command inherits them, and `git -C <dir>` does not override them, so every call would inspect the hook's repository instead of the workspace's. `git_within_env` applies its own pairs after the removal (the merge check sets `GIT_INDEX_FILE` and `GIT_OBJECT_DIRECTORY` itself, see Shared files). Tests check the built command, not the process environment, which parallel tests share. Config injected the same way is dropped too: `GIT_CONFIG_COUNT` and every `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>` present (`injected_config`), since `core.worktree` set so would redirect `-C`. `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` are kept on purpose: they name the user's own config files (identity, aliases, credential helpers) that cornercase's git calls need, they come from the user's setup and not from a parent git process, and stripping them would change behaviour for everyone.
