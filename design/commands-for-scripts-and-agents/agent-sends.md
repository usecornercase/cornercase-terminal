# Commands for scripts and agents › Gemini, Cursor and Copilot sends, and `todo send`

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- **Gemini sends**: confirm ordinary `send --enter` from a real user's parseable session timestamp. Reading a restored history must not count as a fresh prompt. Gemini queues input in memory while working and joins it with blank lines when it takes it. Share Codex's `holds_prompts`: extend the 10 s confirmation clock while working or waiting, bounded by the request's `--timeout`. Trimmed text starting with `/`, `?` or `!` is local input and may write no user record. Return after Enter without confirmation, avoiding spurious failures and duplicate commands. `--wait` still needs the usual reaction; inspect commands that open dialogs or leave status unchanged with `read`. Enter without text still confirms, because cornercase cannot know what is already in the composer.
- **Cursor sends**: `send --enter` is confirmed from a prompt the store records (`Pane::prompted`, a turn whose message was not there before), timed by the user message's `started_at_ms` when present and by the moment it was read otherwise, and fails `CONFIRM_WITHIN` after the Enter like the others. Cursor holds a prompt typed while it works, so it shares `holds_prompts`. `/` and `!` lines return after Enter without a confirmation. It has no input-box check: the screen was not seen live, and a check that refused every send would be worse than none. `read --last-message` reads the store (`Record::Cursor`), skipping thinking, tools and shell turns. All of this rests on the unverified store layout (see Context use): a different layout makes the confirmation fail and the last message unavailable, visibly, never a wrong answer.
- **Copilot sends**: `send --enter` is confirmed from a `user.message` (the prompt rule of Context use) whose event timestamp is at or after the request, and fails `CONFIRM_WITHIN` after the Enter like the others. Copilot holds a prompt typed while it works and writes it, with `delivery: "queued"`, when it takes it, so it shares `holds_prompts`. `/` and `!` lines and a lone `?` return after Enter without a confirmation (live: none of them writes a `user.message`); `? text` is a prompt. There is no dialog check: Copilot's input box was not studied, and a check that refused every send would be worse than none. `read --last-message` and `wait` read the session events and the presence file (`Record::Copilot`).
- Gemini gets no input-box check. Its `>` marker also appears in picker help, YOLO/shell/search modes change it, and narrow or hidden footers change the layout. No shape proved as distinctive and self-calibrating as Claude Code's rule and composer. A fragile check could refuse every send or accept a picker. Refuse the real waiting title, confirm ordinary prompts from the record, and have scripts read other dialogs before sending.
- Gemini's last-message reader shares the bounded backwards iterator. Keep the last version of each id and stop at `$set.messages` boundaries, so superseded replies and removed history cannot reappear. Return the newest Gemini text with its own timestamp; omit thought parts and synthetic summary/context replies without a model, which are not shown as an answer.
- **`todo send ID`** sends a TODO item's text as `send --enter` does: `todo_send_request` builds a `SendText` from the item and hands it to `send_request`, so the target defaults (`--pane`, `--tab`, else the caller's pane, else the shown one), every refusal and the confirmation that the agent recorded the prompt are the same code, not a copy. The item is checked off in `refuse_or_answer` once that confirmation came (`Requests::todo_sends`), so a refused or unconfirmed send leaves it pending, prints the reason and exits 1; the answer is `send`'s plus `todo` and `checked`, printed as `sent todo 3 to pane 5`; when the send cannot be confirmed (`App::confirms`) it is still sent, the item stays pending, the answer has `unconfirmed: true` and exit is 0, printed as `sent todo 3 to pane 5, but cornercase cannot tell whether the agent took it, so it stays to do`. A done item is refused (uncheck it first), an unknown id is `not-found`. It is a request name of its own, `todo-send`, so an older server refuses it by name: as a field of `send` (`todo: 3` with no text) an older server would drop the field, send nothing and leave the item as it was, and as a variant of the `todo` request it would answer a parse error rather than the refusal, and `todo`'s arms answer at once where a send waits for the Enter and the confirmation. The TODO panel sends the same request (see TODO panel). The log has the id and the target (`todo=send id=3 pane=5`), never the text.
