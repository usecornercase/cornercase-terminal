# Worktrees: the list, sizes and build folders

Code: `control/worktrees.rs`, `app/control/worktrees.rs`, `cli/worktrees.rs`, `cli/args/worktrees.rs`, `worktrees/fill.rs`, #485, #536

- **Three operations**, `worktree-size`, `free-builds` and `worktrees` (indexes 108, 109 and 112 of `Command::NAMES`), under one CLI noun: `cornercase worktrees list`, `size` and `free-builds`. `size` and `free-builds` do what the dialog does (see Worktrees dialog › Size, Build folders and Free builds); the feature `build-folders` tells a client that `config project` takes `builds`, and the operations show by themselves in `contract`. `CONTRACT` stays 1: everything is additive. The list is `worktrees`, described below; removing the chosen worktrees is not a request yet (see Worktrees dialog › External clients).
- **The target** is one worktree: `workspace` (a workspace with a worktree of its own; a plain workspace shares its project's folder and answers `conflict`), `path` (any linked worktree, open in cornercase or not, resolved with `discover::linked`, so the main checkout, a submodule or a `--separate-git-dir` checkout answer `conflict`, as the dialog never lists the main checkout), or neither (the window's workspace, else `conflict`). Both given is `malformed`. The CLI adds `--worktree BRANCH`, resolved through `status` as `ports` does. The project's list of names is the repository's (`projects.<folder>.builds`), also for a closed project's worktree.
- **`worktree-size`** answers `path`, `bytes`, `builds_bytes`, `builds` (`path` relative to the worktree, `bytes`) and `nested` (git checkouts found inside build folders). It runs on a job, answered as a `Stage::Reading` pending, because a walk of a big tree takes a second or more.
- **`free-builds`** answers `path`, `check`, `bytes`, `folders`, `kept`, `failed` (`path`, `error`) and `running` (names of the programs in the worktree, shells left out). `check` measures and answers what would go and what runs, and deletes nothing. Without `force` it refuses with `conflict` while a program runs in the worktree (the panes' own, found from the workspace, and every process of the user with its cwd inside, through `scan::outside`) or a build folder holds a git checkout, naming them: the dialog warns and lets the person go on, but a script cannot read a warning, as `close --remove-worktree` refuses changes without `--force`. `force` goes on. The deletion is the dialog's (list again, delete what is chosen and still listed, measure again).
- **Exit 3** (the partial-answer rule above): the answer is printed whole and some folder failed or was kept, so a program can tell it from a refusal (exit 1).
- **Nothing in `status` or `watch`**: a size costs a walk of the whole tree, and `status` and `watch` are cheap snapshots; the same reasoning as `ports`.
- **The check sees background programs**: besides each pane's foreground program, the job lists every process whose cwd is inside the worktree, the panes' own shells' children included (`sleep 47 &` at a prompt counts), so a build left running in the background refuses without `--force`.
- **The check is a snapshot**: the programs running in the worktree are read once, before the job; one started before the deletion is not seen (the same window as the dialog's). The deletion keeps and names any folder that is no longer a plain folder of the worktree or sits on another filesystem (see Worktrees dialog › What freeing does).

The list (#536):

- **The list** is one answer, `{"worktrees": [...]}`, not a stream: a script wants it whole, and a stream would add a format for no reader that needs partial rows. The rows come in the dialog's safe order (leftovers, then merged, then the rest, the oldest first), each with its facts, a verdict `safe` and `risks`.
- **The dialog's discovery and checks**: the request runs the dialog's discovery job (`ListFor::Request`, so a discovery that panics answers `failed` instead of an empty list) and then one job, `worktrees::fill`, that does the scans, the walks and the process check at the dialog's limits (4 at once and 30 s, 2 at once and 120 s). It does not copy the dialog's scheduler and never touches its queue: a request never marks the dialog's scans stale and never waits behind them, so a dialog and a request together run at most 4+4 scans and 2+2 walks. A thread given up on keeps running until git or the walk ends, as the dialog's jobs do. A prunable entry with a branch has its commits counted, as the dialog's confirmation rescan does, because a script has no confirmation step.
- **Sizes by default**: the issue lists the size among a row's fields and the dialog always measures, so one call gives the whole picture. A walk takes seconds per worktree, so `--no-sizes` (`"sizes": false`) skips them; a client that wants rows early asks without sizes and then `worktree-size --path` per row.
- **`safe` and `risks`**: `safe` is `!Row::risky()`: removing it loses no uncommitted file and stops no program. Commits not pushed do not make a row unsafe, since removal keeps the branch; they matter only when deleting the branch too, unless it is `merged` (the dialog's yellow header against its red line). `risks` are the confirmation's lines for that row, from `App::risk_list`, the function the dialog uses, so the words never drift; the fallback `nothing uncommitted or unpushed` and the role sub-lines are left out (each role's worktree is its own row, with `run_role`).
- **Read again at the answer**: a listing can take a minute and a script acts on its ids, so `project`, `workspace`, `running` and `removing` are read again when the answer is built.
- **A reader gone before the list**: a request whose client left before discovery answered does no scans and no walks. Once `fill` started it runs to its end, as the dialog's jobs do.
- **No feature string**: a new operation is detected through `contract`'s `operations`, as `ports`, `processes`, `worktree-size` and `free-builds` are, and an older server refuses the name. A feature string is for fields or behaviour inside an existing request.
- **Exit 3**: some row has `error` (the check failed or was given up) or `size_error`; everything is printed first, as `free-builds` does.
- **`project`**: the default is every worktree on disk, like the footer button; `--project ID` is the project menu's **worktrees**. A project not at a repository's root answers `conflict`, an unknown id `not-found`. There is no default to the caller's project.
