# Worktrees: the list, sizes, build folders and removing

Code: `control/worktrees.rs`, `control/worktrees/remove.rs`, `app/control/worktrees.rs`, `app/control/worktrees/remove.rs`, `cli/worktrees.rs`, `cli/worktrees/remove.rs`, `cli/args/worktrees.rs`, `worktrees/fill.rs`, `worktrees/remove.rs`, #485, #536, #671

- **Four operations**, `worktree-size`, `free-builds`, `worktrees` and `worktrees-remove` (indexes 108, 109, 112 and 119 of `Command::NAMES`), under one CLI noun: `cornercase worktrees list`, `size`, `free-builds` and `remove`. `size` and `free-builds` do what the dialog does (see Worktrees dialog › Size, Build folders and Free builds); the feature `build-folders` tells a client that `config project` takes `builds`, and the operations show by themselves in `contract`. `CONTRACT` stays 1: everything is additive. The list is `worktrees` and removing is `worktrees-remove`, both described below.
- **The target** is one worktree: `workspace` (a workspace with a worktree of its own; a plain workspace shares its project's folder and answers `conflict`), `path` (any linked worktree, open in cornercase or not, resolved with `discover::linked`, so the main checkout, a submodule or a `--separate-git-dir` checkout answer `conflict`, as the dialog never lists the main checkout), or neither (the window's workspace, else `conflict`). Both given is `malformed`. The CLI adds `--worktree BRANCH`, resolved through `status` as `ports` does. The project's list of names is the repository's (`projects.<folder>.builds`), also for a closed project's worktree.
- **`worktree-size`** answers `path`, `bytes`, `builds_bytes`, `builds` (`path` relative to the worktree, `bytes`) and `nested` (git checkouts found inside build folders). It runs on a job, answered as a `Stage::Reading` pending, because a walk of a big tree takes a second or more.
- **`free-builds`** answers `path`, `check`, `bytes`, `folders`, `kept`, `failed` (`path`, `error`) and `running` (names of the programs in the worktree, shells left out). `check` measures and answers what would go and what runs, and deletes nothing. Without `force` it refuses with `conflict` while a program runs in the worktree (the panes' own, found from the workspace, and every process of the user with its cwd inside, through `scan::outside`) or a build folder holds a git checkout, naming them: the dialog warns and lets the person go on, but a script cannot read a warning, as `close --remove-worktree` refuses changes without `--force`. `force` goes on. The deletion is the dialog's (list again, delete what is chosen and still listed, measure again).
- **Exit 3** (the partial-answer rule above): the answer is printed whole and some folder failed or was kept, so a program can tell it from a refusal (exit 1).
- **Nothing in `status` or `watch`**: a size costs a walk of the whole tree, and `status` and `watch` are cheap snapshots; the same reasoning as `ports`.
- **The check sees background programs**: besides each pane's foreground program, the job lists every process whose cwd is inside the worktree, the panes' own shells' children included (`sleep 47 &` at a prompt counts), so a build left running in the background refuses without `--force`.
- **The check is a snapshot**: the programs running in the worktree are read once, before the job; one started before the deletion is not seen (the same window as the dialog's). The deletion keeps and names any folder that is no longer a plain folder of the worktree or sits on another filesystem (see Worktrees dialog › What freeing does).

The list (#536):

- **The list** is one answer, `{"worktrees": [...]}`, not a stream: a script wants it whole, and a stream would add a format for no reader that needs partial rows. The rows come in the dialog's safe order (leftovers, then merged, then the rest, the oldest first), each with its facts, a verdict `safe` and `risks`.
- **The dialog's discovery and checks**: the request runs the dialog's discovery job (`ListFor::Request`, so a discovery that panics answers `failed` instead of an empty list) and then one job, `worktrees::fill`, that does the scans, the walks and the process check at the dialog's limits (4 at once and 30 s, 2 at once and 120 s). It does not copy the dialog's scheduler and never touches its queue: a request never marks the dialog's scans stale and never waits behind them, so a dialog and a request together run at most 4+4 scans and 2+2 walks. A thread given up on keeps running until git or the walk ends, as the dialog's jobs do. A prunable entry with a branch has its commits counted, as the dialog's confirmation rescan does, because a script has no confirmation step.
- **Sizes by default**: the issue lists the size among a row's fields and the dialog always measures, so one call gives the whole picture. A walk takes seconds per worktree, so `--no-sizes` (`"sizes": false`) skips them; a client that wants rows early asks without sizes and then `worktree-size --path` per row.
- **`safe` and `risks`**: `safe` is `!Row::risky()`: removing it loses no uncommitted file and stops no program. Commits not pushed do not make a row unsafe, since removal keeps the branch; they matter only when deleting the branch too, unless it is `merged` (the dialog's yellow header against its red line). `risks` are the confirmation's lines for that row, from `App::risk_list`, the function the dialog uses, so the words never drift; the fallback `nothing uncommitted or unpushed` and the role sub-lines are left out (each role's worktree is its own row, with `run_role`).
- **Read again at the answer**: a listing can take a minute and a script acts on its ids, so `project`, `workspace`, `running` and `removing` are read again when the answer is built.
- **A reader gone before the list**: a request whose client left before discovery answered does no scans and no walks. Once `fill` started it runs to its end, as the dialog's jobs do.
- **No feature string**: a new operation is detected through `contract`'s `operations`, as `ports`, `processes`, `worktree-size` and `free-builds` are, and an older server refuses the name. A feature string is for fields or behaviour inside an existing request.
- **Exit 3**: some row has `error` (the check failed or was given up) or `size_error`; everything is printed first, as `free-builds` does.
- **`project`**: the default is every worktree on disk, like the footer button; `--project ID` is the project menu's **worktrees**. A project not at a repository's root answers `conflict`, an unknown id `not-found`. There is no default to the caller's project.

Removing (#671):

- **Why**: `worktrees list` shows every worktree on disk, those of closed projects and the leftovers too, and a client could not clear those rows: `close --remove-worktree` needs an open workspace and keeps the branch. A client running `git worktree remove` and `git branch -D` itself has no teardown, no second look and none of the rules on which branch goes, and on another machine needs an ssh of its own: that reimplements the server, which #345 rules out.
- **A new operation**, `worktrees-remove`, so an older server refuses it by name; no feature string, as for `worktrees`. The folders are `paths`, the flags `check`, `force`, `unlock` and `delete_branch`, every field written (strict fields), nothing in `status` or `watch`. `--delete-branch` on `close` was rejected: an older server would drop the field and keep the branch, and `close` only reaches an open workspace.
- **Only what the listing knows**: the request runs the dialog's discovery (`discover::Listing`, shared with the dialog and `worktrees`, so an open project's own folder is left out the same way) and compares each path with it in canonical form (`worktrees::remove::named`). What it does not know is refused for that folder, in words, and nothing is done to it: a path that is not absolute (it would resolve against the server's folder), a main checkout, a project's own folder, a plain folder, a folder inside a worktree or above one, nothing at all. After that the path a client gave is never used again, only the row's, so no client text reaches `git` or `remove_dir_all`. A folder that is gone has no canonical form, so `real_place` canonicalises its deepest parent that exists: a prunable entry is named as `worktrees list` prints it or through a link to its parent.
- **Links**: a link to a listed folder names that folder, as `free-builds --path` takes it, and removes the folder, not the link; a link to anything else resolves to something unlisted and is refused; the listing itself skips links in the worktrees folder (see Worktrees dialog). Just before the removal starts, and again in `remove::remove`, `still_listed` refuses a folder that became a link, or whose canonical form changed since it was listed (a parent swapped for a link), so a teardown or a deletion never runs at a link's target; the deleted folder's own links are not followed (`remove_dir_all`). A canonical form that cannot be read at all does not refuse: some Windows drives fail `GetFinalPathNameByHandle`, the listing kept the path as it was, and the dialog must go on working there. This matters because of what git does (checked 2026-11-06 on git 2.53): `git worktree remove` through a folder that became a link passes its validation (the target's `.git` file still points back), walks the link, empties the target, then fails on `rmdir`. A worktree moved away with a link left behind is listed at its target, and git would do the same at once, so `recorded_at_a_link` refuses it for that folder, from the entry's own `gitdir` file; the person moves it back or runs `git worktree repair`. `remove::remove` is the dialog's too, so its closed rows gain `still_listed`; its open workspaces and a worktree already recorded at a link go on as they did. A flow role's folder is not checked this way: cornercase made it, and its run's workspace is what is named.
- **The second look**: a job (`worktrees::fill`, at the dialog's limits, `names: None` so no sizes) scans the named rows and the worktrees of their flow roles, and looks for processes, as the dialog's confirmation does. Its words are the dialog's: `second_look`, split out of `confirm_lines` (which keeps the styles), gives each line with whether it is a red one, so `lines` and `lost` in the answer are what the confirmation would show. `lost` is always answered, whatever `delete_branch` says, so a client drawing its own ` also delete the branch ` needs one check; `lines` follows the flag, as the box changes them (`no branch is checked out, so none is deleted`). `worktree` is the row `worktrees` would give (`WorktreeInfo`), so a client has the same facts in the same shape, and `live`, `running` and `removing` are read again when the look answers, since it may take a minute.
- **What it refuses, and what needs a flag**: what the dialog cannot tick is refused whatever the flags (`Row::tickable`, and the words of `remove_one` and `role_owner`): a worktree of a role of a live run, one being removed or closed, one whose build folders are being freed (`freeing_path`, since `Frees` only had the row's flag while the dialog stayed open). The rest goes as the dialog goes (`remove_one`, `remove_open`, `remove_closed`, the same `Pending`), with `force` and `unlock` instead of the dialog's `ALL`, so git stays the last guard: a file written after the look stops `git worktree remove` without `force`. The gate is `close --remove-worktree`'s, widened where a script cannot read what a person reads (`free-builds` made the same call): without `force` a folder is refused when `confirm::stake` names something: uncommitted files, a scan that failed or gave up, programs of its workspace, processes outside or in another tab, the folder itself when its repository is gone or git no longer knows it (its files cannot be checked), commits on no branch (a detached `HEAD` holding commits that nothing else may hold, which `git worktree remove --force` would drop silently), and with `delete_branch` a branch whose commits `lost_commits` says go. Each counts for the run's roles too. A prunable entry has nothing to lose but its branch, so it needs nothing. Without `unlock` a locked worktree is refused, `force` or not, as `close` does. Commits on a branch that stays do not refuse (see `safe` above). A live flow run alone does not refuse: its agents are programs that run, and with none left nothing is lost. `needs` lists the flags a folder takes for the `delete_branch` asked, whatever `force` and `unlock` say, so a client asks once.
- **Run's roles**: a role named together with its run's workspace goes with it (`removed_with`), even a role of a live run, which alone is refused: that is what the dialog's `covered` does, and answering `refused` for a folder that went would be false. If the workspace is refused, so is the role, with its own reason. The workspace's `roles` name what goes with it.
- **One answer per path, in order**: `folders[i]` answers `paths[i]`, a folder named twice answers twice and goes once, so a client can zip them. `outcome` is `removed`, `failed` (git refused, or the folder changed; `why`), `refused` (`why`; nothing started) or, with `check`, `removable` (`needs` says what it takes). `removed` can still carry `warnings` (a failed teardown, a role that stayed, a branch `delete_branch` refused) and `kept` (the branch changed since the look), in the dialog's words. Pinned by `tests/fixtures/control/worktrees-remove/v1/`.
- **The answer waits, and the window stays out of it**: the request is one `Pending`, `Stage::RemovingFolders`, whose folders fill in as their removals end (`folder_cleaned`), through the dialog's own `git.cleanup` with `Pending::request` set. So `cleaning_path` shows them as `removing` to the dialog and to `worktrees`, a second request or a tick cannot start them twice, and rows go in an open dialog as they do for its own. What a request removes never reaches the dialog's tally (`Pending::tally` instead of `Cleanup::tally`), so it adds no toast, as `close --remove-worktree` adds none, and `finish_cleanup` waits only for the dialog's own removals, so a long teardown of a script's never delays the dialog's toast. `start_removal` is called with no key of its own: `worktree_removed` already sends a `cleaning` workspace there, and deleting its branches after it is what that path does.
- **A client that leaves**: the request's entry goes with its client at any step. Until the look has ended nothing has started, so nothing happens (`Ctrl+C` during a slow look cancels), where `close --remove-worktree` goes on; removals that started are held by `git.cleanup`, not by the request, so they run to their end, branches included, as the dialog's do.
- **Exit 3**: some folder was not removed, or its branch was kept or could not be deleted, or its teardown failed; with `--check`, some folder cannot be removed or could not be checked. A folder that only needs a flag exits 0 under `--check`, since that is an answer. Exit 1 is for the request as a whole (no folders, a stray field, a listing that panicked).
- **The check conflicts with `--force` and `--unlock`** in the CLI, as `close --check` does, since a check that seems to remove would be a surprise. On the socket `check` wins, as in `free-builds`: `needs` does not depend on them.
- **On Windows** the code path is the dialog's: a folder a process holds open makes git or `remove_dir_all` fail, and the folder answers `failed` with its words; the app tests that need no pane (closed projects, leftovers, refusals, branches, links, which `test_util::link_folder` makes junctions there, the races after the look) run there. Open workspaces, flow roles, teardowns and processes are `#[cfg(unix)]`, as every app test that opens a pane or runs a `/bin/sh` script is (Windows › Tests on Windows and CI).
- **Left out**: naming the branch expected (a client's `--check` may be older than its removal, so with `delete_branch` the branch deleted is the one this request's own look saw; without `force` a branch that would lose commits still refuses); `--worktree BRANCH` (a closed project's worktree has no workspace to look the branch up in, and `--path` is what `worktrees list` prints); a stream of outcomes (a client has the row's `removing` from `worktrees`, and the answer is one document).
