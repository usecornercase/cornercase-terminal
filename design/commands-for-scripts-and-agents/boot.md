# Commands for scripts and agents › `--boot`

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md); the contract it builds on is in A versioned contract.

- **`--boot`** on `close` and `rename` (#677), `mark` and `move-pane` (#723), `account restart` and `context` (#729), `collapse` and `expand` (#709), `send`, the one-shot `input` and `paste-file` (#795), every other command that acts on an id (#801), and the commands that only read one, `flow`'s, `go` and `clone` (#809) (`cli/args.rs`, `client/requests.rs`, `client/requests/shared.rs`): a client that aims at an id from a snapshot, above all a machine's workspace through `--remote` (Remote windows › Commands on another machine), says which run of the server the id is from, and the server compares as it acts, as it does for the window (`machines/act.rs`, which stays as it is). #723 and #729 add what a client that draws a machine's tab (#345, #545) acts with on its panes, by the ids its frames and `view` lines give: `account restart --pane` acts (a conversation moves account, a shell at its prompt is replaced), and `context --pane` starts a second `claude` on the conversation. #709 adds the folds of a client that draws a machine's agents (#345, #663, by the pane ids under its entry in `status --json`), whose counterpart in the window already goes with the snapshot's `boot` (Layout › The agents section › A machine's rows fold there). #795 adds what the same client hands those agents with, by the pane ids under the machine's entry or in its frames: a prompt (`send`), keys, text or a paste (`input`), and a picture or a file (`paste-file`); a wrong one types into another agent's input box, and the window's own typing into a machine's tab already sends the snapshot's `boot` (Remote windows › A machine's tab). #801 adds the rest of what that client acts with: it drives a machine's tab with `keys`, `held`, `input --follow`, `scroll`, `selection`, `split`, `ratio`, `resize`, `redraw` and `view-set`, and a script aims `focus`, `move`, `group style` and `delete`, `open`, `new-tab`, `new-workspace`, `setup`, `start`, `agents close`, `reopen` and `forget`, `changes viewed`, `stage`, `unstage`, `discard` and `base`, `queue add` and `edit`, `todo send`, `account add` and `login`, `worktrees free-builds`, `config project` and `plugin run` at a machine's rows. #809 adds what the same client reads a machine's tab with, by the ids its frames give: `read`, `link`, `surface` and `view`, followed with `events`, and what a script reads of a workspace (`changes`, `files`, `processes`, `ports`, `pull-request`, `issue`, `worktrees size` and `list`); `flow` edits flows and runs by a project's or a workspace's id, and `go --view` and `clone --view` move or fill a view by its id. Every form takes it, the `status` behind `--worktree` included. A wrong fold costs the least of these (it only hides or shows rows, and `expand` undoes it), but the client could neither avoid it nor say why, as the window does (`vps restarted; nothing was changed there`). Every form takes it, as every form of `close` does: they are one request, a machine's group, project and workspace ids last one run too, and a client never has to know which forms take it. Comparing the last snapshot's `boot` before sending, or asking `status` first at the cost of another ssh session, narrows the gap and never closes it: a server that restarts in that moment counts its ids from 1 again.
  - **The only requests of the CLI in the structured mode**: `client::answered` reads both shapes, and any code, since a newer server may add one, so an error's `message` is what the person sees and is the text the legacy mode would give. A command given `--boot` with `--machine` (#820) sends `contract` and `args.machine_boot` and no `boot`, so a `stale-boot` from this server or from the machine keeps its code. The other commands send `boot: None`, which is skipped, so their bytes and their answers are what they were (`responses/` and `postcard/` pin them). Reading both shapes for every request costs nothing: only a request with `boot` gets the second one.
  - **`stale-boot` exits with 4** (`Error::StaleBoot`, `main`, and `status` on a line of `requests --follow`), printing the refusal's message as `error: …`: clients branch on the code and never on the message, a command has no other way to give the code, and 1 is also a missing id, a lost connection or an unreachable machine, which call for something else than reading `status` again and aiming anew. Only a command given `--boot` can exit with it, so no client meets it unasked. Printing the code in the message was rejected (a person would read `stale-boot: this request…`, and a program would parse text), as was a `code` key on the lines of `requests --follow` alone (a one-shot command would still have nothing).
  - **It checks the feature `boot` first** (`client::use_boot`, on the link the request then takes, so one ssh connection): a server from before `boot` drops the field and acts, as the compatibility rules of A versioned contract say, so it is refused by name before anything else is sent, as is one with no `contract` at all (`missing`: `… would ignore --boot …`, with how to restart it). No new feature: nothing changed in the server. An older `cornercase` refuses the flag itself as a usage error, status 2.
  - **Every request of the command but `contract` carries it** (`Envelope`, kept as the view is: a `OnceLock` for a one-shot command, `Shared` for a line, cleared by `line_done`). So the `status` behind `--worktree BRANCH` is refused too, and a stale run says so rather than that no workspace has the branch. `contract` must not carry it: it would be refused, and its answer is what decides whether to send anything. An empty `--boot` is a usage error (`NonEmptyStringValueParser`, as for `--remote`), since an unset variable in a script should not read as a restart.
  - **Strict fields are the price of the mode**: `Close.unlock` is always written, so a server between `boot` and `close-unlock` answers `unknown-field` where the legacy mode would ignore the field. It fails by name with status 1 and nothing done, so the direction is safe, and only a command given `--boot` meets it; Remote windows › Commands on another machine rejected this mode for every request for that reason. A second feature check for it was left out: those are two days of releases in October 2026, and the message names the field. The four requests of #723 and #729 have written the same fields since their operations came (`Mark` before `boot`, #246; `MovePane`, #360; `AccountRestart`, #422, behind `account-restart`, which the CLI checks; `ContextRead`, #607), so no server with `boot` answers `unknown-field` for them, and a server older than the operation refuses it by name (status 1, nothing done). Those that have a window of releases write a field of a later operation that is always sent, so `--boot` answers `unknown-field` there, status 1 and nothing done, with no second feature check since the message names the field: `focus` (`args.reveal`, before 0.12.207), `view-set` (`args.visible`, before 0.12.133), `new-tab` (`profile` before 0.12.154, `accounts` before 0.12.159), `config project` (`args.entry.builds`, before 0.12.222; a server before 0.12.135 does not know the operation), `start` (`issue`, `source`, `profile`, `accounts`, `workspace_name`, before 0.12.160; with `--no-fresh`, which writes `fresh: false` with no feature check, also `args.fresh` to 0.13.36, as for `new-workspace --no-fresh`), `events` (`args.host` before 0.12.127, `args.notices` before 0.12.133), `surface` (0.12.122 to 0.12.211: `args.patches`, 0.12.134, and `args.popup`, 0.12.212; before 0.12.122 the operation is refused by name), `view` (0.12.125 to 0.12.132: `args.visible`, 0.12.133), `flow run` (0.12.109 to 0.12.159: `issue`, `source`, 0.12.143, `profile`, 0.12.154, `accounts`, 0.12.159, `workspace_name`, 0.12.160; with `--no-fresh` to 0.13.36; `--fresh`, `--close-when-merged` and `--free-builds` check their features first), `queue add` and `edit` (`accounts`, `repeat`, `flow`, `cleanup`, `fresh` under `args.entry`, before 0.13.37), and `input --follow` on 0.12.126 to 0.12.211 (`args.popup`: each line is refused, nothing typed, exit 3). The others have written the same fields since their operation came, which a server older than that operation refuses by name, nested keys included (`Who`, `Size`, `Point`, `FlowSpec`, `CloneFile`), the commands of #809 among them.   - **`requests --follow` needs nothing** (`cli/requests.rs`): a line's `args` go through the same `Cli` and `run_control`, so a line takes the flag, for that line only, and answers `status` 4 with the message in `error`, and the link stays (`remembered`). A `boot` key on the lines, which #677 also proposed, was rejected as a second way to say the same thing, one that would reach every command whose request nobody checked in this mode.
  - **Which commands** (#801): the commands that act on an id of the run, including `changes base`, `open --into`, `queue edit`, `group style` and `config project --project`, which the issue's list missed. `BootArg` goes on each command's own arguments or subcommand variant (`FoldArgs` for both folds, `SendArgs` for `send`, `QueueAdd`, shared only by `queue add` and `edit`, which both act), never on a struct others share (`Target`, `Create`, `Where`, `Which`, `TargetArgs`, `MachineArg`), so a command takes the flag only once `Control::boot` reads it, once its request has been checked in the strict mode against what an older server knows. `plugin run` is no `Control`, so it calls `use_boot` itself, before its revision lookup, which then carries the boot too (a stale one fails before anything runs; the view stays on the run only). With `--machine` the ids are that machine's, and this server's boot says nothing about them: `Control::machine` makes `run_control` check `machine-boot` instead of `boot`, and the run functions of `start`, `new-workspace`, `flow run` and `focus` copy the value into `machine_boot` (a usage error before #820, set on argument groups). This server's boot is not sent, since the machine is named by its name, which outlives a restart here. #809 adds the commands that only read an id (`read`, also `--last-message` with several targets, `wait`, `link`, `events`, `surface`, `view`, `processes`, `ports`, `pull-request`, `changes list`, `file`, `gap`, `shared` and `merge-check`, `files list`, `read` and `search`, `issue sources`, `list`, `read` and `people`, `worktrees list` and `size`; `worktrees list --project` too, which both issues missed), `flow`'s (`run`, `save`, `import`, `delete`, `default`, `order`, `close-when-merged`, `list`, `export`, `messages` and `files`), `go` and `clone`. Without it a client reads, or follows, whatever took the id after a restart. `SizeArgs` wraps `TargetArgs` for `worktrees size`, since `free-builds` shares it; the boot is on `ProcessesArgs` and `PortsArgs`, which their `stop` refuses (pids and ports are the system's, and `--started` guards a reused pid); `clone --list-ignored` refuses it (it needs no server); Without an id of the run, `status` (where the boot is read), `flow runs`, `hide` and `restore`, `processes stop` and `ports stop` take none. `changes shared` read `status` with `report_now`, which drops every error, so a stale boot would have read as `cannot read the workspaces` (status 1), and every line of `requests --follow` failed the same way; it reads it with `ask` now. Persistent ids (`todo done`, `queue remove`) survive restarts and take none. The wider form #723 offers, `--boot` on `requests --follow` itself so that every line of the link is refused once the server is another run, was left out: it would not reach `context`, which a client runs beside its ordered connection since a read takes 3 to 10 s (#729), and like the rejected `boot` key on lines it would be a second way to say the same thing that turns strict every request nobody checked in this mode. A `global` flag like `--remote` was rejected: the commands that run as a process of their own (`kill-server`, `logs`) or on this machine (`plugin install`) would drop it without a word, which is what the flag exists to prevent, and every request would turn strict.
  - **A stream** (#809: `events`, `surface`, `view`, `changes list`, `files list` and `read` with `--follow`, `flow messages --follow`, the long `wait`): the server compares the boot once, with the stream's first request and before routing it, so a stale boot is refused before the first line: `error: …` on stderr, status 4 and nothing on stdout, with or without `--json` (the CLI prints no JSON error object for 4, as for every command). A server that restarts while a stream runs ends it as before (status 0 when it says it stops or restarts, 1 when the connection drops), since the link holds one run, so no frame is compared. Ending a running stream with 4 was rejected: its lines were from the right run, and a 4 at the end would read as a stale id; a client reads `status` again and restarts the stream. The cross-platform test is `follow_link` in `client/requests/tests.rs`.
  - **`input --follow`** (#801): `--boot` goes with every line, and a stale boot ends the command with 4 on the refused line, with nothing after it sent and nothing printed per line (`main` prints the message). The link holds one run of the server (the proxy connects once and a restart ends the connection), so only the first request can meet a stale boot; answering the line's `--json` with the error and going on with exit 3 would only refuse every later line the same way, which a client could not tell from lines the program did not take. With an empty standard input nothing is sent, so the boot is never compared and the status is 0.
