# Commands for scripts and agents › Reading a workspace's files

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- **Reading a workspace's files** (#477, `control/files.rs`, `app/control/files.rs`, `app/files_panel/streams.rs`, `app/files_panel/feed.rs`, `cli/files.rs`, `cli/args/files.rs`, `cli/help/files.rs`; `cornercase files list|read|search`): #345 left the files panel's listing and viewer out because a GUI reads the disk itself. That holds only while the GUI runs where the server does: a UI on a laptop attached to the server of another machine (`--remote`, see Remote windows) has the sessions, the changes and the terminals, but not the tree, the viewer or a folder to open as a project. Three operations (`files-list`, `files-read`, `files-search`), the feature `files` and the stream `files` version 1; `CONTRACT` stays 1, so an older server refuses each by name. Nothing runs while no client asks.
  - **Rejected: each client reading through `ssh`** (`ls`, `cat`, `rg`): it copies the panel's rules into every client, and they drift: the `ignore` rules, the entry cap, the 8 MiB and 32 MiB caps, images told by their first bytes, binaries by a NUL, refusing devices and FIFOs (a cloned repository can hold a link to `/dev/zero`), and the git marks. **Rejected: sshfs or another mount**: slow on a big tree, and its paths differ from the session's.
  - **One set of rules, in the domain.** `files::disk` gains `folder` (a listing with kind, size, modification time and whether it is a link) and `load` (a raw read that tells text, image, binary, too large, folder and missing); the panel's `list` and `read` are those two plus the panel's shaping (lines, decoded pictures), so the panel and the socket cannot disagree, and the existing `disk` tests are the safety net. Git marks are `changes::git::marks`, one `git status --porcelain=v2` (what the tree shows in Uncommitted mode) run by the listing's job, with `files::statuses` giving folders their `modified` and `added`. Rejected: following the changes model (`panels.changes.follow`), which loads every hunk with highlighting to get letters; reusing a live Uncommitted model to skip git is left for later.
  - **Paths**: relative ones are the workspace's, never the folder the command runs in (as `changes file PATH`), so the CLI resolves nothing and `--remote` needs no absolute-path rule for `files`. An absolute path or one starting with `~/` (expanded by the server with its own home, `config::expand_home`) reaches any folder, as the panel opens paths outside the workspace (#151), needs no workspace, and has marks only inside the workspace. That also gives a client the folder picker's listing. The answer echoes the path as asked (`path`) and gives it in full (`dir`, `file`).
  - **`files-list` takes several folders and answers them in one object**, zero meaning the workspace's root, as the panel lists the root and its open folders in one job. A UI following its tree holds one stream, which with `--remote` is one ssh connection and not one per open folder; to open another folder it restarts the stream with one more path. A folder that cannot be listed has its `error` (`no such folder`, `not a folder`, `permission denied`) and the others still answer. Entries are in the tree's order (folders first, then names ignoring case), at most `MAX_ENTRIES` with `more`, and carry `kind` (`file`, `folder`, `other` for a device, a pipe, a socket or a link to nothing), `link`, `hidden`, `bytes` (files only), `modified` (UTC, as `flow files`) and `status`. **No `--hidden` flag**: the panel has no toggle (it always lists hidden files and never `.git`), so each entry says `hidden` and a client hides them itself. Rejected: the toggle the panel lacks.
  - **`files-read` answers a kind, never a head of the file**: `text` (the whole text, lossy UTF-8, with `language`, the viewer's grammar), `image` (the raw bytes in base64 with the format and the width and height read from the header; the server never decodes a picture), `binary`, `too-large` (with `bytes`: a text over 8 MiB or an image over 32 MiB), `folder` and `missing`. Devices and FIFOs answer `binary` as in the viewer. No highlighting runs (`changes file` already has the hunks, and a client has its own highlighter), no gutter. The base64 and the value are built in the job's thread, so a 32 MiB image (about 43 MiB of JSON, under `protocol::MAX_MESSAGE`) is not encoded on the server loop; the last rendering of the answer still is: measured through the log's slow-step warning, not before, and a pre-rendered path is left for later.
  - **`--follow` moves the panel's polling next to the disk** instead of every client polling through ssh: folders are listed again every `LIST_EVERY` (2 s) and a file is checked every `CHECK_EVERY` (1 s, a stamp compare, so an unchanged file sends nothing). A listing sends a line only when it differs from the last, so a busy folder sends about one every 2 s while something writes, and that is expected. A one-shot request is a stream whose first answer ends it, so there is one code path. Lines go through the held slot (`Streamed::Snapshot`), as `changes` does, so a slow reader reads the latest; the server sends a step's answers before its stream lines, so the first answer always comes first. A connection follows one stream at a time (`conflict`), because the slot is one per connection; one-shot requests on it are fine. A stream ends (`Streamed::End`) when its workspace closes or is removed, and a job stuck for `GIVE_UP_AFTER` is given up and started again.
  - **`files-search` is the panel's search**, names (nucleo, smart case, the best 200, `indices` as characters of the path) or text (ripgrep's matcher, at most 1,000 matches, `ranges` as `[start, end)` characters of the line), over the workspace only. Each request walks a fresh index (no cache shared with the panel or between requests) and is cancelled when its client leaves; a cache would have to be invalidated by the disk. `capped` is `names.len() >= MAX_NAMES` for names and the search's own flag for text. A blank query is `malformed`.
  - **Logging** (see Log): a request logs its workspace, the folders' count or the path, `follow` and, for a search, `mode` and the query's size, never the query or any file's content; paths are fine. A stream logs its start at info and its updates' size at debug.
  - **`open` and `status` for a remote UI**: `open` takes `~` and `~/…`, expanded by the server (the CLI sends them as they are, with or without `--remote`: a program that passes `'~/src/shop'` without a shell used to get `$PWD/~/src/shop`, and now gets the home folder, as a shell would; a folder named `~` is `./~`), and `status --json` gives `home`, the server's home folder, so a client shows `~/…` for paths there as the TUI does. `home` is left out of the JSON when unknown, so the v1 `watch` and `view` fixtures do not change, and `cornercase --remote devbox status` abbreviates with it too.
  - **The CLI**: `list` prints a TSV like `flow files` (a header, `.` for the root, `-` for nothing, control characters as spaces) with `more` and failed folders on stderr, and exits 3 when a folder failed after printing the rest (#472's partial answer); `read` prints the text as it is, or a line saying what the file is (`--json` has the data), and exits 1 for a missing file or a folder; `search` prints one path per line for names and `path:line:text` for text, as `grep -n`, so the lines are clickable in panes. `--follow` is always JSON lines. `skills/cornercase/SKILL.md` is unchanged: agents in panes read the disk themselves.
  - **Pinned by** `tests/fixtures/control/files/v1/{listing,text,image,search}.json`, each written and read back. Not checked live: a real sshd, only the e2e tests' fake `ssh`.
