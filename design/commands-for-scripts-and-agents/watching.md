# Commands for scripts and agents › Watching the session and the rest of the app

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- **Watching the session** (#285, `control/watch.rs`, `app/events.rs`, `server.rs`; `cornercase status --follow`): an external UI, or a script that draws the sidebar its own way, has to keep a whole model of the session (groups, projects, workspaces, tabs and panes, their names, icons, colours and folds, the split tree, the agents' states) and keep it right. `status --json` lacked the presentation and the splits, and `events` says nothing of renames, moves, folds, dividers or group styles, so such a client could only poll. Two changes:
  - **`status --json` grew**, by additions only: each group's `icon` and `colour`, each project's and workspace's `custom_name` (`null` without one) and `collapsed`, each tab's `custom_name` and `layout`, the split tree with pane ids as leaves (`{"leaf": 4}`, `{"split": {"dir": "right", "ratio": 0.6, "first": …, "second": …}}`), the shape `session.json` gives `Node`. It is `control::Layout`, a type of the contract rather than `Node<u64>` serialized as it is: the answer goes through `serde_json::Value`, which widens the `f32` ratio (`0.6000000238418579`), so the ratio is turned into an `f64` from its short form; and a change to the session's own type cannot change the contract by accident. `Eq` went from `Report` with the float. The text of `status` and `status --panes` did not change.
  - **`watch` answers with the current state, then sends a new one each time it changes.** Each message is the whole `Report` with a `revision` (`control::Snapshot`), so a client replaces its model with each one and never applies a change to a model that may have drifted. Patches (only what changed) were rejected: the issue left them optional, a client that misses one is wrong until it notices, and they would need a format of their own to version; a whole snapshot costs more bytes, which a session of usual size can afford. The snapshot is `status --json` itself, `caller` aside (`null`), `shown` and `active` included, since a UI wants to know what the window shows, rather than another model to keep in step with the one `status` already gives.
  - **No gap between the first state and the stream**: the request is answered in the step it arrives in, by building the `Report`, offering it to the clients already watching (so a change they had not seen goes to them, and not twice to the new one) and only then adding the new client, whose answer is that state. Answers go out before streamed messages in `Server::answer`, so the first state always arrives first, and everything after it comes with a higher `revision`. Starting `events` and reading `status` after, as `events` asks, leaves a moment where a change is in neither; this was why the first state is the answer rather than a separate request.
  - **`boot` and `revision`**: `revision` goes up by one per snapshot sent and is kept by `App` for the server's life, also when every watcher left and another one comes (the next one then gets a new revision even for the same state, since the last one is forgotten with the last watcher), so a client that reconnects sees it never go back. It only compares within one `boot` (in every snapshot, see the contract below): a restart starts again from 1, with new ids. Recovering is reconnecting: a new `watch` is a full bootstrap, so there is no resynchronisation message.
  - **The title moves by itself** (#332): see What programs ask of the host terminal; it is part of the `refreshed()` fingerprint.
  - **Only what changed is sent**: a `Report` equal to the last one sent is dropped without raising the revision, so a step that changed nothing a client sees sends nothing. Some fields move by themselves (an agent's context percentage, `at_prompt`, `program`, `path`, `shown`, `active`, `keep_awake`), so a working agent gives a snapshot every few seconds; they are what a UI draws, so they stay.
  - **What it costs**: the `Report` looks up every pane's process and reads each workspace's `.git/HEAD`, about 3.7 ms with 50 panes in a release build on macOS, so it is built only while someone watches, after the trace diff (see Log), and only when something it shows may have changed. Every traced step but the refresh (input, a request, a job's answer, a client coming or going) marks it changed (`App::trace`); the refresh, which runs on every turn of the loop including those woken by PTY output, traces through `App::trace_refresh`, which looks again only when that refresh read the processes and agents (`watch_agents`, every `WATCH_AGENTS_EVERY`, 500 ms), and then marks it changed only when what the refresh reads differs from the last look (`App::refreshed`: a hash of each workspace's branch, `↓n`, setup, the end of its flow run and pull request with its checks, each tab's status, each pane's foreground process, its name and folder, its flow role, its agent's state, model and context, dialog, survey and resume, and keep awake). That fingerprint costs about a third of the `Report` (1.1 ms against 3.2 ms with 50 panes in release: the process name without its arguments, and nothing serialized), so a quiet session builds nothing, output that changes only cells never builds it, and what moves without a step of its own (a program starting, a branch checked out by hand, an agent's status) shows within half a second. A pane's arguments are left out of the fingerprint, since reading them is the costly part: a program that only changes its arguments shows with the next change. Building is also capped at once every `SNAPSHOT_EVERY` (500 ms): a change inside that window marks it due, and `App::tick` asks for a wake-up when the window ends, at once when it already has, so the last change is never left unsent. Comparing only what changed, instead of building the whole `Report`, was left out: names, agent states and processes have no change signal of their own. 200 ms was the first choice for the window and was dropped once measured: up to five builds a second of almost 4 ms each is 2 % of a core, for a feed whose agent states are read only every 500 ms anyway.
  - **Slow readers get the latest**: a snapshot replaces every earlier one, so a reader that falls behind needs only the newest. The server queues at most `SNAPSHOTS_QUEUED` (4) messages for a watcher, which it never takes back, so a reader that falls behind still reads those older snapshots first; past them it holds one snapshot aside (`Client::held`), replaced by each newer one, and sends it when the queue has room, at the next answer step. The jump in `revision` tells the client it skipped some, which it need not act on. Dropping and counting them, as `events` does, would leave the reader on an old state. A reader that stops reading meets the 1 s write timeout like any client, and a large session on a slow remote link can too; reconnecting is the answer.
  - **The CLI is `status --follow`**: one JSON line per snapshot, the first one included, until the server stops (`Shutdown`, `Restart`, `Detached`: exit 0) or the connection drops (exit 1, saying so). Always JSON, `--json` accepted: a tree of text reprinted at each revision helps nobody. It conflicts with `--panes`, a view a script computes from the snapshot. A command of its own (`cornercase watch`) was rejected: the snapshot is `status --json`, and the issue asked for `status --follow`; `watch` stays the wire name, which an older server refuses by name. Like `status`, it needs no window, so it works on a server nobody has attached to yet. The streamed lines are `{"ok": …}` in both modes, as `events`'s are.
  - **Machines' workspaces** (#542, see `status` › A machine's workspaces): a snapshot carries `machines` and `shown_remote` as `status --json` does, so a new snapshot from a machine, or a change of the shown workspace, sends one here. A machine's link is itself a `watch` client of that machine's server (see Remote windows › What a machine has), so what a machine has reaches a client here through two snapshots, never through a patch.
- **Following the rest of the app** (#338, `control/app_state.rs`, `app/events.rs`, `app/control/status.rs`; `cornercase status --app [--follow]`): `watch` carries the session (hierarchy, panes, agents) but the TODO list, the queue, away per chat app, the update found and keep awake lived only in the window, so a GUI could draw the sidebar but not its own TODO panel or update button. Decisions:
  - **A separate stream, not an opt-in part of `watch`**: the request `app` (stream `app`, format 1, its own connection). The session changes on every agent read (500 ms) while these parts change rarely, and a `watch` snapshot is whole each time, so adding them would resend every queued prompt, every TODO and the release notes (every CHANGELOG section since the running version) every few seconds while an agent works. `status --json`, `watch` and `view` lines keep their shape byte for byte (`Report` is untouched, and a test checks they have none of the new keys). One request per connection also lets `Client::held` (the latest-only slot of slow readers) work for a second stream unchanged.
  - **Shared pacing, nothing copied**: `Snapshots<T>` and `control::Snapshot<T>` are generic (`T` is `Report` by default), so the session feed and the app feed share comparison, revision, joining and forgetting (and jscpd stays quiet).
  - **Nothing marks a change**: the snapshot is cheap (no process lookups: clone the TODO items and the queue entries, two away rows, the update info, keep awake), so while someone follows it, every traced step builds it at most every `SNAPSHOT_EVERY` (500 ms) and sends it only when it differs from the last one. No code path (the panel, a request, the queue's tick, the check-off of `todo send`, an update job, a chat's `/away`) can forget to mark a change, and nothing is built while nobody follows.
  - **The shape** (`AppState`, every key always present, `null` when there is no value): `version`, `boot`, `todos` (as `todo list`, in the panel's order), `queue` (the entries `queue list` answers, prompts included), `away` (one row per chat app, `Via::ALL` order: `platform` in lower case like `config`'s connections, unlike `away`'s display `platforms`; `ready` = paired and its token not refused; `away`), `update` and `keep_awake` (as in `status`, `null` while the setting is off; it is also in `Report`, built by the same function). `update` (`UpdateInfo`) holds `release` (`version` and its `notes`, which stays once installed), `none` (why there is no release: `disabled` for a development build, `failed`, `up-to-date`, `off` for `check_updates` false and nothing checked, `unchecked`; `null` with a release), `checking`, `checked` (UTC time of the last answer), `error` (of the last check, cleared by one that worked), `install` (`{"method": "replace", "path"}` or `{"method": "command", "command"}`), `installing`, `installed` and `install_error`. Fixture: `tests/fixtures/control/app/v1/snapshot.json`.
  - **Discord's forum** (#437, see Discord): an away row may carry `forum` (`ForumInfo`: `on`, `ready`, `guild`, `channel`, `pending`, the first setup step left, or the refused Message Content intent while ready), left out when the mode is off and no forum is saved (always on Telegram), so the v1 fixture and older clients are unchanged. It stays while the mode is off with a forum saved (`on: false, ready: true`), since turning it on again reuses the posts. `pending` holds steps only; a failure is the row's note in `config`. `guild` and `channel` are strings, not numbers: Discord's ids pass 2^53, which JavaScript clients (plugins, a Tauri UI) would round, and the post's URL carries them as text anyway.
  - **Machines** (#540, see Machines in Commands for scripts and agents): `machines` holds the same rows as `machines list`, and is left out while no machine is listed, so the v1 fixture and older clients are unchanged. `seen` is a time, never an age, so a snapshot changes only when a state does, and nothing marks the change: the comparison finds it.
  - **`status --app`** prints one snapshot (it is `ask("app", …)`: the first answer, then the connection ends and the server forgets the watcher) and `status --app --follow` one line per change; always JSON, and it conflicts with `--panes` and `--view`. A GUI's stream is `app` on the socket.
  - **Left out**: per-platform away (`away --platform`; an older server would turn away on everywhere, so it needs a feature gate of its own), the queue's `clear started` and the undo of its removals, and browser access (the green `●` on ` Remote `; `config`'s connections already list the paired browsers).
