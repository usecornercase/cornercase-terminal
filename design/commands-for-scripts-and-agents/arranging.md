# Commands for scripts and agents › Arranging the session

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- **Arranging the session** (#335, `control/arrange.rs`, `app/control/arrange.rs`, `app/control/close.rs`, `cli/arrange.rs`, `cli/args/arrange.rs`; `cornercase group new|style|delete`, `move`, `collapse`, `expand`, `move-pane`, `close --check` and `--unlock`): `watch` already showed groups, their styles, folds, the order of rows and the split layout, but only gestures changed them, so an external UI could draw a sidebar it could not rearrange. Eight request names (`group-new`, `group-style`, `group-delete`, `move`, `move-pane`, `collapse`, `expand`, `removal-check`), so an older server refuses each by name; and one field of `close`, `unlock`, behind the feature `close-unlock` (an older server drops the field and refuses with the lock's message, so nothing destructive happens, but a client must be able to tell, and `cornercase close --unlock` checks it before sending). `CONTRACT` stays 1 and `Command::NAMES` has 54 (57 with the update and app requests of #338). None of them takes a view: they act on explicit ids, and `--view` is refused as for every command outside `takes_view`.
  - **The gestures' own methods**: a request calls what the mouse calls, so the trace, `watch`, the saved session and the log see both alike and every accepted change shows in the next snapshot without code of its own. The drag's drop (`drop_row`) became `move_group`, `move_workspace`, `move_tab` and `move_project` (now by ids, converted from the drop's indices at the one call site), a fold click `set_collapsed(target, collapsed)` (`toggle_fold` reads the flag and sets the opposite), the style dialog `style_group`, and the pane drop `Tab::rearranged` (the new layout when it still has room, which `Tab::landing` uses too) and `Tab::land`. A group deleted by a request also drops the window's overlay that names it (`Overlay::names_group`), which the TUI itself could never meet: its dialog was the only way to delete a group.
  - **Set, never toggle**: `collapse` and `expand` (the words Layout → Expand and collapse chose) set the flag whatever it was, so a script that repeats a request changes nothing the second time. Only a group, a project, a workspace or a pane (the agents it started, in the agents section, #383) has a fold, a tab has none; a workspace being removed or closed is refused like every command naming one (`usable_workspace`).
  - **`move`**: `before` names a row of the same kind and none means the end of its list; a project moved before another takes that project's group, as a drop does; `into` puts a project last in a group and `ungroup` last among the loose ones, both through `move_project`, which also keeps the window's project by id and cancels a pending group deletion, where **move to group** in the menu changes the group in place. Only a project joins a group, a workspace stays in its project and a tab in its workspace (the TUI cannot move them elsewhere either: a shell or a worktree would change owner). A project with no place is moved to the end of its own list. The CLI asks for the place (`--before`, `--last`, `--into` or `--ungroup`) so a forgotten flag never sends a row to the end; `--last` sends no `before`.
  - **Groups**: `group-new` takes the next preset like **new group** and answers its id in `Done::group` (`Ids` is untouched, so the events and their fixtures stay as they are); it opens nothing. `group-style` takes an icon and a colour from `GROUP_ICONS` and `GROUP_COLOURS`, refusing others with the sets in the message, and with neither it only reads; its answer lists both sets, so an external picker is built from the server's. `group-delete` keeps the projects (outside any group) or, with `close_projects`, closes them and deletes the group once their shells have gone, as the dialog's two buttons do. `close` on a group still refuses and now names `group delete`.
  - **Panes**: `move-pane` swaps a pane with another of its tab or moves it to the left, right, top or bottom of that one, in the size the tab has (`App::tab_area`: the view's when a view sizes it, else the window's pane area), so a move that would leave a pane without room is refused with `conflict` and changes nothing, and one that fits resizes the terminals as a divider does. The moved pane becomes the tab's active one. The answer is `ratio`'s (`tab` and `layout`). A pane never moves to another tab, which the gesture cannot either.
  - **The removal check** (`removal-check`, `close --check`): the Remove workspace dialog's data, so a client can say what removing a worktree would lose before it stops anything: `changed` (the worktree and its flow roles' together, a failing `git status` counting as changes, as in the dialog), the `lock` with its reason, the locked worktree (`role` for a flow role's), the process the reason names and whether it still runs (shown only: a pid can be reused), the `roles` worktrees that go with it, and whether the project's `teardown` runs first. It runs the same job as the dialog (`spawn_check`, `Stage::Check`, dropped with its client) and refuses what `close --remove-worktree` refuses (`removable`: a plain workspace, one being removed, a role's worktree whose run lives), with the same codes. `close --unlock` does what **unlock and remove** does and does not imply `--force`: changes still refuse, so a script must name each risk it takes; `--check` conflicts with both, since a check that removes would be a surprise. Locks keep being reported by `close` itself, now naming `--unlock`.
  - **Closing an agent** (#399, `close-agent`, `app/control/close/agent.rs`, `cornercase close --agent --pane ID`): the window's **close agent** for scripts, by the same plan (`App::agent_close_plan`, see Layout › Agents section) and the same check (`App::spawn_close_check`: git status, the lock and each worktree's branch scan), so the two never disagree about what closes. A request name of its own rather than a field of `close`: an older server would drop the field and close only the pane, so it must refuse the request by name. Fields: `pane` (required), `check`, `delete_branch`, `force`, `unlock`. `not-found` for a pane that is not there; `conflict` for one that runs no agent cornercase reads, a project that is closing, or a removal target that changed while git checked; a workspace being removed or closed is refused as everywhere (`usable_workspace`). When only tabs close it acts at once: no git, nothing on disk, and `delete_branch`, `force` and `unlock` change nothing. When the workspace goes, it answers once the check ends (`check`), or refuses before anything stops while the check finds changes without `force` or a lock without `unlock` (the messages of `close --remove-worktree`), or, with `delete_branch`, a branch whose commits are in no remote branch without `force` (a scan that fails counts, as in the dialog). Otherwise it removes through `remove_with_shown_branches` (git's `--force` and unlock as passed, as `close` does), deletes only the branches the check reported that are still checked out there, and answers once the worktree is gone and the branches deleted. Its pending `Stage::CloseAgent` of a request without `check` outlives its client from the start, during its check too, like `close --remove-worktree`; one with `check` goes with its client, like `Check`. The cleanup's tallies are kept per request (`Tally`, `Pending::asked` in `worktrees_dialog/cleanup.rs`), so a script's removal shows no toast in the window (`close --remove-worktree` shows none either) and its answer carries its own failures.
  - **The answer**, `AgentClosing`: `pane`, `agent`, `project`, `workspace`; `removes`, the removal check's `Removal` (null when only tabs close); `branches`, one per removed worktree (`path`, `branch`, `lost`, `deletes`, `deleted`); `tabs`; `stops` and `keeps`, panes as `pane`, `agent`, `project`, `workspace`, `tab` (`keeps` are the child agents started elsewhere); `run`, the flow run that ends, only when its workspace goes; `closed`, false for a check; `warning`, a teardown that failed or a branch that could not be deleted or was kept because it changed. Read leniently like every answer and pinned by `tests/fixtures/control/close-agent/answer.json`, written and read back. `cornercase close --agent` prints nothing on success (warnings on stderr), the check as lines in the style of `--remove-worktree --check`, and the answer with `--json`. `--agent` conflicts with every target but `--pane` instead of requiring it, and `--delete-branch` conflicts with `--remove-worktree`, since a `requires` that points into an exclusive group is met by any of its members.
  - **Codes**: `not-found` for ids that name nothing; `malformed` for the wrong kind (a pane in `move`, a tab in `collapse`), a row before itself, two places, a group move with `into`, an icon or colour outside the sets and a missing place or id; `conflict` for a row before one of another parent, a pane in another tab or a move without room; `failed` for the rest, and the refusals `close` already had keep their codes. Left out: `open` into a group (`open` then `move --into`), moving a tab to another workspace or a pane to another tab, and per-worktree detail in the check beyond the roles.
