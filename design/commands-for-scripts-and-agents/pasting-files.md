# Commands for scripts and agents › Pasting a file from another machine

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- **Pasting a file from another machine** (#479, `control/terminal.rs`, `app/control/terminal.rs`, `app/pasted_files.rs`, `app/files_panel.rs`, `files/pasted.rs`, `paths.rs`, `cli/terminal.rs`, `cli/help/paste_file.rs`):
  - **Why**: an agent reads an image or a file from a path. When the window or a script is on another machine than the server (`cornercase remote`, the phone's browser, an external UI over ssh), a file on the laptop has no path on the server: dropping it pastes the laptop's path, which the agent cannot open. The alternatives were `scp` and typing the path, or a shared folder (sshfs, Syncthing), whose paths differ on each side.
  - **The request**: `paste-file` with `pane`, `name` and `data` (the bytes in standard base64, padding optional, ASCII whitespace ignored). The server keeps the bytes in a folder of its own and pastes the file's path into the pane. The answer is `pane`, `path` and `bytes`. The command, `cornercase paste-file --pane ID [--name NAME] [FILE|-]`, reads FILE (or standard input) **on the machine where it runs**, also with `--remote`: it is the one command whose path is this machine's, unlike `open`, `config project`, `flow save --path` and `files`, and that is its point.
  - **A new operation, not a `file` event of `input`.** Rejected, though the issue sketched both. `input` is synchronous, all-or-nothing and encode-only, written in one `Term::write`; a file needs a decode and a disk write first (about 120 ms for 32 MiB here, unbounded on a slow disk), which would run on the loop or make `input` answer late and order the PTY write after a job while the other events' encoding (sizes, modes, the in-flight `send` check) could go stale. An older server answers an unknown event with `malformed`, which a client cannot tell from a bad event without a probe; a new name gets `unsupported`, as the contract asks of a new behaviour. `input` logs at debug and a paste of a file is rare, so it belongs at info. The cost: a UI that types through `input --follow` sends a dropped file on another connection, and the two are not ordered, so it waits for `paste-file`'s answer before sending more, as for any requests on different connections.
  - **The decode and the write run in a job** (`App::spawn_job`), and the answer comes when it ends (a pending `Stage::Reading`, like `files-search`). The job's answer is `FilesEvent::Stored`, the domain's enum for job answers. Typing goes through `type_into`, so a paste is bracketed when the program asked for it, a full queue answers `busy`, a `send` between its paste and Enter answers `busy`, the pane scrolls to the bottom and counts as drafting (a script's `send` waits for the person). Like `input`, none of `send`'s safeguards apply (a waiting agent, a dialog, the survey): it is a person dropping a file through another UI.
  - **The text pasted** is the path, quoted by `agents::quote` only when it needs it, and a space, like ` ask agent `. No third quote helper (jscpd, and `close.rs` already has one).
  - **Names are cleaned to ASCII** `[A-Za-z0-9._+-]` so the path needs no quoting: the last `/` component, each run of other characters one `-`, `-` and `.` trimmed from the ends of the stem (no hidden file, no `..`), at most 100 bytes (the stem is cut, the extension kept), and `pasted` for an empty stem. This covers macOS screenshot names, with their spaces and the narrow space before "AM", and Claude Code, which turns a pasted *bare* image path into an attachment (the quoted forms were not checked). A name without an extension whose bytes sniff as an image (`graphics::decode::sniff`) gets `.png`, `.jpg`, `.gif`, `.webp`, `.bmp` or `.ico`, so `pngpaste - | cornercase paste-file` gives `pasted.png`, which agents recognise; a given extension is never changed. Rejected: keeping Unicode letters, which would need quoting.
  - **The cap is `MAX_IMAGE_BYTES`**, 32 MiB (`files::pasted::MAX_BYTES` is that constant): about 42.7 MiB of base64, under the protocol's 64 MiB message, so it also crosses the proxy. The command checks it before sending, the server checks the decoded length. **Empty files are refused**: `wl-paste --type image/png | …` with nothing in the clipboard, or a pipe that failed, would paste a path to an empty file into an agent.
  - **One folder per paste**, `pasted/<UTC stamp>/<name>` (`2026-10-27T10-03-12Z`, then `…Z-2` when it exists), made with `DirBuilder::create` and never `create_dir_all`, so two pastes never share a folder and a name is kept exactly. `pasted/` and each folder are `0700`, the file `0600` (`create_new`). The folder is `paths::pasted(session)`: `~/.local/state/cornercase/pasted/` in a release build, next to the session file in a development one, and `<socket>.pasted/` with `CORNERCASE_SOCKET`, so each e2e test has its own.
  - **Cleanup** ("removed after some days or with its pane"): a paste's folder goes when its pane closes (`PastedFiles` keeps `(pane, folder)` for this run, in `Clients`, checked once a second in `refresh_slowly`); entries of `pasted/` older than 7 days (`KEEP_FOR`, by modification time, except the folders this run keeps) go in a job at server start and before each paste; the folder also goes when the paste could not be typed. Folders of an earlier run are *not* removed at start just because their panes are gone: agents resume their conversations after a restart or an update and may still read the path, and a second server that shares the state folder must not lose its live pastes. Rejected: keying folders by boot and deleting other boots at start, for the same two reasons.
  - **A client that leaves before the answer gets nothing pasted**: the pending does not outlive its client, and when the job's answer finds no pending the folder is removed. Rejected: pasting anyway, as launches still type; nobody is left to read the path, and a killed command should not type into an agent.
  - **Refusals**: `malformed` for no pane, empty `data`, bytes that are not base64 and a file over the cap; `not-found` for an unknown pane (also when it closes while the job runs); `failed` when the file cannot be written; `busy` from `type_into`.
  - **What the loop pays** (release build, 32 MiB file, 42 MiB of JSON, measured on 2026-10-27): parse to `Value` 69 ms, a `Value` clone 50 ms, `to_value` of the parsed request for the strict-field check 64 ms, decode 77 ms, write 39 ms. So the decode and the write are in the job, and `contract::read` takes the `Value` by value and compares the strict fields only for a structured request (it used to clone the value and serialize the request on every request and drop the result when legacy), which takes a legacy 32 MiB request from about 233 ms on the loop to about 70 ms and a structured one to about 180 ms. The behaviour is the same. A 2 MiB screenshot costs about 3 ms per step. Parsing on the client's reader thread was left for later.
  - **Logging**: the request line at info with `pane` and `data_bytes`; the job line (`files`, `paste stored`) with `pane`, `bytes` and its duration. Never the name or the bytes (`design/log.md`).
  - **Not checked live**: Claude Code turning the pasted bare path into an image attachment (the fake-API setup of #143 could check it), a real sshd, macOS `pngpaste`. The tests use the fake `ssh` of `design/remote-windows.md`.
  - **Left for later**: the TUI's remote window turning a pasted path that names a file on the laptop into a pasted file (the pane is decided by `handle_paste`, where a dialog or a field may take it); the phone's browser (its bridge caps a message at 1 MiB, so it needs chunks or a higher cap); `--tab`, a popup target and a store-only mode; parsing big requests off the loop.
