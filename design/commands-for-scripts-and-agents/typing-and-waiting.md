# Commands for scripts and agents › Typing, starting and waiting

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- Typing goes through `Launch`: `Launch::command` (new-tab/split: the shell step only), `Launch::enter` (send --enter: the submit step only), `Launch::new` with `prompt: None` (start without a prompt). A request that types answers once it is typed, so a following `send` cannot land before the command. The submit step presses Enter after 300 ms of quiet or at most 3 s (`SUBMIT_LATEST`): a working agent's spinner never goes quiet. Launches carry a `key`; `drive_launches` reports `(key, started)` to the requests.
- **A model and a mode per call** (`start --model M --mode NAME`, #263): through `agents::start_line`. The model takes the agent's own flag (`Known::model_flag`) and first removes every spelling of one already in `agent_args` (`--model x`, `--model=x`, `-m x`, `-m=x`; the `-mVALUE` form is not handled; `agents::with_model`, which a flow's roles use too), since clap-based CLIs such as Codex refuse a flag twice and start nothing; the mode is one of `agents::modes` by its name, and an unknown one is refused with the agent's modes. With either flag the request goes as `start-with`, which an older server refuses by name: it would drop the unknown fields from a plain `start` and start, say, `--mode plan` in the settings' mode that never asks. Without them it stays `start`, which every server takes. `flow list` and `flow run` are under Flows.
- Waits are pending requests in `App`, checked by `check_requests` in `refresh` after `watch_agents`, and answered through `take_answers`; `App::tick` asks the loop to wake for their deadlines, but only for instants still ahead (a past one would spin), and the server never waits longer than its 500 ms tick (a 10 s deadline once starved `watch_agents` of reads and the agent was never seen working). A client that leaves drops its waits; what it created goes on (a worktree being made still gets its tab and agent, a launch still types), since a timeout or a killed command does not prove the work was not done.
- `--until shell` needs the shell in the foreground, output since the last input written to the pane (`Term::input_at`, set by `Term::write`: the echo of a typed command at least) **and** a quiet pane: right after a command is typed the shell is still in the foreground until it forks, and its echo may not have been read yet. The quiet is 300 ms once the wait saw another program in the foreground after that input (`Watch::left`), else 1 s (`SHELL_UNSEEN`): a builtin, a command that ended before the wait, or a shell whose preexec hooks run before it forks. After a submission (the last Enter of a launch, `send --enter`, `keys` with `enter`; `Term::submitted`), a wait that ends on idle first needs the agent to react (`agents::activity::Pane::reacted`: working, or a change between two known activities, since then; a pane that lost and found its agent did not react) within 10 s, else it fails: the status file can still say idle (or the old `waiting`) for a moment after the Enter. This covers a separate `wait` after `send --enter` too, not only `--wait`. An agent that finishes faster than one 500 ms read fails that check; the message says to `read` the pane. A background shell (`Activity::Shell`) is not working there: an agent left with one at the Enter would otherwise count as reacting at once, and `--until turn-over` would end on its old turn before the status file shows the new one; it reacts once it is busy again or its activity changes.
- **Turn over with a background shell** (#127): the tab keeps showing a Claude Code agent whose turn is over but whose `run_in_background` Bash still runs as working (see Agent status), and the default `wait` keeps waiting, since the agent wakes up when the shell ends and its scripts may count on that. Scripts see the difference: `status --json` keeps `status: "working"` for the pane and its tab, so a script reading `working` behaves as before, and adds `background_shell: true` (a separate flag rather than a `shell` status, which would have broken those scripts; no count of shells, since the session file does not give one); the text shows `working (background shell)`, and the `activity` log line names `shell`. `wait --until turn-over` ends on what the default ends on (idle, done, waiting) and also on a background shell, printing `shell` (the session file's word; `--until shell` prints the same word for the shell prompt coming back, but one wait has one condition, so the two never meet). Waiting is included because the turn is over for the script's purposes: the agent needs an answer. The default wait's timeout says when only a background shell is left, naming `--until turn-over`. `start --wait` and `send --wait` take `--until` with every state `wait --until` has (`Start::until`, `SendText::until`, default `Stops`); `--text` and `--quiet` stay on `wait` alone. A request from a newer command to an older server: `wait` fails to parse the unknown state and says to update, while `start`/`send` lose the unknown `until` field and wait the default way. Codex, Gemini CLI and opencode have no such state: what they report (Codex's title and rollout turns, Gemini's title, opencode's messages) has no background process in it, and their turn ends when they say it does, so for them `turn-over` is the default wait. Guessing one from their child processes was rejected: a dev server an agent started on purpose would look the same.
- `send` refuses an agent that is `waiting` (an Enter would answer its question or permission prompt); `keys` is how to answer. Agent conditions fail on a pane without Claude Code, Codex, Gemini CLI or opencode (a status, or one of them detected in the foreground; another agent has no state to wait for; opencode never reaches `waiting`), and a pane cannot wait on its own agent or shell (it would wait for itself).
