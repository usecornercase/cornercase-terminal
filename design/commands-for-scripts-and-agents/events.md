# Commands for scripts and agents › Following events

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- **Following events** (#131): `cornercase events [--pane ID …] [--json]` prints one line per event until the server stops (with `--pane`, until those panes have all closed), so a script that coordinates agents reacts to each change instead of polling `status` or waiting again after each `wait --any`. The events: an agent's state changed (`status`, with `agent`, `from` and `to`: `working`, `shell`, `waiting`, `done`, `idle`, or `null` for no agent, so the background shell of #127 is told apart; another agent taking the pane gives two events, the old one to `null` and the new one from `null`), the program in the foreground ended (`exited`, with `program`), a project, workspace, tab or pane opened or closed (`opened`, `closed`, with `kind`; a pane's `opened` also has `parent` when it has one, left out otherwise so the v1 line is unchanged, and its text line ends ` from pane N`). Each carries `time` (UTC with milliseconds, as in `server.log`, so the two can be read side by side) and the ids of the item and its parents, which a closed item no longer has anywhere else. Groups are left out (they arrange the sidebar, nothing runs in them), and so are moves and phases: a workspace being removed ends with `closed`, or stays. Text lines read like `status`'s (`pane 5  claude  working → waiting`, `tab 3  opened in workspace 2`); an event the command does not know (a newer server) prints as its JSON.
- **Where events come from**: the trace diff (see Log), not hooks in each code path, so a new way to open a tab or change an agent's state is told without anyone remembering to. Each pane's entry in `trace::Seen` also keeps its agent, its `agents::activity::Pane::state` and its foreground job, compared on every traced step (strings are only copied when they change). A new subscriber first makes the diff run, so it starts from now: with the log off nothing ran it, and the first subscriber would have got every item as opened. The agent's state changes on the 500 ms reads of `watch_agents` and when its tab is shown (done to idle), and both are steps the diff follows.
- **Programs ending**: `Term::job` (the foreground process's pid and its name as `status` gives it, `Term::current_job`) is read on the same 500 ms reads, only while someone follows events (`None` otherwise, so nobody pays for it, and a job left over from a past subscriber cannot end in front of a new one). The job ended when the shell is back in the foreground or another pid took its place (`cargo build && cargo test`), but not when the same pid `exec`s, which only renames it. A program that runs for less than one read may not show; `wait --until shell` stays the exact way to wait for one. There is no exit code: the program is the shell's child, not cornercase's. A pane's own shell exiting is its `closed`.
- **The stream** keeps the protocol: the `events` request is answered once like any other (`{}`, or the error for an unknown pane), then each event is one more `ServerMessage::Response`, and the server ends it with `Detached` once every `--pane` closed (ids are never reused within a run, so nothing more could come) or with `Shutdown`/`Restart` when it stops; the command exits 0 on those and 1, saying so, when the connection just ends. No new message variant was needed, so the protocol tests did not change; a server without `events` answers that it has no such command (`Command::NAMES`), one from before the commands is "too old", and the one-answer commands are untouched (`client::requests::ask_on`, which `client::follow` reuses for the first answer). A snapshot of the current state at the start was left out: `status --json` is that, and the help says to start `events` first and read `status` after.
- **Slow readers never block the server**: the loop only queues messages for a client's writer thread, and each client's `Outbox` counts what is queued (the writer takes one off after each write). Past `EVENTS_QUEUED` (1024) a streamed event is dropped and counted instead of queued, and once the queue has room again a `dropped` event with the count goes first, at the next answer step even with no new event, so a script knows to catch up with `status`. Disconnecting at once was rejected: a script that is told it lost events can catch up and go on, one that is cut off has to restart as well. A reader that stops reading altogether still meets the 1 s write timeout every client has, which closes the connection, so a stuck reader costs one thread and the bounded queue until then, and the command says the connection ended.
- **What programs ask of the host terminal** (#332, `app/events.rs`, `term/emulator.rs`): an external UI has no window to receive a program's OSC 52 write or its bell, and the title was only read by the agent readers. `events` takes `host` (`cornercase events --host`), and then also sends `clipboard` (`text`) and `bell` (`count`) events, both pane events with the four ids, in events format 1. One stream rather than a new request: a UI needs `events` anyway, for `closed`, to forget a pane, so one connection keeps clipboard writes and bells in order with those, and `--pane` and its end-once-closed rule come for free. The field is additive (`host` always serialises, since the strict-field check serialises the parsed request), and an older server would ignore it and send nothing, so the contract lists the feature `host-events` and the CLI checks it before sending `--host` (as it does for views); `CONTRACT`, `EVENTS_VERSION` and `Command::NAMES` stay.
  - **From `App::output`, not the trace diff**: the emulator counts bells (`on_bell`, kept trivial like the other callbacks, and only for a C0 BEL: one that ends a title, an OSC 52 or an OSC 7501 is a string terminator) and queues clipboard texts, and `App::output` takes both after each feed, even with nobody listening, so old bells never reach a later subscriber. Host events go through `Events::publish` only, never `App::publish`: plugin hooks, `server.log`, `watch`, `view`, `surface` and the windows get none (the window still receives the program's OSC 52 as before, and a BEL still reaches no window).
  - **The clipboard reuses the window's text and filter** (the standard selection, `text/plain`, non-empty; reads and the primary selection tell nothing), one event per write with no coalescing, since each write is a new value. cornercase sets no size cap of its own: the only ceiling is the 64 MiB protocol message, which applies to a window's frame alike. A text dropped by a reader that fell behind is lost like any event, and the log keeps only its size at debug.
  - **Bells are coalesced per pane** (`BELL_EVERY`, 1 s): the first bell in a quiet pane is told at once, with how many rang in that output; the rest within the next second are counted and told as one event when it has passed, so a program ringing in a loop gives about one event a second. `App::tick` wakes only for pending counts. Counting stops when the last reader that asked leaves, and a closed pane's count is dropped.
  - **The title** is not an event: `PaneInfo.title` (`null` when the program never set one) is in `status --json` and the `watch` and `view` snapshots, and in the `refreshed()` fingerprint, so a change reaches a watcher within one agent read plus the 500 ms pacing. A working agent's spinner title gives a snapshot about every half second while someone watches; the issue accepts that. It is left out of `status --panes` and `surface` frames.
  - **`selection --copy`** already answers with the copied text (see Driving a tab's terminals), so it needs no host event: it is the asker's own copy, answered to the asker.
  - Rejected: a separate stream or request, the title as an event, coalescing clipboard writes, a BEL sent to windows.
