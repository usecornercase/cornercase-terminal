# Opening a VS Code workspace

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

Code: `app/control/create.rs` (`open_request`, `import_request`), `app/picker_dialog.rs` (`import_workspace`), `project/vscode.rs`, `control/code_workspace.rs`, `cli/open.rs`, `cli/args/create.rs`, `cli/help/open.rs`, #673

- **Why**: a client that draws cornercase (#345) has a folder picker of its own, and the only command it could call, `open`, took folders. Parsing the file in the client and calling `group new`, `open`, `move` and `rename` was rejected: it copies `project/vscode.rs` (comments and trailing commas, relative paths, `file://` addresses, network paths on Windows), and over `--remote` it needs a file on the other machine. A separate `group import FILE` was rejected too: it would do as well, but `open` is where people try it first, and it is what a picker calls with what was chosen.
- **The request is `open`, its `path` a file**: it decides where the picker decides, on the path as given with `~/` expanded and before anything resolves links, so `link.code-workspace` imports as the picker imports it, with the link's name and its folder as the base. A file with another name and a `.code-workspace` that is not there fall through to the folder's path, so their answers are the ones they were (`… is not a folder`, `cannot open …`). A folder answers byte for byte as before.
- **One import** (Folder picker › One import, two callers): `App::import_workspace` is the picker's, so the group's name, a folder already open, `name`, folders that are gone, a folder listed twice and a shell that cannot start cannot differ. It is split from what the window does around it: a request moves nothing the window shows, so no shown project, no toast, no leaving a machine's tab, and no unfolding, as for every request (**Nothing changes what the UI shows except `focus`, `go` and `--focus`**, in the area's file). `--focus` goes through `show_to`, as `focus --project` does, so a tree sidebar unfolds the group and the others mark it, and with `--view` the view moves and the window stays.
- **The file is read on the server's machine, on the loop**, as the picker does (see Folder picker). So `--remote` needs nothing of its own: `reach::open_path` already takes any absolute path or `~/…` without looking at it, and refuses a relative one, since this machine's folder means nothing there. Without `--remote` it makes a relative path absolute from the folder the command runs in. A relative `path` sent over the socket by another program is read from the server's folder, as a folder's is.
- **The answer**, `control::ImportedWorkspace`, pinned by `tests/fixtures/control/open/imported.json`: `group` (`null` when a new group was left empty and removed, as the picker does), `name` (the group's, or the file's stem when there is none), `projects` (ids in the file's order, distinct), `missing` and `failed` (counts), and `projection` with `--focus --view`. That is what the toast says: the toast's text is `ImportedWorkspace::message`, so the two cannot drift. A client tells it from a folder's answer by `projects`, which a folder's `Done` never has; the CLI does too, since only the server knows what the path is. `name` is there because the toast names the group, and when nothing was imported no `status` could say it. Counts and not lists, as the toast has them: a client's message needs no more, and a list can be added later.
- **Folders on another machine are not counted**: `vscode::read` drops a `vscode-remote://` address, a `file://` one of another host and, on Windows, a network path before the import sees them, so they are neither `missing` nor a reason for status 3, as the toast says nothing of them. Counting them in `missing` was rejected: the toast would call a folder on another machine `not found`, which is not true and would change the window. A count of their own can be added later, should a client need to say so.
- **Exit status 3 (#472) when the answer is not whole**: a folder gone, a shell that could not start, or nothing imported. The answer is printed in full first, and `warning: <the toast's text>` goes to stderr without `--json`. Exit 0 for gone folders was rejected: `files list` already answers 3 for a folder it could not list, a script could not tell without `--json`, and a client's generic runner already takes 0 and 3 as a complete document. Refusing an import that opened nothing was rejected for the same reason: nothing failed in the request, and the counts are what a client shows. Without `--json` the id printed is the group's, and none when there is no group, so `group=$(cornercase open …)` gets nothing there and the status says why.
- **`into`, `--into GROUP`**: as the group's **add project**, for both kinds of path: the picker opened from a group takes a folder or a file, so the request does. A folder goes in the group, and one already open moves there in place, keeps its answer and prints its project's id (the group is known to whoever asked). A file imports there and does not look for a group of its name, and that group is never removed, even when it gets nothing. A group that is not there is `not-found` before anything is read or opened. A group being deleted is kept, as **add project** keeps it. The window's add project also unfolds the group; a request does not, see above. It closes what #335 left out, `open` then `move --into`, which also moves the project last in its group where **add project** leaves it in place.
- **An older server**: a file refuses itself (`… is not a folder`), which is enough to fail by name, so a plain `open` asks for no feature, costs no second round trip and sends the bytes it sent. `into` is what an older server would drop in silence, and a folder would land outside the group, so it is behind the feature `open-code-workspace`, which `cornercase open --into` requires before it sends anything (`client::use_open_into`), and which a client's picker can read to know it may offer these files. One feature for both, since they come in the same release. An older command against a newer server imports the file and prints no id, since it reads a project's id from the answer, and `--json` prints the answer whole. `CONTRACT` stays 1. `into` is skipped when absent, and a structured client's `"into": null` is read as left out (Contract › Strict fields).
- **Refusals**: `failed` for a file that cannot be read or parsed (its `Error::CodeWorkspace` text, which names the file), `not-found` for `into`, `NO_SIZE` from a server with no window, checked after the file was read and before the group is made. No size is refused for the whole file, even when its folders are all open: such a server has no projects yet, since it has not restored its session.
- **Checked**: the tests of `app::tests::control_requests::code_workspace` run on the three systems (`cmd.exe` panes on Windows, as `open`'s), like `cli::open`'s against a fake server; e2e with the real binary, also through the fake `ssh`. **Not checked live**: a real sshd, and Windows (CI runs the tests there).
