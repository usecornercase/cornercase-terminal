# Commands for scripts and agents › Several commands through one process

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- **Several commands through one process** (#558, `cli/requests.rs`, `cli/line.rs`, `cli/lines.rs`, `cli/args/requests.rs`, `cli/help/requests.rs`, `client/requests.rs`, `client/requests/shared.rs`; `cornercase [--remote D] requests --follow -`):
  - **Why**: a window that draws cornercase itself (#345) acts through one-shot commands (`focus`, `scroll`, `split`, `view-set`, `redraw`, the panels' reads). Through `--remote` each one is a whole ssh session: a channel, `cornercase proxy` there, its banner, the request, the answer and the close. Measured on 2026-10-31 from a Mac to an Ubuntu machine over Tailscale (direct, about 55 ms round trip): `focus --tab N --view V` took 1.2 to 1.4 s and `scroll --pane P --up 5` 0.65 to 0.8 s one-shot, against about 48 to 70 ms for a key through `input --follow` (#478), which keeps one link. The server's own work is about 25 ms a command. A client also runs its commands one at a time to keep their order, so quick clicks waited behind each other's sessions. `ControlMaster` halves the cost but keeps several round trips per command.
  - **The command**: `--follow` and the argument `-` are required, as for `input --follow -`, which leaves room for a form with the lines as arguments. It keeps one link (the socket, or one ssh with the proxy) and reads one JSON object per line from standard input, `{"args": [...], "stdin": "..."}`. `args` is the command line after `cornercase`, parsed by the same clap `Cli` and run by the same `run_command` as a one-shot command, so every flag works and each command's `--help` stays the contract. `stdin` is what the command reads from `-`; without it, `-` reads nothing. Unknown keys are refused (`deny_unknown_fields`): a typo such as `stdni` must not run `send -` with empty text. Blank lines are skipped and get no answer. `stdin` is text; bytes go through a FILE argument read by this process (`paste-file FILE`).
  - **The answer**: one compact JSON object per non-blank line, in order, flushed at once: `status` (the exit status the command would have had on its own: 0, 1, 2 or 3), `json` (what it printed with `--json`), `text` (the rest of its standard output), `stderr` (its warnings and notes) and `error` (its message, without `error: `). `--help` and `--version` give 0 and `text`; a clap usage error gives 2 and clap's message without its leading `error: `. Fields are only ever added; lines are strict and clients read answers leniently.
  - **In this process, not a child per line**: the command keeps the shared link in a thread-local (`client::requests::shared`), and `ask`, `ask_starting`, `require` and `use_view` use it while a line runs. `contract` is asked once per link and remembered, since it cannot change while the link lives, so the feature checks before a request cost nothing after the first. `--view` applies to its line only (`line_done` clears it). A transport error met by a line (server gone, the link lost, the reader gone) is kept for `line_done`, and the line gets no answer: `requests` ends with 1 and the error on stderr. It never reconnects, since ids change with a restart and a reconnected `focus --tab 6` would act on another tab; the client restarts it, as it restarts `input --follow`. A panic in a line ends the process the same way.
  - **What a line prints is captured** (`cli/line.rs`, a thread-local): `print_json` gives `json` (a second value goes to `text`), `print_out` and `say` give `text`, `note` (the warnings and notes that were `eprintln!`) gives `stderr`, and reading `-` takes the line's `stdin` once, then nothing (`line::input`). Standard input and output are also isolated once at the start: answers go to a `dup` of fd 1, lines are read from a `dup` of fd 0, fd 0 then points at `/dev/null` and fd 1 at stderr, so a print or a read that was missed can never corrupt the answers or swallow lines, and the commands that ask a question (`is_terminal()` is false) say to pass `--yes` instead.
  - **Which lines run**: those `reach::kind` calls `There`, the commands `--remote` sends as requests. Refused with status 2 and a message, the next lines still running: `--remote` and `--remote-command` (the link was chosen when `requests` started), no command, `remote`, `skill`, `server`, `proxy`; `update`, `restart`, `kill-server` and `logs` (they run as a process of their own: the message gives the command to run on its own, with `--remote` when remote); the plugin commands that act on this machine. A command that keeps a connection of its own (`events`, `surface`, `view`, every `--follow`, `changes list`, `input --follow`, a nested `requests`) is refused by `client::connect`, which returns `Error::OwnConnection` while the link is shared, before anything is sent: no side effect happens before a stream connects, and a new stream cannot be forgotten. A stream on a second connection was rejected (with `--remote` it is the ssh session the command exists to save), and one on the shared link would hold its request forever.
  - **Order**: one line at a time, each request after the answer to the one before, as `input --follow`. A line that waits for its answer (`wait`, `send --wait`, a held `send --enter`, `start --wait`) holds the lines after it. Lines are not ordered with other connections: to put a key before a focus, send both through `requests`, or wait for the answer.
  - **Ending**: when standard input ends, after answering every line, `requests` exits 0 if every line had status 0, else 3 (`Error::Partial`, as #472). The reader of the answers leaving (#475) is watched while a line waits for its answer (`reader_left` in `ask_with`, on the dup of the answers' pipe or socket), so a long `wait` cannot keep the process, and the ssh connection, alive after its client died; it exits 0 quietly, as does a write that meets `EPIPE`. Between lines, the end of standard input ends it. Locally a server must be running (it connects at the start, as `input --follow`); with `--remote`, ssh and the banner happen at the start and the proxy connects at the first line, so a first `start-server` line starts the server there.
  - **The socket does not change**: no new request, field, feature or stream, no contract bump. The server sees an ordinary request connection that sends one request at a time. A program on the socket gets the same by keeping its connection. `--remote` follows the version rule of the other commands, and `requests` runs here, so the machine there needs nothing new.
  - **Rejected**: a child process per line that shares the link's file descriptors (exact output with no changes to the print sites, but a hidden environment protocol for the fds, the cached features and the remote, and the lost-link analysis and `json` versus `text` would have to be guessed); `dup2` of fds 0, 1 and 2 around each line (process-wide, so unit tests share it; `io::stdin()`'s buffer would carry a partial read into the next line; a pipe needs a draining thread); lines holding the framed protocol's request JSON (it makes the internal request types part of the contract, which #345 keeps on the command line); the framed protocol through `cornercase proxy` in every client (#344) and `ControlMaster` (several round trips per action remain); reconnecting after a lost link; an `id` echoed per line (answers come in order, one per non-blank line); answering out of order or running lines concurrently; a scan forbidding `println!` in `src/cli/` (file-level exceptions too coarse to help, and the isolation makes a missed site harmless).
  - **One-shot `--view` commands still open two links** until #557 (ask `contract` on the request's own link); the shared link is small and inside `client::requests` so that a kept link there can become a one-request `Shared`.
  - **Checked**: unit tests for the shared link (a fake server on a socket pair), the lines and the answers; e2e tests locally and through the fake `ssh` (one ssh for all the lines). **Not checked live**: a real sshd and `ControlMaster`.
