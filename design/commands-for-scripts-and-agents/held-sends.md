# Commands for scripts and agents › `send` waits for the person typing

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- **`send` waits for the person typing in the pane** (#371, `app/control/held.rs`, `term/typing.rs`): `send --enter` pasted into an agent's input box whatever was already there, so an orchestrator reporting to the agent a person was typing to merged both texts and submitted the person's half sentence with its instruction in the middle. Stashing the draft (clear the box, send, type it back) was rejected: the draft lives inside the agent (long pastes shown as `[Pasted text #1 +40 lines]`, images, wrapped lines, no cursor), no agent has a safe key to clear its box, and the person keeps typing meanwhile. So `send` waits until the person is done, and their draft goes first.
  - **What the person typed, not what was written**: `Term::input_at` is set by every write (`send` itself, `keys`, launches, query replies), so each pane also keeps a `term::typing::Typing`, fed only by a person's input: the window's keys and pastes (`forward_key`, `handle_paste`, which the browser bridge also goes through), **ask agent**, and the `input` request (a person typing through another UI). Its `at` is the last such input; its draft flag is set by text (a printable key without `Ctrl`, `Alt` or `Super`, `input`'s `text`, a paste that does not end with a line break) and cleared by what submits or drops the line (`Enter` without `Shift` or `Alt`, `Esc`, `Ctrl+C`, `Ctrl+U`, a paste ending with a line break). It belongs to the foreground process it was typed into, so it ends when the agent exits or the shell comes back, and it lapses 60 s after the last input (`DRAFT_FOR`), so a draft emptied with Backspace, or a person who walked away, never holds sends for good. It is a heuristic that works the same for every agent and for shells, and errs on the side of holding: a message arriving late is better than a broken prompt.
  - **Claude Code's box**: once its input box is calibrated for that process (`Term::input_seen`, as for `dialog`), `Term::settle_draft` (every refresh, only for panes with a draft) reads the box from a snapshot of the active screen and clears the draft when it holds no text, so Backspace down to nothing releases at once. Only cells that are not dim count (`Snapshot::lit_lines`), on the `❯` line and the lines down to the bottom rule: an empty box shows a dim prompt suggestion, which would otherwise hold every send. The other agents have no box check (`Known::draft` reads their `INPUT_BOX`, `None`), so their drafts end only by the keys above or the bound.
  - **The hold comes before the paste**: `send_request` runs its refusals, then holds when the pane is busy (`App::holding_back`: a draft, input within `typing_holds`, 2 s by default (`INPUT_HOLDS`, the bound `restart --when-idle` uses), a send between its paste and its Enter (`App::sending`: a launch at its submit step, which also covers `start`'s prompt), or an earlier held send to that pane), as a pending `Stage::Held`. `check_requests` first settles drafts, then releases the first held send of each pane that is clear (`release_held`), one per pane per pass, so held sends go out in arrival order and one at a time: the next waits for the previous one's Enter. Releasing runs the refusals again (the agent may be waiting by then), pastes, and turns the stage into the usual `Stage::Launch` with the request's key, so the confirmation and `--wait` are unchanged; an agent working on the person's prompt by then queues the message like any prompt sent while it works (`holds_prompts`). `--force` skips every hold but one: it still waits for an earlier send's Enter (`App::sending`), then goes out first, passing held sends that wait for the person, so it never lands between another send's paste and its Enter. A held send dropped by its client goes (`forget`), and `--timeout` ends it with what held it (`held::waiting`), saying nothing was sent. `next_request` wakes at the end of the 2 s and of the 60 s bound. `typing_holds` is a field, like `confirm_within`, so app tests set it to zero.
  - **The gap before Enter**: between the paste and its Enter (up to `SUBMIT_LATEST`, 3 s), keys, pastes and mouse events a window sends to that pane are dropped with a toast (`holds_input`, `forward_mouse`, as for a resuming pane), **ask agent** copies instead, and `input` with keys, text or a paste answers `busy`, so nothing typed lands in the middle.
  - **Telling the person**: a one-row bar on the pane's last row, drawn over it like the `↓ n more` badge, so it reserves nothing and PTY sizes never change (`ui::held_notice`): `1 message waiting from pane 40 · goes after yours` (`3 messages waiting, the first from pane 40 · …`; no pane for a sender outside one) in the muted grey on the surface, then ` send now ` (the cyan pill: sends the first held message at once, as `--force`, still after a previous Enter) and ` wait turn ` (a grey pill) at its right. ` wait turn ` only acknowledges: the bar stays while anything is held, loses that pill and reads `queued: goes right after yours` (`2 queued: the first goes right after yours`) behind the working icon of the agent rows (`theme::status_icon` with `View::spin`, so `working_icon` and the spinner's wake-up rules apply, and a still spinner shows its first frame). When to send does not change: the message still goes right after the person submits. `Requests::queued` keeps, per pane, the newest held key at the click, so a send held later shows the bar with ` wait turn ` again. When the badge shows, it keeps its cells and the bar ends one cell before it. A narrow pane cuts the text first, then drops it, then ` wait turn `; ` send now ` stays while it fits. A first version had a band across the pane's middle with ` discard `, which dropped the message with an error to its sender, then a ` hide ` that hid the bar; after trying them, the user asked for the bar at the bottom that never disappears while something is held. Clicks only, no keys. `App::notify` was rejected: it is tied to agent status changes, and the person is looking at that pane.
  - **Scripts**: each pane's `held_sends`, `draft`, `held_from` and `held_queued` in `status --json`, `watch` and `view`, and `held_sends` and `draft` as columns of `status --panes` (`N messages held` and `draft` in the text), additive, so `CONTRACT` stays 1; `refreshed()` hashes all four. `keys` stays immediate: it is how to answer things. An `events` line when a send is held or released was left for later.
  - **A client's bar** (#676, `control/held.rs`, `cli/held.rs`; `cornercase held [--pane ID | --tab ID] [--view ID] --send-now | --wait-turn [--json]`): a client that draws cornercase through its command line (#345) could say a message is held, but not act on it, nor say who sent it or that the person already chose ` wait turn `, so its bar could not read as the window's and two windows could not agree.
    - **One reading, so the bars cannot differ**: `App::held_info` reads the count, `held_from` and `held_queued`, and everything else builds on it: the bar's words (`held_label`), each pane in `status`, `watch` and `view` (`pane_info`), the fingerprint a refresh compares to send those lines (`tab_refreshed`) and the answer of `held`. `held_from` is `Held::from` as the bar uses it, the `caller` the server token let through: a sender since closed is still named, unlike `parent`, which `live_parent` turns into `null`, because the bar names it and ids are not reused within a run. Both fields are always present, like `held_sends` and `draft`, and a server without them reads as `null` and `false`. The client writes the words itself, from the forms under Telling the person: a `held_text` field was rejected, since wording and how much of it fits are the drawing, which stays the client's.
    - **One operation, `held`, with a required `action`** (`send-now`, `wait-turn`), like `machines` and `queue`, not two names: both take the same `pane` and `tab`, and an action this server does not know fails to parse rather than being read as another. It is a new operation, so an older server refuses it by name and no feature is needed; `held` in `operations` also tells a client the two fields are there. `CONTRACT` and the stream versions stay 1.
    - **The same functions as the clicks** (`send_held_now`, `queue_held`), so it does what the window does: forced, still after an earlier Enter (`held_sends` then only drops once that Enter went), the others waiting; the message's sender gets its answer, or the refusal when the pane cannot take it (`refuse_send` still refuses an agent waiting for an answer), and the caller only sees what is left, as the person who clicks does. Giving the caller that refusal as well, or keeping the message when it is refused, was left out: the bar and a client's bar would then behave differently.
    - **Where a request can do more than a click**: while a pane restarts or resumes its agent the window draws that band instead of the bar, so no click reaches `send_held_now`, but `force` passes the resume refusal, and a client's bar drawn a moment before could paste into the agent's start-up. So `send-now` answers `conflict` there and the message stays held. `wait-turn` only records that the person saw it and still goes through. Pressing `wait-turn` twice answers the same both times: a button that has gone from the window's bar is no error for a client whose next line has not arrived.
    - **Refusals**: `conflict` when nothing is held in the pane ("the request no longer fits the target's state", as for `selection --copy` with nothing selected): the message usually went out between the client's last line and the click, so a client can ignore it. `not-found` for a pane or a tab that is gone. A wrong or missing `action` is `malformed`; the CLI needs exactly one of the two flags (a required clap group), with status 2.
    - **The defaults are `send`'s** (`Target`: `--pane`, `--tab`, `--view`, else the caller's or the shown pane), so a client with a view needs no pane id; `takes_view` lists it.
    - **`status --panes` gets no columns**: a row holds what a script filters on (see `status`: the tree, roles and the flat list › A flat list of panes) and does not mirror `PaneInfo` (`title`, `resumes`, `collapsed` and `accounts` are not there either), the two fields are for drawing the bar, and columns are forever. `status --json` has them.
    - **Rejected**: `send --force` from the client (it sends a new message, and the client does not know the held one's text); saying what waits and nothing more (what cornercase-gpui did until now).
    - **Checked**: app tests on every OS (a `cmd.exe` pane on Windows), `/bin/sh` panes for the Enter and the text reaching the program, and e2e with the real binary for the issue's steps, the refusal, `wait-turn` with a `status --follow` line, and a sender that closed.
