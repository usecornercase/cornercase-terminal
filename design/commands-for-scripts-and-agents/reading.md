# Commands for scripts and agents › Reading a pane and its last message

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- `read` and `--text` use libghostty's formatter: `screen_text` formats a selection of the active area, `last_lines` the whole screen with its scrollback (10 MB, see Scrollback); both unwrap soft-wrapped lines and drop trailing empty lines. `--text` re-reads the screen after new output, at most every 100 ms (`TEXT_EVERY`). `regex` has `unicode-perl` so `\d`, `\s`, `\w` work.
- **The last message** (`read --last-message`, #130): an orchestrator that wanted to know what an agent did read its screen, and had to strip the input box, the status lines and the footer, and could not tell Claude Code's grey prompt suggestion from typed text; the workaround was asking every agent to write its report to a file. `read --last-message` prints the agent's last message from its own record instead, whole even once it scrolled off: Claude Code's transcript, Codex's rollout, Gemini's session file and opencode's database, the ones the context line already follows (kept by `watch_agents`). The record is looked up for the agent found in the pane (`agents::context::Pane::record_for`), never taken as whichever one the pane holds: a program that execs another agent keeps its pid, so the pane can still hold the first agent's record next to the new one's, which would read a Claude transcript under Codex's name or refuse an opencode that already has its own; without a record of that agent, the pane answers as one whose record was not found yet. It is a request of its own, `last-message`, rather than a field of `read`: an older server drops an unknown field and would print the screen, which a script would take for the message, while an unknown command answers that the server has none. The reading runs on a thread (`agents::context::Record::last_message`, under `panics::job`) and answers through `AppEvent::LastMessage` (`Stage::Reading`): a transcript can hold tens of MB, and opencode's database waits up to 100 ms for a lock.
- **Searching** (#272): `cornercase search` finds the panes where some text was said, and `focus --reveal` (#467) then shows a match (see Search).
- **Reading several last messages** (#156): `read --last-message` takes `--pane` and `--tab` more than once, so an orchestrator gets what all its agents did in one command after finding their ids with `status --panes`. The command sends the existing `last-message` request once per distinct target, panes first and then tabs, each in the order given; there is no protocol change, so servers that already support one last message support several. Text puts each message under a header with its actual pane id, agent, `turn_over` and `written` (`unknown` for metadata the server did not provide). JSON wraps the unchanged individual answers in `{"panes": [...]}`. A failure gets its own block or an object with `error` and the requested `pane` or `tab` id (a failed tab request has no resolved pane id); all targets are still read, and a target the server refuses makes the command exit 3 without another error on stderr; not reaching the server is not a target's failure, so the command exits 1 with the message and prints nothing. One distinct target, including an implicit one, keeps the previous output and error behavior. Without `--last-message`, more than one target is wrong usage (exit 2), checked before contacting the server: reading several screens was not needed.
- **What the last message is**: the newest assistant text, whatever the turn. Claude Code: the newest assistant `message.id` with text, its text blocks (one line each in the transcript) joined with a blank line; sidechains and `<synthetic>` lines are skipped, except an API error (`isApiErrorMessage`), which is what the agent last showed. Codex: the newest `response_item` `message` with role `assistant`, a progress note (`phase: commentary`) as well as a final answer; `task_complete`'s `last_agent_message` was not used, since an interrupted turn has none and it only comes at the end. opencode: the newest assistant message with text in the `part` table, its parts in `id` order as opencode itself shows them (`orderBy(part.id)`), leaving out parts marked `synthetic` (written for the model, never shown) and the summary `/compact` writes as a reply (`summary: true`), which is for the model too; Claude Code writes its summary as a user line, so it never counts either. While the agent works it is the newest so far; `--json` adds `turn_over` from the live status, with the rule of `--until turn-over` (`Condition::TurnOver`), and `written`, the record's own time (the line's `timestamp` for Claude, Codex and Gemini, `time.completed` for opencode, as `time::Stamp` writes it). Only the latest turn's text was rejected: an agent interrupted before it wrote anything would have none, and `written` says how old the message is. Errors exit 1 and say which: no Claude Code, Codex, Gemini CLI or opencode in the pane, its record not found yet (Codex writes its rollout from the first turn; two Codex, two Gemini with the same home, or two opencode, in one folder hide each other, as for the context line), no message yet, a record that cannot be read.
- Records are read backwards (`agents::context::message::Backwards`: 256 KiB chunks, the newest complete line first, a line still being written left out), at most 64 MiB, so a message behind megabytes of tool output is still found and a long transcript is never read whole. It is a plain iterator over a JSONL file's lines, for whatever else needs the end of one.
- **No input box in `read --json`**: the issue also suggested marking the input box's contents in `read --json`, and whether they are Claude Code's grey suggestion rather than typed text. Left out: it needs each agent's screen layout and the cells' styles, which change between versions, and what it was for, knowing what the agent said, is what the record gives.
