# Commands for scripts and agents › Reading a pane, its last message, its conversation and what it waits for

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- `read` and `--text` use libghostty's formatter: `screen_text` formats a selection of the active area, `last_lines` the whole screen with its scrollback (10 MB, see Scrollback); both unwrap soft-wrapped lines and drop trailing empty lines. `--text` re-reads the screen after new output, at most every 100 ms (`TEXT_EVERY`). `regex` has `unicode-perl` so `\d`, `\s`, `\w` work.
- **The last message** (`read --last-message`, #130): an orchestrator that wanted to know what an agent did read its screen, and had to strip the input box, the status lines and the footer, and could not tell Claude Code's grey prompt suggestion from typed text; the workaround was asking every agent to write its report to a file. `read --last-message` prints the agent's last message from its own record instead, whole even once it scrolled off: Claude Code's transcript, Codex's rollout, Gemini's session file and opencode's database, the ones the context line already follows (kept by `watch_agents`). The record is looked up for the agent found in the pane (`agents::context::Pane::record_for`), never taken as whichever one the pane holds: a program that execs another agent keeps its pid, so the pane can still hold the first agent's record next to the new one's, which would read a Claude transcript under Codex's name or refuse an opencode that already has its own; without a record of that agent, the pane answers as one whose record was not found yet. It is a request of its own, `last-message`, rather than a field of `read`: an older server drops an unknown field and would print the screen, which a script would take for the message, while an unknown command answers that the server has none. The reading runs on a thread (`agents::context::Record::last_message`, under `panics::job`) and answers through `AppEvent::LastMessage` (`Stage::Reading`): a transcript can hold tens of MB, and opencode's database waits up to 100 ms for a lock.
- **Searching** (#272): `cornercase search` finds the panes where some text was said, and `focus --reveal` (#467) then shows a match (see Search).
- **Reading several last messages** (#156): `read --last-message` takes `--pane` and `--tab` more than once, so an orchestrator gets what all its agents did in one command after finding their ids with `status --panes`. The command sends the existing `last-message` request once per distinct target, panes first and then tabs, each in the order given; there is no protocol change, so servers that already support one last message support several. Text puts each message under a header with its actual pane id, agent, `turn_over` and `written` (`unknown` for metadata the server did not provide). JSON wraps the unchanged individual answers in `{"panes": [...]}`. A failure gets its own block or an object with `error` and the requested `pane` or `tab` id (a failed tab request has no resolved pane id); all targets are still read, and a target the server refuses makes the command exit 3 without another error on stderr; not reaching the server is not a target's failure, so the command exits 1 with the message and prints nothing. One distinct target, including an implicit one, keeps the previous output and error behavior. Without `--last-message`, more than one target is wrong usage (exit 2), checked before contacting the server: reading several screens was not needed.
- **What the last message is**: the newest assistant text, whatever the turn. Claude Code: the newest assistant `message.id` with text, its text blocks (one line each in the transcript) joined with a blank line; sidechains and `<synthetic>` lines are skipped, except an API error (`isApiErrorMessage`), which is what the agent last showed. Codex: the newest `response_item` `message` with role `assistant`, a progress note (`phase: commentary`) as well as a final answer; `task_complete`'s `last_agent_message` was not used, since an interrupted turn has none and it only comes at the end. opencode: the newest assistant message with text in the `part` table, its parts in `id` order as opencode itself shows them (`orderBy(part.id)`), leaving out parts marked `synthetic` (written for the model, never shown) and the summary `/compact` writes as a reply (`summary: true`), which is for the model too; Claude Code writes its summary as a user line, so it never counts either. While the agent works it is the newest so far; `--json` adds `turn_over` from the live status, with the rule of `--until turn-over` (`Condition::TurnOver`), and `written`, the record's own time (the line's `timestamp` for Claude, Codex and Gemini, `time.completed` for opencode, as `time::Stamp` writes it). Only the latest turn's text was rejected: an agent interrupted before it wrote anything would have none, and `written` says how old the message is. Errors exit 1 and say which: no Claude Code, Codex, Gemini CLI or opencode in the pane, its record not found yet (Codex writes its rollout from the first turn; two Codex, two Gemini with the same home, or two opencode, in one folder hide each other, as for the context line), no message yet, a record that cannot be read.
- Records are read backwards (`agents::context::message::Backwards`: 256 KiB chunks, the newest complete line first, a line still being written left out), at most 64 MiB, so a message behind megabytes of tool output is still found and a long transcript is never read whole. It is a plain iterator over a JSONL file's lines, for whatever else needs the end of one.
- **The conversation** (`read --messages`, #954): a chat client (a phone app, a bot's view of an agent) had only the last message, so it could not show a conversation it did not follow from its start. `read --messages` prints the user's and the agent's text messages of the pane's current conversation, oldest first: `{"pane", "agent", "conversation", "messages": [{"id", "role", "text", "written"}], "more_before"}`, every key written (`written` and `conversation` `null` when unknown; Grok Build and Vibe CLI never record a time, opencode has no conversation id, as in `status`). Roles are `user` and `assistant`, as a chat names them, although `queue show --conversation` keeps `prompt` and `reply`. It is a request of its own, `read-messages`, with a feature of the same name, for the reason `last-message` is one: an older server would drop unknown fields of `last-message` and answer the last message as if it were the page. It walks the record with `Record::said`, the walker `search`, the Recap dossier and `queue show --conversation` share, so every agent with a last-message reader has it, and what each reader leaves out (tool calls, their results, thinking, sidechains, meta and synthetic lines) stays out; a prompt typed in the pane and one sent with `send` are both prompts there. Granularity is the reader's: Claude Code's text blocks are a message each, so an answer split by a tool call is two messages, and the newest one can differ from `--last-message`, which joins the blocks of one `message.id`.
- **Ids**: a message's id is its position among the messages the reader gives, from 1, in the record's order, never sorted by time (a sort would move ids when a late line has an earlier time, which `queue show`'s sort accepts and paging cannot). They stay while the record only grows. What moves them: a record over the reader's 64 MiB walk is numbered from the oldest message inside it; Gemini rewrites a message with `$set`; an opencode message whose text arrives after a later one. `conversation` changes when the agent starts another (a `/clear`, a resume), and the ids start again. The newest message can still grow under its id for agents that rewrite it (opencode, Copilot's chunks), so a client that follows re-reads from the id before its last one. Byte offsets as ids were rejected: only plain JSONL records have them (opencode and Cursor are SQLite, Gemini rewrites with `$set`, Copilot joins chunks, Vibe reads several files), and they meant rewriting eight readers. An index kept by the activity reader would make `--after` cheap later, with the same ids.
- **Paging**: as `bot history`: `--last N` (default 20) ends at the newest message, `--before ID` gives the `N` just before it, `--after ID` everything after it, or its newest `N` with `--last`; `--before` and `--after` together are refused. `more_before` says that the conversation has messages before the page, for `--after` too; there is no `more_after`, since `--last` and `--before` pages end where asked. Each read walks the whole record on a job thread, the work `search` and `queue show --conversation` already do (on a real 39 MB Claude Code transcript the reader parses about 33 MB of lines). Text is not cut, unlike `queue show`'s 32 KiB: a chat shows the message, and `--last-message` gives it whole too. It takes one target; several can come later with the `{"panes": [...]}` wrapper. The server takes the conversation's id and the record together on its thread, so both are of one conversation; right after an agent starts, `conversation` can be `null` until the reader has seen its first line. Checked with fakes and fixtures only (`tests/fixtures/claude/2.1.332/thread.jsonl`, the Codex and Vibe readers' records), no real agent.
- **No input box in `read --json`**: the issue also suggested marking the input box's contents in `read --json`, and whether they are Claude Code's grey suggestion rather than typed text. Left out: it needs each agent's screen layout and the cells' styles, which change between versions, and what it was for, knowing what the agent said, is what the record gives.
- **The pending question** (`read --pending`, #951): a phone app, a board or a chat bot that wants to show an agent's question as buttons read its screen and parsed Claude Code's menu, which breaks on any layout change and cannot tell an option's label from its description. `read --pending` prints what the agent waits for from its record instead: `{"pane", "agent", "source", "tool", "command", "questions", "open"}`, each question with `header`, `question`, `multi_select`, `free_text` and `options` numbered from 1 in the record's order (the order Claude Code shows), each with `label`, `description` and `selected`; `null` when nothing is pending. Every key is written, `null` included, so a client reads one shape. It is a request of its own, `pending-question`, and not a field of `status` or `read`, for the reason of `last-message`: an older server would drop the field and print the screen. A feature of the same name lets the command refuse an older server before asking.
- **Where it comes from**: Claude Code 2.1.332 writes each tool call as an `assistant` line of its own (the calls of one answer share `message.id`, with other lines between them) as soon as it asks, and the call's result only once it is answered, as a `user` line with a `tool_result` block naming the call's id; the `hook_success` attachment after a call names its id too and is no result. The reader (`agents::claude::awaited`) walks the transcript backwards: results seen so far mark their calls answered, the newest `assistant` line fixes the answer, the calls of that answer still without a result are pending, and a prompt or another answer ends the walk. An `AskUserQuestion` among them is a `question`; else the first call in the agent's order that is not a subagent (`Agent`, `Task`, whose own permissions are in the subagent's transcript and not read) is a `permission`, with its `tool` and, for a shell, its `command`. `ExitPlanMode` is a permission like any other tool, since that is what the record says. Sidechain lines and `isMeta` user lines are skipped.
- **Only while waiting**: a tool that waits for a permission and one that runs read the same in the transcript, so the server reads the record only while the session file says `waiting` (`Status::Waiting`) and answers `null` otherwise, without reading; else every running shell command would be a permission. Right after an answer typed with `keys`, the read can still give the question until Claude Code writes the result. A wait the record does not say (a `/model` menu, the trust question) is `null` too: `status` shows it as `waiting` with its dialog, and `read` prints the screen.
- **What is left null**: `selected` and `open` are always `null`: the highlighted option and the open tab of several questions are only on the screen, and `null` is better than a guess (even one question may be on Claude Code's submit tab). `free_text` is always true, since Claude Code always offers to type an answer. A permission has no `questions`: its menu (`Yes`, `Yes, and don't ask again`, `No`) is drawn, not recorded; `tool` and `command` say what is asked, and a client that wants the buttons reads the screen for them.
- **Only Claude Code**: Codex writes no approval request to its rollout (`tests/fixtures/codex/README.md`) and the other agents were not checked, so their panes, and a shell, fail with the reason (`Known::tells_awaited`) instead of `null`, which would claim that nothing is pending. Several targets work as for `--last-message`: `{"panes": [...]}`, exit 3 when one fails, and a target with nothing pending is `{"pane" or "tab": id, "source": null}`, since the server's `null` does not say which target it is. Checked 2026-11-27 with Claude Code 2.1.332 on macOS: a call on disk before its result, and the shapes of a question, its answer and its rejection in finished transcripts. The fixtures (`tests/fixtures/claude/2.1.332/`) are written to those shapes with invented texts, ids and paths, not cut from one file.
