# Commands for scripts and agents › A versioned contract

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- **A versioned contract** (#283, `control/contract.rs`, `app/control/contract.rs`, `cli/contract.rs`): an external UI or a script written for one release talks to the server of another, and before it had no way to ask what that server understood: an unknown command answered with an error to parse, an unknown field was dropped in silence and the request still succeeded, and an id kept from before a restart could name another pane. The JSON requests already crossed releases (see above), so the contract builds on them rather than on a new transport, and changes nothing a command prints.
  - **Discovery**: the `contract` request (`cornercase contract [--json]`) answers a `control::contract::Descriptor`: `version` (the server's release), `contract` (`CONTRACT`, an integer from 1), `boot`, `operations` (every name of `Command::NAMES` with `available` and, when not, a `reason`; `start-server`, `watch` and `surface` are listed there, additions that do not raise `CONTRACT`), `features` (`boot`, `structured-errors`, `strict-fields`, `views`, `host-events`, `theme`, `notices`, `surface-patches`, `config`, `close-unlock`, `sound`, `issues`, `todo-panel`, `changes`, `agent-folds`, `accounts`, `account-login`, `account-switch`, `issue-names`, `account-restart`, `close-agent-tabs`, `popup-terminal`) and `streams` (`{"name": "events", "version": 1}`, `{"name": "watch", "version": 1}`, `{"name": "surface", "version": 1}`, `{"name": "view", "version": 1}`, `{"name": "app", "version": 1}`, `{"name": "changes", "version": 1}`). It needs no window, like `status`. `available` is the mechanism for an optional operation that a server can turn off (a feature missing on that machine) while `status` and the rest go on working; a development build lists `update-check` and `update-install` as off (see Updates). Clients read the descriptor leniently (`#[serde(default)]`), so a newer server's extra keys pass.
  - **`boot`** is `control::server_token()` (the server's pid and start time, what `CORNERCASE_SERVER` holds in every pane), and `status --json` carries it too. It changes on every start, `restart` included, since pane, tab and workspace ids start again from 1. A request that names a `boot` other than this server's is refused with `stale-boot` before any id is resolved or anything is done, so a `close` or a `send` kept from before a restart cannot hit the pane that took its id. The older `server` field stays as it was: it only drops the `caller` of another server's pane (a pane reached through `CORNERCASE_SOCKET` is legitimate), and turning it into a refusal would break `cornercase` run inside panes.
  - **Opt-in by two fields of the request**, `contract` and `boot` (either one, not null): a request that carries one is *structured*, and only then do errors take the form `{"error": {"code", "message"}}` and unknown fields fail. Without them every answer is byte for byte what it was (`{"ok": …}` / `{"error": "…"}`): an installed command parses `Response` with serde, and any extra key or an error object makes it fail (checked with serde_json 1), so changing the shape for everyone would break every older CLI talking to a newer server. The CLI itself stays in the legacy mode, so its output and exit codes do not change. A wrapper (`{"contract": 1, "request": {…}}`) was rejected: an older server cannot parse it as a request at all, where two additive fields keep one shape for both modes; the cost is that an older server drops them in silence (below). The mode is kept per client (`Requests::structured`) until it is answered or forgotten; a text that is not JSON cannot say its mode, so it is answered in the legacy shape, which a structured client also reads.
  - **Codes** (`control::contract::Code`, kebab-case, stable): `unsupported` (a command this server does not have, checked by name before parsing, or a `contract` newer than `CONTRACT`: a client written for later rules must not be read under these, so it fails rather than being taken as version 1), `malformed` (JSON that is not a request, or arguments that do not deserialize), `stale-boot`, `not-found` (an id that names no group, project, workspace, tab or pane), `unknown-field`, `busy` and `conflict` (see Driving a tab's terminals; only those requests answer them), `unavailable` (an operation in the list `App::unavailable` gives, which both the descriptor and the request reader use, so a request for it is refused with its reason; a development build, whose `Updates::enabled` is false, turns off `update-check` and `update-install`: `this is a development build, which never looks for updates`, and a release lists none) and `failed` for everything else (`From<String>` on `Refusal`, so handlers keep returning their texts), and `busy` and `conflict` for the requests of Driving a tab's terminals (additive; `send` and `keys` keep `failed`). The `message` is the text a legacy client gets, so the two modes never drift apart; clients branch on the code, never on the message. Internal clients (the queue, the chat bots, flows) keep reading the message.
  - **Strict fields**: in structured mode a key the server does not know, in the envelope or anywhere under `args`, answers `unknown-field` naming its path (`extra`, `args.bogus`, `args.entry.repeat`) instead of being ignored. It is found by serializing the parsed request and comparing keys (`contract::unknown_fields`), since `Request` flattens its command and `deny_unknown_fields` does not work with `flatten`; this relies on no request struct skipping a field when it serializes, so a `skip_serializing_if` added to one would make that field look unknown at its default. The envelope's `contract` and `boot` are the exception: they skip when absent, so the CLI's bytes stay as they were, and a `null` one in the request is dropped before comparing, since serializers that write `None` as `null` (Python's, Go's, serde's without `skip`) would otherwise get `unknown-field` on the first `contract` call, made before the boot is known. Legacy requests keep ignoring unknown fields, which is what `start-with` and `wait-several` were designed around.
  - **Compatibility rules**: fields are added, never renamed or removed, and an older peer ignores what it does not know (answers too: read them leniently, and do not depend on key order, since `events` lines come out sorted); a new behaviour that must not be ignored is a new operation name (as `start-with`, `wait-several`, `restart-when-idle`, `last-message` already are), which an older server refuses by name; `contract` goes up only when something that was there changes meaning or shape, never for an addition, which shows in `operations`, `features` or `streams`. A client calls `contract` first: a server that answers `has no \`contract\` command` (or `Rejected`, from before requests) knows none of this and would ignore `boot` and act, so such a client must not send ids kept from before.
  - **Streams have versions**: `events` lines are format 1 (`EVENTS_VERSION`, the JSON of `control::Event`), pinned by one fixture per event in `tests/fixtures/control/events/v1/` that each test serializes and reads back, so changing the format without a new version fails. `watch` lines are format 1 too (`WATCH_VERSION`), pinned by `tests/fixtures/control/watch/v1/snapshot.json`, a snapshot with a group's style, custom names, a fold and a split `layout` whose leaves are the tab's panes; the test writes it, reads it back and checks the ratio streams as `0.6`. `surface` frames are format 1 too (`SURFACE_VERSION`), pinned by `tests/fixtures/control/surface/v1/frame.json`, which #333's keys (`hyperlinks`, `hyperlink`, `colours`, `underline_style`, `underline_colour`, `overline`) extend as additions left out when empty; `changes` summaries (#339) are format 1 (`CHANGES_VERSION`), pinned by `tests/fixtures/control/changes/v1/` (`summary.json`, `every.json` and `patch.json`, each written and read back), with the feature `changes`. `view` lines (#288) are `watch` format 1 plus `view` and the tabs' `controller` (`VIEW_VERSION`), pinned by `tests/fixtures/control/view/v1/snapshot.json`, and the feature `views` and the operations `view` and `view-set` show in the descriptor. `events` format 1 also has `clipboard` and `bell` (`tests/fixtures/control/events/v1/clipboard.json` and `bell.json`), sent only to readers that asked with `host`, and the feature `host-events` tells a client the field exists. `surface` patch frames (#334) are the same format 1 with a `base`, sent only to subscriptions that asked with `patches`, pinned by `tests/fixtures/control/surface/v1/patch.json`, and the feature `surface-patches` tells a client the field exists. `flow-runs` snapshots and `flow-messages` (#342) are format 1 too, pinned by `tests/fixtures/control/flow-runs/v1/snapshot.json` and `tests/fixtures/control/flow-messages/v1/{backlog,message}.json`, and the flow as JSON by `tests/fixtures/control/flows/flow.json`. The streams of later issues get their own entry in `streams`. Fixtures of the legacy and structured answers (`responses/`) and of the framed postcard bytes of a request and an answer (`postcard/`, hex) pin the rest of what a direct client speaks.
