# Commands for scripts and agents › A versioned contract

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- **A versioned contract** (#283, `control/contract.rs`, `app/control/contract.rs`, `cli/contract.rs`): an external UI or a script written for one release talks to the server of another, and before it had no way to ask what that server understood: an unknown command answered with an error to parse, an unknown field was dropped in silence and the request still succeeded, and an id kept from before a restart could name another pane. The JSON requests already crossed releases (see above), so the contract builds on them rather than on a new transport, and changes nothing a command prints.
  - **Discovery**: the `contract` request (`cornercase contract [--json]`) answers a `control::contract::Descriptor`: `version` (the server's release), `contract` (`CONTRACT`, an integer from 1), `boot`, `operations` (every name of `Command::NAMES` with `available` and, when not, a `reason`; `start-server`, `watch` and `surface` are listed there, additions that do not raise `CONTRACT`), `features` (`boot`, `structured-errors`, `strict-fields`, `views`, `host-events`, `theme`, `notices`, `surface-patches`, `config`, `close-unlock`, `sound`, `issues`, `todo-panel`, `changes`, `agent-folds`, `accounts`, `account-login`, `account-switch`, `issue-names`, `account-restart`, `accounts-revision`, `tour`, `close-agent-tabs`, `queue-undo`, `focus-reveal`, `popup-terminal`, `files`, `shared-files`, `build-folders`, `settings-search`, `flow-issue-prompt`, `machines`, `machine-usage`, `machine-workspaces`, `machine-start`, `search-settings`, `queue-routines`,  `plugin-run-view`, `machine-retry-at`, `against-base`, `flow-run-view`, `notice-subagent`, `mode-default`, `flow-close-when-merged`, `held-after-draft`, `fresh-branches`, `notice-messages`, `surface-wrapped`, `account-login-tab`, `config-agents`, `tunnels`, `tunnels-remembered`, `tunnel-hold`, `queue-results`, `agent-models`, `tunnel-orders`, `tunnel-reverse`, `flow-not-run`, `flow-stopped`, `flow-free-builds`, `machine-tunnels`, `tunnel-hold-ended`, `machine-boot`, `merged-builds`, `flow-exited`, `message-failed` and `streams` (`{"name": "events", "version": 1}`, `{"name": "watch", "version": 1}`, `{"name": "surface", "version": 1}`, `{"name": "view", "version": 1}`, `{"name": "app", "version": 1}`, `{"name": "changes", "version": 1}`, `{"name": "flow-runs", "version": 1}`, `{"name": "flow-messages", "version": 1}`, `{"name": "files", "version": 1}`, `{"name": "config-pair", "version": 1}`, `{"name": "tunnel-orders", "version": 1}`). It needs no window, like `status`. `available` is the mechanism for an optional operation that a server can turn off (a feature missing on that machine) while `status` and the rest go on working; a development build lists `update-check` and `update-install` as off (see Updates). Clients read the descriptor leniently (`#[serde(default)]`), so a newer server's extra keys pass.
  - **`boot`** is `control::server_token()` (the server's pid and start time, what `CORNERCASE_SERVER` holds in every pane), and `status --json` carries it too. It changes on every start, `restart` included, since pane, tab and workspace ids start again from 1. A request that names a `boot` other than this server's is refused with `stale-boot` before any id is resolved or anything is done, so a `close` or a `send` kept from before a restart cannot hit the pane that took its id. The older `server` field stays as it was: it only drops the `caller` of another server's pane (a pane reached through `CORNERCASE_SOCKET` is legitimate), and turning it into a refusal would break `cornercase` run inside panes.
  - **Opt-in by two fields of the request**, `contract` and `boot` (either one, not null): a request that carries one is *structured*, and only then do errors take the form `{"error": {"code", "message"}}` and unknown fields fail. Without them every answer is byte for byte what it was (`{"ok": …}` / `{"error": "…"}`): an installed command parses `Response` with serde, and any extra key or an error object makes it fail (checked with serde_json 1), so changing the shape for everyone would break every older CLI talking to a newer server. The CLI itself stays in the legacy mode, so its output and exit codes do not change, except for a command given `--boot` (see `--boot`). A wrapper (`{"contract": 1, "request": {…}}`) was rejected: an older server cannot parse it as a request at all, where two additive fields keep one shape for both modes; the cost is that an older server drops them in silence (below). The mode is kept per client (`Requests::structured`) until it is answered or forgotten; a text that is not JSON cannot say its mode, so it is answered in the legacy shape, which a structured client also reads.
  - **Codes** (`control::contract::Code`, kebab-case, stable): `unsupported` (a command this server does not have, checked by name before parsing, or a `contract` newer than `CONTRACT`: a client written for later rules must not be read under these, so it fails rather than being taken as version 1), `malformed` (JSON that is not a request, or arguments that do not deserialize), `stale-boot`, `not-found` (an id that names no group, project, workspace, tab or pane), `unknown-field`, `busy` and `conflict` (see Driving a tab's terminals; only those requests answer them), `unavailable` (an operation in the list `App::unavailable` gives, which both the descriptor and the request reader use, so a request for it is refused with its reason; a development build, whose `Updates::enabled` is false, turns off `update-check` and `update-install`: `this is a development build, which never looks for updates`, and a release lists none) and `failed` for everything else (`From<String>` on `Refusal`, so handlers keep returning their texts), and `busy` and `conflict` for the requests of Driving a tab's terminals (additive; `send` and `keys` keep `failed`). The `message` is the text a legacy client gets, so the two modes never drift apart; clients branch on the code, never on the message. Internal clients (the queue, the chat bots, flows) keep reading the message.
  - **Strict fields**: in structured mode a key the server does not know, in the envelope or anywhere under `args`, answers `unknown-field` naming its path (`extra`, `args.bogus`, `args.entry.repeat`) instead of being ignored. It is found by serializing the parsed request and comparing keys (`contract::unknown_fields`), since `Request` flattens its command and `deny_unknown_fields` does not work with `flatten`; this relies on no request struct skipping a field when it serializes, so a `skip_serializing_if` added to one would make that field look unknown at its default. The envelope's `contract` and `boot` are the exception: they skip when absent, so the CLI's bytes stay as they were, and a `null` one in the request is dropped before comparing, since serializers that write `None` as `null` (Python's, Go's, serde's without `skip`) would otherwise get `unknown-field` on the first `contract` call, made before the boot is known. The same goes for the arguments that skip when absent, a `machine` (`start`, `start-with`, `new-workspace`, `flow run`, `stats`, `usage`), a `machine_boot` (#820; `start`, `start-with`, `new-workspace`, `flow-run`, `focus-machine`) and a clone's `files`: a `null` `machine` or `machine_boot` or an empty `files` under `args` is dropped before comparing (`without_null_opt_in`), since it asks for nothing, only in those commands, so a `send` with a `null` `machine` still answers `unknown-field`. Legacy requests keep ignoring unknown fields, which is what `start-with` and `wait-several` were designed around. `flow save` runs the same comparison on the flow it reads (see Flows › Through the server).
  - **Compatibility rules**: fields are added, never renamed or removed, and an older peer ignores what it does not know (answers too: read them leniently, and do not depend on key order, since `events` lines come out sorted); a new behaviour that must not be ignored is a new operation name (as `start-with`, `wait-several`, `restart-when-idle`, `last-message` already are), which an older server refuses by name; `contract` goes up only when something that was there changes meaning or shape, never for an addition, which shows in `operations`, `features` or `streams`. A client calls `contract` first: a server that answers `has no \`contract\` command` (or `Rejected`, from before requests) knows none of this and would ignore `boot` and act, so such a client must not send ids kept from before.
  - **Streams have versions**: `events` lines are format 1 (`EVENTS_VERSION`, the JSON of `control::Event`), pinned by one fixture per event in `tests/fixtures/control/events/v1/` that one test writes and another reads back, every sample in turn, while a third fails on a file there that no sample names (#799), so changing the format without a new version fails. `watch` lines are format 1 too (`WATCH_VERSION`), pinned by `tests/fixtures/control/watch/v1/snapshot.json`, a snapshot with a group's style, custom names, a fold and a split `layout` whose leaves are the tab's panes; the test writes it, reads it back and checks the ratio streams as `0.6`. `surface` frames are format 1 too (`SURFACE_VERSION`), pinned by `tests/fixtures/control/surface/v1/frame.json`, which #333's keys (`hyperlinks`, `hyperlink`, `colours`, `underline_style`, `underline_colour`, `overline`) and #701's `wrapped` extend as additions left out when empty; `changes` summaries (#339) are format 1 (`CHANGES_VERSION`), pinned by `tests/fixtures/control/changes/v1/` (`summary.json`, `every.json`, `patch.json` and `gap.json`, each written and read back), with the feature `changes`. `files` answers and lines (#477) are format 1 too (`FILES_VERSION`), pinned by `tests/fixtures/control/files/v1/` (`listing.json`, `text.json`, `image.json` and `search.json`), with the feature `files`. `view` lines (#288) are `watch` format 1 plus `view` and the tabs' `controller` (`VIEW_VERSION`), pinned by `tests/fixtures/control/view/v1/snapshot.json`, and the feature `views` and the operations `view` and `view-set` show in the descriptor. `events` format 1 also has `clipboard` and `bell` (`tests/fixtures/control/events/v1/clipboard.json` and `bell.json`), sent only to readers that asked with `host`, and the feature `host-events` tells a client the field exists. `surface` patch frames (#334) are the same format 1 with a `base`, sent only to subscriptions that asked with `patches`, pinned by `tests/fixtures/control/surface/v1/patch.json`, and the feature `surface-patches` tells a client the field exists. `flow-runs` snapshots and `flow-messages` (#342) are format 1 too, pinned by `tests/fixtures/control/flow-runs/v1/snapshot.json` and `tests/fixtures/control/flow-messages/v1/{backlog,message}.json`, and the flow as JSON by `tests/fixtures/control/flows/flow.json`. `config-pair` lines (#669) are format 1 too (`CONFIG_PAIR_VERSION`), pinned by `tests/fixtures/control/config-pair/v1/` (`shown.json`, `waiting.json`, `paired.json`, `chat.json` and `failed.json`), and the `tunnel-orders` lines (#776) by `tests/fixtures/control/tunnel-orders/v1/` (`taking.json`, `open.json`, `close.json` and `forget.json`). The streams of later issues get their own entry in `streams`. Fixtures of the legacy and structured answers (`responses/`) and of the framed postcard bytes of a request and an answer (`postcard/`, hex) pin the rest of what a direct client speaks.
- **`stats-cached`** (#675): the feature of the `cached` field of `stats` (additive; see Every machine's stats and usage). `cornercase stats --cached --machine` checks it before it asks, so an older server is refused by name (`the running cornercase server cannot read a machine's last stats without asking it`) instead of dropping the field and waiting for the machine. `cached` skips when false, so a `false` one under the `args` of `stats` is dropped before comparing (`without_null_opt_in`), as a `null` `machine` is, and only there: a `notify` with it still answers `unknown-field`.
- **`flow-close-when-merged`** (#734): the feature of the `close_when_merged` field of `flow-run` and of the `flow-close-when-merged` operation (additive; see Flows › Closing a merged run's agents). `cornercase flow run --close-when-merged` checks it before it sends the field, so an older server, which would drop it and start a run that never closes its agents, is refused by name. The field is skipped when false in the request and in the answers, and `close_when_merged: false` is dropped before the strict-fields comparison (`left_out`, for `flow-run` only).
- **`flow-free-builds`** (#789): the feature of the `free_builds` field of `flow-run` and `flow-close-when-merged` (additive; see Flows › Closing a merged run's agents). `cornercase flow run --free-builds` and `flow close-when-merged --free-builds` check it before they send the field, since an older server would drop it and never free. The field is skipped when false in the requests and in every answer, `free_builds: false` is dropped before the strict-fields comparison (`left_out`, for those two commands), and `--free-builds` without `--close-when-merged` is a usage error (`malformed` on the socket), as is `off` together with `free_builds` on `flow-close-when-merged`.
- **`fresh-branches`** (#745): the feature of the `fresh` field of `start`, `start-with`, `new-workspace`, `flow-run` and `queue` `add`/`edit` (additive; see Worktrees › Where a new branch starts). `--fresh` checks it before sending, so an older server, which would drop the field and branch from `HEAD`, is refused by name; `--no-fresh` checks nothing, since that is what an older local server does; relayed to a machine that has reported, either value is refused by an older one as `unknown-field`. `fresh` is skipped when unset in the three requests relayed to machines, and a `null` one is dropped before the strict-fields comparison (`left_out`, those commands only); `queue`'s `entry` always writes it, as `repeat`, `flow` and `cleanup`.
- **`notice-messages`** (#700, #748): the `message` events of `events --notices` (additive; see Views of your own › Notices without a token). No CLI check: an older server just sends none.
- **`surface-wrapped`** (#701): a pane's `wrapped` in `surface` frames and patches (additive; see Streaming a tab's terminals › Which rows go on in the next one). No CLI check: nothing is sent, and an older server leaves the key out, which only this feature tells apart from no row going on.
- **`account-login-tab`** (#702): the `account-login-tab` request, and a `view` on `account-add` and `account-login-tab` (see Accounts and profiles › Logging in again). `account login` checks it always, `account add` only with `--view`, so an older server is refused naming that machine's `restart` and `update` lines under `--remote`.
- **`tunnels`** (#735): `status`'s `tunnels` and the `tunnel` event exist (additive; the three requests are new names, which an older server refuses by name, so the CLI checks no feature). **`tunnels-remembered`** and **`tunnel-hold`** (#766): the state `closed`, a closed tunnel staying listed, `kind` and `tunnel-forget` (the first); **Compatibility** (why `CONTRACT` stays 1): `tunnels` was one release old, and nothing changes shape, but a 0.13.48 client sees three outcomes differently: `tunnel-close` answers with the port still listed as `closed` (it left the list before), the `tunnel` event on a close says `closed` (it said `gone`; `gone` now means forgotten, the window left or the hold ended), and `status` lists closed tunnels. A client that reads a close as the port leaving the list checks `tunnels-remembered` first, and treats any state but `up` and `opening` as not held. The `tunnel-hold` operation (the second, which `cornercase tunnel hold` checks through `client::use_tunnel_hold`, since an older server would answer a request it does not know with a bare error).
- **`tunnel-orders`** (#776): the requests `tunnel-orders` and `tunnel-failed`, the stream of `{order, port}` lines (`{"name": "tunnel-orders", "version": 1}`, pinned by the fixtures in `tests/fixtures/control/tunnel-orders/v1/`: `taking`, `open`, `close` and `forget`) and `takers` in every tunnel answer (a server from before leaves it out, which reads as 0). `cornercase tunnel orders` checks the feature through `client::use_tunnel_orders`; `tunnel failed` checks nothing, since an older server refuses the name and a program reports only after `tunnel orders` checked. `CONTRACT` stays 1: `takers` is an added key, and the two changed outcomes (`tunnel-open` is not `unavailable`, and `tunnel-close` and `tunnel-forget` are not `not-found`, while a program takes orders) happen only while a connection sent the new request.
- **`tunnel-reverse`** (#794): the `direction` field of `tunnel-hold`, `tunnel-close` and `tunnel-forget`, of the tunnel answers (`tunnels`, `status`) and of the `tunnel` events (`reverse` for a reverse hold, left out for the others), and `tunnel hold --reverse`. It is additive: `CONTRACT` stays 1, every v1 fixture keeps its bytes and readers need no check, since an older server lists no reverse tunnel. The CLI checks the feature before `--reverse` on `hold`, `close` and `forget`, because in the legacy mode an older server drops `direction` and would hold or close a forward tunnel of that port. A `null` `direction` is dropped before the strict comparison (`left_out`, for those four commands only), and `tunnel-open` refuses `reverse` as `malformed`. **Compatibility** (why `CONTRACT` stays 1): a reader that ignores `direction` (any client before 0.13.61) sees a reverse hold as a forward hold of its machine port: its `tunnels` prints `→`, and its `tunnel close PORT` answers `not-found` for a port its own list shows. That happens only while a newer client holds a reverse tunnel, and nothing that worked before changes; a reader of a newer server reads `direction` before it treats a `hold` entry as forward.
- **`machine-tunnels`** (#787): the `tunnels` of each `machines` entry of `status`, `watch` and `view`. Additive, left out when empty, no CLI check: an older server leaves the key out, and only the feature tells that from a machine with no tunnels. See `status` › A machine's tunnels.
- **`tunnel-hold-ended`** (#797): the `{"ended": "closed"|"forgotten"}` line a `tunnel-hold` stream gets before a close or a forget ends it. No CLI check, since a hold only lacks the line on an older server. The CLI's own exit status 7 needs no feature, as with 5. See Remote windows › Tunnelling a port › How a hold ends.
- **`flow-exited`** (#826): `exited` on a role of `flow-runs` and in a workspace's `run` of `status`, `watch` and `view`, and `agents-reopen` also bringing back a flow role whose agent exited by itself (`tabs` empty, the pane's own id). Additive, left out when false or empty, no CLI check: an older server leaves the keys out and its `agents-reopen` answers `conflict`, which is right. See Flows › Through the server and Saved session.
- **`message-failed`** (#824): `failed: true` on a `message` event of `events --notices`, a `flow-merged` whose free of the builds failed, and left out otherwise, so every v1 fixture keeps its bytes. Additive, with no CLI check: an older server never sends it, which only this feature tells apart from a free that went well. See Views of your own › Notices without a token.
- **`merged-builds`** (#811): the `merged_builds` (`bytes`, `count`) of `worktrees` answers, present whenever sizes were measured (zeros included) and left out with `sizes: false`. Additive, no CLI check: an older server leaves it out, which only this feature tells apart from `--no-sizes`. The operation `free-merged-builds` is a new name an older server refuses by name, so the CLI checks no feature; `CONTRACT` stays 1 (see Worktrees › Freeing the builds of merged worktrees).
- **`machine-boot`** (#820): the `machine_boot` field of `start`, `start-with`, `new-workspace`, `flow-run` and `focus-machine`, which `--boot` sends with `--machine`. An older server drops it and starts or shows whatever has that id on the machine now, so the CLI requires the feature first (`client::use_machine_boot`). See Starting work on a machine › The machine's boot.
- **`config-agents`** (#704): the `agents` list in `config`'s answer (additive; see Reading and changing settings › What each agent can do). No CLI check: an older server leaves the key out, and `config --json` prints what it gets.
- **`flow-stopped`** (#802): each live run's `stopped` in `flow-runs` (additive; see Flows › Through the server). No CLI check: an older server leaves it out, which only this feature tells apart from a run that moves. The `warning` key of `send` and `mark` (#805) has no feature, like `close`'s: an older server does not send it, and a client prints it only when there.
- **`flow-not-run`** (#782): each run's `not_run` in `flow-runs` (additive). No CLI check: an older server leaves it out, which only this feature tells apart from every stage having run since the last change.
- **`agent-models`** (#759): the `agent-models` request and the `catalogue` of each entry of `config`'s `agents` (additive; see Reading and changing settings › An agent's whole list of models). No CLI check: an older server refuses the request by name and leaves `catalogue` out, which reads as false.
- **`open-code-workspace`** (#673): the feature for `open`'s `.code-workspace` files and its `into` (additive). `cornercase open --into` checks it before it asks, so an older server is refused by name (`the running cornercase server cannot open a project into a group`). `into` skips when absent, and a `null` one is dropped before comparing, as a `machine` is (Strict fields). See Opening a VS Code workspace.
- **`mode-default`** (#726): `default` as the `mode` of `start-with` and of `queue` `add`/`edit`. An older server refuses it in `start-with` and captures the mode chosen in Settings in `queue`, so `queue add`/`edit --mode default` checks it and `start` doesn't (a server from before it refuses `start --mode default` as a mode it does not know and starts nothing). See Agents › The mode `default`.
- **`bots`** (#844): the operation `bot` and the feature `bots` (additive, `CONTRACT` stays 1). One request name whose `args` are `{"action", "entry"}` (`agents`, `new`, `list`, `edit`, `remove`, `reset`, `seen`, `stop`, `say`, `history`), adjacently tagged as `config`, `machines` and `queue` are, because `control.rs` had no room for ten names under the 1,000-line limit; the request types have no `skip_serializing_if`, so a strict client's unknown-field check works. `cornercase bot` checks the feature before it asks, so an older server is refused by name (`the running cornercase server has no bots`). Also the `bot` event and `status --app`'s `bots` (Bots).
- **`recap`** (#656): the operation `recap` and the feature `recap` (additive). `cornercase recap` checks the feature before it asks, so an older server is refused by name (`the running cornercase server has no recap`). See Recap.
- **`against-base`** (#716): `WorkspaceInfo.against_base` and `changes` for the workspaces views show; absence means not drawn or no base on a new server, nothing on an old one.
- **`held-after-draft`** (#708): `send-now` leaves the Enter to the person over a draft, and the `held` answer has `after_draft`. An older server sends both as one line, so a client checks the feature before telling the person their line stays. The request is unchanged, so the CLI checks nothing. See `send` waits for the person typing › Send now over a draft › Compatibility, for why `CONTRACT` stays 1.
