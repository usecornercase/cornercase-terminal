# Commands for scripts and agents › Colours for programs

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- **Colours for programs** (#331, `control/theme.rs`, `app/theme.rs`, `cli/theme.rs`; `cornercase theme`, `start-server --theme`): every emulator answers OSC 10, 11 and 4 and the light or dark query from the server's `HostTheme`, which only came with the first window's `Hello`. A server started with `start-server` and driven by an external UI kept the defaults for its whole life, so Claude Code, Neovim and delta picked a look the UI did not draw, and `surface` frames (palette indices) disagreed with what the program had guessed.
  - **A request of its own, not a field of `view-set`**: `theme` (operation index 42 in the 43-entry `Command::NAMES`; feature `"theme"`, `CONTRACT` stays 1). Programs see one set of colours per server, since each emulator answers one way. A view belongs to one program and dies with its connection, so tying colours to it would suggest per-view colours that cannot exist and would drop them when that program stops. It takes no view (`--view` is refused, as for every request not in `takes_view`).
  - **The shape is `Hello`'s `HostTheme` wire form** (`foreground`, `background`, `palette`, with `truecolor` accepted and ignored), reused as is. A client theme **requires** the foreground, the background and palette entries 0 to 15; entries 16 to 255 are optional (absent or `null` keeps the emulator's cube and greys). One function checks it (`control::theme::check`), for the server and for the CLI, which refuses a bad file before connecting; the server's refusal is `malformed`, since sending the same theme again cannot work. The request fields never use `skip_serializing_if` (the strict-fields check compares the serialized request); only the answers' optional `theme` does.
  - **Read, set and clear**: `theme` with `theme` sets, with `clear: true` clears, with neither reads; both is `malformed`. The answer is `{"from": "default"|"window"|"client", "scheme": "light"|"dark"|null}`, the same `ThemeInfo` that `status --json`, `status --follow`, `view` lines (`Report::theme`, optional, so the v1 watch fixture is unchanged) and `start-server`'s answer carry. `scheme` comes from `HostTheme::is_light` on the colours the terminals use, the rule the emulator answers `CSI ? 996 n` with.
  - **Precedence**: a client theme beats a window's colours, which beat the defaults. It stays until it is replaced, cleared (`theme --clear`) or the server stops; it is not saved, as views are not, so a client reconnecting after a restart gives it again. With none, the first window gives its colours exactly as before. A window attaching after a client theme draws its chrome with its own colours (`App::theme`) and leaves the terminals alone: its cells are palette indices, so it shows programs' output in its own palette. Clearing gives the terminals the first window's colours if one ever gave them, else the defaults. Among clients, the last theme given wins. `Themes` (`app/theme.rs`) keeps `client_theme` and `window_theme` beside `theme`; terminals spawn with `terminal_theme()` and `paint_terminals` repaints every open one.
  - **`start-server` applies its theme even when the server already runs**, unlike the size, where the first one wins: a UI that starts or reconnects with `--theme` must get its colours, and colours only matter to the program drawing them while concurrent scripts would fight over a size. The theme is checked and applied before the restore, so restored terminals spawn with it, and an invalid one starts nothing. A theme given with `theme` before any window or `start-server` also applies to the terminals the first start opens.
  - **Replacing, not layering**: `Emulator::set_theme` first clears the default foreground, background, palette and the scheme callback, then applies the new theme, so a later theme with less in it leaves nothing of the old one. A program's own OSC overrides survive. `Emulator::new` is unchanged.
  - **Mode 2031**: libghostty-vt 0.2.2 stores mode 2031 and answers `CSI ? 996 n`, but leaves unsolicited reports to the host (`ColorScheme::encode_report`, "hosts should gate unsolicited sends on mode 2031"; full Ghostty does it in its termio, outside the VT library). So cornercase sends them: on every `set_theme` whose scheme differs from the last (unknown to known, or dark to light), a program that turned the mode on gets `ESC [ ? 997 ; 1|2 n` through the emulator's reply sink, the ordered PTY writer that query replies use, which does not count as input. Programs that read OSC 10/11 once at start keep their guess until they ask again: there is no standard beyond 2031.
  - **Older servers**: `theme` is refused by name (`unsupported`). `start-server` with a `theme` field is ignored by an older server in legacy mode, so the CLI checks that the answer carries a `theme` and otherwise exits 1 naming the server's version; structured clients of a server from before this get `unknown-field args.theme`.
  - **Not covered**: the cursor colour, telling programs about colour changes other than light and dark, colours per view, the TUI's own chrome (always the window's) and saving the client theme across restarts.
  - **Tests**: the emulator (scheme reports, the same scheme tells nothing, replacement), the wire types, `app::tests::control_requests::theme` (a real pane asks OSC 11 with a `stty -icanon -echo` probe before and after a change, refusals, precedence), `server::startup::tests::client_colours` (the `Cold` harness: restore with a theme, windows after it, clearing, a running server, an invalid theme) and `e2e::startup`. The fixtures `tests/fixtures/theme/{dark,light}.json` are Tokyo Night and the site's paper theme, and the docs' example.
