# Cloning a repository

Code: `git/clone.rs`, `control/clone.rs`, `app/control/clone.rs`, `cli.rs` (`run_clone`), `cli/help/clone.rs`, #541

- **One operation, `clone`** (index 113 of `Command::NAMES`): `url`, `parent` and `focus`. It runs `git clone` into a new folder inside `parent`, named after the repository as git names it (the URL's last part without `/`, `.git` or `.bundle`, `git/clone.rs` `folder_name`), then opens that folder as a project as `open` does (`App::open_folder`, shared by both: an open project of that path is reused, else `add_project`, so it is saved with the session and shows in the sidebar). It answers `path` (canonical), the project's `project`, `workspace`, `tab` and `pane` ids, and `projection` with `focus`. `CONTRACT` stays 1: a new operation, which an older server refuses by name. There is no button: a person clones from a terminal, a script or another machine (#543 builds on it).
- **The folder is the parent, not the clone**: the request says where clones go (`~/src`), and the clone's own name comes from the URL, so a client that picks a machine and a folder needs no name of its own. The CLI's optional `FOLDER` is that parent: the current folder by default, as `git clone` does, and with `--remote` the other machine's home folder (`~`, expanded by the server), since this machine's current folder means nothing there. A given `FOLDER` follows the `--remote` path rule (absolute or `~/…`); the server refuses a relative `parent` too, as `malformed`.
- **Errors say what failed**: before git runs, a name that cannot be read from the URL is `malformed`, a folder that exists and is not empty (a file included) is `conflict`, and a clone already running into the same folder is `busy` (found among the pending requests, `Stage::Clone`), so two clones never write one folder. An existing empty folder is taken, as git takes it. After git, its stderr is read whole, since `worktree::check` keeps only the last `fatal:` line and ssh's `Permission denied` comes before it: a line saying the repository does not exist or was not found is `not-found`, "`URL` is not a git repository"; one saying permission denied, authentication failed or that git could not read a user name or password is `failed`, "access denied to `URL`"; anything else is `failed` with git's first line ("Connection refused"). GitHub answers "not found" for a private repository it will not show, so that case reads as not a repository.
- **A failed clone leaves no folder behind**: git removes the folder it made, but not the folders above it that `git clone URL a/b/c` also makes (checked with git 2.43). So the target remembers the topmost folder that did not exist (`made`); on failure the clone's folder is removed whole and then each folder above it up to `made`, only while empty (`remove_dir`), so another clone writing next to it in the same new parent keeps its files. A folder that was there and empty stays.
- **Never prompts**: git runs with `GIT_TERMINAL_PROMPT=0`, an empty `GIT_ASKPASS` and `SSH_ASKPASS_REQUIRE=never` (the worktree commands' environment), and its standard input is closed, so a missing credential fails at once with "access denied" instead of hanging a server that has no terminal. The server's ssh keys, agent and credential helpers are used as they are.
- **On a job, answered later**: a clone takes seconds to minutes, so it runs with `spawn_job` and answers through `AppEvent::Cloned`, which brings the window's size for the project's first shell. The request still refuses at once without a size (`NO_SIZE`), as `open` does. The pending entry outlives its client: a command interrupted while git works still gets its project opened, since the clone it asked for is on disk. `clone_answered` takes the entry out before it opens the project, as `worktree_ready` does (see Panics).
- **The log holds no URL**: a URL can carry a token (`https://x-access-token:…@github.com/…`), and git's message may quote it, so the job logs the target folder and, on failure, only the kind (`not a repository`, `access denied`, `git failed`); the field list of the request logs `parent` and `focus`.
- **No timeout**: a clone of a big repository can take many minutes, and `ask` waits with no read timeout, as `start --worktree` waits for git; Ctrl+C ends the command, and the clone goes on.
