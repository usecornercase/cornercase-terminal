# Commands for scripts and agents › Driving a tab's terminals

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- **Driving a tab's terminals** (#287, `control/terminal.rs`, `app/control/terminal.rs`, `app/surfaces.rs`, `cli/terminal.rs`, `cli/terminal/follow.rs`, `cli/args/terminal.rs`; `cornercase input`, `scroll`, `selection`, `resize`, `ratio`): a UI that draws a tab with `surface` has to type into a pane and handle its own mouse without the window in between. A window's keys go through `handle_key`, where a dialog or a field takes them, and its clicks are cells of the window's layout. Five requests of their own (`link`, #333, is a sixth, below), so an older server refuses each by name (`unsupported`) and `contract` lists them; none of them changes `send` or `keys`.
  - **`input`** (`pane`, optional `size`, `events`): an ordered list of `key` (the vocabulary of `keys` without prefixes, `mods` ctrl, alt, shift and super, `kind` press, repeat or release), `text`, `paste` and `mouse` (`kind` down, up, drag, moved and four scrolls, cells of the pane's terminal from 0). It never goes through `App::handle_key`, `handle_mouse` or `handle_paste`: events are encoded by the window's own code (`Emulator::encode_key` with Ghostty, the kitty flags and application cursor; `text` as typed characters through `term::keys::typed`; `Term::pasted`, which `paste` shares, bracketed only when the program asked and unable to end itself; `term::mouse::encode` in the program's mouse mode and encoding) and written to the named pane's `Term`, so a dialog, a focused field, the compact menu or the tab the window shows change nothing. The pane is required: input goes where it is aimed, with no default.
    - **All or nothing**: every event is encoded first and the bytes are written in one `Term::write`, so a malformed event, a cell outside the terminal, a `size` that is no longer the terminal's, or a full queue sends nothing. Events that are well formed but not taken by the program's modes, a mouse event its mouse mode does not report and a key release without kitty's report-event-types flag, are not sent and listed in the answer's `skipped` (`event`, `why`: `mouse`, `release`, or `key` for a press or repeat the encoder has nothing for) rather than refused, since a GUI sends them as they happen; nothing is dropped silently, since what was written is `bytes`. `term::keys::encode` never falls back to the legacy encoding for a release, which would type the key again: the window only forwards presses and `keys` only builds them, so nothing existing changes.
    - Keys, text and pastes bring the pane's view back to the bottom after the write, like the window's (`forward_key`, `handle_paste`); `send` and `keys` still do not. `term.submitted` is left alone: it is `send` and `keys` automation. There are none of `send`'s safeguards (waiting agent, dialog, survey): it is a person typing through another UI, who must be able to answer a permission prompt, and the skill keeps agents on `send` and `keys`. A request is not a use of the shared window size.
    - **Into a plugin's popup** (#456, `cornercase input --popup`): `popup` instead of `pane` aims the events at the popup open in the window, encoded and written by the same code (`type_into`), mouse cells being those of the popup's terminal from 0, as its surface frame numbers them; the answer's `pane` is the popup's term id. With `pane` too, it is the popup the client means, its `popup.pane` from the frames: when the open popup has another id (the one it drew closed and another opened, which a client cannot rule out since the `Detached` of its stream and its `input` cross on the socket), nothing is sent and it answers `not-found`, so a line or a secret meant for one popup never reaches the next one, as a pane id never reaches another pane. Without `pane` it types into whatever popup is open, for scripts that do not care. Additive: `pane` with `popup` was `malformed` before this (an unreleased shape). An older server drops `popup` in legacy mode: it refuses `popup` alone for the missing pane (`malformed`), but takes `popup` with `pane` as `input` to that pane, and a legacy request carries no `boot`, so a stale id is not caught either; a client must check `popup-terminal` before sending `popup` (the CLI does, `use_popup_terminal`). In structured mode an older server answers `unknown-field`. No popup is `not-found`. There is no `send` in flight to wait for in a popup, so that check is skipped; the window's `×` stays the way to close it (and `plugin-popup-close`). `scroll`, `selection` and `link` stay on panes: a popup program scrolls itself, and nothing asked for the rest yet.
    - **Typing through one process** (#478, `cornercase input --follow -`): a client drawing the terminals (#286, #287) started a process per batch of keys, and with `--remote` (#476) an ssh session per batch: a round trip to open the channel and a process start there before the first key leaves, about 18 ms a batch through a shared connection to a local sshd. `--follow` keeps one process and one connection until standard input ends, so it cannot outlive its client (#475).
      - **One request at a time**: the next goes after the answer to the one before, carrying the lines that arrived meanwhile (`recv`, then `try_iter`, as `remote::relay` gathers chunks). The server already supports that on any connection: `Requests` keeps one open request per client (`asked`, `structured`, `callers`) and answers go out in order at `Step::Answer`, so the server, the proxy and the protocol are unchanged. On a slow link, lines group into fewer requests.
      - **Rejected**: sending without waiting for the answers (it saves up to a round trip for a line typed while one is in flight, but needs a thread for the answers and relies on `input` always answering at once); one connection per line; a streaming `input` request of its own (a new operation and format for what one connection already does); the framed protocol through `cornercase proxy` in every client (#344).
      - **All or nothing per request**: a request is consecutive lines for one pane, so order holds. A refused request (`Error::Control`) or a wrong line answers on its own and the next lines go; any other error ends the command with 1. It exits with 3 when some line was not sent (#472).
      - **A line's pane**: `{"pane": 14, "key": …}`, only with `--follow`, so without it a command is still one request for one pane; `--pane` is the default and becomes optional. Parsing goes through `serde_json::Value`, not `#[serde(flatten)]`, which ignores the keys after the first variant it finds. With `--popup`, the pane is the popup's id.
      - **Answer lines**: compact, the server's answer plus `events` (how many lines it answers; blank lines are skipped), with `skipped[].event` counted from the first line read so it keeps its meaning without `--follow`; a refusal is `{"error", "events", "pane"}`, as `read`'s failed entries. Without `--json`, warnings and errors go to stderr with positions over the run.
      - **The server stopping is seen at the next line**: the write's `EPIPE` becomes `ServerGone` (`client::requests::server_left`). It never reconnects: ids change across a restart.
      - **Left for later**: `size` on a line (the socket has it), and sending without waiting if real links call for it (the lines already carry `events`, so their format would not change).
    - Rejected: emulating the window's mouse when the program does not read it (the wheel scrolling history or sending arrows, a drag selecting): those are `scroll` and `selection`, and emulating them would share `App::drag` with the window so the two fight; a mini-language of events on the command line (they are the request's JSON, one per argument, or JSON lines on standard input).
  - **`scroll`** (`pane`, `lines` negative upward, or `to` top or bottom): the window's wheel taken apart. The client reads `modes` and picks `input` (the wheel for a program that reads the mouse, arrows on the alternate screen with alternate scroll) or `scroll` (history). The view is the pane's, shared with every window and surface. It refuses with `conflict` on the alternate screen, which has no history, and while the program reads the mouse, since `Emulator::snapshot` would put the view back at the bottom. It answers with the scrollbar as a frame's `scroll`.
  - **`selection`** (`pane`, `from` and `to` in view cells inclusive, `rectangle`, `clear`, `copy`, optional `size`): Ghostty's own selection (`Emulator::select`, `selection_text`, `clear_selection`), shared and drawn as `inverse` in frames and windows. Without `from`, `to` and `clear` it reads. `copy` goes through `App::copy` (OSC 52 and the window's toast) and refuses with `conflict` when nothing is selected. A window drag and a request at once: the last wins, and an external select drops the window's drag anchor. The answer's `text` is what was copied, so a client without a window can put it in its own clipboard; it is no `clipboard` host event, which are what programs ask.
  - **`ratio`** (`tab`, `path`, `ratio`): `Node::set_ratio` by a frame's divider `path`, the value stored as given between 0 and 1 and clamped by the layout as for a drag; the PTYs follow at once with the window's geometry (`App::resize`). An unknown path is `not-found`. `split` and `close` stay the commands for creating and removing panes.
  - **`resize`** (`surface`, `cols`, `rows`): the surface stream's own layout size, in place. Every frame carries `surface`, the subscription's id from a counter (`Surfaces::issued`, from 1 per server run, additive: `SURFACE_VERSION` stays 1 and an older frame reads as 0). The next frame is complete, at the new size, with the next `revision`. It never resizes a PTY: terminal sizes belong to whoever sizes the tab (see Views of your own), and a surface that follows a view takes the view's size, so `resize` refuses it (`view-set` changes that). Rejected for now: letting `resize` also claim the tab's PTY sizes, which would settle #288's policy (one geometry controller per tab, handoff, inactive observers) by accident.
  - **Codes**: `busy` (the pane's input queue is full, `term::MAX_QUEUED`: nothing was sent, send again once its program reads) and `conflict` (the request no longer fits the target's state: another terminal size, a cell outside it, the alternate screen, a program reading the mouse, nothing selected to copy). Both are additive, so `CONTRACT` stays 1; `send` and `keys` keep answering `failed` for a full queue with their text.
  - **Logging**: they come as fast as someone types or drags, so their request and `answered` lines are at debug (`Command::chatty`) and their refusals at info; fields are counts and sizes (`events`, `keys`, `mice`, `text_bytes`, `paste_bytes`), never the text.
  - **Not covered**: requests on different connections are not ordered (send the next `input` after the answer to the previous one, put several events in one request, keep one `input --follow`, or send the `input` through `requests --follow` with the rest); pane focus and the other navigation stay with `focus` and views.
  - **The path under a cell** (`link`, #333, `control/terminal.rs`, `app/control/terminal.rs`, `cli/terminal.rs`; `cornercase link --pane ID --cell X,Y [--json]`): answers what a click on that cell of the pane's view opens in the window, so a GUI gets cornercase's path detection without copying `files::link` and the foreground-program lookups behind it. The answer is `{"pane", "link"}` with `link` always written, `null` when the cell holds no file, else `path` (canonical, absolute), `inside` (inside the pane's workspace), `workspace`, `relative` (inside only: what the files panel shows), `lines` (`first`, `last`; one line has both equal) and `row`, `start`, `end` (the cells the path takes, end excluded). It resolves against **the named pane's own workspace** and `Term::cwd()` (the foreground program's folder), not the active workspace as the click does (`App::link_at` only handles the active pane); `files::link::under` (`at` then `resolve`) is the one lookup the click, the hover and the request share. Cells are those of the pane's view from 0, as a frame's `lines` and `selection` number them; codes as the other terminal requests (`malformed` without a pane or cell, `not-found`, `conflict` for a cell outside or another `size`). It opens nothing and reports no OSC 8 hyperlink (those are in the frame). The text prints `path`, `path:12` or `path:12-30`, and nothing with status 0 when there is none (an empty answer is not an error, as `search`). It logs at debug (`Command::chatty`), since a GUI may ask on every hover. Rejected: clients copying `files::link` and the process lookups. A path soft-wrapped across rows is not found, as in the window.
