# Commands for scripts and agents › Dialogs, the survey and confirming a prompt was taken

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- **A dialog over the input box, and confirming a prompt was taken** (#128, checked live with Claude Code 2.1.295 and Codex 0.161.0 in a dev server): `send --enter` reported success while Claude Code had its `Shell details` panel open (a background shell's panel: `x to stop`, `Esc/Enter/Space to close`): the paste went into the panel, the Enter closed it, and `--wait` passed its reaction check because the background shell kept the agent `working`. `at_prompt` in `status --json` could not have told: it is whether the pane's *shell* is in the foreground (`Term::shell_in_foreground`, what the restart texts read), false whenever any program runs, and says nothing about an agent's input box; it stays as it is.
  - **No agent says that a dialog is open.** Claude Code's session file has the status (`waiting` covers its permission prompts and questions, already refused) and no field for panels, pickers, the transcript view or the prompt history (checked on 2.1.295), and its title neither; Codex and opencode keep their UI state in memory. The screen is the only signal. Claude Code draws its input box as a line that starts with `❯` right under a rule of `─` (`agents::claude::screen::input_box`); every panel and picker checked live (`Shell details`, `/model`, Ctrl+O's transcript, Ctrl+R's history) replaces that pair, and its suggestion list leaves it. Its shell mode (`!` at the start of the input) draws `!` instead of `❯`, and is refused too: a prompt pasted there would run as a shell command. `/model` (and other pickers) also set the session file to `waiting`, so that refusal comes first; the `Shell details` panel leaves it at `shell`, which is why the incident got through. A screen match breaks when the agent changes its UI, and a check that then refused every send would be worse than none, so it calibrates itself: it counts only once cornercase has seen the box drawn by the running process (`Term::input_seen`, the agent's pid, looked for on each agent read until found), so a version that draws it differently is never refused, only confirmed. Codex's composer marker `›` also marks the choices of its menus, and opencode's input is a box of block characters with nothing that tells it from its dialogs, so neither gets a check. `send` refuses a pane whose agent shows a dialog (`Term::dialog`), with or without `--enter` (a paste alone can press `x`); `--force` sends anyway. `--force` does not lift the `waiting` refusal: that one comes from the agent's own file, and `keys` is how to answer. `status` shows the same check as `dialog` in the JSON and `(dialog open)` in the text.
  - **So the confirmation is the safety net**, from the agent's own record of what it was sent: `send --enter` to Claude Code, Codex, Gemini CLI or opencode answers once the agent has recorded a prompt at or after the moment the request arrived (`agents::context::Pane::prompted`, the newest one its readers saw, kept across a new conversation so that `/clear` counts), and otherwise fails `CONFIRM_WITHIN` (10 s) after the Enter with `not confirmed: the prompt may not have been submitted`. Claude Code: a `user` line with `origin.kind` `human`, a typed slash command (`<command-name>`, as a `user` or `system` line) or shell input (`<bash-input>`), or a `queue-operation` `enqueue`, which it writes at once for a prompt sent while it works (task notifications and other agents' messages are enqueued too, and are told apart by their tag). Codex: an `item_completed` event whose item is a `UserMessage`. opencode: a `user` message, by its `time.created`. Times come from the record (`time::Stamp::parse` for the UTC times Claude Code and Codex write), so a reader that lags a tick cannot take an older prompt for the new one; a record without a time it can read counts from when it was read, so a change of format confirms a little too readily instead of failing every send, which would make scripts send their prompts twice.
  - A Codex that works keeps a prompt sent meanwhile in memory (`Messages to be submitted after next tool call`) and writes it when it takes it, after its next tool call or at the end of the turn (checked live on 0.161.0), so for Codex the 10 s count from the last moment it was seen working or waiting (`holds_prompts`), and `--timeout`, now allowed with `--enter` alone, bounds the wait. Claude Code and opencode write such a prompt at once (checked live: Claude Code 2.1.295 wrote the `enqueue` 5 s into a 20 s Bash call and took the prompt when the call ended, with a `remove` (`absorbed_mid_turn`) and a `queued_command` attachment that do not count again; opencode 1.18.35 writes a `user` row it shows as `QUEUED`), so for them the 10 s are not extended.
  - Matching the text was rejected: Claude Code wraps pastes in `<pasted_content>` tags, agents expand or shorten long pastes, and a confirmation that failed on a transformed text would make scripts send the prompt again; without it, only a prompt someone else submits in the same pane in those seconds can confirm a lost one. Reading the screen after the Enter (the issue's alternative) has the screen's fragility without a fallback. Claude Code's peer messaging socket (`messagingSocketPath` in its session file) would take a prompt without going through the input box, but it is undocumented and needs the token cornercase keeps out of panes. A pane without one of the four (a shell, an agent cornercase does not read) has nothing to confirm against, and `send --enter` returns once Enter is pressed, as before. `start` has no confirmation: a fresh agent has no dialog open, and its launch already waits for the screen.
  - The `agents::claude::fake::FakeClaude::CONTROL` script used by `app::tests::control_requests` and the fake Claude Code of `tests/e2e/commands.rs` writes a prompt record for each line it reads, with a time rounded up to the end of its second (`date` has no milliseconds on macOS), and leaves out what it reads while it shows its fake panel.
  - **Claude Code's feedback survey** (#143, checked live on Claude Code 2.1.296): Claude Code sometimes draws `● How is Claude doing this session? (optional)` and `1: Bad    2: Fine   3: Good   0: Dismiss` in the band right above its input box. The box stays and the session file stays `idle`, so neither check above saw it. One character alone in the empty box answers it (a digit, or what a French keyboard's number row types for one: `&`, `é`…), 400 ms after it is typed or at once on Enter: a pasted `2` rated the session `Fine`, left the box empty, and the Enter after it submitted nothing, so `send --enter 2`, the answer to an agent's numbered question, was lost. A longer text hides the survey and goes to the box, as when a person types over it. The surveys after `/compact`, in a long conversation and about a plugin draw the same answers under their own question (the plugin's adds `4: Unsure`).
  - `send` refuses any text while the survey shows, unless `--force`, and says to dismiss it with `cornercase keys --pane N 0` (`Esc` does not close it). Refusing only a one-character text, all it takes today, was rejected: which keys it takes is Claude Code's undocumented choice, and a longer text closes the survey on the user's behalf, which `send` never does to the agent's own UI. Dismissing it before sending was rejected for the same reason: `0` is an answer, and Claude Code reports it. The survey is rare (Claude Code spaces its appearances out), so a refusal costs one `keys 0`.
  - It is found by its shape, not its words (`agents::claude::screen::survey`): the answers line exactly as Claude Code draws it (two columns in, each answer in a cell of 10 columns, so the same words with other spacing, as in the issue, never match), at most three lines above the input box's rule (the `◐ medium · /effort` hint or a blank line sits between), and above it, through at most three lines indented by two (a wrapped question, the plugin's reason), a line starting with `● ` in the first column, the survey's bullet. Lines higher up never count, so the words in the conversation do not either; nor does a quote ending the last message: Claude Code indents a message under its own bullet and a code block further, and ends each turn with a `✻ … for 3s` line. A message ending with an exact copy of the survey, right above the box, would pass for it if a version dropped that line. Not recognised, so `send` goes ahead as before: a pane under about 44 columns (the answers wrap), the memory survey (blank lines inside its question), and what follows an answer `send` never gives: the thanks line (`Press [1] to tell us more`, gone after a few seconds) and the question asking to share the transcript (`y`, `n`, `d`).
  - `status` shows it as `survey` in the JSON, `(survey open)` in the text and the last column of `--panes` (after `path`, since 0.12.16 shipped the others and new columns only go at the end), apart from `dialog`: a dialog replaces the input box and closes when whoever opened it does, the survey sits above the box and waits for its `0`, so a script that sees `survey` knows what to press without reading the screen, and `dialog` keeps the meaning it had (the two never hold at once). A script that only checks `dialog` still meets `send`'s refusal, which names the key. `keys` sends digits as before: it is how to answer. `read` and the skill say what the survey is, so an agent reading a pane does not take it for the other agent's output.
  - Tests: `agents::claude::screen::tests::survey` holds screens copied from the live Claude Code, quotes of the survey in the conversation among them, and `agents::claude::fake::FakeClaude::CONTROL`, used by `app::tests::control_requests`, draws the survey above its box after a `survey` line and drops it on `0`. The live check ran Claude Code with `CLAUDE_FORCE_DISPLAY_SURVEY=1` (its switch to show the survey at start) and a scratch `CLAUDE_CONFIG_DIR`, against a local fake of the API.
- **A compact command** (#444; `Confirm::compacts`, `keeps_open` in `app/control/wait.rs`): Claude Code writes the `<command-name>/compact` line only when the compaction ends, but with the time of the Enter, after the `system`/`compact_boundary` (2.1.308: boundary 11:14:54.518, the `isCompactSummary` user line 53.568, the `<command-name>` and caveat lines 11:13:53.514, `<local-command-stdout>` 54.612; the compaction took 60 s). The session file says `busy` for all of it (the server log of the incident: working at 11:13:54, idle at 11:14:55), and `send` gave up after `CONFIRM_WITHIN` (10 s) with `not confirmed` while the compaction ran. Two changes, only for a send whose text is the foreground agent's compact command (`Known::compacts`): the window keeps extending while the agent works or waits, as it does for the agents that hold prompts (`holds_prompts`), and a compaction record with a time at or after the Enter confirms it too (`Pane::compaction().at`; the `<command-name>` line already confirmed it once the window was long enough, the boundary is a second proof, and Codex, whose compaction writes no `UserMessage`, is confirmed only by its `compacted` item). A normal prompt to a working Claude Code still fails 10 s after the Enter: Claude writes a prompt sent while it works at once (`enqueue`), so extending every send would turn a lost prompt into a wait for the whole turn (rejected). `--timeout` bounds the wait, and its text says the agent "has not recorded the compaction yet: it is still compacting its conversation". A send that is held while the person types goes through `put_through` later, so it gets the same logic. opencode writes its `user` row at once, so it is confirmed as before; the agents whose `/` commands are local (Gemini, Grok Build, Cursor CLI, Copilot) return after the Enter. Claude Code's `DISABLE_COMPACT` turns `/compact` off, so a send then fails visibly. Tests: `app::tests::control_requests::compacting` extends `FakeClaude::CONTROL` with a `/compact` line that works until the test writes `finish` and then writes only the boundary (so the record, not a prompt line, is what confirms), and `/compact nothing`, which writes none.
