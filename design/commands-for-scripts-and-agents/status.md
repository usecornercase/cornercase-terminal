# Commands for scripts and agents › `status`: the tree, roles and the flat list

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- `status` text is a tree of `kind id  name  details  (marks)` lines for humans and agents; `--json` prints the server's JSON (serde_json sorts the keys).
- **A run member's role** (#378): `PaneInfo.role` is the role the pane plays in a flow run (`Run::role_of`, `orchestrator` included), `null` outside one, always present like `parent`, in `status --json`, `status --follow` and `view` lines, the last column of `status --panes` (`-` without one) and `(role coder)` after `parent` among the pane's marks in the text. Additive, so `CONTRACT` and the stream versions stay 1. `App::refreshed` hashes it: a run is forgotten in `forget_runs`, on the refresh's untraced sync step, and a workspace being removed keeps its stopped panes for a moment, so without it the last snapshot could keep a role on panes whose run is gone. `events` carry no role.
- **A pane's accounts** (#397): `PaneInfo.accounts` maps each agent to the account the pane's shell was given (`Term::accounts`), in `status --json`, `watch` and `view`, and is left out when empty, so the v1 fixtures and a session without accounts are unchanged; `App::refreshed` hashes it. It is a map, not one `account`, because a shell can hold an account for every agent; `account` stays the running agent's. Why it replaced `account_stale` is in Accounts and profiles.
- **A flat list of panes** (#141): `status --panes` prints one row per pane, since every script that coordinates agents started with the same recursive walk of `status --json` (a Python one-liner, or `jq '..|objects|select(has("at_prompt"))'`) to find panes by id, and the tree's text is for reading, not for `awk`. The rows are flattened in the command from the `Report` that `status` already answers (`Report::panes`), so there is no new request: it works against any server that answers `status`, an older one giving the defaults of the fields it lacks (`dialog` false, `at_prompt` null), and plain `status` and `status --json` do not change. A `panes` request computed in the server was rejected for that: a server from before it would refuse it. Each row (`control::PaneRow`) holds what a script filters on: the ids of the pane, its tab, workspace and project; program, agent, status, `background_shell`, `dialog`, `at_prompt`, model and context as `PaneInfo` has them; `caller`, `shown` (the pane the window shows, as `(shown)` in the tree, not every pane of a split tab on screen) and `active` (its tab's active pane); the tab's and workspace's names, the branch, `worktree` and the project's name; the pane's path, in full; `parent` (#347) and `role` (#378), last since columns only go at the end. Groups are left out, as in `events`: nothing runs in them. Rows come in the sidebar's order (`Report::loose`, then `Report::grouped` per group, which the tree's text uses too). Filters (`--agent`, `--status`) were left out: `awk` and `jq` already do that on a flat list, and the issue's own alternative, `jq` recipes in the docs, would still leave every script copying the walk.
  - **Text**: tab-separated, under a header line of the column names, which are the JSON's keys. Tabs because names, models and paths hold spaces, which aligned columns would break for `awk` and `cut`. The header makes the output say what it holds, for an agent or a person reading it, and a filter on a value never matches it; `NR > 1` or `tail -n +2` drops it. The output is the same whether or not it goes to a terminal: switching like `gh` does (aligned with a header on a terminal, bare tab-separated values otherwise) would hide the header from an agent, whose tool is no terminal. A missing value (null, or an empty name) is `-`, never an empty cell: `read` with `IFS=$'\t'` treats tabs as whitespace and merges two in a row, which would shift every column after. Control characters in a name become spaces, so a row stays one line with its columns. The values are the JSON's (`true`/`false`, `context` as a number, absolute paths rather than the tree's `~`), taken from the serialized row (`cli::pane_table`), so the two forms cannot drift apart; a test checks that `PaneRow::COLUMNS` are the row's keys in order. New columns only ever go at the end, so `$7` stays the status. `status` writes through `cli::print_out`, which takes a closed pipe as the end (`quietly`, as `logs` does), since `status --panes | head` is how scripts peek and `println!` panics there.
  - **JSON**: `{"panes": [...]}` rather than a bare list, like every other answer (`wait --any`'s `panes`, `todo list`'s `todos`), which also leaves room for keys next to the list later. Every row has every key, `null` when there is no value, so `jq` sees one shape; keys come in the column order (the struct is printed directly, not through a `Value`, whose map would sort them).
