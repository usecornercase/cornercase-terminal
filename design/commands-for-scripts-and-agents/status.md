# Commands for scripts and agents › `status`: the tree, roles and the flat list

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- `status` text is a tree of `kind id  name  details  (marks)` lines for humans and agents; `--json` prints the server's JSON (serde_json sorts the keys).
- **A run member's role** (#378): `PaneInfo.role` is the role the pane plays in a flow run (`Run::role_of`, `orchestrator` included), `null` outside one, always present like `parent`, in `status --json`, `status --follow` and `view` lines, a column of `status --panes` (`-` without one) and `(role coder)` after `parent` among the pane's marks in the text. Additive, so `CONTRACT` and the stream versions stay 1. `App::refreshed` hashes it: a run is forgotten in `forget_runs`, on the refresh's untraced sync step, and a workspace being removed keeps its stopped panes for a moment, so without it the last snapshot could keep a role on panes whose run is gone. `events` carry no role.
- **A pane's accounts** (#397): `PaneInfo.accounts` maps each agent to the account the pane's shell was given (`Term::accounts`), in `status --json`, `watch` and `view`, and is left out when empty, so the v1 fixtures and a session without accounts are unchanged; `App::refreshed` hashes it. It is a map, not one `account`, because a shell can hold an account for every agent; `account` stays the running agent's. Why it replaced `account_stale` is in Accounts and profiles.
- **A pane's pid and memory** (#436): `PaneInfo.pid` is the pane's shell (`Term::shell_pid`), and `PaneInfo.memory` the bytes its shell and descendants hold (`Term.memory`, see Memory), so a plugin or a script can tell which process a pane is and how much it costs without walking `/proc` from the tab's name. The shell, not the foreground program (`foreground_pid`): the shell is the pane's for its whole life, the program under it comes and goes, and a script that wants the agent walks down from it. `memory` is only what the server measured already, gated by `config.memory` when the answer is built (a figure kept from before the switch went off is not given) and never measured for the request: measuring on `status` would put a walk of every pane's process tree in the server loop, and measuring panes off screen is what the switch avoids. So it is off by default, only measured every 2 s for the tabs on screen, and a pane off screen gives its last figure or none. Both are left out of the tree's JSON when `None`, like `accounts`, so the v1 fixtures of `watch` and `view` do not change, and are the last two columns of `status --panes` (`-` and `null` there, as every column). `memory` goes in `status --follow` and `watch` lines but not in `App::refreshed`'s hash: a figure that moves every 2 s would make a working session send a line every 2 s, so a line carries the figure of when it was built, which can be minutes old, and `status --json` gives the current one. `pid` is hashed already, through `pane_refreshed`. Additive, so `CONTRACT` and the stream versions stay 1.
- **A workspace's Discord post** (#437, see Discord): `WorkspaceInfo.post` is `{"url", "archived"}` (`https://discord.com/channels/<guild>/<thread>`) for a workspace with a post, in `status --json`, `watch` and `view`, and left out otherwise, so the v1 fixtures do not change and `CONTRACT` stays 1. A URL rather than the ids: it is what a client opens, and it keeps the ids as text (see Watching). It shows while the mode is off too, as long as the map and the forum are kept, since the post still exists in Discord. `App::refreshed` hashes it, so a new post moves `watch`.
- **A flat list of panes** (#141): `status --panes` prints one row per pane, since every script that coordinates agents started with the same recursive walk of `status --json` (a Python one-liner, or `jq '..|objects|select(has("at_prompt"))'`) to find panes by id, and the tree's text is for reading, not for `awk`. The rows are flattened in the command from the `Report` that `status` already answers (`Report::panes`), so there is no new request: it works against any server that answers `status`, an older one giving the defaults of the fields it lacks (`dialog` false, `at_prompt` null), and plain `status` and `status --json` do not change. A `panes` request computed in the server was rejected for that: a server from before it would refuse it. Each row (`control::PaneRow`) holds what a script filters on: the ids of the pane, its tab, workspace and project; program, agent, status, `background_shell`, `dialog`, `at_prompt`, model and context as `PaneInfo` has them; `caller`, `shown` (the pane the window shows, as `(shown)` in the tree, not every pane of a split tab on screen) and `active` (its tab's active pane); the tab's and workspace's names, the branch, `worktree` and the project's name; the pane's path, in full; `parent` (#347) and `role` (#378), later `pid` and `memory` (#436), last since columns only go at the end. Groups are left out, as in `events`: nothing runs in them. Rows come in the sidebar's order (`Report::loose`, then `Report::grouped` per group, which the tree's text uses too). Filters (`--agent`, `--status`) were left out: `awk` and `jq` already do that on a flat list, and the issue's own alternative, `jq` recipes in the docs, would still leave every script copying the walk.
  - **Text**: tab-separated, under a header line of the column names, which are the JSON's keys. Tabs because names, models and paths hold spaces, which aligned columns would break for `awk` and `cut`. The header makes the output say what it holds, for an agent or a person reading it, and a filter on a value never matches it; `NR > 1` or `tail -n +2` drops it. The output is the same whether or not it goes to a terminal: switching like `gh` does (aligned with a header on a terminal, bare tab-separated values otherwise) would hide the header from an agent, whose tool is no terminal. A missing value (null, or an empty name) is `-`, never an empty cell: `read` with `IFS=$'\t'` treats tabs as whitespace and merges two in a row, which would shift every column after. Control characters in a name become spaces, so a row stays one line with its columns. The values are the JSON's (`true`/`false`, `context` as a number, absolute paths rather than the tree's `~`), taken from the serialized row (`cli::pane_table`), so the two forms cannot drift apart; a test checks that `PaneRow::COLUMNS` are the row's keys in order. New columns only ever go at the end, so `$7` stays the status. `status` writes through `cli::print_out`, which takes a closed pipe as the end (`quietly`, as `logs` does), since `status --panes | head` is how scripts peek and `println!` panics there.
  - **JSON**: `{"panes": [...]}` rather than a bare list, like every other answer (`wait --any`'s `panes`, `todo list`'s `todos`), which also leaves room for keys next to the list later. Every row has every key, `null` when there is no value, so `jq` sees one shape; keys come in the column order (the struct is printed directly, not through a `Value`, whose map would sort them).
- **The server's home folder** (#477): `Report.home` is the server's `App::home`, in `status --json` and the other places a `Report` is written, left out when unknown so the v1 `watch` and `view` fixtures do not change. A client on another machine (`--remote`, see Remote windows) cannot read `HOME` there, and shows `~/…` for paths under it, as the TUI does; `cornercase status` takes it from the report, falling back to the local `HOME` only when attached to this machine's server. Additive, so `CONTRACT` and the stream versions stay 1.
- **`compacted`** (#444): `PaneInfo.compacted` is true from a compaction until the next reply sets `context` again (see Context use › Compaction), so an empty `context` after a compaction is told apart from "not available". It is there only while true (`skip_serializing_if`, like `collapsed`, so the v1 `watch` and `view` fixtures are unchanged), and the 32nd and last column of `--panes` (every row has it, `false` by default; an older server gives `false`). It is part of what `pane_refreshed` hashes, so `watch` and `--follow` send a line when it flips. The text reads `Opus 5.5 · compacted`, or `compacted` alone. Additive: the contract and the stream versions stay 1. `events` carry no context, so they carry no `compacted`. A role's compact command is not in `flow-runs`: it is static knowledge of the agent, not state, and the action itself, `send`, is already reachable.
- **`shared`** (#252): `WorkspaceInfo.shared` lists, per other workspace of the project whose files overlap this one's, `workspace`, `count` and at most 100 `files` (`SHARED_LISTED`, so a formatter run does not bloat every `watch` snapshot; `count` is the real number). Left out when empty (`skip_serializing_if`), so the v1 `watch` and `view` fixtures are unchanged, and a workspace in a project with one checkout never has it. `App::refreshed` hashes it, so `watch` and `status --follow` send a line when it changes; the plain text of `status` says `shares 2 files with workspace 12, 3 with workspace 14`. It is read from the background scan in memory, never from git while answering (see Shared files). Additive: the contract and the stream versions stay 1; the feature is `shared-files`.
- **A project's remotes and repository** (#542, see Remote windows › A repository's identity): `ProjectInfo.remotes` lists its git remotes (`name`, `url` without its secrets: the user and password of a URL whose scheme is not ssh's (`http(s)`, where a token goes, `git://`, or one git would not parse, such as a leftover quote), and only the password of an `ssh://`, `git+ssh://` or `ssh+git://` one, since an ssh user such as `git@` is no secret and the URL must still clone) and `ProjectInfo.repo` its identity (`github.com/acme/web-shop`), both left out until the project's job read them and when there are none, so the v1 fixtures do not change. Each server publishes its own, since only it can resolve its ssh aliases.
- **A machine's workspaces** (#542, `control/machines.rs`, `app/machines/report.rs`; feature `machine-workspaces`): `Report.machines` has one entry per listed machine that has sent a snapshot: `name`, `icon`, `state`, `seen` (when its last snapshot arrived here, not when the link came up: the link stays up while the snapshots stop), its server's `boot` and its `projects`, each marked with `machine` and with `paired` (the id of the project here it pairs with, or `null`), `group` always `null` (a machine's groups are not ours), and each workspace with `machine`. `Report.shown_remote` (`machine`, `boot`, `project`, `workspace`, `tab`, `path`) is the machine's workspace the window shows, from `App::shown_remote()`. Both are left out when empty, and `paired` is absent on the projects here, so the v1 fixtures and older clients are unchanged and `CONTRACT` stays 1.
  - **Apart from `projects`**, not mixed into it: a machine's ids come from another server, and an older client would take them for ours (`status --panes`, `send --pane`, a workspace by its id). `machine` and `paired` are there so another UI can draw the same sidebar.
  - **The text** lists each machine after what is here: `machine vps  ☁  linked` (or `unreachable · seen 2 min ago`, plain `unreachable` if it was never seen), then its tree one level in, with full paths (this computer's home means nothing there), `paired with project 3` on a paired project, and `(shown)` on the project, workspace and tab `shown_remote` names, only under that machine and for that `boot`. While a machine's workspace is shown, nothing here is marked `(shown)`, although `shown` in the JSON keeps naming the local place (it is where the window goes back to): two `(shown)` lines would leave a reader guessing which one the window shows. A `--view` keeps its own `(view)` marks, since they say what the view shows, not the window.
