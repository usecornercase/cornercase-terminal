# Commands for scripts and agents › Views of your own, and what a view sees

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- **Views of your own** (#288, `project/view.rs`, `app/views.rs`, `control/view.rs`, `cli/view.rs`; `cornercase view`): #283 to #286 let an external program read the session and a tab's cells, but it shared one selection with the window and could not own a size: `focus` moved everybody, and `surface` laid out at its size while the PTYs kept the window's. A **view** is a context a program opens over the socket: its own project, workspace and tab selection, an optional size, an active flag.
  - **Lifetime**: `view` is a stream request (answered with the first snapshot, then one line per change on that connection), and the view lives while its connection does (`App::forget` → `forget_views`). No close request: a crashed program releases nothing by hand. One view per connection (a second is `failed`); views are never saved and die with the server (`boot` changes). A view's id comes from the item counter, so it never equals another id of the run. Its lines are `watch` snapshots (`Snapshot`, one revision per view stream) whose `Report` carries `view` (`ViewInfo`: `id`, `projection`, `active`, `cols`, `rows`, `shown`, `controls`, `visible`), paced and held for slow readers like `watch`'s (`publish_views`; a change the view itself made skips the 500 ms pacing for the view's line only, never for `watch` readers, whose build stays due; a line to a view opens the pacing window as a `watch` line does). Rejected: a view without an owner connection (nothing releases it when the program dies), `watch --view` (per-watcher projections of the global feed would break its one revision), and a `CORNERCASE_VIEW` variable (panes inherit the environment, so a shell started from a GUI's terminal would act in that view by surprise).
  - **Naming it**: the request envelope has `view` (`Request::view`, left out when absent so every old byte and fixture stays; it does not opt into structured mode, and `"view": null` is dropped like `contract` and `boot`). The CLI's `--view ID` sets it for the commands that take one (`control::view::takes_view`: `status`, `focus`, `open`, `new-workspace`, `new-tab`, `split`, `run-setup`, `start`, `send`, `keys`, `held`, `read`, `wait`, `mark`, `rename`, `surface`, `view-set`, `plugin-run` since #666 (see Plugins › Through the server) and `flow-run` since #706 (see Flows › Agents never ask, and starting a run), and `account-add` and `account-login-tab` since #702 (see Accounts and profiles › Logging in again)); any other command refuses it (`malformed`: ``X takes no view``) rather than ignoring it, as #283 asks for every field that matters, and an unknown view is `not-found`. `close`, `queue` and the other `flow` requests refuse it for now. A server without the `views` feature would ignore the field and move the window, so the CLI checks the descriptor once per invocation before sending any `--view`, on the connection its request then takes (#557; a command that first sends a request of its own, such as the `status` lookup of `--worktree BRANCH`, uses that connection for the lookup and opens another for the request) (`client::use_view`, which keeps the id for the process: one invocation, one view). Every request of the invocation carries it but `contract` (`client::requests::view_for`), which describes the server and takes no view: the checks made after `use_view` (`--patches`, `--hidden`, `--visible`, `--issue`, `--profile`, `--account`) sent it there, were refused, and read as a server too old (#461). Leaving the view out of every request that takes none was rejected: a `--view` command whose request took none would then act on the window in silence instead of being refused. Socket clients follow the documented order, `contract` first.
  - **Navigation and defaults**: `Asker { caller, view }` is who asks (the pane it runs in, the view it acts for); `here`, `target`, `here_workspace` and `agent_kind` take it (anything convertible from a bare caller, so the queue and the other flow requests are untouched) and a view beats the caller. `focus --view` and `--focus --view` go through `show_to` (`show` for the window, unchanged): a group goes to its first project without expanding it (folds are shared), a project to its active workspace, a pane also focuses itself (pane focus is shared). They never touch `App::active`, the compact menu, folds or a file shown full screen. The answer carries the view's new `shown` ids and `projection`. The async worktree path keeps the view in `Then` (a flow run's in `Starting`), and skips the focus (logged) if the view closed meanwhile.
  - **Settling** (`project::view::Shown::settle`, pure, after every traced step and at the top of requests and surface renders): the selection is held by id with the last known indices, so a moved row keeps it and a removal falls where the window would: a closed tab to the one before it (else the first), a workspace going away to the nearest open one (earlier first), a closing project to the previous one (else the next), nothing left to an empty selection, which adopts what the window shows when something exists again (it reads the window, never moves it). A settle raises `projection` and is **not a claim**: a close must not silently resize a tab someone else is looking at. So a view moved by a settle controls nothing until it claims again, and its surface is laid out at the view's size while the PTYs keep the size of whoever sizes the tab.
  - **Who sizes a tab**: every tab has one geometry controller, so two programs showing one tab never make a PTY bounce between two sizes. The window (every attached window, which keep mirroring each other, or `start-server`'s size) is the default, sized as before (`layout(area).pane`). A view is eligible while connected, active, sized and showing that tab. Claims share one sequence: a view claims when it opens eligible, turns eligible, navigates (re-focusing the same tab included), or with `view-set --claim` (refused before anything changes if not eligible, with the reason); the window's claim is also dropped when the last window detaches (`App::window_gone`, from `Server::remove`), so a view then takes the tab back; the window claims the tab it shows when it is used (a key, paste or click, the events that make a window the last used, `App::window_used`), and that claim lapses when the window's focused tab changes (the focus, not `visible_tab`, so the compact menu or a full-screen file does not flip sizes). The controller is the latest claim, the window winning ties (`project::view::controller`, a pure function with table tests). Retention and handoff are only that rule re-evaluated: when the controller deactivates, navigates away, closes or disconnects, the tab goes to the latest remaining claim, else the window; the processes stay and are resized once. `size_tabs` gives each tab exactly one area (its controlling view's `cols×rows`, with no sidebar, tab bar or panel, else the window's pane area) and `Term::resize` does nothing when the size is unchanged, so calling it on every draw cannot bounce a PTY. The TUI draws a view-controlled tab in its own rectangle (cropped or blank), and pane mouse events are clamped to the terminal's own size so a click in the blank part never reaches a program beyond its columns. New terminals still spawn at the window's size and are resized within the request that focuses them. Rejected: the first viewer keeps the tab (a GUI left open would hold it, and the person at the window could never get it back), the smallest viewer wins (tmux's `smallest`: a phone would shrink every GUI, and every attach would resize), and a size per pane or per subscription (explicit resize operations come with #287, on top of this ownership).
  - **Active and metadata-only**: a view without a size, or inactive, claims nothing, sizes nothing and renders nothing, but its stream keeps following the session. `view-set --inactive` releases its claim and pauses its surfaces; `--active` resumes and claims. `surface --view` takes the view's tab and size (it refuses `tab`, `cols` and `rows`, and is refused while the view is inactive, sizeless or tab-less, so the first answer is always a whole frame). The subscription resolves tab and size from the view on every render, so it follows navigation; while paused it is neither rendered nor dirty (a dirty sub with a past `next` would make the loop spin), and it ends with `Detached` when its view closes, never because its tab closed (the view settles on a neighbour). `--tab` surfaces are unchanged: passive, they never claim or resize.
  - **Projection**: `projection` starts at 1 and goes up each time what the view's surface shows changes: its tab (navigation or settle), its size, or `active`. Frames of a view surface carry `view` and `projection`, and a change of projection forces a whole frame even if the cells did not change. A client shows a frame only if its `projection` equals the latest it knows for the view; an older one was drawn before its last navigation or activation. `boot` still fences restarts, `revision` orders one stream, and `session` keeps its meaning.
  - **What stays shared** by windows and views: the processes and terminal contents, the split layout and its ratios, the focused pane of a tab (`focus --view --pane` moves it for everyone), the scroll position and the text selection (each terminal has one Ghostty viewport), the active children a view lands on when it navigates to a container, folds and group collapse, and names. Window-only, which views have none of: overlays (but a plugin's popup, which every client can stream and type into, and a view can open since #666), hover, the toast, the compact menu, side panels, column widths, list scrolls and the pointer. Independent history viewports per view are not in this version.
  - **Wire**: `view` and `view-set` are new operations (names 34 and 35), `Report.view`, `TabInfo.controller` (the view sizing the tab, absent for the window), `Done.projection`, `Frame.view` and `Frame.projection` are optional and left out when empty, `CONTRACT` stays 1 (additions only), and the feature `views` and the stream `view` are listed.
  - **Tests**: the pure model (`project/view/tests.rs`: settling, the controller table), the JSON (`control/view/tests.rs`, the `view/v1` fixture), `app::tests::control_requests::views` (two clients on two tabs, a size without chrome, two sizes on one tab with no bounce, handoff, inactive and sizeless observers, coexistence with the TUI and the click clamp, projection fencing, settling, refusals), the server's input path, `client::requests::tests::the_view` and `e2e::views` (which also runs the feature checks of `--view` commands).
- **What a view shows counts as seen, and agent notices for other programs** (#337, `app/views.rs`, `app/notifications.rs`, `app/events.rs`, `control/events.rs`, `control/view.rs`; `cornercase go`, `events --notices`, `view-set --hidden`). A tab counted as seen only when the window showed it (`App::visible_tab`), and being seen takes a `✓` off and keeps an agent from notifying. So a GUI showing a tab in its view (#288) kept the `✓` and got toasts and desktop notifications for the agent it showed. The rules that decide a notice live in `App` (a second's settling, one notice per agent, status and workspace, done only when unseen, flow members quiet, the orchestrator's mark); a GUI rebuilding them from `events` would drift from the TUI and could not act on a notice as a click does.
  - **Seen** (`App::seen_tabs`): the window's visible tab as before, plus the tab of every view that is active, has a size and is visible (`View::sees`): the views that can stream it (`surface --view`). A sizeless or inactive view draws no terminal and sees nothing, and a passive `surface --tab` never sees, as it never claims. `watch_agents` (the `✓`, notices, the orchestrator's mark), `watch_setups` and `setup_finished` (a failed setup's `!` and desktop notification) and `window_focus`'s "already on screen" ask it. The compact `≡`, `window_used` and `App::shows` stay the window's.
  - **`visible`**: a GUI's window can be minimised or behind others while its view stays active, and a hidden GUI must not take marks off. `view` takes `visible` (default true), `view-set` changes it (`--visible`, `--hidden`), and `ViewInfo.visible` reports it (read as true when absent). It changes no claim, size or `projection`, only whether the view sees. Turning a hidden view visible also asks the open pull requests again (see Pull requests, A merge shows sooner). Hiding a view does not notify an agent already waiting: its notice was spent while it was seen, as switching tabs away does in the window.
  - **No window attached**: while a view is open, the window's tab counts only while a window is attached (`App::window_attached` on `Hello`, `window_gone` when the last one leaves). Otherwise a GUI on a headless server never hears about agents in the tab the absent window last focused. With no view nothing changes, window or not. A program that only shows notices opens a view without a size.
  - **Notices on `events`**: `events` takes `notices` (`cornercase events --notices`), and `App::tell`, where every agent notice gets its token, also publishes a `notice` event (format 1): `token`, `agent`, `status`, `place` (control characters stripped), `message` (the toast's text), `panes`, and the `project` and `workspace` ids. One stream rather than a request of its own, as for `host` (#332); a `--pane` reader gets the notices naming one of its panes. Notices are told whatever `desktop_notifications` says (a window's channel; the toast shows anyway). Plugin hooks get none. A notice for which the server chose a sound (see Sound) carries `sound` (`needs-you` or `finished`), left out otherwise (`events/v1/notice-sound.json`; `notice.json` unchanged), under the feature `sound`, so a client plays its own sound by the server's rule instead of rebuilding it. It is the cue the server chose when it made the notice, not a sign that a window played it: a window in a plain `ssh` session, the browser or a machine without a player plays nothing. A subagent's notice (see Agent status › Subagents' notices) carries `subagent: true`, left out for a main agent's (`events/v1/notice-subagent.json`), under the feature `notice-subagent`; with `notify_subagents` off there is no such notice to publish.
  - **A machine's notices** (#542, see Agent status › A machine's agents): a notice about an agent on a linked machine carries `machine` (its name), left out otherwise (`events/v1/notice-machine.json`), under the feature `machine-workspaces`. Its `panes` are the machine's ids and its `project` and `workspace` ids are left at their defaults, since ids here would name other places; a `--pane` reader never gets one, as no pane here can match it. `go` on its token picks the machine's workspace and answers `{}`; with `--view` it is `malformed` and picks nothing. The text line is `machine vps  notice  <message>  <token>`.
  - **`go`** (`{"token": …}`, `cornercase go TOKEN [--view ID]`): what a click does, through `App::act_on_notice`, shared with `notification_clicked`. It drops the notice's toast and the windows' missed marks (also when a view asks: the notice was acted on, so the window's ` go ` and its re-show on focus go too), then shows its first pane still needing you, else the first left, else its open workspace, through `show_to`, so with `--view` it moves and claims like `focus --view` and without it moves the window. An unknown token (another server run, or more than `notify::KEPT` ago) and a notice whose agent and workspace are gone answer `not-found` (the click keeps its gone toast). It answers the ids it went to, and `projection` with a view. A request of its own, so an older server refuses it by name.
  - **Left out**: showing a missed notice again when a view turns visible (the issue's optional part): the client got the notice, knew it was hidden, and reads each pane's `status` and the window's `shown` in its view lines. Chat apps keep their rule: away means you are not at the computer, so a view on screen proves nothing.
  - **Wire**: `go` is operation 43 of 44; `Events.notices`, `OpenView.visible` and `SetView.visible` always serialise (strict fields); `What::Notice` joins events format 1 (`events/v1/notice.json`) and `ViewInfo.visible` view lines (`view/v1/snapshot.json`); the feature `notices` covers all of it and the CLI checks it before `--notices`, `--hidden` and `--visible`. `CONTRACT`, `EVENTS_VERSION` and `VIEW_VERSION` stay 1.
  - **Tests**: `app::tests::agent_status::views` (a `✓` cleared by a view, no notice for a tab a view shows, one notice per settle, a token focusing the view, the no-window rule), `control_requests::{events,views}`, `server::startup::tests` (the attach hook), the wire fixtures and `e2e::views`.
- **Notices without a token** (#700, #748, #824, `App::publish_message` and `MessageKind` in `app/notifications.rs`, `What::Message` in `control/events.rs`): the server's other notices reached only an attached window, its toast and desktop notification, so a program that draws cornercase never heard `cornercase notify` (which still answered 0), a flow member waiting for consent, a failed setup, the queue's, or a run whose agents closed after its pull request merged. Each now also publishes a `message` event (format 1) to `events --notices` readers: `kind`, `message` (the toast's text, control characters stripped, less what only the window can do, below), `panes` (always written), `failed` (below) and the `project` and `workspace` ids when it is about a workspace.
  - **Kinds name what happened, the source first**: `notify`; `queue-started`, `queue-failed`, `queue-missed` (a routine's run only: a one-off entry that missed its time stays silent, as in the window), `queue-kept` (the `state` the entry now has in `status --app`; `queue_notice`, which the routine's cleanup now shares); `setup-failed`; `flow-consent` (see Flows › Agents never ask); `flow-merged` (see Flows › Closing a merged run's agents). Clients read `kind` as a string.
  - **Words a program can act on** (#824): `message` is the toast's sentence less what only the window offers. A merged run's toast ends with ` · ▶ on the workspace reopens them` (`closed_agents::reopen_hint`). A program has no ▶ to press (it reopens with `agents reopen --workspace N`), so its message stops before that part (`closed_words`), and the window keeps it with its ` reopen `. Words are not the format (clients show them as they come), so this needs no feature, and an older server still sends the ▶ part. No other kind names a control of the window: `notify` is the caller's words, the queue's and the setup's say what happened where, and `flow-consent`'s `in its tab` names a tab every client draws.
  - **`failed`** (#824): `true` on the bad ending of a kind that has two, and left out otherwise (`skip_serializing_if`). Only `flow-merged` has two.
    - **When it is set**: with `--free-builds`, when a worktree could not be freed, a folder would not go, or the job itself failed (`builds_said`'s flag, the toast's ✗). A worktree that kept its builds because a program runs there, or because it holds a checkout, is not a failure, as in the toast.
    - **Who carries none**: a kind that is a failure by its name (`queue-failed`, `setup-failed`), because the kind decides it, in the code too (`MessageKind::FlowMerged { failed }`).
    - **Feature**: `message-failed`. An older server never sends the field, so a client checks the feature before taking a missing `failed` to mean a free that went well.
    - **Rejected: a kind of its own** (`flow-merged-failed`). A client that acts on `flow-merged` (cornercase-gpui offers Reopen agents) would show it as an unknown kind and lose that, though the agents closed all the same; and the kind names what happened, which is the close.
    - **Rejected: `ok: false`, the issue's example.** Absent would have to mean true for every other kind, and a streamed line already wraps the event in `{"ok": …}`.
    - **Rejected: counts so a client words it itself** (agents closed, bytes freed). The closed agents are the `panes`. The bytes alone word only a free that went well. The rest (which worktree kept what and why, which folder failed) is the `free-builds` answer per worktree, too much for a notice whose words clients show as they come.
  - **The window's rules**: each is published where its desktop notification is sent (where its toast is set for `flow-merged`, which has none), whatever `desktop_notifications` says. So a failed setup is told only while its tab is unseen, and `agents close` sends nothing: whoever closed knows.
  - **Panes**: `notify` names the pane it ran in (the request's `caller`), so a `--pane` reader of an agent hears what it says with `notify`. `queue-started` names the started pane (and its workspace), `queue-failed` and `queue-missed` name no pane or workspace (the entry may have none yet), `queue-kept` the run's pane (only from this run of the server, since pane ids start over), `setup-failed` the setup's pane, `flow-consent` the member's, and `flow-merged` the closed agents', published before their `closed` events.
  - **No token**: `go` stays for agent notices; a client goes by the ids with `focus`, and `agents reopen` brings a merged run back.
  - **Wire**: `What::Message` (fixtures `events/v1/message.json`, `message-workspace.json` and `message-failed.json`), covered by `Event::notice`, with `Event::about` matching its `panes`; the features `notice-messages` and `message-failed`; `CONTRACT` and `EVENTS_VERSION` stay 1. `message-workspace.json` keeps its bytes, ▶ included: it is what a server from before #824 sends, still a format-1 line a client reads, and only `failed` changed the format, left out there. The CLI needs no new check: an older server sends none, and the text line is `[workspace N  ]<kind>  <message>`, `failed` or not (the words say it).
  - **Left out**: the chat apps (the queue's already reach away chats through `announce`); a machine's messages (the link reads only `watch`; `--remote … events --notices` hears them there); toasts that answer an action of the window or a request (`no agent to close`, the window's own `the flow did not start`, `setup was closed …` after the person closed that pane).
  - **Rejected**: a `notice` with a null token (a client that reads `token` as a string, or passes it to `go`, breaks); each client wording these from state (`notify` and the consent leave nothing to read, and the client would decide when to speak); a stream or request of their own (one `events` connection keeps a merged close before its `closed` events and gives `--pane` for free); sending them to every reader, as `recap` is (a script that never asked would get a line per `notify`); #700's coarse kinds `queue`, `routine`, `setup` and `flow` (the queue's three notices differ in weight, and #748 brings a second flow notice); a severity or icon field (the kind decides it; `failed` only tells apart the two endings of one kind); a token for them (`go` acts on an agent); #748's `closed: "merged"` in `flow runs` (see Flows › Closing a merged run's agents).
  - **Tests**: `control::tests::events_v1` (the fixtures, who a message reaches), `cli::tests::output` (the text line), `app::tests::control_requests::messages` (`notify` for every reader and for a pane's), `control_requests::setup` (only while unseen), `control_requests::flows` (consent), `app::closed_agents::tests` (the sentence and the hint), `flow_end::close_when_merged` (the merged close, its words without the ▶ part, and none for a manual one), `flow_end::free_builds` (the words and `failed` of a free that went well, one that kept builds and one that failed), `control::contract::tests`, `queue` (started, failed, missed, kept) and `e2e::views`.
- A view's lines carry `against_base` and its workspace's `changes`; a hidden view stops the sweep (#716).
