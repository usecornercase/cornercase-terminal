# Commands for scripts and agents › Views of your own, and what a view sees

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- **Views of your own** (#288, `project/view.rs`, `app/views.rs`, `control/view.rs`, `cli/view.rs`; `cornercase view`): #283 to #286 let an external program read the session and a tab's cells, but it shared one selection with the window and could not own a size: `focus` moved everybody, and `surface` laid out at its size while the PTYs kept the window's. A **view** is a context a program opens over the socket: its own project, workspace and tab selection, an optional size, an active flag.
  - **Lifetime**: `view` is a stream request (answered with the first snapshot, then one line per change on that connection), and the view lives while its connection does (`App::forget` → `forget_views`). No close request: a crashed program releases nothing by hand. One view per connection (a second is `failed`); views are never saved and die with the server (`boot` changes). A view's id comes from the item counter, so it never equals another id of the run. Its lines are `watch` snapshots (`Snapshot`, one revision per view stream) whose `Report` carries `view` (`ViewInfo`: `id`, `projection`, `active`, `cols`, `rows`, `shown`, `controls`, `visible`), paced and held for slow readers like `watch`'s (`publish_views`; a change the view itself made skips the 500 ms pacing for the view's line only, never for `watch` readers, whose build stays due). Rejected: a view without an owner connection (nothing releases it when the program dies), `watch --view` (per-watcher projections of the global feed would break its one revision), and a `CORNERCASE_VIEW` variable (panes inherit the environment, so a shell started from a GUI's terminal would act in that view by surprise).
  - **Naming it**: the request envelope has `view` (`Request::view`, left out when absent so every old byte and fixture stays; it does not opt into structured mode, and `"view": null` is dropped like `contract` and `boot`). The CLI's `--view ID` sets it for the commands that take one (`control::view::takes_view`: `status`, `focus`, `open`, `new-workspace`, `new-tab`, `split`, `start`, `send`, `keys`, `read`, `wait`, `mark`, `rename`, `surface`, `view-set`); any other command refuses it (`malformed`: ``X takes no view``) rather than ignoring it, as #283 asks for every field that matters, and an unknown view is `not-found`. `close`, `queue` and `flow` refuse it for now (`flow run --focus` opens the TUI's Flow panel). A server without the `views` feature would ignore the field and move the window, so the CLI checks the descriptor once per invocation before sending any `--view`, on the connection its request then takes (#557; a command that first sends a request of its own, such as the `status` lookup of `--worktree BRANCH`, uses that connection for the lookup and opens another for the request) (`client::use_view`, which keeps the id for the process: one invocation, one view). Every request of the invocation carries it but `contract` (`client::requests::view_for`), which describes the server and takes no view: the checks made after `use_view` (`--patches`, `--hidden`, `--visible`, `--issue`, `--profile`, `--account`) sent it there, were refused, and read as a server too old (#461). Leaving the view out of every request that takes none was rejected: a `--view` command whose request took none would then act on the window in silence instead of being refused. Socket clients follow the documented order, `contract` first.
  - **Navigation and defaults**: `Asker { caller, view }` is who asks (the pane it runs in, the view it acts for); `here`, `target`, `here_workspace` and `agent_kind` take it (anything convertible from a bare caller, so the queue and flows are untouched) and a view beats the caller. `focus --view` and `--focus --view` go through `show_to` (`show` for the window, unchanged): a group goes to its first project without expanding it (folds are shared), a project to its active workspace, a pane also focuses itself (pane focus is shared). They never touch `App::active`, the compact menu, folds or a file shown full screen. The answer carries the view's new `shown` ids and `projection`. The async worktree path keeps the view in `Then`, and skips the focus (logged) if the view closed meanwhile.
  - **Settling** (`project::view::Shown::settle`, pure, after every traced step and at the top of requests and surface renders): the selection is held by id with the last known indices, so a moved row keeps it and a removal falls where the window would: a closed tab to the one before it (else the first), a workspace going away to the nearest open one (earlier first), a closing project to the previous one (else the next), nothing left to an empty selection, which adopts what the window shows when something exists again (it reads the window, never moves it). A settle raises `projection` and is **not a claim**: a close must not silently resize a tab someone else is looking at. So a view moved by a settle controls nothing until it claims again, and its surface is laid out at the view's size while the PTYs keep the size of whoever sizes the tab.
  - **Who sizes a tab**: every tab has one geometry controller, so two programs showing one tab never make a PTY bounce between two sizes. The window (every attached window, which keep mirroring each other, or `start-server`'s size) is the default, sized as before (`layout(area).pane`). A view is eligible while connected, active, sized and showing that tab. Claims share one sequence: a view claims when it opens eligible, turns eligible, navigates (re-focusing the same tab included), or with `view-set --claim` (refused before anything changes if not eligible, with the reason); the window's claim is also dropped when the last window detaches (`App::window_gone`, from `Server::remove`), so a view then takes the tab back; the window claims the tab it shows when it is used (a key, paste or click, the events that make a window the last used, `App::window_used`), and that claim lapses when the window's focused tab changes (the focus, not `visible_tab`, so the compact menu or a full-screen file does not flip sizes). The controller is the latest claim, the window winning ties (`project::view::controller`, a pure function with table tests). Retention and handoff are only that rule re-evaluated: when the controller deactivates, navigates away, closes or disconnects, the tab goes to the latest remaining claim, else the window; the processes stay and are resized once. `size_tabs` gives each tab exactly one area (its controlling view's `cols×rows`, with no sidebar, tab bar or panel, else the window's pane area) and `Term::resize` does nothing when the size is unchanged, so calling it on every draw cannot bounce a PTY. The TUI draws a view-controlled tab in its own rectangle (cropped or blank), and pane mouse events are clamped to the terminal's own size so a click in the blank part never reaches a program beyond its columns. New terminals still spawn at the window's size and are resized within the request that focuses them. Rejected: the first viewer keeps the tab (a GUI left open would hold it, and the person at the window could never get it back), the smallest viewer wins (tmux's `smallest`: a phone would shrink every GUI, and every attach would resize), and a size per pane or per subscription (explicit resize operations come with #287, on top of this ownership).
  - **Active and metadata-only**: a view without a size, or inactive, claims nothing, sizes nothing and renders nothing, but its stream keeps following the session. `view-set --inactive` releases its claim and pauses its surfaces; `--active` resumes and claims. `surface --view` takes the view's tab and size (it refuses `tab`, `cols` and `rows`, and is refused while the view is inactive, sizeless or tab-less, so the first answer is always a whole frame). The subscription resolves tab and size from the view on every render, so it follows navigation; while paused it is neither rendered nor dirty (a dirty sub with a past `next` would make the loop spin), and it ends with `Detached` when its view closes, never because its tab closed (the view settles on a neighbour). `--tab` surfaces are unchanged: passive, they never claim or resize.
  - **Projection**: `projection` starts at 1 and goes up each time what the view's surface shows changes: its tab (navigation or settle), its size, or `active`. Frames of a view surface carry `view` and `projection`, and a change of projection forces a whole frame even if the cells did not change. A client shows a frame only if its `projection` equals the latest it knows for the view; an older one was drawn before its last navigation or activation. `boot` still fences restarts, `revision` orders one stream, and `session` keeps its meaning.
  - **What stays shared** by windows and views: the processes and terminal contents, the split layout and its ratios, the focused pane of a tab (`focus --view --pane` moves it for everyone), the scroll position and the text selection (each terminal has one Ghostty viewport), the active children a view lands on when it navigates to a container, folds and group collapse, and names. Window-only, which views have none of: overlays, hover, the toast, the compact menu, side panels, column widths, list scrolls and the pointer. Independent history viewports per view are not in this version.
  - **Wire**: `view` and `view-set` are new operations (names 34 and 35), `Report.view`, `TabInfo.controller` (the view sizing the tab, absent for the window), `Done.projection`, `Frame.view` and `Frame.projection` are optional and left out when empty, `CONTRACT` stays 1 (additions only), and the feature `views` and the stream `view` are listed.
  - **Tests**: the pure model (`project/view/tests.rs`: settling, the controller table), the JSON (`control/view/tests.rs`, the `view/v1` fixture), `app::tests::control_requests::views` (two clients on two tabs, a size without chrome, two sizes on one tab with no bounce, handoff, inactive and sizeless observers, coexistence with the TUI and the click clamp, projection fencing, settling, refusals), the server's input path, `client::requests::tests::the_view` and `e2e::views` (which also runs the feature checks of `--view` commands).
- **What a view shows counts as seen, and agent notices for other programs** (#337, `app/views.rs`, `app/notifications.rs`, `app/events.rs`, `control/events.rs`, `control/view.rs`; `cornercase go`, `events --notices`, `view-set --hidden`). A tab counted as seen only when the window showed it (`App::visible_tab`), and being seen takes a `✓` off and keeps an agent from notifying. So a GUI showing a tab in its view (#288) kept the `✓` and got toasts and desktop notifications for the agent it showed. The rules that decide a notice live in `App` (a second's settling, one notice per agent, status and workspace, done only when unseen, flow members quiet, the orchestrator's mark); a GUI rebuilding them from `events` would drift from the TUI and could not act on a notice as a click does.
  - **Seen** (`App::seen_tabs`): the window's visible tab as before, plus the tab of every view that is active, has a size and is visible (`View::sees`): the views that can stream it (`surface --view`). A sizeless or inactive view draws no terminal and sees nothing, and a passive `surface --tab` never sees, as it never claims. `watch_agents` (the `✓`, notices, the orchestrator's mark), `watch_setups` and `setup_finished` (a failed setup's `!` and desktop notification) and `window_focus`'s "already on screen" ask it. The compact `≡`, `window_used` and `App::shows` stay the window's.
  - **`visible`**: a GUI's window can be minimised or behind others while its view stays active, and a hidden GUI must not take marks off. `view` takes `visible` (default true), `view-set` changes it (`--visible`, `--hidden`), and `ViewInfo.visible` reports it (read as true when absent). It changes no claim, size or `projection`, only whether the view sees. Hiding a view does not notify an agent already waiting: its notice was spent while it was seen, as switching tabs away does in the window.
  - **No window attached**: while a view is open, the window's tab counts only while a window is attached (`App::window_attached` on `Hello`, `window_gone` when the last one leaves). Otherwise a GUI on a headless server never hears about agents in the tab the absent window last focused. With no view nothing changes, window or not. A program that only shows notices opens a view without a size.
  - **Notices on `events`**: `events` takes `notices` (`cornercase events --notices`), and `App::tell`, where every agent notice gets its token, also publishes a `notice` event (format 1): `token`, `agent`, `status`, `place` (control characters stripped), `message` (the toast's text), `panes`, and the `project` and `workspace` ids. One stream rather than a request of its own, as for `host` (#332); a `--pane` reader gets the notices naming one of its panes. Notices are told whatever `desktop_notifications` says (a window's channel; the toast shows anyway). Plugin hooks get none, and neither do `cornercase notify`, the queue's, a failed setup's and a flow's consent notices, which have no token. A notice for which the server chose a sound (see Sound) carries `sound` (`needs-you` or `finished`), left out otherwise (`events/v1/notice-sound.json`; `notice.json` unchanged), under the feature `sound`, so a client plays its own sound by the server's rule instead of rebuilding it. It is the cue the server chose when it made the notice, not a sign that a window played it: a window in a plain `ssh` session, the browser or a machine without a player plays nothing.
  - **`go`** (`{"token": …}`, `cornercase go TOKEN [--view ID]`): what a click does, through `App::act_on_notice`, shared with `notification_clicked`. It drops the notice's toast and the windows' missed marks (also when a view asks: the notice was acted on, so the window's ` go ` and its re-show on focus go too), then shows its first pane still needing you, else the first left, else its open workspace, through `show_to`, so with `--view` it moves and claims like `focus --view` and without it moves the window. An unknown token (another server run, or more than `notify::KEPT` ago) and a notice whose agent and workspace are gone answer `not-found` (the click keeps its gone toast). It answers the ids it went to, and `projection` with a view. A request of its own, so an older server refuses it by name.
  - **Left out**: showing a missed notice again when a view turns visible (the issue's optional part): the client got the notice, knew it was hidden, and reads each pane's `status` and the window's `shown` in its view lines. Chat apps keep their rule: away means you are not at the computer, so a view on screen proves nothing.
  - **Wire**: `go` is operation 43 of 44; `Events.notices`, `OpenView.visible` and `SetView.visible` always serialise (strict fields); `What::Notice` joins events format 1 (`events/v1/notice.json`) and `ViewInfo.visible` view lines (`view/v1/snapshot.json`); the feature `notices` covers all of it and the CLI checks it before `--notices`, `--hidden` and `--visible`. `CONTRACT`, `EVENTS_VERSION` and `VIEW_VERSION` stay 1.
  - **Tests**: `app::tests::agent_status::views` (a `✓` cleared by a view, no notice for a tab a view shows, one notice per settle, a token focusing the view, the no-window rule), `control_requests::{events,views}`, `server::startup::tests` (the attach hook), the wire fixtures and `e2e::views`.
