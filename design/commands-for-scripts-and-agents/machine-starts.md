# Commands for scripts and agents › Starting work on a machine

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- **Starting work on a machine** (#543, `app/control/relay.rs`, `machines/send.rs`, `app/machine_links/relay.rs`, `app/machine_links/selection/awaited.rs`, `cli/args/machine.rs`, `cli/help/start.rs`; how the window does it is Remote windows › Starting work on a machine): `start`, `start-with`, `new-workspace` and `flow run` take `machine`, a machine's name (any case), and this server sends the request to that machine's server, which starts the work as its own; `cornercase start|new-workspace|flow run --machine NAME` send it (`start` with `--model`, `--mode` or `--effort` sends `start-with`).
  - **The machine's ids**: `project` and `workspace` are the machine's, as `status` lists them under `machines`, and so are the ids answered. A client that knows only this computer's project finds its pair through `paired`. Pairing them here was rejected: a request whose ids mean two things by a field would be easy to get wrong, and `focus-machine` already takes the machine's.
  - **The answer** is the machine's, with `machine` added, and its errors keep their codes (`stale-boot` among them, since the request goes with the `boot` of the machine's last snapshot). A machine not listed is `not-found`, one not linked `unavailable`. `focus` is not sent there, so what starts never takes the focus of the machine's own window.
  - **The relay** (`machines/send.rs`, `app/machine_links/relay.rs`): the request goes over a connection of its own, as a machine's stats do (`spawn_ask`), with the `boot` of the machine's last snapshot, so a machine that restarted since answers `stale-boot` and starts nothing. `machine`, `focus` and the waits are taken out: the machine never relays again.
  - **Caps** (`Send::timeout`): `start`, `flow run` and `new-workspace` with a worktree 10 minutes, the cap of removing a worktree there, since git and the project's setup run first; a plain `new-workspace` 15 s. At the cap the answer is `failed`, `it did not answer in time`, and nothing is retried; what runs there goes on, and the next snapshot shows it.
  - **The log** says `relay` with the machine's name, the verb and the project's id there, never the destination. A refusal from the machine is logged by its code and its size alone: its text may quote a URL, a path or a file there, and the client or the dialog gets it whole.
  - **`focus` here** (`app/machine_links/selection/awaited.rs`): the answer comes before the snapshot that lists what started, so the made tab (for `flow run`, the first member's, the orchestrator) or workspace is awaited and selected as the shown remote once a snapshot lists it. The awaited selection is dropped when the user picks anything else, also between the request and its answer (`Machines::picks` counts the picks, and the relay remembers the count it was sent at), when the machine's `boot` changes or it is removed, and after 30 s.
    - **Not before the machine's first snapshot**: `focus`, or a `machine_boot` (#820), to a machine that is linked but has not sent one is `unavailable` (`has not reported yet; try again`), since without its `boot` nothing could be awaited and `focus` would do nothing without a word, and nothing could be compared. Without either the request goes, with no `boot`.
    - **No view**: `focus` with `machine` and `view` is `malformed` (`relay::viewless`: `start`, `start-with`, `new-workspace`, and `flow-run` since it takes a view, #706), since the shown remote is the window's, shared by every client, as for `focus-machine`.
  - **No waiting**: `wait`, `until` and `timeout` with `machine` are `malformed`, and the CLI refuses `--wait`, `--until` and `--timeout` with `--machine` with the same text. Waiting would hold a relay open for an agent's whole turn over a connection of its own; following the work on the machine with `--remote` already does it.
  - **A field, not new operations**, as for `stats` and `usage`: an older server in legacy mode would drop `machine` and start the work here, so the feature `machine-start`, which the CLI requires (`client::use_machine_start`) before sending it. Skipped when absent, so the requests without it are as before (strict fields). #820 adds the feature `machine-boot` the same way (below).
  - **The machine's boot** (#820, feature `machine-boot`; `machines/send.rs` `same_run`, `app/machine_links/relay.rs` `relayed_boot`, `app/machine_links/selection.rs` `reported_run`): with `--machine` the ids are the machine's, so the envelope `boot`, which this server compares with itself, cannot say which run of the machine they are from. A client that read them from `status --json`'s `machines` entry has that entry's `boot` and sends it as `machine_boot`, an optional string in the `args` of `start`, `start-with`, `new-workspace`, `flow-run` and `focus-machine`, skipped when absent (a `null` one is dropped before the strict-fields comparison). This server compares it with the `boot` of the machine's last snapshot, before relaying or picking: another run is `stale-boot` (status 4) and nothing is sent or picked; a machine that has sent nothing yet is `unavailable`, since nothing can be compared. The order for a relay is: not listed (`not-found`), another run (`stale-boot`), not linked (`unavailable`, with the link's reason), no snapshot (`unavailable`), then the relay with the snapshot's boot as before, so a machine that restarted after its snapshot refuses with its own `stale-boot`, which reaches the client with its code. The comparison comes before the link's state because a machine that is down keeps its last snapshot: `stale-boot` is final for those ids, while `unavailable` invites a retry with them. `machine_boot` is never forwarded (`Send::command` clears it). Without `machine` it is `malformed` (`relay::lone_machine_boot`), since it would be dropped without a word and the work would start here. It is a field of the arguments and not the envelope `boot`: that one is compared before routing with this server's own boot, and one field meaning two servers' boots depending on another would be easy to get wrong; and not a third opt-in key of the structured mode, which would be a second way to ask for it. So the CLI sends `contract` with it, to read the code (see the contract's notes on Which commands). **Rejected**: relaying the client's boot instead of the snapshot's and letting only the machine compare, which costs an ssh round trip per refusal, and which `focus-machine` and the awaited selection cannot do, since they only have the snapshot. **Known gap**: a client that read a newer boot straight from the machine (`--remote vps status`) is refused until this server's snapshot catches up. `stats` and `usage --machine` take no ids, `go` acts on a notice that keeps its machine's boot, and the window's dialogs and folds already go with their snapshot's boot, so no other `--machine` command takes it.
