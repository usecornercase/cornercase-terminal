# Commands for scripts and agents › Reading and changing settings

Part of [Commands for scripts and agents](../commands-for-scripts-and-agents.md).

- **Reading and changing settings** (#336, `control/config.rs`, `app/control/config.rs`, `cli/config.rs`; `cornercase config`): one request, `config` (operation index 43 of 44, feature `"config"`, `CONTRACT` stays 1), tagged by `action` like `queue` (`get`, `set`, `project`, `secret`, `remove`; an action an older server does not know fails to parse, never ignored), and one answer shape for every action: `settings`, `connections`, `projects`, the `revision`, the file's `path`, its `problem` and the `notices` of what changed. `set` takes a map of key to JSON value and is all or nothing: the values are applied in turn to a throwaway model, the first refusal is returned, and only then is the result written through `write_config`. Strict JSON types on the wire; the CLI reads the descriptor first (`config` again, as the `--worktree` lookup does) and converts each `KEY VALUE` by the setting's `type`. Codes: `not-found` for an unknown key, `malformed` for a wrong type or a value the modal's check refuses (its text unchanged), `conflict` for what the state blocks (an environment-variable token, Jira's or Plane's prerequisite, a folder that is not a repository, an unreadable `config.json`; its meaning widens to "does not fit the current state"), `failed` when the service refused a token. **Secrets are write-only**: `issues::Secret` is `transparent` for serde and prints `Secret(..)` in `Debug`; `Configure::fields` logs the action and the key, never a token or a value (`jira_jql` could hold something private, so `set` logs key names only, as the modal's log line does); the check runs the modal's own (`check_token_for` and `check_messenger_for` with the request's key) and answers as a `Stage::Reading` pending when the job ends, with the account, never the token; the modal's open copy is refreshed quietly (`refresh_open_settings`), since `Settings::checked` and `bot_checked` clear the edit field the user may be typing in; the refusal log line prints every message, so none carries a token. The CLI reads a token only from standard input (echo off on a terminal through `rustix::termios`), never from argv. `project` sets a folder's setup, teardown and (#485) `builds`, the folders `free-builds` deletes, through `change_config` (`builds` is a list of names: absent keeps the current one, the defaults store nothing, a bad name is `malformed`, and `ProjectEntry.builds` always answers the effective list; feature `"build-folders"`), only for a repository root (clearing is always allowed), by `project` id or `path`; the editor's line-break rule applies (`ProjectSettings::normalised` turns other control characters into spaces). Removing what is not set answers with a notice (`` `linear` is not set ``), not an error. A request does not take a view (`takes_view` is a whitelist).
- **The shell** (#712): `shell` is the one `text` setting with `choices`, which are suggestions (the shells found on the machine), not a limit: `apply` checks a `choice` against them strictly but a `text` only with the modal's own check, so a client can draw a combobox with free entry. `shell.args` is a dotted sub-key like `agents.<kind>.extra`. Nothing is gated by a feature: a server without it answers `not-found` for `shell`, which says it all. `config set shell /usr/bin/fish shell.args -l` works because the keys are applied in order and setting the program first drops the old arguments.
- **Searching settings** (#561, `settings/search.rs`, `cli/config.rs`; `cornercase config search WORDS [--json]`): a `search` action of `config`, not a field of `get`: an older server fails to parse an unknown action, where a field would be ignored and everything listed. It is the one action with another answer, `{"results": [...]}`, since a result can be a tab or a row with no key, which `Setting` cannot say, and ranked order is the point. Each has `title`, `page`, `section`, `label`, `key` (a setting's or a connection's; an agent's row gives its first; none for a tab, a plugin or an account), `shown`, `note` and `hidden`. It runs `Settings::search`, the modal's matcher. A blank text is `malformed`; no match is an empty answer and exit 0, as `cornercase search`. The feature `settings-search` lets the CLI say so on an older server. The text is logged by its size only, since it may name a private value. `search --settings` gives the same results beside what was said (see Search).
- **Sharing a setup** (#414, `control/config.rs`, `app/control/config.rs`, `app/share_settings.rs`, `cli/config/share.rs`; `cornercase config export [--to FILE]`, `config import FILE|- [--only SECTIONS] [--yes | --preview]`): two commands of their own, `config-export` (operation index 96) and `config-import` (index 97, the last of the 98 in `Command::NAMES`), not new `config` actions: an older server refuses an unknown command by name (and `contract` lists both as operations), where an unknown action would only fail to parse; additive, so `CONTRACT` stays 1 and the feature list is unchanged. `config-export` answers `text` (the TOML, see Settings › Sharing settings), the counts of `settings` and `repositories`, `left_out` (what was not shared and why) and `warnings` (possible secrets), and refuses with `failed` when the text would pass 256 KiB. `config-import` takes `text`, `sections` (optional, every section when left out; an unknown id is `malformed`) and `apply`: without it, it answers the preview (`sections`, each with its `changes` as `key`, `label`, `from`, `to` (a repository's setup and teardown are a change each, keys `repositories.setup` and `repositories.teardown`, labelled with the project's folder, the scripts whole, `nothing` when empty) and its `notes`, then the `notes` of no section, each with a `kind`: `risk`, `missing`, `connect`, `unknown`, `repository`, `secret`; a later kind reads as `other`); with it, it applies the ticked sections and answers like `config get` with the `notices`. Both run the same build, so the preview refuses as an apply would: `malformed` for a file that is not a setup, a newer version, a bad value or two entries matching one project, `conflict` for a folder that stopped being a repository, and, when applying, an unreadable `config.json` (the preview reads the settings in use). The CLI shows the preview on stderr and asks `[y/N]`; reading `-`, or without a terminal, it refuses unless `--yes`, as `flow import` does, and exits 1 on any refusal. `--preview` (#464) sends `apply: false` and exits 0 without asking or applying: the same text on stdout, or the `SetupPreview` with `--json`, so a program can tell a preview from a failure. `malformed` and `conflict`, the refusals a preview already has, still exit 1 and print no preview. `--preview` with `--yes` is a usage error: one only asks, the other applies. The logged fields are the text's size, the sections and `apply`, never the text.
- **Pairing a phone** (#669, #670, `control/pair.rs`, `app/control/pair.rs`, `cli/config/pair.rs`; `cornercase config pair browsers|telegram.chat|discord.chat [--json]`): a client that draws cornercase itself could turn remote access on and paste a bot's token, but connecting the phone needed cornercase's own window, since the code only lived while a dialog was open. Building the link in the client is not an option: only the server accepts the code (`Pairing::accepts`), and asking Discord for the owner needs the bot's token, which no command gives. Writing `browsers.json` would skip the code and is a private file.
  - **One operation for both issues, named after the keys `config remove` takes**: `config-pair`, with `key`. An operation of its own, not a `config` action: it answers a stream where every action answers one document, and an older server refuses the name, so it needs no feature. Any other key is `malformed` and names the three.
  - **A stream, as `watch` is one**: the request is answered at once with the first line, no `Pending`, and the client is kept in `Clients::pairings`. Stream `config-pair`, format 1 (`CONFIG_PAIR_VERSION`), pinned by `tests/fixtures/control/config-pair/v1/`. A line is `{"url", "lines"}`, `url` null while there is none. `App::remote_shown` and `App::chat_shown` give what the dialog draws, so the two cannot drift, without drawing a QR code the command never shows; the refresh compares them per follower and sends a line only when they differ (`Streamed::Snapshot`, since a line replaces every earlier one and a slow reader needs only the newest).
  - **The last line says how it ended**, sent as `Streamed::Event` so a held line goes first and it is not replaced, then `Streamed::End`: `{"paired": true}`, with `chat` (the name the toast says) for a chat, or `{"paired": false, "error"}`. The key `paired` is what tells a last line from the others, on no other line, and under the contract's rule that a key never changes meaning it stays so; a tag on every line as well (`{"event": "shown"}`) was rejected, since it would say the same twice, as `flow-messages` tells its backlog by `messages`. As data, not an error line: stream lines are `{"ok": …}` in both modes, and a client that already follows reads one shape. What cannot start is refused before the stream, with a code: `conflict` for what the client can change (remote access off, no bot, a refused token, a second `config-pair` on one connection), `unavailable` for what it cannot and is known at once (Tailscale not installed, the port taken), `failed` when no code could be made. What only Tailscale's own answer can tell (logged out, HTTPS certificates off) is not a refusal: asking starts Tailscale again, as opening the dialog does, so the first line has `url` null and says it is starting, and the next line has the address or is the last line, saying why not. A bot removed (`config remove`), a token refused or remote access turned off ends it in words, rather than leaving a program drawing a QR code nobody can use.
  - **Ten minutes per command**, the life of a code. A dialog goes on showing a dead code, and a person can see it did nothing; a program cannot, so the command ends with status 1. Renewing the code instead was rejected: a forgotten script would keep a code alive for good, and the limit is the point of it. Discord has no code, but a forgotten command would ask Discord every 3 s for good, so the same limit holds. A `--timeout` was left out: the reader can stop the command whenever it likes.
  - **Two at once share one code** (the window's dialog and a command, or two commands for a key). Whoever comes while a code lives takes it, and its ten minutes start again (`Pairing::shared`), so the dialog opened at minute nine does not show a code about to die, and each command still gets its ten minutes; when a phone takes it, every holder ends (the dialog closes, each command says `paired`); it is dropped when the last holder goes, so closing the dialog does not kill what a command shows, nor the reverse. Rejected: `busy`, since the window cannot be refused without changing it, and a client that reconnects before the server saw it go would be refused; one code per holder, since `Web` and `Messenger` would hold a list and every QR code on any screen would be a live way in; a new code for whoever comes, since it would kill the code a phone is scanning. `App::open_remote` and `App::pair` with no holder make a new code as they always did, and keep what they did otherwise. Keys are independent. The same connection cannot hold two (`conflict`). A browser takes a code on a thread of its own, so its news can reach the app after someone new came and got a new code: `Web` counts the codes taken, `Web::pair` tells each holder the count it came at and `Event::Paired` the count it made, and only holders who came before end, so whoever came after keeps waiting on a code that works. Comparing tokens was rejected: a holder who came before may by then have been shown the new one.
  - **A job already asked**: a Discord job in flight when the last holder goes still connects if it lands with the chat, as when the window's dialog closes. `Bot::pair` has sent the welcome by then, so dropping the answer would leave the owner told they are connected by a bot that ignores them, and the owner is the only person it can pair, with no code to guard. `Every` keeps one in flight, so whoever comes next asks once it lands.
  - **Holding** is one question, `App::pairing_held` (the dialog of that key, or a follower): `sync_remote` and `sync_messenger` drop a code nobody holds, and `owner_due` asks Discord for the owner only while it is held, so what the dialog promised holds for the command. `App::forget` drops it at once rather than at the next refresh, so a phone that scans after the reader left is refused. `Every::closed` runs only for the first holder, so joining does not forget a failure on show or a 429's wait.
  - **The reader going** is what every follow has (#475): `follow_on` watches standard output, and the socket's end reaches `App::forget`. A reader that left and a server that stopped both return `Ok` from it; the command tells them apart with `reader_gone_within(0)`, since the first ends quietly with status 0 as every follow does, and the second must fail: without a last line nothing paired. On Windows a follow notices its reader only at its next write (see Windows › Lifting the refusal), so there the code may live until the ten minutes end.
  - **Nothing changes in the window on its own**: no dialog opens and nothing moves. Once a phone pairs the same toast says so as with the dialog, as `away` by command does: a browser that just paired can type into every shell, and the window is where someone would notice. `config pair` is refused on a line of `requests --follow`, like every stream. `--remote` needs nothing more: the address is the server's, and it goes over the same ssh. Without `--json` it prints the address and the lines, no QR code: a program draws it from `url`, `cli` may not draw through `ui`, and a person at a terminal has the window, or `qrencode`.
  - **The log**: the key, and how it ended (`pairing ended`), never a line: `log_answered` reads only `ended`, the lines go past `log::` altogether, and the words of a failure hold no code. `e2e::pair` greps `server.log` at debug level for the code.
  - **Checked** with the debug build on Linux against a stand-in `tailscale` on the `PATH` and local stand-ins for Telegram's and Discord's APIs, not against the real services or a phone (2026-11-06). On Windows only the unit and app tests run; the bots and Tailscale's `serve` are not tried live there (#603).
- **Picking the Discord forum's server** (#668; `cornercase config forum-server ID`): the operation `forum-server`, not a `config` action, as `config-export` and `config-import` are not. Its answer is the server picked (`id`, `name`), not the `config` shape: a client has no use for the whole description here, and its text is one line. `CONTRACT` stays 1 and no feature is added. See Discord › Picking the server without the window.
