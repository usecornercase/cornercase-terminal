- **One identity per supported agent** (#198, PR 2): `agents/known.rs`, re-exported as `agents::Known`, replaces the string constants, `stats::Kind` and `usage::Agent`. - `agents::launch::Launch` types the command once the shell is quiet, waits until the agent is in the foreground, has drawn something and its screen is quiet, waits for the trust prompt to be answered (or answers it), then pastes the prompt. Readiness is a heuristic. "Drawn something" means the screen is no longer the shell's screen plus the command's echo (or its start, or its end: a typed line taller than the pane, as a Windows line past an npm shim can be, scrolls its first rows off, and so does a full screen, so only the end of the echo shows; found in review), compared without whitespace (`Launch::echo`): the quiet second used to count from the echo, so an agent that took over a second to draw (a loaded machine, a cold start) got the prompt before its trust question and read it as the answer (#34). Waiting for the whole echo was rejected, since rows scrolled off never come back. A screen that is none of these (zsh's `RPROMPT` on the same line) counts as drawn, as before. `AGENT_LATEST` (30 s) still types the prompt into an agent that never draws.
- **The trust prompt is left to the user by default** (`accept_trust_prompts`, off). It is the agent's guard against running a repository's own agent config (project settings, hooks, MCP servers) before anyone looked at it, so answering it for the user would run a hostile repository's config as soon as an issue starts. It used to be on by default, as `auto_accept_trust_prompt`; the key was renamed so every saved `true` (settings save the whole file) falls back to off once, and turning it on again is one click. A per-project "trust this project for agents" was left out: off costs one Enter per issue started, and agents remember the folders already trusted. Whatever the setting, the prompt is detected: a launch that may not answer it parks (`Launch::waits_for_you`) until the agent prints again, which the answer does; its clock restarts from that output, so `AGENT_LATEST` never types into the question, and once the screen is quiet without the question it pastes the prompt. A parked launch is not polled: `App::tick` asks for the 100 ms launch wake-up only for launches that are not parked, since the user may take hours to answer and every wake-up draws every client. Before, a launch with answering off typed the prompt into the question, and Enter picked Claude's highlighted "No, exit". If the user says no, the shell comes back and the launch is abandoned as usual. A flow's launches answer it whatever the setting (`launch::Spec::trusted`, see Flows). `trust_prompt_pattern` is matched only against the last 15 non-blank lines of the screen (`agents::asks_trust`), where an agent draws the question, so older output above cannot match; the regex is compiled once per pattern (`agents::TrustPrompt`).

- **On Windows** (#599, a step of #586; checked on Windows 11 10.0.26200 with fake programs and the unit tests only, since no agent is installed on that machine and cornercase still refuses to run there, see Windows):
  - **Folders**: every default home is built from `paths::HOME_VAR`, `HOME` on Unix and `USERPROFILE` on Windows: `AccountHome::default_home`, the server's Claude folder, `discovery::home` (read from the agent's own environment), opencode's cache and Grok's home (which now goes through `discovery::home` too). `HOME` is not read on Windows even when Git Bash sets it, as for cornercase's own folders (Windows, Folders): Node's `os.homedir()` and Python's `Path.home()` take the profile there, so `HOME` would name a folder the agent never uses. Each agent's own variable still comes first, and a variable is read from an agent's environment by its name in any case on Windows, where names ignore case (`discovery::variable`, and `variable_key` for Claude Code's limits), so `$env:Codex_Home` counts. Sources, read on 2026-11-03: Claude Code's settings page ("On Windows, `~/.claude` means `%USERPROFILE%\.claude`", `CLAUDE_CONFIG_DIR`), also seen on the machine of the check, where Claude Code keeps `projects\C--Users-…` there, the slug `project_dir` makes of a Windows folder (tested); GitHub Copilot CLI's config folder reference (`C:\Users\<user>\.copilot`, `COPILOT_HOME`; its cache is `%LOCALAPPDATA%\copilot`, which cornercase does not read); opencode's troubleshooting page (`%USERPROFILE%\.local\share\opencode` and `%USERPROFILE%\.cache\opencode`, the XDG folders under the profile); Gemini CLI's configuration reference (`~/.gemini`, `GEMINI_CLI_HOME`, no Windows user folder named); Vibe's README (`~/.vibe`, `VIBE_HOME`; it works on Windows but targets Unix). **Not confirmed**: Codex (`CODEX_HOME`, `~/.codex`: the pages read say nothing of Windows), Cursor CLI (`CURSOR_DATA_DIR`, `~/.cursor`) and Grok (`GROK_HOME`, `~/.grok`), whose Windows builds and docs were not read. Paths inside a home are joined one part at a time (`app-server-daemon`, `daemon.pid`; `logs`, `session`, `active`): `discovery::home` canonicalises, which gives a verbatim `\\?\` path on Windows, where `/` is no separator.
  - **Finding and starting a program**: `agents::installed` and what cornercase starts itself (the Claude Code and Codex usage probes, Claude Code's context breakdown, the account login checks) go through `process::program::locate` and `command`, which on Windows look a bare name up on the `PATH` through `PATHEXT`, the lookup #600 wrote for the openers, moved from `host::sound` to `process/program.rs` and shared, with its rule that only the extensions `Command` runs count (Opening in other apps). npm installs an agent as `claude.cmd`, beside a `claude` shell script and a `claude.ps1`, and `Command::new("claude")` never finds it, since `CreateProcess` only adds `.exe`. The `.cmd` is started by its full path, and std runs a batch file through `cmd.exe /c` with its own quoting: tested with the empty argument the Claude probe passes, and checked by hand through a `.cmd` running `node` (Rust 1.99.0, Node on Windows 11), where the breakdown's JSON `--settings`, a folder with a space and a `%` arrived unchanged. A name that has one of those extensions is taken as it is; a path is tried with each extension. On Unix nothing changes: there are no extensions, and `Command::new` gets the name as before. Limit: a probe through a `.cmd` that times out kills `cmd.exe`; the agent under it ends when its standard input closes, right after.
  - **Launching**: a launch is typed into the pane's shell by name, as on Unix, so the shell finds the `.cmd` itself. The default shell on Windows is PowerShell (Windows, Panes in ConPTY), so there the typed line follows PowerShell's rules (`agents::typed_line`, used by every launch and resume line and by flows). The words come from places a cloned repository or an issue controls (a flow role's args, env and model, a model given to `create` or an issue start, a project folder passed with `--add-dir`), so a word must never end its quotes:
    - **Bare only when plain**: a word is left bare only when every character is an ASCII letter or digit or one of `-_./\+=`, it starts with a letter, a digit or one of `-_./\`, and it is not `--`. Everything else is quoted, so `@` (a splat), `$`, `` ` ``, `(`, `{`, `<`, `>`, `#`, `,`, `;`, `&`, `|`, `%` (so `--%`, the stop-parsing token, after which a later `|` starts a command), `:` (a parameter's argument), `--` and every character beyond ASCII, which holds PowerShell's typographic dashes and quotes.
    - **Single quotes, each one doubled**: inside single quotes PowerShell's tokenizer ends the string at `'` and at the typographic single quotes U+2018, U+2019, U+201A and U+201B, so each is doubled with itself, as PowerShell's own `EscapeSingleQuotedStringContent` does (`'a’’b'` reads `a’b`). Doubling only `'` let a folder named `Sergio’s code` or a model like `a’; Write-Output INJECTED; ’` run a second statement (found in review, parsed with PowerShell's parser).
    - **The program** is quoted under the same rule, and also when it starts with `-`, which PowerShell would read as an operator; a quoted program is called with `&`, without which PowerShell reads a quoted first word as a string.
    - **Checked** by `agents::tests::arguments::powershell_parses_each_typed_line_as_one_command_with_the_words_given`, which hands every typed line to Windows PowerShell's own parser (`Parser::ParseInput`) and expects one command whose elements are exactly the words given; the rules themselves are string tests on every system. Windows PowerShell 5.1.26100 also passed the words to `node` unchanged, with exceptions it makes itself: the words it passes on in pieces (next point); an empty word is dropped; and a quoted `'--%'` is still dropped and makes it pass the later words without their quotes, which starts no command, since the line was parsed already, but splits a word with a space (checked live: `'--%'` followed by `'opus --some-flag'` gave `opus` and `--some-flag`), so it is refused too (next point). Escaping `"` as `\"` was rejected: pwsh 7.3 and later pass `"` right to a program (`$PSNativeCommandArgumentPassing`), except to a `.cmd` or `.bat`, so the right escape depends on the pane's PowerShell and on the program, neither known where the line is quoted.
    - **A word PowerShell would pass on in pieces is refused** (#632, `agents::typed_on_windows`, `launch::Step::Refuse`): Windows PowerShell 5.1 builds a program's command line by wrapping a word that holds whitespace in `"` and escaping nothing inside, so a `"` in the word ends those quotes early and a trailing `\` escapes the closing one. Checked live with `node` under 5.1.26100: `'a b" --some-agent-flag "c'` arrived as `a b`, `--some-agent-flag` and `c`, and `'a b\'` followed by `'x --injected y'` as `a b" x`, `--injected` and `y`, so a cloned repository's role argument could hand the agent an option of its own, such as one that skips its permission prompts (found in review; two trailing backslashes are only halved, `'a b\\'` arrived as `a b\`). So on Windows an agent's line is refused, whatever its program (an `.exe`, a `.ps1`, or `node` past an npm shim), when a word holds `"`, or holds whitespace and ends with `\`, or is `--%` (only that word stops PowerShell's parsing: `'--%x'`, `'x--%'` and `'--% '` reached `node` as they were, checked); the toast and the answer name the word, and the log names only the kind of refusal (`Refusal::reason`), never the word, since an argument may hold anything. JSON in `agent_args` or a role's args, which 5.1 used to strip of its quotes (`'{"a":1}'` arrived as `{a:1}`), is refused with it. Escaping was rejected for the reason above: pwsh 7.3 and later pass both words whole, and where the line is checked only the name of the pane's shell is known (next points), not its version nor the `$PSNativeCommandArgumentPassing` its profile may set, so `pwsh` is held to 5.1's rules too (by PowerShell's documentation, pwsh 7.2 and earlier, and `Legacy`, pass words as 5.1 does; no pwsh was checked). A typographic `“` is no quote to the program's command line and went through whole (checked), and so did a `\` inside a word with a space, or at the end of one without. The words are read back from the typed line (`typed_words`), which `agents::tests::arguments::each_typed_line_reads_back_as_the_words_powershell_parses` checks on every system against the same cases PowerShell's parser reads above.
    - **By the pane's shell** (`agents::PaneShell`, `process::program::is_powershell`, the name the Windows `imp` of `term` uses for the folder PowerShell reports): the rules above and the npm shim's line (`& 'node.exe' …` is PowerShell's call) apply when the pane's shell process is `pwsh` or `powershell`, or cannot be read, PowerShell being the default. In a Git Bash pane none of them does: bash and MSYS2 pass `'{"a":1}'`, `'a b" --x "c'`, `--%` and a trailing `\` whole (checked with `node` from Git Bash), so they are typed as before; only a batch file keeps its refusal (below), since MSYS2 hands a `.cmd` to `cmd.exe` too. In a `cmd.exe` pane, which reads `&`, `|`, `<`, `>`, `^`, `%`, `!` and `"` in the typed line itself, whatever the program, a line holding one of them is refused (`a character cmd.exe reads`), and so is a word holding whitespace (`a word cmd.exe would split`), since `cmd.exe` takes PowerShell's single quotes as plain characters: `'x --dangerously-skip-permissions y'` reached `node` as `'x`, `--dangerously-skip-permissions` and `y'` (checked under `cmd.exe /d`). The words are still quoted for PowerShell in every Windows pane (`typed_line` knows the system, not the pane, since a line is built before its pane's shell can be seen), so a Git Bash or `cmd.exe` pane reads some quoted words differently (Limits, below).
    - **Limits**: the settings fields keep `join_args`, the Unix quoting `split_args` reads back. Under `cmd.exe` (the fallback when no PowerShell is on the `PATH`) or a Git Bash `SHELL`, a quoted word reads differently; a flow role's `env` needs an `env` program on the `PATH` (Git's `usr\bin`); PowerShell prefers an npm agent's `.ps1` shim (checked), which the `Restricted` execution policy refuses, as it does when the user types the name.
    - **A batch file never gets a word cmd.exe would read** (`agents::typed_on_windows`, `process::program::powershell_runs`, `launch::Step::Refuse`): when the pane's PowerShell runs a `.cmd` or `.bat` (an npm agent without its `.ps1`, or a batch file named in `agent_commands`), it hands `cmd.exe` a word without spaces as it is, and `cmd.exe` reads `&`, `|`, `<`, `>` and `^` in it (checked under Windows PowerShell 5.1: `'x&hostname'` ran `hostname`), so a cloned repository's role argument or a folder named `R&D` given with `--add-dir` could start a command. Quoting cannot prevent it, since PowerShell builds that command line itself and adds quotes only around a space. So on Windows, before an agent's line is typed, its program is resolved as PowerShell resolves an external command (in each folder of the `PATH`, `name.ps1` before the `PATHEXT` extensions; both checked live: an npm `.ps1` beside its `.cmd` wins, and a `.cmd` in an earlier folder wins over a `.ps1` in a later one), or taken as given when it names a file that is not found. Only agent launches are checked, since their lines are built by `typed_line` and read back here (`typed_words`); a command a client types into a pane is its own PowerShell. Aliases and functions of the user's profile, which PowerShell finds first, are not seen. When the program is a batch file:
      - **An npm shim is passed over** (#632, `process::program::shim`): the line typed starts what the shim would, `node` and the package's script, then the line's own words, so no word reaches `cmd.exe`, whatever it holds. It is typed this way whenever the shim can be read, not only when a word holds one of those characters, so an agent starts the same way in every folder; the process is the `node.exe` the shim would have started, so it is recognised as before (Recognising below), and `launch::Launch` waits on the echo of the line it typed. Only what npm's `cmd-shim` writes is read, compared byte for byte around the script's path (npm 10.9.9, whose `cmd-shim` is 7.0.0): `"%_prog%"` with `_prog` the `node.exe` beside the shim when there is one, else `node`; and a shim of a file without a shebang, which runs that file itself, read only when the file is an `.exe`. `node` on the `PATH` is the one PowerShell would run, and counts only as an `.exe`: a `node.cmd` (or `.ps1`) would hand the words to a shell again. The script's path is the shim's folder joined with its relative path part by part (`..` goes up, so a `node_modules\.bin` shim works), and it must be a file; the shim is read only by a full path, never against the server's working folder, only up to 4 KiB (a longer file is not read), and on a worker thread the server waits on for 2 s at most (as the probes do, `agents::probe`), since the launch runs on the server's loop and a read from a share can stall (found in review; not seen live); a shim not read in time is not read, so the line is checked as any other batch file's, and a worker stuck on it is left behind. The checks that the script and a `node.exe` beside it are files run after the read, in the same folder. A shim on a network share is read like any other: `os::fs::reaches_network` refuses paths that came from someone else (Windows, Network paths), while this one is on the user's own `PATH`, which the lookup has reached already, and skipping it would leave an npm prefix under a redirected `%APPDATA%` with the refusal. The lookup itself (`powershell_runs`) is not bounded in time, as no lookup of a program on the `PATH` is. **Limit**: `node`, like the agent's program, is looked up in the server's `PATH`, which the pane inherits, so a PowerShell profile that changes the pane's `PATH` (fnm's `fnm env`, a version manager's own lines) is not seen, and since `node` is typed by its full path the pane runs the one the server's `PATH` names, not one only the profile adds. Typing `node` bare when there is none beside the shim was rejected: the pane's PowerShell could then find a `node.cmd` or `node.ps1` this check never saw, and the words would reach a shell again. Anything else is not read and keeps the refusal below: a shebang with arguments or variables (`#!/usr/bin/env -S node --no-warnings`, `#!/usr/bin/env FOO=bar node`, which would need the arguments split as `cmd.exe` splits them or the variables set), a path holding `%` (`cmd.exe` expands it), `"`, `:` or `/`, lines ending in `\n` alone, anything after the command, the shapes older npm versions wrote, and pnpm's (`@zkochan/cmd-shim`, read from its source: `@SETLOCAL`, and usually a `NODE_PATH` the shim sets, which typing `node` would lose; it writes a `.ps1` too, which PowerShell runs first); yarn's shims were not checked. Checked live on Windows 11 with Node 22.23.4: a shim npm's own `cmd-shim` wrote in a folder named `R&D` (which `cmd.exe` cannot run at all, since `SET dp0=%~dp0` is unquoted) was read, and the typed line gave `node` `--add-dir`, `C:\Users\me\R&D`, `50%`, `!x!`, `a^b|c`, `<in` and `x&hostname` unchanged; an empty word was dropped, as Windows PowerShell 5.1 does for any program.
      - **Any other batch file is refused such a word**: if the line (the program included) holds `&`, `|`, `<`, `>`, `^`, `%`, `!` or `"` (a `"` is refused for every program, above), the launch is refused instead of typed: a toast and the answer to the request that started it name the character and the batch file. Every word is checked, with or without a space, rather than counting on PowerShell's quotes.
