# Client / server

Code: `client.rs`, `client/`, `server.rs`, `server/startup.rs`, `protocol.rs`, `cli/start_server.rs`, #284

- The server owns the PTYs so shells outlive the UI. The client starts it if needed (`cornercase server`, its output going to `server.log`, see Log).
- **One server per session** (#355): the socket and `server.lock` sit next to `session.json`, and `flock` on the lock keeps one server on them. The server calls `setsid` and ignores SIGHUP.
- **Input failures**: the input thread polls the tty with a 100 ms bound and reads one ready batch. Poll and read run under `panics::contain`; an interrupted system call immediately polls again without clearing partial input, pausing or logging, so SIGWINCH cannot break a split key or mouse sequence. Other transient errors and reader panics clear partial decoder state, log to `server.log` and retry after 20 ms, so a bad fd cannot spin a core. Diagnostics repeat only at powers of two. EOF, hangup, an invalid fd or a gone terminal send `Incoming::InputEnded`, which detaches the window even during remote reconnection; a drop guard also sends it if the input thread unexpectedly unwinds; the server's shells keep running. SIGWINCH supplies resize events through the signal thread. The client's panic hook restores modes, images and ratatui only for its main thread: calling ratatui's previous hook on a contained input panic would disable raw mode, mouse capture and the alternate screen while frames kept arriving. Other threads' panics are logged without touching the terminal. A debug PTY reproduction confirmed this path for zero-coordinate SGR input; a timeout alone did not kill input on Linux, and the original macOS failure's exact bytes remain unknown.
- The server renders, the client only writes frames. Input travels as serialized crossterm events. Several clients mirror each other; the shared size is the last used client's (attach, key, paste or mouse other than a bare move), like tmux's `window-size latest` (windows only: a program that opened a view sizes the tabs it claims, see Views of your own), so a hung client (a phone whose SSH dropped) never shrinks a new one. Ping/pong would not catch that: the hung client is a healthy local process. Smaller clients get the frame cropped by `CropBackend`.
- **Starting without a window** (`cornercase start-server`, #284): a fresh server waited for the first window's `Hello` before it restored the session, so a script or an external UI could not start cornercase, look at its session and launch work without opening a terminal window; every command that creates a terminal answered `NO_SIZE`. `start-server [--cols N] [--rows N] [--json]` starts the server if none runs (`client::connect_or_start`, the same socket, lock and `setsid` as a window; no terminal needed), sends a `start-server` request, and answers once the session is restored and its terminals exist. It is a JSON request, so it skips `Hello`'s build check and needs no colour probe.
  - **One start, whoever comes first**: `Server::startup` is `Waiting`, `Headless` (started by `start-server`) or `Windowed`, replacing the `started` flag. Restoring (`open_first_terminals`, `server/startup.rs`) runs once, on the first `Hello` or the first `start-server`, with the same rules either way: `resume_agents`, the partial restore and its `session.json.bak`, and the folder the server was started from when there is no session (`open_here`, the same rule as a window; a `--no-project` was left for when an external UI needs an empty start). Run again, `start-server` restores nothing and answers `already: true`, so it is also how a caller learns that the start is over. The answer is `control::start_server::Started`: `already`, `restored` (a session was found), `complete`, `cols`, `rows`, `size` (`window` or `start-server`, where the size in use comes from), `boot` and `version`. `restored` and `complete` describe only the call that restored: an `already` answer says `false` and `true`, since keeping the first start's result in `Server` only for a later caller who missed it was not worth the state. When no first terminal opens (`open_here` fails, say the shell cannot start), the answer is an error with the cause rather than a success a script would act on: the server stays `Headless`, so a later call answers `already: true`. It comes when the terminals exist, not when resumed agents are back in their conversations: their resume lines are still being typed (`Launch::command`), and `status` or `wait` say when.
  - **The size without a window**: 160×48 by default, wide enough for the wide layout (`COMPACT_WIDTH` is 90), where 80×24 would give compact mode and panes of another width than a normal window's. `--cols` takes 90 to 1000 and `--rows` 10 to 500 (the browser bridge's caps); one given alone keeps the other's default. A size out of range is refused before connecting, so nothing starts, and the server checks again (`StartServer::size`): structured clients get `malformed`, since retrying the same size cannot work. It is set only while no window gave one (`area` is `None`), and a second `start-server` with another size changes nothing, so the first size wins and concurrent scripts do not fight over it; the answer says the size in use. A window that attaches later takes it over by the usual rule (`fit`, the last used client), and once every window leaves the last size stays. Other requests never claim it, only `start-server` sets it: their connections have no size, so `status`, `events`, `contract`, `stats`, `read` and `wait` neither set it nor start the restore. A program that wants a size of its own opens a view (see Views of your own): the windows keep mirroring each other, and the view sizes the tabs it claims.
  - **Colours come with the first window**: shells made before any window use the emulator's default colours (`HostTheme::default()`). The first window after a headless start gives its theme to every open terminal (`App::retheme`, `Emulator::set_theme` over the same `apply_theme` a new emulator gets) and the start becomes `Windowed`; later windows change nothing, as before. Limit: a program that asked for the colours (OSC 10, 11 or 4) before that window got the defaults and keeps them. When a client gave the terminals colours (`start-server --theme`, `theme`; see Colours for programs), the first window still draws its own chrome with its colours but `retheme` leaves the terminals alone (it returns whether it painted), and says so in the log. With no client theme nothing changed, so a TUI-only setup behaves as before. Whenever `Emulator::set_theme` changes the scheme, a program that turned on mode 2031 is told.
  - **Another build**: since the request skips the build check, a server left from another build (after `brew upgrade`) answers `already`; the command compares the answer's `version` with its own and warns, naming `cornercase restart`, without failing. Same version and another build gives no warning; the next window asks, as it does today.
  - `start` would have read as starting an agent, which `cornercase start` already does, and the docs never say daemon, so the name mirrors `kill-server`. Restoring headless on every start was rejected (see Queue): the request makes it explicit. `cornercase restart` with no window attached still leaves no server, since only windows `exec`; run `start-server` again.
- **Event batches yield after a frame interval** (#493): a continuously printing pane can refill the queue as it is drained, so an empty queue is not a reliable boundary for answering requests, refreshing, drawing, streaming surfaces or saving. The loop checks its elapsed budget after each event and leaves the next event in the queue for the following turn. A single event is still handled to completion; output events are bounded by the reader.
- **When the server draws** (`Server::due`): a frame is drawn when an event other than PTY output arrived (input, a client, a job's answer, a request, a timeout wake-up), when a pane on screen printed (`App::shows`) and `FRAME` (16 ms) has passed since the last frame, and at least every `TICK` (500 ms). Output in a hidden tab draws nothing (a `surface` that streams it renders in its own `Step::Surfaces` after the draw, only for the surfaces that show that pane; see Streaming a tab's terminals): the sidebar's icons and `↓n` come from `refresh` and show within a tick. A visible pane printing without pause gets at most ~60 frames a second, counted from the last frame that showed output (`printed_at`), not from any frame: a key draws at once and its echo, a moment later, draws at once too instead of waiting a frame. Host writes (OSC 52, notifications) go out in their own `Step::Flush` every turn, framed or not. A draw that panics sets `changed`, so the screen is rebuilt on the next draw (forcing an immediate turn instead would spin while a draw keeps panicking). The session is observed at most every `SAVE_EVERY` (500 ms), since building `App::state()` looks up every pane's cwd and the `Saver` waits 2 s anyway. Before, every batch of events drew every client and built the state (#25).
- Every shell gets `CORNERCASE=1`; a client seeing it refuses to start (no nesting).
- **`kill-server` asks before stopping the server it runs in** (#297): it is how a dev build is stopped after every rebuild, and typed in a pane of the real server (an agent working on cornercase does) it killed that server, every shell and the agent's own session, whose resume then shows nothing. The command asks the server for a `status` report first (`client::report_now`, the one-second read `running_now` already used) and takes `Report::caller` as the signal: the server sets it only when the request carries its own `CORNERCASE_SERVER` token, so a pane of another server (reached through `CORNERCASE_SOCKET`) is not inside. In that case it lists what stops (`restart::stopping`) and asks `[y/N]`; a no keeps the server and exits 0; without a terminal it refuses with status 1 unless `--yes`, naming `CORNERCASE_SOCKET` as the way to say which server. A hung server, a server that predates request support or an absent one gives no report and the command goes ahead as before. No protocol change, so it works against any server that answers `status`. Rejected: a refusal in the server of a `KillServer` from another build (it cannot tell a script from a person at a prompt, and `client::kill_server` is also the restart fallback); the `CORNERCASE` variable as the signal (every pane has it, also when `CORNERCASE_SOCKET` points at another server).
- Every shell loses Claude Code's per-session variables (`agents::claude::CLAUDE_SESSION_ENV`) and GitHub Copilot CLI's (`agents::copilot::SESSION_ENV`: `COPILOT_CLI`, `COPILOT_AGENT_SESSION_ID`, `COPILOT_LOADER_PID`, `COPILOT_SUPERVISED`, `COPILOT_CLI_RESOLVED_DIST_DIR` and `COPILOT_CLI_BINARY_VERSION`, which Copilot puts in its own shells, live): a server started from inside Claude Code would otherwise make every pane's `claude` a child of that session and expose its messaging token, and from inside Copilot a nested `copilot` would believe it runs under a loader it does not have (`COPILOT_LOADER_PID`, `COPILOT_SUPERVISED`), share the MCP login store of that session (`COPILOT_AGENT_SESSION_ID`) and could resolve another package version than its own (`COPILOT_CLI_BINARY_VERSION`, `COPILOT_CLI_RESOLVED_DIST_DIR`). User settings such as `COPILOT_HOME`, `COPILOT_MODEL`, `COPILOT_ALLOW_ALL`, `COPILOT_OFFLINE`, `COPILOT_PROVIDER_*` and `COPILOT_AUTO_UPDATE` pass through. An explicit list, not a `CLAUDE_CODE_*` prefix, so user settings like `CLAUDE_CODE_USE_BEDROCK` and `CLAUDE_CONFIG_DIR` pass through.
- `Hello` carries a protocol version and build id, and the notification channel of the client's terminal; a server from another build rejects the client. Keep `ClientMessage::KillServer` and `ServerMessage::Rejected` as the first variants (`protocol::tests::compatibility`).
- **The socket sits next to the session** (#355): `$XDG_STATE_HOME/cornercase/server.sock`, else `~/.local/state/cornercase/server.sock`, with `server.lock` beside it; `CORNERCASE_SOCKET` overrides it as before. It used to be `$XDG_RUNTIME_DIR/cornercase/server.sock`, else `$TMPDIR/cornercase-<uid>/`, which depends on the login: an `ssh -T` session has no `XDG_RUNTIME_DIR`, so `cornercase remote` computed another path, found no server and started a second one that shared every state file with the first: a double restore, agents resumed twice, `stats.json` and `server.log` with two writers, and a `session.json` overwritten by the second. Only `XDG_STATE_HOME` and `HOME` decide it now; they are on disk and survive a logout, as tmux keeps its socket out of the runtime folder, and a server and its session cannot be told apart. Relative or empty `XDG_*` and `HOME` values are ignored (`paths::absolute`; the XDG spec calls them invalid): a relative one would give a socket, and so a server, per working folder. The path functions are pure over an environment lookup (`paths::user_file`, `state_folder`, `socket_in`, `earlier_sockets_from`), so tests cover them without touching the process environment. Rejected: a lock plus a pointer file in the runtime folder (two files to keep in step, and the pointer would be what the login changes), and guessing the runtime folder (`/run/user/<uid>`) as the fix (it fails wherever systemd is absent).
  - **Path length** (`protocol::MAX_SOCKET_PATH`: 107 bytes, 103 on macOS, `sun_path` minus the NUL) is checked before anything is created, and `Error::SocketTooLong` names `XDG_STATE_HOME` or `CORNERCASE_SOCKET`.
  - **A disk that cannot hold a socket or a lock** (a network home, NFS without locking): `client::server_process::can_listen`, run by `find_or_start` before it starts the server, takes the real lock, binds the real socket path and removes it again (a live server always holds the lock, so a stale file is safe to remove), and turns a failure into `Error::Listen` naming `CORNERCASE_SOCKET`, instead of `failed to start the cornercase server` after five seconds. A server on another machine that shares the home folder holds the lock but does not answer: the start deadline then says `Error::ServerUnreachable`.
  - Known limit: panes inherit the server's environment, so `cornercase` in a pane finds its server; but `XDG_STATE_HOME` exported only in an interactive rc file, with a server started non-interactively (the proxy over `ssh -T`), gives other shells another socket, as it already gave them another `session.json`. Set it where every shell reads it.
- **A debug build keeps to folders of its own, one set per source tree** (#357): a build with `debug_assertions` (`cargo run`, `cargo build`, the e2e tests' binary) used the release's socket and files, so a dev client reached the real server and offered to kill it as another build, a plain `cargo run -- kill-server` stopped it, and a dev server started without `CORNERCASE_SOCKET` restored the real `session.json` and wrote its own over it, with its stats and log (#355 shows what two servers on one session do). Agents working on cornercase in parallel, one per worktree, would also collide in one dev folder.
  - **Where**: the state (session, log, stats, TODOs, queue, star, issue cache, run folders, plugin state and installs) in `$XDG_STATE_HOME/cornercase-dev/<key>/`, else `~/.local/state/cornercase-dev/<key>/`; and, since #355, the socket and lock beside the session in that same folder. The settings in one `$XDG_CONFIG_HOME/cornercase-dev/` (else `~/.config/cornercase-dev/`) shared by every tree, written only when a setting changes, so a new worktree does not start from nothing. `<key>` is the first 8 hex digits of the SHA-256 of `env!("CARGO_MANIFEST_DIR")`, the tree the binary was built from: a SHA-256 does not change between Rust releases as `DefaultHasher` may, and a hash keeps the socket's path short (a worktree's folder name is often 50 characters; `sun_path` holds 108 bytes on Linux, 104 on macOS). The server writes the tree's path to `source` in the state folder when it starts (`paths::dev_source`), since the key does not say which folder is which; folders of removed worktrees stay until deleted by hand.
  - **Release builds** keep their folders, `cargo install --path .` and `cargo run --release` included (so `cargo run --release` reaches the real server, as before). `CORNERCASE_SOCKET` overrides everything in both kinds of build, so the e2e tests, the capture scripts and two dev servers from one tree are unchanged.
  - **The key is a parameter** of `paths`' functions (`socket_in`, `config_in`, `session_in` and `log_in` take the environment as a closure and the key as `Option<&str>`), and only `paths::this_tree` reads `cfg!(debug_assertions)`: `cargo test` always builds in debug, so a `cfg!` inside them would leave the release paths untested.
  - **Its panes get its socket** (`App::set_pane_socket`, from `server::run`): panes inherit the server's environment, which no longer names a socket, so `cornercase` in a dev server's pane, usually the installed release, would reach the release server: a flow's orchestrator would send its team's work into the real session's panes of the same ids, and `kill-server` there would stop the real server. So a debug build's own server adds `CORNERCASE_SOCKET` to its panes, the one exception to keeping it out of them (Commands for scripts and agents). The cost: in those panes, the commands that read files rather than ask the server (`logs`, `plugin`, `stats` without a server) look next to the socket, not in the tree's folders. Putting the dev binary first on the panes' `PATH` was rejected: shell rc files put `~/.local/bin` first.
  - **Shared between dev servers**, as they sit next to `config.json`: tokens, flows, paired browsers, the chat bots' pairings and `plugins.json`. A bot paired there is polled by every running dev server, an enabled plugin's services run in each, and browser access in two of them fights for one port and Tailscale's `serve`. All rare, since a dev config starts empty; copy `config.json` there to start from your settings. Settings changed in two dev servers keep the last one's file.
  - **Nesting** is unchanged: `CORNERCASE=1` still refuses a debug window in a pane of any server, so `env -u CORNERCASE` stays needed; letting it through when `CORNERCASE_SERVER` names another server than the one at its socket was left for later.
- **The socket's folder must be the user's alone** (`protocol::check_socket_dir(socket, Folder)`): a real folder, not a symbolic link, owned by the user and not writable by group or others; it is created `0700` when missing. The client checks it before connecting or starting a server, `kill-server` before connecting, the server before binding, also under `CORNERCASE_SOCKET` (a name without a folder is checked in the current folder). `Folder::Own` (the default path, cornercase's own folder, which holds the session, stats, TODOs, queue, run folders and logs) is made `0700` instead of refused when it is ours but too open (the state folder is often `0775`); a symbolic link, a file or another user's folder is still refused, and the message never advises removing it. `Folder::Given` (`CORNERCASE_SOCKET`) refuses as before and never changes a mode, since that folder may hold other files. The mode is a parameter, not read from the environment inside, so a unit test run from a pane cannot chmod its temp folder. Without the check, another local user could create the folder first (for the earlier `/tmp/cornercase-<uid>` guess) and pose as the server: read every key and send a `Restart`. Read access for others is allowed, since connecting needs write access to the socket file.
- **A server of an earlier version is still found** (#355, temporary): releases before 0.12.140 bound the socket in the runtime or temp folder, so right after an update the running server is there. Every client entry point (a window, `start-server`, the commands for scripts, `kill-server`, `restart`, `update`, the proxy) resolves the server through `client::find`: the socket next to the session first, then `paths::earlier_sockets` (`$XDG_RUNTIME_DIR/cornercase/server.sock`, or `/run/user/<uid>/cornercase/server.sock` on Linux when it is unset, then `<temp dir>/cornercase-<uid>/server.sock`, the paths that 0.12.134 computed; no other hard-coded guess, which would also find a developer's stray server when tests set `TMPDIR`). The server itself never probes them. An earlier path is tried only when its folder passes `protocol::socket_dir_is_safe` (the same checks, but it never creates or changes anything) and the peer is the user's. A window gets `Rejected` (another build) and goes through the existing restart offer; `start-server` answers `already: true` with its usual warning; commands for scripts keep working, so agents in panes of the old server are not cut off by `brew upgrade`. Waits for the server to exit use the path that answered, so a restart of the old server cannot return while it still saves `session.json`. A debug build never probes them (`paths::earlier_sockets` is empty there, so a dev client cannot reach the real server, #357); the resolver is unit-tested with real listeners and the e2e test of an earlier server runs in release builds only. Remove this probe once releases before 0.12.140 are gone (about six months): open an issue then.
- Both ends check the peer's uid (`protocol::check_peer` on `process::peer_uid`: `SO_PEERCRED` on Linux, `getpeereid` on macOS): the client refuses a server of another user, and the server drops another user's client, which a loose umask could otherwise let in.
- **A client of its own on the socket** (#283): a program that does not run `cornercase` connects to the socket and frames each message as a 4-byte little-endian length followed by its postcard bytes (`protocol::send`, at most 64 MiB). A request is `ClientMessage::Request(json)`, variant 4 (the variant as a varint, then the string's length as a varint and its UTF-8 bytes), and each answer `ServerMessage::Response(json)`, variant 5; `events` ends with `Detached` (2), `Shutdown` (3) or `Restart` (4), and `surface` with `Detached` (2) when its tab closes, else 3 or 4. No `Hello` comes first, so no build check: requests are what crosses releases, and the TUI's same-build handshake is untouched. The server checks the peer's uid like any client's. One request at a time per connection (#478: `input --follow` keeps one for all its lines). `tests/fixtures/control/postcard/` holds the exact bytes; JSON over postcard rather than a second wire, since the framing is a few lines in any language and the socket already has one.
