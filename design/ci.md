# CI

Code: `.github/workflows/ci.yml`, `.config/nextest.toml`, #753, #754

- **Time limits** (#753): each `clippy + tests` job has a limit sized to what a passing run takes on its runner, written beside the runner in the matrix. A job that reaches its limit ends as cancelled, and a cancelled required check blocks the merge until someone reruns it, and the rerun can be cancelled again; flows that merge on their own and Dependabot's pull requests wait on it like everyone else.
  - **macOS has 45** (#754; it had 60 from #753 to #754). Before #754 a passing run took 25 to 30 minutes (main run 43143894106 on 2026-11-12: 29m47), and a quarter of the runs from 2026-11-09 to 2026-11-11 reached the old limit, 30, and were cancelled. After it, two runs in a row passed in 13m54 and 20m53 (runs 43181865830 and 43183832793, warm cache; the difference is mostly the tests' build, 4 to 7 minutes depending on the runner); the limit is about twice the slower, rounded up to 5. A Dependabot run, which rebuilds what it bumps, took 5 to 10 minutes more than a warm one (31 and 35 minutes with the old tests), and a run from a cold cache builds Ghostty and every dependency again, so a cold one at the new speed is expected near 30, under the limit.
  - **Linux keeps 30**, about twice what a passing run took by 2026-11-11, so a run that hangs there still ends at 30 (a passing one takes 8 to 10 minutes since #754, from 11 to 12).
  - **Windows has 45** (#601), so that a run from a cold cache (Ghostty with Zig, then every dependency checked for clippy and compiled for the tests) fits; a warm one took about 8 minutes by 2026-11-11.
  - A longer limit did not make the tests faster; #754 did (below), and brought the macOS limit down.
  - Rejected: splitting the macOS job into partitions (a build job that archives the tests with nextest, N macOS runners that run one partition each, and a final job carrying the required check's name, `clippy + tests (macos-15)`, that fails unless all passed), because a run now passes in 14 to 21 minutes: it would cost a build job, more macOS runners per run and a gate job holding the name `main`'s ruleset requires; and one limit for the whole matrix, which would let a Linux run that hangs hold its runner twice as long; and picking the limit with an expression on the runner's name (`startsWith(matrix.os, 'macos') && 60 || 30`), which keeps the limit away from its runner in an `&& ||` idiom that actionlint cannot type, where an `include` entry states it as a number beside the runner.
  - Checked (2026-11-11): `actionlint` 1.7.7 accepts the matrix and reads `timeout` as a number; the jobs keep their names, which `main`'s ruleset requires.
- **The tests run with cargo-nextest on Linux and macOS, and with `cargo test` on Windows** (#754, 2026-11-12). On macOS's 3 cores the tests took about 1,200 s (unit tests and e2e), and most of it was waiting, not work: launches' quiet periods, a messenger's cadence, a process's start. nextest starts a process per test, which the suite allows (`design/test-helpers.md`), and what it costs is small: a test binary starts in about 8 ms on Linux and 15 to 25 ms on macOS, 20 to 30 s over a macOS run. It brings a limit per test and a JUnit report per run, the list of the slowest tests. It does not run doc tests, and there are none (no comments, by rule). The version is pinned (`cargo-nextest@0.9.151`, the latest then, installed by `taiki-e/install-action`), and `cargo test --locked` still passes, so contributors need nothing new. Windows keeps `cargo test`: its job is short (8 minutes) and nextest was not measured there.
- **More test threads than cores** (#754): the threads are in the matrix (`threads`) and passed as a flag, never as `RUST_TEST_THREADS` or any `CARGO*` or `RUST*` variable at the job or the workflow, since `Swatinem/rust-cache` keys its cache on those and a new key builds Ghostty and every dependency again.
  - **8 on Linux (4 cores) and 8 on macOS (3 cores)**, which more than halved the macOS tests (1,012 s with 3 threads, about 450 to 600 s with 8). 12 threads was a little faster on both (macOS 427 s), but tests that measure the load failed in two of three runs (a process's cpu time against the wall time, the panic reports of `server::tests::a_bug`, a clipboard copy through a program on another machine), and 16 on macOS was slower than 12 with five failures: a 3-core runner stops gaining once its cores are busy. 8 passed in every run.
  - A test must not depend on the load: `cpu_time`'s test only needs more than 100 ms and no more than the wall time (a share of it failed under load), `a_bug`'s tests wait 30 s because a panic's backtrace is slow to symbolize on a loaded runner, `last_message` asks again while an agent has not yet shown where its conversation is, and the Discord forum's `Posting::waits` moves its clock only while no agent is launching (a clock that runs ahead of a launch makes it give up early).
- **A limit per test** (#754): `.config/nextest.toml` sets `slow-timeout = { period = "30s", terminate-after = 4 }`: SLOW is printed every 30 s, and the test is killed at 120 s, so a hung test ends in 2 minutes instead of at the job's limit. The slowest passing test on macOS at 8 threads takes about 16 s, 7 times less. The `ci` profile (`--profile ci`) keeps going after a failure (`fail-fast = false`) and writes `target/nextest/ci/junit.xml`, which the job uploads as an artifact for 14 days (`junit-<os>`, overwriting on a re-run): the slowest tests of a run are in it. Retries stay at 0, so a flaky test fails as it did.
- **What was left alone** (#754): the launch's quiet periods (about 1.6 s per started agent, so 66 tests of `control_requests` take 1.5 to 2 s: a timing held by `Launch` would shorten them, but a fake that draws its screen in two writes under load could be typed into early) and macOS's `open_files`, which runs `lsof` for each call (about 18 ms; no test of the readers is among the slowest). Both are the next places to look. `Term::kill`'s 50 ms is in `design/terminals.md`; the one line pasted into the flow import page, which was slow in the app too, was #768 (see Text fields).
