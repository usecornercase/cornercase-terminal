# Plugins

Code: `plugins/`, `app/plugins.rs`, `app/plugin_popup.rs`, `ui/dialog/popup.rs`, `cli/plugin.rs`, `cli/plugin/windows.rs`, `client/window.rs`, `script.rs` (Windows)

- **What a plugin is** (PR 1 of 3 is the core; PR 2 adds installing, below; the catalogue is PR 3): a folder with `cornercase-plugin.toml` that declares argv commands, modelled on herdr's plugins (`herdr-plugin.toml`). The plugin's API is the existing commands for scripts and agents: it calls `$CORNERCASE_BIN status --json`, `events --json`, `send`, `notify`… No SDK and no runtime inside cornercase (WASM, Lua, JS were rejected): every improvement to the commands is one to plugins at no cost, and a plugin can be written in any language. TOML, like herdr's, so plugins port easily; it costs the `toml` crate (parse and serde only). Entries: `[[actions]]` (one-shot, in the menus, on the plugin's own button, as a job or in a popup), `[[events]]` (one-shot per event), `[[service]]` (kept running by the server), `[[window]]` (kept running by each local window, and by each `plugin windows`, #674), `[button]` (the title and icon of its button, #435), and for installing `[[build]]` and `[download.<target>]` (see Installing). Left out: `[[tab]]` (`new-tab --command` covers it), link handlers, per-entry `platforms`, plugin-defined settings, declarative dialogs (a list or form schema) and areas of the TUI drawn by the plugin (sidebar sections, panel tabs).
- **What a plugin shows in the window** (#435): a button of its own and a popup terminal, as herdr does with `placement = "popup"`, rather than a schema of widgets cornercase would draw. A popup is a PTY in a bordered dialog, so a plugin draws anything a terminal program can (fzf, a curses menu, a TUI written in any language) and cornercase keeps one surface to maintain, the emulator it already has; a schema would be a second UI toolkit with its own versions, and would still not cover what a program in a terminal does. Sidebar areas and panel tabs stay out: they would hold a plugin's process for as long as they show and share the columns' room with the built-in lists. Other UIs get its state, opening and closing (#435), and its content and input (#456: `surface --popup`, `input --popup`; see Through the server). So a popup is not only the person's: like a pane, what it shows and what it is answered with reach every socket client, an agent in a pane included (the socket's trust model: whoever reaches it can type into every shell). The plugin guide says so, and that a popup is no place for a secret only the person may see or a confirmation only the person may give; a popup reserved for the window was not built, since the browser and `cornercase remote` windows are socket clients too, and it would cut the UIs #456 is for.
- **On Windows** (#595, `script.rs`, `plugins/run.rs`, `plugins/manifest.rs`): commands stay argv, never a shell. Windows starts a program by its file, as std's `Command` does: an `.exe` with or without its extension, a `.cmd` or `.bat` through cmd with std's own escaping, a bare name looked up on the `PATH` as `name.exe` (so `npm` needs `npm.cmd`). A plugin's programs are mostly scripts written for `sh` (`bin/run`, `./on-status`), which Windows cannot start, so **a program whose file begins with `#!` runs through Git for Windows' `sh`** (found as for worktree scripts, see Windows): `sh -c 'exec "$@"'` with the program and its arguments, so `sh` reads its first line as Unix does (`#!/bin/sh`, `#!/usr/bin/env node`), with Git's `usr\bin` first on its `PATH`. Its arguments travel in the environment rather than on the command line, and it runs with `MSYS2_ARG_CONV_EXCL=*`, which its children inherit, so neither `sh` nor a Windows program it starts (`node` behind `#!/usr/bin/env node`) gets them expanded or rewritten as paths (see Windows): they arrive as on Unix. A job (actions, hooks, services, window processes, build steps) appends to the plugin's log with `sh`'s own `>>`: a program of Git's `sh` cannot write to the append-only handle a native program gets (every write fails, checked), and the log is shared with cornercase's own lines, so a handle with a position of its own was rejected. **Without Git's `sh`, such a program is refused when the manifest is read** (`it is a script, and on Windows cornercase runs one only through Git for Windows' sh, which was not found`), so Settings and `plugin list` say why rather than a failed start saying `%1 is not a valid Win32 application`. Rejected: reading the `#!` line ourselves and mapping `/bin/sh` or `/usr/bin/env node` to Windows programs (a second implementation of what `sh` does, and a `#!/bin/sh` script still needs an `sh`), and PowerShell for such scripts (they are written for `sh`). Jobs and services are spawned through `os::process::Grouped` as on Unix, so `sh` and everything it starts are in one Job object and stopping a service, or a job past its time, ends the whole tree (#597). **The folder and file check** reads the owner and the DACL (`os::fs::owner_and_mode`, the reading and rules the socket's folder uses since #591), the manifest's own from the handle it was opened with (`file_owner_and_mode`), so a file put in its place after the open is not the one checked; the owner must be the user, SYSTEM or Administrators and no one else may write. A manifest that is a reparse point is refused (`it is a link or another reparse point`): opened without following, a symbolic link is the link itself, and a junction is a folder that does not open as a file. That includes OneDrive's files on demand, which are reparse points, so a plugin in a folder OneDrive syncs can be refused, a known limit (not checked live). The plugin's folder is checked as the path given, a junction as the junction itself, while the manifest and every program are checked at their real paths, so a junction cannot lead to another user's files. Checked live on 2026-11-03 (Windows 11 10.0.26200, Git for Windows 2.39.2): `plugins::run::tests::on_windows`, `plugins::manifest::tests::on_windows`, `script::tests::on_windows`.
- **Tests**: fake plugins are `/bin/sh` scripts in temporary folders (`plugins::*::tests`, `app::tests::plugins`, `e2e::plugins`); supervision is tested on the real thread with a service that records its pid, killed, disabled and dropped.
