# Dialogs

Code: `ui/dialog.rs`, `ui/dialog/`, `ui/combo.rs`, `list.rs`, `app/overlay.rs`, `app/dialogs.rs`

- Dialogs, menus and the toast have rounded borders (`BorderType::Rounded`); a title sits after one border cell (`╭─ settings ─`), bold in the default colour, so it reads as the dialog's heading rather than part of the border.
- A dialog (form, confirmation, picker, settings, issues, usage, update, group style: `Overlay::is_modal`) dims everything behind it (`Modifier::DIM` on the whole buffer before it is drawn), so it reads as on top. A menu or the search does not: they belong to what they were opened from. DIM leaves backgrounds alone, so surfaces stay.
- Lists inside overlays (menus, picker, issues, search results, a settings pick, settings rows) mark the selected row like the sidebar: surface background, a cyan `▌` in its first cell and bold text; a hovered row takes the hover fill. The filled cyan bar they had was loud, and two of them lit at once (the selected row and the hovered one). The active tab of a tab row (settings, issues, the changes panel: `tab_style`) is cyan bold on the surface.
- **A text field's menu floats above its dialog**; a click outside it closes only the menu (see Text fields).
- **A left press outside a dialog closes it** (`App::outside_dialog`, before each dialog's own mouse handling), like its cancel button (`cancel_form`), so a busy one (`Overlay::busy`: creating a worktree, installing an update, checking a token, starting an issue) stays open. Menus and the search already closed that way; dialogs only closed with their buttons or `Esc`, which is not what anyone expects of a modal. Where the dialog is comes from `ui::Overlay::area`, which uses the geometry functions the drawing uses (`form_area`, `picker_area`, `usage_area`, `issues_area`, `settings_area`), and a test per dialog checks its border is drawn at that area's corners. It closes the whole dialog, not one level as `Esc` does in the issues browser or a settings pick. What was typed in a form is dropped, as with `Esc`; keeping forms with text open was considered and left out: one rule for every dialog is easier to learn than a click that sometimes does nothing. **The exception is a plugin's popup** (#435, see Plugins › Popups): a click outside it does nothing (`outside_dialog` swallows it, so it reaches neither the popup nor the columns). Its program may hold work a stray click would kill, and unlike a form it has no text cornercase could keep; it closes with its `×`, when its program exits or over the socket.
- Dialog buttons are pills on the surface (`dialog_button_style`): the submit one cyan bold, the others grey; hover fills them cyan or grey. Without a background they read as coloured words, not as something to click. A destructive confirmation (`Confirm::dangerous`, so far only discarding a file's changes, #421) draws its submit button red instead of cyan; no other dialog does.
- **Dialogs that read something outside** (the Remote dialog's pairing, `Overlay::Pairing`; Discord's forum setup, `Overlay::Forum`, #437): while open, a job polls on `app/messenger/every.rs` and the dialog ticks as the user acts elsewhere (a phone, the Developer Portal), so it has no submit: `Enter` closes it like its ` done `, and so do `Esc` and a click outside. Closing it stops the polling. The forum's also has ` turn off `, the only way in the window to turn a mode that is not ready off (see Settings), and a list of the user's servers where a click picks one, since there are no keys to move in it.
- **Comboboxes** (`list::Combo`, `ui/combo.rs`): a choice among a few named options is a field showing the chosen one with a `▾`, whose list opens below it like a web page's select (above it when it does not fit), at most `COMBO_ROWS` (8) rows with ` ↑ n more ` / ` ↓ n more ` on its border and the wheel to scroll. A click, `Space`, `↑` or `↓` opens it; `↑` `↓` `PageUp` `PageDown` `Home` `End` move, typing filters (case-insensitive, a substring, as the search does), `Enter` or a click chooses, `Esc` or a click elsewhere closes only the list. The model (options, choice, and while open a `list::Search` for the filter, selection and scroll) is a shared leaf so other dialogs can take it (settings' picks, the issues browser's agent and place pickers, the changes panel's branch picker); the field, the list and their hit testing share the geometry in `ui/combo.rs`. The open list belongs to its dialog: `ui::Overlay::area` includes it, so a click on a list that reaches past the dialog's border chooses instead of closing the dialog. A list over the form rather than in place (as the issues browser's pickers are) was left out: the form's other rows stay in view.
- **A tab row that does not fit tightens** (`tabs_in`, #540): it first drops the gaps between tabs, then the padding inside each one, before any tab falls off its end. A row that fits is drawn as before. Settings' ninth tab, Machines, fell off the row at 80 columns, out of reach of the mouse. Rejected: a `more` tab or a row that scrolls, either of which is one more control on a narrow window, where a tighter row still reads.
