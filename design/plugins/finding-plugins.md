# Plugins › Finding plugins

Part of [Plugins](../plugins.md).

- **Finding plugins** (`site/src/lib/plugins/`, `site/scripts/plugins-index.mjs`, `site/plugins/`, `src/pages/plugins/`) is herdr's marketplace (herdr.dev/docs/marketplace): found automatically, not reviewed, listed by repository. A curated index reviewed per commit, and a catalogue inside the app, were built first and dropped: review by maintainers does not scale once anyone can publish, a plugin runs as the user whatever a reviewer read, and herdr has neither.
  - **The crawl** (`crawl.ts`): GitHub's repository search for `topic:cornercase-plugin fork:false archived:false`, 100 a page, at most 10 pages (the search stops at 1,000 results); for each repository the head commit of its default branch, its tree at that commit (`git/trees?recursive=1`), and every `cornercase-plugin.toml` in it, at the root or in a folder, nearest first, at most 20 per repository, read from `raw.githubusercontent.com` (64 KiB each), eight repositories at a time. A repository whose head commit is the one in the published index is not read again: its plugins and its count of invalid manifests come from the index (`skipped` keeps the repositories with no valid manifest for that), as herdr rescans only when the head changes. Each manifest is parsed with `smol-toml` (a dev dependency of the site); one that does not parse or breaks the rules `src/plugins/manifest.rs` applies counts as invalid, checked by one function (`checkManifest`): `api` a whole number from 0 to 1 when present; `actions`, `events`, `service`, `window` and `build` lists of tables with their required fields, a non-empty command of strings whose program does not climb out of the folder, action contexts from `project`, `workspace`, `tab`, `pane` and `button` (case matters, as in serde), an action's `placement` `job` or `popup`, its `width` (20 to 500) and `height` (5 to 200) whole numbers and only on a popup, a `[button]` table only with an action in the `button` context, its `title` not blank and its `icon` one character one cell wide, event names from `opened`, `closed`, `status` and `exited`, ids of the app's shape and unique per kind, at most 64 entries, `download` targets with an https address (or loopback) and a 64-digit sha256, and no control or bidirectional formatting character in any string, keys included, however deep. What the crawler cannot know, such as whether the plugin runs on the reader's platform, is left to the app. The icon's width is approximate, not a port of `unicode-width`: one code point that is no control, format or non-spacing or enclosing mark (`Mn`, `Me`; a spacing mark counts as one cell, as in `unicode-width`), no emoji shown as a picture by default (`Emoji_Presentation`, the ones `unicode-width` makes wide; symbols such as `▶`, `⚙` or `✔` are text by default and one cell) and not in the main wide CJK and Hangul blocks. It leans permissive because a crawler stricter than the app hides a plugin from everyone (#509, when the `button` context of #435 was missing here), while a looser one only lists a plugin that `cornercase plugin install` then refuses with the reason. A test reads every example manifest in the guide (`guides/plugins.mdx`, each ```toml block with `[[actions]]`, at least two, sha256 placeholders filled in) and checks the crawler accepts each, so the guide and the crawler cannot drift apart. A rule change reaches a repository already read only at its next commit, since an unchanged head is never read again: a plugin skipped by an older rule shows up once its repository moves. **A failed request is not an invalid manifest**, and what fails it depends on the scope. *The whole crawl* stops, and `plugins-index.mjs` keeps the published index, only when the search fails, is incomplete or is malformed (a non-success answer, `incomplete_results` true, no `items` or `total_count`, as `refresh-flows.mjs` treats its own search; a complete, empty search is accepted): then nothing is known about who is listed. *One repository* never stops the others, as in `refresh-flows.mjs`. A repository that is gone (404, 410 or 451 on its head or its tree) is skipped. Any other error for it (a 5xx, 403, a rate limit, a malformed answer, a head without a commit or a tree that is not a list of objects (a truncated but well-formed one is read as it comes), a failing manifest download, a network error) keeps that repository's card from the published index when it has one and skips it otherwise; each case is logged with `console.warn` naming the repository and the reason, and a kept card goes through the current blocklist and the duplicate rules like any other. Unchanged: a 409 on the head (an empty repository) leaves it out, and a 404 for a manifest the tree listed counts as an unreadable one, so only a transient failure is ever retried. Before, a failed request dropped the repository for the run, or was stored as an invalid manifest and reused for as long as the commit stayed the same, and then aborted the whole crawl and froze the catalogue for everyone. **A kept index gets the current blocklist** (`keep`: the published index is turned back into `assemble`'s input and assembled again, so the blocklist, the counts and the duplicate marks follow the same rules, and `blocked` marks survive so the repository is read again once unblocked). Cards that were hidden as all-duplicate are not in the published file, so a kept index cannot bring them back and its `total` counts only what it lists. Forks and archived repositories are left out, and so is a repository with no valid manifest. Two plugins with one `id`: the one in the older repository (by creation date) keeps it and the other is marked `duplicate` and not shown, so a newer repository cannot take an id by gathering stars.
  - **Moderation is a blocklist** (`site/plugins/blocklist.json`: `repos` and `ids`), changed by pull request. The published index holds the plugins left after the blocklist, so a repository reused from it could never get a blocked plugin back. A card or `skipped` entry that lost plugins to the blocklist therefore says how many (`blocked`), and `previousScans` does not reuse it: that repository is read again on every run until the id is unblocked, and a blocked repository, which has no entry at all, is read again too. Filtering when the page is drawn over scans that keep the blocked plugins was rejected: the published file would then list what moderation removed. The cost is one tree and its manifests per blocked repository per run.
  - **The index** (`plugins/index.json`, version 1): `generated`, `source` (`total`, `missing`, `invalid`, `duplicate`, `blocked`), `repos` (one card per repository: `repo`, `description`, `stars`, `language`, `pushed`, `created`, `commit`, `invalid`, `blocked` and `plugins`, each with its folder `path` and the manifest's `id`, `name`, `version`, `description`, `platforms`, `permissions`, `min_cornercase`) and `skipped`. It holds no address: the page builds `https://github.com/<repo>/tree/<commit>/<path>` and `cornercase plugin install <repo>[/<path>]@<commit>` itself (`owner/repo/sub/dir`, see Installing). `catalogue.ts` validates it strictly (unknown fields, types, at most 1,000 repositories and 8 MiB) at build time, so a bad crawl fails the build instead of publishing.
  - **Joined and star history** (`joined`, `stars_history` on a card, optional, `VERSION` stays 1; `site/src/lib/plugins/market.ts` for what reads them): trending and new need what a single crawl cannot see, so a card carries `joined` (when the crawl first listed the repository) and up to 8 daily samples `[YYYY-MM-DD, stars]`, oldest first, one per UTC day. `assemble` takes the published index as its last argument and carries both forward: a repository it lacks joins at the crawl time; a published card without `joined` (written before this) gets its GitHub `created` date, so the first run after deploy does not mark everything new; the first crawl of a UTC day appends that day's sample and a second one the same day changes nothing; the ninth sample drops the oldest. A card kept after a per-repository failure, and every card of a kept index (`foundFrom`), carries its `joined` and history as they were, without a new sample, since its stars are as old as the card. Validation refuses unknown fields as before, a history of more than 8, a sample that is not a real `YYYY-MM-DD` day with a whole non-negative number, and days that are not strictly ascending. A repository that was only in `skipped` (no valid plugin) has no `joined`, so it joins when it first gets a card.
  - **Trending and new, herdr's rules** (`market.ts`, pure, tested at each edge): the **weekly gain** is the stars now minus the sample dated exactly 7 days before the crawl's UTC day, else the newest sample at least 7 days old, and none when there is no such sample (it never trends). The **trending score** is `gain / max(stars − gain, 1)`, only for a gain of 10 or more, so the long tail's 1 to 3 stars cannot flood it while a big repository must grow in proportion; the shelf is the top 6 by score and is hidden when fewer than 3 qualify. **New** is joined within 14 days of the index's `generated` time and created within 60 days (a long-known project that was only found this week is not new), newest joined first, 6 shown, hidden under 3. The sorts are Popular (stars, then last push), Trending (score with none as −1, then gain, then stars), Recently updated (push), Newest (`joined`, else `created`) and Name (`localeCompare`). Search lower-cases and splits the query on whitespace, and every word must be a substring of one text made of the repository, owner, name, description, language and each visible plugin's name, id and description. Visible plugins exclude duplicates, and a card with none is neither shown nor counted (the empty card of a repository whose only plugin copies another's id); the page's counts are visible plugins, shown cards, the sum of positive weekly gains and the cards joined within 7 days. Language colours are GitHub linguist's for nine languages and nothing for the rest. Relative times floor each unit (year 365 days, month 30) and say `just now` under a minute.
  - **The dev fixture** (`site/tests/fixtures/plugins/fixture.ts`): crawl input, not a finished index: 14 fake repositories (several with more than one plugin, a duplicate id whose newer repository must disappear, invalid manifests, one blocked by a fixture blocklist, histories and dates that fill trending and new), with dates relative to a clock, assembled through the real `assemble` by `fixtureIndex(now)`. The tests use a fixed `now`; `npm run plugins:dev` writes it for the current time to `site/plugins/index.dev.json`, which is not committed, for the page to read when asked (`plugins/index.json` never holds fake data).
  - **The page** (`/plugins/`, `src/pages/plugins/index.astro`, `src/lib/plugins/page.ts`, `client.ts`): a standalone page, not Starlight (no docs search, no table of contents), replicating herdr's marketplace page in the landing's style: its `Nav` and `Footer` (taking a `standalone` prop, so their anchors go to the landing, and the star-count fetch is off), fonts and tokens, light and dark. Nothing on it reads like herdr's page: the header is one column at every width: `Extend your terminal.`, the count in cobalt (`13 plugins · 10 repositories · refreshed every hour`, with singular forms, from `page.ts`'s `headline`), one sentence of lead and the trust line (herdr's big number in a right aside and its `Publish yours` link are gone, since the publish line at the bottom says it); then **Rising this week**, **Just landed** and **Every plugin**, each titled alone (until the rebrand each had a small command line above its title, `$ sort --stars --since 7d`, `$ ls --newest`, `$ ls --all`, dropped with the landing's labels), and no ids or `aria-labelledby` changed (search with a `/` hint that also focuses it, five sorts, a stats line, 24 cards then `show N more` naming the remainder, never in the URL) and, instead of a closing card, a **Publish yours** section titled like the others, set as a split (title, paragraph and guide link on the left, the command on the right), one paragraph saying to add the manifest (`MANIFEST`) to a public repository and tag it with the topic, that it shows up on the next refresh with no submission and no review, the guide link as an item of its own, and a dark terminal line holding the full command (built from the `TOPIC` constant, with a copy button), its text directly on the box with no inner field: the light inline-code look is only for the `<code>` of the paragraph. The standalone footer leaves out the landing's call to action (`Footer`'s `standalone` prop), which has no reveal here and showed as an empty block with a glow. **Everything is rendered at build time** from the validated index by `view()` (market.ts's rules): the shelves, every card in Popular order, the counts and the stats line, so the page works without JavaScript (all cards shown); each card carries its rank for each sort (computed by market.ts, so the script holds no second copy of the comparators) and a lower-cased haystack, and the script only reorders, hides and pages them, matching words with market.ts's `matches`. Times are `<time datetime>` with the date as text, turned into `2h ago` by the script (the build has no clock a visitor shares). Cards are not links (a copy button cannot sit inside one): `owner/repo ↗` links to GitHub in a new tab with `noopener noreferrer`, and the card highlights as a whole. **The install command is in the card** (herdr shows none): a single-plugin card shows its commit-pinned command with a copy button, a repository with several visible plugins an `N plugins` pill that opens each plugin's name, version and command. A card with no visible plugin never renders. The language dots are set by attribute selectors in the page's stylesheet (a style attribute would break the CSP), and a test keeps their colours equal to market.ts's table. **Empty state**: while the index lists nothing (at launch it is empty), the header's count line reads `no plugins yet · be the first` (`headline`), and the Every plugin section is not rendered at all, so there are no search or sort controls and no count line to look at; the one Publish section, titled `Publish the first one` and saying `Your plugin shows up here` (the header already says nothing is listed), is then the page's only call to publish. Showing the empty controls and a second call at the bottom was rejected: two invitations and controls that do nothing read as broken. With plugins listed the page is unchanged.
  - **The CSP and the avatars**: a meta policy as the stats page has (`default-src 'none'`, `script-src 'self'`, `style-src 'self'`, `connect-src 'none'`: the script makes no request) except `img-src 'self' data: https://avatars.githubusercontent.com https://github.com`, for each owner's avatar (`https://github.com/<owner>.png?size=64`, redirected to `avatars.githubusercontent.com`). The trade-off, chosen by the user over copying the avatars into the site: the visitor's browser contacts GitHub, which sees their IP address and that they opened the list; `referrerpolicy="no-referrer"` keeps the page's address from it, and an image that fails (or is blocked) is replaced by the owner's initial. Self-hosting them would have made the crawl download and the site serve up to a thousand images. `CSP` lives in `page.ts` and a test pins it. **In dev only** (`import.meta.env.DEV`) the policy of this page and of `/stats/` is relaxed by one helper (`src/lib/csp.ts`: `'unsafe-inline'` for scripts and styles, and `ws:`/`http:` to localhost for the dev server's socket), since `astro dev` injects its CSS as inline `<style>` and an inline script and the strict policy left the preview unstyled; the production strings are pinned unchanged by a test, and the dev page was checked in a headless browser (styles apply, no violation reported). The plugin pages' copy buttons carry `data-plugin-copy`, so the listener cannot touch the shared footer's install box, which has its own handler and `data-copy`.
  - **Dev preview**: `PLUGINS_INDEX=dev` makes the page read `plugins/index.dev.json` (the fixture, see above) instead of `plugins/index.json`, read from disk only on that branch and only under Astro's dev mode (`import.meta.env.DEV`), so a build never reads it, whatever the variable says, and a production page can never show fake repositories: `npm run dev:plugins` writes the fixture for the current time and starts the dev server on it. `index.json` and its endpoint are unchanged.
  - **When**: the Pages workflow runs on its one hourly `schedule` (`23 * * * *`), shared with the community flows' refresh, besides pushes, so every scheduled build refreshes both; outside pull requests it runs `npm run plugins` (with the workflow's token, for GitHub's limits) after `npm run check` and before `npm run build`, with the flows' refresh and its stale warning before the check. The script first fetches the published index, both to skip unchanged repositories and to keep it when the crawl fails, so an outage of GitHub's API never empties the list. Pull requests build with the committed `plugins/index.json`, an empty list, so their checks never depend on the network.
  - **Pinning**: the page's command installs the commit the crawl saw, and PR 2 resolves a full commit only as that commit, never as a branch or tag of that name, so what someone copied is what installs, with the preview and the question before anything runs.
  - **No catalogue in the app**, as herdr has none: Settings › Plugins lists what is installed or linked; finding plugins is the website, installing is `cornercase plugin install`.
