# Plugins › The manifest, commands and the registry

Part of [Plugins](../plugins.md).

- **The manifest** (`plugins/manifest.rs`): `id` (lower-case letters, digits, `.`, `_`, `-`, at most 64), `name`, `version` required; `min_cornercase` (refused when newer than the binary, as herdr does), `api` (an integer, 1 today, refused when newer: it moves only when a command or event changes incompatibly, which the tolerant JSON makes rare), `description`, `platforms` (`macos`, `linux`; empty is everywhere), `permissions`. Unknown fields are ignored, so a manifest written for a newer cornercase loads; warning about them was left out (it needs another crate). Unknown contexts and event names are refused by serde with the list of known ones. **Buttons and popups** (#435): the `button` context, `[button]` (`title`, `icon`), and on an action `placement` (`job`, the default, or `popup`) with `width` and `height` for a popup. A `placement` other than those two is refused; `width` or `height` without `popup` too, and outside 20 to 500 columns and 5 to 200 rows (the minimum is the popup's own; the maximum only catches nonsense); an `icon` that is not one character one cell wide, or holds a hidden one; a blank `title`; and `[button]` with no `button` action, which would show nothing. A `button` action without `[button]` is fine: the title is the `name`, the icon its first letter. **These need `min_cornercase`**: an older cornercase refuses the whole manifest over the unknown `button` context (serde names the known ones) and silently ignores `placement`, which would run a popup's program as a job with no terminal; so the docs tell plugins that use them to set `min_cornercase` to the first version that has them. Raising `api` to 2 was rejected: it would refuse plugins that use neither. Every text in it (ids, name, version, description, platforms, permissions, titles, every command and argument, the build steps and the downloads' targets, addresses and sha256) is refused when it holds a control character or an invisible one (`text::hidden`: Unicode's format characters, such as the bidi overrides and isolates `U+202A`–`U+202E` and `U+2066`–`U+2069`, the zero-width ones `U+200B`–`U+200F` and `U+FEFF`, the line and paragraph separators, variation selectors and tags, and the fillers that draw as blanks), since such a character makes a command read differently from what runs (`bin/run\u{202E}hs.txt` shows as `bin/runtxt.sh`): a plugin is chosen by reading what it runs. Escaping them for display instead was rejected for the manifest: a plugin has no reason to use them, and one refusal covers the CLI, Settings and every future preview. Errors about a manifest or a program, which can quote the text that failed, show such characters escaped (`text::escape_hidden`, `\u{202e}`), never raw. The file is opened non-blocking and read only when it is a regular file, at most 64 KiB (the read itself stops there), and a plugin declares at most 64 entries: a FIFO named like the manifest would otherwise block the server loop, which reads manifests (below). The plugin's folder and its manifest must belong to the user and be writable by no other user, close to the rule the socket's folder follows: a plugin linked from a shared folder such as `/tmp` would let another user run code as you. herdr checks neither the owner nor the mode of a plugin's folder (only that an installed plugin's manifest sits inside its managed checkout); cornercase does. Group write is refused too, unless the group is the user's own primary group: distributions with a group per user (umask `002`) make every clone group-writable, and refusing those would refuse most plugins there for no gain. A manifest that cannot be read never hides the others (herdr #4312): the plugin is listed with its reason and cannot be turned on.
- **Commands are argv, never a shell**: nothing is expanded or split. A program with a `/` resolves inside the plugin's folder: `..` is refused when the manifest is read, and at run time the path is canonicalised and must stay under the canonical folder, so a symbolic link leading out is refused too. A bare name goes through the `PATH`, like any command. The resolved program and every folder from the plugin's folder down to it get the folder's and the manifest's check (owned by the user, writable by no other user, group write only for the user's own primary group), since a program another user can rewrite runs as you all the same. A bare name, an absolute path and the files a program reads (`["python3", "main.py"]`'s script) are not checked: the plugin's own code is the user's to keep. The check is about mistakes and surprises, not containment: a plugin runs as the user and its own script can run anything.
- **The registry** (`plugins/registry.rs`): `plugins.json` next to `config.json` (`paths::plugins`), private (`persist::write`, `0600`), `{"version":1,"plugins":[{"id","source","enabled"}]}`. `source` is a tagged enum with `{"kind":"link","path"}` and `{"kind":"git",…}` (see Installing) today, so the catalogue may add variants without a new version. A missing, corrupt or unknown file reads as empty for the readers (the supervisors, the menus, Settings' rows), but the writers (`Registry::open`: the commands, Settings' switch) refuse a file they cannot read rather than write an empty registry over it, saying so. Every writer (the commands, Settings) loads it from disk, changes one entry and writes it back, so the commands work with no server running and two writers never work from a stale copy.
