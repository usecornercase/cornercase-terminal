# Plugins › Through the server

Part of [Plugins](../plugins.md).

- **Through the server** (#343, `control/plugins.rs`, `app/control/plugins.rs`, `cli/plugin.rs`; `cornercase plugin actions|run`): actions showed only in the window's menus, so another UI could not offer them nor run one the way the menu does, and what Settings › Plugins shows (on, off, cannot run, what a service does) was only on screen. Three request names, `plugin-list`, `plugin-actions` and `plugin-run` (`Command::NAMES` had 71 then), refused by name by an older server; no feature, `CONTRACT` stays 1, none took a view then (`plugin-run` does since #666, below).
  - **What is on disk now**: each reloads the plugins first (`App::reload_plugins`, what `watch_plugins` does once a second), so an answer right after `plugin link` or `enable` is current and a revision is checked against the files, not a reload up to a second late.
  - **The menu's revision**: `plugin-actions` answers the runnable actions, for a `context` or all, in the menus' order, with `plugin`, `name`, `action`, `title`, `contexts` and the `revision` (`Plugins::revision`, up by one each time the loaded plugins differ). `plugin-run` names `plugin`, `action`, `revision` and `item`; a revision the plugins moved past is `conflict`, as a menu opened before the change does nothing, so an action whose command or contexts changed since it was listed never runs. Ids rather than the menu's index, which means nothing to a client; the revision is required, and `cornercase plugin run` reads the current one when `--revision` is left out. It counts from the server's start like ids, so `boot` guards it across a restart.
  - **The target** is `close`'s `item`: a group, or a kind the action is not offered for, is `malformed` (the client listed its contexts); an id naming nothing is `not-found`; a workspace being removed or closing, or a project closing, is refused as for every command that names one, since the action would run in a folder being deleted. A plugin unknown, off or that cannot run, and an action it lacks, are `not-found` with the reason: the revision matched, so it was never listed.
  - **The menu's job**: `App::start_plugin_action` runs both, with the environment of what was named (`spot_env` gives the `Ids` the answer echoes), the workspace's folder, the five minutes, the plugin log's notes and the `plugins: action` job line. `run_to_end` moved to `plugins/run.rs` and returns a `Ran` (`Ended::Status`, `Timeout`, `Failed`, and how long it took) instead of an error, so a request gets the exit code; `Ran::failure` keeps the toast's texts, and `Job::fail` keeps a failed action's job line at WARN although the work itself succeeded. The menu still toasts a failure; a request never does, since nothing a request does changes what the window shows unless it asks to.
  - **The outcome** comes when the action ends (`Stage::Reading`): `plugin`, `action`, `context`, the ids it got, `ended` (`exited`, `signal`, `timeout`, `error`), `code`, `signal`, `error` (`null` once it exited with 0, else the toast's reason), `ms` and `log`. A failed action is an answer, not a refusal, as a failing tracker is for `issue-list`; `cornercase plugin run` exits 1 then. A client that leaves drops the answer and the action runs to its end, as a menu entry's does. No limit on how many run at once, as for the menu; whoever reaches the socket can already type into every pane, so running an enabled plugin's action asks for no new trust.
  - **What Settings shows**: `plugin-list` gives each registered plugin what `plugin list --json` prints (`id`, `enabled`, `source`, `log`, `manifest`, `error`) plus `state` (`on`, `off`, `cannot-run`), Settings' `label` and `note` (`Plugin::label` and `note`, shared with the row) and `services`, with `revision` and `problem` (why `plugins.json` cannot be read, where Settings just shows none). A service is `running` (with `pid`), `stopped` (with `restart_in`, the seconds the note shows) or `starting` (declared, not started yet, also before the session is back). Window processes run in each local window's client and in each `plugin windows`, so the server cannot tell; a client that runs that command reads their state from its lines (#674, see Actions, hooks, services and running files).
  - **`cornercase plugin list` is unchanged**: it reads the files, as before; only the request gives service states.
  - **`cornercase plugin status`** (#469, `cli/plugin.rs`): the command for the `plugin-list` request, as `actions` is for `plugin-actions`. It asks the running server. `--json` prints that answer, escaping hidden characters as `plugin list --json` does so a path cannot spoof the terminal; a program still reads the same values: `plugins` (each with `state`, `label`, `note`, `services` and `button`) plus `revision` and `problem`. The text gives the revision, the problem when `plugins.json` cannot be read, then each plugin's id, state and label, its note, and each service (`running` with its pid, `stopped` with the seconds until it starts, `starting`). `plugin list` stays on the files and still works with no server.
  - **Buttons and popups** (#435): `plugin-list` gives each plugin its `button` (`title`, `icon` and the ids of its `button` actions in order, left out without any), and `plugin-actions` each action's `placement` and, for a popup, `width` and `height`, with `context: "button"` accepted. `plugin-run` without an `item` runs a `button` action as its button does, on what the window shows (`Spot::Shown`); any other action without one is `malformed`, and an older server, which requires `item`, refuses it as `malformed` rather than running it somewhere. A popup action answers when the popup closes, with the same outcome (`ended`, `code`), so a client knows what the user did in it: `ended` is `closed` when its `×` or `plugin-popup-close` closed it before its program ended (with an `error`, as anything but an exit with 0 has one), and a program ended by a signal has `signal` null and the signal's name in `error`, since the PTY's child status names the signal rather than numbering it (`Term::exit_status`); the context is the one it opened in (`button` without an `item`); with no window attached it is refused (`failed: no window is attached`), since a headless server would leave it open with nobody to see it, unless a view asks for it (#666, below). While a dialog or another popup is open in the window it is refused too, as a `conflict` (`a dialog is open in the window`, `a popup is already open`) answered at once: opening it would replace a form with its text, or a dialog busy installing an update or creating a workspace, which the window's own openers (the tour, the star card) wait for; only a menu is replaced, since the window's own button and menu entries open a popup from one. `open_plugin_popup` holds the same guard for every way in. `plugin-popup-close` (`Command::NAMES` grows by one) closes it as `×` does, `not-found` without one, and the `app` feed (`status --app`) has `popup` (`plugin`, `action`, `cols`, `rows`) while one is open, left out otherwise. Additive: `CONTRACT` stays 1. Its content and input go through `surface` and `input` with `popup` (#456, see Commands for scripts and agents › Streaming a tab's terminals and Driving a tab's terminals).
  - **Acting for a view** (#666, `control/view.rs`, `app/control/plugins.rs`, `app/plugins.rs`, `app/plugin_popup.rs`; `cornercase plugin run --view ID`): a program that draws cornercase itself (#345) can offer a plugin's buttons, but a `button` action ran on what the window shows, so a view that moved to another project ran it on the first one with nothing to tell the person, and a popup needed a window attached, although a view can show one and type into it since #456, so someone who only uses that program could never open one. `plugin-run` takes the envelope's `view` (`takes_view`), the mechanism `focus`, `new-tab` and `start` use, with no field of its own, and without it nothing changes.
    - **A `button` action with no `item`** runs on `Spot::ShownIn(view)`: context `button`, the ids `ViewInfo.shown` reports (`view_ids`) and the folder of the view's workspace (`view_env`; the project's with none open, `$HOME` with no project, as `shown_env` for the window). A request settles the views before it is routed, so a view on something closing has already moved. A `button` action named with a target stays refused and any other action without a target stays `malformed`: `--view` keeps the rule that a button acts on what is shown, and an `item` next to it runs where it says, the view only answering for the popup below.
    - **A popup opens while the view lives**: a live view is someone who can see it, so `popup_allowed` takes it in place of a window; `check_view` has already refused one that closed (`not-found`). Lives means connected: inactive and sizeless views count, since a program that follows the session with a view without a size can still draw the popup from `surface --popup`. The rest of the guard stays: another popup or a dialog is a `conflict`, also a dialog a window left open when it detached, which only a window can close (a limit kept rather than replacing a form that holds someone's text).
    - **Its size**: `Popup.view` remembers the view, and `popup_bounds` picks the area: a window's while one is attached (`has_window`), else the view's, else none. `Server::draw` calls `App::resize` with the last window's or `start-server`'s size on every draw, also with no window attached, so without that check the next draw resizes the popup to a size nobody sees: `size_popup` takes that area only while a window is attached or for a popup with no view. With no area the popup keeps its size: `width`×`height` or 80×24 when it opens in a sizeless view. `view-set` and the last window leaving call `size_popup(None)`, which moves only a popup a live view sizes, so it follows the view and goes back to it, as a tab does when the window's claim drops. A popup opened with a window attached keeps following that window, and one with no `view` is sized as before.
    - **When the view goes away** the popup stays, as it does when the last window leaves (`window_gone` closes no popup, and `e2e::plugins::a_popup_stays_open_when_the_last_client_leaves` pins it): its program keeps running at the size it has, a `plugin-run` still connected keeps waiting, and the next window shows it and sizes it. A program that comes back reads `popup` in the `app` feed, then shows it with `surface --popup` or closes it with `plugin popup-close`; until someone does, the next `plugin-run` of a popup is a `conflict`. Closing it with its view was rejected: a GUI that crashes or restarts would lose what the person was doing in it, for the reason a window that detaches does not, and the two rules would differ for one popup a window and a view can share. The view's id stays in `Popup.view` after that and finds nothing, and ids never repeat, so it cannot start following another view.
    - **The CLI and older servers**: `use_view` stops a server without views, which would drop the field and act on the window, and a server with views that predates this refuses the field by name (`` `plugin-run` takes no view ``). The feature `plugin-run-view` (additive, `CONTRACT` stays 1) lets a client know before it offers the button, and the CLI checks it after `use_view`, so that refusal comes as the usual `update cornercase` message. The revision lookup (`plugin-actions`, which takes no view: what is listed does not depend on where you stand) and the `status` lookup of `--worktree` go first, so only `plugin-run` carries the view; on a `requests` line it goes with that line only.
    - **Rejected**: moving the window first with `focus` and no `--view` (it moves the person's other window behind their back and does nothing for the popup); letting a `button` action take explicit ids (a client would have to pick how precise a target to pass, and the action would no longer run as its button does); a `view` in `PluginRun` (a second way to name a view, which strict fields and the envelope's checks would have to learn again). Left out: a `view` in the `popup` of the `app` feed and a popup only its view can see: it stays one popup for every client, as a popup reserved for the window was rejected in #456.
    - **Tests**: `app::tests::control_requests::plugin_views` runs on every OS, with `cmd.exe` panes and `fake_program` actions on Windows; the environment an action gets is in `control_requests::plugins::buttons_and_popups`, and the issue's own steps, the `requests` line and a view that dies with its popup open in `e2e::plugin_views`.
  - **Rejected or left for later**: turning plugins on and off, installing, updating and removing through the server (they work on the files, and installing shows a preview and asks; on another machine they run there as processes through `--remote` instead, #703, see Remote windows; a program shows that preview itself with `plugin install|update --preview --json` and confirms the commit with `--commit`, #468; `config` left the page to `cornercase plugin` too); a plugins part of the `app` feed (a client lists when it opens a menu, as the window builds its menu on the click); a run that answers at once and forgets the outcome; a request timeout (the action's five minutes bound it); window processes' state (the server does not have it; `plugin windows --json` prints it, #674); service states in `cornercase plugin list` (`plugin status` prints the `plugin-list` answer instead, #469).
