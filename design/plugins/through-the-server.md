# Plugins › Through the server

Part of [Plugins](../plugins.md).

- **Through the server** (#343, `control/plugins.rs`, `app/control/plugins.rs`, `cli/plugin.rs`; `cornercase plugin actions|run`): actions showed only in the window's menus, so another UI could not offer them nor run one the way the menu does, and what Settings › Plugins shows (on, off, cannot run, what a service does) was only on screen. Three request names, `plugin-list`, `plugin-actions` and `plugin-run` (`Command::NAMES` has 71), refused by name by an older server; no feature, `CONTRACT` stays 1, none takes a view.
  - **What is on disk now**: each reloads the plugins first (`App::reload_plugins`, what `watch_plugins` does once a second), so an answer right after `plugin link` or `enable` is current and a revision is checked against the files, not a reload up to a second late.
  - **The menu's revision**: `plugin-actions` answers the runnable actions, for a `context` or all, in the menus' order, with `plugin`, `name`, `action`, `title`, `contexts` and the `revision` (`Plugins::revision`, up by one each time the loaded plugins differ). `plugin-run` names `plugin`, `action`, `revision` and `item`; a revision the plugins moved past is `conflict`, as a menu opened before the change does nothing, so an action whose command or contexts changed since it was listed never runs. Ids rather than the menu's index, which means nothing to a client; the revision is required, and `cornercase plugin run` reads the current one when `--revision` is left out. It counts from the server's start like ids, so `boot` guards it across a restart.
  - **The target** is `close`'s `item`: a group, or a kind the action is not offered for, is `malformed` (the client listed its contexts); an id naming nothing is `not-found`; a workspace being removed or closing, or a project closing, is refused as for every command that names one, since the action would run in a folder being deleted. A plugin unknown, off or that cannot run, and an action it lacks, are `not-found` with the reason: the revision matched, so it was never listed.
  - **The menu's job**: `App::start_plugin_action` runs both, with the environment of what was named (`spot_env` gives the `Ids` the answer echoes), the workspace's folder, the five minutes, the plugin log's notes and the `plugins: action` job line. `run_to_end` moved to `plugins/run.rs` and returns a `Ran` (`Ended::Status`, `Timeout`, `Failed`, and how long it took) instead of an error, so a request gets the exit code; `Ran::failure` keeps the toast's texts, and `Job::fail` keeps a failed action's job line at WARN although the work itself succeeded. The menu still toasts a failure; a request never does, since nothing a request does changes what the window shows unless it asks to.
  - **The outcome** comes when the action ends (`Stage::Reading`): `plugin`, `action`, `context`, the ids it got, `ended` (`exited`, `signal`, `timeout`, `error`), `code`, `signal`, `error` (`null` once it exited with 0, else the toast's reason), `ms` and `log`. A failed action is an answer, not a refusal, as a failing tracker is for `issue-list`; `cornercase plugin run` exits 1 then. A client that leaves drops the answer and the action runs to its end, as a menu entry's does. No limit on how many run at once, as for the menu; whoever reaches the socket can already type into every pane, so running an enabled plugin's action asks for no new trust.
  - **What Settings shows**: `plugin-list` gives each registered plugin what `plugin list --json` prints (`id`, `enabled`, `source`, `log`, `manifest`, `error`) plus `state` (`on`, `off`, `cannot-run`), Settings' `label` and `note` (`Plugin::label` and `note`, shared with the row) and `services`, with `revision` and `problem` (why `plugins.json` cannot be read, where Settings just shows none). A service is `running` (with `pid`), `stopped` (with `restart_in`, the seconds the note shows) or `starting` (declared, not started yet, also before the session is back). Window processes run in each local window's client, so the server cannot tell.
  - **`cornercase plugin list` is unchanged**: it reads the files, as before; only the request gives service states.
  - **Rejected or left for later**: turning plugins on and off, installing, updating and removing through the server (they work on the files, and installing shows a preview and asks; `config` left the page to `cornercase plugin` too); a plugins part of the `app` feed (a client lists when it opens a menu, as the window builds its menu on the click); a run that answers at once and forgets the outcome; a request timeout (the action's five minutes bound it); window processes' state; service states in `cornercase plugin list`.
