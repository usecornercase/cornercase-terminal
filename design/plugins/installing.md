# Plugins › Installing

Part of [Plugins](../plugins.md).

- **Installing** (`plugins/source.rs`, `plugins/install.rs`, `plugins/archive.rs`; `cornercase plugin install|update|remove`): one model, in steps that never touch a terminal, so the CLI and any later dialog drive it the same way:
  1. `source::Origin::parse(spec)`: `owner/repo` (GitHub, `https://github.com/owner/repo.git`), an `https://` address without credentials, or an absolute folder, each with an optional `@ref` (a branch, tag or commit; letters, digits, `._/+-`, not starting with `-`, `/` or `.`, no `..`). Every other transport is refused (`file://`, `ssh://`, `git://`, `http://`, `ext::`, scp-like `host:path`); the CLI turns a relative or `~` folder into an absolute one first. **Plugins in a folder of a repository**, as herdr's `owner/repo[/subdir…]`: a repository can hold several plugins. On GitHub the parts after `owner/repo` are the folder (`acme/tools/plugins/notes`, also as `https://github.com/acme/tools/plugins/notes`). Any other address, and a folder on disk, cannot tell where the repository's path ends, so the folder comes after `//` (`https://host/acme/tools.git//plugins/notes`, `/srv/tools.git//notes`), the separator Terraform and go-getter use; `//` never occurs in a clean repository address or path, and `Origin::spec` writes it back the same way. Each part is letters, digits, `._-`, never empty, `.` or `..`, and never starting with `-`. `fetch` walks the folder in the checkout part by part and refuses one that is missing, a file or a symbolic link; the manifest is read there, a download unpacks and the build runs there, and only that folder is moved to `plugins/installed/<id>/<commit12>/`, so it is the plugin's root and `Manifest::program` confines its commands to it (a link to a sibling folder of the repository is refused like one out of the plugin). `Source::Git` keeps `subdir`, optional and left out when empty, so `update` fetches the same folder, and an id installed from another folder of the same address counts as another source.
  2. `install::fetch(&origin, &places) -> Fetched` (network, no plugin code runs): clones into a private staging folder (`plugins/installed/.staging/<pid>-<n>`, `0700`, cleared of folders whose process is gone), resolves the ref (a full 40-digit commit only as that commit, never as a branch or tag an author could name after a reviewed commit, and checked to be exactly it after the checkout; otherwise `origin/<ref>`, `refs/tags/<ref>`, then `<ref>` as a commit; `HEAD` without one), checks the commit out detached, drops `.git`, and reads the manifest without checking its programs (a build may make them). It refuses an id already linked or installed from another address. `Fetched` holds the origin, the full commit, the manifest and `replacing` (the installed commit and whether that version is on, so the preview says an update of a plugin that is on runs its new commands at once); dropping it deletes the staging folder, so a cancelled preview leaves nothing.
  3. `Fetched::preview() -> Vec<String>`: plain lines for any view: name, version, id, description, source (with its folder) and commit, permissions, the download (URL and sha256) or the build steps, every command it will run and in which entry, and that it is installed off and runs as you once on.
  3b. `Fetched::details()`: the same facts as fields (`id`, `name`, `version`, `description`, `repo`, `url`, `ref`, `subdir`, `commit`, `permissions`, `download`, `build`, `runs`, `replacing`) plus `lines`, the preview's own lines, for `--json`. `Manifest::declared()` is the one list of what a plugin runs, behind both the preview's commands and `runs`.
  4. `install::install(fetched, &places) -> Installed` (runs only after a confirmation, on a job thread in the app): downloads and unpacks the archive for this target when `[download]` has one, else runs the `[[build]]` steps in the checkout (argv, the plugins' environment, output to the plugin's log, 15 minutes each); then reads the manifest again and aborts if it differs from the previewed one in any field, checks its programs (`Manifest::load`), moves the checkout (or the plugin's folder of it) to `plugins/installed/<id>/<commit12>/` and records it in `plugins.json` as `{"kind":"git","repo","url","ref","subdir","commit","path"}`. A new plugin is off; an update keeps it on or off, since the user confirmed the new preview. Each version is its own folder, so a running service keeps its files until the supervisor restarts it on the new path; the folder before it is kept, older ones deleted. Installing again at the commit already installed (`owner/repo@stable` when `stable` is the installed default branch's commit) moves nothing: the existing folder is reused, the staged copy is dropped, and the entry is rewritten with the new origin (ref, address, subdir) and the same `enabled`, so later updates follow the new ref.
  5. `install::check_update(&places, id) -> Update::{UpToDate(commit), Changed(Box<Fetched>)}`: fetches the recorded address and ref again; the same commit changes nothing, another goes through `preview` and `install`. A linked plugin is refused. `install::remove(&places, id) -> Removed::{Unlinked, Deleted}` first turns the plugin off, then waits until nothing it ran is alive (below), and only then drops the entry and deletes `plugins/installed/<id>/`, so a service never loses its files while it still runs; a linked plugin is only forgotten, and the plugin's config and state folders stay.
  - Installed copies live next to the plugins' state (`paths::plugin_installs`, `plugins/installed/` beside `session.json`, so under `CORNERCASE_SOCKET` next to the socket), not in `$XDG_DATA_HOME`: one fewer base folder to find, clear and test.
  - **`[download]`**: `[download.<target>]` with `url` and `sha256`, the four targets `update::target` names. The URL must be `https://` (or `http://127.0.0.1:`/`localhost:`, for tests); the archive is a `.tar.gz` downloaded with `http::download` (256 MiB cap), checked against the sha256 before anything is written, and unpacked with the `tar` and `flate2` crates (both new; `flate2` was already built as a dependency of a dependency). A crate rather than the `tar` program, as `update.rs` uses, because each entry has to be looked at before it is written, which GNU tar and bsdtar do not let a caller do portably: only files and folders are unpacked (a symbolic link, hard link, device or FIFO refuses the archive), a path that is absolute or has `..` refuses it, a file is never written through a symbolic link already in the checkout (every folder above it is checked, and the file is created anew), modes are `0755` or `0644` (no setuid), and at most 20,000 entries and 1 GiB unpacked. A target without a download runs the build steps instead.
  - **git** runs as a process with no prompts, as elsewhere, plus `GIT_ALLOW_PROTOCOL` and `protocol.allow=never` with only `https` (or `file` for a folder) allowed, `core.hooksPath=/dev/null`, `transfer.fsckObjects`, a low-speed timeout, `--` before the address and `--end-of-options` before the ref, and without the `GIT_DIR`-style variables a shell may have set. Submodules are not fetched.
  - **A preview for programs** (#468, `cli/plugin.rs`): a client without a terminal (a GUI driving the CLI) could only pass `--yes`, which installs what nobody read and defeats the defence, or take the failure after the text, which meant scraping lines meant for people and fetching again, when a branch might resolve to another commit. `plugin install SOURCE --preview` runs steps 1 to 3 only and exits 0: nothing asked, nothing installed, the staging folder dropped. `--json` prints `details()`; `plugin update ID --preview --json` takes one ID, so each plugin gets one object and one exit status, and one up to date prints only `id`, `commit` and `up_to_date`. In `--json` mode stdout holds only the JSON (`fetching…` goes to stderr), and it passes through the same escaping of invisible characters as `plugin list --json`. Refusals still exit 1 with no preview. `--preview` with `--yes` or `--commit` is a usage error.
  - **`--commit SHA`** is the confirmation: install or update only when the fetch resolves to that commit, else exit 1 and nothing changes. A commit names its files, so what installs is what was shown. The origin keeps its ref, so updates still follow the branch or tag. Rejected: `SOURCE@COMMIT` as the confirmation (it works, but pins the plugin, so `update` never moves it again, and `update` has no SOURCE to take it); keeping the staged copy for a later command (the staging folder belongs to the process that fetched it and is cleared once that process is gone); a socket request (installing works on files, see Through the server).
  - **Security review** (of this diff against the core): the one finding was that a manifest could carry terminal escapes (`\u001b[6A\u001b[J`, `\r`) in a command argument, the description or a permission, which, printed in the preview, moved the cursor up and erased the build step or the changed service the user was about to confirm. `Manifest::check` now refuses a control character in any text of the manifest (every string, walked through its serde value, so a field added later is covered too), and `Fetched::preview` and git's errors escape any control or invisible character that would reach them (`text::escape_hidden`, as the core's errors do). The rest was checked and found as designed: options and transports, `.git` and hooks, the archive's paths and link types, the sha256 before unpacking, nothing built before the confirmation, the manifest compared again after the build, the private staging folder, and ids that cannot climb out of `plugins/installed/`. **Accepted risks**: the plugin's build steps and, once on, its commands run as the user (the preview and the confirmation are the defence, as for any installer); a build step can change any file in its folder but the manifest, so what the preview says it runs is what is recorded, not what those programs then do; a git folder given as the source is cloned with git's local transport, so it is trusted like any folder of the user's; `git` follows the user's own configuration (`url.<x>.insteadOf`, credential helpers, `git-lfs` filters), which is theirs to set; and the preview is shown once, so whoever confirms with `--yes` without reading it accepts what it says (a program shows it with `--preview --json` and confirms that exact commit with `--commit`).
  - **The symlink gap of PR 1**: a command whose program is a symbolic link out of the folder was only refused when it ran, so `link` and `enable` accepted it and `list` showed it on. `Manifest::load` now resolves every action, hook, service and window program (`Manifest::read` is the same without it, for previews), so `link` refuses it, `enable` refuses it, and `list` and Settings show the plugin as cannot run with the reason, as for any manifest error. A missing program counts too: a linked plugin whose binary is not built yet cannot be linked until it is. The manifest itself is opened with `O_NOFOLLOW`.
