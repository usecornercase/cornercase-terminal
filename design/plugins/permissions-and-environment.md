# Plugins › Turning plugins on, permissions, environment and folders

Part of [Plugins](../plugins.md).

- **Nothing runs until the user turns it on**: `link` adds a plugin turned off and says how to turn it on; `enable` (or `Enter` on its row in Settings › Plugins) is the explicit step, and both say that it runs as the user and what it asks for. Following herdr #2109, acquiring and enabling are separate steps. PR 2 follows what herdr does on `plugin update` (`src/cli/plugin.rs` at `6521382`): an update fetches the recorded ref, says it is up to date and changes nothing when the commit is the same, and otherwise shows the whole preview again (source, commit, every command) and asks before installing, with `--yes` required when there is no terminal; a build that changes the manifest after the preview aborts the update. A linked plugin cannot be updated and is read again when it changes, as in herdr, since it is a folder the user is writing.
- **Permissions are shown, not enforced** (the user's decision): a plugin runs as the user, and anything the user can do through the socket, it can do, including typing into every pane. Enforcing would need per-plugin tokens and a server that refuses requests without one, and since any local process of the user can reach the socket, that buys little until every unauthenticated request is refused, which would change how scripts work. The socket's authentication is unchanged. The risk is accepted and said plainly in Settings' hint, `enable`'s output and the docs. Also accepted: a linked plugin's manifest and scripts are read again when they change and keep running without asking again, since linking is for a folder the user is writing (PR 2 pins installed plugins to a commit); a plugin can read `secrets.json` (it is the user's file), its log holds whatever its commands print, and an action runs in the clicked workspace's folder, whose files it can change.
- **What a command inherits** (`plugins/run.rs`): the server's environment (the window's, for window processes), so `CORNERCASE_SOCKET` reaches the right server, minus `CORNERCASE_PANE`, `CORNERCASE_SERVER`, `CORNERCASE_RESTARTED`, Claude Code's and GitHub Copilot CLI's session variables (as `term` strips them from panes) and the issue trackers' token variables (`SHORTCUT_API_TOKEN`, `LINEAR_API_KEY`, `JIRA_API_TOKEN`, `PLANE_API_KEY`), which the server may hold and a plugin has no use for; plus `CORNERCASE_BIN` (`current_exe`), `CORNERCASE_PLUGIN_ID`, `_ROOT`, `_CONFIG` and `_STATE`, and `CORNERCASE=1` from the server. An action gets the ids of what was clicked (`CORNERCASE_PROJECT`, `_WORKSPACE`, `_TAB`, `CORNERCASE_PANE`), `CORNERCASE_PLUGIN_ACTION` and `CORNERCASE_CONTEXT`; only an action on a pane gets `CORNERCASE_SERVER`, since that token is what makes a command take `CORNERCASE_PANE` as its caller, and a hook or service has no pane to be. Tokens never go in the environment: `secrets.json` is never read for plugins. stdin is `/dev/null`; stdout and stderr go to the plugin's log. Each command is the leader of its own process group, so stopping it (`kill_process_group`) also stops what it started; a plugin that `setsid`s away escapes that, as in herdr, and the docs say a service must not detach.
- **Folders and the log**: `plugins/config/<id>/` next to `config.json` and `plugins/state/<id>/` next to `session.json` (`paths::plugin_config`, `paths::plugin_state`), created `0700`; the two prefixes keep them apart under `CORNERCASE_SOCKET`, where config and state share one folder. The log, `plugin.log` (`0600`), holds what the commands print and a line from cornercase per start, stop and exit of a service or window process and per failed hook or action, in `server.log`'s format. It moves to `plugin.log.1` past 1 MiB, checked each time a command starts: a service that runs for days keeps writing to the moved file until it restarts, accepted for a simple rotation without a pipe thread per process. `server.log` gets one line per start, stop, exit and hook or action (`plugins` target, through `log::Job`), never what the plugin printed, which keeps its never-logged rules.
