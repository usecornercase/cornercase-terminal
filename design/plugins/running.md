# Plugins › Actions, hooks, services and running files

Part of [Plugins](../plugins.md).

- **Actions in the menus** (`app/plugins.rs`, herdr #1722, its most asked-for plugin request): an action's `contexts` (`project`, `workspace`, `tab`, `pane`) put it at the bottom of the ` ⋯ ` and right-click menus of those rows, the tab bar and the pane menu, below the built-in entries (`App::target_menu`, `App::plugin_menu`). `MenuAction::Plugin` holds the spot, the action's index among the enabled plugins' actions and the registry's revision, so it stays `Copy`; an index from before a reload is ignored rather than running another action. An action runs on a job (`spawn_job`) in the clicked workspace's folder (the project's for a project), is killed after 5 minutes, and a failure comes back as `AppEvent::Plugin` with a toast naming the exit status and `cornercase plugin logs <id>`. No keys: a `plugins` group in the keys menu was left for later.
- **Event hooks**: the trace diff that feeds `cornercase events` also feeds hooks (`App::run_hooks` after `Events::publish`), so a hook sees exactly what `events --json` prints, as `CORNERCASE_EVENT`. While an enabled plugin has hooks the diff runs as if someone followed events (`App::following`, also for reading foreground jobs), and when hooks first appear the diff is run once before, as a new subscriber does, so the first one does not hear every open item as opened. Each hook is a job, killed after 60 s; at most 16 run at once and the rest are dropped with a `WARN`, so a burst of events cannot start a thread per pane forever. A long reaction belongs in a service following `events --json`.
- **Services and window processes** (`plugins/supervise.rs`): a `Supervisor` thread: one in the server for services, and one in each local window's client for window processes, the third kind of thread kept by hand beside the file read and the Tailscale worker (see Code layout), since it runs for the server's or the window's life rather than once. It reloads the registry when `plugins.json` or an enabled plugin's manifest changes (inode, modification time and size, checked every 250 ms), starts what is wanted, restarts what ended after 1, 2, 4… up to 60 s (back to 1 s once it ran for a minute) and stops what is no longer wanted (`SIGTERM` to its group, `SIGKILL` after 2 s). Watching the file rather than asking the server means `plugin enable` needs no new request (it works with no server and against older ones), and editing a linked manifest reloads it. A changed command or manifest restarts the entry. The server starts the service supervisor once the session is restored (`App::start_plugins`, after `open_first_terminals`, also when that failed to open a first terminal), so a service's first `status` sees the projects, and stops it in `Server::shutdown`, before the clients are told, on `kill-server`, a signal and a restart; the new server starts them again. What a supervisor is doing is shared with Settings as one note per plugin (`Supervisor::note`). A window process is started by each local window's client (`client::window::attach`, dropped when it returns, also before a restart's `exec`), so two local windows run two; under `cornercase remote` none runs, since the window's machine has no socket (a relay over the link was left for later). The supervisor publishes what each entry does (`Seen::Running { pid }`, `Stopped { until }`, per plugin and entry in key order) rather than one note per plugin, and the Settings note is derived from it with the same texts: a stopped entry wins, else the first running one.
- **Running files** (`plugins/supervise.rs`): each supervisor writes `plugins/state/<id>/running/<pid>` (`0600`, in the `0700` state folder; its text is the kind and entry) when it spawns a service or window process, and deletes it once that process is stopped or reaped, so the files list what is alive in the server's services and in every local window's processes alike. Only the leader of the command's process group is recorded, the one the supervisor signals and waits for. `plugin remove` (`install::remove`) sets the plugin off in `plugins.json` (nothing else to ask: the supervisors notice within 250 ms and stop it, `SIGKILL` after 2 s), polls `running/` every 100 ms for at most `STOP_WAIT` (10 s) and counts a file only when `process::alive` says its pid lives; a file for a dead pid is stale and deleted, so a supervisor killed with `SIGKILL` never blocks a removal. **An empty `running/` is not proof by itself, and neither is elapsed time**: a supervisor may hold an enabled list from before the save, a pass can be slow (stopping each changed entry takes up to 2 s before the next one is spawned), and a process exists for a moment before its file does, so no grace period or number of empty polls can show that spawning has stopped. Removal excludes spawns with a file lock instead (`flock`, as `server.lock` does): `plugins/state/<id>/running.lock` (`0600`). A supervisor spawns an entry only while holding a shared lock on it (`try_shared`, non-blocking: if removal holds it, that pass skips the entry and tries again later, so a supervisor never waits) and, once it has the lock, re-reads `plugins.json` from disk and spawns only if the entry is still the same one and still on (`on_disk`); it writes the marker before releasing, and never holds the lock while stopping or sleeping. `remove` saves the plugin off, then takes the exclusive lock (`exclude_spawns`, retried every 20 ms until the `STOP_WAIT` deadline, else it fails with the plugin installed and off) and releases it at once: every spawn that saw the plugin on has finished and written its marker by then, and every later one re-reads it as off and skips. The markers are then polled until none names a live process, within the same deadline. A supervisor never spawns from a folder that is gone (`spawn` checks it and takes the failed-start path with its backoff). Reading `running/` returns a `Result`: a missing folder is empty, any other error (the folder, or one entry) makes `remove` fail with the plugin installed and off, since a failed read proves nothing; likewise a supervisor that cannot write a file stops that child at once and counts a failed start. After the wait `remove` reopens the registry and goes on only if the entry equals the one it just turned off (same source, still off): Settings or another command may have turned it on or replaced it meanwhile, and then nothing is deleted. On timeout it fails naming the pids, leaving the plugin installed, listed and off, and says to run `remove` again; the same wait precedes forgetting a linked plugin (no folder is deleted there), while `unlink` stays a plain edit of the list. Files rather than a request to the server: the commands work on the files and never use the socket (a plugin can be removed with no server running), and window processes belong to each window's client, which the server does not know about. A reused pid can hold a stale file for as long as that other process lives, which the timeout bounds and `remove` again clears once it ends; a descendant that left the group (`setsid`) is not tracked, as for stopping.
- **The server loop never waits on a plugin**: hooks and actions run on job threads with timeouts, supervision on its own thread, and the loop only reads `plugins.json` and the manifests (bounded, regular files) once a second (`App::watch_plugins`), when Settings opens or switches a plugin and when a `plugin-*` request arrives (the action itself runs on a job).
- **Settings › Plugins** (`settings::Page::Plugins`, last): one row per linked plugin under **Installed** (`Row::Plugin`), its name and version, `[x] on` or `[ ] off`, and as note what it asks for while off and its description or its service's state while on; a plugin that cannot run shows its reason and refuses `Enter`. No plugin shows **no plugins yet** with the command that adds one. The page's hint says plugins run as the user and their permissions are not enforced. The app has no catalogue of its own (see Finding plugins).
- **The commands** (`cli/plugin.rs`): `cornercase plugin link <folder>`, `unlink`, `list [--json]`, `enable`, `disable`, `logs [-n] [--follow] [--path]` (sharing `cornercase logs`' printing). They work on the files, never through the socket, except `actions` and `run`, which ask the server (see Through the server).
