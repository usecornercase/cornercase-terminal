# Plugins › Actions, hooks, services and running files

Part of [Plugins](../plugins.md).

- **Actions in the menus** (`app/plugins.rs`, herdr #1722, its most asked-for plugin request): an action's `contexts` (`project`, `workspace`, `tab`, `pane`) put it at the bottom of the ` ⋯ ` and right-click menus of those rows, the tab bar and the pane menu, below the built-in entries (`App::target_menu`, `App::plugin_menu`). `MenuAction::Plugin` holds the spot, the action's index among the enabled plugins' actions and the registry's revision, so it stays `Copy`; an index from before a reload is ignored rather than running another action. An action runs on a job (`spawn_job`) in the clicked workspace's folder (the project's for a project), is killed after 5 minutes, and a failure comes back as `AppEvent::Plugin` with a toast naming the exit status and `cornercase plugin logs <id>`. No keys: a `plugins` group in the keys menu was left for later.
- **A button of its own** (#435, `app/plugins.rs`, `ui/chrome.rs`, `ui/activity.rs`): an action with the `button` context lands on its plugin's button, one per enabled plugin that has such an action, titled by `[button]` (its `name` by default). A context rather than a list of actions in `[button]`: it reuses the filter the menus and `plugin-actions --context` already apply, and keeps the rule that contexts put an action somewhere. With one `button` action the click runs it; with several it opens a menu of their titles in the manifest's order (`MenuAction::PluginButton` with the plugin's index and the revision, so an old menu does nothing, as for `MenuAction::Plugin`). The run's `Spot::Shown` carries no ids and resolves when it runs to what the window shows (`Report.shown`): it gets those ids, `CORNERCASE_CONTEXT=button`, and the shown workspace's folder, or `$HOME` with no project. The buttons sit in a row of their own, which exists only while some plugin has a button (`Areas.plugins`, height 0 otherwise) and costs the lists one line: side by side under the projects column's line (the workspaces column gets a blank row so the lines stay level); in the stacked and tree layouts under the tools, above ` More ▴ `'s line; in compact mode in the projects menu above ` Worktrees `. Buttons that do not fit leave a ` ⋯ ` in the last slot, which opens a menu of the plugins left out, each opening its own menu or running its one action. One `⋯` that holds only what does not fit, not an "app" menu shared by every plugin: that was rejected, since a plugin's entries would hide one click deeper for no reason. Drawing and the hit test share one geometry (`ui::plugin_buttons`), as for Help. With the icon bar each button takes a slot instead (see Tabs above the pane and the icon bar).
- **Popups** (#435, `app/plugin_popup.rs`, `ui/dialog/popup.rs`): an action with `placement = "popup"` runs in a terminal inside a dialog rather than as a job, from a menu, its button or `plugin-run`. The PTY is the server's, the one process that owns PTYs, so every attached client sees it (a browser or `cornercase remote` window too) and any client's keys reach it; its size follows the shared one, the last client used, as panes do. It is a `Term` spawned with the action's argv, the environment and folder a job of that action would get (`Places::launch`, shared with the job so the two never differ) and an id from the panes' counter, so `AppEvent::Output` and `Exited` find it; it is not in the `Hierarchy`, so `status`, `send` and `close` never see it. It lives in `Overlay::Popup`: modal (the window dims), one at a time like every overlay, never saved in `session.json`. Its size, side by side, is the action's `width` (or `height`), the program's terminal inside the border, when it fits in the area less 4 columns (2 rows), else 80 % of the area with its border; at least 20×5, the manifest's minimum (drawn cropped below that). It is resized (`SIGWINCH`) when the shared size changes (`App::resize`); one opened before any window gave a size starts at `width`×`height` or 80×24. The `×` acts on the press, as dialog buttons do. **Keys**: every key, `Esc` and the prefix key included, and pastes go to its program, checked before the prefix key and the panels' `Esc`; the mouse reaches it only when the program asked for it. A popup hosts programs that use `Esc` themselves (fzf, curses menus), so `Esc` closing it was rejected; the `×` cornercase draws on the border is always there. **Closing**: when the program exits, on `×`, on `plugin-popup-close`, and on `kill-server`, a signal and a restart (`stop_plugins`). It sends `SIGHUP` to the program's group and `SIGKILL` 2 s later if it still runs (`Stopping`, reaped on each refresh; on Windows to its tree, see Windows), the group so that the program's children go too; a child that left it (`setsid`) escapes, as for services. When the server stops, no refresh comes to send that `SIGKILL`, and dropping the `Term` kills only the program, not its children, so `stop_plugins` waits for what it hung up on, for at most 2 s and returning as soon as everything exited, then sends `SIGKILL` to the group of what still runs (`Stopping::finish`): a program that ignores `SIGHUP` and its children never outlive the server. A program that exits with another code than 0 toasts as a failed action, with `cornercase plugin logs <id>`. Opening and closing write a line to the plugin's log and to `server.log` (`plugins: popup`). No 5-minute limit: it is interactive, so a forgotten popup stays until someone closes it. While one is open nothing replaces it, since replacing the overlay would drop its `Term` and kill the program unlogged: every opener of another overlay is reached only from a key, a paste or a click, which the popup takes first, or (the tour's sections) waits for no overlay; the mouse goes to the popup before the star card, the tour card and the toast, so their buttons (a notice's ` go ` included) do nothing meanwhile; it counts as busy, so cancelling a form leaves it; and the recovery from a panic closes it as `×` does rather than dropping it. Checked by audit (October 2026) rather than by one `open_overlay` that every opener would call: no opener outside input could reach it.
- **Event hooks**: the trace diff that feeds `cornercase events` also feeds hooks (`App::run_hooks` after `Events::publish`), so a hook sees exactly what `events --json` prints, as `CORNERCASE_EVENT`. While an enabled plugin has hooks the diff runs as if someone followed events (`App::following`, also for reading foreground jobs), and when hooks first appear the diff is run once before, as a new subscriber does, so the first one does not hear every open item as opened. Each hook is a job, killed after 60 s; at most 16 run at once and the rest are dropped with a `WARN`, so a burst of events cannot start a thread per pane forever. A long reaction belongs in a service following `events --json`.
- **Services and window processes** (`plugins/supervise.rs`): a `Supervisor` thread: one in the server for services, and one in each local window's client (and each `plugin windows`, below) for window processes, the third kind of thread kept by hand beside the file read and the Tailscale worker (see Code layout), since it runs for the server's or the window's life rather than once. It reloads the registry when `plugins.json` or an enabled plugin's manifest changes (inode, modification time and size, checked every 250 ms), starts what is wanted, restarts what ended after 1, 2, 4… up to 60 s (back to 1 s once it ran for a minute) and stops what is no longer wanted (`SIGTERM` to its group, `SIGKILL` after 2 s; on Windows the group is a Job object, see Windows). Watching the file rather than asking the server means `plugin enable` needs no new request (it works with no server and against older ones), and editing a linked manifest reloads it. A changed command or manifest restarts the entry. The server starts the service supervisor once the session is restored (`App::start_plugins`, after `open_first_terminals`, also when that failed to open a first terminal), so a service's first `status` sees the projects, and stops it in `Server::shutdown`, before the clients are told, on `kill-server`, a signal and a restart; the new server starts them again. What a supervisor is doing is shared with Settings as one note per plugin (`Supervisor::note`). A window process is started by each local window's client (`client::window::attach`, dropped when it returns, also before a restart's `exec`), so two local windows run two; while the window is on another machine none runs, since the window's machine has no socket (a relay over the link was left for later); a window that switches to this machine starts them and stops them when it leaves (see Remote windows › Switching machines from the window). The supervisor publishes what each entry does (`Seen::Running { pid }`, `Stopped { until }`, per plugin and entry in key order) rather than one note per plugin, and the Settings note is derived from it with the same texts: a stopped entry wins, else the first running one.
- **`cornercase plugin windows`** (#674, `cli/plugin/windows.rs`, `cli/help/plugin_windows.rs`): only cornercase's own window kept window processes running, so beside a client that draws cornercase itself (#345) they never ran, although `plugin status` said they run in local windows. The command runs that same supervisor in its own process, for as long as the client keeps it, so a client gets the environment, the restarts, `running/` and its lock from the one implementation, and no request is needed. `Supervisor::of_a_window` is what it and `client::window` both call.
  - **It keeps running with nothing to do**: the plugin list comes from the local plugins folder, never from a request, so no server, no plugin that has a window process, and a `plugins.json` that cannot be read (read as `Registry::load` reads it, empty, where `plugin list` fails) all leave it running and watching, and it picks up whatever changes. The client keeps it for as long as its window is open: failing would make it restart the command in a loop, or give up on plugins turned on later. So it is dispatched before `run_here`, which opens the registry strictly. It never starts a server, as the supervisor never needed one. A server's restart does not touch it, where a window's restart `exec`s and starts its processes anew: what it runs and depends on the server ends when its stream does, and starts again by the backoff.
  - **A client running it counts as a local window**: two run two copies, as two windows do, and a window beside them runs its own. So `Plugin::note` now names the command after "local windows": it says what makes one run, since the server still cannot tell whether any does (see Through the server), and a client that does not run the command should not read the note as a state. It is in the Settings row too, the one thing this changes in the window.
  - **What it prints**: the supervisor publishes a snapshot rather than events, so `Known` compares `Supervisor::notes` with the last one each 200 ms, between waits for the reader. A new pid counts even if the stop between was missed, and each failed start is a change, since its `until` moves. An entry that left the notes (its plugin turned off, its entry removed) is `stopped` with no `restart_in`, which a client must see or it would show a process that is gone. A line is a `ServiceInfo` with its `plugin`, the fields `plugin status --json` gives a service, and in words `service_line`'s text; it goes to standard output, the stream whose reader is watched, as the follows' does. No last line per entry at the end: its output ending is that signal, and a reader that left or stopped reading could not get it anyway. Without `--json` a first line says what it does, or with no plugin it would look hung.
  - **Ending**: `os::process::on_end_signal` (`SIGTERM`, `SIGINT`, `SIGHUP`, `SIGQUIT`; registered before the supervisor starts, so a signal never finds children and no handler) or its reader leaving (`client::reader_gone_within`, with `watched`'s rules, as `logs --follow`, #475, since it reads no socket), then `Supervisor`'s drop stops them all as a window's close does: `SIGTERM` to each group, `SIGKILL` after 2 s, on Windows the job's windows and then the job. Status 0, as a follow whose reader left. `on_stop_signal` was not enough: the server outlives a hangup, and this command's terminal going is its end, as for a window. It catches `SIGQUIT`, which the window never meets (its raw mode keeps `Ctrl+\` from being a signal), since `Ctrl+\` here would leave the children behind.
  - **The report has a thread of its own**: `report` writes and polls the reader there, and the main thread waits for the first of a signal or the report's end. A client that keeps the pipe open and stops reading fills it, the next write blocks for good, and in one loop a `SIGTERM` would then never be seen, so the processes could only outlive the command. `a_reader_that_stopped_reading_does_not_hold_up_the_end` covers it. Rejected: `O_NONBLOCK` on standard output (it belongs to the open file, shared with whoever else holds it), and stopping from the signal's thread with `process::exit` (the same thread count, with an exit in the middle of a write). `panics::job` makes a panic in the report end the command with `Error::Bug` rather than leave it running silent.
  - **`SIGKILL` cannot clean up, as for a window**: on Linux and macOS what it ran keeps running with nothing to restart it; `running/` still names it, so `plugin remove` fails after its 10 s naming the pids rather than deleting a folder in use, and a pid that died is a stale file, deleted (see Running files). Since Rust's `Child::kill` is `SIGKILL`, the docs tell a client to close the pipe or send `SIGTERM`; a client that dies is fine, since its end of the pipe closes with it. A second process that outlives the first to do the cleaning was rejected, for what the window does not do either. On Windows the `Grouped` jobs' `KILL_ON_JOB_CLOSE` takes them along (see Windows › Processes, ports and stopping).
  - **On Windows a reader that left is seen only at the next failed write** (`watched` answers `None` there, see Windows › Lifting the refusal), which for this command can be never, so a client that dies leaves it and its window processes running. It is a known limit, on the website's list, with the way out (end it, or a Job object that kills it with the client), rather than a heartbeat line, which #475 rejected for changing a stream's output. There `on_end_signal` is `on_stop_signal`: its Ctrl events, and the hidden window's logoff, shutdown and `WM_CLOSE`.
  - **`--remote` is refused** (`reach::Kind::BesideTheWindow`, status 2): window processes run on the machine that shows the window, and a request is not what it needs. `Kind::Here`'s message would say to run it there through ssh, which is the one thing it should not suggest. A line of `requests` is refused too, with its own message: it would never answer, and hold every line after it. `CORNERCASE_REMOTE` counts as the flag does, as for every command that is not `Apart`: a client set up for another machine's server should not start this machine's plugins by accident, as its window would not.
  - **Rejected** (the issue): reading `manifest.window` from `plugin list --json` and running them in the client, which copies the environment, the restarts, and the files and lock `plugin remove` relies on; having the server start them for a `view`, which may be on another machine.
  - **Checked**: `tests/e2e/plugin_windows.rs` (Linux, and macOS in CI) with a real manifest and no server: the process appears, `--json` tells, killing it restarts it, each signal and a closed pipe end it, a full pipe does not hold up the end, plugins turned on and off and removed while it runs. On every system `cli::plugin::windows::tests` runs a real `fake_program` through the supervisor and ends it each way but the signal itself, since `tests/e2e` does not run on Windows; live with a debug build on Linux (2026-11-06), a real terminal's Ctrl+C and its closing included. Not checked: Windows' Ctrl events and `taskkill` with this command, which `on_stop_signal`'s own checks cover (see Windows › The server's process).
- **Running files** (`plugins/supervise.rs`): each supervisor writes `plugins/state/<id>/running/<pid>` (`0600`, in the `0700` state folder; its text is the kind and entry) when it spawns a service or window process, and deletes it once that process is stopped or reaped, so the files list what is alive in the server's services and in every local window's processes alike. Only the leader of the command's process group is recorded, the one the supervisor signals and waits for. `plugin remove` (`install::remove`) sets the plugin off in `plugins.json` (nothing else to ask: the supervisors notice within 250 ms and stop it, `SIGKILL` after 2 s), polls `running/` every 100 ms for at most `STOP_WAIT` (10 s) and counts a file only when `process::alive` says its pid lives; a file for a dead pid is stale and deleted, so a supervisor killed with `SIGKILL` never blocks a removal. **An empty `running/` is not proof by itself, and neither is elapsed time**: a supervisor may hold an enabled list from before the save, a pass can be slow (stopping each changed entry takes up to 2 s before the next one is spawned), and a process exists for a moment before its file does, so no grace period or number of empty polls can show that spawning has stopped. Removal excludes spawns with a file lock instead (`flock`, as `server.lock` does): `plugins/state/<id>/running.lock` (`0600`). A supervisor spawns an entry only while holding a shared lock on it (`try_shared`, non-blocking: if removal holds it, that pass skips the entry and tries again later, so a supervisor never waits) and, once it has the lock, re-reads `plugins.json` from disk and spawns only if the entry is still the same one and still on (`on_disk`); it writes the marker before releasing, and never holds the lock while stopping or sleeping. `remove` saves the plugin off, then takes the exclusive lock (`exclude_spawns`, retried every 20 ms until the `STOP_WAIT` deadline, else it fails with the plugin installed and off) and releases it at once: every spawn that saw the plugin on has finished and written its marker by then, and every later one re-reads it as off and skips. The markers are then polled until none names a live process, within the same deadline. A supervisor never spawns from a folder that is gone (`spawn` checks it and takes the failed-start path with its backoff). Reading `running/` returns a `Result`: a missing folder is empty, any other error (the folder, or one entry) makes `remove` fail with the plugin installed and off, since a failed read proves nothing; likewise a supervisor that cannot write a file stops that child at once and counts a failed start. After the wait `remove` reopens the registry and goes on only if the entry equals the one it just turned off (same source, still off): Settings or another command may have turned it on or replaced it meanwhile, and then nothing is deleted. On timeout it fails naming the pids, leaving the plugin installed, listed and off, and says to run `remove` again; the same wait precedes forgetting a linked plugin (no folder is deleted there), while `unlink` stays a plain edit of the list. Files rather than a request to the server: the commands work on the files and never use the socket (a plugin can be removed with no server running), and window processes belong to each window's client, which the server does not know about. A reused pid can hold a stale file for as long as that other process lives, which the timeout bounds and `remove` again clears once it ends; a descendant that left the group (`setsid`) is not tracked, as for stopping.
- **The server loop never waits on a plugin**: hooks and actions run on job threads with timeouts (a popup's PTY is read by its own thread, as a pane's), supervision on its own thread, and the loop only reads `plugins.json` and the manifests (bounded, regular files) once a second (`App::watch_plugins`), when Settings opens or switches a plugin and when a `plugin-*` request arrives (the action itself runs on a job).
- **Settings › Plugins** (`settings::Page::Plugins`, last): one row per linked plugin under **Installed** (`Row::Plugin`), its name and version, `[x] on` or `[ ] off`, and as note what it asks for while off and its description or its service's state while on; a plugin that cannot run shows its reason and refuses `Enter`. No plugin shows **no plugins yet** with the command that adds one. The page's hint says plugins run as the user and their permissions are not enforced. The app has no catalogue of its own (see Finding plugins).
- **The commands** (`cli/plugin.rs`): `cornercase plugin link <folder>`, `unlink`, `list [--json]`, `enable`, `disable`, `logs [-n] [--follow] [--path]` (sharing `cornercase logs`' printing). They work on the files, never through the socket, except `status`, `actions`, `run` and `popup-close`, which ask the server (see Through the server). `status` prints the `plugin-list` answer, what Settings › Plugins shows, including each service; `--json` escapes hidden characters as `list --json` does. `list` stays on the files.
