# Terminals

Code: `term.rs`, `term/emulator.rs`, `term/reader.rs`, `term/shell.rs`

- The emulator is libghostty-vt: it answers terminal queries (DSR, DA, DECRQM, kitty keyboard…) that programs like fzf and nvim wait for, and reflows on resize.
- Its types are `!Send`, so the emulator lives on the server's main thread; the reader thread only forwards bytes. Query replies go out from `on_pty_write`, ordered with the output that asked.
- **Output applies backpressure per pane** (#493): the reader takes a permit before reading and each output event keeps it until the main thread has parsed or discarded the bytes. The permits travel with the event through both the app and server queues; bounding only an intermediate channel would let the forwarder move the backlog into the next queue. A full window blocks that reader, fills the PTY buffer and slows the program without losing or reordering output. Other panes and control requests keep their own senders. Dropping an event returns its permit even when the pane has closed, its generation changed or handling panicked.
- Every write to a PTY (keys, pastes, launches, query replies) goes through one writer thread per pane (`term::spawn_writer`), in order: once a terminal's input buffer is full, a write to a program that doesn't read blocks, and on the server loop that froze every client (a long paste or `cornercase send` into a pane running `sleep`). Each pane queues at most 16 MiB (`term::MAX_QUEUED`): past that `Term::write` refuses and returns `false`, `send` and `keys` answer that the program is not reading, and typing or pasting in the UI shows a toast instead of losing keys silently. A write is taken whenever the queue is below the limit, so one long paste still goes through. Linux and macOS both block a write once the terminal's input queue is full and either a line is waiting or the terminal is not in canonical mode; in canonical mode with no newline waiting, both take the excess and drop it, so that queue never fills (the App tests that need a full pane turn canonical mode off). Pastes drop `\x1b[201~` from the text (`term::bracketed`), so a paste cannot end itself and type the rest.
- Cells keep palette indices so the outer theme applies. The client asks the outer terminal for its foreground, background and 16 ANSI colours (OSC 10/11/4, then XTVERSION, then DA1 as an end marker) before starting the input thread, and every emulator uses them, or the colours a client gave (see Colours for programs), as defaults. Entries 16-255 keep the emulator's (libghostty-vt's) default colour cube and greys: these are normally fixed, unlike the themed ANSI colours, and indexed cells still draw through the outer terminal's own palette. The 256-slot `HostTheme` and its wire representation stay the same; unset entries leave the emulator defaults intact. Programs querying a customised entry above 15 therefore see the default value, while their indexed output still uses the host's value.
- **Cells cleared with a background keep it** (#333): Ghostty stores a cell erased while a background colour is set (`\e[44m\e[K`, `\e[48;2;1;2;3m\e[2X`: background-colour erase, which `TERM=xterm-256color`'s `bce` promises, so vim, less, htop and ncurses rely on it) as content `BgColorPalette` or `BgColorRgb` with `has_styling()` false and no `bg_color` in its style, so the snapshot, which read `cell.style()` only when styled, drew those cells with the default background in the window and in surfaces. `capture` reads the raw cell once per cell (also for `wide()` and `has_hyperlink()`) and, for an unstyled cell, takes the background from its content tag, keeping the palette index (not the resolved colour, which loses it). The cost is one tiny getter per cell.
- **A snapshot also knows what a surface needs** (#286): `Cell::spacer` marks the right half of a wide character (Ghostty's `CellWide::Wide` on the cell before it, asked only for cells with text; its `symbol` stays `" "`, so `contents()`, path links and launches keep their columns), `Snapshot::shape` and `blinking` the cursor's DECSCUSR style, and `Snapshot::scroll` the scrollbar, computed once (`below` comes from it; Ghostty warns the call can be expensive). The window ignores the spacer, since ratatui's diff already skips the cell after a wide symbol. `Emulator` also answers `focus_events` (DEC 1004) and `kitty_keyboard` (the flag bits).
- cwd, name and arguments of the PTY's foreground process group leader come from `process.rs`: `/proc` on Linux, `proc_pidinfo` / `proc_name` / `sysctl(KERN_PROCARGS2)` on macOS (with `getpeereid`, the only `unsafe` and the only use of `libc`). In a pipeline the leader may be dead (`process::alive`), so the shell is used instead. Agent launch and detection depend on it. Windows has no process groups: there it is the first program under the shell that is not a shell (see Windows).
- **The shell** a new pane starts is chosen once, when the server starts (`term::shell::default`): `$SHELL`, else `/bin/sh` on Unix; on Windows the order is under Windows.
- **ConPTY** (Windows; checked 2026-11-03 on Windows 11 25H2, build 26200.9711, with portable-pty 0.9.0, which asks for `PSEUDOCONSOLE_INHERIT_CURSOR`, `PSEUDOCONSOLE_RESIZE_QUIRK` and `PSEUDOCONSOLE_WIN32_INPUT_MODE`, under both console hosts it may load: the system's `conhost.exe`, which started with `--inheritcursor` alone, and WezTerm's `OpenConsole.exe` from the `PATH`, see Windows; `term::tests::on_windows` checks the start, the size, titles, links, the mouse, status reports and copies, and passed under both):
  - **It repaints rather than passes bytes through**: what the shell writes arrives as the host's own frames of its buffer (cursor moves, the cursor hidden and shown around a frame). A line longer than the pane came whole from conhost, and from OpenConsole as `\r\n` then its last cell again, so the soft wrap is marked either way. Sequences the host does not interpret (OSC 7501, OSC 52, OSC 9, OSC 777, RIS) go through as they are written, so they can arrive before text written ahead of them, which waits for the next frame; titles come after the frame. So program status reports and copies reach the emulator.
  - **The start**: the host sends `ESC[6n` before anything of the shell, and shows nothing and runs nothing until the cursor report comes back (checked: a command typed meanwhile did not run in 3 s, and ran once the report went back, so typing is held, not lost). The emulator answers once that output is fed, so no first output is lost; a pane whose output nobody feeds never starts, and closing it needed a report of its own (see Windows). It also turns on `ESC[?9001h` (win32-input-mode, which Ghostty ignores, so keys stay plain VT and the host translates them) and `ESC[?1004h` (focus reports, so every Windows pane gets focus in and out): OpenConsole before the request, conhost after the report.
  - **The size**: programs see the size the pane was opened with (`[Console]::WindowHeight` and `WindowWidth`), and a resize reaches them; the host then sends `ESC[8;rows;colst`, which the emulator ignores, and repaints the screen.
  - **Titles**: `title` (the console's own) and an OSC 0 or 2 a program writes both arrive as OSC 0, with non-ASCII intact (`✳`), so agent status from titles works. cmd retitles the console while it runs a program (`<title> - <command line>`).
  - **Links**: an OSC 8 link keeps its address; the host adds an `id=`.
  - **Mouse**: a mouse mode a program asks for (`ESC[?1000h`, `ESC[?1006h`) stays in the host and never reaches the emulator, so a Windows pane never reports one and a click there selects text in cornercase. Whether a program that turns on mouse input through the console API gets clicks was not checked. Bracketed paste (`ESC[?2004h`) does reach it.
