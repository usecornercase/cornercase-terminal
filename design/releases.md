# Releases

Code: `.github/`, `dist-workspace.toml`, `site/public/install.sh`, `site/public/install.ps1`

- **How a release happens**: on a push to `main`, `.github/workflows/version.yml` runs `.github/version.sh release`, which tags `v<version>` if it is new and dispatches `.github/workflows/release.yml` (`dist`, `dispatch-releases`, because a tag pushed with `GITHUB_TOKEN` triggers no workflow). That builds the five targets (Linux and macOS on x86_64 and arm64, Windows on x86_64), makes the GitHub Release (notes from `CHANGELOG.md`) with `cornercase-installer.sh` and `cornercase-installer.ps1`, and pushes the formula to `usecornercase/homebrew-tap` (secret `HOMEBREW_TAP_TOKEN`, a fine-grained token that expires). `.github/build-setup.yml` is the Zig step `dist generate` puts into `release.yml`, for every build runner. `site/public/install.sh` (served at `usecornercase.dev/install.sh`) runs the latest release's shell installer, and `site/public/install.ps1` (`usecornercase.dev/install.ps1`) its PowerShell one.
- **Windows** (#602): `x86_64-pc-windows-msvc` builds on `windows-2025` into a `.zip` (dist's zips are flat: `cornercase.exe` at the root) with the PowerShell installer, which puts it in `%USERPROFILE%\.local\bin` (`install-path`) and adds that folder to the user's `PATH`. The line it is run with, `powershell -ExecutionPolicy Bypass -c "irm https://usecornercase.dev/install.ps1 | iex"`, is dist's own: `irm | iex` runs no script file, but the installer's `Expand-Archive` is a script module, which the default `Restricted` policy of Windows PowerShell refuses to load.
  - **Installing over a running cornercase** (`site/public/install.ps1`): dist's installer copies the new `cornercase.exe` over the old one (`Copy-Item`), which Windows refuses while it runs, and the background server almost always does, so running the line again (to repair or reinstall) failed. `install.ps1` is ours and the installer is dist's (generated, never edited by hand), so ours first renames an existing `cornercase.exe` in the folder the installer will use (its rule: `CORNERCASE_INSTALL_DIR`, `CARGO_DIST_FORCE_INSTALL_DIR`, `CORNERCASE_UNMANAGED_INSTALL`, else `~\.local\bin`) to the first free `cornercase.old.exe` or `cornercase.old.N.exe`, the names the app's startup cleanup removes once nothing runs from them (see Updates › On Windows), then runs the installer, and puts the old file back when no new `cornercase.exe` landed. The rename is the first step of the `try` whose `finally` puts it back, so a stop right after it (Ctrl+C) still restores it; a killed PowerShell runs no `finally`. The installer ends a failure with `exit 1`, which inside `iex` would end the whole PowerShell before the old file could come back, so ours writes it to a temporary `.ps1` (UTF-8 with a BOM, which Windows PowerShell needs to read it as UTF-8) and runs it as a script, where `exit` ends only that script and sets `$LASTEXITCODE`, which ours turns into an error. A script file needs an execution policy that runs it, which the published line's `-ExecutionPolicy Bypass` gives; a bare `irm | iex` under Windows PowerShell's default `Restricted` fails there, as dist's own `Expand-Archive` would. The server keeps running the old version until it restarts, as after an update. Checked on 2026-11-03 with the published line in Windows PowerShell 5.1 against a local server (as in Checked below, a stand-in `cornercase.exe` running from the install folder): dist's installer alone failed with a sharing violation; through `install.ps1` the install went through and left `cornercase.old.exe`, and an install whose download failed put the file back and ended with status 1.
  - **Long paths**: Ghostty's sources hold files past `MAX_PATH`, so its clone needs `core.longpaths` (see Windows › Long paths). dist's generated workflow sets it with `git config --global` as the first step of every build, and Ghostty is cloned by the `git` command under the same user, so no step of ours is needed. Linking stays under the limit: the runner's `target\x86_64-pc-windows-msvc\dist\` is shorter than the folder of the local check below.
  - **Checked** (2026-11-03, Windows 11 26200, dist 0.33.0 built from its tag, since 0.33.0 is not on crates.io): `dist build --artifacts=local --target=x86_64-pc-windows-msvc` with a `CARGO_TARGET_DIR` 18 characters deeper than the runner's `target\` built the zip and its `.sha256`, and its `cornercase.exe --version` ran; `dist plan` lists the zip and `cornercase-installer.ps1`. The published line, run in Windows PowerShell 5.1 with `install.ps1`'s URL and `CORNERCASE_DOWNLOAD_URL` pointed at a local server serving them as `application/octet-stream` (as GitHub does) and `CORNERCASE_UNMANAGED_INSTALL` set (so the `PATH` was left alone), went through `install.ps1`, the generated installer and the zip, and the installed binary ran. `release.yml` did not change: dist computes the build matrix in its `plan` job. The runner and the release job were not run before merging.
  - **Every release now needs the Windows build**: `host` runs only when every build succeeded, so a change that breaks the Windows build holds back the release on every system. `clippy + tests (windows-2025)` in `ci.yml` catches a broken build on the pull request, and since 2026-11-04 it is a required check, so such a change cannot merge.
  - **No arm64 build**: `libghostty-vt` has never been built for `aarch64-pc-windows-msvc` and no CI job checks it, and a target that fails holds back every release (above). Windows on Arm runs the x64 build under emulation, which dist's installer picks there (its platform table lists x64 as emulated support on arm64), and `update::target()` follows the build rather than the machine, so an emulated install updates to the x64 build again. Adding arm64 means a CI job on a `windows-11-arm` runner first.
- **Feature branches**: a feature made of several pull requests that means nothing to users until all of them land (remote hosts, #539) gathers them on `feat/<issue>-<name>`, branched from `main`, and reaches `main` in one pull request. Only that last one bumps the version and names the `## Unreleased` section of `CHANGELOG.md` where the others write their notes, so CI checks the version only for pull requests into `main`; CodeRabbit reviews pull requests into `feat/` branches too (`base_branches`). The branch takes `main` in with merges, never a rebase, so a revert made on `main` to hold part of it back, reverted again on the branch, stays reverted.
