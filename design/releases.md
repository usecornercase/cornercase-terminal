# Releases

Code: `.github/`, `dist-workspace.toml`, `site/public/install.sh`, `site/public/install.ps1`

- **How a release happens**: on a push to `main`, `.github/workflows/version.yml` runs `.github/version.sh release`, which tags `v<version>` if it is new and dispatches `.github/workflows/release.yml` (`dist`, `dispatch-releases`, because a tag pushed with `GITHUB_TOKEN` triggers no workflow). That builds the five targets (Linux and macOS on x86_64 and arm64, Windows on x86_64), makes the GitHub Release (notes from `CHANGELOG.md`) with `cornercase-installer.sh` and `cornercase-installer.ps1`, and pushes the formula to `usecornercase/homebrew-tap` (secret `HOMEBREW_TAP_TOKEN`, a fine-grained token that expires). `.github/build-setup.yml` holds the steps `dist generate` puts into `release.yml` before every build, on every build runner: Zig, then Ghostty's build, tried three times (see When a release fails). `site/public/install.sh` (served at `usecornercase.dev/install.sh`) runs the latest release's shell installer, and `site/public/install.ps1` (`usecornercase.dev/install.ps1`) its PowerShell one.
- **Windows** (#602): `x86_64-pc-windows-msvc` builds on `windows-2025` into a `.zip` (dist's zips are flat: `cornercase.exe` at the root) with the PowerShell installer, which puts it in `%USERPROFILE%\.local\bin` (`install-path`) and adds that folder to the user's `PATH`. The line it is run with, `powershell -ExecutionPolicy Bypass -c "irm https://usecornercase.dev/install.ps1 | iex"`, is dist's own: `irm | iex` runs no script file, but the installer's `Expand-Archive` is a script module, which the default `Restricted` policy of Windows PowerShell refuses to load.
  - **Installing over a running cornercase** (`site/public/install.ps1`): dist's installer copies the new `cornercase.exe` over the old one (`Copy-Item`), which Windows refuses while it runs, and the background server almost always does, so running the line again (to repair or reinstall) failed. `install.ps1` is ours and the installer is dist's (generated, never edited by hand), so ours first renames an existing `cornercase.exe` in the folder the installer will use (its rule: `CORNERCASE_INSTALL_DIR`, `CARGO_DIST_FORCE_INSTALL_DIR`, `CORNERCASE_UNMANAGED_INSTALL`, else `~\.local\bin`) to the first free `cornercase.old.exe` or `cornercase.old.N.exe`, the names the app's startup cleanup removes once nothing runs from them (see Updates › On Windows), then runs the installer, and puts the old file back when no new `cornercase.exe` landed. The rename is the first step of the `try` whose `finally` puts it back, so a stop right after it (Ctrl+C) still restores it; a killed PowerShell runs no `finally`. The installer ends a failure with `exit 1`, which inside `iex` would end the whole PowerShell before the old file could come back, so ours writes it to a temporary `.ps1` (UTF-8 with a BOM, which Windows PowerShell needs to read it as UTF-8) and runs it as a script, where `exit` ends only that script and sets `$LASTEXITCODE`, which ours turns into an error. A script file needs an execution policy that runs it, which the published line's `-ExecutionPolicy Bypass` gives; a bare `irm | iex` under Windows PowerShell's default `Restricted` fails there, as dist's own `Expand-Archive` would. The server keeps running the old version until it restarts, as after an update. Checked on 2026-11-03 with the published line in Windows PowerShell 5.1 against a local server (as in Checked below, a stand-in `cornercase.exe` running from the install folder): dist's installer alone failed with a sharing violation; through `install.ps1` the install went through and left `cornercase.old.exe`, and an install whose download failed put the file back and ended with status 1.
  - **Long paths**: Ghostty's sources hold files past `MAX_PATH`, so its clone needs `core.longpaths` (see Windows › Long paths). dist's generated workflow sets it with `git config --global` as the first step of every build, and Ghostty is cloned by the `git` command under the same user, so no step of ours is needed. Linking stays under the limit: the runner's `target\x86_64-pc-windows-msvc\dist\` is shorter than the folder of the local check below.
  - **Checked** (2026-11-03, Windows 11 26200, dist 0.33.0 built from its tag, since 0.33.0 is not on crates.io): `dist build --artifacts=local --target=x86_64-pc-windows-msvc` with a `CARGO_TARGET_DIR` 18 characters deeper than the runner's `target\` built the zip and its `.sha256`, and its `cornercase.exe --version` ran; `dist plan` lists the zip and `cornercase-installer.ps1`. The published line, run in Windows PowerShell 5.1 with `install.ps1`'s URL and `CORNERCASE_DOWNLOAD_URL` pointed at a local server serving them as `application/octet-stream` (as GitHub does) and `CORNERCASE_UNMANAGED_INSTALL` set (so the `PATH` was left alone), went through `install.ps1`, the generated installer and the zip, and the installed binary ran. `release.yml` did not change: dist computes the build matrix in its `plan` job. The runner and the release job were not run before merging.
  - **Every release now needs the Windows build**: `host` runs only when every build succeeded, so a change that breaks the Windows build holds back the release on every system. `clippy + tests (windows-2025)` in `ci.yml` catches a broken build on the pull request, and since 2026-11-04 it is a required check, so such a change cannot merge.
  - **No arm64 build**: `libghostty-vt` has never been built for `aarch64-pc-windows-msvc` and no CI job checks it, and a target that fails holds back every release (above). Windows on Arm runs the x64 build under emulation, which dist's installer picks there (its platform table lists x64 as emulated support on arm64), and `update::target()` follows the build rather than the machine, so an emulated install updates to the x64 build again. Adding arm64 means a CI job on a `windows-11-arm` runner first.
- **When a release fails** (#738, #812, #816, #840, #841):
  - **The story**: 0.13.30's Intel macOS build timed out on `deps.files.ghostty.org`, and nothing ran it again or told anyone. #732's work could not be installed for 2.5 h, and 0.13.31's notes lacked 0.13.30's.
  - **The story, again** (#812, #816, 2026-11-13): 0.13.63's `aarch64-apple-darwin` build (and 0.13.40's, on 2026-11-11) was cancelled after 15 minutes in the queue with no step run: GitHub had no macOS runner, and nothing inside a job can retry a job that never started. And `after-release.yml` (#738) never ran for a tag: 0.13.52, 0.13.58 and 0.13.63 failed with no issue, and the notes of v0.13.53 and v0.13.59 lack 0.13.52's and 0.13.58's sections.
  - **The story, a third time** (#840, #841, 2026-11-14): 0.13.73's `host` job (run 43581442033, attempt 1) failed at `Download GitHub Artifacts` a second after uploading `artifacts-dist-manifest`: GitHub listed it but could not serve it (`No artifacts found for ID: 14108639112`). Release watch left it, since the job had run steps; a re-run by hand published 0.13.73 at 10:45 UTC, 44 minutes later, with nothing changed. And GitHub had started the watch's schedule twice in 14 hours.
  - **Ghostty's build tries three times**, 60 s apart, before dist's build, which then finds it fresh (the `ghostty` step of `build-setup.yml`):
    - It uses the same profile, target and features as dist. Checked on Linux on 2026-11-10: a full `cargo build` with dist's profile and target, after the `-p libghostty-vt-sys` one, printed `Fresh libghostty-vt-sys` (dist itself and the real runners were not run before merging).
    - On every `*-windows-msvc` target it sets the `RUSTFLAGS` dist 0.33.0 adds there (`-Ctarget-feature=+crt-static`). If dist changes them, only time is lost: Zig's packages stay in `ZIG_GLOBAL_CACHE_DIR`, which setup-zig points at the workspace's `.zig-cache` for the whole job.
    - `dist generate` drops `timeout-minutes`, so the step has none.
    - Rejected: caching Zig's packages between runs. A Release runs on its tag, and a cache saved on one tag cannot be restored on another, only one saved on `main`. On `main`, CI's `rust-cache` keeps Ghostty built in `target/`, so its build script and Zig's download seldom run there to fill a cache, and a cache key filled empty would stay empty.
    - Rejected: retrying `dist build` itself, because `release.yml` is generated.
  - **Release watch** (`release-watch.yml`, `version.sh watch`, #816): 50 minutes after each Release run that `version.sh` dispatches or re-runs (see Dispatched after each release), every 15 minutes (minutes 7, 22, 37 and 52) as a backstop, and by hand, on `main` only, it re-runs or tells the newest tag's last Release run, then completes the notes of the five newest tags.
    - **Why a schedule and a dispatch**: GitHub's rule is that "events triggered by the `GITHUB_TOKEN` will not create a new workflow run", with `workflow_dispatch` and `repository_dispatch` as exceptions (https://docs.github.com/en/actions/concepts/security/github_token, read on 2026-11-13). A tag's Release run is dispatched by the Version workflow with its `GITHUB_TOKEN`, so its actor is `github-actions[bot]`. The docs do not name `workflow_run`, but `after-release.yml` had 124 runs from 2026-11-10 to 2026-11-13, all skipped and all after pull requests' Release runs; none followed a tag's run, not even a person's re-run of one (0.13.63's attempt 2). A scheduled run is GitHub's own, on `main`'s latest commit. `workflow_dispatch` is the exception the Version workflow uses to start Release runs, and the one both `release` and `watch` use to start a delayed watch.
    - **Dispatched after each release** (#841):
      - **Why**: between its first run (a dispatch, 2026-11-13 20:31 UTC) and 2026-11-14 14:55 UTC GitHub dropped most scheduled runs (the count is under Limits; `gh run list --workflow release-watch.yml`). A release whose job never started could wait hours, and a newer tag could be released first.
      - **How**: right after `version.sh release` dispatches a Release run, and right after `version.sh watch` re-runs one, it dispatches `release-watch.yml` on `main` with `wait=50`. That run's `wait` job sleeps 50 minutes, then its `watch` job runs `version.sh watch`. The `wait` job is limited to 60 minutes, so a dispatch by hand asks for at most 55; a longer wait ends at the limit and the watch then runs anyway.
      - **Why 50 minutes**: of the tag Release runs from 2026-10-30 to 2026-11-14, the 115 that ended on their first attempt took a median of 24 minutes, 31 at the 90th percentile and at most 48.5; every first attempt that failed ended within 32. `host` runs after the slowest build, so a failure there comes late; 50 covers every run seen.
      - **The re-run first, then the dispatch**: if GitHub refuses the re-run (the run is too old, or already re-running), `set -e` ends the watch before it dispatches the next one. A watch dispatched first would come back, fail the same re-run and dispatch again, every 50 minutes without end. Re-runs stop at three attempts, so each Release run brings at most three dispatched watches: one from Version and two after re-runs.
      - **The wait outside the concurrency group**: a run that held `release-watch` while sleeping would keep a scheduled run pending; a newer dispatched run would then wait behind it and could be replaced by the next scheduled one, which runs at once, before the newest Release run has ended, and never comes back. So only the `watch` job holds the group, and parallel sleepers are harmless.
      - **Cost**: a Linux runner sleeps 50 minutes per Release dispatch (about 12 a day in November 2026) and per re-run; standard runners are free on a public repository, and the sleeping job takes one of its concurrent job slots.
      - **Kept: the schedule**, as the backstop for a dispatched watch that finds the run still going or for a dispatch that failed.
      - **Rejected**: more cron minutes (GitHub drops most of them); an external scheduler (one more service to keep running); an environment's wait timer (the delay would live in the repository's settings, not in the code; GitHub creates a missing environment on first use with no timer, so the watch would run at once; and each run would record a deployment); following the Release run with `gh run watch` (it acts sooner, but holds a runner as long, needs a polling loop with its own limit, and must follow every re-run again); the Version workflow sleeping (see the rejection below); a `push` trigger (it fires just as the next version is being tagged, which would re-run the previous tag inside the window where a re-run's release becomes Latest).
      - **Limit**: a dispatched watch that finds the Release run still going does nothing and dispatches nothing; the schedule or the next release comes back to it.
    - **It replaced `after-release.yml`** rather than sitting beside it: `workflow_run` fires only for a Release run a person creates, which a dispatched watch or the schedule reaches too; it made a skipped run for every pull request's Release run; and one workflow is one path, with no concurrency group to share.
    - **Rejected: the Version workflow waiting for its dispatch.** Its `version` group keeps one pending run, so a push meanwhile would replace the pending one and that version would never be tagged by its own run. Holding a runner for the wait is accepted now, in the Release watch's own `wait` job (see Dispatched after each release).
    - **Rejected: a token that is not `GITHUB_TOKEN`.** A GitHub App or a personal token is a secret a person must create and renew, and none is configured.
    - **Rejected: dist's `post-announce-jobs`.** They do not run once a build failed, and `release.yml` is generated.
    - **Limits**: GitHub delays or drops scheduled runs under load, more at the start of the hour (for this one it dropped most: 3 of 74 slots, 2026-11-13 20:31 to 2026-11-14 14:55 UTC, #841, so the schedule is only a backstop); it disables a public repository's schedule after 60 days without activity; a scheduled watch run that fails is notified to whoever last changed its `cron` line (who is told when a dispatched one fails was not checked). The `watch` job's concurrency group stops a dispatched run, a run by hand and a scheduled one from acting at once, and the `wait` job is outside it; it does not share Version's group, because a group keeps one pending run and sharing it could cancel a pending Version run and leave a version untagged.
  - **A job GitHub never started runs again** (#812):
    - **The rule**: the newest tag's last run ended in `failure` and every job that did not pass has no step, as a job no runner took looks (`steps` empty). Then `gh run rerun <id> --failed`, up to three attempts in all, counted by the run's `attempt`, a person's re-runs included. Shortages lasted at least 15 minutes twice in three days.
    - **What GitHub re-runs**: the cancelled job and the jobs that need it, keeping the jobs that passed and their artifacts. 0.13.63's re-run by hand rebuilt only `aarch64-apple-darwin` and published all five archives. It is a re-run rather than a fresh dispatch like the Version workflow's, so only that job is built again.
    - **Not re-run**: a job that ran a step and failed (a real failure, such as 0.13.58's `plan`), except `host`'s lost manifest (below), a run that ended `cancelled` (someone stopped it; Release has no concurrency group, and a job with no runner made both observed runs end in `failure`), any tag but the newest, and a run while another Release run of its tag has not ended. A tag with no Release run at all is left to the Version workflow.
    - **After the third attempt** the issue names the jobs that never started.
    - **Accepted**: a version tagged while a re-run waits for its runner can be released first, and the re-run's release then becomes Latest. The Version workflow's re-dispatch has the same window.
  - **A `host` that could not download its own manifest runs again** (#840):
    - **The rule**: the newest tag's last run ended in `failure`; `host` is the only job that did not pass, and its only failed step, from the jobs API, is `Download GitHub Artifacts`; `gh run view <id> --attempt <n> --log-failed` holds `No artifacts found for ID`; the tag has no GitHub Release. Then `gh run rerun <id> --failed`, within the same three attempts. After the third, the issue says how the last attempt failed.
    - **Why a re-run is safe**: `Create GitHub Release` comes after the failed step, so nothing was published; GitHub re-runs `host` and the jobs that need it and keeps the builds and their artifacts. 0.13.73's attempt 2 did just that.
    - **The step from the jobs API, the line from the log**: the run's log archive holds one file per job, not per step, and `gh` 2.103.3 labels the lines it cannot place `UNKNOWN STEP`. It did so for every line of 0.13.34's, 0.13.41's, 0.13.42's and 0.13.52's runs on 2026-11-14, while it placed 0.13.73's. So the step's name is read from the jobs API and the line is searched in the whole failed log. A log that cannot be read counts as not lost: the failure is told.
    - **Not re-run**: `host` failing at another step (0.13.52's `Create GitHub Release`, an HTTP 500 from `gh release create`); `host` failing at `Download GitHub Artifacts` with another error; another job failing too; a tag that already has a release. The rule matches dist's generated names `host` and `Download GitHub Artifacts`: if dist renames them, it stops matching and the failure is told.
    - **Rejected**: a wait between the upload and the download (`build-setup.yml` runs only on the build runners, and `release.yml` is generated); re-running every `host` failure (a real one, such as a bad token, would be retried three times for nothing).
  - **A failed Release opens an issue** (`version.sh failed`, from Release watch):
    - When the newest tag's last run did not pass and is not re-run, it opens "Release vX failed" or comments on the open one. The issue is closed by hand.
    - It tells once per attempt: the issue links `…/runs/<id>/attempts/<n>`, and an issue with that title, open or closed, that already links the attempt is enough. A closed one counts because closing it is how a person says they saw it; without that, every scheduled run would open a new issue.
    - Only the newest tag is told. An older one is left, and the next release's notes carry it.
  - **The Version workflow releases a tag left without a release**:
    - Only the version on `main`, when no Release run is pending. An older tag released after a newer one would become the Latest release, because GitHub marks a new release Latest by default and dist's `gh release create` passes nothing to stop it. `install.sh`, `install.ps1` and the update check all read Latest. So an older tag is left, and the next release's notes carry it.
    - It makes a fresh dispatch rather than `gh run rerun`: one path for every case (a dispatch that never ran, a run too old to re-run), at the cost of building every target again.
    - It also runs by hand, on `main` only.
  - **Release notes carry the versions that never got a release** (`version.sh notes`, from Release watch on the five newest tags, which cover the releases published between two watch runs even when GitHub drops most scheduled runs, since each release dispatches a watch):
    - The body's `## Release Notes` part holds every `CHANGELOG.md` section newer than the previous published release, newest first, each under `### x.y.z`. With one version the body stays as dist wrote it. It edits only when the body lacks the `### x.y.z` heading of a version it carries, so each release is edited once and a person's later wording stays. It passes `--latest=false` when the release is older than the newest: `gh release edit` sends `make_latest` only with `--latest`, and GitHub's docs say only that it "defaults to true for newly published releases". `###` keeps the app's fallback reading all of them (see Updates).
    - The update dialog itself already read every version from the `CHANGELOG.md` asset; this fixes the Releases page and other programs that read the body.
    - The notes are written after the release exists, because dist writes the body from the version's own section and nothing can run before it in the generated `host` job.
  - **Where `notes` runs**: Release watch, not a dist `post-announce-jobs` job, which would not run when Homebrew failed after the release was published.
  - **Holding a version back** now means bumping it: deleting only a bad release and keeping its tag no longer holds it, since the next push to `main` releases the tag again.
  - **Tests**: `.github/version.test.sh` runs `version.sh` against a fake `gh` (which answers `run list`, `run view` (jobs, and the failed log), `issue list` and `issue view` from files each case writes; a re-run is checked by its own line, since the issue's text quotes the command) and a bare origin, in the guardrails job.
  - **Checked** (2026-11-10): the tests, and against the repository's real tags with `DRY_RUN=1`: `release` on the current version, `notes` on v0.13.32, v0.13.30 and v0.13.31 (which gets 0.13.30's section), `release` from a clone at v0.13.30 (dispatches it again) and `failed` for the run that failed. `after-release.yml` runs only from `main`, so it was not run before merging; it then never ran for a tag (#816).
  - **Checked** (2026-11-13): the tests, actionlint 1.7.7, and `watch` with `DRY_RUN=1` against the real repository and from clones with the newer tags deleted: at v0.13.40 it re-runs run 43051288651 (attempt 2 of 3), at v0.13.58 it tells the failed run, at v0.13.59 it prints the notes with 0.13.58's section added (the `--latest=false` of an older release is checked by the tests only). Release watch runs only from `main` (a `workflow_dispatch` needs the file on the default branch), so it first ran after merging.
  - **Checked** (2026-11-14): the tests, actionlint 1.7.7 (with shellcheck 0.10.0), and `watch` with `DRY_RUN=1` against the real repository (v0.13.75's run ended in success, nothing to do) and from a clone at v0.13.73 with a stand-in `gh` that shows run 43581442033 as its failed attempt 1 and hides v0.13.73's release: it re-runs run 43581442033 (attempt 2 of 3) and dispatches a watch with `wait=50`, where the script before this change opened an issue. The `wait` input, the `wait` job and the dispatches first ran after merging.
- **Feature branches**: a feature made of several pull requests that means nothing to users until all of them land (remote hosts, #539) gathers them on `feat/<issue>-<name>`, branched from `main`, and reaches `main` in one pull request. Only that last one bumps the version and names the `## Unreleased` section of `CHANGELOG.md` where the others write their notes, so CI checks the version only for pull requests into `main`; CodeRabbit reviews pull requests into `feat/` branches too (`base_branches`). The branch takes `main` in with merges, never a rebase, so a revert made on `main` to hold part of it back, reverted again on the branch, stays reverted.
