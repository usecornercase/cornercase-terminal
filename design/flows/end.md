# Flows › The end

Part of [Flows](../flows.md).

- **The end** (#372, `Run::reached`, `Run::latch`, `Run::moved_to`, `ui::flow::Ending`): `◆` was purple only while the orchestrator's status was exactly `pending`, so it meant "the orchestrator rests with its review mark", not "the pull request exists", and went grey again when the orchestrator kept working after opening it (a mark put on during a turn only shows once the turn ends), when a follow-up made it work again (going from idle or waiting to working clears the mark), when another status outranked it (waiting, failed), and never lit for an orchestrator that skipped the brief's last rule.
  - **The rule is in the model**, a pure `Run::reached(pull)`; the diagram takes its answer in `Ending` and no longer reads the orchestrator's state. A pull request counts only for a flow whose end is `pull_request`, and only while it is open, a draft or merged (closed does not, as the row draws it muted and crossed out). The pull request is the run's workspace's (`App::pull_request`, the row's own `gh pr view` or `glab mr view`, so no new call): a role with a worktree of its own (#313) never shows its own, since its branch is a candidate, not what the run delivers. Without the CLI that applies to the project (`gh`, or `glab` on GitLab), a remote or with `pull_requests` off there is none and the end falls back to the mark.
  - **The mark is latched, raw** (`Run::ended`): `App::latch_run_ends` checks the orchestrator's `agent.pending()` on every refresh, before `watch_agents`, because `Pane::update` clears the mark when the agent goes from idle or waiting to working: a mark followed at once by a new prompt is still seen. It reads the raw mark, not `Status::Pending`, since a mark put on during a turn stays set through it, which covers the first case above even for a flow that leaves the commits (whose only signal this is). Every way of marking sets that flag (menu, keys `m`, `cornercase mark`, a restored session), so one check covers all, sessions from older versions included. Unmarking does not clear it: it is latched for the run.
  - **It holds the branch it was taken on** (`Run::ended: Option<String>`, saved as the optional `RunState::ended`, so a restart keeps it and `VERSION` stays 5), taken only when `git::checked_out` reads one (a detached HEAD waits for the next refresh; the mark lasts far longer). The 1 s sync step forgets it when the workspace is checked out on another branch (`forget_moved_run_ends`), as `Found::branch` does for the pull request; a detached HEAD keeps it, since that is what a rebase looks like. Forgetting it also clears the orchestrator's mark, or the next refresh would latch the new branch from the same mark. The simulation latches in the mark action too, not only when the panel draws, so a mark reviewed while the panel is closed still counts.
  - **The tag** is the row's `ui::theme::pull_tag` as it is, after the label and a muted ` · `. Where it fits beside the `◆` it sits there, else the whole line goes on the row under it, centred, as the label alone did. In a narrow panel the label is cut first and the tag kept while its cells fit; with fewer than 2 cells left for the label, the label and the separator go and only the tag is drawn; when not even the tag fits it is dropped. `natural_width` leaves the tag out on purpose: counting it would widen the diagram when a pull request appears and the loop lanes and boxes would jump; as is, the only change is one more row under `◆` at the built-ins' widths (Full issue is about 50 columns; Arena at 100 has room beside it). The geometry stores the label and the tag's cells (`Geometry::end_label`, `end_tag`), which drawing and hit testing share; a click on the tag (`Hit::Pull`) opens the pull request dialog for the run's workspace (`open_pull_request`, like the row's badge), and hover underlines it. **ask agent** there keeps its rule, the active tab's agent first, which in a run's workspace is usually the orchestrator.
  - **Scripts** get `run` in each workspace of `status --json`, `watch` and `view`, an optional object left out when the workspace runs no flow (`{"end": "pull_request", "reached": true}`; `end` is a string so an older CLI does not fail on a future kind), additive under the contract's rules, so the v1 fixtures are unchanged; it is in the `refreshed()` fingerprint, so a latch flipping sends a snapshot. An object rather than a bool because #342 plans a run's state per workspace, which can join it.
  - **Known costs**: a mark put on by mistake keeps the end lit for the run; a run started on a branch that already has an open or merged pull request shows its end reached from the start (telling whether the run opened it would need `createdAt` from `gh`, which is not asked). A GitLab merge request (#402) lights the end like a pull request: `App::pull_request` returns either, so `Run::reached` and the tag (`#486`, see Pull requests) did not change. The brief says to open a merge request with `glab mr create` when the repository is on GitLab, in one clause, since a provider argument would be a sixth parameter for something the agent reads from `git remote -v`.
