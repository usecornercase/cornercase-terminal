# Flows › Syncing your flows with your machines

Part of [Flows](../flows.md). Code: `flows/sync.rs`, `machines/flows.rs`, `app/flow_sync.rs`, `cli/flow/sync.rs`, #915.

- **Why**: your flows live in `flows/` next to one computer's `config.json`, so a flow made or tuned on the laptop did not exist on the VPS, and the `run on` row of Start flow (#543) listed the machine's own, older copy. Copying by hand (`flow export | cornercase --remote vps flow import - --replace --yes`) after every edit, on three or four machines, drifted. A project's flows already travel with the repository; this is about yours.
- **What syncs**: the files of `flows/` (yours, your edits of built-ins included) and the built-ins you deleted (`hidden_flows`). `default_flow` and `flow_order` stay per computer: they name what each one has, and two computers with different flows would fight over them. Broken files are not sent.
- **Opt-in per machine**: `sync_flows` on an entry of `machines` (the form's box `sync your flows to it`, after `show its work here`; `machines add|edit --sync-flows`, `edit --no-sync-flows`; `sync_flows` in `machines --json`, left out when false). Off by default, so nothing is written on a machine without asking. Turning it off stops the sends and leaves the flows there. Only a machine this server links, so a hidden one (`shown: false`, #917) gets nothing until it is shown again; one reached only by a window (`cornercase remote`) has no link to send through, which the issue left open and this keeps out.
- **Push, with the requests a script would send**: on a machine's own connection per request (Remote windows › Asking a machine), the server asks `flow-list` there, plans, then sends `flow-import` (`place: yours`, `replace: true`), `flow-delete`, `flow-hide` or `flow-restore`, one request each, so the machine needs no new storage or request and decides as it does for a script. Pull was rejected in the issue (it breaks when the linking computer is off). One round runs on a job per machine at a time; a change during a round marks it to run again once, rather than queueing one round per change. **The round's start time is taken on the loop, when the flows and the journal are read** for it (not when its job starts), so a change recorded after that snapshot is always after the time the round records, and the next round sends it. A round is started only for a machine `config.json` marks to sync at that moment, so turning it off stops the very next send, before the peer list is refreshed. Requests carry no `boot` (no ids are involved), so the answers are read in both shapes, plain and structured.
- **When**: when a sync machine's link comes up (also the first time, and after this server restarts), when `sync_flows` is turned on, after every change to your flows here (a save in Settings › Flows or `flow-save`, a rename, a move to the project, an import into yours, a delete, a hide, a restore), and on ` sync now ` or `flow sync`. A machine that is down gets everything it missed when its link comes back, since the round compares the whole state. A hand edit of a file in `flows/` is sent with the next round, not when it is made: nothing watches the folder.
- **Last saved wins, by each computer's clock**: every save of a flow of yours stamps `changed` (a UTC time with milliseconds, the `Stamp` format) in its file; a project's flow is never stamped, so a repository's diffs do not churn. A flow is sent when the machine has none of that name among its own or an older one (`changed` missing counts as oldest); a newer one there is kept (`kept` in the answer) and comes back here only if that machine syncs to this one. When neither side has a time (files from before #915) the flow is sent only if it differs, compared as `FlowSpec` from the raw `flow-list` answer, not the cleaned one the run on row shows, so a hidden character can never make two machines send a flow back and forth forever. An import with `synced_from` keeps the incoming `changed`; any other import stamps the time of the import, since a shared flow becomes yours when it is imported. **Clocks decide**: `changed` is each computer's wall clock, so a machine whose clock runs ahead wins conflicts it should lose; this is inherent to the rule the issue chose, and the website says so in one line. Two bounds keep a wrong time from pinning a flow: a sync import whose `changed` is more than 5 minutes (`sync::SKEW`) ahead of the receiver's clock is saved with the receiver's time instead (and logged), and the sender treats one of its own times in the future as now when it compares. Rejected: a logical clock or version vector (a new field on both ends and a harder rule to explain for a few machines of one person).
- **Deletions need a journal**: a deleted flow leaves nothing to compare, so `flow-sync.json` next to `session.json` (the state folder, like `star.json` and `tour.json`, since its round times are this computer's: kept beside `config.json`, a config folder shared through dotfiles or a cloud folder would hand one computer another's times and make it skip deletions) keeps the last change per name that is not a save (`deleted`, `hidden`, `restored`, with its time, at most 256), and per destination the time the last round with it started (`synced`). A save of that name drops its entry. A round sends the entries newer than the machine's `synced`, and each only while what the machine has is older than the change. **A deletion, hide or restore the machine refuses, or that times out, is kept in `retry` for that machine** and sent again with every later round (still only while it holds: a newer change of that name here, or a newer save there, drops it), while `synced` moves on, so one stuck change does not make every other change be sent again; a flow deleted because it held a secret must not stay runnable there because one request failed. Sends need no retry: files are compared every round: a flow saved there after the deletion stays (`kept`). A deleted edit of a built-in is a `flow-restore` there (`flow-delete` refuses a built-in's name). **A flow only the machine has is never deleted**, and **a first round sends no deletion at all**: a machine just marked could otherwise lose its own flows to a deletion made here months ago. A first round does send the built-ins deleted here (from the journal's time, or as the oldest change when the journal has none, so a built-in edited there wins). The journal lives only on the sending side; the receiving server records the deletion in its own journal like any other, so it travels on along its own links.
  - **Limit**: a built-in hidden or restored on the machine while it was out of reach, after the opposite change here, is overwritten by the change made here: the machine's journal is not read, which kept the requests unchanged. Files are compared by their time and never have this gap.
- **Secrets in `env` go too**: a flow is sent whole, `env` values included, as `flow export` would. The form's note and `--sync-flows`'s help say so, and **a flow file that sets `env` is written readable only by its owner** (`0600`, `persist::Kind::Private`) on both ends, also for a flow saved here, so a shared or multi-user machine does not hand its other users the values. Windows has no such mode; the file is in the user's profile.
- **No question, and the log never holds the text**: a flow runs its `env` and `args` unattended, so an import from the CLI asks. Here both ends are the same person's machines, marked on purpose, so nothing asks (as the issue asked). The sending side logs `flow synced` with the machine, the flow's name and the change, `flow not synced` with why; the receiving side logs `flow imported` with sizes as every import does, and `flow replaced by a sync` with the name. Agents a synced flow uses that are not installed there get the usual note on that machine's Flows list.
- **The receiving side says so**: a `flow-import` with `synced_from` (this computer's name, `host::name::computer`, read on the job) that replaces a different flow of yours shows a toast, `Duo was replaced by laptop's copy: your flows sync from there`, and a new flow `Duo arrived from laptop's flows: your flows sync from there`, kept 6 s, and both are logged with the sender's name (`flow replaced by a sync`, `flow added by a sync`). The same flow again says nothing. `synced_from` is cleaned before it is shown or logged (hidden characters dropped, one line, at most 64 characters, `machines::flows::sender`), since any client of the socket may send it. **A deletion, hide or restore arriving from a sync is not told** on the receiving side: they are the plain `flow-delete`, `flow-hide` and `flow-restore` requests, which carry no `synced_from`, and adding it to three more requests for a toast was left out; the receiver's log has `flow deleted` and the sender's names the machine. Nor can the receiving side refuse a sync: the sender already has ssh and the socket there, and the machine was marked on the sender on purpose (a receive-side opt-out was left for later).
- **Over the socket** (contract stays 1): `flow-sync` (`{machine}`, operation 138, `Command::NAMES` has 139) answers once every machine asked has finished a round started after the request, as a `Stage::Reading` pending answer: `{"machines": [{"machine", "sent", "deleted", "hidden", "restored", "kept", "same", "failed": [{"name", "error"}], "error"}]}`, names in each list, `same` a count, `error` why a machine could not be reached (a machine not linked is answered at once with why, and does not wait). It is refused as `conflict` when no machine syncs flows or `machine` names one that does not (the message says how to turn it on), `not-found` for an unknown name or a hidden one (the message says `machines show`). **A machine whose link falls while a request waits on its round** is answered as soon as its round ends and the link is down, with an `error` (`vps unreachable: your flows go there when its link comes back`), so `flow sync` never hangs on a machine that went away. `cornercase flow sync` exits 1 when a machine has an `error` or any `failed` entry, after printing the answer. Behind the feature `flow-sync`, so `cornercase flow sync` against an older server says what it cannot do instead of sending an unknown request. `flow-list` entries gain `changed` (yours only) and `synced` (the machines whose last round confirmed this exact version; left out when empty), `machines` entries `sync_flows`, `flow-import` `synced_from`: all additive. A bot cannot sync flows (`NO_FLOWS`, like the other flow changes).
- **The window**: Settings › Flows has ` sync now ` while a machine syncs flows (dropped first after Share when the row is narrow), and a flow of yours notes `synced to vps, mini` in its row. What `synced` knows is in memory: after a restart it fills in with the first round of each link.
- **Tests**: the plan and the journal (retries, times) are unit tests; one round against a fake machine over socket pairs (a refused deletion kept for retry); the app with a linked fake machine: sends, deletions, a deletion refused once and sent again, a change during a round giving exactly one more round that a request waits for, a link falling under a waiting request, a newer copy there kept, turning the box off stopping the next send, the receiving side's times and toasts; the file mode on Unix; e2e with two real servers.
- **Rejected**: a flows folder in a git repository or a cloud folder (a remote or a sync tool on every machine, conflicts in git; a symlink already does it for those who want it); syncing the whole `config.json` (machines, ports and accounts differ; sharing settings, #414, moves a setup once); a new request that writes a whole set of flows at once (a machine would need new storage and an older one could not take part); asking the machine's journal (one more request shape for the narrow limit above).
- **Checked** with the e2e tests' two real servers and the fake `ssh`: an import here reaches the machine with its `changed`, a hidden built-in is hidden there, `flow sync` names the machine in `synced`, and a deletion here deletes it there. Not checked against a real sshd.
