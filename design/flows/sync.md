# Flows › Syncing your flows with your machines

Part of [Flows](../flows.md). Code: `flows/sync.rs`, `machines/flows.rs`, `app/flow_sync.rs`, `cli/flow/sync.rs`, #915.

- **Why**: your flows live in `flows/` next to one computer's `config.json`, so a flow made or tuned on the laptop did not exist on the VPS, and the `run on` row of Start flow (#543) listed the machine's own, older copy. Copying by hand (`flow export | cornercase --remote vps flow import - --replace --yes`) after every edit, on three or four machines, drifted. A project's flows already travel with the repository; this is about yours.
- **Manual, not automatic** (the user's decision, 2026-11-20, after an automatic version was built): the issue described sync on every save, delete and hide, opted into per machine, with a journal of deletions, a first round that deleted nothing, retries with backoff and rounds owned by the server. The user wanted a button instead: you send what you saved when you want a machine to have it. That removed the per-machine `sync_flows` field and its form box, the journal (`flow-sync.json`), deletions and hidden built-ins travelling, the retry list and the automatic retry, and the background rounds with their races (a round outliving a turned-off box, a stale round's answer, a clock stepping back past a recorded deletion): a sync now runs only when asked and ends with its answer.
- **What is sent**: the files of `flows/` (yours, your edits of built-ins included), all of them or one. A built-in you did not change and a project's flow are not yours to send (the button is not offered for them, and the request refuses their names: `conflict` for a built-in, `not-found` for any other name). **Nothing is deleted on the machine**, and **hiding or restoring a built-in stays on each computer**, as do `default_flow` and `flow_order`: they name what each one has, and two computers with different flows would fight over them.
- **Where**: every machine of Settings › Machines that this server links (`machines::linked`: shown here and with a valid entry), or only `--machine`'s. A hidden one (`shown: false`, #917) is refused by name (`not-found`, the message says `machines show`) and left out of "all"; one reached only by a window (`cornercase remote`) has no link to send through. No opt-in per machine: you choose when you click.
- **Push, with the requests a script would send**: on a machine's own connection per request (Remote windows › Asking a machine), a job per machine asks `flow-list` there, plans, then sends `flow-import` (`place: yours`, `replace: true`, `synced_from`), one request per flow, so the machine needs no new storage or request and decides as it does for a script. Pull was rejected in the issue (it breaks when the linking computer is off). A machine that is not linked at that moment is answered at once with why (`vps is still connecting`, `vps unreachable`), with nothing queued for later: syncing again once it is back is the user's call. Requests carry no `boot` (no ids are involved), so the answers are read in both shapes, plain and structured.
- **Last saved wins, by each computer's clock**: every save of a flow of yours stamps `changed` (a UTC time with milliseconds, the `Stamp` format) in its file; a project's flow is never stamped, so a repository's diffs do not churn. A flow is sent when the machine has none of that name among its own or an older one (`changed` missing counts as oldest); a newer one there is left alone and reported as `kept`. A copy with the same text and the same time is `same` before any time is compared. When neither side has a time (files from before #915) the flow is sent only if it differs, compared as `FlowSpec` from the raw `flow-list` answer, not the cleaned one the run on row shows. An import with `synced_from` keeps the incoming `changed`; any other import stamps the time of the import, since a shared flow becomes yours when it is imported.
  - **The receiver checks too**: the plan is made from the listing, and a flow can be saved there between that `flow-list` and the `flow-import`. So a `flow-import` with `synced_from` is refused when the copy it would replace has a newer `changed` (`a newer copy of it was saved here`, `sync::NEWER_HERE`), and the sender counts that refusal as `kept`, not as a failure. An import without `synced_from` (`flow import --replace`) replaces as asked, whatever the times.
  - **Clocks decide**: `changed` is each computer's wall clock, so a machine whose clock runs ahead wins conflicts it should lose; this is inherent to the rule the issue chose, and the website says so in one line. Two bounds keep a wrong time from pinning a flow: a sync import whose `changed` is more than 5 minutes (`sync::SKEW`) ahead of the receiver's clock is saved with the receiver's time instead (and logged), and a flow of yours whose own `changed` is that far ahead is saved once with this computer's time before a sync compares it, and logged. **If that fix cannot be saved** (a folder that cannot be written), the flow is left out and reported as failed (`its time is ahead of this computer's clock and could not be fixed: …`): sending it with a time made up for this sync would win every later sync, since the time would move each time. Rejected: a logical clock or version vector (a new field on both ends and a harder rule to explain for a few machines of one person).
- **Nothing is left out silently**: a flow that cannot go (too large to share, over `share::MAX_BYTES`, which the receiver would refuse anyway; a time ahead that could not be fixed) is a `failed` entry of every machine, with why, so `flow sync` exits 1 and the notice names it.
  - **What cannot be read is a failure too**: a file of `flows/` that cannot be read or parsed (one written by a newer cornercase, a TOML error) is listed by the store as broken and never reaches the plan, so `sync all` reports each one as `failed` under its file name with the store's reason, and still sends the readable flows. A `flows/` folder that cannot be read lists nothing at all, so it is a `failed` entry named by its path (`the folder of your flows could not be read: …`), for `sync all` and for a named flow alike (instead of refusing a name it could not look for). A folder that does not exist yet is not a failure: you have saved no flow of yours. A named sync leaves the broken files out of its answer, since their names cannot be read and they are not what was asked; `flow list` names them.
  - **Two files of yours with one name** (copied or edited by hand; the store does not prevent it) are both left out and reported as one `failed` entry naming the files (`2 files of yours have this name (copy.toml, duo.toml): rename or delete one`), whether all or that name was asked. Sending one of them would pick a copy by file order, not by `changed`, and the receiver keeps one flow per name; carrying each file's own text was rejected for the same reason: two sends of one name in one sync would leave whichever arrived last, which is not "last saved wins".
- **Secrets go too**: a flow is sent whole, `env` values and `args` included, as `flow export` would. The help and the website say so, and **every flow file of yours is written readable only by its owner** (`0600`, `persist::Kind::Private`; the caller says the folder, `store::save_in` with `Folder::Yours` or `Folder::Project`, and `App::folder_of` gives `Project` only to a folder that is exactly an open project's `.cornercase/flows` and not yours, so a mistake fails closed: guessing from the path's last two names wrote the flows of someone whose socket, and so `config.json`, sits in a folder named `.cornercase` with the usual mode) on both ends, whether it sets `env` or not, since an argument can hold a token too; a project's flows keep the usual mode, as they live in a repository. A file written before this with a wider mode is narrowed the next time it is saved (a save writes a new file and renames it); tightening every file on listing was left out, as a listing only reads. Windows has no such mode; the file is in the user's profile (Windows › Files and folders). The mode tests compare a project's flow with an ordinary file written in the same folder, so they hold under any `umask`.
- **No question, and the log never holds the text**: a flow runs its `env` and `args` unattended, so an import from the CLI asks. Here both ends are the same person's machines and the user clicked, so nothing asks. The sending side logs `flow synced` or `flow kept newer there` with the machine and the flow's name, `flow not synced` with why for what the machine refused or could not take, and `flow left out of a sync` with only the name (a flow, a file or the folder) for what never left this computer, once per sync. What was left out never enters a machine's job or its report, which is logged as it arrives, even after a second click dropped its wait; only the answer puts it, with its reason, first in each machine's `failed`. The answer keeps the reason, but a broken file's reason is serde's, which can quote a value of the file (`invalid type: string "API_TOKEN=…"`), and the log never holds tokens; the receiving side logs `flow imported` with sizes as every import does, and `flow replaced by a sync` or `flow added by a sync` with the name and the sender. Agents a synced flow uses that are not installed there get the usual note on that machine's Flows list.
- **The receiving side says so**: a `flow-import` with `synced_from` (this computer's name, `host::name::computer`, read on the job) that replaces a different flow of yours shows a toast, `Duo was replaced by laptop's copy: it synced its flows here`, and a new flow `Duo arrived from laptop's flows: it synced them here`, kept 6 s. The same flow again says nothing. `synced_from` is cleaned before it is shown or logged (hidden characters dropped, one line, at most 64 characters, `machines::flows::sender`), since any client of the socket may send it. The receiving side cannot refuse a sync: the sender already has ssh and the socket there.
- **Over the socket** (contract stays 1): `flow-sync` (`{machine, name}`, both optional, operation 138, `Command::NAMES` has 139) answers once every machine asked has answered, as a `Stage::Reading` pending answer: `{"machines": [{"machine", "sent", "kept", "same", "failed": [{"name", "error"}], "error"}]}`, names in each list, `same` a count, `error` why a machine could not be reached. It is refused as `conflict` when no machine is linked and shown (naming `cornercase machines show NAME` when a hidden one is listed), `not-found` for an unknown or hidden machine, and for a flow name that is none of yours (`conflict` for an unchanged built-in). `cornercase flow sync [FLOW] [--machine NAME] [--json]` exits 1 when a machine has an `error` or any `failed` entry, after printing the answer. Behind the feature `flow-sync`, so `cornercase flow sync` against an older server says what it cannot do instead of sending an unknown request. `flow-list` entries gain `changed` (yours only) and `flow-import` `synced_from`: both additive. A `synced` list per flow was dropped with the automatic sync: without rounds it could only say what one past click found, and a hand edit or a save there would make it wrong without anything noticing. A bot cannot sync flows (`NO_FLOWS`, like the other flow changes).
- **The window**: Settings › Flows' bottom row acts on the selected flow (` edit `, ` duplicate `, ` set default `, ` export `, ` delete `); ` sync ` joins them for a flow of yours, after ` export `, and ` sync all ` sends every flow of yours. Both show only while a machine is linked and shown (read when the tab opens, when its list refreshes and whenever the machines of `config.json` change, so showing or hiding a machine while the tab is open adds or drops them; the click reads the machines again), and they are dropped, after Share, when the row is narrow. The click says `sending Duo to vps…` (or `your flows`), then replaces it with each machine's outcome on one line, the words `flow sync` prints (`vps: sent Duo · 2 already the same`, `vps: kept its newer Duo`, `vps: not synced: <why>`, a refused flow as `Duo not synced: <why>`). It replaces only its own notice: one the user has cleared, by a click, or replaced is left alone, and a second click forgets the first click's wait.
- **Tests**: the plan and the times are unit tests; one sync against a fake machine over socket pairs (sends, a refusal, a newer copy refused while it ran counted as kept, flows left out reported); the app with a linked fake machine: nothing sent on a save, a delete or a link, the request for all and for one, refusals, a newer copy there kept, a machine still connecting answered at once, a flow too large and a time ahead that could not be fixed reported, a file that cannot be read, two files with one name and a folder not made yet (`app::tests::control_requests::flow_sync`, on every system) and a folder that cannot be read (Unix), the receiving side's times, toasts and its refusal of an older copy (the refusal and a newer copy replacing with its toast also in `app::tests::control_requests::flow_sync`, which runs on every system, since `app::tests::machine_links` is Unix-only), Settings › Flows' ` sync all ` and ` sync ` (offered only while a machine is shown, never on a built-in or a project's flow) and their notices; the file modes on Unix; e2e with two real servers, one of which checks that a file that cannot be read is answered with serde's reason and logged by its name only.
- **Rejected**: a flows folder in a git repository or a cloud folder (a remote or a sync tool on every machine, conflicts in git; a symlink already does it for those who want it); syncing the whole `config.json` (machines, ports and accounts differ; sharing settings, #414, moves a setup once); a new request that writes a whole set of flows at once (a machine would need new storage and an older one could not take part); the automatic sync described above.
- **Checked** with the e2e tests' two real servers and the fake `ssh`: nothing reaches the machine until `flow sync`, `flow sync Mine` sends it with its `changed`, a hidden built-in stays shown there, a flow deleted here stays there, and a name that is none of yours is refused. Not checked against a real sshd.
