# Flows › Closing a merged run's agents

Part of [Flows](../flows.md).

- **Why** (#734, `flows/run.rs`, `app/flow_runs/merged.rs`): five merged `classic pro` runs left 35 idle agent processes, and nothing stopped them from piling up. A routine's cleanup (see Queue) only removes what the routine started, so it cannot tell that a workspace someone else started is no longer wanted; a caller that starts a run knows whether it wants to let go of it, so the choice belongs to the run.
- **Per run, opt-in.** `flow run --close-when-merged` (the `close_when_merged` field of `flow-run`, skipped when false) starts the run opted in, and `flow close-when-merged [--off]` (the `flow-close-when-merged` request, operation 124, `Command::NAMES` has 125) sets it on a run already going, from the window, an issue or a routine. It sets the choice and never toggles it, so it is idempotent and answers `changed`, like `flow default`. `Run::close_when_merged` is saved as the optional `RunState::close_when_merged`, so a restart keeps it and `VERSION` stays 5; it also survives a manual close agents and the reopen.
- **What it waits for**, every step on the 1 s sync step (`App::close_merged_runs`), for 3 minutes without a break (`MERGED_GRACE`, `Run::close_due`, whose `merged_since` goes back to `None` on any step that is not ready):
  - the run's flow ends on the pull request and `App::pull_request` of its workspace is merged (`Run::merged`; a GitLab merge request counts);
  - `App::agents_close_plan` succeeds, **no agent is working or waiting** (`cut`), **no pane that is not an agent would be stopped** (`others`: a shell opened in the team's tabs keeps them open, since stopping it can lose work), no launch is in flight on an agent pane, nobody is at the keyboard of one (a draft in its input, keys typed lately, a send going out or held: `App::person_holds`, the rule of a held send) and none has a turn that is not over or a prompt it has not reacted to yet (`App::holds_restart`, the rule of an idle restart), since a draft would be lost with the tab and a turn just started would be cut; typing restarts the 3 minutes;
  - every agent in the plan that cannot resume is a member of the run: an agent you opened yourself in the run's worktree (opencode, a custom kind) blocks the close, as a shell does, since the opt-in is the consent for the team only;
  - no wake of the orchestrator is due or running (`run.due()`, `Runs::waking`), or the close would cut a hand-over between two members;
  - no routine's cleanup is counting down or running for the workspace (`App::cleaning_up`): that removal goes first, since closing the agents first would end the run, `flow_finished` would never be true again and the routine would keep the workspace for good.
- **The 3 minutes** are a routine's cleanup grace. They cover the gap between a member finishing and the orchestrator's wake, and leave time for a follow-up. The memory an idle agent holds is the same after 3 minutes or 3 hours, so a longer grace would only cost.
- **Agents that cannot resume their conversation close anyway** (`Plan::fresh`: opencode, a custom kind, a role that never had a turn) and start over on reopen. The opt-in is the consent, as `--force` is for `agents close`; the run's folder keeps every role's answers as files, so what is lost is an agent's context, not the run's record. A turn is never cut and a non-agent pane never stopped: those states wait.
- **It closes as `agents close` does** (`App::close_agents`, unchanged): the tabs go, the run is kept whole under its id (`flow runs` lists it with `state: "closed"`) and the workspace's ▶ or `agents reopen` brings the agents back. **The automatic close turns the opt-in off on the kept run**, so a reopen keeps the agents open instead of closing them again 3 minutes after they go idle; a manual close keeps it, and `Runs::take_of` drops the countdown, so a reopened run starts a new one; a reopen after the pull request merged (`reseat_run`) turns it off too, since whoever reopens the team wants it, and closing it again 3 minutes after it goes idle would fight them. The window shows a toast with ` reopen ` (`pull request merged in fix-login: 5 agents closed · ▶ on the workspace reopens them`, cut at its end before the button when the window is narrow: `ui::draw_toast` draws the message only in the room left of it); `server.log` has one info line (`agents closed after the merge`), never a task or prompt text. There is no desktop, Telegram or Discord notice: closing is quiet, as for `agents close`.
- **The countdown is in memory.** A restart starts it over, which also lets go of runs that merged while the server was down.
- **Nothing is removed**: not the workspace, its worktree, the role worktrees, the branches or the run's folder, so the rule about uncommitted or unpushed work can never be broken by this. Removal stays with `close --workspace --remove-worktree --check` and a routine's `--cleanup`.
- **Exposure.** `close_when_merged` (skipped when false, so the v1 fixtures keep their bytes) is in each run of `flow-runs` (live and kept), in the `run` object of `status`, `watch` and `view` (part of the `refreshed()` fingerprint, so a flip sends a snapshot) and in the answer of `flow-run`. The feature `flow-close-when-merged` is in `contract`: an older server would drop the field and start a run that never lets go, so `flow run --close-when-merged` checks it before sending; the operation is refused by name by an older server. `close_when_merged: false` is dropped before the strict-fields comparison (`left_out`, for `flow-run` only). A `flow-run` relayed with `--machine` is closed by the machine's own server; the relay is strict once the machine has reported, and before its first snapshot it sends no `boot`, so an older machine there would drop the field; the answer then lacks `close_when_merged: true`, which the docs tell a caller to look for. A gate was not added: the relay cannot know the machine's features before its first snapshot, so the only gate would be refusing every such run.
- **Known costs.** A run started on a branch whose pull request had already merged counts it, as the end does (the 3 minutes with nothing at work make a close mid-run unlikely, and a reopen undoes it); a workspace checked out on another branch whose pull request merged counts that one, as the end's tag does; it needs `pull_requests` on and `gh` or `glab` signed in.
- **Checked live**: not against a real merge on GitHub or GitLab; the pull request is a fake `gh` answering `MERGED`, in the app tests that drive `close_merged_runs` with explicit instants.
- **Rejected**:
  - A global setting: it would close runs people started by hand to watch, and the Flows tab of Settings has no rows to put it in.
  - A key in the flow's TOML: a file format, `FlowSpec` contract, editor and simulation change for a choice that belongs to how a run is started.
  - Copying the pull request into the `flow-runs` feed: `status` already has it per workspace, and the feed's snapshots carry every prompt, so each check flip would resend them.
  - Removing the worktree.
  - Waiting forever on agents that cannot resume: an opencode role would never let go.
  - A `closes_at` time in the JSON and a window toggle (start dialog or row menu): left for later.
