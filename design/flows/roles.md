# Flows › Roles and their agents

Part of [Flows](../flows.md).

- **Several roles on one agent**: roles work in the run's one worktree unless one asks for a worktree of its own (below), and cornercase finds some agents' records by their folder rather than their pid: Codex when its app-server daemon writes the rollouts, Gemini CLI by its home and folder, opencode by its database (Context use). Two of one kind in one worktree hide each other's records. Each agent folder states both sides (`Known::record_by_folder`: Codex, Gemini CLI, opencode; `Known::status_by_folder`: opencode alone). Codex and Gemini CLI still take several roles: their status and waits come from their titles, so only `read --last-message` fails for them, and the brief tells the orchestrator to read such a member's screen instead (`read --lines 300`): an LLM reads a screen well enough, where a parser of cornercase's would not. Their `send --enter` cannot be confirmed from a hidden record either, so it returns once Enter is pressed when the agent finds its record by folder, has none, and another pane of this server runs the same agent in the same folder; a lone fresh Codex keeps the confirmation. opencode's status itself comes from its database, so its waits would fail: `Flow::problems` refuses it in several roles of one worktree, and the built-ins move a repeated opencode to another installed agent; roles with a worktree of their own do not count (opencode can take one per worktree). A per-role home (`CODEX_HOME`, `GEMINI_CLI_HOME`, `OPENCODE_DB`) would lift all of it and is left for later, since Codex and Gemini keep their login there. A worktree per role for every flow was rejected: members would stop seeing each other's uncommitted work, and each worktree builds from scratch. It is a choice per role instead (#313, below).
- **Cursor CLI in flows** (#290): it can take several roles, since its record is found by the store its own process holds open and its status by title and transcript, neither of which another Cursor in the folder hides (if a live check shows the store is not held, `RECORD_BY_FOLDER` becomes true and `known/tests.rs` and this paragraph change with it). Its unattended arguments are `--force --trust`, it has no effort switch (effort is part of the model id) and no model list (`--list-models` needs the network).
- **Vibe CLI in flows**: it takes several roles in one worktree, since its record and context line are found by the pid lease its own process holds, which another Vibe in the folder does not hide (its status is its own OSC 7501 report, so it is never hidden either). Its unattended arguments are `--agent auto-approve`: `--auto-approve`/`--yolo` are ignored when an admin forbids the auto-approve agent, while the agent name fails loudly instead of waiting on approvals. `--add-dir` gives it the run's folder. It has no model flag, so a role that sets a model is refused rather than given an argument Vibe would reject, and no effort switch (thinking is `/thinking`).
- **GitHub Copilot CLI in flows** (#330): it takes several roles in one worktree, since its record and status are found by the session its own process holds, which another Copilot in the folder does not hide. Its unattended arguments are `--allow-all --no-ask-user`: `--allow-all` is `--allow-all-tools --allow-all-paths --allow-all-urls`, and `--no-ask-user` keeps it from waiting on its own question tool, since a team that stops to ask defeats the point. **Autopilot is never used**: it keeps sending itself continuation messages after the answer (`isAutopilotContinuation`), which a role waiting for the orchestrator must not do. `--add-dir` gives it the run's folder (the folder has no `.github/skills` or `.github/agents`, which `--add-dir` would also load as trusted config), and effort is `--reasoning-effort` like Claude Code's and Codex's. The trust question is answered by the run's launches like any agent's.
- **Effort per role** (added at the user's request, as pstack does per role): `Role::effort`, a pick of the agent's own levels in the editor, and `start --effort`. Each agent folder states its switch (`EFFORT`, `Known::effort`): Claude Code `--effort` (low to max), Codex the config key `-c model_reasoning_effort=` (minimal to xhigh), Grok Build `--reasoning-effort` (none to max, from its README; its per-model ids such as `deep` are not offered); Gemini CLI and opencode have none, and an effort set on them is a problem. Like the model, a role's effort replaces every spelling of one in `agent_args` (other `-c` settings stay), so no flag is given twice; without one, the role's own `args` beat the settings'. The diagram's boxes and the brief show it (`claude · opus · high`).
