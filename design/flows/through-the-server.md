# Flows › Through the server

Part of [Flows](../flows.md).

- **Through the server** (#342, `control/flow.rs`, `app/control/flow.rs`, `app/control/flow/`, `cli/flow.rs`): flows had a list, a run and sharing over the socket, but an external UI could not draw the editor's data (the list gave names, agents and problems, not stages, loops or prompts), save a draft, delete, hide or restore, nor follow a run. The additions are new operation names (an older server refuses them by name, as it did `usage`) and new keys of answers a client sees are missing, so `CONTRACT` stays 1 and no feature string was added (`Command::NAMES` has 78: the seven of #342 are indices 71 to 77, after the plugin requests of #343). `flow-save` also refuses, as `malformed`, a flow whose file would pass `share::MAX_BYTES`, so what a client saves can always be exported and imported; and the `flow messages` command prints a `dropped` frame as a count and not as a message.
  - **The flow as JSON is a contract type, not `Flow`'s serde** (`FlowSpec`, `RoleSpec`, `StageSpec`, `BackSpec`): `Flow` serializes as the TOML file (singular `role` and `stage` keys, a `version`, and fields skipped when empty), and a change to the file would have changed the contract by accident, as `Layout` is for `Node`. Every key is always written (`null`, `[]` or `{}` when empty), since `flow-save` carries the same type and the strict-fields check serializes the parsed request: a `skip_serializing_if` would make a default look like an unknown key. `version` is left out (it is the file's, `Flow::file_version` decides it), and the orchestrator's name is forced to `orchestrator`, as `store::parse` does. `back.to` stays a stage number counted from 1, as in the file and the editor (`stage 1`), so what a client reads in `flow list` is what it writes in `flow-save`; the run's feed counts stages from 0 (see Following a run). A test turns every built-in and a flow using every field into JSON and back.
  - **The list grew by additions**: each flow carries `flow` and `edited` (your version of a built-in, which offers restore), and the answer has `hidden` (the deleted built-ins, with their flow) and `builtins` (every built-in name, reserved even while hidden, so a client makes names unique as the dialog's `unique` does). There is no `flow-get`: the list already has every flow whole. `flow-run` answers `run`, the run's id, which the run feed names.
  - **`flow-save`** (`app/control/flow/manage.rs`) validates the draft with `Flow::problems`, as the editor does, plus the conflict it would have once saved (another flow of that name that runs instead, a deleted built-in's name), escaped for display. With `check` it answers those and writes nothing; without it, it is refused as `malformed` while the flow has problems of its own (the value-check rule of #336), and conflicts alone do not refuse, since the dialog saves those too and the list shows them in red. `place` is `yours` or `project`; `check` also says what a project's flow runs unattended (`env`, `args`), as the dialog's red line. **`path` is the file being edited, and the only way from the socket to a deletion**: `store::save` deletes `previous` when the name or the place changes, so a path that is not the path of a listed flow is `not-found`, never joined or trusted. Moving between places is allowed, as in the dialog. The last write wins over an editor open on the same flow, as with a hand edit.
  - **Delete, hide and restore mean one thing each**: the dialog's delete button deletes a file and, on a built-in, hides it, which a script cannot tell from what it asked for, so `flow-delete` only deletes files (yours or the project's, by name with an `in` place, or by a listed or unreadable file's `path`) and refuses a built-in and your version of one with the command that does what was meant (`conflict`), and a hidden built-in as already deleted (`not-found`); an ambiguous name asks for its place. `flow-hide` hides a built-in (and deletes your version of it, as the button does), `flow-restore` unhides it and deletes your version (the dialog's restore default and restore), both idempotent (`changed: false`, the #336 rule) and `not-found` for a name that is not built in. All of them go through the dialog's own methods (`save_flow_file`, `delete_flow_file`, `hide_builtin`, `unhide_builtin`), which also refresh an open Flows dialog, and `hide_builtin` writes `config.json` through `write_config`, so the revision goes up. A run already going keeps its flow. Asking before delete, hide or restore was left out: commands for scripts act, as `close` and `group delete` do, and hiding is undone by restore.
  - **Following a run** (`flow-runs`, `app/control/flow/feed.rs`): the run's state is its own feed, like `app` (#338), and not part of `watch`: the task and every prompt of the flow would ride each session snapshot, about twice a second while agents work. `FlowRuns` is a whole snapshot with a `revision` (`Snapshots<FlowRuns>`, so the pacing, the held latest for slow readers and the forgetting are the session feed's and `app`'s; `Snapshots::ready` is the one paced gate that `publish_app` and `publish_flow_runs` share), built at most every 500 ms and only while someone follows, sent only when it differs, and nothing marks a change: it is cheap (memory only, no process lookups) and rebuilt after every traced step. Each run carries `run` (its id; a restore gives a new one), the plan it was briefed with (`Run::flow`, frozen), the task, the folder, every role (the orchestrator first; `pane`, `tab`, `status` from the pane's agent, `closed` once the pane is gone, `awaited` (#443: `working` while it holds work the orchestrator sent it, `finished` until the orchestrator is told, omitted otherwise, so the v1 fixture is unchanged), a member missing after a partial restore all `null`; `worktree` and `branch` of an own role from the workspace's `role_worktrees`), `stage` (an index from 0, `Progress::active`), `rounds` (one per stage), `holder`, `last` (a step: the edge, `from` the previous holder, `to`, UTC `time`), `outside` (the last step outside the plan, as the diagram draws it), `ended` (the orchestrator's pane is `pending`, as `Diagram::live` decides it) and `messages` (how many were recorded). Edges are `{"kind": "forward"|"loop"|"outside", …}`. Stages count from 0 here and `back.to` from 1, which the docs say.
  - **Following messages** (`flow-messages`): a stream of its own on its connection, not `events --flows`: `events` has no backlog, and a window opened mid-run needs what was sent before it connected (the panel's arrows). The answer is every kept message (at most 256, oldest first) and the follower is registered in the same step, so there is no gap, as `surface` gives its first frame; each later message is one `Streamed::Event` line, in order. An event rather than a replaceable snapshot, since messages must not be dropped for the latest; the bound is the server's `EVENTS_QUEUED` and its `{"event": "dropped"}` line, and a client that falls behind reconnects to read what is kept. The stream ends with `Detached` when its run does (`forget_runs`), a second one on a connection is `conflict`, a workspace with no run `conflict` and an unknown one `not-found`. Texts stay in memory and out of the log (debug lines carry the run, the sequence number and the size).
  - **Files** (`flow-files`): a job answered when it ends (`Stage::Reading`, like `read --last-message`), chatty in the log because a client may poll it as the panel does every 2 s. The folder is the one `status` gives as `run_dir` (`App::workspace_run_dir`: the run's, else the workspace's last), so a run that ended is covered, which the panel cannot show. No folder is `conflict`, a folder that cannot be read `failed` with its path. The names are the panel's (relative, newest first, at most 200, `more`). Reading a file's text over the socket was left out, as for the files panel.
  - **The CLI**: `flow runs [--follow]`, `flow messages [--workspace|--worktree] [--follow]`, `flow files` and the manage commands (`flow delete|hide|restore`), `--json` giving the request's own answer (one message per line for `messages`, the backlog expanded). Text is a sketch pinned by `cli/flow/tests.rs`: stages count from 1 for people. There is no `flow save` command: people edit in Settings or the TOML file and `flow import --replace` saves one from a file, and the request is for programs holding a draft in their own editor, as `update-check` has no CLI.
  - **Logging**: requests log names, ids, flags and sizes; never a prompt, env value, task or message text (`Command::fields`, a test pins it).
  - **Rejected or left out**: run state in `watch`, `status` or `view` (it would ride every session snapshot; `status` keeps `run_dir`); messages as `events` lines; a `flow-get` request (the list has every flow whole, the deleted ones included, and `flow-runs` each run's frozen plan); `flow delete` hiding built-ins as the dialog's button does (one verb, one meaning for scripts); asking before delete, hide or restore; reading a run file's text; the editor's choices (installed agents, model lists, effort levels: `flow-save` with `check` refuses invalid ones); patches for `flow-runs` and a run filter; starting a flow from an unsaved JSON draft; and message history beyond the 256 kept.
  - **Closed runs in the feed** (#430): a run whose agents are closed (see Saved session) is listed with `state: "closed"` (omitted for a running one, so the v1 fixture is unchanged), every role with `pane`, `tab` and `status` null and `closed: true`, and `ended` read from the saved orchestrator pane's mark. Message streams (`flow-messages`) end as for an ended run, since the run is out of the live ones; after a reopen it has the same `run` id.
