# Flows › Recording, progress, the diagram and the Flow panel

Part of [Flows](../flows.md).

- **Recording** (`app/flow_panel.rs`, hooked in `app/control.rs`): from the requests, not from what agents say: a request whose caller pane (with the server's token) and target pane belong to the same run becomes a message with role names: `send` with its text, `keys`, `read` and `wait` (one per target) when accepted, `read --last-message` with the message when its answer comes, kept for its own run (`Run::id`) so a late answer never reaches the next run in that workspace. So a new way to send work cannot be forgotten. Texts stay in memory, cut at 32 KiB, never logged (the log keeps sizes) nor saved. What roles hand over lives in the run's folder (below), where it outlives the run. Since #342 each recorded message also gets a number (`Message::seq`, counted per run by `Run::record`, which goes on past the 256 kept), a wall time (`Message::time`, next to the `Instant` the panel's travelling dot uses) and the edge it moved the work along (`Message::edge`, what `Progress::step` now returns), so external clients rebuild the panel's arrows from the history; they follow the messages with `flow-messages` (see Through the server).
- **Where a run stands** (`flows/progress.rs`, pure): only the orchestrator's `send`s into a role of a stage move the work: except a compact command to that role's agent (#444: compacting the coder while the reviewer's stage is active would count a loop round and then a step outside the plan; the message is still recorded and shown), a member writing to another is recorded but moves nothing. Into the next stage is its arrow; into the stage the active stage's loop returns to, a round of that loop; anywhere else, a step outside the plan (the last one is drawn dashed on the left). A send to another role of the active stage travels that stage's arrow again (each parallel branch lights), a follow-up to the same role moves nothing. Rounds past `at_most` still count and turn the label orange: the orchestrator decides, the diagram shows it. The last message is kept per arrow and target role, so each branch of an arrow into a parallel stage opens the message its own role got (before, the reviewer's branch opened the one sent to security).
- **The diagram** (`ui/flow.rs`, `ui/flow/`): one renderer for the editor's preview, the start dialog and the panel (`Diagram::plan`, overlaid for a run with `Diagram::live`). Vertical, to fit a side panel: the orchestrator on top, apart and without arrows (it moves the work, it is not a step; arrows to every stage were noise); stages top to bottom; parallel roles side by side, or stacked under a bracket when a box would get under 14 columns, since names are what the diagram is for; one lane per loop on the right with its label (`findings · at most 3`, live `findings · 1/3`); the end as `◆ open a pull request`. Every line cell carries its connections and its arrows, so glyphs come from the bits and a click anywhere on an arrow knows it (strings per case were the first idea). Roles take the group presets' colours without red (failed) and orange (waiting, and a loop past its limit). Live: a working role's box gets a heavy border in its colour, the arrow the work last took the colour of the role it left, a `●` travels along it for a second (the only time frames are asked for), and `◆` turns the brand blue once the run reaches its end (see The end). The diagram itself shows no times (the panel's messages and files do). Widths are display widths with saturating sums, so a wide name is cut inside its box and a huge loop label falls back to its short form.
- **The Flow panel**: `Side::Flow`, the fourth panel of the changes column, shown only while the active workspace has a run, so another workspace gets its width back. Opened by **show flow** in a run workspace's menu, `w f`, the icon bar's Flow slot, and when a run starts from the window. A click on a box goes to its pane; on an arrow or a loop's label that carried a message (only those light up), **Message** (`orchestrator → security · sent`, the text, ` copy `), which closes when its run goes.
  - **Heading, team and messages** (#574): the panel is a column of sections built from one `View` (`App::flow_view` in `app/flow_panel/view.rs`; `ui/flow/heading.rs`, `team.rs`, `history.rs`, `files.rs`, laid out by `stack.rs`'s `Slot`, one rule for where a section's rows land when scrolled, so drawing and hit testing cannot drift). The first two rows stay fixed (name and state with `×`, the task's first line); everything else scrolls as one content, since fixing the whole heading would eat 4 to 6 rows of a 20-row terminal. The state is `running` or `reached its end`, from `Run::reached`, the rule of the diagram's `◆`, so the heading never disagrees with it; "agents closed" can never show, because a run with closed agents leaves `App::runs` and the panel hides (#430). The summary reads `stage N of M` (`not started` before the first step) followed by every loop that took a round (`findings 1/3`, orange past its limit), as cornercase-gpui's does, so the loop's count stays visible after the work went back to the coder. The stage bar has one segment per stage, lit up to the active one, all of them once the run reached its end. ` stop ` is **close agent** on the orchestrator (the first member whose pane still exists when the orchestrator's is gone), the same confirmation as the agents section (#399, #438), but built from the run's members without asking for an agent status, so a run can be stopped while setup still holds the agents back (`CloseAgent.stop`); the branch in the heading is read by a background job every 2 s while the panel shows and kept for drawing (a draw never touches the disk), listing the team that stops with it; the reopenable close of #430 was rejected, since "stop" means the run ends. The team lists the orchestrator and then the roles, with the branch of a role's own worktree dropped first in a narrow panel and a closed member dimmed and not clickable. Messages come newest first and show at most two preview rows of a bounded head (1 KiB) of each text, never the whole 32 KiB of 256 messages per frame; the step goes on its own row when it does not fit beside the names. A message opens the existing **Message** dialog through `Shown::Number(seq)` (the arrows use `Shown::Along`), and the dialog closes when its message rolls out of the 256 kept. Known cost: while you are scrolled into the list, a new message pushes the older ones down (no scroll anchoring). Nothing here needs a new request: `status`/`watch` give `run: {end, reached}`, `flow-runs` the place, number, stage, rounds, team (pane, tab, status, worktree, branch) and message count, `flow-messages` the messages, `flow-files` the files and sizes, `close-agent` is ` stop `, `focus --pane` is ` orchestrator `, and ` open folder ` is the window's open-in menu, exempt as in Opening in other apps.
