# Flows › Personas

Part of [Flows](../flows.md). Code: `machines/flows/personas.rs`, `ui/icons/lucide.rs`, `flows/persona.rs`, `flows/persona/source.rs`, `flows/persona/draft.rs`, `flows/persona/catalogue.rs`, `flows/dialog/personas.rs`, `flows/dialog/personas/`, `app/flows_dialog/personas.rs`, `control/persona.rs`, `app/control/persona.rs`, `cli/persona.rs`, `cli/persona/catalogue.rs`, `cli/args/persona.rs`, `cli/help/persona.rs`, #884 (steps 1 and 2 of its plan, and #939 for step 3), #944.

- **Why**: a role had a CLI, a model, an effort and a free prompt, so how a reviewer reviews lived in each flow's prompt, written again for every flow. Collections of agent definitions exist ([msitarzewski/agency-agents](https://github.com/msitarzewski/agency-agents), MIT, some 280 of them: Markdown with a YAML front matter of `name`, `description`, `color`, `emoji`, `vibe`, grouped in folders listed in `divisions.json`). A **persona** is one of them, imported once and named by any role (`persona = "engineering-code-reviewer"`), on any agent: the same Code Reviewer runs on Claude Code or Codex.
- **The word**: "agent" already means the CLI in cornercase (Claude Code, Codex…, `Role::agent`), and "profile" means an account's login (Accounts and profiles). "Persona" says what it is, how an agent behaves, and collides with nothing in the code, the docs or the window. Rejected: "agent" (every `agent` field and the agents section would become ambiguous), "profile" (taken), "skill" (Claude Code's skills are something else that an agent loads by itself).
- **The library** (`persona::list`, `save`, `remove`): `personas/` beside `config.json`, one `<id>.md` per persona, like `flows/` (`paths::personas`, so it follows `CORNERCASE_SOCKET` as `flows/` does). Beside the config, not in the state folder, since a persona is something the user chose and keeps, like a flow, and not something the server makes. No project folder (`.cornercase/personas/`) yet: a project's flows already run its prompts unattended only after a red line, and a persona that comes with a cloned repository would be one more such text; left for when someone asks. **The file is kept as it came**, front matter and body, so it reads like the original and diffs against it; cornercase adds one key, `source:` (the repository path, the address or the absolute file it came from, quoted), replacing any `source:` it had, a block's indented lines included, so that importing that source again with `--replace` refreshes it. **The id** is the file's name slugged (`engineering-code-reviewer.md` → `engineering-code-reviewer`), else the name's, else `persona`: lower-case ASCII letters, digits and `-`, at most 64 bytes, and never a Windows device name (`con`, `prn`, `aux`, `nul`, `com0`–`com9`, `lpt0`–`lpt9`, on every system, since a library moves between machines; the import then takes the next candidate) (`valid_id`), so it is a safe file name on every system and a plain TOML string. A file in the folder whose stem is not an id is ignored; one that cannot be read is listed with its reason (`broken`), as for flows, and so is the folder itself when it exists but cannot be read, rather than listing an empty library. **A persona a flow can follow** is one the library reads (`persona_ids` lists `persona::list`'s, not the file names), so a flow naming an unreadable file is refused when listed, saved or imported, not when its run starts.
- **The front matter is read by hand** (`persona::front`, `field`): `key: value` lines between two `---` lines, values with or without quotes, and folded or literal blocks (`>`, `|`) joined into one line. No YAML crate for five keys of display text; a front matter that YAML would read differently only shows a different description. A persona is a file whose front matter gives a non-empty `name` (`is_persona`); its name, description, emoji and colour must hold no control character, since clients print them. The body is never parsed: it is the agent's to read. 256 KiB at most (as a flow), and a file of the library is read only that far.
- **Names** (`app/control/persona.rs`, `collisions`): a persona whose id you have is refused unless `--replace`, which overwrites that file; a file of that id that cannot be read, or any entry the disk finds at `<id>.md` (`persona::taken`, a lookup on the disk, so `Reviewer.md` on a case-insensitive disk), counts as one you have, so it is never overwritten without `--replace`; one whose name (trimmed, ignoring case, `store::same_name`) is another id's is refused even with `--replace`, naming that id, since replacing would leave two files of one name or remove a file a flow names. The id is what flows name, so it is what `--replace` matches. **An import is all or nothing**: one persona that cannot be read, two that would take one id or one name, or one collision refuses the whole import with every reason, so a repository is never half imported; and a save that fails halfway (`persona::save_all`) removes the files it created and writes back the bytes of those it replaced before answering the error, naming any it could not put back; a file it would replace but cannot read, or too large to keep a copy of, refuses the import before anything is written, and `--check` already says so (`persona::keepable`). `--name` (as `flow import` has) is left out: the file's name is the id, and a persona under two ids would only confuse the picker of step 2.
- **Importing** (`persona/source.rs`): the CLI resolves the source and reads it, the server checks and saves, as for flows (Community flows › The CLI downloads, the server does not), so no request makes the server fetch anything; the window's import fetches on a job of its own, as the Flows dialog's flow import does (see The window). Sources: `-`, an `https://` address (`http://` refused), an existing file or folder (which beats the next), then `OWNER/REPO[/PATH]`. A path ending in `.md` is one file from `raw.githubusercontent.com/<repo>/HEAD/<path>`; anything else in a repository (the root or a folder) is **one download of the repository's tarball** from `codeload.github.com/<repo>/tar.gz/HEAD` (at most 64 MiB, 120 s, `tar` and `flate2` already in the tree for plugins), read in memory, only its `.md` files and `divisions.json`. Rejected: the GitHub API's contents or trees (60 requests an hour without a token, and one request per file: agency-agents would take some 280), a `git clone` (needs git and a temporary folder, and fetches history), and `gh` (not required anywhere else for an import). `CORNERCASE_PERSONAS_URL` and `CORNERCASE_PERSONAS_ARCHIVE_URL` replace the two hosts; tests give the hosts directly (`Hosts`) with `FakeHttp`. Downloads go through `http::download_strictly` (three redirects, never from `https://` to `http://`, no token sent).
  - **A folder or a repository imports every persona in it**: every `.md` file (folders up to 8 deep, those starting with `.` skipped, the same in a folder and in a repository's archive, 20,000 entries at most) whose front matter gives a `name`; the rest is counted (`skipped N files that are not personas` on stderr) and left, and dropped as it is read, so only personas are held in memory, 64 MiB of them at most. **`divisions.json`**: when the folder or repository being imported holds one at its root with a `divisions` object, only the folders it names are read. agency-agents keeps per-tool converted copies under `integrations/`, one of them with a front matter, and its own `divisions.json` says those folders are not agents; a generic "every file with a name" would import that copy too. The rule is that repository's, but cheap and harmless elsewhere. At most 500 personas per import (agency-agents has 283 once `integrations/` is left out); more asks for a folder of it.
- **The risk check**: a persona is prompt text that an agent running without permission prompts reads and follows, so it is a flow's prompt by another name. Every answer of `persona-import` carries `check` (the sentence that says so), `--check` sends the request with `check: true` (validation, ids and collisions run, nothing is saved) and prints each persona's id, emoji, name, size and description, and whether it replaces yours. From an address or a repository the import always asks `[y/N]` after that preview (on stderr, so `--json` keeps stdout to its answer, the preview with `saved: false` when the answer is no), with where it came from, that nobody reviewed it and the page to read it at (`https://github.com/<repo>/tree/HEAD/<path>`); without a terminal on stdin and stderr (a redirected stderr would hide the question) it refuses unless `--yes`, as `flow import` does. A file or folder of yours does not ask. The whole text is not printed: hundreds of KiB of prompts on a terminal is not a review, the page and the files are.
- **The role field**: `Role::persona: Option<String>`, skipped when unset, so every flow file and every answer without one keeps its bytes, and the flow's `version` stays 1: an older cornercase reading a flow with a persona runs the role without it, which loses how it works but not what it may do (unlike a worktree of its own, which needed `version = 2`). `Flow::problems` refuses a persona that is not an id (pure, so the editor and the dialogs see it); **a persona not in the library** is `Flow::persona_problems(known)`, added where the server knows the library: `flow-list`'s problems, `flow-save` (so it is not saved), `flow-import` (import the personas first), and `run_refusal` (so `flow run`, the start dialog, an issue and a routine refuse to start). The Flows dialog's editor lists it with the flow's other problems, and its persona row is red, and the start dialog's list shows it in red on the flow (only for this computer's flows: a machine's are checked there), both from the library the dialog read when it opened. Any role may have one, the orchestrator too: its brief has a `## Persona` section saying the plan and the rules come first.
- **Delivery through the run's folder, the same for every CLI** (`brief::member`, `brief::own_persona`, `folder::persona`): at the start of a run each persona a role names is read from the library and written to `<run>/personas/<id>.md`, created new and never written through a link, before any shell spawns, like `task.md`. A member's prompt adds, after whether it may edit: read the persona `<path>` before the first work it is sent and follow it in how it works, read it again after a compaction, and the role and the orchestrator's messages come first where they differ. "Before the first work it is sent", not "now": the prompt's last sentence stays "Wait for the orchestrator's first message before doing anything." (The brief, the team and the session). The orchestrator's team list says which persona each role follows. Why the folder first: every agent reads files, so one mechanism works for the eight CLIs and needs no live check per CLI; the prompt stays short (a persona is 5 to 25 KiB, typed into every agent's input otherwise, the cost that kept the task out of the prompts in #778). Its cost is that the persona is something the agent read, not a system prompt, so a long run or a compaction can weaken it; step 4 gives the CLIs that have a switch for it (a system prompt that survives compaction, such as Claude Code's) a native delivery, checked live per CLI. Rejected: the persona inside the role prompt (above), and `--append-system-prompt`-style flags now (different per CLI, absent in some).
- **A copy per run** (`Run::personas`, `RunState::personas`): the run keeps the text of each persona it started with, by id, as it keeps its flow and its task, saved in `session.json` (optional, so `VERSION` stays 5 and the fixtures are unchanged). Editing, replacing or removing a persona later never changes a running team, and a restore or a reopen writes a missing copy again from it (`folder::ensure_personas`, never overwriting, logged, refusing a saved key that is not a persona id before writing any), since the prompts promise the file. Reading the library again on a restore was rejected: the team would change under a run that already started, or lose a file it was told to read. A failed start removes the copies with the task and the empty folder (`folder::discard`).
- **For clients** (`flow-personas` in `contract`, additive, `CONTRACT` stays 1; steps 1 and 2 ship in one release, so one feature covers both): `persona-save` (`id`, `text`, `replace`: the whole file, checked and saved exactly as a one-persona `persona-import` whose file is `<id>.md`, so the same validation and collisions; an empty `id` takes the name's; it answers `persona`) and `persona-show` (`id`: `persona` and the whole `text`), which `persona new|edit|show` use; `persona_name` and `persona_emoji` on the roles of `flow-list` when the library has the persona, so `flow list` prints `reviewer: claude · sonnet · 👁️ Code Reviewer` without a second request, and the id alone when it does not; `persona-list` (`dir`, `personas` with `id`, `name`, `description`, `emoji`, `color`, `source`, `bytes`, `path`, and `broken`), `persona-import` (`personas`: `file`, `text`, `source`; `replace`; `check`; it answers `personas`, `check` and `saved`) and `persona-remove` (`id`), request names of their own so an older server refuses them by name; `persona` on the roles of `flow-list`, `flow-runs`' flows and every `RoleSpec` and `RoleInfo`, skipped when unset; a strict client that sends `"persona": null` on a role or the orchestrator, or `"source": null` on a persona of an import, is not refused for a field the answer leaves out (`contract::unknown_fields`, `skipped_when_null`); a null key anywhere else still is. `flow save` and `flow import` check the feature when a role has a persona, since an older server would drop the field in silence. The log has `personas imported` with the count and bytes and `persona removed` with the id, never a text (`PersonaImport::fields` logs `count` and `text_bytes`).
- **The window** (step 2, #884; the user tried step 1 and found nothing of it in the window: "import agents from repositories, and also save my own so I can reuse them"). **A Personas page inside the Flows dialog**, behind a ` personas ` button on the flows list, not a tab: in Settings the dialog's top row is already Settings' own tabs, and the dialog opened from the start dialog has none, so a page reached the same way from both (as the import page and the editor are) was the one place that fits both; a section of the flows list was rejected because ` new ` and ` import ` would then mean two things on one row of buttons. The page reuses the dialog's drawing (rows, the one-line field, the multi-line text, the note beside, buttons, warnings), so it added no drawing code but a preview box titled `Persona`. The button is the last one a narrow row drops.
  - **The library**: one row per persona (emoji and name, description, `yours` or the source's repository), the files it cannot read in red with their reason, and beside the list what the selected one is, its id, size, source and **the flows that follow it**. ` edit `, ` remove `, ` import `, ` new `, ` done ` (back to the flows).
  - **New and edit** (`personas/form.rs`, `persona/draft.rs`): rows for the name, description and emoji (one-line, as the flow editor's rows) and the instructions, the multi-line `Editor` of the other prompts. Saving writes the front matter from the fields (`draft::compose`) and goes through `persona-save`'s own path (`App::save_persona`), so the window and a client are refused the same way. **An edit keeps the id** (flows name it) and the front matter's other keys (`color`, `vibe`), **and drops `source:`**: an edited persona is yours, and the list stops naming a source it no longer matches. It keeps its id, so importing that source again with `--replace` still replaces it, edit and all; `--replace` matches the id, not the source. Leaving a changed form asks first, as the flow editor does.
  - **Remove asks first and names the flows that follow the persona**, which then cannot start until another one is picked or it is imported again; running flows keep their copy. The ids come from the flows the dialog lists (`personas::followers`).
  - **Import** (`personas/catalogue.rs`): one line for the source, the same sources as `persona import` but `-`. ` import ` fetches on a job (`AppEvent::PersonasFetched`, the hint naming the source), as the Flows dialog fetches a flow: the CLI's way (a process that downloads) would need a terminal for its `[y/N]` and a way back into the dialog, while a job gives the dialog the same answer the CLI gets, through the same `source::gather`. The answer is **a catalogue grouped by division**: the top folder of each persona, with the `label` of `divisions.json` (its icon and colour below), a row per division that checks or unchecks all of it, and per persona its emoji, name, description, size and `replaces yours`; one whose name another id of yours has, or that is not a persona, is red with why and cannot be imported. Nothing is checked at first. The risk sentence and, from the web, where it came from and that nobody reviewed it, stay in red under the list, and ` import selected ` asks again with them before saving the checked ones **all or nothing** through `import_personas`, with `--replace` only when one of them replaces yours (that row said so). An answer for a source no longer being fetched is dropped. `App`'s flow runs hold the hosts (`Hosts::from_env`), so app tests point them at `FakeHttp`.
  - **The filter** (#944; the GPUI already had one): a one-line field (`editor::Editor`) above the list, drawn with Settings' search field in the dialog's blank row under the heading (`ui::Flows::find`, its own prompt), so the list keeps its height and no new drawing was added. Every word typed (ignoring case) must appear in the persona's name, description or id or in its division's label, so `engineering` shows a whole division and `eng review` its reviewers; a division row shows only its matching personas and is dropped when none match, and the heading says `N of M … match`. **Checking a division while filtered checks only what shows** (its note says `check all shown`): checking what you cannot see would import personas you never read the name of. What is checked stays checked when the filter changes, and the question before importing counts it. Keys: while the catalogue shows, every key that edits a one-line field goes to the filter (typing, Backspace, Delete, `←` `→`, Home, End, the word moves, `Ctrl+A` `Ctrl+E`, Shift to select, paste), so a space types instead of checking; `↑` `↓` Tab move in the list, Enter checks the selected row, and Esc clears the filter first, then leaves. A click still checks a row; the field takes no click (it is always the one with the keys).
  - **Division icons and colours** (#944): `divisions.json` gives each division a Lucide icon name and a hex colour. A terminal cannot draw Lucide, so `ui/icons/lucide.rs` maps the 18 names agency-agents uses to Nerd Font glyphs of the sets the symbols subset already licenses (Codicons and Material Design Icons, all in Nerd Fonts 3.1.1, checked against its `glyphnames.json` and 3.5.1's), drawn before the division's label only when the window draws icons (`View::icons`, the `icons` setting), and nothing otherwise; an unknown name draws nothing. The 17 new code points joined `tests/fixtures/icons/symbols.txt` and the browser window's subset. The colour (`#RRGGBB` only, `ui::tint`) tints the division row's label and icon in both states, since a colour needs no font; Font Awesome's glyphs were rejected because the subset's licence file does not cover them. The row carries the name and the hex (`RowText::icon`, `tint`) and the app turns them into a glyph and a `Color` (`SettingsRow::glyph`, `tint`), so `flows/` stays free of `ui`. `divisions.json`'s `color` is also in `--catalogue --json`'s divisions (`null` when it has none).
  - **The catalogue's problems are the server's** (#939, `persona/catalogue.rs`, `offers`): one function says, per incoming persona, whether it replaces yours and why it cannot be imported, in this order: it cannot be read (not a persona, a control character), its id or its name appears more than once in the source (on every one that shares it, since picking either is the user's choice and `--only` names an id, which would be ambiguous), a persona of yours under another id has its name, or the file it would replace cannot be kept a copy of. The page's catalogue and `persona-import` with `catalogue` both use it, so the window and the command line say the same thing; before #939 the page computed its own, and missed two personas of the source sharing an id or a name until the import refused them.
  - **The role editor**: a `persona` row on every role tab and on the orchestrator's, a pick like the agent's and the model's (`none` and the library by emoji and name, the id as its note) rather than a `ui/combo.rs` combobox, since every other row of that editor opens the same pick and one combobox among them would be the odd row out. An id the library does not have shows red, `not among your personas`.
  - **The diagram** (`Node::persona`, `Diagram::named`): a role box's second line ends with ` · ` and the persona (emoji and name, else the emoji alone, else nothing) only when it fits, so a box never grows for it and no layout changed; without a label it shows the id. The Flows and start dialogs label it from the library they read on opening, the Flow panel from the run's own copies (`persona::labels`), so it shows what the run follows.
  - **For bots**: `persona-save` and `persona-remove` are closed and `persona-import` is ruled like `flow-import` (Bots › The boundary): step 1 let a bot replace a persona a flow follows, which is changing that flow's prompts.
  - **Socket**: everything the page writes goes through `persona-save`, `persona-import` and `persona-remove`, and its catalogue is `persona-import` with `catalogue` (below). The page, its form and its checks are TUI state, exempt.
- **The catalogue for other windows** (#939, step 3 of #884: cornercase-gpui drives cornercase only through the command line). `--check` refuses the whole preview on the first problem, which is right for a script about to import but leaves a picker nothing to show; it keeps that behaviour. **`persona import SOURCE --catalogue`** never refuses because of one persona and never asks `[y/N]`, since it saves nothing; `--json` prints `label`, `page`, `web`, `check` (the risk sentence, with where it came from for the web), `skipped`, `divisions` (`key`, `label`, `icon`: `divisions.json`'s `icon`, a Lucide name that a native window can draw, `null` when it has none) and `personas` in the source's order (`file`, the path inside the source, `division`, the top folder or `null`, `id`, `name`, `description`, `emoji`, `color`, `bytes`, `replaced`, and `problem`, `null` when it can be imported). A file that is not a persona has an empty `id` and `name`: its `file` names it. Without `--json` it prints the same list grouped by division. The CLI still reads the source; the server checks: `persona-import` takes `catalogue` (skipped when false, so an older server never sees it), which answers `personas` with one entry per request persona in its order (a strict client that sends `"catalogue": false` is not refused for the key the server leaves out, `contract::without_skipped_false`), each with its `file` and `problem`, saves nothing even without `check`, and is not gated for bots (it writes nothing). The divisions and the paths inside the source stay the CLI's, since the server never sees the source. Its own feature, `persona-catalogue`, which the CLI requires, so an older server is named rather than refusing an unknown field. **`--only ID`**, repeatable, keeps the personas of the source whose id (computed by the CLI as the server will, `persona::imported`) is asked, then imports them as before, all or nothing, with `source:`; an id the source does not have is an error naming every missing one, before any request. It needs nothing new on the socket: a client already sends the personas it chose. `--catalogue` conflicts with `--check`, `--yes`, `--replace` and `--only`, which mean nothing for a list that saves nothing.
- **Machines** (#944): a run on another machine reads that machine's library (its server starts the run), and `flow-import` there refuses a flow naming a persona it lacks, so both a sync and a relayed run send the personas along, **pushed with the machine's own requests**, as the flows are (Flows › Syncing with your machines): `persona-list` there once, then per id `persona-import` (`<id>.md`, the file's text as this library keeps it, `source:` included, no `replace`) for one it lacks, or `persona-show` to compare one it has. The far server checks and saves; nothing fetches, and no request was added.
  - **What goes**: for `flow sync`, the personas the flows it sends name (after the plan, so a flow `same` or `kept` there sends none), before those flows, read on the loop with the flows (`personas::library`); for a relayed `flow-run`, the ones the machine's own flow of that name names (its `flow-list` for the run's `project`, since the run follows the machine's flow, not ours), read from this library on the relay's job, before the `flow-run` on the same job (`App::spawn_ask_after`). A flow there that follows none, or a `flow-list` that fails, sends nothing and the answer has no `personas`.
  - **A different text of the same id is never replaced**: personas have no `changed`, so "last saved wins" cannot decide, and a persona there may be one the user edited there on purpose; replacing it would change how that machine's other flows work. So it is kept and named (`differ`: `kept its own personas ID, which differ from yours`), not a failure, and the flow there follows that copy; replacing it is `persona import --replace` there, the user's call. A refusal offering to replace was rejected: the sync has no question and a button that asks per persona would be the only one. The same text (a byte-for-byte match, a BOM aside) is `same`. An id this computer lacks (a flow saved before its persona was removed, or a far flow naming one only that machine has) is a `failed` entry (`it is not among this computer's personas`), and so is one the far end refused (a name another id there has), with its reason; the flow's own `flow-import` there is then refused too and reported as before.
  - **An older far server**: one without the feature `flow-personas` (the `contract` a sync asks first) gets the flows as before, which it would save without the field, and `personas.error` says `it runs a cornercase without personas: update it there, then send them again`; the sync's exit status is unchanged, since what reached the machine is what reached it before. A relayed run needs no check: a far flow that lists a persona comes from a server that has them.
  - **The answer**: `personas` (`PersonasSent`: `sent`, `same`, `differ`, `failed` with `id` and `error`, `error`), skipped when nothing was named, on each `machines` entry of `flow-sync` and on the relayed `flow-run`'s answer (`RunInfo::personas`, which `flow run` prints on stderr, one line per outcome); a relayed run refused there adds what was not sent to its refusal. The window's sync notice adds the same words to each machine's line. Logged per id (`persona sent`, `persona kept, it differs there`, `persona not sent`), never a text; the receiving side logs `personas imported` as any import.
