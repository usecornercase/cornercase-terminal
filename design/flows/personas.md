# Flows › Personas

Part of [Flows](../flows.md). Code: `flows/persona.rs`, `flows/persona/source.rs`, `control/persona.rs`, `app/control/persona.rs`, `cli/persona.rs`, `cli/args/persona.rs`, `cli/help/persona.rs`, #884 (step 1 of its plan).

- **Why**: a role had a CLI, a model, an effort and a free prompt, so how a reviewer reviews lived in each flow's prompt, written again for every flow. Collections of agent definitions exist ([msitarzewski/agency-agents](https://github.com/msitarzewski/agency-agents), MIT, some 280 of them: Markdown with a YAML front matter of `name`, `description`, `color`, `emoji`, `vibe`, grouped in folders listed in `divisions.json`). A **persona** is one of them, imported once and named by any role (`persona = "engineering-code-reviewer"`), on any agent: the same Code Reviewer runs on Claude Code or Codex.
- **The word**: "agent" already means the CLI in cornercase (Claude Code, Codex…, `Role::agent`), and "profile" means an account's login (Accounts and profiles). "Persona" says what it is, how an agent behaves, and collides with nothing in the code, the docs or the window. Rejected: "agent" (every `agent` field and the agents section would become ambiguous), "profile" (taken), "skill" (Claude Code's skills are something else that an agent loads by itself).
- **The library** (`persona::list`, `save`, `remove`): `personas/` beside `config.json`, one `<id>.md` per persona, like `flows/` (`paths::personas`, so it follows `CORNERCASE_SOCKET` as `flows/` does). Beside the config, not in the state folder, since a persona is something the user chose and keeps, like a flow, and not something the server makes. No project folder (`.cornercase/personas/`) yet: a project's flows already run its prompts unattended only after a red line, and a persona that comes with a cloned repository would be one more such text; left for when someone asks. **The file is kept as it came**, front matter and body, so it reads like the original and diffs against it; cornercase adds one key, `source:` (the repository path, the address or the absolute file it came from, quoted), replacing any `source:` it had, so that importing that source again with `--replace` refreshes it. **The id** is the file's name slugged (`engineering-code-reviewer.md` → `engineering-code-reviewer`), else the name's, else `persona`: lower-case ASCII letters, digits and `-`, at most 64 bytes (`valid_id`), so it is a safe file name on every system and a plain TOML string. A file in the folder whose stem is not an id is ignored; one that cannot be read is listed with its reason (`broken`), as for flows.
- **The front matter is read by hand** (`persona::front`, `field`): `key: value` lines between two `---` lines, values with or without quotes, and folded or literal blocks (`>`, `|`) joined into one line. No YAML crate for five keys of display text; a front matter that YAML would read differently only shows a different description. A persona is a file whose front matter gives a non-empty `name` (`is_persona`); its name, description, emoji and colour must hold no control character, since clients print them. The body is never parsed: it is the agent's to read. 256 KiB at most (as a flow), and a file of the library is read only that far.
- **Names** (`app/control/persona.rs`, `collisions`): a persona whose id you have is refused unless `--replace`, which overwrites that file; a file of that id that cannot be read counts as one you have, so it is never overwritten without `--replace`; one whose name (trimmed, ignoring case, `store::same_name`) is another id's is refused even with `--replace`, naming that id, since replacing would leave two files of one name or remove a file a flow names. The id is what flows name, so it is what `--replace` matches. **An import is all or nothing**: one persona that cannot be read, two that would take one id or one name, or one collision refuses the whole import with every reason, so a repository is never half imported; and a save that fails halfway (`persona::save_all`) removes the files it created and writes back the bytes of those it replaced before answering the error. `--name` (as `flow import` has) is left out: the file's name is the id, and a persona under two ids would only confuse the picker of step 2.
- **Importing** (`persona/source.rs`): the CLI resolves the source and reads it, the server checks and saves, as for flows (Community flows › The CLI downloads, the server does not), so the server never fetches anything. Sources: `-`, an `https://` address (`http://` refused), an existing file or folder (which beats the next), then `OWNER/REPO[/PATH]`. A path ending in `.md` is one file from `raw.githubusercontent.com/<repo>/HEAD/<path>`; anything else in a repository (the root or a folder) is **one download of the repository's tarball** from `codeload.github.com/<repo>/tar.gz/HEAD` (at most 64 MiB, 120 s, `tar` and `flate2` already in the tree for plugins), read in memory, only its `.md` files and `divisions.json`. Rejected: the GitHub API's contents or trees (60 requests an hour without a token, and one request per file: agency-agents would take some 280), a `git clone` (needs git and a temporary folder, and fetches history), and `gh` (not required anywhere else for an import). `CORNERCASE_PERSONAS_URL` and `CORNERCASE_PERSONAS_ARCHIVE_URL` replace the two hosts; tests give the hosts directly (`Hosts`) with `FakeHttp`. Downloads go through `http::download_strictly` (three redirects, never from `https://` to `http://`, no token sent).
  - **A folder or a repository imports every persona in it**: every `.md` file (folders up to 8 deep, those starting with `.` skipped, 20,000 entries at most) whose front matter gives a `name`; the rest is counted (`skipped N files that are not personas` on stderr) and left, and dropped as it is read, so only personas are held in memory, 64 MiB of them at most. **`divisions.json`**: when the folder or repository being imported holds one at its root with a `divisions` object, only the folders it names are read. agency-agents keeps per-tool converted copies under `integrations/`, one of them with a front matter, and its own `divisions.json` says those folders are not agents; a generic "every file with a name" would import that copy too. The rule is that repository's, but cheap and harmless elsewhere. At most 500 personas per import (agency-agents has 283 once `integrations/` is left out); more asks for a folder of it.
- **The risk check**: a persona is prompt text that an agent running without permission prompts reads and follows, so it is a flow's prompt by another name. Every answer of `persona-import` carries `check` (the sentence that says so), `--check` sends the request with `check: true` (validation, ids and collisions run, nothing is saved) and prints each persona's id, emoji, name, size and description, and whether it replaces yours. From an address or a repository the import always asks `[y/N]` after that preview (on stderr, so `--json` keeps stdout to its answer), with where it came from, that nobody reviewed it and the page to read it at (`https://github.com/<repo>/tree/HEAD/<path>`); without a terminal it refuses unless `--yes`, as `flow import` does. A file or folder of yours does not ask. The whole text is not printed: hundreds of KiB of prompts on a terminal is not a review, the page and the files are.
- **The role field**: `Role::persona: Option<String>`, skipped when unset, so every flow file and every answer without one keeps its bytes, and the flow's `version` stays 1: an older cornercase reading a flow with a persona runs the role without it, which loses how it works but not what it may do (unlike a worktree of its own, which needed `version = 2`). `Flow::problems` refuses a persona that is not an id (pure, so the editor and the dialogs see it); **a persona not in the library** is `Flow::persona_problems(known)`, added where the server knows the library: `flow-list`'s problems, `flow-save` (so it is not saved), `flow-import` (import the personas first), and `run_refusal` (so `flow run`, the start dialog, an issue and a routine refuse to start). The TUI's editor and start dialog do not list that problem until step 2 brings a picker; a start from them is refused by `run_refusal` with the sentence. Any role may have one, the orchestrator too: its brief has a `## Persona` section saying the plan and the rules come first.
- **Delivery through the run's folder, the same for every CLI** (`brief::member`, `brief::own_persona`, `folder::persona`): at the start of a run each persona a role names is read from the library and written to `<run>/personas/<id>.md`, created new and never written through a link, before any shell spawns, like `task.md`. A member's prompt adds, after whether it may edit: read the persona `<path>` before the first work it is sent and follow it in how it works, read it again after a compaction, and the role and the orchestrator's messages come first where they differ. "Before the first work it is sent", not "now": the prompt's last sentence stays "Wait for the orchestrator's first message before doing anything." (The brief, the team and the session). The orchestrator's team list says which persona each role follows. Why the folder first: every agent reads files, so one mechanism works for the eight CLIs and needs no live check per CLI; the prompt stays short (a persona is 5 to 25 KiB, typed into every agent's input otherwise, the cost that kept the task out of the prompts in #778). Its cost is that the persona is something the agent read, not a system prompt, so a long run or a compaction can weaken it; step 4 gives the CLIs that have a switch for it (a system prompt that survives compaction, such as Claude Code's) a native delivery, checked live per CLI. Rejected: the persona inside the role prompt (above), and `--append-system-prompt`-style flags now (different per CLI, absent in some).
- **A copy per run** (`Run::personas`, `RunState::personas`): the run keeps the text of each persona it started with, by id, as it keeps its flow and its task, saved in `session.json` (optional, so `VERSION` stays 5 and the fixtures are unchanged). Editing, replacing or removing a persona later never changes a running team, and a restore or a reopen writes a missing copy again from it (`folder::ensure_personas`, never overwriting, logged), since the prompts promise the file. Reading the library again on a restore was rejected: the team would change under a run that already started, or lose a file it was told to read. A failed start removes the copies with the task and the empty folder (`folder::discard`).
- **For clients** (`flow-personas` in `contract`, additive, `CONTRACT` stays 1): `persona-list` (`dir`, `personas` with `id`, `name`, `description`, `emoji`, `color`, `source`, `bytes`, `path`, and `broken`), `persona-import` (`personas`: `file`, `text`, `source`; `replace`; `check`; it answers `personas`, `check` and `saved`) and `persona-remove` (`id`), request names of their own so an older server refuses them by name; `persona` on the roles of `flow-list`, `flow-runs`' flows and every `RoleSpec` and `RoleInfo`, skipped when unset; a strict client that sends `"persona": null` or `"source": null` is not refused for a field the answer leaves out (`contract::unknown_fields`). `flow save` and `flow import` check the feature when a role has a persona, since an older server would drop the field in silence. The log has `personas imported` with the count and bytes and `persona removed` with the id, never a text (`PersonaImport::fields` logs `count` and `text_bytes`).
- **Machines**: a run on another machine reads that machine's library (its server starts the run), and is refused there when it lacks a persona; copying personas along with a relayed `flow-run` is left for later.
- **Left for later**: the persona pick in the Flows dialog's role editor and a catalogue browser with the divisions' labels, icons and colours (step 2), cornercase-gpui (step 3), native delivery per CLI (step 4), a project's personas, the community flows page showing a flow's personas (its loader ignores the key, so a listed flow that names one imports only once its persona is there), and refreshing every persona from its `source` in one command.
- **Checked live** (0.13.88 before its release, a debug build's own server, Claude Code 2.1.325 with Sonnet for the three roles, macOS): `persona import msitarzewski/agency-agents/engineering/engineering-code-reviewer.md` saved it with its `source:`; `--check` of the whole repository listed 283 personas, `integrations/` left out by its `divisions.json`; without a terminal and `--yes` the import was refused. A flow of a coder and a reviewer that follows that persona, run on a scratch repository with a bug in `add()`: the run's folder held `personas/engineering-code-reviewer.md`, the reviewer waited for its first message, then its first command read the persona with the task, and its review used the persona's priority marks (💭 for a nit). Not checked live: the other seven CLIs (the same files and sentence), a restore that writes a copy again.
