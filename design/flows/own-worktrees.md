# Flows › A worktree of its own

Part of [Flows](../flows.md).

- **A worktree of its own (#313)**: Arena-like flows have coders that compete, and in one worktree they overwrite each other, which is why a role can ask for its own: `Role::worktree` is `Worktree::Shared` (the default, left out of the file) or `Own`, a pick in the editor's role tab (not on the orchestrator) and `worktree = "own"` in TOML. Models and pure rules are in `flows/`; the job and the tabs are in `app/flow_runs.rs`.
  - **File version 2, only when it is needed**: `VERSION` is 2, but `to_text` writes `version = 2` only when a role is own (`Flow::file_version`), else 1, so every flow without one stays readable by older cornercase and the built-ins' site copy only gained Arena. `Flow.version` defaults to 1 when a file has none, and `store::parse` refuses a file with an own role under version 2 with the reason: an older cornercase would ignore the unknown key and run the coders in one worktree, the opposite of what the file says. After the check the flow is normalised to `VERSION` in memory, so a round trip is equal.
  - **Branches and folders**: `flows::role_branch(run, role)` is `<run>--<slug of the role>` (24 characters, `role` when the slug is empty), and its folder is the ordinary `checkout_path`, so it is a worktree like any other. Two own roles whose names make one branch are a problem. Role worktrees are made from the run's branch (`git::worktree::create_from`, where `create` is `create_from(.., "HEAD")`), not from the project's `HEAD`. A run on a **new** branch needs its role branches absent (auto-naming skips a run branch with a leftover one; a chosen branch is refused with the leftover's name), since a stale branch would start from old code; on a branch that **exists**, role branches and their worktrees (`git::checkout_of`, read from files) are reused, continuing earlier work.
  - **One job** (`spawn_run_worktrees`, `WorktreeEvent::Run`) makes the run's worktree when it is missing and then each role's, in order, and answers once (`Made`), replacing the `Stage::Run` arm of `worktree_ready`: a failure anywhere (a plain folder in the way) opens no tab, and the job first removes every worktree it made itself (registered before `git worktree add` runs, so one that fails after adding is cleaned too; a path that does not exist is skipped) (`git worktree remove --force`, branches kept), as does a hand-off that fails afterwards (`open_run`'s error), so a retry does not meet leftovers; reused worktrees are never touched. `.worktreeinclude` is copied by `create` as for any worktree.
  - **Tabs stay in the run's workspace** (the panel, the brief, launches and saved seats all assume one workspace), and a role's shell starts in its worktree folder; `Starting::trees` carries them to `open_run`. Records already go by the pane's folder, so Codex, Gemini CLI and opencode in different folders do not hide each other, and `Flow::problems`' folder rule counts only roles that share. Each role worktree is also an ordinary sidebar row (added by `open_run`, found by `sync_worktrees` anyway), so its Changes and Files panels compare candidates; nesting them under the run's row was left for later. Each row asks `gh pr view` once a minute like any worktree.
  - **The project's setup runs in every worktree cornercase made** (the run's, as before, and each new role's, with its own `CORNERCASE_BRANCH`), in that role's setup pane, which belongs to the run's workspace: `held_launch_panes` holds every launch until all setups end, and one failure drops the launches and ends the run as for a single worktree. A reused role worktree runs no setup, as any reused one.
  - **Two editors in one worktree are a problem** (and the flow does not start), also for flows written before: two roles of one stage that edit and share the worktree overwrite each other. The fix offered is a worktree of their own or stages of their own. The orchestrator cannot be own (it works where the team is). This changes user flows that had two parallel editors, which is in the CHANGELOG.
  - **Integration is a role's job** (cornercase never merges): the brief's `## Worktrees` section tells the orchestrator how to read a candidate (`git log run..B`, `git diff run...B`, `git show B:path`, build in its folder) and to ask a role that edits the shared worktree to merge or cherry-pick, never to check a role's branch out itself. Each own role's prompt tells it to commit on its branch, since nobody sees the rest. The built-in **Arena** has two or three own coders (agents spread over the installed ones, a second coder on the same agent when only one is installed), a read-only judge, an integrator that edits the shared worktree and a reviewer; it is listed last in `planned()` so `Start::new` keeps Full issue as its default. Merging by a `flow` command was left for later.
  - **Removal goes with the run's workspace**: the removal check also reads each role worktree's changes and lock (`worktree::status`; a role's lock is the one shown, carrying the role and folder (`Lock::role`) so the dialog and the command's `git worktree unlock` hint name that worktree rather than the run's, and **unlock and remove** unlocks them all, while `close --remove-worktree` refuses with the lock's reason unless `--unlock` is given), the confirmation names how many roles' worktrees go, and the job runs, for each role worktree still on disk, the teardown (with its branch) and `git worktree remove`, then the run's own, whose result stays the job's; a role's failure is a warning in the toast naming the role and the folder that stays (`could not remove the worktree of coder A, which stays in /…: …`) rather than a refusal, since the run's checkout is what the user asked to remove. One role worktree alone cannot be removed while its run lives (the toast, and `close --remove-worktree` as an error, name the role and the run's workspace): its checkout belongs to the run, and removing it behind the run's back would leave a pane in a deleted folder. Once the run ended the row is an ordinary worktree. Branches are always kept.
  - **The diagram** tags an own role's box on its top border, muted and right-aligned, with ` own worktree ` or, when the name leaves no room, ` own ` (`Node::own`; `natural()` reserves the short tag so a box is wide enough for it); the simulation draws the same, and the site's listing, its page's team table and `flow list` (` (edits, own worktree)`) and `flow run --json` (`worktree` and `branch` per member) say it too. Costs: a checkout and a build per worktree, and the setup per worktree, which the docs say.
