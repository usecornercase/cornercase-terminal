# Flows › The Flows and start dialogs

Part of [Flows](../flows.md).

- **The Flows dialog** (`flows/dialog/`, `app/flows_dialog.rs`), Settings › Flows (#322, see Settings): one list in the user's order (by name for the flows not placed, see The order and the default flow), with a muted tag only for `default`, `this project` and `edited` (the other origins are the common case, and section headings cost rows and made the list read like Settings; files that cannot be read stay at the end with their reason), and an edit page per flow drawn with the settings dialog's pieces, up to 140×40 so the diagram fits beside the form from 112 columns (else behind ` diagram `). **The list previews the selected flow too** (#292), from the same 112 columns, in the same box: a user's flow is picked from a name and a count, and seeing its plan took opening it, so a click now selects and draws, and a second click edits as before (on release since #445, see The order and the default flow). `Dialog::preview` answers `Preview::Flow` (the edit page's flow, or the selected one on the list) or `Preview::Note` where there is no flow: a file that cannot be read says `<file> cannot be read as a flow, so it has no diagram: <reason>`, an empty list says how to get one; importing and a text field have none. Narrower, the list's buttons get ` diagram ` / ` list ` (the editor's ` diagram ` / ` form `) after the selection's buttons, so ` import `, ` new ` and ` done ` keep their places. Duplicate saves a copy at once (a file is what the start dialog lists), new saves on ` save `, delete and leaving with unsaved changes ask first, and ` save ` refuses while there are problems. Stages open in place; loops stay valid by rule when stages move or go, and a stage's `when` or `at most` being typed follows its stage. Renaming a role renames it in the stages; changing its agent clears its model. `+ add stage` and `+ add role` are worded as actions. Models are a pick: Claude Code's aliases (`MODELS`), opencode's from the models.dev cache it keeps (`CATALOGUE`, read on a job), `default` and `other…` for the rest; no model id is invented.
- **The preview scrolls** with the wheel within the diagram's height, with ` ↑ more ` / ` ↓ more ` at its edges (`ui::flow::draw_scrolled`, which the Flow panel draws through too), and the offset belongs to the dialog's model: the list's is `Dialog::preview`, apart from the editor's (`Editing::preview`), so opening a flow starts at its top and coming back finds the list as it was; it goes back to the top on every change of selection, through `Dialog::select` (click, `↑` `↓`, `Tab`, the wheel over the list, and a listing that changes the selected entry). The wheel over the diagram scrolls it and, over a note, does nothing; elsewhere it moves the selection. `room()` still counts the editor's preview alone: the list's buttons already drop by a whole button row, and the list's rows never wrap. In the editor **it follows the stage being changed** (the one whose pick or field is open, else the one under the cursor): its boxes get the heavy border in their own colour (`Diagram::focused`), a working box's look without its status icon, so it cannot be taken for a live one; when that stage changes, the preview scrolls once to show all its boxes (`ui::flow::scroll_to`), only when they are out of view, so the wheel stays free. A background behind the stage (it fights the diagram's colours) and a marker beside it (the boxes move with the layout) were rejected.
- **The start dialog** (`flows/start.rs`, `app/start_flow_dialog.rs`): one dialog for the three entries (an issue's ` start a flow `, in the Issues list beside ` start ` and on the issue's page; the list's button reads the issue and asks the place first when the tracker needs one, as ` start ` does, but needs no agent; a narrow row drops ` schedule ` then ` start a flow `, **start a flow…** in the workspaces' `+ New`, `w s`). From an issue, the prompt and the branch are what ` start ` would use, so a flow and a single agent land on the same branch name. The prompt has the keys first (`Enter` is a new line there; in the branch field it starts), and the branch follows the prompt until it is touched. The list is a `Flow templates` heading and two lines per flow: the name, its tag and ` N agents `, then the description, or the first problem in red, so flows with problems stay in the list, a click from ` edit `. It takes `1 + 2·items` rows and the prompt the rest; a click on either line selects the flow, and choosing another one brings the preview back to its top. Refusals stay in the dialog in red, and it stays busy until the run opens, showing a git failure with the task kept: it closed at once before, and a long issue prompt was lost to a toast. ` edit ` opens the selected flow's edit page, whatever its origin, in the Flows dialog for the dialog's own project; ` done ` goes back to that list and another ` done ` to the start dialog, with the edited flow selected.
- **The order and the default flow** (#445, `flows/store.rs`, `flows/dialog/order.rs`, `flows/start.rs`, `app/flows_dialog.rs`, `ui/dialog/flows.rs`): going fast started a flow nobody chose (`Start::new` picked Full issue), and the flows could not be ordered, so the ones used most sat under built-ins never run, while the start dialog has room for few. **Two settings, `default_flow` (a name) and `flow_order` (names)**, both compared with `store::same_name` and never shared (they name flows a colleague may not have). Making the default the first flow of the order was rejected: a project's flow or a new built-in sorted by name could take the top spot and become the default without a choice. No preselection (an extra click every time), the last flow started (it changes on its own) and ` ↑ ` / ` ↓ ` buttons (the list already has many; dragging is what the sidebar does, #50) were rejected too, and the start dialog has no drag of its own, so it stays a form.
  - **The default** is the first listed flow with the name (`store::default_of`, the one `flow run NAME` runs); `Listing::default` holds that flow's own name, `None` when it is missing, hidden or another project's. The start dialog selects it when it can start, else today's rule (the first built-in, else the first that can start), never a later flow of the same name, which is a red duplicate; the focus stays on the prompt and an issue's ` start ` starts it. The `default` tag comes first, in both lists, and also on a red row, so a broken default is visible and explains the fallback. ` set default ` stays on the default flow and does nothing when pressed, saying so. Deleting a flow or hiding a built-in clears the default only when it is the flow the name resolves to (deleting a red duplicate keeps it); deleting your version of a built-in that is the default clears it too, since that delete hides the built-in; a save that renames a file moves the default and the order's entry (`flow_renamed`, from the dialog's save or `flow-save` with `path`), only when the renamed file is the one the default resolved to (a project's flow of the same name renamed leaves it), while saving an edited built-in under a new name is not a rename.
  - **The order** sorts `store::list` by the place of the first matching name, then name and rank, so yours and a project's flow of one name share a place and keep their rank; unreadable files and deleted built-ins stay apart. A drag writes the whole list in its new order (`Action::Order`), so after one drag the list is what is shown and later flows go after, by name. Settings › Flows lists the active project's flows, so a write also keeps the stored names it does not list that still name a flow the server knows (yours, every built-in name, every open project's flows), after the listed name each followed (`store::reorder`); a name no flow has is removed on the next write, and a closed project's names with it, which is the limit of this rule.
  - **Press holds, release opens**: a press on a flow selects it and holds it for a drag (`Dialog::grab`), and the second click on the selected flow opens the editor on release, since opening on press would make the selected flow impossible to drag. A cyan line shows the landing, drawn by the settings table like the TODO panel's (the scroll does not count it, so the view does not jump); `Esc` or any other key cancels the drag and keeps the dialog open, a new listing cancels it too and re-finds the selected flow by identity, so the selection follows a change of order. The pointer reaches the model as a plain row index (`ui::flows_row_at`), since `flows::dialog` does not import `ui`. In a narrow room the buttons drop ` share `, ` import `, ` export `, then ` set default ` before ` duplicate `.
- **Line breaks and display columns** (`editor`, on ratatui-textarea since #454; see Text fields): the TODO field stays single-line; prompts and notes get line breaks, paste with lines and vertical scrolling. Wrapping, the cursor and clicks count display columns (`unicode-width`), so wide characters wrap and place correctly, in the TODO panel too.
