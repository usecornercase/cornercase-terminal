# Flows › The Flows and start dialogs

Part of [Flows](../flows.md).

- **The Flows dialog** (`flows/dialog/`, `app/flows_dialog.rs`), Settings › Flows (#322, see Settings): one list sorted by name, with a muted tag only for `this project` and `edited` (the other origins are the common case, and section headings cost rows and made the list read like Settings; files that cannot be read stay at the end with their reason), and an edit page per flow drawn with the settings dialog's pieces, up to 140×40 so the diagram fits beside the form from 112 columns (else behind ` diagram `). **The list previews the selected flow too** (#292), from the same 112 columns, in the same box: a user's flow is picked from a name and a count, and seeing its plan took opening it, so a click now selects and draws, and a second click edits as before. `Dialog::preview` answers `Preview::Flow` (the edit page's flow, or the selected one on the list) or `Preview::Note` where there is no flow: a file that cannot be read says `<file> cannot be read as a flow, so it has no diagram: <reason>`, an empty list says how to get one; importing and a text field have none. Narrower, the list's buttons get ` diagram ` / ` list ` (the editor's ` diagram ` / ` form `) after the selection's buttons, so ` import `, ` new ` and ` done ` keep their places. Duplicate saves a copy at once (a file is what the start dialog lists), new saves on ` save `, delete and leaving with unsaved changes ask first, and ` save ` refuses while there are problems. Stages open in place; loops stay valid by rule when stages move or go, and a stage's `when` or `at most` being typed follows its stage. Renaming a role renames it in the stages; changing its agent clears its model. `+ add stage` and `+ add role` are worded as actions. Models are a pick: Claude Code's aliases (`MODELS`), opencode's from the models.dev cache it keeps (`CATALOGUE`, read on a job), `default` and `other…` for the rest; no model id is invented.
- **The preview scrolls** with the wheel within the diagram's height, with ` ↑ more ` / ` ↓ more ` at its edges (`ui::flow::draw_scrolled`, which the Flow panel draws through too), and the offset belongs to the dialog's model: the list's is `Dialog::preview`, apart from the editor's (`Editing::preview`), so opening a flow starts at its top and coming back finds the list as it was; it goes back to the top on every change of selection, through `Dialog::select` (click, `↑` `↓`, `Tab`, the wheel over the list, and a listing that changes the selected entry). The wheel over the diagram scrolls it and, over a note, does nothing; elsewhere it moves the selection. `room()` still counts the editor's preview alone: the list's buttons already drop by a whole button row, and the list's rows never wrap. In the editor **it follows the stage being changed** (the one whose pick or field is open, else the one under the cursor): its boxes get the heavy border in their own colour (`Diagram::focused`), a working box's look without its status icon, so it cannot be taken for a live one; when that stage changes, the preview scrolls once to show all its boxes (`ui::flow::scroll_to`), only when they are out of view, so the wheel stays free. A background behind the stage (it fights the diagram's colours) and a marker beside it (the boxes move with the layout) were rejected.
- **The start dialog** (`flows/start.rs`, `app/start_flow_dialog.rs`): one dialog for the three entries (an issue's ` start a flow `, in the Issues list beside ` start ` and on the issue's page; the list's button reads the issue and asks the place first when the tracker needs one, as ` start ` does, but needs no agent; a narrow row drops ` schedule ` then ` start a flow `, **start a flow…** in the workspaces' `+ New`, `w s`). From an issue, the prompt and the branch are what ` start ` would use, so a flow and a single agent land on the same branch name. The prompt has the keys first (`Enter` is a new line there; in the branch field it starts), and the branch follows the prompt until it is touched. The list is a `Flow templates` heading and two lines per flow: the name, its tag and ` N agents `, then the description, or the first problem in red, so flows with problems stay in the list, a click from ` edit `. It takes `1 + 2·items` rows and the prompt the rest; a click on either line selects the flow, and choosing another one brings the preview back to its top. Refusals stay in the dialog in red, and it stays busy until the run opens, showing a git failure with the task kept: it closed at once before, and a long issue prompt was lost to a toast. ` edit ` opens the selected flow's edit page, whatever its origin, in the Flows dialog for the dialog's own project; ` done ` goes back to that list and another ` done ` to the start dialog, with the edited flow selected.
- **Line breaks and display columns** (`todo::editor`): the TODO field stays single-line; prompts and notes get line breaks, paste with lines and vertical scrolling. Wrapping, the cursor and clicks count display columns (`unicode-width`), so wide characters wrap and place correctly, in the TODO panel too.
