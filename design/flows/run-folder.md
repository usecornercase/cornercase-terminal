# Flows › The run's folder

Part of [Flows](../flows.md).

- **The run's folder (#312)** (`flows/folder.rs`, `app/flow_runs.rs`): agents handed long reports over `read --last-message`, so each stage's output piled up in the orchestrator's context and nothing was kept once the run ended. Every run now gets a folder for its files, and roles write each answer to a file and reply with its path and a few lines.
  - **Where**: `<state>/cornercase/runs/<date>-<workspace folder slug>` (`paths::runs`; with `CORNERCASE_SOCKET`, `<stem>.runs/` beside the session file like `paths::queue`, so two servers sharing a socket folder never share one; `App::set_runs_dir` makes it absolute). Mode 0700 for the root and each folder (set again after creating it, so a tight umask does not matter); a name taken the same local day gets `-2`, `-3`… (`folder::make`). A path that is not UTF-8 is refused: it goes into the environment and the brief as text. Rejected: inside the repository's `.git` (agents refuse to write there), and under the worktree in an ignored folder (cornercase would edit the repository's ignore rules, `git clean -fdx` would delete it, and the files panel's ignore rules would hide it).
  - **The day** (#781): `<date>` is the local day, from `queue::clock::day` in `App::window_zone`, the zone of the last window that sent input, else this machine's: the rule the queue form and the Recap use; it was the UTC day, so `queue list` printed `2026-11-13 00:27` for a routine whose run was filed `2026-11-12-issue-…` in CET. Same-day numbering counts local days, folders made before keep their names, and a run on a machine takes that server's zone. Rejected: UTC with a sentence in the docs, a full timestamp with its offset (longer paths in every brief and message), and the starting client's own zone as a new `flow-run` field (a second way to learn the zone, for the rare server whose window and command sit in different zones). Tests: `clock::day` is pure with fixed instants, `folder::make` takes the day, and the app test gives the window a zone whose day is not UTC's at the hour it runs (`-12:00` before 11:00 UTC, `+14:00` after), so it fails with UTC names at any hour and never crosses a local midnight (#783).
  - **A run that cannot get its folder does not start** (`could not make the run's folder: …`); a spawn that fails afterwards removes the empty folder, so a failed start leaves nothing.
  - **The variable**: every pane of the run gets `CORNERCASE_RUN_DIR` at spawn (`App::pane_env`), also after a restore, since roles are spawned with it again (`App::spawn_with`). Only a run's panes have it.
  - **Always a file, no opt-out**: each role writes every answer to `<role slug>-<n>.md` and replies with the path; the orchestrator passes paths on and writes its own decisions (`orchestrator-<n>.md`). One rule is simpler than a threshold, and `read --last-message` stays short. A `files = false` flow option was left for later; a flow's own prompts can still say otherwise. A role that may not edit is told "the worktree's files", or it would be forbidden to write its answer.
  - **Agent flags** (`Known::add_dir`, `ADD_DIR` per folder; checked against installed Claude Code 2.1.302, Codex 0.162.1, Cursor CLI 2026.10.14, GitHub Copilot CLI 1.0.98 and Gemini CLI 0.64.0, no live runs of the folder dialog): Claude Code, Codex, Cursor CLI and GitHub Copilot CLI take `--add-dir DIR` so their file tools reach the folder; the role's command appends it last (`flows::command`, `flows::resume`), so Claude's variadic flag only meets an option (`--resume`) or the end, and Codex's `resume … --add-dir DIR <id>` reads as one value. Gemini CLI has `--include-directories` but is left out: with folder trust on (the default) an included folder with no rule in `trustedFolders.json` opens a dialog at every start (`MultiFolderTrustDialog`), which a first launch would answer but a resume (`Launch::command`, which never answers) would not, and pre-trusting it means writing Gemini's config. Its shell already writes there under `--yolo`, as opencode's and Grok Build's do (they have no such flag); the prompt says to use the shell when file tools cannot reach it.
  - **Lifecycle**: the workspace owns its folders (`Workspace::run_dirs`), since a run ends when its tabs close while its files must stay, and a workspace can run a second flow later (a folder each). They go with the workspace, once it is really gone (`App::defer_run_dirs`: a closing workspace keeps them until its shells have exited and it left the hierarchy, checked every refresh, so an agent still writing cannot race the removal; `sync_worktrees` removes at once, since nothing runs there), in a background job each (`App::remove_run_dirs`, logged with files and bytes): `drop_workspace` (a plain close and a successful worktree removal), `close_project`, and `sync_worktrees` for a worktree that vanished. They stay on a failed removal, on `close --workspace` of a worktree (it only stops the shells), on a server stop and when a restore skips a workspace or project (a missing disk must not cost files). Removal walks regular files only, never follows a link, and visits at most 2,000 entries to count them.
  - **Saved as names**: `RunState::dir` and `WorkspaceState::run_dirs` hold folder names only, joined to the runs root on restore, and only when `folder::valid` (one plain component), so an edited `session.json` can never point a removal elsewhere. A deleted folder is made again (`folder::ensure`, which refuses a link or a file). Optional fields, so `VERSION` stays 5 and the v5 fixture is unchanged. A run saved before this has none, since its brief never named one.
  - **Shown**: the Flow panel lists the folder under the diagram (`Files · n`, newest first, name cut at the end, size and age right-aligned, the size dropped first when the name would get under 8 cells; ` open folder ` on the title opens the run's folder through open in…, or copies its path when the window can open nothing), from a listing job every 2 s while the panel shows (one in flight, given up after 30 s; at most 200 files, three folders deep, `n+` when cut); a click opens the file in the files panel with `open_link` (an absolute path, like any file outside the workspace); its ` ‹ ` comes back to the Flow panel, scrolled where it was (#580, see Files panel). `flow run` prints the folder on stderr (`run_dir` with `--json`, so stdout is unchanged), and `status --json` gives each workspace `run_dir` (the run's, else the last one made), so a script finds the files of a run that ended. An ended run's files in the panel (it shows only while a run does) and an opt-out are left out.
  - **With a worktree of its own (#313)**: the folder is the run's, not a worktree's, so a role in its own worktree gets the same `CORNERCASE_RUN_DIR` and `--add-dir` (the folder is outside every worktree, and that role's shell and resume line pass it like any other), and a role whose worktree is gone and works in the run's now keeps it too. The folder belongs to the run's workspace, whose removal (with its role worktrees) removes it.
  - **The task as a file (#778)** (`folder::write_task`, `App::make_run_dir`): the task reached only the orchestrator's brief, and each role got the orchestrator's retelling: in two measured runs (0.13.39, a Sonnet orchestrator) it passed on 47 % and 13 % of a 13 to 15 KB task, and dropped per-issue conditions, how to take captures and the checks' rules. So `task.md` holds `Run::task` byte for byte (the `task` of `flow-runs`, no trim, no added newline), written right after the folder is made and before any shell spawns, whatever started the run (`open_run` is the one place: `flow run`, the start dialog, an issue, a routine). A routine's closing sentence is the orchestrator's own and stays out. A run on a machine is written by that machine's server in its own folder; an older server there writes none and its brief names none. Always a file, also for a one-line task. It is created new (`create_new`, never overwritten, never written through a link) and a run that cannot write it does not start: `folder::discard` removes the file and the folder, when it is empty, on any failed start. A restore or a reopen writes it again only when it is missing (a run from before this, or a deleted folder), since the prompts promise it; it never overwrites, and failing is only logged. It cannot collide with an answer (`<slug>-<n>.md`). The brief's `## Files` names it and its plan tells the orchestrator to give each role the path of `task.md` and what the stage adds, never a retelling; each member's prompt says the task in full is there and to read it before the work it is sent. The orchestrator still has the task in its brief. Nothing is new for clients: `flow-runs` gives `task` and `dir`, `flow-files` lists the file and `files-read` reads it. Rejected: a size threshold (one rule, as for answers); the task inside each member's prompt (typed into every agent's input and in its context from the start); leaving it to the orchestrator (it races the first message, and it kept 47 % when it did); the user's prompt file itself (the server may be on another machine, and the file can change).
  - **Log**: the folder made (path and the task's size, never its text), made again at a restore, the task written again at a restore or a reopen, each removal (path, files, bytes), listings at debug (a count); never file names or contents.
