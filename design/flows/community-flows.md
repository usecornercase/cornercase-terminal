# Flows › Community flows

Part of [Flows](../flows.md).

- **Community flows** (`flows/registry.rs`, `site/src/lib/registry.ts`, `site/scripts/refresh-flows.mjs`, `site/src/data/flows.json`, `site/src/pages/flows/`): a directory of flows that anyone publishes, shown at `usecornercase.dev/flows/` and imported by `OWNER/REPO`. **Open discovery, like a plugin directory, no pull request here** (the user's decision, over a curated folder in this repository): any public repository with the topic `cornercase-flow` and a `flow.toml` (else `cornercase-flow.toml`) at its root is listed. It is not reviewed, and the page, the import and the docs say so: a flow's prompts drive agents that never ask for permission, and what an imported flow does is the importer's responsibility. A curated registry would have bought review at the price of a bottleneck, and its prompts could not be audited by a script anyway.
  - **A scheduled script builds the list** (`refresh-flows.mjs`, `npm run flows`): the GitHub search for `topic:cornercase-flow` (sorted by stars, at most 300 repositories, forks, archived and private ones left out; `GITHUB_TOKEN` when present, and sent only to the default API address, never to a `GITHUB_API_URL` override), then each repository's file from `raw.githubusercontent.com/<repo>/HEAD/` (at most 256 KiB, 15 s per request, eight at a time), written to `flows.json` with the stars, the repository's description and topics. The build reads only that snapshot, so it needs no network and the committed one is the fallback: `pages.yml` runs the refresh before the check on every build that is not a pull request (push, the hourly `schedule`, manual) with `continue-on-error`, so a rate limit or an outage keeps the last snapshot and the site still deploys, and a following step (`steps.flows.outcome == 'failure'`) writes a workflow warning that the list is stale. The snapshot is not committed back by CI (it would need a token that pushes to `main`); it is committed by hand now and then, and an empty one lists nothing. The schedule is hourly, at minute 23 (GitHub delays scheduled runs most at the top of the hour): a build takes a minute or two and makes one search, so the list is meant to be about an hour old at most instead of a day, and more often would mostly redeploy an unchanged site. It is a target, not a deadline: GitHub can delay scheduled runs under load and drop some. GitHub turns scheduled workflows off after 60 days without activity in the repository.
  - **The loader validates for listing** (`registry.ts`, `problems`): the 256 KiB cap, a TOML that parses, a name, 1 to 8 roles, known agents, unique role names, every role in exactly one stage, loops only to earlier stages, no control characters, **no `env` or `args` in any role**, `worktree` only `shared` or `own` (never on the orchestrator, and `own` only in a file that says `version = 2`; a version above 2 is a newer cornercase), no two roles that edit the shared worktree in one stage, a repository name of the shape `owner/repo` (never `.` or `..`, since it becomes a path and a link), and caps on what a page prints (name 80, description 300, a role's name, model, effort and a loop's label 60, a prompt 32 KiB), with types checked. The Rust `Flow::problems` is not run here (the site cannot build cornercase), so the two lists are kept in step by hand: the TypeScript one is deliberately a little stricter about what a listing may contain. An entry that fails is skipped with one log line (`flows: skipped owner/repo: …`), never fails the build.
  - **Built-in flows are listed too, first** (`site/src/data/builtin-flows.json`, `builtIns()`): the page would otherwise be empty until someone publishes, and it shows what a flow looks like. The site cannot run Rust, so the file is generated from `builtin::flows` with every agent installed and `claude` as the default, and `flows::tests::site_copy` fails when the committed file differs, with `CORNERCASE_UPDATE_BUILTIN_FLOWS=1 cargo test --locked site_copy` to rewrite it (so a change to a built-in flow's prompts must be committed with its copy). They sort before the community's rather than among them by stars (they have none), are tagged `built in`, name `cornercase` as author without a link, link the project's repository, live at `/flows/built-in/<slug>/` (a community repository whose owner is `built-in` is skipped, so the paths never collide), carry no import command or caution but a note that they already come with cornercase and are edited or deleted in Settings → Flows, and go through the same validation, which fails the build instead of skipping. The empty state is for the community's flows only.
  - **The pages**: `/flows/` lists cards most starred first, with a client-side search over name, description, author, repository and tags (an inline script, nothing external, and the cards are plain HTML without it); `/flows/<owner>/<repo>/` shows the stars and the link to the repository, a caution naming how many agents run without asking, the import command, the plan drawn with the simulation's own diagram, the roles, **every prompt in full** and the raw file as it was at the last refresh. There is no raw `.toml` endpoint: the repository serves it.
  - **The CLI downloads, the server does not**: `flow import SOURCE` resolves the source (`registry::source`: `-`, an `https://` address, an existing path, which beats `owner/repo`, then `owner/repo`; `http://` is refused) and sends the text in the same `flow-import` request, so there is no protocol change and it works with older servers. `owner/repo` reads `raw.githubusercontent.com/<repo>/HEAD/flow.toml`, then `cornercase-flow.toml` on a 404 (`HEAD` is the default branch, so no GitHub API call or token is needed). A source that is an address or a repository always asks `[y/N]` (without a terminal it refuses unless `--yes`), with a line saying where it came from, that nobody reviewed it, and where to read it, besides the risks of `env` and `args`. `CORNERCASE_FLOWS_URL` replaces the raw host for tests. `registry::fetch` reads through `http::download_strictly` (20 s, `share::MAX_BYTES` plus one byte; at most 3 redirects, and none from an `https://` address to plain `http://` (`https_only` on the agent, since a typed address must not end up somewhere the user did not type; the cap is tested with chains of three and four redirects, but the downgrade refusal is **not tested**, because it needs a TLS server); no token is sent). A body past the limit is the `too long for a flow` message, not a download failure. A redirect to a private address is not checked: the server fetches only what the user typed, and the answer is shown as text to be read before anything is saved.
  - **The Flows dialog** takes the same sources on the import page: one line that `registry::typed` turns into a repository or an address makes **import** fetch it on a job (`AppEvent::FlowFetched`, `fetching…` on the hint line) and open the flow in the editor unsaved, with a notice that nobody reviewed it, like any import. While it waits the hint names the exact address (`fetching https://raw.githubusercontent.com/…/flow.toml…`), so a line typed as a path but read as `owner/repo` is visible before the answer. An answer for a source that is no longer being fetched, or after the page closed, is dropped. A line like `dir/file` that is meant as a path cannot be told from a repository there, since the server has no say over the user's disk; on the page a pasted text is the way to import a file.
  - **Rejected or left for later**: a curated folder reviewed through pull requests (and a `[registry]` table, `min_version` and author checks in `cargo test`, which went with it); versions and pinning (an import is a copy); a GitHub API call per import; committing the snapshot from CI; an `index.json` and browsing the list inside the app (nothing consumes them yet).
