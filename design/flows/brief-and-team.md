# Flows › The brief, the team and the session

Part of [Flows](../flows.md).

- **The brief** (`flows/brief.rs`, pure): the task, the team (role, pane, agent and model, whether it edits), the stages in words with their loops and limits, the final action, the flow's notes and the orchestrator role's prompt, then the driving rules from the skill and the fleet runs: one self-contained `send --enter` per step, `read --last-message` rather than the screen, never edit the worktree's files, commit or answer a permission prompt, stay in the worktree, and at the end the final action and `cornercase mark` on its own pane. With the run's folder (below) a `## Files` section sits before the rules, and they say the folder is the only place the orchestrator writes. **Waits run in the foreground**, with `--timeout 540` and the shell tool's longest limit (600000 ms on Claude Code's Bash), one wait at a time with a `--pane` for each role it waits for and never several identical waits, again on a timeout, and again after the user writes to the orchestrator (a wait moved to the background that ends is not news). The rules hold after the plan too. A background wait ends the orchestrator's turn, which then showed as finished while its team worked (Claude Code 2.1.300 writes `idle`, not `shell`, for a background Bash). Why the rules say all that (#443): in one long run (Claude Code 2.1.308, Sonnet 5.5) the orchestrator went idle 14 times while the coder worked on what it had just sent; waits of `--timeout 100` to `110` against 30 to 90-minute rounds cost about 50 timed-out waits per round, three in parallel; and in 32 of 77 orchestrator transcripts on that machine Claude Code moved a command to the background when a message arrived. Short on purpose: a long brief wastes the orchestrator's context. Each member's prompt ends with whether it may edit the worktree's files, then (with a folder) where its answers go, and with "Wait for the orchestrator's first message", once, so a user's prompt that forgets them keeps both rules.
- **Members' notifications and marks**: a member's finished turn is the orchestrator's business, so it gets no `✓` (it is marked seen on each read, and the run's workspace row stays clear) and no toast, desktop or Telegram notice. A member waiting (a permission prompt the orchestrator must not answer) or failing still notifies. The orchestrator turning from working to `pending` (its own `cornercase mark`) notifies once, like a finished agent, since `pending` never notifies. Before, one small run of three agents sent seven notices and its end none. A member that finishes work the orchestrator sent it is told to the orchestrator instead (see Waking the orchestrator).
- **Waking the orchestrator** (#443; `app/control/flow/wake.rs`, `Run::sent`, `Requests::callers`): the brief's rules do not depend on a model remembering them for hours, so cornercase also tells the orchestrator when a role finishes work it sent. What counts: the orchestrator's `send --enter` goes out into a member's pane (hooked in `put_through`, not where the message is recorded, since a send held while the person types (#371) is recorded when accepted but goes out later, and comparing the person's typing with acceptance time would treat their later Enter as theirs); the role was seen working since then (`worked_since`, not `reacted`: a background shell ending right after the send is a move and would look like a finished turn); and its turn is over by the `turn-over` rule, `failed` included, but not `waiting` (that already notifies the person). Any other send into that pane, or the person typing there after the send (a follow-up, an `Esc`, ask agent), forgets it: that turn is theirs. It is not told when a wait from the orchestrator's pane covers the role (a `wait`, a part of `--any`/`--all` not yet ended, `send --wait`): that wait, or its background-task notice, reports it. Coverage is checked right after `watch_agents` and before `check_requests`, so a wait that ends on the same read is still pending; any later message from the orchestrator to that role (send, keys, read, wait) also drops a finished entry. **When**: once the orchestrator's own turn is over, not at once (deviating from the issue's idea of typing it and letting Claude Code queue it): a message arriving while a foreground command runs makes Claude Code move that command to the background, so a wake about role A typed during `wait --pane B` would cause the failure it fixes; deferring also drops the wake when a role finishes between the orchestrator's `send` and its `wait`, so no step runs twice. **How**: one message for every role finished by then, as a `send --enter` from an internal client (`1 << 59`, no caller, so it is no run message and moves no progress), through the held-send path, one in flight per run; if the orchestrator's pane is gone or the send is refused, the person gets the role's ordinary finished notice instead. Memory only: a closed run drops it, and a restore starts with none (`brief::restored` and `reopened` cover it). `flow-runs` gives each role `awaited` (`working`, `finished`, omitted otherwise; additive, so the v1 fixture is unchanged); no `events` line, as held sends have none. Rejected: the brief alone, notifying the person (someone still has to tell the orchestrator), `/loop` or cron (agent-specific, turns every check into a turn), and a hidden internal `wait` per send (it ends on `waiting` and needs re-arming, and its answer comes in the same `check_requests` pass as the orchestrator's own wait, so which one told it would depend on the order of pending requests). Costs: a turn shorter than a status read (500 ms) is never seen working and wakes no one; any key the person presses in the role's pane after the send hands the turn to them, even a draft they drop; an orchestrator whose agent exited keeps its wake until the agent is back (only a closed pane falls back to the person); `keys` with Enter neither sets nor forgets.
- **The team hangs under its orchestrator** (#347): `open_run` gives each member the orchestrator's pane as its parent, and the orchestrator the pane that ran `flow run` (`Starting::parent`; none from the window), so the agents section draws the run as a tree, and names each member by its role (see Layout). `restore_run` gives a member with no saved parent the restored orchestrator, which covers runs saved before parents existed; a saved parent wins, and a saved parent that cannot be restored falls back to the orchestrator.
- **The session**: `WorkspaceState::run`, optional so `VERSION` stays 5, holds the whole flow (a built-in changes with updates and a user's may be edited or deleted, but the team follows the plan it was briefed with), the task, each role's tab and pane position (pane ids last one server run) and where the plan stands (the active stage and the loop rounds, as numbers). Messages are never saved. A restore rebuilds the run with the new pane ids, and a member resumes with its role's command (`flows::resume`) only when the saved conversation is its role's agent. A resumed orchestrator not marked for review gets `brief::restored`, its team's new pane ids: the new server numbers panes from 1, so its old ids may name other panes, in another project. Telling it to look panes up again was rejected: it cannot notice that an id now names another pane. It is also told the run's folder, which a restore keeps.
- **Closing and reopening a run** (#430, see Saved session): a workspace's agents closed with their orchestrator keep the run whole (the same id, messages, progress and folder) in `AgentRuntime::closed`, out of `App::runs`. Reopening reseats the members from their saved positions, gives each its saved conversation (a role closed earlier with its `×`, or one whose conversation cannot resume, starts fresh from `brief::member`, in a tab named after the role), and starts the orchestrator last. A resumed orchestrator gets `brief::reopened`: the new pane ids, the folder, who was cut in the middle of a turn and who starts over, and the same advice as after a restart (read what each last answered, then go on; answer `ok` if the plan was done). One with no conversation gets the full brief plus a short `## Where the run stands` note. `brief::restored`'s text is unchanged and shares the pane list and folder sentences with the new ones. The agents section's ` × ` on a member closes the team for good and the run ends (#438, see Layout › Agents section).
- **Context and compaction** (#444; `brief::CONTEXT_RULE`, `Known::compact`): a long run fills a role's context (the person saw the coder at 76 % after hours of follow-ups) and neither the orchestrator nor the person could act on it: the brief did not say `status --panes` has a `context` column, so the orchestrator looked only when asked and found the column with `awk`; right after its own `/compact` the value was empty and it read that as "not available"; and `send --enter '/compact …'` failed `not confirmed` while the compaction ran (see Confirming sends). So the brief has one rule: before a large piece of work, check `cornercase status --panes | cut -f 1,7,12,13,26,32` (pane, status, context, caller, role, compacted: the columns never move, since new ones only go at the end), and above about 70 % send the role its compact command first, with what it must keep when the command takes that (the branches, the checks to run, what is left), in the foreground with `--timeout 540` as any wait, then send the work; an empty context with `compacted` true is the compaction, not a missing figure; and the orchestrator cannot compact itself (a command typed into its own input box is no tool call), so past about 80 % it tells the person with `cornercase notify`, who can type `/compact` in its tab. The team line of each role ends with its agent's command (`compacts with `/compact` and what it must keep`, or `compacts with `/compress` alone`; nothing for an agent string cornercase does not know), from the agent's folder (`Known::compact`). `cut -f` rather than `awk '$1==N'` or the whole table: fixed columns keep the orchestrator's context small, and a dev server whose `PATH` has an older `cornercase` without the column gives an empty last field, so live checks put `target/debug` first on the `PATH`. Rejected: cornercase compacting at a threshold by itself (the orchestrator knows when a role is between tasks and what it must keep, and the orchestrator drives the work), a fresh role instead (loses what was never written down, such as how a tricky rebase was done; it stays the orchestrator's choice), and leaning on the agents' auto-compaction (it comes late, in the middle of a task, and keeps what the agent picks). Known limit: Claude Code's `DISABLE_COMPACT` turns `/compact` off, so the advice then fails visibly.
