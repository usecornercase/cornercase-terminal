# Flows › The brief, the team and the session

Part of [Flows](../flows.md).

- **The brief** (`flows/brief.rs`, pure): the task, the team (role, pane, agent and model, whether it edits), the stages in words with their loops and limits, the final action, the flow's notes and the orchestrator role's prompt, then the driving rules from the skill and the fleet runs: one self-contained `send --enter` per step, `read --last-message` rather than the screen, never edit the worktree's files, commit or answer a permission prompt, stay in the worktree, and at the end the final action and `cornercase mark` on its own pane. With the run's folder (below) a `## Files` section sits before the rules, the plan tells it to give each role the path of `task.md` and what the stage adds instead of retelling the task (see The run's folder › The task as a file), and they say the folder is the only place the orchestrator writes. **Waits run in the foreground**, with `--timeout 540` and the shell tool's longest limit (600000 ms on Claude Code's Bash), one wait at a time with a `--pane` for each role it waits for and never several identical waits, again on a timeout, and again after the user writes to the orchestrator (a wait moved to the background that ends is not news). The rules hold after the plan too. A background wait ends the orchestrator's turn, which then showed as finished while its team worked (Claude Code 2.1.300 writes `idle`, not `shell`, for a background Bash). Why the rules say all that (#443): in one long run (Claude Code 2.1.308, Sonnet 5.5) the orchestrator went idle 14 times while the coder worked on what it had just sent; waits of `--timeout 100` to `110` against 30 to 90-minute rounds cost about 50 timed-out waits per round, three in parallel; and in 32 of 77 orchestrator transcripts on that machine Claude Code moved a command to the background when a message arrived. Short on purpose: a long brief wastes the orchestrator's context. Each member's prompt ends with whether it may edit the worktree's files, then (with a folder) where its answers go, and with "Wait for the orchestrator's first message", once, so a user's prompt that forgets them keeps both rules.
- **After a loop, every later stage runs again (#780)** (`brief::plan`, `stage_line`, `END_WHEN`): in 3 of 4 runs the orchestrator skipped the reviewers after a fix the reviewers asked for, and one opened its pull request with the last fix untested; the fourth reran them and found a regression. "Go back to stage n" did not say that the stages after it run again, and "then go on" read as leave to go on. So `## Plan` says once that after going back, that stage and every stage after it run again, in order, on what changed, before the work goes on; each loop's line says "then run every stage after it again, in order" and that past its limit the work goes on *even if the stage reports again*, listing what is left; and the end reads "At the end, once every stage after the last change has run on it, and each of them that has a loop answered clean or reached its limit (then list what is left): …" (a stage with no loop passes once it has run: a flow whose last stage never goes back would otherwise wait for an answer nothing can force). Rejected: cornercase holding the final action or refusing a `send` that skips a stage (the orchestrator is an agent, not a workflow engine, and cornercase never reads a verdict). #782 shows it: see Recording, progress, the diagram and the Flow panel › Not run since the last change. **The small cases (#805)**: an orchestrator on 0.13.57 still skipped the reviewers after a second loop (a docs-only fix and a rebase on a moved `main`), so `## Plan` also says "however small the change (a fix of docs only, a rebase or a merge of a moved branch included)", and cornercase tells it when it does: an orchestrator's `send` that moves the work on while a stage before the target is still not run since the last change, and `mark` on its own pane with stages owed, answer `warning: stage 3 (reviewer, security) has not run since the last change in stage 2: run it first, or say in your summary why not` (`brief::owed`, `Run::skipped`, `Run::owed`, `Runs::owed_at`). The send still goes (rejected in #780 and #782). **On stderr, and in the answer's `warning` key** (the one `close` has; `--json` leaves stderr empty): stdout is what scripts parse (nothing for `send`, one ending with `--wait`, whose `$(…)` is compared to `idle`; with `--json` it is one complete document), and the orchestrator still reads it, since Claude Code's Bash result and Codex's exec carry stderr with a status 0. Rejected: stdout (breaks `$(cornercase send … --wait)`), and a flow-level "only when code changed" stage (a rebase is a change the reviewers must see; the warning and the brief cover it). The warning is given for each send into a later stage, so each parallel role of the target gets it; the first pass that skips a stage still gives none, as in #782. Also seen in #780, left as it is: a round counts every send back along the loop, whatever it carries (progress comes from requests, never from what agents say), so the count reads as times the work went back, not as times the stage failed; with this rule each such send goes through the later stages too.
- **Members' notifications and marks**: a member's finished turn is the orchestrator's business, so it gets no `✓` (it is marked seen on each read, and the run's workspace row stays clear) and no toast, desktop or Telegram notice. A member waiting (a permission prompt the orchestrator must not answer) or failing still notifies, unless `notify_subagents` is off (see Agent status › Notifications › Subagents' notices): a member is a subagent, so it is then silent on every channel and only its `!` shows, while an orchestrator started from the window still tells its `pending`. The orchestrator turning from working to `pending` (its own `cornercase mark`) notifies once, like a finished agent, since `pending` never notifies. Before, one small run of three agents sent seven notices and its end none. A member that finishes work the orchestrator sent it is told to the orchestrator instead (see Waking the orchestrator).
- **Waking the orchestrator** (#443; `app/control/flow/wake.rs`, `Run::sent`, `Requests::callers`): the brief's rules do not depend on a model remembering them for hours, so cornercase also tells the orchestrator when a role finishes work it sent. What counts: the orchestrator's `send --enter` goes out into a member's pane (hooked in `put_through`, not where the message is recorded, since a send held while the person types (#371) is recorded when accepted but goes out later, and comparing the person's typing with acceptance time would treat their later Enter as theirs); the role was seen working since then (`worked_since`, not `reacted`: a background shell ending right after the send is a move and would look like a finished turn); and its turn is over by the `turn-over` rule, `failed` included, but not `waiting` (that already notifies the person). Any other send into that pane, or the person typing there after the send (a follow-up, an `Esc`, ask agent), forgets it: that turn is theirs. It is not told when a wait from the orchestrator's pane covers the role (a `wait`, a part of `--any`/`--all` not yet ended, `send --wait`): that wait, or its background-task notice, reports it. Coverage is checked right after `watch_agents` and before `check_requests`, so a wait that ends on the same read is still pending; any later message from the orchestrator to that role (send, keys, read, wait) also drops a finished entry. **When**: once the orchestrator's own turn is over, not at once (deviating from the issue's idea of typing it and letting Claude Code queue it): a message arriving while a foreground command runs makes Claude Code move that command to the background, so a wake about role A typed during `wait --pane B` would cause the failure it fixes; deferring also drops the wake when a role finishes between the orchestrator's `send` and its `wait`, so no step runs twice. **How**: one message for every role finished by then, as a `send --enter` from an internal client (`1 << 59`, no caller, so it is no run message and moves no progress), through the held-send path, one in flight per run; if the orchestrator's pane is gone or the send is refused, the person gets the role's ordinary finished notice instead. Memory only: a closed run drops it, and a restore starts with none (`brief::restored` and `reopened` cover it). `flow-runs` gives each role `awaited` (`working`, `finished`, omitted otherwise; additive, so the v1 fixture is unchanged); no `events` line, as held sends have none. Rejected: the brief alone, notifying the person (someone still has to tell the orchestrator), `/loop` or cron (agent-specific, turns every check into a turn), and a hidden internal `wait` per send (it ends on `waiting` and needs re-arming, and its answer comes in the same `check_requests` pass as the orchestrator's own wait, so which one told it would depend on the order of pending requests). **A role brought back (#826)**: reopening a flow role whose agent exited (see Saved session) while the orchestrator kept running records it like a finished role (`Run::brought_back`, `Sent::back`), so it rides the same machinery: the orchestrator is told once its turn is over (`brief::back`: it exited and cornercase started it again in its pane, read what it last wrote, then send it again any work it had not finished), the message is dropped when the orchestrator already talks to the role, and `tell_person` skips it, since the person reopened it. **A role whose turn ended `failed` (#802)** counts as finished (`Sent::failed`), and the wake says so (`brief::failed`: it ended its turn on an error, such as an API error, so the work was not done; read its last message and send it again, and tell the user with `cornercase notify` if it fails again), as the rules (`FAILED_RULE`) tell. **An orchestrator whose own turn ended `failed` is woken again** (`Run::retry`, `Retry`): 1 minute after it was seen failed, then 2 and 4 (3 retries at most, counted from its last turn that ended another way; working or a background shell keep the count), with "Your last turn ended on an error … go on with the plan from where you stopped". A block of the API can last minutes (four failures within 3 minutes in #802), so an immediate retry could hit it again; after 3 the person has had the `failed` notice and `flow runs` shows the run stopped. A role that finishes while the orchestrator is failed waits for that delay too (its entry stays due, so the retry is not spent outside the schedule); once the three retries are spent, the wake goes out with the role's line alone. A run that ended (latched or marked) is not retried. The wake texts avoid the words the test fake agent branches on (`ask`, `panel`, `survey`, `questions`, `subagent`, `background`, `api-error`, `/compact`), pinned by a test. `Retry` counts a retry as answered only once the orchestrator was seen working or in a background shell after it: the prompt line reaches the transcript (clearing `failed`) a moment before the session file turns busy, and a read between the two must not restart the three. Memory only, like `sent`. Costs: a turn shorter than a status read (500 ms) is never seen working and wakes no one; any key the person presses in the role's pane after the send hands the turn to them, even a draft they drop; an orchestrator whose agent exited keeps its wake until the agent is back (only a closed pane falls back to the person), and an exited orchestrator that is reopened is told about the roles that exited with it by `brief::exited`, not by the wake; `keys` with Enter neither sets nor forgets.
- **The team hangs under its orchestrator** (#347): `open_run` gives each member the orchestrator's pane as its parent, and the orchestrator the pane that ran `flow run` (`Starting::parent`; none from the window), so the agents section draws the run as a tree, and names each member by its role (see Layout). `restore_run` gives every member the restored orchestrator (`By::Pane`), never its saved parent, which covers runs saved before parents existed. The orchestrator's own link is its caller's agent's (#717).
- **The session**: `WorkspaceState::run`, optional so `VERSION` stays 5, holds the whole flow (a built-in changes with updates and a user's may be edited or deleted, but the team follows the plan it was briefed with), the task, each role's tab and pane position (pane ids last one server run) and where the plan stands (the active stage and the loop rounds, as numbers). Messages are never saved. A restore rebuilds the run with the new pane ids, and a member resumes with its role's command (`flows::resume`) only when the saved conversation is its role's agent. A resumed orchestrator not marked for review gets `brief::restored`, its team's new pane ids: the new server numbers panes from 1, so its old ids may name other panes, in another project. Telling it to look panes up again was rejected: it cannot notice that an id now names another pane. It is also told the run's folder, which a restore keeps.
- **A resumed orchestrator takes its brief** (#843; `Launch::confirm`, `launch_briefed`): after a restart Claude Code is still finishing `--resume` when the brief is typed (its resume hooks, a synthetic `No response requested.` for the interrupted turn, a `<task-notification>` for each background shell the old process left), and in 2 of the 4 restarts with runs in one server's log (2026-11-13 09:11, 2026-11-14 11:08; Linux, Claude Code 2.1.325) the Enter was lost: the text sat in the input box, the launch logged `done` and the run stood still until a person pressed Enter. A launch can confirm its submission: the Enter moves it to a `confirm` stage instead of ending it, and it presses Enter again 3 s after an Enter that got no reaction (`CONFIRM_EVERY`), at most 5 Enters in all (`MAX_ENTERS`), so it ends at most 15 s after the first whatever happens. **Taken** means the agent recorded a prompt at or after the paste (the record `send --enter` confirms with, compared with the paste's wall-clock time, since Claude Code writes milliseconds and a record made within the Enter's millisecond would compare as earlier) or was seen working after the first Enter. Any change of activity does not count: the synthetic turn and the notifications move it without taking the brief, and in both stalled restarts none of them made the agent work. Any other non-idle state (waiting, failed, a background shell, subagents) ends the confirmation as taken, because an Enter there is never safe; an unknown status or a dialog over the input box skips that Enter and the time bound still runs; the shell back in the foreground ends it. A pane with no agent status at the first Enter is done at that Enter, as before. The confirming launch still `submits`, so the pane holds window keys, `input` and held sends meanwhile, and its ` cancel ` on the resume band drops the retries. `server.log` gets `launch: wrote … to=confirm`, `launch: enter again … enters=N`, `launch: taken … seen=prompt|working|<state>` and, at the bound or when the agent left, `WARN launch: the agent did not take the prompt … status=… input=text|empty|unknown` (`input` is what Claude Code's input box shows, so a lost text can be told from a lost Enter); the run's `stopped` already shows a stalled run, so no socket field was added. The brief is never typed again: in both stalled restarts the text stayed in the box, typing it into a box that still holds it would double it, and for 7 of the 8 agents the box cannot be read. Only the briefed launches (`launch_briefed`, which serves `brief::restored`, `brief::reopened` and `brief::exited`) switch it on: every lost Enter seen followed a `--resume`; confirming every launch with a prompt would make `start` answer only once the agent's record is read, a fresh run's orchestrator wait for every member's record, every new agent's pane hold keys for up to 15 s whenever its record cannot be read (two Codex in one folder), and press Enter again into agents whose empty Enter was never checked; and `send --enter` already confirms through its own path and leaves the next step to its caller. Rejected: a longer wait before typing the brief (still a guess at a start-up that grows with the hooks and shells), the brief on the resume line (only some agents take it there, and it would sit in the process's arguments, which `agents::mode_of` reads), any change of activity as the reaction, and reading the input box before each Enter (only Claude Code's box can be read, and it is fragile; it is read only for the give-up line). Not checked live: no real agent may run from a try; the evidence is the log and the transcripts (2026-11-14).
- **Closing and reopening a run** (#430, see Saved session): a workspace's agents closed with their orchestrator keep the run whole (the same id, messages, progress and folder) in `AgentRuntime::closed`, out of `App::runs`. Reopening reseats the members from their saved positions, gives each its saved conversation (a role closed earlier with its `×`, or one whose conversation cannot resume, starts fresh from `brief::member`, in a tab named after the role), and starts the orchestrator last. A resumed orchestrator gets `brief::reopened`: the new pane ids, the folder, who was cut in the middle of a turn and who starts over, and the same advice as after a restart (read what each last answered, then go on; answer `ok` if the plan was done). One with no conversation gets the full brief plus a short `## Where the run stands` note. A run whose orchestrator's agent exited by itself (#826) gets the same two forms from `brief::exited` and `brief::exited_stands`, which also say which roles exited too and were started again. `brief::restored`'s text is unchanged and shares the pane list and folder sentences with the new ones. The agents section's ` × ` on a member closes the team for good and the run ends (#438, see Layout › Agents section).
- **Context and compaction** (#444; `brief::CONTEXT_RULE`, `Known::compact`): a long run fills a role's context (the person saw the coder at 76 % after hours of follow-ups) and neither the orchestrator nor the person could act on it: the brief did not say `status --panes` has a `context` column, so the orchestrator looked only when asked and found the column with `awk`; right after its own `/compact` the value was empty and it read that as "not available"; and `send --enter '/compact …'` failed `not confirmed` while the compaction ran (see Confirming sends). So the brief has one rule: before a large piece of work, check `cornercase status --panes | cut -f 1,7,12,13,26,32` (pane, status, context, caller, role, compacted: the columns never move, since new ones only go at the end), and above about 70 % send the role its compact command first, with what it must keep when the command takes that (the branches, the checks to run, what is left), in the foreground with `--timeout 540` as any wait, then send the work; an empty context with `compacted` true is the compaction, not a missing figure; and the orchestrator cannot compact itself (a command typed into its own input box is no tool call), so past about 80 % it tells the person with `cornercase notify`, who can type `/compact` in its tab. The team line of each role ends with its agent's command (`compacts with `/compact` and what it must keep`, or `compacts with `/compress` alone`; nothing for an agent string cornercase does not know), from the agent's folder (`Known::compact`). `cut -f` rather than `awk '$1==N'` or the whole table: fixed columns keep the orchestrator's context small, and a dev server whose `PATH` has an older `cornercase` without the column gives an empty last field, so live checks put `target/debug` first on the `PATH`. Rejected: cornercase compacting at a threshold by itself (the orchestrator knows when a role is between tasks and what it must keep, and the orchestrator drives the work), a fresh role instead (loses what was never written down, such as how a tricky rebase was done; it stays the orchestrator's choice), and leaning on the agents' auto-compaction (it comes late, in the middle of a task, and keeps what the agent picks). Known limit: Claude Code's `DISABLE_COMPACT` turns `/compact` off, so the advice then fails visibly.
