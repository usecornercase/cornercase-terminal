# Browser access

Code: `web/`, `web/tailscale.rs`, `app/remote_access.rs`, `ui/remote_access.rs`

- **Why** (#178): agents keep working after you leave the computer, and what they need from you is short (a `!`, a `✓`, a look at who still works). From a phone that meant a mobile SSH app, Remote Login on the Mac (often locked on a managed laptop) and reconnecting by hand after every drop; `cornercase remote` cannot help, since it needs the binary on the device showing the window. So the server can serve itself to a browser, and a QR code opens it on a phone.
- **The browser is one more client.** `web/` listens on `127.0.0.1:remote_port` (`config::DEFAULT_PORT`, 47681) inside the server process, and each WebSocket (`web/bridge.rs`) connects to the server's own Unix socket and speaks the protocol a terminal client speaks, like `cornercase proxy` does: a `Hello` (the page's size and theme, `terminal=browser`, `Channel::Bell`, no image protocol), `ClientMessage::Event`s, frames back. So `Server` needed no change and the browser follows every rule the other clients do: the shared size is the last used client's (attaching counts), overlays and the toast are shared, `Hello`'s build check passes since the bridge is the same binary. Input arrives as the bytes xterm.js emits and goes through the terminal client's own parser (`client::input::Parser`), so keys, SGR mouse and bracketed paste decode exactly as from a terminal. The bridge writes the modes the terminal client sets itself (alternate screen, mouse, bracketed paste) before the first frame, since frames never carry them.
- **Only HTTP, WebSocket and a QR code are new** (`httparse`, `tungstenite`, `qrcode` without its image features): blocking, one thread per connection, at most 32, which fits the server's threads; `tiny_http` and `axum` were not needed (the latter would bring tokio). The page (`web/assets/`) is xterm.js 5.5 and its fit addon, vendored with their license (no CDN: the phone may load it on a slow link, and nothing from elsewhere runs next to the shells), and `app.js`, about 290 lines. The listener polls `accept` every 50 ms instead of blocking, so switching off joins its thread and frees the port at once (waking a blocked `accept` with a connection of its own left the port taken for a moment on macOS, and switching back on failed). Frames wait for the browser in a queue of 64 (`sync_channel`): when a slow phone fills it, the bridge stops reading the socket and the server's 1 s write timeout drops it like any stuck client, instead of the queue growing in the server's memory. The page's size is capped at 1000×500 cells, since the browser becomes the shared size.
- **For phones**, from trying ttyd with `tailscale serve` on an iPhone before writing this: `width=device-width` in the viewport (without it iOS lays the page out at ~980 px, the client attaches at ~124 columns and the phone gets the wide layout, cropped); a vertical swipe becomes wheel events at the finger's cell (xterm.js scrolls its own scrollback on a swipe, and the alternate screen has none, so scrolling a Claude Code conversation did nothing), a tap stays a click; the terminal takes the visual viewport's height (`visualViewport`, plus `interactive-widget=resizes-content` for Android), since iOS lays the keyboard over the page without resizing it and the cursor's row, an agent's input box at the bottom, went under it, so with the keyboard up the session gets fewer rows and the bottom row sits right above it; both sides send a ping every 15 s and give up after 45 s of silence (ttyd's 5 s ping dropped the link every 8-30 s on mobile data); a dropped link keeps the screen and reconnects on its own with the backoff of `cornercase remote` (1, 2, 4, 8, then every 15 s), and at once when the page comes back to the foreground. A link refused before it opened asks `/` why: a browser no longer paired (forgotten in Settings) or another account says so and stops retrying. A detach (` Quit ` on the phone) stops reconnecting until the notice's button is tapped. The page follows the phone's light or dark scheme and sends its colours in the hello, so the muted greys and tints work as with a terminal. Left for later: a row of the keys a phone lacks, a native field for long prompts, images (xterm.js's image addon) and notifications (the Notification API).
- **Authentication.** Loopback is reachable by every local user and process, and the port is published to the tailnet, so nothing but the static assets is served without pairing. Opening ` Remote ` makes a pairing token (16 random bytes from `/dev/urandom`, single use, 10 minutes, dropped as soon as the dialog closes, compared in constant time); `GET /pair?t=` exchanges it for a cookie (`HttpOnly`, `SameSite=Lax`, a year, `Secure` when it came through Tailscale) and redirects to `/`, so the token leaves the address bar. Paired browsers live in `browsers.json` next to `config.json` (`0600`, written like `secrets.json`), with only a SHA-256 of their secret, so the file alone opens nothing. `/` and `/ws` need the cookie; `/ws` also needs an `Origin` equal to the `Host` or `X-Forwarded-Host` it came with, against cross-site WebSocket hijacking. A request that came through a proxy (`X-Forwarded-For`, `X-Forwarded-Host` or `Tailscale-Headers-Info`, which `tailscale serve` adds) must carry `Tailscale-User-Login` naming the node's owner, from `tailscale status --json`, so another member of a shared tailnet cannot pair, and neither can a tagged device, which `serve` sends without a login; a local process could forge those headers, so they back the cookie up rather than replacing it. The cookie is scoped to the host, not the port (cookies have no port), so another web service on the same machine name would receive it; a Mac that is itself a tagged node has no owner login and every phone gets the other-account page. Both are in the guide. Settings › Remote lists how many browsers are paired; `Enter` there forgets them all and drops their connections. The log says when a browser pairs, connects and goes, and what was refused; never a token or a cookie.
- **Tailscale** (`web/tailscale.rs`): cornercase drives the CLI the user already has (`tailscale` on the `PATH`, else the macOS app's bundled binary), so it never holds a Tailscale credential. Switching `remote` on runs `tailscale status --json` (connected, the node's MagicDNS name, HTTPS certificates on for it, its owner's login) and then `tailscale serve --bg --yes --https=8443 http://127.0.0.1:<port>`; off runs `tailscale serve --https=8443 off`. Both go through one worker thread in the order they were asked for: on threads of their own, switching on and off quickly could run `off` before `serve --bg`, which survives reboots, and leave the port published with the setting off. A command that passes the limit is killed, not left behind. 8443 rather than 443, so a user's own `serve` on 443 is left alone; `--yes` and a closed stdin, since `serve` would otherwise wait on a prompt, and a 15 s limit. `--bg` survives reboots and points at a dead port while no server runs (the phone gets a 502 until cornercase starts). What is missing is said in Settings and in the dialog (not installed, not logged in, HTTPS certificates off for the tailnet with the admin console's address), and opening ` Remote ` tries again on the listener it already has. Embedding Tailscale was rejected for now: the libtailscale wrappers load a Go runtime and need Go to build, and tailscale-rs is a preview; the phone needs the Tailscale app either way. A public tunnel (Funnel, Cloudflare) was rejected: a public address to the shells.
- **UI**: `remote` in `config.json` (Settings › Remote, section Browser, off by default; `remote_port` has no row). While it is on, or a Telegram or Discord bot is set (see Telegram and Discord), ` Remote ` sits at the right of the ` Usage ` row (`ui::remote_button`, like ` ↑ x.y.z ` on the settings row), so no layout changes for anyone who uses neither; it is left out when the row has no room for both, as in the compact layout's thirds below about 51 columns (a phone showing the compact layout is usually the remote end already). It shows a green `●` while a browser is attached or you are away on a chat app. It opens a menu (`MenuAction::Browser`, `MenuAction::Away`, like ` + New `'s): **open in your phone's browser** and, per chat app, **continue on Telegram** / **stop messaging on Telegram** (the same for Discord); one that is not set up reads **set up …** and opens its row in Settings › Remote (`App::open_settings_on`). They live in one tab and behind one button because they answer the same need, using cornercase away from the computer: the browser to work there, a chat app to be told. The browser's dialog (`Overlay::Remote`, modal) draws the QR code in half blocks with fixed black and white (palette 16 and 231, never themed, so it scans on any theme), with four modules of quiet zone, as the QR standard asks, the address as text under it, and who the phone must be logged in as; a window too short for the code shows the address alone. The dialog closes when a browser pairs with its code, with a `a browser connected` toast.
