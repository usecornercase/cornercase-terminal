# Plan usage

Code: `agents/usage/`, `agents/{claude,codex}/usage.rs`, `app/usage_dialog.rs`, `control/usage.rs`, `app/control/usage.rs`, `cli/usage.rs`, `app/control/stats.rs` (the wait for machines)

- **usage** is an entry of ` More ▴ ` (see Layout › The footer; in the icon bar, of the gear's menu). It opens `Overlay::Usage` on Stats (see Stats); the Limits tab has the plan probes, and ` done `, `Esc` or `Enter` close it.
- One section per agent (`Known::ALL` entries with a `usage::Spec`: Claude Code, Codex), in that order (Cursor CLI has none either: its plan limits are not a command-line interface cornercase uses; opencode has none: it uses whichever providers the user set up, its own Zen and Go subscriptions among them, each billed apart, and cornercase asks none of them for usage; GitHub Copilot CLI has none either: its quota is behind `/usage` in its own TUI and an `account.getQuota` call of its API, and no command-line probe was checked, so it is left for an issue of its own; Grok Build has none either: `grok usage` accounts for one session and does not answer while that session is running, and cornercase does not read its credentials), each with its title and plan, its status on the right (`loading…` or `updated 2m ago`), its error under the title and its bars: thin `━` lines in the severity's colour on a track of the same line in the line colour. Only agents whose command (`agent_commands`, else the name) is an executable file, by path or on the server's `PATH` (`agents::installed`), get one; when neither is, both show, so each says why it could not run. A modal taller than the screen is cut at the bottom, the ` done ` row stays.
- Gemini CLI has no usage section. API-key sessions have no plan limits; Google-login `/stats` (`/usage`) calls Code Assist's `retrieveUserQuota` with OAuth. There is no usable CLI probe: headless `/stats` omits the non-text quota report, and ACP exposes sessions rather than account usage. Reading or refreshing Gemini's credentials ourselves is rejected for the same reason as Claude Code's. Use Gemini's own `/stats` instead.
- **Claude** (`agents/claude/usage.rs`): Claude Code's SDK control protocol: `claude -p --setting-sources '' --no-session-persistence --input-format stream-json --output-format stream-json --verbose`, then an `initialize` and a `get_usage` control request with `skip_behaviors: true` (below) on stdin; the `control_response` for `get_usage` holds `subscription_type`, `rate_limits_available` and `rate_limits` (`limits[]` with `kind`, `percent`, `severity`, `resets_at`, `scope.model.display_name`; `spend` for extra usage). No prompt, no tokens, 1–2 s. Claude handles OAuth (credentials file, Keychain, refresh), so cornercase never reads or refreshes a token; `GET /api/oauth/usage` was rejected for that (and refreshing the token ourselves can log Claude out). `--setting-sources ''` keeps the user's hooks from firing, `--no-session-persistence` keeps the probe out of the session list, `--bare` does not work (API key only).
- **`skip_behaviors`**: since 2.1.169 `get_usage` also answers `behaviors`, the "What's contributing to your limits usage?" part of `/usage`, which Claude Code builds by reading every transcript touched in the last seven days, on one thread. cornercase shows none of it, yet it was most of the probe: for an account with a busy week (some 270 MB of transcripts) the probe was several times slower with the scan than without it, and past `TIMEOUT` while other agents worked, so its section said `claude did not answer in time` (2.1.312, 2026-10-28). `skip_behaviors: true` (2.1.261 on, meant for "a usage meter") skips the scan and answers `behaviors` as `null`. Claude Code 2.1.169 to 2.1.260 ignore it: their `get_usage` schema is a plain zod object, which drops unknown keys, and their handler reads only `subtype` (read in the 2.1.260 binary, not run), so unlike Codex's option it needs no version check or retry. A longer timeout was rejected: the scan grows with the history, and its answer is thrown away.
- The protocol is not documented as a CLI interface, so parsing is lenient (unknown fields and kinds pass, a missing `limits[]` falls back to `five_hour` / `seven_day`, an unknown `severity` comes from the percentage), but `rate_limits_available` must be there, and `rate_limits` too when it is true, so a changed answer shows as unavailable instead of "no plan limits". Every failure shows `usage unavailable: <reason>`.
- **Codex** (`agents/codex/usage.rs`, checked live on 0.160.0 and 0.162.1; 0.153.4 only signed out): `codex app-server` (stdio JSON-RPC, lines without the `jsonrpc` field): `initialize` with `clientInfo`, the `initialized` notification, then `account/rateLimits/read` without `params` (#462): Codex 0.153 and older take none and refuse an option as `Invalid request: invalid type: map, expected unit`; the only one that would help, `excludeResetCreditDetails` (0.154.0 on), skips a reset-credit lookup that Codex otherwise runs beside the read, capped at 5 s and dropped silently on failure, so leaving it out cost nothing measurable (0.162.1, 2026-10-23). Retrying without the option after a refusal (the probe would have to write after reading, for both agents) and choosing by version (`codex --version` or the `initialize` user agent) were rejected for that. ~1 s, no Codex thread is created, no daemon starts (the stdio server is the probe's child and dies with it), no model call; Codex reads its own login from `CODEX_HOME`. The answer has `rateLimits` (`planType`, `primary` / `secondary` with `usedPercent`, `windowDurationMins`, `resetsAt` in Unix seconds, `credits`) and `rateLimitsByLimitId` (one per metered bucket, `codex` first, others suffixed with their `limitName` or id). Windows are named by their length, never by their slot: 300 minutes is `session (5h)`, 10080 is `week`. Unix-second resets need no date parsing. Not logged in answers the error `codex account authentication required to read rate limits`; it becomes `Report::notice` (a grey `not signed in · run codex login`, not a red error), so a Codex installed once and never used does not look broken. The rollouts' `token_count` events also carry `rate_limits`, but only as of the last turn (a window that reset since still shows its old percentage), so they were rejected.
- **The view is built in `app`** (#193): `usage` keeps the probes' state and reads it through `State::shown`, `Probe::last`/`loading`/`error` and `Known::title` and `usage::Spec::no_limits`; `app/usage_dialog.rs` turns them into `ui::UsageSection`s and `App::usage_view` builds the `ui::Usage` once, so `usage` imports no `ui`. The tests of the built sections live beside that code and reach the probe fixtures through `agents::claude::usage::tests` and `agents::codex::usage::tests`, `pub(crate)` under `cfg(test)`.
- **Per account** (#379): with agent accounts, every probe runs once per (agent, account), keyed `(Known, Option<String>)` in `usage::State` (`None` is the usual login), with the account's variable set and the variables a pane loses removed (`usage::probe`, from `AccountHome`, so no agent folder repeats it); without accounts the probes and their order are as before. See Accounts and profiles.
- `usage::Spec` holds the command builder, request producer, answer parser and no-limits text supplied by the agent folder. `usage::State` keeps one probe per `Known`, indexed by its position in `Known::ALL`; only entries with a spec are shown or run. `AppEvent::Usage` carries that same identity.
- On demand only: showing the Limits tab, or a `usage` request (below), starts one probe per shown agent on a thread (never two for one agent at once) that answers with `AppEvent::Usage(agent, result)`; nothing polls. The last answer per agent stays in memory (not in the session file) and shows with its age while a new one loads. Probes run on the server's machine with `agent_commands`, are killed after `agents::usage::TIMEOUT` (10 s; `usages.timeout` in tests); Claude's strips `agents::claude::CLAUDE_SESSION_ENV` like `Term::spawn` and inherits `CLAUDE_CONFIG_DIR`, Codex's inherits `CODEX_HOME`.
- Reset times are relative (`resets in 2h 13m`, `3d 4h`): local time would need a time zone database, and the server may sit in another zone than the client anyway. The `usage` request gives them as UTC (`resets_at`) for the client to show in its own zone.
- **Through the server** (#341, `control/usage.rs`, `app/control/usage.rs`, `cli/usage.rs`; `cornercase usage [--cached] [--json]`): the probes ran only for the dialog, so another UI or a script could not know how much of a plan was left before starting more agents. The `usage` request answers what the Limits tab shows.
  - **Which agents**: the tab's own list (`App::usage_agents`: the installed agents with a `usage::Spec`, in `Known::ALL` order, or all of them when none is installed, each saying why it could not run), shared with the tab so the two cannot disagree. `Report::notice_for` is the other shared rule: the Codex sign-in notice or the spec's `no_limits` text. Other agents have no probe (see above).
  - **Fresh** (the default) starts the probes the tab would start, through the same `State::start`, so a probe already running (from the dialog or another request) is waited for, never started twice, with the tab's timeout. The request is a pending `Stage::Usage` that holds, per agent, how many answers its probe had when the request came (`Probe::answers`, counted for success and error) and answers once every count has moved. Waiting for "no probe loading" instead would starve an earlier request for as long as clients keep sending fresh ones faster than probes end. There is no request timeout: each probe is bounded by `usages.timeout`, and `spawn_job` always answers. A client that leaves drops its request; its probes go on and fill the cache.
  - **Cached** (`cached: true`) answers at once from the stored state for the same agents, starts nothing and leaves the tab's `shown` list alone. Nothing polls: a program that wants fresh numbers asks again, one that wants cheap ones asks `cached`.
  - **The answer** is `{"agents": [...]}`, every key present and `null` when it has no value: `agent`, `title`, `loading`, `read_at` (UTC; worked out as now minus the probe's age, so it agrees with `age` and the state is not touched), `age`, `plan`, `limited` (`Option<bool>`: a plain `false` would claim no limits before anything was read), `limits`, `extra`, `notice`, `error`. After a failed probe the numbers are from the answer before it, as old as `age` says, as in the tab. A limit has `label` (the tab's text), `kind` (the agent's own name: Claude Code's list item `kind`, with the `five_hour` and `seven_day` fallback fields mapped to `session` and `weekly_all` so `kind` is stable across versions; Codex's slot, `primary` or `secondary`), `scope` (Claude Code's model display name, Codex's non-default bucket name or id, `null` for the whole plan), `percent`, `severity` (a string, `normal`, `warning` or `critical`, so a client reads it leniently) and `resets_at`. `kind` and `scope` together name a limit from one answer to the next; `label` is what to show. Extra usage and credits stay text: the two agents' shapes differ.
  - **No feature**: `usage` is a new operation name (`Command::NAMES` has 68), which an older server refuses by name and `contract` lists. It takes no view. It is not in `status` or `watch`: the limits are read on demand and a field in a snapshot would suggest they move by themselves.
  - **The CLI** needs a server, since the probes and their cache live there (`stats` can read a file; this cannot). Text follows the tab (header with the plan and `loading…` or `updated …`, the error as `usage unavailable: …`, the limits with relative resets, the notice, the extra line, `not asked yet` when nothing was read), and the command exits 3 after printing everything when any agent has an error (a partial answer, see Commands for scripts and agents), as `issue list` does.
  - **Rejected**: probing without a server, an agent filter, polling, events when a probe ends, a structured money object, and a `usage` field in `status` or `watch`.
- **An account's identity** (#547, `usage::fingerprint`, `Report::identity`, `PlanInfo::identity`): to list an account seen on two machines once, a client must know that both machines report the same provider account, and no probe said which account it read. The rule is the issue's: with no reliable identity, rows never merge, since two equal rows are better than one summed wrongly.
  - **A fingerprint, never the data**: sha256 of the agent's name and the account's parts, a NUL before each so that a part cannot slide into the next, cut to 16 bytes, in hex. It is opaque, not anonymous: never shown, never logged, and only it crosses the socket, but whoever knows an email and an organization can check a guess against it. No salt is possible, since every machine must reach the same text with nothing shared beforehand. The probe's reader (`Heard`, kept between the answer's lines) holds the fingerprint, not the parts, so an email lives in memory only while it is hashed and cannot reach a `Debug`.
  - **Claude Code**: the email and the organization of the `initialize` answer's `account`, only when both are there and `apiProvider` is `firstParty` (read in the 2.1.316 binary: `account` has `email`, `organization`, `subscriptionType`, `tokenSource`, `apiKeySource` and `apiProvider`). An API key, Bedrock, Vertex or a gateway gives none, and so does a version whose `initialize` has no `account`, without an error. `organization` is a name, not an id: the same email in two organizations of the same name would merge, which is accepted as unlikely.
  - **Codex gives none** for now: `account/rateLimits/read` has an `accountId`, but it is the ChatGPT workspace's, which every member of a Team, Business or Enterprise plan shares, so it alone would merge two people. Its email (`account/read`) could not be checked against a real Codex (none was installed), so it was left out rather than trusted. Add it once `account/read` is checked live.
  - **The socket never merges**: each `PlanInfo` carries `identity` when it has one (left out otherwise, so an answer without it is the same as before), and the client that shows several machines merges by it (the Usage dialog, see Stats).
- **Another machine's limits** (#547): `usage` takes `machine`, a machine's name or `all` (see Commands for scripts and agents › Every machine's stats and usage; asking a machine is Remote windows › Asking a machine).
  - **A name** answers that machine's `agents` as its own server gave them (its `agent_commands`, accounts, labels and identities), plus `machine` (`name`, `state`, `seen`, `read_at`, `error`). Its `read_at` is when this server read the answer; each agent keeps its own `read_at` and `age` from there.
  - **`all`** answers this computer's `agents`, then `machines[]` in `config.json`'s order, each with the same keys and its `agents`. This computer's probes and the machines are asked at once, and the request answers when all of them ended.
  - **Fresh** asks the machine, whose server runs its own probes with its own timeout; **cached** answers this server's last copy of each machine's answer and asks nothing, as it does for the probes here. A machine that is down answers its last copy with why it is down, and with none `failed`, naming the machine and why.
  - **The CLI** (`cornercase usage --machine NAME|all`) puts a line per machine above its agents (its state's mark, its name, `read 4 min ago` or its error) and exits 3 when a machine or any agent, here or there, has an error, or a machine has no `read_at` (never read, for example under `--cached`). A link that turns out to be this computer counts as one.
