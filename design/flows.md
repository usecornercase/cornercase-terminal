# Flows

Code: `flows/`, `app/flow_runs.rs`, `app/flow_panel.rs`, `app/flows_dialog.rs`, `app/start_flow_dialog.rs`, `app/control/flow.rs`, `app/control/flow/`, `control/flow.rs`, `cli/flow.rs`, `ui/flow.rs`, `ui/flow/`, `ui/dialog/flows.rs`, `ui/dialog/start_flow.rs`, #263

- **Why**: a team of agents (one coding, others reviewing, testing, auditing, one orchestrating) already worked through the commands for scripts (`start`, `send --enter`, `wait --any --until turn-over`, `read --last-message`), and much of cornercase was built that way, but every run was set up by hand: each agent with the right CLI, model and mode, a long brief for the orchestrator with the pane ids and the rules learned the hard way, and no way to keep a team that worked. Nothing showed how the work moved between them either. A **flow** is a saved team and the plan it follows; starting one opens the team in a new worktree with an orchestrator that runs the plan, and the **Flow** panel draws the plan and lights it up as the work moves.
- **The orchestrator is an agent**, not a workflow engine: it reads what the others answer and decides what comes next, and cornercase never parses a verdict out of an agent's text. A deterministic pipeline was rejected: it only fits straight flows, and a loop ("back to the coder while the reviewer finds problems") needs judgement.
- **The model** (`flows/mod.rs`): `Flow { name, description, notes, end, orchestrator, roles, stages }`; a `Stage` holds one role or several in parallel and may go back (`Back { to, when, at_most }`, `to` counted from 1, `when` the loop's label); `End` is a pull request or the commits. Structured so it can be drawn before anything runs: free text alone was the first idea, and nothing could be drawn from it. `Flow::problems` gives sentences, shared by the editor, the start dialog and the commands (names, the agents `flows::takes` (which `config` gives a client as `flows`, see Commands for scripts and agents › Reading and changing settings), roles in stages, loops only to earlier stages, `env` keys, and the rules below). **A role works in one stage**: progress and the diagram resolve a role to its stage, so `coder → reviewer → coder` could never reach its third stage; a loop is how a role works again, and occurrences of a role were rejected. Files are TOML (long prompts read well in a repository): yours in `flows/` next to `config.json`, the project's in `.cornercase/flows/`, the built-ins compiled in. A file is named after its flow's slug and renamed with it, one that cannot be read is listed with its reason rather than dropped, and a newer `version` is refused. **The slug is cut at 209 bytes** (#764, `store::MAX_SLUG`), at the last whole character and without a trailing `-`, so that the longest name a save makes (the slug, `-1000` from `MAX_COPIES`, and `.toml`) is `persist::MAX_NAME` and still leaves room within the 255-byte file-name limit for the temporary name it is written through (see Saved session › Writing a file). Uncut, a slug past about 237 bytes (some 80 CJK characters) could not be saved once that temporary name took a pid and a counter (#761), and one past 246 bytes never could. The name itself lives in the file and is never cut. Two names that share the cut slug take `-2` and on, as two names of one slug always did. A file saved under a longer slug before still loads, and moves to the cut name when it is next saved. Bytes, not characters: a CJK character takes three, and a name within 255 bytes is also within NTFS's 255 UTF-16 units. Rejected: a hash of the name in the file name (unreadable, and the numbering already keeps colliding names apart), and a shorter temporary name (its pid and counter are what keep two writers apart).
- **Live check** (Claude Code 2.1.300 and Codex on a scratch repository, a dev server on a private socket): Quick ran in about 70 s, and a strict reviewer took a loop to its limit, where the orchestrator stopped and listed what was left. It found the background waits, the seven notices and the silent end above. Two restarts brought both runs back with each member on its role's flags, and the orchestrators already marked for review were left alone. A dev server's agents reach it through the socket a debug build gives its panes (Client / server); a `CORNERCASE_SOCKET` set by hand must be absolute, since panes inherit it and a relative one starts a second server.
- **Tests**: the model, files, built-ins (every set of installed agents), brief, progress and editor are unit tests; the diagram is `insta` snapshots from 30 to 100 columns, plan and live, with hits and hover checked by cell; app tests drive whole runs with a fake `claude` that asks the trust question and logs its arguments and prompt (restore, refusals, cleanup, a project closing while git works); the dialogs' pages are snapshots; the site's tests play the simulated run.
