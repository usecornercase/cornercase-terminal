# Telegram

Code: `telegram/`, `messenger/`, `app/messenger.rs`, `app/messenger/`

- **Why**: once you leave the desk, what agents need from you is short (an answer, a look at what one wrote), and you want to be told rather than to check. Browser access (#178) shows the whole window, but needs Tailscale and a screen to read it on; a chat is pushed to you, works on mobile data, and a reply is one line. **WhatsApp was rejected**: its Cloud API needs a Meta business account, a number of its own, a public webhook (the public address Browser access rejected), a 24-hour window and paid replies, and the unofficial linked-device libraries break its terms and can get the user's own number banned.
- **One bot per user, long polling**: the user makes a bot with @BotFather and pastes its token; the server asks Telegram for updates (`getUpdates`, 30 s) and sends with the Bot API, all over outgoing HTTPS. No webhook (a public address to the server) and no relay run by cornercase (every message would go through it).
- **The model** (`telegram/mod.rs`): `Bot` makes the calls through `http::post_within`, which leaves the statuses to Telegram's own rules: 401 or 404 (a malformed token) is a refused token, 409 another program reading the bot, 429 its `retry_after`. The token is scrubbed from every error, since ureq can quote the URL that holds it. `Order` (in `messenger/`, like the rest of this list) is what the app sends, `Update` what it reads (messages and button presses), `Tap` the button data (`<run>:<verb>:<ids>`, at most 64 bytes, with a random nonce per server run: pane ids restart with the server, so an older button is refused as stale rather than pressing keys in another pane), `choices` the numbered options at the bottom of a screen (read upwards until `1.`, so a numbered list in the conversation above is not taken), `Saved` the bot's name and the paired chat. `html.rs` turns an agent's Markdown into the HTML Telegram takes (bold, italics, code, `pre`, http links only, lists as bullets; the agent's own HTML is escaped), in messages of at most 4000 UTF-16 units (Telegram allows 4096 after entities), at most four, the rest left in cornercase; a block too long is cut by lines, keeping code in `pre`. A title goes in front of the first one only when the two fit in 4096 (`html::fits`), else on its own, and a screen under a title gets the room the title leaves (`html::room`); places in titles are cut at 120 characters. Two threads run per bot: the poller (`telegram/link.rs`, backoff from 1 to 60 s, messages older than a minute before it started dropped, so a reply sent while the server was down does not land in a pane that now has another id) and the sender (`messenger/link.rs`), in order, waiting out `retry_after` (at most 60 s, three tries), sending again as plain text when Telegram cannot parse the entities, and answering each sent message's id (`Sent`) so replies can be routed. A link has an id and its answers are dropped once it is replaced; dropping it stops the poller after its current poll.
- **Telegram is an internal client of the commands**: `App::run_request` (split out of `request`) takes a parsed `Request`, and Telegram sends `send`, `keys`, `start` and `last-message` with client ids from `1 << 62`; `answer` hands those to `chat_answered`. So a reply gets every refusal and the confirmation `send --enter` has, and `server.log` shows Telegram's actions as the commands they are. Calling the app's methods directly was rejected: the refusals and the confirmation would have to be repeated.
- **Pairing**: the phone row opens the Remote dialog (`ui::RemoteAccess` got a title) with a QR of `https://t.me/<bot>?start=<token>`, the token from `web::auth::Pairing` (single use, ten minutes, compared in constant time, dropped when the dialog closes). A `/start <token>` from a private chat pairs that chat and user; groups cannot. `telegram.json` (0600, next to `config.json`) keeps the bot's name and the chat, `secrets.json` the token (`telegram_bot_token`). Only that chat and user are heard; anything else is ignored and logged by chat id. A new bot forgets the chat, and pairing again replaces it.
- **In the app feed** (#338): `away` has one row per platform (`ready`, `away`) in `status --app`.
- **Away changes only by hand** (the user's choice, over always on, which is noise at the desk, and on after idle minutes, which guesses): **More › remote… › continue on Telegram** and **stop messaging on Telegram**, `o` in the keys menu (**away on chat apps**: back on every platform that is away, else away on every ready one; with none ready it opens the first bot row in Settings), `cornercase away [--off]` (an `away` request answering `{"away": bool}`), `/away` and `/back`. Nothing turns it off by itself: a first version ended it on any use of a window, which also ended it when you only looked at a phone's browser, and stopped the messages without telling. Forgetting to turn it off costs some messages at the desk; the `●` on ` More ▴ ` shows it is on. Away is refused while Telegram refuses the token (the link stopped), so it never looks on while nothing reaches the chat; the menu and `o` then lead to the bot's row. The bot says when it starts and ends. Not saved: a server restart turns it off. Toasts and desktop notifications are unchanged.
- **When to message**: while away and paired, an agent's state (`agents::activity::Pane::state`) has to hold for a second (`SETTLE`). Turning to waiting sends `! claude needs you · project › workspace`, the last 15 lines of its screen and a button per option found, plus `esc` and `screen`. A turn that ends (idle, done, failed, or a background shell) after the agent was busy (working or waiting at any read since its last settled state) sends `✓ claude finished` and its last message from its record, or its screen when there is none. An explicit OSC `done` also sends a finished notice without an observed working sample, including for a visible tab, whose UI mark is already acknowledged; Telegram reads `Pane::reported_done` rather than losing that signal to `Pane::state`. Reported `idle` cancels a turn without a finished notice. A reported failure also sends `! claude failed`, even without an observed working sample. Busy is remembered rather than compared with the settled state, so a turn shorter than the second still counts. This is not the desktop notifications' rule: a seen tab never notifies there, but away, a visible tab, or a view's, proves nothing. The watch runs whenever a phone is paired, so turning away on does not report an old change.
- **Replies**: a reply to the bot's message goes to the pane that message was about (message ids kept in memory, at most 256, filled from `Sent`); one that replies to nothing goes to the only agent, else the bot asks which, with a button per agent holding the text (at most 16 held). Before `send`, an agent that is waiting gets its buttons again (a text would answer its question), Claude Code's survey a button for `0`, a dialog `screen` and `esc`. A 👍 reaction says the agent took the text; a refusal comes back as a reply. A digit pressed on a question removes that message's buttons, so an answer is not pressed twice. **The next question** (#248): an agent can stay `waiting` from one question to the next (Claude Code's `AskUserQuestion` with several questions, a permission prompt right after another one, when the turn between them is shorter than `SETTLE`), so no change of state says a new one is on screen, and the bot sent only the first. Each watch keeps the question it last sent (`notices::question`: the excerpt the notice shows, with `messenger::MARKS` trimmed from each row, so moving the selection is not a new question; `None` when the screen has no numbered options). A pane that is still waiting is looked at again only when input reached it since that notice (`Term::input_at`, from a button, a reply or the window), it printed after that input and since it was last looked at (so a screen drawn before the input is never taken for its answer), and it has been quiet for `SETTLE`; a question that differs is sent like the first. So a redraw of the same question sends nothing, a screen that keeps changing sends nothing until it settles, and there is at most one new notice per input. The choices alone were rejected as the key: two permission prompts in a row offer the same options. A next question whose excerpt is identical to the one sent (the same 15 lines) is not sent again: it cannot be told from the same question left on screen after an answer the agent ignored, and the screen above a new question (the previous tool result) almost always differs. Watching the screen without the input condition was rejected too: anything the agent redraws while it waits would become a message. A question without numbered options (free text) gets no second notice, since nothing on its screen tells it apart from other output.
- **Commands**: `/status` lists the agents in sidebar order with the tabs' icons, model and context, and per agent buttons to write to it (a forced reply), show its last 40 lines, or press `esc` (at most 25 agents, models cut at 40 characters, in as many messages as the limit needs with the buttons on the last, `html::lines`). `/new` asks in turn for the project, the workspace or a new worktree (only in a repository root) and its branch, the agent when the default is `auto` (installed ones only), and the prompt, then sends `start` without focus, so the window stays where it is. `control::Start` got `project`, used with `worktree` so the worktree is made in the project chosen, not the one shown; the command line does not set it. Topics in private chats (Bot API 9.3 and later) were left out: they need a setting in @BotFather and one regression was reported for them; replies work everywhere.
- **Never logged**: texts and the token. The log says what kind of message or button came in and its size (`message kind=reply bytes=14`, `button tap=keys`). Chats with bots are not end-to-end encrypted, so Telegram keeps what agents write; the guide says so.
- **Settings** (Remote page, section Telegram, under the browser's section, then section Discord with the same two rows, `settings::Row::Bot(Via)` and `Row::Chat(Via)`): `bot` (a masked token field checked with `getMe` on a job; `Backspace` removes it) and `phone`, once a bot is set (`Enter` pairs, `Backspace` forgets). `Settings::removal` replaced `removable` and returns the action, for tokens and these two rows.
- **Simulation**: the landing's has neither Tailscale nor a chat app: its Remote tab shows the Browser, Telegram and Discord sections, and their rows, like its `o`, say they need a real cornercase.
- **Shared with other chat bots** (#265): a Discord bot is to do what this one does, and both can be paired at once, so what does not depend on Telegram moved out of it before a second platform exists. `messenger/` holds the orders, updates, buttons (`Tap`), choices, the paired chat (`Saved`, one file per platform, `telegram.json` unchanged) and `Via`, one identity per platform whose exhaustive arms call into the platform's folder, as `agents::Known` does for agents: its name and log target, token key, file, API, pairing link and code, the size of a button's data, and its `Markup`. `Markup` is the formatting the app writes with (escape, bold, a screen in `pre`, an agent's Markdown, lists), which each platform renders and splits by its own limits; `telegram::html::Html` keeps the HTML and the 4096 above. A link starts from two halves: the platform's listener (Telegram's poller) and a `Transport` that performs one order and says what a failure means (`Next`: wait, try again, or done), which the shared sender loops on with three tries; the transport keeps its state across the tries of one order (`Transport::Attempt`), so Telegram's plain-text fallback, once taken, holds across a `retry_after` wait, as before the move, and its `message is not modified` stays in its `Transport`. Each link event comes with its `Via`. Discord's forum mode (#437, see Discord) added orders to the same `Order` under neutral names (`Post` a new post with its first message, `Retag` its tag) and link events (`Posted` with the new thread's id, `Failed` for a tagged order that failed, `Gone` for an order whose thread was deleted, `DirectOnly`), rather than a second order type: the sender, its retries and the tags that route replies stay shared. `Transport::posted` and `Transport::gone` default to nothing, and Telegram performs none of the forum orders (no call, no event): it has no forum mode, and its topics were left out (see Commands). The app keeps one `Messenger` per `Via` (`App::messengers`), each with its own link, routes, watches, drafts and away, and every method of `app/messenger.rs` and `app/messenger/` takes the `Via` it answers for; request client ids get a range per platform (`CLIENTS_PER_VIA`), so `chat_answered` finds the one that asked. `cornercase away` turns away on for every paired platform, succeeds when at least one went away (the others' refusals are dropped; the first is answered only when none could) and `--off` turns it off for all; its answer names the platforms now away (with `--off`, the ones it turned off) as `platforms`, which the command prints (`away: agents message you on Telegram until you turn it off`, or `back: nothing was away` when `--off` found none), and an older server's answer without them can only be Telegram's, so it is printed as `Telegram`; the `o` key, turning several platforms on at once, toasts the ones that went away and why the others did not in one line; the Remote menu has an entry per platform. That move changed nothing a user sees; Discord (below) then added its rows in Settings, and `o` and the help texts now speak of every platform.
- **Tests**: `app::tests::control_requests::telegram` drives the app with captured orders (`Link::capture`), updates made by the test and the fake Claude Code (`Agent`, moved up to `control_requests` to be shared); `telegram::link` runs the threads against `FakeHttp`; `messenger::tests` keeps the buttons, choices and the saved chat. Checked live with the real binary against a local fake Bot API (pairing, away, notices, replies, buttons, `/new` with a worktree), not against Telegram itself.
