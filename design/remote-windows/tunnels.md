# Remote windows › Tunnelling a port

Code: `remote/tunnel.rs`, `remote/tunnels.rs`, `client/window/tunnels.rs`, `client/window/tunnels/kept.rs`, `protocol.rs` (`Holding`, `TunnelOrder`), `server/windows.rs`, `app/tunnels.rs`, `app/ports_dialog.rs`, `ui/dialog/ports.rs`, `control/tunnels.rs`, `app/control/tunnels.rs`, `cli/tunnels.rs`, `cli/tunnels/hold.rs`, `cli/tunnels/orders.rs`, `app/machines.rs`, `ui/chrome.rs`, `test_util/program.rs` (#735, #766, #776, #786, #794).

## Why

A dev server in a pane of the machine a remote window reached listens on that machine's loopback, so the browser of the window's computer cannot open it. The Ports dialog's ` open ` used to copy the URL there. A tunnel forwards that port to the computer of the window, with the user's own `ssh`, so their keys, agent and `ProxyJump` apply and cornercase handles no credential.

## The ssh line

One process per tunnel, started by the window and never by the server:

`ssh -N -T -o ServerAliveInterval=5 -o ServerAliveCountMax=3 -o ConnectTimeout=10 -o BatchMode=yes -o ExitOnForwardFailure=yes -o ControlPath=none -L 127.0.0.1:LOCAL:localhost:PORT -- DESTINATION`

- `-N`: nothing runs on the machine, so no shell and no `sh -c`, and the line is the same on every OS (`ssh.exe` on Windows).
- `--` before the destination, as in the links, so a destination can never be read as an option. The destination is the one the window used.
- `BatchMode=yes` because a prompt would read the terminal the window holds in raw mode; `ExitOnForwardFailure=yes` so a taken local port ends ssh at once with its own message instead of a half-open tunnel.
- **`ControlPath=none`** is the one change to the issue's line. With the user's `ControlMaster auto` (which the docs recommend for `remote`), an `ssh -N -L` becomes a client of the master, which holds the forward: the listener is then not our process, killing ours does not close it, it outlives the window by `ControlPersist`, and "ssh's pid listens" cannot say it is up. A tunnel therefore makes its own connection (one more handshake); keys, agent and `ProxyJump` still apply. Rejected: `-O forward` through the master (our own `ControlMaster` handling) and accepting the orphans.
- The far end is always `localhost` of the machine. The server sends only a port number, never a command, a host or a URL, so a server cannot make the laptop reach anything but the loopback of the machine it is attached to. It does choose which of the laptop's loopback ports are probed: each `Open` connects to `127.0.0.1` and `[::1]` on that port to see whether it is free, and the `local` port reported back tells the server whether something listens there. A server can therefore map the laptop's loopback services one port at a time (each `Open` also starts an ssh, bounded by the cap of 32 running); accepted as the cost of "same port when free".
- A `LocalForward`, `RemoteForward` or `DynamicForward` for that host in the user's ssh config makes every tunnel fail with `ExitOnForwardFailure` (the window's own connection already holds that forward, and `ClearAllForwardings`, which the links use, would clear ours too). A documented limit; the toast shows ssh's own line.

## Same port or another

LOCAL is PORT when nothing there is on it, else the last port used for it, else one the OS hands out (`local_port`). "Taken" is either of: a connect to `127.0.0.1` or `[::1]` answers within 200 ms, or `127.0.0.1` cannot be bound. A bind alone is not enough: std sets `SO_REUSEADDR` on Unix, so on macOS a bind of `127.0.0.1:p` succeeds while a program listens on `*:p`, and ssh (also `SO_REUSEADDR`) would then take that program's IPv4 traffic, and `http://localhost:PORT` would open the wrong thing. The connect probe can appear in a local service's log; accepted.

## Up means ssh's pid listens

The tunnel is up once the pid of its own ssh listens on `127.0.0.1:LOCAL` (`ports::listen::listeners`, every 100 ms, on Linux, macOS and Windows). Rejected: a probe connection (each opens a channel on the machine, and an unused port fills stderr with `open failed`), and parsing `ssh -v` (brittle across versions and `ssh.exe`). After 30 s without it, ssh is stopped and the tunnel is down with the reason. ssh's last stderr line is the reason when it ends first (`remote::Stderr`).

## Retries and endings

- ssh ends before it was up: down, with the reason, not retried by itself (the same thing would happen again).
- ssh ends after it was up: retried with `remote::backoff` while the window is linked.
- Every link of the window (a reconnect, or a switch back) starts the tunnels that are down again, and brings back the remembered ones (below).
- Switching to another machine, or to this one, stops them all (`Tunnels::sync`) and then brings back what is remembered for the new destination; `Drop` of the handle stops ssh, so the window ending does too, while the memory stays. At most 32 tunnels per window, since a server can make the laptop start processes.
- A window killed with `SIGKILL` leaves its ssh until the connection drops. Linux's `PR_SET_PDEATHSIG` was left out: macOS has no equivalent and it would split the behaviour per OS.

## The protocol

`ClientMessage::Tunnels(Holding)` (index 9) carries the window's whole list, `browse` (whether it can open its default app) and each tunnel's port, local port and state (`Opening`, `Up`, `Down(reason)`, `Closed`); `ServerMessage::Tunnel(TunnelOrder)` (index 10) carries `Open(port)`, `Close(port)` or `Forget(port)`. `Closed` and `Forget` were appended last (#766), all are last in their enums, `VERSION` is 13, and an older peer reads them as `InvalidData` (`protocol/tests.rs`). A remote window sends its list after every link, order and change; a local window and the browser never send it, and the server drops a browser's. The proxy copies the bytes, so it needed no change. Orders go to windows only, never to the connections of commands.

The window opens a browser only for a port it tunnels: `Browse` for any other port, or for a LAN address, is refused with `port N is not tunnelled to this computer`, mapped to its local port otherwise. A remote window still sends no openers in `Hello`, so a server on the other machine never offers it ` open ` for the paths of its files.

## The server's side

`App` keeps each window's last report (`Holders`), with how many it sent, and which tunnels were asked by a click or by a request (`Origin`). The screen is drawn once for every client, so the dialog shows the tunnels of the window in use (`opening.machines.client`, the window that sent input last), as the openers do. A click orders its own window; `tunnel-open` orders every attached window (holds, below, are not windows: they get no orders and `windows` counts only windows, so `tunnel-open` with only a hold is still `unavailable`; a program that takes orders is counted in `takers`, below); a close or a forget orders every holder that lists the port, since the tunnel belongs to the destination, not to a window. A hold's "order" is the end of its stream.

## The dialog and the toasts

In the Ports dialog of a remote window, a program listening on every address, `127.0.0.1` or `::1` gets ` tunnel ` (not tunnelled), or ` close tunnel ` and the mark `⇄ …` (opening) or `⇄ :LOCAL` (up), with ` open ` (the window can browse) and ` copy ` of `http://localhost:LOCAL`. A LAN-only listener gets none: the far end is always `localhost`. A local window's dialog is unchanged.

A click that comes up says `port 5173 is tunnelled to localhost:5174 (5173 is taken here)` with ` open `; a request that comes up says `a program tunnelled port 5173 to localhost:5174` with ` close `; a failure always shows `could not tunnel port 5173: <ssh's line>`, so a tunnel that cannot come up is never silent. A tunnel that drops after it was up shows nothing: it is retried, and `cornercase tunnels` shows it down meanwhile.

## Requests

`tunnels`, `tunnel-open`, `tunnel-close`, `tunnel-forget`, `tunnel-hold`, `tunnel-orders` and `tunnel-failed` (see Commands for scripts and agents › Tunnels). `tunnel-open` answers once every window asked reported (the window reports after every order, changed or not, so the request never waits for a change that will not come), within 45 s (the window's 30 s plus connection slack); a close or a forget within 10 s (a close answers once the window reports the tunnel `closed`, a forget once it is no longer listed). `status`'s `tunnels` (left out when empty, so the v1 fixtures keep their bytes) and the `tunnel` event ride the traced step of the report, so `watch` and `status --follow` send a new snapshot.

## Remembered per destination

- **`tunnels.json`**, beside `machines.json` in the window's state folder (`paths::tunnels`): `{"vps":[{"port":5173,"local":5174,"pid":4242},{"port":3000,"local":3000,"closed":true}]}`. Compact, private (0o600) and written with `persist::write`; `closed` is left out when false, `local` and `pid` when unknown. It is per destination and per computer: it belongs to the window, not to the server (the server's machine does not know it).
- It is reread whole before every write and written only when something changed, with no lock, as `machines.json` is (`remote/tunnels.rs`). Each entry is parsed on its own, so a broken one, port 0 or a repeated port is skipped without losing the others; at most 64 per destination, sorted by port. Healing is the same as for `machines.json`: a lost write is repaired by the next write of that entry, and a link never removes a held port that the file lacks. A window that was not attached when another forgot a tunnel writes it back at its next own spawn; accepted, as for `machines.json`.
- **Close keeps the entry, forget removes it.** Close stops the ssh and leaves `closed: true` (state `Closed`, still listed by `tunnels`, `status` and the events); opening it again clears the flag. Forget stops it and removes the entry (an `Open` after that starts from nothing). The window brings back, at every link and switch, the entries that are not closed, on their remembered local port when it is free (`local_port`'s `before`). Rejected: removing on close (the issue wants the dev server's tunnels to come back, and closing one is not forgetting it).
- **The pid is written as soon as ssh is spawned**, not when it is up: a claim. Other windows then see a live process with the same forward that does not listen yet and wait (`Opening`) instead of starting a second ssh, which narrows the race that having no lock leaves.
- Forgetting a machine (`forget…`, `remote --forget`) leaves its tunnels in the file; they come back if the machine is reached again. Not built: it would need `Window::order(Forget)` and `cli/known.rs` to call a `forget_destination`.

## Shared by the windows of one computer

- Each entry's **owner** is the pid it records (`tunnel::owner`): it counts only when it is a live process (`process::running`) whose arguments hold the consecutive pair `-L 127.0.0.1:LOCAL:localhost:PORT` and end with `-- DESTINATION` (`process::args`: `/proc`, `KERN_PROCARGS2`, the PEB on Windows). The line is not compared whole, so options or a program in front still match (the e2e forwarder). `Listening` (it listens on LOCAL) is `Up`; `Starting` is `Opening`; `Gone` (dead, another program, another forward, or no `args` on this system) means the window opens its own, as before.
- A window whose entry has an owner other than itself starts no ssh: it shows the tunnel `Up` or `Opening` with the recorded local port and looks at that pid again every second (`CHECK_EVERY`). When it is gone the window **takes the tunnel over**: it rereads the entry (forgotten: the port is dropped; closed: it stays `Closed`; another window's new pid already listening: it watches that one) and otherwise starts its own ssh on the same local port and rewrites the pid, within about a second of noticing. The issue asked for 5 s.
- Ports held elsewhere cost no process, so they do not count toward the cap of 32. A tunnel closed or forgotten in the window in use is ordered in every holder (the server's close/forget orders all that list the port), so the window that runs the ssh stops it.
- **Converging after the fact, with no lock.** `tunnel open` orders every attached window in the same flush, so two windows of one computer usually both read the file before either claims, and both spawn. Both claims are written at spawn, long before either ssh is up, so when each comes up it reads the entry again (`converge`): if it names another pid that listens for the same destination, the window drops its own ssh and follows that one (`elsewhere`); otherwise it writes its claim again. Both read the same last claimer, so one ssh is left. A window whose ssh ends before it was up while the entry still holds its own pid (it lost the bind, and its claim was the last write) stays `Opening` and looks again after a second (`settling`), when the winner has rewritten the entry, instead of going down. A window that comes up in the instant between another's read and write can still leave two; accepted. Two windows noticing a dead owner within the same second can do the same.
- A tunnel adopted from an owner that listens counts as having been up (`was_up`), so a take-over that fails before it comes up is retried with `remote::backoff` like a tunnel of the window's own.
- `run_window` runs `tick` after an event when a timer is due (`wait` is zero): `tick` only ran when `recv_timeout` timed out, so a busy screen could starve tunnel retries and this take-over.

## The machine button and menu

- The button reads `vps ⇄2 ▴` while the window in use holds tunnels that are not closed (opening, up or down: what it tries to hold); with none it is as it was. The name is cut at its end, never the count: a row too narrow for one letter, `…`, the count and the mark falls back to the form without the count, and is left out only below the old minimum (8 cells). `View.machine_tunnels` and `ui::machine_button`'s third argument carry it.
- The machine menu lists the window in use's tunnels after its last row (`⇄ 5173 → localhost:5174  up`, `⇄ 3000  closed`, by port); holds are never listed there. A click opens a submenu at the same place, as `forget…` does: `open in browser` (up, and only when the window can browse), `close` (up, opening, down), `open` (down, closed) and `forget` (all). Each is `MachineItem::Tunnel(port)` and `TunnelDo(port, verb)`: a port is stable, so no index is kept. Close and forget go to every holder and toast (`closed the tunnel of port N`, `forgot the tunnel of port N`); open orders the window in use as the Ports dialog does.
- The Ports dialog shows ` tunnel ` again for a closed tunnel, like a down one.

## Holding a tunnel without a window

`cornercase --remote vps tunnel hold PORT` is for a UI with no window of its own (a Tauri or GPUI app, a script): it holds a tunnel for as long as it runs.

- It runs on the computer that should listen, starts its own `ssh -N -L` (`remote::tunnel::spawn`, the same line) and waits until it is up, then prints one compact JSON line, `{"port":5173,"local":5174,"url":"http://localhost:5174"}`, and registers with the `tunnel-hold` request. The request is the stream: the server lists the connection as a holder of kind `hold` (`kind` is `window` or `hold` in `tunnels --json` and the events, always written in the list, only `hold` in events), and `tunnel close` or `tunnel forget` ends its stream with `Detached`. The check of the server's feature (`tunnel-hold`, from the contract) shares the ssh connection with the request.
- The order matters: the line is printed after the server answered `tunnel-hold`, so a program that read it knows the server counts the hold, and a `tunnel open` it answers is settled; `--remote` is required (exit 2 without it, and inside a line of `cornercase requests`, which keeps no connection of its own).
- Exit codes: 0 when killed (SIGTERM, SIGINT, SIGHUP; Ctrl+C or Ctrl+Break on Windows, through `on_end_signal`), when its stdout reader leaves (not noticed on Windows, as with every follow), when it is closed or forgotten, or when the server stops or restarts (the stream's end); 1 when ssh fails before or after it was up (it is not retried: the program that holds it decides), or the server connection is lost; 2 for wrong usage.
- It reads and writes no `tunnels.json`: the program decides what to remember, and a hold killed with `SIGKILL` must not come back in a window. Its local port comes from `local_port(port, --local)`: `--local N` (#786) is what `before` is for a window, the port to take when PORT is taken here and any free one when N is taken too; a program passes the port its hold had because it remembers its holds, and cornercase still writes nothing. Without it, the port may differ from a window's for the same port. The request connection's ssh ends with the process, so the server forgets the hold even after `SIGKILL`; the tunnel's own ssh is left, the same limit as a window's.
- A hold never gets a `TunnelOrder`: `end_tunnel` branches on the kind. The server counts it in the list but not in `windows`.
- A hold whose ssh fails before the server registered it (`local_port`, `spawn`, or ssh ending before it is up or before the registration) sends `tunnel-failed {port, error}` with ssh's raw reason, best effort, over the link the feature check left when `local_port`, `spawn` or ssh fails before it is up, and over a new connection (a new `--remote` ssh) once the registration thread took that link; the answer is ignored since an older server refuses the name. So running `tunnel hold PORT` is a whole answer to an order. Nothing is reported after the registration, or on exit 0.

## Taking orders without a window

#776: a program that holds its tunnels with `tunnel hold` could not be asked for one by a script on the machine: `tunnel-open` orders windows only, and `windows` counts windows only, so with only holds attached `tunnel open` was refused `unavailable`.

- **Shape.** `cornercase --remote vps tunnel orders` sends the stream request `tunnel-orders`. The server counts the connection in `takers` (beside `windows`, in every tunnel answer; a server from before leaves it out, which reads as 0), answers with the whole `TunnelList` counting it, and then writes one line per order, `{"order":"open"|"close"|"forget","port":N}`, through the events queue (`Streamed::Event`), the way `config-pair` streams. The line is built in `app/tunnels.rs` from `TunnelOrder::id`, since `control/` imports nothing from `protocol`. The postcard protocol does not change: `ServerMessage::Tunnel` stays for windows, which a command connection cannot read.
- **Answering.** The program answers an `open` with what it already does: `tunnel hold PORT`, whose registration settles the request, or `tunnel failed PORT REASON` (the request `tunnel-failed`), which fails it with `could not tunnel port P: REASON`. It keeps deciding what to remember, as holds do. A program that already holds the port can ignore the order.
- **Settling an open.** The windows' part is as before. The programs' part settles when no program was asked, when the port is held for the request (an asked window lists it `up`, or, when programs were asked, any hold lists it: a hold listed before the ask counts, because the question is whether the port is held; with no program asked a hold never counts, so a window that could not open is still reported), or when as many failures were reported as the asked programs still attached. A window that comes up settles the programs' part, so a silent program never turns a window's success into a timeout. The words of an unanswered request say who was asked: `no window answered`, `no program answered`, `no window or program answered`, and the timeout names the same.
- **Failure reports** go to the requests waiting at that moment for that port and not to later ones, are cut to one line of 300 characters like a window's, and are logged by size, never by text (ssh's line can name the host). A report is not tied to the program that sent it: with several programs, or a `tunnel hold` of the same port failing elsewhere, a request may fail while another program still comes up; that tunnel is then held and listed all the same. One program per server is the case served; attributing reports would need ids passed between processes.
- **Close and forget** are told to every program and answer `not-found` only when no holder lists the port and no program is attached: the server cannot know what a program holds or remembers, and this is what lets `tunnel forget` reach a port it remembers as closed. Programs are not waited for; their holds are separate connections and already in the wait. The holders still end as before.
- **One role per connection.** A connection that holds a tunnel cannot take orders, nor the reverse, nor take them twice (`conflict`). A program that leaves, even by `SIGKILL` (its `--remote` connection closes), stops being counted, and an open that waited only for it fails with `no program answered`; with no window and no program attached, `tunnel open` is `unavailable` again and its message names `tunnel orders`.
- **No toast, no event, no `status` key.** The toast belongs to the asking window and the program shows its own UI; a taker holds no tunnel; `takers` is in every tunnel answer. A program that attaches late hears no backlog of opens that were pending before.
- **Rejected.** Polling `tunnels` or the `tunnel` event: the ask is refused before anything is listed or sent, and counting `events` readers as answerers would make every `tunnel open` wait 45 s on any logger. `tunnel hold` with no PORT: a hold that holds nothing, which would change the one-line output and mix two roles in `end_tunnel`. Counting programs in `windows`: that changes what an existing key means. Answering on the orders process's stdin: shell scripts would need a coprocess and a failing `tunnel hold` would have to be relayed, while a one-shot request works from any process. `--json` and a text mode as the issue sketched: it prints JSON only, like `tunnel hold`, because a person running it would be counted and make every `tunnel open` wait.
- **CLI.** `tunnel orders` needs `--remote` (exit 2), is refused inside `requests`, checks the feature `tunnel-orders` first, prints the first line too (a program learns it is counted, as `tunnel hold` prints its line), exits 0 when its reader leaves or the server stops or restarts and 1 when the connection is lost. It has no signal handler: killing it closes the connection, so the server forgets it. `tunnel failed` needs no `--remote` and checks no feature: a program reports only after `tunnel orders` checked. `CONTRACT` stays 1 (see the contract topic of Commands for scripts and agents).

## A reverse tunnel

#794: `tunnel hold --reverse LOCAL [--there PORT]` makes port LOCAL of the computer that runs it (the client's) reachable on the machine's loopback, so an agent on a linked machine can reach, say, a headless Chrome's DevTools port on the client. A program used to run its own `ssh -N -R`, which cornercase did not list, could not close and did not end with the link or the server. It is a hold like the forward one (own ssh, own connection, nothing remembered, ends with it), in the other direction.

- **The ssh line** is `-N -T` with the forward's options and `-o LogLevel=… -R 127.0.0.1:THERE:localhost:LOCAL -- DESTINATION` (`remote::tunnel::reverse_args`, sharing its helper with `args`). The far end is `localhost:LOCAL`, as a forward's far end is the machine's `localhost`: a service on `::1` only is reached too.
- **`--there` defaults to port 0: the machine's sshd picks** and ssh reports it (`Allocated port P for remote forward to localhost:LOCAL`, at INFO). Rejected: LOCAL itself with a fallback to a free port. A fixed port's success is reported only at debug level, so it would need debug output on the common path and a second ssh whenever LOCAL is taken there; port 0 never collides and needs one attempt. It would also put the client's service at its well-known number (9222 is the first one scanners try) on a machine others may share. The program learns the port from the hold's line and passes the `url` on.
- **`--there PORT` is strict**: exactly PORT, or exit 1 at once with ssh's `remote port forwarding failed for listen port PORT` (`ExitOnForwardFailure`). A program asks for the port it had before to keep its agent's URL and decides itself what to do when it is taken, as it decides what to remember (#766). This differs on purpose from `--local N`, whose issue asked for a fallback: a fallback here would silently move the agent's URL and cost a second ssh.
- **Up is ssh's own report.** The listener is the machine's sshd, not our child, so "ssh's pid listens" cannot say it. With port 0 the `Allocated port` line says it (the line passes `LogLevel=INFO`, which wins over `~/.ssh/config` because ssh keeps the first value it reads, so a quiet config cannot hide it). With `--there PORT` ssh says it only at debug level (`debug1: remote forward success for: listen 127.0.0.1:PORT, connect localhost:LOCAL`), so that line passes `LogLevel=DEBUG1`. The collector drops `debug…` lines and the reporting line, so ssh's reasons stay what a plain run prints. This is a deliberate exception to "parsing `ssh -v`" being rejected: a fixed remote port has no other signal. The debug wording is an internal message: if OpenSSH rewords it, a `--there` hold gives up after 30 s with `ssh did not report the forward to localhost:LOCAL within 30 s`, and the default keeps working. Both wordings were read in openssh-portable `master` on 2026-11-13 (`ssh.c`, `ssh_confirm_remote_forward`). Rejected: a probe connection from the machine (it connects through to the client's service and an unused port fills ssh's stderr with `connect_to … failed`), `-f` (it forks away from our pid and Windows' ssh has no fork), a second sentinel `-R 0` (one more open port), the server checking its own listeners (a new request, it races with a program holding the port, and port 0 still needs the line), `-O forward` (no ControlMaster on Windows).
- **It listens on `127.0.0.1` of the machine only**: an explicit bind address, never empty, `*`, `0.0.0.0` or `localhost`, and nothing that turns `GatewayPorts` on. sshd accepts it under `GatewayPorts no` and `clientspecified`. The `url` is `http://127.0.0.1:P`, since `localhost` there may try `::1` first. Still exposed, and documented: every program and user of the machine can connect to its loopback for as long as the hold runs, and a browser's DevTools port gives whoever connects that browser and its logins; with `GatewayPorts yes` in the machine's `sshd_config` sshd listens on every address whatever cornercase asks, which the client hears only in a server debug message and cornercase does not detect.
- **A tunnel is named by (direction, machine port).** The registry (`Holders.by`) is still keyed by connection; every lookup by port in `app/tunnels.rs` is scoped by direction (`Kind::goes`), and `Kind::held` maps a direction to the holder kind, so the request handler never picks one. A reverse hold is a third holder kind, `Kind::ReverseHold`, still `kind: "hold"` in JSON, with `direction: "reverse"` beside it (a new optional field of `TunnelInfo`, of the `tunnel` events, of `tunnel-hold` and of the hold's line; absent means forward, so every v1 fixture keeps its bytes and `CONTRACT` stays 1). A machine port can equal a forward tunnel's, so: `tunnel close|forget PORT` never end a reverse hold and `tunnel close|forget --reverse PORT` never end a forward tunnel (`end_tunnel` takes the direction); a reverse hold never settles a `tunnel open` (`held_by_a_hold` counts `Hold` only) and never sends `tunnel-failed`; port-scoped answers list only their direction. Forget equals close for a reverse hold, which remembers nothing; `--reverse` on both exists for symmetry, and `not-found` comes when no reverse hold lists the port whether or not programs take orders.
- **Windows and takers.** Reverse closes and forgets are not told to programs that take orders (their lines carry only a port: they would drop a forward tunnel of it). `tunnel open` cannot ask for a reverse tunnel (`malformed`, no `--reverse` on `open`): a link that opened one by itself would expose a port of the client without the client asking. Windows hold no reverse tunnels, so `protocol.rs`, `client/window/`, the Ports dialog, the machine button and `tunnels.json` are untouched, and a reverse hold counts in no `windows` and makes no toast.
- **The feature `tunnel-reverse`.** `--reverse` on `hold`, `close` and `forget` checks it before sending: the CLI speaks the legacy mode, where an older server silently drops `direction` and would hold, or close, a forward tunnel of that port. Readers need no check: an older server lists no reverse tunnel.
- **Limits.** Killed with `SIGKILL` it leaves its `ssh` (and so the machine's listener) until the connection drops, as a forward hold does. A `RemoteForward` for that host in the user's ssh config is requested too and can fail the hold. Checked only through the fake `ssh`, never against a live OpenSSH.
