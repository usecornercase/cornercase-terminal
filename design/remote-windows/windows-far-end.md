# Remote windows › A Windows machine at the other end

Part of [Remote windows](../remote-windows.md).

Code: `remote/shell.rs` (the probe and the lines for cmd and PowerShell), `remote/known.rs` (the shell remembered per destination), `remote/attempts.rs` (the order of the tries, unit-tested with a scripted far end), `process/handles.rs` (`hand_down_nothing`), #603

- **Why**: Windows' OpenSSH Server (Win32-OpenSSH) runs a command with its `DefaultShell` (`HKLM\SOFTWARE\OpenSSH`): `cmd.exe /c "<command>"` unless an administrator set it, often to `powershell.exe -c <command>` or `pwsh`. Neither has `sh`, and cmd reads no single quotes, so sh's line failed there with status 1 (see Windows › Beyond this machine).
- **sh's line first, a probe only after a failure**: the line for `sh` goes first, unchanged, so a Linux or macOS machine costs nothing more when it works. Only when it ends without the banner, and with a status that is not ssh's 255, sh's 127 (or 126 and `No such file`), 0, or clap's `unrecognized subcommand` (`Failed::maybe_another_shell`), cornercase sends one probe, `echo cornercase-shell-"x"-$true-$env:OS`, and reads its line: cmd keeps quotes and knows no `$` (`cornercase-shell-"x"-$true-$env:OS`), PowerShell on Windows joins the quoted word and expands `$true` and `$env:OS` (`cornercase-shell-x-True-Windows_NT`, Windows PowerShell 5.1 and pwsh alike), sh joins it and expands unset variables (`cornercase-shell-x--:OS`). `$env:OS` is there because PowerShell is not Windows: a Linux or macOS user whose login shell is pwsh prints `cornercase-shell-x-True-`, which counts as sh, as does any other line with the prefix; sh's line works under pwsh, which only turns a native 127 into 1 (that 1 is what makes such a machine probe at all), whereas taking pwsh for Windows sent the Windows line, which never looked in `~/.local/bin`. The message of a failure is no help (cmd's and PowerShell's are translated: here cmd says `"sh" no se reconoce como un comando interno o externo`), and the probe holds nothing but `echo`, so a shell that reads it otherwise runs nothing else. A probe that prints no marked line but whose ssh did not fail (a status other than 255: fish drops a word whose variable is unset, csh refuses an undefined variable, zsh may read `:O` as a modifier) answers sh too, since cmd and PowerShell always print it; one whose ssh failed answers nothing (`remote::answered`). An answer of sh, or none, keeps the first failure, so the probe never makes cornercase run another command than the one it tried; an answer of cmd or PowerShell sends the line for that shell.
- **A Windows path as `--command` asks first** (`shell::windows_program`: a drive, `\\`, `~\`): on a machine not yet known, sh's line would paste it raw, and cmd would split a path holding `&` before any probe and run the rest; so the probe goes first, and an answer of sh still tries sh's line as before.
- **Remembered per destination** (`remote/known.rs`): cmd or PowerShell is written to `remote-shells.json` beside `session.json` in the client's state folder (`$XDG_STATE_HOME/cornercase` or `~/.local/state/cornercase`, `%LOCALAPPDATA%\cornercase` on Windows, beside the socket with `CORNERCASE_SOCKET`, a debug build's own folder), so later commands and a window's reconnects take one connection again; sh is what cornercase tries anyway and is never written, so for a Linux or macOS machine the file is only read, once per process. Deleting the file, or its destination's entry, forgets the answer. A name can come to mean another machine (an alias moved, an address reused, a dual boot, `DefaultShell` set to bash), so a remembered shell is asked about again after any failure without the banner but ssh's own 255, 127 and 126 included, and the answer replaces it: under `sh`, cmd's line exits 127 (`set` takes the quoted word as a positional parameter and the `( … || exit 127)` group runs, checked in bash and dash) and PowerShell's 127 too, or clap's 2 for the stray `}` it hands a cornercase on sh's own `PATH`; cmd's line under Windows PowerShell 5.1 is a parse error at `&&`; PowerShell's under cmd runs nothing, since cmd looks for a program named `'C:\…'` with its quotes. The probe's own answer is never asked again in the same command. The file is read again before each write, so two commands that learned two machines keep both.
- **The cost**: the first connection to a Windows machine takes three sessions (sh's line, the probe, the right line), and three password prompts for a password login. A Linux or macOS machine pays nothing when the connection works; when sh's line fails without the banner in a way cmd or PowerShell could explain (status 1, a pwsh login shell's 127), the probe follows the failure, one more session and possibly one more password prompt. A process command (`update`, `restart`, `kill-server`, `logs`) has its stderr inherited, so the far shell's `'sh' is not recognized` shows first; holding it back would change how those commands print everywhere. For them the probe follows only status 1 (any failure but 255 for a remembered shell), what cmd and PowerShell give for a missing `sh`. Only `logs`, which changes nothing, is then run again through the right shell; `update`, `restart` and `kill-server` are not, and say `` `winbox` runs commands with cmd.exe, which cornercase uses from now on: run the command again… ``, since status 1 does not prove nothing ran: with an `sh` on the Windows machine's `PATH` (Git's `usr\bin`, MSYS2, Cygwin, a busybox) sh's line runs the command itself, and its own 1 (no server, a question answered no, `--when-idle --timeout` reached) would have run it twice. Rejected: a marker that sh's script prints before `exec`, which would change the line Linux and macOS get.
- Rejected: probing first (a round trip more on every Linux or macOS connection); one line that sh, cmd and PowerShell all read (their quoting differs, and cmd would still find no `sh`); a `--shell` flag (the user seldom knows sshd's `DefaultShell`, which an administrator can change); sshd's `RemoteCommand` or a subsystem (configuration only an administrator can change); cmd's line running `powershell -Command` to have one language (about half a second more on every connection, and two quoting layers).
- **cmd's line** (`shell::cmd_line`): `set "PATH=%PATH:"=%;%USERPROFILE%\.local\bin;%USERPROFILE%\.cargo\bin" && [set "CORNERCASE_TIED=1" && ]("%SystemRoot%\System32\where.exe" /q "<program>" || exit 127) && "<program>" <words>`. `%PATH:"=%` drops the quotes of the `PATH` it extends: a quoted entry (legal in a `PATH`) flips cmd's quote state inside `set "…"`, so an `&` in it ran the rest of the entry as commands (checked with `"C:\R&echo INJECTED&rem D Tools\bin"`). The program is always quoted, in `where` too, since cmd cuts an unquoted program name at `=` and `,` (checked: `C:\tools\a=b\cornercase.exe` ran `C:\tools\a`); its arguments are passed whole, so they stay bare when they can. The folders are where the PowerShell installer puts cornercase (`install-path`, which it also adds to the user's `Path`; Win32-OpenSSH builds a session's `PATH` from the machine's and the user's in the registry, so it is usually there already) and `cargo install`'s. `where` comes first because cmd ends with status 1, not its own 9009, when it finds no program, and with 1 too for a path that is not there (`The system cannot find the path specified`), so a missing cornercase looked like any failure; `where /q "<folder>\:<file>"` looks in that folder with `PATHEXT` as cmd does (checked: a folder, `%SystemRoot%:`, a drive's root, a name without `.exe`; a folder of that name is not a match). An `if errorlevel` after the program was rejected: a false `if` sets the status to 0 (checked), and `call exit %^ERRORLEVEL%` works only through a caret trick. The line never starts with a quote, which `/c` would strip together with the line's last one. A word is bare when it holds only letters, digits and `-_./\:,+=@`, else double-quoted with the backslashes before the closing quote doubled for the C runtime; `&|<>^()` are plain inside quotes, while `"`, `%` and `!` (with `DelayedExpansion` set in the registry) are read even there, so a word or `--command` holding one is refused (`Error::WrongUsage`, saying which character), as is a control character.
- **PowerShell's line** (`shell::powershell_line`): `$env:PATH = $env:PATH + ';' + $env:USERPROFILE + '\.local\bin' + …; [$env:CORNERCASE_TIED = '1';] try { & '<program>' '<word>' … } catch [System.Management.Automation.CommandNotFoundException] { exit 127 } catch { [Console]::Error.WriteLine($_); exit 126 }; exit $LASTEXITCODE`. `-Command` ends with 1 whenever its last command failed and drops a native program's own status, so `exit $LASTEXITCODE` passes it on (3, `Partial`, came through), and a missing program, a terminating error caught there, exits 127 as sh does. Any other error starting it (a file that is no program, a program AppLocker or Defender blocks, a broken download) left `$LASTEXITCODE` empty, and `exit` then gave 0, so `kill-server` said it had worked and a window kept reconnecting; the second `catch` says why on stderr and exits 126, as sh does for a program it cannot run. An empty `--command` is refused for both shells. Words are single-quoted (`agents::powershell_quoted`, typographic quotes doubled too), and what Windows PowerShell 5.1 hands a program in pieces is refused as in an agent's line (`agents::splits`, `--%`), with an empty word (5.1 drops it) and two spaces in a row: in a terminal session (`ssh -t`, `update`'s question) Win32-OpenSSH appends the command to `powershell -c` unquoted, so it is split at spaces and PowerShell joins the words with one. The line holds no `"`, so Win32-OpenSSH's quoting of it (`"` as `\"`, backslashes doubled only before a quote, not at the end, read in its `build_commandline_string`) has nothing to get wrong. Under both shells 127 reads as `RemoteMissing`, as sh's does, so its texts did not change.
- **`--command` there is a path**, or a name, not shell text: which shell runs it depends on sshd, a path means the same to both, and quoting it is what lets the line tell a missing program apart. `~\` or `~/` at its start stands for `%USERPROFILE%` (`$env:USERPROFILE`), and `/` becomes `\`. sh's line still reads it as sh does, so the first try on a machine not yet known is the same as before.
- **Bytes pass through both shells**: cmd only starts the program on the session's pipes, and Windows PowerShell 5.1 does not redirect a native command whose output it does not capture, inside `try` too; 00, FF, CR LF and 80 came back unchanged through both (checked with a program that copies its input to its output).
- **The proxy keeps its handles from the server** (`process::handles::hand_down_nothing`, Windows only, called first in `remote::proxy`): in the check below, the window through PowerShell never noticed its killed `ssh.exe`, while the one through cmd did, and it did once the proxy kept every handle from what it starts. So Windows PowerShell hands a native program inheritable handles besides its three standard ones, a second copy of the session's pipes among them, and the server the proxy started inherited that copy, since `spawn_detached` clears only the three standard handles (Windows › The server in the background), and held the pipe open (the handles were not listed one by one). With a real sshd the local `ssh` would still end, but the session there would linger on the pipe the server holds. Now the proxy clears the inherit flag of every handle it has, from the snapshot `NtQueryInformationProcess` gives (the one the context line reads, `process/handles.rs`), before it can start a server, which gets its log and `NUL` only. In the proxy and not in `spawn_detached`: clearing every handle of a process while another thread starts a child (the test binary does, and std makes that child's handles inheritable only around its `CreateProcess`) could leave the child without its standard handles, and the proxy starts nothing else and runs no other thread by then. Rejected: `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` (std's `raw_attribute` is unstable, and a `CreateProcessW` of our own gives up std's `Child`).
- **The session there**, read in Win32-OpenSSH's source (`contrib/win32/win32compat`, branch `latestw_all`, on 2026-11-04): sshd, running as SYSTEM (its default), loads the user's profile (`LoadUserProfileW`) and starts the session with `CreateEnvironmentBlock` for the user's token, so `USERPROFILE`, `APPDATA` and `LOCALAPPDATA` are the user's and `paths` finds the socket a window at that desktop uses; without `LOCALAPPDATA` it takes `%USERPROFILE%\AppData\Local`, the same folder unless it was redirected (checked with the stand-in below). The shell runs in a job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE | JOB_OBJECT_LIMIT_BREAKAWAY_OK`, whose handle it holds last, so what is left in it ends with the session; the server starts with `CREATE_BREAKAWAY_FROM_JOB` (Windows › The server in the background), and leaving a job that allows it leaves the jobs above it that allow it too (Microsoft's Nested Jobs), so the server outlives the session and nothing needed changing. A key logon is an S4U network logon, a password one `LOGON32_LOGON_NETWORK_CLEARTEXT`; an administrator's session is elevated, by design (Win32-OpenSSH #1652), so a server started through ssh runs its shells and agents elevated, and a window at that desktop still attaches to it (the peer check reads the user's SID, which a process that is not elevated can read from an elevated one, see Windows › The local socket), which UAC, in Microsoft's terms not a security boundary, does not stop. A server started at the desktop first stays as it was for both.
- **Not covered**: `restart --when-idle`'s tie reaches the command (`CORNERCASE_TIED`, tested through both shells), but Windows cornercase does not watch its input yet (`client::watched` answers `None` there), so killing the command here leaves the wait there, as before #537. A key logon has no network credentials and no DPAPI key, so Credential Manager (where `gh` and Git Credential Manager keep tokens) may not work in the panes of a server started through ssh (not checked). A machine whose `DefaultShell` is bash (Git's or WSL's) counts as a POSIX one, as before.
- **Checked live** (2026-11-04, Windows 11 10.0.26200, Windows PowerShell 5.1.26100, a debug build): there is no sshd here (installing OpenSSH Server needs an administrator), so a stand-in `ssh.exe` skipped the options and the destination, joined the rest as ssh does, put itself in a job with `KILL_ON_JOB_CLOSE | BREAKAWAY_OK`, gave the shell only its standard handles (as Win32-OpenSSH's `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` does), a session's `PATH` (the machine's and the user's from the registry, with no `sh.exe` in it), `HOME` and `SSH_CONNECTION`, with and without `LOCALAPPDATA`, and started `cmd.exe /c "<command>"` or `powershell.exe -c <command>` quoted as Win32-OpenSSH does. Through each shell: the first command (`logs --path`) took sh's line, the probe and the right line, three sessions, and wrote the answer; then one session per command: `start-server`, `status` with the same `boot` as a local `status`, `new-tab`, `send` and `keys` into a pane there and `read` here showing it, `logs --path`, `open` with a `C:\…` path (and `\Windows` refused), `kill-server`; the server outlived every session's job, with no stand-in, shell or proxy left; a missing `--command` path gave `RemoteMissing` for a request and for `kill-server`, and a `%` in it was refused for cmd; a wrong remembered shell was asked again (three sessions) and replaced. The window, in a ConPTY read with vt100, through each shell: attached after those three sessions, ran a typed line there, showed Connection lost when its `ssh.exe` was killed, attached again through one session with the remembered shell, the same pane still held its variable, and ` More ▴ ` › `quit` ended it with status 0. After a review the same day (the `$env:OS` in the probe, re-asking a remembered shell, no rerun of `update`, `restart` and `kill-server`, `%PATH:"=%`, the quoted program, PowerShell's second `catch`, a Windows `--command` asking first), the commands were checked again through each shell with the stand-in: a `--command` path probed first (two sessions), a wrong remembered shell made `logs --path` probe, rerun through the right shell and replace the answer, a remembered shell's 127 was asked about once and still read as `RemoteMissing`, and the rest as above. The tests of `remote::shell` run both lines through the real `cmd.exe` and `powershell.exe` on Windows (plain and as a terminal session runs them): found in `.local\bin`, words with `& | < > ^ ( ) '` and spaces arriving whole, status 3 passed on, a missing program 127, `~\`, the tie. Not checked: a real sshd, so neither its environment, job and handle list nor a PowerShell session's profile (sshd passes no `-NoProfile`; what a profile prints before the banner is skipped like an rc file's), PowerShell 7 (`pwsh`, not installed here) as `DefaultShell`, a password login, a Linux or macOS client reaching a Windows machine (its ssh passes the status in 8 bits, which 1 and 127 keep), a real elevated session.
