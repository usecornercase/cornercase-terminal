# Remote windows › Switching machines from the window

Code: `remote/machines.rs`, `client/window/switch.rs`, `cli/known.rs`, `client/window.rs`, `client.rs` (`Target`, `Guard`), `app/machines.rs`, `ui/chrome.rs` (`machine_button`), `ui/activity.rs`, `ui/remote.rs`, `server.rs`, `server/windows.rs`, `protocol.rs`

- **Why**: `cornercase remote devbox` tied a window to one machine for its whole life; going to another machine, or back to this one, meant quitting and typing another command, though the shells and agents of each machine keep running anyway, so there is nothing to tear down. The window now changes the server it is attached to without closing.
- **Where the list lives**: on the window's machine, `machines.json` in its state folder beside `remote-shells.json`: every destination a window reached (`cornercase remote X` or a switch) or a program added with `cornercase remote --remember` (#751, below), with its `--command`, in the order first reached or added, so the menu never reshuffles, the last `--command` winning. It is written only when it changes, so a reconnect writes nothing unless a program changed the entry meanwhile; when read, each entry is parsed alone and one that is broken or not a valid destination is skipped, so an edit by hand never loses the others. Each change rereads the file just before writing it, as `remote-shells.json` does, with no lock: two windows writing in the same instant can lose one entry, which that window writes again on its next link (every link remembers its machine). A window's list is a snapshot of the file at its last link or forget: a machine another window or a program added or forgot shows up in its menu once it links again, and picking a destination forgotten meanwhile asks first, as any unknown one does. A write by `--remember` or `--forget` keeps only the entries `read` accepts, as a link's does. The server cannot hold it: while the window is on devbox, devbox's server draws the sidebar and knows nothing of the laptop's ssh. So the window sends it in `Hello.machines` (`here`, the destination it is on or none for this machine, and `known`), the proxy forwards it as it is (unlike the openers, which it empties: a list of names gives the other machine nothing to act on), and `ClientMessage::Machines` sends it again after a forget. The browser bridge sends none, and a browser's is dropped, so it never gets the button. Rejected: the hosts of `~/.ssh/config` (most entries, GitHub or a bastion, have no cornercase, and `Host *` names nothing) and a `config.json` key (while on devbox it would be devbox's config).
- **The button** sits on **a row of its own under the Worktrees row** (`ui::machine_button`, `Areas::machine`, `Screen::machine`; the name cut at its end, its ` ▴` kept), labelled with where the window is (`devbox ▴`, `this machine ▴`). It had the second column of the Worktrees row at first (#657), which ` Recap ` (#656) took: the row is shown only while the window knows another machine or is on one (`App::machine_label`), so a window with one machine has exactly the rows it had (see Layout › The footer): side by side the projects column gets one more footer row and the workspaces column a blank one, so the lines of both columns stay level; stacked and tree add a row to the footer; compact mode adds a band to the projects menu. With the icon bar it is a slot over Help (codicon `remote`, VS Code's remote indicator), named on hover, dropped before Help on a short bar. Someone who never ran `cornercase remote` sees nothing new until the first machine comes: from `cornercase remote`, which also lets ssh ask for an unknown host key, or from a program's `--remember`, whose first connection is a switch with `BatchMode`, so a host ssh does not know fails in the notice until `cornercase remote <host>` runs once in a terminal. A projects column under about 8 cells leaves it out. Rejected: the second column of the Worktrees row (Recap lives there, and a narrow column would lose one of the two) and an entry of ` More ▴ ` (where the window is would not show).
- **The menu** (`MenuAction::Machine`): `this machine`, the known machines (the one the window is on marked `✓`, and listed even once forgotten), **add machine…** (`Overlay::NewMachine`, one field checked by `machines::valid`: one word, no whitespace or control character, not starting with `-`, at most 255 bytes) and **forget…** (a submenu of the known ones). As for the openers, the server keeps each window's machines per `Client` and tells `App` whose input it handles (`App::set_machines`, beside `set_window`, also on `Hello` and, when a window leaves, for the most recently used one left), so the button and the menu follow the last window used (a `Machines` message from a window used less recently changes its own record but not what shows), and a menu built for one window and clicked in another acts for the clicker. The menu keeps the names it listed and its entries name them by index, since `MenuAction` is `Copy`.
- **The order** (`ServerMessage::Machine`, the last variant, index 9, and `ClientMessage::Machines`, index 8; `protocol::VERSION` 11, which `cornercase remote` does not feel since its window needs the same release anyway): `Switch(None)` for this machine, `Switch(Some(destination))` or `Forget(destination)`, queued as `(client, order)` and sent to that window only, never to a browser, as `Open` is. New `ServerMessage` variants go to windows only (see Commands on another machine), so commands never meet it. `server.log` says an order was sent and how many machines a window knows, never their names.
- **The window decides** (`client/window/switch.rs`, `chosen`): an order is a request. The window acts only on `this machine` or a valid destination, ignores the machine it is on, and **asks first, in a notice it draws itself, before reaching a destination it never reached** (`Step::Asking`, ` connect ` and ` back `, `Enter` and `Esc`): a remote server can draw anything, a form included, and only the window's own notice is out of its reach, since no input goes to the server while it shows. Without it, a server on another machine could make the laptop run ssh, with its keys and agent, to any host. A known machine is reached at once (`Step::Connecting`), unless a program added it and no window reached it yet (`unreached`, see Writing the list from a program): that one is asked like an unknown one, with its `--command`, and loses the mark at its first link. This machine is refused, in the notice and with `Error::Nested`'s words, to a window that runs inside one of its panes (`CORNERCASE` set, as `cornercase remote` from a pane): `cornercase` refuses to open there for the same reason, a window drawn inside itself.
- **Switching**: the connection runs on a thread (`Incoming::Switched`, numbered, so a late answer after ` back ` is dropped and its `Link` with it, which kills its ssh) through `Target::connect`, the reconnect's path, so the banner, the version rule, the Windows shells and `--command` are the same, always with `BatchMode`: the terminal is in raw mode and a password prompt would read it. A banner that has not come within 30 s stops that ssh (`remote::watched`, for every attempt with `BatchMode`: reconnects and commands too, never the first connection of `cornercase remote`, where ssh may be waiting for a password), so a thread left behind by ` back ` ends within 30 s and repeated tries cannot pile up. **The switch is made only once the new server accepted the window**: a banner proves the proxy runs, not that its server takes this build, so the new link is pending (`Pending`, with an id of its own from the same counter as the links, so no stale message is ever taken for another link's) while it sends `Hello`; its first message decides (`answer`): `Rejected` (a server of another build), an unreadable message or the link's end fails the switch in the notice, its reason or ssh's last line shown, anything else commits it. ` back ` drops a pending link at once, closing its socket or killing its ssh, and no answer within 30 s fails the switch. **The old link stays attached until the new one answers**: its frames are dropped meanwhile, under the notice drawn over the last screen as when reconnecting, so ` back ` or a failure costs nothing: the window asks its server for a whole screen with a `Resize` to the same size, which `Server::fit` turns into `reset_screen` for that window, rather than reconnecting. If the old link ends meanwhile, ` back ` does what its end would have done (reconnect a remote one, end the window on a local server's end, or `exec` the new binary after a local server's restart: the first end is kept, since a restart is followed by the socket's end). A sound, an `Open` or a `Browse` the old server sent meanwhile still runs: the server has already let it go. A resize under a notice clears the screen through the backend (`clear_region`), never `Terminal::clear`, which asks the terminal where the cursor is and waits for an answer the input thread reads first, so the window ended after 2 s with `The cursor position could not be read`; the reconnecting notice called it on a resize too and now does the same. On commit the old link is dropped (a socket is shut down through a clone its `Guard` keeps, since the reader thread holds another and the server would otherwise keep a window that is gone; a remote's ssh is killed), the target, the openers and the window plugins change, the machine is remembered and the new server gets the list again, and a resize made while pending is sent. An opener's failure is tagged with the link it ran for, so a late one never reaches the next server. A window that ends with an error after it switched wraps it (`Error::Elsewhere`): the recovery its first target would offer (restart that server, update that machine) would act on the wrong machine; a restart of this machine's binary removes `CORNERCASE_REMOTE`, so a window started with it and switched home comes back home. A failure of any kind (ssh, a version apart, no cornercase there) stays in the notice (`Step::Failed`) and never ends the window, where the first connection of `cornercase remote` ends with it. Rejected: committing on the banner (a server of another build refused the window after the old link was gone, ending the window), a lock around `machines.json` (two windows linking in the same instant is rare and heals on the next link), a notice when a forget cannot be written (the menu shows the list as the file has it, so it says the truth), dropping the old link first (` back ` would cost a reconnect, through ssh for a remote) and a prompt for passwords by leaving the screen to ssh for a moment (the input thread would have to stop reading the terminal; left out, as for reconnects).
- **What follows the target**: the openers, detected only on this machine (elsewhere the folders are not here, and a window whose openers are empty refuses any `Open`); the window plugins (`Supervisor` of `Kind::Window`, started when the window comes to this machine and stopped when it leaves, since they talk to this machine's socket, see Plugins › Services and window processes); a restart after an update (`exec` of this machine's binary only while on this machine, a remote's reconnects); and the host named when ` quit ` gives up reconnecting. The sound player does not: it plays on the laptop wherever the window is.
- **No request, a read and writes for programs** (#705, `cli/known.rs`): the list and the switch belong to the window, not to a server. No request carries them and the contract gains nothing (the exemption AGENTS.md gives what only means something inside the window, as for the openers).
  - **Why a read**: a program that draws cornercase (#345) and offers to move to another server could not offer the machines a window reached, so a `me@10.0.0.5` in no `~/.ssh/config` had to be typed again, and one person's machines sat in two lists that never met. Reading `machines.json` itself is reading a private file whose shape can change with any release.
  - **What it is**: `cornercase remote --known` prints the list, as `clone --list-ignored` prints what `--file` can copy: a read of this machine's file with no server, no ssh and no request. It goes through the menu's own `machines::read`, so it lists what the menu lists (broken entries and destinations `valid` refuses left out, a missing or unreadable file as none) in the order first reached; only the machine a window is on after being forgotten is the window's alone.
  - **Its output**: `--json` gives `{"machines": [{"destination", "command"}]}`, both keys always written (`command` is `null` without one) and keys only ever added. The text is a line per machine with its `--command`, its hidden characters escaped, and a sentence when there is none.
  - **Where it runs**: it is `remote`'s, so `reach::Kind::Apart` ignores `CORNERCASE_REMOTE` (a program that sets it once reads this machine's list without unsetting it) and refuses `--remote` and a line of `requests` with status 2. A line runs under the link `requests` chose, which can be another machine's, so a line would read as that machine's list, as `--remote` would; and the read needs no connection, so a client starts `cornercase remote --known --json` on its own. Unlike `clone --list-ignored`, which reads here whatever machine the clone goes to, `--remote devbox remote --known` reads as devbox's list, which it does not print.
  - **No feature in `contract`**: no server is involved, and an older binary refuses `--known` with status 2.
  - **Rejected**: a request or a field of `status` (the window's machine's server knows nothing of the laptop's ssh, and a client that wants to switch may be attached to no server); each client keeping its own list; reading the file in each client; `remote --list`; a subcommand `remote known` (a host named `known`); `machines --known` (the server's list, behind a server and `--remote`); `here` in the answer (only a window has one).
  - **Writing the list from a program** (#751, `cli/known.rs`): `cornercase remote --remember DESTINATION [--command C]` and `--forget DESTINATION`, so the list is shared in both directions (#345) and a machine another interface reached shows in the window's menu too.
    - **Where it runs**: as `--known` (above). New here: the menu and the server never see the mark, and an older binary refuses both flags with clap's status 2 (`unexpected argument`).
    - **The destination** is checked by `machines::valid` through a clap value parser on both flags, so a destination ssh cannot take exits with 2 (`invalid value`), with the form's own words (`NOT_A_DESTINATION`, shared by the form and the CLI). `--command` is taken as `cornercase remote` takes it.
    - **Asked once**: a new entry is written with `"unreached": true`, and `chosen` asks for it as for an unknown destination (` connect ` / ` back `) but with its remembered `--command`. Any link to it rewrites the entry without the mark (` connect `, `cornercase remote DESTINATION`, a reconnect), so it is asked once; ` back ` or a failed switch keep it. The key is written only while it is `true` and an entry without it counts as reached, so every older entry and file keeps its bytes. Rejected: marking reached entries instead (every existing entry would ask again), not asking (every known machine was chosen by the person until now, and a program would skip that) and asking at `--remember` (a program has no terminal to ask in).
    - **Remembering again**: the last `--command` wins and none clears it, as for a link; the stored mark becomes `old && new`, so an entry no window reached keeps it and one a window reached never gets it. Nothing changed writes nothing. Forgetting and remembering again starts over, with the mark.
    - **Forgetting what is not listed** writes nothing and exits with 1 (`is not on this machine's list`), as `plugin unlink`, `account remove` and `machines remove` do for a name they lack: status 0 would let a program that misspelt a destination believe it gone.
    - **Errors**: the CLI says a write failed (status 1, `cannot write <file>`), since a script would otherwise believe the list changed; the window keeps ignoring it (see Rejected above).
    - **Open windows** keep their snapshot, as for another window: they see the change at their next link or forget, or when opened again; a local window with no button never reconnects. A window on the machine a program changes writes its own entry back at its next reconnect (every link remembers its machine), with the `--command` it holds, and re-adds a forgotten one, so the program's change holds only once that window has left. Rejected: a watcher on `machines.json` in each window (a thread for a list that rarely changes) and telling windows through a server (none is involved, and a window on another machine is attached to that machine's).
    - **Older releases**: one reads a marked entry and ignores the key, so it reaches that machine without asking; when it rewrites the file the marks are lost and those entries count as reached.
    - **No lock**: each write rereads the file just before writing, as a window's does. A `--remember` that meets a window's write in the same instant can be lost, and no link writes it again, unlike a window's own entry: a program that must be sure reads `--known --json` afterwards.
    - **Output**: one line on stdout (`remembered X; a window asks before it first connects there`, `remembered X` for one a window reached, `forgot X`), no `--json`. `--known --json` gains `unreached`, `true` and left out otherwise, so the output for an existing list keeps its bytes; the text form appends `(not reached yet)`.
    - **One list for both is not waited for**: `--remember` writes only `machines.json`, never `config.json`'s `machines` (Remote windows › Two lists of machines, for now).
- **Tests**: the choice and the notice's keys are pure functions (`chosen`, `pressed`); the list is a file in a temp dir; the menus and the form are app tests, the routing server tests (two windows, a browser), the notices and the button snapshots. E2e with the fake `ssh`, which reaches the test's own server, so a switch is the same server through another link: remote, this machine and remote again with one more ssh, a machine added by hand and reached once the window asks, ` back ` before connecting, this machine refused to a window inside one of its panes, and a server that refuses the window (a fake `cornercase` that prints the real banner, then a `Rejected` frame) leaving it where it was with nothing remembered. `remote --known` has unit tests of the read (order, `command` kept or none, broken entries skipped, a missing file), its JSON and text, its arguments and `reach` (the variable ignored, the flag refused) on every system, and e2e tests: a window reaches devbox through the fake `ssh` and a program lists it with its `--command`, and a list written by hand is read with and without `CORNERCASE_REMOTE`, with no server and no ssh; `--remember` and `--forget` have unit tests of the mark (written, dropped by a link, kept by a second `--remember`, a list it cannot write), of `chosen`, of the arguments (conflicts, destinations refused with status 2) and of the CLI's texts and errors, and e2e tests: with no server and no ssh, `--forget` of an unlisted machine (1, nothing written), and a window that asks once for a machine a program remembered, with its command. Not checked live: a real sshd, a host that only takes a password (refused by `BatchMode`, said in the notice) and two laptops attached to one server with different lists.
