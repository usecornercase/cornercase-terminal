# Remote windows › Switching machines from the window

Code: `remote/machines.rs`, `client/window/switch.rs`, `client/window.rs`, `client.rs` (`Target`, `Guard`), `app/machines.rs`, `ui/chrome.rs` (`machine_button`), `ui/activity.rs`, `ui/remote.rs`, `server.rs`, `server/windows.rs`, `protocol.rs`

- **Why**: `cornercase remote devbox` tied a window to one machine for its whole life; going to another machine, or back to this one, meant quitting and typing another command, though the shells and agents of each machine keep running anyway, so there is nothing to tear down. The window now changes the server it is attached to without closing.
- **Where the list lives**: on the window's machine, `machines.json` in its state folder beside `remote-shells.json`: every destination a window reached (`cornercase remote X` or a switch) with its `--command`, in the order first reached, so the menu never reshuffles, the last `--command` winning. It is written only when it changes, so a reconnect writes nothing; entries that are not valid destinations are skipped when read. The server cannot hold it: while the window is on devbox, devbox's server draws the sidebar and knows nothing of the laptop's ssh. So the window sends it in `Hello.machines` (`here`, the destination it is on or none for this machine, and `known`), the proxy forwards it as it is (unlike the openers, which it empties: a list of names gives the other machine nothing to act on), and `ClientMessage::Machines` sends it again after a forget. The browser bridge sends none, and a browser's is dropped, so it never gets the button. Rejected: the hosts of `~/.ssh/config` (most entries, GitHub or a bastion, have no cornercase, and `Host *` names nothing) and a `config.json` key (while on devbox it would be devbox's config).
- **The button** sits in the Worktrees row, in the second column of the tools grid (`ui::machine_button`, `ui::changes_button`'s geometry, never left of Worktrees' label; the name cut at its end, its ` ▴` kept), labelled with where the window is (`devbox ▴`, `this machine ▴`). The footer gains no row (see Layout › The footer) and the lines of both columns stay level. In compact mode it shares Worktrees' band of the projects menu; with the icon bar it is a slot over Help (codicon `remote`, VS Code's remote indicator), named on hover, dropped before Help on a short bar. It shows only while the window knows another machine or is on one (`App::machine_label`), so someone who never ran `cornercase remote` sees nothing new; the first machine comes from `cornercase remote`, which also lets ssh ask for an unknown host key. A projects column under about 22 cells leaves it out, since Worktrees' label takes the room; the icon bar or a wider column shows it. Rejected: a row of its own (every layout pays it, which Layout rejected for the update too) and an entry of ` More ▴ ` (where the window is would not show).
- **The menu** (`MenuAction::Machine`): `this machine`, the known machines (the one the window is on marked `✓`, and listed even once forgotten), **add machine…** (`Overlay::NewMachine`, one field checked by `machines::valid`: one word, no whitespace or control character, not starting with `-`, at most 255 bytes) and **forget…** (a submenu of the known ones). As for the openers, the server keeps each window's machines per `Client` and tells `App` whose input it handles (`App::set_machines`, beside `set_window`, also on `Hello` and, when a window leaves, for the most recently used one left), so the button and the menu follow the last window used, and a menu built for one window and clicked in another acts for the clicker. The menu keeps the names it listed and its entries name them by index, since `MenuAction` is `Copy`.
- **The order** (`ServerMessage::Machine`, the last variant, index 9, and `ClientMessage::Machines`, index 8; `protocol::VERSION` 11, which `cornercase remote` does not feel since its window needs the same release anyway): `Switch(None)` for this machine, `Switch(Some(destination))` or `Forget(destination)`, queued as `(client, order)` and sent to that window only, never to a browser, as `Open` is. New `ServerMessage` variants go to windows only (see Commands on another machine), so commands never meet it. `server.log` says an order was sent and how many machines a window knows, never their names.
- **The window decides** (`client/window/switch.rs`, `chosen`): an order is a request. The window acts only on `this machine` or a valid destination, ignores the machine it is on, and **asks first, in a notice it draws itself, before reaching a destination it never reached** (`Step::Asking`, ` connect ` and ` back `, `Enter` and `Esc`): a remote server can draw anything, a form included, and only the window's own notice is out of its reach, since no input goes to the server while it shows. Without it, a server on another machine could make the laptop run ssh, with its keys and agent, to any host. A known machine is reached at once (`Step::Connecting`). This machine is refused, in the notice and with `Error::Nested`'s words, to a window that runs inside one of its panes (`CORNERCASE` set, as `cornercase remote` from a pane): `cornercase` refuses to open there for the same reason, a window drawn inside itself.
- **Switching**: the connection runs on a thread (`Incoming::Switched`, numbered, so a late answer after ` back ` is dropped and its `Link` with it, which kills its ssh) through `Target::connect`, the reconnect's path, so the banner, the version rule, the Windows shells and `--command` are the same, always with `BatchMode`: the terminal is in raw mode and a password prompt would read it. **The old link stays attached until the new one answers**: its frames are dropped meanwhile, under the notice drawn over the last screen as when reconnecting, so ` back ` or a failure costs nothing: the window asks its server for a whole screen with a `Resize` to the same size, which `Server::fit` turns into `reset_screen` for that window, rather than reconnecting. If the old link ends meanwhile, ` back ` does what its end would have done (reconnect a remote one, end the window on a local server's end). A resize under a notice clears the screen through the backend (`clear_region`), never `Terminal::clear`, which asks the terminal where the cursor is and waits for an answer the input thread reads first, so the window ended after 2 s with `The cursor position could not be read`; the reconnecting notice called it on a resize too and now does the same. On success the old link is dropped (a socket is shut down through a clone its `Guard` keeps, since the reader thread holds another and the server would otherwise keep a window that is gone; a remote's ssh is killed), the target changes, and the new link sends `Hello`, as after a reconnect. A failure of any kind (ssh, a version apart, no cornercase there) stays in the notice (`Step::Failed`) and never ends the window, where the first connection of `cornercase remote` ends with it. Rejected: dropping the old link first (` back ` would cost a reconnect, through ssh for a remote) and a prompt for passwords by leaving the screen to ssh for a moment (the input thread would have to stop reading the terminal; left out, as for reconnects).
- **What follows the target**: the openers, detected only on this machine (elsewhere the folders are not here, and a window whose openers are empty refuses any `Open`); the window plugins (`Supervisor` of `Kind::Window`, started when the window comes to this machine and stopped when it leaves, since they talk to this machine's socket, see Plugins › Services and window processes); a restart after an update (`exec` of this machine's binary only while on this machine, a remote's reconnects); and the host named when ` quit ` gives up reconnecting. The sound player does not: it plays on the laptop wherever the window is.
- **No request**: the list and the switch belong to the window, not to a server; another UI reaches any machine with `--remote` and keeps its own list, so the contract gains nothing (the exemption AGENTS.md gives what only means something inside the window, as for the openers).
- **Tests**: the choice and the notice's keys are pure functions (`chosen`, `pressed`); the list is a file in a temp dir; the menus and the form are app tests, the routing server tests (two windows, a browser), the notices and the button snapshots. E2e with the fake `ssh`, which reaches the test's own server, so a switch is the same server through another link: remote, this machine and remote again with one more ssh, a machine added by hand and reached once the window asks, ` back ` before connecting, and this machine refused to a window inside one of its panes. Not checked live: a real sshd, a host that only takes a password (refused by `BatchMode`, said in the notice) and two laptops attached to one server with different lists.
