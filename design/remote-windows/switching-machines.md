# Remote windows › Switching machines from the window

Code: `machines/list.rs`, `remote/machines.rs`, `client/window/switch.rs`, `cli/known.rs`, `client/window.rs`, `client.rs` (`Target`, `Guard`), `app/machines.rs`, `ui/chrome.rs` (`machine_button`), `ui/activity.rs`, `ui/remote.rs`, `server.rs`, `server/windows.rs`, `protocol.rs`

- **Why**: `cornercase remote devbox` tied a window to one machine for its whole life; going to another machine, or back to this one, meant quitting and typing another command, though the shells and agents of each machine keep running anyway, so there is nothing to tear down. The window now changes the server it is attached to without closing.
- **Where the list lives** (#898): in `config.json`'s `machines`, the one list of machines of a computer that Settings › Machines manages (see Remote windows › One list of machines). An entry gives two things: **show its work here** (`shown`, the server links it) and **open the window there** (the button, `cornercase remote`). The window reads and writes the file itself (`machines/list.rs`: `read` is tolerant, so a `config.json` with an unrelated bad key still gives the button its list; `change` goes through `config::read`, strict, and writes the whole `Config` as the server does, or only `{"machines": …}` when the file is missing, so a laptop that only runs `cornercase remote` gets no full default `config.json`, and a broken file is refused and never overwritten). A window's first connection (its start, a switch's commit) to a destination in the list sets its `command` (the last one wins, none clears it) and clears `unreached`; a reconnect clears `unreached`, adds the machine only if it is missing and never touches the command. A link to one that is not listed adds an entry with `shown: false`, named after the destination's host (`name_for`: made valid, at most 20 characters, unique), folder `~`. Nothing changed writes nothing. These writes take the lock on `config.json.lock`, as `remote --remember`, `--forget` and the migration do (see Remote windows › One list of machines, Who writes the file). The server cannot hold the window's snapshot: while the window is on devbox, devbox's server draws the sidebar and its `config.json` is devbox's. So the window sends the list in `Hello.machines` (`here`, the **name** of the entry the window is on, or its destination when none has it, and none on this computer; `known`, the names of the accepted entries), the proxy forwards it as it is, and `ClientMessage::Machines` sends it again after a switch. While the window is on this computer it shares the server's `config.json`, so the server builds the menu from its own live list and a machine added in Settings shows at once. A browser's is dropped, so it never gets the button. Rejected: the hosts of `~/.ssh/config` (most entries, GitHub or a bastion, have no cornercase, and `Host *` names nothing) and keeping `machines.json` beside `config.json`: two lists that offer each other's machines (the issue's other option) would keep two sets of fields to reconcile.
- **Migration** (#898): the first read by this release (server start through `server::startup::config_file`, a window, `remote --known`, `--remember`, `--forget`) moves each valid entry of the old `machines.json` into `config.json` (`machines::list::migrate`): a destination not listed is added with `shown: false`, its host as name, `~` as folder, its `command` and its `unreached` mark; a listed one with no `command` takes the old one. Then `machines.json` is removed, so a machine removed in Settings never comes back from it; with a `config.json` that cannot be read it is kept for the next start. Not shown, because the person never chose to link those machines. A downgrade has no window list; an older release links every entry (it ignores `shown`) and may recreate `machines.json`, which the next start merges again without duplicates. No `protocol::VERSION` bump: a window attaches only to its own build locally and to its own release remotely, and `Machines` keeps its shape (it carries names now). The migration code goes in a later release. `remote-shells.json` and `tunnels.json`, keyed by destination, are untouched.
- **The button** sits on **a row of its own under the Worktrees row** (`ui::machine_button`, `Areas::machine`, `Screen::machine`; the name cut at its end, its ` ▴` and the tunnels' count kept: see Tunnelling a port), labelled with where the window is (`this computer ▴`, `on devbox ▴`, `on devbox ⇄2 ▴`). It had the second column of the Worktrees row at first (#657), which ` Recap ` (#656) took: the row is shown while the list holds an accepted machine, shown or not, or the window is on one (`App::machine_label`), even if no window ever ran `cornercase remote` (#898), so a window with no machine has exactly the rows it had (see Layout › The footer): side by side the projects column gets one more footer row and the workspaces column a blank one, so the lines of both columns stay level; stacked and tree add a row to the footer; compact mode adds a band to the projects menu. With the icon bar it is a slot over Help (codicon `remote`, VS Code's remote indicator), named on hover, dropped before Help on a short bar. A machine added in Settings › Machines or with `cornercase machines add` makes it appear at once while the window is on this computer. A machine ssh does not know fails in the switch notice until its host key is accepted, with a plain `ssh` or `cornercase remote <host>` with the same `--command` (a plain one remembers the entry without it). A projects column under about 8 cells leaves it out. Rejected: the second column of the Worktrees row (Recap lives there, and a narrow column would lose one of the two) and an entry of ` More ▴ ` (where the window is would not show).
- **The menu** (`MenuAction::Machine`): on this computer, `✓ this computer`, each accepted machine by name with a ` ▸` (the names padded so the arrows line up), **only this computer** and **show all** (#899), **add machine…** (the Settings machine form, opened from the button: its ` back ` closes it back to the window and a save closes it with a toast, instead of returning to Settings) and **manage machines…** (Settings › Machines), then the window's tunnels, one row each with a submenu (see Tunnelling a port › The machine button and menu). On another machine, `this computer`, the machines of the window's computer (the one it is on marked `✓`, and listed even when the window did not send it), then the tunnels, and neither add nor manage: the form writes the server's `config.json`, which there is the other machine's list, not the one the button offers. For the same reason a name there switches at once, with no submenu and no **only this computer** or **show all**.
  - **A machine's submenu** (#899), on this computer: **show its work here ✓** (shown; a click hides it) or **show its work here ·** (hidden; a click shows it), then **open the window there**, the switch the name was before. It opens at the same place as a tunnel's (a second `Overlay::Menu`), and a name no longer listed opens nothing. **only this computer** hides every machine and **show all** shows every one, each in one write; each is dim when it would change nothing, which shows the state without a mark the issue's mock-up does not have, and a click on a dim one does nothing. A pick says what it did in a toast, with the notices of Settings' toggle. The main list does not mark a hidden machine; its submenu does. **forget…** is gone (#898): a machine is removed in Settings, where its link ends too. As for the openers, the server keeps each window's machines per `Client` and tells `App` whose input it handles (`App::set_machines`, beside `set_window`, also on `Hello` and, when a window leaves, for the most recently used one left), so the button and the menu follow the last window used (a `Machines` message from a window used less recently changes its own record but not what shows), and a menu built for one window and clicked in another acts for the clicker. The menu keeps the names it listed and its entries name them by index, since `MenuAction` is `Copy`.
- **The order** (`ServerMessage::Machine`, the last variant, index 9, and `ClientMessage::Machines`, index 8): `Switch(None)` for this computer, `Switch(Some(name))` for an entry, queued as `(client, order)` and sent to that window only, never to a browser, as `Open` is. The `Forget` order went with the menu's forget… (#898). New `ServerMessage` variants go to windows only (see Commands on another machine), so commands never meet it. `server.log` says an order was sent and how many machines a window knows, never their names.
- **The window decides** (`client/window/switch.rs`, `chosen`): an order is a request, and it names an entry of this computer's list, never a destination: the window picks the accepted entry with that name (ignoring case), ignores the machine it is on, and **asks first, in a notice it draws itself, before reaching a machine a program added and no window reached yet** (`unreached`, `Step::Asking`, ` connect ` and ` back `, `Enter` and `Esc`): a remote server can draw anything, a form included, and only the window's own notice is out of its reach, since no input goes to the server while it shows. Orders carrying names means a server on another machine can only pick among the laptop's own entries and can no longer make it run ssh, with its keys and agent, to a host outside its list; the old case of asking for any unknown destination went with the one-field dialog. The `unreached` mark is kept for the entries a program wrote (`remote --remember`, a `machines` request that creates an entry or changes its destination; the migration keeps the old entry's own mark) and is false for what a person typed in the Settings form on this computer's own server or what a window linked; it is written only while true. Asking once for `cornercase machines add` from a shell is a mild cost, accepted for one rule for every program. A reached machine is connected at once (`Step::Connecting`). This computer is refused, in the notice and with `Error::Nested`'s words, to a window that runs inside one of its panes (`CORNERCASE` set, as `cornercase remote` from a pane): `cornercase` refuses to open there for the same reason, a window drawn inside itself. The notices keep naming the real destination (`connect to cc@vps.example?`), which is the point of the window's own notice.
- **Switching**: the connection runs on a thread (`Incoming::Switched`, numbered, so a late answer after ` back ` is dropped and its `Link` with it, which kills its ssh) through `Target::connect`, the reconnect's path, so the banner, the version rule, the Windows shells and `--command` are the same, always with `BatchMode`: the terminal is in raw mode and a password prompt would read it. A banner that has not come within 30 s stops that ssh (`remote::watched`, for every attempt with `BatchMode`: reconnects and commands too, never the first connection of `cornercase remote`, where ssh may be waiting for a password), so a thread left behind by ` back ` ends within 30 s and repeated tries cannot pile up. **The switch is made only once the new server accepted the window**: a banner proves the proxy runs, not that its server takes this build, so the new link is pending (`Pending`, with an id of its own from the same counter as the links, so no stale message is ever taken for another link's) while it sends `Hello`; its first message decides (`answer`): `Rejected` (a server of another build), an unreadable message or the link's end fails the switch in the notice, its reason or ssh's last line shown, anything else commits it. ` back ` drops a pending link at once, closing its socket or killing its ssh, and no answer within 30 s fails the switch. **The old link stays attached until the new one answers**: its frames are dropped meanwhile, under the notice drawn over the last screen as when reconnecting, so ` back ` or a failure costs nothing: the window asks its server for a whole screen with a `Resize` to the same size, which `Server::fit` turns into `reset_screen` for that window, rather than reconnecting. If the old link ends meanwhile, ` back ` does what its end would have done (reconnect a remote one, end the window on a local server's end, or `exec` the new binary after a local server's restart: the first end is kept, since a restart is followed by the socket's end). A sound, an `Open` or a `Browse` the old server sent meanwhile still runs: the server has already let it go. A resize under a notice clears the screen through the backend (`clear_region`), never `Terminal::clear`, which asks the terminal where the cursor is and waits for an answer the input thread reads first, so the window ended after 2 s with `The cursor position could not be read`; the reconnecting notice called it on a resize too and now does the same. On commit the old link is dropped (a socket is shut down through a clone its `Guard` keeps, since the reader thread holds another and the server would otherwise keep a window that is gone; a remote's ssh is killed), the target, the openers and the window plugins change, the machine is remembered and the new server gets the list again, and a resize made while pending is sent. An opener's failure is tagged with the link it ran for, so a late one never reaches the next server. A window that ends with an error after it switched wraps it (`Error::Elsewhere`): the recovery its first target would offer (restart that server, update that machine) would act on the wrong machine; a restart of this machine's binary removes `CORNERCASE_REMOTE`, so a window started with it and switched home comes back home. A failure of any kind (ssh, a version apart, no cornercase there) stays in the notice (`Step::Failed`) and never ends the window, where the first connection of `cornercase remote` ends with it. Rejected: committing on the banner (a server of another build refused the window after the old link was gone, ending the window), dropping the old link first (` back ` would cost a reconnect, through ssh for a remote) and a prompt for passwords by leaving the screen to ssh for a moment (the input thread would have to stop reading the terminal; left out, as for reconnects).
- **What follows the target**: the openers, detected only on this machine (elsewhere the folders are not here, and a window whose openers are empty refuses any `Open`); the window plugins (`Supervisor` of `Kind::Window`, started when the window comes to this machine and stopped when it leaves, since they talk to this machine's socket, see Plugins › Services and window processes); a restart after an update (`exec` of this machine's binary only while on this machine, a remote's reconnects); and the host named when ` quit ` gives up reconnecting. The sound player does not: it plays on the laptop wherever the window is.
- **No request, a read and writes for programs** (#705, #898, `cli/known.rs`): the switch belongs to the window, not to a server. No request carries it and the contract gains nothing (the exemption AGENTS.md gives what only means something inside the window, as for the openers). The list itself is `config.json`'s `machines`, so a program also reads it with `cornercase machines --json` (which says `shown` and `command` too, see Commands for scripts and agents).
  - **Why a read**: a program that draws cornercase (#345) and offers to move to another server needs the machines a window offers, so a `me@10.0.0.5` in no `~/.ssh/config` is not typed again; reading `config.json` itself is reading a file whose shape can change with any release.
  - **What it is**: `cornercase remote --known` prints the list, as `clone --list-ignored` prints what `--file` can copy: a read of this computer's file with no server, no ssh and no request, through `machines::list::read`, so it lists the accepted entries (broken ones and destinations `valid` refuses left out, a missing or unreadable file as none), shown or not, in the order of the file.
  - **Its output**: `--json` gives `{"machines": [{"name", "destination", "command"}]}`, all keys always written (`command` is `null` without one) and keys only ever added (`name` came with #898), plus `unreached` (`true` and left out otherwise). The text is a line per machine with its name, destination and `--command`, its hidden characters escaped, `(not reached yet)` after one a program added, and a sentence when there is none.
  - **Where it runs**: it is `remote`'s, so `reach::Kind::Apart` ignores `CORNERCASE_REMOTE` (a program that sets it once reads this computer's list without unsetting it) and refuses `--remote` and a line of `requests` with status 2. A line runs under the link `requests` chose, which can be another machine's, so it would read as that machine's list; and the read needs no connection, so a client starts `cornercase remote --known --json` on its own.
  - **No feature in `contract`**: no server is involved, and an older binary refuses `--known` with status 2.
  - **Rejected**: a request or a field of `status` (the window's machine's server knows nothing of the laptop's ssh, and a client that wants to switch may be attached to no server); `remote --list`; a subcommand `remote known` (a host named `known`); `here` in the answer (only a window has one).
  - **Writing the list from a program** (#751, #898, `cli/known.rs`): `cornercase remote --remember DESTINATION [--command C]` and `--forget DESTINATION`.
    - **Where it runs**: as `--known` (above). An older binary refuses both flags with clap's status 2 (`unexpected argument`).
    - **The destination** is checked by `machines::valid` through a clap value parser on both flags, so a destination ssh cannot take exits with 2 (`invalid value`), with the form's own words (`NOT_A_DESTINATION`, shared by the form and the CLI). `--command` is taken as `cornercase remote` takes it.
    - **`--remember`** adds an entry that is not shown and `unreached: true` (named after the host), or gives the listed one this `--command` (none clears it) and keeps its mark. **Asked once**: `chosen` asks for a marked entry (` connect ` / ` back `) with its remembered `--command`, and any link to it clears the mark, so it is asked once; ` back ` or a failed switch keep it. Rejected: not asking (every machine was chosen by the person until now, and a program would skip that) and asking at `--remember` (a program has no terminal to ask in).
    - **`--forget`** removes the entry, as Settings' `×` does: its link ends and its server keeps running there. A machine not listed writes nothing and exits with 1 (`is not on this computer's list`), as `plugin unlink`, `account remove` and `machines remove` do for a name they lack: status 0 would let a program that misspelt a destination believe it gone.
    - **A file it cannot read**: `config::read` is strict, so a `config.json` that cannot be read is refused with 1 and left alone (`cannot read or write <file>`), never overwritten; a missing one is an empty list. A running server reloads a change as an outside edit, so the link follows.
    - **Open windows** keep their snapshot, as for another window: they see the change at their next link, or when opened again; a window on this computer builds its menu from the server's live list. A window on the machine a program changes adds its entry back at its next reconnect only when it is gone (after a `--forget`), with the `--command` it holds, and leaves the command of an entry that is there as the program set it.
    - **Older releases**: one reads a marked entry and ignores the keys it does not know, so it links a `shown: false` entry and reaches a marked one without asking; when it rewrites `config.json` those keys are lost.
    - **Lock**: `--remember` and `--forget` take `config.json.lock` and wait at most 5 s (`another cornercase is changing the list of machines; try again`). What does not take it (Settings' save, `machines add|edit|remove`) is said in One list of machines, so a program that must be sure still reads `--known --json` afterwards.
    - **Output**: one line on stdout (`remembered X; a window asks before it first connects there`, `remembered X` for one a window reached, `forgot X`), no `--json`.
- **Tests**: the choice and the notice's keys are pure functions (`chosen`, `pressed`, `machines_of`); the list is a pair of files in a temp dir (`machines::list`: names, reading, changing, reaching, remembering, migrating); the menus and the form are app tests, the routing server tests (two windows, a browser, a `config.json` with machines), the notices and the button snapshots. E2e with the fake `ssh`, which reaches the test's own server, so a switch is the same server through another link: remote, this computer and remote again with one more ssh, a machine added in the form and reached once the window asks, ` back ` before connecting, this computer refused to a window inside one of its panes, a server that refuses the window (a fake `cornercase` that prints the real banner, then a `Rejected` frame) leaving it where it was with the machine still marked, the old `machines.json` moved into `config.json` once, and `machines add --hidden` showing the button without reconnecting. `remote --known`, `--remember` and `--forget` have unit tests of the CLI's texts and errors (a broken `config.json` refused and left alone), of the arguments (conflicts, destinations refused with status 2) and of `reach` (the variable ignored, the flag refused), and e2e tests with no server and no ssh. Not checked live: a real sshd, a host that only takes a password (refused by `BatchMode`, said in the notice) and two laptops attached to one server with different lists.
