# Remote windows › Hints that name the machine

Code: `remote/hints.rs`, `remote/hints/stream.rs`, `remote.rs` (`run_with`), `app/control/relay.rs` (`relay_answered`), `client/requests.rs` (`answered_through`, `hinted`), `cli/` (#807, #834, #835)

Part of [Remote windows](../remote-windows.md).

- **What it fixes** (#807): the server writes its hints without knowing how the command reached it, so through `--remote`, `` `cornercase read --pane 7` `` named that machine's pane in a command that, run as written, reads this computer's.
- **Where**: `client::requests::answered_through`, used by `received` and `follow_on`, so every answer of a link gets it: one-shot requests, the lines of `requests --follow` and `input --follow`, the later lines of a stream and the feature checks. It uses the link's own `Remote` (`Guard::remote`), so a socket link is never touched, and without `--remote` an answer is byte for byte what it was.
- **What changes** (`Remote::hinted`, `Remote::hint_answer`): every closed backtick span starting `cornercase ` in a refusal's message (`Control` and `StaleBoot`, which keeps its code and exit 4) and in the `error` strings, at any depth, of an OK answer or a stream line. The hint becomes `Remote::line(…)`: `--remote DEST` and `--remote-command CMD` quoted as sh reads them. `CORNERCASE_REMOTE` gives the flag spelled out, so the hint also works in a terminal without the variable. A substring check on the raw answer comes first, so an answer with no hint costs one search.
- **Why on this side**: it knows how it reached the server and which strings are messages, it works with every release `--remote` accepts there, and the destination, a name from this computer's ssh config, never goes to a server whose log keeps destinations out (see The log).
- **What a hint is**: a backtick-quoted `` `cornercase …` ``. The repo writes every hint that way; the four that were not (the `close --pane` of `processes stop` on a pane's shell, and the `agents reopen` of `agents close`, of the note of `flow run --close-when-merged` and of the `exited` line of `flow runs`) got backticks, since run as written they acted on this computer's pane or agents. A future hint written without them would not be rewritten.
- **Left alone**, each with a test:
  - a hint that already has `--remote`, first or after the command (it names a machine of that server, and two `--remote` are a usage error; this also makes the rewrite idempotent);
  - `` `cornercase` `` alone;
  - the commands that take no `--remote` (`remote`, `skill`, `server`, `proxy`, `plugin windows`; a test ties the list to `reach::kind`);
  - a hint followed by `there` or `here`: it names a command for the machine the message names, in its own shell (`RemoteTooOld`, `RemoteOlder`, `RemoteNewer`).
- **Data is never rewritten**: a pane's `text` may show an earlier hint, and fields such as `why` or `note` name a command as a reference. Only a refusal's message and `error` strings are walked. A hint a person is meant to run in another field would need the walk widened on purpose.
- **Limits**: the quoting is sh's (`Remote::line`), so a `--remote-command` with spaces or other characters sh would quote does not run as written in Windows `cmd`, which groups with double quotes; the hint is for sh and PowerShell-like shells, and a destination or command made of plain characters works everywhere. A message that embeds text this CLI did not write (a plugin's error) is hinted only in the part the CLI wrote, since an unmatched backtick in that text would shift the spans.
- **The CLI's own messages** about the server there go through `client::hinted` (the same rewrite, a no-op without `--remote`): `account remove`, `config set`, `files read` of a folder, `flow hide` and the `flow list` line, `plugin run`, `requests` lines, the `--branch` lookups (`cli.rs`, `changes shared`), `config forum`, `events` (its line for dropped events), `agents close`, `flow run --close-when-merged`'s note and `flow runs`' `exited` line. `config secret`'s pipe hint (`printf … | cornercase config secret KEY`) starts with `printf`, so it is built with `Remote::line` where it is written (`piped`). Left out: `start-server`'s version warning (it compares the server with this binary, a different problem), the `flow list` format notes, and texts whose command stays here.
- **No feature and no contract change**: messages are not part of the contract (clients branch on `code`). For `--remote` the server is not involved, as in #718; only the relaying server takes part, for a `--machine` relay (#835, below), and it changes message text only. A program that speaks the protocol over its own ssh knows how it got there.
- **`--boot` is not carried**: a hint names ids the server wrote in the answer, in the run `--boot` was just checked against, and otherwise the answer is `stale-boot`, whose hint (`status`) takes no `--boot`. A program builds commands from the JSON, never from a message. Carrying it would need this side to know which hinted commands take `--boot` (it sits on each command's own arguments, #801), and a wrong guess turns the hint into a usage error.
- **A refusal relayed with `--machine`** (#835): the relaying server rewrites the hints of what the machine answers, in `relay_answered`, for the relayed requests only (`start`, `start-with`, `new-workspace`, `flow-run`).
  - **Why there**: it knows the machine's canonical name (the client only knows what was typed, `VPS` or `vps`), and its own refusals about a machine (unknown, not linked, `stale-boot` of another run) never pass there, so a hint such as `` `cornercase machines` `` stays as written. The destination never enters the text (`hide_destination` is kept).
  - **What changes** (`remote::hints::on_machine`), for each backtick-quoted `cornercase …` span: a command that takes `--machine` (`ON_A_MACHINE`: `start`, `new-workspace`, `focus`, `flow run`, `stats`, `usage`) gets `--machine NAME` right after its words, so a positional or a `--` never swallows it; `status` and `status --json` stay, since this server's `status` lists the machine's ids under its name (`status --panes` lists only this computer's panes, so it gets `there`); any other command keeps its span and gets ` there` right after the closing backtick, since run as written it would act on this computer. A hint that already names `--machine` or `--remote`, or is followed by `there` or `here`, is left alone, and the rewrite is idempotent.
  - **Why `there`, not ` on NAME`**: #807's client rule, already released, leaves a hint followed by `there` alone, so `--remote X --machine NAME` never turns a command meant for the machine into X's; an older client would add `--remote X` to ` on NAME`.
  - **`focus`** never gets `--machine` beside `--pane`, `--worktree`, `--project`, `--view` or `--reveal`, which clap refuses with it. A test walks the whole clap tree and ties the list, and those flags, to the arguments, as #807 did for `--remote` with `reach::kind`, so a hint never becomes a usage error.
  - **With `--remote X`** the server adds `--machine NAME` and the client adds `--remote X`, giving `cornercase --remote X start --machine NAME claude`, which the CLI parses (tested).
  - A program that relays with the `machine` field gets the same text: messages are not contract. The window's dialogs show a machine's refusal as it is (their texts are UI). `--boot` is not carried, for the reason above.
- **Commands that run there as a process** (#834): `update`, `restart`, `kill-server` and the plugin commands on files print their own hints there, with their stdio passed through ssh. This side rewrites ssh's output as it streams (`remote/hints/stream.rs`, `Remote::run_with`).
  - **Why this and not an environment variable** for the far process: it works with every release there, which matters most for `update`, the command run against an older machine; the destination, a name from this computer's ssh config, never leaves this computer (a variable would reach the server `restart` and `update` start there, and every pane of it, unless removed, and would need quoting for cmd and PowerShell far ends); and it is the same rule as #807.
  - **What streams** (`printed`): `logs` and `plugin logs` are data and keep their stdio; with `--json` before a `--`, stdout is data and stays inherited while stderr is rewritten; everything else has both streams piped and rewritten.
  - **How**: complete lines are rewritten at once (parity of backticks starts again at each line). The partial line goes out at once, except where a hint may be incomplete: from the opening backtick of an open span, or of a closed `` `cornercase …` `` with fewer than 7 bytes after it (the `there` or `here` is not known yet), and a partial line that is a prefix of `cornercase update`. So a prompt such as `Restart it now? [y/N] ` (no backtick) shows before it is answered, with a terminal too: with `ssh -t` the far pty merges both streams onto ssh's stdout, which this side copies to its own terminal, and the window size and the escape character work off stdin. Each write is flushed.
  - **`update --check`** prints the command on a line of its own with no backticks (`cornercase update`); that whole line is rewritten, whatever version prints it.
  - **Limits**: invalid UTF-8 becomes U+FFFD; `--json` in a terminal merges the streams, so nothing is rewritten; the plugin commands mix messages with a plugin's own texts (name, description, preview), so a `cornercase` command in those gets `--remote` too, which names the machine the plugin is on; a hint split across lines is no hint; on Windows an interactive run (`Run::Terminal`) keeps its stdio as it was and is not rewritten, since Win32-OpenSSH reads the console mode and size from the output handle when it allocates a pty (`ConEnterRawMode`), which a pipe would break (not tried live: no Windows machine here, so a run there prints the far hints as they are).
- **Rejected**: the request telling the far end how it was reached (the destination would travel to, and could be logged by, the other server; an older server ignores it; a new request field needs a feature check); the answer marking each hint (a contract feature and every message site changed, for what the backticks already say); an environment variable for a process run there (above); a line-buffered filter (it would hold a `[y/N]` prompt); a flush after a quiet time (depends on timing); the client adding `--machine` (it cannot tell the machine's text from this server's, and knows only the typed name); and ` on NAME` (older clients).
- **Not covered**: the window's run-on dialogs show a machine's refusal as it is; `stats` and `usage --machine` read machines through `machine_usage`, with no hint there today; `--json` with a terminal; and a far hint written without backticks other than `update --check`'s line.
- **Checked**: unit tests, app tests and the e2e tests with the fake `ssh` (`tests/e2e/hints.rs`, a PTY included). Not checked live: a real sshd, `ssh -t` with a piped stdout, and Windows' `ssh.exe` with a piped stdout; the proxy copies answers byte for byte.
