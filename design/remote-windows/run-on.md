# Remote windows › Starting work on a machine

Part of [Remote windows](../remote-windows.md). How a machine's link, its snapshot, the pairing of projects and asking a machine work is in Remote windows › Machines' links; the `machine` field of the requests is in Commands for scripts and agents (Machines), and the copied files of `clone` in its topic Cloning a repository.

- **What it is** (#543, `machines/run_on.rs`, `machines/send.rs`, `machines/clone_form.rs`, `app/machines/run_on.rs`, `app/machines/relay.rs`, `app/machines/checks.rs`, `app/machines/selection/awaited.rs`, `app/control/relay.rs`, `app/issues_dialog/run_on.rs`, `app/start_flow_dialog/run_on.rs`, `app/new_workspace_there.rs`, `app/clone_on_machine.rs`, `issues/browser/run_on.rs`, `flows/start/run_on.rs`, `git/ignored.rs`, `git/clone/files.rs`, `ui/dialog/run_on.rs`, `ui/dialog/clone_on_machine.rs`): Issues, Start flow and New workspace get a `run on` row, `● this computer   ○ vps`. Choosing a machine sends that machine's server the request a script would send it (`start`, `flow run`, `new-workspace`), so what starts there belongs to that server, shows in the sidebar under the machine (Machines' links › What a machine has) and is seen here as A machine's tab. No request is new on the machine's side: it does what it does for its own window and scripts.
- **The row**:
  - It exists only while `config.json` lists a machine (`run_on_for` gives `None` otherwise), so without machines the three dialogs draw and behave as before; their snapshots did not change.
  - It lists this computer, then every machine in the order of Settings › Machines, with its icon. A machine that is not `linked`, or linked with no snapshot yet, is dimmed with why (`connecting…`, `not seen yet`, `unreachable`, or the link's reason through `hide_destination`) and cannot be chosen.
  - `this computer` is chosen when a dialog opens; the choice is never saved, since a machine chosen by habit would start work somewhere the user did not look.
  - Issues picks the machine through its ` run on… ` button and picker (`Pick::Machine`, the pattern of the account picker), since the row is drawn by the issue's page; Start flow and New workspace take a click on the row (`ui::RunOnRow`, shared by both).
  - **A project with no repository identity cannot run elsewhere**: the row ends with `— needs a git remote` and no machine can be chosen. The identity is the only way to pair the project here with one there, and a folder copied by hand would not stay in step. The identity is read on a job (Machines' links › A repository's identity), so a dialog opened in the first moments after a project opens says `needs a git remote` until the next machine event or action redraws the row; the e2e tests wait for `status` to show the identity first.
- **Where it starts there**: the project there is the first of the machine's snapshot whose `repo` equals this project's identity (any case), as the sidebar pairs them. The ids sent are the machine's, never the ones here. The `start` row then says `in its own worktree on vps, in ~/code/web-shop` or `in a tab on vps, in …`, from the same choice that is made here (the place picked for the issue, or whether the project is at a repository's root), and New workspace `in a workspace on vps, in …`. A place that is a workspace here has no pair there, so it stands for its project: the machine gets that project's id there and places the work as `start --issue --project` does.
- **Checks before starting** (`app/machines/checks.rs`): the open dialog asks its machine for what it shows (`Wanted`): `account list --check` for Issues and Start flow and, when the project is there, for its id there `issue sources` for Issues and for Start flow from an issue, `flow list` for Start flow. New workspace shows none of them, so it asks nothing, also after a clone. They are asked when the machine is chosen, and again whenever the dialog's rows are worked out (below) and one it shows was never asked or was emptied: a project the machine lists only later, another issue focused (its project there), a machine that restarted. One being asked is not asked twice, and one that failed is not asked again at every event, so a machine that keeps refusing is not asked in a loop; it is asked again when the machine is chosen again, when its link comes up again (a timeout or `unreachable` while it reconnected must not stick until the user chooses it again), and when ` start ` is pressed while that failure blocks it: ` start ` still refuses with the reason, and the next answer replaces it. Each is an ssh round trip of its own, and `account list --check` asks each login with a cap of 60 s, so a dialog never asks for answers it does not show. They go over the relay below, and the dialog reads the answers:
  - **Accounts**: the account picker and Start flow's combos list the machine's accounts and its active ones, marked `(vps's accounts)`. Nothing is copied: what is chosen travels as the request's `accounts`, and the machine resolves the names. While they are asked again, the account picked stays picked, and is kept once the answer still lists it. Only one picked on that same machine: choosing a machine drops the account picked here or on another one, whose name means nothing there, and a machine that cannot list its accounts shows none rather than this computer's. ` start a flow ` from Issues carries the account picked on the machine into Start flow, which asks the machine again: once its accounts come, that account is chosen if they still list it, else the machine's active one.
  - **The agent**: `account list --check` answers `agents`, each agent the machine knows with its command and whether that command is on its server's `PATH` (a field added for this, Accounts and profiles). The row says `not installed on vps`, or `not logged in on vps` when the chosen account (or the agent's own login) is `signed-out` there and none of its token variables is in `tokens`, and offers ` open login tab `. Neither blocks ` start `: the server there was started by ssh with a short `PATH` (Remote windows › PATH), so an agent installed with npm or nvm can be missing for the server and present in the shell of the tab it opens. An answer without `agents`, or an `unknown` or `failed` login, says nothing. What the machine writes there is read with `blank` (below): an account with a blank name is left out, since the agent's own login is the one with no name and a blank one would stand for it; a blank label falls back to the name, or `System` for the agent's own; a blank command is neither shown nor sent, and the login tab runs the agent's own name instead.
  - **The tracker** (Issues, and Start flow from an issue): when `issue sources` there does not give the issue's source as `connected`, the row says what is missing (`vps has no GitHub token for web-shop`, or the machine's own `missing` or `reason`, three entries at most with `… and N more`, blank ones left out and not counted, each text and the project's name there cut at 60 characters on one line, since the machine writes them; what is blank falls back to words of ours, never an empty gap: `settings` for a list with nothing left, `failing` for a reason, the source's id for its name, `the project` for the project's; blank means only spaces and the characters `text::hidden` drops everywhere else, controls and those that show nothing, such as U+200B to U+200F, U+2060 to U+206F, U+00AD, U+3164 or the variation selectors) and ` start ` sends nothing, since the machine would refuse `start --issue` anyway. A check that failed blocks with its reason; one still waiting does not.
  - **The flows** (Start flow): the list is the machine's own `flow list`, turned into the dialog's listing, so what is drawn is what runs there; a built-in flow edited here could differ from the machine's, and a flow of your own here may not exist there. ` edit ` is hidden while a machine is chosen, or one left the list: editing the machine's flows from here is left out. **Its answer is cleaned on its own** (`run_on::heard_flows`, chosen by `Send::hearing`), not as the link's text, which is one line of at most 200 characters: the preview would show a flattened, cut prompt, and a name past 200 characters would go back cut to `flow run`, which the machine refuses. A `prompt`, `description` or `notes` keeps its line breaks (a `\r` is dropped) and loses every other control and hidden character; every other string is one line, as the link's; a path is cleaned as a path. Each field is cut at 65,536 characters, far above a real flow file's prompt and a bound on what one answer can make this side hold and draw. A flow whose name (the listing's or its spec's) the cleaning would change, cut or joined into one line or rid of a hidden character, is not offered, listed or hidden: it would be run by another name there. Each list (`flows`, `hidden`, `broken`, `builtins`) keeps its first 200 entries, the cap a flows folder has here (`flows::folder::MAX_FILES`): what passes it is not offered, so a machine cannot make this side hold and draw an endless list. When the machine restarts (another `boot`), Start flow reads its flows and accounts again, keeping the account chosen if the machine still lists it.
  - **A cache in each `Held`**, in memory only, per check and per project there, kept by the link's `era`: a snapshot with another `boot` makes the answers stale, and choosing a machine in a dialog empties its cache and asks again, so each opening reads fresh answers while the dialog itself reuses them. Emptying it starts a new generation, and an answer to a question of an earlier one is dropped, so a stale answer still in flight never fills the fresh cache. Within a generation a machine is never asked the same check twice at once.
  - The dialog's rows are worked out again after every key, click and machine event but a live tab's stream (`MachineEvent::Stream`, a frame at a time, which changes none of them), rather than at chosen moments: the agent, the account, the place and the focused issue change through keys with no action of their own, and the work is small.
- **The relay** (`machines/send.rs`, `app/machines/relay.rs`): the dialogs, their checks and the clone dialog send through the relay of a script's `--machine` (its connection, `boot`, caps, log and errors are in Commands for scripts and agents › Starting work on a machine); `Then` says whose answer it is: a client's request, a check, a dialog or the clone dialog.
  - A machine that restarted between the check and the start answers `stale-boot`, and the dialog says `vps restarted; nothing was started there`.
  - **Caps of the dialogs' own requests**: `new-tab`, `issue sources` and `flow list` 15 s; `account list --check` 60 s, the cap of the removal check, since each login is asked; `clone` 30 minutes.
  - **The log** of a `clone` also says how many files and how many bytes, never a URL or a file's content. Files that cannot be read here, or listed, are logged by the kind of failure alone (the `io::ErrorKind`, or `git`), since git's stderr and the error name the file; the dialog shows the error cut like the machine's texts. A flow started on a machine is logged by the machine and the project's id there, not by the flow's name, which comes from the machine and may be 65,536 characters long.
  - **`start-with` stays `start-with`** (`Send::StartWith`): a client's `start-with` with `machine` (what `start --model … --machine` sends) reaches the machine under its own name, so the model, mode and effort are never ignored there, by the contract's rule that a behaviour that must not be ignored has its own operation.
- **Waiting and the selection** (`app/machines/selection/awaited.rs`): while a dialog waits it says `starting on vps…` and takes no keys or clicks, as a local start with a worktree does. A refusal stays red in the dialog, cut like the tracker's texts; a blank one, or a check that failed without a word, says `vps gave no reason`, so an error is never an empty line. A machine that left before its answer came still ends the wait, with `vps is no longer listed`: a dialog left waiting takes no key, `Esc` included. On success the dialog closes, and the new tab or workspace is awaited and selected as `focus` does for a script (Commands for scripts and agents › Starting work on a machine), dropped by the same picks and limits; the dialogs send no `focus`, so a machine that has not reported yet is not refused, and nothing is then selected. A dialog closed while it waited still selects what started. A worktree made here (New workspace, or ` start ` on this computer) touches only the dialog that waits for it, the same project and branch, never one that waits for a machine: one that ends after its dialog was left neither closes nor colours the next one. **Each answer finds only its own dialog**: the request goes with a key (`Then::Dialog`), which the dialog keeps in its `RunOn` (`awaiting`) while it waits, so the answer of a dialog that was closed, arriving while another waits on the same machine, neither closes nor colours the new one.
- **A chosen machine that goes down stays chosen** (`RunOn::kept`), drawn `● vps · unreachable`, and ` start ` then answers the link's `unavailable` in red. Dropping the choice back to this computer was rejected: a start pressed a moment later would run here, where the user did not ask for it.
  - **One that leaves the list is not swapped for this computer either**: removed in Settings, or edited so that its link is a new one, or the last machine gone. Nothing is chosen then (`lost`), the row says why in red (`vps is no longer listed`, or `vps changed in Settings; choose it again` when a machine of that name is listed again), and ` start `, ` start a flow `, the naming step's start and New workspace's submit start nothing and say it; ` schedule ` stays hidden. Only the user's next choice ends it. Start flow keeps the machine's flows and accounts until then (` edit ` hidden, no warning about this computer's repository, and from an issue its prompt row still `from the machine's template …` and closed to typing, which choosing the machine again would throw away), and lists this computer's only once this computer is chosen. The ` run on… ` picker opens with no row highlighted, so `Enter` and ` choose ` choose nothing, however often, until an arrow or a letter moves to one.
- **Issues** (`app/issues_dialog/run_on.rs`): ` start ` (and the naming step's) sends `start` with the issue's key and its `source`, not its URL, so the machine reads it with its own tracker and builds the prompt with its own template (the URL by default), which the `prompt` row says (`from vps's template (the issue's URL by default)`) instead of showing this computer's; the branch and the workspace's name come from the naming step here, as `worktree` and `workspace_name`; the agent's modes and command are the machine's. ` schedule ` is hidden while a machine is chosen: the queue starts work on this computer only. ` start a flow ` opens Start flow with the same machine chosen, which then sends the issue's key and source with an empty prompt. Its prompt row says the same `from vps's template …`, dimmed, and takes no typing, focus or paste: `flow run` refuses a prompt together with an issue, and the machine builds the prompt as Issues lets it, so text typed here would be lost without a word. Choosing this computer gives the prompt back as it was.
- **` open login tab `**: a `new-tab` in the project's workspace there, named `<agent> login`, running the agent's login command for the chosen account (its `AccountHome` login, with the account's variables through `accounts`), or a shell when the agent is not installed, so the user can install it. It is offered only when the project is there, since a tab needs a workspace; the dialog closes and the tab shows here. When the project there lists no workspace, nothing is sent and the dialog says `vps has no workspace of this project for the login tab`: a `new-tab` without a workspace opens in the one active there, maybe of another project, with the account's variables.
- **A project that left the machine** after the row was worked out: Start flow says `the project is not on vps` in red, as Issues does, and logs it without the path.
- **New workspace** (`app/new_workspace_there.rs`): the form keeps its size, the row using the free line under the worktree box. It sends `new-workspace` with the name, the project's id there and the worktree box.
- **A project that is not there**: the row says `not on vps · clone…`, and ` start ` (or the form's submit) opens **Clone <project> on <machine>** instead of starting.
  - **From and into**: the URL is the remote the identity comes from (`git::remote::identity_url`: `upstream`, else `origin`, else the first), without credentials, and editable. `upstream` makes the clone pair with this project but leaves `origin` there pointing at the upstream repository, where the user may not push; an ssh alias (`gh-work:acme/shop`) lives in this computer's `~/.ssh/config` and may not exist there, and git's error then says so. Editing the URL is the way out of both; a clone of the fork pairs only when the fork is the identity here too. The folder is the machine's `folder` from Settings, and the clone's name is the one `clone` gives it.
  - **Git-ignored files, copied only when ticked** (`git/ignored.rs`): `git ls-files --others --ignored --exclude-standard --directory --full-name` in the project's folder, read on a job. `--full-name` names each file from the repository's root (`git rev-parse --show-toplevel`), which is where the machine writes it, so a project in a subfolder of its repository copies `web/.env` to the clone's `web/.env` and not to its root; the files are read from that root too. With `--directory` an ignored folder is one entry ending in `/`, which is dropped, so `node_modules` and `target` are never offered or walked. Only regular files are offered (`symlink_metadata`), so a `.env` that links to `~/.ssh/id_rsa` is not. Every box starts unticked, since these are often secrets. A listing belongs to the opening of the dialog that asked for it (its key): one that comes late, from a dialog closed and opened again on the same project, is dropped, since it would untick what was ticked meanwhile.
  - **Caps**: 200 entries, 1 MiB per file and 8 MiB in all. Past the 200th, a dimmed line says `… and N more not offered (200 at most)`: the entries past it are only counted, never looked at, so a folder with many ignored files costs no `stat` each, and N may count a link or a special file the list would not have offered. A file past 1 MiB is listed with its size and `too big to copy`, and no box. The total counts only the ticked files, so many big ignored files listed first never hide a small `.env`: a tick that would pass 8 MiB is refused with `over the 8 MiB a clone takes`. The files travel inside the one `clone` request, base64, far below the protocol's 64 MiB message. They are read on a job when ` clone ` is pressed, only by a path of plain components, opened one folder at a time from the repository's root (`openat`, each folder with `O_NOFOLLOW`), so neither the file nor a folder on its way that became a link since the listing is followed out of the project, nor a FIFO put in its place waited on (`O_NONBLOCK`); checking a canonical path first and opening it after would leave a window between the two, and refused when a file grew past the cap since it was listed. The total is counted again with the sizes read: files that grew past 8 MiB in all since they were listed fail the clone here with `over the 8 MiB a clone takes`, before anything is sent, rather than crossing ssh to be refused there.
  - **The machine writes them** after `git clone` succeeded (Commands for scripts and agents › Cloning a repository): a field of `clone`, because no request writes files, and scp or sshfs would be a second channel from here to there, against the link's one way. ` skip files ` clones without them and ` back ` returns with nothing sent.
  - **Back to the dialog it came from**, with the machine still chosen, rather than starting at once: the user then sees the machine's accounts, agent and tracker before anything starts. ` back ` and `Esc` still work while it clones, since a clone may take long, and cancel nothing: the user asked for it and the machine is already at work, so the clone goes on to its end and files still being read are sent once read. They are the files ticked before ` clone `, sent with that clone only.
  - **Its result is a toast, never a dialog's note**: `cloned web-shop on vps`, with `· not copied: .env (it is already in the clone)` for files the machine could not write (three at most with `… and N more`, each cut at 60 characters; one with a blank path is left out, and a blank reason reads `vps gave no reason`), or `the clone on vps failed: …` cut at 60 characters; an answer that cannot be read as a clone's is a failure, `its answer could not be read`, as for the other requests, never a success that would say nothing of the files. The machine is named as it is called when the answer comes, found by its link, so a rename meanwhile shows. Handing the answer to whichever dialog was open for that project and machine found a new wrong case in each round of review (a dialog opened meanwhile, another machine chosen, the dialog closed, a stale `still cloning` in red), and the user may be anywhere by then. A failed clone leaves the clone dialog, if it is still open, ready to try again.
  - **A clone on its way** (`Machines::clones`, by key, link and project here): the `start` row of Issues, Start flow and New workspace for that project on that machine says `cloning on vps…`, a hint that goes away with the answer, and ` start ` (or the submit) does nothing meanwhile. A second clone would find the folder taken, and the machine may list the new project before it has written the files. Once it worked, a dialog open for that project on that machine has its own checks asked again for the new project (its trackers or flows, and for Issues and Start flow the accounts only if not read yet, since a clone changes none); with none open nothing is asked, since a dialog never asks for answers it does not show and the next one asks when it opens. The checks go to the machine on that link only: one that took its name may have another project under that id.
- **No feature for the new fields there**: a machine is linked only at an equal or newer release (Machines' links › Versions), so its server always knows `files`, `unwritten` and `agents`. The feature `machine-start` is for clients of this server: an older one would drop `machine` and start the work here.
- **Left out**: the queue on a machine (` schedule ` is hidden); starting from a project that is only on the machine (its own row in the sidebar), since the dialogs start from a project here; editing the machine's flows; installing an agent there, beyond opening a shell; `wait` with `machine` (follow the work there with `--remote`); Telegram's, Discord's and the TODO panel's sends to a machine.
- **Tests**: unit tests of the row, the clone form, the ignored list (folders, links, caps) and the written files (each refused path); app tests with the injected connector and a fake machine that answers `account-list`, `issue-sources`, `flow-list`, `start`, `flow-run`, `new-workspace`, `new-tab`, `clone` and `stale-boot` (`app/tests/machines/acting/run_on.rs` and its children); `tests/e2e/run_on.rs` with a second `Session` as the machine, its `HOME` in a temporary folder, its own fake `gh` and fake agents: `start`, `new-workspace` and `flow run` with `--machine`, cloning from New workspace with one ticked file (its URL rewritten to a local bare repository with `insteadOf` in that `HOME`'s `.gitconfig`), and an issue started on the machine from the window.
- **Not checked live**: a real sshd, a real tracker or agent login on a machine, and a big clone; only the fakes were.
