# Remote windows › Starting work on a machine

Part of [Remote windows](../remote-windows.md). How a machine's link, its snapshot, the pairing of projects and asking a machine work is in Remote windows › Machines' links; the `machine` field of the requests is in Commands for scripts and agents (Machines), and the copied files of `clone` in its topic Cloning a repository.

- **What it is** (#543, `machines/run_on.rs`, `machines/send.rs`, `machines/clone_form.rs`, `app/machines/run_on.rs`, `app/machines/relay.rs`, `app/machines/checks.rs`, `app/machines/selection/awaited.rs`, `app/control/relay.rs`, `app/issues_dialog/run_on.rs`, `app/start_flow_dialog/run_on.rs`, `app/new_workspace_there.rs`, `app/clone_on_machine.rs`, `issues/browser/run_on.rs`, `flows/start/run_on.rs`, `git/ignored.rs`, `git/clone/files.rs`, `ui/dialog/run_on.rs`, `ui/dialog/clone_on_machine.rs`): Issues, Start flow and New workspace get a `run on` row, `● this computer   ○ vps`. Choosing a machine sends that machine's server the request a script would send it (`start`, `flow run`, `new-workspace`), so what starts there belongs to that server, shows in the sidebar under the machine (Machines' links › What a machine has) and is seen here as A machine's tab. No request is new on the machine's side: it does what it does for its own window and scripts.
- **The row**:
  - It exists only while `config.json` lists a machine (`run_on_for` gives `None` otherwise), so without machines the three dialogs draw and behave as before; their snapshots did not change.
  - It lists this computer, then every machine in the order of Settings › Machines, with its icon. A machine that is not `linked`, or linked with no snapshot yet, is dimmed with why (`connecting…`, `not seen yet`, `unreachable`, or the link's reason through `hide_destination`) and cannot be chosen.
  - `this computer` is chosen when a dialog opens; the choice is never saved, since a machine chosen by habit would start work somewhere the user did not look.
  - Issues picks the machine through its ` run on… ` button and picker (`Pick::Machine`, the pattern of the account picker), since the row is drawn by the issue's page; Start flow and New workspace take a click on the row (`ui::RunOnRow`, shared by both).
  - **A project with no repository identity cannot run elsewhere**: the row ends with `— needs a git remote` and no machine can be chosen. The identity is the only way to pair the project here with one there, and a folder copied by hand would not stay in step. The identity is read on a job (Machines' links › A repository's identity), so a dialog opened in the first moments after a project opens says `needs a git remote` until the next machine event or action redraws the row; the e2e tests wait for `status` to show the identity first.
- **Where it starts there**: the project there is the first of the machine's snapshot whose `repo` equals this project's identity (any case), as the sidebar pairs them. The ids sent are the machine's, never the ones here. The `start` row then says `in its own worktree on vps, in ~/code/web-shop` or `in a tab on vps, in …`, from the same choice that is made here (the place picked for the issue, or whether the project is at a repository's root), and New workspace `in a workspace on vps, in …`. A place that is a workspace here has no pair there, so it stands for its project: the machine gets that project's id there and places the work as `start --issue --project` does.
- **Checks before starting** (`app/machines/checks.rs`): choosing a machine asks it `account list --check` and, when the project is there, what the open dialog reads for its id there (`Wanted`): `issue sources` for Issues and for Start flow from an issue, `flow list` for Start flow. Each is an ssh round trip of its own, so a dialog never asks for answers it does not show. They go over the relay below, and the dialog reads the answers:
  - **Accounts**: the account picker and Start flow's combos list the machine's accounts and its active ones, marked `(vps's accounts)`. Nothing is copied: what is chosen travels as the request's `accounts`, and the machine resolves the names.
  - **The agent**: `account list --check` answers `agents`, each agent the machine knows with its command and whether that command is on its server's `PATH` (a field added for this, Accounts and profiles). The row says `not installed on vps`, or `not logged in on vps` when the chosen account (or the agent's own login) is `signed-out` there and none of its token variables is in `tokens`, and offers ` open login tab `. Neither blocks ` start `: the server there was started by ssh with a short `PATH` (Remote windows › PATH), so an agent installed with npm or nvm can be missing for the server and present in the shell of the tab it opens. An answer without `agents`, or an `unknown` or `failed` login, says nothing.
  - **The tracker** (Issues, and Start flow from an issue): when `issue sources` there does not give the issue's source as `connected`, the row says what is missing (`vps has no GitHub token for web-shop`, or the machine's own `missing` or `reason`) and ` start ` sends nothing, since the machine would refuse `start --issue` anyway. A check that failed blocks with its reason; one still waiting does not.
  - **The flows** (Start flow): the list is the machine's own `flow list`, turned into the dialog's listing, so what is drawn is what runs there; a built-in flow edited here could differ from the machine's, and a flow of your own here may not exist there. ` edit ` is hidden while a machine is chosen: editing the machine's flows from here is left out.
  - **A cache in each `Held`**, in memory only, per check and per project there, kept by the link's `era`: a snapshot with another `boot` makes the answers stale, and choosing a machine in a dialog empties its cache and asks again, so each opening reads fresh answers while the dialog itself reuses them. A machine is never asked the same check twice at once.
  - The dialog's rows are worked out again after every key, click and machine event but a live tab's stream (`MachineEvent::Stream`, a frame at a time, which changes none of them), rather than at chosen moments: the agent, the account, the place and the focused issue change through keys with no action of their own, and the work is small.
- **The relay** (`machines/send.rs`, `app/machines/relay.rs`): one function sends any of these requests to a machine, for a dialog, a check, the clone dialog or a client's request (`Then`).
  - Only a `linked` machine is asked, over a connection of its own per request, on a job, as Asking a machine does; the asking code is shared with #544's actions and #547's stats (`spawn_ask`).
  - Each request carries the `boot` of the machine's snapshot, so a machine that restarted between the check and the start answers `stale-boot`, and the dialog says `vps restarted; nothing was started there`. `machine`, `focus`, `caller`, `view` and the waits are taken out: the machine never relays again, and what it starts never takes the focus of its own window.
  - **Caps** (`Send::timeout`): `start`, `flow run` and `new-workspace --worktree` 10 minutes, the cap of removing a worktree, since git and the project's setup run there; a plain `new-workspace`, `new-tab`, `issue sources` and `flow list` 15 s; `account list --check` 60 s, the cap of the removal check, since each login is asked; `clone` 30 minutes. At the cap the answer is `it did not answer in time` and nothing is retried; what runs there goes on, and the next snapshot shows it.
  - **The log** says `relay` with the machine's name, the verb and the project's id there, and for `clone` how many files and how many bytes, never the destination, a URL or a file's content.
  - Errors keep the machine's code and message, cleaned and through `hide_destination`.
  - **`start-with` stays `start-with`** (`Send::StartWith`): a client's `start-with` with `machine` (what `start --model … --machine` sends) reaches the machine under its own name, so the model, mode and effort are never ignored there, by the contract's rule that a behaviour that must not be ignored has its own operation.
- **Waiting and the selection** (`app/machines/selection/awaited.rs`): while a dialog waits it says `starting on vps…` and takes no keys or clicks, as a local start with a worktree does. A refusal stays red in the dialog. On success the dialog closes, and the new tab or workspace is selected as soon as a snapshot lists it, since the answer comes before the snapshot that shows it. The awaited selection is dropped when the user picks anything else, when the machine's `boot` changes or it is removed, and after 30 s. A dialog closed while it waited still selects what started. **Each answer finds only its own dialog**: the request goes with a key (`Then::Dialog`), which the dialog keeps in its `RunOn` (`awaiting`) while it waits, so the answer of a dialog that was closed, arriving while another waits on the same machine, neither closes nor colours the new one.
- **A chosen machine that goes down stays chosen** (`kept`), drawn `● vps · unreachable`, and ` start ` then answers the link's `unavailable` in red. Dropping the choice back to this computer was rejected: a start pressed a moment later would run here, where the user did not ask for it.
- **Issues** (`app/issues_dialog/run_on.rs`): ` start ` (and the naming step's) sends `start` with the issue's key and its `source`, not its URL, so the machine reads it with its own tracker and builds the prompt with its own template (the URL by default), which the `prompt` row says (`from vps's template (the issue's URL by default)`) instead of showing this computer's; the branch and the workspace's name come from the naming step here, as `worktree` and `workspace_name`; the agent's modes and command are the machine's. ` schedule ` is hidden while a machine is chosen: the queue starts work on this computer only. ` start a flow ` opens Start flow with the same machine chosen, which then sends the issue's key and source with an empty prompt.
- **` open login tab `**: a `new-tab` in the project's workspace there, named `<agent> login`, running the agent's login command for the chosen account (its `AccountHome` login, with the account's variables through `accounts`), or a shell when the agent is not installed, so the user can install it. It is offered only when the project is there, since a tab needs a workspace; the dialog closes and the tab shows here.
- **New workspace** (`app/new_workspace_there.rs`): the form keeps its size, the row using the free line under the worktree box. It sends `new-workspace` with the name, the project's id there and the worktree box.
- **A project that is not there**: the row says `not on vps · clone…`, and ` start ` (or the form's submit) opens **Clone <project> on <machine>** instead of starting.
  - **From and into**: the URL is the remote the identity comes from (`git::remote::identity_url`: `upstream`, else `origin`, else the first), without credentials, and editable. `upstream` makes the clone pair with this project but leaves `origin` there pointing at the upstream repository, where the user may not push; an ssh alias (`gh-work:acme/shop`) lives in this computer's `~/.ssh/config` and may not exist there, and git's error then says so. Editing the URL is the way out of both; a clone of the fork pairs only when the fork is the identity here too. The folder is the machine's `folder` from Settings, and the clone's name is the one `clone` gives it.
  - **Git-ignored files, copied only when ticked** (`git/ignored.rs`): `git ls-files --others --ignored --exclude-standard --directory --full-name` in the project's folder, read on a job. `--full-name` names each file from the repository's root (`git rev-parse --show-toplevel`), which is where the machine writes it, so a project in a subfolder of its repository copies `web/.env` to the clone's `web/.env` and not to its root; the files are read from that root too. With `--directory` an ignored folder is one entry ending in `/`, which is dropped, so `node_modules` and `target` are never offered or walked. Only regular files are offered (`symlink_metadata`), so a `.env` that links to `~/.ssh/id_rsa` is not. Every box starts unticked, since these are often secrets.
  - **Caps**: 200 entries, 1 MiB per file and 8 MiB in all. Past the 200th, a dimmed line says `… and N more not offered (200 at most)`. A file past 1 MiB is listed with its size and `too big to copy`, and no box. The total counts only the ticked files, so many big ignored files listed first never hide a small `.env`: a tick that would pass 8 MiB is refused with `over the 8 MiB a clone takes`. The files travel inside the one `clone` request, base64, far below the protocol's 64 MiB message. They are read on a job when ` clone ` is pressed, without following a link (`O_NOFOLLOW`) nor waiting on a FIFO put in its place (`O_NONBLOCK`), only by a path of plain components, and refused when a file grew past the cap since it was listed.
  - **The machine writes them** after `git clone` succeeded (Commands for scripts and agents › Cloning a repository): a field of `clone`, because no request writes files, and scp or sshfs would be a second channel from here to there, against the link's one way. ` skip files ` clones without them and ` back ` returns with nothing sent.
  - **Back to the dialog it came from**, with the machine still chosen and its checks asked again, rather than starting at once: the user then sees the machine's accounts, agent and tracker before anything starts. Files the machine could not write are named in that dialog's note (`cloned on vps · not copied: .env (it is already in the clone)`). A failed clone stays red in the clone dialog. ` back ` and `Esc` still work while it clones, since a clone may take long; its answer then goes to whichever of the dialogs is open.
- **No feature for the new fields there**: a machine is linked only at an equal or newer release (Machines' links › Versions), so its server always knows `files`, `unwritten` and `agents`. The feature `machine-start` is for clients of this server: an older one would drop `machine` and start the work here.
- **Left out**: the queue on a machine (` schedule ` is hidden); starting from a project that is only on the machine (its own row in the sidebar), since the dialogs start from a project here; editing the machine's flows; installing an agent there, beyond opening a shell; `wait` with `machine` (follow the work there with `--remote`); Telegram's, Discord's and the TODO panel's sends to a machine.
- **Tests**: unit tests of the row, the clone form, the ignored list (folders, links, caps) and the written files (each refused path); app tests with the injected connector and a fake machine that answers `account-list`, `issue-sources`, `flow-list`, `start`, `flow-run`, `new-workspace`, `new-tab`, `clone` and `stale-boot` (`app/tests/machines/acting/run_on.rs` and its children); `tests/e2e/run_on.rs` with a second `Session` as the machine, its `HOME` in a temporary folder, its own fake `gh` and fake agents: `start`, `new-workspace` and `flow run` with `--machine`, cloning from New workspace with one ticked file (its URL rewritten to a local bare repository with `insteadOf` in that `HOME`'s `.gitconfig`), and an issue started on the machine from the window.
- **Not checked live**: a real sshd, a real tracker or agent login on a machine, and a big clone; only the fakes were.
