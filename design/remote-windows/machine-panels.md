# Remote windows › The side panels on a machine

Code: `machines/follow.rs`, `machines/heard.rs`, `app/machine_links/panels.rs`, `app/machine_links/panels/` (#546)

With a machine's workspace shown, Changes and Files read the machine: what each panel shows is in Changes panel › A machine's workspace and Files panel › A machine's workspace. This topic is how they reach it.

- **A connection of its own per stream and per one-off request** (`machines/follow.rs`): `Follow` connects with `Remote::connect(Use::Link)`, from the destination alone like the link, writes one `Request` with the snapshot's `boot`, and hands on each answer until the stream ends. It reads as the link does (`link::listen`: frames and window messages skipped, the end at `Detached`, `Shutdown` or `Restart`); `once` hands on one answer and ends.
  - **Why not the link's connection**: answers carry no id, so a stream's lines could not be told from the snapshots of `watch` or from another answer, the reason of Asking a machine. With Files open there are at most three (the tree, the open file, a search), with Changes one plus one patch; the user's `ControlMaster` makes them cheap (see Commands on another machine).
  - **A piece for any one-request stream**: `Follow` knows nothing of changes or files, only a request, its answers and their end. A machine's tab (`machines/stream.rs`, see A machine's tab) is not one: it holds a view, its surface, its copies and its orders on four connections, so it has its own. Both read with `link::listen` and take an answer, or its refusal, with `link::replied`; each keeps what it says of an answer it cannot read.
  - **Never on the loop**: connecting and reading happen on the `Follow`'s thread under `panics::job`; a bug ends it with `cornercase hit a bug`. Dropping a `Follow` stops it: it kills the ssh while it connects (a `Killer` of its own, since the link's `Control` keeps its own private) or cuts the line once it holds one, so the machine sees the stream end. A stream lasts as long as it shows, so it has no cap; a one-off request has none of its own either: the machine caps its work (`changes-file` at 30 s) and ssh's keepalive (`ServerAliveInterval`) ends a dead connection within about 15 s.
- **The machine's pace**: `changes` pushes a summary when something changed (it looks every second), `files-list --follow` lists every 2 s and `files-read --follow` checks the file every second. Asking from here on a timer was rejected, as in #477: an ssh connection per tick and per panel.
- **Reopen rather than steer**: another mode, or another set of open folders, ends the stream and starts one with the new request (`follow_wanted` compares the request it wants with the one running). `changes-mode` on the open stream would answer on the same lines as its summaries.
- **What comes back is cleaned** (`machines/heard.rs`) after it is parsed, field by field, with one of four rules, except paths:
  - names, errors, the base, digests, languages and the query: `link::clean`, one line of at most 200 characters, as the link's text (so a search's answer is matched with the query asked, not the cleaned one it echoes);
  - the folders a read or a listing names (`file`, `dir`), never asked for again: `link::clean_path`, hidden and control characters dropped, at most 4,096 characters, never joined into one line;
  - a file's text: line breaks and tabs kept, every other control character (`ESC`, `BEL`, a lone `\r`) and hidden character dropped, so nothing from there writes a sequence to this terminal. A local file only relies on the drawing, which drops control characters; a machine's text loses them before it is kept.
  - code of one line (a diff line, a gap line, a highlighted segment, a search hit): tabs kept and every other control or hidden character dropped, line breaks included, since one would shift the columns, the selection and the emphasis, and add lines to a copied hunk.
  - **Paths are kept as the machine wrote them** (a file's and a rename's old path, a gap's and a read's path, a folder's path, an entry's name, a search's names and files): they go back in requests (`changes-file`, `changes-gap`, `files-list`'s folders, `files-read`, a result opened) and in **copy path**, and a cleaned one asks for another file or none (`a\u{200b}b.txt` asked as `ab.txt`). They are cleaned where they are drawn instead (`text::visible`, in `ui/files.rs` and `ui/changes.rs`, for this computer's panels too): no hidden character reaches the screen or takes room when a name is cut, and a search's lit letters move with the characters left (ratatui also drops control characters). A copy goes in OSC 52's base64, so a path's characters write no sequence here. Limit: the workspace's own path comes from the snapshot, which the link cleans, so **copy path** under a workspace folder with a hidden character keeps that folder cleaned.
  - Counts are capped only where the machine caps them (`disk::MAX_ENTRIES`, `search::MAX_NAMES`, `MAX_MATCHES`, `diff::MAX_LINES`), plus a gap's unchanged lines, cut to `diff::MAX_LINES` like a patch: the machine bounds a gap only by the 1 MiB of the file it reads, which with short lines is far more than a diff holds. The panel says what was cut (see Changes panel › A machine's workspace). A style index out of the table draws plain, an incoherent hunk is cut to what it holds, and JSON it cannot read is a refusal; none panics. An image's base64 is not cleaned: it is never drawn, and a stray character fails its decoding.
- **`boot` in every request**, as for actions: a server there that restarted answers `stale-boot`, which drops what the panel showed, since its ids may now name another workspace. A snapshot with a new `boot` changes the panel's aim anyway.
- **When the streams live** (`App::sync_remote_panels`, on every refresh): while the panel shows a machine's workspace, a window is attached and the machine is `linked`.
  - Choosing anything else (here, another workspace, another machine, the same one with another `boot`) drops both panels' state and streams; closing a panel or switching to another side panel drops that panel's. Nothing is saved in `session.json`.
  - With no window, or the link down, the streams go and the state stays, to be drawn with the machine's notice; they reopen when a window or the link comes back. Removing the machine or changing its destination drops everything at once (`drop_unheld_panels`).
- **Retries**: a stream that ends while the link is up is tried again after `remote::backoff`, counting failures until something is heard, and the panel says `reconnecting in N s`. Each stream counts its own failures (Changes, the tree, the viewer), so a viewer whose connection ended leaves the tree's stream open, and the note follows what shows: the viewer's while a file is open, else the tree's. A link that is down retries on its own schedule and the panel says what its card says. A one-off request is not retried on its own: a patch waits for its digest to change or for its file to be unfolded again by hand, a search for another query.
- **The log** says `panel stream` with the machine's name, the request's name and the stream's id, never a path from there or the destination.
- **Rejected**: a request on this server that reads a machine's panels for clients. The side panels are the window's, and a client reads a machine with `cornercase --remote DESTINATION changes|files`.
- **Tests**: `Follow` through an injected `Connect` (socket pairs), the app with a fake machine answering `changes`, `changes-file`, `changes-gap`, `files-list`, `files-read` and `files-search` through the injected connector, and `tests/e2e/machine_panels.rs` with a second `Session` as the machine. The e2e drop needs a gate before the fake `ssh` that exits 255 once a file exists, then `kill-server` there: killing only the server lets the next connection's proxy start it again.
- **Not checked live**: a real sshd, `ControlMaster`, a big image over a slow link.
