# Discord

Code: `discord/`, `app/messenger/pairing.rs`, `app/messenger/every.rs`, `app/messenger/forum.rs`, `app/messenger/forum/`, `ui/forum.rs`, #265, #437

- **Why**: a Telegram bot needs a Telegram account, and many developers already live in Discord all day (their teams', their projects' servers). It does what the Telegram bot does (see Telegram) through the shared `messenger/` and `app/messenger/` code: one `Via::Discord`, its arms in `messenger/mod.rs`, and nothing in the app that names the platform but the pairing job and the forum's setup (below). Telegram and Discord can be paired and away at the same time, each with its own `Messenger`.
- **One app per user**: the user makes an application in the Discord Developer Portal, turns on **User Install** and pastes its bot token (`discord_bot_token` in `secrets.json`; `discord.json`, 0600, keeps the bot's name and the chat like `telegram.json`). Like Telegram, no bot run by cornercase: every message would go through it, and its token would reach every user's shells. `CORNERCASE_DISCORD_API` points the REST calls at another server, for tests.
- **Pairing by the app's owner, without a code**: Telegram pairs whoever sends `/start <token>`; Discord has no link that carries a payload to a DM, and a bot can only message someone it shares a server with or who installed it. A user install adds the app to the owner's own account, after which the bot can open a DM with them without any shared server (checked live with a prototype). So the phone row opens the Remote dialog with a QR of the install link (`discord::install_link`: `oauth2/authorize?client_id=…&integration_type=1&scope=applications.commands`), and while that dialog is open a job (`app/messenger/pairing.rs`, on `app/messenger/every.rs`, the periodic job any messenger dialog polls with: every 3 s, one in flight) asks Discord for the app's owner (`/oauth2/applications/@me`, the team's owner for a team app), opens a DM with them and sends the welcome there. Until the app is installed Discord answers `50007` (cannot message this user), which keeps waiting quietly, and a rate limit (429) waits quietly too, for as long as its `retry_after` asks before the next try (`messenger::Owned::Later`), instead of showing in the dialog and retrying every 3 s; any other error is shown in the dialog and logged once per distinct error. Success saves the chat, closes the dialog and toasts `Discord connected with <name>`; the bot already sent the welcome, so the app does not send it again. Only the owner's DM is heard: a message from anyone else, or in a server, is ignored (forum mode, below, adds the owner's posts in the forum, and nothing else). A code typed into the DM was rejected: the owner is the only person who can pair anyway, since only they hold the token, so the code proved nothing and cost a step on the phone.
- **The app's id is read from the token**: its first segment is the bot's id in base64, which is also the application's id, so the install link and the webhook for ephemeral answers need no call; a token that does not decode falls back to `/users/@me` for the webhook and shows `the token does not name its app` instead of a QR.
- **A private app, said in the window** (`discord::advice`): a public bot can be added by anyone who finds its install link or id; it would then share servers with strangers and receive their DMs. The bot only listens to its owner's DM, but a private app (**Public Bot** off, which Discord accepts only once **Install Link** is **None**) leaves nobody else a way in, and **User Install** is what lets the owner pair at all. The guide lists the steps, and the window says them too: the token field's label names the three settings, and the token check, every pairing read and one read when the link starts (at server start and after a new token; `App::read_advice`, a job, never polled, Discord only) of `/oauth2/applications/@me` look at `bot_public` and `integration_types_config` (key `1`, user install). A public app or one without user install puts a short line in the `bot` row's note in place of `connected` (`turn on User Install in the Developer Portal`, else `public app: Install Link to None, then Public Bot off`), after `away · ` while away (`connected · away…` would push the advice off the row), short enough that both fit beside a ten-letter bot name at the 110-column capture width, and at the bottom of the pairing dialog; the next read after fixing it in the portal clears it, without pasting the token again. It never blocks pairing: a public app still works, and the owner may keep it public on purpose. A read that fails says nothing and changes nothing, whether it is the token check's, a pairing read's or the link's (`messenger::Advice::Unread`, apart from `Read(None)`, a read that found nothing to advise), so a 429 while pairing does not make the advice flicker, and the advice is kept in memory only: the read at the link's start brings it back after a server restart, so an already paired public app does not show `connected`.
- **The Gateway** (`discord/gateway.rs`): Discord delivers messages only over its WebSocket Gateway (no long polling), so one listener thread per bot opens it (`/gateway/bot` for the address, `v=10`, JSON, TLS through tungstenite's rustls with webpki roots, already a dependency for browser access) with the `DIRECT_MESSAGES` intent alone (`1 << 12`). Message content arrives in DMs without the privileged Message Content intent, so the user never has to turn one on in the portal; only forum mode asks for more (below). It identifies on hello, sends heartbeats at the interval Discord gives (the first after a random part of it, as Discord asks), beats at once on op 1 without waiting for the last beat's acknowledgement (only the scheduled beat checks it, so an op 1 right after a beat is not taken for a dead connection), and reconnects when a scheduled beat finds the last one unacknowledged. A dropped link, op 7 (reconnect) and op 9 with `d: true` resume the session (op 6 with the last sequence, at `resume_gateway_url`), so nothing sent meanwhile is lost; op 9 with `false`, 4007 and 4009 identify anew after 2 s; 4004 is a refused token (`Event::Rejected`, like Telegram's 401); 4010-4014 (bad intents, sharding, API version) stop the listener with one problem shown, since retrying cannot fix them, except a 4014 in forum mode (below). Resuming rather than identifying each time also because Discord allows 1,000 identifies a day per bot. Other failures back off from 1 to 60 s with `messenger::link::backoff`; messages older than the listener's start are dropped, as Telegram's are.
- **Buttons are acknowledged on the Gateway thread**: Discord shows `This interaction failed` unless a press is answered within 3 s, and the sender may be waiting out a rate limit, so the listener acks each press itself (callback type 6, deferred update: nothing visible changes) before handing it to the app. The ack has its own 3 s limit (`ACK_TIMEOUT`) rather than the 20 s of other calls: past 3 s Discord refuses it anyway (`10062`), and the thread neither reads nor beats meanwhile; a rate limit of at most a second is waited out and the ack tried once more. The texts the app answers a press with (`stale`, a refusal) go as ephemeral follow-ups (flag 64) through the interaction's webhook, seen only by the owner; an empty answer sends nothing.
- **Messages**: 2,000 characters, in Discord's Markdown (`discord/markdown.rs`, the `Markup` for this platform): bold as `**`, a screen in a fenced block (a ``` inside it broken with a zero-width space), split at 1,900 by blocks without breaking a fence (closed and reopened with the same opener; a `~~~` fence, which Discord does not draw as code, becomes one of backticks, with the ``` inside it broken the same way), at most four messages and `*… the rest is in cornercase*`, like Telegram's. No mentions are parsed (`allowed_mentions` empty), so an agent writing `@everyone` pings nobody.
- **Buttons**: at most 5 per row and 5 rows per message, labels cut at 80; a row of more is split, and rows past the fifth go in following messages (`…`) with the rest, so `/status` with many agents keeps every button. A send that fails part way remembers how many calls went out and the ids they got (`discord::Sent`), so a retry after a rate limit does not send the first messages twice. Every message of a send is reported (`Transport::more`, one `Sent` event each with the send's tag, which is kept until 256 newer ones push it out rather than dropped on the first), so a reply to a continuation routes like a reply to the first message. Editing and removing buttons only touch the one message the order names, with the first five rows of its keyboard, never the rest of its send: `/status` is never edited, so the buttons of its continuations stay and still act on what they name; a press on a continuation of the agents to pick for a held text edits that continuation, and the buttons left on the other messages then find the text delivered and do nothing.
- **Slash commands** (`Order::Commands`, sent when a link starts, as Telegram's `setMyCommands`): the first version had none, and `/status`, `/new`, `/away` and `/back` were typed as text. Testing it live showed why that fails: Discord's client autocompletes a typed `/` with the slash commands of every other app the user has (`/new` became `/wordle`), so the message could not be sent. So the bot registers the four from `messenger::COMMANDS` with one bulk overwrite (`PUT /applications/{app}/commands`, the app's id from the token), which also drops a command removed later, each with `integration_types: [1]` (user install, the only way the app is installed) and `contexts: [1]` (only the DM with the bot, so they never show in servers or other DMs). A failure is logged like any undelivered order and the commands keep working as typed text where the client lets them through. On the Gateway a command is an `INTERACTION_CREATE` of type 2, turned into an `Update::Message` whose text is `/<name>` from the invoking user in that channel, so the app handles it exactly like the typed one (paired check, closing the open question). Discord shows `The application did not respond` unless it is answered within 3 s, so the listener acknowledges it on its own thread like a press, with a deferred ephemeral message (type 5, `flags: 64`), and once the app has the update deletes that `thinking…` placeholder (`DELETE /webhooks/{app}/{token}/messages/@original`, the app's id from the interaction), so the chat holds only the bot's ordinary messages. Answering with the bot's reply itself (type 4) was rejected: the app makes its reply later, on the sender thread, and a message sent through the interaction's webhook is not one the rest of the code edits and replies to by its channel and id like the others. Ephemeral, so if the deletion fails only the user sees the leftover placeholder. A command that cannot be acknowledged comes in all the same.
- **Replies**: a reply to the bot's message routes to its pane, as on Telegram. Discord has no forced reply (`Via::forces_reply`), so a message that asks for one (`ask`: the prompt of `/new`, a branch's name, **write**) ends with a small `reply to this message` line, cut so the whole stays within 2,000 characters, and the bot remembers it as the open question (`Messenger::open_ask`). In a DM the natural answer is a plain message, which without this would go to the only agent running (typing the new agent's prompt into the old one) or ask which agent. So a plain message that is not a command and replies to nothing routable answers the open question; the question is closed once answered, replaced by a newer one, by any command, by a reply that answers it, by any newer bot message about an agent (a notice, a screen, a refusal: a plain message sent after `✓ codex finished` is meant for codex, not for the prompt of a `/new` asked before it, which would start an agent), and after ten minutes (`ASK_FOR`), so a message sent long after is not taken for an answer. Telegram keeps its forced reply and never has an open question.
- **Rate limits** are per route on Discord: a 429 gives its `retry_after`, which the shared sender waits out (at most 60 s, three tries) before trying that order again; the bot sends one order at a time, so it never needed to track buckets ahead.
- **Not end-to-end encrypted**: Discord keeps what agents write, like Telegram; the guide says so. Texts and the token are never logged, the token is scrubbed from errors and left out of `Debug`.
- **Checked**: live, a prototype paired by owner over a user install and talked over the Gateway, and the Gateway's hello was read from `wss://gateway.discord.gg`; the rest (sending, buttons, acks, slash commands, follow-ups, rate limits, resuming, close codes) only against fakes: `discord::tests` and `app::tests::control_requests::discord` (pairing through `50007` then success, a refused token in the dialog, a message and a button round trip, `/new` answered with a plain message while another agent runs, a reply to a continuation, `away` with one platform unpaired, `o` with both and with none, the advice read when a link starts and cleared when it finds the app private, kept when a pairing read fails, shown with away in the `bot` row); the Gateway against a local fake WebSocket (`discord::gateway::tests`: identify, heartbeats and op 1, a dead connection, resume on op 7 and op 9, identify anew on op 9 `false`, 4007 and 4009, refused tokens and intents, recovery, messages before the start, closing on stop).

## Forum mode (#437)

- **Why**: with several agents at work, every notice, screen and reply lands in the one DM, so following one line of work means scrolling past the others, and a plain message goes to the only agent or asks which. Forum mode (`discord_forum` in `config.json`, off by default; the **forum mode** row under **phone**) gives each workspace its own post in a forum channel of a server of the user's, with a status tag, and a message in a post goes to that workspace's agent. A forum was chosen over plain threads in a text channel: its list is a card per post ordered by activity, tags filter it, each post has its own notifications, and it reads well on the phone. The DM does not change and stays the place of `/status`, `/new`, `/away`, `/back`, the welcome and whatever belongs to no workspace; with the mode off nothing the bot sends or reads differs from before.
- **cornercase joins only the server the user picks, for forum mode**: the DM needs no server (see Pairing), and before this mode the bot never was in one. A forum needs a server, and an app cannot make its own (Discord stopped apps from calling `POST /guilds` on 15 July 2025), so the user makes one (Discord's **+ › Create My Own**) and adds the app to it with a second install link (`discord::forum::guild_install_link`: `integration_type=0`, `scope=bot applications.commands`, and the permissions the forum needs: View Channel, Manage Channels, Send Messages, Send Messages in Threads, Manage Threads, Read Message History, and Add Reactions for the 👍). A private app stays the advice: only its owner can add it to a server, and the bot listens in one forum of one server, to one person.
- **The setup is a dialog that ticks itself** (`Overlay::Forum`, `app/messenger/forum/setup.rs`, `ui/forum.rs`): turning the row on in the window opens it, and while it is open a job on `app/messenger/every.rs` (every 3 s, one in flight, a 429 waited out quietly, an error logged once per distinct error, like pairing) reads Discord (`Bot::set_up`) and ticks four steps: **Guild Install** (`integration_types_config["0"]` of `/oauth2/applications/@me`), **Message Content Intent** (its `flags`, bit 18 or 19, and no refusal since the link last started, below), **the app is in your server** (`/users/@me/guilds`, then each one's `owner_id`, which must be the app's owner, the team's owner for a team app, so a server a friend added the app to does not count; read only once Guild Install is on) and **the forum channel**. The user never pastes anything again: they change the portal or add the app, and the next read sees it. While no server is found the dialog shows the install link as a QR and as text, with `no server yet? In Discord: + › Create My Own › For me and my friends`; several servers are listed and a click picks one, a single one is picked by itself. A `50013` names the missing permission and shows the link again to authorize it; `10004` or `50001` (the app was removed from the server) forgets the server picked and goes back to that step. Once the forum is there, it is saved, the dialog closes, a toast says `Discord forum ready in <server> › #cornercase` and the link restarts with the forum's intents. **Done** closes it with the mode still on and waiting (the row's note names the first step left); **turn off** turns the mode off, since from the window the row's `Enter` otherwise reopens the dialog until the forum is ready. Turned on through `config` or the file, nothing opens: the row says `enter sets it up` until Discord is read, and the setup then goes on in the background (next point). The dialog closes when the mode is turned off with it open, by `config`, another client or the file, so it stops reading and no forum is made with the mode off.
- **The same reads go on without the dialog**: while the mode is on, the forum is not ready and a chat is paired, the job keeps reading every 30 s with the dialog closed (every 3 s while it shows), so a script or another UI that turns the mode on through `config` sees the first step left in `status --app`'s `forum.pending`, and the forum is made without the window as soon as the steps are done and there is one server, with the same toast. Picking one of several servers stays in the window, since it is a choice and the socket has no request for it yet; `pending` says `pick the server for the forum` meanwhile. A read is dropped when it lands after the mode was turned off (no `ready` toast after the `off` one), and the row's note and the settings revision change only when a read changes what the row shows, so a dialog left open does not wake every client every 3 s. A token of another bot forgets the forum and its posts with the paired chat (`Messenger::forget_forum`): the old server, channel and tags belong to the old app, which the new bot cannot use, and setting the forum up again starts from the first step. Without a paired chat nothing is read in the background, since the row and the `config` key exist only with one; reading starts once the chat is paired.
- **The channel** (`discord/forum.rs`): one forum channel named `cornercase` (`type 15`), made by the bot only once the intent is on (made earlier, the link would only be refused), private: an overwrite denies View Channel to `@everyone` and allows the forum's permissions to the bot, since the server may have other members, and the server's owner sees it anyway. Posts archive after a week without activity (`default_auto_archive_duration`, the longest), and sending to one unarchives it. When `discord.json` has no forum, or Discord says the saved one is gone (`10003`), the server's channels are searched for a forum named `cornercase` before making one, so losing the file does not make a second channel; a forum missing a tag gets it added beside the tags it has (`PATCH available_tags`). Guild, server name, channel and the three tag ids are saved in `discord.json` (`Saved.forum`, optional, so `VERSION` stays 1).
- **Tags**: `working`, `needs you`, `done`, one applied at a time, as names alone: the name already says the state, and a tag's emoji is a separate field that takes a Unicode emoji, not the sidebar's `!` and `✓`. A post's tag is computed on the workspace's agents (`forum/tags.rs`): `needs you` if one waits or failed, else `working` if one works, else `done`. A new result must hold for a second (`NOTIFY_AFTER`, the notices' settle) before the `Retag` goes out, a change undone within it sends nothing, and each post keeps at most one pending tag, the latest; so a busy workspace makes at most one edit a second per post. Tags change whether or not away is on (an edit notifies nobody); only messages follow away. A post restored after a restart is retagged once on its first settled read, even if unchanged, so it is right after a restart.
- **One post per workspace, not per agent**: a workspace is the line of work the user switches between, and its agents (a coder and a reviewer, a flow's team) belong to the same thread of talk; every notice already names its agent (`! claude needs you · …`). A post is made lazily, by the first message about one of its agents (`Order::Post`: the thread's name, its tag and that message as its first, buttons included), never ahead. Its title is `<project> › <workspace>` (both always, so a second workspace does not change the first one's form), cut at 100; it is not renamed when the workspace is (Discord allows two renames of a channel in ten minutes). What goes to the post is any message about a pane (`Route::Pane`) that replies to nothing: notices, screens; replies to the user's own messages go where the message was, except `/new`'s `Started … in …`: it is about the new pane, so it goes to the workspace's post (making it if needed) like a notice, and the DM, where `/new` was typed, gets a line replying to it, `Started <agent> in <place>: <the post's link>`, sent once the post exists, so the user is not left wondering where the agent went; if the post cannot be made, `Started` goes to the DM and the line is dropped, as there is nothing to link to. Until Discord answers with the thread's id (`Event::Posted`), later messages of that workspace wait in the app and then go in order; if the post cannot be made, it and what waited go to the DM, the row's note says so and the next message tries again; a link restart drops what waited to the DM too, since the old link's answers are dropped. A post deleted by hand is noticed by whichever order finds its thread gone first (`10003` on a send, an edit, buttons, a reaction, a retag, a close, a reopen or a removal): the link sends `Event::Gone` with the thread and the order instead of a warning, and the app forgets the post at once, so `status` drops it and no further retag goes to it. A message that found it gone is not lost: it makes a new post for its workspace (or waits for the one being made) and goes there, once; if that post cannot be made it goes to the DM like any post that fails, and a message that finds the new thread gone too goes to the DM rather than making a third, so a forum that keeps losing posts cannot loop. The other orders only forget, since a retag or a close of a post that no longer exists has nothing left to do (a closed workspace whose post was deleted is simply done). A post whose forum is gone stays a failed post (`Event::Failed`), as it has no thread to forget. `10004` (unknown server) is not taken for a deleted post: it means the app left the server (`Failure::Removed`).
- **The map lives in `session.json`**: `WorkspaceState::discord_post` (`channel`, `thread`, and `archived` only while it is `true`), optional, so the session's `VERSION` stays 5 (see Saved session). Not in `discord.json`: workspace ids change with every server run, and plain workspaces share one folder, so neither an id nor a path names a workspace across a restart; the session does. A saved post of another forum channel is dropped on restore, and setting the forum up again in another channel forgets the threads in memory, so no message reaches an old forum's post. Turning the mode off keeps the map, so turning it on again in the same channel reuses the posts; they are not archived in bulk.
- **Cleanup** (`forum/cleanup.rs`), by gesture: a workspace that is gone (its `×`, closing its project, `close --workspace`; noticed on the slow refresh, so every way is covered) gets its post tagged `done`, archived and locked, or deleted when `discord_forum_close` is `delete` (the **closed workspaces** row, see Settings), and its mapping is forgotten. Archiving is the default: it clears the forum's list as well as deleting (archived posts drop out of the active list and do not count against the server's limit of active threads), keeps the history to read back, and can be undone, while deleting cannot; deleting stays a choice for whoever wants no trace. Locking stops a message in a closed workspace's post from unarchiving it, since nothing would answer. **close agents** archives the post without locking it (`DiscordPost.archived`, kept in the session and in `status`'s `post`), and reopening them (its undo included) unarchives it, so the next notice goes to the same post; a notice sent to an archived, unlocked post also unarchives it on Discord's side, so the mark is cleared then. The retag skips archived posts, which Discord does not edit. A `×` always sends `Reopen` before the `done` tag and the locking close, because Discord may have archived the post on its own after a week without messages, the app does not know, and whether it accepts editing or locking an archived thread is not known. A retag or a close Discord refuses because the thread is archived (`50083`) is no delivery failure: the link sends `Event::Archived` instead of logging a warning, the post is marked archived in memory and its tag forgotten, so the retag stops until a notice unarchives it and the tag is then sent again; for a close (**close agents** on a post Discord archived after a week) the post is already as it was asked to be. While the mode is off (or not ready, or the link down) nothing is sent and the mapping is kept until it can be cleaned, since forgetting it would leave the post open for good; a gone workspace is not in the session, though, so a restart in between loses it and that post stays as it was.
- **Reading the posts needs Message Content**: in a server, Discord sends a message's text only to bots with that privileged intent, unless the message mentions the bot. So in forum mode the Gateway identifies with `DIRECT_MESSAGES | GUILD_MESSAGES | MESSAGE_CONTENT` (`1 << 12 | 1 << 9 | 1 << 15`; the DM's `4096` otherwise, so the mode off identifies as before). The intent is a switch in the portal, granted without review below 100 servers, which a one-user app always is. Reading by mention instead was rejected: every message in a post would have to ping the bot, and a reply with the ping turned off would arrive empty. A 4014 (the intent refused) would otherwise stop the listener, taking the DM with it, so in forum mode it logs a warning, sends `Event::DirectOnly` and identifies again with `4096` after 2 s: the DM keeps working, posts are still made and tagged (sending needs no intent), and only replies in posts stop arriving. The app keeps the refusal (`Forum::refused`, not the link's `Problem`, which a later recovery would clear) and shows it in the **forum mode** row's note (`gateway::DIRECT_ONLY`), not the **bot** row's; the intent step goes back to pending, and the next link start tries the forum's intents again and clears it.
- **Only the owner, only in the forum's posts**: `discord::written` keeps a message from a server only when it is the forum's server (`Message.guild`) and marks it not private, so it can never pair; the app then takes it only from the paired owner in a thread it made, and checks the server once more there (`posted_by_owner`, against the saved forum's guild), so a message cannot reach a pane through a thread id alone. Anything else, someone else's message in a post, the owner's in another channel or in a post cornercase did not make, another server, is ignored and logged by chat id, never its text. A button press in a known thread from the owner is taken like one in the DM, and is answered where it was pressed; `/status`'s buttons in the DM answer in the DM.
- **Replies in a post** (`forum/replies.rs`), in this order: a reply to the bot's message goes to its pane (as in the DM); an open question about a pane of this workspace (`write` pressed in the post) takes the text; else the workspace's only agent, or the bot asks which with buttons for this workspace's agents only, or says `No agent is running in this workspace. /new in the direct message starts one.` What the bot answers (the 👍, a refusal, the question) goes to the post the message came from (`Heard`, the last 256 messages read in posts). Commands stay the DM's: they are registered for the DM only (`contexts: [1]`), and a `/…` typed in a post is not run, answered with `Commands work in the direct message with the bot.` In the DM an open question stays global, so a plain message there can answer a `write` pressed in a post.
- **Not checked live** (only against fakes: `discord::forum::tests`, `discord::gateway::tests::forum_mode`, `messenger::link::tests`, `app::tests::control_requests::discord_forum`, `ui::tests::forum`): that the bot's own allow overwrite is accepted with Manage Channels when the channel is made, whether `applied_tags` edits fall under the limit of two channel renames in ten minutes (hence the settle and one pending tag), a thread's first message carrying buttons, a real 4014 when the intent is off, the content of the owner's messages reaching the bot in forum posts, archiving a post with and without locking it and unarchiving it, with Manage Threads, whether locking an archived post needs it reopened first (`app::tests::control_requests::discord_forum::cleanup` checks only the orders sent), and that a retag or a close of a post Discord archived after a week answers `50083` (the code Discord documents for a thread that is archived), which only the fakes send.
