# Processes

Code: `processes/`, `process.rs`, `process/escalation.rs`, `app/processes_dialog.rs`, `app/control/processes.rs`, `ui/dialog/processes.rs`, `control/processes.rs`, `cli/processes.rs`, #486

- **Why**: every pane can run an agent, a dev server and a watcher, and a runaway one (a `next dev` stuck at 100 % of a core, an agent's leftover `esbuild`) was only found with `top` in another window, with nothing saying which pane it belongs to. The **Processes** dialog lists every pane of every open project with the CPU and memory of everything under its shell, and stops a program; `cornercase processes` and `processes stop` do the same for scripts and agents. Orca's Resource Manager (v1.4.238) has a terminals view of the same shape.
- **What is listed** (`processes::sample`, on a job): for each pane, the tree under its shell (`process::tree`, breadth first, capped at 256 processes), with each process's name, arguments, start, CPU and footprint, in depth-first order; zombies are skipped. A last group, **cornercase**, is the server and its children that are not pane shells (plugin services, plugin popups, its own `git` and probe jobs), each with its subtree, so the totals cover everything cornercase runs and a runaway plugin service is visible. It has no actions: a plugin service has its own supervisor, and stopping the server from its own dialog would end the window. It is left out when a request narrows to a pane or workspace and while a filter is typed.
- **Measuring**:
  - **CPU** is the share of one core over the interval between two samples (100 % is one full core, as in `top`, so several cores go over). It is the difference of `process::cpu_time` (user plus system time of all threads) divided by the wall time between the two readings, per `(pid, start stamp)`: a process missing from the earlier sample was born in the interval and counts all its time, and a reused pid has another start stamp and so is a new key. Linux reads `utime` and `stime` of `/proc/<pid>/stat` over `clock_ticks_per_second` (the rustix `param` feature, no new crate). macOS reads `ri_user_time` and `ri_system_time` of `proc_pid_rusage`, which are in mach absolute time units: on Apple Silicon one unit is 125/3 ns, so they go through `mach_timebase_info` (read once). libc marks that call and its struct deprecated in favour of `mach2` (an error under `-D warnings`, found by the macOS CI), which would be a new dependency for one call, so `process.rs` declares the one function and its two-field struct itself in an `unsafe extern "C"` block (libSystem always links). A test checks that a busy loop's CPU time is at least a quarter of the wall time, which fails by a factor of 41 without the conversion.
  - **Memory** is `process::footprint`, the figure the tab rows show (see Memory), summed per pane. The dialog measures whatever the `memory` setting says, only while open, and does not feed `Term.memory`: the two stay independent.
  - The first sample of an opening has no earlier one, so the job reads the times once, waits 500 ms and reads again: CPU shows on the first answer. A request does the same with its `interval`.
  - **Known limit**: a process that starts and ends between two samples is not counted, and the CPU a process spent before ending inside the interval is lost with it.
- **The dialog** (`Overlay::Processes`, `processes::dialog`, `app/processes_dialog.rs`, `ui/dialog/processes.rs`):
  - **Entry points**: **processes** in More ▴ (after **usage**), so it is in every layout (footer, icon bar gear, compact More), and `k` in the keys menu. The issue asked for the command palette and Settings; cornercase has no palette and its keyboard equivalent is the keys menu, whose root mirrors More's items. Settings was left out for the reason Worktrees left it (see Worktrees dialog): it is a task you come back to, not a preference. A footer or icon bar button like ` Worktrees ` was left out: it changes every footer layout, the icon bar and the simulation's footer, for a dialog opened now and then. `k` and not `P`: an uppercase letter can arrive as `p` with Shift under the kitty keyboard protocol and run "previous tab".
  - **Rows**: one per pane, `project › workspace › tab` (with `· pane N` when the tab is split) at the left, the pane's program (agent-aware, as the tab row) in a column, then CPU and memory right aligned. A click or `→` expands the row into its process tree, each process with its command line (cut to 40 characters), pid, CPU and memory; `←` goes back. The sort selector (` cpu ` ` memory ` ` name `, `Tab` cycles) orders the panes by CPU or memory descending and by name ascending, ties in sidebar order; it is kept for the server run, as Usage keeps its tab. The totals line (`12 panes · 87 processes · cpu 136.0% · 3.4 GB`) is the sum of the rows, the cornercase one included. The filter field takes any printable key, matches the place, the program or any command line, and a pane that matches only through one of its processes shows expanded; `Esc` clears it, then closes.
  - **Order**: re-sorted on every sample, except while any client's pointer is over the list. The codebase treats rows jumping under the pointer as a defect (Worktrees dialog, agents section), but a list sorted by CPU that never re-sorts goes stale. While the pointer is inside, the figures update in place, new rows go at the end and gone rows disappear in place. The selection and the expanded rows follow their item by identity (the pane's id, or a process's pid and start stamp), never by index, and the stop confirmation names exactly what it captured, so a click on a row that moved can never stop something unnamed.
  - **Buttons**: ` go ` and ` close ` on a pane row, ` stop ` on a process line, on the hovered and the selected row and always in compact mode, where the dialog takes the screen and a row takes three lines. The shell line (depth 0) has no ` stop `.
  - **Refreshing**: every 2 s on a job while the overlay is open (`watch_processes_dialog`, from the sync step), never two at once, with a generation per opening (`app::refresh::Refresh`, shared with Ports) so an answer for a closed dialog is dropped. The next sample's earlier times are kept in `ProcessesState`, so the CPU of the second and later samples is over the real 2 s.
- **Go and close**: ` go ` closes the dialog and shows the pane. ` close ` replaces the dialog with the existing confirmation: Close agent (see Layout, agents section) when the pane runs an agent cornercase reads, else close pane in a split tab and close tab for the tab's last pane (`ask_close_pane_of`, which the keys menu's `x` also uses). It does not come back to the dialog afterwards: a `back` would touch every way those dialogs end, and one overlay is open at a time.
- **Stopping** (`processes::stop`, on `process::escalation`): never before a confirmation, a second step of the same overlay. Only a process under a pane's shell has a ` stop `; never the shell, the server or what is outside every pane.
  - **The process and everything it started, never an ancestor.** Ports signals only the pid that holds the port, so its children may live on: there that is the point, since the shell or agent above must stay. Here the user asked to stop a program, and signalling only its pid would leave its children reparented to init or launchd, gone from the view and still burning CPU: the worst outcome for a runaway tool. The group is the root and its subtree as listed, plus its current descendants when the stop runs (children started since the confirmation); the members keep their start stamps, so ones already reparented away are still found and signalled.
  - **Checked first**: the root still runs with the start it was listed with, else `pid N is no longer running` or `…is no longer the program that was listed`. Every signal goes through the start stamp, so a reused pid is never signalled. A member that cannot be signalled (`sudo`) is skipped and, if it stays alive, the outcome says so.
  - **Then** SIGTERM to the whole group at once, a check every 50 ms for up to 3 s, SIGKILL to the members still running, and up to 1 s more. **Stopped is every member being gone or a zombie** (`process::running`: `alive` is true for a zombie, so a killed child waiting for its parent would read as still running until the SIGKILL). The outcomes are `stopped`, `killed` and `still-running`. A toast says it (`stopped node (pid 48211) and 2 programs it started`) and the list refreshes at once.
  - **The confirmation** names the command, pid and place, lists what else it stops, warns in yellow when the process is the pane's agent (its conversation ends, and close agent closes its tab instead) or something the agent started (it may start it again or fail without it), and says what will happen. "Under the agent" is the agent's pid or a descendant of it in the sample.
- **Shared escalation** (`process/escalation.rs`): Ports' check, SIGTERM, wait, SIGKILL, wait loop moved into the `process` leaf behind a `Stoppable` trait (`check`, `signal`, `holds`) and `escalate`, so both stop requests have one loop (jscpd would flag a copy, and a fix would be made twice). Ports' `holds` also covers a changed start; its messages and outcomes did not change.
- **The requests**:
  - **`processes`** (`{pane?, workspace?, interval?}`) answers `{interval, total, panes, cornercase}`; each pane has `pane`, `tab`, `workspace`, `project`, `program`, `agent`, `foreground`, `pid` (its shell), `cpu`, `memory` and `processes` (`pid`, `parent`, `name`, `args`, `started`, `cpu`, `memory`, in tree order). CPU is the percentage of one core with one decimal and memory the footprint in bytes; both are null where a process cannot be read. `interval` is in ms, default 1,000, clamped to 100..=10,000 by the server. `started` is opaque: it exists to be given back to `stop-process`. The default is **every pane** (the view is global), unlike `ports`, which uses the caller's workspace; `pane` and `workspace` narrow it, `--worktree` through `status`.
  - **Not in `status`**: `status` never measures (see Memory), CPU needs two samples an interval apart, and a figure that moves every 2 s cannot go in the digest that tells a UI to ask again. So they are two requests, `processes` (a job; the request waits for it, `Stage::Processes`) and `stop-process`, new operations that `contract` lists, with no new feature string (Ports added none either).
  - **`stop-process`** (`{pid, started?}`) answers `{pid, program, pane, outcome, processes}` after the escalation, `processes` being how many were signalled. It is refused with `not-found` (no running process with that pid) or `conflict`: the server or anything it runs outside the panes (`cornercase itself`), a pane's shell (`close the pane instead`), a process of no pane, or a `started` that changed. Ownership is `process::owners` over the panes' shells, as the Worktrees dialog does it, so the socket cannot stop any program of the user by its pid.
  - **`cornercase processes`** prints the panes sorted by CPU, highest first, each with its tree indented under it, then cornercase's line and the total; `--json` keeps the sidebar's order, which is stable for a client. `processes stop PID` exits 1 when something is still running. Both work with `--remote`.
- **Left out**: ticks and a multi-stop (a "stop all" across every pane is a footgun, and the issue asks for none); a footer or icon bar button; a `back` from a close confirmation; stopping cornercase's own children; sorting the siblings of a tree by the sort key (they are in pid order); a stream that follows the figures (`processes --interval` in a loop does it).
- **Windows** (#596, the `cfg(windows)` `imp` of `process.rs`; checked on Windows 11 build 26200 with 360 processes; how names and `alive` fit the rest of the port is under Windows):
  - **Sources**: `all`, `children` and `parent` come from a process snapshot (`CreateToolhelp32Snapshot`). `name` is the file name of the image path (`QueryFullProcessImageNameW`, 34 µs), and the snapshot's name only for a process cornercase may not open. `args`, `env` and `cwd` come from the process's PEB: `NtQueryInformationProcess` gives its address, `ReadProcessMemory` reads its parameters block, then the command line, the current folder (`CurrentDirectory.DosPath`, without its trailing `\`) and the environment, read to the end of its memory region (`VirtualQueryEx`, at most 1 MiB) and cut at its empty entry before it is converted (4 ms before the cut, 0.7 ms after); a block the 1 MiB cuts short drops its last, half-read variable. `footprint` is `PrivateUsage` of `GetProcessMemoryInfo` (see Memory). `cpu_time` (kernel plus user, in 100 ns ticks) and `start_stamp` (creation) come from `GetProcessTimes`. `start_stamp` is turned into µs since the Unix epoch, as on macOS: a creation time in ticks (about 1.3e17) is past 2^53, so the `started` a client reads as a JSON number and hands back to `stop-process` came back rounded and was refused. `zombie` is always false: an exited process is not running, whoever still holds a handle to it. `open_files` is empty: its only source, the system's handle table, is slow and can hang on a pipe, and its readers (Copilot, Cursor, opencode, Codex) are #599's. `started` is `None`, as on macOS: its one reader matches Grok Build's `pid_start`, which is Linux's boot ticks, and an unknown start never rejects a row.
  - **One snapshot for 50 ms**: a snapshot took 8 ms, and `tree` asks for each process's children, so a pane of ten processes cost eleven of them and a Processes sample about a second. The `imp` keeps the last snapshot that succeeded for 50 ms (`SNAPSHOT_FOR`) behind a mutex, with the time read right after it was taken, so a whole sample or tree walk takes one or two; a failed one is not kept, so it never reads as no processes. A process started in those 50 ms can be missing from `all` and `children` until the next one.
  - **Pids that changed hands**: Windows gives a pid to a new process within milliseconds of the last one ending, and keeps a dead parent's pid in its children's entries. So an entry answers only for the process it was taken from: `children` keeps a child only when its start is known and falls between its parent's start and the snapshot's time (an exited child, a child older than a reused parent pid, and a pid reused since the snapshot are dropped); `parent` and the snapshot's `name` take the entry of a live pid that did not start after the snapshot, and `parent` answers only a live parent that started first. An unreadable start is accepted for those two, since the snapshot's name exists for processes cornercase may not open. Creation times move with the clock tick (up to 15.6 ms), so a pid reused within the snapshot's own tick can still pass. Linux reparents to init and has no such case.
  - **The parameters block** is declared in `process.rs` up to the environment pointer, since windows-sys's stops at `CommandLine`. A compile-time assertion checks its `CommandLine` against windows-sys's offset. A 32-bit (WOW64) process's 64-bit PEB has the same command line, but its folder may lag behind what its 32-bit side set. Only a 64-bit cornercase is built.
  - **Command lines** are split by the rules Windows programs follow (`CommandLineToArgvW`'s): the program is quoted or ends at the first blank; `2n` backslashes before a quote give `n` and toggle quoting, `2n+1` give `n` and a literal quote; `""` inside quotes is one quote. They are written in Rust and tested on every OS, rather than calling `shell32`, which would load that DLL into the server for one function. Empty arguments are dropped, as on Linux.
  - **Access**: a process is opened with `PROCESS_QUERY_LIMITED_INFORMATION`, plus `PROCESS_VM_READ` for the PEB. The user's own processes are read in full. An elevated one or another user's shows its name and place in the tree, without its arguments, folder or environment.
  - **Own code over `sysinfo`**: `sysinfo` reads all of this on Windows, the same PEB walk included. But it is a large dependency that keeps a whole system table in a `System` value refreshed by one query, while every caller here asks about one pid from any thread, and it brings the `windows` crate. Here it is about 340 lines over `windows-sys` (pinned `=0.61.2`, already in the lock through other crates), each `unsafe` call in a small function, with the same shape as the Linux and macOS `imp`s.
  - **Known limits**: a process that exits with code 259 (`STILL_ACTIVE`) reads as alive while anything holds its handle; Windows reuses an exited process's pid within milliseconds (tests spawning in parallel took each other's), so every signal stays behind the start stamp check; a process in another session or a protected one may show only its name.
- **Known limits**: children are read again only once, when the stop runs, so a supervisor that respawns a child after SIGTERM leaves the new one running while the outcome says `stopped` (the root is gone); a member whose start could not be read is never signalled, since a reused pid could not be told apart; when the root cannot be signalled (a `sudo` program) but some of its members were, the stop goes on and the outcome follows what still runs; only the server's PID namespace is seen (a program in a container is not); a daemonized program leaves its pane's tree; macOS cannot read other users' processes, so a `sudo` child shows no figures; walking the trees reads a few files per process every 2 s (Linux reads one `children` file per thread), which is fine while the dialog is open and never runs otherwise.
- **Tests**: the `process` leaf (CPU time parsed from `stat` lines with spaces and parentheses in the name, a busy child's CPU time against wall time, `running` for a live process, a changed start and a zombie, `tree` over `Family`; on every OS, Windows command lines, environment blocks (cut ones too), the FILETIME conversions and the snapshot's pid checks; on Windows, `process::tests::on_windows`: a `ping` child's place in the tree, name, arguments, folder, environment, start and memory, `cmd` running `ping` as a tree, `alive` until a kill, a pid with no process, memory committed but never touched (which a working set would miss), a start in µs since the epoch, and a busy thread's CPU time between a quarter of the wall time and all the cores); the sampling on real processes (a busy shell with CPU, the tree's parents and depths, the server's own children as the cornercase group, zombies skipped), the CPU arithmetic, sort, filter, order keeping and keys of the model (`processes::tests`, `processes::dialog::tests`); the stop on real processes (a subtree ends, a program that ignores SIGTERM is killed, a changed start and a gone pid are left alone, a child started after the confirmation is stopped), and Ports' own stop tests unchanged on the shared escalation; the dialog in the app with real PTYs (`app::tests::processes_dialog`: More lists it, sampling every 2 s and never two at once, a `sleep` under its shell, stop asking first and then ending it, go, close for an agent, a split and a last pane, the order held under the pointer); the requests (`app::tests::control_requests::processes`); snapshots of the dialog (`ui::tests::processes_dialog`); the CLI text; and `e2e::processes` against the real binary.
