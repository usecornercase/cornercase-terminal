# Saved session

Code: `state.rs`, `persist.rs`, `app.rs`, `app/session.rs`

- Groups (name, icon, colour, collapsed), projects (with their group's index and whether they are folded), workspaces (with their changes base and fold), tabs, panes (cwd, the agent conversation to resume and its `done` and `pending` marks), split layouts, custom names, active children, column widths (and the stacked line and the agents section's height), the changes panel (open, scope, mode), whether the TODO, files or Flow panel is open, a pane's parent (below), whether its agents are collapsed in the agents section (`collapsed`, left out when false, on the parent itself) and a workspace's flow run (see Flows), in `$XDG_STATE_HOME/cornercase/session.json` (a debug build's `cornercase-dev/<key>/`, or next to the socket). The TODO list is not in it (see TODO panel). Processes are not restored; each pane gets a new shell in its folder. `project::group::known_icon` replaces an unknown saved group icon with `GROUP_ICONS[0]`. Preset selection and saved-icon normalization belong to the group model, so `App` calls its rules instead of defining them.
- **The mapping is in `state.rs`** (#195): `ProjectState::of`, `WorkspaceState::of` and `TabState::of` build `State::projects`; `restore` on each builds the model from the saved data and clamps the active child. `App` keeps what is not mapping (canonical paths, skipping missing folders, spawning, resuming, toasts) and takes ids in the same order as before: a project's and a workspace's id before their children's, a tab's after its panes'.
- Saved only once the state is stable for 2 s, so the burst of `Exited` events at logout does not save an empty session.
- Only a fresh server restores, once: on its first window's `Hello` or its first `cornercase start-server`, whichever comes first (see Client / server). Missing folders are skipped. `VERSION` is 5; older versions are migrated: versions 3 and 4 are read as is (a version 3 file has every project ungrouped), then, like versions 1 and 2, every project but the active one is folded.
- A tab whose shell cannot start (a folder it may not enter, no PTY left, a `$SHELL` that is gone) is left out whole, also a split one, and the restore goes on: its workspace and project stay, so `+ Tab` can try again, a toast names the projects (`could not restore n tabs (…), see server.log`) and `server.log` has, per tab, the folder that failed and the cause: `Error::SpawnShell` puts both in its message, like `RunGit`, since `thiserror`'s `Display` leaves out a `#[source]`, and `cornercase new-tab` or `split` into such a folder answer the same text. `App::restore` returns whether every tab came back. When one did not, the server copies `session.json` to `session.json.bak` before its `Saver` can write the smaller session over it; an older `.bak` moves to `session.json.bak.1` first, so a second incomplete restore with other failing tabs cannot overwrite the only full copy. Keeping an existing `.bak` instead (a review suggestion) was rejected: after one incident every later one would keep a stale copy. If the copy fails the `Saver` still saves: it writes to the same folder and disk, so what breaks the copy breaks the save too, and holding it back would lose every later change of that server run. Stopping at the first failure was the bug (#24): it dropped every project after it and then saved that. The fallback shell opens in the current folder when no project came back, as when there is no session, or when the restore was incomplete and no shell came back at all (`App::has_terms`). A session saved without tabs (closing the last tab keeps the workspace) comes back as it was, without it.
- **Agents resume their conversations** (#28, `resume_agents` in `config.json`, Settings → Agents, on by default): a pane that ran Claude Code, Codex, Gemini CLI, Grok Build, Cursor CLI or GitHub Copilot CLI comes back in the same conversation instead of a bare shell, since finding it again by hand with `claude --resume` was what a restart cost most. `App::watch_agents` (every 500 ms, every pane) keeps `Term::resume`, a `agents::AgentState`: the agent's kind, its conversation (`agents::context::Pane::conversation`: the `sessionId` of `sessions/<pid>.json` once its transcript has content, or the id of the Codex rollout the context line follows, which Codex creates with the first turn, or Gemini's `sessionId` after a real prompt or a Gemini response, including a compressed history) and its mode, read from the process's arguments (`agents::mode_of`), so an agent started in plan mode comes back in plan mode whatever the settings say now. A conversation with nothing in it is not kept: `claude --resume` on it fails with `No conversation found`. The pane saves it in `PaneState::agent`; once the shell is back in the foreground it is forgotten, so an agent that was quit comes back as a shell. The field is optional, so `VERSION` stays 5: a bump would make an older cornercase drop the whole session, and an older one ignores the field. On restore, `App::resume` types `agents::resume_line` (`claude <args> --resume <id>`, `codex resume <args> <id>`, `gemini <args> --resume <id>`, `cursor-agent <args> --resume <chat id>` (the chat id is the name of the chat's folder in the store, kept once the root has a turn; it must run in the folder the chat started in), `copilot <args> --resume=<session id>` (the session folder's name, kept once a prompt or a reply exists; the conversation is also kept before its first prompt after a restore, when the resumed process holds no lock yet, from its own `--resume=` argument), the command and extra arguments from settings, the mode from the saved state) as an agent launch without a prompt (`Launch::resume`, #324): it waits for the shell to be quiet, types the line, then waits until the agent is in the foreground and has drawn its screen, as `start` does; the resumed agent is idle, and what it was doing is not started again. A trust question parks it for the user (it is not answered, whatever `accept_trust_prompts` says, as before), except for a flow's role resumed in its role's own agent (the role's command, whose first launch answered it too); a flow pane that saved another agent resumes with that agent's ordinary line and leaves the question to the user. It was a `Launch::command`, done once the line was typed, which left nothing to say when the agent was back. The restored conversation is kept until the agent shows up with it, or for at most `RESUME_GRACE` (30 s, `Term::resuming`): until the command is typed the shell is in the foreground, and an agent that is slow to start has no session file yet, so a state saved meanwhile (2 s of quiet is enough) would lose it, and a restart then would not resume. A resume that fails (`No conversation found`) is forgotten once the grace runs out. Its JSON in `status` (`PaneInfo::resumes`) lets the restart texts count `n agent conversations resume in their tabs` instead of the `claude --continue` hint, which stays for a server from before it and with the switch off. Off by default was rejected: the agent comes back idle, so resuming costs nothing but the screen, and a resumed agent in a dangerous mode was already running in it. Reading the agent's own arguments to resume with them was rejected: they may hold a prompt, which would be sent again.
- **A resuming pane takes no input** (#324): the window shows as soon as the server restores the session, while each resume waits for its shell, types its line and the agent starts, which takes seconds; keys typed meanwhile went in front of the resume line (`lsclaude --resume …`, a resume that fails) or into the agent's start-up, where an `Enter` can answer a question nobody saw. So while a pane has a resume launch (`Launch::resume`, or a flow orchestrator's restored brief) that is not parked on a question for the user (`App::resume_holds`), what the window sends it is dropped: keys and pastes (`App::holds_input`, which toasts `claude is resuming its conversation in this pane; wait for it, or press cancel`), mouse events for its program (`forward_mouse`) and the wheel's arrow keys on the alternate screen; **ask agent** copies its reference instead, as with no agent. Dropped rather than queued: sent once the agent is back, a queued `Enter` could still answer whatever the agent shows first. cornercase's own mouse (selection, the scrollback wheel, the pane menu, dividers) still works, and so do other panes. The hold ends when the launch does (the agent drew and went quiet, or the shell came back because the agent exited), or once `RESUME_GRACE` (30 s from when the resume was queued) runs out, whichever comes first: the launch carries that deadline (`Launch::resume`'s `until`, the pane's own `Term::resuming` for an orchestrator's brief) and `Launch::holds` reads it, since the launch's own timeouts restart at each stage and could hold the pane longer. The launch is not dropped at the deadline, so a slow orchestrator still gets its brief. A trust question parks the launch, so the pane takes keys to answer it. The pane shows ` resuming claude… ` and a grey ` cancel ` pill on a surface band across its middle (`ui::resume_notice`, shared by drawing and the click). **cancel** drops the launch: before the line is typed it is never typed, and the pane forgets the conversation and its marks (`Pane::give_up`); after, the agent keeps starting and only the keys come back, since a typed command cannot be taken back. `Esc` was left out as the way to cancel: it is a key, and AGENTS.md asks before adding any. Only window input is held, not the commands: `send` refuses a resuming pane unless `--force` (its text would land in the same places), `keys` goes through since it is how to answer things, and `status` shows `resuming` (in the JSON and as the last column of `--panes`). Holding every launch that types into a fresh pane (`start`, the issues, the queue) was left out: those panes open while the user is doing something else, where a restart puts every pane on screen at once.
- **Marks come back with the conversation**: a pane saves `done` (`✓`, `activity::Pane::unseen`) and `pending` (see Agent status) only while it has a conversation to resume (`Term::resume`), as optional fields of `PaneState`, so `VERSION` stays 5. Without them a restart or an update wiped every `✓` and lost which agents were still to review. A shell pane saves neither: a mark without its agent means nothing, and would show on whatever agent is started there later. On restore, `App::resume` returning true (resuming on and a resume line for that agent) hands them to `Pane::restore`, which keeps them while the resumed agent has not shown up (`follow` from no agent keeps a restored pane's marks; `update` with no activity leaves them), so they reach the same agent whatever its start-up time, and marks it as told (`notified`), so a restored `✓` does not toast or send a desktop notification again for work finished before the restart. If the agent never shows up within `RESUME_GRACE`, `Pane::give_up` drops them with the resume. With `resume_agents` off nothing comes back, as with the conversation.
- **Role worktrees come back too** (#313): `WorkspaceState::role_worktrees` (role, folder, branch), optional like `run`, so `VERSION` stays 5, lives on the run's workspace and outlives the `Run`, which ends when its panes close while the worktrees stay until the workspace goes. Panes already save their folder, so an own role comes back in its worktree; one whose folder is gone gets a shell in the run's worktree and its agent is not resumed there (a toast names the role, and `server.log` has a warning), since the conversation would continue in the shared tree. `sync_worktrees` drops entries whose folder is gone.
- **Accounts come back with their pane** (#379, see Accounts and profiles): `PaneState::accounts` (agent to account name) and `AgentState::account`, both optional and omitted when empty, so `VERSION` stays 5 and the v5 fixture is unchanged (`accounts.json` pins them). A pane is respawned with the accounts it saved (`saved_accounts`), never the selection; an account that is gone opens it without that variable, without resuming, with a toast (`account_gone`).
- **Parents come back with new ids** (#347): `PaneState` gets two optional fields, `id` and `parent`, so `VERSION` stays 5 and a session without parents writes the same bytes (the v5 fixture is unchanged; `parents.json` pins one with them). `id` is written only for a pane some other pane names as its parent (`state::named_parents`), and `parent` only when that parent is saved too, so a closed parent is never written. Ids change on restore and a parent can come back after its child (another project), so `App::restore` keeps a map from old ids to new ones (`session::Parents`) and resolves the parents after every project (`adopt_saved`). A parent is dropped, with a debug line in the log and no toast, when its pane did not come back (a skipped project, a tab that failed to start), when it is the pane itself, or when it is not lower than the child's old id: ids come from one counter, so a parent is always older, and the rule keeps a hand-edited file from making a cycle.
- **A flow run comes back with its workspace** (#263, see Flows): `WorkspaceState::run` holds the flow, the task, each role's tab and pane position and where the plan stands, and the session's `flow` flag (beside `todo` and `files`, skipped when false) reopens the Flow panel. A run also saves `ended`, the branch on which the orchestrator's review mark was latched (see Flows, The end; optional, so `VERSION` stays 5). Both are optional, so `VERSION` stays 5 and the v5 fixture is unchanged. A role resumes with its role's command (its mode that never asks, model, args and env) rather than the settings' line, so a role on another provider stays there.
- **A workspace's agents closed and reopened** (#430): a restart cost a session's agents in two ways at once, and closing them one by one lost their place. Stopping a workspace's agents to free memory or a plan's quota, then coming back to them tomorrow, meant keeping the panes open, or losing which conversations were running, in which mode and account, and for a flow the whole team's seats. **close agents** (the workspace row's menu, the keys menu's `w a`, `cornercase agents close`) closes every tab with an agent, whole, and keeps what restoring needs; a **`▶`** on the workspace row, **reopen agents** in the row's menu, `w o` and `cornercase agents reopen` bring them back, each in its own conversation.
  - **Where it lives**: `AgentRuntime::closed` (`app/closed_agents/kept.rs`), one `Kept` per workspace id, and not a field of `App` (`App::new` is at clippy's 40 lines, see Code layout). A `Kept` is the closed tabs as `state::TabState`, the session's own type, so reopening goes through `restore_tab` and gets, for free, accounts that are gone, a role's worktree that is gone, the marks and the parent bookkeeping. `TabState::of` is given every live pane id when closing, so each pane writes its `id` and its `parent`; a pane that was an agent also writes `PaneState::closed` (`ClosedAgent`: its kind, its mode and whether its turn was `cut`, working or waiting), which an agent with no conversation to resume needs (opencode, a custom kind, an agent that never had a turn): it starts again in its kind and mode. `WorkspaceState::closed` (`ClosedState`: the tabs and the kept run) saves it, all optional and skipped when empty, so `VERSION` stays 5 and the v5 fixture does not change (`closed.json` pins the new fields).
  - **What closes**: every tab with at least one agent pane (`term.agent.status()` is some, or a member of the workspace's run, even at its prompt), whole, with the shells that share it. Tabs with only shells stay, and so do the workspace and its worktree. A pane still waiting for its launch (a shell in front) is not an agent, so its tab stays: closing it would drop its prompt. It closes at once when nothing would be lost; it asks (`Overlay::CloseAgents`, the scrolling dialog Close agent uses) when an agent is working or waiting (its turn is cut), when one cannot resume its conversation (it starts a new one), or when other panes share the tabs (`Also stops:`). Confirming plans again and asks again if the plan grew. A second close while the first panes are still dying skips them (`ClosedAgents::closing`), or they would be kept twice. Closing is a toast with ` reopen ` (6 s) in the window; a request shows none.
  - **Quiet**: the panes it kills are not notified about. `ClosedAgents::quiet` is read by `watch_agents`, whose one filter in `settled_notice` covers the toast, the desktop notice, Telegram, Discord and the sound, since they all go through `App::notify`; the set empties as the panes exit (`forget_gone_closed`, in the slow refresh).
  - **Reopen is all or none**, like a run start: every pane is spawned before any tab is added; on an error what was spawned is killed, its launches dropped, the entry put back and the error shown (a toast, or `failed`). Every agent's command must be on the server's `PATH` first (the refusal of a run start, shared as `agents_missing`). The new tabs come after the workspace's others and the focus does not move. `restore_tab` takes a `reopen` flag: an explicit reopen resumes even with `resume_agents` off, since the user asked. A pane with no conversation gets `Launch::restart` with `agents::fresh_line` (the start line of its kind and mode, moved out of the account restart), which shows ` starting opencode… ` and ` cancel ` and leaves the trust question to the user, like a resume.
  - **After a restart**: the closed entries are saved and restored, and each closed pane gets a new id on restore (`reissue_closed`): the saved ids belong to the previous server, and a parent outside the set, translated to the new server's ids, could equal an id inside it. A parent outside the set is remembered apart (`Parents::outside`) and translated after every project is back (`adopt_closed`), or dropped. A reopen translates the same way (`adopt_reopened`): a parent inside the set maps to its new pane, one outside keeps its id while that pane lives.
  - **A flow's agents**: the run leaves `App::runs` while its agents are closed and is kept whole in the entry (messages, progress, `ended`, folder, the same `id`), before any shell is killed. That is the whole of "does not latch the run's end": `latch_run_ends` and `forget_runs` only walk the live runs, the Flow panel hides (`screen.side` stays, so it comes back), **show flow** leaves the menu and message streams end as for an ended run. A flag on the live run was rejected: every walk of the runs would need an exception. What learns about the kept run on purpose: a new run is refused in that workspace (or on that branch) with `workspace N has a flow's agents closed: reopen or forget them`, before any worktree is made; the role worktrees stay protected (`role_owner`: removing one is refused); and the `flow-runs` feed lists it with `state: "closed"`. Reopening reseats the members from the saved positions, spawns a pane for every role that has none (one closed earlier with its `×`, in its own worktree when it has one and it is still there) in a tab named after it, and starts the orchestrator last. A resumed orchestrator gets `brief::reopened` (the new pane ids, the folder, who was cut and who starts over, `read --last-message`); one with no conversation gets the full brief followed by `## Where the run stands`. A marked (pending) orchestrator gets none, as in a restore.
  - **Forgetting**: **forget closed agents** (a confirmation, in the row's menu only: destroying is not worth a key) and `cornercase agents forget` drop an entry and end a kept run (`run ended` in the log); the run's folder and role worktrees stay. Removing or closing the workspace forgets them: the sync step drops entries whose workspace is gone (a removal that fails puts the phase back to `Open`, so they survive it), and the dialogs that remove or close the workspace or the project say `Its 4 closed agents are forgotten.` A plain workspace's `×` in the wide layout asks when it holds closed agents, where it used to close at once, since that would drop them without a word. A script's `close --workspace` forgets without asking, as scripts act.
  - **The `▶`** (`ui::REOPEN_ICON`): on the workspace row in every layout (the list, stacked, compact, tabs on top, the tree) and in the empty pane, after the attention badge and before `setting up…`, the pull request tag and `↓n`, so a narrow row drops the others first. It shows with every badge setting, not while the row says `removing…`, and takes the click on press, like the pull tag (`Tag`, shared by drawing and hit testing). Cyan, the UI's action colour (`+ New`, the lit ` ⋯ `): green is passing checks, yellow working and waiting, blue pending, purple merged, grey the tab's `▸`. Hovered it is bold and underlined, like the pull tag. U+25B6 is East Asian Ambiguous and has an emoji variant, and `▶` was rejected for tab icons for being drawn wider than a cell in some fonts (see Agent status): checked in the tmux of this Linux VM and in the site's renderer only. Ghostty, iTerm2 and Terminal.app on macOS were not checked, so it is one constant: `►` (U+25BA, Neutral width, no emoji variant) is the fallback if one draws it wide. The empty pane shows `4 agents closed`, a ` ▶ reopen agents ` pill and the usual `+ Tab opens a shell here` (`ui::reopen_button` is the geometry of drawing and click, and nothing when the pane is too short to draw them).
  - **Scripts**: see Commands for scripts and agents. Rejected: a pause button in the Flow panel (a run's agents are closed like any workspace's, from its row), `SIGSTOP` (memory is the point, and a stopped agent keeps its sockets), saving on a single tab's close (one `×` is the user's way to end an agent for good), keeping the run in `App::runs` with a flag, and a flag of `close` for scripts (an older server would drop it and close only the pane, so the request has its own names).
