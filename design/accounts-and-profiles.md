# Accounts and profiles

Code: `accounts/`, `agents.rs`, `app/tabs.rs`, `app/control/accounts.rs`, `app/accounts_page.rs`, `app/account_menu.rs`, `settings/accounts.rs`, `ui/accounts_bar.rs`, `control/accounts.rs`, `cli/accounts.rs`, #379

- **Why**: people with two accounts of one agent (work and personal) logged out and in again, or kept a second terminal with another `CLAUDE_CONFIG_DIR`, to switch. An **account** is a folder of its own in which an agent keeps its login, and each agent has an account selected for its new tabs (a **profile**, for scripts, picks one per agent under a name); new tabs and agents start with the selected folders. cornercase passes the folder through the variable the agent already reads and never reads, copies or refreshes a token: the agent logs in itself, in its folder. The first pull request was the server, the requests and the CLI; the second the window: Settings › Accounts, a button per agent to switch its account (as Orca does), names for accounts, the account mark, an account picker where agents are started and plan usage per account (below). Trying the profile button it first had showed that one switches one agent at a time and wants to call `~/.claude` `work`, so the window shows accounts per agent and profiles stay a tool for scripts.
- **Which agents** (`AccountHome`, the `ACCOUNT` constant of each agent folder, dispatched by `Known::account`; `None` means no accounts). An agent gets accounts only when its login is known to follow the folder:

  | Agent | Variable | Login separate per folder | How it was checked |
  |---|---|---|---|
  | Claude Code | `CLAUDE_CONFIG_DIR` | yes: on macOS the keychain item is `Claude Code-credentials-<sha256 of the path>[0..8]`, on Linux `<dir>/.credentials.json`; `.claude.json` (account, project trust, user-scope MCP) moves too | live, 2.1.302 |
  | Codex | `CODEX_HOME` | yes: `auth.json`, or the keyring entry `cli|<sha256 of the canonical home>[0..16]` | source (`codex-rs/login`) |
  | Gemini CLI | `GEMINI_CLI_HOME` (replaces `HOME`, files under `<dir>/.gemini/`) | yes, unless `GEMINI_FORCE_ENCRYPTED_FILE_STORAGE=true`, which uses one shared keychain item | source |
  | GitHub Copilot CLI, Cursor CLI, Grok Build | `COPILOT_HOME`, `CURSOR_CONFIG_DIR`, `GROK_HOME` | not verified (their logins may sit in a keychain item that does not depend on the folder) | left out: checking needs a real login with each binary |
  | opencode | — | out of scope: its providers are its own | — |

  Announcing an isolation that may not exist was rejected; the three left out come back once a live check shows the login moves with the folder.
- **Where accounts live** (`paths::accounts_of(session)`): `<state>/accounts/<agent>/<name>` beside `session.json`, `<stem>.accounts/` beside the socket under `CORNERCASE_SOCKET`, and a debug build's `cornercase-dev/<key>/accounts`, so a dev server never touches the real logins (its keychain keys differ too). The state folder rather than `~/.cornercase/accounts`, to follow the rules of `paths`. Folders and the `<agent>` level are `0700`. The folder on disk is the truth: `accounts::list` reads it, nothing lists accounts elsewhere. Names are letters, digits, `.`, `_` and `-`, at most 32 (`accounts::valid`), never `.` or `..`.
- **The path is always the canonical one** (`accounts::add` canonicalises after creating; `Accounts::of` canonicalises each folder; `account list` answers the canonical `path`): Claude Code derives its keychain key from the exact string it gets, so `/var/…` and `/private/var/…` would be two logins. Moving the state folder or changing `CORNERCASE_SOCKET` changes the string and loses the login (the docs say so).
- **Shared settings are symbolic links** (`accounts/links.rs`): a new account links each entry of the agent's whitelist (`AccountHome::links`) that exists in its default home (`AccountHome::default_home`: the variable if the server has it, else `$HOME/.claude`, `.codex`, `$HOME` for Gemini, with `subdir` `.gemini`). Claude: `settings.json`, `settings.local.json`, `CLAUDE.md`, `agents`, `commands`, `skills`, `plugins`, `output-styles`, `hooks`, `keybindings.json`, `statusline*`; Codex: `config.toml`, `AGENTS.md`, `prompts`, `skills`, `rules`; Gemini: `settings.json`, `GEMINI.md`, `commands`, `extensions`, `skills`, `policies`, `trustedFolders.json`. Everything else (login, history, sessions, caches, Claude's `.claude.json`) stays per account. `links::ensure` runs again before every spawn with that account (`Accounts::link`), creating what is missing and never replacing a real file; `links::status` names entries that became real files (an agent writing atomically replaces the link), shown as `unshared` and `(not shared: …)` in `account list`, never fixed by itself so no setting is lost. Claude's `.claude.json` mixes the login with project trust and user-scope MCP servers, so each account asks for trust again and does not see those servers.
- **Profiles** are `profiles` (`{name: {agent: account}}`) and `profile` (the active one, `""` for none) in `config.json`, both omitted when empty so the config fixtures did not change, written through `change_config` like every setting, so an outside edit applies live and raises the revision. A profile naming an account that no longer exists leaves that agent on its system login (a `debug` line, target `accounts`, since it is looked up on every spawn); an active profile that does not exist counts as none and is logged once (`warn_unknown_profile` in `app/config_file.rs`). *System* (no profile) is not stored and cannot be deleted, and no profile may be named `system` (any case), which `profile list` uses for it. The window never shows or edits profiles (see The switcher).
- **The selection per agent** (`active_accounts`, `{agent: account}` in `config.json`, omitted when empty; an agent left out uses its own login): what the window chooses. The **effective selection** for new panes (`Config::selected_accounts`) is the active profile when it exists, as in #386, else `active_accounts`. Choosing an account in the window or with `account-use` writes `active_accounts` = the effective selection with that agent changed, and sets `profile` to `""`, so the window never edits a named profile and the buttons keep showing what new tabs get. `profile-use NAME` is unchanged; `profile-use ""` (*System* in #386) also empties `active_accounts`, so it still means every agent's own login. Editing one profile from the window instead was rejected: a profile is a script's, and a click must not change what another script switches to.
- **Names for the window** (`account_names`, `{agent: {account: name}}`, `""` the agent's own login, omitted when empty; `Config::account_label`, `App::account_label`): an account cannot be renamed on disk (Claude Code's keychain key comes from the folder's path, so moving the folder logs it out), so a name is only what the window shows: the buttons, the menus, Settings, the mark, Usage and the start dialogs. Without one, the own login is `System` and an account its folder. A name follows a profile name's rules (at most 32, no hidden characters) and is unique per agent among the names shown, case-insensitively, so a picker can choose by it. Requests and the CLI always name an account by its folder (`""` for the own login): a label that could also be a folder's name would make a command ambiguous. Removing an account forgets its name and its place in `active_accounts` (`Config::forget_account`).
- **Per pane, when it is made** (`App::spawn_in`, `pane_env`): every new pane (a tab, `start`, a flow role, a worktree's setup pane) gets the variables of the accounts it was started with (`Accounts::env`: the request's `accounts`, over its `profile`, over the accounts of the pane that sent it, over the effective selection; `requested_accounts`), so typing `claude` in a tab opened from the window uses the selection too, and `SpawnOptions::remove` drops `CLAUDE_SECURESTORAGE_CONFIG_DIR`, which would override the folder's keychain key. An agent without an account there gets no variable and keeps whatever the server inherited. `split` copies the accounts of the pane it splits (`Term::accounts`), whatever is selected now, looked up again by name, so an account removed since leaves the new pane on the system login rather than pointing it at a deleted folder. `start` and `new-tab` sent from a pane of this server without a `profile` start from that pane's accounts the same way (#409): the `caller`, which the server token already filters (see Commands for scripts and agents), taken as a whole like `split`, with `accounts` replacing only the agents it names; an agent on `personal` that starts more agents must not spend `work` because the window's selection moved since. A request with no caller (a script outside a pane, the window's dialogs, the queue, the bots), from another server's pane or from a pane already closed uses the effective selection, and so does `flow run`, whose run resolves its accounts once (see Flows, below). The editor's pane gets none. Changing the selection never touches open panes: their environment was fixed when they started. Token variables (`ANTHROPIC_API_KEY`, `CODEX_API_KEY`, `GH_TOKEN`…) are left as they are: they are the user's choice, and they win over the folder.
- **Which account a pane's agent uses** (`Term::see_account`, `accounts::Seen`, read on each agent read in `agent_in`): first the accounts cornercase gave the pane (`Term::accounts`), with no process read; else the agent's variable in its own environment (`process::env`), once per `(pid, arguments)`: a folder under `accounts/<agent>/` is that account, any other absolute path is `custom`, no variable is none. Reading the process first was rejected: macOS 26 refuses to read the environment of some processes, and what cornercase set is known exactly. The cost: a variable exported by hand inside a pane that has an account is not seen.
- **Claude's readers follow the pane's folder** (`Look::account_dir`, `claude::Reader::home`): the session file, the transcript, its subagents, `read --last-message` and the context window read `<account>/sessions/<pid>.json` and the projects under it; then the process's own `CLAUDE_CONFIG_DIR` (absolute only), then the server's (`AgentRuntime::claude_dir`). Before, status, context and resume would have read the wrong folder. Codex, Gemini CLI and the others already found their home in the process's environment. The plan probes run once per account with its folder (see Plan usage).
- **Exposed**: `account` on each pane of `status --json`, `watch` and `view` (the name, or `custom`; left out without one, so the v1 fixtures are unchanged), `accounts` (`{agent: account}`) on a pane's `opened` event (at that moment no agent runs yet, so one name would be a guess), `profile` in `status --app` while the active profile exists, and `accounts` there, the effective selection (left out when empty).
- **Saved session**: `AgentState::account` and `PaneState::accounts` (names, never paths), both optional, so `VERSION` stays 5 (`tests/fixtures/session/accounts.json`). A `custom` account is not saved: there is nothing to recreate. A restored pane is spawned with its saved accounts, never the selection (a pane saved without accounts comes back without them, so a system-login conversation never resumes in another account's folder); a resumed agent's account is added for its agent when the pane did not list it. An account that is gone opens the pane as a shell without its variable, does not resume the conversation (it is not in the system folder), logs a `WARN` and toasts `the claude account `work` is gone: its conversation does not resume`.
- **Flows**: a run resolves its accounts when it starts (`Starting::accounts`; `flow run --account` over `--profile`, else the effective selection), every role spawns with those accounts, and changing the selection meanwhile does not move live roles; a restore uses each pane's saved accounts. `start --worktree` keeps the request's accounts across git's answer (`Then::accounts`).
- **Requests** (feature `accounts`; `CONTRACT` stays 1): `account-list`, `account-add` (`provider`, `name`, and `login` with `workspace` and `focus`), `account-remove`, `profile-list`, `profile-new` (`name`, `accounts`), `profile-set` (`name`, `provider` with or without `account`, `rename`), `profile-use` (`""` is *System*) and `profile-delete`. All answer one shape, `AccountsInfo` (the agents with their variable and accounts with `path` and `unshared`, the profiles, the active one, and the login tab's ids), as `config` does. Codes: `malformed` for an unknown agent or invalid name, `conflict` for one that exists, `not-found` for a missing account or profile; everything is checked before anything is made. `account-add` with `login` opens a tab named `<name> login` with that account only and types the agent's login (`AccountHome::login`: `claude auth login`, `codex login`, `gemini`), not focused unless asked; a new account whose links cannot be made is removed again, so adding it again works, while one whose login tab fails to open stays and the error says so. `account-remove` checks that `config.json` can be read before it deletes anything, then deletes the folder (never the keychain: logging out first is `claude auth logout` in a tab of that account) and removes the account from every profile. Renaming or deleting the active profile renames it or goes back to none. `start`, `start-with`, `new-tab` and `flow-run` take `profile` (`null` is the active one, `""` *System*, an unknown name `not-found`, checked before any network for `--issue`); an older server would drop it, so the CLI checks the feature first (`client::use_accounts`), only when `--profile` is given. `fixtures/control/accounts/v1/` pins the answer and the requests.
- **Switching requests** (feature `account-switch`, PR 2): `account-rename` (`provider`, `account`, `""` the own login, `label`, `""` removes it) and `account-use` (`provider`, `account`) answer `AccountsInfo`, which gained per account `label`, per agent `system_label`, `system_path`, `system_login` and `active` (the effective account, `""` the own login), all left out when empty so `answer.json` v1 is unchanged (`answer-switch.json` pins them). Codes: `not-found` for an unknown account, `malformed` for an agent without accounts or an invalid name, `conflict` for a name another account of that agent shows. `start`, `start-with`, `new-tab`, `flow-run` and the queue's `add` and `edit` take `accounts` (`{agent: account}`, always serialized, `""` the own login), which wins over `profile` for its agents; an unknown agent or account is `not-found` before anything is made, also before any network for `--issue`. An older server would drop the field, so the CLI checks `account-switch` first (`client::use_account_switch`) whenever `--account` is given.
- **CLI**: `cornercase account list|add|remove|rename|use` and `cornercase profile list|new|set|use|delete`, `--profile NAME` on `start`, `new-tab` and `flow run`, `--account AGENT=ACCOUNT` (repeatable, `AGENT=` the own login, an agent twice is wrong usage) on those and `queue add|edit`. `account list` prints a `system` line per agent with accounts or a name, `called <name>` and `(in use)`. `account remove` asks `[y/N]` naming the folder and refuses without a terminal unless `--yes`.
- **Never** opens a credentials file or the keychain (a test checks `src/accounts` has no `security` command), and logs names and agents, never a variable's value.
- **In the window only once there is an account** (`App::has_accounts`, from `accounts::list`, listed again when the folder's or an agent folder's modification time changes, on the 1 s sync step and after every `account-*` request, never on a draw): the switcher, the account mark and the account pickers draw nothing without one, so nobody who never adds an account sees a change and no existing snapshot moved (a test checks that the layout and the screen are those of before, in every layout). Each also has a switch of its own in Settings › UI, on by default (`account_mark`, `account_switcher`, `account_picker`; three more `settings::Detail` variants, so they get the note, the `config` key and the request for free): whoever has accounts but does not want the chrome turns it off. The Settings › Accounts tab always shows, since it is where the first account is added.
- **Settings › Accounts** (`settings/accounts.rs` the rows and their texts, `app/accounts_page.rs` the wiring): one section per agent that takes accounts: its own login (`Row::System`, its name or `System`, its default home and its login, checked with the server's own variable), each account, each followed by `rename…` (`Row::RenameAccount`), then `+ add account`; `●` marks the effective selection (a selected account that is gone leaves the own login marked). `Enter` uses a row (`account-use`), `rename…` opens a field with the saved name (empty removes it), `Backspace` on an account asks to remove it. Its actions are the requests' own types (`AccountAdd`, `AccountRename`, `AccountUse`), run by the request handlers, so the window and scripts share every check and refusal; a refusal shows as the page's notice. Names and the selection come from `config`, so an outside edit of `config.json` shows through `take_config` like any setting. No profiles there (see The switcher). Adding an account opens its login tab focused and closes Settings, since the next step is logging in there. Removing one asks first (`Overlay::RemoveAccount`), and the question says the keychain item stays and how to log out before. *System* is recognised as the pick's first item, not by its text, so an account named `System` cannot be mistaken for it.
- **Login state without reading credentials** (`accounts/login.rs`): each agent's own status command (`AccountHome::status`: `claude auth status --json`, `codex login status`; Gemini CLI has none, so no state) runs in a job per account with the account's variable, its folder as working directory, the variables a pane loses removed, empty stdin and 20 s (`process::output_within`). `Known::login` reads only whether it is logged in, the email and the plan (Claude's JSON is read whatever the exit status, since a logged-out Claude exits 1; Codex writes its line to stderr and only `chatgpt` or `api key` is kept). The own login is checked too, only for agents with accounts and a status command, so no test without accounts runs the real `claude`. It runs when the tab opens and every 30 s while it shows, and for `account-list` with `check` (feature `account-login`: an older server would drop the field and answer without checking), which answers once every check has; an account removed meanwhile drops its answer. Reading the credentials files was rejected: Claude keeps them in the keychain on macOS, and a parser of cornercase's would break with their format. The email and the output never reach `server.log`.
- **Token variables by name** (`AccountHome::tokens`, `login::tokens`): `AccountsInfo.tokens` lists the names of the token variables set in the server's environment (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `CODEX_API_KEY`…), never their values, and the Accounts tab and `account list` say they win over every account: otherwise an account that changes nothing looks broken. `GEMINI_FORCE_ENCRYPTED_FILE_STORAGE` is not among them: it is no token and wins over nothing, it makes Gemini CLI's accounts share one keychain item, which the guide says. The check runs without the session variables of a Claude Code or Copilot the server was started in (`CLAUDE_SESSION_ENV`, `copilot::SESSION_ENV`), as panes and the usage probes do, and logs its result at debug, since it repeats every 30 s while the tab shows. Both `login` and `tokens` are left out when empty, so the v1 fixture is unchanged (`answer-login.json` pins them).
- **The switcher** (`ui/accounts_bar.rs`, `app/account_menu.rs`; Orca's hot swap): a status bar along the bottom of the window (see Layout) with a button per agent with accounts, ` claude: work ▾ `, in the order of `Known::ALL`, naming the effective selection (the own login when the selected account is gone); when they do not all fit, the short form ` work ▾ `, then the last ones are left out, and a single one too long is cut with `…`, measured in cells (`text::cells`). `accounts_bar::pills` is the geometry drawing and hits share; hover lights only the button under the pointer. A button opens its agent's menu: the own login and each account by name, `✓` on the one in use, and **manage accounts…** (Settings › Accounts). Choosing runs `account-use` and toasts `new claude tabs use home · open tabs keep theirs`, since nothing else on screen changes. `MenuAction::Account` carries the agent and an index (`AccountItem`) with `config_file.revision` and the generation of the account listing (`Logins::generation`, raised whenever `accounts::list` gives another list), so it stays `Copy`, and a menu opened before `config.json` or the accounts changed (an `account add` from the CLI shifts the indices) does nothing rather than picking another account, as plugin actions do with their revision. The window never shows profiles: one row per agent is what a person switches, and a profile button made people pick a named set to change one agent. Profiles stay in `config.json`, the requests and `cornercase profile`, for scripts; while one is active the buttons show its accounts, and choosing leaves it. Restarting the open agents with the new account is below (Restarting open agents); the window's question about it comes in a later change, so for now choosing only toasts.
- **The account mark** (`ui::Details::account`): a tab's second line, the tab bar's details and the agents section name the account after the model (`Opus 5.5 · work · 12%`), by its name (`App::pane_account`, from `Term::agent_account`: the active pane's, else any pane's of the tab, as for the context; the focused pane's in the tab bar; the row's own pane in the agents section); `custom` shows as such; an agent on its own login shows that login's name, or `System`, only while the agent has accounts (else nothing, so a session without accounts looks as before). A narrow column cuts and then drops the model first, then cuts the account down to 3 cells and then drops it; the percentage, subagents and memory stay. Without an account the line is laid out exactly as before. The cost: a `CLAUDE_CONFIG_DIR` set by hand with no account listed shows no mark.
- **An account where agents are started**: the issue browser (**start** opens the account pick, the one in use selected, whenever the agent that starts has accounts and none was picked for this issue, so `Enter` twice keeps it; trying it showed that an **account…** button on the issue's page alone was never found, and it stays there to pick ahead; `issues::browser::Accounts`, its choice forgotten when the agent changes or another issue is read), the start-a-flow dialog (a combo per agent of the selected flow's team that has accounts, under the branch) and the schedule form (an Account combo beside Agent, on the same row so the form keeps its 23 rows, following the agent); both combos are `accounts::AgentAccounts`, kept with the accounts rather than with flows, since the queue uses it too choose the account for that start only, defaulting to the effective selection, as the agent pick does; the selection never changes. Offered while `account_picker` is on. They send `accounts`, so the start goes through `requested_accounts` like a request; an issue's **start a flow** seeds the flow's combos with the issue's choice. An account removed between choosing and starting is refused where it was chosen, never replaced by another: an issue's **start** shows the refusal in the issue's detail (`Browser::error`) and starts nothing; the flow dialog says so and starts nothing (from an issue it opens without that account, with the refusal as its notice); the schedule form refuses to save it, and a queued entry whose account goes later fails with the reason when its time comes, as a lost destination does; editing such an entry says `the claude account `home` is gone: pick another account`, its combo shows `home (gone)` (`AgentAccounts::missing`, until another account is picked) and saving it unchanged is refused like a new pick, so nothing moves the entry to another account in silence. Starting with an account the user did not choose could spend the wrong account.
- **Plan usage per account**: Usage › Limits and the `usage` request show one section per (agent, account), the usual login's first and the accounts in folder order, the effective selection's marked `●` (only for agents with accounts; the own login's when the selection gives that agent none or names an account that is gone), titled by its name through `usage::heading` (`● Claude Code · work`; the own login is `System` until named), which the CLI shares. `PlanInfo.account`, `label` and `active` are left out when empty, so an answer without accounts is byte for byte as before (`answer-accounts.json` pins one with them).
- **Restarting open agents on another account** (#397, `accounts/transfer.rs`, `app/account_restart.rs`, `app/account_restart/`, `app/control/account_restart.rs`, `cli/accounts.rs`): an agent reads its account from its pane's environment, fixed when the pane was made, so after choosing another account the agents already open kept the old one, and the way to move one was closing its tab and starting it again, losing its conversation. Orca restarts them (its #29898 for Claude Code: a "Switched to X" dialog with keep or restart and a setting ask, always or never; busy sessions restart when their turn ends), so cornercase does too.
  - **Which panes** (`App::panes_on_other_accounts`): those running a live agent of the kind asked for whose account (`Term::agent_account`, `""` for its own login) is not the one asked for (the effective selection when none is named). Left out, with the reason: a `custom` account (its folder was not set by cornercase, so there is nothing to move it to) and a flow's members and orchestrator (`App::seat`: a team keeps the accounts it started with, see Flows). An earlier version marked such panes `account_stale` in `status` and moved waiting restarts along when the selection or a profile changed (`account use --restart` chose and restarted at once); both were dropped before release, since the selection is only what panes start with when they inherit from no one, and a pane differing from it is not stale. `PaneInfo.accounts` (agent → account folder name, from `Term::accounts`, left out when empty so the v1 fixtures are unchanged, and hashed in `refreshed()`) gives each pane's accounts instead, so a script compares them with what it wants.
  - **A shell at its prompt** (`app/account_restart/shell.rs`, `App::respawn_shell`): a pane named in `account-restart` that runs no agent of that kind gets a new shell in its place (`respawn_in`, as below) with that agent's account changed and the others kept, in `Term::cwd` (else the workspace's folder), and nothing typed: a `claude` typed next reads the new account from the environment. Typing `export CLAUDE_CONFIG_DIR=…` into the shell was rejected: it would show in the history, the pane's accounts would not change, and a program reading the old value would keep it. Refused, with the reason (`App::shell_blocker`, checked again when it runs): a flow's seat, a setup that runs, a resume, launch, restart or move in progress (`wait for it to resume`), a person's work by the rule of `send` (`App::person_holds`: a line being typed, or sends held for the pane; `wait for what is typed in it to be sent or cleared`, since the new shell would lose the line and the held sends would fail, the same rule that holds a busy agent), a program in front of the shell (`stop <program> first`, since killing it could lose work) and a shell whose agent variable came from outside cornercase (`its account was not set by cornercase`; read from the process's environment, which macOS 26 hides from other processes, so there it never refuses). Without `panes` shells are left alone: a restart by agent kind should not end shells nobody named.
  - **The same pane, a new shell** (`App::respawn_in`): restarting kills the pane's shell and spawns one in its place with the same id, size, folder (the `cwd` of Claude Code's session file, which names its `projects/` folder, else `Term::cwd`, else the workspace's), `parent` and `collapsed`, and the pane's accounts with only that agent's changed, so the layout, the tab, a flow seat and every id a script holds stay. `Term::generation` goes up on each respawn and the reader tags `Output` and `Exited` with it, so the old shell's last output and its `Exited` are dropped (`App::current_shell`) and never close the new one; the trace sees the same pane id, so `events` sends no `closed` or `opened`. Requests waiting on the pane (`wait`, a held `send`, a launch's confirmation) answer an error naming the restart (`fail_pane_requests`) and its launches are dropped, both only once the new shell has started, so a shell that cannot start (no PTY left, the shell gone) leaves the pane, its requests and its queue as they were. Making a new pane and closing the old one was rejected: every id would change, and a parent would lose its children.
  - **The conversation goes along**: Claude Code keeps it under its folder (`projects/<cwd>/<id>.jsonl`, and `projects/<cwd>/<id>/` with its subagents and tool results), Codex under `CODEX_HOME/sessions/YYYY/MM/DD/`, so `--resume <id>` on the other account would not find it. Before the respawn, a job (`accounts: conversation`) puts those files in the new account's folder (its own login's when it is the agent's own login, `App::default_home`) at the same relative path (`agents::context::Record::conversation_files`, the files the pane's reader follows), then the pane types `agents::resume_line` (the command and arguments from settings, the mode read from the process, `--resume <id>` or `codex resume <id>`) as a `Launch::restart`, the resume launch with its input hold, its ` cancel ` and the band ` restarting claude on personal… `. Marks (`✓`, `●`) come back with the conversation, as after a restore. Gemini CLI's sessions are found by its folder and home, not by a file it is told about, so it is not moved: Gemini starts a new conversation (`agents::start_line`, no `--resume`), without its marks. A Claude Code or Codex agent that has not written its conversation yet starts fresh too.
  - **Why cornercase now writes into the agents' folders**, which until then it only read: the alternative, a fresh conversation, loses the context the user wanted to keep, and the other, Orca's, links every account's `projects/` (and `file-history`, `todos`…) to the agent's own login, so every account shares one history, which is more than a switch asks for (left as a possible setting). So cornercase adds files and nothing else (`accounts::transfer`): each file is a `hard_link` (which never replaces a file), or, when linking fails (another file system), a copy into a private temporary file in the target folder, compared byte for byte with the source and then linked to its name, the temporary file always removed. A target that exists with the same contents (same inode or same bytes) counts as there; one with other contents fails the pane, which keeps running as it was, with the reason in a toast and in the answer, and nothing is overwritten. Every target is checked before anything is linked, so a conflict on the second file leaves no first one behind. New folders are `0700`; the sources are never touched, and a path that is not plain components under the account refuses. The log says `agent restarted pane=… provider=… from=… to=… conversation=linked|copied|moved|fresh` (`moved` when the files were already there), never a path's contents.
  - **A hard link is shared**: the two folders then hold one file, so what the agent writes after resuming shows from the old account too, and resuming it there later writes the same file. An agent that rewrites the file atomically breaks the link without harm. Not moved: Claude Code's `file-history/<id>` (its rewind of past file edits is lost in the new account), `todos/` and `session-env/`, which `--resume` does not need. The trust question of the new account (its own `.claude.json`) is left to the user, as for any resume.
  - **Busy agents wait for their turn** (`App::ask_restart`, `drive_restarts` right after `watch_agents`): an agent waiting (a permission it asked for must not be cut), or held by the rule of `restart --when-idle` (`App::holds_restart`: its turn not over, a launch typing into it, input from a window in the last 2 s, or a submission it has not reacted to), or holding a person's work by the rule of `send` (`App::person_holds`, #371: a draft the person is typing, or sends held for that pane), is kept in `AgentRuntime::restarts` and restarted once none of that holds: idle, done or left with a background shell (which the restart stops). `drive_restarts` decides only on a refresh that has just read every agent (`agents.watched == Some(now)`), so a prompt sent as the turn ends is never cut by a status file that still says idle. Meanwhile its pane shows ` restarts on personal after this turn ` with ` cancel ` (`PaneBand::Restarts`; the input is not held, since the agent is still working), and `status` says `account_restart: "waiting"`. Choosing an account in use or a profile leaves waiting restarts as they are (the selection is a default, not each pane's account); removing the account they wait for drops them (`forget_restarts_to`); an `account-restart` of the pane to the account it already uses cancels its waiting restart (skipped with `already uses that account, so its waiting restart was cancelled`), since the last request says where the pane should be; a pane that closes, respawns or changes agent drops its own. They live in memory only: `kill-server` forgets them, and the restored pane resumes on the account it was saved with.
  - **While the conversation moves** (`Restarts`, `app/account_restart/pending.rs`, which also keeps the restarts waiting for their turn): copying a large transcript to another disk takes a while, and until the respawn the old agent still runs. The pane then shows ` restarting claude on personal… ` with ` cancel ` and takes no keys (what it would type dies with the old shell), a second `account-restart` of that pane to the same account joins the one in flight and is answered with it (to another account it is skipped, saying a restart is already moving), and each move carries a number (`Moving::job`) so a job answering after ` cancel ` and a newer request never takes the newer entry, and ` cancel ` drops the restart when the job answers. The job's answer is applied only if the pane still has the same generation and the same agent process (`context::Pane::agent`, its pid and when it was first seen), so an agent that exited and was started again meanwhile is not killed for the old conversation. A folder on the way that is a symbolic link stops the move with a message saying cornercase does not write through links, and a file that grows while it is copied fails with `changed while it was copied; try again`; with copies, going back to the first account later finds a different file there and is refused (with hard links it is the same file).
  - **For scripts**: the request `account-restart` (`provider`, `account`, `null` for the effective selection, `""` the own login, and `panes`, none for every agent of that kind on another account; feature `account-restart`) answers once every immediate restart has moved its conversation (`Stage::Reading`), with `restarted`, `waiting` and `skipped` (`pane` and `why`; a shell respawned goes in `restarted`); a pane named that does not exist is `not-found` before anything restarts, an agent without accounts `malformed`. The CLI is `cornercase account restart AGENT [ACCOUNT|--system] [--pane ID…]`. `status` text marks `(restarts after this turn)`, and `status --panes` gets `account_restart` as its last column. The window's question (a dialog listing the agents on another account, and a setting ask, always or never) is a later change; until then the status bar only toasts.
- **Left out**: Copilot, Cursor and Grok (above), switching automatically when a limit is reached, profiles in the window, a profile per project, shared history, stats per account, and a red **remove** in the confirmation (`ui::Confirm` has no danger style).
