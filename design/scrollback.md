# Scrollback

Code: `term/emulator.rs`, `app/panes.rs`, `ui/pane.rs`

- **The wheel reads a pane's history**: over a pane whose program does not read the mouse, on the main screen, the wheel moves that pane's view `WHEEL_ROWS` rows through the history the emulator keeps, which before only `read --lines` reached. It acts on the pane under the pointer, active or not, without moving the focus, as tmux and Ghostty's splits do: reading a neighbour's build output should not take the keys from the agent you are typing to. A program that reads the mouse keeps the wheel, as before.
- **How much history**: `term::SCROLLBACK_BYTES`, 10 MB per pane, Ghostty's own default: about 14,000 lines in an 80-column pane, 4,500 at 250 columns. libghostty-vt's `max_scrollback` is documented as lines but Ghostty reads it as bytes (`Screen.init`, `PageList`'s `max_size`), so the 5,000 it was given kept Ghostty's minimum of two pages, about 600 lines at 80 columns and 300 at 250, while the docs promised 5,000. Pages are allocated as output arrives, so a quiet pane costs nothing; one that printed a lot holds up to 10 MB in the server. `term::tests::scrollback` pins a floor at both widths.
- **libghostty-vt's own viewport** (`scroll_viewport`, `scrollbar`) holds the position, so the snapshot the UI draws, the selection (viewport points with a tracked anchor) and path links (`files::link::at` on snapshot rows) follow the scrolled view unchanged. The position belongs to the pane, in the server, so every client, windows and views alike, sees the same view, like the other interaction state (no per-view viewport yet). Rejected: a scroll offset per client (snapshot, selection and links rewritten, and it breaks shared interaction state), and a line buffer of cornercase's own (Ghostty already reflows, styles and measures wide characters).
- **`input` and `scroll`** (see Driving a tab's terminals): `input` brings the view back to the bottom like a window's keys; `scroll` moves the shared view through the history.
- **New output does not move the view** (Ghostty pins a viewport that is not at the bottom); ` ↓ n more ` at the bottom right of the pane (`ui::scrollback_badge`, shared by drawing and hit testing; `Snapshot::below`, `total − offset − len` of the scrollbar) says how many rows are under it and grows while the program prints. It covers the pane's last row and reserves nothing, so the PTY size never changes. A click on it returns to the bottom, as does a key or a paste from a window (`forward_key`, `handle_paste`). `cornercase send` and `keys` do not: an orchestrating agent sending work must not pull a person away from what they are reading.
- **The alternate screen** has no history: the wheel sends `WHEEL_ROWS` Up or Down keys there (encoded like typed arrows, so application cursor mode applies) while the program leaves alternate scroll (DEC mode 1007) on, which is libghostty's default and Ghostty's, iTerm2's and kitty's behaviour, so less, man and git's pager scroll. libghostty scrolls only the active screen, so a program that switches to the alternate screen leaves the main screen where the reader left it, and it shows there again when the program ends. A program that turns mouse reporting on while its pane is scrolled gets its pane back at the bottom on the next snapshot (`Emulator::snapshot`), so the wheel's meaning never depends on a stale view.
- **Readers that decide what a program does read the active screen, never the view**: `Launch` reads `Emulator::active_contents` (the bottom snapshot, the viewport restored after), since a `send --enter` into a pane someone is reading up in would otherwise compare the history with its echo and trust prompt; dialog and survey detection, `read` and `wait --text` already read the active screen.
- Left out: searching the history, keyboard scrolling (keys menu entries or a copy mode), a scrollbar. The landing page's simulation has no history in its fake shells.
