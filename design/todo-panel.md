# TODO panel

Code: `todo/`, `ui/todo.rs`, `app/todo_panel.rs`

- ` TODO ` opens a panel in the changes panel's column (`Areas::changes`, `Widths::changes`, `Border::Changes`); `App::side` selects at most one of the four (changes, TODO, files, flow), and opening the compact menu closes it through `show_side(None)`.
- **A dot while items are pending** (#179): the footer's ` TODO ` button shows a muted `●` after its label (` TODO ● `) while at least one item is pending, and nothing there when every item is done or the list is empty; the compact bar's ` ☐ ` gets the dot one cell to its right, inside its own 7-cell slot (`ui::chrome::todo_icon`, like the ` ≡ `'s badge), so the icon and the buttons beside it never move. Without it, a closed panel looked the same with ten pending items as with none, and items were forgotten. A dot rather than the count that was rejected before ("a number there would always be lit and say little"): it carries no number, it goes away when nothing is left, and it does not light up, since it is the muted grey (`View::muted`), never cyan or a status colour, so it does not compete with ` Changes n ` or an agent that needs you. The count stays in the panel's header. The dot sits inside the button, after its label (` TODO ● `), like Remote's green one (` Remote ● `), and the button grows two cells to the left to hold it, keeping its right edge in line with ` Changes ` (`Areas::todo_with_dot`, which drawing and hit testing share, so a click on the dot opens the panel). Until then the dot sat outside the button, on the cell left of its padding (` ● TODO `), so the button never moved; the user asked for it to work like Remote's. A column too narrow for the wider button (it would touch ` Files `) keeps the plain one and leaves the dot out. `todo_dot` in `config.json` (Settings → UI, on by default, like `counts`) turns it off, for whoever finds the mark noise.
- **`Esc` closes the side panel** (#164), whichever of the three shows (`App::panel_shown`, so a changes panel left open in a workspace without git leaves it to the pane), in every layout, as ` × ` does (`App::close_panel`: the files panel keeps its places, the changes panel its filter). A drag's `Esc`, the compact menu's and an overlay's come first, and the files panel's find field takes one step per press (its text, then the field) and then a file shown full screen goes back to its panel, all before the panel closes, a panel field with text keeps its `Esc` (it clears the files search or the changes filter, or drops the TODO field's text); on an empty field `Esc` closes the panel at once, so `f f`, `g d` or `t` then `Esc` opens and closes. That `Esc` never reaches the pane, so interrupting an agent or leaving insert mode with a panel open takes one more: accepted because the panel is on screen, so the first `Esc` shows what it did, whereas in compact mode, where the panel covers the pane, the `Esc` that reached the hidden pane did something nobody saw. Taking `Esc` only where the pane cannot use it (compact mode, an empty field) was rejected: in wide mode it would close a panel only sometimes, which is harder to learn than one rule. Giving the panel the keys on any click in it, with `Esc` then closing it, was rejected too: every click in the tree or the diff would quietly move the keys away from the pane; worth another look if the panels ever get keyboard navigation. One global list, the same in every project: lists per project and per workspace, and starting an agent from an item (` ▶ `, a worktree or tab per item), were built and dropped as more than a TODO list needs.
- **Storage**: `todos.json` next to `session.json` (`paths::todos`), its own `VERSION`, only `text` and `done` per item, written by a second `persist::Saver<todo::Saved>` once it settles, and flushed on shutdown (a list has no logout burst to fear, and a just-typed item must not be lost to `kill-server`). Item ids are `Todos`' own counter, not the hierarchy's. A missing, corrupt or other-version file means an empty list. The list lives in `App`, so every client sees the same.
- **Order**: pending items, then done ones. A new item goes to the end of the pending ones; checking moves an item to the end of the list, unchecking to the end of the pending ones; a drag keeps an item among its kind (`Todos::move_before` clamps). Undo (`todo::Removed`) puts items back at their old index, clamped to that order.
- **Layout** (`ui::todo`): a header (` TODO n `, ` clear done ` when something is done, ` × `), a gap, then a `ui::Rows` (variable heights, scroll by item, ` ↑ n more ` / ` ↓ n more `, sticky `+ New TODO`), the same as the sidebar lists, so the wheel, `Rows::edge` auto-scroll and `reveal` come for free. Items soft-wrap at a fixed text width (`text_width`: the row minus the checkbox and the reserved ` × ` column), so hover never reflows. The checkbox is `○`, a green `✓` once done, in the middle of its three cells (the hit area `[ ]` had). `ui::todo::{rows, check, delete, clear_done, spot}` serve drawing and hit testing.
- **Editing**: `todo::editor::Editor` is the only text field with a cursor (chars and an index; wrap keeps every char so line/column map back to the text; a full last line gets an empty one for the cursor). The terminal cursor is placed with `set_cursor_position`. `+ New TODO` turns into the field at the bottom; `Enter` adds and keeps it open for the next item, `Enter` on an empty field or `Esc` closes it. A click on an item's text edits it in place with the cursor at the click. Any press outside the field (in the panel or elsewhere) commits it (blur saves, so nothing typed is lost) and gives the keys back; `Esc` is the only way to drop a change. Saving an empty text keeps the old one. Pastes go in as one line.
- **Rows**: a press on an item grabs it (`Grab::Todo` in `Drag::Row` on `App::drag`); release in place is the click (edit), leaving the row is a drag. The landing is computed from the layout without the line (`ui::todo::drop`), and drawing inserts a one-row line. `[ ]` and ` × ` act on press; both also on the item being edited (`ui::todo::hit` looks at them before the field), committing the text first like any press outside the field (#108), so undo brings back what was typed. That item shows its ` × ` without hover: the row is not lit while it is a field, and the button used to vanish exactly while the item was selected.
- **Undo instead of confirming**: ` × ` and ` clear done ` remove at once and set a toast with an ` undo ` button (`Toast::undo`, `UNDO_FOR` 6 s instead of 2 s). Only the last removal can be undone. The toast's button is checked before overlays, so it works with a menu open.
- **The requests cover the panel** (#338, `control/todo.rs`, `app/control/arrange.rs`, `todo::Undos`; feature `todo-panel`): `todo` only added, listed, toggled and removed, so an external UI could not edit an item, put one back, reorder, clear the done ones or undo a removal, all of which the panel does. The `todo` request grew `edit`, `undone`, `move`, `clear-done` and `restore` (`rename_all` went from lowercase to kebab-case, which keeps the four old strings; a test pins them; an older server answers the new ones `malformed`, never ignores them, and the CLI checks the feature before sending them).
  - **`done` stays a toggle**: it is documented as "checks off, or back on", and making it idempotent would change what it means (#283). `undone` is idempotent, like `collapse` and `expand`: a done item goes back among the pending ones, a pending item is left alone. A client that wants an idempotent check reads `done` in the app feed and sends `done` for a pending item only.
  - **`move` uses ids and the panel's rule**: `before` names another item, none means the end of the item's kind, and positions go through `Todos::move_before`, so an item stays among its kind: before an item of the other kind it stops at the end of the pending ones (or becomes the first done one), exactly as a drop does. `before` equal to the item is `malformed`, an unknown id `not-found`. `edit` with a blank text refuses as `add` does.
  - **Undo by token**: `rm` and `clear-done` answer the removed items and an `undo` number; `restore N` puts that removal back where it was (clamped to pending-before-done). The server keeps the last 16 made by requests (`todo::Undos`, in memory, numbered from 1 per server run like every id), apart from the panel's own removals, whose ` undo ` stays in its toast, so the two never hold the same removal; `Todos::restore` skips an item already in the list, so a removal is never restored twice. `clear-done` with nothing done removes nothing and has no `undo`.
  - **A request that removes the item open in the panel's field closes the field**: otherwise the field kept the keys for an item no longer drawn (reachable today with `todo rm`). An `edit` of the item open in the field closes the field too, so a later blur or `Enter` cannot overwrite the request's text.
  - **CLI**: `todo edit`, `undone`, `move ID (--before ID | --last)`, `clear-done`, `restore UNDO`; `rm` and `clear-done` print the `undo` number (`--json` the answer). The command moved to `cli/todo.rs` and `cli/args/todo.rs` (`cli/args.rs` was near the 1,000-line limit).
- **Sending an item to an agent**: an item on the list is often the next prompt for an agent, and getting it there took selecting its text, pasting it into the pane and checking it off by hand. Each pending item now has a `▸` (`ui::todo::send`, shared by drawing and `hit`) in a reserved 3-cell column left of the ` × ` column (`BUTTONS` reserves both, so `text_width` wraps 3 cells earlier and hover never reflows), shown on hover in wide mode and cyan under the pointer, always shown and muted in compact mode, since touch screens have no hover (the TODO `×` still shows only on hover there). Done items and the item being edited have none: a done item is not sent (the command refuses it too), and a text still being typed is not settled. `▸` rather than `▶`, which has an emoji presentation some fonts draw two cells wide.
  - **A menu, not a dialog**: pressing it opens the row menus' `Overlay::Menu` at the pointer with one `MenuAction::SendTodo { todo, pane }` per agent pane, in the agents section's order (`App::agent_places`), labelled with the status icon, the project, the workspace only when the project has several (`› default` says nothing, as in the agents section) and the agent's kind: `● web-shop › feat/x · claude` (`App::todo_agent_label`). The panel has one question to ask, which agent, and a menu at the pointer is how every row already asks for more; a dialog would dim the whole screen for one pick. Sending to the pane on screen without asking was rejected: it is not always an agent, and a prompt into the wrong one costs a turn. With no agent running the toast says `no agent is running` rather than opening an empty menu.
  - **The panel sends the command's request**: choosing an agent builds the same `todo-send` request the CLI sends (`App::send_todo`) and runs it through `run_request` as an internal client of the range `1 << 61` (the chat bots' is `1 << 62`, the queue's `1 << 63`), so every refusal `send --enter` has (an agent waiting for an answer, resuming, showing a dialog, a panel or its shell mode, Claude Code's survey, a full input queue) and the confirmation that the agent recorded the prompt apply to the panel exactly as to the command and cannot drift. `App::todo_answered` takes the answer by its client id: `sent to claude in web-shop › feat/x` with a `✓` on success, `sent to claude in web-shop › feat/x, not confirmed: stays to do` when cornercase cannot confirm (below), the server's own reason with the bug icon on a refusal, and the item stays pending.
  - **Checked off only on a confirmed success**, in `refuse_or_answer` (`Requests::todo_sends`, a `Sending` with the item's id, the text sent and whether the send can be confirmed, by client), the one place every answer goes through, so the command and the panel mark alike and an unconfirmed send (the agent recorded nothing within 10 s) leaves the item pending. Only if the item still exists, is pending and still has the text that was sent: an item edited while its send was in flight is not checked off for text the agent never got, nor one whose open field holds other text not saved yet. A send that cannot be confirmed at all (`App::confirms`, shared with `send --enter`: a local `/` or `!` command, an agent cornercase cannot watch, a record hidden by another agent of the folder) is still sent but never checks the item off, since nothing recorded the prompt; the answer says so with `unconfirmed: true`. The answer also carries `checked` (true only when the item was toggled), so a confirmed send of an item edited meanwhile says that it stays to do (the command's text and the panel's toast). Agent menu labels that would be identical get the tab's label appended, then `pane <id>`. A client that leaves mid-send (`App::forget`) hands its pending entries and its `Sending` to a fresh internal client of the panel's range, silent in `todo_answered`, so the item is still checked off once the agent records the prompt and a second send of it stays refused meanwhile. No special undo: the checkbox unchecks it, and the text is already in the agent. No keyboard shortcut (the keys menu's `t` opens the field; AGENTS.md asks before adding one). The log carries the item's id and the target, never its text.
