# Ports

Code: `ports/`, `control/ports.rs`, `app/control/ports.rs`, `cli/ports.rs`, #496

- **Why**: with several workspaces open, each often runs its own dev server (`vite`, `next dev`, `rails s`, a Storybook), sometimes started by an agent in a pane nobody looked at. Which `localhost:5173` belongs to which worktree was guesswork, and an agent that just started a server had no way to find its URL. This first step lists the ports for scripts and agents (`cornercase ports`, the `ports` request); the dialog in the workspace menu, stopping a server and opening it in the browser come next in #496.
- **What is listed**: every TCP socket in LISTEN state held by one of the user's processes, HTTP or not (a database, `node --inspect` and a Vite HMR socket alike): telling them apart would mean connecting to each, and a wrong guess would hide a server. The server's own pid is left out (browser access listens there). UDP is left out.
- **Discovery** (`ports/listen.rs`), on a job, only when asked:
  - **macOS**: `proc_pidinfo(PROC_PIDLISTFDS)` for each pid's descriptors, then `proc_pidfdinfo(PROC_PIDFDSOCKETINFO)` for each socket. The `libc` crate has the first and `proc_fdinfo`, but not `socket_fdinfo` (libc 0.2.191), so `tcp_listener` reads the kernel's 792-byte answer at fixed offsets (kind, local port in network order, the address families, the local address, the TCP state), measured with `offsetof` against the macOS 26 SDK (Darwin 25.6). The test that listens on `127.0.0.1:0` and `[::1]:0` in the test process fails if a later SDK moves them, and an answer of another size is no listener. Every pid of the user, about 550 processes, takes 3 to 4 ms; `lsof -iTCP -sTCP:LISTEN` took about 40 ms and is not used, not even as a fallback. Processes of other users answer nothing and are skipped.
  - **Linux**: `/proc/net/tcp` and `/proc/net/tcp6`, state `0A`, give each listening socket's inode, address and port; then each pid's `/proc/<pid>/fd` links (`socket:[inode]`, `process::open_files`) say whose it is. The addresses are 32-bit words printed in the machine's byte order, so they are read back with `to_ne_bytes`. Only the server's network namespace is seen: a program in a container or another namespace is not.
  - A pid that ends between the listing and the read answers nothing and is skipped.
- **One row per program and port**: the IPv4 and IPv6 sockets of one process on one port (`0.0.0.0` and `::`) are merged, with every address listed. A dual-stack socket (IPv6, `IPV6_V6ONLY` off) reads as `::`, and an IPv4-mapped address as IPv4. Two processes on one port stay two rows: a socket inherited by forked workers (or a reloader and its child) shows once per process holding it.
- **The URL**: `http://localhost:PORT` when the program listens on every address (`0.0.0.0`, `::`) or on `127.0.0.1`; `http://[::1]:PORT` when it listens only on `::1` (`localhost` may resolve to `127.0.0.1` first, where nothing answers); else the address it listens on, IPv4 first, IPv6 in brackets. Always `http`: the scheme cannot be known without connecting.
- **Which workspace** (`ports::Attribution`, on `process::owners`, see Worktrees dialog):
  1. A process started by one of a workspace's panes (the pane's shell or a descendant, found by walking up its ancestors) belongs to that workspace and pane. This wins over the folder, so a server started in one workspace's tab that `cd`'d into another worktree stays with the tab that started it.
  2. Otherwise, a process whose cwd is inside a workspace's own worktree (the deepest one, so a worktree inside another folder wins), or a flow run's role worktree (it belongs to the run's workspace), belongs to that workspace, with no pane.
  3. **A plain workspace (no worktree of its own) is never matched by folder**: it shares its folder with the project's other plain workspaces and the main checkout, so a cwd cannot say which one it is. Only its panes count.
  4. Anything else belongs to no workspace and is listed only with `--all`.
- **`via`** says which rule matched: `pane`, `agent` or `cwd`; null for no workspace. `agent` is a `pane` match where the process is the pane's agent or one it started: the pane's foreground program is a known agent (`agents::Known`, from its status or `agents::detect`), and the process is that program or descends from it. `agent` then names the agent (`claude`). Agents' own listeners (an MCP bridge, opencode's server) are listed and marked rather than hidden: hiding them would also hide the dev servers agents start, which are the reason for this feature.
- **The request**: `ports` takes `workspace` and `all`, both optional. With neither, the caller's workspace inside a pane, else the shown one (the defaults every command uses); `all` lists every port, each with its workspace or null. `--worktree BRANCH` is resolved by the command through `status`, as the other commands do. The scan runs on a job and the request waits for it (`Stage::Ports`, answered by `AppEvent::Ports`); the attribution needs every workspace's panes even for one workspace, since descent from another workspace's pane wins. The answer is `{"ports": [...]}`: `port`, `addresses`, `url`, `pid`, `program`, `args`, `project`, `workspace`, `pane`, `via`, `agent`. Nothing is in `status`, `watch` or `events`: a scan costs a few ms per call and nothing else changes when a port opens, so a stream would have to poll.
- **Known limits**:
  - **Docker**: a port published by Docker (`docker run -p`, `docker compose up`) is held by Docker's own process (`com.docker.backend` on macOS, `docker-proxy`, run as root, on Linux), not by the `docker` command in the pane, so it cannot be tied to the workspace. It shows with `--all` on macOS, with no workspace, and not at all on Linux, where `docker-proxy` belongs to root. Reading compose labels was left out.
  - A server that daemonizes leaves its pane's process tree; it is found by its folder in a worktree workspace and not at all in a plain one.
  - A program of another user (a `sudo` server) is not seen.
- **Tests**: discovery on ephemeral listeners in the test process on both systems, a closed socket and a pid that is gone; `/proc/net/tcp{,6}` lines and the macOS buffer as data, so both parsers run on either system; merging, URLs, attribution by descent, by an agent, by cwd and by nothing (with `test_util::Family` and sleepers in temp folders); the server left out; the request, a plain workspace's folder never listed and an unknown workspace refused in `app::tests::control_requests::ports`; `e2e::ports` starts a `python3` listener in a tab and finds it with its pane and URL.
