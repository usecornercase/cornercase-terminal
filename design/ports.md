# Ports

Code: `ports/`, `control/ports.rs`, `app/control/ports.rs`, `app/ports_dialog.rs`, `ui/dialog/ports.rs`, `cli/ports.rs`, #496

- **Why**: with several workspaces open, each often runs its own dev server (`vite`, `next dev`, `rails s`, a Storybook), sometimes started by an agent in a pane nobody looked at. Which `localhost:5173` belongs to which worktree was guesswork, and an agent that just started a server had no way to find its URL. The workspace menu's **ports** dialog shows them, opens them in the browser and stops them; `cornercase ports` and `ports stop` do the same for scripts and agents.
- **What is listed**: every TCP socket in LISTEN state held by one of the user's processes, HTTP or not (a database, `node --inspect` and a Vite HMR socket alike): telling them apart would mean connecting to each, and a wrong guess would hide a server. The server's own pid is left out (browser access listens there). UDP is left out.
- **Discovery** (`ports/listen.rs`), on a job, only when asked:
  - **macOS**: `proc_pidinfo(PROC_PIDLISTFDS)` for each pid's descriptors, then `proc_pidfdinfo(PROC_PIDFDSOCKETINFO)` for each socket. The `libc` crate has the first and `proc_fdinfo`, but not `socket_fdinfo` (libc 0.2.191), so `tcp_listener` reads the kernel's 792-byte answer at fixed offsets (kind, local port in network order, the address families, the local address, the TCP state), measured with `offsetof` against the macOS 26 SDK (Darwin 25.6). The test that listens on `127.0.0.1:0` and `[::1]:0` in the test process fails if a later SDK moves them, and an answer of another size is no listener. Reading libproc directly is an order of magnitude faster than `lsof -iTCP -sTCP:LISTEN` (checked in October 2026), so `lsof` is not used, not even as a fallback. Processes of other users answer nothing and are skipped.
  - **Linux**: `/proc/net/tcp` and `/proc/net/tcp6`, state `0A`, give each listening socket's inode, address and port; then each pid's `/proc/<pid>/fd` links (`socket:[inode]`, `process::open_files`) say whose it is. The addresses are 32-bit words printed in the machine's byte order, so they are read back with `to_ne_bytes`. Only the server's network namespace is seen: a program in a container or another namespace is not.
  - A pid that ends between the listing and the read answers nothing and is skipped.
- **One row per program and port**: the IPv4 and IPv6 sockets of one process on one port (`0.0.0.0` and `::`) are merged, with every address listed. A dual-stack socket (IPv6, `IPV6_V6ONLY` off) reads as `::`, and an IPv4-mapped address as IPv4. Two processes on one port stay two rows: a socket inherited by forked workers (or a reloader and its child) shows once per process holding it.
- **The URL**: `http://localhost:PORT` when the program listens on every address (`0.0.0.0`, `::`) or on `127.0.0.1`; `http://[::1]:PORT` when it listens only on `::1` (`localhost` may resolve to `127.0.0.1` first, where nothing answers); else the address it listens on, IPv4 first, IPv6 in brackets. Always `http`: the scheme cannot be known without connecting.
- **Which workspace** (`ports::Attribution`, on `process::owners`, see Worktrees dialog):
  1. A process started by one of a workspace's panes (the pane's shell or a descendant, found by walking up its ancestors) belongs to that workspace and pane. This wins over the folder, so a server started in one workspace's tab that `cd`'d into another worktree stays with the tab that started it.
  2. Otherwise, a process whose cwd is inside a workspace's own worktree (the deepest one, so a worktree inside another folder wins), or a flow run's role worktree (it belongs to the run's workspace), belongs to that workspace, with no pane.
  3. **A plain workspace (no worktree of its own) is never matched by folder**: it shares its folder with the project's other plain workspaces and the main checkout, so a cwd cannot say which one it is. Only its panes count.
  4. Anything else belongs to no workspace and is listed only with `--all`.
- **`via`** says which rule matched: `pane`, `agent` or `cwd`; null for no workspace. `agent` is a `pane` match where the process is the pane's agent or one it started: the pane's foreground program is a known agent (`agents::Known`, from its status or `agents::detect`), and the process is that program or descends from it. `agent` then names the agent (`claude`). Agents' own listeners (an MCP bridge, opencode's server) are listed and marked rather than hidden: hiding them would also hide the dev servers agents start, which are the reason for this feature.
- **The request**: `ports` takes `workspace` and `all`, both optional. With neither, the caller's workspace inside a pane, else the shown one (the defaults every command uses); `all` lists every port, each with its workspace or null. `--worktree BRANCH` is resolved by the command through `status`, as the other commands do. The scan runs on a job and the request waits for it (`Stage::Ports`, answered by `AppEvent::Ports`); the attribution needs every workspace's panes even for one workspace, since descent from another workspace's pane wins. The answer is `{"ports": [...]}`: `port`, `addresses`, `url`, `pid`, `program`, `args`, `project`, `workspace`, `pane`, `via`, `agent`. Nothing is in `status`, `watch` or `events`: a scan costs a few ms per call and nothing else changes when a port opens, so a stream would have to poll.
- **The dialog** (`Overlay::Ports`, `ports::dialog`, `app/ports_dialog.rs`, `ui/dialog/ports.rs`): **ports** in a workspace's row menu (after **open in…**, every layout), always offered, since the menu is built at once and a scan to hide it would cost every right-click. One row per port: tick, URL, the program and its arguments cut to 40 characters (`ports::command_line`: the program's name, never the path, so a Discord helper does not fill the line), pid and where it runs (`pane 12 · dev`, `agent claude · pane 9 · claude`, `in the worktree, no tab`). The row's buttons ` copy ` ` open ` ` go ` ` stop ` show on the hovered and the selected row, and always in compact mode, where the dialog takes the whole screen and a row takes three lines, as in the Worktrees dialog. ` go ` only for a row with a pane (it closes the dialog and shows the pane), ` open ` only in a window that can open it (see Opening in other apps). The empty state says `Nothing in this workspace is listening on a port.`; before the first answer the note says `looking for ports…`. No filter field: a workspace rarely holds more than a handful of ports.
- **Refreshing**: only while the dialog is open, a scan of the workspace every 2 s on a job (`watch_ports_dialog`, from the sync step), never two at once. Each opening gets a new generation, and an answer for another generation is dropped, so a slow scan of a closed dialog never fills the next one. Ticks survive a refresh by pid and port; a port that went away loses its row. The dialog closes when its workspace closes.
- **Stopping** (`ports::stop`): never before a confirmation, a second step of the same overlay, like the Worktrees dialog. ` stop ` on a row asks for that one, the bottom button for the ticked ones (` stop 2 `) or, with nothing ticked, for every port of the workspace (` stop all `), and `Enter` only with ticks. The confirmation names each program, its pid, port and place, warns in yellow when it is the pane's agent or something it started (`via: agent`) and when no tab started it (a process found by its folder, outside cornercase), and says what will happen. The confirmation keeps what was shown, so a refresh does not change what is stopped.
  - **Only the pid that holds the port** gets the signals, never its process group: a group kill would also end the shell or the agent that started the server, and `npm run dev` or `cargo run` end when their child does.
  - **Checked first**: the pid must still listen on that port, and its start (`process::start_stamp`: `pbi_start_tvsec` and `pbi_start_tvusec` on macOS, the start time in jiffies on Linux) must be the one the scan saw, so a pid reused since the list is never signalled. `process::started` stays `None` on macOS, since Grok's session matching compares it with its own record.
  - **Then** SIGTERM to every target at once, a check every 50 ms for up to 3 s, SIGKILL to those still holding their port, and up to 1 s more. **Stopped is the port being released**, not the process being gone: a killed child stays a zombie until its parent reaps it, and a process can close its socket and keep running. The outcome is `stopped`, `killed` (it ignored SIGTERM) or `still-running`; a target that failed the check is left alone and named. It runs on a job, so the 3 s never block the server, and one toast says what happened (`stopped node (pid 48211) on port 3000`, or counts for several); the list refreshes at once.
- **`stop-port`** (`cornercase ports stop PORT [--pid PID]`): the same check and escalation for one port, answered after it (`{port, pid, program, outcome}`). It scans every port and refuses what belongs to no workspace (`conflict`), so the socket cannot be used to stop any program of the user by its port; `not-found` when nothing listens there, `conflict` with the pids when several programs do and no `--pid` says which. The command exits 1 when the program is still running. No `--yes`: unlike discarding changes, stopping a dev server loses nothing that is not restarted by running it again.
- **Opening in the browser**: see Opening in other apps. The server sends the window only the port and the address (`host::open::Browse`), never a URL, and the window builds `http://`.
- **Known limits**:
  - **Docker**: a port published by Docker (`docker run -p`, `docker compose up`) is held by Docker's own process (`com.docker.backend` on macOS, `docker-proxy`, run as root, on Linux), not by the `docker` command in the pane, so it cannot be tied to the workspace. It shows with `--all` on macOS, with no workspace, and not at all on Linux, where `docker-proxy` belongs to root. Reading compose labels was left out.
  - A server that daemonizes leaves its pane's process tree; it is found by its folder in a worktree workspace and not at all in a plain one.
  - A program of another user (a `sudo` server) is not seen.
- **Tests**: discovery on ephemeral listeners in the test process on both systems, a closed socket and a pid that is gone; `/proc/net/tcp{,6}` lines and the macOS buffer as data, so both parsers run on either system; merging, URLs, attribution by descent, by an agent, by cwd and by nothing (with `test_util::Family` and sleepers in temp folders); the server left out; the request, a plain workspace's folder never listed and an unknown workspace refused in `app::tests::control_requests::ports`; `e2e::ports` starts a `python3` listener in a tab and finds it with its pane and URL, then stops it with `ports stop` and is refused the second time. The dialog: snapshots of the list, the empty state, a narrow and a compact window and the confirmation (`ui::tests::ports_dialog`), its model (`ports::dialog::tests`: ticks kept across a refresh, nothing stops before the confirmation, what the stop button takes), the refresh and dropped generations, copy instead of open in a window that cannot open, and a program that no longer holds its port left running (`app::tests::ports_dialog`). The escalation runs on real `python3` listeners (`ports::stop::tests`): one that ends on SIGTERM is stopped, one that ignores it is killed, and a wrong port or a changed start leaves the process running. `server::tests::opening` checks that only the window that can open gets `Browse`.
