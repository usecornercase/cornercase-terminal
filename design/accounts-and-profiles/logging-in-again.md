# Logging in again

Part of [Accounts and profiles](../accounts-and-profiles.md). Code: `control/accounts.rs`, `app/control/accounts.rs`, `cli/accounts.rs`, `cli/args/accounts.rs`, `control/view.rs`, `control/contract.rs`, #702.

- **Why**: a login expires, `account list --check` then says `signed-out`, and no command could log that account in again: `account add --login` only works for a name that does not exist yet. A client that draws cornercase has no login table (which agent logs in with which words), so the one that wanted a "log in" button ran the plain agent in a tab, and an account that exists could not be logged in by a script either.
- **The request `account-login-tab`** (`provider`, `account`, `workspace`, `focus`) opens the tab `account add --login` opens, through the same `open_login_tab`: the tab is named `<account> login`, its pane gets that agent's account and nothing else (never the caller's other accounts: the tab exists to run one login), the request's caller adopts the pane, and cornercase types `<agent command> <AccountHome::login words>` into it (`claude auth login`, `codex login`). `account` is `""` for the agent's own login: the tab is `<agent> login` and its pane has no account, so the agent uses its own. `account` rather than `name`, as in `account-use` and `account-restart`: it names one that exists. `account add` keeps `name` since it makes one. The CLI needs NAME or `--system`, as `account use` does: logging in acts on one login, and a default that moved since (the window's, a profile's) would log in another one without a word. The wire has no `null` for "the default".
- **Refusals, in order, before anything opens**: `malformed` for an agent that is unknown, has no accounts or has no login command; `not-found` for an account that does not exist (a name that is not valid is simply not found, as in `account-use`) and for an unknown workspace; then the refusals `account add --login` has, from the same `login_place` (a closing or removing workspace, no project, a server without a size). Gemini CLI has no login command (`AccountHome::login` is empty), so it is refused with how to sign in instead: start it in a tab of that account and use its first screen. `account add --login` keeps typing plain `gemini` for it, since a new home asks to sign in at once. A refusal after `account add` made the folder says "the account `x` was added, but …" as before.
- **The answer** is `AccountsInfo`, the shape every account request answers, with `login` holding the tab's ids as `account add --login` does. With a view and `focus` it also carries the view's `projection`, an optional field left out otherwise (as `Done.projection` is). The list does not change, so nothing is listed again.
- **Views**: `account-add` and `account-login-tab` are in `takes_view`, so `--view ID` makes the view's workspace the default place and, with `focus`, `show_if` shows the tab in the view and leaves the window alone; without a view `show_if` still moves the window, so Settings › Accounts, which sends no view, is as it was. A view on `account-add` without `login` is ignored on the wire, as `workspace` and `focus` are; the CLI's `--view` requires `--login`, as those do.
- **The feature `account-login-tab`** covers the request and a view on `account-add` and `account-login-tab`. An older server refuses the request by name and a view on `account-add` as `malformed`, but the check is there for the message: the CLI names the machine's `restart` and `update` lines under `--remote`, which an `unsupported` answer would not. `account login` always checks it, `account add` only with `--view`, so `account add --login --focus` still works against an older server. The operation and the feature share the name, as `account-restart` and `flow-close-when-merged` do, because the feature `account-login` already means the `check` of `account-list`: one name must not mean two things in `contract`'s `operations` and `features`.
- **Through `--remote`** both work with no code of their own: `account` is a `Command::Control`, and the tab opens on that machine.
- **Rejected**: letting `account add --login` take an existing name (an add that logs in does not say what it does to an account that exists); `new-tab --account` plus typing the login (every client would copy the table of login words); running the plain agent (it has no account); a `null` account meaning the default one; a field in `AccountsInfo` listing each agent's login command.
- **Left out**: a "log in" action in Settings › Accounts for a signed-out row (TUI only; the issue asks for the command); the issues dialog's login tab for a machine, which keeps sending `new-tab` with the local table (switching it needs every machine to have this release); a login check when the tab's command ends (a client asks `account list --check` again).
