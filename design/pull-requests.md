# Pull requests

Code: `pull_request.rs`, `pull_request/gitlab.rs`, `pull_request/glab.rs`, `pull_request/stack.rs`, `gh.rs`, `app/pull_requests.rs`, `app/pull_requests/glab_hosts.rs`, `app/pull_requests/stack.rs`, `app/control/pull_request.rs`, `control/pull_request.rs`, `cli/pull_request.rs`, `ui/workspaces.rs`, #251, #402, #448, #567

- **Why**: after reviewing the diff, the loop went on outside cornercase: push, open the pull request, watch CI in a browser, come back to tell the agent what broke. With several agents in their own worktrees nothing said which line of work was green, still running or broken. The issue asks for creating the pull request too (`gh pr create` from a button, `cornercase pr`); this first step only shows the pull request an agent or a person already opened, and its checks, since that is what tells you where to look next.
- **Where it comes from**: `gh pr view --json number,title,url,state,isDraft,mergeable,baseRefName,statusCheckRollup`, run in the workspace's folder with no argument, so `gh` picks the pull request of the branch checked out there with its own rules (the branch's upstream and push remote, a fork's owner, open ones first, only open ones for the default branch). Querying GitHub's GraphQL for several head branches in one call was rejected: it would redo those rules, and `gh` already holds the user's login, so cornercase never reads a token. `gh` saying `no pull requests found` is no pull request, not a failure.
- **`gh.rs`**: the runner moved from `issues/github.rs` into a shared leaf, used by both: the environment that keeps `gh` from prompting, paging or colouring, the first line it prints as the error, and now a minute's limit (`process::output_within`, shared with the Tailscale worker, which had the same loop), since a hung `gh` would otherwise hold a project's job for good. The limit covers reading the output too: a program that exits and leaves a child holding its stdout (a wrapper running something in the background) would otherwise keep the readers waiting, so the command runs in a process group of its own, and the whole group is killed when the time is up.
- **Checks** (`pull_request::Check`): `statusCheckRollup` mixes GitHub Actions jobs (`CheckRun`: `status`, `conclusion`, `detailsUrl`, `workflowName`) and commit statuses set by apps (`StatusContext`: `state`, `targetUrl`). Like `gh`'s own summary: a job not `COMPLETED` is pending; `SUCCESS` passed; `NEUTRAL` and `SKIPPED` skipped; `FAILURE`, `CANCELLED`, `TIMED_OUT`, `ACTION_REQUIRED` and `STARTUP_FAILURE` failed (gh counts the last as pending; a job that could not start needs looking at); a status's `SUCCESS` passed, `FAILURE` and `ERROR` failed, the rest pending. A check listed twice (same workflow and name) keeps the run started last, as `gh pr checks` does, except that a run not started yet (gh writes a zero `startedAt`) counts as the latest, so a queued rerun shows as pending rather than as the old result. `gh` fetches every page of the rollup when `statusCheckRollup` is asked for (`preloadPrChecks` in its finder), so a pull request with more than 100 checks is complete. The rollup (`Ci`) is failing if any failed, else pending if any runs, else passing if any passed, else none (no checks, or only skipped ones). They are listed failed first, then pending, passed and skipped, each by workflow and name, with commit statuses (no workflow) after the jobs. Unknown fields and kinds pass, missing ones are empty; `tests/fixtures/gh/2.101.0/pr-view.json` keeps the shape gh 2.101.0 printed.
- **When it is asked** (`App::ask_pull_requests`, on the 1 s sync step of `refresh`): every open workspace on a branch (`git::checked_out`: a detached `HEAD` has no pull request) of a repository with a remote (`git::has_remote`, from the config file, so a local repository, and every test repository, never runs `gh`), except the default branch (`git::origin_head`, `origin`'s `HEAD`, read from the file; gh would only find an open pull request from it, rarely what anyone wants, and the main checkout would cost a call a minute). One job per project at a time, which asks its due workspaces one after the other and stops at the first failure: the next ones would fail the same way (no `gh`, logged out, offline, not a GitHub repository), and calling them all in parallel would hit GitHub at once. Workspaces sharing a folder (plain workspaces) are asked once. A workspace is due every 20 s while its checks run (`RUNNING_EVERY`), every minute otherwise, a pull request newly opened included (`OPEN_EVERY`), and every 5 minutes once merged or closed (`SETTLED_EVERY`); a project whose job failed waits 5 minutes (`FAILED_EVERY`). Opening the dialog, or the `pull-request` request (below), asks again at once and lifts the wait. With `gh` taking about a second, the job's line in `server.log` is promoted to `INFO` only past 30 s (`Job::slow_after`), not past the usual second. The cost: a call a minute per feature branch, a GraphQL point each, against GitHub's 5,000 an hour per user; the server keeps asking while no window is attached, like the `↓n` fetch, since `status` reads it too.
- **Branch changes**: what is found is kept per workspace id with the branch it was asked for (`app::pull_requests::Found`). A workspace that is now on another branch, a detached `HEAD` or the default branch drops it on the next sync, so a checkout never shows another branch's pull request for more than a second, and an answer for a branch the workspace has left is dropped. Closing a workspace drops it too (only open workspaces are listed).
- **The row** (`ui::theme::pull_tag`): `#485` plus the rollup's glyph, all in its colour: `✗` red, `•` yellow, `✓` green; muted without checks; merged in purple (index 99, `ui::theme::MERGED_COLOR`, GitHub's merged colour; it was the brand colour until the brand turned blue, and stayed so a merged pull request reads as GitHub draws it) without a glyph, since its checks no longer matter; closed muted and crossed out. One colour for the whole tag rather than a muted number and a coloured glyph: `Tags::fit` treats each span as one tag, and one colour reads at a glance; the glyph keeps it readable without colour. It sits after the agents' attention icon and before the stack, `⇄n` and `↓n` (`Tags::fit` drops the last tags first in a narrow column), on every layout that draws workspace rows (lists, tree, compact), and at the end of a flow run's diagram, with the same click (see Flows, The end). A draft looks like an open one there; the dialog says draft. It is clickable (see The dialog).
- **The dialog** (`Overlay::PullRequest`): ` ⋯ ` or right-click on a workspace row offers **pull request #485** when there is one (`target_menu`), and `g p` opens it for the workspace on screen. It reuses the update dialog's view (`ui::Update`, as Restart does) with a second button: the title and number as its message, then the summary (`open · 1 failed, 3 passed`) and one line per check with its glyph and workflow. **copy link** (the submit, so `Enter` copies) copies the pull request's address through OSC 52, since the server may be on another machine and cannot open a browser on yours; **ask agent**, only while a check failed or the pull request conflicts (see Merge conflicts), pastes `pull request #485 failed its checks: <name> <link>, … ` into the workspace's agent like a hunk's reference (`App::ask_agent`), not sent, so the user adds a note; without an agent it copies the text. Pasting the failed job's log was rejected: logs run to megabytes, and an agent with the link reads the part it needs with `gh run view`. The dialog closes when the pull request goes away. Clickable check lines (to copy one job's link) were left out: the pull request's page lists them.
  - **The badge opens it** (#279): a left press on the row's `#485✗` opens the same dialog for that workspace, like ` ⋯ ` and `×` on press, without making it active, as the menu entry does (`open_pull_request` closes the compact menu). Pressing anywhere else on the row still grabs it, so selecting, dragging and folding work as before; a right-click on the badge still opens the row menu. The geometry is `ui::pull_badge` (`workspace_pull` for the lists, `tree_pull` for the tree), shared by drawing and hit testing: it runs `Tags::fit` over the same marks (`marks`, shared with `draw_workspace_band`) and asks `Tags::place` where the pull tag landed, so a badge that was dropped in a narrow row, a row being removed and a row scrolled out of view have no target. The area is the badge's cells, one row high, or the band's height in compact mode like its buttons. Hover underlines it in its own colour (`Tags::highlight`), so the colour keeps its meaning, only while `sidebar_hovered`. The name is truncated and measured in cells (`truncate_cells`, `text::cells`) rather than characters, since a wide name would otherwise shift the tags away from the click area. The simulation has no badges, so it has nothing to click.
- **GitLab** (#402): a project on GitLab shows its workspaces' merge requests and pipelines in the same row, dialog and `status`, read with `glab` (`pull_request/gitlab.rs`). Same `PullRequest` and `Check`, with `PullRequest::provider` for the words.
  - **Which provider** (`App::pull_route`, `GlabHosts::route`): by the host of the project's `origin` remote, else its first (`git::remote::primary`). GitLab when the host has `gitlab` in its name, or a host `glab auth status` lists serves it (the same host, a subdomain, or its `ssh_host`); GitHub otherwise (a host that is neither named `gitlab` nor served by a listed host), so GitHub Enterprise and every other host behave as before. `github.com` and its subdomains never cause a glab call, and a remote that is a local path has no host (every test repository). Deciding by `origin` keeps a GitHub project with a GitLab mirror remote on gh, where glab itself would pick the mirror (it ranks `gitlab` above `origin`). Any other host waits for one `glab auth status --all --output json` (`glab::hosts`, the parse `merged` already did), repeated every 15 minutes while glab is signed in to a host, every 5 while not or after a failure, and at once when a project on a new host appears. A signed-out glab is still explained for a host named `gitlab`, since the name alone says glab is the tool to ask. When the list changes, the GitLab projects' last answers are dropped so a fresh `glab auth login` shows without the 5 minutes of waiting.
  - **Which merge request**: `glab mr view --output json` in the workspace's folder with no argument. glab picks the base repository (`upstream`, `gitlab`, `origin`, or `glab repo set-default`) and lists its merge requests whose `source_branch` is the checked-out branch, in any state, so a merged or closed one still shows, as on GitHub. A fork's merge request is found when its parent is a remote (`upstream`, the usual setup); a clone of the fork alone finds none. When glab says `you must select a merge request … Possible matches:` (a reused branch name, or forks sharing one) the newest listed (`!N`, glab lists them newest first) is read with `glab mr view N`: without it that branch would fail the project's poll every time. It may be someone else's on a shared fork branch name, where gh decides by the head repository's owner. `no open merge request available` is none, not a failure.
  - **The pipeline's jobs**: `head_pipeline` of the merge request (a merged results pipeline when the request is mergeable; GitLab runs a detached merge request pipeline instead while it conflicts, so jobs are not missing as on GitHub and the dialog has no conflict note) and one `glab api --paginate projects/<head_pipeline.project_id>/pipelines/<id>/jobs?per_page=100`, run in the same folder so glab picks the same host. The project is the pipeline's, not the merge request's: a fork's pipeline ran in the fork. Retried jobs are left out by the API. The answer is read as consecutive JSON arrays, since glab 1.124 prints one merged array and older ones concatenated pages. A job is `success` passed; `failed` failed, unless `allow_failure` (skipped, GitLab's "passed with warnings"); `canceled` failed; `skipped` and `manual` skipped; everything else (`created`, `preparing`, `waiting_for_resource`, `pending`, `running`, `scheduled`, `canceling`, unknown) pending. The stage is what the dialog shows where GitHub shows the workflow. Ordering is the GitHub one.
  - **The pipeline as a check**: the jobs call leaves out bridges (a trigger job whose child pipeline failed), and a pipeline with a YAML error has no jobs. When the pipeline's own status is worse than its jobs (it failed while no job did, or it runs while no job failed or runs) one more check named `pipeline`, with no stage and the pipeline's link, carries its outcome, so the row is never greener than GitLab's verdict. A second call for the bridges was rejected: it costs another call a poll for a rarer case that this covers.
  - **Conflicts**: `has_conflicts` (always present), except `detailed_merge_status` `checking`, `unchecked` and `preparing`, which are unknown (`None`, so `keep_known` keeps the last value) and `conflict`, which always conflicts. `detailed_merge_status` names only the first thing that blocks the merge, so it is not the conflict flag: on 2026-10-21 (glab 1.124.0, gitlab.com) of 78 open merge requests in gitlab-org/cli, 32 were `unchecked` and several had `has_conflicts: true` with `draft_status`, `discussions_not_resolved` or `requested_changes`.
  - **Words** (`Provider`): the row and the flow's tag keep `#486` (`pull_tag`, `Mark`), since `!` is already the waiting icon's mark and the conflict mark, and `! !486!` would read badly. Every text that names the noun uses GitLab's own reference: the menu (**merge request !486**), the dialog (title `Merge request`, message `!486 …`), ask agent (`merge request !486 has merge conflicts … failed its pipeline: …`), the `g p` toast and `status`. None starts with `!`, so Claude Code's shell mode never sees one. The setting's note says `from gh or glab`.
  - **Without glab**: glab is not run for a host it is signed out of (verified with glab 1.124.0: public merge requests read without a token, so skipping the call is a choice, and the same as gh, which needs a login). The project's answer is the reason instead: `glab is not logged in: run glab auth login` when the host's `token_source` is `none` or its error holds `401`, else the host's own error, `install glab, GitLab's CLI, to see them`, or `update glab to see them`. The note shows a reason when every project read with one tool failed (GitHub's first, then GitLab's): "every project" would hide a missing glab whenever some GitHub project works. A project that can no longer be read through glab (logged out, host gone) also drops the merge requests it showed, unlike a failed poll, which keeps the last known ones. A pipeline without a status adds no `pipeline` check. Nothing is explained for a project with nothing due, so one on its default branch never gets an error, as gh is never asked for it.
  - **glab's errors** (`glab::said`): since about 1.9x glab styles stderr with fang even through a pipe (blank lines, a line `ERROR`, the message capitalized with a final period), where `gh::failure` would have returned `ERROR`; 1.123 and later also print the message as `{"error":{"message":…}}` on stdout under `--output json`. `said` reads that envelope (an object `error` with a string `message`; an API body with `"error": "<text>"` is not one), else stderr without its header, else stdout. Matches are case-insensitive. The same function now reads Stats' glab errors, which looked for `unknown flag` in lower case. Only `no open merge request available`, `possible matches:`, `glab auth login` and a 401 status (`401 Unauthorized`, `HTTP 401`, `: 401 `, never the bare digits, which a project or job id can hold) are matched: glab's wording is not a contract, and `tests/fixtures/glab/1.124.0` pins today's.
  - **Cost**: `mr view` is three API calls on GitLab's side (the list, the merge request, its approvals), plus one for the jobs, per workspace per poll, and one `auth status` per 15 minutes while a host other than github.com is open. Pacing, gates and one job per project are the GitHub ones.
  - **Rejected**: GraphQL in one call for several branches (it would redo glab's branch rules); the Issues tab's token (cornercase reads no token for gh, and glab knows the user's self-hosted hosts); a provider argument in the flow's brief (the agent can read `git remote -v`; one clause says `glab mr create`); `!486` on the row.
- **Merge conflicts** (#359): GitHub runs no `pull_request` workflows while a pull request conflicts with its base (`mergeable: CONFLICTING`, `mergeStateStatus: DIRTY`), so its rollup held only what apps had set (a review bot's commit status): a conflicting pull request with one passing status showed a green `#356✓` and a dialog of one check. `gh pr view` is now asked for `mergeable` and `baseRefName` too; `CONFLICTING` and `MERGEABLE` become `PullRequest::conflicting` (`Some(true)`, `Some(false)`). `UNKNOWN`, which GitHub answers while it works the value out in the background (the first time anyone asks, after a push to the branch or its base, and always for merged and closed ones), and a missing field are `None` and change nothing: the answer keeps what the last one knew for the same pull request (`PullRequest::keep_known`, applied before the mark is compared and logged), so a known conflict never flashes green for a poll, and with nothing known the row shows the checks as before. Asking sooner while it is unknown was left out: the next poll (a minute, 20 s while checks run) gets it, and opening the dialog asks at once. Merged and closed pull requests never conflict. `tests/fixtures/gh/2.101.0/pr-view-conflicting.json` is the real shape of one.
  - **The row**: an open or draft pull request that conflicts shows `#486!` in the waiting orange (208) whatever its checks: the mark ranks before the rollup, since its checks did not run. `!` in orange is what needs you elsewhere (an agent waiting), and a conflict needs someone to merge or rebase; red stays for failed checks. Rejected: `⚠` (emoji presentation, two cells in some fonts), `≠` and `⇄` (do not read as a conflict), `✗` (the failed checks' mark), a word (too wide for the row's tags).
  - **The dialog**: the summary says it before the counts (`open · conflicts with main · 1 passed`; `with its base` when gh named none), and two muted lines under it say GitHub runs no `pull_request` workflows until the conflict is resolved, so checks may be missing. Two fixed lines of 47 cells rather than one, since notes are not wrapped and the dialog's text is 68 cells wide. The notes are built in one place (`App::pull_notes`, which also builds the stack section), whose length the scroll uses.
  - **ask agent** is offered for a conflict too and pastes `pull request #486 has merge conflicts with main ` (then ` and failed its checks: …` when some failed). No `git` command is suggested: the agent knows how, and the text is not sent, so the user adds a note.
  - **Scripts**: `pull_request` gets `conflicts` and `base` (or `null`), additive under the contract's rules; `checks` stays the rollup of what ran. `App::refreshed` hashes both, so `status --follow` and views see a conflict appear.
- **Stacks** (#448): GitHub's stacked pull requests (generally available on github.com, 2026-10-06) chain pull requests of one repository: the bottom one targets the trunk, each one above the branch of the one below, and they merge bottom up. One agent per worktree makes a layered change several workspaces whose pull requests depend on each other, and each row said only its own `#579✓`. This step shows what GitHub knows about the stack of the pull request already on the row; creating, syncing and merging stacks are left to `gh stack` and later issues.
  - **Where it comes from** (`pull_request::stack`): `gh pr view --json` has no stack field (gh 2.101.0), so after it finds a pull request the same `pr` job runs one `gh api graphql --hostname <host>` on `resource(url:)` → `PullRequest.stack` (`number`, `size`, `baseRefName`, `entries(first: 100)`: each layer's position, number, title, URL, state, draft, `mergeable`, `reviewDecision`, `statusCheckRollup.state`), one point (`rateLimit { cost }`, 2026-10-22). The pull request is named by its URL and the host comes from it, so it is asked where it lives, never in gh's default repository; `gh pr view` stays the way to find the branch's pull request (#251). Rejected: REST's `/stacks?pull_request=N` (no checks or reviews: what blocks would cost a call per layer) and gh-stack's local catalogue (optional, internal format).
  - **Pacing**: an answer records every layer's URL and covers every workspace of the project whose pull request is in the stack, so a stack of three open workspaces costs one call per poll. A pull request in a stack is asked at its own pace (20 s while checks run, else a minute) unless another layer's answer covered it since; one in no stack every 5 minutes (`SETTLED_EVERY`), since joining a stack is rare; opening the dialog asks at once; merged and closed ones keep their last answer (asked once per server run if never asked). Without stacks that is about one point per open feature branch every 5 minutes.
  - **Failures**: GitHub Enterprise Server has no stacks yet and answers `undefinedField` (gh exits 1 with the error body on stdout, hence `gh::run_output`): its pull requests have no stack and the host is not asked again until the server restarts (or the setting is turned off and on), without a note in the settings. That body was captured on github.com with a misspelt field, not on a GHES. Any other failure keeps the last known stack and logs `cannot read the stack` once per reason; the pull request still shows and the project's poll goes on.
  - **What blocks** (`Stack::blocker`): the lowest open or draft layer below that conflicts or failed its checks, else the lowest with changes requested; per layer a conflict ranks before failed checks, as on the row. Merged and closed layers never block: GitHub answers `mergeable: CONFLICTING` for merged layers (seen on github/gh-stack, 2026-10-22). A layer's checks are GitHub's rollup state (`FAILURE`/`ERROR` failing, `PENDING`/`EXPECTED` pending, `SUCCESS` passing), not cornercase's per-check rollup, so in rare cases (a rerun) a layer's line can differ from that layer's own row; this layer's own glyph in the dialog comes from its own checks so it never contradicts its row. An unknown `mergeable` keeps the last known value per layer (#359). cornercase cannot see all GitHub checks (linear history, branch rules), so the dialog only says what it saw.
  - **The row**: `position/size` after the pull tag (GitHub's numbers, 1 at the bottom; merged layers stay counted, as on GitHub), muted, red when what blocks is a failed check, orange (208) when it is a conflict, since either keeps this layer from merging whatever its own checks say; changes requested stay muted. Plain digits rather than a glyph: one cell in every font. `Tags::fit` drops it after `↓n` and `⇄n` (see Shared files) and before the pull tag; pressing it opens the dialog (`Tag::Stack`). Every layout that draws the pull tag shows it; a flow's diagram does not.
  - **The dialog**: between the summary and the checks, `stack #484 on main · layer 2 of 3` and the layers top first (as `gh stack view` prints them), each with its position, number, glyph, title and the workspace of this project that holds it (by its found pull request, no git reads while drawing), this one marked `▸`, merged ones purple, closed ones crossed out; a click on a line goes to its workspace. One line says what blocks the merge, only when something does. When a layer below merged and the branch is behind its remote, a muted note says to pull before pushing again (what GitHub does to the branch after a partial merge was not checked live: creating a stack on a real repository is an outward action). ask agent is unchanged: the agent to ask about a layer below is the one in its workspace. Lines are cut to the dialog's width (`PullNotes` builds the lines and the workspace each one leads to, so the view, the scroll and the click cannot drift apart). The hovered line is not filled.
  - **GitLab**: no stack (`null`): its API has no stack object (`glab stack` is local and experimental; merge request dependencies are another, paid feature).
  - **Left for later**: stacking a new workspace on this one (`worktree::create_from`), merging and syncing from cornercase, chains GitHub does not know as stacks, a line between a stack's rows in the sidebar.
- **Reading one at once (#567)**: `status` and `view` give a program that draws cornercase (#345) the rollup and the failed names, not the dialog's list (pending, passed and skipped checks, workflows, links), and nothing asked again at once or said why a read failed. `pull-request` (operation 113; `cornercase pull-request [--workspace ID | --worktree BRANCH] [--json]`) does what opening the dialog does (`App::ask_pull_request_now`, shared with `open_pull_request`: the workspace and its stack due now, the project's wait lifted, `ask_pull_requests` run) and answers once that workspace was read: `{"workspace", "branch", "pull_request", "reason"}`, `pull_request` being `status`'s object plus `all_checks` (`name`, `workflow`, `outcome`, `url`, in the dialog's order). The list is an optional field of `PullRequestInfo` that `status`, `watch` and `view` leave out, so their lines keep their size and the v1 fixtures their bytes, and the two answers come from one builder. It waits on state, not on a job: the pending `Stage::PullRequest` is answered on the step where the workspace's `Found::at` is set again (the reset made it `None`), so a read already under way when the request comes counts, as it does for the dialog; or when the project's `answered` holds an error (the handler removed the previous one), and then it is refused with the dialog's reason, exit 1. Since a project's job stops at its first failure, a failure on another workspace of the project fails it too, as the dialog's note shows it. A workspace cornercase never asks about (pull requests off, not on a branch, no remote, the default branch: `branch_to_ask`, the rule the poll uses too, so the two cannot disagree) is answered at once with `pull_request: null` and the reason, exit 0, like the `g p` toast; so is a branch with none. No timeout of its own: gh and glab have their minute, and a workspace that closes ends the wait. Rejected: every check in `status` and `view` (each `view` line would grow by every check of every workspace, and nothing could ask again or say why); the program running `gh pr view` itself (it would redo the server's rules, need to know which tool a host takes, and poll twice); a `--cached` read for the flow of asking again when `view`'s `pull_request` changes (one more read per change while that dialog is open, accepted for now). No feature string: an older server refuses the name.
- **Without gh**: nothing shows on the rows; **settings → Worktrees → pull requests** (`pull_requests` in `config.json`, on by default) says why in its note when every project read with one tool (gh, then glab) failed on its last answer (`install gh, GitHub's CLI, to see them`, `gh is not logged in: run gh auth login`, or gh's own line), `g p` toasts it, and `server.log` has one `WARN` per new reason (`pr: cannot read pull requests`). Off asks nothing and drops what was found. On by default because a user without `gh`, or without remotes, pays nothing (the spawn fails at once, or nothing is asked), and the feature is invisible until a pull request exists.
- **Scripts**: `status --json` gives each workspace a `pull_request` (`number`, `title`, `url`, `state`, `checks`, `failed`, `conflicts`, `base`, `provider`, `stack`), the text form `pull request #485 open, checks failing` (`pull request #486 open, conflicts with main, checks passing` with a conflict, `pull request #483 open, checks passing, layer 2 of 3 of stack #484 on main` in a stack). `stack` is `null` outside one: `number`, `base`, `position`, `size` and `layers` bottom first (`number`, `title`, `url`, `state`, `checks`, `conflicts`, `review`), additive; `App::refreshed` hashes it. `provider` is `github` or `gitlab` (`""` from an older server, read as GitHub), additive under the contract's rules; on GitLab `number` is the merge request's `iid`, `checks` sums up the latest pipeline's jobs, and the text form is `merge request !486 open, conflicts with main, pipeline passing`. `App::refreshed` hashes the provider too. A command to create one (`cornercase pr`) and events when checks finish were left for later.
