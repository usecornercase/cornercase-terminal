# Pull requests

Code: `pull_request.rs`, `gh.rs`, `app/pull_requests.rs`, `ui/workspaces.rs`, #251

- **Why**: after reviewing the diff, the loop went on outside cornercase: push, open the pull request, watch CI in a browser, come back to tell the agent what broke. With several agents in their own worktrees nothing said which line of work was green, still running or broken. The issue asks for creating the pull request too (`gh pr create` from a button, `cornercase pr`); this first step only shows the pull request an agent or a person already opened, and its checks, since that is what tells you where to look next.
- **Where it comes from**: `gh pr view --json number,title,url,state,isDraft,mergeable,baseRefName,statusCheckRollup`, run in the workspace's folder with no argument, so `gh` picks the pull request of the branch checked out there with its own rules (the branch's upstream and push remote, a fork's owner, open ones first, only open ones for the default branch). Querying GitHub's GraphQL for several head branches in one call was rejected: it would redo those rules, and `gh` already holds the user's login, so cornercase never reads a token. `gh` saying `no pull requests found` is no pull request, not a failure.
- **`gh.rs`**: the runner moved from `issues/github.rs` into a shared leaf, used by both: the environment that keeps `gh` from prompting, paging or colouring, the first line it prints as the error, and now a minute's limit (`process::output_within`, shared with the Tailscale worker, which had the same loop), since a hung `gh` would otherwise hold a project's job for good. The limit covers reading the output too: a program that exits and leaves a child holding its stdout (a wrapper running something in the background) would otherwise keep the readers waiting, so the command runs in a process group of its own, and the whole group is killed when the time is up.
- **Checks** (`pull_request::Check`): `statusCheckRollup` mixes GitHub Actions jobs (`CheckRun`: `status`, `conclusion`, `detailsUrl`, `workflowName`) and commit statuses set by apps (`StatusContext`: `state`, `targetUrl`). Like `gh`'s own summary: a job not `COMPLETED` is pending; `SUCCESS` passed; `NEUTRAL` and `SKIPPED` skipped; `FAILURE`, `CANCELLED`, `TIMED_OUT`, `ACTION_REQUIRED` and `STARTUP_FAILURE` failed (gh counts the last as pending; a job that could not start needs looking at); a status's `SUCCESS` passed, `FAILURE` and `ERROR` failed, the rest pending. A check listed twice (same workflow and name) keeps the run started last, as `gh pr checks` does, except that a run not started yet (gh writes a zero `startedAt`) counts as the latest, so a queued rerun shows as pending rather than as the old result. `gh` fetches every page of the rollup when `statusCheckRollup` is asked for (`preloadPrChecks` in its finder), so a pull request with more than 100 checks is complete. The rollup (`Ci`) is failing if any failed, else pending if any runs, else passing if any passed, else none (no checks, or only skipped ones). They are listed failed first, then pending, passed and skipped, each by workflow and name, with commit statuses (no workflow) after the jobs. Unknown fields and kinds pass, missing ones are empty; `tests/fixtures/gh/2.101.0/pr-view.json` keeps the shape gh 2.101.0 printed.
- **When it is asked** (`App::ask_pull_requests`, on the 1 s sync step of `refresh`): every open workspace on a branch (`git::checked_out`: a detached `HEAD` has no pull request) of a repository with a remote (`git::has_remote`, from the config file, so a local repository, and every test repository, never runs `gh`), except the default branch (`git::origin_head`, `origin`'s `HEAD`, read from the file; gh would only find an open pull request from it, rarely what anyone wants, and the main checkout would cost a call a minute). One job per project at a time, which asks its due workspaces one after the other and stops at the first failure: the next ones would fail the same way (no `gh`, logged out, offline, not a GitHub repository), and calling them all in parallel would hit GitHub at once. Workspaces sharing a folder (plain workspaces) are asked once. A workspace is due every 20 s while its checks run (`RUNNING_EVERY`), every minute otherwise, a pull request newly opened included (`OPEN_EVERY`), and every 5 minutes once merged or closed (`SETTLED_EVERY`); a project whose job failed waits 5 minutes (`FAILED_EVERY`). Opening the dialog asks again at once and lifts the wait. With `gh` taking about a second, the job's line in `server.log` is promoted to `INFO` only past 30 s (`Job::slow_after`), not past the usual second. The cost: a call a minute per feature branch, a GraphQL point each, against GitHub's 5,000 an hour per user; the server keeps asking while no window is attached, like the `↓n` fetch, since `status` reads it too.
- **Branch changes**: what is found is kept per workspace id with the branch it was asked for (`app::pull_requests::Found`). A workspace that is now on another branch, a detached `HEAD` or the default branch drops it on the next sync, so a checkout never shows another branch's pull request for more than a second, and an answer for a branch the workspace has left is dropped. Closing a workspace drops it too (only open workspaces are listed).
- **The row** (`ui::theme::pull_tag`): `#485` plus the rollup's glyph, all in its colour: `✗` red, `•` yellow, `✓` green; muted without checks; merged in purple (index 99, `ui::theme::MERGED_COLOR`, GitHub's merged colour; it was the brand colour until the brand turned blue, and stayed so a merged pull request reads as GitHub draws it) without a glyph, since its checks no longer matter; closed muted and crossed out. One colour for the whole tag rather than a muted number and a coloured glyph: `Tags::fit` treats each span as one tag, and one colour reads at a glance; the glyph keeps it readable without colour. It sits after the agents' attention icon and before `↓n` (`Tags::fit` drops the last tags first in a narrow column), on every layout that draws workspace rows (lists, tree, compact), and at the end of a flow run's diagram, with the same click (see Flows, The end). A draft looks like an open one there; the dialog says draft. It is clickable (see The dialog).
- **The dialog** (`Overlay::PullRequest`): ` ⋯ ` or right-click on a workspace row offers **pull request #485** when there is one (`target_menu`), and `g p` opens it for the workspace on screen. It reuses the update dialog's view (`ui::Update`, as Restart does) with a second button: the title and number as its message, then the summary (`open · 1 failed, 3 passed`) and one line per check with its glyph and workflow. **copy link** (the submit, so `Enter` copies) copies the pull request's address through OSC 52, since the server may be on another machine and cannot open a browser on yours; **ask agent**, only while a check failed or the pull request conflicts (see Merge conflicts), pastes `pull request #485 failed its checks: <name> <link>, … ` into the workspace's agent like a hunk's reference (`App::ask_agent`), not sent, so the user adds a note; without an agent it copies the text. Pasting the failed job's log was rejected: logs run to megabytes, and an agent with the link reads the part it needs with `gh run view`. The dialog closes when the pull request goes away. Clickable check lines (to copy one job's link) were left out: the pull request's page lists them.
  - **The badge opens it** (#279): a left press on the row's `#485✗` opens the same dialog for that workspace, like ` ⋯ ` and `×` on press, without making it active, as the menu entry does (`open_pull_request` closes the compact menu). Pressing anywhere else on the row still grabs it, so selecting, dragging and folding work as before; a right-click on the badge still opens the row menu. The geometry is `ui::pull_badge` (`workspace_pull` for the lists, `tree_pull` for the tree), shared by drawing and hit testing: it runs `Tags::fit` over the same marks (`marks`, shared with `draw_workspace_band`) and asks `Tags::place` where the pull tag landed, so a badge that was dropped in a narrow row, a row being removed and a row scrolled out of view have no target. The area is the badge's cells, one row high, or the band's height in compact mode like its buttons. Hover underlines it in its own colour (`Tags::highlight`), so the colour keeps its meaning, only while `sidebar_hovered`. The name is truncated and measured in cells (`truncate_cells`, `text::cells`) rather than characters, since a wide name would otherwise shift the tags away from the click area. The simulation has no badges, so it has nothing to click.
- **Merge conflicts** (#359): GitHub runs no `pull_request` workflows while a pull request conflicts with its base (`mergeable: CONFLICTING`, `mergeStateStatus: DIRTY`), so its rollup held only what apps had set (a review bot's commit status): a conflicting pull request with one passing status showed a green `#356✓` and a dialog of one check. `gh pr view` is now asked for `mergeable` and `baseRefName` too; `CONFLICTING` and `MERGEABLE` become `PullRequest::conflicting` (`Some(true)`, `Some(false)`). `UNKNOWN`, which GitHub answers while it works the value out in the background (the first time anyone asks, after a push to the branch or its base, and always for merged and closed ones), and a missing field are `None` and change nothing: the answer keeps what the last one knew for the same pull request (`PullRequest::keep_known`, applied before the mark is compared and logged), so a known conflict never flashes green for a poll, and with nothing known the row shows the checks as before. Asking sooner while it is unknown was left out: the next poll (a minute, 20 s while checks run) gets it, and opening the dialog asks at once. Merged and closed pull requests never conflict. `tests/fixtures/gh/2.101.0/pr-view-conflicting.json` is the real shape of one.
  - **The row**: an open or draft pull request that conflicts shows `#486!` in the waiting orange (208) whatever its checks: the mark ranks before the rollup, since its checks did not run. `!` in orange is what needs you elsewhere (an agent waiting), and a conflict needs someone to merge or rebase; red stays for failed checks. Rejected: `⚠` (emoji presentation, two cells in some fonts), `≠` and `⇄` (do not read as a conflict), `✗` (the failed checks' mark), a word (too wide for the row's tags).
  - **The dialog**: the summary says it before the counts (`open · conflicts with main · 1 passed`; `with its base` when gh named none), and two muted lines under it say GitHub runs no `pull_request` workflows until the conflict is resolved, so checks may be missing. Two fixed lines of 47 cells rather than one, since notes are not wrapped and the dialog's text is 68 cells wide. The notes are built in one place (`App::pull_request_lines`), whose length the scroll uses.
  - **ask agent** is offered for a conflict too and pastes `pull request #486 has merge conflicts with main ` (then ` and failed its checks: …` when some failed). No `git` command is suggested: the agent knows how, and the text is not sent, so the user adds a note.
  - **Scripts**: `pull_request` gets `conflicts` and `base` (or `null`), additive under the contract's rules; `checks` stays the rollup of what ran. `App::refreshed` hashes both, so `status --follow` and views see a conflict appear.
- **Without gh**: nothing shows on the rows; **settings → Worktrees → pull requests** (`pull_requests` in `config.json`, on by default) says why in its note when every project's last answer failed (`install gh, GitHub's CLI, to see them`, `gh is not logged in: run gh auth login`, or gh's own line), `g p` toasts it, and `server.log` has one `WARN` per new reason (`pr: cannot read pull requests`). Off asks nothing and drops what was found. On by default because a user without `gh`, or without remotes, pays nothing (the spawn fails at once, or nothing is asked), and the feature is invisible until a pull request exists.
- **Scripts**: `status --json` gives each workspace a `pull_request` (`number`, `title`, `url`, `state`, `checks`, `failed`, `conflicts`, `base`), the text form `pull request #485 open, checks failing` (`pull request #486 open, conflicts with main, checks passing` with a conflict). A command to create one (`cornercase pr`) and events when checks finish were left for later.
- **Simulation**: its workspaces have no pull requests (it has no GitHub); its Worktrees tab lists the row and its keys menu `g p`, and both say they need a real cornercase, as the icon bar does.
- **Tests**: a fake `gh` (`test_util::fake_gh`) answers by the branch it runs on; app tests use a clone with a worktree, so the default branch and remotes count. `new_app` points a default `gh` at `/nonexistent/gh`, so no app test runs the real one even in a repository with a remote.
