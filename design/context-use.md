# Context use

Code: `agents/context.rs`, `agents/claude/transcript.rs`, `agents/codex/rollout.rs`, `agents/gemini/session.rs`, `agents/opencode/database.rs`, `agents/grok/session.rs`, `agents/cursor/store.rs`, `agents/copilot/session.rs`

- `agents/context.rs` owns `Record`, the last-message location chosen by a pane, and dispatches its reads to each agent's folder. `context/message.rs` keeps only the shared backwards JSONL and text helpers and `Said`. The `context::Record` path used by callers stays the same.
- **One reader per pane** (#198, PR 3): `context::Pane` owns only the shared identity and first-seen time, shown context, newest prompt time, counting ledger and `Option<Reader>`. The exhaustive `Reader` enum dispatches to `claude::Reader`, `codex::Reader`, `gemini::Reader` and `opencode::Reader` in their folders' `mod.rs`. Each reader owns its record state and discovery job: Claude's transcript, subagent tails and last session file; Codex's rollout; Gemini's session plus the record retained while a job owns the session; opencode's session and model cache. Readers update the shared shown value directly, so Claude still recomputes it only on a new reply, and return their newest prompt time for the pane's monotonic maximum. A changed pid or identity replaces all shared and reader state, and no detected agent clears the pane. Conversation switches keep the prompt time and counting ledger as before. `record_for` first checks the pane's current identity, then asks its reader, so a process that execs another agent cannot answer from the former record. Conversation and activity use the same reader; unknown Gemini titles and unread opencode databases still give no activity.
- `Look` carries the process id, owned arguments and title, the Claude config folder and a lazy screen callback. Arguments move from process detection into the look and back to the common watcher's resume step, without another copy. Gemini reads the screen every watch for its footer; Claude's update reads only its session file. `Known::input_box` accepts a lazy callback so the common watcher reads Claude's screen only until calibration succeeds, and never reads Codex's or opencode's screen. Each discovery job remains one in flight per pane at the same 500 ms pace; no new thread or scan is added. Claude's `Limits::read` takes the look's pid and arguments directly, replacing the transient `Claude` wrapper. Its pane tests write the same session data to an isolated registry now that the reader owns that read; their assertions, fixtures and test names stay the same. The record-selection test follows one reader and checks that every other identity gets no record.
- A tab running Claude gets a second line, `Opus 5.5 · 23%`: the model and the share of the window used, as Claude's statusline computes it (`round(used / window * 100)`, at most 100). `sessions/<pid>.json` gives `sessionId` (re-read every tick: `/clear` changes it) and `cwd`; the transcript is `projects/<cwd with every non-alphanumeric UTF-16 unit as '-'; past 200 characters cut, plus '-' and a base36 hash>/<sessionId>.jsonl`. Its last `assistant` line (not `isSidechain`, model not `<synthetic>`) gives `message.model` and used = `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`; a later `system`/`compact_boundary` hides the line until the next reply.
- The transcript is read as it grows (the first time, its last MiB), lines scanned backwards to the first reply or boundary, so a quiet tick costs one `stat`. The window is worked out again only when the reply changes.
- No file holds the window, so it mirrors Claude Code 2.1.289's own rule: `DISABLE_COMPACT` with `CLAUDE_CODE_MAX_CONTEXT_TOKENS` gives that; otherwise 1M for models with a native 1M window (Opus 4.7 and later, anything from version 5) or a model setting ending in `[1m]` that names the transcript's model (`--model`, `ANTHROPIC_MODEL`, then `model` in local > project > user settings), unless `CLAUDE_CODE_DISABLE_1M_CONTEXT`; `CLAUDE_CODE_MAX_CONTEXT_TOKENS` for non-Claude models; else 200k, or 1M once past 200k. Variables are the process's (`process::env`) overlaid by each settings file's `env`, as Claude applies them. Not seen: an unsaved `/model` switch, accounts without 1M, the SDK's 1M beta header. Claude's statusline input has the exact numbers but needs a `statusLine` command in the user's settings (rejected like hooks).
- Wide mode gives the tab two rows (`ui::Details::lines`, height `pitch.max(lines)`), with `×` on the first only; compact mode puts the line on the band's third row. The model is cut first and dropped below 4 columns; the percentage turns orange at 75 % and red at 90 % (`agents::usage::Severity::of`).
- The line's fourth part, `N subagents` while an agent's subagents run (#358, see Agent status), has no switch and sits after the percentage, before the memory. What the line shows is three switches in `config.json` (Settings → UI, `settings::Detail`): `model` and `context` (the percentage), on by default, and `memory` (off, see Memory below). `App::tab_details` applies them once into a `ui::Details { model, percent, memory }`, used by the view and by `App::tab_lines`, and `ui::Details::lines` gives the second row when any part is there, so drawing and hit testing agree; with all three off every tab takes one row. 0.6 had one switch, `context_line`, for model and percentage together: `config::load` reads it as `context`, and a file without `model` gets `context`'s value, so a line turned off then stays off. This happens on the JSON before deserializing rather than with a serde `alias`, which would reject a file holding both keys and fall back to all defaults. Plan limits stay in the ` Usage ` modal; showing them under every tab was tried and dropped, since they belong to the account, would repeat the same number in every tab and push out the one thing each tab has of its own.
- Codex context (`agents/codex/rollout.rs`) was verified against CLI 0.160.0; versioned synthetic fixtures and tagged source links are in `tests/fixtures/codex/README.md`. Associate by the JSONL held open under the agent's `CODEX_HOME/sessions` (or its `HOME/.codex/sessions`), never the newest rollout. Follow only Codex descendants of the foreground process, including npm's `node …/codex/bin/codex.js` wrapper; accept CLI/exec/VSCode source labels, reject subagent metadata and ambiguous root rollouts. A child whose environment cannot be read (a `fork` about to `exec`, a process that just exited) is skipped, never a reason to drop the line. Discovery (`agents::codex::rollout::rollout_path`: `lsof` on macOS, every process in daemon mode) runs on a thread per pane, one job in flight, so it never blocks the server loop; the main thread only takes its answer and reads the rollout as it grows. Linux reads `/proc` (children across all threads); macOS uses `proc_listchildpids` / `proc_listallpids` (both return a count of pids, not bytes) and `/usr/sbin/lsof -n -P -a -p <pid> -Fn`. Missing inspection access omits the line.
- **Codex's app-server daemon**: 0.160.0 installs and starts `codex app-server --managed-daemon` (pid in `CODEX_HOME/app-server-daemon/daemon.pid`, parent 1); the TUI talks to it over a socket and the daemon writes every rollout (hence `source: "vscode"`), so no descendant holds one. Nothing links a TUI's pid to its thread (locks, snapshots and the socket carry no pid), so when no descendant holds a rollout the folder decides, only when unambiguous: the daemon's open rollouts whose `session_meta.cwd` is the agent's cwd, written since the pane first saw that pid (the daemon keeps a finished session open ~60 s, so a new Codex in the same folder would otherwise take the old one), exactly one of them, and exactly one native Codex TUI (`argv[0]` named `codex`, no `app-server`) in that folder with that home among all processes (`process::all`). Two Codex in one folder show nothing; after one exits the other comes back once the daemon closes its rollout. `codex -C <dir>` gives a cwd that does not match, so no line. The line appears with the first turn: the rollout is created lazily.
- Codex models come from `turn_context.model` and `thread_settings_applied.thread_settings.model` for the current thread. Usage is `last_token_usage.total_tokens / model_context_window`, rounded and capped at 100%; no lifetime totals, extra cached/reasoning tokens, inferred window or Codex baseline adjustment. `Context.percent` is optional: unavailable/malformed usage shows the model alone. Model switches and compaction clear the old percentage; switching rollouts, replacement, truncation, deletion or process exit resets the reader. Read only complete JSONL lines, starting with a tail of at most one MiB, then bounded incremental batches; validate session metadata at the head. An initial tail without a model omits the line until a model is reported.
- **opencode** (`agents/opencode/database.rs`, checked live on 1.18.35; fixtures in `tests/fixtures/opencode/1.18.35`, rows from a real session with paths replaced): every opencode process shares one SQLite database (WAL), `$XDG_DATA_HOME/opencode/opencode.db`, `opencode-<channel>.db` outside the stable channel, or what `OPENCODE_DB` names. The pane's database is the one its opencode holds open (the foreground process or an `opencode` descendant: `process::open_files`, `lsof` on macOS, like Codex's rollout), read with `rusqlite` (SQLite compiled in, `bundled`, so nothing is needed on the machine) read only, with a 100 ms busy timeout. No row holds a pid, so the folder decides, as for Codex's daemon: the newest session (no `parent_id`, which marks a subagent's; not archived) whose `directory` is the process's cwd and that was updated since the pane first saw that pid, and only while no other opencode holding the same database runs in that folder (an `opencode run` counts too). So the line appears with the first prompt, follows `/new` once it is used, and two opencode in one folder show nothing. The whole job (find, query, parse) runs on a thread per pane, one in flight, started again each refresh, so the server loop only takes answers. The line mirrors opencode's own footer: the newest assistant message with output, `input + output + reasoning + cache.read + cache.write` over the model's `limit.context`, rounded; after `/compact` that is the summary's reply, as opencode shows. The model is the newest message's (a user message names the one picked), so a switch shows the new model without a percentage until it replies. Names and windows come from models.dev's file opencode caches (`$XDG_CACHE_HOME/opencode/models.json`, or `OPENCODE_MODELS_PATH`), 5 MB, so it is parsed only when the model or the file changes; a model it lacks (a custom provider's, whose limits live in opencode's config) shows its id without a percentage. Tests use `agents::opencode::fake::FakeOpencode`: a database built from the fixture schema, with rows written by the test, held by a script named `opencode` that app tests type into a pane, or by `FakeOpencode::start`, a `/bin/sleep` named `opencode` with the database as its stdin, for the tests that call `look` on a process of their own. That one never forks: the script's shell forks for each `sleep` of its loop, and until that child `exec`s it is a copy of the fake (its arguments, its folder, the database on fd 3), which the check for another opencode in the folder rightly counts. macOS' `/bin/sh` is bash, which forks where Linux's dash uses `vfork`, so `two_opencode_in_one_folder_show_nothing` failed there now and then, finding a second opencode after the second fake was gone.
- **Gemini CLI** (`agents/gemini/session.rs`, 0.63.0): discovery and parsing share one job per pane, using `discovery::Job` with Codex and opencode and `jsonl::Tail` with Codex. Read the process's `GEMINI_CLI_HOME/.gemini` or `HOME/.gemini`. `projects.json` maps its canonical cwd to a slug; `.project_root`, when present, checks the owner to avoid symlink and slug collisions. Choose the newest top-level `kind: main` JSONL updated since the pane first saw the pid. Failed discovery, stale files, missing registries and subagents give no conversation data. Follow Gemini children past Node runtime flags: the npm parent may keep its original cwd while the child enters `--worktree`. One CLI family counts as one; an independent Gemini sharing that home and cwd hides conversation data. The process list is read first and the agent's descendants after it, so a child born between the two is in the family: taken the other way round, a child forked at that moment (a copy of its parent until it execs, which bash's `/bin/sh` on macOS makes for every command of the fake) counted as another Gemini and one look hid the line, the record and the last message until the next job (`a_process_the_agent_starts_during_the_scan_is_not_another_gemini`, through `look_among`'s scan seam). A look that finds nothing still clears the record: an ambiguous folder must not keep answering from an old one. opencode's check for another process holding its database takes the same order and leaves the holder's descendants out; Codex's daemon fallback has no family to leave out (it counts native TUIs only). Different homes are independent. In 0.63.0's source, `--worktree` changes the child's cwd and slug; `--include-directories` adds folders without changing the storage root. Those flags were not checked live.
- Do not inject `--session-id` into issue launches, `start` or resumes. `/clear` and `/resume` change sessions in the same pid, so an exact initial match would still need folder discovery and another lifecycle to abandon that id. The folder rule is smaller and also works for agents started by hand. Two Gemini hide context, resume and last-message data, while their titles still provide status.
- Read complete Gemini lines from an initial tail of at most one MiB, then bounded batches. Replacement, truncation and deletion reset the reader. Keep the newest value of each reply id in conversation order, at most 512 replies, and of each only its model, input tokens and time: tool results and long answers are not held in the server; `$set.messages` replaces the whole array. Follow Gemini's ignored-user-content rule: empty text and trimmed text starting with `/`, `?`, `<session_context>` or `<hook_context>` cannot confirm a prompt or make a session resumable. Also exclude function responses, `<state_snapshot>` and `<scratchpad>`. A Gemini response makes a session resumable, including compression's synthetic acknowledgement, because compaction removed its real prompts. That acknowledgement confirms no send and is not a last message. `Pane` keeps prompt times across message replacement and conversation switches; a new process starts fresh. A live resume restored `$set.messages` with the original times. Use those times, so new metadata cannot confirm a send. Model, usage and last message were checked in an isolated cornercase server.
- Show Gemini's recorded model ID, as for Codex, because there is no stable display-name source. Context use is the newest real reply's `tokens.input / tokenLimit(model)`, rounded and capped: 1,048,576 tokens, or 256,000 for Gemma 4. Do not add output, thoughts, cached or lifetime totals. An `info` record `Model set to <id>` changes the model and clears old usage; `/model set auto` wrote one live. The unsaved picker only changes the footer. Read its `/model` column in the last six screen lines, splitting header and values on two or more spaces and requiring equal cell counts. This handles hidden cwd and trailing context/quota columns without mistaking a branch for a model. Accept only complete Gemini/Gemma IDs or `Auto`; hidden, missing or truncated values fall back to the file. A changed selection clears old usage until a fresh reply. Show `Auto` as `auto` only after an explicit change, then use the reply's routed ID. This footer read only supplies context; it cannot refuse input or invent status. `/clear` follows the new file and clears old usage. Live `/compress` replaced history with synthetic context and a summary without fresh `tokens.input`. Its reported reduction from 10,570 to 505 tokens was not saved, so keep the model and hide the percentage until a real reply rather than estimate it.
- **Grok Build** (`agents/grok/session.rs`, 1.0.52; fixtures in `tests/fixtures/grok/1.0.52`): one discovery job per pane. The job takes the previous session so the tails and the fold survive, and a snapshot keeps the status on screen until the job returns. Home is `GROK_HOME` when set and non-empty, else `HOME/.grok`. The row's cwd is percent-encoded (uppercase hex, RFC 3986 unreserved bytes kept) to find `sessions/<name>/<id>/`. A short directory is accepted when its sibling `.cwd`, or `summary.json` `info.cwd`, is that folder; the hash in the short name is not rebuilt. A live subagent directory was not captured. What was checked is a `session_relationship` other than `primary` in the same events file: a prompt belongs to the turn whose start and end cover its time, so a worker prompt is not a confirmation. A `turn_completed` belongs to the newest turn that started at or before it, including one written a few milliseconds after `turn_ended`, so a worker completion keeps that turn's model and adds tokens only, never the parent's percentage. An immediate child directory that has `updates.jsonl` still adds that file's tokens only; that separate layout was not seen live. The model is `summary.json` `current_model_id`, else the latest `turn_started` `model_id`. The window is `signals.json` `contextWindowTokens`, else `summary.json` `context_window`. The percentage is the newest primary `turn_completed` when `modelCalls` is at most 1, `inputTokens` is within the window, the model matches (a usage record with no model is allowed) and the reply is newer than `auto_compact_completed` or `compaction_checkpoint` and newer than the recorded model or window change (a new `turn_started` of the new model; a reply read in the same poll as that change still counts). A model change that is only in `summary.json`, with no new `turn_started` for it, drops the retained reply and the current `signals.json` reading until a newer reply or a newer signals file, so switching back does not restore the old percentage. An older one-call reply is never used. A normal multi-call turn instead uses `signals.json` `contextTokensUsed` over `contextWindowTokens` when that file's mtime is at or after the reply, `primaryModelId` is the current model, and no compaction or model boundary is newer than the file. It stays hidden when the file is older than the reply or after a boundary. The window is taken from `signals.json` (a live session used 500000, not 256000). `contextWindowUsage`, `compactionCount` (it stayed 0 across a real compact) and `_meta.totalTokens` are not used. Stats split that usage into input minus `cachedReadTokens`, output (not plus `reasoningTokens`), cache read and cache write, once per prompt id. A prompt is a `user_message_chunk` with `promptIndex`, timed from `agentTimestampMs` (else the update's `timestamp`). `_meta.syntheticPrompt` decides when it is present: true is never a prompt and false always is, including when the text begins with `<system-reminder>` or `<user_info>`. That tag check applies only when the field is absent. One submission is `promptIndex` plus that millisecond, so a repeated index still counts again and chunks from the same instant count once. `chat_history.jsonl` is not paired for prompts. It still decides `resumable`, with the last message. On a first read or a reset, the newest human chunk behind the tail is recovered. Only a bounded set of recent prompt ids is kept; counting once is the ledger's job. `?` is a prompt. `/` and `!` are local. There is no survey and no input-box marker. The last message is the newest assistant string, and its time is the `agent_message_chunk` whose text is that string, not a later `turn_ended`. A session is resumable once it has a prompt, an assistant message or `compaction_meta`. Resume is `grok <normalized args> --resume <id>`. `grok --resume` is the flag; `--session-id` starts a new session. `--yolo`, `--always-approve` and `--permission-mode bypassPermissions` normalize to `--always-approve`. There is no built-in plan mode. `Known::usage` is `None`: `grok usage` is per session, not an account plan. Inherited `GROK_SESSION_ID` and `GROK_AGENT` did not join the parent session, so they are not stripped, and neither is `GROK_HOME`. `grok worktree create` did not lock the git worktree. OSC 7501 is not read. Old sessions are not imported into stats.
- **Cursor CLI** (`agents/cursor/store.rs`, `proto.rs`, bundle 2026.10.14-941492e, **from the code, no live store was read**; synthetic fixtures are built by `agents::cursor::fake::FakeCursor`, whose encoder is test-only): the chat store is `<CURSOR_CONFIG_DIR, else $XDG_CONFIG_HOME/cursor, else ~/.cursor>/chats/<md5 of the folder>/<chat id>/store.db`, SQLite in WAL mode with `blobs(id, data)` (content addressed: the id is the lowercase hex SHA-256) and `meta(key, value)`, whose one row `0` is the hex of a JSON with `latestRootBlobId`, `lastUsedModel` and `createdAt`. The TUI is the only writer and is expected to keep the file open, so the pane's chat is the one `store.db` under `chats/<32 hex>/<id>/` that `process::open_files` shows for the foreground pid, and only when there is exactly one; no folder rule is needed, so two Cursor in one folder each follow their own chat (`RECORD_BY_FOLDER` is false). If a live check shows the TUI does not hold the file, the fallback is the folder rule Codex's daemon uses (newest chat of the folder updated since the pid started, exactly one Cursor there), and `RECORD_BY_FOLDER` becomes true. The root blob is protobuf `agent.v1.ConversationStateStructure`: field 5 `token_details` (`1 used_tokens`, `2 max_tokens`, exactly what the TUI shows as context use) and field 8, the turns as blob ids (raw 32 bytes, or 64 hex characters, both taken). A turn blob is `1` an agent turn or `2` a shell (`!`) turn; an agent turn has `1` the user message blob, `2` the step blobs, `7 routed_model_display_name` and `10 user_message_id`; a step is `1` an assistant message (`1 text`, `2 started_at_ms`, `3 completed_at_ms`), `2` a tool call or `3` a thinking message. `proto.rs` is a wire reader of about 80 lines (varints, length-delimited fields, fixed widths skipped, groups and truncation refused) rather than prost and a build step; every malformed, truncated or missing blob gives nothing, never a wrong value, and the fields are named by number only where this document says so. The meta row is read on every poll and the root decoded only when `latestRootBlobId` changes; turn blobs are cached by id and dropped when they leave the list (the newest turn's blob changes id with each step, its message id does not). The model is the newest turn's routed name, else `lastUsedModel` (`default` shows as `Auto`); the percentage is `used_tokens / max_tokens` when the window is positive, and when `lastUsedModel` changes while the root stays the same the percentage is hidden until the next checkpoint, as for Codex. A prompt is a turn whose `user_message_id` (else the user message's own id) was not known: the turns found on a first read are the history and never count, unless the chat was created after the pane first saw the process (`createdAt`, so a `/clear` chat or a new one counts its first turn); the first read is the first one that opens the store, even before it has a root. Its time is the user message's `started_at_ms` when the server filled it, else the moment it was read, which DESIGN allows for prompts ("counts from when it was read"), so a first checkpoint that comes late shows working late and the 10 s confirmation of `send --enter` can fail before Cursor records the prompt. **Token usage per turn is never written to disk** (`TurnEndedUpdate` stays in memory), so Stats counts agents, prompts, turns and time for Cursor and no tokens. The last message is the newest non-empty assistant text of the newest turn that has one (thinking, tool and shell steps skipped), with its completion or start time; the record is the store's path. The transcript is found from `meta.json`'s `cwd`: `<CURSOR_DATA_DIR, else ~/.cursor>/projects/<cwd with every non-alphanumeric run as -, trimmed>/agent-transcripts/<chat id>/…`. The same chat open in two panes shares one store and is a known limitation.
- **GitHub Copilot CLI** (`agents/copilot/session.rs`, `events.rs`, `message.rs`, 1.0.98; fixtures in `tests/fixtures/copilot/1.0.98`, reduced from a real run against a fake provider): the record is the session folder; `events.jsonl` is created lazily with the first prompt (a session that never got one has a folder and lock but no file), is read as it grows with the shared `Tail` (the first time its last MiB) and one fold (`events::Fold`). The first read, and a replaced file, also seed the fold from a backwards scan bounded at 64 MiB (`BACK_DEFAULT`, `set_back_limit` in tests) for the newest model selection, the boundaries after it, the newest main usage record and whether a prompt or reply exists, since a long session's `session.start` is far behind the 1 MiB tail. **Model**: `selectedModel` of `session.start`/`session.resume`, `newModel` of `session.model_change`, `chosenModel` of `session.auto_mode_resolved` and the model of the newest main reply or usage record; with `auto` selected it shows `auto` until a concrete one is known, and the id is shown as Codex and Gemini show theirs (no display name). **Percentage**: the newest **main** `session.usage_record` as `inputTokens / maxPromptTokens`, rounded and capped (the shared `context::percent`); main means no `parentToolCallId`, no `initiator` of `sub-agent` or `mcp-sampling` and an `interactionType` of `conversation-agent` or none. It is hidden after a successful `session.compaction_complete`, `session.truncation`, `session.context_cleared` and a `session.model_change` that is not the startup one, until the next main record; a `session.resume` with the same model hides nothing. Sub-agent records add tokens to Stats and never move the percentage. **Prompts** (`events::is_prompt`): a `user.message` with no `source` (skills and other agents set one), no `isAutopilotContinuation: true` and an `agentMode` other than `shell`, whatever its `delivery`; its time is the event's, which for a queued prompt is when Copilot took it, and that is what `send --enter` needs. It also makes the session resumable (`resumable`: a prompt or a main reply). **Last message** and search: the newest `assistant.message` with non-empty `content` and no `parentToolCallId`, chunks of one `apiCallId` joined in `chunkIndex` order, read backwards (`context::message`); `reasoningText` and `encryptedContent` are never read; `written` is the newest chunk's `timestamp`. **Several in one folder**: nothing is found by folder, so two Copilot in one worktree each follow their own session (`STATUS_BY_FOLDER` and `RECORD_BY_FOLDER` are false), which is why flows can give it several roles. The tab shows the model and percentage like Codex's. Not checked: `/context`'s own figure against the usage record (the fake provider's `prompt_tokens` is not Copilot's count, so only that its limit equals `maxPromptTokens` could be compared) — the percentage is the provider's input over the model's prompt limit, as the issue asked.
- Codex fake-agent tests use `agents::codex::fake::FakeCodex`, with a shell imitating the npm wrapper's parent/child topology, and no real model calls. `FakeCodex::serve` starts a fake daemon (a `codex app-server` script holding the rollout, not a descendant of the agent, pid in `daemon.pid`) and `FakeCodex::agent` a TUI that is `/bin/sleep` with `argv[0]` `…/codex` (`Sleeper::named`; a symlink would break multi-call coreutils). App tests cover two sessions sharing cwd and Codex home, session/model changes, compaction and cleanup; UI snapshots cover wide and compact lines, including model-only text.
