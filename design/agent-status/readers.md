# Agent status › Each agent's reader

Part of [Agent status](../agent-status.md).

- **Codex** (`agents::codex::Reader::activity`, checked live on 0.160.0): waiting while the title starts with `[ ! ] Action Required` or `[ . ] Action Required` (it blinks between the two during an approval); working while it starts with a braille spinner and a space (`⠴ <thread> | <project>`) or while the rollout the context line follows (`agents/codex/rollout.rs`) is inside a turn (`task_started`, until `task_complete` or `turn_aborted`); otherwise idle (the title is then `<thread> | <project>`, or just the project). Approvals are never written to the rollout, so `!` needs the title; the title's items are configurable (`/title`, `tui.terminal_title`), and without its activity item the rollout still gives working and done. Both rather than one: the rollout alone has no waiting, the title alone breaks when its activity item is removed. Hooks were rejected as for Claude (they mean writing to `~/.codex`).
- **opencode** (`agents::opencode::Reader::activity`, checked live on 1.18.35): no status until the job has found its database, read it and told its session apart (a query that fails, or two opencode in one folder, give none, rather than an idle that would turn a working pane into a false done); idle while it has no session yet; working while the newest message of its session is the user's (sent, its reply not written yet) or an assistant message without `time.completed` (an Esc interrupt completes it, with a `MessageAbortedError`; `/compact` is a reply like any other, with `summary: true`), else idle. The session comes from the database the context line reads (`agents/opencode/database.rs`, see Context use), on the same thread. opencode never says it waits for you: a permission or a question lives only in its memory (the tool part already reads `running`), its title stays `OpenCode` or `OC | <session title>` whatever it does, and its log (`log/opencode.log`, shared by every process, no pid) writes `asking` but never the answer, so a pane waiting for you shows `◐`. Rejected: reading that log (a format of its own, cut by `--log-level`, and the reply would have to be guessed from the database), its HTTP API (`/session/status`, `/permission`, which only exists with `--port` and then listens on localhost without a password), and its own notifications (`attention` in its TUI config, off by default and only while its window is unfocused, so cornercase would have to inject a config and report focus). It asks no trust question, so a launch goes straight to the prompt once its screen is quiet.
- **Gemini CLI** (`agents::gemini::Reader::activity`, 0.63.0): trim the padded OSC 0 title; `✋` means waiting, `✦` and `⏲` working, `◇` idle. Fixed (`ui.dynamicWindowTitle` off), hidden (`ui.hideWindowTitle` on) and unknown titles give no status, because losing a signal does not mean the turn ended. There is no session fallback: the file has no turn markers, text can precede a pending tool, and tool results and message updates arrive separately. Hooks would require writing the user's settings, so they are rejected. Follow Gemini's quiet-shell `✋` heuristic even when it mistakes a slow command for input; guessing from descendants would be less reliable. Fixtures pin working, ready, thought, fixed, confirmation and silent-shell titles observed inside tmux. Hidden titles were checked against the source. The source has no tmux, screen or Zellij exception; screen and Zellij were not checked live.
- **Grok Build** (`agents::grok::Reader::activity`, checked live on 1.0.52): no status until `active_sessions.json` has a row for the foreground pid. On Linux that row's `pid_start` must equal field 22 of `/proc/<pid>/stat`; macOS has no start time, so a missing one does not reject the row. The previous status stays on screen while the next read runs, including while that read holds the session tails. A turn is open from `events.jsonl` `turn_started` until `turn_ended` (`completed` or `cancelled`). The reader keeps one tail per file and the fold, and applies only new lines; a replaced or truncated file clears the fold. The first read, and a reset, seeds the open turn from the newest `turn_started` or `turn_ended` behind the tail, so a turn whose start is more than a megabyte earlier still reads as working. If that backwards scan reaches its bound without either marker, the turn is unknown, not closed: newer phase or tool events keep it working until a `turn_ended` arrives, so a wait or an idle restart does not treat it as finished. Waiting is a `permission_prompt` phase, a `permission_requested` with no later `permission_resolved` for that same tool, or an open `ask_user_question` or `exit_plan_mode` until its `tool_completed`. Resolving one permission does not clear another tool's request. A question's permission returns `allow` with `wait_ms` 0 and the phase goes back to `tool_execution` while the question is still unanswered, so that phase does not close the ask; `tool_completed` does, and the same turn then continues (`loop_started`) as working. `enter_plan_mode` is how a turn enters plan mode and is not itself the approval. A live `/plan` called `exit_plan_mode`; its permission returned `allow` with `wait_ms` 0 while the approval was still open, and `tool_completed` arrived when it was approved, after which the same turn continued (`loop_started`, then another tool). The ask stays open until that `tool_completed`. Any other tool, including `run_terminal_command`, is working. `waiting_for_model` is how a healthy turn starts. An unknown model is rejected before any turn. Starts that have `turn_started` and no `turn_ended` in real logs are not explained yet, and there is no timeout. A background command with `block_until_ms: 0` ended the turn while the process kept running, so there is no `Activity::Shell`. Esc did not end a turn. Ctrl+C did (`cancelled`, `mid_turn_abort`, `cancellation_context.trigger` `ctrl_c`). One Enter while a turn is open queues the text and leaves the turn running. A second Enter is Grok's send now: the open turn ends `cancelled` with trigger `send_now`, and the next `turn_started` has `redirect_kind` `queued_after_cancel`. `send` presses Enter once, so it queues and is not refused. A title containing `Action Required` forces waiting only while the turn is open. A braille spinner, and the word Waiting in a compact title, do not, and neither overrides `turn_ended`. The trust screen says "Do you trust the contents of this directory?" and "Yes, proceed", which the default trust pattern already matches; cornercase does not write `trusted_folders.toml`.
- **Cursor CLI** (`agents::cursor::Reader::activity`): the title is OSC 0 and carries no state by default (the chat's name or `Cursor Agent`); with `display.showStatusIndicators` (`/status-indicators` in Cursor, off by default) it reads `<name> - <emoji> <text>`. The last ` - ` is taken, so a chat name holding one is no problem: `❓` and `🔐` mean waiting, `⏳` `🧭` `⌨️` `📋` `📝` working and `✅` idle; any other (`🔄` reconnecting, `📂` loading, `📤` moving to the cloud) says nothing and falls through, as does a title without one. Without a title signal the status comes from the transcript (`agent-transcripts/<chat id>/<chat id>.jsonl`, read with the shared incremental tail): a `user` line opens a turn, `{"type":"turn_ended"}` (`success`, `aborted` or `error`) closes it, and a rewrite (compaction) is read again from the start of its tail; the file has no timestamps. "Send now" writes no `turn_ended`, so the next user line keeps the turn open. Nothing on disk says waiting, so without `/status-indicators` a permission prompt shows as working, like opencode, and `!` never appears; the optional fallback of reading the screen's `Waiting for decision (y/n/p)...` placeholder was left out, since this design avoids reading the screen for status. A fresh Cursor before its first turn has no store and shows idle, so a first turn without indicators shows working a moment late. Cursor writes no OSC 7501.
- **Vibe CLI** (3.0.3, live-checked; `agents::vibe::Reader::activity` returns `None`): Vibe reports its own status with OSC 7501, so no reader is involved and its title (`Vibe`) carries no state. Observed live: a support query `ESC ] 7501 ; ?` at startup, then `state=idle:app=vibe`, `state=working:app=vibe`, **`state=done:app=vibe:msg=VmliZQ==` at the end of a successful turn**, and `state=error:app=vibe:msg=<base64>` for a failure; the binary also carries `blocked:kind=permission` and `blocked:kind=question`. `done` is real, so the unseen-finish mark and its notice do not need inferring from idle. A failed turn reports `error` and then `idle` at once (observed), so the red `!` can pass without holding the second the failure notice needs; the store's `latestTurn.status` still records `failed`. `/compact` emits no OSC report: the TUI prints `✓ Compaction completed.` and the store's `compaction_count` grows, which confirms the compact. The reader counts running subagents (`runtime-state.json` `subagents.children` with `reserved` or `running`), so the second line and `status --json` show the count, but `Pane::activity` cannot promote `None` to `Activity::Subagents`: Vibe's own reports decide the icon. `agents/vibe/session.rs` names the session by the pid lease, not by the folder, so two Vibe in one folder each follow their own conversation and their own OSC reports (`STATUS_BY_FOLDER` and `RECORD_BY_FOLDER` are false). `send --enter` after a prompt queued behind a running turn is confirmed only when its turn starts (`latestTurn.startedAt`), which can lag.
- **GitHub Copilot CLI** (`agents::copilot::Reader::activity`, `agents/copilot/session.rs`, `events.rs`, live-checked): the pane's session is the folder `<home>/session-state/<id>/` whose `inuse.<pid>.hold` the pane's process (or a Copilot process under it: the npm loader's child, `gh copilot`'s) holds **open** (`process::open_files`; `<home>` is `$COPILOT_HOME` or `~/.copilot`, read from the process's own environment). Holding the file proves the pid is alive and is not a reused pid, so a lock left by a `kill -9` is ignored without reading its `.lock`; the package folder under `~/.cache/copilot/pkg/` has an `inuse.<pid>.hold` of its own, which does not count, since only one directly under `session-state/<id>/` does. A process holding two sessions (an overlap during `/clear`) has none until the next poll. Before it holds one (a resumed pane, whose session takes its lock with the first prompt, live), the session is named by `--resume=<id>`, `-r`, or `--session-id` in the process's arguments, only when that folder exists and no live process outside the family has a lock in it, and shows idle. **Working** is `working` for that id in `<home>/open-sessions-state.json` (`{id: {schemaVersion, openedAt, refreshedAt, working}}`, which Copilot rewrites, so a read that does not parse keeps the last value, and a missing file or entry is unknown, never a guessed idle that would end a wait). `true` is waiting when `events.jsonl` has an open `permission.requested`, or an open `tool.execution_start` of `ask_user` or `exit_plan_mode` (the plan review: live, it stays open until the plan is accepted or cancelled), else a background shell when the turn is over and an `async` bash is still running, else working. `false` is idle. **A background shell** keeps `working` true after the last `assistant.turn_end` until the shell ends (live: 25 s, then a `system.notification` of kind `shell_completed` wakes the agent), so it is `Activity::Shell`, like Claude Code's `run_in_background`: the shell is started by a `tool.execution_complete` whose `toolTelemetry.properties.executionMode` is `async` and whose result says `started in background with shellId: N`, and ends by the notification; the wake-up message is a `system.notification`, never a `user.message`, so it is not a prompt. `abort` (`user_initiated` for Ctrl+C, `user_abort` for Esc, live) and `session.shutdown` clear what was pending. One prompt gives several `assistant.turn_start`/`turn_end` pairs, so they are not the end of the work, and the presence file, not the events, says it. **Not detected**: the title carries no state (and can be turned off), so it is not used; the rate-limit, session-limit and auto-mode-switch questions are ephemeral events that are never written and show as working; `session.error` is not mapped to `Failed` (model errors are retried and no reader reports a heuristic `Failed`, which would stick until replaced). Copilot writes no OSC 7501, so the program-status protocol takes over only for what reports it.
