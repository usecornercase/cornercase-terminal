# Agent status › Notifications

Part of [Agent status](../agent-status.md).

- **Notifications**: `Pane::update` returns `Waiting`, `Failed` or `Done` once that status has held for `NOTIFY_AFTER` (1 s) and its tab was not seen, in the window or a view, meanwhile, once per change, so a prompt answered at once stays quiet. `App::notify` sets a toast with the status icon (`<agent> needs you in <project> › <workspace>`, the agent's kind such as `claude` or `codex`, control characters stripped) and queues a `host::notify::Notification`, which the server encodes per client. Panes of the same agent that settle on the same status in the same workspace on one tick give one notice: the text would be the same, and Ghostty drops a repeat within 5 s anyway. The agent is part of that key, so Claude and Codex in one workspace each get theirs. A pane's state remembers its agent (`agents::activity::Pane::follow`) and starts over when another one takes the pane, so a Codex replacing a waiting Claude without a tick in between still notifies. They go through the outer terminal like OSC 52, so they work over SSH (no `notify-send`/`osascript` on the server's machine).
- The channel is the client's: inside tmux, screen or Zellij it is BEL (tmux drops notification OSCs, passthrough is off by default, BEL goes through); otherwise `host::notify::detect` trusts the XTVERSION reply when there is one (asked with the colours, so it survives SSH, where only `TERM` arrives; env vars may also be inherited from another terminal), else `TERM_PROGRAM`, `LC_TERMINAL` (iTerm2 sets it for SSH), `TERM`, `KITTY_WINDOW_ID`, `KONSOLE_VERSION`. OSC 777 for Ghostty, WezTerm, Warp, Rio, foot before 1.18 and Konsole before 24.12 (or with no version); OSC 9 for iTerm2 (its only one); OSC 99 with `o=unfocused` for kitty, Contour, VS Code (VS Code knows only 99), foot 1.18+ and Konsole 24.12+ (from the XTVERSION version, or `KONSOLE_VERSION` 241200, since those two report a click); BEL otherwise. Never several, since terminals that know several would show each.
- OSC 9 and 777 end with BEL, which every parser accepts; OSC 99 with ST, as kitty's spec says. `;` in the text becomes `,`: WezTerm, Rio and Konsole cut the body at it, WezTerm drops an OSC 9 holding one. Ghostty on macOS, foot, Konsole and Warp hide notifications while their window is focused; the others show them. `desktop_notifications` (`auto`, a channel, `off`) overrides the channel; the toast always shows. The visible tab never notifies, even while the outer window is unfocused: focus reporting (`CSI ? 1004 h`) is now on, but it is per window while what is visible is shared, so it only brings a toast back (below).
- **Clicking a notification (#316)**: a desktop notification carried only its text, so a click could not say which agent it was for.
  - **Tokens**: each agent notice (`App::notify`, through `App::tell` in `app/notifications.rs`) gets `cc-<nonce>-<n>` (`[a-zA-Z0-9_+.-]`, the nonce per server run like the chat buttons', so a notification left in the notification centre across a restart is ignored rather than taken for a pane that now has its id). `Notices` keeps 64 (`notify::KEPT`, oldest out) with the agent, place, status, project, workspace and the panes behind it: the dedup key of `notify` (agent, status, workspace) covers several panes, so `watch_agents` collects them. `cornercase notify`, queue, setup-failure and flow bypass-consent notices keep no token and the old sequence; programs hear them, and a merged run's close, as `message` events (see Commands for scripts and agents › Views of your own).
  - **Asking for the report**: `Channel::Osc99` with a token encodes `ESC ] 99 ; i=<token> : a=focus,report : o=unfocused ; text ESC \`. `a=focus` keeps what the terminal did; terminals that know neither key ignore them, as kitty's spec requires. kitty (checked live on 0.45), VS Code, Contour (`i=x:p=activated;`), foot 1.18 and Konsole 24.12 write back `ESC ] 99 ; i=<token> ; [button] ESC \`. Ghostty parses OSC 99 but does not act on it (ghostty-org/ghostty#5634), so it stays on OSC 777 and its click only focuses the window; the same goes for iTerm2, WezTerm, Warp and Rio. A `p=?` query in the startup probe was left out: kitty's answer alone is about 230 bytes and the probe's largest reply is kept under macOS' 1024-byte tty input queue.
  - **The client reads the answer**: `ESC ] 99 ;` joins `REPLY_PREFIXES`, so it is never decoded as `Alt+]` and typed text. `host::notify::activation` parses leniently (the metadata before the first `;`, `i` of 1 to 64 allowed characters, `p` absent, empty or `activated`, so `close`, `alive` and `?` answers give nothing) and the decoder emits `client::input::Input::Activated`, which the window sends as `ClientMessage::Activated` (last client variant, `protocol::VERSION` 5, 6 since the sound below; the browser bridge sends it too). A split inside the 5-byte prefix is held only while replies are expected or more bytes wait, like every reply, since Alt+`]` must not be delayed; a terminal writes its answer in one write. Bracketed paste stays text.
  - **The app jumps**: `App::notification_clicked` ignores an unknown token (not logged), drops the notice's own toast and missed mark, goes (through `App::act_on_notice`, shared with `go`, #337) to the first of its panes in sidebar order whose agent still needs you, else the first that exists, through `jump_to_pane`; with all its panes gone, to the workspace if it is open, else a toast `<agent> in <place> is gone`. A project closing or a workspace being removed counts as gone. An open overlay stays, and focus is shared, so every window shows the jump as after any click. The log says the pane or `workspace` or `gone`, never the text.
  - **The toast's ` go `** (`Toast::go`, `ui::ToastButton::Go`) does the same for the same token in any terminal, also inside tmux, and lasts 6 s like an ` undo `. It is the way to the agent where a click reports nothing.
  - **The toast again on focus**: the client enables `?1004` and disables it on every way out (`restore_input_modes`, `release_screen`); the server passes `FocusGained` and `FocusLost` to `App::window_focus` and they are not a use. State is per window (`Notices::windows`, dropped in `forget`): a notification sent while a window is unfocused marks it missed, and on gaining focus its toast shows again with ` go ` if the agent still needs you and none of its panes is in the tab on screen. Ghostty, iTerm2 and WezTerm bring the window forward on a click, usually after the 6 s. Jumping straight to the agent on focus was left out: alt-tabbing back looks the same. In kitty the click's answer and the focus arrive in either order; the click drops the missed mark and a notice whose tab is on screen is skipped, so there is no duplicate. Gaining focus after losing it also asks the open pull requests again (see Pull requests, A merge shows sooner).
  - **Leaving**: the server keeps what it sent each window (`notify::Sent`, the tokens of notices sent as OSC 99, 64 at most) and sends their closes (`p=close`) before `Detached`, `Shutdown` or `Restart`, so a click later writes no answer into the shell that outlives cornercase. A killed or lost window can still leave one; its answer then shows as typed text in the shell.
- **A machine's agents** (#542, `app/machine_links/notices.rs`, `app/notifications.rs`; see Remote windows › What a machine has): an agent on a linked machine tells this window as one here does, with `<agent> on <machine> needs you in <project> › <workspace>` (`failed`, `finished`), the toast's ` go `, the desktop notification, the sound and the `notice` event.
  - **From two snapshots, not the machine's own notices**: the link reads only `watch`, so each snapshot is compared with the one before it, pane by pane, and a pane whose agent was `working` and is now `waiting` or `failed` needs you, `done` has finished; the pane must still run the same agent (by its name), since a pane id that now runs another one is not the turn that ended. Comparing what the machine's server already decided (its `notice` events) was rejected: a second ssh connection per machine for `events`, and the machine's rule of a tab seen is about its own windows, not this one. Grouped by agent, status and workspace like `notify`, with the wording and sound rule (`sound`, and `sound_subagents` for a subagent, by the rule of Subagents' notices below) shared through `notifications::wording` and `App::sound_for`.
  - **Quiet when nothing was there before**: the first snapshot after the link comes up or comes back, and one from a new `boot` (its ids start again), are compared with nothing (`Held.watching`, and the two snapshots must share a `boot`), so a reconnect never tells what changed while the link was down. A shell in the background (`background_shell`) and the machine's workspace shown here never tell, the second as the visible tab never does.
  - **No settling second**: the notice goes with the snapshot that shows the change, without `NOTIFY_AFTER`, since the snapshots already come apart in time; a status that changes and comes back between two snapshots is never seen.
  - **The notice holds the machine and its `boot`** (`Notice.machine`) and the machine's ids. The machine is its link's id (`There.link`), which lasts while its destination does, plus the name for the text and the event: the name can be edited in Settings, and ` go ` found nothing after a rename. ` go `, a click on the notification and `go` select that workspace as a click on its row does, only while the machine is on the same `boot`, else `<agent> in <place> is gone`; it is the workspace, not the tab, since a snapshot's tab ids may already have moved on. Over the socket, `go` answers `{}` for it: the machine's ids are not ids here, and `status`'s `shown_remote` says what was picked. `go --view` with its token is `malformed` before anything moves, since the machine's workspace shows only in the window, shared by every client (as `focus-machine` takes no `--view`).
  - **Known limit**: a remote notice missed while the window was unfocused does not show again on focus (`window_focus` skips it), since knowing whether the agent still needs you would mean looking it up in the latest snapshot.
- **Subagents' notices** (#715, `notify_subagents`, on by default; `App::tells` in `app/notifications.rs`): with it off, only the agents you started tell you. A subagent is the same pane as for `sound_subagents` (`App::subagent_panes`, see Sound): a child of a live agent in the agents section's tree, so a flow's members and agents an agent started with `start`, `new-tab` or `split` go quiet, while one started from a shell, one whose parent has closed or whose parent's agent is gone (#717) and an orchestrator started from the window still tell. A notice that groups several panes is a subagent's only when none of them is a main agent, the rule the sound already had.
  - **Every channel, at one place each**: `App::notify` stops before `App::tell`, so there is no token, toast, ` go `, desktop notification, cue, missed mark or `notice` event; the log keeps its `notify` line with `subagent`, `sent = false` and `sound = none`, so `server.log` explains the silence without naming a sound that never played. A machine's agents (`tell_turn`) follow the same rule: a pane there is a subagent only when its `parent` is an agent of the same snapshot (`subagents` in `app/machine_links/notices.rs` runs `agents::tree::order` on the snapshot's agents, as the agents section does for the machine's rows), so one started from a shell there, one whose parent has closed or whose parent's agent is gone and the first agent of a cycle tell, as here. Before, any pane with a `parent` there counted as a subagent, a shell's child included. The chat apps keep their own watch (see Telegram), so `watch_messenger` drops a subagent's notices there too.
  - **What it does not hide**: the marks stay. A subagent that finishes in a hidden tab keeps its `✓` in its tab, the tree and the workspace and project rows until its tab is seen, and one that waits keeps its `!`, also on a folded parent: the user asked to stop being interrupted, not to lose what to review, and `✓` is the only trace of it (marking it seen at once, as a flow's members are, was rejected, since the setting would then change the sidebar too). The cost is that a subagent waiting on a permission tells nobody; the `!` stays, and the setting is on by default. A notice silenced while it was off is never sent once it is turned on.
  - **Scripts**: with the setting on, a subagent's `notice` event carries `subagent: true` (see Commands for scripts and agents › Views of your own), so a client can make the choice by itself.
