# Opening in other apps

Code: `host/open.rs`, `app/opening.rs`, `client/window.rs`, `server.rs`, `protocol.rs`, #388

- **Why**: the worktrees cornercase makes live under `~/.cornercase/worktrees/<repo>/<branch>`, a path nobody types, and most tools that run lines of work have an **Open in…**. Getting a project, a workspace or the folder of a pane into Finder, the file manager or an editor meant copying a path out of a shell.
- **Where**: **open in…** ends the project and workspace row menus (` ⋯ ` or right-click, in the lists, the tree and the compact layout, which share the menu builders), sits before **close pane** in the pane menu (the folder of the pane's foreground program, `Term::cwd()`, so it follows `cd`, else the workspace's folder), is a button ` open in… ` in the files viewer's header (text, images and binary files alike; a workspace opens its own folder, so a worktree opens the worktree) and the menu of a right-click on a file or folder row in the tree. Tabs and groups get nothing. The submenu replaces the menu at the same spot, like **move to group**. The header drops the button first when the buttons would leave fewer than 11 cells for the line info (`MIN_INFO`), as the issues browser drops ` schedule `: at the panel's default width it fits, at 45 columns (the docs captures) it would squeeze `lines 11–12` to 4 cells, and at the minimum width four buttons overflow. The tree's right-click still offers it.
- **What it lists**, in a fixed order (`Opener`'s declaration order, so the menu never reshuffles): Finder (macOS) or the file manager (Linux), VS Code, Cursor, Zed, Sublime Text and **default app**, each only when the computer has it. Detection (`Openers::find`, pure over the environment, the `PATH` and the Applications folders so tests fake all three): macOS needs `open`, which gives Finder and the default app, and an editor is its command on the `PATH` (`code`, `cursor`, `zed`, `subl`) or else its bundle in `/Applications` or `~/Applications`, run through `open -a <the .app found>`; `-a` with the path found rather than `open -b` with a bundle id, since it opens exactly the bundle detected and needs no table of ids (Cursor's is `com.todesktop.230313mzl4w4u92`). Linux needs `xdg-open` (file manager and default app) and `code`, `cursor`, `zeditor`, `subl` and `zed`, and a graphical session (`WAYLAND_DISPLAY` or `DISPLAY`), else every entry would fail on a console. `zed` counts only when its canonical path has a `zed.app` component: on Ubuntu with ZFS `/usr/sbin/zed` is ZFS's event daemon and the default `PATH` has `/usr/sbin`, while Zed's own installer (`~/.local/zed.app/bin/zed`) and the macOS CLI sit inside a `Zed.app`; distribution packages call the CLI `zeditor`.
- **How each runs** (`Openers::steps`, fixed argv, never a shell, the path always absolute so it cannot start with `-`): a folder is `open DIR` / `xdg-open DIR` / `code DIR`; a file in an editor is `code -g FILE:LINE` (Cursor likewise), `zed FILE:LINE`, `subl FILE:LINE`, with the line the first selected one (none for images and folders), and a bundle without its command takes no line. Finder reveals a file (`open -R`) and also a bundle-like folder (`.app`, `.xcodeproj`, `.framework`… `BUNDLES`), since `open Tool.app` launches the app and `open X.xcodeproj` opens Xcode; any other folder, `usecornercase.dev` included, is opened with `open DIR`. The client stats the path on the thread that runs the opener, never on the window's loop, so a hung network mount cannot stall input. The Linux file manager reveals a file through `org.freedesktop.FileManager1.ShowItems` with `dbus-send` (the URI percent-encodes everything but `A-Za-z0-9-._~/`, the comma included, since `array:string:` splits on commas) and falls back to `xdg-open` on its folder when `dbus-send` is missing or fails within 5 s. **Default app** opens plain files only, never a folder (the desktop would show it in the file manager, which is the file manager's entry) and never an executable (macOS `open` runs a Unix executable in Terminal, as a double-click does, and an entry called default app must not run a just-built binary); the server leaves it out of the menu and the client refuses it too.
- **It runs where the window is.** The server's environment is the one it started with (no `DISPLAY` over ssh) and it may be on another machine, so the server never runs an opener. The client detects at startup (a local window, `sound::local_machine`, not under ssh) and sends `Hello.openers` (`protocol::VERSION` 7); `cornercase remote` finds none, since the folders are on the other machine, the proxy empties the openers it forwards (`remote::rebuilt`) and the browser bridge sends none, so a remote server cannot start programs on the laptop. The server keeps them per `Client` and tells `App` whose input it is about to handle (`App::set_window`, beside `set_queue_zone`), since overlays are shared by every window; menus are built from that window's openers. A click queues `(client, Open)` in the outbox and `Server::flush` sends `ServerMessage::Open` (the last variant, index 7, with `ClientMessage::OpenFailed`, also last) to that one window; a client with no openers ignores the order. A menu built for one window and clicked in another acts for the clicker: the opener missing there copies the path instead.
- **The client's side** (`Openers::open`): it refuses a relative path, an opener it did not find, a path that is gone and the default app for a folder or a program, each sent back as `OpenFailed`; otherwise it runs the steps on a thread: the early steps (the D-Bus reveal) through `process::output_within`, the last one spawned with null stdio and a process group of its own (the terminal's SIGHUP never reaches the app) and waited for, **never killed** (a generic `xdg-open` can run the app as its own child). Only a spawn error or a non-zero exit within 10 s (`REPORT_WITHIN`) is reported, as `exit status N`, and the server logs it and shows `could not open in VS Code: exit status 1`; an editor closed an hour later raises nothing. The client has no logger.
- **Copy path** is what a window that can open nothing sees instead (a remote window, the browser, an ssh session, a machine without the apps, a Linux console): it copies the path through OSC 52 and the toast says it is on the server's machine, since for a remote window the path is not where the user's file manager is. The viewer's header button copies at once, without a one-entry menu.
- **`MenuAction` stays `Copy`**: menu entries name what they open by id (`Subject`: project, workspace, pane, the file open in a workspace's viewer, the tree row last right-clicked); a tree row has no id, only a relative path, so the right-click keeps `(workspace, path)` in `Opening::row`, which only one open overlay at a time makes enough.
- **No request**, the exemption AGENTS.md allows for what is only meaningful inside the window: `status --json`, `watch` and `view` already give every project's, workspace's and pane's path, and a native UI opens them better with its platform's calls than through a server that may be elsewhere.
- **Left out**: custom entries (`open_with`), JetBrains and terminal apps, `code --remote ssh-remote+HOST` for remote windows, a keys-menu entry and a CLI command (AGENTS.md asks before keys), and naming the Linux file manager.
- **Tests**: detection and argv are unit tests over fake `PATH` folders, Applications folders and environments (`host/open/tests.rs`); running uses `/bin/sh` scripts for fake openers; the wire is in `protocol::tests`, the routing in `server::tests::opening` (two windows, one that can open and one that cannot) and the menus in `app::tests::opening`; `e2e::opening` runs the real binary with a fake `code` and `xdg-open` first on the `PATH`. No test runs a real opener.
