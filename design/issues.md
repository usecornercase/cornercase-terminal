# Issues

Code: `issues/`, `issues/browser/`, `http.rs`, `app/issues_dialog.rs`

- `Browser` takes `browser::Room` (list rows, detail rows and width) and `browser::IssuesHit`, and returns `Action`s. `app/issues_dialog.rs` builds the issues view and hit-tests that same view with `ui::issues_hit` or, for a detail, `ui::issue_button_hit`; the model imports no `ui` types. The browser is `browser.rs` (its types and what `App` feeds it) with a child per concern: `buttons.rs`, `token_form.rs`, `people.rs`, `picker.rs`, `input.rs` and `view.rs` (the detail's Markdown lines; the view itself moved to the app in #193, so it is small, and kept as its own file so the lines stay out of the state). `Choice` and the other types stay in the parent because several children read their private fields. It keeps its buttons and labels, token-field text and masking, and Markdown lines: the scroll limit needs their count, and ratatui text is independent of the app's view.
- `Browser` is pure state that returns `Action`s; `App` does the I/O on threads. Answers carry their query and issue key so stale ones are dropped, and lists, people, reads and token checks also the source's epoch, bumped by `App::forget_issues` when its connection goes or changes (disconnect, token removed or replaced, GitLab, Jira, Plane or Asana settings changed), so an answer still in flight cannot refill the cache with the old connection or save a token checked against it. Lists are cached in memory and in `issues.json` (titles and metadata only, never tokens).
- GitHub goes through `gh` in the project folder, run by `gh.rs` (see Pull requests). GitLab (REST v4), Shortcut (REST v3), Linear (GraphQL), Jira Cloud (REST v3) and Plane (REST v1 and v2) go through `ureq`, capped at 100 issues. People filters go into each tracker's query.
- Tokens come from `GITLAB_TOKEN` / `SHORTCUT_API_TOKEN` / `LINEAR_API_KEY` / `JIRA_API_TOKEN` / `PLANE_API_KEY` or are typed in the app, checked, and saved to `secrets.json` (0600). `issues::Secret` hides them in `Debug`; they are never logged.
- **A rejected token names where it came from** (#487): a user's saved Linear key was revoked while a working `LINEAR_API_KEY` sat in their shell but not in the server's environment, and every message said only "Linear rejected the API key", so they checked the key's permissions in Linear instead. A 401 or 403 (and Linear's `AUTHENTICATION_ERROR`) is `Error::TokenRejected`, raised by `http::finish` for every service; the app, which alone knows where the token came from, adds it when an answer arrives (`App::rejected_from`, `Source::rejected_from`): the saved one says to paste a new one in Settings or with `config secret`, the environment's names the variable, says it wins over a saved one and that the server reads it when it starts, so it is fixed or unset and the server restarted. Every path gets it: the dialog's list, read and people, `issue list` (and so `issue sources`' `failing` reason), `issue read`, `issue people`, `start --issue` and `flow run --issue`. A token being checked before it is saved is the one just typed, so its check keeps the plain text. Adding it where the error is built was rejected: the trackers' clients hold only the token, and threading its origin through seven clients and `locate::find` was more code for the same text.
  - **The environment's token wins, and says so**: saving or removing a token while its variable is set is still refused (Settings, `config secret`, `config remove`), now with `Source::env_wins`, which says the server read it when it started and to restart the server once it is unset; "change or unset it there" read as if the shell's value mattered. `issue sources` adds `shadowed` (only when true) when a saved token exists under the environment's, and the command prints `from LINEAR_API_KEY, over the saved one`.
  - **Why the list showed issues next to the error**: the dialog fills a tab from the list cache (in memory and `issues.json`, which outlive the server and are keyed without the token) while it loads, and an error left those rows in place, so a list fetched with an earlier, working token sat under "rejected". `issue list` already marks such rows `cached`. Now a failing list that still shows rows says `showing the list from before:`, and a rejected token drops the rows and forgets the source's cached lists (`note_list`, so the dialog and `issue list` alike), since they belong to a connection that no longer works and would otherwise come back the next time the dialog opens; with no rows the error also fills the list area, wrapped, as the one-line note cuts the advice off.
- **No redirects with a token in a custom header**: ureq keeps every header but `Authorization` when it follows a redirect, even to another origin, so GitLab (`PRIVATE-TOKEN`), Shortcut (`Shortcut-Token`), Plane (`X-API-Key`) and Asana (`Authorization: Bearer`; #305 asked for the same rule as the other token trackers) read through `http::get_without_redirects` (`max_redirects(0)`), which answers a 3xx with an error saying the redirect was not followed and to use the address it leads to. Jira and Linear send `Authorization`, which ureq drops on a redirect to another origin, so they keep `http::get` and `http::post`; so do the update checks, which carry no token.
- **Starting an issue**: in a repo root, a worktree on `issue-<n>-<slug>` / `<iid>-<slug>` (GitLab) / `sc-<n>-<slug>` / `ENG-123-<slug>` / `PROJ-123-<slug>` (Plane's keys look the same) / `ENG-42-<slug>` or `asana-<gid>-<slug>` (Asana, with and without an ID field); elsewhere a new tab. GitHub and GitLab issues belong to the repository the browser was opened from (`Source::in_repository`); Shortcut, Linear, Jira and Plane issues ask which open project or workspace to use. Then the agent starts with the prompt.
- **Naming the branch and the workspace** (#392, `issues/naming.rs`, `issues/browser/naming.rs`, `app/issues_dialog.rs`): teams have their own branch conventions (`feat/ENG-42-…`, `<user>/<ticket>`), and **start** always named the branch for them.
  - **A step before the worktree**: when **start** would make a worktree (the place's `worktree`, else a repository root, the rule `start_issue` already used for `in_a_tab`), the browser answers `Action::Name` instead of `Action::Start`; the app computes the prefill and hands back a `Naming` (`Browser::name_start`), shown over the list or the issue like the pickers: a heading, the branch and the workspace's name as two fields (plain strings with the cursor at the end, like the start-a-flow dialog's branch field and the token form, not an `Editor`), help lines, and ` start ` ` back `. `Tab` and the arrows move between the fields, `Enter` or ` start ` sends `Action::StartNamed`, `Esc` or ` back ` returns to where it was. `Enter` twice keeps today's names, the cost the account pick (#379) already set. A new tab (no worktree) asks nothing, and ` schedule ` and ` start a flow ` keep their own branch fields. The branch is checked as git would (`naming::check_branch`: `git check-ref-format --branch`'s rules) before anything starts; an empty name keeps the issue's. An existing branch is checked out by `git worktree add` and a workspace that has it open is reused, as before.
  - **A template** (`issue_branch` in `config.json`, Settings › Worktrees › **issue branches**, a text row, so `settings::tests::requests` covers it and the `config` request sets it): placeholders `{key}` (the key without `#`), `{number}` (the digits after the key's last dash, else the key's digits, else `Issue::number`), `{slug}` (the title's slug), `{source}` (the tracker id) and `{user}`. Empty keeps each tracker's own name (`issues::branch`), so nothing changes for anyone who sets nothing, and a per-tracker default could not be one template anyway (GitHub's `issue-` and Asana's `asana-` prefixes). A template must hold `{key}` or `{number}` (`naming::check`), or every issue would share one branch; unknown placeholders and unmatched braces are refused with the list. The result is cleaned, not refused, into a name git takes (`naming::clean`: each `/` part keeps `A-Za-z0-9._-`, repeats collapse, dots and dashes are trimmed, `.lock` dropped, empty parts removed), and an empty result falls back to the default. The note shows an example for a Linear issue and warns, in red, when the GitLab example does not start with `<iid>-`, since GitLab's automatic closing needs it.
  - **`{user}` is git's `user.name`**, read from files (`git::user_name`: the repository's common `config`, then `~/.gitconfig`, then `$XDG_CONFIG_HOME/git/config`; first found wins, `include` not followed, no git process) and slugged to 24 characters, only when the template uses it. The tracker's account was considered and rejected: GitHub goes through `gh`, whose login cornercase never reads, so the most common tracker would have no user; the OS login was rejected as often not the name a team uses.
  - **One rule everywhere**: `App::issue_branch(issue, project)` is the prefill, the issue page's "start" line (the browser's `Agents` carries the template and the user), `issue-list` and `issue-read`'s `branch` and `prompt`, the queue's prepared branch (the template and user are read before the job), flows started from an issue (dialog and `flow run --issue`) and `start --issue`. The chat bots' `/new` starts from no issue, so it has nothing to name.
  - **Flows from an issue** take the same names: the start dialog's branch was already prefilled with `App::issue_branch` and editable, so for an issue it gains a **workspace** row under the branch (`Focus::Workspace`, after the branch in `Tab` order, and its own row in `ui::start_flow`'s layout, which only exists for an issue, so the other start dialogs did not move), prefilled with `issues::workspace_name`; an empty one keeps the issue's. Every start, from an issue or not, now checks the branch with `naming::check_branch` and says `… cannot be a branch` in the dialog, where git used to refuse it after the dialog had started waiting. The name travels in `flows::start::Action::Start::workspace` and `Starting::name`, and `open_run` gives it to the run's workspace once the team's panes exist, only when that workspace has no name yet (a reused workspace keeps its own). `flow run --issue` takes `--workspace-name` too (the `workspace_name` field of `flow-run`, the same `issue-names` feature); without `--issue` it is refused as `malformed`.
  - **External clients**: `start --issue` already took an explicit branch with `--worktree` (since #340, so any server with `issues` honours it, and `flow run --issue --worktree` likewise); the workspace's name is the new `workspace_name` field (`--workspace-name`, `requires = "issue"`), behind the feature `issue-names`, which the CLI checks first since an older server would drop the field and name the workspace after the issue. `--name` keeps meaning the tab's name. Left out: a per-project template (`projects.<path>` could hold one later).
- **Through the server** (#340, `control/issues.rs`, `app/trackers.rs`, `app/control/issues.rs`, `cli/issue.rs`, `cli/args/issue.rs`; `cornercase issue sources|list|read|people`, `start --issue`, `flow run --issue`): the trackers' clients, caches, epochs and people lists lived behind the Issues dialog, so a native UI would have rebuilt seven clients and kept the tokens itself. Requests now reach what the dialog uses.
  - **Four request names** (`issue-sources`, `issue-list`, `issue-read`, `issue-people`; `Command::NAMES` has 58) rather than one tagged `issues` request, since the four answers have four shapes and an older server refuses each by name. None takes a view (as `queue` and `flow`); each defaults its project to `project`, else the caller's, else the shown one. `start` and `flow-run` gain `issue` and `source`, behind the feature `issues`: an older server would ignore them and start an agent without the issue, so the CLI checks it first (`client::use_issues`), as for `--unlock`, `--host` and `--patches`. `CONTRACT` stays 1.
  - **The dialog's connection layer moved to `app/trackers.rs`** (`IssueConnections`, clients, epochs, accounts, `places`, `locate_issue`) and `issues/locate.rs`, with no change of behaviour, so the dialog and the requests share one implementation; `IssueConnections::failures` is new.
  - **Sources** (`issue-sources`, no network): the dialog's tabs first, the others after, each `connected`, `missing` (with what: `token`, `site`, `email`, `workspace`, `repository`) or `failing` (with the last list's error), plus the account, where a token comes from (`gh`, `saved`, `env` with the variable's name, and `shadowed` when a saved one is under it), the people fields and the window's remembered filter, and the places an issue can start in with the asker's marked. `failing` is only a list's failure: `note_list` records it per source (per project for GitHub and GitLab, keyed like `people_cache`) from the dialog's lists and the request's, and `forget_issues` clears it, so a token or setting change starts over; a read of an issue that does not exist or a people error does not mark a source failing. A token whose Asana account has several workspaces is saved by `config secret` without a workspace (the dialog's settings treat it as good), so `config secret` records the check's message as that source's failure: it is `failing` with the reason, which names the workspaces and `asana_workspace`, until the workspace is set.
  - **Lists share the dialog's keys and epochs**: `issue-list` builds the same `Query` and `cache_key`, so the two share cache entries, and `cached: true` answers from them with no network. Without `source` it lists what the All tab lists, every source in parallel inside one job; a person's handle needs a source (a filter names one tracker's people), `me` and `anyone` do not. A tracker's failure never refuses the request (the precedent of `read --last-message` with several targets): it is that source's `error`, with its cached list when there is one, and the command exits 1 after printing the others. An answer whose source's epoch moved while it ran (token or tracker setting changed) is that source's error and is not cached. Merged lists are ordered newest first as the All tab does.
  - **Reads and people** (`issue-read`, `issue-people`): the key or URL goes through `issues::locate` with the queue's rules and refusals (`conflict` for a tracker that is not connected), and the answer carries the dialog's detail (info line, Markdown body, comments) and the prompt `start` would paste. People carry `id` for Jira, Plane and Asana, which a filter must send back.
  - **`start --issue` and `flow run --issue`** do what the dialog's **start** and **start a flow** do: the branch is `App::issue_branch` (the `issue_branch` template, `issues::branch` when it is empty) unless `--worktree` names one, the prompt comes from the template, a repository-root project gets a worktree on that branch and a workspace named after the issue, and anything else a tab named after it. The checks that need no tracker (agent, mode, model, effort, flow problems, the place) run first and refuse before any network; the tracker is then asked on a job (`Stage::Issue`, so a `--timeout` names it, and a client that leaves drops it with nothing created), and the continuation runs the same `start_within` or `run_flow` an ordinary request does with the original deadline. A prompt together with an issue is refused.
  - **The place rule mirrors **where…****: a GitHub or GitLab issue belongs to the repository of the project asked (`--project`, else the caller's or the shown one); Shortcut, Linear, Jira, Plane and Asana issues are refused with `conflict` listing the places, the asker's marked, when `--project` (a new worktree) and `--workspace` (a new tab) say neither and more than one exists. No "where you are" default, not even in a pane: the dialog asks too, and a script that starts work in the wrong repository costs more than one more flag. A flow needs a repository root, so its list is those projects.
  - **Differences from the dialog**, on purpose: `start --issue` always submits the prompt (every `start` does, as the queue; following settings' `submit` would leave it unsent and end `--wait` at once); a workspace already on the branch gets a new tab with the agent (`start`'s rule, since a script needs a pane id back) where the dialog only switches there; and no request changes the window's remembered tab or filter (`issue-sources` reports them).
  - **Connecting stays `config`'s** (#336: `config secret`, `config remove`, `config set jira_site`…), which runs the dialog's checks with the token write-only; `issue-sources` reports the result. A connect request of its own was rejected as a second path to the same checks.
  - **Logging**: requests log the project, the source, the filter kinds (`anyone,me`, `person`, never a handle), sizes and presence; jobs log the source and project (the dialog's start logs the key and branch as before). Titles, bodies, comments, prompts and people never reach the log, and refusal texts name keys and URLs only.
  - Rejected: a text search filter (clients filter what they got), patches for lists, a connect request, and a "where you are" default.
- **Jira** (Cloud only; Server/Data Center use other auth, API v2 and wiki markup): HTTP Basic with `email:token`. The site and email are not secret, so they live in `config.json` (`jira_site`, `jira_email`) and only the token in `secrets.json`; the browser's connect form asks site → email → token (one field, three steps; `SaveJira` saves the first two before the token is checked), settings has a row for each. `jira_jql` is ANDed with the generated JQL (its `ORDER BY` dropped). `/rest/api/3/search/jql` refuses unbounded queries, so a list with no condition at all sends `project IS NOT EMPTY`. Jira Cloud no longer takes names in JQL, so a picked person is `Who::User { id, name }` (the `accountId`); other trackers keep `Who::Person(handle)`. Descriptions and comments are ADF (JSON), turned into Markdown by `jira/adf.rs`; unknown nodes give their text. A `config.json` without `jira_site` was written before Jira, so `config::load` appends `jira` to its `issue_tabs` (once saved, the key exists and hiding the tab sticks). Changing the site, email or filter forgets the cached lists, people and account. Timestamps carry an offset (`+0200`), which `parse_time` applies.
- **Plane** (Cloud and self-hosted, `plane.rs`): `X-API-Key` with a personal access token. The workspace slug, the server's URL (`plane_url`, blank is Plane Cloud: API at `https://api.plane.so`, web app at `https://app.plane.so`; a self-hosted server serves both from one URL) and the filter are not secret and live in `config.json` (`plane_workspace`, `plane_url`, `plane_filter`); only the key is in `secrets.json` (`plane_api_key`, or `PLANE_API_KEY`). The connect form asks workspace → key (`SavePlane` saves the workspace before the key is checked), settings has a row for each. The list is the workspace-wide `GET /api/v2/workspaces/{slug}/work-items/`, one request per page of 100 with the cursor envelope (`paginate=cursor`; at most 10 pages, so a local creator filter cannot loop), ordered by `-updated_at`, with `expand=state,assignees,labels` (v2 has no `project` expand, but each row carries its readable key as `identifier`, so the key is the row's and nothing else is needed to build it). Open means `state_group__in=backlog,unstarted,started` (the state's group, which every workspace has whatever its states are called); the assignee is `assignee_id`, and `plane_filter` is raw query parameters (`key=value&key=value`, trimmed, not validated: the server's own error is shown) added to the request. A `state_group__in` in it is merged into the open one rather than sent twice (which of two the server reads is up to it, and the filter's would bypass **closed**): with closed off only its open groups are asked for, and none of them means an empty list without asking for work items; with closed on it is sent as it is. v2 has no creator filter, so the creator is filtered after fetching, on `created_by_id`. v2 rows have no `updated_at` among their documented fields, so `updated_at` falls back to `created_at` when the server leaves it out. Names come from the members list (`/api/v1/workspaces/{slug}/members/`, also the people picker, active non-bot members as `Who::User { id, name }`), so a list takes three requests (the account, the members, the work items) against Plane's 60 a minute per key. The key is checked against the account and the workspace together (`whoami` reads `/api/v1/users/me/` and the members), so a misspelled workspace fails at the connect step. The v2 work item has no description and no comments, so reading one goes through v1: `GET /api/v1/workspaces/{slug}/work-items/{KEY}/` (the key alone, no project id) and its comments under `projects/{project}/work-items/{id}/comments/`. Descriptions and comments are HTML (TipTap's), turned into Markdown by `html.rs` (a small tolerant parser: unknown tags give their text), falling back to the plain text the API also sends; the Markdown helpers it shares with `jira/adf.rs` live in `md.rs`. The parser is `issues/html.rs` (it was `plane/html.rs` until Asana needed it too, in a commit that only moved it). A work item is closed when its state's group is `completed` or `cancelled`. A `config.json` without `plane_workspace` was written before Plane, so `config::load` appends `plane` to its `issue_tabs`, as for Jira. Changing the workspace, URL or filter forgets the cached lists, people and account. Not covered: Plane's pages, intake and epics as separate things (an epic is a work item), and servers too old to serve `/api/v2`.
- **Asana** (`asana.rs`, #305): an issue is a top-level task of one workspace; subtasks are not listed, and neither are milestones and approvals (only `resource_subtype` `default_task`, and rows with `is_rendered_as_separator` are dropped: a task shows under a project when it was added to it directly, whatever its kind). The token is a personal access token sent as `Authorization: Bearer`, from `secrets.json` (`asana_token`) or `ASANA_ACCESS_TOKEN`; `CORNERCASE_ASANA_API` moves the API (`https://app.asana.com/api/1.0`) for tests. Requests go through `http::get_without_redirects`. `config.json` has `asana_workspace` (a name or gid; empty is the account's only workspace) and `asana_projects` (gids or project links, kept as typed; settings save them as gids joined by `, `, and `asana::project_gids` reads both forms at use time, so old values keep working). **Key and branch**: the value of the task's ID custom field when its project has one (`representation_type` `custom_id`, `display_value` such as `ENG-42`), else the gid; the branch is `ENG-42-<slug>` or `asana-<gid>-<slug>`, the full gid since Asana has no shorter handle. `Issue::number` is the gid when it fits a `u64`, else 0. The URL is the task's `permalink_url`, never built by hand: Asana moved its links from `/0/<project>/<task>` to `/1/<workspace>/project/<p>/task/<t>`. The state is the name of the task's section in its first project (`memberships.section.name`), `completed` once it is, else `open`; closed is completed; labels are the tags. **Settings → Issues → Asana** has the workspace, the projects and the access token, in that order; the token is checked against `/users/me` alone, so it needs neither first. The workspace row shows the workspace's name once the account is known (the token row's account, with no extra request) and puts the saved ID in its note (`ID 1200…`); before that it shows the saved value, and `your only one` when none is set.
  - **The list is plan-independent**: with no projects set, `GET /tasks?assignee=me&workspace=<gid>` (your tasks); with projects, `GET /projects/<gid>/tasks` once per project (at most 10), merged without repeats. Asana's search (`/workspaces/<gid>/tasks/search`) has every filter and sorting, but is premium only (402) and capped at 60 requests a minute, so a free workspace could not use the tab. Each call asks `limit=100` and explicit `opt_fields`, follows `next_page.offset` (at most 10 pages per source, stopping at 100 kept tasks), and the merge is sorted by `modified_at` and cut at 100. Open sends `completed_since` as the current UTC time in RFC 3339 on both calls: the keyword `now` is documented only on the project and section lists, and on `GET /tasks` the parameter is typed as a date-time. Closed sends none, so completed tasks come too. People filters are local (`GET /tasks` cannot filter by assignee together with a project, nor by creator at all), on `assignee.gid` and `created_by.gid`; **me** is the gid of `/users/me`. In the your-tasks list the assignee is already you, so an assignee other than anyone or me is not sent anywhere and the list answers that it is your tasks and to set **Asana projects** to filter by someone else; the creator filter still applies. The people picker is `GET /workspaces/<gid>/users` (at most 20 pages). `created_by` carries only a gid, so the author is resolved from that same list, which makes a list three or more requests against Asana's 150 a minute on free plans (1,500 on paid ones).
  - **Choosing the workspace**: `whoami` reads `/users/me?opt_fields=name,email,workspaces.name`. The setting is matched by gid or case-insensitively by name; with none set, the only workspace is used. With several and none matching, the list answers an error naming them and the setting. The connect form asks for the token first and, when the account has several workspaces and the setting names none of them, goes to a workspace step that reuses `Step::Workspace`: type a name or gid, checked against the token's workspaces (the help lists their names), saved to `asana_workspace` as its gid, with the token, which is written only then. The gid rather than the name, since two workspaces can share a name and a saved name would then resolve to the first; a name typed in settings that two workspaces share is refused with their ids, and the account's name still shows in the list's hint. That ambiguity comes back from the check as `Error::Workspaces` (boxed, carrying the account's name and the workspaces) rather than as a field of `Account`: the check has to succeed for the settings (their token row needs no workspace first) but the form needs the names, and a new field in `Account`, even boxed, pushed `server::Step` over clippy's `large_enum_variant` limit; the settings treat the variant as a good token. With a single workspace and a setting that names another, the check fails with the plain error.
  - **Reading**: a key of digits is a gid (`GET /tasks/<gid>`); any other is an ID-field key, looked up with `GET /workspaces/<gid>/tasks/custom_id/<key>`, which takes no query parameters, and then `GET /tasks/<gid>` with `opt_fields` (the list's plus `html_notes`, `notes`, `due_on` and `memberships.project.name`). Comments are the task's stories with `resource_subtype` `comment_added` (also checked locally; up to 5 pages), so the activity log (assignments, section moves) stays out. The info line is the section, `due`, `created by`, `assigned to` and the projects. Rich text is Asana's XHTML (`html_notes`, `html_text`) through `issues/html.rs`: a mention (`data-asana-type="user"`) and a link the reader cannot open (`data-asana-accessible="false"`) become their text, and an image becomes `[image]`, since its URL expires within minutes and has no alt; empty rich text falls back to `notes` or `text`.
  - **Errors**: 401 and 403 say the token was rejected, 429 that the rate limit was reached (the shared text of `http.rs`, as for the other trackers), 402 that this needs a paid Asana plan, and any other status the first of `errors[].message`. A `config.json` without `asana_workspace` was written before Asana, so `config::load` appends `asana` to its `issue_tabs`, as for Plane; it is last in `Source::ALL` and `Source::REMOTE`. Changing the workspace or the projects forgets the cached lists, people and account. Not covered: subtasks, milestones, approvals, premium search, portfolios, goals and writing back to Asana.
  - **Why built in**: herdr, whose design cornercase's was compared with, keeps trackers out of its core and leaves them to plugins (herdrdev/herdr#301 asked for a built-in board and was closed for that reason). cornercase builds them in because a plugin could not reach the Issues tab, `start`, the queue, flows or `/new`, which all read an `Issue`.
- **GitLab** (gitlab.com and self-hosted, `gitlab.rs`, #253): it works like GitHub, not like the trackers: the tab lists the issues of the GitLab project the open project's repository comes from, and **start** works in that repository without asking where. A workspace-wide list was rejected: GitLab's `/issues` with `scope=all` is every issue the token can see, which on gitlab.com is every public project, and the issue asked for a project's issues. `glab` was not used the way `gh` is: the issue asked for a base URL and a personal access token, and the trackers already go through `ureq` and `FakeHttp`. The token goes in a `PRIVATE-TOKEN` header and needs the `read_api` scope; it is in `secrets.json` (`gitlab_token`) or the `GITLAB_TOKEN` environment variable, which cornercase reads itself; the name is the one `glab` uses, so a token already exported for it works too. The server is `gitlab_url` in `config.json` (blank is `https://gitlab.com`; a self-hosted server serves the API under `/api/v4` of the same URL, also under a path such as `https://acme.dev/gitlab`), so the connect form asks server → token (`SaveGitlab` saves the server first; an empty one is gitlab.com) and settings has a row for each. **Which project**: every job runs `git remote -v` in the project folder (on its thread), takes the fetch URLs (`origin` first) and keeps the first whose host is the server's or one of its subdomains (`altssh.gitlab.com`), reading scp-like (`git@host:group/project.git`), `ssh://` and `http(s)://` URLs (a server under a path drops that path from web remotes only, since ssh paths never carry it); the path, with every subgroup, goes URL-encoded into `/projects/{path}/…`. No match says where the remotes are, and names the setting when one of them looks like a self-hosted GitLab. A host alias from `~/.ssh/config` does not match; not covered. The list is `GET /projects/{path}/issues` (`state=opened` unless **closed**, `order_by=updated_at`, `sort=desc`, 100 per page, one page), people are usernames (`assignee_username`, `author_username`, `Who::Person` like GitHub; **me** is the token's user, read from `/user` on every list, which also gives the account), and the people picker is the project's active members (`/members/all`, inherited ones included, at most 5 pages, bots left out). Reading an issue is `/projects/{path}/issues/{iid}` and its notes (`sort=asc`), leaving out system notes; descriptions and notes are Markdown already. The key is `#<iid>`, as GitLab writes it inside a project. The branch is GitLab's own `<iid>-<slug>`, not `issue-<iid>-…`: a merge request from a branch that starts with an issue's number followed by a dash gets `Closes #<iid>` in its description, so the issue closes when that merge request reaches the default branch, as long as the project keeps automatic issue closing on (the default; a self-managed server can also change the closing pattern). 401 and 403 say the token was rejected and may have expired or lack `read_api`, and a 404 on the project says the token cannot see it (GitLab answers 404 for a private project). A `config.json` without `gitlab_url` was written before GitLab, so `config::load` puts `gitlab` after `github` in its `issue_tabs` (at the end without one); `Source::REMOTE` puts it last, so the settings page adds its section after Plane's. Changing the server forgets the cached lists, people and account; the cache and the people are kept per project, as for GitHub. Requests go through `http::get_without_redirects` (see above): following a redirect, even from `http://` to `https://` on the same host, could send the token elsewhere, so a 3xx answer says to use the URL it leads to instead. The URL may still be `http://`, for a server on a private network: refusing it would leave those users out, so the settings notice and the connect form warn that the token travels unencrypted, except on `localhost`, `127.x` and `[::1]`.
- **Copy URL** uses OSC 52 through the outbox (`Outbox::copy`), because the server may run on another machine.
- Markdown renders with `pulldown-cmark`; code blocks are highlighted with syntect (pure Rust `regex-fancy`), mapping scopes to palette colours so the terminal theme applies. Highlighting is cached and warmed on the reading thread; syntect and its regex crates build with `opt-level = 3` in dev.
