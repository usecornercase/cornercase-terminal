# What fills the context

Code: `agents/breakdown.rs`, `agents/claude/breakdown.rs`, `agents/probe.rs`, `app/context_dialog.rs`, `app/context_dialog/`, `ui/dialog/context.rs`, `control/context.rs`, `app/control/context.rs`, `cli/context.rs` (#585)

The tab's second line says how full the window is. When it is 40 % and AGENTS.md is 8 k tokens, the question is what the rest is: MCP servers, skills, memory files or the conversation. Claude Code answers it with `/context`, which writes into the conversation and needs the agent idle. **view context** answers it without touching the agent.

- **A second `claude`, not the pane.** The PTY is the only channel to the agent, and `/context` there prints into the conversation (a message in the transcript, nothing to read back but the screen). cornercase starts `claude -p --no-session-persistence --input-format stream-json --output-format stream-json --verbose --resume <conversation>` in the pane's folder, which reloads the same transcript and settings, and sends `initialize` and `get_context_usage {"detail":"full"}` over its stdin as the plan usage probe does (`get_usage`). Nothing is typed into the agent, no prompt is sent and no tokens are spent. `get_context_usage` and `mcp_status` are control requests of Claude's stream-json protocol, not a documented interface: the parser requires only `categories`, `totalTokens` and `maxTokens`, ignores every other key and shows Claude's own error text when it refuses.
- **One runner for both probes** (`agents/probe.rs`): the usage probe writes both requests at once and reads one answer, the context probe asks again after reading an answer (`mcp_status` until no server is `pending`, then the context), so the runner takes a function from each line read to a step (read on, write, answer) and the usage probe is that function with no writes. `Probe<T>` (the loading flag, the last answer, the error, the count of answers a request waits on) is shared too. After an answer the runner drops the program's stdin, which makes Claude exit by itself within a second and delete `sessions/<pid>.json`, and waits `grace` for it before killing. The usage probe keeps its immediate kill (grace zero) and so still leaves that session file behind; changing it was left out.
- **Hooks off, settings on.** The probe passes `--settings '{"disableAllHooks":true}'`: a resumed conversation fires `SessionStart` again, a side effect of looking. It does **not** pass `--setting-sources ''` (the usage probe does): the user's settings are what brings the MCP servers, skills and memory being measured.
- **It waits for the MCP servers.** They connect after `initialize`: asked at once, 10 servers were `pending` and MCP tools counted 0 where the waited answer had 8,490 tokens (measured with 2.1.316, 2026-11-02). The probe polls `mcp_status` every 250 ms while a server is `pending`, at most 8 s from its start, then asks; the whole probe is capped at 15 s (`breakdown::TIMEOUT`). A Claude without `mcp_status` answers an error, and the probe goes straight to the context. A typical read takes 2.5 to 6 s.
- **The pane's own environment, never a default `CLAUDE_CONFIG_DIR`.** The probe gets the environment of the pane's agent (`process::env(pid)`) minus `CLAUDE_SESSION_ENV`, so its account, proxy and provider variables apply; when that cannot be read (macOS without access, a process that just left) it takes the server's environment minus those variables, plus the account's folder when the pane has one. Setting `CLAUDE_CONFIG_DIR` to the default `~/.claude` makes Claude read `~/.claude/.claude.json` instead of `~/.claude.json`: the user's MCP servers vanished (341 tools to 0) and Claude created `~/.claude/.claude.json`, so it is set only from the pane or its account.
- **Flags repeated from the pane**: `--model` (the last reply's model id, with `[1m]` added when the tab's window is 1M and the model is not natively 1M, since the suffix carries the window: 200k without it; with no reply yet, the pane's own `--model`), `--add-dir` (only directories that exist), `--mcp-config` (an existing file or inline JSON) and `--strict-mcp-config`, which cornercase and flows launch with. `--system-prompt`, `--append-system-prompt`, `--plugin-dir` and `--agents` are left out: they would change the numbers rarely, and copying a long prompt into a second command line costs more than it explains.
- **No conversation yet** (no transcript, or right after `/clear`): the probe runs without `--resume`, in the same folder, and the dialog adds "No conversation yet: this is what a new conversation starts with." The fixed costs (system prompt, tools, MCP, memory, skills) are what the person wants to see before the first prompt. An unknown conversation id gives Claude's own error (`No conversation found with session ID`) as a `result` line, then the process exits; it reaches the dialog as the error text.
- **Messages is the remainder.** The categories marked `used` add up to the last reply's usage, and `Messages` is what is left, so a late MCP server moves tokens between MCP and Messages without changing the total. That is why the wait matters. The numbers are a reload of the transcript with today's settings: a skill added since the agent started shows, and while the agent works they lag by the reply in progress. The docs say so beside "read … ago".
- **Two name spaces for MCP servers**: `mcpTools[].serverName` is normalized (`claude_ai_Docs`) and `mcpInstructions[].serverName` is the display name (`claude.ai Docs`). The two lists are never merged by name; they are two sections of the dialog and two lists in the answer.
- **`kind` is the agent's own string**, passed through. A new Claude can add a kind, and the dialog places a category by `kind` only (`used`, `free`, `buffer`, `deferred`, anything else out of the bar and the rows), never by its name. The per-server sums of `mcpTools` do not have to match the category totals, and nothing relies on it.
- **The dialog** reuses the frame of Merge check and Pull request (`ui::Update`: a message, scrolling notes, a note row and two buttons), so geometry, scrolling, hit testing and the corners test are shared. Title `Context`, message `Claude Code · Opus 5.5` then `251.9k of 1M tokens · 25%`, buttons ` refresh ` and ` done `, the note row `reading…`, `read just now` / `read 2m ago` or the error (the previous numbers stay under it). The title is static (`Update.title` is a `&'static str`) and there is a ` done ` button, a little different from the issue's mock; a custom frame that matched it exactly cost a new geometry, hit testing and corners test. The bar is `width` cells: used slices in the answer's order in a fixed palette by position (violet, rose, steel, sand, mauve, teal, terracotta, grey-blue, indigo: none of the status colours, none of the cobalt of the brand), then free `□` and the autocompact buffer `▒`, muted, at the far end as `/context` draws it. Each slice gets the cells between its cumulative boundaries (`round(cumulative / max · width)`), so they always add up to the width and a tiny one may get none. Deferred categories fold into one muted line, `Not loaded: MCP tools 199.9k · System tools 19.0k`. Memory file paths show `~` for the home folder and are cut at the start. Closing the pane closes the dialog; a click outside closes it (nothing in it is busy).
- **Menus**: `view context` is in the tab's menu (` ⋯ `, right-click, the tab bar's), once per pane running an agent in that tab (`term.agent`, as `mark` counts them), in pane order: with several it reads `view context · Claude Code`, `view context · Codex`, and ` 2`, ` 3` are appended when titles repeat. It is also in the agents section's right-click menu, right before `close agent`. An entry in the keys menu and in the pane's own menu were left out.
- **Other agents** get the model and percentage the tab line shows and "X does not say what fills its context": Codex records its tokens by kind only (input, cached, output, reasoning) and the rest record a total. A second `Spec` in an agent's folder (`BREAKDOWN`, `None` for now) is where a breakdown for another agent goes.
- **One probe per pane** (`App::contexts`, in memory only, never in `session.json`): a second ` refresh ` or request while one runs waits for it. The answer is dropped when the pane's agent process changed meanwhile.
- **Through the server** (`context`, `cornercase context [--pane ID | --tab ID] [--cached] [--json]`): the request returns `{pane, agent, title, model, percent, compacted, loading, read_at, age, breakdown, notice, error}`, every key present (`null` without a value), `breakdown` being the model above (snake_case, `kind` a string). A pane that runs no agent is a `conflict` (`pane N runs no agent cornercase reads`, as Close agent says), an unknown pane `not-found`. The agent's own failure is text in an ok answer (`error`, beside the previous numbers) and the command exits 3, as `usage` does. `cached` answers at once from memory and starts nothing. The request shares the dialog's probe and waits for it, with no timeout of its own: the probe is bounded and always answers; a client that leaves drops it. **No feature string** (the issue said "a feature in the contract"): by the contract's rules a new operation already shows in `contract`'s `operations`, which is how `usage` and `pull-request` went out; a `FEATURES` entry is for a change to an existing request. The note goes here and not in the scripts topic, following `plan-usage.md` and `pull-requests.md`, which keep their requests.
- **Checked live** with Claude Code 2.1.316 on 2026-11-02: the probe against a real session, answered in 2.6 s without the wait and 3.8 s to 6 s with it; the answers in `tests/fixtures/claude/2.1.316/` are real ones with names and paths made generic and the lists cut. No test runs a real `claude`: `FakeClaude::PROBE` answers from the fixture.
- **Left out**: a ` ⋯ ` button on the agent rows; opening a memory file from the dialog; a live breakdown under the tab; acting from the dialog; the answer's `agents[]` and `slashCommands`; repeating the pane's other flags; a breakdown for the other agents.
