# Text fields

`editor.rs`, #454. One component for every field with a cursor.

- **One component, two ways of use.** The multi-line fields (the start dialog's prompt, a flow's prompts and notes, the import page, a project's setup and teardown, the paste field in Settings › Share, the tour's prompt) and the one-line fields (TODO items; the schedule form's prompt, time, date, amount and branch) are the same `Editor`.
  - A multi-line field uses `key`: `Enter` breaks the line, `Home` and `End` reach the ends of the wrapped line, the cursor is revealed; pastes go through `insert_lines` (`\r\n` and `\r` become `\n`).
  - A one-line field uses `one_line_key`: the caller keeps `Enter`, `Home` and `End` reach the ends of the text; pastes go through `insert`, which turns line breaks, tabs and control characters into spaces. TODO and queue shared two copies of this mapping before.
  - Fields without a cursor (changes filter, files search and find, search dialog, comboboxes, the flow editor's one-line rows, the start dialog's branch and workspace) are plain strings and are not built on it.
- **ratatui-textarea as a model only** (0.9.3, `default-features = false`): lines, cursor, edits and history. Its widget is not used: viewport and screen layout live in cells that its own render updates, while fields live in `App` and every window draws a copy of the view. Its `input` brings emacs `Ctrl` and `Alt` bindings, which AGENTS.md rules out, and `input_without_shortcuts` lacks the arrows and `Home`/`End`, inserts four spaces for `Tab` and has a `Delete` that removes a line break before a zero-width character ending a line, so keys are mapped by us.
  - Wrapping, scroll, vertical moves, clicks and drawing stay ours: wrap keeps every char and counts display columns, a full last line gets an empty one for the cursor. The snapshots did not change.
  - `TextArea` is `Send` but not `Sync`; `App` and the views stay on the server's loop.
  - The `TextArea` is boxed so that enums holding an `Editor` stay small.
  - Cost, measured on 2026-10-22 in release: an edit rebuilds the screen map, about 0.8 ms per keystroke on a 256 KiB text and nothing on normal fields; a view's clone carries the history (50 edits), about 0.2 ms for 4,096 lines. The default history stays so that undo is ready.
- **Our moves, applied with `Jump`.** `Forward`, `Back`, `Up` and `Down` read the screen map in screen columns and skip or stop short of zero-width characters at the start or end of a line, so typing there would split a character. `left`, `right` and `place` compute the offset as before and jump to it. `Delete` is `delete_str(1)`, guarded at the end of the text.
- **The `u16` limit.** `Jump` takes `u16`, so a row or column of 65,536 or more cannot be reached; such a line only comes from a paste (up to 256 KiB). `jump` refuses instead of clamping: `←` `→` fall back to `Back` and `Forward`, which have no limit, and a click, `↑` `↓` or `Home`/`End` of a wrapped line leave the cursor in place.
- **Word moves** (#454, asked by the user): `Ctrl+←` and `Ctrl+→` (and `Alt+←` `Alt+→`, `Alt+b` `Alt+f`) are `WordBack` and `WordForward`. A word is a run of the same class (whitespace; ASCII punctuation, where a run is one word; everything else), as in vim's `w` and `b`, and a line break is a stop.
  - `Ctrl` with an arrow is neither `Alt` nor `Ctrl+letter` (shell bindings). `Ctrl+↑` `Ctrl+↓` stay `↑` `↓`. `Shift` with an arrow selects (see Selection), one character, or a word with `Ctrl` or `Alt`.
  - It cannot clash with the prefix key, which is `Ctrl` or `Alt` with a character, or a function key.
  - macOS: Mission Control takes `Ctrl+←` `Ctrl+→` by default, so they reach the terminal only after turning those shortcuts off. So the fields also take Option+arrows, the macOS habit, which arrive as `Alt+←` `Alt+→` (kitty, WezTerm) or as `Esc b` and `Esc f` (Ghostty's default; the client decodes them as `Alt+b` and `Alt+f`). The user approved this as the one narrow exception to the rule against `Alt` shortcuts: it is only inside these fields, where Option+arrows compose no character and did nothing, and `Alt+b` / `Alt+f` match only with `Alt` alone (a macOS terminal composes a character for Option+letter, so typing is unaffected). The prefix key is checked first, so a user whose prefix is `Alt+b` keeps it.
  - These are keys of the TUI's own fields, exempt from reaching the socket.
- **Equality** compares text, cursor and scroll, not history or styles.
- **Selection** (#454, the user's decisions D1-D3).
  - Model: `TextArea`'s anchor plus cursor. Its moves extend a selection while one is open, even an empty one, so every plain move unselects first and `Shift` moves only anchor. `←` `→` collapse to the selection's start or end, as native fields do; anything else drops it. Typing, a paste, `Enter`, `Backspace` and `Delete` replace or remove it through `TextArea`'s own deletion, so `Delete` at the end of the text must still act when a selection exists. `copy()` cancels the selection and `select_all()` jumps with `u16::MAX`, so neither is used: the text is taken ourselves and `select_all` uses the ends of the text. `Shift+Home` and `Shift+End` extend to the wrapped line's ends (the text's, in a one-line field).
  - Keys: `Shift` with the arrows, one character; with `Ctrl` or `Alt`, one word. No prefix clash, since none of these is `Ctrl` or `Alt` with a character. kitty and Ghostty on Linux take `Ctrl+Shift+←` `Ctrl+Shift+→` for tabs, which is why `Alt+Shift` also works.
  - Mouse: a click places the cursor and drops the selection; a drag anchors at the press; a double click selects a word, with the word-move classes, within the line. A drag past the edge scrolls one line per event, with no timer. `Shift`+click cannot extend a selection because terminals keep `Shift`+mouse for their own. One hook after the normal handling of a left press (`handle_mouse`) starts the drag or the word, so each dialog keeps its own click path: the press only counts when the field it landed on has the keys afterwards, which also covers a busy dialog or an open list.
  - Drawing: `Highlight` rows from our wrap, painted reversed like a pane's and the files viewer's selection, filled to the edge when the selection goes past a row's end, and only in the field that has the keys, because a field remembers its selection while unfocused but does not show it.
  - The field menu (`copy`, `cut`, `select all`) is not an `Overlay`: `Overlay::Menu` would replace the dialog that holds the field. It is a floating layer like the toast, drawn with the same menu drawing, that takes every mouse event while open, so a click outside closes only it; `Esc` closes it and any other key closes it and goes on to the field. A right press outside the selection first clicks there, through the normal left-click path, so the field gets the keys and the cursor. It opens on press, since the release is swallowed. Copy goes through `App::copy` (OSC 52 and the toast). Nothing copies on release, for the files viewer's reason: a stray drag would replace the clipboard. No paste item: the window cannot read the clipboard, and the terminal's paste replaces the selection.
  - Undo and redo are not offered (D2): `TextArea` records one step per typed character, and typing over a selection is two, so a menu item would undo one letter per click. It needs grouping first.
  - Socket: nothing. A field's selection is pointer and key state of an editor that only the TUI draws, in overlays, the TODO panel and the tour card, which AGENTS.md exempts; even the text being typed is not on the socket, a client edits through `todo`, `queue`, `flow` and `config` requests, and an external UI draws its own inputs with the platform's selection and clipboard. Precedent: the files viewer's characters (#455).
  - Touch screens (the browser window) can drag-select but have no right-click, so copy and cut are not reachable there.
- **Left out**: triple click; dragging by words after a double click; a timed edge scroll; undo, redo and word deletion (each needs a key or a button, so each asks the user first); word moves and selection in the fields without a cursor.
