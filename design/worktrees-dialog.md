# Worktrees dialog

Code: `worktrees/`, `app/worktrees_dialog.rs`, `app/worktrees_dialog/`, `ui/dialog/worktrees.rs`, #256

- **Why**: worktrees made for issues, `+ New workspace` and flows stay until someone removes them, each with its `node_modules` or `target/`. Cleaning up meant asking an agent, which does not know which branches are merged and can remove one with uncommitted or unpushed work. Nobody, person or agent, had at hand what says "this one is safe to go", so the dialog lists every worktree with that and removes several after one confirmation that names every risk.
- **A dialog, not a panel**: an `Overlay` (modal, dims what is behind), opened from the ` Worktrees ` button (every project; see Layout › The footer) or a project's menu (**worktrees**, only a repository root, titled `Worktrees › <project>`). A side panel or a mode of the changes panel was rejected: it is a task you do now and leave, and the side panels are for what stays beside the pane. The diff view of that option is the row's ` changes ` action, which closes the dialog and opens that workspace's changes panel (open projects only). It takes the settings dialog's size (`settings_area`, 140×40) and, below 90 columns, the whole screen with three-line rows. The model (`worktrees/`: `mod.rs` the list, `dialog.rs` state and keys, `discover.rs`, `scan.rs`, `remove.rs`) imports no `app` or `ui`, so the later `cornercase worktrees` command (left out: its own issue) can reuse the scan and the removal.
- **Which worktrees**: every linked worktree of every open repository project, plus those of repositories of closed projects, found by walking `worktrees_dir` two levels (`<repo>/<slug>`), reading each folder's `.git` to its common dir and listing that repository with `git worktree list --porcelain` (so its worktrees outside `worktrees_dir` show too). Prunable entries (folder gone) are listed; each is matched to its entry under `<common dir>/worktrees/` by that entry's `gitdir` file, read relative to the entry's own folder, since git 2.48 can write it as a relative path (`--relative-paths`, `worktree.useRelativePaths`). A folder there whose `.git` points at a git folder that no longer exists is an orphan (`repository gone`); one whose git folder exists but belongs to no repository (no `commondir`) is `unknown to git`, and its confirmation says `git no longer knows this folder; deletes it and its files`, since calling it `repository gone` would hide that the folder may hold uncommitted files of a repository that is still there. Both are removed by deleting the folder, and each removal checks again that the folder is still what it was listed as. A folder whose git folder is a whole repository (`--separate-git-dir`, a submodule's checkout) is not a worktree and is ignored, like a plain folder. Entries of `worktrees_dir` that are symbolic links are skipped (`DirEntry::file_type`, which does not follow them), since the discovery canonicalises paths and a linked orphan would otherwise be listed, and deleted, at its target. Never a main checkout.
- **What decides "safe"** (`scan`, one job per worktree through `App::spawn_job`, at most `SCANS_AT_ONCE` (4) at once, each given up after `SCAN_GIVE_UP` (30 s)): `last_changed` is the newest of the last commit on `HEAD` and the modification time of the files `git status` lists as changed or untracked, so ignored folders are never walked and agent activity (lost on restart) is not used; `●n` changed and untracked entries; `↑n` commits in no remote-tracking ref and not in the base (pushed means contained in some remote-tracking ref); `upstream gone`, an amber mark of its own, when the configured upstream no longer exists (the remote branch was deleted after a squash merge). Its commits still count in `↑n`, since no remote-tracking ref holds them once `git fetch --prune` has run, so with ` also delete the branch ` the red line says they would be lost from this machine: the scan cannot tell a squash merge from work never merged, and saying less would hide a real loss in the second case (the spec first wanted no red line there; the safer reading was kept). `merged`; the lock with its reason and holder; the branch checked out at that moment (`discover::branch_at`, read from the worktree's own `.git`, never from a folder above, and `None` when `HEAD` is detached). git runs through `git::worktree::git` with `--no-optional-locks` and `-c diff.autoRefreshIndex=false`, so a scan never takes `index.lock` against an agent's commit.
- **Merged is `merge-base --is-ancestor HEAD <base>`**, the base being the workspace's own for an open one, else the default branch as the changes panel resolves it; a pull request already known as merged also counts for open workspaces, so squash merges are recognised (closed projects only get the ancestor check, a known limit). A branch in its base that has no remote upstream configured (`%(upstream)` under `refs/remotes/`) and no merged pull request has no commits of its own, such as a worktree just made: it is marked `no commits`, not `merged`, and sorts with the rest. An earlier ruling counted such branches as merged, since removing them loses no commit, but it put the work just started at the top of the list as if it were done. An unborn `HEAD` fails to scan and is treated as risky.
- **Order** (decided once): prunable and orphan rows first (certainly stale), then merged ones whatever their age, then the rest; oldest `last_changed` first within each band, unknown dates last. While scans run the list shows `checking n of m…` and a stable provisional order (project, then branch), and sorts once when the last scan answers or gives up; after that rows never reorder, and removed rows disappear in place. Rows jumping under the pointer while ticking boxes was an anti-goal.
- **The list**: a filter field (a substring of project or branch; project tabs were rejected, seven would not fit and the project menu already gives one project), then per row a checkbox, project, branch, folder (cut at the start, and dropped when it would get fewer than 8 cells, the room going to the marks), age (`5 min ago`, `2h ago`, `3 days ago`) and marks (`●n`, `↑n`, `merged` or `no commits`, `upstream gone`, `locked`, the open workspace's running program (`claude`) or how many run (`2 running`), `n outside` for processes its workspace does not run, `open`, `?` for a failed scan, `prunable`, `repository gone`, `unknown to git`), dropped from the right when narrow. A failed or panicked scan leaves `?` and counts as risky, as `worktree::status` does. Rows that cannot be ticked say why: a role worktree of a live flow run (`role_owner`; it goes with the run's workspace), one already being removed or closing. The run's own workspace can be ticked, and its confirmation says the run ends and lists its role worktrees, which `start_removal` removes with it (and their branches, when asked). **Ticks on rows the filter hides are kept and removed**, since the confirmation lists every ticked row, so nothing goes unseen; ` remove n ` counts them.
- **Processes outside cornercase**: a job lists the user's processes whose cwd (`process.rs`) is inside a listed worktree and names them (`2 processes outside cornercase: node, claude`), since an agent or dev server started in another terminal would otherwise lose its folder unannounced. Only the process trees of the panes of the row's own workspace (and, for a run's role worktree, of the run's workspace) are left out, since the confirmation names those as programs that stop; a process of any other pane is named as `<program> in another cornercase tab`, because a shell in another workspace that `cd`'d into the worktree, or a dev server started there, would lose its folder just the same. Ownership is found by walking each process's ancestors (`process::parent`) to a pane's shell at the moment it is looked at, so a child started after the snapshot is still placed; cornercase's own `git` is left out the same way, and the server's plugins are reported. The map from a pid to the pane whose shell started it, the walk up its ancestors and the deepest folder holding a cwd live in `process/owners.rs`, generic over what owns a pane (here the rows of its workspace), so other views that place processes in workspaces (the ports of #496, the processes view of #486) share them. The check runs again for every confirmation, even one with only orphans or prunable entries ticked, which have nothing else to rescan. A process whose cwd cannot be read is ignored; a failed or given-up process scan is named in the confirmation rather than hiding them.
- **The confirmation is a second step of the same overlay**, and it scans the ticked worktrees again (and the outside processes) before ` remove ` is enabled, showing `checking…`: the list's scan may be minutes old, and what was written meanwhile must be named. A rescan drops the answer of any older list scan of the same path, so a late answer never overwrites the fresh one, but that scan still counts against `SCANS_AT_ONCE` until it answers or is given up on, so a rescan never runs more git at once. A prunable entry with a branch gets its branch counted again (`git rev-list --count <branch> --not --remotes [<base>]` in the repository), since it has no folder to scan and its commits would otherwise go unnamed. It lists per worktree, before anything stops, uncommitted files, unpushed commits, `upstream gone`, the lock with reason and holder, shells and agents that stop, a teardown that will run, an orphan folder to delete or a prunable entry to clean, or `nothing uncommitted or unpushed`; risky ones in yellow. The body wraps in the app by display width (`confirm::wrap`), so the scroll limit, the `↓ scroll for more` hint and the drawing agree. ` also delete the branch ` is off by default; ticked, the branches that are neither merged nor pushed are named in red as losing their commits, each role worktree's line names its branch, and a worktree with no branch checked out says none is deleted. `Esc` or ` back ` returns to the list with the ticks kept. Nothing is removed, and no shell stopped, before ` remove ` in the confirmation (a test pins it).
- **Removal**: an open workspace goes through `App::start_removal(.., force, unlock)` as a single removal does (shells stop, teardown, `git worktree remove --force`, unlock when locked), recorded in `Cleanup::pending`; a closed project's worktree through `worktrees::remove` on a job with the project's teardown from `config.json` when it has one (the `remove_with_teardown` shared with the single removal in `git::worktree`, extracted rather than copied); a prunable entry by deleting only its admin folder under `<common dir>/worktrees/` after checking it is prunable and its `gitdir` target is still gone (`git worktree prune` would prune every prunable entry of the repository, which the user did not tick); an orphan by deleting the folder. Only rows still tickable at that moment are removed, re-read live. Several run at once; a role worktree ticked together with its run's workspace is removed once, with the run, and paths are deduplicated before anything starts. Branches are deleted after the worktree is gone with `git branch -D` through `delete_branch`, only when asked, never the default branch or the main checkout's, and git's refusal goes into the summary. The branch deleted is exactly the one the confirmation showed: when ` remove ` is pressed, the branch checked out now (`discover::checked_out`, from the worktree's `.git`, or from its admin folder for a prunable entry) must still be it, else it is kept and the summary says `kept the branch X: it changed since the confirmation`; a detached `HEAD` deletes nothing, and a commit id is never passed to `delete_branch` (`git::branch` would give one, and it walks up to the folders above). One toast at the end (`removed 4 worktrees and 3 branches`, counting a run's role worktrees, then kept branches and failures named, `see server.log` when something failed). Logs hold paths, branches and counts.
- **Calls made on the way** (the spec's list): orphans are listed and removable; a known merged pull request counts for open workspaces; the order is fixed until every scan answers; a filter field and no tabs; four scans at a time; role worktrees of a live run are not selectable but the run's workspace is; closed-project removal runs the project's teardown; the simulation's entries only say they need a real cornercase; the confirmation rescans; pushed means in some remote-tracking ref; outside processes are found by cwd and named.
- **Left out**: removing automatically (after a merge or N days), keyboard shortcuts and keys-menu entries, and a per-row diff inside the dialog.
- **External clients**: the list, its marks and the removal are not requests yet. Exposing them (a `worktrees` request answering the rows with their marks, and one that removes the chosen ones after the same rescan) is a job of its own, left to an issue as AGENTS.md allows; until then a script uses `git worktree list` and `cornercase close --remove-worktree`.
