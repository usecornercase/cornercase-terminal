# Stats

Code: `agents/stats.rs`, `agents/known.rs`, `app/agent_watch.rs`, `app/usage_dialog.rs`, `agents/stats/sum.rs`, `app/control/stats.rs`, `cli/stats.rs`

- Per-agent arrays use the position in `Known::ALL`, whose names and order are pinned by a test. New variants go last. PR 2 leaves the four-entry schema and serialization unchanged; accepting other lengths belongs to PR 4.

- Counts begin with this feature and only for Claude Code, Codex, Gemini CLI, opencode, Grok Build, Cursor CLI and GitHub Copilot CLI in this server's panes (Cursor has no token counts, see Context use). No histories are imported. Grok Build, Cursor CLI and GitHub Copilot CLI are last in `Known::ALL`, so a stats file written before them still loads (the arrays pad). Copilot's tokens come from every `session.usage_record`, counted once by event `id`: `inputTokens` includes what the cache served (live: a provider answering `prompt_tokens` 12345 with 2000 cached gave `inputTokens` 12345 and `cacheReadTokens` 2000), so input is `inputTokens - cacheReadTokens - cacheWriteTokens`, output is `outputTokens` (`reasoningTokens` is part of it), plus the cache read and write; sub-agent records count too. Its prompts are the `user.message` rule of Context use and its turns and time follow the shared activity rules. `Stats` takes wall times and durations, with fixed times in its unit tests; `App::watch_agents` supplies the wall clock and the `Instant` delta. A start is a changed `(kind, foreground pid)` in a pane, suppressed while the pane is automatically resuming. Start identity is kept separately from the previous activity sample, as one last `(kind, pid)` per pane. An absence does not clear it: Claude's foreground editor must not count as another start when Claude returns. A different pair replaces it, so reused pids following another agent count. Closing panes has no dedicated counting lifecycle; retaining a small numeric entry per pane opened is simpler than adding one. The context pane remembers the first observation even before its record exists. Manual resumes start a process and count. Working excludes `Activity::Shell`, as keeping awake does. A turn counts working or waiting → idle, done or shell; one that leaves subagents running ends when the last of them does, and their time counts as working time (see Agent status). Waiting and unseen done accumulate `Status::needs_you` time.
- Intervals belong to the previous sample's state, ending at the new read: finishing must not discard the final half second of work, and entering a waiting state must not charge that preceding work to waiting. No duration is charged on first observation or across a changed process. Each interval is capped at two seconds. Integer milliseconds preserve the half-second samples without float drift; command JSON reports fractional seconds, while share links floor seconds. Busy time is global time with any matching previous sample working; removed or replaced processes cannot extend it, keeping busy time within summed agent time; peak parallelism is a maximum of current working samples. The three windows are current epoch hour plus 23 or 167 preceding hours, and a separate lifetime total. Records use their own timestamp's hour; samples use the read's wall-clock hour. Per-kind counters hold starts, prompts, turns, working/waiting milliseconds and four token kinds; busy time and peak are global.
- `agents/context/counting.rs::Ledger` keeps each conversation's prompt high-water time and recent ids, reply high-water time and last maximum token values per id, bounded to 512 of each. It stays in the context pane across conversation switches, `/clear`, `/resume`, truncation and replacement, and is reset only when the agent process changes. Full id maps are retained for only the 16 conversations most recently used by nonempty record batches. Older conversations keep only prompt/reply cutoff times and a cumulative time/token baseline; returning seeds these cutoffs, so old records cannot count again. This bounds expensive id storage while preserving counting once across arbitrarily many conversation switches; compact numeric cutoffs remain until the process exits. Evicted records older than the high-water time cannot be counted again. An eviction also records a cutoff that excludes unknown ids at that same timestamp: with more than 512 ids sharing one instant, preferring an undercount to a replay double count keeps bounded memory and the counting-once guarantee. Records without a parseable time, and those before first observing the process, contribute nothing. Confirmation retains its existing permissive rule for missing times. Claude's shell input is excluded from stats while it can still confirm a send. Typed slash commands count, but enqueue records only confirm a send. Claude Code records a queued human prompt either as an absorbed `attachment` (`queued_command`, `commandMode: prompt`, `origin.kind: human`) or, after dequeue, a human `user` record. Stats counts those final records by their uuid and timestamp, never the enqueue, task notifications or peer origins. The synthetic queued-prompts fixture covers both paths, each once. Confirmation and counting use the same parsed JSON value, keeping their different rules explicit. A substring gate before parsing accepts usage, origin, queued-command attachments, queue operations, slash commands, shell input and compact boundaries. Ordinary tool results, inputs without usage and metadata skip JSON allocation, including on a resumed pane's initial MiB. The subagent job uses the same gate; the context marker also skips assistant lines without usage.
- Every reader produces only timestamp/id/numeric observations during its existing pass. Gemini and opencode still do their reading on their existing background jobs. Claude now shares Codex and Gemini's bounded `jsonl::Tail`, keeping deletion and truncation behavior; its subagent files use the same tail on one background job per pane, so enumerating or reading many Task transcripts cannot block the server loop. Claude main and subagent transcripts keep separate conversation ledgers. The subagent directory is re-listed only when its modification time or path changes. A transcript modified before the pane began starts at EOF, including skipping any old partial line, so a resumed conversation does not read a MiB of every old Task file; subsequent complete appended records still count. Subagents and old `isSidechain` records add tokens only, never prompts or sampled activity. These transient ids and paths never enter `stats.json`, a share link or the stats log.
- Token semantics were checked against installed Claude Code 2.1.296, Gemini CLI 0.63.0 and opencode 1.18.35 sources, and read-only numeric record shapes. Claude repeats the same usage per `message.id` across content blocks and writes Task transcripts under `projects/<dir>/<sessionId>/subagents/agent-*.jsonl`; each id contributes only positive changes. Its output already includes thinking. Codex counts cumulative `total_token_usage` differences, with `last_token_usage` only when no preceding baseline was read. Repeats add zero; a lower total starts a new baseline. Input excludes cached input; output includes reasoning. opencode's installed accounting subtracts `reasoningTokens` from stored `tokens.output` (and its newer usage object exposes `visibleOutputTokens` with the same subtraction): add stored output and reasoning. Count a completed id only once, at `time.completed`. Its numeric records also showed total = input + output + reasoning + cache kinds. Subagent sessions remain excluded.
- Gemini's installed `recordMessageTokens` maps `input` to `promptTokenCount`, `cached` to `cachedContentTokenCount`, `output` to `candidatesTokenCount`, `thoughts` to `thoughtsTokenCount`, and `tool` to `toolUsePromptTokenCount`. Cached input is part of input: inspected numeric records had total = input + output + thoughts, with substantial cached values, and [the API's usage definition](https://googleapis.github.io/js-genai/release_docs/interfaces/types.UsageMetadata.html) describes cached content as part of the prompt. `tool` is separate API tool-use prompt usage, not generated output or the CLI's local function-response text. It is omitted in v1 as specified: no extra invented input category. A rewritten reply adds only increases over its last values; a `$set.messages` restore retains deduplication state and cannot add old history. Synthetic versioned fixtures record these shapes without copying conversation text.
- `stats.json` lives next to `session.json`, including private instances selected by `CORNERCASE_SOCKET`. Version 1 is compact JSON: `since` in Unix seconds, a separate total, and sparse `hours` arrays `[epoch_hour, [claude, codex, gemini, opencode], busy_ms, most_at_once]`. Each agent's array is `[agents, prompts, turns, agent_ms, waited_ms, input, output, cache_read, cache_write]`. The total uses named counters for inspection; hours use arrays to keep months of data small. Keep 26 weeks and one day, pruning only when the epoch hour changes; snapshots also filter retention. Missing, corrupt or unknown versions begin empty. The per-agent arrays hold `Known::ALL.len()` entries (`Bucket::by_agent` and the hours' lists): reading pads a shorter list with zeros and ignores entries past the last known agent, while writing is unchanged and `version` stays 1, so adding an agent last in `Known::ALL` never makes serde reject the file and start over empty. Tests cover a file with every agent written back byte for byte, one with an agent fewer and one with an agent more. Every numeric mutation increments `Stats::revision`. `agents::stats::Saver` observes only that number until a minute has passed from the first dirty instant, then builds one `Saved` directly for writing; it keeps no cloned saved or pending buckets. Shutdown and restart flush the current changed revision. This removes full-map serialization, comparison and cloning from the half-second server save steps. Shared `persist::write` atomically renames a temporary file, writes compact private files at 0600 and syncs them; secrets reuse it too. The ordinary session and TODO savers retain their quiet-time policy.
- Usage opens on Stats and remembers its page only for the server run. Limits probes run only when that tab shows, including reopening there. The tab row reuses settings' geometry and drawing. Tab, BackTab and horizontal arrows switch pages; the simulation's client routes Tab and Shift+Tab to Usage instead of letting browser focus take them; Enter, Esc, done and a press outside close the dialog. Height is the larger of the limits body and the actual stats lines at the dialog width, plus tabs and buttons, clipped to the screen while keeping done. Stats ends with one blank line separating its content from share/done, including the empty state, as in Limits and other dialogs. Computing height from the same lines used for drawing removes the three unused wide rows while accounting for wrapped phone headlines and legends. Below 49 screen columns the dialog takes the full width, with the usual one-cell padding inside each border, leaving 42 text columns at 46 columns. Labels of 18 and three seven-column values then have explicit one-column gaps, so full durations cannot run together. Narrow legends wrap to a second line. Shared stats number formats drive the dialog and plain command output; counts below 10000 stay whole, larger thousands keep one decimal, tokens use k/M/B, and durations use minutes or hours/minutes.
- Heatmap blocks are the preceding 24-hour buckets from the current hour, newest at the bottom right, up to 26 seven-block columns. They are rolling blocks, not weekdays. The quartile boundaries are the nearest-rank 25th, 50th and 75th percentiles of positive displayed blocks; ties share their level. Every one of the 182 blocks is drawn, in the dialog, `cornercase stats` and the card: a block with no agent time takes the line colour, also before counting began. Those used to be blank, so a server counting for a day showed two loose squares in an empty frame instead of a grid with two days lit, which read as broken; a block before `since` holds no work, which is what grey says, and `counting for n days` says how long the numbers go back. The share map carries the blocks that overlap the counting period, the first incomplete day and the block containing `since` included, so `min(days + 1, 182)` levels, while `days` remains whole counting days; the page draws the rest as zeros. This deliberately changes the issue's `min(days, 182)` contract: hiding the first day and the oldest partial block omitted work already included in the counters. Rust, the strict site parser and the shared fixture enforce the revised contract. `days` reads `1 day` in the singular. Dark blues are 24, 26, 33, 75, getting brighter level by level; light blues are 153, 75, 27, 19, ending darker so the maximum remains visible. They were purples ending in the old brand purple until the brand turned blue. Snapshots cover both. The site's term renderer draws U+25A0 as a snapped square with equal sides, independent of font fallback.
- `cornercase stats` requests live memory without starting a server; with none running, it loads the file. JSON includes every window counter and every kind, plus 182 blocks newest first. Text uses the same formatting and `·░▒▓█`, written through the existing closed-pipe-safe output function. Unknown-command refusals retain the normal old-server behavior. `--share` and the Stats share pill use the same pure link builder; the pill copies with OSC 52 and a toast only after something was counted.
- Sharing is opt-in copying, never uploading. The constant URL is `https://usecornercase.dev/stats/#v2`; fields are `24h`, `7d`, `all` (agents, prompts, whole agent seconds, whole busy seconds, peak, output tokens, turns, whole waited seconds, input tokens as the dialog's `tokens in` counts them (uncached input plus cache writes), cache reads), whole counting `days`, and `map`. The card shows the Stats tab's nine rows in its order (`ROWS` in `model.ts`, which the simulation's table also uses) for the window picked on the page; v1 carried only the first six numbers, and a card with five of the dialog's nine rows looked like something was missing. v2 appends the four rather than reordering, so v1 is its prefix: a v1 link, made by 0.12.36 to 0.12.85, still parses and draws the five rows it holds, while each version must carry exactly its count of numbers. v3 (#293) appends an eleventh number, the merged pull requests (see Merged pull requests), and is made only when that count is complete, so the card has 9 or 10 rows; the simulation's `EXAMPLE` carries the eleventh number. Pack three bits per level, newest first, most significant bit first within each byte; unused trailing bits are zero. Base64url has no padding. The shared fixture contains an exact link, its windows and nonzero levels, checked by Rust and the site. Agent breakdowns, models, project names and paths are omitted. Anyone with the link sees its numbers.
- `/stats/` is an English static page, with no analytics or third-party script. Its strict whole-fragment expression, 1024-character cap (thirty numbers of up to sixteen digits fit), safe integer checks, exact decoded map size, legal levels, canonical base64url and zero trailing bits reject crafted links before drawing. No text goes through HTML. CSP permits only self scripts/styles/fonts, self/blob/data images and no network connections. The fragment never reaches the host. No fragment shows an explicitly marked example. The default card window is seven days, with tabs for 24 h and total. The card is a ticket (next bullet). Font loading completes before drawing. Every stats-page mount gets a generation number: font and mask awaits, drawing and action callbacks discard stale generations so a slow old fragment cannot overwrite the current ticket, handlers or status. File-share support is probed with an empty PNG-typed File only when the share button exists; the PNG is rendered and encoded on click, keeping initial mounts free of needless image encoding. PNG download, supported clipboard and file sharing run entirely in the browser. Intent links carry the public share URL; the written post text is visible for copying, and the page tells users to attach the PNG because crawlers cannot read fragments. `stats-og.png` is a 1200×630 example: the same render with `?preview`, whose stage is 630 high.
- **Every machine's stats** (#547, `agents/stats/sum.rs`, `app/control/stats.rs`, `cli/stats.rs`): `stats` takes `machine`, a machine's name or `all` (see Commands for scripts and agents › Every machine's stats and usage; asking a machine is Remote windows › Asking a machine). A name answers that machine's `View` plus `machine` (`name`, `state`, `seen`, `read_at`, `error`); `all` answers the sum of this computer's and every machine's, plus `machines[]` in `config.json`'s order. A machine is in the sum if and only if it has `read_at`, so no `summed` flag was added; a link that is this computer, or the same server as another, is never summed.
  - **The sum** (`View::sum`): windows and `by_agent` add up field by field, which is the same as adding hour by hour, since every server's windows are whole epoch hours; no hourly data had to travel. The blocks add their seconds and the levels come again from the sum, with the local rule. `since` is the oldest and `days` counts from it; `empty` only when every view is.
  - **The peak is the largest**, not a sum: whether two machines' peaks fell in the same hour is not known. The largest peak per hour, taken over a window, is also the largest of each machine's peak over that window, so `most_at_once` needs nothing more. Whatever shows the sum says so: the text of `stats --machine all` has a line above `summed from:`, and the Usage dialog's machine picker, still to come under #547, says `largest peak of one machine, not a sum`.
  - **Busy time is added up**, as the issue asks: it is machine-hours, not the union of wall time, so `× in parallel` under `all` is the summed agent time over the summed busy time.
  - **Merged pull requests are never added**: the same GitHub account's pull requests would count twice. The row is kept only when every machine that gives one lists the same accounts (`provider`, `host`, `login`, in any order, errors aside), and then it is this computer's; otherwise it is left out.
  - **`empty` and `days` do not travel** (`serde(skip)`), so a view read from a machine gets them again when it is read (`View::settled`): empty when its `total` window has no agent and no agent seconds and no block has seconds. That is close to the local rule (a `total` equal to an empty one) without giving `Window` an equality for it.
  - **A copy read days ago**: a machine that is down is summed from the copy it gave last. Its blocks are moved on by the whole days since it was read (`View::moved_on`), the oldest dropped and the newest left at zero, so its last day lands on its day in the heatmap rather than on today; within a day, nothing moves. Its `24h` and `7d` windows count as they were read, since a copy holds no hours to move them by: a machine down for three days still adds its last 24 hours to `24h`. Its line says when it was read. Leaving such a copy out of the windows was rejected: `total` would still hold it, and a window that drops a machine while the others keep it is harder to read than an old copy that says its age.
  - **Clocks**: each machine's windows are relative to its own clock, so a machine whose clock is off across an hour's edge has its windows shifted by an hour. Accepted.
  - Nothing of another machine is written to `stats.json`: its numbers live in this server's memory (Remote windows › Asking a machine), so `cornercase stats --machine` needs a server, with no fallback to the file. Its text puts the machine's line (its state's mark, its name, `read 4 min ago` or its error) above the view, and under `all` ends with `summed from:` and a line per machine, `not summed` on those left out; `--share` prints the link of what was asked. It exits 0 when a machine is missing from the sum, which its line says, unlike `usage --machine`, which exits 3.
- **The card is a ticket that moves** (`site/src/lib/stats/`: `ticket.ts` what it says, `face.ts` drawing it, `sheen.ts` the foil and the light, `pose.ts` the 3D matrices, `stage.ts` the PNG, `tilt.ts` the live page): the first card was a flat picture of the Stats tab's terminal box, and it was asked to be more visual, in 3D and moving, like the conference tickets people post. The face is drawn once on a canvas at 2×, 1000×520: the logo; the window in a pill, which also says `EXAMPLE` (in yellow) on the example and the link previews; the parallel factor as the hero, shrunk to fit beside `in parallel` and the agent and busy times, or `no agent work` below a minute of busy time; the Stats tab's rows in its order, five to a line, their columns sized by their widest label or value, values shrinking before columns meet; the counting days. Past a perforation with two notches, the stub holds the 182 heatmap blocks as 7 columns by 26 rows of weeks, oldest at the top, so the newest block stays at the bottom right as in the app and the blocks read like text, with a caption on its edge instead of a legend, and the address. The ramp is the ticket's own (dark violet to light lavender, the top level glowing), not the terminal's palette indices, since nothing here is a terminal.
  - **One matrix, two renderers**: a pose (rotations, lift, scale) and the light give one 4×4 matrix with CSS's conventions (`rotateX`, `rotateY`, `rotateZ`, `perspective`; `css` in `pose.ts` writes it as `matrix3d`). The page sets it on the ticket, its halo and its shadow inside a 1200×675 stage scaled to the column; the PNG projects the same face through the same matrix as a 40×20 mesh of affine triangles, each grown half a pixel against seams. So the ticket at rest on the page is the PNG, and a test checks that the matrix CSS gets is the one the canvas draws with. WebGL was rejected for the PNG, since a context can be missing or blocked by privacy settings while the mesh is exact enough at this distance; one affine transform (no foreshortening) made the ticket read as skewed rather than tilted.
  - **Foil**: two layers masked to what is printed in foil, the masks being canvases turned into blob URLs (CSP allows blob images): `iris` on the hero, multiplied over its white-to-lavender fill with the brand's colours, since a colour dodge on white text only gives white; and `edge` on the border and the pill, a colour dodge of the full rainbow. Their gradients repeat every 520 pixels, so each layer is the ticket plus one period, moved with `transform` only; the light sets the phase. The canvas rebuilds CSS's gradient line and repetition, so the page and the PNG agree. A soft-light spot and streak follow the light.
  - **Motion**: a mouse or a pen over the stage presses the side under it away and brings the light there, and so does a touch drag (`touch-action: pan-y` keeps vertical scrolling); otherwise the ticket drifts slowly around its rest pose. A spring follows the targets. Frames run only while the stage is on screen, and `prefers-reduced-motion` gets the rest pose, still. The PNG is always the rest pose with the light at rest, 2400×1350.
  - Left for later: a video of the ticket moving (MediaRecorder gives MP4 only in some browsers, and X refuses WebM), a name on the ticket (the link carries none, and adding one is a new link version), and tilting by the phone's gyroscope (iOS asks a permission for it).
