# Layout › Side panels, folding, scrolling and the active row

Part of [Layout](../layout.md).

- **Side panels**: the changes, files, TODO and Flow panels share the column right of the pane (`Areas::changes`, `Widths::changes`, `Border::Changes`), one at a time (`App::side`). An open file can take the whole window instead (see Files panel). Flow (#263) shows only while the active workspace has a run (`App::panel_shown`), so a workspace without one gets the pane's width back and returning shows it again. It has no footer button or compact bar slot, since it exists only while a run does: it opens from the run workspace's menu (**show flow**), `w f`, the icon bar's Flow slot, and when a run starts from the window. Its flag is saved beside `todo` and `files` and applied after the runs are restored, so it opens only when the active workspace still has one.
- **Folding** (`Project::collapsed`, `Workspace::collapsed`, saved in the session; `App::set_collapsed` sets them for a click and for the `collapse` and `expand` requests; the tree draws both, the workspaces list draws the workspaces', #294): new projects and workspaces start unfolded. `follow` unfolds the active project and workspace, and in the tree its group, when the focus changes; a click on a row and `goto` (search) do too, for when the focus stays the same. Other layouts leave a collapsed group alone, as before. The first follow after a restore (`followed` still default) unfolds nothing, so saved folds survive. The workspaces list (side by side, stacked, compact) draws `Workspace::collapsed` with the tree's arrow, `▾`/`▸`, in the row's lead (`[▌, arrow]`, 4 cells; the name moved from 2 to 4 cells, level with the tab icons, as in the tree), always visible rather than on hover, since a click that folds should be findable and touch screens have no hover. The whole lead, the row's full height, is the target (`ui::workspaces::fold_button`, shared by drawing and hit testing; `WorkspaceHit::Fold` grabs the row with `fold: true`, so a drag from the arrow still reorders). One flag serves both views, so a fold made in the tree shows in the list. A folded workspace lists no tabs and no `+ Tab` (`TabLines::folded`, read by drawing, hit testing, drops and `follow` through `workspace_rows`); its shells keep running. With `tabs` on top there is nothing to fold: the lead keeps a blank 2-cell slot and folds are ignored there. A folded active workspace takes the surface and the `▌`, since its active tab row is hidden (the tree's nearest shown ancestor rule, only for folded rows); no `│` hangs under it. The memory gate skips a collapsed workspace's tabs in the lists too.
- Lists scroll by item with the wheel, show ` ↑ n more` / ` ↓ n more`, and keep the `+` button sticky at the bottom. The scroll follows the active item only when it changes (`App::follow`), otherwise the wheel could never move away from it.
- The active row (project, tab, a collapsed group holding the active project, the tree's marked row) gets a surface background (palette 236, or 254 on light themes) and a cyan `▌` in the column's first cell over the row's full height (a tab's second line, a compact band), so every list shares one selection rail on the left edge. `draw_rail` and the tree lines only draw on blank cells, so text pushed left in a narrow column wins over them. Colours use palette indices so they work without truecolor; the brand blue is index 27 (`#005fff` in the xterm cube, the website's cobalt), merged pull requests keep index 99 (see Pull requests).
