# Layout › Stacked sidebar and tree

Part of [Layout](../layout.md).

- **Stacked sidebar** (`projects_on_top`, `workspaces_on_top`): one column of `Widths::projects` holds both lists, split by a line that drags (`Border::Stack`; `Widths::stack` = rows of the top section, `None` = half, each section at least `MIN_STACK_SECTION`), with one footer anchored at the bottom (issues and changes, files and todo, settings, usage, quit). `stacked_layout` fills the same `Areas`, so drawing and hit testing are shared; `Areas::sidebar` and `Areas::workspaces` are the two sections, so the wheel scrolls the list under it. Column borders are drawn from their `Areas` rects, not from `Block`s, so a stacked column gets one full-height border.
- **Tree** (`tree`): one column on the same frame and footer as the stacked layouts (`ui::layout::one_column`, `ui::layout::tree_layout`, `Areas::tree`) with one list, `ui::TreeRow` rows from a plain `ui::TreeShape` that `App::tree_shape` builds and `View::tree` carries: group headers, projects, for an unfolded project its workspaces and a `+ New` row (the workspaces' menu, see Hierarchy), for an unfolded workspace its tabs and `+ Tab`; `+ New` is also the sticky button, the projects' one. Content starts at `2 + 2·depth`. The arrow (`▾`/`▸`, two cells) folds a project or workspace on release (`RowDrag::fold`, so rows still drag); the rest of the row activates it and unfolds it; a group header folds anywhere, as elsewhere. One row holds the `▌` and the surface: the active tab, else its nearest shown ancestor (`ui::tree_active_row`); the active project and workspace are bold white. Folded projects show counts and `agents::activity::attention`; a folded workspace shows `agents::activity::highest` (see Agent status); open ones leave it to their tabs. `+ Tab` under another project switches to it; a project's `+ New` row acts for that project without switching (its menu, the form and the start dialog carry its id, and switching behind a form the user may cancel would change the pane). Drops follow the other lists' rules on one row list (`ui::tree_drop`): the row under the pointer counts as its owner at the dragged row's level, a project lands after a whole project block, workspaces and tabs stay in their parent; the landing line takes the dragged level's indent. The App learns the tree is on from `Areas::tree`, never from the config (below 90 columns the layout is compact whatever the setting), and keeps the last drawn layout in `App::drawn` (its `Areas::tree`), so `follow` reveals the active row again when the layout changes. `View::tree` labels only what is unfolded: a tab's label looks up processes and a workspace's reads `.git/HEAD`.
