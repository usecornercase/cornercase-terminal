# Design decisions

Why cornercase works the way it does, area by area. The rules every change follows are in [AGENTS.md](AGENTS.md).

## Layout (`ui.rs`)

- `sidebar` in `config.json` lays out the lists (wide mode only; below 90 columns the compact menu below applies to every value): `projects_on_top` (the default since 0.9.0, `ui::Sidebar`'s `#[default]`, so unknown values fall back to it), `workspaces_on_top`, `side_by_side` and `tree`. One column was made the default because it gives the panes the most room; a `config.json` that names `side_by_side` keeps it (settings save the whole file, so anyone who changed any setting before 0.9.0 keeps three columns). App tests pin `side_by_side` in `new_app`, since their geometry helpers assume it; `tests/e2e.rs` lays out its geometry with `Sidebar::default()`, so e2e covers the shipped default.
- Side by side: projects (32), workspaces (26), pane (after one blank column). Columns are always present so PTY sizes do not jump. Borders drag to resize (double click resets), within `MIN_COLUMN_WIDTH` and `MIN_PANE_WIDTH`; `Widths::fit` squeezes them on small terminals. Widths are saved in the session. PTYs follow the drag live.
- **Stacked sidebar** (`projects_on_top`, `workspaces_on_top`): one column of `Widths::projects` holds both lists, split by a line that drags (`Border::Stack`; `Widths::stack` = rows of the top section, `None` = half, each section at least `MIN_STACK_SECTION`), with one footer anchored at the bottom (issues and changes, files and todo, settings, usage, quit). `stacked_layout` fills the same `Areas`, so drawing and hit testing are shared; `Areas::sidebar` and `Areas::workspaces` are the two sections, so the wheel scrolls the list under it. Column borders are drawn from their `Areas` rects, not from `Block`s, so a stacked column gets one full-height border.
- **Tree** (`tree`): one column on the same frame and footer as the stacked layouts (`ui::one_column`, `ui::tree_layout`, `Areas::tree`) with one list, `ui::TreeRow` rows from a plain `ui::TreeShape` that `App::tree_shape` builds and `View::tree` carries: group headers, projects, for an unfolded project its workspaces and `+ New workspace`, for an unfolded workspace its tabs and `+ Tab`; `+ New` is the sticky button. Content starts at `2 + 2·depth`. The arrow (`▾`/`▸`, two cells) folds a project or workspace on release (`RowDrag::fold`, so rows still drag); the rest of the row activates it and unfolds it; a group header folds anywhere, as elsewhere. One row holds the `▌` and the surface: the active tab, else its nearest shown ancestor (`ui::tree_active_row`); the active project and workspace are bold white. Folded rows show counts and `activity::attention`; open ones leave it to their tabs. `+ Tab` under another project switches to it; `+ New workspace` asks for that project without switching (the form carries its id, and switching behind a form the user may cancel would change the pane). Drops follow the other lists' rules on one row list (`ui::tree_drop`): the row under the pointer counts as its owner at the dragged row's level, a project lands after a whole project block, workspaces and tabs stay in their parent; the landing line takes the dragged level's indent. The App learns the tree is on from `Areas::tree`, never from the config (below 90 columns the layout is compact whatever the setting), and keeps the last drawn layout in `App::drawn` (its `Areas::tree`), so `follow` reveals the active row again when the layout changes. `View::tree` labels only what is unfolded: a tab's label looks up processes and a workspace's reads `.git/HEAD`.
- **Agents section** (`agents_section` in `config.json`, Settings → UI, off by default): one list of every pane running Claude Code, Codex or opencode, in every project, at the bottom of the sidebar, so an agent that needs you is one click away whatever project is shown; the status icons on project rows said that something needed you, not which agent, and finding it meant three clicks. Off by default so the sidebar of someone who runs no agents stays as it was; off, every layout is drawn exactly as before (the existing snapshots did not change). `ui::full_layout` takes the switch (`layout_with` is the same without it, for the callers that never show it). It sits below the lists and above the footer, after a line that drags (`Border::Agents`; `Widths::agents` = its rows, title included, saved in the session; `None` = a third of the room; at least `MIN_STACK_SECTION`, and the lists keep theirs: `ui::split_agents` with a `keep` of one section for side by side and the tree, two and their line when stacked). In side by side it takes the bottom of the projects column; in the one-column layouts `ui::one_column` cuts it off the room above the footer, so stacked and tree share it, and `Widths::stacked_dragged` takes the switch so the stack line stops at the section. The drag stores what the layout made of the pointer (`App::agents_dragged` lays out again with the wanted rows and keeps the height it got), so every layout clamps it the same way. Rows (`ui::AgentEntry`, `ui::agent_rows`: two lines each, `pitch.max(2)`, no sticky button, scrolled by item like the other lists) are in sidebar order (`App::agent_places`: projects as `sidebar_rows` orders them with every group open, then workspaces, tabs and panes), not most urgent first: rows that move are hard to click, and the icon already says which one waits. One row per pane, so a click focuses that pane in a split tab. The first line is the status icon and `project › workspace` (the workspace only when the project has more than one, `› default` says nothing); the second is the agent's kind, then the model and the context percentage as the tab line shows them (the same `model` and `context` switches; `ui::draw_details` takes the kind as a lead that is never cut). Memory is left out: it is only measured for panes on screen (see Memory), and widening that gate would run a thread every 2 s per agent off screen. A narrow column cuts the model first, then drops it, then drops the workspace (kept while 4 cells of it fit), then cuts the project; the icon stays. The pane in focus gets the surface and the `▌`. A press grabs the row (`Grab::Agent`), a release on it jumps (`App::jump_to_pane`: `goto`, which unfolds in the tree and closes the compact menu, then `Tab::focus`); there is no drag to reorder, since the order is computed. No agents shows `no agents running` rather than hiding the section, so the lists do not jump when the first agent starts. Only Claude Code, Codex and opencode are listed (a pane with an `activity::Pane` status): another agent has no status to show.
- **Row menus** (` ⋯ `, `ui::row_menu_button`): every group, project, workspace and tab row has a ` ⋯ ` just left of its `×` (never right of it), shown and lit like the `×` (on hover in wide mode, cyan instead of red; always, dimmed, in compact mode), that opens on press the menu a right-click opens there, anchored at the pointer (`SidebarHit::Menu`, `GroupMenu`, `WorkspaceHit::WorkspaceMenu`, `TabMenu`, `TreeHit::Menu`, all handled by the same `open_*_menu` as the right-click). The menus were only behind the right button, which nothing on screen hinted at. Three dots rather than a gear: a gear says settings, three dots say more actions for this item, the convention of the sidebars it resembles (Notion, Linear, GitHub), and `⚙` is an emoji some fonts draw two cells wide. Its column (2 cells, 4 in compact mode) is reserved in `Band::room` like the `×`'s, so hovering never reflows a row and never hides its status icon or `↓n`; names lose 2 cells. Rows narrower than `MIN_MENU_ROW_WIDTH` (20) get no ` ⋯ ` and keep those cells, since a 16-column list needs them for the names and the right-click still opens the menu. A workspace being removed shows neither.
- **Counts** (`counts` in `config.json`, Settings → UI, on by default): a project row ends with its number of workspaces, `(n)`, and a folded group with its number of projects; off, neither shows (`View::counts`), for those who find the numbers noise. One switch for both, since they read the same.
- **Tabs above the pane** (`tabs` in `config.json`, Settings → UI: `sidebar`, the default, or `top`; `ui::Tabs`; #119): with `top`, the active workspace's tabs leave the sidebar for a bar of `tab_bar::HEIGHT` (2) rows on top of the pane (`Areas::tab_bar`, cut off `Areas::pane` by `Areas::with_tab_bar`, which `App::layout` and `ui::draw` both apply, so the PTYs are sized without it). Tabs in the sidebar only mattered for the workspace on screen, yet took a row each (two with the details line) plus `+ Tab`, pushing projects and workspaces off the list. `sidebar` is the default so nobody's layout changes on update. The first row is the tabs (`tab_bar::Strip`: status icon, name cut at 24, a split tab's muted `+n` as on its row (`TabEntry::others`), then a ` ⋯ ` and a ` × ` whose cells are always reserved and that show on hover, lit like the rows' (`Strip::menu`, `Strip::close`; `ui::row_menu_button` is not reused, since it leaves out rows under `MIN_MENU_ROW_WIDTH` and a tab is usually narrower), ` + ` after them), the active one on the surface and bold; the second is the details of the focused pane (`App::tab_bar_view`, not the tab's: in a split it follows the pane you are in; a shell pane shows only its memory, and nothing with the memory off), in the muted grey, with the same `model`/`context`/`memory` switches. A path there for shells was rejected: the prompt already shows the folder. Both rows are always there, even with one tab or a shell, so switching tabs never resizes the PTYs. Too many tabs reserve ` ‹ ` / ` › ` at the ends (` + ` goes to the right edge); they and the wheel scroll by one tab, `follow` brings the active tab into view when the focus changes (and starts over at the first tab when the workspace changes), and a drag held on an arrow scrolls like `↑ n more`. A press grabs a tab as a `Target::Tab` row (`RowDrag`), so click, drag and `Esc` work as in the lists; the landing (`Strip::drop`) is a cyan `│` between tabs (`ui::Drag::Bar`), and the drop goes through `move_before` like `Spot::Tab`. The sidebar learns the tabs are elsewhere from `Areas::tab_bar` (`App::drawn`, as with the tree): `ui::TabLines::new(lines, listed)` leaves out tab rows and `+ Tab` from the workspaces list, and `TreeShape::tab_bar` ends the tree at workspaces, which lose their fold arrow (nothing to fold) and show `activity::attention` like folded ones. Compact mode ignores the setting: its bar already names the tab and its menu keeps listing them, and two bars would cost rows a phone does not have. No project, no bar (the rows stay, so the pane does not jump when the first project opens).
- **Folding** (`Project::collapsed`, `Workspace::collapsed`, saved in the session; only the tree draws them): new projects and workspaces start unfolded. `follow` unfolds the active project and workspace, and in the tree its group, when the focus changes; a click on a row and `goto` (search) do too, for when the focus stays the same. Other layouts leave a collapsed group alone, as before. The first follow after a restore (`followed` still default) unfolds nothing, so saved folds survive.
- Lists scroll by item with the wheel, show ` ↑ n more` / ` ↓ n more`, and keep the `+` button sticky at the bottom. The scroll follows the active item only when it changes (`App::follow`), otherwise the wheel could never move away from it.
- The active row (project, tab, a collapsed group holding the active project, the tree's marked row) gets a surface background (palette 236, or 254 on light themes) and a cyan `▌` in the column's first cell over the row's full height (a tab's second line, a compact band), so every list shares one selection rail on the left edge. `draw_rail` and the tree lines only draw on blank cells, so text pushed left in a narrow column wins over them. Colours use palette indices so they work without truecolor; the brand purple is index 99.
- **Lines** (column borders, the stack and footer separators, split dividers, the changes panel's rules, tree lines, the usage track) take `View::line()`: palette 239, or 250 on light themes, a step quieter than the muted grey, so structure recedes behind text. Hover and drag still light borders and dividers cyan.
- **Tree lines**: tabs hang from their workspace, in the workspaces list and in the tree: `├` before each tab, `└` before `+ Tab`, `│` on a tab's other rows (its second line, a compact band), below a compact workspace's name and on a landing line among them (`draw_guide`, `among_tabs`, `tree_among_tabs`). In the tree they sit in the workspace's arrow column; projects and workspaces keep only their arrows, since lines at every level made the tree busy.
- **Empty panes**: a workspace without tabs centers `no tab open` and `+ Tab opens a shell here`. With no project at all the pane shows the logo (the favicon's corner and cursor in half blocks, purple 99 and cyan), the wordmark, the tagline and `+ New opens a folder`, or the words alone when the pane is too short (`draw_welcome`); it needs an empty project list, not just no active project.
- **Capitals**: the names of the main UI start with a capital letter, so they read as names rather than as words in a sentence: the column titles (`Projects`, `Workspaces`, `Agents`), the sidebar and footer buttons (`+ New`, `+ New workspace`, `+ Tab`, ` Issues `, ` Changes n `, ` Files `, ` TODO `, ` Settings `, ` Usage `, ` Quit `, `‹ Projects`, `Agents ›`), the panels' titles and tabs (` Files `, `TODO`, `+ New TODO`, `Uncommitted` / `Commits` / `All`, like the settings and issues tabs already were) and every dialog title (`New workspace`, `Remove workspace`, `Keys › Git`…). TODO is in capitals, as the word is written in code. Menu entries, the buttons inside dialogs, placeholders, toasts and messages stay lower case: they are actions and sentences, and a menu of capitalised verbs reads louder than its rows. `Overlay::name` and log targets keep their lower-case ids; a rename has its own title (`Target::rename_title`), since `rename_label` is also its menu entry.
- **Grey text** (titles, the footer, the search field, arrows, notes) is `View::muted`, never `Color::DarkGray` directly: `ui::muted` keeps the theme's bright black (ANSI 8) when `HostTheme::muted_is_readable`, else palette 243 (245 on light themes). Readable means its WCAG contrast with the background is at least 2:1, or the background is unknown (nothing to compare with, so as before). Some themes make bright black the background or close to it: Solarized Dark (1:1), Warp's adeberry (#2b2b2a on #1d2022, about 1.15:1, the footer and arrows vanished), Nord (1.7:1); One Dark (2.5:1), Dracula (3:1) and Gruvbox (4:1) keep theirs. A known background with an unknown bright black also gets the fixed grey: Warp answers OSC 11 but not OSC 4, and the 256-colour greys are not themed (the surfaces rely on that too). The changes panel's `View` carries the same colour.
- A hovered project, workspace, tab or group row is filled edge to edge with palette 235 (255 on light themes), one step between the background and the surface (`View::row_background`). The active row keeps its surface. No hover fill while an overlay is open or a border or divider is being dragged. The site's palette tints 235 like 236 (`site/src/lib/term/palette.ts`), so it stays between them, and 239, the line colour, so it stays between the surface and the muted grey.
- **Compact mode** below 90 columns (`ui::compact_layout`): a top bar (` ≡ `, `project › workspace › tab`, then ` ± `, ` ▤ `, ` ☐ `, ` ⌕ ` right-aligned; ` ± ` only in git workspaces and ` ▤ ` only with a project, so their slots are left of ` ☐ ` and an empty one merges into the breadcrumb) and a full-screen menu showing one column at a time. Every clickable item is a 3-row band (`Areas::pitch`). Both columns' areas share one rect and `Areas::shown(nav)` blanks the hidden one, so drawing and hit testing reuse the wide-mode code. With the agents section on, it is a third menu (`Nav::Agents`): ` Agents › ` at the right of the projects menu's title opens it, ` ‹ Projects ` (the same `Areas::back`) goes back, and a click on a row closes the menu on that pane.

## Dialogs (`ui.rs`)

- Dialogs, menus and the toast have rounded borders (`BorderType::Rounded`); a title sits after one border cell (`╭─ settings ─`), bold in the default colour, so it reads as the dialog's heading rather than part of the border.
- A dialog (form, confirmation, picker, settings, issues, usage, update, group style: `Overlay::is_modal`) dims everything behind it (`Modifier::DIM` on the whole buffer before it is drawn), so it reads as on top. A menu or the search does not: they belong to what they were opened from. DIM leaves backgrounds alone, so surfaces stay.
- Lists inside overlays (menus, picker, issues, search results, a settings pick, settings rows) mark the selected row like the sidebar: surface background, a cyan `▌` in its first cell and bold text; a hovered row takes the hover fill. The filled cyan bar they had was loud, and two of them lit at once (the selected row and the hovered one). The active tab of a tab row (settings, issues, the changes panel: `tab_style`) is cyan bold on the surface.
- **A left press outside a dialog closes it** (`App::outside_dialog`, before each dialog's own mouse handling), like its cancel button (`cancel_form`), so a busy one (`Overlay::busy`: creating a worktree, installing an update, checking a token, starting an issue) stays open. Menus and the search already closed that way; dialogs only closed with their buttons or `Esc`, which is not what anyone expects of a modal. Where the dialog is comes from `ui::Overlay::area`, which uses the geometry functions the drawing uses (`form_area`, `picker_area`, `usage_area`, `issues_area`, `settings_area`), and a test per dialog checks its border is drawn at that area's corners. It closes the whole dialog, not one level as `Esc` does in the issues browser or a settings pick. What was typed in a form is dropped, as with `Esc`; keeping forms with text open was considered and left out: one rule for every dialog is easier to learn than a click that sometimes does nothing.
- Dialog buttons are pills on the surface (`dialog_button_style`): the submit one cyan bold, the others grey; hover fills them cyan or grey. Without a background they read as coloured words, not as something to click.

## Hierarchy (`project.rs`)

- Optional group > project (a canonicalized folder) > workspace (the project folder, or its own git worktree) > tab > panes. Every level has an id from one counter; menus, forms and background jobs refer to ids, never indices.
- Labels: custom name, else folder name (project), branch or `default` (workspace), foreground program (tab).
- **A split tab is named after its first pane** (`Tab::label`: the first leaf of `Tab::layout`, the top-left pane), not the active one, so the name stays put while the focus moves between panes; it followed the focus before (#40), and the row changed name on every click. Its row ends with a muted `+n`, the number of other panes (`TabEntry::others`), also for a custom name, fitted first like `↓n` (`Tags::fit`) so a long name is cut before it. Only the rows show it; search and the compact bar's breadcrumb keep the plain label. Model and context still follow the active pane (`Tab::context`), since they describe the agent you are looking at.
- **A tab's program** (`term::program`): a known agent (`agents::detect`) gives its kind; for an interpreter (`node`, `bun`, `deno`, `python`, `python3`, `ruby`) the whole argv is matched, for anything else only `argv[0]`, so `less claude` stays `less`. An interpreter whose first non-flag argument is a script (contains `/` or has a script extension, no whitespace, and no `-e`, `--eval`, `-p`, `--print`, `-c` or `-m` before it, so modules and inline code keep the interpreter's name) gives the script's stem: npm installs run `node /…/bin/codex`. Linux `comm` is the main thread's name, which recent Node renames to `node-MainThread`; that becomes `node`. Its PTY test runs a copy of `/bin/bash` named `node` (`comm` comes from the executed file; a symlink to dash would do on Linux, but macOS names the process after the target).
- Closing kills processes; removal waits for the shell to exit, never synchronous. A pane goes when its reader hits the PTY's end (`Exited`) or, on any `App::refresh`, when `Term::exited` finds the shell reaped (`try_wait`), whichever comes first. Both, because the PTY's end only comes once every process has closed the terminal: one that left the shell's session and ignores SIGHUP (`nvim --embed` outliving its UI, `nohup`, `setsid`) would keep the tab as `?` forever. Like tmux, the pane goes with the shell; the reader thread and the master's fd stay until that process exits. `Term::kill` skips a reaped shell, since portable-pty signals the pid unconditionally and it may have been reused. Closing a project asks first (`Overlay::CloseProject`), since it stops every shell in it, agents included; a tab or a plain workspace closes at once in wide mode and asks first in compact mode. Closing the last tab keeps the workspace; closing the last workspace keeps the project.
- **Groups**: one level, no nesting; a new one goes last. A project holds `group: Option<u64>`; the projects column is `ui::sidebar_rows` (loose projects first, then per group a gap, the header and, unless collapsed, its projects), which drawing, hit testing and `App::follow` share. A collapsed group holding the active project gets the `▌` on its header. Deleting a group (the `×` on its header, or its menu) asks first (`Overlay::DeleteGroup`) and only ungroups its projects. Icons are a fixed set of one-cell symbols (`ui::GROUP_ICONS`, no emoji or Nerd Font glyphs, whose width varies); colours are palette indices (`ui::GROUP_COLOURS`, no greys, black or white, which vanish on some themes). A new group takes the first of eight presets (`ui::GROUP_STYLES`) that no group has, the same icon and colour, else they repeat in order, and nothing opens: the icon and colour modal used to open after the name, a question asked at the moment one only wanted a group, and it is one click away in the group's menu (` ⋯ ` or right-click → **icon and colour**), whose clicks apply at once. The presets start with blue, the favourite colour in every one of the ten countries of YouGov's 2015 survey, then green, purple and red (the runners-up there), orange, yellow, pink and teal; each has its own shape, so groups differ without colour. Each is in `GROUP_ICONS` and `GROUP_COLOURS`, so the modal marks it.
- **Adding to a group**: the group's menu starts with **add project**, which opens the picker (`Overlay::Picker { group: Some(_) }`, titled ` add project `) in the folder above the group's first project; what it opens lands in the group (an already open project moves there) and the group expands. `+ new project` never guesses a group from the active project: a new project landing in a group you did not pick would surprise.
- **VS Code workspaces** (`vscode.rs`): the picker lists `*.code-workspace` files after the folders, tagged `vs code`, also while filtering (folders first, then the match rank), so a quick `Enter` on a filter goes into a folder rather than importing; choosing one imports it once, never linked (cornercase does not write the file nor watch it). The group is the file's stem, reused when a group has that name (re-importing brings in folders added since), else a new one with the next preset. Each folder opens as a project in it, in order, the first one active; a folder already open moves into the group; its `name` (only when it differs from the folder's name) becomes the project's custom name when the project has none: a new one, or an open one never renamed; a name given in cornercase is never overwritten. `path` is relative to the file's folder, `uri` is read only as a local `file://` path, `file:///…` or `file://localhost/…` (another host or scheme is skipped, never read as a relative path); missing folders are skipped and counted in the toast, and a new group left empty is removed. A folder whose shell cannot start (`open_into` fails) does not end the import, as in the restore: it is logged with its cause, counted apart from the missing ones (`n could not open, see server.log`, with the bug icon) and the next folder goes on. The toast counts distinct projects (a folder listed twice, `api` and `./api`, opens once and counts once) and says `nothing imported from <name>` when none opened, since the empty new group is gone by then. A UTF-8 byte order mark is skipped, and every read error, not only a JSON one, names the file. VS Code accepts comments and trailing commas, `serde_json` does not, so `strip_jsonc` removes both outside strings first, rather than adding a JSON5 crate. A file that cannot be read keeps the picker open with the error.
- Menus are one `Overlay::Menu { actions: Vec<MenuAction> }`, labels from `App::menu_label`; a submenu (move to group) replaces the menu at the same spot. `+ New` opens a menu (open project / new group); it was `+ new project`, which named only one of the two.
- **Reordering** (drag): project, group, workspace and tab rows act on release. A press grabs the row (`App::row_drag`, a `Target`); leaving the row's rect, or releasing outside it, makes it a drag, otherwise the release is the click (activate, collapse), so a cancelled drag changes nothing and the compact menu stays open while dragging. `×` and `+` still act on press. Releasing outside the list, `Esc` or another button cancels; no hover while dragging.
- Where it lands (`ui::sidebar_drop`, `ui::workspace_drop`) comes from the pointer and the layout without the line, so the line never feeds back: the row under the pointer gives its slot (before it when above the dragged row, after when below); a group with its projects and a workspace with its tabs are one block; a group header takes a project in first (last when collapsed); a gap is the end of the section above; tabs stay in their workspace, workspaces in their project (moving a shell or a worktree elsewhere was left out). The line goes on a neighbouring gap, on the line above or below the visible rows at an edge, else as an inserted one-line `Landing` row; it is indented where a grouped project or a tab would start.
- Holding a drag on `↑ n more` / `↓ n more` scrolls one item every `AUTO_SCROLL_EVERY` (150 ms); `App::tick` shortens the server's wait meanwhile. Moving only changes `Vec` positions (`project::move_before` keeps the active index on its item), so ids, menus and jobs are unaffected and the session saves the order as is; worktrees found outside cornercase go last.

## Splits (`split.rs`)

- A binary tree (`Leaf` / `Split { dir, ratio, first, second }`). Right-click in a pane opens split/close/right-click-passthrough; this works even when the program captured the mouse, since almost no program uses the right button.
- A vertical divider is followed by a blank column so text does not touch it. Inactive panes are dimmed (configurable). A left click on an inactive pane only focuses it. Dividers drag like column borders.
- **Every pane keeps its minimum** (`MIN_COLS`×`MIN_ROWS`, the size a split needs on each side). `Node::min_size` is what a subtree needs along a direction: a leaf its minimum, a split along that direction both sides plus the divider's gap, a split across it the larger side. Each split hands its sides at least their minimum when its area allows it (`split::divide`), so a client smaller than the one the splits were made on squeezes the panes down to their minimum, never to nothing; the stored `ratio` does not change, so growing back restores the proportions. A divider drag is clamped to the same minimum of both sides, nested splits included (`Divider` carries them, `ratio_at` clamps), so the stored ratio is what the screen shows. Before (#33), the drag left 1 cell on each side, and that side could be a nested split whose panes then got 0 rows: invisible, unclickable, and the active one still took the keys.
- **A tab too small for every pane shows only its active pane** over the whole tab (`Node::has_room`, `Node::visible`), until there is room again: a phone attaching to splits made on a big screen, a narrow window. Drawing, hit testing, `App::resize` and `control` all go through `visible` (`Tab::shown`, `Tab::rect`, `Tab::pane_at`), so keys and clicks never reach a pane that is not on screen. The hidden panes keep running at their last size (their PTYs are not resized), there are no dividers, and the pane menu offers no split (`Tab::can_split`), since a new pane would be hidden too. Squeezing every pane to 1 cell was rejected: visible but useless. A single pane always shows, whatever the size.
- **Moving panes** (#107): a right-button drag from one pane onto another moves it there, keeping every program running (only the tree changes, then the PTYs are resized). The right button because it is already cornercase's in a pane (the menu), whatever the program does with the mouse; a left drag is the program's or the selection, panes have no title bar to grab (one would cost a row per pane), and modifier drags do not arrive reliably (Cmd never, Ctrl and Alt are taken by some outer terminals). So the pane menu now opens on the release, when the pointer never left the pane (`App::pane_drag`, like the rows' `RowDrag`). Where it lands is `split::Place::at` on the pane under the pointer: the middle third in both directions swaps the two leaves (`Node::moved` keeps the shape and ratios); elsewhere the nearest edge, relative to the pane's size, removes the pane (`Node::remove`) and splits the target on that side at half (`Node::insert`, `before` for left and above). `Tab::landing` offers only moves whose tree still `has_room`; drawing (`TabView::landing`: the half the pane would take, or the whole target, on the surface with ` move here ` / ` swap `) and the drop share it. The moved pane becomes the active one. `Esc`, another button, or a release on the same pane or outside the panes cancels. Menu entries (move pane, flip a split) and Ctrl+drag were considered and left out: one gesture covers every case, flipping included (drop a pane on its neighbour's bottom edge).
- A pane can still have no room when the whole pane area is empty. Its PTY is sized at least 1×1, and mouse events for it are dropped (`pane_cell` returns `None`), never clamped into an empty range: `clamp` panics when `min > max`, which drops the event and shows the bug toast (see Panics).

## Search (`search.rs`)

- One global search across groups, projects, workspaces (label and branch) and tabs (label and their workspace's keys). Ranking: exact, prefix, substring; ties by kind (group, project, workspace, tab) then sidebar order. A group result expands it and activates its first project. Results are recomputed on every key and draw; the query is never kept after closing.

## Folder picker (`picker.rs`)

- Starts in the parent of the active project (of the group's first project for **add project**). `Enter` goes into the selected folder (or imports the selected `.code-workspace`), or opens the current one when nothing is selected. Typing a path walks it; a paste goes through the same path (e2e opens projects this way). Folders are read on the main thread.

## Worktrees (`worktree.rs`)

- Only when the project folder is a repo root. The name is the branch; the slugged name is the folder, under `<worktrees folder>/<repo>/<slug>` (`~/.cornercase/worktrees` by default). `git worktree add` runs on a thread and answers with an `AppEvent`.
- Every linked worktree of the repo shows up, also ones created outside cornercase (`App::refresh`, throttled to once a second).
- Removing asks first, runs `git worktree remove` (`--force` after a "remove anyway") and never deletes the branch.
- **Removal runs in the background** (#98): deleting a checkout with `node_modules` or a `target/` folder takes seconds, and the dialog used to stay open (`removing…`, unclosable) until git finished. Opening the dialog runs `git status --porcelain` on a thread (`worktree::changed`, `AppEvent::WorktreeChecked`), which is what makes `git worktree remove` refuse, so a worktree with changes says so at once and offers **remove anyway** before anything stops. Only an explicit clean answer counts as clean: a git status that fails (or a job that panics) counts as changes, so the shells keep running unless the user confirms **remove anyway**. Confirming closes the dialog (`Overlay::RemoveWorkspace`'s `Check`: `Running`, `Confirmed` when confirmed before git status answers, which shows `checking…` and goes on by itself when the answer is clean, then `Clean` or `Changed`, the latter being what offers **remove anyway**; `Esc` always closes it). The workspace becomes `Phase::Removing(label)`: its shells are stopped first, since an agent or a dev server would keep writing into a folder being deleted, and that is why the check comes before; the view steps off it to the nearest open workspace (`Project::step_off`), as closing does. `App::start_removal` is the one place that starts it, and only on an `Open` workspace, so a dialog and a command racing on one worktree start one removal. The phase keeps the label because a checkout git is deleting has no branch left to read: the row would turn into `default` halfway. Its row stays, dimmed, with `removing…` where `↓n` goes, without `×` or `+ Tab`; `App::workspace_hit` and `App::tree_hit` drop hits on it, so left clicks and right-click menus ignore it in every layout; search and the issue places list only `Workspace::open` ones. `sync_worktrees` keeps it even once its folder is gone, so the row does not vanish and come back while git cleans up. Git's answer drops the row with a `removed <name>` toast, or puts it back (`App::settle_removal`), without its tabs, with git's message in a toast; opening the dialog again checks again and offers **remove anyway**. Several removals can run at once. Checking at confirm time instead of on open was rejected: the dialog would need a busy state again. A server that stops meanwhile leaves `git` to finish on its own; `sync_worktrees` brings the worktree back if its folder survived.
- **Locked worktrees**: The removal check reads whether the worktree is locked (`worktree::lock`: `git rev-parse --absolute-git-dir`, then its `locked` file, whose text is the reason, as gitrepository-layout documents), since `git worktree remove` refuses a locked worktree even with `--force`, and that refusal used to come after the shells had stopped. Claude Code locks the worktrees it creates (`claude session <name> (pid N start …)`) and unlocks them only when it exits cleanly, so a ` restart now ` that kills it leaves the lock behind. A locked worktree's dialog names the reason and, when the reason names a pid (`worktree::Holder`), whether that process still runs (shown only: a pid can be reused, so it never decides anything), and its button is **unlock and remove** (`git worktree unlock`, then `git worktree remove`; the unlock runs only if the lock is still there, since a Claude Code in the workspace may have released it when its shell was stopped and `git worktree unlock` fails on an unlocked one; `--force` is added when it also has changes). A lock found after confirming early (`checking…`) stops there, like changes do. Unlocking silently when the pid is gone (it depends on Claude Code's undocumented format) and `--force --force` on **remove anyway** (which would skip locks under a button that only speaks of changes) were rejected. `cornercase close --remove-worktree` never unlocks: with or without `--force` it answers an error naming the reason and `git worktree unlock <path>`, before anything stops; `--force` now waits for the same check.
- `cornercase close --remove-worktree` still answers once the worktree is gone and takes the same path: it checks first and answers an error, stopping nothing, when the worktree is locked or, without `--force`, has changes; then it stops the shells and removes, and a refusal puts the row back. Every command that names a workspace (`close`, `new-tab`, `start`, `focus`, `rename`) refuses one being removed or closed (`usable_workspace`): a tab opened there would run in a folder being deleted.
- `.worktreeinclude`: files matching it **and** ignored by git are copied into a new checkout. Matching is delegated to git (`ls-files`, `check-ignore`).
- **Commits to pull** (`↓n` at the end of a workspace row, before the `×`): every 3 s a thread per project counts `HEAD..@{upstream}` in each workspace and answers with `AppEvent::Behind`; it runs `git fetch --all` first once `fetch_minutes` (default 5, 0 turns all of it off) have passed. One thread per project at a time. Git never prompts (`GIT_TERMINAL_PROMPT=0`, empty `GIT_ASKPASS`, `SSH_ASKPASS_REQUIRE=never`); failures count as 0.

## Changes panel (`changes/`, `ui/changes.rs`)

- Git workspaces only: ` Changes n ` next to ` Issues ` (` ± ` in the compact bar) opens a fourth column right of the pane (full screen in compact mode). Its border drags; its width is `Widths::changes` (`None` = half the free space, at most `DEFAULT_WIDTH`).
- Tabs: uncommitted (`git diff HEAD` + untracked), commits (`git diff <merge-base> HEAD`), all (`git diff <merge-base>` + untracked). The base is `Workspace::base` (saved per workspace) or the default branch: `origin/HEAD`, else `main`/`master`. Comparing from the merge-base keeps commits made on the base later out of the diff.
- Git runs on a thread, one job at a time, every second while it or the files panel is open (`Panel::watched`, for its marks) and every 3 s while closed (for the button's count). Flags matter: `--no-optional-locks` and `-c diff.autoRefreshIndex=false`, because a plain `git diff` rewrites `.git/index` (takes `index.lock`) even with `--no-optional-locks` and would fight an agent's `git commit`. `--relative` keeps paths inside the workspace folder. Untracked files are read directly (never `git add -N`), capped at 1 MiB, NUL in the first 8000 bytes means binary; a symlink shows its target path, like git, never the file it points to. The branch list and "unchanged lines" also run on threads and answer with `AppEvent::Branches` / `AppEvent::Gap`.
- The job hashes git's output; an unchanged hash answers without a diff, and files whose patch section did not change are reused, so highlighting runs only for what changed. syntect costs ~150-200 µs per line, far more than computing the diff.
- Rendering: lines paired delta-style (word tokens, changed share ≤ 60 %) get word emphasis; each hunk side (context + removed, context + added) is highlighted separately. Tints blend the host background with palette red/green when the client has `COLORTERM=truecolor` and the background is known; otherwise palette colours, and on dark themes only the `▎` bar, coloured numbers and word emphasis (palette greens and reds are too loud as line backgrounds).
- **Filter** (`changes/filter.rs`, pure): ` ⌕ ` left of the panel's `×` opens a field under the tabs (the header grows a row, so the summary and the base selector stay) that filters files by path only; searching the lines was tried and dropped as not useful. While it is focused (`Filter::focused`, and only while the panel shows and no overlay is open) keys and pastes go to it, like the global search: `Enter` keeps the filter and unfocuses, `Esc` or its `×` closes and clears. Any press outside the panel gives the keys back and keeps the query; a click on the field or ` ⌕ ` takes them again; closing the panel unfocuses it. Each word is an include, or an exclude with `!`; a file stays if it matches any include (or there is none) and no exclude, by its path or its old path. A word without `*`/`?` is a substring of the path; with them a `.gitignore`-like glob (no `/`: any path component, a trailing `/` only folders; with `/` or a leading `/`: the whole path, also everything under it; `*` and `?` stop at `/`, `**` crosses it). Smart case per word. Folds are untouched; typing resets the scroll. Shared by clients, never saved; switching tab or workspace keeps it.
- Hunk actions on hover: open (new tab running `/bin/sh -c 'exec ${VISUAL:-${EDITOR:-vi}} "+$1" "$2"'`), ask agent (pastes `path:lines ` into the workspace's agent pane, found with `agents::detect`; without one it copies the reference), copy (the hunk as a patch, OSC 52). Viewed marks are keyed by the file's patch digest, so they clear when the file changes.

## TODO panel (`todo/`, `ui/todo.rs`, `app/todo_panel.rs`)

- ` TODO ` (no count: a number there would always be lit and say little) opens a panel in the changes panel's column (`Areas::changes`, `Widths::changes`, `Border::Changes`); only one of the three (changes, TODO, files) is open at a time, and opening the compact menu closes them. One global list, the same in every project: lists per project and per workspace, and starting an agent from an item (` ▶ `, a worktree or tab per item), were built and dropped as more than a TODO list needs.
- **Storage**: `todos.json` next to `session.json` (`todo::path`), its own `VERSION`, only `text` and `done` per item, written by a second `state::Saver<todo::Saved>` once it settles, and flushed on shutdown (a list has no logout burst to fear, and a just-typed item must not be lost to `kill-server`). Item ids are `Todos`' own counter, not the hierarchy's. A missing, corrupt or other-version file means an empty list. The list lives in `App`, so every client sees the same.
- **Order**: pending items, then done ones. A new item goes to the end of the pending ones; checking moves an item to the end of the list, unchecking to the end of the pending ones; a drag keeps an item among its kind (`Todos::move_before` clamps). Undo (`todo::Removed`) puts items back at their old index, clamped to that order.
- **Layout** (`ui::todo`): a header (` TODO n `, ` clear done ` when something is done, ` × `), a gap, then a `ui::Rows` (variable heights, scroll by item, ` ↑ n more ` / ` ↓ n more `, sticky `+ New TODO`), the same as the sidebar lists, so the wheel, `Rows::edge` auto-scroll and `reveal` come for free. Items soft-wrap at a fixed text width (`text_width`: the row minus the checkbox and the reserved ` × ` column), so hover never reflows. The checkbox is `○`, a green `✓` once done, in the middle of its three cells (the hit area `[ ]` had). `ui::todo::{rows, check, delete, clear_done, spot}` serve drawing and hit testing.
- **Editing**: `todo::editor::Editor` is the only text field with a cursor (chars and an index; wrap keeps every char so line/column map back to the text; a full last line gets an empty one for the cursor). The terminal cursor is placed with `set_cursor_position`. `+ New TODO` turns into the field at the bottom; `Enter` adds and keeps it open for the next item, `Enter` on an empty field or `Esc` closes it. A click on an item's text edits it in place with the cursor at the click. Any press outside the field (in the panel or elsewhere) commits it (blur saves, so nothing typed is lost) and gives the keys back; `Esc` is the only way to drop a change. Saving an empty text keeps the old one. Pastes go in as one line.
- **Rows**: a press on an item grabs it (`Grab::Todo` in `App::row_drag`); release in place is the click (edit), leaving the row is a drag. The landing is computed from the layout without the line (`ui::todo::drop`), and drawing inserts a one-row line. `[ ]` and ` × ` act on press; both also on the item being edited (`ui::todo::hit` looks at them before the field), committing the text first like any press outside the field (#108), so undo brings back what was typed. That item shows its ` × ` without hover: the row is not lit while it is a field, and the button used to vanish exactly while the item was selected.
- **Undo instead of confirming**: ` × ` and ` clear done ` remove at once and set a toast with an ` undo ` button (`Toast::undo`, `UNDO_FOR` 6 s instead of 2 s). Only the last removal can be undone. The toast's button is checked before overlays, so it works with a menu open.

## Files panel (`files/`, `syntax.rs`, `ui/files.rs`, `app/files_panel.rs`)

- ` Files ` (on the todo row, under ` Issues `; ` ▤ ` in the compact bar) opens a panel in the changes panel's column with the active workspace's folder, so each worktree shows its own files; git or not. Read only: editing goes through ` open `.
- **Tree**: folders first, then files, by name ignoring case. Each open folder is listed on its own, on a thread, with `ignore` (one level; `.gitignore`, `.ignore`, the global and `.git/info/exclude` rules, also from parent folders; hidden files shown, `.git` never), at most `disk::MAX_ENTRIES` (10,000) entries. Listing per folder rather than walking the whole workspace keeps a huge folder (a home folder opened as a project) free until it is opened. The root and the open folders are listed again every `LIST_EVERY` (2 s) while the panel shows, one job at a time, so files an agent creates appear. Open folders, scroll, the open file and the last one opened live per workspace in `files::Panel`, in memory; the session keeps only whether the panel is open.
- **Viewer**: a click on a file reads it on a thread (`disk::read`): at most `disk::MAX_BYTES` (8 MiB) for text, or `disk::MAX_IMAGE_BYTES` (32 MiB) for a file whose first bytes are a recognised image (see Images), NUL in the first 8000 bytes means binary, invalid UTF-8 is replaced. Only regular files are read: the tree lists a link to a device or a FIFO as a file (a cloned repository can hold one to `/dev/zero`), and reading it would never end, growing the server's memory until it dies with every shell, or block its thread for good, so it shows as binary. The read itself stops after `MAX_BYTES + 1` bytes, so a file that grows after the size check cannot get past the cap. The first read answers plain text at once and the highlighted text after; then the file is checked every `CHECK_EVERY` (1 s) by size and modification time and read again when they change, answering only highlighted text, so colours never flash while an agent writes. Lines are cut at the panel's edge with `…`, tabs are four spaces. ` ‹ ` goes back to the tree with the file's row marked. An image file (by its first bytes, not its name) is not text: see Images.
- **Highlighting** (`syntax.rs`): tree-sitter through arborium, about 60 grammars compiled in: the languages agents touch most (TypeScript, TSX, JavaScript, Python, Rust, Bash, Markdown, Java, C) and every grammar under 0.3 MB (Go, JSON, YAML, TOML, HTML, CSS, GraphQL, Lua, HCL, Vue, Svelte, Dockerfile, Make…). Grammars weigh 0.01-17 MB each (SQL 9 MB, C++ and Kotlin 5 MB); all 112 of arborium's made a 169 MB binary. A language without a grammar borrows a relative's by its comment syntax (`syntax::FAMILIES`): `//` JavaScript, `#` Python, `--` Lua, `;` Scheme, so comments and strings come out right and only some keywords stay plain; a hand-written fallback lexer was built and dropped in favour of this table. Every JavaScript file goes to the TSX grammar, whose query colours JSX tags and attributes (JavaScript's does not). The grammar comes from the file name, then the extension, then the shebang. Captures map to palette colours (`syntax::style`) so the terminal's theme applies: keyword magenta, function blue, type cyan, string green, number and constant yellow, property and tag red, comment the muted grey in italics. tree-sitter was picked for speed and precision: a 3,500-line TypeScript file takes 48 ms against 0.47 s for syntect with fancy-regex and the JavaScript syntax (2.4 s with a real TypeScript one), and it colours types and fields the same everywhere. Sources over `syntax::MAX_BYTES` (2 MiB) stay plain. syntect still colours the changes panel and Markdown.
- **Git marks** follow the changes panel: its model for the active workspace, with its mode and base. A changed file gets its status letter and colour in the tree; a folder holding changes gets a `●`, yellow, or green when everything under it is new. Deleted files are not on disk, so only the changes panel lists them. In the viewer every change block of the file's hunks marks the margin (`files::gutter`): `▎` green on added lines, `▎` blue on changed ones, `▁` red on the line after which lines went (`▔` on line 1 when they were above it); an untracked or added file is all green. A click on a mark shows the old lines above the block in red, tinted like the changes panel's removed lines, and another click hides them (`Viewer::unfolded`, keyed by the line the block sits before; `files::Lines` maps rows to lines and old lines).
- **Search**: one bar under the title (`files::Query`, per workspace), with no query the tree shows everything. It searches the text in the files; the ` ▤ ` at its right switches it to file names and back (`files::Mode`, lit while on). Tabs (tree, names, text) were built first and dropped: one bar with a toggle is less to read, and an empty bar giving the whole tree makes the tree the search's starting point. The bar takes the keys like the changes panel's filter (`Query::focused`; a click on it takes them, any press outside the panel gives them back): typing searches at once, `↑` `↓` pick a result, `Enter` opens it, ` × ` clears it and `Esc` clears it and gives the keys back. Until the answer to what was typed comes, the list keeps the previous results under `searching…` instead of going blank on every key (a text search can take tens of milliseconds on a large repository); an `Enter` pressed meanwhile waits for that answer and opens its first result (`Query::enter`), so typing and pressing `Enter` at once never opens a result of the previous query. Any other key, or a press outside the panel, drops the waiting `Enter`. Both modes search an index of the workspace's file paths (`search::index`: one parallel `ignore` walk with the tree's rules, at most `search::MAX_FILES` (200,000)), built on a thread once the bar is used and again every `INDEX_EVERY` (10 s) while it is; an answer remembers the index it came from, so a new index searches again. Measured on a 32,000-file repo: the walk takes 25 ms, a name search 1-20 ms, a text search 52 ms for everything and 1-3 ms for the first 50 matches.
- **Names** (`search::names`): nucleo's matcher (Helix's, fzf's scoring) with its path bonuses and smart case, best `MAX_NAMES` (200) first; on a tie the shorter file name, then the shorter path, so the file a query names comes before longer names in shallower folders (`workspace-session` gave `src/relay/workspace-session-handler.ts` before `src/renderer/src/lib/workspace-session.ts`); the matched letters are lit, and a path too long for the row loses its start so the file's name stays. One job at a time; a newer query waits for it and goes next.
- **Text** (`search::text`): ripgrep's `grep-searcher` and `grep-regex` over the indexed paths on up to 8 threads, the query a literal with smart case (regular expressions were left out: one more thing to learn for a quick look), binary files skipped (a NUL ends the file), at most `MAX_MATCHES` (1,000) matches: each match takes a slot before it is kept, so the threads together never keep more, and the search goes on until one more match is seen, so `Text::capped` (the note's `the first 1000 matches`) means a match was really left out, not just that the count reached the cap. A new query cancels the running search (`AtomicBool`) and starts at once. Results come grouped by file in path order; each line keeps its number, its text without the indent (at most 400 characters) and where it matched, and a long line is shifted so the first match shows. Opening a match opens the file at that line, selected so ` ask agent ` takes it at once, with every occurrence of the query lit in the viewer (`Viewer::find`); ` ‹ ` returns to the results.
- **Paths in panes** (`files/link.rs`): a path printed in the active pane, by an agent, a compiler, `git` or `rg`, opens in the files panel on a click, at its line or lines (`:12`, `:12:5`, `:12-30`, `#L12-L30`) and with them selected, so ` ask agent ` takes them at once; the panel opens if it was closed. The path is the run of path characters under the pointer (letters, digits, `_-./~@+,%:#`; brackets, quotes and backticks end it, a trailing `.,:;#` is dropped, a URL is none), resolved from the foreground program's folder, then the workspace's root, and taken only if it is a file inside the workspace. The one under the pointer is underlined in cyan (`ui::TabView::link`), checked on each draw: a snapshot row is already there and the check is a `canonicalize`. Claude Code's fullscreen renderer reads the mouse, so its clicks would never reach cornercase, but a plain click on a path does nothing there (it opens links with Ctrl+click, through a desktop file manager a server lacks). So a press on a path in a program that reads the mouse is held back (`App::link_press`): released on the same cell it opens the file and the program never sees it; moved to another cell, the held press is sent first and the drag goes on, so the program's own selection still works. The cost: a click right on a path in a Claude tool's header no longer expands it (a click elsewhere on the row does). A program that does not read the mouse keeps cornercase's selection; a release without moving opens the path instead of copying nothing. Modifier clicks were rejected: the protocol cannot carry Cmd, and Ctrl and Alt clicks are taken by the outer terminal on some systems.
- **Lines for the agent**: a press on a line selects it and dragging selects a range (`Panel::selecting`, followed by `continue_drag` even outside the panel; past the body's edges the nearest line counts). Any event but a left drag ends it, like the other drags: a release outside the window may never be reported, and the next click would be swallowed. ` ask agent ` pastes `path:a-b ` (`path ` with nothing selected) into the workspace's agent like the hunk action, ` copy ` copies the selected lines (else the path), ` open ` opens the editor at the first selected line in a new tab.

## Images (`graphics/`, files panel)

- **Overview**: a click on a PNG, JPEG, GIF (its first frame), WebP, BMP or ICO in the files panel shows the picture itself, drawn by each window's own terminal, because agents write screenshots, diagrams and icons into the workspace and opening another app to look at one breaks the flow. Three protocols cover the terminals people use: kitty graphics with Unicode placeholders (Ghostty, kitty), iTerm2's inline images (iTerm2, WezTerm, Warp, VS Code with its image setting) and sixel (foot, Konsole, xterm as a VT340); a terminal with none gets, where the picture would be, a message naming what it lacks and how to get it, rather than an empty panel that looks broken. Each window decides for itself at startup (Detection) and the server follows: two windows on one server, say Ghostty and an xterm, each get what their terminal can show, in their own size. The pipeline: the reading thread decodes the file once into a `graphics::Picture` (Decoding and encoding); per window, `App::draw` fits it to that window's room and cell size and draws the cells of its area; the bytes for that window's protocol are made on a job thread and cached; the server writes them into that window's frame and keeps them right while the screen changes (Rendering). SVG stays text: it is source code an agent edits, and drawing it needs a renderer of its own. Animations show their first frame: playing them would mean a stream of frames to every window for an image someone glances at.

- **Detection** (`graphics/detect.rs`, `host_theme.rs`, `client.rs`): each client decides once, at startup, what its own terminal can show and sends it in `Hello` as a `graphics::Support` (the protocol, or the `Missing` reason when there is none; the cell size; whether to wrap for tmux; `id_hi`); the server only follows it, since two clients of one server can sit in different terminals. `detect::decide` is a pure function of `Facts` (the replies, whether the kitty query went out, the window's cell size, what tmux said) and the environment, tested as a table on the replies the bench recorded (Ghostty 1.3.1, kitty 0.45, WezTerm stable and nightly, Konsole 25.12, foot 1.25, xterm 407 with and without `-ti vt340`, each directly, through tmux 3.6 locally and as seen over ssh), and checked live in each of them.
  - **The probe** adds `CSI 16 t` (cell size), XTSMGRAPHICS `CSI ?1;1;0S` and `CSI ?2;1;0S` (sixel colour registers and geometry) and, where it is wanted (below), the kitty query `ESC _G i=31,s=1,v=1,a=q,t=d,f=24;AAAA` to the existing batch, ahead of it, so the batch still ends `OSC 4;255;? CSI > q CSI c` and DA1 stays the end marker: every terminal answers in order, so no round trip is added (2-22 ms on the bench, as before). The parser reads APC replies (`G i=31;OK`), CSI with private markers, intermediates and empty parameters (kitty's `?62;52;c`, iTerm2's `?1;3;S`), and skips any other reply whole (DA2, DECRQM's `$y`). Strings never nest: an ESC inside one that is not its `ST` drops it and parsing starts again there, so Alt+`_`, Alt+`P` or Alt+`]` typed during the probe cannot swallow the replies after it (a swallowed kitty reply would be a false Ghostty message). It runs right after `ratatui::init()` and before mouse, paste and kitty-keyboard modes are on, so no mouse report lands in it and tmux has no key mode to re-encode the forwarded replies with. Nothing is asked in band once the input thread runs, and a probe that ends on its deadline rather than on DA1 keeps reading and dropping stdin until 200 ms pass without a byte (at most 1 s): crossterm reads a late `ESC _ G i=31;OK ESC \` as Alt+`_`, `G`, `i`… and the window would type it into a pane (DA1 alone it swallows). Starts that end on DA1 pay nothing.
  - **The kitty query** goes out only outside a multiplexer the environment shows (`TMUX`, `STY`, `ZELLIJ`, `TERM` `tmux*`/`screen*`): tmux turns an unwrapped APC into the pane's title (`Gi=31,s=1,…` in the status line), screen into its hardstatus. And only when `TERM`, `TERM_PROGRAM`, `KITTY_WINDOW_ID` or `GHOSTTY_RESOURCES_DIR` point at Ghostty, kitty or Rio, the only terminals whose answer changes anything: Konsole and WezTerm answer `OK` and still draw `U=1` at the cursor (bench), so the name decides, never the reply, and the reply only tells a Ghostty with `image-storage-limit = 0` (which then answers nothing) from a working one. Only `OK` counts as an answer; an error is taken as silence (its text stays in the log). Without the query (Ghostty over ssh with `TERM=xterm-256color`), XTVERSION alone decides, so a Ghostty with `image-storage-limit = 0` reached that way shows blank cells and no message: kept, since sending the APC to every terminal without a hint is what the gating avoids. If it went out and XTVERSION then says tmux (`default-terminal` set to `xterm-ghostty`, over ssh), tmux has renamed the pane, so the client sets the title to `cornercase` rather than leave the query's text there (checked live).
  - **Picking**, in this order: `CORNERCASE_IMAGES`, the multiplexer, the terminal's name, DA1. Kitty placeholders only for Ghostty, kitty ≥ 0.28 and Rio ≥ 0.5.27; iTerm2's inline images for iTerm2, WezTerm, Warp, mintty, older Rio, and xterm.js when DA1 has `4`, which its image addon adds (`TERM_PROGRAM` tells Tabby and Hyper from VS Code, so each gets its own setting in the message; Cursor reports `vscode` too and gets VS Code's; over plain ssh the addon's own DA1 `?62;4;9;22c` names xterm.js, which needs no cell size); sixel for Konsole ≥ 22.04, foot, xterm and mlterm when DA1 has `4`, contour, VTE before 0.83.90 with `4`, and any unknown terminal with `4`; a `Missing` otherwise, naming the terminal by brand and version (`xterm 407`, not `XTerm(407)`). The name comes from XTVERSION by prefix, else from the environment, where a hint naming a terminal that answers XTVERSION is ignored when DA1 came without one: `TERM_PROGRAM=ghostty` inherited by an Alacritty started from Ghostty would otherwise get placeholders, drawn as tofu. Sixel needs a cell size (`Missing::NoCellSize`); kitty and iTerm2 images fall back to 8×16. Zellij's DA1 `4` is trusted only from 0.45 (`Zellij(4500)`), which advertises sixel only when the terminal has it; older ones always do. `TERM=screen*` with neither `STY` nor XTVERSION is a multiplexer cornercase cannot name (screen, or a tmux older than 3.2, which has no XTVERSION and nothing this design uses), and gets a message saying so. An unknown `CORNERCASE_IMAGES` value is ignored and written into the log's `probe` line.
  - **tmux** (XTVERSION `tmux …`, or `TMUX` with no reply). Locally, `tmux display-message -p -t $TMUX_PANE '#{pane_tty}|#{allow-passthrough}|#{client_termtype}|#{client_termfeatures}'`, started before the batch and waited for at most 500 ms, names the outer terminal and says whether passthrough is on, without reading stdin. `allow-passthrough` prints `off`/`on`/`all` from 3.4, `0`/`1` in 3.3 (a flag there), and nothing before 3.3, when passthrough was always allowed. A `pane_tty` that is not the client's own tty means `TMUX` was inherited by a terminal started from a tmux pane: it is ignored, else Alacritty (no XTVERSION) would get placeholders decided from the tmux client's Ghostty. Over ssh, where `TMUX` does not arrive, or when that command fails, a wrapped probe (kitty query, XTVERSION, DA1, each in `ESC P tmux;` with ESC doubled) asks the outer terminal, at least 150 ms after entering the alternate screen, since with `on` tmux drops passthrough while the pane's redraw is pending (it got through 16 of 16 times at 0-50 ms on the bench; a dropped probe would show the passthrough message for the client's whole life), and waits twice the batch's round trip plus 300 ms, at most 1 s: silence means passthrough is off, which costs that wait at every start until it is turned on or `CORNERCASE_IMAGES` skips the check. tmux sends the outer terminal's replies to the client's active pane, so a cornercase started in a pane that is not active (`new-window -d`, a layout script) or in a hidden window under `on` hears nothing and its message says so; the late-reply drain protects only cornercase's own pane, and nothing tells that case apart remotely. Kitty placeholders go through (wrapped transmissions, plain cells) for an outer Ghostty, kitty or Rio when passthrough is on, else the passthrough message; otherwise tmux's own sixel, unwrapped, when tmux's DA1 has `4` and the outer terminal has sixel (`client_termfeatures`, or the outer DA1 over ssh), since tmux decodes and redraws it (foot, WezTerm, Konsole and xterm as a VT340 through tmux on the bench); a sixel terminal behind a tmux without sixel (older than 3.4, or built without it) gets `TmuxNoSixel` with tmux's version, since the fix is tmux, not the terminal; iTerm2 images through passthrough are never offered, as tmux's redraws wipe them. tmux inside tmux, GNU screen, and Zellij without sixel get messages.
  - **tmux's clients**: `#{client_termtype}` is the most recently active client of the session, and tmux shows one pane to every client, so placeholders and wrapped images reach all of them, including one that draws tofu; nothing in cornercase can fix that. When the local check was used, every resize (attaching from a terminal of another size sends SIGWINCH to the pane) runs it again on a short-lived thread, one at a time, whose answer comes back through the window's event channel, so input never waits; a changed decision is sent as `ClientMessage::Graphics`. A remote client (the wrapped probe) cannot be asked again, since nothing may be asked in band once the input thread runs. tmux 3.0 and 3.1 have no `client_termtype`, so locally the outer terminal is unknown and the message says so. When tmux does not know the outer terminal's pixel size it reports a 16×32 cell; it is kept, since tmux places its own sixel images with it, and kitty placeholders are scaled by the outer terminal anyway, so the only effect is an image smaller than the panel allows.
  - **Cell size**: `TIOCGWINSZ` pixels over cells (crossterm's `window_size`; OpenSSH forwards them), else the `16 t` reply, the reply winning when both exist and differ (yazi does the same), each only when plausible (2-256 by 4-512 px, at most twice as wide as tall). On a resize the client reads `TIOCGWINSZ` again; a new window cell size means the font changed, so the old `16 t` answer is dropped (it cannot be asked again), and when the decision changes it sends `ClientMessage::Graphics(Support)` before the resize event, so the server lays out with it (Ghostty's font zoom, checked live).
  - **Messages** (`Missing::lines`): lower case, the first line what, the next ones what to do, naming the setting to change (`allow-passthrough`, with `~/.config/tmux/tmux.conf` as the other place tmux reads and `all` marked as tmux 3.4 or later; `enableImages`; `-ti vt340`; `sixel=no`; `image-storage-limit`, which Ghostty applies on a config reload) and the terminal and its version where known. `CORNERCASE_IMAGES=kitty|iterm|sixel|off` in the client's environment overrides the decision and skips the kitty query and the tmux checks, for terminals nothing can recognise (Blink and a-Shell send no XTVERSION) and to turn images off; per client like `COLORTERM`, not a setting, since each client has its own terminal.
  - **Kitty ids and leaving**: `id_hi`, random in 1-255 per client run (`RandomState`, no new crate), is the high byte of every kitty id of that client (`KITTY_LO` the two low bytes), so clients drawing in one outer terminal (tmux panes) do not collide, and the client can delete its own images without the server, whose link may be gone. kitty and Ghostty keep virtual placements and their data across ED 2 and the alternate screen, so on every way out (quit, detach, restart, kill-server, a signal, a remote window giving up, a panic on the main thread) the client writes `a=d,d=I` for both ids, wrapped under tmux, before leaving the alternate screen; a panic on another thread does not end the client, so the hook leaves its images alone. Checked live: after quit, SIGTERM and kill-server, directly and through tmux, Ghostty answers `ENOENT` for the client's ids and still has a control image under another `id_hi`. A killed client leaves its images until the tab closes, and so does one leaving while its tmux window is hidden under `on`, which drops the wrapped deletes like any passthrough (`all` avoids it).
  - **Protocol and log**: `Hello` carries `graphics` and `probe`, one line of what the terminal answered and how long it took, which `server.log` keeps with the decision on the `client attached` line (`images=kitty cell=10x19 tmux=none missing=- id_hi=175 probe="da1=62;22;52 kitty=OK 16t=10x19 window=10x19 registers=- geometry=- tmux=- ms=13"`), so a wrong decision in an untested terminal can be fixed from a log; `protocol::VERSION` is 2.

- **Decoding and encoding** (`graphics/decode.rs`, `encode.rs`, `kitty.rs`, `iterm.rs`, `sixel.rs`, `tmux.rs`): pure functions with no I/O, run on the reading thread (decoding) and on encode jobs (encoding), never on the server loop.
  - **Sniffing** (`decode::sniff`, which needs the first `decode::HEAD` bytes): the format comes from the content, never the name: the PNG signature, `FF D8 FF`, `GIF87a`/`GIF89a`, `RIFF`…`WEBP`; BMP's `BM` alone would take a text file starting with `BMW` for a bitmap (and show `cannot read this image` instead of the text), so it also needs a known DIB header size at byte 14, and ICO's `00 00 01 00` needs at least one entry with a zero reserved byte and 0 or 1 planes. TIFF, AVIF, SVG and the rest stay text or binary. The name (`PNG`, `JPEG`, `GIF`, `WebP`, `BMP`, `ICO`) is `Picture::format`, which the viewer's header shows.
  - **Decoding** (`decode::decode`): `image` 0.25 with only `png`, `jpeg`, `gif`, `webp`, `bmp` and `ico` (+1.2 MB). The decoder is opened first with only a 256 MiB allocation cap, its size read from the header, and a picture over `LIMIT_SIDE` (16384) per side or whose decoded pixels pass `LIMIT_BYTES` (256 MiB) is refused before any pixel buffer exists, as `too large to preview (W×H)`: a 12 KB PNG can declare 50000×50000, and an OOM kill of the server takes every shell with it. The decoder then gets the full limits for its own buffers. Each format's bomb is a test with a crafted file (PNG `IHDR`, JPEG `SOF0`, GIF screen, WebP `VP8L`, BMP header, a PNG inside an ICO); image-webp wraps a 16384-wide lossless header to width 0, so that one is checked at 16383. EXIF orientation is applied (`into_decoder` → `orientation` → `apply_orientation`, which `decode()` alone skips), on the shrunk pixels so a full-size copy is never made, and `Picture::width`/`height` are the size after it, for the header. Animations give their first frame (`from_decoder` on GIF, animated WebP, APNG), as most terminal image viewers do; playing them would need per-window frame pacing. Pictures larger than `MAX_SIDE` (2048) are shrunk once with an area average (`thumbnail`, the fastest on big sources and the right filter for shrinking: 104 ms for 6000×4000 against 314 ms for Triangle), premultiplied when the source is 8- or 16-bit RGBA so transparent edges do not darken (transparent pixels are usually black); grey with alpha and float images are averaged as they are, so a huge one is never converted to RGBA at full size first. Errors are short and lower case, for `cannot read this image: <reason>`: `too large to preview (W×H)`, `this kind of <format> is not supported`, `the file ends too early`, `the <format> data is damaged`.
  - **Fit** (`encode::fit`): `s = min(1, room·cell / size)`, never enlarging (a 16×16 icon stays 16×16 pixels), `cols = ceil(width / cell width)`, at least one cell, with 8×16 assumed when the terminal gave no cell size. It takes the protocol, unlike the first sketch, because each has a ceiling: kitty's diacritics table numbers 297 rows and columns, iTerm2 (and Warp) index image rows in a byte (255), and a sixel's pixels are the size it is drawn at, so its ceilings must shrink the box rather than the bitmap: the terminal's XTSMGRAPHICS geometry (xterm drops what passes its 1000×1000), `SIXEL_PIXELS` (1.2 MP, about 2 MB for a photo) and whole bands (below). Kitty and iTerm2 scale the bitmap into the cells themselves, so their ceilings never change the cells. `Fit` carries the cell size it used, since the iTerm2 payload is padded to exactly `cols·cell width × rows·cell height`, and `encode::Key` (the payload cache's key) holds the whole `Fit`.
  - **Kitty** (`kitty.rs`): the picture is sent as PNG (`f=100`) rather than the zlib-compressed raw pixels (`f=32`/`f=24`, `o=z`) the research started from: the `png` crate's fast mode filters rows before compressing, so it is both smaller and faster (the research's figures, before base64: an 800×589 photo is 806 KB in 6 ms against 1.34 MB in 34 ms, a screenshot 216 KB against 232 KB), no zlib crate is needed, and every terminal that gets placeholders decodes it (Ghostty, kitty and Rio read `f=100`; the bench showed `a=T,U=1,f=100` in Ghostty 1.3.1 and kitty 0.45). RGB when the picture is opaque, RGBA otherwise; it is never flattened, since the terminal blends it on the cell's background itself. It is sent at the fit's pixel size, or the picture's own pixels when those are fewer (the terminal scales into `c×r`, so enlarging would only cost bytes). `kitty::transmit` cuts the base64 into chunks of `CHUNK` (4096) bytes, all but the last a multiple of 4: the first `a=t,q=2,i=<id>,f=100,m=1`, the middle ones only `m=1,q=2` (the spec allows only `m` and `q` on continuations), the last `m=0,q=2`, one chunk with no `m` at all. Every command carries `q=2`: after startup a reply would reach the input thread and be typed into the pane. `encode` ends with the virtual placement, `a=p,U=1,q=2,i=<id>,p=1,c=<cols>,r=<rows>` (always `p=1`, so placing again replaces it instead of adding one, and the terminal never has to choose); `kitty::place` and `kitty::delete` (`a=d,d=I`, which frees the data too) are there for re-placing and cleaning up, unwrapped (callers wrap them for tmux). `kitty::cell` gives `U+10EEEE` with the row, column and high-byte diacritics in every cell, so a cell drawn alone (ratatui rewrites single cells, overlays cut rows) is still complete, and the id's low byte as a 256-colour foreground, which tmux passes as it is (it reduces 24-bit colours when it does not know the outer terminal has them). The table is kitty's `rowcolumn-diacritics.txt`, checked identical to Ghostty 1.3.1's `graphics_unicode.zig`, sorted (Ghostty searches it by bisection); a test checks that every cell, all 297×297 with three high bytes, is one column wide for ratatui.
  - **iTerm2 inline images** (`iterm.rs`): one `ESC ] 1337 ; File=inline=1;size=<n>;width=<cols>;height=<rows>;doNotMoveCursor=1:<base64> BEL`. The payload is exactly the cell box in the terminal's pixels, the picture centred in it like kitty letterboxes, on the window's background, or transparent when it is unknown: terminals disagree on how `width`/`height` scale and on `preserveAspectRatio` (WezTerm and xterm.js let the width win, Konsole stretches), and a payload with the box's exact shape looks the same in all of them. No `name` (some extensions make iTerm2 render the file as a document), no `preserveAspectRatio`, no `inlineMedia` (Konsole plays it as audio); `size` because xterm.js's addon refuses a file without it; `doNotMoveCursor` is WezTerm's and ignored by the rest. Format: PNG while anything is see-through (padding included); otherwise JPEG at quality 85 for a JPEG source, and for the rest PNG unless it comes out more than twice the JPEG, which catches photos saved as PNG or lossy WebP while flat graphics and screenshots stay sharp. The terminal gets PNG or JPEG whatever the file was: WezTerm draws a WebP as a black box and Konsole draws nothing.
  - **Sixel** (`sixel.rs`): `icy_sixel` (pure Rust, +0.1 MB) with Wu's quantiser and Floyd-Steinberg at 0.875 (as good as libsixel to the eye, 25-35 ms for 800 px), at most 256 colours or the terminal's registers (0, unknown, means 256; at least 2). It writes `ESC P 9;1;0 q "1;1;W;H`: square pixels, raster attributes with the exact size (WezTerm and xterm.js crop to them), and P2=1. The picture is laid on the window's background when it is known, so the payload is opaque (Konsole ignores P2: on the bench it painted the transparent pixels of an uncomposited sixel with colour register 0), else pixels under half alpha stay unpainted. Its height is a whole number of 6-pixel bands (`sixel::bands`, in `fit` and in every smaller retry: at most 5 rows less, the width scaled to keep the shape), because Konsole also paints the unused rows of a partial last band, a 4-pixel strip of register 0 under the picture on the bench (img2sixel's and chafa's sixels leave a strip there too). The final `-` before `ESC \` is cut: it moves the sixel cursor a band down, and terminals that leave the text cursor at the sixel cursor would then scroll on the last rows. No DECSDM (`?80`, whose meaning flipped in xterm 369), `?8452` or `?1070`: the renderer positions with CUP inside DECSC/DECRC.
  - **Size budget** (`encode::BUDGET`, 1 MiB): tmux drops a whole DCS longer than its `input-buffer-size` (1 MiB by default), including the raw sixel its native sixel support decodes, which `encode` cannot tell from a terminal of its own, and every payload has to cross the server's 1 s write timeout to remote windows. A sixel over it is encoded again with 64 colours (`sixel::FEWEST`), then, if still over, at `sqrt(budget / size) · 0.9` the scale, at most three times; an iTerm2 image wrapped for tmux only shrinks. Colours go first because a smaller sixel no longer fills its cells (it sits in their top-left corner) while 64 dithered colours look close to 256: a 1271×936 photo (Retina-sized cells) is 1.7 MB with 256 colours and 1.0 MB with 64, which then fits at full size, where shrinking alone left it at 898×661. Kitty needs no budget: each chunk is wrapped on its own and stays far below.
  - **tmux** (`tmux::wrap`): `ESC P tmux;` + the sequence with every ESC doubled + `ESC \`, one wrap per sequence (each kitty chunk, the placement, a delete), never around the placeholder cells, which tmux carries as text.
  - **Payload sizes** (release build, bytes on the wire with base64 and escapes; `~/.cctmp/images/live/encode/measure.txt` has every image): in an 80×40 room at 10×19-pixel cells (an 800-pixel box), a 1738×1280 photo is 1.0 MB as kitty PNG, 161 KB as iTerm2 JPEG and 804 KB as sixel; a 1998×1250 screenshot 278 KB, 94 KB and 265 KB; a 512×512 16-bit icon 159 KB, 64 KB and 140 KB. At Retina-sized 16×34 cells (a 1280-pixel box) the photo is 2.3 MB, 342 KB and 1.0 MB (64 colours), the screenshot 652 KB, 195 KB and 585 KB. Encoding takes at most ~75 ms at 10×19 and up to ~300 ms at 16×34 (a photo's sixel, encoded twice); decoding a 6000×4000 JPEG (450-550 ms) is the slowest step, and it runs on the reading thread. For the same 24×20-cell box at 10×20-pixel cells, chafa 1.18 sends 519 KB for kitty (raw RGBA) and 512 KB for iTerm2 (an uncompressed TIFF) against 159 KB and 30 KB here; sixel costs about the same per pixel (1.5 bytes against 1.7). Kitty's PNG is the heaviest for photos (kitty takes no JPEG), so it is the one to watch over slow links.
  - **Checked live** on the bench (`~/.cctmp/images/live/encode/`, a small crate that draws `encode`'s output the way the renderer does): every format (PNG, JPEG with EXIF orientation 6, GIF's first frame, lossless and lossy WebP, a 16-bit RGBA icon, an 8×8 icon left at 8×8, alpha) in Ghostty 1.3.1 and kitty 0.45 (placeholders), WezTerm 20240203 (iTerm2 and sixel), Konsole 25.12 (iTerm2 and sixel), foot 1.25 and xterm 407 `-ti vt340` (sixel); tmux 3.6 with passthrough on (placeholders in place in Ghostty and kitty), off (blank cells, no tofu), and tmux's own sixel in foot, WezTerm and xterm; side by side with chafa 1.18 for the same boxes, which looks the same.
  - **Dev builds**: `image`, `png`, `fdeflate`, `zune-jpeg`, `image-webp`, `gif`, `icy_sixel`, `quantette` and `palette` build with `opt-level = 3` in dev, like syntect: unoptimised, quantising a 1 MP photo took seconds, which made the tests slow (one sixel test 6.3 s, 1.5 s now) and the dev binary unusable on real photos.

- **Rendering** (`files/disk.rs`, `ui/files.rs`, `app/images.rs`, `server/images.rs`, `server.rs`):
  - **Reading**: `disk::read` sniffs the first bytes (`decode::sniff`) before the binary check (every image holds a NUL) and decodes on the reading thread it already had, so the server loop never decodes: `Body::Image(Arc<Picture>)`, or `Body::Unreadable { format, bytes, reason }` shown as `cannot read this image: <reason>` (logged at info with the path, never pixels). Images may be up to `MAX_IMAGE_BYTES` (32 MiB), text files still 8 MiB: a phone photo is often 10 MB and decoding is bounded by the decoder's limits anyway; the cap is chosen from the head, read first only for files over 8 MiB. Each read takes a new `Picture::id` from a process-wide counter, so the 1 s change check (size and time, as for text) gives an image an agent rewrites a new id, and every cache and every terminal sees a new picture. The `Arc` keeps one decoded copy (at most 2048 px a side) whatever the windows.
  - **The viewer**: the header reads `PNG · 1280×720 · 245 KB` (the original size, before any downscaling); ` ask agent ` pastes `path ` (agents read images from a path) and ` copy ` copies the path; ` open ` is left out, since an editor cannot show it; an image has no lines, so clicks select nothing and the wheel scrolls nothing. The picture is centred horizontally under the header and top aligned, in the body less a column each side, cut to what that window sees (`ui::files::image_room`: a smaller window is cropped, so its picture is fitted to what it shows), and never on the window's last row: iTerm2 makes an image's rows with line feeds and several terminals add one after a sixel, so an image ending there scrolls the whole screen. It is never enlarged (`encode::fit`): a 16 px icon stays small, as it is.
  - **Per window** (`app::Sight` in, `app::Placed` out): `App::draw` takes what the window can do (its `Support`, its visible rect, its background, and for kitty which of its two ids to use and whether that id already holds this picture) and returns what it placed (`encode::Key`, rect, path, payload if ready, whether its cells are on screen), so the frame differs per window while everything else stays shared. A window without a protocol gets `Missing::lines` in place of the picture (muted, wrapped, a blank line after the first, which says what; the next ones say what to do).
  - **Payloads** are made off the loop: `App::payload` looks the key up in a small cache (`images::Payloads`: 8 payloads and 64 MiB at most, the least recently used going first, the last one always kept) and starts a job under `panics::job` when it is missing, answered by `AppEvent::Encoded`; at most two jobs run, and a key that is not started is asked again by the next draw, so dragging the panel's border runs the latest size rather than a queue of every step. A job that fails or panics marks its key failed (the window says so) instead of retrying every frame. Until its payload comes a window shows blank cells: a placeholder text that flashes for 50 ms was worse than nothing.
  - **Dialogs hide the picture** (`Overlay::is_modal`): the image is drawn as plain blank cells while one is open, since the dialog dims the screen with SGR 2, which no terminal applies to an image, and a bright picture behind a dimmed screen looks like a bug. Menus, the search, the keys menu and toasts are drawn over it like over text.
  - **Kitty** (placeholders): the picture's cells are `U+10EEEE` with its row, column and high-byte diacritics (`kitty::cell`), the low byte of the id as a 256-colour foreground, `ForcedWidth(1)`, so they are plain text to ratatui, tmux and every overlay: a menu covers its cells and the image comes back when they are drawn again, at no cost. Each window has two ids, `id_hi << 24 | 0xF0` and `| 0xF1` (`id_hi` random per window, from Detection), and a new picture takes the one not on screen (`server::images::Graphics::sight`), so the new cells always differ from the old and ratatui rewrites every one of them; the id is chosen before the payload is asked for and kept while the picture shows, since it is part of the payload's key. After the frame, the server writes the payload (transmit and the virtual placement) when this id does not hold the picture yet, or holds it smaller than the new fit; when it holds it as large or larger (the panel got narrower, the window smaller), only a new placement (`kitty::place`, ~60 bytes) and the terminal scales it down; while a larger payload is being made the old one is placed larger meanwhile, so a resize never blanks it. Then it deletes the other id. A picture hidden by a dialog or by the compact menu stays in the terminal; it is deleted once the viewer shows no image (another file, the panel closed, another workspace), and the window deletes both ids when it leaves (Detection), since kitty keeps virtual placements across clears and screen switches. A screen reset (resize, attach, a panic while drawing) costs nothing: the cells are drawn again. Inside tmux a transmit never goes out in the same turn as a reset, but 100 ms later (`Graphics::wake` shortens the server's wait): tmux drops a passthrough sent right after the pane is redrawn.
  - **iTerm2 inline images and sixel** are drawn by the terminal over cells it no longer tracks, so ratatui's diff must leave those cells alone and the server must know when something else drew over them. The picture's cells hold a marker (`U+10FFFD`, which nothing else draws) with `CellDiffOption::Skip`, so the diff never writes them. After every widget, overlay and toast, a pass in the same draw (`app::images::owned`) keeps `Skip` on marker cells and resets the others in the rect to `None`, since `set_symbol` keeps `Skip` and a menu drawn there would otherwise never reach the terminal; the picture is owned when every cell is still a marker. `CropBackend::draw` sees every cell ratatui writes, and one inside the shown rect marks it damaged (a menu or toast drew over it, or Konsole and tmux dropped all of it); a reset of the screen does too. After the frame the server sends the payload when the picture is owned, its payload ready, and its key or rect changed or it was damaged: `CSI ?2026h ESC 7 CSI 0m`, printed spaces over every row (ECH and EL do not erase sixel in xterm, and WezTerm keeps the old text under an iTerm2 image, where it shows through transparency), the cursor to the corner, the payload, `ESC 8 CSI ?2026l`, so the blank-then-image never shows where synchronized output is known. While something covers it nothing is sent; the uncovered part stays where the terminal erases per cell, and the whole picture comes back once it is owned again, so a toast costs one more send when it goes. When the picture leaves, its marker cells become ordinary cells that differ from the last frame's, so ratatui writes them and erases it like text; nothing else is needed (both protocols live on the alternate screen and go with it).
  - **Two windows**: everything above lives per window in the server's `Client` (`Graphics`: the `Support`, the background for compositing, the kitty ids and what they hold, what was sent and whether it is intact); the payload cache is shared, and two windows with the same terminal, size and background share a sixel or iTerm2 payload (kitty's carry the window's own id). A window that attaches later gets everything sent to it on its first frame.
  - **Big frames and `cornercase remote`**: payloads are sized for the display, not the file (a full-panel photo is ~100-800 KB), but the server writes each window with a 1 s timeout and drops one that makes no progress. Locally that never happens; through `cornercase remote` the proxy used to copy the socket to ssh's stdout in one blocking loop, so a slow link stopped it reading the socket and the server dropped the window. The proxy now reads the socket on a thread into a channel and writes stdout from another (`remote::relay`), so only the proxy buffers and the server always finishes its write. Payload sizes are logged per window at debug (`images` target), each picture shown at info with its path.

## Issues (`issues/`)

- `Browser` is pure state that returns `Action`s; `App` does the I/O on threads. Answers carry their query and issue key so stale ones are dropped, and lists, people, reads and token checks also the source's epoch, bumped by `App::forget_issues` when its connection goes or changes (disconnect, token removed or replaced, Jira settings changed), so an answer still in flight cannot refill the cache with the old connection or save a token checked against it. Lists are cached in memory and in `issues.json` (titles and metadata only, never tokens).
- GitHub goes through `gh` in the project folder. Shortcut (REST v3), Linear (GraphQL) and Jira Cloud (REST v3) go through `ureq`, capped at 100 issues. People filters go into each tracker's query.
- Tokens come from `SHORTCUT_API_TOKEN` / `LINEAR_API_KEY` / `JIRA_API_TOKEN` or are typed in the app, checked, and saved to `secrets.json` (0600). `issues::Secret` hides them in `Debug`; they are never logged.
- **Starting an issue**: in a repo root, a worktree on `issue-<n>-<slug>` / `sc-<n>-<slug>` / `ENG-123-<slug>` / `PROJ-123-<slug>`; elsewhere a new tab. Shortcut, Linear and Jira issues ask which open project or workspace to use. Then the agent starts with the prompt.
- **Jira** (Cloud only; Server/Data Center use other auth, API v2 and wiki markup): HTTP Basic with `email:token`. The site and email are not secret, so they live in `config.json` (`jira_site`, `jira_email`) and only the token in `secrets.json`; the browser's connect form asks site → email → token (one field, three steps; `SaveJira` saves the first two before the token is checked), settings has a row for each. `jira_jql` is ANDed with the generated JQL (its `ORDER BY` dropped). `/rest/api/3/search/jql` refuses unbounded queries, so a list with no condition at all sends `project IS NOT EMPTY`. Jira Cloud no longer takes names in JQL, so a picked person is `Who::User { id, name }` (the `accountId`); other trackers keep `Who::Person(handle)`. Descriptions and comments are ADF (JSON), turned into Markdown by `jira/adf.rs`; unknown nodes give their text. A `config.json` without `jira_site` was written before Jira, so `config::load` appends `jira` to its `issue_tabs` (once saved, the key exists and hiding the tab sticks). Changing the site, email or filter forgets the cached lists, people and account. Timestamps carry an offset (`+0200`), which `parse_time` applies.
- **Copy URL** uses OSC 52 through `App::host_writes`, because the server may run on another machine.
- Markdown renders with `pulldown-cmark`; code blocks are highlighted with syntect (pure Rust `regex-fancy`), mapping scopes to palette colours so the terminal theme applies. Highlighting is cached and warmed on the reading thread; syntect and its regex crates build with `opt-level = 3` in dev.

## Agents (`agents.rs`, `launch.rs`)

- Config: `agent` (`auto` = the one running in the tab, else ask), `agent_args`, `agent_modes`, `agent_commands`, `prompt` (placeholders like `{url}`, `{key}`, `{title}`), `submit`, `accept_trust_prompts`, `trust_prompt_pattern`.
- `launch::Launch` types the command once the shell is quiet, waits until the agent is in the foreground, has drawn something and its screen is quiet, waits for the trust prompt to be answered (or answers it), then pastes the prompt. Readiness is a heuristic. "Drawn something" means the screen is no longer the shell's screen plus the command's echo (or part of it), compared without whitespace (`Launch::echo`): the quiet second used to count from the echo, so an agent that took over a second to draw (a loaded machine, a cold start) got the prompt before its trust question and read it as the answer (#34). A screen that is not the prompt plus the command (zsh's `RPROMPT` on the same line, a line scrolled off the top) counts as drawn, as before. `AGENT_LATEST` (30 s) still types the prompt into an agent that never draws.
- **The trust prompt is left to the user by default** (`accept_trust_prompts`, off). It is the agent's guard against running a repository's own agent config (project settings, hooks, MCP servers) before anyone looked at it, so answering it for the user would run a hostile repository's config as soon as an issue starts. It used to be on by default, as `auto_accept_trust_prompt`; the key was renamed so every saved `true` (settings save the whole file) falls back to off once, and turning it on again is one click. A per-project "trust this project for agents" was left out: off costs one Enter per issue started, and agents remember the folders already trusted. Whatever the setting, the prompt is detected: a launch that may not answer it parks (`Launch::waits_for_you`) until the agent prints again, which the answer does; its clock restarts from that output, so `AGENT_LATEST` never types into the question, and once the screen is quiet without the question it pastes the prompt. A parked launch is not polled: `App::tick` asks for the 100 ms launch wake-up only for launches that are not parked, since the user may take hours to answer and every wake-up draws every client. Before, a launch with answering off typed the prompt into the question, and Enter picked Claude's highlighted "No, exit". If the user says no, the shell comes back and the launch is abandoned as usual. `trust_prompt_pattern` is matched only against the last 15 non-blank lines of the screen (`agents::asks_trust`), where an agent draws the question, so older output above cannot match; the regex is compiled once per pattern (`agents::TrustPrompt`).
- When answering, the prompt may highlight "No" by default (Claude Code does), so `answer_keys` moves the selection to the "yes" option before pressing Enter.

## Agent status (`activity.rs`)

- Every 500 ms (`WATCH_AGENTS_EVERY`, from `App::refresh`) each pane whose foreground process is Claude Code, Codex or opencode (`agents::detect` on its arguments) gets an `Activity`: working, waiting or idle. For Claude the source is the file Claude Code keeps for each running process, `<CLAUDE_CONFIG_DIR or ~/.claude>/sessions/<pid>.json`, the registry behind `claude agents --json` (its documented interface for status bars): `status` is `busy`, `waiting` (permission prompt, question, dialog), `idle` or `shell` (turn over but a Bash it started with `run_in_background` still runs). `shell` counts as working, like Claude's own agents view: Claude wakes up when the command ends, so it was not done (a dev server left running keeps the tab `◐`). It is its own `Activity::Shell` all the same, which `Pane::status` shows as working (so the UI, the rollups and the notifications are unchanged) and only the commands for scripts tell apart (`Pane::background_shell`, `Pane::state`; see Commands for scripts and agents): an orchestrating agent whose agents leave watchers behind had no way to stop waiting for them (#127). A Monitor that runs a command is a background Bash too, so it gives `shell` (checked live on 2.1.289); one on a WebSocket runs no shell and may leave it `idle`. Its fields are not documented, so a missing file or an unknown value falls back to the title Claude sets (`◐`/`◑`, or braille in older versions, while busy; `✳` otherwise; it stays `✳` when Claude sees `TMUX`, `STY` or `ZELLIJ`), then to idle.
- No hooks and no screen scraping. Hooks mean editing the user's `~/.claude/settings.json` (or shipping a plugin), `Stop` never fires on an Esc interrupt and the permission notification comes ~6 s late; Claude's screen changes too often to match. The session file turns idle within a tick of an interrupt and waiting as soon as a prompt shows.
- `Status` adds done: a pane that went from working or waiting to idle while its tab was not the visible one (`App::visible_tab`: the active tab, unless the compact menu covers the pane) is done until that tab is shown. `watch_agents` clears it for the visible tab on every `refresh`, not only every 500 ms, so a click shows `○` at once. An unknown state counts as idle, so a fresh Claude never looks done.
- A tab shows its most urgent pane (`Tab::status`, the order of `Status`): waiting `!` > done `✓` > working `◐` > idle `○`, before the name. A tab without an agent shows its shell instead (`TabEntry::icon`), in the muted grey: `▸` while a program runs in the foreground of any of its panes (`Tab::running`), `›` at the prompt. Every tab has an icon so their names start in one column: a shell tab used to start two cells to the left of an agent's, and the list read as two indents. Two states rather than one fixed mark, so the icon answers what an agent's does (is it doing something?) and a dev server that died back to its prompt shows at a glance. It is `!Term::shell_in_foreground()`, read when the row is drawn, like the tab's label (an editor started with a command counts as running); caching it on the 500 ms agent reads was tried and dropped: the label already looks up the foreground process on every draw, and the cache only added a field and up to half a second of lag. Grey, never yellow, so a dev server that runs for hours does not compete with an agent working, and no done: every `ls` in a hidden tab would leave a mark. The agents' own glyphs were rejected for the same reason (a `◐` then a `○` means done for an agent and would not for a program), and `▶` because it has an emoji presentation that some fonts draw wider than a cell. Shell icons never reach the workspace, project or group rows. Workspace, project and collapsed group rows show only what needs you (`activity::attention`: waiting or done), right-aligned and before `↓n`; working stays on the tab so the sidebar is not always full of icons. The compact `≡` shows the same for every tab but the visible one (`View::attention`). The agents section (see Layout) lists each agent pane with its own status, not its tab's.
- **Codex** (`activity::codex`, checked live on 0.160.0): waiting while the title starts with `[ ! ] Action Required` or `[ . ] Action Required` (it blinks between the two during an approval); working while it starts with a braille spinner and a space (`⠴ <thread> | <project>`) or while the rollout the context line follows (`context/codex.rs`) is inside a turn (`task_started`, until `task_complete` or `turn_aborted`); otherwise idle (the title is then `<thread> | <project>`, or just the project). Approvals are never written to the rollout, so `!` needs the title; the title's items are configurable (`/title`, `tui.terminal_title`), and without its activity item the rollout still gives working and done. Both rather than one: the rollout alone has no waiting, the title alone breaks when its activity item is removed. Hooks were rejected as for Claude (they mean writing to `~/.codex`).
- **opencode** (`activity::opencode`, checked live on 1.18.35): no status until the job has found its database, read it and told its session apart (a query that fails, or two opencode in one folder, give none, rather than an idle that would turn a working pane into a false done); idle while it has no session yet; working while the newest message of its session is the user's (sent, its reply not written yet) or an assistant message without `time.completed` (an Esc interrupt completes it, with a `MessageAbortedError`; `/compact` is a reply like any other, with `summary: true`), else idle. The session comes from the database the context line reads (`context/opencode.rs`, see Context use), on the same thread. opencode never says it waits for you: a permission or a question lives only in its memory (the tool part already reads `running`), its title stays `OpenCode` or `OC | <session title>` whatever it does, and its log (`log/opencode.log`, shared by every process, no pid) writes `asking` but never the answer, so a pane waiting for you shows `◐`. Rejected: reading that log (a format of its own, cut by `--log-level`, and the reply would have to be guessed from the database), its HTTP API (`/session/status`, `/permission`, which only exists with `--port` and then listens on localhost without a password), and its own notifications (`attention` in its TUI config, off by default and only while its window is unfocused, so cornercase would have to inject a config and report focus). It asks no trust question, so a launch goes straight to the prompt once its screen is quiet.
- Claude Code, Codex and opencode only; another agent plugs in by returning an `Activity` from its own signals (`app::agent_in`). An agent running through `ssh` or in a container is not seen (no local process, no local file).
- **Notifications**: `Pane::update` returns `Waiting` or `Done` once that status has held for `NOTIFY_AFTER` (1 s) and its tab was not shown meanwhile, once per change, so a prompt answered at once stays quiet. `App::notify` sets a toast with the status icon (`<agent> needs you in <project> › <workspace>`, the agent's kind such as `claude` or `codex`, control characters stripped) and queues a `notify::Notification`, which the server encodes per client. Panes of the same agent that settle on the same status in the same workspace on one tick give one notice: the text would be the same, and Ghostty drops a repeat within 5 s anyway. The agent is part of that key, so Claude and Codex in one workspace each get theirs. A pane's state remembers its agent (`activity::Pane::follow`) and starts over when another one takes the pane, so a Codex replacing a waiting Claude without a tick in between still notifies. They go through the outer terminal like OSC 52, so they work over SSH (no `notify-send`/`osascript` on the server's machine).
- The channel is the client's: inside tmux, screen or Zellij it is BEL (tmux drops notification OSCs, passthrough is off by default, BEL goes through); otherwise `notify::detect` trusts the XTVERSION reply when there is one (asked with the colours, so it survives SSH, where only `TERM` arrives; env vars may also be inherited from another terminal), else `TERM_PROGRAM`, `LC_TERMINAL` (iTerm2 sets it for SSH), `TERM`, `KITTY_WINDOW_ID`, `KONSOLE_VERSION`. OSC 777 for Ghostty, WezTerm, foot, Konsole, Warp and Rio; OSC 9 for iTerm2 (its only one); OSC 99 with `o=unfocused` for kitty, Contour and VS Code (VS Code knows only 99); BEL otherwise. Never several, since terminals that know several would show each.
- OSC 9 and 777 end with BEL, which every parser accepts; OSC 99 with ST, as kitty's spec says. `;` in the text becomes `,`: WezTerm, Rio and Konsole cut the body at it, WezTerm drops an OSC 9 holding one. Ghostty on macOS, foot, Konsole and Warp hide notifications while their window is focused; the others show them. `desktop_notifications` (`auto`, a channel, `off`) overrides the channel; the toast always shows. The visible tab never notifies, even while the outer window is unfocused (that would need focus reporting, `CSI ? 1004 h`).

## Context use (`context.rs`)

- A tab running Claude gets a second line, `Opus 5.5 · 23%`: the model and the share of the window used, as Claude's statusline computes it (`round(used / window * 100)`, at most 100). `sessions/<pid>.json` gives `sessionId` (re-read every tick: `/clear` changes it) and `cwd`; the transcript is `projects/<cwd with every non-alphanumeric UTF-16 unit as '-'; past 200 characters cut, plus '-' and a base36 hash>/<sessionId>.jsonl`. Its last `assistant` line (not `isSidechain`, model not `<synthetic>`) gives `message.model` and used = `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`; a later `system`/`compact_boundary` hides the line until the next reply.
- The transcript is read as it grows (the first time, its last MiB), lines scanned backwards to the first reply or boundary, so a quiet tick costs one `stat`. The window is worked out again only when the reply changes.
- No file holds the window, so it mirrors Claude Code 2.1.289's own rule: `DISABLE_COMPACT` with `CLAUDE_CODE_MAX_CONTEXT_TOKENS` gives that; otherwise 1M for models with a native 1M window (Opus 4.7 and later, anything from version 5) or a model setting ending in `[1m]` that names the transcript's model (`--model`, `ANTHROPIC_MODEL`, then `model` in local > project > user settings), unless `CLAUDE_CODE_DISABLE_1M_CONTEXT`; `CLAUDE_CODE_MAX_CONTEXT_TOKENS` for non-Claude models; else 200k, or 1M once past 200k. Variables are the process's (`process::env`) overlaid by each settings file's `env`, as Claude applies them. Not seen: an unsaved `/model` switch, accounts without 1M, the SDK's 1M beta header. Claude's statusline input has the exact numbers but needs a `statusLine` command in the user's settings (rejected like hooks).
- Wide mode gives the tab two rows (`ui::Details::lines`, height `pitch.max(lines)`), with `×` on the first only; compact mode puts the line on the band's third row. The model is cut first and dropped below 4 columns; the percentage turns orange at 75 % and red at 90 % (`usage::Severity::of`).
- What the line shows is three switches in `config.json` (Settings → UI, `settings::Detail`): `model` and `context` (the percentage), on by default, and `memory` (off, see Memory below). `App::tab_details` applies them once into a `ui::Details { model, percent, memory }`, used by the view and by `App::tab_lines`, and `ui::Details::lines` gives the second row when any part is there, so drawing and hit testing agree; with all three off every tab takes one row. 0.6 had one switch, `context_line`, for model and percentage together: `config::load` reads it as `context`, and a file without `model` gets `context`'s value, so a line turned off then stays off. This happens on the JSON before deserializing rather than with a serde `alias`, which would reject a file holding both keys and fall back to all defaults. Plan limits stay in the ` Usage ` modal; showing them under every tab was tried and dropped, since they belong to the account, would repeat the same number in every tab and push out the one thing each tab has of its own.
- Codex context (`context/codex.rs`) was verified against CLI 0.160.0; versioned synthetic fixtures and tagged source links are in `tests/fixtures/codex/README.md`. Associate by the JSONL held open under the agent's `CODEX_HOME/sessions` (or its `HOME/.codex/sessions`), never the newest rollout. Follow only Codex descendants of the foreground process, including npm's `node …/codex/bin/codex.js` wrapper; accept CLI/exec/VSCode source labels, reject subagent metadata and ambiguous root rollouts. A child whose environment cannot be read (a `fork` about to `exec`, a process that just exited) is skipped, never a reason to drop the line. Discovery (`codex::rollout_path`: `lsof` on macOS, every process in daemon mode) runs on a thread per pane, one job in flight, so it never blocks the server loop; the main thread only takes its answer and reads the rollout as it grows. Linux reads `/proc` (children across all threads); macOS uses `proc_listchildpids` / `proc_listallpids` (both return a count of pids, not bytes) and `/usr/sbin/lsof -n -P -a -p <pid> -Fn`. Missing inspection access omits the line.
- **Codex's app-server daemon**: 0.160.0 installs and starts `codex app-server --managed-daemon` (pid in `CODEX_HOME/app-server-daemon/daemon.pid`, parent 1); the TUI talks to it over a socket and the daemon writes every rollout (hence `source: "vscode"`), so no descendant holds one. Nothing links a TUI's pid to its thread (locks, snapshots and the socket carry no pid), so when no descendant holds a rollout the folder decides, only when unambiguous: the daemon's open rollouts whose `session_meta.cwd` is the agent's cwd, written since the pane first saw that pid (the daemon keeps a finished session open ~60 s, so a new Codex in the same folder would otherwise take the old one), exactly one of them, and exactly one native Codex TUI (`argv[0]` named `codex`, no `app-server`) in that folder with that home among all processes (`process::all`). Two Codex in one folder show nothing; after one exits the other comes back once the daemon closes its rollout. `codex -C <dir>` gives a cwd that does not match, so no line. The line appears with the first turn: the rollout is created lazily.
- Codex models come from `turn_context.model` and `thread_settings_applied.thread_settings.model` for the current thread. Usage is `last_token_usage.total_tokens / model_context_window`, rounded and capped at 100%; no lifetime totals, extra cached/reasoning tokens, inferred window or Codex baseline adjustment. `Context.percent` is optional: unavailable/malformed usage shows the model alone. Model switches and compaction clear the old percentage; switching rollouts, replacement, truncation, deletion or process exit resets the reader. Read only complete JSONL lines, starting with a tail of at most one MiB, then bounded incremental batches; validate session metadata at the head. An initial tail without a model omits the line until a model is reported.
- **opencode** (`context/opencode.rs`, checked live on 1.18.35; fixtures in `tests/fixtures/opencode/1.18.35`, rows from a real session with paths replaced): every opencode process shares one SQLite database (WAL), `$XDG_DATA_HOME/opencode/opencode.db`, `opencode-<channel>.db` outside the stable channel, or what `OPENCODE_DB` names. The pane's database is the one its opencode holds open (the foreground process or an `opencode` descendant: `process::open_files`, `lsof` on macOS, like Codex's rollout), read with `rusqlite` (SQLite compiled in, `bundled`, so nothing is needed on the machine) read only, with a 100 ms busy timeout. No row holds a pid, so the folder decides, as for Codex's daemon: the newest session (no `parent_id`, which marks a subagent's; not archived) whose `directory` is the process's cwd and that was updated since the pane first saw that pid, and only while no other opencode holding the same database runs in that folder (an `opencode run` counts too). So the line appears with the first prompt, follows `/new` once it is used, and two opencode in one folder show nothing. The whole job (find, query, parse) runs on a thread per pane, one in flight, started again each refresh, so the server loop only takes answers. The line mirrors opencode's own footer: the newest assistant message with output, `input + output + reasoning + cache.read + cache.write` over the model's `limit.context`, rounded; after `/compact` that is the summary's reply, as opencode shows. The model is the newest message's (a user message names the one picked), so a switch shows the new model without a percentage until it replies. Names and windows come from models.dev's file opencode caches (`$XDG_CACHE_HOME/opencode/models.json`, or `OPENCODE_MODELS_PATH`), 5 MB, so it is parsed only when the model or the file changes; a model it lacks (a custom provider's, whose limits live in opencode's config) shows its id without a percentage. Tests use `test_util::FakeOpencode`: a database built from the fixture schema, with rows written by the test, held by a script named `opencode` that app tests type into a pane, or by `FakeOpencode::start`, a `/bin/sleep` named `opencode` with the database as its stdin, for the tests that call `look` on a process of their own. That one never forks: the script's shell forks for each `sleep` of its loop, and until that child `exec`s it is a copy of the fake (its arguments, its folder, the database on fd 3), which the check for another opencode in the folder rightly counts. macOS' `/bin/sh` is bash, which forks where Linux's dash uses `vfork`, so `two_opencode_in_one_folder_show_nothing` failed there now and then, finding a second opencode after the second fake was gone.
- Codex fake-agent tests use `test_util::FakeCodex`, with a shell imitating the npm wrapper's parent/child topology, and no real model calls. `FakeCodex::serve` starts a fake daemon (a `codex app-server` script holding the rollout, not a descendant of the agent, pid in `daemon.pid`) and `FakeCodex::agent` a TUI that is `/bin/sleep` with `argv[0]` `…/codex` (`Sleeper::named`; a symlink would break multi-call coreutils). App tests cover two sessions sharing cwd and Codex home, session/model changes, compaction and cleanup; UI snapshots cover wide and compact lines, including model-only text.

## Memory (`memory.rs`)

- `memory` in `config.json` (Settings → UI, off by default) ends every tab's second line with the memory it uses: `Opus 5.5 · 23% · 1.2 GB`, or `1.2 GB` alone with the model and context off or in a shell tab. Shell tabs got no row at first (agents are what grows, and a row for a shell's few MB doubles every tab's height), but a dev server, a build or a test run in a shell tab grows as much as an agent, and with the switch on every tab gets the row, so the list keeps one rhythm. Off by default: most people never need it, and it costs a thread every 2 s per pane on screen.
- What: the memory each process holds on its own (`process::footprint`), for each pane's shell and its descendants (`process::descendants`, breadth first over `process::children`, at most 256), summed per tab over all its panes: the figure is what the tab costs, so a split shell beside the agent counts too. macOS reads `ri_phys_footprint` (`proc_pid_rusage`, `RUSAGE_INFO_V0`), the figure in Activity Monitor's Memory column and `top`'s MEM; Linux reads `RssAnon` + `VmSwap` from `/proc/<pid>/status`, its anonymous memory including what was swapped out. Neither counts clean file-backed pages (the program, its libraries, mapped files), which every process maps and the system can drop at any time, so the sum over a tree is close to what the agent costs. The two are not identical (footprint also counts compressed and IOKit memory), but both mean memory only that process keeps.
- RSS (`statm`, `pti_resident_size`) was used before and overstated about twice: it counted Claude Code's 224 MB binary once per process (a fresh Claude showed ~440 MB against ~200 MB of footprint; a session with five `npx` MCP servers 1.26 GB against 0.79 GB), and it fell when macOS compressed an idle agent although the memory was still taken. PSS (`smaps_rollup`) was rejected because the kernel walks every mapping; `status` only reads counters. `process::tests::footprint` measures the test process itself: reading a mapped 64 MiB file must not count and writing 64 MiB must (the only check that catches a constant), written to an anonymous mapping of its own rather than a `Vec`, since macOS' malloc hands back pages another test freed, which were counted already, so other tests could disturb it only by allocating or freeing half of that within the same milliseconds. The mapping needs `rustix`'s `mm` feature, enabled in `[dev-dependencies]` only.
- When: `App::watch_agents` (every refresh) calls `memory::Pane::update` for the panes whose tabs are on screen, while the switch is on: the active project's, or in the tree every unfolded workspace of an unfolded project in an open group (`App::drawn` tells which layout was last drawn). The sum runs on a thread every `memory::MEASURE_EVERY` (2 s), one job in flight per pane, like Codex discovery, so a deep tree never blocks the server loop. Panes not on screen keep their last figure, so switching projects shows an old number for one refresh instead of making the row jump. The tree's gate is tested (two open projects are both measured); that hidden panes are skipped is not, since skipped work cannot be observed without timing.
- `ui::memory_size`: binary units, whole MB below 1024 MB, then GB with one decimal. In a narrow column the model is cut first, then dropped (`MIN_MODEL_WIDTH`); the percentage and the memory stay. At the default width (26) with both on, a two-digit percentage leaves no room for the model.

## Plan usage (`usage/`)

- ` Usage ` sits under ` Settings ` (wide: its own row; the workspaces column puts ` Files ` on that row under ` Issues ` and ` TODO ` right-aligned under ` Changes `, and keeps a blank row level with ` Quit `, so its separator and ` Issues ` stay level; compact: the footer is settings | usage | quit in thirds). It opens `Overlay::Usage`; ` done `, `Esc` or `Enter` close it.
- One section per agent (`usage::Agent`: Claude Code, Codex), in that order (opencode has none: it uses whichever providers the user set up, its own Zen and Go subscriptions among them, each billed apart, and cornercase asks none of them for usage), each with its title and plan, its status on the right (`loading…` or `updated 2m ago`), its error under the title and its bars: thin `━` lines in the severity's colour on a track of the same line in the line colour. Only agents whose command (`agent_commands`, else the name) is an executable file, by path or on the server's `PATH` (`agents::installed`), get one; when neither is, both show, so each says why it could not run. A modal taller than the screen is cut at the bottom, the ` done ` row stays.
- **Claude** (`usage/claude.rs`): Claude Code's SDK control protocol: `claude -p --setting-sources '' --no-session-persistence --input-format stream-json --output-format stream-json --verbose`, then an `initialize` and a `get_usage` control request on stdin; the `control_response` for `get_usage` holds `subscription_type`, `rate_limits_available` and `rate_limits` (`limits[]` with `kind`, `percent`, `severity`, `resets_at`, `scope.model.display_name`; `spend` for extra usage). No prompt, no tokens, ~3 s. Claude handles OAuth (credentials file, Keychain, refresh), so cornercase never reads or refreshes a token; `GET /api/oauth/usage` was rejected for that (and refreshing the token ourselves can log Claude out). `--setting-sources ''` keeps the user's hooks from firing, `--no-session-persistence` keeps the probe out of the session list, `--bare` does not work (API key only).
- The protocol is not documented as a CLI interface, so parsing is lenient (unknown fields and kinds pass, a missing `limits[]` falls back to `five_hour` / `seven_day`, an unknown `severity` comes from the percentage), but `rate_limits_available` must be there, and `rate_limits` too when it is true, so a changed answer shows as unavailable instead of "no plan limits". Every failure shows `usage unavailable: <reason>`.
- **Codex** (`usage/codex.rs`, checked live on 0.160.0): `codex app-server` (stdio JSON-RPC, lines without the `jsonrpc` field): `initialize` with `clientInfo`, the `initialized` notification, then `account/rateLimits/read` (`excludeResetCreditDetails`, so it skips a second backend call). ~1 s, no Codex thread is created, no daemon starts (the stdio server is the probe's child and dies with it), no model call; Codex reads its own login from `CODEX_HOME`. The answer has `rateLimits` (`planType`, `primary` / `secondary` with `usedPercent`, `windowDurationMins`, `resetsAt` in Unix seconds, `credits`) and `rateLimitsByLimitId` (one per metered bucket, `codex` first, others suffixed with their `limitName` or id). Windows are named by their length, never by their slot: 300 minutes is `session (5h)`, 10080 is `week`. Unix-second resets need no date parsing. Not logged in answers the error `codex account authentication required to read rate limits`; it becomes `Report::notice` (a grey `not signed in · run codex login`, not a red error), so a Codex installed once and never used does not look broken. The rollouts' `token_count` events also carry `rate_limits`, but only as of the last turn (a window that reset since still shows its old percentage), so they were rejected.
- On demand only: opening the modal starts one probe per shown agent on a thread (never two for one agent at once) that answers with `AppEvent::Usage(agent, result)`; nothing polls. The last answer per agent stays in memory (not in the session file) and shows with its age while a new one loads. Probes run on the server's machine with `agent_commands`, are killed after `usage::TIMEOUT` (10 s; `App::usage_timeout` in tests); Claude's strips `activity::CLAUDE_SESSION_ENV` like `Term::spawn` and inherits `CLAUDE_CONFIG_DIR`, Codex's inherits `CODEX_HOME`.
- Reset times are relative (`resets in 2h 13m`, `3d 4h`): local time would need a time zone database, and the server may sit in another zone than the client anyway.

## Settings (`config.rs`, `settings.rs`)

- Tabs: Worktrees, Agents, Issues, UI. Every change is saved to `config.json` at once. The prefix key row is the one that captures a key instead of editing text (see Keyboard shortcuts). File: `$XDG_CONFIG_HOME/cornercase/config.json`, or next to the socket when `CORNERCASE_SOCKET` is set (so tests never touch the real one). Missing keys take defaults; a corrupt file means all defaults.

## Terminals (`term.rs`, `emulator.rs`)

- The emulator is libghostty-vt: it answers terminal queries (DSR, DA, DECRQM, kitty keyboard…) that programs like fzf and nvim wait for, and reflows on resize.
- Its types are `!Send`, so the emulator lives on the server's main thread; the reader thread only forwards bytes. Query replies go out from `on_pty_write`, ordered with the output that asked.
- Every write to a PTY (keys, pastes, launches, query replies) goes through one writer thread per pane (`term::spawn_writer`), in order: once a terminal's input buffer is full, a write to a program that doesn't read blocks, and on the server loop that froze every client (a long paste or `cornercase send` into a pane running `sleep`). Each pane queues at most 16 MiB (`term::MAX_QUEUED`): past that `Term::write` refuses and returns `false`, `send` and `keys` answer that the program is not reading, and typing or pasting in the UI shows a toast instead of losing keys silently. A write is taken whenever the queue is below the limit, so one long paste still goes through. Only Linux blocks a write to a full terminal; macOS drops what the terminal cannot take, so its queue never fills, and the App test that needs a full pane runs on Linux only. Pastes drop `\x1b[201~` from the text (`term::bracketed`), so a paste cannot end itself and type the rest.
- Cells keep palette indices so the outer theme applies. The client asks the outer terminal for its colours (OSC 10/11/4, then XTVERSION, then DA1 as an end marker) before starting the input thread, and every emulator uses them as defaults.
- cwd, name and arguments of the PTY's foreground process group leader come from `process.rs`: `/proc` on Linux, `proc_pidinfo` / `proc_name` / `sysctl(KERN_PROCARGS2)` on macOS (with `getpeereid`, the only `unsafe` and the only use of `libc`). In a pipeline the leader may be dead (`process::alive`), so the shell is used instead. Agent launch and detection depend on it.

## Keys and mouse (`keys.rs`, `mouse.rs`)

- Special keys, and all keys once the program enabled kitty, go through Ghostty's encoder; a legacy encoder handles the rest. The client asks the outer terminal for kitty's disambiguate level, so `Ctrl+Enter` / `Shift+Enter` keep their modifiers.
- Pane mouse events are forwarded only when the program enabled a mouse mode, in its encoding, relative to the pane, clamped to its edges.
- **Paths**: a simple click on a path in the active pane opens it in the files panel, even in a program that reads the mouse (see Files panel); a drag that starts on one still reaches the program.
- **Selection:** when the program did not ask for the mouse, press-drag-release selects with Ghostty's selection and copies via OSC 52, with a toast. Programs' own OSC 52 writes are forwarded to the outer terminal too (reads and primary-clipboard writes are dropped).

## Keyboard shortcuts (`shortcuts.rs`, `app/shortcuts.rs`, `ui/keys.rs`)

- **Opt-in, behind one prefix key** (#31): the mouse stays the default and nothing changes for whoever does not turn it on. It is for people whose hands stay on the keyboard, and for clients the mouse does not reach (some mobile SSH apps, a terminal with mouse reporting off).
- **The prefix** is `prefix_key` in `config.json`, set in Settings → UI → **prefix key** by pressing it (`Settings::capturing`: the next key is taken, `Backspace` turns it off, `Esc` keeps the old one). No default is shipped: `Ctrl+b` is tmux's (and `e2e::ctrl_b_reaches_the_shell`), `Ctrl+Space` switches the input source on macOS, `Ctrl+]` needs AltGr on Spanish and German layouts. It must be `Ctrl` or `Alt` with a character, or a function key with any modifiers; `Ctrl+c`, `Ctrl+d` and `Ctrl+z` are refused, since every one of them would open the menu instead of reaching the program. Known clashes (`Prefix::clash`: `Ctrl+b`, `Ctrl+a`, `Ctrl+Space`, …) are named in the row and the notice, not refused. `Prefix::normal` makes a key match however a terminal sends it: the legacy bytes for `Ctrl+4`…`Ctrl+7` are `Ctrl+\` `Ctrl+]` `Ctrl+^` `Ctrl+_`, an upper-case letter is the letter with `Shift`, and `Shift` on a symbol is dropped (it made the symbol). The string form (`ctrl+]`, `alt+k`, `f12`) is what the file and the row show.
- **Where it works**: while no overlay but a right-click menu is open, also while a panel's field has the keys (the files search, the changes filter, a TODO field: none of them takes `Ctrl` or `Alt` keys anyway). Dialogs keep it: they already take arrows, `Enter` and `Esc`, and the settings must get the key to capture it.
- **The menu** (`Overlay::Keys(Option<Group>)`) works like Neovim's which-key: the prefix opens it, the next key runs an action or opens a group (`f` find, `g` git, `w` workspace), whose menu replaces it. A key is either an action or a group (`shortcuts::Step`), never both, so nothing waits for a timeout. `Esc` or a key the menu does not list closes it and is dropped, since it was meant for the menu; the prefix again closes it and types the prefix in the pane, for programs that use that key; a paste closes it and goes to the pane. A click on an entry runs it, a click elsewhere closes it; entries naming several keys (`1-9`, the arrows) are not clickable. It is drawn at the bottom of the pane, in columns filled top to bottom, over the whole screen when the pane cannot hold it, and dims nothing (like the row menus, it belongs to what is behind it). Like every overlay it is shared by every client. It shows at once: which-key's delay (draw only after ~300 ms without a key) needs a timer wake-up and was left for later.
- **What the keys do** (`shortcuts::items`, `App::shortcut`): tabs (`n` `p`, `1`-`9`), workspaces (`]` `[`) and projects (`}` `{`) wrap around; workspaces skip one being removed, projects follow the sidebar's order (every group open) and skip one closing. Arrows focus the pane on that side among the shown ones (`split::beside`: the nearest that shares part of that edge, then the one sharing most). `a` jumps to the next agent pane, in the agents section's order after the focused one, whose status needs you (waiting or done), or toasts `no agent needs you`. `x` asks first: `Overlay::ClosePane` in a split tab, `CloseTab` for its last pane (a key is easier to press by mistake than `×`); `w x` asks like the compact `×`, and a worktree gets the removal dialog. A panel opened from the keyboard takes the keys where it has a field, or the mouse would be needed right after: `f f` and `f w` open the files panel with its search focused in that mode (closing an open file, `files::Panel::search`), `g d` focuses the changes filter, `t` opens a new TODO field; `f e` only opens or closes the files panel, `g b` opens the changes and their branch picker. `g` outside git and a split without room toast why. Restart, kill-server and closing a project were left out (destructive and rare), and so was remapping the actions: the menu is on screen, so there is nothing to memorise.

## Client / server (`client.rs`, `server.rs`, `protocol.rs`)

- The server owns the PTYs so shells outlive the UI. The client starts it if needed (`cornercase server`, its output going to `server.log`, see Log).
- One server per socket, guarded by `flock` on `server.lock`. The server calls `setsid` and ignores SIGHUP.
- The server renders, the client only writes frames. Input travels as serialized crossterm events. Several clients mirror each other; the shared size is the last used client's (attach, key, paste or mouse other than a bare move), like tmux's `window-size latest`, so a hung client (a phone whose SSH dropped) never shrinks a new one. Ping/pong would not catch that: the hung client is a healthy local process. Smaller clients get the frame cropped by `CropBackend`.
- **When the server draws** (`Server::due`): a frame is drawn when an event other than PTY output arrived (input, a client, a job's answer, a request, a timeout wake-up), when a pane on screen printed (`App::shows`) and `FRAME` (16 ms) has passed since the last frame, and at least every `TICK` (500 ms). Output in a hidden tab draws nothing: the sidebar's icons and `↓n` come from `refresh` and show within a tick. A visible pane printing without pause gets at most ~60 frames a second, counted from the last frame that showed output (`printed_at`), not from any frame: a key draws at once and its echo, a moment later, draws at once too instead of waiting a frame. Host writes (OSC 52, notifications) go out in their own `Step::Flush` every turn, framed or not. A draw that panics sets `changed`, so the screen is rebuilt on the next draw (forcing an immediate turn instead would spin while a draw keeps panicking). The session is observed at most every `SAVE_EVERY` (500 ms), since building `App::state()` looks up every pane's cwd and the `Saver` waits 2 s anyway. Before, every batch of events drew every client and built the state (#25).
- Every shell gets `CORNERCASE=1`; a client seeing it refuses to start (no nesting).
- Every shell loses Claude Code's per-session variables (`activity::CLAUDE_SESSION_ENV`): a server started from inside Claude Code would otherwise make every pane's `claude` a child of that session and expose its messaging token. An explicit list, not a `CLAUDE_CODE_*` prefix, so user settings like `CLAUDE_CODE_USE_BEDROCK` and `CLAUDE_CONFIG_DIR` pass through.
- `Hello` carries a protocol version and build id, and the notification channel of the client's terminal; a server from another build rejects the client. Keep `ClientMessage::KillServer` and `ServerMessage::Rejected` as the first variants (`protocol::tests::compatibility`).
- Socket: `$XDG_RUNTIME_DIR/cornercase/server.sock` or `$TMPDIR/cornercase-<uid>/server.sock`; `CORNERCASE_SOCKET` overrides it. Paths must fit in 108 bytes.
- **The socket's folder must be the user's alone** (`protocol::check_socket_dir`): a real folder, not a symbolic link, owned by the user and not writable by group or others; it is created `0700` when missing. The client checks it before connecting or starting a server, `kill-server` before connecting, the server before binding, also under `CORNERCASE_SOCKET` (a name without a folder is checked in the current folder). The refusal suggests removing the folder only on the default path, which is cornercase's own; under `CORNERCASE_SOCKET` it asks to change the variable, since that folder may hold other files. Without it, another local user could create `/tmp/cornercase-<uid>` first (no `XDG_RUNTIME_DIR` nor `TMPDIR`, as in some SSH sessions and containers) and pose as the server: read every key and send a `Restart`. Read access for others is allowed, since connecting needs write access to the socket file.
- Both ends check the peer's uid (`protocol::check_peer` on `process::peer_uid`: `SO_PEERCRED` on Linux, `getpeereid` on macOS): the client refuses a server of another user, and the server drops another user's client, which a loose umask could otherwise let in.

## Remote windows (`remote.rs`, `client.rs`, `ui/remote.rs`)

- **`cornercase remote <destination>`** (#104) runs the window locally and attaches it to the server of another machine: `ssh -T … -- <destination> sh -c '<PATH>; exec cornercase proxy'`, and the protocol goes through ssh's stdin and stdout instead of the socket. The user's own `ssh`, so their config, keys, agent, `ProxyJump` and `ControlMaster` apply and cornercase never handles a credential; `--` ends ssh's options, so a destination can never be read as one. Nothing in the protocol needed the socket: frames, OSC 52 and notifications already went through the client, and the colours and the notification channel come from the local terminal in `Hello`. `ssh -t host cornercase` already worked but ends with the connection and puts one more terminal layer on the remote side.
- **`cornercase proxy`** (hidden, like `server`) prints a banner line, `cornercase-proxy <protocol> <release>`, reads the client's first message, and only then connects (starting the server like a client does, `client::connect_or_start`), so a client that refuses the version starts nothing there. Then it copies bytes both ways; the socket's end ends it, and its stdin's end shuts the socket's write side, so the server sees the client go. The banner is a text line rather than postcard so that any future version can read it; the client skips other lines first (`BANNER_LINES`, `BANNER_BYTES`), since some shell rc files print in non-interactive shells, and reads it byte by byte through the `BufReader` it then keeps for the protocol. The socket folder and peer checks stay, since the proxy is a local process of the same user there.
- **Versions**: `Hello`'s build id is the binary's modification time, so two machines never match (and are often not the same platform). The client attaches only when the banner's protocol and release equal its own, and says which side to update otherwise (`Error::RemoteOlder` / `RemoteNewer`, from `update::newer`); a cornercase from before the proxy fails with clap's `unrecognized subcommand` (`RemoteTooOld`), a missing one with sh's 127, or 126 and `No such file or directory` from bash, which is macOS' `sh` and says so for a path that is not there (`RemoteMissing`). With a terminal, an older remote is offered `cornercase update` through `ssh -t`. The proxy replaces the build in the forwarded `Hello` with its own (`remote::rebuilt`), so the server's check still means what it means locally: the server must come from the binary that answers. A server from an older build there is offered a restart like locally, through `ssh <destination> cornercase kill-server`, with `restart::confirmation(None)` (asking the old server for its list would take another ssh connection).
- **PATH**: a command run through ssh gets a short `PATH` without the login shell's profile, where the install script's `~/.local/bin` and Homebrew's folders are usually added. The remote command appends those, `~/.cargo/bin` and `/usr/local/bin` to the `PATH` (after it, so the user's own order wins) and `--command` replaces `cornercase`, put in the script as is so `~` and `$HOME` expand. The script is single-quoted for the login shell, which may be fish or zsh, and run by `sh`.
- **Reconnecting**: a remote window does not end when its link does (`Received::Ended`, or the server's `Restart` after an update, which it never `exec`s for). It keeps the last screen and draws a notice over it (`ui::remote`: the rounded dialog, ` quit ` as a grey pill, written cell by cell to the backend so the blank cells inside cover the old screen, which ratatui's diff would skip). Attempts run on a thread (`Incoming::Linked`, numbered by `generation` so a late answer for a dropped link is ignored): at once, then after 1, 2, 4, 8 and every 15 s (`backoff`), the countdown redrawn on the second (`until_next_second`). A link counts as healthy only once it showed a frame (`Retries`): the banner comes before the proxy reaches the socket, so a proxy that fails after it (a socket folder it refuses, a server that does not start) would otherwise reset the count and run ssh back to back; the notice then shows the remote's error. ssh errors are retried and shown (the last of the 20 stderr lines it keeps, `remote::Stderr`); a version mismatch, a missing cornercase or a rejection ends the window (`remote::fatal`). Once linked, the client sends `Hello` again and the server, which counts it as a new client, clears and redraws everything. `Esc` or a press on ` quit ` gives up, a detach and not an error. The sidebar's ` Quit ` (`Detached`) and `kill-server` (`Shutdown`) still close the window.
- **Noticing a dead link**: a laptop that sleeps or changes network leaves a TCP connection that nobody closes. ssh's `ServerAliveInterval=5` and `ServerAliveCountMax=3` end it within ~15 s; they override the user's config (the command line wins in ssh), which was preferred to a heartbeat in the protocol, since an old server would not answer one. `ConnectTimeout=10` bounds each attempt. Reconnects add `BatchMode=yes`: a password or passphrase prompt would read the terminal the window holds in raw mode. The first connection is made before the window opens, on the plain terminal, so it can still prompt (ssh asks on `/dev/tty`; its stderr is piped and kept for the error).
- **The client loop** (`Window`): one channel (`Incoming`) for terminal input, server messages, link attempts and signals, so the main thread can draw the notice and take `Esc` while no server is there. Messages to the server go through a writer thread per link (a hung ssh blocks it, not the loop). The input thread polls (`event::poll`, 100 ms) and stops when `attach` returns (`Threads`), waiting at most 300 ms for it: a thread left in `event::read` after a rejection read the terminal's answer to the next window's colour query, and the client hung blank after the `[y/N]` (locally too, now and then). The wait is bounded because crossterm spins on a terminal that hung up. Its signal thread is closed there too (`Handle::close`).
- Left for later: `--remote` for the commands for scripts and agents (they would go through the same proxy), and several servers in one sidebar (the server renders the whole screen, so the client would have to merge them).

## Panics (`panics.rs`, `server.rs`)

- An uncaught panic on the server's main thread ends the process, and every shell with it (`Term::drop` kills them), so `Server::serve` runs each `Step` under `catch_unwind` (`Server::contain`): the refresh, the answers to requests, the draw, the save and each event. The step that panicked is dropped, the loop goes on, and `App::report_bug` shows `cornercase hit a bug, see server.log` (`Error::Bug`'s text) with a red `✗` for `BUG_FOR` (6 s). Each panic still has to be fixed where it happens; this only keeps the shells alive.
- `App` keeps whatever the step had changed. A panic in input or drawing also resets the interaction (`App::reset_interaction`: overlay, compact menu, hover, drags, selection, the TODO field, the filter's focus), since a dialog that panics while it draws would otherwise freeze the screen for good. A background one (refresh, save, job answers, PTY output) does not, because one that repeats every tick would close every dialog as soon as it opens. A panic while drawing also starts every client's screen over (`reset_screen`), since ratatui's buffer is left half drawn. Saving the session and exiting was rejected: it kills the shells just the same.
- Background jobs that something waits for run under `panics::job`, which turns a panic into `Err(Error::Bug)`. A busy dialog (creating a worktree, installing an update, checking a token, starting an issue) cannot be closed, so a job that never answered would leave `kill-server` as the only way out; issue lists, people, details, usage and changes would stay loading, and a worktree being removed would stay `removing…` (a panic in its job counts as a refusal and puts the row back). `↓n` counts a panic as 0 for every workspace it checked, like a git that fails, so an old count does not stay. The branch list and unchanged lines need nothing (nothing waits for them); memory and Codex discovery already see the dropped sender (`Disconnected`) and start over.
- The server replaces the panic hook (`panics::log_to_stderr`; stderr is `server.log`, see Log): a timestamped `ERROR panic:` line with thread, location, message and a backtrace (`Backtrace::force_capture`; release builds keep function names, not lines). The first panic at a location is written in full, later ones there without the backtrace and only at 2, 4, 8… times, so one that repeats every tick cannot fill the disk. It writes with `writeln!` and ignores errors: `eprintln!` panics when writing fails, and a panic inside the hook aborts.
- Panics must unwind: with `panic = "abort"` in any profile every contained panic would kill the server again, so `panics.rs` does not build without `cfg(panic = "unwind")`.
- Not contained: a panic inside a libghostty-vt callback (`on_pty_write`, `on_clipboard_write`) crosses an `extern "C"` frame and aborts, so keep those callbacks trivial; a crash in Ghostty's Zig code is no Rust panic. A draw that panics for a reason the reset does not touch leaves the screen blank, while the shells keep running.

## Log (`log.rs`, `app/trace.rs`)

- **Who reads it**: whoever fixes a bug, most often a coding agent told to look at the log. So it is a timeline of what the server did, detailed enough to turn into steps or a failing test; the user only sees it through `cornercase logs`. Before (#114) the server wrote only panics and about 15 failures, and bugs were found by reproducing them by hand.
- **Where**: `server.log` next to `session.json` (`$XDG_STATE_HOME/cornercase`, else `~/.local/state/cornercase`), or next to the socket when `CORNERCASE_SOCKET` is set (`log::path`). It used to sit next to the socket in `$XDG_RUNTIME_DIR`, which is cleared at logout and reboot, so the log of the crash that matters was gone. The client opens it as the server's stdout and stderr (early failures still land there), and `log::start` reopens it and `dup2`s it onto stderr, so panics, a stray `eprintln!` and Ghostty's own output share the file and the rotation.
- **Format**: one line per event, `2026-10-07T21:09:51.482Z INFO  worktree: add done ms=812 branch=fix-login`: UTC time (local time needs a time zone database; `log::Stamp` does the calendar by hand), level, target (`server`, `app`, `ui`, `control`, `launch`, `activity`, `worktree`, `changes`, `git`, `issues`, `files`, `images`, `usage`, `update`, `log`, `panic`), a message, then `key=value` fields; a value with spaces, quotes or control characters is quoted with Rust's escapes, so a line never breaks. Panic reports are the one exception: their first line has the time and `ERROR panic:`, and the message and backtrace follow on lines of their own, since a backtrace escaped onto one line cannot be read. Text rather than JSON lines: it reads well in a pane with `tail -f`, and `grep` and agents take it as is.
- **Own writer, not `tracing`**: `log::info!` and friends (`warning!`, since `warn` clashes with the built-in attribute) check the level, format the line on the caller and `try_send` it to a writer thread through a bounded queue (4096 lines); a full queue drops the line and the writer says how many it dropped, so a stuck disk never blocks the server loop. Rotation has to move stderr with the file, which `tracing-appender` cannot do, and spans were not needed: `log::Job` gives a background job its start, end, duration and error. A job logs at its level; a failed `Info` one becomes `WARN`, and a `Debug` one that took a second or more (`log::SLOW`) becomes `INFO`, so slow git runs stand out without debug.
- **Size**: past `MAX_BYTES` (8 MiB) the writer renames the file to `server.log.1` (replacing the older one) and starts a new one, `dup2`ing it onto stderr again, so the log stays under 16 MiB however long the server runs. When the rename fails the file is emptied instead, with a line saying why, so the cap holds anyway. The panic hook's throttling stays.
- **Levels**: `info` by default, cheap enough to be always on; `CORNERCASE_LOG=debug` (read by the server when it starts) adds every event the loop handled (keys as their name only, `a character` for text; mice without moves; pastes as their length), connections, frequent jobs (the diff every second, `↓n`, the files panel) and frames slower than 16 ms. A config key was left out: it is a switch for a bug hunt, set when starting the server.
- **What is logged**: the server's start (version, build, pid, OS, socket, session path, level) and stop, clients attaching (size, the terminal's XTVERSION name, now sent in `Hello`, the notification channel, whether its background is known), rejected and gone, the shared size changing, kill-server, restart and signals; the restore (how many projects, complete or not, each tab that failed and why) and saves (debug); every command for scripts with its safe fields (`Command::fields`) and its answer or refusal with the time it took and how a wait ended; each step of a `Launch` (stage before and after, bytes written, abandoned); every agent status change per pane, and each notification and the channel it went out on; background jobs; shell exits with their status; menu actions, moved rows and panes, renames, settings changed (keys only), issues started; the errors toasts show; panics and the step they hit, and any loop step slower than 100 ms.
- **Changes are found, not announced** (`app/trace.rs`): after every step that can change the app (a refresh, input, a request, a job's answer; not PTY output, drawing or saving) `App::trace` compares the hierarchy (groups, projects, workspaces, tabs, panes, with their parent and phase) and the focus, overlay, side panel, compact menu and toast with what it saw last, and logs what opened, closed, moved or changed phase, closed ones from the inside out. One place covers the UI, the commands and background answers alike, so a new code path cannot forget to log a tab it opens. It is a merge of two sorted lists of ids, with labels read only for new items (a workspace's label reads `.git/HEAD`), so a step costs about 6 µs with 80 items (release build). The same diff feeds `cornercase events` (see Commands for scripts and agents): it yields `Change`s, of which the log takes what opened, closed, moved or changed phase, and the events what opened, closed, changed agent state or ended a program. It runs while the log is at `info` (the default) or someone follows events.
- **Never logged**: typed characters (debug names only the other keys, such as `Enter` or `Esc`, and says `a character` for the rest), pasted text (only its length), PTY output, screen contents, prompts, issue texts and titles (the branch of an issue's worktree carries a slug of its title, and is logged like any branch: it is the workspace's name, its folder and its label everywhere else), search queries, TODO texts, agents' messages, tokens and environment variables. Commands log what they carry as sizes or yes/no (`send` its bytes, `start` whether it has a prompt, `wait --until text` without the pattern, `read --last-message` whether it found one), and a request that cannot be parsed logs only its size, since serde's error may quote it. Paths and the names of groups, projects, workspaces, tabs and branches are fine: they say where something happened, and the log stays on the user's machine, readable only by its owner (created `0600`, and set back to it when an older log is reopened). `e2e::the_server_log_tells_what_happened_but_never_what_was_typed` types, pastes and sends markers at debug level and checks the log has none of them.
- `cornercase logs [-n N] [--follow] [--path]` reads the file directly (no server needed): the last lines, from `server.log.1` too when the new file is short, then follows it across a rotation (`log::Follower` reopens when the inode changes or the file shrinks). The agent skill names it, so an agent debugging cornercase knows where to look. Left for later: the client's own errors (they still reach only its terminal) and a `bug-report` bundle.

## Commands for scripts and agents (`cli.rs`, `control.rs`, `app/control.rs`, `app/events.rs`)

- `clap` (derive) parses every command, the old ones included; `cornercase` alone still opens the UI and `server` is hidden. Help texts go in `about`/`help`/`after_help` attributes, never `///`. Features: `std`, `derive`, `help`, `usage`, `error-context`, `suggestions` (no colours, no wrapping). Exit status: 2 for wrong usage (clap's), 1 for errors and timeouts (the message says which). A `requires` pointing into an exclusive `#[group]` is satisfied by any member of the group (it conflicts with the one given), so `--remove-worktree` uses `conflicts_with_all` instead.
- One request per connection: `ClientMessage::Request(json)`, answered by one `ServerMessage::Response(json)`, both after the existing variants (`protocol::tests::compatibility`). JSON, not postcard, so a command and a server from different releases still work together after `cornercase update`: unknown fields are ignored (`#[serde(default)]` everywhere) and an unknown command answers an error naming the server's version (`Command::NAMES`, checked before parsing). Requests skip `Hello`'s build check. A server from before them reads `InvalidData` and answers `Rejected`, which the command turns into "too old, restart it". The connection is an ordinary client without a size, so it gets no frames and never counts as a use (it never changes the shared size). `events` is the one request answered by a stream (see Following events).
- Ids come from the app's counter, so they last one server run. - **Programs ending**: `Term::job` (the foreground process's pid and its name as `status` gives it, `Term::current_job`) is read on the same 500 ms reads, only while someone follows events (`None` otherwise, so nobody pays for it, and a job left over from a past subscriber cannot end in front of a new one). The job ended when the shell is back in the foreground or another pid took its place (`cargo build && cargo test`), but not when the same pid `exec`s, which only renames it. A program that runs for less than one read may not show; `wait --until shell` stays the exact way to wait for one. There is no exit code: the program is the shell's child, not cornercase's. A pane's own shell exiting is its `closed`.
- **The stream** keeps the protocol: the `events` request is answered once like any other (`{}`, or the error for an unknown pane), then each event is one more `ServerMessage::Response`, and the server ends it with `Detached` once every `--pane` closed (ids are never reused within a run, so nothing more could come) or with `Shutdown`/`Restart` when it stops; the command exits 0 on those and 1, saying so, when the connection just ends. No new message variant was needed, so the protocol tests did not change; a server without `events` answers that it has no such command (`Command::NAMES`), one from before the commands is "too old", and the one-answer commands are untouched (`client::ask_on`, which `client::follow` reuses for the first answer). A snapshot of the current state at the start was left out: `status --json` is that, and the help says to start `events` first and read `status` after.
- **Slow readers never block the server**: the loop only queues messages for a client's writer thread, and each client's `Outbox` counts what is queued (the writer takes one off after each write). Past `EVENTS_QUEUED` (1024) a streamed event is dropped and counted instead of queued, and once the queue has room again a `dropped` event with the count goes first, at the next answer step even with no new event, so a script knows to catch up with `status`. Disconnecting at once was rejected: a script that is told it lost events can catch up and go on, one that is cut off has to restart as well. A reader that stops reading altogether still meets the 1 s write timeout every client has, which closes the connection, so a stuck reader costs one thread and the bounded queue until then, and the command says the connection ended.
- `skills/cornercase/SKILL.md` (Agent Skills format) is what teaches agents: installed with `npx skills add usecornercase/cornercase-terminal --skill cornercase -g`, printed by `cornercase skill` (`include_str!`), never installed by cornercase (like hooks). It stays short and points to `cornercase --help`.
- A panic must not leave a command waiting forever: its timeout lives in the server too. `Requests::open` lists the clients still owed an answer; after every contained panic `Server::contain` calls `App::answer_lost_requests`, which answers `Error::Bug`'s text to each of them that has no pending entry left (the request panicked while it was handled, or `check_requests` lost the entries it had taken out). Pending ones keep waiting, so whatever answers an entry takes it out of `pending` before doing the work that can panic (`worktree_ready`, `worktree_gone`); one left behind would wait for an answer that never comes.
- Whoever reaches the socket can type into every shell; the docs page says so for sandboxed agents.

## Updates (`update.rs`)

- Release builds only (`debug_assertions` off), so `cargo run` and tests never call GitHub. The server asks `releases/latest` when it starts and then every hour (`update::CHECK_EVERY`, `check_updates` in config). Unauthenticated, GitHub allows 60 requests an hour per IP, so hourly leaves room for many servers behind one address; a refused check is only logged and the next hour tries again. A newer one shows ` ↑ x.y.z ` at the end of the settings row and a toast; a later release found before updating replaces it and toasts again, the same one stays quiet. The dialog shows every `CHANGELOG.md` section after the running version up to the release, newest first, so a skipped release's notes are not lost: `CHANGELOG.md` is a release asset (`extra-artifacts` in `dist-workspace.toml`), downloaded only once a newer release is found (never by `cornercase update`). Releases without that asset, or a download that fails, fall back to the `## Release Notes` part of the release body. Scrolled by wheel or ↑/↓.
- Updating downloads `cornercase-<target>.tar.gz` and its `.sha256`, unpacks with `tar` next to the binary, runs `--version` on it (a binary that cannot run here never replaces a working one), then renames it over the old one. Homebrew installs (`/Cellar/`…), a folder we cannot write and unknown platforms get a command to copy instead. Homebrew's is `brew update && brew upgrade cornercase`: `brew upgrade` refreshes taps only when the last refresh is older than `HOMEBREW_AUTO_UPDATE_SECS` (a day by default), so on its own it often answered that the release cornercase had just announced was not there. The check still reads GitHub's latest release, not the tap's formula, although the formula is pushed about a minute after the release: a check that falls in that minute is rare, and trying again later fixes it.
- **`cornercase update [--check] [-y|--yes]`** (`client::update`) does the same from a shell: `update::install_latest` (check, then `update` or the command for `Install::Command`, which it prints and exits 1 without running), then, if a server is running, asks `RESTART` (`--yes` skips; no terminal and no `--yes` means no restart) and sends `ClientMessage::Restart`. It never attaches. Debug builds refuse unless `CORNERCASE_RELEASES_URL` is set (the e2e tests serve a fake release and update a copy of the binary). `--check` exits 0 either way, so 1 stays for errors. A same-version server from another build (after `brew upgrade`) is left to the client's `[y/N]`.
- **Before a restart, say what stops** (`restart.rs`): every restart (` restart now `, settings' ` restart `, `cornercase update`, `cornercase restart`, a client rejected by another build) first lists what runs in the terminals, from a `status` `Report`: agents counted by what they do, other programs by name and place, and panes at their shell prompt and the pane that asks left out (`PaneInfo::at_prompt`; a server from before it is told apart by the program's name). The app builds the Report itself, and the commands ask the running server, the old one: requests are JSON and skip the build check, and they wait at most 1 s (`client::running_now`), so a hung server or one older than requests falls back to `restart::generic` and never hangs the command. The text leads with what stops, not with "your session comes back", which read as if nothing was lost (#92). The installed step's dialog has ` restart now ` and ` later `, and `Enter` still restarts (the user's call); its message is one short line and the list goes in the scrollable notes area, since the message row is three lines high and the release notes were already shown before installing. `Term::shell_in_foreground` is false for a pane started with a command (`/bin/sh -c 'exec $EDITOR …'` from the changes panel, `Term::interactive`): its program runs in the shell's pid, so comparing pids alone called an editor idle, here and for `wait --until shell`. An agent always counts as running. The dialog's list is built when it opens and every `WATCH_AGENTS_EVERY` while it is open, not on every frame, since a `status` report looks up every pane's process. `cornercase update --yes` prints the list before restarting, and it and `kill-server` print what they stopped. Waiting until no agent is working is `--when-idle` (below).
- **Restarting on demand**: the settings modal has a grey ` restart ` left of ` done ` (`ui::settings_restart`, `settings::Action::Restart`), and `cornercase restart [-y|--yes]` does it from a shell. Both take the update's path: the button opens `Overlay::Restart`, the update dialog's view with its own title and message, listing what stops and refreshed like the installed step (`Overlay::lists_running`), and ` restart now ` sets `App::restart`; `take_restart` hands the server the replaced binary after an update, else `current_exe`. The command shares `client::restart_if_confirmed` with `update`, so it asks the same `[y/N]` with the same list and prints what it stopped; without a server it says so and succeeds, like `kill-server`. Before, the only restart without an update was `kill-server`, which closes every window instead of bringing them back. It sits in settings, not in the footer next to ` Quit `, where a slip would stop every agent.
- **Restarting once no agent is working** (#142, `cornercase restart --when-idle`, `update --when-idle`): every restart stops every program, and an agent in the middle of a turn loses the turn (its tool call, its build) even though its conversation resumes, so whoever runs several long agents could not take a release without watching for the moment they were all idle. A script could `wait --all --until turn-over` then restart, but an agent can start a turn between the two; the server instead restarts in the same step it sees every agent stopped.
  - **A request**: `restart-when-idle` (JSON, with `timeout`) is a pending `Stage::Restart` in `App`, checked by `check_requests` after `watch_agents` like the other waits. JSON rather than a new `ClientMessage`: a server from before it refuses an unknown command by name, which the command turns into `the running cornercase server is too old to wait for its agents`, whereas a postcard variant it cannot decode gets `Rejected`, which reads as another build. A command of its own rather than a field of a `restart` request, for the reason `last-message` is one: an older server would drop the field and restart at once. The plain restart stays `ClientMessage::Restart`, which older servers understand.
  - **Stopped** is the rule of `--until turn-over` (`Condition::TurnOver`) on every pane with an agent: idle, done, waiting for you, or a Claude Code turn that is over with only a background shell left (the issue's choice: waiting means the turn needs a person anyway). Also held (`App::holding`): a launch still typing (`start`, `send --enter`, `new-tab --command`), unless it is parked on a trust prompt, which waits for a person like `waiting`; a pane running an agent that got input in the last 2 s (`INPUT_HOLDS`: a prompt typed in the window shows as busy in the status file only once the agent took it, up to a read later); and a submission the agent has not reacted to within 10 s (`Term::submitted`, the reaction check of `wait`). It fires only on a refresh that has just read every agent's state (`App::watched == now`), so the decision is never older than its own step, and answers with that moment's `status` Report, which the command prints as what it stopped. Programs that are not agents (a dev server, a build) never hold it, since they may run for days and the confirmation already names them; neither does an agent cornercase cannot read. opencode never says it waits for you, so one at a permission prompt holds it until the timeout. The pane the command runs in never holds it, as `wait` refuses to wait on its own pane: an agent running `update --when-idle` in its turn would wait for itself; the restart stops it like any program.
  - **The server** takes `App::restart` after any step (`Server::step`) and leaves the loop at once, so no event (a key, a `send`) is handled between the check and the restart; `shutdown` sends the answers still queued before `ServerMessage::Restart`, so the command reads its answer first. A command that gets `Restart` without an answer (someone else restarted meanwhile) counts it as done; `Shutdown` (`kill-server`) is an error, since nothing comes back by itself.
  - **Giving up**: `--timeout` answers `timed out after …: the agent in pane N has not ended its turn, so the server keeps running` (status 1); a command that is interrupted closes its connection, and `App::forget` drops its pending restart like a wait.
  - **The window says so**: while a restart is pending, every window shows `↻ restart pending until 2 agents end their turn` with a ` cancel ` button (`ui::ToastIcon::Restart`, `ui::ToastButton::Cancel`, beside ` undo `), so nobody starts a long turn by surprise. Toasts last 2 s, so this one is not timed (`Toast::lasts`): `App::show_pending_restart`, after `check_requests`, puts it back whenever no other toast shows, keeps its count current and drops it once nothing is pending; a toast that comes meanwhile (an agent needs you) shows for its own time first. ` cancel ` answers every pending restart `the restart was cancelled in the window` (status 1), since whoever sits at the window may not see the command's terminal (a script, an agent, another machine). A mark in the footer or on the settings row was rejected: the toast is where the window says things, and covering a corner of the pane while it waits is the price of nobody missing it.
  - **Confirming**: the `[y/N]` is asked when the command starts, not when the restart comes: nobody sits at a prompt for an hour, and the answer covers what the list names (the agents resume, the other programs stop). The question is `Restart it once no agent is working?`; `--yes` skips it and works without a terminal, and no terminal without `--yes` does not restart, as before. `update --when-idle` installs first, then waits, so the release is on disk however the wait ends, and the restart reaches the new binary the usual way (the clients `exec` their own replaced file).
- `ClientMessage::Restart` (last variant) makes the server save and send `ServerMessage::Restart`, like ` restart now `, so attached clients come back, even when `update` ran inside one of its panes (it prints everything first). A server from before it cannot decode it and answers `Rejected` (`protocol::tests::compatibility`), so `client::restart_server` falls back to `KillServer`, whose clients just exit.
- The running server keeps the old code. ` restart now ` saves the session, sends `ServerMessage::Restart(path)`, and each client `exec`s its own executable (`current_exe`, read at start; the update replaced that file), never the path in the message, which starts a new server that restores the session. A new client rejected by an older server asks `[y/N]` on the plain terminal before running `kill-server`.

## Saved session (`state.rs`)

- Groups (name, icon, colour, collapsed), projects (with their group's index and whether they are folded), workspaces (with their changes base and fold), tabs, panes (cwd, and the agent conversation to resume), split layouts, custom names, active children, column widths (and the stacked line and the agents section's height), the changes panel (open, tab) and whether the TODO or files panel is open, in `$XDG_STATE_HOME/cornercase/session.json` (or next to the socket). The TODO list is not in it (see TODO panel). Processes are not restored; each pane gets a new shell in its folder.
- Saved only once the state is stable for 2 s, so the burst of `Exited` events at logout does not save an empty session.
- Only a fresh server restores, on its first client's `Hello`. Missing folders are skipped. `VERSION` is 5; older versions are migrated: versions 3 and 4 are read as is (a version 3 file has every project ungrouped), then, like versions 1 and 2, every project but the active one is folded.
- A tab whose shell cannot start (a folder it may not enter, no PTY left, a `$SHELL` that is gone) is left out whole, also a split one, and the restore goes on: its workspace and project stay, so `+ Tab` can try again, a toast names the projects (`could not restore n tabs (…), see server.log`) and `server.log` has, per tab, the folder that failed and the cause: `Error::SpawnShell` puts both in its message, like `RunGit`, since `thiserror`'s `Display` leaves out a `#[source]`, and `cornercase new-tab` or `split` into such a folder answer the same text. `App::restore` returns whether every tab came back. When one did not, the server copies `session.json` to `session.json.bak` before its `Saver` can write the smaller session over it; an older `.bak` moves to `session.json.bak.1` first, so a second incomplete restore with other failing tabs cannot overwrite the only full copy. Keeping an existing `.bak` instead (a review suggestion) was rejected: after one incident every later one would keep a stale copy. If the copy fails the `Saver` still saves: it writes to the same folder and disk, so what breaks the copy breaks the save too, and holding it back would lose every later change of that server run. Stopping at the first failure was the bug (#24): it dropped every project after it and then saved that. The fallback shell opens in the current folder when no project came back, as when there is no session, or when the restore was incomplete and no shell came back at all (`App::has_terms`). A session saved without tabs (closing the last tab keeps the workspace) comes back as it was, without it.
- **Agents resume their conversations** (#28, `resume_agents` in `config.json`, Settings → Agents, on by default): a pane that ran Claude Code or Codex comes back in the same conversation instead of a bare shell, since finding it again by hand with `claude --resume` was what a restart cost most. `App::watch_agents` (every 500 ms, every pane) keeps `Term::resume`, a `state::AgentState`: the agent's kind, its conversation (`context::Pane::conversation`: the `sessionId` of `sessions/<pid>.json` once its transcript has content, or the id of the Codex rollout the context line follows, which Codex creates with the first turn) and its mode, read from the process's arguments (`agents::mode_of`), so an agent started in plan mode comes back in plan mode whatever the settings say now. A conversation with nothing in it is not kept: `claude --resume` on it fails with `No conversation found`. The pane saves it in `PaneState::agent`; once the shell is back in the foreground it is forgotten, so an agent that was quit comes back as a shell. The field is optional, so `VERSION` stays 5: a bump would make an older cornercase drop the whole session, and an older one ignores the field. On restore, `App::resume` types `agents::resume_line` (`claude <args> --resume <id>`, `codex resume <args> <id>`, the command and extra arguments from settings, the mode from the saved state) with `Launch::command`, like `new-tab --command`; it waits for the shell to be quiet, nothing else, since the agent then waits for the user anyway: the resumed agent is idle, and what it was doing is not started again. The restored conversation is kept until the agent shows up with it, or for at most `RESUME_GRACE` (30 s, `Term::resuming`): until the command is typed the shell is in the foreground, and an agent that is slow to start has no session file yet, so a state saved meanwhile (2 s of quiet is enough) would lose it, and a restart then would not resume. A resume that fails (`No conversation found`) is forgotten once the grace runs out. Its JSON in `status` (`PaneInfo::resumes`) lets the restart texts count `n agent conversations resume in their tabs` instead of the `claude --continue` hint, which stays for a server from before it and with the switch off. Off by default was rejected: the agent comes back idle, so resuming costs nothing but the screen, and a resumed agent in a dangerous mode was already running in it. Reading the agent's own arguments to resume with them was rejected: they may hold a prompt, which would be sent again.
