# Design decisions

Why cornercase works the way it does, area by area. The rules every change follows are in [AGENTS.md](AGENTS.md).

## Layout (`ui.rs`)

- `sidebar` in `config.json` lays out the lists (wide mode only; below 90 columns the compact menu below applies to every value): `projects_on_top` (the default since 0.9.0, `ui::Sidebar`'s `#[default]`, so unknown values fall back to it), `workspaces_on_top`, `side_by_side` and `tree`. One column was made the default because it gives the panes the most room; a `config.json` that names `side_by_side` keeps it (settings save the whole file, so anyone who changed any setting before 0.9.0 keeps three columns). App tests pin `side_by_side` in `new_app`, since their geometry helpers assume it; `tests/e2e.rs` lays out its geometry with `Sidebar::default()`, so e2e covers the shipped default.
- Side by side: projects (32), workspaces (26), pane (after one blank column). Columns are always present so PTY sizes do not jump. Borders drag to resize (double click resets), within `MIN_COLUMN_WIDTH` and `MIN_PANE_WIDTH`; `Widths::fit` squeezes them on small terminals. Widths are saved in the session. PTYs follow the drag live.
- **Stacked sidebar** (`projects_on_top`, `workspaces_on_top`): one column of `Widths::projects` holds both lists, split by a line that drags (`Border::Stack`; `Widths::stack` = rows of the top section, `None` = half, each section at least `MIN_STACK_SECTION`), with one footer anchored at the bottom (issues and changes, files and todo, settings, usage, quit). `stacked_layout` fills the same `Areas`, so drawing and hit testing are shared; `Areas::sidebar` and `Areas::workspaces` are the two sections, so the wheel scrolls the list under it. Column borders are drawn from their `Areas` rects, not from `Block`s, so a stacked column gets one full-height border.
- **Tree** (`tree`): one column on the same frame and footer as the stacked layouts (`ui::one_column`, `ui::tree_layout`, `Areas::tree`) with one list, `ui::TreeRow` rows from a plain `ui::TreeShape` that `App::tree_shape` builds and `View::tree` carries: group headers, projects, for an unfolded project its workspaces and `+ new workspace`, for an unfolded workspace its tabs and `+ tab`; `+ new project` is the sticky button. Content starts at `2 + 2·depth`. The arrow (`▾`/`▸`, two cells) folds a project or workspace on release (`RowDrag::fold`, so rows still drag); the rest of the row activates it and unfolds it; a group header folds anywhere, as elsewhere. One row holds the `▌` and the surface: the active tab, else its nearest shown ancestor (`ui::tree_active_row`); the active project and workspace are bold white. Folded rows show counts and `activity::attention`; open ones leave it to their tabs. `+ tab` under another project switches to it; `+ new workspace` asks for that project without switching (the form carries its id, and switching behind a form the user may cancel would change the pane). Drops follow the other lists' rules on one row list (`ui::tree_drop`): the row under the pointer counts as its owner at the dragged row's level, a project lands after a whole project block, workspaces and tabs stay in their parent; the landing line takes the dragged level's indent. The App learns the tree is on from `Areas::tree`, never from the config (below 90 columns the layout is compact whatever the setting), and keeps the last drawn layout in `App::drawn` (its `Areas::tree`), so `follow` reveals the active row again when the layout changes. `View::tree` labels only what is unfolded: a tab's label looks up processes and a workspace's reads `.git/HEAD`.
- **Folding** (`Project::collapsed`, `Workspace::collapsed`, saved in the session; only the tree draws them): new projects and workspaces start unfolded. `follow` unfolds the active project and workspace, and in the tree its group, when the focus changes; a click on a row and `goto` (search) do too, for when the focus stays the same. Other layouts leave a collapsed group alone, as before. The first follow after a restore (`followed` still default) unfolds nothing, so saved folds survive.
- Lists scroll by item with the wheel, show ` ↑ n more` / ` ↓ n more`, and keep the `+` button sticky at the bottom. The scroll follows the active item only when it changes (`App::follow`), otherwise the wheel could never move away from it.
- The active row (project, tab, a collapsed group holding the active project, the tree's marked row) gets a surface background (palette 236, or 254 on light themes) and a cyan `▌` in the column's first cell over the row's full height (a tab's second line, a compact band), so every list shares one selection rail on the left edge. `draw_rail` and the tree lines only draw on blank cells, so text pushed left in a narrow column wins over them. Colours use palette indices so they work without truecolor; the brand purple is index 99.
- **Lines** (column borders, the stack and footer separators, split dividers, the changes panel's rules, tree lines, the usage track) take `View::line()`: palette 239, or 250 on light themes, a step quieter than the muted grey, so structure recedes behind text. Hover and drag still light borders and dividers cyan.
- **Tree lines**: tabs hang from their workspace, in the workspaces list and in the tree: `├` before each tab, `└` before `+ tab`, `│` on a tab's other rows (its second line, a compact band), below a compact workspace's name and on a landing line among them (`draw_guide`, `among_tabs`, `tree_among_tabs`). In the tree they sit in the workspace's arrow column; projects and workspaces keep only their arrows, since lines at every level made the tree busy.
- **Empty panes**: a workspace without tabs centers `no tab open` and `+ tab opens a shell here`. With no project at all the pane shows the logo (the favicon's corner and cursor in half blocks, purple 99 and cyan), the wordmark, the tagline and `+ new project opens a folder`, or the words alone when the pane is too short (`draw_welcome`); it needs an empty project list, not just no active project.
- **Grey text** (titles, the footer, the search field, arrows, notes) is `View::muted`, never `Color::DarkGray` directly: `ui::muted` keeps the theme's bright black (ANSI 8) when `HostTheme::muted_is_readable`, else palette 243 (245 on light themes). Readable means its WCAG contrast with the background is at least 2:1, or the background is unknown (nothing to compare with, so as before). Some themes make bright black the background or close to it: Solarized Dark (1:1), Warp's adeberry (#2b2b2a on #1d2022, about 1.15:1, the footer and arrows vanished), Nord (1.7:1); One Dark (2.5:1), Dracula (3:1) and Gruvbox (4:1) keep theirs. A known background with an unknown bright black also gets the fixed grey: Warp answers OSC 11 but not OSC 4, and the 256-colour greys are not themed (the surfaces rely on that too). The changes panel's `View` carries the same colour.
- A hovered project, workspace, tab or group row is filled edge to edge with palette 235 (255 on light themes), one step between the background and the surface (`View::row_background`). The active row keeps its surface. No hover fill while an overlay is open or a border or divider is being dragged. The site's palette tints 235 like 236 (`site/src/lib/term/palette.ts`), so it stays between them, and 239, the line colour, so it stays between the surface and the muted grey.
- **Compact mode** below 90 columns (`ui::compact_layout`): a top bar (` ≡ `, `project › workspace › tab`, then ` ± `, ` ▤ `, ` ☐ `, ` ⌕ ` right-aligned; ` ± ` only in git workspaces and ` ▤ ` only with a project, so their slots are left of ` ☐ ` and an empty one merges into the breadcrumb) and a full-screen menu showing one column at a time. Every clickable item is a 3-row band (`Areas::pitch`). Both columns' areas share one rect and `Areas::shown(nav)` blanks the hidden one, so drawing and hit testing reuse the wide-mode code.

## Dialogs (`ui.rs`)

- Dialogs, menus and the toast have rounded borders (`BorderType::Rounded`); a title sits after one border cell (`╭─ settings ─`), bold in the default colour, so it reads as the dialog's heading rather than part of the border.
- A dialog (form, confirmation, picker, settings, issues, usage, update, group style: `Overlay::is_modal`) dims everything behind it (`Modifier::DIM` on the whole buffer before it is drawn), so it reads as on top. A menu or the search does not: they belong to what they were opened from. DIM leaves backgrounds alone, so surfaces stay.
- Lists inside overlays (menus, picker, issues, search results, a settings pick, settings rows) mark the selected row like the sidebar: surface background, a cyan `▌` in its first cell and bold text; a hovered row takes the hover fill. The filled cyan bar they had was loud, and two of them lit at once (the selected row and the hovered one). The active tab of a tab row (settings, issues, the changes panel: `tab_style`) is cyan bold on the surface.
- Dialog buttons are pills on the surface (`dialog_button_style`): the submit one cyan bold, the others grey; hover fills them cyan or grey. Without a background they read as coloured words, not as something to click.

## Hierarchy (`project.rs`)

- Optional group > project (a canonicalized folder) > workspace (the project folder, or its own git worktree) > tab > panes. Every level has an id from one counter; menus, forms and background jobs refer to ids, never indices.
- Labels: custom name, else folder name (project), branch or `default` (workspace), foreground program (tab).
- **A tab's program** (`term::program`): a known agent (`agents::detect`) gives its kind; for an interpreter (`node`, `bun`, `deno`, `python`, `python3`, `ruby`) the whole argv is matched, for anything else only `argv[0]`, so `less claude` stays `less`. An interpreter whose first non-flag argument is a script (contains `/` or has a script extension, no whitespace, and no `-e`, `--eval`, `-p`, `--print`, `-c` or `-m` before it, so modules and inline code keep the interpreter's name) gives the script's stem: npm installs run `node /…/bin/codex`. Linux `comm` is the main thread's name, which recent Node renames to `node-MainThread`; that becomes `node`. Its PTY test runs a copy of `/bin/bash` named `node` (`comm` comes from the executed file; a symlink to dash would do on Linux, but macOS names the process after the target).
- Closing kills processes; removal waits for the shell to exit, never synchronous. A pane goes when its reader hits the PTY's end (`Exited`) or, on any `App::refresh`, when `Term::exited` finds the shell reaped (`try_wait`), whichever comes first. Both, because the PTY's end only comes once every process has closed the terminal: one that left the shell's session and ignores SIGHUP (`nvim --embed` outliving its UI, `nohup`, `setsid`) would keep the tab as `?` forever. Like tmux, the pane goes with the shell; the reader thread and the master's fd stay until that process exits. `Term::kill` skips a reaped shell, since portable-pty signals the pid unconditionally and it may have been reused. Closing a project asks first (`Overlay::CloseProject`), since it stops every shell in it, agents included; a tab or a plain workspace closes at once in wide mode and asks first in compact mode. Closing the last tab keeps the workspace; closing the last workspace keeps the project.
- **Groups**: one level, no nesting; a new one goes last. A project holds `group: Option<u64>`; the projects column is `ui::sidebar_rows` (loose projects first, then per group a gap, the header and, unless collapsed, its projects), which drawing, hit testing and `App::follow` share. A collapsed group holding the active project gets the `▌` on its header. Deleting a group (the `×` on its header, or its menu) asks first (`Overlay::DeleteGroup`) and only ungroups its projects. Icons are a fixed set of one-cell symbols (`ui::GROUP_ICONS`, no emoji or Nerd Font glyphs, whose width varies); colours are palette indices (`ui::GROUP_COLOURS`, no greys, black or white, which vanish on some themes). A new group gets the next icon and colour, then opens the icon and colour modal, whose clicks apply at once.
- Menus are one `Overlay::Menu { actions: Vec<MenuAction> }`, labels from `App::menu_label`; a submenu (move to group) replaces the menu at the same spot. `+ new project` opens a menu (open project / new group).
- **Reordering** (drag): project, group, workspace and tab rows act on release. A press grabs the row (`App::row_drag`, a `Target`); leaving the row's rect, or releasing outside it, makes it a drag, otherwise the release is the click (activate, collapse), so a cancelled drag changes nothing and the compact menu stays open while dragging. `×` and `+` still act on press. Releasing outside the list, `Esc` or another button cancels; no hover while dragging.
- Where it lands (`ui::sidebar_drop`, `ui::workspace_drop`) comes from the pointer and the layout without the line, so the line never feeds back: the row under the pointer gives its slot (before it when above the dragged row, after when below); a group with its projects and a workspace with its tabs are one block; a group header takes a project in first (last when collapsed); a gap is the end of the section above; tabs stay in their workspace, workspaces in their project (moving a shell or a worktree elsewhere was left out). The line goes on a neighbouring gap, on the line above or below the visible rows at an edge, else as an inserted one-line `Landing` row; it is indented where a grouped project or a tab would start.
- Holding a drag on `↑ n more` / `↓ n more` scrolls one item every `AUTO_SCROLL_EVERY` (150 ms); `App::tick` shortens the server's wait meanwhile. Moving only changes `Vec` positions (`project::move_before` keeps the active index on its item), so ids, menus and jobs are unaffected and the session saves the order as is; worktrees found outside cornercase go last.

## Splits (`split.rs`)

- A binary tree (`Leaf` / `Split { dir, ratio, first, second }`). Right-click in a pane opens split/close/right-click-passthrough; this works even when the program captured the mouse, since almost no program uses the right button.
- A vertical divider is followed by a blank column so text does not touch it. Inactive panes are dimmed (configurable). A left click on an inactive pane only focuses it. Dividers drag like column borders.
- A pane can end up with no room (a divider dragged to the edge over a nested split, or a small client). Its PTY is still sized at least 1×1, and mouse events for it are dropped (`pane_cell` returns `None`), never clamped into an empty range: `clamp` panics when `min > max`, which drops the event and shows the bug toast (see Panics).

## Search (`search.rs`)

- One global search across groups, projects, workspaces (label and branch) and tabs (label and their workspace's keys). Ranking: exact, prefix, substring; ties by kind (group, project, workspace, tab) then sidebar order. A group result expands it and activates its first project. Results are recomputed on every key and draw; the query is never kept after closing.

## Folder picker (`picker.rs`)

- Starts in the parent of the active project. `Enter` goes into the selected folder, or opens the current one when nothing is selected. Typing a path walks it; a paste goes through the same path (e2e opens projects this way). Folders are read on the main thread.

## Worktrees (`worktree.rs`)

- Only when the project folder is a repo root. The name is the branch; the slugged name is the folder, under `<worktrees folder>/<repo>/<slug>` (`~/.cornercase/worktrees` by default). `git worktree add` runs on a thread and answers with an `AppEvent`.
- Every linked worktree of the repo shows up, also ones created outside cornercase (`App::refresh`, throttled to once a second).
- Removing asks first, runs `git worktree remove` (offering `--force` when git refuses) and never deletes the branch.
- `.worktreeinclude`: files matching it **and** ignored by git are copied into a new checkout. Matching is delegated to git (`ls-files`, `check-ignore`).
- **Commits to pull** (`↓n` at the end of a workspace row, before the `×`): every 3 s a thread per project counts `HEAD..@{upstream}` in each workspace and answers with `AppEvent::Behind`; it runs `git fetch --all` first once `fetch_minutes` (default 5, 0 turns all of it off) have passed. One thread per project at a time. Git never prompts (`GIT_TERMINAL_PROMPT=0`, empty `GIT_ASKPASS`, `SSH_ASKPASS_REQUIRE=never`); failures count as 0.

## Changes panel (`changes/`, `ui/changes.rs`)

- Git workspaces only: ` changes n ` next to ` issues ` (` ± ` in the compact bar) opens a fourth column right of the pane (full screen in compact mode). Its border drags; its width is `Widths::changes` (`None` = half the free space, at most `DEFAULT_WIDTH`).
- Tabs: uncommitted (`git diff HEAD` + untracked), commits (`git diff <merge-base> HEAD`), all (`git diff <merge-base>` + untracked). The base is `Workspace::base` (saved per workspace) or the default branch: `origin/HEAD`, else `main`/`master`. Comparing from the merge-base keeps commits made on the base later out of the diff.
- Git runs on a thread, one job at a time, every second while it or the files panel is open (`Panel::watched`, for its marks) and every 3 s while closed (for the button's count). Flags matter: `--no-optional-locks` and `-c diff.autoRefreshIndex=false`, because a plain `git diff` rewrites `.git/index` (takes `index.lock`) even with `--no-optional-locks` and would fight an agent's `git commit`. `--relative` keeps paths inside the workspace folder. Untracked files are read directly (never `git add -N`), capped at 1 MiB, NUL in the first 8000 bytes means binary; a symlink shows its target path, like git, never the file it points to. The branch list and "unchanged lines" also run on threads and answer with `AppEvent::Branches` / `AppEvent::Gap`.
- The job hashes git's output; an unchanged hash answers without a diff, and files whose patch section did not change are reused, so highlighting runs only for what changed. syntect costs ~150-200 µs per line, far more than computing the diff.
- Rendering: lines paired delta-style (word tokens, changed share ≤ 60 %) get word emphasis; each hunk side (context + removed, context + added) is highlighted separately. Tints blend the host background with palette red/green when the client has `COLORTERM=truecolor` and the background is known; otherwise palette colours, and on dark themes only the `▎` bar, coloured numbers and word emphasis (palette greens and reds are too loud as line backgrounds).
- **Filter** (`changes/filter.rs`, pure): ` ⌕ ` left of the panel's `×` opens a field under the tabs (the header grows a row, so the summary and the base selector stay) that filters files by path only; searching the lines was tried and dropped as not useful. While it is focused (`Filter::focused`, and only while the panel shows and no overlay is open) keys and pastes go to it, like the global search: `Enter` keeps the filter and unfocuses, `Esc` or its `×` closes and clears. Any press outside the panel gives the keys back and keeps the query; a click on the field or ` ⌕ ` takes them again; closing the panel unfocuses it. Each word is an include, or an exclude with `!`; a file stays if it matches any include (or there is none) and no exclude, by its path or its old path. A word without `*`/`?` is a substring of the path; with them a `.gitignore`-like glob (no `/`: any path component, a trailing `/` only folders; with `/` or a leading `/`: the whole path, also everything under it; `*` and `?` stop at `/`, `**` crosses it). Smart case per word. Folds are untouched; typing resets the scroll. Shared by clients, never saved; switching tab or workspace keeps it.
- Hunk actions on hover: open (new tab running `/bin/sh -c 'exec ${VISUAL:-${EDITOR:-vi}} "+$1" "$2"'`), ask agent (pastes `path:lines ` into the workspace's agent pane, found with `agents::detect`; without one it copies the reference), copy (the hunk as a patch, OSC 52). Viewed marks are keyed by the file's patch digest, so they clear when the file changes.

## TODO panel (`todo/`, `ui/todo.rs`, `app/todo_panel.rs`)

- ` todo ` (no count: a number there would always be lit and say little) opens a panel in the changes panel's column (`Areas::changes`, `Widths::changes`, `Border::Changes`); only one of the three (changes, TODO, files) is open at a time, and opening the compact menu closes them. One global list, the same in every project: lists per project and per workspace, and starting an agent from an item (` ▶ `, a worktree or tab per item), were built and dropped as more than a TODO list needs.
- **Storage**: `todos.json` next to `session.json` (`todo::path`), its own `VERSION`, only `text` and `done` per item, written by a second `state::Saver<todo::Saved>` once it settles, and flushed on shutdown (a list has no logout burst to fear, and a just-typed item must not be lost to `kill-server`). Item ids are `Todos`' own counter, not the hierarchy's. A missing, corrupt or other-version file means an empty list. The list lives in `App`, so every client sees the same.
- **Order**: pending items, then done ones. A new item goes to the end of the pending ones; checking moves an item to the end of the list, unchecking to the end of the pending ones; a drag keeps an item among its kind (`Todos::move_before` clamps). Undo (`todo::Removed`) puts items back at their old index, clamped to that order.
- **Layout** (`ui::todo`): a header (` todo n `, ` clear done ` when something is done, ` × `), a gap, then a `ui::Rows` (variable heights, scroll by item, ` ↑ n more ` / ` ↓ n more `, sticky `+ new todo`), the same as the sidebar lists, so the wheel, `Rows::edge` auto-scroll and `reveal` come for free. Items soft-wrap at a fixed text width (`text_width`: the row minus the checkbox and the reserved ` × ` column), so hover never reflows. The checkbox is `○`, a green `✓` once done, in the middle of its three cells (the hit area `[ ]` had). `ui::todo::{rows, check, delete, clear_done, spot}` serve drawing and hit testing.
- **Editing**: `todo::editor::Editor` is the only text field with a cursor (chars and an index; wrap keeps every char so line/column map back to the text; a full last line gets an empty one for the cursor). The terminal cursor is placed with `set_cursor_position`. `+ new todo` turns into the field at the bottom; `Enter` adds and keeps it open for the next item, `Enter` on an empty field or `Esc` closes it. A click on an item's text edits it in place with the cursor at the click. Any press outside the field (in the panel or elsewhere) commits it (blur saves, so nothing typed is lost) and gives the keys back; `Esc` is the only way to drop a change. Saving an empty text keeps the old one. Pastes go in as one line.
- **Rows**: a press on an item grabs it (`Grab::Todo` in `App::row_drag`); release in place is the click (edit), leaving the row is a drag. The landing is computed from the layout without the line (`ui::todo::drop`), and drawing inserts a one-row line. `[ ]` and ` × ` act on press.
- **Undo instead of confirming**: ` × ` and ` clear done ` remove at once and set a toast with an ` undo ` button (`Toast::undo`, `UNDO_FOR` 6 s instead of 2 s). Only the last removal can be undone. The toast's button is checked before overlays, so it works with a menu open.

## Files panel (`files/`, `syntax.rs`, `ui/files.rs`, `app/files_panel.rs`)

- ` files ` (on the todo row, under ` issues `; ` ▤ ` in the compact bar) opens a panel in the changes panel's column with the active workspace's folder, so each worktree shows its own files; git or not. Read only: editing goes through ` open `.
- **Tree**: folders first, then files, by name ignoring case. Each open folder is listed on its own, on a thread, with `ignore` (one level; `.gitignore`, `.ignore`, the global and `.git/info/exclude` rules, also from parent folders; hidden files shown, `.git` never), at most `disk::MAX_ENTRIES` (10,000) entries. Listing per folder rather than walking the whole workspace keeps a huge folder (a home folder opened as a project) free until it is opened. The root and the open folders are listed again every `LIST_EVERY` (2 s) while the panel shows, one job at a time, so files an agent creates appear. Open folders, scroll, the open file and the last one opened live per workspace in `files::Panel`, in memory; the session keeps only whether the panel is open.
- **Viewer**: a click on a file reads it on a thread (`disk::read`): at most `disk::MAX_BYTES` (8 MiB), NUL in the first 8000 bytes means binary, invalid UTF-8 is replaced. Only regular files are read: the tree lists a link to a device or a FIFO as a file (a cloned repository can hold one to `/dev/zero`), and reading it would never end, growing the server's memory until it dies with every shell, or block its thread for good, so it shows as binary. The read itself stops after `MAX_BYTES + 1` bytes, so a file that grows after the size check cannot get past the cap. The first read answers plain text at once and the highlighted text after; then the file is checked every `CHECK_EVERY` (1 s) by size and modification time and read again when they change, answering only highlighted text, so colours never flash while an agent writes. Lines are cut at the panel's edge with `…`, tabs are four spaces. ` ‹ ` goes back to the tree with the file's row marked.
- **Highlighting** (`syntax.rs`): tree-sitter through arborium, about 60 grammars compiled in: the languages agents touch most (TypeScript, TSX, JavaScript, Python, Rust, Bash, Markdown, Java, C) and every grammar under 0.3 MB (Go, JSON, YAML, TOML, HTML, CSS, GraphQL, Lua, HCL, Vue, Svelte, Dockerfile, Make…). Grammars weigh 0.01-17 MB each (SQL 9 MB, C++ and Kotlin 5 MB); all 112 of arborium's made a 169 MB binary. A language without a grammar borrows a relative's by its comment syntax (`syntax::FAMILIES`): `//` JavaScript, `#` Python, `--` Lua, `;` Scheme, so comments and strings come out right and only some keywords stay plain; a hand-written fallback lexer was built and dropped in favour of this table. Every JavaScript file goes to the TSX grammar, whose query colours JSX tags and attributes (JavaScript's does not). The grammar comes from the file name, then the extension, then the shebang. Captures map to palette colours (`syntax::style`) so the terminal's theme applies: keyword magenta, function blue, type cyan, string green, number and constant yellow, property and tag red, comment the muted grey in italics. tree-sitter was picked for speed and precision: a 3,500-line TypeScript file takes 48 ms against 0.47 s for syntect with fancy-regex and the JavaScript syntax (2.4 s with a real TypeScript one), and it colours types and fields the same everywhere. Sources over `syntax::MAX_BYTES` (2 MiB) stay plain. syntect still colours the changes panel and Markdown.
- **Git marks** follow the changes panel: its model for the active workspace, with its mode and base. A changed file gets its status letter and colour in the tree; a folder holding changes gets a `●`, yellow, or green when everything under it is new. Deleted files are not on disk, so only the changes panel lists them. In the viewer every change block of the file's hunks marks the margin (`files::gutter`): `▎` green on added lines, `▎` blue on changed ones, `▁` red on the line after which lines went (`▔` on line 1 when they were above it); an untracked or added file is all green. A click on a mark shows the old lines above the block in red, tinted like the changes panel's removed lines, and another click hides them (`Viewer::unfolded`, keyed by the line the block sits before; `files::Lines` maps rows to lines and old lines).
- **Search**: one bar under the title (`files::Query`, per workspace), with no query the tree shows everything. It searches the text in the files; the ` ▤ ` at its right switches it to file names and back (`files::Mode`, lit while on). Tabs (tree, names, text) were built first and dropped: one bar with a toggle is less to read, and an empty bar giving the whole tree makes the tree the search's starting point. The bar takes the keys like the changes panel's filter (`Query::focused`; a click on it takes them, any press outside the panel gives them back): typing searches at once, `↑` `↓` pick a result, `Enter` opens it, ` × ` clears it and `Esc` clears it and gives the keys back. Until the answer to what was typed comes, the list keeps the previous results under `searching…` instead of going blank on every key (a text search can take tens of milliseconds on a large repository); an `Enter` pressed meanwhile waits for that answer and opens its first result (`Query::enter`), so typing and pressing `Enter` at once never opens a result of the previous query. Any other key, or a press outside the panel, drops the waiting `Enter`. Both modes search an index of the workspace's file paths (`search::index`: one parallel `ignore` walk with the tree's rules, at most `search::MAX_FILES` (200,000)), built on a thread once the bar is used and again every `INDEX_EVERY` (10 s) while it is; an answer remembers the index it came from, so a new index searches again. Measured on a 32,000-file repo: the walk takes 25 ms, a name search 1-20 ms, a text search 52 ms for everything and 1-3 ms for the first 50 matches.
- **Names** (`search::names`): nucleo's matcher (Helix's, fzf's scoring) with its path bonuses and smart case, best `MAX_NAMES` (200) first, shorter paths first on a tie; the matched letters are lit, and a path too long for the row loses its start so the file's name stays. One job at a time; a newer query waits for it and goes next.
- **Text** (`search::text`): ripgrep's `grep-searcher` and `grep-regex` over the indexed paths on up to 8 threads, the query a literal with smart case (regular expressions were left out: one more thing to learn for a quick look), binary files skipped (a NUL ends the file), at most `MAX_MATCHES` (1,000) matches: each match takes a slot before it is kept, so the threads together never keep more, and the search goes on until one more match is seen, so `Text::capped` (the note's `the first 1000 matches`) means a match was really left out, not just that the count reached the cap. A new query cancels the running search (`AtomicBool`) and starts at once. Results come grouped by file in path order; each line keeps its number, its text without the indent (at most 400 characters) and where it matched, and a long line is shifted so the first match shows. Opening a match opens the file at that line, selected so ` ask agent ` takes it at once, with every occurrence of the query lit in the viewer (`Viewer::find`); ` ‹ ` returns to the results.
- **Paths in panes** (`files/link.rs`): a path printed in the active pane, by an agent, a compiler, `git` or `rg`, opens in the files panel on a click, at its line or lines (`:12`, `:12:5`, `:12-30`, `#L12-L30`) and with them selected, so ` ask agent ` takes them at once; the panel opens if it was closed. The path is the run of path characters under the pointer (letters, digits, `_-./~@+,%:#`; brackets, quotes and backticks end it, a trailing `.,:;#` is dropped, a URL is none), resolved from the foreground program's folder, then the workspace's root, and taken only if it is a file inside the workspace. The one under the pointer is underlined in cyan (`ui::TabView::link`), checked on each draw: a snapshot row is already there and the check is a `canonicalize`. Claude Code's fullscreen renderer reads the mouse, so its clicks would never reach cornercase, but a plain click on a path does nothing there (it opens links with Ctrl+click, through a desktop file manager a server lacks). So a press on a path in a program that reads the mouse is held back (`App::link_press`): released on the same cell it opens the file and the program never sees it; moved to another cell, the held press is sent first and the drag goes on, so the program's own selection still works. The cost: a click right on a path in a Claude tool's header no longer expands it (a click elsewhere on the row does). A program that does not read the mouse keeps cornercase's selection; a release without moving opens the path instead of copying nothing. Modifier clicks were rejected: the protocol cannot carry Cmd, and Ctrl and Alt clicks are taken by the outer terminal on some systems.
- **Lines for the agent**: a press on a line selects it and dragging selects a range (`Panel::selecting`, followed by `continue_drag` even outside the panel; past the body's edges the nearest line counts). Any event but a left drag ends it, like the other drags: a release outside the window may never be reported, and the next click would be swallowed. ` ask agent ` pastes `path:a-b ` (`path ` with nothing selected) into the workspace's agent like the hunk action, ` copy ` copies the selected lines (else the path), ` open ` opens the editor at the first selected line in a new tab.

## Issues (`issues/`)

- `Browser` is pure state that returns `Action`s; `App` does the I/O on threads. Answers carry their query and issue key so stale ones are dropped, and lists, people, reads and token checks also the source's epoch, bumped by `App::forget_issues` when its connection goes or changes (disconnect, token removed or replaced, Jira settings changed), so an answer still in flight cannot refill the cache with the old connection or save a token checked against it. Lists are cached in memory and in `issues.json` (titles and metadata only, never tokens).
- GitHub goes through `gh` in the project folder. Shortcut (REST v3), Linear (GraphQL) and Jira Cloud (REST v3) go through `ureq`, capped at 100 issues. People filters go into each tracker's query.
- Tokens come from `SHORTCUT_API_TOKEN` / `LINEAR_API_KEY` / `JIRA_API_TOKEN` or are typed in the app, checked, and saved to `secrets.json` (0600). `issues::Secret` hides them in `Debug`; they are never logged.
- **Starting an issue**: in a repo root, a worktree on `issue-<n>-<slug>` / `sc-<n>-<slug>` / `ENG-123-<slug>` / `PROJ-123-<slug>`; elsewhere a new tab. Shortcut, Linear and Jira issues ask which open project or workspace to use. Then the agent starts with the prompt.
- **Jira** (Cloud only; Server/Data Center use other auth, API v2 and wiki markup): HTTP Basic with `email:token`. The site and email are not secret, so they live in `config.json` (`jira_site`, `jira_email`) and only the token in `secrets.json`; the browser's connect form asks site → email → token (one field, three steps; `SaveJira` saves the first two before the token is checked), settings has a row for each. `jira_jql` is ANDed with the generated JQL (its `ORDER BY` dropped). `/rest/api/3/search/jql` refuses unbounded queries, so a list with no condition at all sends `project IS NOT EMPTY`. Jira Cloud no longer takes names in JQL, so a picked person is `Who::User { id, name }` (the `accountId`); other trackers keep `Who::Person(handle)`. Descriptions and comments are ADF (JSON), turned into Markdown by `jira/adf.rs`; unknown nodes give their text. A `config.json` without `jira_site` was written before Jira, so `config::load` appends `jira` to its `issue_tabs` (once saved, the key exists and hiding the tab sticks). Changing the site, email or filter forgets the cached lists, people and account. Timestamps carry an offset (`+0200`), which `parse_time` applies.
- **Copy URL** uses OSC 52 through `App::host_writes`, because the server may run on another machine.
- Markdown renders with `pulldown-cmark`; code blocks are highlighted with syntect (pure Rust `regex-fancy`), mapping scopes to palette colours so the terminal theme applies. Highlighting is cached and warmed on the reading thread; syntect and its regex crates build with `opt-level = 3` in dev.

## Agents (`agents.rs`, `launch.rs`)

- Config: `agent` (`auto` = the one running in the tab, else ask), `agent_args`, `agent_modes`, `agent_commands`, `prompt` (placeholders like `{url}`, `{key}`, `{title}`), `submit`, `auto_accept_trust_prompt`, `trust_prompt_pattern`.
- `launch::Launch` types the command once the shell is quiet, waits until the agent is in the foreground, has drawn something and its screen is quiet, answers the trust prompt, then pastes the prompt. Readiness is a heuristic. "Drawn something" means the screen is no longer the shell's screen plus the command's echo (or part of it), compared without whitespace (`Launch::echo`): the quiet second used to count from the echo, so an agent that took over a second to draw (a loaded machine, a cold start) got the prompt before its trust question and read it as the answer (#34). A screen that is not the prompt plus the command (zsh's `RPROMPT` on the same line, a line scrolled off the top) counts as drawn, as before. `AGENT_LATEST` (30 s) still types the prompt into an agent that never draws.
- The trust prompt may highlight "No" by default (Claude Code does), so `answer_keys` moves the selection to the "yes" option before pressing Enter.

## Agent status (`activity.rs`)

- Every 500 ms (`WATCH_AGENTS_EVERY`, from `App::refresh`) each pane whose foreground process is Claude Code or Codex (`agents::detect` on its arguments) gets an `Activity`: working, waiting or idle. For Claude the source is the file Claude Code keeps for each running process, `<CLAUDE_CONFIG_DIR or ~/.claude>/sessions/<pid>.json`, the registry behind `claude agents --json` (its documented interface for status bars): `status` is `busy`, `waiting` (permission prompt, question, dialog), `idle` or `shell` (turn over but a Bash it started with `run_in_background` still runs). `shell` counts as working, like Claude's own agents view: Claude wakes up when the command ends, so it was not done (a dev server left running keeps the tab `◐`). A Monitor that runs a command is a background Bash too, so it gives `shell` (checked live on 2.1.289); one on a WebSocket runs no shell and may leave it `idle`. Its fields are not documented, so a missing file or an unknown value falls back to the title Claude sets (`◐`/`◑`, or braille in older versions, while busy; `✳` otherwise; it stays `✳` when Claude sees `TMUX`, `STY` or `ZELLIJ`), then to idle.
- No hooks and no screen scraping. Hooks mean editing the user's `~/.claude/settings.json` (or shipping a plugin), `Stop` never fires on an Esc interrupt and the permission notification comes ~6 s late; Claude's screen changes too often to match. The session file turns idle within a tick of an interrupt and waiting as soon as a prompt shows.
- `Status` adds done: a pane that went from working or waiting to idle while its tab was not the visible one (`App::visible_tab`: the active tab, unless the compact menu covers the pane) is done until that tab is shown. `watch_agents` clears it for the visible tab on every `refresh`, not only every 500 ms, so a click shows `○` at once. An unknown state counts as idle, so a fresh Claude never looks done.
- A tab shows its most urgent pane (`Tab::status`, the order of `Status`): waiting `!` > done `✓` > working `◐` > idle `○`, before the name. Workspace, project and collapsed group rows show only what needs you (`activity::attention`: waiting or done), right-aligned and before `↓n`; working stays on the tab so the sidebar is not always full of icons. The compact `≡` shows the same for every tab but the visible one (`View::attention`).
- **Codex** (`activity::codex`, checked live on 0.160.0): waiting while the title starts with `[ ! ] Action Required` or `[ . ] Action Required` (it blinks between the two during an approval); working while it starts with a braille spinner and a space (`⠴ <thread> | <project>`) or while the rollout the context line follows (`context/codex.rs`) is inside a turn (`task_started`, until `task_complete` or `turn_aborted`); otherwise idle (the title is then `<thread> | <project>`, or just the project). Approvals are never written to the rollout, so `!` needs the title; the title's items are configurable (`/title`, `tui.terminal_title`), and without its activity item the rollout still gives working and done. Both rather than one: the rollout alone has no waiting, the title alone breaks when its activity item is removed. Hooks were rejected as for Claude (they mean writing to `~/.codex`).
- Claude Code and Codex only; another agent plugs in by returning an `Activity` from its own signals (`app::agent_in`). An agent running through `ssh` or in a container is not seen (no local process, no local file).
- **Notifications**: `Pane::update` returns `Waiting` or `Done` once that status has held for `NOTIFY_AFTER` (1 s) and its tab was not shown meanwhile, once per change, so a prompt answered at once stays quiet. `App::notify` sets a toast with the status icon (`<agent> needs you in <project> › <workspace>`, the agent's kind such as `claude` or `codex`, control characters stripped) and queues a `notify::Notification`, which the server encodes per client. Panes of the same agent that settle on the same status in the same workspace on one tick give one notice: the text would be the same, and Ghostty drops a repeat within 5 s anyway. The agent is part of that key, so Claude and Codex in one workspace each get theirs. A pane's state remembers its agent (`activity::Pane::follow`) and starts over when another one takes the pane, so a Codex replacing a waiting Claude without a tick in between still notifies. They go through the outer terminal like OSC 52, so they work over SSH (no `notify-send`/`osascript` on the server's machine).
- The channel is the client's: inside tmux, screen or Zellij it is BEL (tmux drops notification OSCs, passthrough is off by default, BEL goes through); otherwise `notify::detect` trusts the XTVERSION reply when there is one (asked with the colours, so it survives SSH, where only `TERM` arrives; env vars may also be inherited from another terminal), else `TERM_PROGRAM`, `LC_TERMINAL` (iTerm2 sets it for SSH), `TERM`, `KITTY_WINDOW_ID`, `KONSOLE_VERSION`. OSC 777 for Ghostty, WezTerm, foot, Konsole, Warp and Rio; OSC 9 for iTerm2 (its only one); OSC 99 with `o=unfocused` for kitty, Contour and VS Code (VS Code knows only 99); BEL otherwise. Never several, since terminals that know several would show each.
- OSC 9 and 777 end with BEL, which every parser accepts; OSC 99 with ST, as kitty's spec says. `;` in the text becomes `,`: WezTerm, Rio and Konsole cut the body at it, WezTerm drops an OSC 9 holding one. Ghostty on macOS, foot, Konsole and Warp hide notifications while their window is focused; the others show them. `desktop_notifications` (`auto`, a channel, `off`) overrides the channel; the toast always shows. The visible tab never notifies, even while the outer window is unfocused (that would need focus reporting, `CSI ? 1004 h`).

## Context use (`context.rs`)

- A tab running Claude gets a second line, `Opus 5.5 · 23%`: the model and the share of the window used, as Claude's statusline computes it (`round(used / window * 100)`, at most 100). `sessions/<pid>.json` gives `sessionId` (re-read every tick: `/clear` changes it) and `cwd`; the transcript is `projects/<cwd with every non-alphanumeric UTF-16 unit as '-'; past 200 characters cut, plus '-' and a base36 hash>/<sessionId>.jsonl`. Its last `assistant` line (not `isSidechain`, model not `<synthetic>`) gives `message.model` and used = `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`; a later `system`/`compact_boundary` hides the line until the next reply.
- The transcript is read as it grows (the first time, its last MiB), lines scanned backwards to the first reply or boundary, so a quiet tick costs one `stat`. The window is worked out again only when the reply changes.
- No file holds the window, so it mirrors Claude Code 2.1.289's own rule: `DISABLE_COMPACT` with `CLAUDE_CODE_MAX_CONTEXT_TOKENS` gives that; otherwise 1M for models with a native 1M window (Opus 4.7 and later, anything from version 5) or a model setting ending in `[1m]` that names the transcript's model (`--model`, `ANTHROPIC_MODEL`, then `model` in local > project > user settings), unless `CLAUDE_CODE_DISABLE_1M_CONTEXT`; `CLAUDE_CODE_MAX_CONTEXT_TOKENS` for non-Claude models; else 200k, or 1M once past 200k. Variables are the process's (`process::env`) overlaid by each settings file's `env`, as Claude applies them. Not seen: an unsaved `/model` switch, accounts without 1M, the SDK's 1M beta header. Claude's statusline input has the exact numbers but needs a `statusLine` command in the user's settings (rejected like hooks).
- Wide mode gives the tab two rows (`ui::Details::lines`, height `pitch.max(lines)`), with `×` on the first only; compact mode puts the line on the band's third row. The model is cut first and dropped below 4 columns; the percentage turns orange at 75 % and red at 90 % (`usage::Severity::of`).
- What the line shows is three switches in `config.json` (Settings → TUI, `settings::Detail`): `model` and `context` (the percentage), on by default, and `memory` (off, see Memory below). `App::tab_details` applies them once into a `ui::Details { model, percent, memory }`, used by the view and by `App::tab_lines`, and `ui::Details::lines` gives the second row when any part is there, so drawing and hit testing agree; with all three off every tab takes one row. 0.6 had one switch, `context_line`, for model and percentage together: `config::load` reads it as `context`, and a file without `model` gets `context`'s value, so a line turned off then stays off. This happens on the JSON before deserializing rather than with a serde `alias`, which would reject a file holding both keys and fall back to all defaults. Plan limits stay in the ` usage ` modal; showing them under every tab was tried and dropped, since they belong to the account, would repeat the same number in every tab and push out the one thing each tab has of its own.
- Codex context (`context/codex.rs`) was verified against CLI 0.160.0; versioned synthetic fixtures and tagged source links are in `tests/fixtures/codex/README.md`. Associate by the JSONL held open under the agent's `CODEX_HOME/sessions` (or its `HOME/.codex/sessions`), never the newest rollout. Follow only Codex descendants of the foreground process, including npm's `node …/codex/bin/codex.js` wrapper; accept CLI/exec/VSCode source labels, reject subagent metadata and ambiguous root rollouts. A child whose environment cannot be read (a `fork` about to `exec`, a process that just exited) is skipped, never a reason to drop the line. Discovery (`codex::rollout_path`: `lsof` on macOS, every process in daemon mode) runs on a thread per pane, one job in flight, so it never blocks the server loop; the main thread only takes its answer and reads the rollout as it grows. Linux reads `/proc` (children across all threads); macOS uses `proc_listchildpids` / `proc_listallpids` (both return a count of pids, not bytes) and `/usr/sbin/lsof -n -P -a -p <pid> -Fn`. Missing inspection access omits the line.
- **Codex's app-server daemon**: 0.160.0 installs and starts `codex app-server --managed-daemon` (pid in `CODEX_HOME/app-server-daemon/daemon.pid`, parent 1); the TUI talks to it over a socket and the daemon writes every rollout (hence `source: "vscode"`), so no descendant holds one. Nothing links a TUI's pid to its thread (locks, snapshots and the socket carry no pid), so when no descendant holds a rollout the folder decides, only when unambiguous: the daemon's open rollouts whose `session_meta.cwd` is the agent's cwd, written since the pane first saw that pid (the daemon keeps a finished session open ~60 s, so a new Codex in the same folder would otherwise take the old one), exactly one of them, and exactly one native Codex TUI (`argv[0]` named `codex`, no `app-server`) in that folder with that home among all processes (`process::all`). Two Codex in one folder show nothing; after one exits the other comes back once the daemon closes its rollout. `codex -C <dir>` gives a cwd that does not match, so no line. The line appears with the first turn: the rollout is created lazily.
- Codex models come from `turn_context.model` and `thread_settings_applied.thread_settings.model` for the current thread. Usage is `last_token_usage.total_tokens / model_context_window`, rounded and capped at 100%; no lifetime totals, extra cached/reasoning tokens, inferred window or Codex baseline adjustment. `Context.percent` is optional: unavailable/malformed usage shows the model alone. Model switches and compaction clear the old percentage; switching rollouts, replacement, truncation, deletion or process exit resets the reader. Read only complete JSONL lines, starting with a tail of at most one MiB, then bounded incremental batches; validate session metadata at the head. An initial tail without a model omits the line until a model is reported.
- Codex fake-agent tests use `test_util::FakeCodex`, with a shell imitating the npm wrapper's parent/child topology, and no real model calls. `FakeCodex::serve` starts a fake daemon (a `codex app-server` script holding the rollout, not a descendant of the agent, pid in `daemon.pid`) and `FakeCodex::agent` a TUI that is `/bin/sleep` with `argv[0]` `…/codex` (`Sleeper::named`; a symlink would break multi-call coreutils). App tests cover two sessions sharing cwd and Codex home, session/model changes, compaction and cleanup; UI snapshots cover wide and compact lines, including model-only text.

## Memory (`memory.rs`)

- `memory` in `config.json` (Settings → TUI, off by default) ends a Claude Code or Codex tab's second line with the memory it uses: `Opus 5.5 · 23% · 1.2 GB`, or `1.2 GB` alone with the model and context off. Shell tabs never get the row: agents are what grows, and a row for a shell's few MB would double every tab's height. Off by default: most people never need it, and it costs a thread every 2 s per agent.
- What: the memory each process holds on its own (`process::footprint`), for each agent pane's shell and its descendants (`process::descendants`, breadth first over `process::children`, at most 256), summed per tab over its agent panes, so a split shell beside the agent does not count. macOS reads `ri_phys_footprint` (`proc_pid_rusage`, `RUSAGE_INFO_V0`), the figure in Activity Monitor's Memory column and `top`'s MEM; Linux reads `RssAnon` + `VmSwap` from `/proc/<pid>/status`, its anonymous memory including what was swapped out. Neither counts clean file-backed pages (the program, its libraries, mapped files), which every process maps and the system can drop at any time, so the sum over a tree is close to what the agent costs. The two are not identical (footprint also counts compressed and IOKit memory), but both mean memory only that process keeps.
- RSS (`statm`, `pti_resident_size`) was used before and overstated about twice: it counted Claude Code's 224 MB binary once per process (a fresh Claude showed ~440 MB against ~200 MB of footprint; a session with five `npx` MCP servers 1.26 GB against 0.79 GB), and it fell when macOS compressed an idle agent although the memory was still taken. PSS (`smaps_rollup`) was rejected because the kernel walks every mapping; `status` only reads counters. `process::tests::footprint` measures the test process itself: reading a mapped 64 MiB file must not count and writing 64 MiB must (the only check that catches a constant), so other tests could disturb it only by allocating or freeing half of that within the same milliseconds. The mapping needs `rustix`'s `mm` feature, enabled in `[dev-dependencies]` only.
- When: `App::watch_agents` (every refresh) calls `memory::Pane::update` for the agent panes whose tabs are on screen, while the switch is on: the active project's, or in the tree every unfolded workspace of an unfolded project in an open group (`App::drawn` tells which layout was last drawn). The sum runs on a thread every `memory::MEASURE_EVERY` (2 s), one job in flight per pane, like Codex discovery, so a deep tree never blocks the server loop. A pane without an agent drops its figure; panes not on screen keep their last one, so switching projects shows an old number for one refresh instead of making the row jump. The tree's gate is tested (two open projects are both measured); that hidden panes are skipped is not, since skipped work cannot be observed without timing.
- `ui::memory_size`: binary units, whole MB below 1024 MB, then GB with one decimal. In a narrow column the model is cut first, then dropped (`MIN_MODEL_WIDTH`); the percentage and the memory stay. At the default width (26) with both on, a two-digit percentage leaves no room for the model.

## Plan usage (`usage/`)

- ` usage ` sits under ` settings ` (wide: its own row; the workspaces column puts ` files ` on that row under ` issues ` and ` todo ` right-aligned under ` changes `, and keeps a blank row level with ` quit `, so its separator and ` issues ` stay level; compact: the footer is settings | usage | quit in thirds). It opens `Overlay::Usage`; ` done `, `Esc` or `Enter` close it.
- One section per agent (`usage::Agent`: Claude Code, Codex), in that order, each with its title and plan, its status on the right (`loading…` or `updated 2m ago`), its error under the title and its bars: thin `━` lines in the severity's colour on a track of the same line in the line colour. Only agents whose command (`agent_commands`, else the name) is an executable file, by path or on the server's `PATH` (`agents::installed`), get one; when neither is, both show, so each says why it could not run. A modal taller than the screen is cut at the bottom, the ` done ` row stays.
- **Claude** (`usage/claude.rs`): Claude Code's SDK control protocol: `claude -p --setting-sources '' --no-session-persistence --input-format stream-json --output-format stream-json --verbose`, then an `initialize` and a `get_usage` control request on stdin; the `control_response` for `get_usage` holds `subscription_type`, `rate_limits_available` and `rate_limits` (`limits[]` with `kind`, `percent`, `severity`, `resets_at`, `scope.model.display_name`; `spend` for extra usage). No prompt, no tokens, ~3 s. Claude handles OAuth (credentials file, Keychain, refresh), so cornercase never reads or refreshes a token; `GET /api/oauth/usage` was rejected for that (and refreshing the token ourselves can log Claude out). `--setting-sources ''` keeps the user's hooks from firing, `--no-session-persistence` keeps the probe out of the session list, `--bare` does not work (API key only).
- The protocol is not documented as a CLI interface, so parsing is lenient (unknown fields and kinds pass, a missing `limits[]` falls back to `five_hour` / `seven_day`, an unknown `severity` comes from the percentage), but `rate_limits_available` must be there, and `rate_limits` too when it is true, so a changed answer shows as unavailable instead of "no plan limits". Every failure shows `usage unavailable: <reason>`.
- **Codex** (`usage/codex.rs`, checked live on 0.160.0): `codex app-server` (stdio JSON-RPC, lines without the `jsonrpc` field): `initialize` with `clientInfo`, the `initialized` notification, then `account/rateLimits/read` (`excludeResetCreditDetails`, so it skips a second backend call). ~1 s, no Codex thread is created, no daemon starts (the stdio server is the probe's child and dies with it), no model call; Codex reads its own login from `CODEX_HOME`. The answer has `rateLimits` (`planType`, `primary` / `secondary` with `usedPercent`, `windowDurationMins`, `resetsAt` in Unix seconds, `credits`) and `rateLimitsByLimitId` (one per metered bucket, `codex` first, others suffixed with their `limitName` or id). Windows are named by their length, never by their slot: 300 minutes is `session (5h)`, 10080 is `week`. Unix-second resets need no date parsing. Not logged in answers the error `codex account authentication required to read rate limits`; it becomes `Report::notice` (a grey `not signed in · run codex login`, not a red error), so a Codex installed once and never used does not look broken. The rollouts' `token_count` events also carry `rate_limits`, but only as of the last turn (a window that reset since still shows its old percentage), so they were rejected.
- On demand only: opening the modal starts one probe per shown agent on a thread (never two for one agent at once) that answers with `AppEvent::Usage(agent, result)`; nothing polls. The last answer per agent stays in memory (not in the session file) and shows with its age while a new one loads. Probes run on the server's machine with `agent_commands`, are killed after `usage::TIMEOUT` (10 s; `App::usage_timeout` in tests); Claude's strips `activity::CLAUDE_SESSION_ENV` like `Term::spawn` and inherits `CLAUDE_CONFIG_DIR`, Codex's inherits `CODEX_HOME`.
- Reset times are relative (`resets in 2h 13m`, `3d 4h`): local time would need a time zone database, and the server may sit in another zone than the client anyway.

## Settings (`config.rs`, `settings.rs`)

- Tabs: Worktrees, Agents, Issues, TUI. Every change is saved to `config.json` at once. File: `$XDG_CONFIG_HOME/cornercase/config.json`, or next to the socket when `CORNERCASE_SOCKET` is set (so tests never touch the real one). Missing keys take defaults; a corrupt file means all defaults.

## Terminals (`term.rs`, `emulator.rs`)

- The emulator is libghostty-vt: it answers terminal queries (DSR, DA, DECRQM, kitty keyboard…) that programs like fzf and nvim wait for, and reflows on resize.
- Its types are `!Send`, so the emulator lives on the server's main thread; the reader thread only forwards bytes. Query replies go out from `on_pty_write`, ordered with the output that asked.
- Every write to a PTY (keys, pastes, launches, query replies) goes through one writer thread per pane (`term::spawn_writer`), in order: once a terminal's input buffer is full, a write to a program that doesn't read blocks, and on the server loop that froze every client (a long paste or `cornercase send` into a pane running `sleep`). Each pane queues at most 16 MiB (`term::MAX_QUEUED`): past that `Term::write` refuses and returns `false`, `send` and `keys` answer that the program is not reading, and typing or pasting in the UI shows a toast instead of losing keys silently. A write is taken whenever the queue is below the limit, so one long paste still goes through. Only Linux blocks a write to a full terminal; macOS drops what the terminal cannot take, so its queue never fills, and the App test that needs a full pane runs on Linux only. Pastes drop `\x1b[201~` from the text (`term::bracketed`), so a paste cannot end itself and type the rest.
- Cells keep palette indices so the outer theme applies. The client asks the outer terminal for its colours (OSC 10/11/4, then XTVERSION, then DA1 as an end marker) before starting the input thread, and every emulator uses them as defaults.
- cwd, name and arguments of the PTY's foreground process group leader come from `process.rs`: `/proc` on Linux, `proc_pidinfo` / `proc_name` / `sysctl(KERN_PROCARGS2)` on macOS (with `getpeereid`, the only `unsafe` and the only use of `libc`). In a pipeline the leader may be dead (`process::alive`), so the shell is used instead. Agent launch and detection depend on it.

## Keys and mouse (`keys.rs`, `mouse.rs`)

- Special keys, and all keys once the program enabled kitty, go through Ghostty's encoder; a legacy encoder handles the rest. The client asks the outer terminal for kitty's disambiguate level, so `Ctrl+Enter` / `Shift+Enter` keep their modifiers.
- Pane mouse events are forwarded only when the program enabled a mouse mode, in its encoding, relative to the pane, clamped to its edges.
- **Paths**: a simple click on a path in the active pane opens it in the files panel, even in a program that reads the mouse (see Files panel); a drag that starts on one still reaches the program.
- **Selection:** when the program did not ask for the mouse, press-drag-release selects with Ghostty's selection and copies via OSC 52, with a toast. Programs' own OSC 52 writes are forwarded to the outer terminal too (reads and primary-clipboard writes are dropped).

## Client / server (`client.rs`, `server.rs`, `protocol.rs`)

- The server owns the PTYs so shells outlive the UI. The client starts it if needed (`cornercase server`, logging to `server.log` next to the socket).
- One server per socket, guarded by `flock` on `server.lock`. The server calls `setsid` and ignores SIGHUP.
- The server renders, the client only writes frames. Input travels as serialized crossterm events. Several clients mirror each other; the shared size is the last used client's (attach, key, paste or mouse other than a bare move), like tmux's `window-size latest`, so a hung client (a phone whose SSH dropped) never shrinks a new one. Ping/pong would not catch that: the hung client is a healthy local process. Smaller clients get the frame cropped by `CropBackend`.
- **When the server draws** (`Server::due`): a frame is drawn when an event other than PTY output arrived (input, a client, a job's answer, a request, a timeout wake-up), when a pane on screen printed (`App::shows`) and `FRAME` (16 ms) has passed since the last frame, and at least every `TICK` (500 ms). Output in a hidden tab draws nothing: the sidebar's icons and `↓n` come from `refresh` and show within a tick. A visible pane printing without pause gets at most ~60 frames a second, counted from the last frame that showed output (`printed_at`), not from any frame: a key draws at once and its echo, a moment later, draws at once too instead of waiting a frame. Host writes (OSC 52, notifications) go out in their own `Step::Flush` every turn, framed or not. A draw that panics sets `changed`, so the screen is rebuilt on the next draw (forcing an immediate turn instead would spin while a draw keeps panicking). The session is observed at most every `SAVE_EVERY` (500 ms), since building `App::state()` looks up every pane's cwd and the `Saver` waits 2 s anyway. Before, every batch of events drew every client and built the state (#25).
- Every shell gets `CORNERCASE=1`; a client seeing it refuses to start (no nesting).
- Every shell loses Claude Code's per-session variables (`activity::CLAUDE_SESSION_ENV`): a server started from inside Claude Code would otherwise make every pane's `claude` a child of that session and expose its messaging token. An explicit list, not a `CLAUDE_CODE_*` prefix, so user settings like `CLAUDE_CODE_USE_BEDROCK` and `CLAUDE_CONFIG_DIR` pass through.
- `Hello` carries a protocol version and build id, and the notification channel of the client's terminal; a server from another build rejects the client. Keep `ClientMessage::KillServer` and `ServerMessage::Rejected` as the first variants (`protocol::tests::compatibility`).
- Socket: `$XDG_RUNTIME_DIR/cornercase/server.sock` or `$TMPDIR/cornercase-<uid>/server.sock`; `CORNERCASE_SOCKET` overrides it. Paths must fit in 108 bytes.
- **The socket's folder must be the user's alone** (`protocol::check_socket_dir`): a real folder, not a symbolic link, owned by the user and not writable by group or others; it is created `0700` when missing. The client checks it before connecting or starting a server, `kill-server` before connecting, the server before binding, also under `CORNERCASE_SOCKET` (a name without a folder is checked in the current folder). The refusal suggests removing the folder only on the default path, which is cornercase's own; under `CORNERCASE_SOCKET` it asks to change the variable, since that folder may hold other files. Without it, another local user could create `/tmp/cornercase-<uid>` first (no `XDG_RUNTIME_DIR` nor `TMPDIR`, as in some SSH sessions and containers) and pose as the server: read every key and send a `Restart`. Read access for others is allowed, since connecting needs write access to the socket file.
- Both ends check the peer's uid (`protocol::check_peer` on `process::peer_uid`: `SO_PEERCRED` on Linux, `getpeereid` on macOS): the client refuses a server of another user, and the server drops another user's client, which a loose umask could otherwise let in.

## Panics (`panics.rs`, `server.rs`)

- An uncaught panic on the server's main thread ends the process, and every shell with it (`Term::drop` kills them), so `Server::serve` runs each `Step` under `catch_unwind` (`Server::contain`): the refresh, the answers to requests, the draw, the save and each event. The step that panicked is dropped, the loop goes on, and `App::report_bug` shows `cornercase hit a bug, see server.log` (`Error::Bug`'s text) with a red `✗` for `BUG_FOR` (6 s). Each panic still has to be fixed where it happens; this only keeps the shells alive.
- `App` keeps whatever the step had changed. A panic in input or drawing also resets the interaction (`App::reset_interaction`: overlay, compact menu, hover, drags, selection, the TODO field, the filter's focus), since a dialog that panics while it draws would otherwise freeze the screen for good. A background one (refresh, save, job answers, PTY output) does not, because one that repeats every tick would close every dialog as soon as it opens. A panic while drawing also starts every client's screen over (`reset_screen`), since ratatui's buffer is left half drawn. Saving the session and exiting was rejected: it kills the shells just the same.
- Background jobs that something waits for run under `panics::job`, which turns a panic into `Err(Error::Bug)`. A busy dialog (creating or removing a worktree, installing an update, checking a token, starting an issue) cannot be closed, so a job that never answered would leave `kill-server` as the only way out; issue lists, people, details, usage and changes would stay loading. `↓n` counts a panic as 0 for every workspace it checked, like a git that fails, so an old count does not stay. The branch list and unchanged lines need nothing (nothing waits for them); memory and Codex discovery already see the dropped sender (`Disconnected`) and start over.
- The server replaces the panic hook (`panics::log_to_stderr`; stderr is `server.log`): thread, location, message and a backtrace (`Backtrace::force_capture`; release builds keep function names, not lines). The first panic at a location is written in full, later ones there without the backtrace and only at 2, 4, 8… times, so one that repeats every tick cannot fill the disk. It writes with `writeln!` and ignores errors: `eprintln!` panics when writing fails, and a panic inside the hook aborts.
- Panics must unwind: with `panic = "abort"` in any profile every contained panic would kill the server again, so `panics.rs` does not build without `cfg(panic = "unwind")`.
- Not contained: a panic inside a libghostty-vt callback (`on_pty_write`, `on_clipboard_write`) crosses an `extern "C"` frame and aborts, so keep those callbacks trivial; a crash in Ghostty's Zig code is no Rust panic. A draw that panics for a reason the reset does not touch leaves the screen blank, while the shells keep running.

## Commands for scripts and agents (`cli.rs`, `control.rs`, `app/control.rs`)

- `clap` (derive) parses every command, the old ones included; `cornercase` alone still opens the UI and `server` is hidden. Help texts go in `about`/`help`/`after_help` attributes, never `///`. Features: `std`, `derive`, `help`, `usage`, `error-context`, `suggestions` (no colours, no wrapping). Exit status: 2 for wrong usage (clap's), 1 for errors and timeouts (the message says which). A `requires` pointing into an exclusive `#[group]` is satisfied by any member of the group (it conflicts with the one given), so `--remove-worktree` uses `conflicts_with_all` instead.
- One request per connection: `ClientMessage::Request(json)`, answered by one `ServerMessage::Response(json)`, both after the existing variants (`protocol::tests::compatibility`). JSON, not postcard, so a command and a server from different releases still work together after `cornercase update`: unknown fields are ignored (`#[serde(default)]` everywhere) and an unknown command answers an error naming the server's version (`Command::NAMES`, checked before parsing). Requests skip `Hello`'s build check. A server from before them reads `InvalidData` and answers `Rejected`, which the command turns into "too old, restart it". The connection is an ordinary client without a size, so it gets no frames and never counts as a use (it never changes the shared size).
- Ids come from the app's counter, so they last one server run. Every shell gets `CORNERCASE_PANE=<id>` and `CORNERCASE_SERVER=<token>` (`Term::spawn`, `control::server_token`: the server's pid and start time); the command sends both, and a server takes the pane as the `caller` only when the token is its own: every server numbers its panes from 1, so a pane of another server (reached through `CORNERCASE_SOCKET`) would be taken for one of its own, and `send --enter` would type into it. Inside a pane the defaults are the caller's pane, tab, workspace and project; outside, the active ones (`Here`). `--tab` means the tab's agent pane, else its active one. `CORNERCASE_SOCKET` is never added to panes: it would also move `config.json` and `session.json`; shells inherit the server's environment, so `cornercase` in a pane finds its server anyway.
- **Nothing changes what the UI shows except `focus` and `--focus`**: the selection is shared by every client, so an agent opening a tab must not move everyone's view. The creation helpers (`push_tab`, `add_project`, `split_pane(.., focus)`) never touch the active indices; `add_tab`/`open_project` are the UI's focusing wrappers.
- A server that never had a client has no size and has not restored the session, so commands that create terminals refuse instead of making 1×1 ones (`area: None`).
- Typing goes through `Launch`: `Launch::command` (new-tab/split: the shell step only), `Launch::enter` (send --enter: the submit step only), `Launch::new` with `prompt: None` (start without a prompt). A request that types answers once it is typed, so a following `send` cannot land before the command. The submit step presses Enter after 300 ms of quiet or at most 3 s (`SUBMIT_LATEST`): a working agent's spinner never goes quiet. Launches carry a `key`; `drive_launches` reports `(key, started)` to the requests.
- Waits are pending requests in `App`, checked by `check_requests` in `refresh` after `watch_agents`, and answered through `take_answers`; `App::tick` asks the loop to wake for their deadlines, but only for instants still ahead (a past one would spin), and the server never waits longer than its 500 ms tick (a 10 s deadline once starved `watch_agents` of reads and the agent was never seen working). A client that leaves drops its waits; what it created goes on (a worktree being made still gets its tab and agent, a launch still types), since a timeout or a killed command does not prove the work was not done.
- `--until shell` needs the shell in the foreground, output since the last input written to the pane (`Term::input_at`, set by `Term::write`: the echo of a typed command at least) **and** a quiet pane: right after a command is typed the shell is still in the foreground until it forks, and its echo may not have been read yet. The quiet is 300 ms once the wait saw another program in the foreground after that input (`Watch::left`), else 1 s (`SHELL_UNSEEN`): a builtin, a command that ended before the wait, or a shell whose preexec hooks run before it forks. After a submission (the last Enter of a launch, `send --enter`, `keys` with `enter`; `Term::submitted`), a wait that ends on idle first needs the agent to react (`activity::Pane::reacted`: working, or a change between two known activities, since then; a pane that lost and found its agent did not react) within 10 s, else it fails: the status file can still say idle (or the old `waiting`) for a moment after the Enter. This covers a separate `wait` after `send --enter` too, not only `--wait`. An agent that finishes faster than one 500 ms read fails that check; the message says to `read` the pane.
- `send` refuses an agent that is `waiting` (an Enter would answer its question or permission prompt); `keys` is how to answer. Agent conditions fail on a pane without Claude Code or Codex (a status, or one of them detected in the foreground; another agent has no state to wait for), and a pane cannot wait on its own agent or shell (it would wait for itself).
- `read` and `--text` use libghostty's formatter: `screen_text` formats a selection of the active area, `last_lines` the whole screen with its scrollback (5,000 lines); both unwrap soft-wrapped lines and drop trailing empty lines. `--text` re-reads the screen after new output, at most every 100 ms (`TEXT_EVERY`). `regex` has `unicode-perl` so `\d`, `\s`, `\w` work.
- `status` text is a tree of `kind id  name  details  (marks)` lines for humans and agents; `--json` prints the server's JSON (serde_json sorts the keys).
- `skills/cornercase/SKILL.md` (Agent Skills format) is what teaches agents: installed with `npx skills add usecornercase/cornercase-terminal --skill cornercase -g`, printed by `cornercase skill` (`include_str!`), never installed by cornercase (like hooks). It stays short and points to `cornercase --help`.
- A panic must not leave a command waiting forever: its timeout lives in the server too. `Requests::open` lists the clients still owed an answer; after every contained panic `Server::contain` calls `App::answer_lost_requests`, which answers `Error::Bug`'s text to each of them that has no pending entry left (the request panicked while it was handled, or `check_requests` lost the entries it had taken out). Pending ones keep waiting, so whatever answers an entry takes it out of `pending` before doing the work that can panic (`worktree_ready`, `worktree_gone`); one left behind would wait for an answer that never comes.
- Whoever reaches the socket can type into every shell; the docs page says so for sandboxed agents.

## Updates (`update.rs`)

- Release builds only (`debug_assertions` off), so `cargo run` and tests never call GitHub. The server asks `releases/latest` when it starts and then every hour (`update::CHECK_EVERY`, `check_updates` in config). Unauthenticated, GitHub allows 60 requests an hour per IP, so hourly leaves room for many servers behind one address; a refused check is only logged and the next hour tries again. A newer one shows ` ↑ x.y.z ` at the end of the settings row and a toast; a later release found before updating replaces it and toasts again, the same one stays quiet. The dialog shows every `CHANGELOG.md` section after the running version up to the release, newest first, so a skipped release's notes are not lost: `CHANGELOG.md` is a release asset (`extra-artifacts` in `dist-workspace.toml`), downloaded only once a newer release is found (never by `cornercase update`). Releases without that asset, or a download that fails, fall back to the `## Release Notes` part of the release body. Scrolled by wheel or ↑/↓.
- Updating downloads `cornercase-<target>.tar.gz` and its `.sha256`, unpacks with `tar` next to the binary, runs `--version` on it (a binary that cannot run here never replaces a working one), then renames it over the old one. Homebrew installs (`/Cellar/`…), a folder we cannot write and unknown platforms get a command to copy instead.
- **`cornercase update [--check] [-y|--yes]`** (`client::update`) does the same from a shell: `update::install_latest` (check, then `update` or the command for `Install::Command`, which it prints and exits 1 without running), then, if a server is running, asks `RESTART` (`--yes` skips; no terminal and no `--yes` means no restart) and sends `ClientMessage::Restart`. It never attaches. Debug builds refuse unless `CORNERCASE_RELEASES_URL` is set (the e2e tests serve a fake release and update a copy of the binary). `--check` exits 0 either way, so 1 stays for errors. A same-version server from another build (after `brew upgrade`) is left to the client's `[y/N]`.
- **Before a restart, say what stops** (`restart.rs`): every restart (` restart now `, `cornercase update`, a client rejected by another build) first lists what runs in the terminals, from a `status` `Report`: agents counted by what they do, other programs by name and place, and panes at their shell prompt and the pane that asks left out (`PaneInfo::at_prompt`; a server from before it is told apart by the program's name). The app builds the Report itself, and the commands ask the running server, the old one: requests are JSON and skip the build check, and they wait at most 1 s (`client::running_now`), so a hung server or one older than requests falls back to `restart::generic` and never hangs the command. The text leads with what stops, not with "your session comes back", which read as if nothing was lost (#92). The installed step's dialog has ` restart now ` and ` later `, and `Enter` still restarts (the user's call); its message is one short line and the list goes in the scrollable notes area, since the message row is three lines high and the release notes were already shown before installing. `Term::shell_in_foreground` is false for a pane started with a command (`/bin/sh -c 'exec $EDITOR …'` from the changes panel, `Term::interactive`): its program runs in the shell's pid, so comparing pids alone called an editor idle, here and for `wait --until shell`. An agent always counts as running. The dialog's list is built when it opens and every `WATCH_AGENTS_EVERY` while it is open, not on every frame, since a `status` report looks up every pane's process. `cornercase update --yes` prints the list before restarting, and it and `kill-server` print what they stopped. Waiting until every agent is idle was left for another issue.
- `ClientMessage::Restart` (last variant) makes the server save and send `ServerMessage::Restart`, like ` restart now `, so attached clients come back, even when `update` ran inside one of its panes (it prints everything first). A server from before it cannot decode it and answers `Rejected` (`protocol::tests::compatibility`), so `client::restart_server` falls back to `KillServer`, whose clients just exit.
- The running server keeps the old code. ` restart now ` saves the session, sends `ServerMessage::Restart(path)`, and each client `exec`s its own executable (`current_exe`, read at start; the update replaced that file), never the path in the message, which starts a new server that restores the session. A new client rejected by an older server asks `[y/N]` on the plain terminal before running `kill-server`.

## Saved session (`state.rs`)

- Groups (name, icon, colour, collapsed), projects (with their group's index and whether they are folded), workspaces (with their changes base and fold), tabs, panes (cwd), split layouts, custom names, active children, column widths (and the stacked line), the changes panel (open, tab) and whether the TODO or files panel is open, in `$XDG_STATE_HOME/cornercase/session.json` (or next to the socket). The TODO list is not in it (see TODO panel). Processes are not restored; each pane gets a new shell in its folder.
- Saved only once the state is stable for 2 s, so the burst of `Exited` events at logout does not save an empty session.
- Only a fresh server restores, on its first client's `Hello`. Missing folders are skipped. `VERSION` is 5; older versions are migrated: versions 3 and 4 are read as is (a version 3 file has every project ungrouped), then, like versions 1 and 2, every project but the active one is folded.
- A tab whose shell cannot start (a folder it may not enter, no PTY left, a `$SHELL` that is gone) is left out whole, also a split one, and the restore goes on: its workspace and project stay, so `+ tab` can try again, a toast names the projects (`could not restore n tabs (…), see server.log`) and `server.log` has, per tab, the folder that failed and the cause: `Error::SpawnShell` puts both in its message, like `RunGit`, since `thiserror`'s `Display` leaves out a `#[source]`, and `cornercase new-tab` or `split` into such a folder answer the same text. `App::restore` returns whether every tab came back. When one did not, the server copies `session.json` to `session.json.bak` before its `Saver` can write the smaller session over it; an older `.bak` moves to `session.json.bak.1` first, so a second incomplete restore with other failing tabs cannot overwrite the only full copy. Keeping an existing `.bak` instead (a review suggestion) was rejected: after one incident every later one would keep a stale copy. If the copy fails the `Saver` still saves: it writes to the same folder and disk, so what breaks the copy breaks the save too, and holding it back would lose every later change of that server run. Stopping at the first failure was the bug (#24): it dropped every project after it and then saved that. The fallback shell opens in the current folder when no project came back, as when there is no session, or when the restore was incomplete and no shell came back at all (`App::has_terms`). A session saved without tabs (closing the last tab keeps the workspace) comes back as it was, without it.
